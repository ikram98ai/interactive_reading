part iii · dynamic sets and their operations

A set that changes, and seven things to ask it

A sports club keeps a card for every member: a membership number and a name. Members join and leave all year, so the pile of cards grows and shrinks. In the book's words that pile is a dynamic set. Each card is an object. The number on it is its key, and the name is satellite data: the set carries it around but never looks at it.

Programs use a set through a handful of operations. Queries only look: SEARCH for a key, MINIMUM, MAXIMUM, and SUCCESSOR or PREDECESSOR, the next larger or smaller key. Modifying operations change the set: INSERT and DELETE. Notice what the queries hand back: a pointer to the object, or NIL, and never just the key. And DELETE takes that pointer too, not a key.

How long each operation takes depends on how the set is stored, measured in terms of its size n. Here the cards sit in an array, first in any order and then kept sorted. Each layout makes some operations instant and others slow.

Try it: press SEARCH, then drag k to a missing key and press it again: you get NIL. Click a card to point x at it, then press SUCCESSOR and DELETE. Now switch to Sorted array and try the same buttons. Watch elements touched: SUCCESSOR drops to one, while INSERT and DELETE now have to shift cards.

What the book says

Sets manipulated by algorithms “can grow, shrink, or otherwise change over time. We call such sets dynamic.” A dynamic set that supports inserting, deleting and testing membership is a dictionary. Min-priority queues (Chapter 6) support inserting and extracting the smallest element. “The best way to implement a dynamic set depends upon the operations that you need to support.”

Each element is typically an object whose attributes can be examined and manipulated given a pointer to the object. Some dynamic sets assume that one attribute is an identifying key. Satellite data ride along in other attributes but are otherwise unused by the set implementation. Some dynamic sets presuppose that keys come from a totally ordered set, such as the real numbers or words in alphabetical order, which defines the minimum and the next larger element.

Operations are either queries, “which simply return information about the set,” or modifying operations, “which change the set.” SEARCH(S, k) returns a pointer x with x.key = k, or NIL. INSERT(S, x) adds the element pointed to by x. DELETE(S, x) removes the element x points to (“this operation takes a pointer to an element x, not a key value”). MINIMUM and MAXIMUM return pointers to the smallest and largest keys. SUCCESSOR and PREDECESSOR return the next larger or smaller element, or NIL at the maximum or minimum. MINIMUM followed by n − 1 calls to SUCCESSOR normally lists the set in sorted order.

Time is measured in terms of the size of the set. An array is the simple choice, but many operations then take Θ(n) in the worst case. Unsorted, INSERT and DELETE take Θ(1) and the rest Θ(n). Sorted, MINIMUM, MAXIMUM, SUCCESSOR and PREDECESSOR take Θ(1), SEARCH takes O(lg n) with binary search, and INSERT and DELETE take Θ(n) in the worst case. Chapters 11–13 improve on this: hash tables, binary search trees, and red-black trees with O(lg n) worst-case operations.

10.1.1 · arrays

One multiplication away from any element

Picture a street where every house has the same width. To find house number 40 you don't walk past the first 39: you start at the corner and pace off 39 house widths. Memory is that street, numbered byte by byte, and an array is a row of equally wide houses in one unbroken stretch: it is contiguous.

If the array starts at address a, each element takes b bytes and the first index is s, element i starts at a + b(i − s) and ends b − 1 bytes later. That is a subtraction, a multiplication and an addition, the same work for index 2 as for index 2 million, so reading any element takes constant time. The book counts from s = 1; Rust and C count from 0.

The formula needs one fixed width b. Names like “Li” and “Bartholomew” don't have one, so the array stores a pointer to each name instead. Every pointer is the same size, so the formula finds the pointer, and one more memory access follows it to the name.

Try it: click an element and watch the address get computed, then try other element sizes b and start indices s. Press Read all: every read takes the same three steps. Then switch to Pointers to names and click a name's pointer. In the Rust view the memory strip shows where each piece lives.

What the book says

“We assume that, as in most programming languages, an array is stored as a contiguous sequence of bytes in memory.” If the first element has index s, the array starts at memory address a, and each element occupies b bytes, then the ith element occupies bytes a + b(i − s) through a + b(i − s + 1) − 1.

Most arrays in the book start at 1 and a few at 0. With s = 1 the ith element occupies bytes a + b(i − 1) through a + bi − 1, and with s = 0 bytes a + bi through a + b(i + 1) − 1. If the computer can access all memory locations in the same amount of time, as in the RAM model of Section 2.2, “it takes constant time to access any array element, regardless of the index.”

Most programming languages require each element of an array to be the same size. If elements might occupy different numbers of bytes, the formulas fail, since b is not a constant. The elements are then usually objects of varying sizes, and each array element holds a pointer to its object. A pointer typically takes the same number of bytes whatever it references, so the formulas give the address of the pointer, and the pointer must then be followed to reach the object itself.

10.1.2 · matrices

Flattening a grid into a line

A seating chart has rows and columns, but memory is one long street. To store a matrix you flatten it. Row-major order lays the rows end to end; column-major order lays the columns end to end. Either way the position of M[i, j] is arithmetic: in row-major order skip i − 1 whole rows of n, so it sits at index n(i − 1) + j. In column-major order skip j − 1 columns of m: index i + m(j − 1).

You can also give every row its own array and keep a small array A of pointers to the rows, so M[i, j] is A[i][j]. That costs an extra pointer, but rows may then differ in length. A block representation cuts the matrix into tiles and stores each tile contiguously.

The order matters when a loop walks the whole matrix. In this machine memory arrives in lines of 4 neighbouring cells, roughly the way processors fetch cache lines. Walking in the storage order uses all 4 cells of each line. Walking across it can need a fresh line at every step.

Try it: click a cell of M to see where it lives and how its index is computed. Switch between Row-major, Column-major, Array of rows and Blocks. Then pick 4 × 4 and press Walk rows and Walk columns: compare the line loads.

What the book says

A matrix, or two-dimensional array, is typically represented by one or more one-dimensional arrays. The two most common ways to store an m × n matrix are row-major order, row by row, and column-major order, column by column. For the 2 × 3 matrix M with rows 1 2 3 and 4 5 6 (equation 10.1), row-major order stores the two rows and column-major order the three columns 1 4, 2 5 and 3 6 (Figure 10.1, parts a and b).

If the rows, the columns and the single array all start at index s, then M[i, j] is at index s + n(i − s) + (j − s) in row-major order and s + m(j − s) + (i − s) in column-major order. With s = 1 these are n(i − 1) + j and i + m(j − 1); with s = 0 they are ni + j and i + mj. For M with 1-origin indexing, M[2, 1] is at index 3(2 − 1) + 1 = 4 in row-major order and 2 + 2(1 − 1) = 2 in column-major order.

The multiple-array strategies of Figure 10.1(c) and (d) store each row in its own array of length n, with another array A of m elements pointing to the row arrays, so A[i][j] stores M[i, j]. The column-major version has n arrays of length m, and M[i, j] is in A[j][i]. “Single-array representations are typically more efficient on modern machines than multiple-array representations.” Multiple arrays can be more flexible, though, allowing “ragged arrays” whose rows (or columns) have different lengths.

In the block representation, the matrix is divided into blocks and each block is stored contiguously. A 4 × 4 matrix divided into 2 × 2 blocks might be stored in the order ⟨1, 2, 5, 6, 3, 4, 7, 8, 9, 10, 13, 14, 11, 12, 15, 16⟩.

10.1.3 · stacks

Last in, first out

In a cafeteria the clean plates sit on a spring-loaded stack. You can only take the plate on top, so the plate you get is always the one put down last. A stack is a dynamic set with exactly that rule for DELETE: the element removed is the most recently inserted one, a last-in, first-out or LIFO policy. INSERT is called PUSH and DELETE is called POP, and POP takes no argument because there is never a choice.

An array S[1 : n] and one number are enough. S.top is the index of the newest element, so the stack is S[1 : S.top], bottom first. PUSH moves top up one and writes. POP moves top down one and returns what was there. Each takes O(1) time, whatever the stack holds.

POP doesn't erase anything: the old value stays in the array, but it is past S.top, so it is no longer in the stack. Two things can go wrong. Popping an empty stack is underflow. Pushing onto a full one is overflow.

Try it: press Play to replay Figure 10.2: push 17 and 3, then pop. Then press Pop until the stack underflows, and Push until it overflows. Exercise 10.1-2 plays the book's exercise on an empty S[1 : 6].

What the book says

“Stacks and queues are dynamic sets in which the element removed from the set by the DELETE operation is prespecified.” In a stack, the element deleted is the one most recently inserted: the stack implements a last-in, first-out, or LIFO, policy. A queue removes the element that has been in the set for the longest time: first-in, first-out, or FIFO. Here both are stored in an array with attributes.

INSERT on a stack is often called PUSH, and DELETE, which does not take an element argument, is often called POP, after physical stacks such as the spring-loaded stacks of plates in cafeterias. Plates are popped in the reverse of the order they were pushed, since only the top plate is accessible.

A stack of at most n elements uses an array S[1 : n] with attributes S.top, indexing the most recently inserted element, and S.size = n. The stack consists of S[1 : S.top], with S[1] at the bottom and S[S.top] at the top. When S.top = 0 the stack is empty, which STACK-EMPTY tests. “Upon an attempt to pop an empty stack, the stack underflows, which is normally an error.” If S.top exceeds S.size, the stack overflows.

In Figure 10.2 the stack holds 15, 6, 2, 9 with S.top = 4; after PUSH(S, 17) and PUSH(S, 3), S.top = 6; POP(S) then returns 3, and S.top = 5. “Although element 3 still appears in the array, it is no longer in the stack.” Each of the three stack operations takes O(1) time.

10.1.3 · queues

A line that bends into a ring

At a bakery counter, newcomers join at the back and the counter serves whoever has waited longest. That is a queue, a first-in, first-out (FIFO) set. Its INSERT is called ENQUEUE and its DELETE is DEQUEUE, which, like POP, takes no argument: the queue decides who leaves.

In an array Q[1 : n] nobody shuffles forward. Q.head indexes the element at the front and Q.tail the next free slot. ENQUEUE writes at Q.tail and steps it right; DEQUEUE reads at Q.head and steps that right. An index that steps past n wraps around to 1, so the array behaves like a ring and both operations take O(1) time, however long the line.

The ring has a catch. Q.head = Q.tail means empty, so a ring of n slots holds at most n − 1 elements: filling the last free slot would make a full queue look empty. The book's procedures also leave out the checks for overflow and underflow (Exercise 10.1-5 asks for them). Here you can run them both ways.

Try it: press Play Fig. 10.3: three enqueues wrap the tail past 12 round to 3, then a dequeue serves 15. Now press Enqueue until the queue is full. With Book's code, one more enqueue makes head = tail, and the whole queue silently vanishes. Switch to With checks and the same enqueue is refused with one slot still free. Try Dequeue on an empty queue in both modes. In Rust the slots count 0–11.

What the book says

Stacks and queues are dynamic sets in which the element removed by the DELETE operation is prespecified. In a queue it is always the one that has been in the set for the longest time: “the queue implements a first-in, first-out, or FIFO, policy.” ENQUEUE is the queue's INSERT and DEQUEUE its DELETE; like POP, DEQUEUE takes no element argument. An enqueued element takes its place at the tail, like a newly arriving customer at the end of a line, and the element dequeued is always the one at the head, the customer who has waited the longest.

Figure 10.3 implements a queue of at most n − 1 elements with an array Q[1 : n] and the attribute Q.size = n. Q.head indexes the head; Q.tail indexes the next location at which a newly arriving element will be inserted. The elements reside in Q.head, Q.head + 1, …, Q.tail − 1, wrapping around so that location 1 immediately follows location n in a circular order. Q.head = Q.tail means the queue is empty; initially Q.head = Q.tail = 1. Dequeuing from an empty queue makes it underflow. When Q.head = Q.tail + 1, or both Q.head = 1 and Q.tail = Q.size, the queue is full, and an enqueue makes it overflow.

In Figure 10.3 the queue Q[1 : 12] first holds 5 elements, in Q[7 : 11]. After ENQUEUE(Q, 17), ENQUEUE(Q, 3) and ENQUEUE(Q, 5), Q.tail = 3; after DEQUEUE(Q) returns 15, formerly at the head, Q.head = 8 and the new head has key 6.

ENQUEUE and DEQUEUE as printed omit the error checking for underflow and overflow; Exercise 10.1-5 asks you to supply it. Each operation takes O(1) time. Exercise 10.1-6 extends the idea to a deque (double-ended queue), which allows insertion and deletion at both ends.

10.2 · linked lists

Pointers instead of positions

In a treasure hunt, each clue says where the next one is hidden; the clues can be anywhere. A linked list works the same way: the order of its objects is set not by where they sit in memory but by a pointer in each object. In a doubly linked list each object holds a key and two pointers, next to its successor and prev to its predecessor. L.head points at the first object; a NIL prev marks the head and a NIL next marks the tail.

Finding a key means following next pointers from L.head, one object at a time, so LIST-SEARCH takes Θ(n) in the worst case. But once you hold a pointer to an object, changing the list is a handful of pointer writes, however long it is: LIST-PREPEND puts x at the front, LIST-INSERT splices x in after y, and LIST-DELETE splices x out, each in O(1). An array is the mirror image: inserting at its front moves every element, but its kth element is one address computation away.

In Rust every object here has two pointers aimed at it, one from each neighbour, while a Box has exactly one owner. So the Rust version keeps all the nodes in one Vec, an arena, and a pointer becomes an index into it. The memory strip shows the arena: prev and next are plain slot numbers.

Try it: pick an operation and press Step; each pointer assignment lights its line and draws the new arrow in yellow. Search 4 and Search 7 are the book's two examples. Prepend, Insert and Delete replay Figure 10.4(b)–(d); in Delete, compare the pointers followed by the search with the two writes of the splice. Switch to Rust and read prev and next as slot numbers in the memory strip.

What the book says

“A linked list is a data structure in which the objects are arranged in a linear order.” Unlike an array, whose order is fixed by the indices, “the order in a linked list is determined by a pointer in each object.” Linked lists support all the dynamic-set operations, though not necessarily efficiently. Each element of a doubly linked list L is an object with a key and two pointer attributes, next and prev, and possibly satellite data. If x.prev = NIL, x is the first element, the head; if x.next = NIL, it is the last, the tail. L.head points to the first element, and L.head = NIL means the list is empty.

A list may be singly or doubly linked (singly: next but no prev), sorted or not (sorted: the minimum is the head and the maximum the tail), and circular or not (circular: the head's prev points to the tail and the tail's next to the head, a ring of elements). The rest of the section assumes unsorted, doubly linked lists.

LIST-SEARCH(L, k) finds the first element with key k by a simple linear search and returns a pointer to it, or NIL; on Figure 10.4(a), LIST-SEARCH(L, 4) returns a pointer to the third element and LIST-SEARCH(L, 7) returns NIL. It takes Θ(n) time in the worst case. LIST-PREPEND adds x, whose key is already set, to the front in O(1). LIST-INSERT “splices” a new element x into the list immediately after y in O(1); since it never references the list object L, L is not a parameter. LIST-DELETE must be given a pointer to x and runs in O(1), but to delete an element with a given key you first call LIST-SEARCH, which makes the worst case Θ(n).

Insertion and deletion are faster on doubly linked lists than on arrays: inserting or deleting the first element of an array while keeping the order moves every other element, Θ(n) in the worst case, against O(1) for the list. Finding the kth element, though, takes O(1) in an array and Θ(k) in a linked list. Exercise 10.2-1: in a singly linked list, DELETE takes Θ(n) in the worst case.

10.2 · sentinels

A dummy that guards both ends

Most of LIST-DELETE is edge cases: is x the head (no prev)? Is it the tail (no next)? A sentinel makes them disappear. It is a dummy object L.nil with all the attributes of a real one, and every reference to NIL becomes a reference to it. The list closes into a ring: L.nil.next is the head, L.nil.prev is the tail, and the tail's next and the head's prev both point back at L.nil. L.head is no longer needed.

Now every object has two real neighbours, so LIST-DELETE′ is two lines and LIST-INSERT′ four, with no if at all. Prepending is inserting after L.nil; appending is inserting after L.nil.prev. Searching gets a trick too. LIST-SEARCH asks two questions per object: off the end yet? is this the key? LIST-SEARCH′ first stores k in the sentinel, so a k is sure to turn up and the loop asks only the second question. If the k it finds is the sentinel's own, k was never in the list.

The order of growth stays Θ(n); only the constant shrinks. For a missing key that is n + 2 tests instead of 2n + 1. The price is one extra object per list, which adds up across many small lists, so the book uses sentinels only where they make the code much simpler. In Rust the sentinel is slot 0 of the arena: links are plain usize with no Option, and search needs &mut self because it writes the sentinel's key.

Try it: in Search, press Play. Both lanes walk the same list, and every dot under an object is one test: blue for “off the end?”, yellow for “is this the key?”. Pick k = 7, a key that isn't there: the lower lane stops at L.nil, holding the 7 it was given. In Insert′ · delete′, step through Figure 10.5(c)–(e) and watch deleting the tail need no special case. In Many lists, slide the keys per list down to 1.

What the book says

The code for LIST-DELETE is simpler if you ignore the boundary conditions at the head and tail: LIST-DELETE′ is two lines. “A sentinel is a dummy object that allows us to simplify boundary conditions.” In a linked list L, the sentinel is an object L.nil that represents NIL but has all the attributes of the other objects, and references to NIL are replaced by references to L.nil. That turns a regular doubly linked list into a circular, doubly linked list with a sentinel, with L.nil between the head and the tail: L.nil.next points to the head, L.nil.prev to the tail, and the tail's next and the head's prev point to L.nil. L.head is eliminated altogether. An empty list is just the sentinel, with L.nil.next and L.nil.prev both pointing to L.nil.

LIST-DELETE′, like LIST-INSERT, never references L, and you should never delete the sentinel unless you are deleting the entire list. LIST-INSERT′ inserts x after y. “No separate procedure for prepending is necessary”: to insert at the head let y be L.nil, and to insert at the tail let y be L.nil.prev. In Figure 10.5, (c) LIST-INSERT′(x, L.nil) with x.key = 25 makes 25 the head; (d) deleting the object with key 1 makes 4 the new tail; (e) LIST-INSERT′(x, y) inserts 36 after the object with key 9.

Searching a circular, doubly linked list with a sentinel has the same asymptotic running time, but the constant factor can drop. The test in line 2 of LIST-SEARCH makes two comparisons: one for whether the search has run off the end of the list, one for whether the key is in the current element. LIST-SEARCH′ first puts the key in the sentinel, so the search is guaranteed to find it, in an element or in the sentinel. Found only in the sentinel, the key is not really in the list, and the procedure returns NIL. (If your sentinel requires its key attribute to be NIL, assign L.nil.key = NIL before line 5.)

Sentinels often simplify code and might speed it up by a small constant factor, but they don't typically improve the asymptotic running time. “Use them judiciously.” When there are many small lists, the extra storage used by their sentinels can represent significant wasted memory, so the book uses sentinels only when they significantly simplify the code.

10.3 · binary trees

Three pointers per node

A list is a queue of people where each one knows who stands next. A tournament bracket, a family tree or the formula (a + b) × c branches instead: a thing can have two things under it. The book stores each node of a binary tree as an object with a key and three pointers: x.p to its parent, x.left and x.right to its children. A missing child is NIL. The root is the one node whose p is NIL, and the tree itself keeps only T.root, which is NIL when the tree is empty.

The machine holds the ten records of Exercise 10.3-1. Each record is an index, a key, and the indices of its left and right child. Drawn from those numbers alone, they make a tree of height 4 rooted at record 6. Every move (up, left or right) reads one attribute, so a hop costs Θ(1) however big the tree is. The parent pointer is what lets DEPTH climb back to the root without having remembered the way down.

In Rust, a tree that only points down can be built from Option<Box<Node>> children, with each parent owning its children. A parent pointer would be a second owner of the same node, and Box allows only one. So the Rust version is an arena: one Vec<Node> owns all the nodes, and p, left and right are Option<usize> indices into it, which is exactly the exercise's table. and_then follows a pointer when there is one and passes NIL along when there isn't.

Try it: click any node to make it x, then press x = x.left, x = x.right or x = x.p. Keep going down from a leaf and x falls off the tree into NIL. x = T.root starts again. Then switch to Climb with x.p, click the deepest node, 14, and press Play: DEPTH follows four parent pointers. In the Rust view the indices under the nodes count from 0.

What the book says

“Linked lists work well for representing linear relationships, but not all relationships are linear.” Section 10.3 represents rooted trees by linked data structures. Each node of a tree is an object with a key attribute, and the remaining attributes of interest are pointers to other nodes, which vary according to the type of tree.

Figure 10.6 uses the attributes p, left and right to store pointers to the parent, left child and right child of each node in a binary tree T. If x.p = NIL, then x is the root. If node x has no left child, then x.left = NIL, and similarly for the right child. The attribute T.root points to the root of the entire tree; if T.root = NIL, the tree is empty.

10.3 · rooted trees with unbounded branching

Any number of children, two links

A folder can hold any number of subfolders, and a manager can have any number of reports. If every node had fields child1, …, childk, you would have to choose k in advance. A node with k + 1 children wouldn't fit, and when most nodes have only one or two children, most of those fields would hold NIL. The left-child, right-sibling representation keeps just two links per node, plus the parent pointer p. x.left-child points to x's leftmost child, and x.right-sibling points to the next child of the same parent. To list x's children, step down once and then go sideways. The whole tree takes O(n) space, whatever its shape.

Turn the picture 45° and the two links become a left pointer and a right pointer, so any rooted tree can be stored as a binary tree. Other representations exist too. A heap is a complete binary tree stored in an array (Chapter 6), and the trees of Chapter 19 keep only parent pointers, because they are only ever climbed toward the root. With only p, though, finding x's children means checking every node.

The Rust version uses the same arena idea. PRINT-CHILDREN becomes an iterator: std::iter::successors starts at x's left child and keeps asking for the right sibling until it gets None. The return type impl Iterator<Item = usize> + '_ gives the caller something it can loop over, count() or collect(), and the '_ records that it borrows the tree.

Try it: press Play to list A's children. Switch the picture between Tree, LCRS links, Binary and Parent only: the nodes stay the same and only the pointers change. Click a node to make it x, then press Add child. Give A a fifth child and watch the fixed k = 4 layout overflow while LCRS adds one sibling link. In Parent only, Play has to check every node.

What the book says

The binary-tree scheme extends to any class of trees in which each node has at most some constant k children: replace left and right by child1, child2, …, childk. “This scheme no longer works when the number of children of a node is unbounded, however, since we do not know how many attributes to allocate in advance.” And if k is bounded by a large constant but most nodes have a small number of children, a lot of memory may be wasted.

The left-child, right-sibling representation (Figure 10.7) uses only O(n) space for any n-node rooted tree. As before, each node has a parent pointer p and T.root points to the root. Instead of a pointer to each child, each node x has two pointers: x.left-child to the leftmost child of x, and x.right-sibling to the sibling of x immediately to its right. If x has no children, x.left-child = NIL, and if x is the rightmost child of its parent, x.right-sibling = NIL.

Other tree representations: Chapter 6 represented a heap, which is based on a complete binary tree, by a single array plus an attribute giving the index of the last node. The trees of Chapter 19 are traversed only toward the root, so only the parent pointers are present. “Many other schemes are possible. Which scheme is best depends on the application.”

problem 10-1 · comparisons among lists

Twenty-eight costs, one walk at a time

Four kinds of list and seven operations make 28 worst-case costs to work out. You don't have to memorize the table, because every cell follows from two questions. Is the list sorted? If it is, the smallest key sits at the head and x's successor is x.next. If it isn't, MINIMUM, MAXIMUM, SUCCESSOR and PREDECESSOR have to look at every key. Is it doubly linked? If it is, x.prev reaches the node before x in one step, so DELETE, and PREDECESSOR on a sorted list, cost Θ(1). A singly linked list has to walk from the head to find that node.

SEARCH costs Θ(n) on all four, sorted or not, because a list has no middle to jump to: binary search needs an array. INSERT costs Θ(1) when order doesn't matter (just prepend) and Θ(n) when it does, because the right spot has to be found first. These lists keep only L.head, like the ones in Section 10.2, so MAXIMUM walks to the tail even when the list is sorted. Keep a tail pointer, or use a circular list with a sentinel, and that cost drops to Θ(1).

The Rust listing covers the two singly linked columns with Option<Box<Node<T>>> and generics. fn minimum<T: Ord> works for any key type that can be compared, which is what the trait bound T: Ord promises, and main reuses the same code for strings. A sorted insert walks a &mut Link<T> cursor to the gap. The borrow rules forbid holding a pointer x into a list while changing that list, so the Rust delete takes x's key instead.

Try it: click any cell of the table. The list of that kind runs the operation on its worst case, and the cell fills in with the cost. Play runs the selected cell, Step goes one line at a time, and Fill table runs every empty cell. Compare the DELETE row, singly against doubly, then look at the MAXIMUM row.

What the book says

Problem 10-1 asks, for each of four types of lists (unsorted singly linked, sorted singly linked, unsorted doubly linked and sorted doubly linked), for the asymptotic worst-case running time of each dynamic-set operation: SEARCH, INSERT, DELETE, SUCCESSOR, PREDECESSOR, MINIMUM and MAXIMUM.

The operations are defined in the Part III introduction. SEARCH(S, k) returns a pointer x to an element with x.key = k, or NIL. INSERT(S, x) adds the element pointed to by x. DELETE(S, x) “takes a pointer to an element x, not a key value.” MINIMUM and MAXIMUM return pointers to the elements with the smallest and largest keys. SUCCESSOR(S, x) returns a pointer to the next larger element, or NIL if x is the maximum, and PREDECESSOR(S, x) the next smaller one, or NIL if x is the minimum.

From Section 10.2: a singly linked list has a next pointer in each element but no prev pointer. In a sorted list the linear order of the list corresponds to the linear order of the keys. “The minimum element is then the head of the list, and the maximum element is the tail.” LIST-SEARCH takes Θ(n) time in the worst case, LIST-PREPEND and LIST-INSERT take O(1), and LIST-DELETE runs in O(1) given a pointer to the element. Exercise 10.2-1 asks you to explain why the worst-case time for DELETE on a singly linked list is Θ(n).

For comparison, the Part III introduction gives the array version. If the array is not sorted, INSERT and DELETE can take Θ(1) time and the remaining operations Θ(n). If it is sorted, MINIMUM, MAXIMUM, SUCCESSOR and PREDECESSOR take Θ(1), SEARCH takes O(lg n) with binary search, but INSERT and DELETE take Θ(n) in the worst case.

problem 10-3 · searching a sorted compact list

Roll a die, maybe skip ahead

A sorted list can't be binary-searched, because a pointer only leads to the next node. But suppose the list lives in two arrays: key[i] holds a node's key and next[i] the index of the node after it. If the list is compact, meaning its n nodes fill positions 1 to n exactly, then every index from 1 to n is some node of the list. So you can pick a random position j and land on a node without walking to it.

COMPACT-LIST-SEARCH is an ordinary sorted-list walk with a lucky dip at each step. It draws j = RANDOM(1, n), and if key[j] lies between the current key and the target k, it jumps there, skipping every node in between. Late in the search most jumps miss, but early on they cut the distance fast. The problem shows that the expected number of loop iterations is O(√n) instead of the plain walk's Θ(n). The keys must be distinct, otherwise a jump can't tell how far along the list it landed.

In Rust, next is a Vec<Option<usize>>, and the loop condition “i ≠ NIL and key[i] < k” is one call, i.filter(|&x| l.key[x] < k), which keeps a Some only while the test holds. The final check is a match with a guard. The random numbers come from a 32-bit xorshift: u32 shifts simply drop the bits that fall off, with no overflow panic. The machine uses the same generator, so its first run draws the same numbers as the Rust program.

Try it: in Plain walk, press Play. Lines 3–7 are switched off, and finding 90 takes 8 iterations. Switch to Random skips and press Play: the dashed arcs are probes, and the solid jumps skip ahead. Reroll draws new random numbers, and clicking a key searches for that key instead. Then open Average and press Run: 1000 searches for each list size, plain against skips, with √n drawn for comparison.

What the book says

A singly linked list can be represented with two arrays, key and next: given the index i of an element, its value is in key[i] and the index of its successor in next[i], with next[i] = NIL for the last element, plus the index head of the first element. An n-element list stored this way is compact if it is stored only in positions 1 through n. Assume all keys are distinct and the list is sorted, so key[i] < key[next[i]] whenever next[i] ≠ NIL. The problem shows that the randomized algorithm COMPACT-LIST-SEARCH searches for key k in O(√n) expected time.

Ignoring lines 3–7, the procedure is an ordinary search of a sorted linked list: it stops once i falls off the end or key[i] ≥ k, and if key[i] > k the key cannot be in the list. Lines 3–7 attempt to skip ahead to a random position j, which helps if key[j] is larger than key[i] and no larger than k: then j marks a position that i would reach during an ordinary search. “Because the list is compact, we know that any choice of j between 1 and n indexes some element in the list.”

The analysis goes through COMPACT-LIST-SEARCH′(key, next, head, n, k, t), which runs at most t random skips in a for loop and then walks with a while loop. With the same random numbers, both return the same result and the original does no more iterations. If Xt is the distance in the list from i to k after t skips, the second procedure's expected time is O(t + E[Xt]), E[Xt] = Σr=1n (1 − r/n)t ≤ n/(t + 1), so the time is O(t + n/t). Choosing t = √n gives O(√n).

Part (h) asks why the keys are assumed distinct, and to argue that random skips don't necessarily help asymptotically when the list contains repeated key values.

The chapter on one page

Chapter 10 in eight cards. Each one points at the scenes that act it out.

A set, and what you ask of it

A dynamic set grows and shrinks. Its elements are objects with a key and satellite data. Queries (SEARCH, MINIMUM, MAXIMUM, SUCCESSOR, PREDECESSOR) return a pointer or NIL. Modifying operations (INSERT, DELETE) change the set, and DELETE takes a pointer, not a key. → III Dynamic sets

Arrays: arithmetic, not search

Element i starts at a + b(i − s), so any element is one computation and one memory access away: constant time. Elements of different sizes break the formula, so the array stores same-size pointers to them instead. → 10.1.1 Arrays

Flattening a matrix

Row-major order puts M[i, j] at n(i − 1) + j, column-major at i + m(j − 1). An array of row pointers allows ragged rows, and blocks store tiles contiguously. One array is usually faster, especially when loops walk in storage order. → 10.1.2 Matrices

Who leaves first

Stacks and queues are dynamic sets whose DELETE is prespecified. A stack (PUSH, POP, S.top) is last-in, first-out. A queue (ENQUEUE, DEQUEUE, head and tail) is first-in, first-out and wraps around its array, using at most n − 1 slots. Every operation is O(1). → 10.1.3 Stacks, Queues

Order by pointers

In a linked list each object's next (and prev) pointer sets the order. Given a pointer, LIST-PREPEND, LIST-INSERT and LIST-DELETE splice in O(1). Finding an element by key is LIST-SEARCH, Θ(n), and so is reaching the kth element. → 10.2 Linked lists

A dummy at both ends

The sentinel L.nil turns the list into a circle and removes the NIL boundary cases: LIST-DELETE′ is two lines. Storing the key in it gives LIST-SEARCH′ one test per object instead of two. Same asymptotic time, a smaller constant, and one extra object per list. → 10.2 Sentinels

Trees from pointers

A binary tree node keeps p, left and right, and T.root points at the root. For any number of children, left-child, right-sibling uses just two child-side pointers per node: O(n) space for any n-node rooted tree. → 10.3 Binary trees, Any branching

Costs depend on the shape

Sorted or not, singly or doubly linked: each choice moves some operations between Θ(1) and Θ(n). A sorted compact list in two arrays can even skip ahead at random and search in O(√n) expected time. → 10-1 List costs, 10-3 Compact lists

Words to know

The book's words from this chapter, in plain language.

dynamic set
A set that algorithms change over time: elements are inserted and deleted.
dictionary
A dynamic set that supports only INSERT, DELETE and testing membership.
key
The attribute that identifies an element, such as a membership number.
satellite data
The rest of an element's data. The set carries it along but never looks at it.
query / modifying operation
A query only returns information about the set; a modifying operation, INSERT or DELETE, changes it.
successor / predecessor
The element with the next larger or next smaller key, or NIL at the maximum or minimum.
totally ordered
Any two keys can be compared, like numbers or words in alphabetical order, so minimum and successor make sense.
contiguous
Stored as one unbroken run of bytes, which is how an array lives in memory.
1-origin / 0-origin
Whether the first index is 1 (the book, mostly) or 0 (Rust, C). The start index is s in the address formula.
row-major / column-major
Storing a matrix in one array row after row, or column after column.
ragged array
A matrix stored as separate row arrays of different lengths, reached through an array of pointers.
block representation
Cutting a matrix into tiles and storing each tile contiguously.
stack (LIFO)
A dynamic set whose DELETE removes the most recently inserted element: last in, first out.
PUSH / POP
A stack's INSERT and DELETE. POP takes no element argument.
underflow / overflow
Removing from an empty stack or queue, or adding to a full one. Normally an error.
queue (FIFO)
A dynamic set whose DELETE removes the element that has waited longest: first in, first out.
head / tail
A queue's front, where DEQUEUE removes, and the next free slot, where ENQUEUE inserts. In a list, the first and last element.
wrap around
In a queue's array, position 1 follows position n, so the queue can circle the array.
linked list
Objects in a linear order set by a pointer in each object rather than by array indices.
singly / doubly / circular
A next pointer only, or next and prev; circular means the tail points back to the head.
sentinel
A dummy object, L.nil, that stands for NIL and removes boundary cases from the code.
T.root
The attribute pointing at a tree's root. NIL means the tree is empty.
left-child, right-sibling
A representation for any number of children: each node points to its leftmost child and to its next sibling.
compact list
A list stored in key and next arrays that uses exactly positions 1 through n.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

trait
An interface. trait DynamicSet lists the seven operations; an unsorted and a sorted array both implement it, and fn in_order<S: DynamicSet> works with either.
&self vs &mut self
A method that takes &self can only read, so the compiler enforces “a query doesn't change the set.” LIST-SEARCH′ needs &mut self because it writes the key into the sentinel.
Option<usize> as NIL
A handle to an element is Some(index); the book's NIL is None, and the compiler makes every caller handle it.
Result and ?
push returns Result<(), Overflow>; ? passes an Err straight back to the caller. A unit struct like Overflow is an error type with no fields.
size_of::<T>()
The bytes one T takes, known at compile time: the b of the address formula. A String is a 24-byte header whatever its length.
Index trait
Implementing Index<(usize, usize)> lets a matrix type be read as mx[(i, j)]; the [] operator is just a trait.
enum + match
enum Order { Row, Col, Block }, and a match that must cover every variant, picks the index formula.
take()
Moves a value out of an Option and leaves None behind: how a queue slot is emptied and a list head is replaced without copying.
VecDeque
The standard library's ring-buffer queue, the same idea as the book's wrap-around array, except that it grows when full.
Option<Box<Node>>
A singly linked list where each node owns the next one. When a Box goes out of scope, its node is freed.
arena + usize index
One Vec<Node> owns every node and links are indices into it. It handles doubly linked lists and parent pointers, which a single owner per node can't; Rc<RefCell<…>> with Weak is the costlier alternative.
impl Iterator
A function can return “some iterator” without naming its type, such as the children of a node walked along right-sibling links.
