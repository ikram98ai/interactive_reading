2.1 · insertion sort

Sorting a hand of cards

Pick up cards from a pile on the table one at a time. Your left hand holds the cards picked so far, always in order. Compare each new card with the cards in your hand from right to left, and slip it in just right of the first card that is no bigger. If every card in your hand is bigger, it goes on the far left. That is insertion sort.

In the procedure, the hand and the pile share one array. While the loop is at position i, A[1 : i − 1] is the sorted hand, A[i] is the card being placed, which the code calls the key, and A[i + 1 : n] is the pile. Bigger cards slide one place right to open a gap, so the only extra room it needs is one held card. When the loop ends, A[1 : n] holds the original values in sorted order.

The numbers being sorted are called keys for a reason: a key usually belongs to a record that carries other satellite data, like a spreadsheet row with a student's name, age and courses taken. Sort by age and each whole row moves with its age; sort by courses and the same rows land in a different order.

Try it: press Next card to place one card at a time and compare each picture with the book's Figure 2.2, panels (a) to (f). Step goes one line of pseudocode at a time. Then switch to Student records, pick a key and press Play: the names travel with their keys. In Rust, one generic function sorts numbers, letters and records alike.

What the book says

Insertion sort solves the sorting problem of Chapter 1: given a sequence of n numbers ⟨a1, a2, …, an⟩, output a permutation ⟨a′1, a′2, …, a′n⟩ with a′1 ≤ a′2 ≤ ⋯ ≤ a′n. “The numbers to be sorted are also known as the keys.” The input comes as an array with n elements.

Keys are often associated with other data, called satellite data; a key and its satellite data form a record. In a spreadsheet of student records, age, grade-point average or number of courses taken could each be the key, and when the spreadsheet sorts, it moves the whole record with the key. “When describing a sorting algorithm, we focus on the keys, but it is important to remember that there usually is associated satellite data.”

Insertion sort is “an efficient algorithm for sorting a small number of elements.” It works like sorting a hand of playing cards (Figure 2.1): start with an empty left hand and the cards in a pile, then insert one card at a time into the correct position, comparing from right to left. “At all times, the cards held in your left hand are sorted, and these cards were originally the top cards of the pile on the table.”

INSERTION-SORT(A, n) takes an array A and the number n of values to sort, which occupy A[1 : n]. When it finishes, A[1 : n] contains the original values in sorted order. Figure 2.2 traces it on ⟨5, 2, 4, 6, 1, 3⟩: panels (a)–(e) are the iterations of the for loop, and (f) is the sorted array.

Pseudocode uses whatever is clearest, sometimes an English phrase, and often ignores software-engineering concerns such as data abstraction, modularity and error handling, to convey the essence of the algorithm concisely.

2.1 · loop invariants and the correctness of insertion sort

A promise kept at every lap

How do you know insertion sort works on every input, not just the ones you tried? Find a sentence that is true each time the loop is about to start another lap. For insertion sort it is: A[1 : i − 1] holds the items that started in A[1 : i − 1], now in sorted order. Such a sentence is a loop invariant.

You prove three things about it. Initialization: it is true before the first lap. Maintenance: if it is true before a lap, it is still true before the next one. Termination: the loop stops, and the invariant at that moment says something useful. The first two are the base case and the inductive step of a proof by induction, except that this induction stops when the loop does. Here it stops at i = n + 1, and the invariant then covers all of A[1 : n]: sorted.

The invariant has two halves for a reason. A broken loop can keep the hand sorted while losing items, or keep every item while the hand falls out of order, or keep the invariant perfectly and stop one lap too soon.

Try it: press Next check to jump from one invariant check to the next and watch the three cards fill in. Then plant a bug: to n − 1 keeps the invariant but fails termination, while j > 1 breaks the sorted half, and no line 8 stays sorted while it loses items. In Rust, the check is a function over the slice &a[..i], and its output lists every check.

What the book says

At the beginning of each iteration of the for loop, which is indexed by i, the subarray (a contiguous portion of the array) A[1 : i − 1] is the currently sorted hand, and A[i + 1 : n] is the pile of cards still on the table. The loop invariant: at the start of each iteration of the for loop of lines 1–8, the subarray A[1 : i − 1] consists of the elements originally in A[1 : i − 1], but in sorted order.

“Loop invariants help us understand why an algorithm is correct.” You must show Initialization: it is true prior to the first iteration. Maintenance: if it is true before an iteration, it remains true before the next. Termination: the loop terminates, and when it does, the invariant, usually along with the reason the loop terminated, gives a useful property that helps show the algorithm is correct.

“A loop-invariant proof is a form of mathematical induction”: initialization is the base case and maintenance the inductive step. Termination is perhaps the most important property, since it is how the invariant shows correctness. Mathematical induction typically applies the inductive step infinitely, but in a loop invariant the induction stops when the loop terminates.

For insertion sort: before the first iteration, i = 2 and A[1 : 1] is the single original element, which is sorted. (For a for loop the check happens right after the counter is first assigned and before the first test i ≤ n.) Each iteration moves A[i − 1], A[i − 2], … one position right until it finds the proper position for A[i] and inserts it, so A[1 : i] then holds the original elements, sorted; incrementing i preserves the invariant. A formal treatment would need an invariant for the while loop too. The loop terminates once i equals n + 1; substituting n + 1 for i shows that A[1 : n] holds the original elements in sorted order. “Hence, the algorithm is correct.”

2.1 · pseudocode conventions

The house rules of pseudocode

The book's pseudocode is not a real language, but it has rules, and a few of them change what a program does. Indentation is the block structure: a loop's body is whatever is indented under it. // starts a comment, variables are local to their procedure, and A[i : j] means A[i] through A[j], both ends included. Most arrays start at index 1, and each procedure says which.

Three rules surprise programmers. After for i = 2 to n finishes, i is still there and equals n + 1, the first value past the bound. A variable that holds an object is really a pointer to it, and parameters are passed by value: a procedure gets its own copy of the pointer, so x.f = 3 reaches the caller but x = y does not. A pointer to no object at all is NIL.

And and and or short-circuit: in x and y, y is evaluated only if x is true, and in x or y only if x is false. That is what makes insertion sort's j > 0 and A[j] > key safe: once j reaches 0, A[0] is never read. Finally, return may hand back several values at once, and error stops a procedure that was called under the wrong conditions.

Try it: in Loop counter, set n and press Play: inside the loop the three languages agree, afterwards the book keeps n + 1, Python keeps n, and Rust has no i at all. In Pointers, step through CHANGE and see which assignments the caller notices. In and / or, press Play, then Swap operands and play again: the swapped test reads A[0].

What the book says

“We use the following conventions in our pseudocode.” Indentation indicates block structure: the body of INSERTION-SORT's for loop is lines 2–8, and the body of its while loop is lines 6–7 but not line 8. The looping constructs while, for and repeat-until and the if-else conditional work much as in C, C++, Java, Python and JavaScript. “In this book, the loop counter retains its value after the loop is exited, unlike some situations that arise in C++ and Java.” Right after a for loop, the counter holds the value that first exceeded the bound; the correctness argument for insertion sort used this (i = n + 1). to counts up, downto counts down, and by gives a step larger than 1. A footnote adds that a Python loop counter keeps the value it had in the final iteration instead.

// marks a comment. Variables are local to the procedure. Most arrays use 1-origin indexing, and the bounds are stated explicitly; in a 0-origin language you can subtract 1 from each index or allocate one extra position and ignore position 0. A[i : j] is the subarray A[i], A[i + 1], …, A[j], and unlike a Python slice it includes A[j].

Compound data lives in objects with attributes, written x.f. A variable representing an array or object is a pointer to it: after y = x, setting x.f = 3 makes y.f equal 3 as well. Attribute notation cascades, so x.f.g means (x.f).g. A pointer that refers to no object has the special value NIL. Parameters are passed by value: “the called procedure receives its own copy of the parameters, and if it assigns a value to a parameter, the change is not seen by the calling procedure.” For an object, the pointer is copied but the attributes are not, so x = y inside the callee is invisible to the caller while x.f = 3 is visible. Arrays are passed by pointer too.

A return statement transfers control back to the caller at once, and may return several values without packaging them in an object. The boolean operators and and or are short-circuiting, which is what lets you write x ≠ NIL and x.f = y without worrying about x.f when x is NIL. The keyword error means the procedure was called under the wrong conditions and terminates immediately; the caller handles the error.

2.2 · analyzing algorithms

A pretend computer you can count on

To predict how long an algorithm takes without timing one particular run, you need a model of the machine it runs on. Most of the book uses the random-access machine, or RAM: one processor that runs instructions one after another, never two at once, and charges a constant amount of time for each. The instructions are the ones real computers have: arithmetic (add, subtract, multiply, divide, remainder, floor, ceiling), data movement (load, store, copy) and control (branches, subroutine call and return). Every data access costs the same, even A[i]: its address is one subtraction, one multiplication and one addition away.

The model stays honest by copying real hardware. A RAM with a SORT instruction could sort in one step, so it gets no such instruction. Its data are integers, floating-point numbers and characters, and each word holds c lg n bits for a constant c ≥ 1: enough to hold the number n and so index every input item, but not so many that one word could carry a whole array through a single instruction.

Some instructions are a gray area. Is xk one step? In general, no: computing it takes time that grows with lg k, and the result has to fit in a word. But 2k is a single shift of the integer 1 by k bits, so the book counts it as constant time when the result fits in a word. Finally, the RAM has no memory hierarchy: no caches, no virtual memory. Real machines have both, yet RAM analyses usually predict real performance very well.

Try it: in x^k vs 2^k, pick a word size and k, then press Play: repeated squaring needs more steps as k grows, the shift always needs one, and both fail once 2k no longer fits in the word (try 16 bits and k = 16). In Array access, drag i and press Play: the address costs the same four steps for every i. In Rust, checked_mul and checked_shl return None instead of a wrong number.

What the book says

Analyzing an algorithm means predicting the resources it requires, most often computational time. That needs a model of the technology. “Most of this book assumes a generic one-processor, random-access machine (RAM) model of computation as the implementation technology, with the understanding that algorithms are implemented as computer programs.” “In the RAM model, instructions execute one after another, with no concurrent operations.” Each instruction takes the same amount of time as any other, and each data access the same as any other: in the RAM model “each instruction or data access takes a constant amount of time—even indexing into an array.” A footnote explains: if A[1 : n] starts at address 1000 with four bytes per element, A[i] is at 1000 + 4(i − 1), which takes at most one subtraction, one multiplication (often a shift) and one addition.

The model must not be abused: with an instruction that sorts, you could sort in one step. “Such a RAM would be unrealistic, since such instructions do not appear in real computers.” The RAM has the instructions commonly found in real computers: arithmetic, data movement and control. Its data types are integer, floating point and character. Integers are represented by c log2 n bits for some constant c ≥ 1: c ≥ 1 so a word can hold the value of n and index the input elements, and c constant so the word size does not grow arbitrarily, which would let one word hold huge amounts of data operated on in constant time.

Gray areas: computing xn for general integers typically takes time logarithmic in n, and you must worry whether the result fits into a word. Shifting the bits of an integer left by 1 multiplies it by 2, so shifting 1 left by n positions computes 2n in one constant-time instruction, as long as n is no more than the number of bits in a word. The book treats computing 2n and multiplying by 2n as constant-time when the result is small enough to fit in a computer word.

“The RAM model does not account for the memory hierarchy that is common in contemporary computers. It models neither caches nor virtual memory.” Models that include the memory hierarchy are much more complex. “Moreover, RAM-model analyses are usually excellent predictors of performance on actual machines.”

2.2 · analysis of insertion sort

Count the lines, not the seconds

How long does insertion sort take? A stopwatch only answers for one run: your computer, your compiler, this input, and whatever else happened to be running. Run it again and you may get a different number. To predict the time on an input nobody has tried yet, the book counts instead of timing.

Every line k of the pseudocode gets a cost ck: one run of that line always takes the same constant time, whatever the numbers are. Then count how many times each line runs. The running time T(n) is the sum of cost × times over all the lines.

Most counts are easy. Lines 2, 4 and 8 run once for each i, so n − 1 times. The for test in line 1 runs n times, one more than its body, because the last test is the one that fails. Line 5 is the hard one: for each i its while test runs ti times, a number that depends on the data, and the loop body (lines 6 and 7) runs one time fewer, ti − 1.

Try it: press Step and watch the row of the line that just ran grow by one block, then press Play. Line 5's bar is built from one group of blocks per i, so you can read each ti straight off it (they are also written above the array). Tap a number in the cost column to make that line more expensive and watch T(n) change. In Rust the counters are a [u64; 9] array, and the memory strip shows it sitting inside the stack frame.

What the book says

Timing one run tells you how long insertion sort takes on that computer, on that input, with that implementation, compiler or interpreter, linked libraries and background tasks, and a second run on the same input might even give a different result. “We need a way to predict, given a new input, how long insertion sort will take.” So instead of timing runs, the book analyzes the algorithm itself: how many times it executes each line of pseudocode, and how long each line takes.

The running time depends on the input: on its size, and on how nearly sorted it already is. The book describes running time as a function of the input size. For sorting, the natural measure is the number of items n; for multiplying two integers it is the total number of bits; for a graph it is the number of vertices and the number of edges.

“The running time of an algorithm on a particular input is the number of instructions and data accesses executed.” For now, each execution of the kth line takes ck time, where ck is a constant, in keeping with the RAM model. For each i = 2, 3, …, n, ti denotes the number of times the while loop test in line 5 is executed for that value of i. When a for or while loop exits in the usual way, because its test comes up FALSE, the test runs one time more than the loop body. “Because comments are not executable statements, assume that they take no time.”

A statement that takes ck steps and executes m times contributes ckm to the total. Summing the products of the cost and times columns gives T(n) = c1n + c2(n − 1) + c4(n − 1) + c5 Σi=2n ti + c6 Σi=2n (ti − 1) + c7 Σi=2n (ti − 1) + c8(n − 1).

2.2 · worst-case and average-case analysis

Same size, very different times

Two inputs of the same size can take very different times. Give insertion sort a list that is already sorted, and each key is at least as big as everything before it: line 5's test fails straight away, so every ti = 1. T(n) comes out as an + b, a linear function of n. That is the best case.

Give it the list in reverse order and every key has to travel all the way to the front: ti = i. The sums of 2 + 3 + … + n turn T(n) into an² + bn + c, a quadratic function. That is the worst case. A shuffled list lands in between, but not halfway between: on average a key is smaller than about half of the sorted part, so ti is about i/2 and the average case is still quadratic.

For the rest of the book the usual target is the worst-case running time, for three reasons. It is a guarantee: no input of size n takes longer, which matters when a deadline must be met. For some algorithms the worst case happens a lot, like searching a database for a record that isn't there. And the average case is often roughly as bad as the worst one anyway.

Try it: pick Sorted, Reversed or Random and press Run to sort one input of size n and drop its dot on the plot (Step goes one line at a time). All sizes does n = 2 to 16 in one go. Do all three kinds: the sorted dots sit on a line, the reversed dots on a parabola, and the random dots scatter around the dashed curve, never above the worst case. Press All sizes on Random a few times to see the spread. In Rust, see the three inputs built with iterators.

What the book says

Even for inputs of a given size, an algorithm's running time may depend on which input of that size is given. In insertion sort, “the best case occurs when the array is already sorted.” Each time line 5 runs, key is already greater than or equal to all values in A[1 : i − 1], so the while loop exits on its first test, ti = 1, and T(n) = (c1 + c2 + c4 + c5 + c8)n − (c2 + c4 + c5 + c8): an + b, a linear function of n.

“The worst case arises when the array is in reverse sorted order—that is, it starts out in decreasing order.” Every A[i] is compared with each element of the sorted subarray A[1 : i − 1], so ti = i. Using Σi=2n i = n(n + 1)/2 − 1 and Σi=2n (i − 1) = n(n − 1)/2, the running time becomes an² + bn + c with a = c5/2 + c6/2 + c7/2: a quadratic function of n.

The book usually concentrates on the worst-case running time, the longest running time for any input of size n, for three reasons. It is an upper bound on the running time for any input, a guarantee, which is especially important for real-time computing, where operations must finish by a deadline. “For some algorithms, the worst case occurs fairly often,” as when a database search looks for information that is not present. And the average case is often roughly as bad as the worst case: for n randomly chosen numbers, on average half the elements of A[1 : i − 1] are less than A[i], so ti is about i/2, and the average-case running time is a quadratic function of n, like the worst case.

The scope of average-case analysis is limited, because it may not be apparent what constitutes an “average” input; often the book assumes that all inputs of a given size are equally likely. When that assumption fails, a randomized algorithm, which makes random choices of its own, can allow a probabilistic analysis and yield an expected running time (Chapter 5).

2.2 · order of growth

Only the biggest term survives

Even an² + bn + c says more than we need. For large inputs only one thing about it matters: how fast it grows. Take a running time of n²/100 + 100n + 17 microseconds. At n = 100 the 100n term is nearly all of it, and n²/100 looks like a rounding error. But n² grows faster than n: at n = 10,000 the two terms are equal, and from there on the n² term takes over.

So the book keeps only the leading term (an²), drops the lower-order terms (bn + c), and then drops the leading term's coefficient too. What is left, n², is the order of growth, written with the Greek letter theta: insertion sort's worst case is Θ(n²) and its best case Θ(n). For now, read Θ as “roughly proportional when n is large”: in the table, f(n)/n² settles down to the constant a.

That is also how algorithms get ranked: a lower order of growth is more efficient. A Θ(n³) algorithm with a small constant can beat a Θ(n²) one on small inputs, but past some n0 the Θ(n²) algorithm wins, and keeps winning, whatever the constants are.

Try it: in Leading term, press Play to fill the table one n at a time: the lilac n² share takes over at n = 10,000 and f(n)/n² settles at 0.01. Drag b up: the takeover moves to bigger n, but it still comes. In Θ(n²) vs Θ(n³) both axes are logarithmic, so each running time is a straight line whose steepness is its order of growth, and a constant only lifts or lowers the line. Drag the constants and press Find n₀: the steeper line always crosses in the end.

What the book says

To ease the analysis of insertion sort the book used simplifying abstractions: first the constants ck instead of actual statement costs, then the forms an + b and an² + bn + c, which ignore even the abstract costs. One more abstraction: “it is the rate of growth, or order of growth, of the running time that really interests us.” Only the leading term of a formula counts, since the lower-order terms are relatively insignificant for large values of n, and the leading term's constant coefficient is ignored too, since constant factors matter less than the rate of growth for large inputs.

An algorithm that takes n²/100 + 100n + 17 microseconds on an input of size n is an example: although the coefficients 1/100 and 100 differ by four orders of magnitude, the n²/100 term dominates the 100n term once n exceeds 10,000. “Although 10,000 might seem large, it is smaller than the population of an average town. Many real-world problems have much larger input sizes.”

Insertion sort has a worst-case running time of Θ(n²), pronounced “theta of n-squared,” and a best-case running time of Θ(n). For now, think of Θ-notation as saying “roughly proportional when n is large”; Chapter 3 defines it precisely.

One algorithm is usually considered more efficient than another if its worst-case running time has a lower order of growth. Because of constant factors and lower-order terms, an algorithm with a higher order of growth might take less time on small inputs. But regardless of the constants hidden by the Θ-notation, there is always some n0 such that for all input sizes n ≥ n0, a Θ(n²) algorithm beats a Θ(n³) algorithm in the worst case.

2.3.1 · the divide-and-conquer method

Two sorted piles become one

Insertion sort is incremental: it grows a sorted prefix one item at a time. Many algorithms work another way. They are recursive: to solve a problem, they call themselves on smaller pieces of it. That is the divide-and-conquer method. If the problem is small enough (the base case), solve it directly. Otherwise divide it into smaller instances of the same problem, conquer each one by solving it recursively, and combine their solutions into the answer.

Merge sort's combine step is MERGE, and the book pictures it with cards. Two piles lie face up on the table, each sorted with its smallest card on top. Compare the two top cards, take the smaller one and lay it face down on the output pile, which uncovers a new top card. Repeat until one pile is empty, then flip the rest of the other pile onto the output. Each basic step looks at just two cards, so it takes constant time.

MERGE(A, p, q, r) does the same with arrays. It copies the sorted runs A[p : q] and A[q + 1 : r] into new arrays L and R, then refills A[p : r] from the smaller front of the two, with k moving one place each time. Every one of the n = r − p + 1 values is copied back exactly once, so merging takes Θ(n) time.

Try it: press Step to walk through MERGE(A, 9, 12, 16) from Figure 2.3, or Play. First L and R are filled, then each comparison of L[i] with R[j] sends one card up. Lilac cells of A already hold their final values; blue ones still hold old values that will be overwritten. Try L all smaller (only 4 basic steps, then the rest of R is copied as a block) and Interleaved (7, the most two piles of four can need). In Rust, watch the memory strip: L and R appear as new heap buffers and are freed when merge returns.

What the book says

Insertion sort uses the incremental method: it inserts each element A[i] into its proper place in A[1 : i], having already sorted A[1 : i − 1]. Many useful algorithms are recursive in structure instead: they call themselves one or more times to handle closely related subproblems. They typically follow the divide-and-conquer method. If the problem is small enough, the base case, you solve it directly without recursing; otherwise, in the recursive case, you perform three characteristic steps.

“Divide the problem into one or more subproblems that are smaller instances of the same problem.” “Conquer the subproblems by solving them recursively.” “Combine the subproblem solutions to form a solution to the original problem.” Merge sort divides A[p : r] at its midpoint q into A[p : q] and A[q + 1 : r], sorts those two recursively, and merges them back into A[p : r].

The key operation is the combine step, MERGE(A, p, q, r), where p ≤ q < r and the adjacent subarrays are already sorted. With two sorted piles of cards face up, smallest on top, the basic step chooses the smaller of the two top cards, removes it from its pile and places it face down onto the output pile; when one input pile is empty, the remaining pile is flipped over onto the output. With two piles of n/2 cards there are at least n/2 and at most n − 1 basic steps, each taking constant time, so merging takes Θ(n) time.

In detail, lines 1–7 copy A[p : q] and A[q + 1 : r] into temporary arrays L and R, a rare case that uses both 1-origin indexing (for A) and 0-origin indexing (for L and R). The while loop of lines 12–18 repeatedly copies the smallest value not yet copied back into A[p : r]; k is the position being filled, and i and j index the smallest remaining values in L and R. When it ends, one of the loops of lines 20–23 and 24–27 copies the rest of the other array, and the other iterates 0 times. Every value is copied back exactly once, n iterations in all, so MERGE runs in Θ(n) time.

2.3.1 · the divide-and-conquer method (merge sort)

Split down to single cards, merge back up

MERGE-SORT(A, p, r) sorts the subarray A[p : r]. If it holds zero or one element it is already sorted: that is the base case, where the recursion bottoms out. Otherwise it divides at the midpoint q = ⌊(p + r)/2⌋, conquers by calling itself on A[p : q] and then on A[q + 1 : r], and combines the two sorted halves with MERGE.

So the calls cut the array into halves, halves of halves, and so on down to single elements, and then the merges build sorted runs of 2, 4 and 8 on the way back up. The first call, MERGE-SORT(A, 1, n), sorts the whole array. When n is not a power of 2 the two halves differ by one: A[p : q] gets ⌈n/2⌉ elements and A[q + 1 : r] gets ⌊n/2⌋.

Every call that is waiting for its halves to come back is a frame on the call stack. There are 2n − 1 calls of MERGE-SORT in all, but at any moment only one chain of them is open, from the first call down to the current one, so the stack never holds more than one frame per level of halving.

What the book says

Merge sort sorts a subarray A[p : r], starting with the entire array A[1 : n] and recursing down to smaller and smaller subarrays. Divide: compute the midpoint q of A[p : r], taking the average of p and r, and split it into A[p : q] and A[q + 1 : r]. Conquer: sort each of the two subarrays recursively using merge sort. Combine: merge the two sorted subarrays back into A[p : r].

The recursion bottoms out, reaching the base case, when the subarray has just 1 element, that is, when p equals r; as the initialization argument for insertion sort's loop invariant noted, “a subarray comprising just a single element is always sorted.” Otherwise p < r, and the divide step computes an index q that partitions A[p : r] into A[p : q], with ⌈n/2⌉ elements, and A[q + 1 : r], with ⌊n/2⌋. The initial call MERGE-SORT(A, 1, n) sorts the entire array.

Figure 2.4 runs the procedure on ⟨12, 3, 7, 9, 14, 6, 11, 2⟩ and numbers the MERGE-SORT and MERGE calls in the order they are made after the initial call. The array is divided down to 1-element subarrays; pairs of them are merged into sorted subarrays of length 2, those into length 4, and those into the final sorted subarray of length 8. If n is not an exact power of 2, some divide steps create subarrays whose lengths differ by 1: dividing a subarray of length 7, for example, gives lengths 4 and 3. Regardless of the two lengths, merging a total of n items takes Θ(n) time.

2.3.2 · analyzing divide-and-conquer algorithms

A running time that calls itself

A recursive algorithm solves a big problem by solving smaller copies of it. Its running time can be written the same way: the time for size n is the time for the smaller pieces, plus the time to cut the problem up and glue the answers together. An equation like that is a recurrence.

Divide-and-conquer hands you the recurrence. A small enough problem (n < n0) takes constant time, Θ(1). Otherwise, dividing costs D(n), the a subproblems of size n/b cost a·T(n/b), and combining costs C(n). Merge sort has a = b = 2: finding the middle is Θ(1) and MERGE is Θ(n), so T(n) = 2T(n/2) + Θ(n), which Chapter 4 solves to Θ(n lg n).

The halves are not really n/2. MERGE-SORT splits 13 items into 7 and 6: a ceiling ⌈n/2⌉ and a floor ⌊n/2⌋. The machine evaluates the exact recurrence, floors and ceilings included. At every depth only two sizes turn up, and they differ by at most 1. That is why the book calls both of them n/2: the order of growth doesn't change.

Try it: press Step and follow T(13) down to T(1) and back up. Each size is worked out once and stored in the memo, so the second request for T(3) is a mint cache hit. Slide n and compare the calls with the 2n − 1 calls the recursion would make without a memo. In Settle, drag c₁ up: the base cases only add c1n, and T(n)/(n lg n) still sinks toward c2.

What the book says

When an algorithm contains a recursive call, its running time can often be described by “a recurrence equation or recurrence, which describes the overall running time on a problem of size n in terms of the running time of the same algorithm on smaller inputs.” Mathematical tools then solve the recurrence and bound the algorithm's performance.

Let T(n) be the worst-case running time on a problem of size n. If n < n0 for some constant n0 > 0, the straightforward solution takes constant time, Θ(1). If the division yields a subproblems, each 1/b the size of the original, and it takes D(n) time to divide and C(n) time to combine, then T(n) = Θ(1) if n < n0, and D(n) + aT(n/b) + C(n) otherwise. For merge sort both a and b are 2; other divide-and-conquer algorithms have a ≠ b. Chapter 4 shows how to solve common recurrences of this form.

MERGE-SORT divides a problem of size n into subproblems of sizes ⌈n/2⌉ and ⌊n/2⌋. Their difference is at most 1, so the book will “squint a little” and call both of them size n/2; ignoring floors and ceilings does not generally affect the order of growth of a solution to a divide-and-conquer recurrence. It also omits the base cases, which are pretty much always T(n) = Θ(1) if n < n0. “That's because the running time of an algorithm on an input of constant size is constant.”

Analysis of merge sort. Divide: computing the middle takes constant time, so D(n) = Θ(1). Conquer: two subproblems of size n/2 contribute 2T(n/2). Combine: MERGE on an n-element subarray takes Θ(n), so C(n) = Θ(n). Hence T(n) = 2T(n/2) + Θ(n) (2.3), and Chapter 4's master theorem gives Θ(n lg n). Compared with insertion sort's Θ(n²), merge sort “trades away a factor of n for a factor of lg n. Because the logarithm function grows more slowly than any linear function, that's a good trade.”

2.3.2 · analysis of merge sort

Every level costs the same

You don't need Chapter 4's master theorem to see why merge sort is Θ(n lg n). Let n be an exact power of 2 and write the recurrence with two constants: a problem of size 1 costs c1, and a bigger one costs 2T(n/2) + c2n, where c2 is the time per element to divide and combine.

Now draw it as a recursion tree. The root costs c2n and has two subtrees, each a T(n/2). Expand those: each costs c2n/2 and has two T(n/4) below it. Keep going until the problems have size 1. Then add up each level: it has twice as many nodes as the level above, each costing half as much, so every level above the leaves costs exactly c2n, and the n leaves cost c1n.

How many levels? A tree with one leaf has one level, and doubling the leaves adds one more, so n leaves make lg n + 1 levels. The total is c2n lg n + c1n = Θ(n lg n).

Try it: press Step to grow the tree one level at a time, the way Figure 2.5 goes from (a) to (d). Keep pressing to add up each level in the right-hand column: 1 × 48, 2 × 24, 4 × 12, … all 48. Then slide n to 32 and press Play: one more level, and still 96 per level.

What the book says

The master theorem isn't needed to understand intuitively why the solution to recurrence (2.3) is Θ(n lg n). Assume that n is an exact power of 2 and that the implicit base case is n = 1. Then the recurrence is essentially T(n) = c1 if n = 1 and 2T(n/2) + c2n if n > 1 (2.4), where c1 > 0 is the time to solve a problem of size 1 and c2 > 0 is the time per array element of the divide and combine steps. It is unlikely that these are exactly the true times; Chapter 4 bounds recurrences more carefully.

Figure 2.5 expands T(n) into an equivalent tree. The c2n term is the cost of dividing and combining at the top level, and the two subtrees of the root are the two smaller recurrences T(n/2). Each node is expanded in turn until the problem sizes get down to 1, each with a cost of c1.

Then the costs are added across each level. Each level has twice as many nodes as the level above, but each node contributes only half the cost: “doubling and halving cancel each other out, so that the cost across each level is the same”, c2n. The level i levels below the top has 2i nodes, each costing c2(n/2i). The bottom level has n nodes costing c1 each, for c1n.

The tree has lg n + 1 levels, by an informal inductive argument: for n = 1 there is 1 level and lg 1 = 0, and a tree with 2i+1 leaves has one more level than a tree with 2i leaves. Adding up the levels gives a total of c2n lg n + c1n = Θ(n lg n).

problem 2-1 · insertion sort on small arrays in merge sort

Stop splitting at k

Merge sort's Θ(n lg n) beats insertion sort's Θ(n²), but on a handful of items insertion sort's smaller constant factors win. So stop the recursion early: cut the array into n/k sublists of length k, sort each one with insertion sort, then merge them with the usual MERGE. This is coarsening the leaves of the recursion.

Each sublist costs Θ(k²) in the worst case, and there are n/k of them: Θ(nk). Merging then doubles the run length level by level, from k up to n: lg(n/k) levels of Θ(n) each. Together that is Θ(nk + n lg(n/k)).

The two terms pull against each other: a bigger k means fewer merge levels but slower blocks. Keep k = O(lg n) and the nk term is O(n lg n), so the total stays Θ(n lg n); a larger k lets nk take over. Which k is best in practice depends on how much a merge step costs next to an insertion step on your machine, so you measure.

Try it: press Play and watch insertion sort fix each block of bars, then MERGE combine the runs level by level while the counters climb. Drag k: the curves below count the real steps for every k from 1 to 64, and the mint dot is the cheapest. Raise the merge cost, what one merge step costs in insertion steps: the best k moves right. On Random input insertion sort has less to do, so bigger blocks pay off.

What the book says

Merge sort runs in Θ(n lg n) worst-case time and insertion sort in Θ(n²), but the constant factors in insertion sort can make it faster in practice for small problem sizes on many machines. Thus it makes sense to “coarsen the leaves of the recursion by using insertion sort within merge sort when subproblems become sufficiently small.”

The modification sorts n/k sublists of length k using insertion sort and then merges them “using the standard merging mechanism, where k is a value to be determined.”

problem 2-2 · correctness of bubblesort

The smallest bubbles to the front

Bubblesort walks j from the right end of the array down to i + 1. Whenever A[j] is smaller than its left neighbour, it exchanges the two. So the smallest item of A[i : n] gets carried left one swap at a time until it lands in position i. Then i moves one place right and the walk starts again.

Its proof needs one loop invariant per loop. The inner loop: at the start of each iteration, A[j] is the smallest item in A[j : n]. When that loop ends, j = i, so A[i] is the smallest of A[i : n]. The outer loop: at the start of each iteration, A[1 : i − 1] holds the i − 1 smallest items in sorted order. When i reaches n, only the largest item is left, already at the end. Being in order isn't enough on its own: you also need the output to be a permutation of the input, which holds because the only change bubblesort ever makes is an exchange.

Bubblesort makes all n(n − 1)/2 comparisons on every input, even one that is already sorted, so it is Θ(n²) in the best case as well as the worst. On sorted input insertion sort stops comparing after one test per item: Θ(n).

Try it: press Step and watch the two checks under the array: the inner invariant before every comparison, the outer one at the start of every pass. Then Play. Pick Sorted: no exchanges at all, but still 15 comparisons, against 5 for insertion sort. In the Rust view, see why the code calls a.swap.

“Bubblesort is a popular, but inefficient, sorting algorithm. It works by repeatedly swapping adjacent elements that are out of order.” The procedure BUBBLESORT sorts the array A[1 : n].

problem 2-3 · correctness of horner's rule

One multiplication per coefficient

To evaluate a polynomial P(x) = a0 + a1x + a2x² + ⋯ + anxn, the obvious way computes every term from scratch: x² takes one multiplication, x³ two more, and so on. That is 1 + 2 + ⋯ + n = n(n + 1)/2 multiplications, Θ(n²).

Horner's rule pulls x out again and again: P(x) = a0 + x(a1 + x(a2 + ⋯ + x(an−1 + xan)⋯)). Evaluate it from the inside out: start with p = 0, then for i from n down to 0 set p = A[i] + x · p. One multiplication and one addition per coefficient: Θ(n).

Why does that give P(x)? The loop invariant: at the start of the iteration for i, p is the polynomial built from the coefficients above i, A[i + 1] + A[i + 2]x + ⋯ + A[n]xn−i−1. Before the first iteration that sum has no terms, so it is 0. The loop ends at i = −1, where the sum is exactly P(x).

Try it: press Step and watch p grow from the top coefficient down, while the row under the array checks the loop invariant at the start of every iteration. Switch to Naive and press Play: the same 109, but every term rebuilds its power of x. Drag the degree n to 8 and compare the bars: 9 multiplications against 36.

What the book says

Horner's rule says to evaluate it according to the parenthesization P(x) = a0 + x(a1 + x(a2 + ⋯ + x(an−1 + xan)⋯)). problem 2-4 · inversions

Counting the pairs that are out of order

In an array of distinct numbers, two positions i < j with A[i] > A[j] form an inversion: the bigger item comes first. ⟨2, 3, 8, 6, 1⟩ has five of them, drawn here as arcs. A sorted array has none. A reversed one has the most possible: every one of its n(n − 1)/2 pairs.

Inversions are exactly the work insertion sort does. Each shift moves one bigger item a place right, past the key: that fixes one inversion and creates none. So insertion sort shifts once per inversion, and its running time is Θ(n + I) on an input with I inversions: linear when the input is nearly sorted, quadratic when it is reversed.

Testing every pair takes Θ(n²). Merge sort can count them in Θ(n lg n): when MERGE takes R[j] while L[i : nL − 1] is still waiting, R[j] is smaller than every one of them, so it forms nL − i inversions in one go. One addition counts a whole batch.

Try it: in Brute force, press Play: every pair is tested and the inversions appear as coral arcs. In Insertion sort, watch each shift erase exactly one arc. In Merge count, the arcs that cross the middle of a merge turn mint in batches. Then pick Reversed: 21 inversions for n = 7, the most there can be.

Chapter 2 sets up how the whole book works: write an algorithm down, prove it correct, count its steps. Each card points at the scenes that show it.

One card at a time

Insertion sort keeps A[1 : i − 1] sorted, lifts A[i] as the key, slides bigger items right and drops the key into the gap. Only the key is ever held aside. → 2.1, Insertion sort

Prove it with an invariant

Show a statement is true before the first lap, stays true lap to lap, and says something useful when the loop stops. It is induction that ends with the loop. → 2.1, Loop invariants · Problems 2-2, 2-3

Pseudocode has house rules

Indentation is block structure, a loop counter outlives its loop, objects are pointers passed by value, and and / or short-circuit. → 2.1, Pseudocode rules

Count steps on a RAM

One processor, one instruction at a time, a constant cost for every instruction and every data access, words of c lg n bits, no caches. Real machines differ, but the model predicts them well. → 2.2, The RAM model

The worst case is the guarantee

T(n) adds cost × times over every line. Sorted input gives insertion sort an + b, reversed input an² + bn + c, and random input is about as bad as the worst. → 2.2, Counting steps · Worst and average

Keep only the order of growth

Drop the lower-order terms and the leading constant: insertion sort is Θ(n²) in the worst case. A lower order of growth always wins once n is large enough. → 2.2, Order of growth

Divide, conquer, combine

Merge sort halves A[p : r], sorts both halves recursively, and merges them in Θ(n) time through the new arrays L and R. → 2.3.1, Divide and merge · Merge sort

Recurrences add up level by level

T(n) = 2T(n/2) + Θ(n): a recursion tree with lg n + 1 levels of cn each gives Θ(n lg n), which beats Θ(n²) for large n. → 2.3.2, Recurrences · Recursion tree · Ch 4

Words to know

The book's words from this chapter, in plain language.

insertion sort
Sorting by taking the items one at a time and inserting each into its place among the ones already sorted.
key
A value being sorted. It usually belongs to a larger record that moves with it.
satellite data / record
The other data that travels with a key, such as a student's name. Key plus satellite data make a record.
pseudocode
An algorithm written in whatever notation is clearest, even plain English, without software-engineering details.
A[i : j]
The subarray A[i], A[i + 1], …, A[j], with both ends included.
loop invariant
A statement that is true before every iteration of a loop, used to prove the loop does its job.
initialization · maintenance · termination
What you prove about an invariant: true before the first lap, kept by every lap, useful when the loop stops.
passed by value
A procedure gets its own copy of each parameter. For an object, that copy is a pointer to the same object.
NIL
The value of a pointer that points to no object at all.
short-circuiting
In “x and y”, y is evaluated only if x is true; in “x or y”, only if x is false.
RAM model
The model computer for analysis: one processor running instructions one after another, each in constant time.
word
A fixed number of bits the RAM works on at once: c lg n for a constant c ≥ 1, enough to hold n.
input size
How big an input is: the number of items for sorting, the number of bits for multiplying integers.
running time T(n)
The number of instructions and data accesses an algorithm executes on an input of size n.
worst case / best case
The longest and the shortest running time over all inputs of size n.
average case
The expected running time over all inputs of size n, usually assuming each is equally likely.
order of growth
How fast the running time rises with n: keep the leading term and drop its constant.
Θ-notation
“Roughly proportional to, when n is large”: Θ(n²), Θ(n lg n). Chapter 3 makes it precise.
divide-and-conquer
Split a problem into smaller instances of itself, solve them recursively, and combine their answers.
base case
A problem small enough to solve directly, where the recursion stops.
merge
Combine two sorted runs into one by repeatedly taking the smaller front item. It takes Θ(n) time.
recurrence
An equation giving T(n) in terms of T on smaller inputs, such as T(n) = 2T(n/2) + Θ(n).
recursion tree
A recurrence drawn as a tree of costs: add up each level, then add up the levels.

log₂ n: how many times you can halve n before reaching 1. lg 1,024 = 10.
inversion
A pair of positions i < j whose items are out of order: A[i] > A[j].
