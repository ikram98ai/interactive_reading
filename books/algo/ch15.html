Greedy Algorithms

A greedy algorithm always grabs the choice that looks best right now and never takes it back. This chapter shows when that is enough to be optimal: for booking a room, packing a knapsack, compressing text and keeping the right blocks in a cache.

15.1 · an activity-selection problem

Eleven requests, one room

You run a conference room that can host one event at a time, and eleven teams want it. Each request is an activity with a start time s and a finish time f. Two events that overlap can't both happen, so some teams must be turned away. Your goal is to say yes to as many as you can.

An activity holds the room during the half-open interval [s, f): from s up to, but not including, f. So one that ends at 5 and one that starts at 5 fit back to back. Two activities are compatible when their intervals don't overlap. The activity-selection problem asks for a largest set of activities that are all compatible with one another.

A big schedule is not always the biggest one. The set {a3, a9, a11} is a valid schedule of three, yet there is a schedule of four. With nothing smarter than trying subsets you must check 2n of them, so every extra request doubles the work. The rest of the section finds a way around that.

Try it: click bars to put activities in your set or take them out. Add a1 and a2 and watch the overlap turn coral, then swap a2 for a4: they touch at time 5 and are compatible. Build {a3, a9, a11} and press Check my set to see the pairs tested. Then press Search every subset: the machine tries all 2,048 subsets and keeps the biggest compatible one. In the Rust view the same search is a loop over bit masks.

What the book says

The chapter opens with the idea: “A greedy algorithm always makes the choice that looks best at the moment.” It makes a locally optimal choice in the hope that it leads to a globally optimal solution. Greedy algorithms do not always yield optimal solutions, but for many problems they do, and for those, dynamic programming is overkill. Section 15.1 starts with a simple but nontrivial example: it first considers a dynamic-programming approach, then shows that an optimal solution can result from always making greedy choices.

Imagine scheduling a conference room that can serve only one activity at a time. The proposed activities are S = {a1, …, an}, and activity ai has a start time si and a finish time fi, where 0 ≤ si < fi < ∞. If selected, it takes place during the “half-open time interval” [si, fi). Activities ai and aj are compatible if their intervals do not overlap, that is, if si ≥ fj or sj ≥ fi. Any changeover time for the staff is built into the intervals.

In the activity-selection problem the goal is to select a maximum-size subset of mutually compatible activities. The book assumes the activities are sorted by finish time, f1 ≤ f2 ≤ ⋯ ≤ fn, and promises to show later what that assumption buys.

For the 11 activities of Figure 15.1, the subset {a3, a9, a11} is mutually compatible but not a maximum subset, since {a1, a4, a8, a11} is larger. That set is a largest one, and so is {a2, a4, a9, a11}. The machine's exhaustive search finds two more, which are not named in the book.

15.1 · the dynamic-programming solution

Cut at one booking, solve both halves

Look at the best schedule for a stretch of time, and pick one activity ak in it. Every other member of the schedule runs either before ak starts or after it finishes, so ak cuts the problem in two. Name the stretch between two activities: Sij is the set of activities that start after ai finishes and finish before aj starts.

Each half must be solved optimally. If the part after ak could hold more activities, swap in that better part and the whole schedule grows, which contradicts its being the best. This cut-and-paste argument is what makes the problem have optimal substructure, and it gives a recurrence for c[i, j], the size of a best schedule in Sij: it is 0 when Sij is empty, and otherwise the largest value of c[i, k] + c[k, j] + 1 over every ak in Sij.

Nobody tells you which ak belongs to the best schedule, so you try them all. A table of n × n subproblems with up to n choices each is heavy machinery for the question “which booking goes first?”, and the next scene shows you can skip it. The machine adds two pretend activities, a0 finishing at time 0 and a12 starting at ∞, so that S0,12 is the whole problem.

Try it: click a square in the grid, or move the i and j sliders, to choose a subproblem. The shaded stretch of the time line is Sij, and each chip below is one choice of ak with the size of the best schedule that uses it. Click a chip to see the cut: two smaller stretches, each with its own best schedule in mint. Press Try each k to watch the choices tested, then Fill the table to see c computed from short stretches outward and count the sums it needs.

What the book says

Denote by Sij the set of activities that start after ai finishes and finish before aj starts. Suppose a maximum set of mutually compatible activities in Sij is Aij, and that it includes some activity ak. Choosing ak leaves two subproblems, Sik and Skj. With Aik = Aij ∩ Sik and Akj = Aij ∩ Skj, we have Aij = Aik ∪ {ak} ∪ Akj, so |Aij| = |Aik| + |Akj| + 1.

“The usual cut-and-paste argument” shows that Aij must include optimal solutions to both subproblems. A larger set A′kj in Skj would give a set of |Aik| + |A′kj| + 1 > |Aij| compatible activities, contradicting the assumption that Aij is optimal. A symmetric argument applies to Sik.

Writing c[i, j] for the size of an optimal solution for Sij, the book gets c[i, j] = c[i, k] + c[k, j] + 1 when the choice is known. Since it is not, you must examine all activities in Sij: recurrence (15.2) is 0 if Sij = ∅, and the maximum of c[i, k] + c[k, j] + 1 over ak ∈ Sij otherwise. You can memoize a recursive algorithm or fill table entries bottom-up. “But you would be overlooking another important characteristic of the activity-selection problem” that can be used to great advantage, which the next subsection explains. Exercise 15.1-1 asks for the dynamic-programming algorithm and a comparison with GREEDY-ACTIVITY-SELECTOR.

15.1 · the greedy choice and GREEDY-ACTIVITY-SELECTOR

Always take the earliest finisher

The table in the last scene tried every ak as the cut. But a schedule has to start with somebody, so ask which activity costs the room the least time: the one that finishes earliest. Taking it leaves the room free for as long as possible, so surely it can't hurt. That is a greedy choice: grab what looks best now, before solving any subproblem. Once it is made only one subproblem is left, the activities that start after it finishes.

Theorem 15.1 says the hunch is right. Take any largest schedule A, and let aj be the activity in it that finishes first. Swap aj for the earliest finisher am. It finishes no later than aj, and everything else in A starts no earlier than aj finishes, so the new set is still compatible and just as big. Some largest schedule always contains am.

Repeat the choice and you get the book's two procedures. With the activities sorted by finish time, GREEDY-ACTIVITY-SELECTOR makes one pass, remembering the latest pick k and taking the next activity that starts no earlier than fk. The recursive version does the same as a chain of calls. Each activity is looked at once, so the pass is Θ(n). Other rules sound just as sensible and fail.

Try it: in Sweep, press Play. The dashed line is fk and the yellow bar is the candidate: one that starts left of the line overlaps it and is skipped (coral), one that starts at or right of it is taken (mint). Open the Recursive tab to see the same run as calls stacking up and returning. In Why it's safe pick a largest set and watch the swap. Then run Shortest first and Earliest start on both instances: each wins on one and loses on the other.

What the book says

Intuition suggests choosing an activity that leaves the resource available for as many other activities as possible. One of the chosen activities must be the first to finish, so choose the activity in S with the earliest finish time (any one of them if there is a tie). With the activities sorted, that is a1. It is not the only greedy choice for this problem; Exercise 15.1-3 asks for examples where the least duration, the fewest overlaps, or the earliest start does not work.

After the greedy choice only one subproblem remains: activities that start after a1 finishes. No activity can finish at or before s1, because s1 < f1 and f1 is the earliest finish time, so everything compatible with a1 must start after it finishes. With Sk = {ai ∈ S : si ≥ fk}, optimal substructure says an optimal solution is a1 plus an optimal solution to S1.

Theorem 15.1: consider any nonempty subproblem Sk, and let am be an activity in Sk with the earliest finish time. Then am is included in some maximum-size subset of mutually compatible activities of Sk. In the proof, A′k = (Ak − {aj}) ∪ {am} is compatible because aj is the first activity in Ak to finish and fm ≤ fj, and |A′k| = |Ak|. Because the earliest finish is always chosen, the finish times of the chosen activities strictly increase and each activity is considered just once.

“Greedy algorithms typically have this top-down design: make a choice and then solve a subproblem.” RECURSIVE-ACTIVITY-SELECTOR(s, f, k, n) takes the arrays s and f, the index k of the subproblem Sk and the size n; a fictitious a0 with f0 = 0 makes S0 the whole set, so the first call is RECURSIVE-ACTIVITY-SELECTOR(s, f, 0, n). Its while loop in lines 2–3 finds the first activity in Sk to finish. Each activity is examined exactly once in the loop test of line 2, so the running time is Θ(n), assuming the activities are sorted. Figure 15.2 runs it on Figure 15.1 and selects {a1, a4, a8, a11}; if the activities are not sorted, sorting costs O(n lg n).

The recursive procedure is almost “tail recursive”: it ends with a recursive call followed by a union operation, which converts to a loop (see Problem 7-5). GREEDY-ACTIVITY-SELECTOR is that loop. Since fk is always the maximum finish time of any activity in A, line 4 only has to check that sm is not earlier than fk. It also takes Θ(n) time on sorted input. The two counterexample instances on the machine's buttons are its own examples, not the book's.

15.2 · elements of the greedy strategy

Pick now, solve what is left

Walk down a buffet and fill your plate with whatever looks best right now. That is the greedy habit: a greedy algorithm takes the choice that seems best at the moment, then solves the one smaller problem that remains. Dynamic programming is the careful cousin: it solves the subproblems behind every choice first, and only then chooses.

The habit is safe only with two ingredients. The greedy-choice property: some optimal solution contains the choice that looks best now, so taking it can never cost you the optimum. And optimal substructure: what is left, solved optimally and added to that choice, is optimal for the whole problem. Without the first, a greedy algorithm can be beaten.

The machine makes change. The coins are our own example (the book's version is Problem 15-1). At every stage it lists the coins that fit. Try-all has already filled a table c[r] of the fewest coins for every amount, so it knows what each coin would lead to. Greedy never looks at the table: it just takes the largest coin. The question is whether that coin starts an optimal solution.

Try it: with coins 1 · 5 · 10 · 25 and amount 30, press Play. At each stage the badges show the total each coin would give, and greedy's pick sits on a mint badge: it is safe. Then choose 1 · 3 · 4 → 6 and press Step until the verdict: greedy takes 4, but 4 is no start of an optimal solution (3 coins, not 2), and the middle check turns coral. Compare the last two counters: greedy visits a few subproblems, try-all fills the whole table.

What the book says

A greedy algorithm obtains an optimal solution by making a sequence of choices. “At each decision point, the algorithm makes the choice that seems best at the moment.” That does not always produce an optimal solution, but sometimes it does, as in activity selection. The way Section 15.1 reached its greedy algorithm took six steps: find the optimal substructure, write a recursive solution, show that the greedy choice leaves only one subproblem, prove the greedy choice safe, write a recursive greedy algorithm, and turn it into an iterative one. Those steps show the dynamic-programming underpinnings of a greedy algorithm.

A more direct design takes three steps. Cast the problem as one where you make a choice and are left with one subproblem. Prove that there is always an optimal solution that makes the greedy choice, so the choice is always safe. Show optimal substructure: combine an optimal solution to the remaining subproblem with the greedy choice, and you get an optimal solution to the original problem. Beneath every greedy algorithm there is almost always a more cumbersome dynamic-programming solution.

“No way works all the time, but the greedy-choice property and optimal substructure are the two key ingredients.” In dynamic programming the choice usually depends on the solutions to subproblems, so the work goes bottom up. A greedy algorithm instead goes top down: it “makes its first choice before solving any subproblems.” Its choice may depend on the choices so far, but never on future choices or on subproblem solutions.

You can usually make the greedy choice faster than you could weigh a wider set of choices, by preprocessing the input or by using a suitable data structure, often a priority queue. Because both strategies exploit optimal substructure, one can be tempted to use dynamic programming where greedy suffices, or to assume greedy works where dynamic programming is needed. The next scene takes the book's two knapsack variants as the example.

15.2 · the 0-1 and fractional knapsack problems

Gold ingots or gold dust

A thief can carry 50 pounds. The store has three things: item 1 (10 lb, $60), item 2 (20 lb, $100) and item 3 (30 lb, $120). The greedy instinct says to grab the best value per pound first: $6, then $5, then $4.

If the loot is gold dust, that instinct is exactly right. In the fractional knapsack problem the thief takes all of item 1, all of item 2, and fills the last 20 lb with two thirds of item 3: $240. If the loot is gold ingots, each item goes in whole or stays behind: the 0-1 knapsack problem. Now greedy takes items 1 and 2, item 3 no longer fits, and 20 lb stay empty with only $160 on board. Items 2 and 3 together fill the sack for $220.

Why does the same idea fail? In the 0-1 problem the empty space drags down the value per pound of the whole load, so whether to take item 1 depends on how the rest fits. You must compare the best load with the item against the best load without it. Those overlapping subproblems are the signature of dynamic programming, not of a greedy choice.

Try it: in 0-1 knapsack, press Play: items 1 and 2 go in, item 3 is refused, and the unused 20 lb turns coral. Press Try every subset to see the case analysis of Figure 15.3(b) and its winner, items 2 and 3. Then switch to Fractional and press Play: item 3 goes in as a 20 lb scoop and nothing is wasted. You can also click items to load the sack yourself, and click the sack to unload. Try to beat the bars.

What the book says

In the 0-1 knapsack problem a thief robbing a store can carry at most W pounds in a knapsack and may take any subset of n items. Item i is worth vi dollars and weighs wi pounds, both integers. Each item is taken or left, with no fractions and no repeats. In the fractional knapsack problem the thief can take fractions of items. An item in the 0-1 problem is like a “gold ingot”, and one in the fractional problem is more like “gold dust”.

Both problems have optimal substructure. For the 0-1 problem, if the most valuable load of weight at most W includes item j, the rest must be the most valuable load of weight at most W − wj from the other n − 1 items. For the fractional version, if the best load includes weight w of item j, the rest must be the most valuable load of weight at most W − w from the other n − 1 items plus the remaining wj − w pounds of item j.

A greedy strategy solves the fractional problem but not the 0-1 problem. Compute the value per pound vi / wi of each item, take as much as possible of the item with the greatest value per pound, then of the next, until the weight limit W is reached. Sorting makes this O(n lg n). Exercise 15.2-1 asks you to prove the greedy-choice property for the fractional problem.

Figure 15.3 uses the three items above with W = 50. Item 1 has the greatest value per pound ($6, against $5 and $4), so greedy takes it first. But the optimal 0-1 load is items 2 and 3 for $220, and the two loads that contain item 1 are worth $160 and $180. Taking item 1 fails in the 0-1 problem because the thief cannot fill the knapsack to capacity, and “the empty space lowers the effective value per pound of the load.” For the fractional problem, taking item 1 first does give the optimum: $60 + $100 + $80 = $240.

In the 0-1 problem you must compare the subproblem that includes an item with the one that excludes it before choosing. That gives many overlapping subproblems, a hallmark of dynamic programming, and Exercise 15.2-2 asks for a dynamic-programming solution that runs in O(nW) time.

15.3 · prefix codes

Short words for common letters

A file of 100,000 characters uses only six letters, and a is nine times as common as f. Give every letter 3 bits and the file costs 300,000 bits. Give the common letters short codewords and the rare ones long ones, and the same file fits in 224,000 bits: about 25% less. A character code is exactly this: a unique binary string for each character.

But with codewords of different lengths, where does one end and the next begin? The cure is a prefix-free code: no codeword is the beginning of another. Then the first codeword of any bit string is unambiguous: read bits until they spell a codeword, write its letter, start over. A code tree does the reading for you. Walk down from the root, 0 for left and 1 for right, and the letters sit at the leaves, so a codeword is simply the path to its letter.

The tree also prices the code. A letter at depth d costs d bits every time it occurs, so the file costs B(T) = Σ freq × depth. An optimal code is always a full tree, where every inner node has two children. The fixed-length tree has a gap (no codeword starts with 11), so it cannot be optimal.

Try it: build a message with the letter buttons, press Encode and watch each letter's path light up in the tree, then Decode to see the pointer walk down one edge per bit and jump back to the root at every leaf. Cost B(T) adds up freq × depth leaf by leaf. Compare Fixed-length with Variable-length. Then pick Not prefix-free (our own example: e = 110 is the start of f = 1100) and decode: the walk cannot tell where e ends.

What the book says

A 100,000-character file contains only the characters a–f, with frequencies (in thousands) 45, 13, 12, 16, 9 and 5 (Figure 15.4). The book designs a binary character code in which each character is represented by a unique binary string, its codeword. A fixed-length code needs ⌈lg n⌉ bits per character, so 3 bits here (a = 000 through f = 101) and 300,000 bits in all. For a variable-length code, “give frequent characters short codewords and infrequent characters long codewords”: a = 0, b = 101, c = 100, d = 111, e = 1101, f = 1100 takes (45·1 + 13·3 + 12·3 + 16·3 + 9·4 + 5·4)·1,000 = 224,000 bits, “a savings of approximately 25%”, and this code is optimal for the file.

The book considers only codes in which no codeword is also a prefix of some other codeword: prefix-free codes. Although it does not prove it, a prefix-free code can always achieve the optimal compression among character codes, so nothing is lost. Encoding concatenates the codewords: face becomes 1100 0 100 1101 = 110001001101. Decoding is simple because the codeword that begins an encoded file is unambiguous: identify it, translate it back, and repeat on the rest. The string 100011001101 parses uniquely as 100 0 1100 1101, which decodes to cafe.

To pick off the initial codeword easily, represent the code as a binary tree whose leaves are the characters: a codeword is the simple path from the root to its character, where 0 means “go to the left child” and 1 means “go to the right child” (Figure 15.5). These are “not binary search trees”: leaves need not be sorted and inner nodes hold no keys. An optimal code is always represented by “a full binary tree, in which every nonleaf node has two children”. The fixed-length tree is not full, since it has codewords beginning with 10 but none beginning with 11. So for an alphabet C with positive frequencies, the tree of an optimal prefix-free code has exactly |C| leaves and |C| − 1 internal nodes.

Given a tree T, let c.freq be a character's frequency and dT(c) the depth of its leaf, which is also its codeword's length. The bits needed to encode the file are B(T) = Σ c.freq · dT(c) (equation 15.4), which the book defines as the cost of the tree.

15.3 · constructing a Huffman code

Merge the two rarest, again and again

Huffman's idea is a tournament of the rarest. Put every letter in a min-priority queue keyed on its frequency. Then repeat: pull out the two least frequent items, hang them under a new parent whose frequency is their sum, and put the parent back in the queue. The rare letters are merged first, so they end up deepest in the tree and get the longest codewords.

After n − 1 merges a single tree is left: the code tree. Label each merge's left edge 0 and its right edge 1, and a letter's codeword is the path from the root to it. With the book's frequencies this rebuilds exactly the 224,000-bit code of the last scene. The choice made at every step is greedy: of all possible mergers, take the cheapest one.

Each merge is two EXTRACT-MINs and one INSERT, and there are n − 1 merges, so a binary min-heap gives O(n lg n) in all. When two trees tie on frequency the choice is free: swapping left and right anywhere gives a different code of the same cost. The machine breaks ties in favour of the older tree.

Try it: press Step and watch the Q strip along the top: each merge takes the two leftmost trees, x and y, hangs them under a new z, and slides z to its sorted place. After the last merge the codewords appear under the leaves and the cost counter reads 224k bits. Then try Skewed, a deep lopsided tree, and Four equal: equal frequencies give a balanced tree and no saving at all. In Rust the memory strip shows Box::new moving x and y onto the heap under z.

What the book says

Huffman invented a greedy algorithm that constructs an optimal prefix-free code, called a Huffman code. The procedure HUFFMAN assumes that C is a set of n characters and that each character c has an attribute c.freq. It builds the tree T bottom-up. It begins with |C| leaves and performs |C| − 1 “merging” operations. The algorithm uses “a min-priority queue Q, keyed on the freq attribute”, to identify the two least-frequent objects to merge. The result of a merge is a new object whose frequency is the sum of the two.

Line 2 initializes Q with the characters. The for loop of lines 3–10 repeatedly extracts the two nodes x and y of lowest frequency and replaces them with a new node z, whose frequency is computed in line 9. The node z has x as its left child and y as its right child. This order is arbitrary: switching the left and right child of any node yields a different code of the same cost. After n − 1 mergers, line 11 returns the one node left in the queue, the root of the code tree. For the six letters of Figure 15.4 the initial queue size is 6, five merges build the tree (Figure 15.6), and the final tree represents the optimal prefix-free code.

The algorithm gives the same result without the variables x and y, assigning the EXTRACT-MIN results directly to z.left and z.right. The book keeps the names because the proof of correctness uses them.

The running time depends on how Q is implemented. With a binary min-heap (Chapter 6), BUILD-MIN-HEAP initializes Q in line 2 in O(n) time. The loop runs exactly n − 1 times and each heap operation takes O(lg n), so the loop contributes O(n lg n), and the total running time of HUFFMAN on n characters is O(n lg n).

15.3 · correctness of huffman's algorithm

Why the greedy merge never loses

Huffman's algorithm makes one bet and never takes it back: glue the two rarest letters together, then carry on with a smaller alphabet. Could a cleverer tree beat that bet? The book rules it out with two lemmas, and each is a trick you can watch on a code tree. The alphabet is the one from Figure 15.4, renamed p to u, so that a, b, x and y keep the roles the proof gives them.

First, the bet is safe. This is Lemma 15.2, the greedy-choice property. Take any code tree. Call the two rarest letters x and y, and two leaves that share a parent at the greatest depth a and b. Swap x with a, then y with b. Each swap lifts a common letter and sinks a rare one, so the cost B(T) = Σ freq × depth can only fall: it changes by (a.freq − x.freq)(d(a) − d(x)), a product of two numbers that are never negative. Start from an optimal tree and the cost cannot fall, so it stays put: some optimal tree keeps x and y as its deepest siblings, exactly where Huffman puts them.

Second, the smaller problem is faithful. This is Lemma 15.3, the optimal-substructure property. Glue x and y into one new letter z with z.freq = x.freq + y.freq, and take any tree T′ for the smaller alphabet. Grow two children under z and you have a tree T for the full one. Only x and y get one bit longer, so B(T) = B(T′) + x.freq + y.freq, whatever T′ looks like. The cheapest T′ makes the cheapest T. Together the lemmas give Theorem 15.4: HUFFMAN produces an optimal prefix-free code.

Try it: in Lemma 15.2 press Step. The rarest letters x, y (blue) and the deepest siblings a, b (yellow) light up, then two swaps happen and the ledger under the tree records B(T), B(T′), B(T″). Try the other start trees, then click any two leaves to swap them yourself: lifting a common letter pays, sinking one costs. In Lemma 15.3 press Step to grow z's children, then pick A poor tree and grow them again: the cost still rises by exactly 5 + 9.

What the book says

To show that HUFFMAN is correct, the book shows that the problem of finding an optimal prefix-free code has the greedy-choice and optimal-substructure properties. Lemma 15.2 says that if x and y are two characters of C with the lowest frequencies, then “there exists an optimal prefix-free code for C in which the codewords for x and y have the same length and differ only in the last bit.”

The proof takes the tree T of an arbitrary optimal code and modifies it so that x and y become sibling leaves of maximum depth. Let a and b be any two sibling leaves of maximum depth in T, with a.freq ≤ b.freq and x.freq ≤ y.freq, so that x.freq ≤ a.freq and y.freq ≤ b.freq. Exchanging a and x gives T′, and exchanging b and y in T′ gives T″. Then B(T) − B(T′) = (a.freq − x.freq)(dT(a) − dT(x)) ≥ 0, because x has minimum frequency and a is a leaf of maximum depth. The second exchange is the same, so B(T″) ≤ B(T′) ≤ B(T), and as T is optimal, B(T″) = B(T). The book assumes x ≠ b: if x.freq = b.freq, all four frequencies are equal and the lemma is trivial.

Why is merging a greedy choice? The cost of one merger is the sum of the frequencies of the two items merged, and Exercise 15.3-4 shows that the total cost of the tree equals the sum of the costs of its mergers. “Of all possible mergers at each step, HUFFMAN chooses the one that incurs the least cost.”

Lemma 15.3: let x and y have minimum frequency in C, let C′ = (C − {x, y}) ∪ {z} with z.freq = x.freq + y.freq, and let T′ be a tree for an optimal prefix-free code for C′. Replacing the leaf z of T′ by an internal node with children x and y gives a tree T for an optimal prefix-free code for C. The proof first shows B(T) = B(T′) + x.freq + y.freq, because dT(x) = dT(y) = dT′(z) + 1 and every other character keeps its depth. It then argues by contradiction: a better tree for C could, by Lemma 15.2, be taken with x and y as siblings, and collapsing them into z would beat T′.

Theorem 15.4 is immediate from the two lemmas: “Procedure HUFFMAN produces an optimal prefix-free code.”

15.4 · offline caching

Throw out what you'll need last

A cache is a small, fast shelf in front of a big, slow warehouse. Every request asks for one block. If it is on the shelf, that is a hit. If not, it is a miss: the block is fetched, and when the shelf already holds k blocks, one of them must be thrown out first. The goal is to make as few misses as possible over the whole request sequence.

A real cache cannot see the future, but the offline version of the problem hands you all n requests in advance. Then a greedy rule is optimal, called furthest in future: when you must evict, drop the block whose next request is the latest. A block that is never requested again is the perfect victim. Any other choice throws out something you will need sooner, and you pay for it before you would have paid for the block you kept.

Two other rules look just as sensible but lose. FIFO evicts the block that has been on the shelf longest. LRU (least recently used) evicts the block that has gone unrequested longest, a guess about the future made from the past. The machine runs all three on the same requests, so you can see where they part ways.

Try it: with the book's sequence and k = 3, press Play and watch the lines at each miss on a full cache: one from every cached block to its next request. Furthest in future evicts the block whose line reaches furthest, or has no line at all. Switch to FIFO and LRU and compare the three miss counters. Then pick Cyclic scan: FIFO and LRU miss on every single request, while furthest in future misses fewer than half of them. Raise k to 4 and every policy only pays the compulsory misses.

What the book says

A cache stores a subset of main memory in a small but faster memory, organised into cache blocks of typically 32, 64, or 128 bytes. Main memory can also be viewed as a cache for disk-resident data, where the blocks are called pages, typically 4096 bytes. A program makes n requests to blocks b1, b2, …, bn, which need not be distinct. The cache holds up to k blocks and starts out empty, and each request causes at most one block to enter and at most one to be evicted. A request is a cache hit if the block is already in the cache; otherwise it is a cache miss, and if the cache is full some other block must be evicted. A miss while the cache holds fewer than k blocks is a compulsory miss. The goal is to minimize the number of cache misses.

“Typically, caching is an online problem.” The book considers the offline version, in which the computer knows in advance the entire sequence of requests and the cache size k. The offline problem still matters: some systems plan their reads and writes in advance, and the number of misses of an optimal offline algorithm is a baseline for judging online ones (Section 27.3). The example request sequence for four blocks p, q, r, s is s, q, s, q, q, s, p, p, r, s, s, q, p, r, q.

The greedy strategy, furthest-in-future, evicts the block in the cache whose next access in the request sequence comes furthest in the future. The book first shows optimal substructure. Define the subproblem (C, i) as processing requests bi, …, bn when the cache holds C at the time bi is requested. On a hit the cache stays the same; on a miss with a full cache there are k configurations that can follow, one for each block that could be evicted. This gives a recurrence for miss(C, i), the minimum number of misses.

Theorem 15.5 gives the greedy-choice property. When the cache is full and bi misses, let z be the block in C whose next access is furthest in the future; if some block is never referenced again, any such block can serve as z, with a dummy request bn+1 = z added. Then evicting z is included in some optimal solution. The proof takes an optimal solution S that evicts another block x and builds a solution S′ that evicts z instead, keeping the two caches within one block of each other and making no more misses than S. With optimal substructure, this shows that furthest-in-future gives the minimum possible number of cache misses.

Exercise 15.4-2 introduces LRU, which evicts the block that, of all blocks currently in the cache, was the least recently requested; the book says you can think of it as “furthest-in-past.” It asks for a request sequence on which LRU makes more misses than furthest-in-future.

problem 15-1 · coin changing

Greedy change, and where it breaks

Make change for n cents with as few coins as possible. The cashier's rule is greedy: hand over the biggest coin that still fits, and repeat. With quarters, dimes, nickels and pennies it never fails, and neither does any system whose coins are powers of one number c, such as 1, 2, 4, 8 or 1, 3, 9, 27.

The rule bets that the biggest coin is always part of some best answer, and some coin systems break the bet. With coins 1, 3 and 4, change for 6 is 4 + 1 + 1 by the cashier's rule, three coins, when 3 + 3 does it in two. The chart marks every amount where greedy loses. When a penny is among the coins there is an exact method anyway: a dynamic program fills c[j], the fewest coins for j cents, from the answers for smaller amounts, in O(nk) time for k denominations.

Try it: pick 1 · 3 · 4 and drag the amount to 6: greedy shows three coins and the fewest-coins bar shows two. In the chart each bar is the fewest coins for that amount and each dot is what greedy used: mint when they agree, coral and above the bar when greedy loses. Press Play in Greedy to watch the cashier, then switch to Fewest coins (DP) and play it to see the bars grow left to right. Then try Powers of 2 and Powers of 3, where nothing turns coral, and build your own system with the coin chips.

What the book says

Problem 15-1 considers making change for n cents using the smallest number of coins, where each coin's value is an integer. Part (a) asks for a greedy algorithm for coins of quarters, dimes, nickels and pennies, with a proof that it is optimal. In part (b) the denominations are powers of c: c0, c1, …, ck for integers c > 1 and k ≥ 1, and the task is to show that the greedy algorithm always yields an optimal solution.

Part (c) asks for a set of coin denominations for which the greedy algorithm does not yield an optimal solution; the set should include a penny, so that there is a solution for every value of n. Part (d) asks for an O(nk)-time algorithm that makes change for any set of k different coin denominations using the smallest number of coins, assuming that one of the coins is a penny.

The book states the problem and leaves the proofs to the reader. The coin sets, the greedy loop and the table c[j] on this page illustrate parts (a) to (d); they are not the book's own text.

problem 15-2 · scheduling to minimize average completion time

Shortest task first

One machine, a queue of tasks. Task ai needs pi units of processing time and finishes at its completion time Ci. The score is the average completion time, (1/n) Σ Ci. Run a long task first and everyone behind it waits for it, so the order matters a lot.

Here is the exchange argument. Find a long task sitting right before a short one and swap the two. Every task before the pair and after it finishes exactly when it did. The short task now finishes earlier by the long one's length, and the long task finishes later by the short one's length, so the two completion times together fall by plong − pshort. No order with such a neighbouring pair can be best, and the orders with none are the ones that run tasks by increasing processing time: shortest processing time first.

Part (b) changes two rules. A task cannot start before its release time bi, and a running task may be stopped and resumed later, which is called preemption. Now a short newcomer can cut in front of a long task that is already running. The rule on the machine is shortest remaining processing time: at every moment, run the released, unfinished task with the least work left.

Try it: in All ready at 0, drag the blocks to reorder them, or tap one and press ← →, and watch the average. Step swaps the first long-before-short neighbours and shows how much the sum falls, Play keeps going until none are left, and Longest first builds the worst order. In Release times, pick No preemption or SRPT and press Play. The grey part of a row is before the task's release; under SRPT, watch task A get cut off twice.

What the book says

Problem 15-2 gives a set S = {a1, a2, …, an} of tasks, where task ai requires pi units of processing time. Let Ci be the completion time of task ai, the time at which it completes processing. The goal is to minimize the average completion time, (1/n) Σ Ci. For two tasks with p1 = 3 and p2 = 5, running a2 first gives C2 = 5, C1 = 8 and an average of 6.5, while running a1 first gives C1 = 3, C2 = 8 and an average of 5.5.

Part (a) asks for an algorithm that minimizes the average completion time when each task runs nonpreemptively: once task ai starts, it runs continuously for pi units of time until it is done. It also asks for a proof that the algorithm is optimal and an analysis of its running time.

In part (b) the tasks are not all available at once: each task cannot start until its release time bi, and tasks may be preempted, so a task can be suspended and restarted later. The book's example is a task with pi = 6 and bi = 1 that runs from time 1 to 4, again from 10 to 11, and again from 13 to 15: it has run a total of 6 time units, divided into three pieces. The task is again to give, prove and analyze an algorithm that minimizes the average completion time.

The book leaves the algorithms and proofs to the reader. The exchange step, the shortest-remaining-time rule and the task sizes on this page are an illustration of the two parts, not the book's own text.

The chapter on one page

Chapter 15 in eight cards. Each one points at the scenes that act it out.

Take what looks best now

A greedy algorithm makes the locally best choice at each step and hopes for a global optimum. It does not always get one, but for many problems it does. Activity selection asks for a largest set of mutually compatible activities, where ai holds the room for the half-open interval [si, fi). → 15.1 Activity selection

Cut at one activity

Sij holds the activities that start after ai finishes and finish before aj starts. A largest schedule containing ak splits into optimal schedules for Sik and Skj (cut and paste), so c[i, j] is the largest c[i, k] + c[k, j] + 1, or 0 for an empty set. It works, but it is more machinery than the problem needs. → 15.1 DP first

The earliest finisher is safe

Theorem 15.1: the activity with the earliest finish time in a nonempty Sk is in some maximum-size subset. So choose it, solve the one subproblem left, and repeat. RECURSIVE-ACTIVITY-SELECTOR does it with calls and GREEDY-ACTIVITY-SELECTOR with a loop: Θ(n) once the activities are sorted by finish time. → 15.1 Greedy choice

Two ingredients, one test

A greedy algorithm needs the greedy-choice property (a locally optimal choice can be part of a global optimum, made before any subproblem is solved) and optimal substructure. Dynamic programming solves subproblems first. The knapsack shows the line: greedy by value per pound is optimal for the fractional problem and fails for the 0-1 problem. → 15.2 Greedy elements, 0-1 vs fractional

Short codes for common letters

A fixed-length code spends 3 bits per character and needs 300,000 bits for the book's 100,000-character file. A variable-length prefix-free code needs 224,000. No codeword is a prefix of another, so decoding is unambiguous, and the code is a binary tree whose leaves are the characters. Its cost is B(T) = Σ c.freq · dT(c). → 15.3 Prefix codes

Merge the two rarest

HUFFMAN keeps a min-priority queue of trees and, n − 1 times, extracts the two with the lowest frequencies and puts back a new node whose frequency is their sum: O(n lg n) with a binary min-heap. Lemma 15.2 (the two rarest can be sibling leaves at maximum depth, because swapping never raises the cost) and Lemma 15.3 (merging them leaves an optimal subproblem) prove it. → 15.3 Huffman, Why it's optimal

Evict what you need last

In offline caching the whole request sequence is known. When a miss finds the cache full, furthest-in-future evicts the block whose next request is furthest away. Theorem 15.5 shows this greedy choice lies in an optimal solution, so it causes the fewest misses, which also makes it a baseline for online algorithms. → 15.4 Offline caching

Problem 15-2 asks for a schedule that minimizes the average completion time of tasks, first without preemption and then with release times and preemption. Words to know

The book's words from this chapter, in plain language.

greedy algorithm
An algorithm that always makes the choice that looks best at the moment, in the hope that it leads to a globally optimal solution.
greedy-choice property
You can assemble a globally optimal solution by making locally optimal choices, deciding without looking at the solutions of subproblems.
optimal substructure
An optimal solution to the problem contains within it optimal solutions to subproblems. Both greedy algorithms and dynamic programming rely on it.
activity-selection problem
Given activities that each need a common resource for an interval, select a maximum-size subset of mutually compatible activities.
compatible
Activities ai and aj are compatible when their intervals do not overlap: si ≥ fj or sj ≥ fi.
half-open interval
[s, f) includes its start s but not its finish f, so one activity can begin exactly when another ends.
Sij and Sk
Sij is the set of activities that start after ai finishes and finish before aj starts. Sk is the set that starts after ak finishes.
cut and paste
The argument that an optimal solution contains optimal subsolutions: if a part were improvable, paste in the better part and the whole beats the optimum, a contradiction.
c[i, j]
The size of an optimal solution for Sij. It is 0 if the set is empty, and otherwise the maximum of c[i, k] + c[k, j] + 1 over ak in Sij.
Theorem 15.1
The activity with the earliest finish time in a nonempty Sk is included in some maximum-size subset of mutually compatible activities of Sk.
GREEDY-ACTIVITY-SELECTOR
The iterative greedy algorithm: scan the activities in finish-time order, keep the finish time of the last pick, and take each activity that starts at or after it.
tail recursion
A procedure whose last act is a recursive call, which makes it easy to turn into a loop. RECURSIVE-ACTIVITY-SELECTOR is almost tail recursive.
0-1 knapsack problem
A thief with a weight limit W must take or leave each item whole, for the most valuable load. Greedy by value per pound does not solve it.
fractional knapsack problem
The same, but the thief may take fractions of items: gold dust instead of ingots. Taking items in order of value per pound is optimal.
fixed-length code
A binary character code that spends the same number of bits on every character, ⌈lg n⌉ for n characters.
prefix-free code
A character code in which no codeword is a prefix of another. Decoding reads off the first codeword and repeats.
code tree
A binary tree whose leaves are the characters; a codeword is the path from the root, 0 for left and 1 for right. An optimal code's tree is full.
cost B(T)
The bits needed to encode the file with tree T: the sum over characters of frequency times depth of its leaf.
Huffman code
The optimal prefix-free code built by Huffman's greedy algorithm.
min-priority queue
A collection that gives back its smallest key first (EXTRACT-MIN) and accepts new items (INSERT). HUFFMAN keys it on frequency.
Lemma 15.2
The two lowest-frequency characters can be sibling leaves of maximum depth in some optimal tree, with codewords that differ only in the last bit.
Lemma 15.3
Merging the two lowest-frequency characters x and y into one character z leaves a problem whose optimal tree, with z replaced by x and y, is optimal for the original.
cache hit, miss
A request for a block already in the cache is a hit. Otherwise it is a miss, and a full cache must evict some block to make room.
offline caching
Caching when the whole sequence of requests is known in advance, which an online cache cannot know.
furthest-in-future
On a miss, evict the cached block whose next request is furthest in the future. It is optimal for the offline problem.
average completion time
The mean over tasks of the time Ci at which each finishes. Preemption means a running task may be suspended and resumed later.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

struct and &self
struct Activity { s: u32, f: u32 } groups named fields. A method written fn compatible(&self, other: &Activity) only borrows the activity: it reads it and the caller keeps it.
const arrays and slices
const S: [u32; 11] is data baked into the program, not on the heap. &S can be passed where a slice &[u32] is expected, so the callee sees the numbers without copying them.
half-open ranges and bit masks
0..n includes 0 but not n, the same convention as an activity's [s, f); 1..=n includes n. for mask in 0u32..(1 << n) counts through every subset, and (mask >> i) & 1 asks whether item i is in it.
Vec<Vec<T>>
A table as a vector of rows. vec![vec![0; w]; w] builds it; each row is its own heap buffer, indexed c[i][j].
a returned Vec moves
A function that returns a Vec hands over ownership. The heap buffer stays where it is and only the small header moves up the call chain, so a recursion that builds its result copies nothing. Vec::new() allocates nothing until the first push.
closures as arguments
|a| a.f is a small anonymous function. A parameter typed impl Fn(&Activity) -> K accepts any such closure, which is how one function picks by length, by start or by finish. min_by_key, sort_by_key and retain all take one.
patterns in parameters
|&(s, f)| takes a tuple apart as it arrives; |&&i| strips two layers of reference; let Reverse((fx, ix)) = q.pop().unwrap(); unpacks a wrapper and a tuple in one step.
u32::MAX as infinity
The largest u32 stands in for ∞ in a table. saturating_add(1) keeps ∞ + 1 at ∞ instead of wrapping around to 0.
as and partial_cmp
x as f64 converts a number by hand; Rust never does it silently. An f64 can be NaN, so it has no total order, and a.partial_cmp(&b) returns an Option that you unwrap when sorting by ratio.
enum with Box children
enum Node { Leaf(char), Inner(Box<Node>, Box<Node>) } is a code tree. Box puts each child on the heap; without it a Node would contain itself and have infinite size.
BinaryHeap and Reverse
BinaryHeap pops its largest item first. Wrapping items in Reverse(…) flips the order, giving the min-priority queue HUFFMAN needs. slots[i].take() moves a value out of an Option and leaves None.
HashMap<char, String>
A table from characters to codewords. Its iteration order is random, so the code collects the keys and sorts them before printing.
