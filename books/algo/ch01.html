The Role of Algorithms in Computing

An algorithm is a recipe precise enough for a machine: it takes an input, works through exact steps, and stops with the right output. This chapter tours the problems algorithms solve, the ones nobody can solve fast, and why a better algorithm can beat a computer a thousand times faster.

“Having a solid base of algorithmic knowledge and technique is one characteristic that defines the truly skilled programmer.” — Cormen, Leiserson, Rivest & Stein

1.1 · algorithms

A recipe that always finishes

A recipe turns ingredients into a cake. An algorithm turns an input into an output: a well-defined sequence of steps that always stops after a finite amount of time.

Every algorithm answers a computational problem, which says what output each input should get. In the sorting problem the input is any sequence of n numbers and the output is the same numbers, reordered so each one is no bigger than the next. One particular input, such as ⟨31, 41, 59, 26, 41, 58⟩, is an instance of the problem.

The machine sorts with insertion sort, which the book studies in Chapter 2. It works like sorting a hand of cards: lift the next card, slide the bigger ones one place right, drop the card into the gap.

Try it: press Step a few times and follow the highlighted line, then Play. Switch to Rust: the index numbers under the cells change from 1–6 to 0–5, and the memory strip shows v owning the numbers while a only borrows them. Then try Already sorted and Reversed, and compare the counters.

What the book says

Informally, an algorithm is “any well-defined computational procedure that takes some value, or set of values, as input and produces some value, or set of values, as output in a finite amount of time.” It is a sequence of computational steps that transform the input into the output, and a tool for solving a well-specified computational problem, whose statement gives the desired input/output relationship for problem instances, typically of arbitrarily large size.

The sorting problem. Input: a sequence of n numbers ⟨a1, a2, …, an⟩. Output: a permutation (reordering) ⟨a′1, a′2, …, a′n⟩ of the input such that a′1 ≤ a′2 ≤ ⋯ ≤ a′n. Given ⟨31, 41, 59, 26, 41, 58⟩, a correct sorting algorithm returns ⟨26, 31, 41, 41, 58, 59⟩. Such an input is an instance of the sorting problem.

Sorting is a fundamental operation because many programs use it as an intermediate step. Which algorithm is best depends on the number of items to be sorted, the extent to which they are already somewhat sorted, possible restrictions on the item values, the architecture of the computer, and the kind of storage devices used: main memory, disks, or even tapes.

1.1 · correct and incorrect algorithms

Halts, and gets it right. Every time.

A sorting procedure is correct only if, for every instance, it halts (finishes in finite time) and its output is the right answer. Passing one test proves nothing about the next input.

An incorrect algorithm fails in one of two ways. It halts with a wrong answer, or on some inputs it never halts. From outside, “still running” and “stuck forever” look the same, so this machine gives each procedure a budget of 40 steps and stops watching after that.

How you write a procedure is up to you: plain English, a program, even a hardware design. The only rule is that the description is precise.

Try it: press Run on each of the three procedures and read the verifier. Then pick No repeated values and run Never halts again: this time it sorts correctly. One good run does not make it correct, because on the book's instance it loops forever.

What the book says

An algorithm for a computational problem is correct if, for every problem instance provided as input, it halts (finishes its computing in finite time) and outputs the correct solution to the problem instance. A correct algorithm solves the given computational problem.

“An incorrect algorithm might not halt at all on some input instances, or it might halt with an incorrect answer.” Incorrect algorithms can sometimes be useful, if you can control their error rate; the book's example comes in Chapter 31, with algorithms for finding large prime numbers. Ordinarily the book is concerned only with correct algorithms.

“An algorithm can be specified in English, as a computer program, or even as a hardware design.” The only requirement is that the specification gives a precise description of the computational procedure to be followed.

1.1 · a controllable error rate

Wrong on purpose, but rarely

Contrary to what you might expect, an incorrect algorithm can be useful, as long as you control how often it is wrong. The book's example is deciding whether a huge number is prime, a question public-key cryptography asks all the time (Chapter 31).

The Miller–Rabin test picks a random base a and runs WITNESS(a, n), a quick check built on repeated squaring. If n is prime, no base is ever a witness. If n is composite, at least half of all bases are. So an answer of COMPOSITE is always right, and PRIME is wrong only if every base drawn was a liar.

Each round at least halves the chance of being fooled, so after s rounds the error is at most 2−s. You pick s, so you pick the error rate.

Try it: choose 91 = 7 · 13, set the slider to 1 round and press Run several times. About one run in six is fooled and says PRIME. Then raise s and watch both markers slide toward zero. 561 is a Carmichael number, the kind that fools simpler tests, yet MILLER-RABIN still catches it.

What the book says

A correct algorithm halts on every instance with the correct solution. “Contrary to what you might expect, incorrect algorithms can sometimes be useful, if you can control their error rate.”

The book points ahead: “We’ll see an example of an algorithm with a controllable error rate in Chapter 31 when we study algorithms for finding large prime numbers.” Ordinarily, however, the book concerns itself only with correct algorithms.

The same chapter's list of applications names public-key cryptography and digital signatures as core technologies of electronic commerce, based on numerical algorithms and number theory, which is why fast primality tests matter.

1.1 · what kinds of problems are solved by algorithms?

How alike are two strands of DNA?

The Human Genome Project set out to find the roughly 30,000 genes in human DNA and the order of its roughly 3 billion chemical base pairs. Every step needs sophisticated algorithms.

A strand of DNA is a string over four letters: A, C, G and T. One way to measure how alike two strands are is their longest common subsequence (LCS): the longest run of letters that appears in both, in the same order but not necessarily side by side. Trying every subsequence is hopeless, because a strand of n letters has 2n of them.

Dynamic programming (Chapter 14) fills a table instead. Cell c[i, j] holds the LCS length for the first i letters of X and the first j of Y, and needs only three neighbours: up-left plus one when the two letters match, otherwise the bigger of up and left. Here that is 36 cells instead of 64 candidates; for real strands the gap is astronomical.

Try it: press Step to fill one cell and see which neighbours it reads (blue). Play fills the table, then follows the arrows back from the corner to spell out an LCS. Tap a letter of Y along the top to mutate it, then play again.

What the book says

“Practical applications of algorithms are ubiquitous.” The first example: the Human Genome Project has made great progress toward identifying all the roughly 30,000 genes in human DNA, determining the sequences of the roughly 3 billion chemical base pairs that make up human DNA, storing this information in databases, and developing tools for data analysis. Each of these steps requires sophisticated algorithms.

The solutions are beyond the scope of the book, but many methods for these biological problems use its ideas. Dynamic programming (Chapter 14) is an important technique for several of them, particularly those that involve determining how similar two DNA sequences are. The savings are in time, both human and machine, and in money, as more information can be extracted by laboratory techniques.

X and Y on the machine are the first six bases of the two strands that Section 14.4 compares; the pseudocode is the book's LCS-LENGTH and PRINT-LCS.

Which pages mention a word?

The internet lets people everywhere find huge amounts of information, and clever algorithms are what let sites cope with it. Two of the book's examples: finding good routes for data to travel (Chapter 22), and a search engine that quickly finds the pages where some information lives (Chapters 11 and 32).

The slow way reads every page, sliding the word along the text one position at a time and comparing letter by letter: the naive string matcher. Every single search pays for the total length of all the pages.

A search engine does that reading once, ahead of time, and builds an index: for each word, the pages that contain it, kept in a hash table. A hash function turns the word into a slot number, so a search reads one short chain instead of every page.

Try it: pick a word and press Run with Scan every page, watching the comparison counter. Switch to Use an index and run the same word: one hash, then a comparison or two. Try tree, which no page contains.

What the book says

A padlock anyone can close, and one key opens

Electronic commerce depends on keeping credit card numbers, passwords and bank statements private. Its core technologies, public-key cryptography and digital signatures (Chapter 31), are built from number theory.

In RSA, Alice publishes a public key (e, n) and keeps a secret key (d, n). Anyone can lock a message M as C = Me mod n; only Alice can unlock it with Cd mod n. Swap the keys and you get a signature: only Alice can make σ = Md mod n, and anyone can check that σe mod n = M.

The work is raising a number to a power modulo n. MODULAR-EXPONENTIATION does it by repeated squaring: an even exponent is halved, an odd one drops by one, so a 1024-bit exponent needs at most 2047 calls instead of 21024 multiplications. The machine uses a toy key, n = 33, so every number fits on screen.

Try it: press Run to watch Bob lock a message and Alice unlock it. Each box is one recursive call: the calls go down to b = 0, then the answers come back up, and the memory strip grows and shrinks with them. Switch to Sign & verify and turn Tamper on: the message changes on the wire and the signature no longer checks out.

What the book says

Electronic commerce enables goods and services to be negotiated and exchanged electronically, and it depends on the privacy of personal information such as credit card numbers, passwords, and bank statements.

“The core technologies used in electronic commerce include public-key cryptography and digital signatures (covered in Chapter 31), which are based on numerical algorithms and number theory.”

The best plan sits on a corner

An oil company choosing where to drill, a candidate choosing where to buy ads, an airline putting crews on flights: each wants the best result from limited resources. When the goal and every limit are linear (sums of amounts times prices), the problem is a linear program.

With two decisions you can draw it. Each limit is a straight line with an allowed side, and the points on the allowed side of every line form the feasible region. All plans of equal value lie on one straight line. Slide that line toward better values: the last feasible point it touches is a corner of the region. That is why linear-programming methods only need to look at corners.

The machine uses the small two-variable example from the book's Chapter 29: maximize x₁ + x₂ under three limits, with x₁ and x₂ not negative.

Try it: drag objective value up and watch the dashed line cross the region, shrink to one point at 8, then miss it. Press Check every corner: every pair of boundary lines meets at one point, and only the feasible ones count. Then pick 2x₁ + x₂: a whole edge ties for best, and both of its ends are corners.

What the book says

“Manufacturing and other commercial enterprises often need to allocate scarce resources in the most beneficial way.” An oil company might wish to know where to place its wells to maximize its expected profit. A political candidate might want to decide where to spend money on campaign advertising to maximize the chances of winning an election. An airline might wish to assign crews to flights in the least expensive way possible, making sure each flight is covered and that government regulations on crew scheduling are met. An internet service provider might wish to decide where to place additional resources to serve its customers more effectively.

“All of these are examples of problems that can be solved by modeling them as linear programs, which Chapter 29 explores.” Although some details of these examples are beyond the scope of the book, it gives underlying techniques that apply to these problems and problem areas.

The shortest way across town

A road map marks the distance between every pair of neighbouring crossings, and you want the shortest drive from one crossing to another. You could list every route that never visits a crossing twice and keep the shortest. On six crossings that is 13 routes. A 6 × 6 grid of streets already has 1,262,816 routes from one corner to the opposite one.

Model the map as a graph: crossings are vertices, roads are edges with lengths. Dijkstra's algorithm (the book's Chapter 22) never lists routes. It keeps a best-known distance d for every vertex, always settles the closest unsettled vertex next, and relaxes its roads: if going through it makes a neighbour closer, it lowers that neighbour's d.

Try it: press Play on Try every route and watch the counter. Switch to Dijkstra and press Step: tan vertices wait in the queue Q, blue ones are settled in S, and the blue roads say where each best distance came from. The winning route, A–C–B–D–E–F, uses five roads, not the fewest.

What the book says

You have a road map on which the distance between each pair of adjacent intersections is marked, and you wish to determine the shortest route from one intersection to another. “The number of possible routes can be huge, even if you disallow routes that cross over themselves.”

You can start by modeling the road map (itself a model of the actual roads) as a graph, met in Part VI and Appendix B. In this graph, you wish to find the shortest path from one vertex to another. “Chapter 22 shows how to solve this problem efficiently.”

The internet uses the same idea: finding good routes on which the data travels is one of the problems that make essential use of algorithms.

Every part before the parts that use it

A bicycle design is a library of parts, and parts are made of other parts: spokes, a rim and a bolt go into a wheel; wheels and a frame go into the bike. To list the parts in an order where each one appears before anything that uses it, you could try every order and check it. Six parts already have 6! = 720 orders, and only 18 of them work.

The factorial grows faster than any exponential, so that plan dies quickly. A topological sort (the book's Chapter 20) does it in one pass: a depth-first search walks from each part to the parts that use it, and when a part has nothing left to explore it is finished and goes onto the front of a list. Whatever uses it finished earlier, so it already sits further back.

Try it: press Play on Try every order and watch the red pair that breaks each bad order. Switch to Topological sort and Step: each part turns gray when discovered and green when finished, gets its discover/finish times, and drops onto the front of the list. The memory strip shows one dfs_visit frame per level of recursion.

What the book says

Given a mechanical design in terms of a library of parts, where each part may include instances of other parts, list the parts in order so that each part appears before any part that uses it.

If the design comprises n parts, there are n! possible orders. “Because the factorial function grows faster than even an exponential function, you cannot feasibly generate each possible order and then verify that, within that order, each part appears before the parts using it (unless you have only a few parts).”

“This problem is an instance of topological sorting, and Chapter 20 shows how to solve this problem efficiently.”

Tell the two kinds apart

A doctor has a new scan of a tumor and many old scans whose outcome is known: some cancerous, some benign. Tumors of one kind tend to look like each other. So group the old scans by similarity, see which group the new scan falls into, and that group's known outcomes say which is more likely.

Grouping by similarity is clustering. Picture each scan as a point, here with two toy measurements: size and irregularity. Lloyd's procedure for k-means (the book's Chapter 33) puts k centers among the points and repeats two moves: give every point to its nearest center, then move every center to the centroid (average position) of its points. It stops when no point changes group.

Try it: press Step to alternate between “assign” and “move centers” and watch f, the total squared distance to the centers, fall. Both starting centers sit among the benign scans, yet three rounds sort it out. Then press New image. New start picks two random starting points, as the book does.

What the book says

A doctor needs to determine whether an image represents a cancerous tumor or a benign one. The doctor has available images of many other tumors, some of which are known to be cancerous and some of which are known to be benign.

“A cancerous tumor is likely to be more similar to other cancerous tumors than to benign tumors, and a benign tumor is more likely to be similar to other benign tumors. By using a clustering algorithm, as in Chapter 33, the doctor can identify which outcome is more likely.”

1.1 · what kinds of problems are solved by algorithms?

Short codes for common letters

A text file stores every character as the same number of bits. But in abracadabra the letter a turns up five times and d only once. Give a a 1-bit code and the rare letters longer ones, and the whole file shrinks. One family of methods, such as LZW, hunts for repeating runs of characters instead; this machine shows the other idea.

Huffman coding (the book's Chapter 15) builds the codes as a tree. Put every character in a min-priority queue keyed by how often it occurs, then repeat: take out the two least frequent, join them under a new node whose count is their sum, and put that node back. Reading the tree from the top, left is 0 and right is 1. Since no code is the start of another, the bits decode without separators.

Try it: press Step and watch the two smallest leave the queue and become a subtree. At the end, compare the bits with a 3-bit fixed code. Then try the book's file: 100,000 characters, a to f. In Rust, every merge moves two nodes into Boxes on the heap, owned by their new parent.

What the book says

You need to compress a large file containing text so that it occupies less space. Many ways to do so are known, including “LZW compression,” which looks for repeating character sequences.

Chapter 15 studies a different approach, “Huffman coding,” which encodes characters by bit sequences of various lengths, with characters occurring more frequently encoded by shorter bit sequences.

1.1 · what kinds of problems are solved by algorithms?

Thousands of answers, a handful that work

Look back over the book's list of problems and two traits stand out. First, each one has a huge number of candidate solutions, and almost all of them are wrong. The hard part is finding one that works, or the best one, without checking every candidate.

A toy version: a courier van should leave the depot carrying exactly 20 kg, and loading is quicker with fewer parcels. Each parcel is either in or out, so n parcels give 2n possible loads. Brute force checks every one. One more parcel doubles the work; 30 parcels would already mean more than a billion loads.

Second, these problems matter in practice. Shortest paths are the easiest example: a trucking company pays less for labor and fuel on shorter routes, an internet router needs them to deliver messages quickly, and a navigation app finds the drive from New York to Boston.

Try it: press Play and watch every dot get checked. A green dot fits exactly, a grey one does not, and the ring marks the best load so far. Drag n to 8 and play again: four times as many dots. In Rust, the same search is one generic function that takes closures.

What the book says

The lists of problems are far from exhaustive, but they exhibit two characteristics common to many interesting algorithmic problems. First, “They have many candidate solutions, the overwhelming majority of which do not solve the problem at hand.” Finding one that does, or the best one, without explicitly examining each possible solution, can be quite a challenge.

Second, “They have practical applications.” Finding the shortest path provides the easiest examples. A transportation firm, such as a trucking or railroad company, has a financial interest in shorter paths through a road or rail network, because they mean lower labor and fuel costs. A routing node on the internet might need the shortest path to route a message quickly, and a person driving from New York to Boston might want directions from a navigation app.

Hearing the notes inside a wave

Not every problem comes with a pile of candidates to check. Record a sound and you get samples: numbers taken at regular moments. Which pure tones, and how strong, add up to that sound? The discrete Fourier transform (DFT) answers it. It turns the time domain into the frequency domain, describing the signal as a weighted sum of sine waves.

Done directly, n samples cost about n² multiplications. The fast Fourier transform (FFT) of Chapter 30 splits the samples into even and odd positions, transforms each half the same way, then glues the halves back with one multiply, one add and one subtract per pair, a step called a butterfly. That is about n lg n work instead of n².

Fourier transforms sit at the heart of signal processing, and they also help with data compression and with multiplying huge polynomials and integers.

Try it: mix a signal with the three sliders, then press Transform. The bars rise two at a time, one pair per pass of the loop. Switch to Inside the recursion and press Step: eight samples split down to single values, then butterflies combine them back up. In Rust, a + b works on complex numbers because the program implements the Add trait for them.

What the book says

“Not every problem solved by algorithms has an easily identified set of candidate solutions.” Given numerical values representing samples of a signal taken at regular time intervals, the discrete Fourier transform converts the time domain to the frequency domain: it approximates the signal as a weighted sum of sinusoids, producing the strength of various frequencies which, when summed, approximate the sampled signal.

Besides lying at the heart of signal processing, discrete Fourier transforms have applications in data compression and in multiplying large polynomials and integers. Chapter 30 gives an efficient algorithm for this problem, the fast Fourier transform, commonly called the FFT, and sketches out the design of a hardware FFT circuit.

1.1 · data structures

Same keys, two different shelves

A data structure is a way to store and organize data so that reading and changing it is easy. Picking the right one is a big part of designing an algorithm, because none of them is good at everything.

Put the keys 9, 16, 4, 1 in an array and they sit side by side in one block of memory, so the third item is one quick jump away. But to squeeze a new key in at the front, every item has to shuffle one place right. Put them in a linked list and each key lives in its own node, anywhere in memory, holding a pointer to the next. Adding a node at the front changes two pointers, however long the list. Finding the third item, though, means following pointers from the start.

Try it: pick an operation and press Play, then compare the two step counters. Search is a tie; inserting at the front favors the list; reading the 3rd item favors the array. Switch to Rust and watch the memory strip: the array is one block, while each list node is a separate Box on the heap, chained by pointers.

What the book says

The book presents several data structures. “A data structure is a way to store and organize data in order to facilitate access and modifications.” Using the appropriate data structure or structures is an important part of algorithm design.

“No single data structure works well for all purposes, and so you should know the strengths and limitations of several of them.”

1.1 · technique

When there is no recipe, build one

You can use the book like a cookbook, but one day you will meet a problem with no published recipe. So it also teaches techniques: ways to design an algorithm yourself, show that it gives the correct answer, and work out how fast it is.

Three of them are in this machine. Divide-and-conquer (Chapters 2 and 4) splits a problem into halves, solves each half the same way, and combines the answers. Dynamic programming (Chapter 14) notices the same small problems coming up again and again, and solves each one only once. Amortized analysis (Chapter 16) judges a whole sequence of operations, where a rare expensive step is paid for by many cheap ones.

Other chapters attack particular problems instead: medians in Chapter 9, minimum spanning trees in Chapter 21, maximum flow in Chapter 24.

Try it: in Divide and conquer, play merge sort and count the levels: 8 items need lg 8 = 3. In Dynamic programming, run CUT-ROD, then the MEMOIZED-CUT-ROD tab, and compare the calls. In Amortized analysis, press Insert until the table doubles: one cost bar spikes, but the average never passes 3, and the memory strip shows the old block being freed.

What the book says

Although you can use the book as a “cookbook” for algorithms, you might someday encounter a problem for which you cannot readily find a published algorithm (many of the book's exercises and problems, for example). The book teaches techniques of algorithm design and analysis so that you can develop algorithms on your own, show that they give the correct answer, and analyze their efficiency.

Some chapters address specific problems, such as finding medians and order statistics in Chapter 9, computing minimum spanning trees in Chapter 21, and determining a maximum flow in a network in Chapter 24. Other chapters introduce techniques, such as divide-and-conquer in Chapters 2 and 4, dynamic programming in Chapter 14, and amortized analysis in Chapter 16.

1.1 · hard problems

The delivery van nobody can route fast

Most of the book is about fast algorithms. For some problems, though, nobody knows any algorithm that finishes in a reasonable time. The best-known family of them is called NP-complete.

A delivery company loads its vans at a depot each morning. Every van visits its stops and must end the day back at the depot. Picking the order of stops with the shortest round trip is the traveling-salesperson problem, and it is NP-complete. Trying every order works for 6 stops (360 tours), but each extra stop multiplies the count. Yet the problem looks a lot like an easy one: the shortest path between just two stops has a fast algorithm (Chapter 22).

Once you know a problem is NP-complete, stop hunting for a perfect fast algorithm. Build an approximation algorithm instead: fast, and provably close to the best. For tours, one walks around a minimum spanning tree and is never worse than twice the best.

Try it: press Play in Try every tour and watch the best tour improve; slide stops to 7 and the count jumps to 2,520. Then switch to Approximate. Drag k to ask the yes/no version: one short tour proves “yes” at once, but “no” needs every tour checked, or the approximation's guarantee.

What the book says

Most of the book is about efficient algorithms, but there are some problems for which no algorithm is known that runs in a reasonable amount of time. Chapter 34 studies an interesting subset of them, known as NP-complete.

Why are they interesting? First, no efficient algorithm for an NP-complete problem has ever been found, yet nobody has ever proven that one cannot exist. Second, the set of NP-complete problems has “the remarkable property that if an efficient algorithm exists for any one of them, then efficient algorithms exist for all of them.” Third, several NP-complete problems are similar, but not identical, to problems with known efficient algorithms: a small change to the problem statement can cause a big change to the efficiency of the best known algorithm.

Some arise surprisingly often in real applications. If you can show a problem is NP-complete, you can spend your time developing an efficient approximation algorithm, one that gives a good, but not necessarily the best possible, solution. The book's example is a delivery company with a central depot whose trucks must end each day back at the depot: finding the order of stops with the lowest overall distance is the traveling-salesperson problem, which is NP-complete. Under certain assumptions, efficient algorithms compute overall distances close to the smallest possible (Chapter 35).

Strictly, only decision problems, those with a yes/no answer, can be NP-complete. The decision version of the traveling-salesperson problem asks whether there exists an order of stops whose distance totals at most a given amount.

1.1 · alternative computing models

More cores, not more gigahertz

For years programs got faster for free: every new chip ran at a higher clock speed. That stopped. Push the clock up and the heat on the chip climbs faster than the speed does, because power density grows superlinearly with clock speed. Past some point the chip would melt.

So chip makers put several processing cores on one chip: several sequential computers side by side, a kind of parallel computer. A program written as one long list of steps still uses only one of them. To use the others, the algorithm itself has to say which work may happen at the same time.

Chapter 26's task-parallel model does that with two words. spawn means “start this call and don't wait for it”; sync means “now wait for everything I spawned”. P-FIB uses them to compute Fibonacci numbers. Its work is every step added up; its span is the longest chain of steps that must run one after another. No number of cores can finish faster than the span.

Try it: in Clock wall, drag the clock past 4 GHz and watch the heat, then bring it back and add cores instead. In P-FIB(4) on cores, press Step: each core (one colour each) takes a ready strand. Try 1, 2 and 4 cores: 17 steps, then fewer, but never fewer than 8.

What the book says

For many years processor clock speeds rose at a steady rate. Physical limitations are a fundamental roadblock: “because power density increases superlinearly with clock speed, chips run the risk of melting once their clock speeds become high enough.”

To perform more computations per second, chips are designed with several processing cores. “We can liken these multicore computers to several sequential computers on a single chip.” They are a type of parallel computer, and to get the best performance from them we need to design algorithms with parallelism in mind.

Chapter 26 presents a model for task-parallel algorithms, which take advantage of multiple processing cores. The model has advantages from both theoretical and practical standpoints, and many modern parallel-programming platforms embrace something similar to it.

1.1 · alternative computing models

Deciding before the future arrives

Most algorithms in the book get their whole input before they start. Many real ones don't. A data center has to place each job as it arrives. The internet has to route traffic without knowing what comes next. An emergency room has to decide whom to treat first without knowing who walks in later. Algorithms that get their input bit by bit, over time, are online algorithms.

Chapter 27 starts with a choice you have made yourself. Your office is k floors up. The stairs take k minutes. The elevator climbs in 1 minute, but it reaches the ground floor only after m minutes, and you don't know m. A seer who knows m waits if m ≤ k − 1 and walks otherwise.

An online strategy is judged by its competitive ratio: its time divided by the seer's, in the worst case over every possible m. Always walking is k times too slow when the elevator was already there. Always waiting is B/k times too slow when it takes the longest it can, B − 1 minutes. Waiting k minutes and then walking is never worse than 2×.

Try it: pick a strategy and press Call the elevator a few times: the dot shows how you did against the seer. Then Worst case, and Try every m to draw the whole curve: its top is the competitive ratio. The book's numbers are k = 10, B = 300.

What the book says

Most of the examples in the book assume all of the input data are available when an algorithm begins running, and much of the work in algorithm design makes the same assumption. For many important real-world examples, however, the input arrives over time, and the algorithm must decide how to proceed without knowing what data will arrive in the future.

In a data center, jobs are constantly arriving and departing, and a scheduling algorithm must decide when and where to run a job. Traffic must be routed in the internet based on the current state. Hospital emergency rooms make triage decisions without knowing when other patients will arrive and what treatments they will need.

“Algorithms that receive their input over time, rather than having all the input present at the start, are online algorithms,” which Chapter 27 examines.

1.2 · algorithms as a technology

Even an infinitely fast computer needs the right answer

Picture a computer that runs any program instantly and has free memory. Would algorithms still matter? Yes: you would still need a method that stops, and stops with the right answer. Beyond that, any correct method would do, so you would pick the easiest one to write.

Real computers are fast, not infinitely fast. Time is a bounded resource, and unlike money, time spent never comes back. Memory is cheap but neither infinite nor free. So you choose algorithms that use both well, and often you trade one for the other.

The machine asks one question: does a list hold the same number twice? Nested loops compare every pair: slow, but no extra memory. Sort first and duplicates end up side by side. A hash set remembers every number it has seen: fast, but it costs memory. Neighbors only skips the sort: fast, frugal, and wrong.

Try it: press Play in each mode and watch the memory strip: only the hash set grows a table on the heap. Then drag n up to millions and switch on Infinitely fast: every time bar drops to zero, but the memory bars stay, and the wrong method stays wrong.

What the book says

If computers were infinitely fast and computer memory were free, would you have any reason to study algorithms? Yes, if for no other reason than that you would still like to be certain that your solution method terminates and does so with the correct answer.

“If computers were infinitely fast, any correct method for solving a problem would do.” You would want the implementation to follow good software engineering practice (well designed and documented), but you would most often use whichever method was the easiest to implement.

Computers may be fast, but they are not infinitely fast, so computing time is a bounded resource, which makes it precious: “you can get back money after you spend it, but once time is spent, you can never get it back.” “Memory may be inexpensive, but it is neither infinite nor free.” “You should choose algorithms that use the resources of time and space efficiently.”

Is any number there twice?
1.2 · efficiency

n against lg n: the constant can't save you

Two algorithms can solve the same problem and still differ in speed far more than two computers do. Chapter 2's insertion sort takes about c1n² steps to sort n items; merge sort takes about c2n lg n. The constant factors c1 and c2 depend on the machine and the code, not on n, and insertion sort's is usually smaller.

Write the costs as c1·n·n and c2·n·lg n. Where insertion sort has a factor n, merge sort has lg n, which is tiny: about 10 when n is 1,000 and only about 20 when n is 1,000,000. So for small inputs insertion sort usually wins, but there is always a crossover point past which merge sort is faster, however much smaller c1 is.

Merge sort pays for its speed in memory: its MERGE step copies the two halves into new arrays L and R. Insertion sort works inside the array it was given.

Try it: in Crossover, drag c2 up as far as it goes: the crossover moves right, but it never disappears. The two exercise buttons answer Exercises 1.2-2 and 1.2-3. In Race, press Play: on a dozen numbers insertion sort finishes first, and the memory strip shows merge sort's L and R appear on the heap and get freed.

What the book says

“Different algorithms devised to solve the same problem often differ dramatically in their efficiency. These differences can be much more significant than differences due to hardware and software.”

Insertion sort takes time roughly equal to c1n² to sort n items, and merge sort roughly c2n lg n, where lg n stands for log2 n and neither constant depends on n. Insertion sort typically has the smaller constant factor, so that c1 < c2. The constant factors can have far less of an impact on the running time than the dependence on the input size n.

When n is 1000, lg n is approximately 10, and when n is 1,000,000, lg n is approximately only 20. Insertion sort usually runs faster for small input sizes, but once n is large enough, merge sort's advantage of lg n versus n more than compensates. “No matter how much smaller c1 is than c2, there is always a crossover point beyond which merge sort is faster.”

Exercise 1.2-2 asks for which n insertion sort in 8n² steps beats merge sort in 64n lg n steps; Exercise 1.2-3 asks for the smallest n at which 100n² runs faster than 2n.

Where the curves cross
1.2 · efficiency

A race car with a slow recipe

Two computers must sort the same ten million numbers. Computer A is a race car: ten billion instructions a second, a thousand times faster than computer B. A runs insertion sort, hand-written in machine language by the best programmer alive, and needs 2n² instructions. B runs merge sort, written by an average programmer with a sloppy compiler, and needs 50 n lg n.

A sounds unbeatable. But for n = 10 million, A has 2 × 10¹⁴ instructions to do and B only about 1.2 × 10¹⁰. A works for more than five and a half hours, B for under twenty minutes. A faster machine only divides the time by a constant. The algorithm decides how fast the time grows as n grows, and growth wins.

The bars use a logarithmic time scale: equal steps along the axis multiply the time, so a millisecond and a century fit on one line.

Try it: press Race for the book's ten million numbers, then pick 100 million. Drag n down until A wins again: that is the crossover point. Then give A an even faster processor and see how little the crossover moves.

What the book says

Computer A executes 10 billion instructions per second and runs insertion sort, coded in machine language by “the world’s craftiest programmer,” needing 2n² instructions. Computer B executes only 10 million instructions per second, so A is 1000 times faster in raw computing power, and runs merge sort written by an average programmer in a high-level language with an inefficient compiler, needing 50n lg n instructions. Ten million eight-byte integers occupy about 80 megabytes.

Sorting 10 million numbers, A takes 2 · (10⁷)² / 10¹⁰ = 20,000 seconds, more than five and a half hours, while B takes 50 · 10⁷ lg 10⁷ / 10⁷ ≈ 1163 seconds, under 20 minutes. “By using an algorithm whose running time grows more slowly, even with a poor compiler, computer B runs more than 17 times faster than computer A!”

For 100 million numbers, insertion sort takes more than 23 days and merge sort under four hours. That size is not exotic: there are more than 100 million web searches every half hour and more than 100 million emails sent every minute. “In general, as the problem size increases, so does the relative advantage of merge sort.”

1.2 · algorithms and other technologies

Algorithms all the way down

Think of a travel app: type two addresses, get a route on a map. It needs fast hardware, a friendly screen, a network and well-organized code. Those are technologies too, so do algorithms still matter? Yes. The app itself needs algorithms to find a route, draw the map and turn a street address into a point.

Even an app with no clever code of its own stands on algorithms. The chip it runs on was designed with them. The screen toolkit, the network that routes its messages, the compiler that translated its source code: all full of algorithms. Treat algorithms as a technology, like hardware.

One small, real example: a street block is numbered 1 to 99, and the map knows only where its two corners are. To place No. 37, the app interpolates: 37 is 36/98 of the way along, so the pin goes 36/98 of the way from one corner to the other.

Try it: press Play to send a trip request down through the layers, or tap a layer to look inside. Then switch to Interpolate an address, drag the house number, and try one past the end of the block: the Rust version answers None.

What the book says

“You should consider algorithms, like computer hardware, as a technology.” Total system performance depends on choosing efficient algorithms as much as on choosing fast hardware, and algorithms advance as quickly as other computer technologies.

Other technologies include advanced computer architectures and fabrication technologies, easy-to-use graphical user interfaces (GUIs), object-oriented systems, integrated web technologies, fast networking, machine learning, and mobile devices. A web-based service that determines how to travel from one location to another relies on fast hardware, a GUI, wide-area networking and possibly object orientation. It also requires algorithms for finding routes (probably using a shortest-path algorithm), rendering maps, and interpolating addresses.

Even an application without algorithmic content at the application level relies heavily on algorithms: the hardware design used algorithms, the design of any GUI relies on them, routing in networks relies heavily on them, and code in a language other than machine code was processed by a compiler, interpreter, or assembler, “all of which make extensive use of algorithms.”

1.2 · algorithms and other technologies

Learned rule or designed recipe?

Machine learning skips designing the steps. Show it labeled examples, and it infers a rule from the data. That sounds like the end of studying algorithms, but the learning itself is an algorithm: here it is a loop that tries 21 cut-off values and keeps the one with the fewest mistakes on the examples.

The task is one people understand completely: is this list sorted? The learner sees one number per list, the share of neighbouring pairs already in order, and learns a threshold. The designed algorithm checks every neighbouring pair and stops at the first one out of order. It is right every time, because it was built from an understanding of the problem.

The learned rule passes its training examples and still calls a nearly sorted list sorted. Learning shines where nobody knows the right steps, such as recognizing faces or translating languages. When people do know them, a designed algorithm usually wins.

Try it: press Train and watch the threshold sweep, then Test. Add a few tricky lists: sorted lists with one neighbouring pair swapped. The learned rule keeps falling for them; the designed one never does.

What the book says

Machine learning “can be thought of as a method for performing algorithmic tasks without explicitly designing an algorithm, but instead inferring patterns from data and thereby automatically learning a solution.” It may seem to make learning about algorithms obsolete, but the opposite is true: “Machine learning is itself a collection of algorithms, just under a different name.”

The successes of machine learning seem to be mainly for problems where humans do not really understand what the right algorithm is, such as computer vision and automatic language translation. For problems humans understand well, like most in the book, efficient algorithms designed for the specific problem are typically more successful than machine-learning approaches.

Data science extracts knowledge and insights from structured and unstructured data, using methods from statistics, computer science, and optimization; the design and analysis of algorithms is fundamental to it. And as computers grow, we solve larger problems, which is exactly where differences in efficiency become prominent. “Having a solid base of algorithmic knowledge and technique is one characteristic that defines the truly skilled programmer.”

How big a job fits in a second? In a century?

The chapter ends with a table to fill in. Each row is an algorithm whose running time is f(n) microseconds. Each column is a time budget, from one second to one century. Each cell asks: what is the largest n that finishes within the budget?

Two rows can be solved with algebra. lg n ≤ t means n ≤ 2t, and √n ≤ t means n ≤ t². For the rest, the machine uses exponential search: keep doubling n until f(n) is too big, then binary-search the gap between the last two guesses. About 2 lg n tries find the answer, even when it is in the trillions.

Read the table down a column and the lesson of the chapter appears. With a whole century, a 2n algorithm handles 51 items and an n! algorithm only 17. An n lg n algorithm handles 62,746 items in a single second.

Try it: tap a cell, then press Compute and watch the doublings and halvings follow the highlighted lines. Try n in a century (52 doublings) and n! in a second (four). Fill the table does every cell at once; switch to Rust to see the same table printed by the program.

What the book says

Problem 1-1, Comparison of running times: “For each function f(n) and time t in the following table, determine the largest size n of a problem that can be solved in time t, assuming that the algorithm to solve the problem takes f(n) microseconds.”

The rows are lg n, √n, n, n lg n, n², n³, 2n and n!; the columns are 1 second, 1 minute, 1 hour, 1 day, 1 month, 1 year and 1 century. The book leaves the lengths of a month, a year and a century to the reader. Here a month is 30 days, a year 365 days and a century 100 such years.

Words to know

The book's words from this chapter, in plain language.

algorithm
A well-defined procedure that turns any valid input into the right output in a finite amount of time.
computational problem
A statement of which output each input should get, for inputs of any size.
instance
One particular input of a problem, such as ⟨31, 41, 59, 26, 41, 58⟩ for sorting.
permutation
The same items in a different order. A sorted output must be a permutation of the input.
correct / halts
An algorithm is correct if it halts (finishes in finite time) on every instance with the right answer.
data structure
A way to store and organize data so the operations you need are quick.
graph / shortest path
Points joined by weighted links, and the cheapest way from one point to another.
topological sort
An order of tasks or parts in which everything comes before whatever uses it.
dynamic programming
Solving each overlapping subproblem once and keeping the answer in a table.
linear program
Best value of a linear goal under a list of linear limits, such as a budget.
NP-complete
A family of problems with no known efficient algorithm; a fast algorithm for one would give one for all.
approximation algorithm
A fast algorithm that finds a good, not necessarily best, solution.
decision problem
A problem whose answer is yes or no. Only these can be NP-complete.
multicore / task-parallel
Several processors on one chip, and algorithms written to keep them all busy.
online algorithm
One that gets its input bit by bit over time and must act before it knows the rest.
efficiency
How much time and memory an algorithm uses as its input grows.
lg n
log₂ n: how many times you can halve n before reaching 1. lg 1,000,000 ≈ 20.
constant factor
The c in c·n²: it depends on the machine and the code, not on n.
crossover point
The input size past which the slower-growing algorithm wins, whatever the constants.
machine learning
Algorithms that infer patterns from data instead of following steps someone designed for the task.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

ownership
Every value has one owner. When the owner goes out of scope, the value is freed. No garbage collector.
&T / &mut T
A borrow: a reference that lends a value without moving it. Many readers or one writer, never both.
slice &[T]
A borrowed view of a run of items: a pointer plus a length. &v[2..5] is three items of v.
Vec<T>
A growable array. Its pointer, length and capacity live on the stack; the items live on the heap.
Box<T>
A smart pointer that owns one value on the heap. Lets a type contain itself, like a tree node.
enum + match
A type that is exactly one of several variants, each with its own data. match must handle every one.
Option<T>
Some(value) or None. Rust's replacement for null, checked by the compiler.
trait
A set of methods a type promises to have, like Ord for comparing or Debug for printing.
generics
Code written once for many types, such as fn f<T: Ord>(x: &[T]), compiled separately for each.
closure
An unnamed function that can use variables from where it was written: |x| x * k.
usize / u64 / f64
Exact-size numbers. usize indexes arrays and can never be negative.
stack / heap
The stack holds each call's local variables and is freed on return; the heap holds data that outlives a call or has a size known only at run time.
