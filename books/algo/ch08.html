Sorting in Linear Time

Every sort so far learned the order of its input by comparing two elements at a time, and this chapter proves that any such sort needs Ω(n lg n) comparisons in the worst case. Then it gets under that floor three times: counting sort, radix sort and bucket sort use the values themselves, and sort in linear time when the input fits their assumptions.

“In fact, no comparisons between input elements occur anywhere in the code.” — Cormen, Leiserson, Rivest & Stein

8.1 · the decision-tree model

Every sort is a game of questions

Insertion sort, merge sort, heapsort and quicksort all learn about their input the same way: by asking yes/no questions of one kind: is ai ≤ aj? They never look at a value for any other reason. Sorts like that are comparison sorts, and the orders they produce depend only on the answers.

Write down every question one such sort can ask on inputs of size n, and which question it asks after each answer, and you get a decision tree. An internal node i:j compares ai with aj (go left if ≤, right if >). A leaf is a permutation ⟨π(1), …, π(n)⟩ that says aπ(1) ≤ aπ(2) ≤ ⋯ ≤ aπ(n). Running the sort on one input is one path from the root to a leaf. Moving data around costs nothing in this model: only the questions count.

Three distinct numbers can arrive in 3! = 6 orders, and a correct sort has to produce each one, so each of the 6 permutations must sit at a leaf that some input actually reaches. Insertion sort's tree has exactly 6 leaves. Two inputs get sorted after 2 questions, the other four need 3. The longest path, the height of the tree, is the sort's worst-case number of comparisons.

Try it: press Step to follow the book's input ⟨6, 8, 5⟩ from the root, one question at a time, or Play. Then tap any leaf: the input changes to one that ends there. Switch to All 3! inputs and press Play to send all six orders down the tree, and watch each one land on its own leaf. In Rust the tree is a recursive enum, its children in Boxes, walked with match.

What the book says

A comparison sort uses only comparisons between elements to gain order information about an input sequence ⟨a1, a2, …, an⟩. Given ai and aj, it performs one of the tests <, ≤, =, ≥ or >. “It may not inspect the values of the elements or gain order information about them in any other way.”

Because the goal is a lower bound, the section assumes without loss of generality that all input elements are distinct: a lower bound for distinct elements also holds when they may or may not be distinct. Then tests for equality are useless, and the four remaining tests all give the same information, so all comparisons are taken to have the form ai ≤ aj.

A decision tree is a full binary tree (each node is either a leaf or has both children) that represents the comparisons a particular sorting algorithm performs on an input of a given size; control, data movement and every other aspect of the algorithm are ignored. Each internal node is annotated i:j with 1 ≤ i, j ≤ n, each leaf by a permutation ⟨π(1), π(2), …, π(n)⟩, and the indices always refer to the original positions of the elements. Figure 8.1 is the tree for insertion sort on three elements; its highlighted path, for ⟨a1 = 6, a2 = 8, a3 = 5⟩, ends at the leaf ⟨3, 1, 2⟩.

Running the algorithm is tracing a simple path from the root down to a leaf: the left subtree dictates the comparisons that follow once ai ≤ aj, the right subtree those that follow when ai > aj. Because any correct sorting algorithm must be able to produce each permutation of its input, each of the n! permutations must appear as at least one leaf, and each such leaf must be reachable by an actual execution. The book considers only trees in which each permutation appears as a reachable leaf.

8.1 · a lower bound for the worst case

Not enough leaves, wrong answers

The worst-case number of comparisons a comparison sort makes is the longest path from the root of its decision tree to a leaf: the tree's height h. So a lower bound on the height of every possible decision tree is a lower bound for every comparison sort, including ones nobody has invented yet.

Counting leaves gives that bound. All n! orders need a reachable leaf, so the tree has l ≥ n! leaves. A binary tree of height h has at most 2h leaves. So n! ≤ l ≤ 2h, and taking logarithms, h ≥ lg(n!). That sum, lg 1 + lg 2 + ⋯ + lg n, is at most n lg n and at least (n/2) lg(n/2), because its top half of terms are each at least lg(n/2). So lg(n!) = Θ(n lg n): any comparison sort needs Ω(n lg n) comparisons in the worst case (Theorem 8.1).

Merge sort and heapsort sort in O(n lg n) time, which matches the bound, so they are asymptotically optimal comparison sorts (Corollary 8.2). No comparison sort is faster by more than a constant factor. A sort that wants to be faster has to learn about its input some other way, and that is the rest of this chapter.

Try it: the top bars compare n! with 2h on a log scale. Drag h below the dashed line: the tree has fewer leaves than there are orders, so some order shares a leaf and comes out wrong. Press Play to add up lg k bar by bar; the run ends by setting h to the smallest height that works. Slide n to 16 and compare merge sort's worst case with that minimum in the counters. In Rust, see how checked_mul notices that 21! no longer fits in a u64.

What the book says

The length of the longest simple path from the root of a decision tree to any of its reachable leaves represents the worst-case number of comparisons that the sorting algorithm performs; so the worst-case number of comparisons equals the height of its decision tree. A lower bound on the heights of all decision trees in which each permutation appears as a reachable leaf is therefore a lower bound on the running time of any comparison sort algorithm.

Theorem 8.1: “Any comparison sort algorithm requires Ω(n lg n) comparisons in the worst case.” Proof: consider a decision tree of height h with l reachable leaves for a comparison sort on n elements. Each of the n! permutations appears as one or more leaves, so n! ≤ l. A binary tree of height h has no more than 2h leaves, so n! ≤ l ≤ 2h. Taking logarithms, h ≥ lg(n!), since lg is monotonically increasing, and lg(n!) = Ω(n lg n) by equation (3.28).

Corollary 8.2: “Heapsort and merge sort are asymptotically optimal comparison sorts.” Their O(n lg n) upper bounds match the Ω(n lg n) worst-case lower bound. As the chapter's introduction puts it, no comparison sort exists that is faster by more than a constant factor.

8.2 · counting sort

Count first, then drop each item in its slot

Suppose every key is a small whole number, from 0 to k. Then you don't need to compare anything. If 17 elements are less than or equal to x, then x belongs in output position 17. Counting sort works out that number for every value and writes each element straight into its place.

It takes three passes. Count how many times each value occurs, in an array C[0 : k]. Turn the counts into running totals, so C[i] is the number of elements ≤ i: the last slot that value i may use. Then walk A from the end, put each element at B[C[key]] and step C[key] down by one, so the next equal key lands just before it. The loops cost Θ(k), Θ(n), Θ(k) and Θ(n): Θ(n + k) in all, which is Θ(n) when k = O(n). No comparison of two elements happens anywhere, so the Ω(n lg n) bound doesn't apply.

Walking backwards makes counting sort stable: equal keys come out in the order they went in. With bare numbers you can't tell, but real keys carry satellite data, and radix sort (next) depends on it. The letters on the cells are that satellite data.

At the end, check the letters: the two 0s come out as d, g and the three 3s as c, f, h, their input order. Now switch to Forward · Ex. 8.2-3: the output is still sorted, but every tie comes out reversed. What the book says

Counting sort assumes that each of the n input elements is an integer in the range 0 to k. It runs in Θ(n + k) time, so when k = O(n) it runs in Θ(n) time. It first determines, for each input element x, the number of elements less than or equal to x, and uses that to place x directly into its position in the output array; the scheme is modified slightly so that several elements with the same value don't all end up in the same position.

COUNTING-SORT takes A[1 : n], the size n and the limit k, returns the sorted output in B[1 : n] and uses C[0 : k] for temporary working storage. Lines 2–3 set C to zeros, lines 4–5 count each value, lines 7–8 keep a running sum, and lines 11–13 make another pass over A, in reverse, placing each A[j] in B. Decrementing C[A[j]] makes the previous element with the same value, if any, go to the position immediately before A[j]. The loops take Θ(k), Θ(n), Θ(k) and Θ(n) time, Θ(k + n) overall.

Counting sort beats the Ω(n lg n) lower bound because it is not a comparison sort. “In fact, no comparisons between input elements occur anywhere in the code.” Instead it uses the actual values of the elements to index into an array.

An important property is that counting sort is stable: elements with the same value appear in the output array in the same order as they do in the input array. Stability normally matters only when satellite data are carried around with the element being sorted, but counting sort's stability matters for another reason: radix sort uses it as a subroutine and needs it to be stable. Exercise 8.2-3 rewrites the header of line 11 to run j from 1 up to n and asks you to show that the algorithm still works properly but is not stable.

8.3 · radix sort

Sort on the last digit first

Radix sort is what the old punched-card sorters did. The machine reads one column of each card and drops the card into one of a few bins, by the digit punched there. The obvious plan for d-digit numbers is to sort on the leftmost digit, then sort each bin on its own, recursively. But then the operator has to set aside 9 of the 10 bins at every level and keep track of a growing number of piles.

Radix sort does the opposite. Sort the whole deck on the least significant digit, gather the bins in order (0s on top of 1s on top of 2s…), then sort the whole deck again on the next digit, and so on. After d passes the deck is sorted. Why? After pass i the numbers are sorted on their last i digits, but only if each pass is stable: two numbers with the same digit i must keep the order the earlier passes gave them, because that order is the tie-breaker.

With counting sort as the stable sort, one pass over n numbers whose digits take k values costs Θ(n + k), so all d passes cost Θ(d(n + k)) (Lemma 8.3). That is linear when d is a constant and k = O(n). The same idea sorts records with several keys: dates by day, then by month, then by year.

Try it: press Play to run Figure 8.3. The tan digit in each column is the one that pass sorted on. Look at 457 and 657 in the digit-2 pass: both have a 5 there, and 457 stays first because the digit-1 pass put it first. Switch to Unstable pass: every pass still sorts its digit, but reverses ties, and the last column comes out wrong. Most significant first makes stable passes in the wrong order. What the book says

Radix sort is the algorithm used by card-sorting machines now found only in computer museums. The cards have 80 columns, each with 12 places to punch a hole; the sorter examines one column of each card and distributes the card into one of 12 bins. For decimal digits each column uses only 10 places. Sorting on the most significant digit first and recursively sorting each bin generates many intermediate piles of cards to keep track of, since 9 of the 10 bins must be put aside to sort each bin (Exercise 8.3-6).

Radix sort solves the problem counterintuitively by sorting on the least significant digit first, combining the bins into one deck in order, then sorting the entire deck on the second-least significant digit, and so on, until the cards have been sorted on all d digits. “Remarkably, at that point the cards are fully sorted on the d-digit number.” Only d passes are required. “In order for radix sort to work correctly, the digit sorts must be stable.” The card sorter's sort is stable, but the operator must not change the order of the cards as they come out of a bin.

On a computer, radix sort can sort records keyed by multiple fields, such as dates by year, month and day: sort three times with a stable sort, first on day, next on month, and finally on year. RADIX-SORT(A, n, d) assumes digit 1 is the lowest-order digit and digit d the highest. It does not say which stable sort to use, but COUNTING-SORT is common; RADIX-SORT can then preallocate the output array and alternate input and output between the two arrays in successive passes.

Lemma 8.3: given n d-digit numbers in which each digit can take on up to k possible values, RADIX-SORT correctly sorts them in Θ(d(n + k)) time if the stable sort it uses takes Θ(n + k) time. Correctness follows by induction on the column being sorted (Exercise 8.3-3). When d is constant and k = O(n), radix sort runs in linear time.

8.3 · radix sort (lemma 8.4: choosing the digits)

How many bits make a digit?

Nothing says a radix-sort digit has to be a decimal digit. A 32-bit key can be cut into 32 one-bit digits, four 8-bit bytes, two 16-bit halves, or a single 32-bit "digit". Each cut is a different radix sort. Every pass is one counting sort over the digit's 2r possible values, so the cost is passes × (n + 2r), and it pulls two ways: small digits mean many passes, big digits mean a huge count array.

For n keys of b bits in r-bit digits there are ⌈b/r⌉ passes, and radix sort takes Θ((b/r)(n + 2r)) time: that is Lemma 8.4. While 2r stays below n, a bigger r is almost free, since each pass costs about n anyway. Once 2r passes n, the count array grows faster than the passes shrink. So the sweet spot is r ≈ ⌊lg n⌋, for a total of Θ(bn/lg n). If the keys are short, b < ⌊lg n⌋, take r = b: one pass, linear time.

The digit itself is plain bit arithmetic: shift the key right by (i − 1)r bits, then keep the low r bits with a mask of r ones. Memory follows the same curve as time. The count array has 2r entries, so at r = 24 it takes 128 MiB of 8-byte counters on its own, while the output array always needs room for n keys. Radix sort with counting sort does not sort in place.

What the book says

Lemma 8.3: given n d-digit numbers in which each digit can take on up to k possible values, RADIX-SORT correctly sorts them in Θ(d(n + k)) time if the stable sort it uses takes Θ(n + k) time. When d is constant and k = O(n), radix sort runs in linear time. More generally, there is some flexibility in how to break each key into digits.

Lemma 8.4: given n b-bit numbers and any positive integer r ≤ b, RADIX-SORT correctly sorts these numbers in Θ((b/r)(n + 2r)) time if its stable sort takes Θ(n + k) time for inputs in the range 0 to k. Proof: view each key as having d = ⌈b/r⌉ digits of r bits each, each an integer from 0 to 2r − 1, and use counting sort with k = 2r − 1. A 32-bit word, for example, has four 8-bit digits: b = 32, r = 8, k = 255 and d = 4.

Which r ≤ b minimizes (b/r)(n + 2r)? If b < ⌊lg n⌋, then n + 2r = Θ(n) for every r ≤ b, and choosing r = b gives Θ(n), which is asymptotically optimal. If b ≥ ⌊lg n⌋, choosing r = ⌊lg n⌋ gives the best running time to within a constant factor, Θ(bn/lg n): above it the 2r term grows faster than the r in the denominator, and below it b/r grows while n + 2r stays Θ(n).

Is radix sort better than quicksort? If b = O(lg n) and r ≈ lg n, radix sort's Θ(n) looks better than quicksort's expected Θ(n lg n), but the constant factors differ: radix sort may make fewer passes, yet each pass may take significantly longer. The choice depends on the implementations, on the machine (“quicksort often uses hardware caches more effectively than radix sort”), and on the input. And the counting-sort version of radix sort does not sort in place, so when primary memory is at a premium an in-place algorithm such as quicksort could be the better choice.

8.4 · bucket sort

Ten trays, one for every tenth

Amara sorts the morning's ten exam scores, each a fraction between 0 and 1. She doesn't compare them yet. She lays out ten trays, one for every tenth of the range: scores from .0 up to .1 go in tray 0, from .1 up to .2 in tray 1, and so on. The tray number is just the first digit, ⌊10 · score⌋. Then she tidies each tray, which holds only a score or two, and stacks the trays in order.

That is bucket sort. It splits [0, 1) into n equal buckets, drops each of the n inputs into bucket ⌊n · A[i]⌋, sorts every bucket with insertion sort, and concatenates them. It is correct for any input: two values in different buckets are already in the right order, because a smaller value never lands in a higher bucket, and two values in the same bucket get ordered by the insertion sort.

It is fast only when the buckets stay small, which is what the input's uniform distribution buys: with values spread evenly over [0, 1), each bucket expects about one value. In Rust the buckets are a Vec<Vec<f64>>: a Vec of headers, each pointing to its own heap buffer. And since an f64 can be NaN, it has no total order: total_cmp supplies one.

Try it: press Play to run Figure 8.4: watch each value fly to bucket ⌊10 · A[i]⌋, each bucket sort itself, and the buckets pour back in order. Switch to Rust to see the Vec of Vecs in the memory strip: an empty bucket owns no buffer at all, and the first push allocates room for four. Then try Random for a fresh uniform draw.

What the book says

“Bucket sort assumes that the input is drawn from a uniform distribution and has an average-case running time of O(n).” “Like counting sort, bucket sort is fast because it assumes something about the input.” Counting sort assumes integers in a small range; bucket sort assumes the input is generated by a random process that distributes elements uniformly and independently over the interval [0, 1).

Bucket sort divides [0, 1) into n equal-sized subintervals, or buckets, distributes the n inputs into them, sorts the numbers in each bucket, and then goes through the buckets in order, listing the elements in each. BUCKET-SORT assumes an input array A[1 : n] with 0 ≤ A[i] < 1 and uses an auxiliary array B[0 : n − 1] of linked lists (buckets). Figure 8.4 runs it on ten numbers: bucket i holds values in the half-open interval [i/10, (i + 1)/10).

Correctness: take A[i] ≤ A[j]. Since ⌊n · A[i]⌋ ≤ ⌊n · A[j]⌋, either A[i] goes into the same bucket as A[j] or into one with a lower index. In the same bucket, the for loop of lines 6–7 puts them in order; in different buckets, line 8 does. “Therefore, bucket sort works correctly.”

8.4 · bucket sort (the analysis)

Why the trays stay small

Everything in bucket sort is linear except line 7, the insertion sorts. Insertion sort on ni values costs O(ni2), so the total is Θ(n) + Σ O(ni2). The whole question is how big Σ ni2 gets. The bucket sizes always add up to n, but their squares punish piles: ten buckets of one cost 10, one bucket of ten costs 100.

Watch a single bucket. Each of the n values lands in it with probability 1/n, independently, so its size ni is a binomial count of successes in n trials: mean np = 1 and variance npq = 1 − 1/n. Then E[ni2] = Var[ni] + E2[ni] = 2 − 1/n. Summed over n buckets, by linearity of expectation, E[Σ ni2] = 2n − 1, and the expected running time is Θ(n).

Uniform is a sufficient condition, not a necessary one: any input whose squared bucket sizes add up to O(n) is sorted in linear time. Values spread evenly over just [0, .5) leave half the buckets empty and still stay linear. Values piled near 0 do not: one bucket swallows a big share and its insertion sort turns quadratic.

Try it: press Throw to drop n uniform values into n buckets and watch the bars, then the Σ ni2 marker on the scale. Press Run 1000: the average settles on the mint 2n − 1 line. Switch to Half range (still linear, about 3n) and then Skewed, and drag n up: the skewed marker heads toward n2.

What the book says

All lines of BUCKET-SORT except line 7 take O(n) time in the worst case. With ni the random variable for the number of elements placed in bucket B[i], and insertion sort running in quadratic time, the running time is T(n) = Θ(n) + Σi=0n−1 O(ni2) (8.1). Taking expectations over the input distribution and using linearity of expectation, E[T(n)] = Θ(n) + Σ O(E[ni2]) (8.2).

The claim is E[ni2] = 2 − 1/n (8.3) for every bucket, which is no surprise since each input value is equally likely to fall in any bucket. View ni as the number of successes in n Bernoulli trials, where success means the element goes into bucket B[i], with probability p = 1/n of success and q = 1 − 1/n of failure. The binomial distribution gives E[ni] = np = 1 and Var[ni] = npq = 1 − 1/n, so E[ni2] = Var[ni] + E2[ni] = (1 − 1/n) + 12 = 2 − 1/n.

Using this in (8.2), the average-case running time of bucket sort is Θ(n) + n · O(2 − 1/n) = Θ(n). Even if the input is not drawn from a uniform distribution, bucket sort may still run in linear time: “As long as the input has the property that the sum of the squares of the bucket sizes is linear in the total number of elements, equation (8.1) tells us that bucket sort runs in linear time.” Exercise 8.4-2 asks why the worst case is Θ(n2).

problem 8-4 · water jugs

Pairing jugs you can only pour

Kofi has eight red jugs and eight blue ones, every jug a different odd shape, so looks tell him nothing about how much each holds. For every red jug exactly one blue jug holds the same amount. His only test: fill a red jug, pour it into a blue one, and see whether the blue overflows, ends up short, or fills exactly. Two reds or two blues can never be compared with each other.

The plain way takes Θ(n2) pours: take each red and pour it into the blues still unpaired until one fits exactly. The worst case is n(n + 1)/2. The faster way is quicksort with two pivots: pick a random red, pour it into every blue to split the blues into smaller, equal and bigger; then use that equal blue to split the reds the same way. Both colours now share a pivot, so recurse on the two smaller halves and the two bigger halves. That makes O(n lg n) pours expected, though an unlucky run can still take Θ(n2).

No algorithm can beat Ω(n lg n). Every pour has three outcomes, so h pours can tell apart at most 3h cases, while there are n! possible pairings to tell apart: h ≥ log3 n! = Ω(n lg n), the decision-tree argument of Section 8.1 with three-way branches. In Rust, giving red and blue jugs different types makes a red-against-red comparison a compile error.

Try it: press Play and follow the pours: each red jug glows, the drop flies to a blue jug, and the sign between them is the result. Matched pairs turn mint and show their amounts. What the book says

You are given n red and n blue water jugs, all of different shapes and sizes. All the red jugs hold different amounts of water, as do all the blue jugs, and “you cannot tell from the size of a jug how much water it holds.” For every jug of one color there is a jug of the other color that holds the same amount. The task is to group the jugs into pairs of red and blue jugs that hold the same amount.

The only operation: pick a red jug and a blue jug, fill the red jug with water, and pour it into the blue jug. “This operation tells you whether the red jug or the blue jug can hold more water, or that they have the same volume.” Each comparison takes one time unit, the goal is an algorithm with a minimum number of comparisons, and “you may not directly compare two red jugs or two blue jugs.”

problem 8-7 · the 0-1 sorting lemma and columnsort

Sort the columns, shuffle, repeat

A compare-exchange looks at two fixed positions and swaps them if they are out of order. An algorithm is oblivious when its whole list of compare-exchanges is fixed in advance: which positions it compares may depend on n, but never on the values or on what earlier compare-exchanges found. COMPARE-EXCHANGE-INSERTION-SORT, in the listing below, is one: it walks every adjacent pair in a fixed order, whatever the values.

Proving such an algorithm correct sounds hard, but the 0-1 sorting lemma makes it easy: if it sorts every input made of only 0s and 1s, it sorts every input. The contrapositive explains why: if it misplaces some value A[p], relabel every value ≤ A[p] as 0 and every bigger value as 1. Compare-exchange can't tell the difference, so the same mistake shows up on the 0-1 input.

Columnsort sorts n = rs values in an r × s grid in eight fixed steps: the odd steps sort every column, the even steps are fixed permutations (transpose and reshape, undo it, shift down half a column, undo that). Its rules are r even, s dividing r, and r ≥ 2s2. With 0s and 1s you can see why: after step 4 the 0s and 1s are mixed only in a short dirty stretch of at most s2 cells, and steps 6–8 straighten out any dirty stretch that fits in half a column, which r ≥ 2s2 guarantees.

Try it: press Play on Figure 8.5 and compare each step with panels (b)–(i). Then pick 0-1, 8 × 2: watch the dirty rows (sun brackets) shrink to a short dirty stretch in the bar strip, and press New 0-1 for other inputs. Last, 0-1, 6 × 3: the figure's own shape breaks the rule r ≥ 2s2, and this input ends unsorted. By the lemma, some input of real numbers fails on that grid too.

What the book says

A compare-exchange operation on A[i] and A[j], where i < j, exchanges them if A[i] > A[j], so that afterward A[i] ≤ A[j]. An oblivious compare-exchange algorithm operates solely by a sequence of prespecified compare-exchange operations: the indices can depend on the number of elements, but not on the values being sorted or on the result of any prior compare-exchange. COMPARE-EXCHANGE-INSERTION-SORT is such a variation of insertion sort, and it runs in Θ(n2) time in all cases.

The 0-1 sorting lemma states that “if an oblivious compare-exchange algorithm correctly sorts all input sequences consisting of only 0s and 1s, then it correctly sorts all inputs containing arbitrary values.” The proof goes through the contrapositive: if algorithm X fails on A[1 : n], let A[p] be the smallest value it puts in the wrong location and A[q] the value it moves into A[p]'s place; define B[i] = 0 if A[i] ≤ A[p] and 1 otherwise, and show that X fails to sort B.

Columnsort works on an array with r rows and s columns, n = rs, where r must be even, s must be a divisor of r, and r ≥ 2s2. When it completes, the array is sorted in column-major order. It operates in eight steps regardless of n: “The odd steps are all the same: sort each column individually. Each even step is a fixed permutation.” Step 2 transposes the array and reshapes it back to r rows and s columns, turning the leftmost column into the top r/s rows, and so on; step 4 inverts it; step 6 shifts the top half of each column into its bottom half and the bottom half into the top half of the next column, with an empty top half on the left and a new rightmost column; step 8 inverts that. Figure 8.5 runs it with r = 6 and s = 3, which violates r ≥ 2s2 but happens to work.

An area is clean if it holds only 0s, only 1s, or nothing, and dirty otherwise. The problem asks you to prove that after steps 1–3 there are clean rows of 0s at the top, clean rows of 1s at the bottom and at most s dirty rows between; that after step 4 the column-major order has a dirty area of at most s2 elements; and that steps 5–8 then produce a fully sorted 0-1 output, so columnsort sorts every input.

COLUMNSORT, eight fixed steps

The chapter on one page

Chapter 8 in eight cards. Each one points at the scenes that act it out.

A comparison sort is a tree of questions

A sort that learns order only from tests like ai ≤ aj is a decision tree: one path per input, one leaf per output order, and all n! permutations must be reachable leaves. → 8.1 Decision trees

The floor is n lg n

A tree of height h has at most 2h leaves, so n! ≤ 2h and h ≥ lg(n!) = Θ(n lg n). Every comparison sort needs Ω(n lg n) comparisons in the worst case (Theorem 8.1). → 8.1 The lower bound

Merge sort and heapsort can't be beaten by much

Their O(n lg n) matches the floor, so they are asymptotically optimal: no comparison sort is faster by more than a constant factor (Corollary 8.2). → 8.1 The lower bound

Use the value as an address

Counting sort counts each key in C[0 : k], turns the counts into running totals and drops each element into its slot: Θ(n + k), with not one comparison between keys. → 8.2 Counting sort

Stable means ties keep their order

Placing from the end of A makes counting sort stable. That matters for satellite data, and it is what makes radix sort correct. Run the loop forward and ties come out reversed. → 8.2 Counting sort, 8.3 Radix sort

Least significant digit first

Radix sort runs d stable passes, ones digit first: Θ(d(n + k)). For b-bit keys cut into r-bit digits that is Θ((b/r)(n + 2r)), best near r = ⌊lg n⌋. → 8.3 Radix sort, Choosing digits

Spread out, then sort the little piles

Bucket sort drops n inputs into n buckets over [0, 1) and insertion-sorts each one. For uniform input E[ni2] = 2 − 1/n, so the expected time is Θ(n); a skewed input piles up and goes quadratic. → 8.4 Bucket sort, Why it's linear

The same ideas, in puzzles

Pairing red and blue jugs by pouring is a comparison problem: Θ(n²) is easy, Ω(n lg n) is the floor, and a quicksort-like randomized plan gets O(n lg n) expected. Columnsort sorts an r × s grid in 8 fixed steps, proved with the 0-1 sorting lemma. → 8-4 Water jugs, 8-7 Columnsort

Words to know

The book's words from this chapter, in plain language.

comparison sort
A sort whose output order depends only on comparisons between input elements. Insertion, merge, heap and quicksort all are.
decision tree
A full binary tree of every comparison a given sort makes on inputs of one size. Running the sort is one path from the root to a leaf.
internal node i:j
One comparison, ai ≤ aj, between the elements that started at positions i and j. Left if yes, right if no.
leaf
A permutation ⟨π(1), …, π(n)⟩: the order the sort settled on, aπ(1) ≤ ⋯ ≤ aπ(n).
reachable leaf
A leaf that some real input actually ends at. A correct sort needs one for each of the n! orders.
height
The longest root-to-leaf path in a tree. For a decision tree, the sort's worst-case number of comparisons.
lower bound
A cost no algorithm in a class can beat. Comparison sorts need Ω(n lg n) comparisons in the worst case.
asymptotically optimal
Matching the lower bound up to a constant factor, like merge sort and heapsort.
counting sort
Sorts integers in 0 to k by counting each value and placing elements by running totals: Θ(n + k) time.
running sum (prefix sum)
Each entry replaced by itself plus everything before it. After it, C[i] is the number of elements ≤ i.
stable
Equal keys come out in the same order they went in.
satellite data
The rest of a record that travels with its key, like a name sorted by age.
radix sort
Sorts d-digit keys with d stable passes, least significant digit first: Θ(d(n + k)).
least significant digit
The lowest-order digit, the ones place. Radix sort's first pass sorts on it.
r-bit digit
A slice of r bits of a b-bit key, taken as one digit with 2r possible values.
bucket sort
Splits [0, 1) into n equal buckets, sorts each with insertion sort, then concatenates them. Expected Θ(n) on uniform input.
uniform distribution
Every value in the range is equally likely, so no bucket expects more than its fair share.
average-case running time
The expected time over the input distribution, as in bucket sort's Θ(n).
compare-exchange
Compare A[i] with A[j] and swap them if they are out of order, so A[i] ≤ A[j] afterwards.
oblivious algorithm
One whose compare-exchanges are fixed in advance and never depend on the values or on earlier results.
0-1 sorting lemma
An oblivious compare-exchange algorithm that sorts every input of 0s and 1s sorts every input.
columnsort
Sorts an r × s array into column-major order in eight steps: four column sorts and four fixed permutations.
column-major order
Read down each column in turn, left to right.
