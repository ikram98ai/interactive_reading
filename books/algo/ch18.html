B-Trees

A B-tree is a search tree built for disks. Each node fills a whole disk block, so it can have hundreds of children and a search touches only a handful of blocks. Chapter 18 defines B-trees, then searches, builds, splits, inserts and deletes while counting every disk read and write.

“A large branching factor dramatically reduces both the height of the tree and the number of disk accesses required to find any key.” — Cormen, Leiserson, Rivest & Stein

18 · why B-trees: secondary storage

Fetch a crate, not a sheet

Your desk is main memory: fast, but small. The warehouse across town is the disk: enormous, but every trip takes as long as thousands of reaches across the desk. So you never fetch one sheet of paper. You bring back a whole crate and hope every sheet in it is useful.

A disk drive spins its platters and swings an arm, so a read means waiting for metal to move: about 4 ms on average, against about 50 ns for main memory. The drive reads and writes whole blocks, typically 512 to 4096 bytes, so a trip costs the same for one key or for every key in the block. That is why the book counts disk accesses, DISK-READ and DISK-WRITE, separately from CPU time.

A search tree should respect that. Make each node as big as a block, so one read brings in hundreds of keys and the node has hundreds of children. A billion keys then fit in three levels instead of thirty, and a search touches few blocks. A tree built this way is a B-tree.

Try it: on One page per trip, press the four buttons one by one and watch the clock. A whole block costs the same 4 ms as one key; eight keys from eight blocks cost eight times as much; changing a key costs two trips, because DISK-WRITE is a trip too. Then open How tall a tree and press Play: the binary tree stacks up 29 disk reads for a billion keys, a node of 1000 keys needs 2. Drag the sliders to see how fast the gap grows.

What the book says

B-trees are balanced search trees designed to work well on disk drives or other direct-access secondary storage devices. They are similar to red-black trees, but they are better at minimizing the number of operations that access disks. B-tree nodes may have many children, from a few to thousands, and the branching factor usually depends on the disk drive. Every n-node B-tree has height O(lg n), but with a larger base for the logarithm the height can be considerably lower.

A disk drive has platters that rotate around a spindle, and heads at the ends of arms that move toward or away from the spindle. At 7200 RPM one rotation takes 8.33 milliseconds, over five orders of magnitude longer than the 50 nanosecond access times, more or less, of main memory: more than 100,000 main-memory accesses in one rotation. Average access times for commodity drives are around 4 milliseconds. To amortize that latency, a drive reads and writes whole blocks, typically 512 to 4096 bytes.

Reading a block often takes longer than processing it, so the chapter looks separately at the number of disk accesses and at the CPU time. The algorithms copy selected blocks from disk into main memory as needed and write changed blocks back. To use an object x that lives on disk, call DISK-READ(x); after changing it, call DISK-WRITE(x). If x is already in memory, DISK-READ is a no-op. Only a constant number of blocks are in memory at any time, so memory does not limit the size of a B-tree.

Since the running time depends mostly on these operations, each should move as much information as possible: “a B-tree node is usually as large as a whole disk block”. Large B-trees often have branching factors between 50 and 2000. Figure 18.3 shows a branching factor of 1001 and height 2 that stores over one billion keys, and if the root is kept permanently in main memory, at most two disk accesses find any key.

18.1 · definition of B-trees

Not too empty, not too full

A binary node holds one key and has two children. A B-tree node holds many: a node with n keys has n + 1 children, and its keys are the dividers between them. Everything under the first child is at most the first key, everything under the second child lies between the first and second keys, and so on. A search makes an (n + 1)-way decision at each node.

Two limits keep the tree healthy. Pick a number t ≥ 2, the minimum degree. Every node except the root must hold at least t − 1 keys, so it is at least half full, and no node may hold more than 2t − 1. A node with exactly 2t − 1 keys is full. All leaves sit at the same depth. With t = 2 every internal node has 2, 3 or 4 children, a 2-3-4 tree.

The lower limit is what keeps the tree short. Every node below the root has at least t children, so even the thinnest legal tree of height h holds 2th − 1 keys. Turned around, any tree with n keys has height at most logt((n + 1)/2). Since a node is a disk block, that bound counts disk reads.

Try it: on Check the rules, click a node and read its allowed key count off the gauge. Then switch t from 2 to 4: the two-key nodes turn coral, because Figure 18.1 is legal only for t = 2 and 3. Use Add a key, Take a key and Swap two keys on the selected node and see which of the five checks fails, then press Run checker to watch the validator walk the tree. On Fewest keys, move t and h to see the thinnest tree of that height and its key count.

What the book says

For simplicity the chapter assumes that satellite information lives in the same node as its key. A common variant, the B+-tree, stores all satellite information in the leaves and only keys and child pointers in internal nodes, which maximizes the branching factor. Another variant, the B*-tree, requires internal nodes to be at least 2/3 full rather than half full.

A B-tree T is a rooted tree with five properties. Every node x has x.n, the number of keys, the keys themselves in monotonically increasing order, and a boolean x.leaf. Each internal node has x.n + 1 child pointers; leaves have none. The keys x.keyi separate the ranges of keys stored in the subtrees: k1 ≤ x.key1 ≤ k2 ≤ … ≤ x.keyx.n ≤ kx.n+1. All leaves have the same depth, which is the tree's height h.

Nodes have lower and upper bounds on their key counts, in terms of a fixed integer t ≥ 2 called the “minimum degree”. Every node other than the root has at least t − 1 keys, so every internal node other than the root has at least t children; a nonempty tree's root has at least one key. Every node may hold at most 2t − 1 keys, so an internal node has at most 2t children. The simplest B-tree has t = 2: every internal node has 2, 3 or 4 children, and it is a “2-3-4 tree”. In practice much larger values of t give smaller height.

Theorem 18.1: if n ≥ 1, then for any n-key B-tree of height h and minimum degree t ≥ 2, h ≤ logt((n + 1)/2). The proof counts nodes: the root has at least one key, there are at least 2 nodes at depth 1, at least 2t at depth 2, at least 2t2 at depth 3, down to at least 2th−1 at depth h, each holding at least t − 1 keys, so n ≥ 2th − 1 (Figure 18.4). Although the height of both a B-tree and a red-black tree grows as O(log n), the base of the logarithm can be many times larger for B-trees, which saves a factor of about lg t in the number of nodes examined and so avoids a substantial number of disk accesses.

18.2 · searching a B-tree

One path, one read per level

Searching a B-tree is searching a binary tree with a wider fork. At a node, run along the keys in order until you reach the first one that is not smaller than the key you want. If it is equal, you are done. If not, the gap you stopped in leads to exactly one child: read that child from the disk and start again. The book calls this B-TREE-SEARCH, and its decision at each node has n + 1 outcomes.

Count the two costs apart. Each step down needs a DISK-READ, so a search reads at most h blocks, O(logt n), and the root costs nothing because it always stays in memory. Inside a node the scan makes up to 2t − 1 comparisons, so the CPU time is O(t · h) = O(t logt n).

The keys in a node are sorted, so you could binary-search them instead. That cuts the comparisons per node from about t to about lg t and changes nothing on the disk, since the whole block is already in memory. A node of 1000 keys costs up to 1000 comparisons by scanning and about 10 by binary search.

Try it: pick a letter with the slider and press Play. Dashed nodes are still on the disk, and every DISK-READ brings one into memory. Search R (the book's example: 2 reads), then M (found in the root: no reads) and A (not in the tree, yet the search still has to walk down to a leaf). Then switch to Binary search and compare the counts: in nodes this small, scanning is about as cheap.

What the book says

Searching a B-tree is much like searching a binary search tree, except that instead of a two-way branching decision at each node, the search makes a multiway decision according to the number of the node's children: an (x.n + 1)-way decision at each internal node x. B-TREE-SEARCH generalizes TREE-SEARCH. It takes a pointer to the root x of a subtree and a key k; the top-level call is B-TREE-SEARCH(T.root, k). If k is in the tree it returns the ordered pair (y, i) with y.keyi = k, and otherwise NIL.

Lines 1–3 use linear search to find the smallest index i such that k ≤ x.keyi, or else set i to x.n + 1. Lines 4–5 check whether the key has been found. Otherwise, if x is a leaf, line 7 ends the search unsuccessfully, and if x is internal, lines 8–9 recurse into the right subtree after the necessary DISK-READ on that child.

Section 18.2 states two conventions for its procedures. The root of the B-tree is always in main memory, so no procedure ever needs a DISK-READ on the root, though any change to the root needs a DISK-WRITE. Any node passed as a parameter must already have had a DISK-READ performed on it. The procedures are one-pass algorithms that go downward from the root without backing up.

The nodes met during the recursion form a simple path down from the root, so B-TREE-SEARCH accesses O(h) = O(logt n) disk blocks. Since x.n < 2t, the while loop takes O(t) time in each node, and the total CPU time is O(th) = O(t logt n). Exercise 18.2-6 asks to show that binary search inside each node makes the CPU time O(lg n), whatever t is.

18.2 · creating an empty B-tree

An empty tree is one empty page

A library does not build its catalogue shelf by shelf. It starts with one empty drawer and adds cards to it. An empty B-tree starts the same way: not with “nothing”, but with a single node, a leaf that holds no keys yet, and a pointer to it.

B-TREE-CREATE has five lines. ALLOCATE-NODE claims one free block on the disk and hands back a node to fill in. The procedure marks it as a leaf, sets its key count to 0, saves it with DISK-WRITE and points T.root at it. A brand-new block needs no DISK-READ, because nothing useful is stored on it yet, so the whole procedure costs O(1) disk operations and O(1) CPU time.

That pointer carries a convention. The root is always kept in main memory, so no procedure ever pays a DISK-READ for it. The price: whenever the root changes, the change must be saved with DISK-WRITE. Every other node has to be read from the disk before a procedure may look inside it.

Try it: press Play and follow the five lines: a free block is claimed, the node is filled in in memory, one copy goes to the disk, and T.root points at it. Then press Add a key to the root: memory and disk now disagree and the disk copy is marked stale until you press DISK-WRITE(T.root). Change t to see how many keys a node can hold (2t − 1). In Rust, the memory strip shows x being moved into the tree.

What the book says

The basic operations follow two conventions. The root of the B-tree is always in main memory, so no procedure ever needs a DISK-READ on the root, but if the root changes, DISK-WRITE must be called on it. And any node passed as a parameter must already have had a DISK-READ performed on it. The procedures are “one-pass” algorithms that proceed downward from the root, without having to back up.

To build a B-tree T, you first create an empty root node with B-TREE-CREATE and then add keys with B-TREE-INSERT. Both use an auxiliary procedure, ALLOCATE-NODE, whose pseudocode the book omits and which allocates one disk block to be used as a new node in O(1) time.

A node created by ALLOCATE-NODE needs no DISK-READ, since the disk holds no useful information for it yet. B-TREE-CREATE requires O(1) disk operations and O(1) CPU time.

Behind these calls is the book’s model of the disk. DISK-READ(x) copies the block containing x into main memory before its attributes can be used, and is a “no-op” if x is already there. DISK-WRITE(x) saves changes made to x by writing the block back; it is omitted if no attributes of x were changed.

18.2 · splitting a node

Cut in the middle, push the middle up

A full shelf has no free slot. A librarian does not squeeze one more book in: she cuts the shelf in half and hangs a label between the halves. A full B-tree node holds 2t − 1 keys. Splitting it around its median key leaves two nodes with t − 1 keys each, and the median moves up into the parent, where it becomes the dividing key between them.

B-TREE-SPLIT-CHILD(x, i) does this for a full child y = x.ci of a node x that is not full. It allocates a new node z, gives it the t − 1 greatest keys of y (and the t matching children, if y is internal), cuts y down to t − 1 keys, makes room in x for the median and for z, and writes the three changed nodes. That is Θ(t) CPU time and O(1) disk operations: no reads, three writes.

Splitting is also the only way a B-tree grows taller. When the root is full, B-TREE-SPLIT-ROOT allocates an empty node s, makes the old root its only child and then splits that child. The tree gains a level at the top, so every leaf stays at the same depth. In Rust, y.keys.split_off(T) is the whole key loop, and std::mem::take lets the new root take over the old one without leaving a hole behind.

Try it: press Play on Child (Figure 18.5, t = 4): z is allocated, the three greatest keys and four subtrees move to it, the median S flies up into x, and the three nodes are written. Then try Leaf child: with no children to move, lines 8–9 are skipped. Root shows Figure 18.6: the old root gets a new parent and the tree grows one level. In Rust, the memory strip shows split_off giving z a new buffer while y keeps its own.

What the book says

You cannot simply create a new leaf for a new key, because the resulting tree would fail to be a valid B-tree. So the key goes into an existing leaf, and a full node y (with 2t − 1 keys) is first split around its median key y.keyt into two nodes with only t − 1 keys each. The median key moves up into y’s parent.

B-TREE-SPLIT-CHILD takes a nonfull internal node x (assumed to be in main memory) and an index i such that x.ci (also assumed to be in memory) is a full child of x. Node y originally has 2t children and 2t − 1 keys, and splitting reduces it to t children and t − 1 keys. The t largest children and t − 1 largest keys move to z, which becomes a new child of x just after y.

Lines 2–9 create z and give it the largest keys and children of y. Line 10 adjusts y’s key count. Lines 11–17 shift keys and child pointers in x, insert z as a child and move the median up. Lines 18–20 write out all modified blocks. The CPU time is Θ(t), because of the loops in lines 5–6 and 8–9, and the procedure performs O(1) disk operations.

To split a full root, you first make it a child of a new empty root node, so that B-TREE-SPLIT-CHILD can be used. B-TREE-SPLIT-ROOT allocates the new node s, sets s.leaf to FALSE and s.n to 0, makes the old root its first child, sets T.root to s, calls B-TREE-SPLIT-CHILD(s, 1) and returns s. Figure 18.6 shows it with t = 4. The book notes that “splitting is the only means by which the tree grows taller” and that, “Unlike a binary search tree, a B-tree increases in height at the top instead of at the bottom.”

18.2 · inserting in a single pass down the tree

Split on the way down, never climb back

To add a key you walk from the root to a leaf. The trouble starts when that leaf is full: it must split, which pushes a key into its parent, which may be full too, and so on back up the tree. The book avoids the climb: split every full node you meet on the way down. Then, whenever a split is needed, the parent is guaranteed to have room, and one pass from the root is all it takes.

B-TREE-INSERT-NONFULL(x, k) is the walk. In a leaf it slides the greater keys one place right and puts k in, then calls DISK-WRITE. In an internal node it finds the child where k belongs and reads it with DISK-READ. If that child is full it calls B-TREE-SPLIT-CHILD first and picks the half k belongs to, so the recursion never enters a full node. B-TREE-INSERT only has to guard the root: if it is full, B-TREE-SPLIT-ROOT makes the tree one level taller, and the walk starts from the new root.

One pass costs O(h) disk accesses, with O(1) reads and writes per level. The price of splitting early is that a full node on the path is split even when the leaf below it would have had room. In Rust, the walk is a method that calls itself on &mut self.kids[i]: each level borrows the next one, so only one path of the tree is ever being changed.

Try it: press Play to insert B, the book’s first key: it lands in a leaf, no split. Press Play again for Q: the full node RSTUV splits on the way down and T moves up. L meets a full root and the tree grows a level; F splits ABCDE. Blue nodes are in main memory and lilac ones are on the disk: only one path is ever loaded. Click any free letter to insert that one next, or switch to the empty 2-3-4 tree and build one from nothing. Insert fast skips the animation.

What the book says

Inserting a key k into a B-tree T of height h requires just a single pass down the tree and O(h) disk accesses. The CPU time is O(th) = O(t logt n). B-TREE-INSERT uses B-TREE-SPLIT-CHILD to guarantee that the recursion never descends to a full node. If the root is full, B-TREE-INSERT splits it by calling B-TREE-SPLIT-ROOT, and a new node s with two children becomes the root. Either way it finishes by calling B-TREE-INSERT-NONFULL on the nonfull root.

The reason for splitting on the way down: a full leaf has to be split, but if its parent is also full you could end up splitting full nodes all the way up the tree. So the book says “To avoid having to go back up the tree, just split every full node you encounter as you go down the tree.” In this way, whenever you need to split a full node, you are assured that its parent is not full.

B-TREE-INSERT-NONFULL inserts k into node x, which is assumed to be nonfull when the procedure is called. Lines 3–8 handle a leaf: shift the greater keys right, insert k, and write the node. For an internal node, lines 9–11 determine the child x.ci to descend to. Line 13 detects a full child, line 14 splits it, and lines 15–16 decide which of the two halves is the right one. A DISK-READ is not needed after line 16, since the recursion then descends to a child that was just created by the split.

Figure 18.7 uses t = 3, so a node holds at most 5 keys, and inserts B, Q, L and F. B is a simple insertion into a leaf. For Q, the node RSTUV splits into RS and UV, T moves up to the root, and Q goes into RS. For L, the root is full and splits right away, so the tree grows in height by one, and L goes into the leaf containing JK. For F, the node ABCDE splits before F is inserted into the DE node.

Since B-TREE-INSERT-NONFULL is tail-recursive, it can be written as a while loop instead, which shows that the number of blocks that must be in main memory at any time is O(1).

18.3 · deleting a key from a B-tree

Never step onto a thin node

Deleting is insertion run backwards, with one new difficulty: the key you want gone can sit in any node, not only in a leaf. And where insertion fears a node that is too full, deletion fears a node that is too thin.

The book keeps the whole job to a single pass down the tree with one promise: B-TREE-DELETE never steps into a node that has only the legal minimum of t − 1 keys. If the child it must enter is that thin, it first makes the child one key richer, by borrowing through the parent from a sibling (case 3a) or by merging with a sibling (case 3b). A node with at least t keys can lose one and stay legal, so no repair ever has to climb back up.

That leaves the key itself. In a leaf it is simply removed (case 1). In an internal node it is replaced by its predecessor or successor, taken from a neighbouring child that has a key to spare (2a, 2b); if both neighbours are thin, they are merged around the key (2c). A merge can empty the root. Then its only child becomes the root and the tree is one level shorter.

Try it: in Book's figure 18.8 press Play five times: F, M, G, D and B are the book's own deletions, one case each (1, 2a, 2c, 3b with the tree shrinking, then 3a). Watch the bar under the tree: every node the pass steps into has at least 3 keys. Then switch to Pick a key and click any key: C is case 2b, X needs a 3a repair on the way down to a 2c, and the root's P is replaced by O. Delete H shows a search that fails in a leaf.

What the book says

Deletion is analogous to insertion but a little more complicated, because a key can be deleted from any node, not just a leaf, and deleting from an internal node means rearranging its children. A node must not get too small: “a node must not get too small during deletion”, except that the root may have fewer than the minimum t − 1 keys. A simple approach might have to back up if a node on the path has the minimum number of keys, just as a simple insertion might back up over a full node.

B-TREE-DELETE combines the search for k with the deletion, unlike TREE-DELETE and RB-DELETE, which are given the node to delete. Just as B-TREE-INSERT prevents any node from becoming overfull, B-TREE-DELETE prevents any node from becoming underfull (fewer than t − 1 keys) while making a single pass down the tree. Its design guarantees “whenever it calls itself recursively on a node x, the number of keys in x is at least the minimum degree t at the time of the call”. The root may have fewer than t keys, but no recursive call is made on the root. This takes one more key than the usual minimum, so a key may have to move from x into a child before the recursive call.

The book describes the procedure in three cases (Figure 18.8) instead of presenting detailed pseudocode; writing it is Exercise 18.3-2, so the listing under the machine is a sketch of ours. Case 1: the search reaches a leaf; if it holds k, delete it, otherwise k was not in the tree. Case 2: the search reaches an internal node x that holds k = x.keyi. If the child before k has at least t keys (2a), find the predecessor k′ of k in that subtree, recursively delete k′ from it and replace k by k′ in x. If it has t − 1 keys but the child after k has at least t (2b), do the same with the successor. If both have t − 1 keys (2c), merge k and all of the later child into the earlier one, which now holds 2t − 1 keys, free the later child and recursively delete k from the merged node.

Case 3: the search reaches an internal node that does not hold k. Continue down, making sure each node visited has at least t keys. If the child x.ci has only t − 1 keys, case 3a applies when an immediate sibling has at least t: move a key from x down into the child, a key from the sibling up into x, and the appropriate child pointer from the sibling into the child. Case 3b applies when the child and each of its immediate siblings have t − 1 keys: merge the child with one sibling, moving a key from x down to become the median of the merged node. In cases 2c and 3b, if x is the root and ends up with no keys, it is deleted and its only child becomes the new root, decreasing the height by one.

Most keys are in leaves, so deletions often end up deleting from leaves. When a key in an internal node is replaced by its predecessor or successor, the procedure can keep a pointer to x and the key position and put the key directly there, without walking back up. Only O(1) calls to DISK-READ and DISK-WRITE are made between recursive invocations, so a B-tree of height h needs only O(h) disk operations, and the CPU time is O(th) = O(t logt n).

problem 18-1 · stacks on secondary storage

Keep the top of the stack close

A stack can grow far bigger than main memory, so most of it lives on disk, in blocks of m words. PUSH and POP only ever touch the top word, but the disk hands over a whole block at a time, and every block read or written is one disk access.

The simplest design keeps the whole stack on disk: a push reads the block, changes one word and writes it back, and a pop reads the block. Keep one block of the stack in memory and a run of pushes swaps blocks only once per m words. But a stack hovering at a block boundary makes that swap happen again and again.

Keep two blocks in memory, write one out only when both are full, and read one back only when memory is empty. After any disk access memory is half full, so about m operations pass before the next one: the cost is amortized O(1/m) accesses per operation.

Try it: on All on disk press Push ×8, then 3 zig-zags (push, pop, pop, push, three times) and read accesses per op. Press Reset, pick One block in memory and run the same two: the pushes get cheap, but the zig-zag across the block boundary still swaps blocks on every other operation. Then Two blocks in memory: the zig-zag costs nothing and the pushes cost one write per block.

What the book says

Consider a stack on a computer with a relatively small amount of fast primary memory and a relatively large amount of slower disk storage. PUSH and POP work on single-word values, and the stack can grow much larger than memory, so most of it must be stored on disk.

The simple implementation keeps the entire stack on disk and only a stack pointer in memory: the disk address of the top element. With block numbers and word offsets indexed from 0, a pointer p puts the top element at word p mod m of block ⌊p/m⌋, where m is the number of words per block. PUSH increments the pointer, reads the block into memory, copies the element into the right word and writes the block back. POP reads the block, saves the top of the stack, decrements the pointer and returns the saved value. “You need not write back the block, since it was not modified”, and the word that held the popped value is ignored.

As with B-tree operations, two costs matter: the total number of disk accesses and the total CPU time. A disk access to a block of m words incurs one disk access and Θ(m) CPU time.

The problem asks for the cost of these designs in terms of m and n. Part (a): the worst-case disk accesses and CPU time of n stack operations in the simple implementation. Parts (b) and (c): the same for n PUSH operations and for n arbitrary stack operations when one block of the stack is kept in memory, writing it out and reading another only when the relevant block is not already there. Part (d): with two blocks in memory, describe how to manage the blocks so that the amortized number of disk accesses per operation is O(1/m) and the amortized CPU time is O(1). The book states these as questions; the access counts in the machine are measured from our own implementation of each design, not quoted from the book.

problem 18-2 · joining and splitting 2-3-4 trees

Glue two trees, or cut one in two

A 2-3-4 tree is a B-tree with t = 2: every node holds one to three keys. The problem asks for two operations on whole trees. JOIN glues a tree T′, a key k and a tree T″ into one tree, when every key of T′ is below k and every key of T″ is above it. SPLIT cuts one tree around a key k into the keys below it and the keys above it.

JOIN is cheap because every node stores its height. If the trees are equally tall, k becomes a new root with the two roots as its children. If one is taller, walk down its near edge (the right spine of T′, or the left spine of T″) to the node whose children are as tall as the short tree, and hang the short tree there beside k, splitting any full node on the way, just as insertion does. That is O(1 + |h′ − h″|) work.

SPLIT follows the search path to k. What hangs to the left of the path, with its separating keys, belongs to the smaller tree, and what hangs to the right to the larger one. In key order the left pieces get shorter and shorter, so JOINing them from the short end costs 1 plus the difference in heights each time, and those differences telescope: O(lg n) in all.

Try it: in Join pick T′ taller and press Play: the short tree is hung at the end of the right spine. Full node on the spine shows the split that insertion would also make on the way down. Then switch to Split: press Play to cut the tree around L, or press Reset, click another key (try A, whose left side is empty) and press Play. The pieces on each side are then joined from the short end.

What the book says

The join operation takes two dynamic sets S′ and S″ and an element x such that every key in S′ is less than x.key and every key in S″ is greater, and returns the set S′ ∪ {x} ∪ S″. The split operation is like an “inverse” join: given a set S and an element x in it, it creates a set S′ of all the other elements whose keys are less than x.key and a set S″ of those whose keys are greater. The problem implements both on 2-3-4 trees, which are B-trees with t = 2, assuming that elements are only keys and that all key values are distinct.

Part (a) asks how to maintain the height of the subtree rooted at every node x as an attribute x.height without changing the asymptotic running times of searching, insertion and deletion. Part (b) asks for JOIN on two 2-3-4 trees T′ and T″ and a key k, running in O(1 + |h′ − h″|) time, where h′ and h″ are the heights of the trees.

Part (c) considers the simple path p from the root of a 2-3-4 tree T to a given key k, the set S′ of keys in T less than k and the set S″ of keys greater than k. It asks you to show that p breaks S′ into a set of trees and a set of keys, one key between each pair of consecutive trees, to give the relationship between the heights of consecutive trees, and to describe how p breaks S″. Part (d) asks for SPLIT, using JOIN to assemble the keys of S′ into a single 2-3-4 tree and those of S″ into another, in O(lg n) time for n keys in T, with the hint that the costs for joining should telescope.

The book states these as parts to solve. The machine and the listings are our own sketch of one answer, not the book's.

The chapter on one page

Chapter 18 in eight cards. Each one points at the scenes that act it out.

The disk sets the price

A disk access waits for moving metal, around 4 ms, against about 50 ns for main memory, and it moves a whole block of 512 to 4096 bytes at once. So the chapter counts disk accesses, DISK-READ and DISK-WRITE, apart from CPU time. → 18 Why B-trees

Fat nodes, short tree

A B-tree node is as big as a block, with 50 to 2000 children. A branching factor of 1001 holds over a billion keys in height 2, and with the root kept in memory a search needs at most two disk reads. → 18 Why B-trees

Not too empty, not too full

With minimum degree t ≥ 2, every node but the root holds t − 1 to 2t − 1 keys, an internal node with n keys has n + 1 children, and all leaves share one depth. Then h ≤ logt((n + 1)/2). → 18.1 Definition of B-trees

One path down

B-TREE-SEARCH scans a node's keys, finds the gap, and does one DISK-READ for the child. That is O(h) = O(logt n) disk accesses and O(t logt n) CPU time. → 18.2 Searching a B-tree

Create, then split

B-TREE-CREATE allocates one empty leaf as the root. A full node, 2t − 1 keys, splits around its median: the median moves up, a new node takes the top t − 1 keys, and three blocks are written. Splitting the root is the only way a B-tree grows taller. → 18.2 Creating, Splitting

Split on the way down

B-TREE-INSERT splits every full node it meets on its way to the leaf, so a parent always has room and no pass ever climbs back. A full root is split first with B-TREE-SPLIT-ROOT. O(h) disk accesses. → 18.2 Inserting

Never step onto a thin node

B-TREE-DELETE makes sure every node it enters has at least t keys, by borrowing a key from a sibling (case 3a) or merging (3b). A key in an internal node is replaced by its predecessor or successor, or its two children merge (2a, 2b, 2c). The tree shrinks when the root empties. → 18.3 Deleting

Beyond the basics

A stack larger than memory keeps only its top blocks in memory, and with two blocks in memory a stack operation costs O(1/m) disk accesses amortized. Join and split on 2-3-4 trees run in time proportional to a height difference, then O(lg n). → 18-1 Disk stacks, 18-2 2-3-4 trees

Words to know

The book's words from this chapter, in plain language.

secondary storage
Disk drives and SSDs: much bigger and cheaper than main memory, and much slower to reach.
block
The unit a disk reads or writes, typically 512 to 4096 bytes. A B-tree node is usually as large as one block.
latency
The wait for the platter to turn and the arm to move before a block can be read. Disks read whole blocks to amortize it.
disk access
One block read or written. Counting these is the first-order estimate of a B-tree operation's time.
DISK-READ(x) / DISK-WRITE(x)
Copy x's block into main memory before using x, and write it back after changing it. DISK-READ is a no-op if x is already in memory.
branching factor
How many children a node can have. B-trees use 50 to 2000, so a tree can hold billions of keys in a few levels.
B-tree
A balanced search tree whose nodes hold many keys and have many children, designed to minimize disk accesses.
x.n, x.keyi, x.ci, x.leaf
A node's key count, its sorted keys, its n + 1 child pointers, and whether it is a leaf.
minimum degree t
The integer ≥ 2 that sets the bounds: every non-root node holds t − 1 to 2t − 1 keys, and an internal one has t to 2t children.
full node
A node holding exactly 2t − 1 keys. It cannot take another key without splitting.
2-3-4 tree
The B-tree with t = 2: every internal node has 2, 3 or 4 children.
Theorem 18.1
An n-key B-tree of height h and minimum degree t has h ≤ logt((n + 1)/2).
B+-tree
A variant that keeps all satellite data in the leaves, so internal nodes hold only keys and pointers and branch more.
B-TREE-SEARCH
Scan the node, then DISK-READ and descend into the one child whose range holds the key. Returns (node, index) or NIL.
ALLOCATE-NODE
Takes one disk block for a new node in O(1) time, with no DISK-READ because nothing useful is stored there yet.
median key / split
B-TREE-SPLIT-CHILD cuts a full node around its middle key, which moves up into the parent, leaving two nodes of t − 1 keys.
B-TREE-SPLIT-ROOT
Hangs a full root under a new empty root and splits it, which makes the tree one level taller.
one-pass algorithm
A procedure that goes down from the root once, without backing up. B-TREE-INSERT and B-TREE-DELETE both are.
underfull
A non-root node with fewer than t − 1 keys. B-TREE-DELETE never lets one appear.
predecessor / successor
The next smaller or larger key. Case 2 of deletion replaces a key in an internal node by one of them.
merge
Combine two minimum-size sibling nodes and the key between them into one node of 2t − 1 keys (cases 2c and 3b).
join / split (Problem 18-2)
Join two sets around a key that sits between them; split a set around one of its keys. On 2-3-4 trees they take O(1 + |h' − h''|) and O(lg n) time.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

owned Vec<Node> children
A node holds its children in a Vec, so each node has exactly one owner, its parent. No Box, arena or free is needed, and dropping the root frees the whole tree.
const T: usize
The minimum degree as a compile-time constant, so 2 * T - 1 is the node limit everywhere.
[i32; 8] is Copy
A fixed-size array lives inline and is copied by =. *disk.disk_read(x) copies a block out from behind a borrow into memory, and the stack in Problem 18-1 reads blocks the same way.
&mut self returning &T
A method that takes &mut self and hands back a shared borrow keeps self borrowed until the caller is done with the reference.
lifetime 'a
In fn search<'a>(x: &'a Node, …, reads: &mut u32) -> Option<(&'a Node, usize)> it says the answer points into the tree, not into reads.
Option<char> as −∞ and ∞
A range check carries lo and hi as Options, where None means no bound, tested with matches!(lo, Some(l) if k < l).
binary_search
On a sorted slice it returns Result<usize, usize>: Ok(i) when the key is at i, Err(i) with the place it would be inserted, which is the child to descend into.
Vec::split_off, insert, remove
split_off(t) cuts a Vec in two at index t. insert and remove shift the items after the index, like the book's shifting loops.
std::mem::take
Moves a value out of a place that must stay valid, leaving a default value behind, as when the old root becomes the new root's child.
split_at_mut
Splits a slice into two disjoint &mut halves, so deletion can edit a child and its sibling at once.
derive(Default) and ..Default::default()
The compiler writes an all-empty value, and ..Default::default() fills in the fields you leave out.
partition_point and closures
keys.partition_point(|&c| c < k) is a binary search that takes a closure and returns how many keys pass the test, which is the index where k belongs among a node's keys.
