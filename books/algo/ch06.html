Heapsort

A heap is an array you can read as a binary tree, with the largest value always at the root. This chapter keeps that rule true in O(lg n) per repair, builds a heap in linear time, sorts with it in O(n lg n) without any second array, and turns it into a priority queue.

6.1 · heaps

A tree hiding in an array

Write ten numbers into an array, then read them out row by row: one on top, two under it, four under those, and the rest on the last row, filled from the left. That is a nearly complete binary tree, and the array stores nothing else. No pointers anywhere: the shape lives in the index arithmetic. The parent of node i is ⌊i/2⌋, its children are 2i and 2i + 1, and each of those is a single shift of i's bits.

A max-heap adds one rule, the max-heap property: every node except the root is at most its parent, A[PARENT(i)] ≥ A[i]. So the largest value sits at the root, and the root of every subtree is the largest value in that subtree. A min-heap flips the rule and keeps the smallest value on top. Only the first A.heap-size cells belong to the heap; the array behind it may be longer.

The height of a node is the number of edges on the longest path down from it to a leaf, and the heap's height is the root's. An n-element heap has height ⌊lg n⌋, so ten elements give height 3. Every basic heap operation in this chapter walks at most one such path, which is why each costs O(lg n).

Try it: tap any node or array cell: its parent and children light up in both pictures, and the code panel shows the arithmetic in binary. Walk visits every node in turn. Drag value to change the selected number until it breaks the rule: the edges that violate the heap property turn coral. Shrink heap-size and watch the height fall to ⌊lg heap-size⌋. Min-heap loads a sorted array, which is a min-heap already. In Rust the indices start at 0, so the formulas become 2i + 1, 2i + 2 and ⌊(i − 1)/2⌋.

What the book says

The (binary) heap data structure is “an array object that we can view as a nearly complete binary tree”, each node of the tree corresponding to an element of the array. The tree is filled on all levels except possibly the lowest, which is filled from the left up to a point. An array A[1 : n] that represents a heap has an attribute A.heap-size: although A[1 : n] may contain numbers, only A[1 : A.heap-size], where 0 ≤ A.heap-size ≤ n, are valid elements of the heap. The root of the tree is A[1].

PARENT(i) returns ⌊i/2⌋, LEFT(i) returns 2i and RIGHT(i) returns 2i + 1. On most computers LEFT computes 2i in one instruction by shifting the binary representation of i left by one bit, RIGHT shifts left and then adds 1, and PARENT shifts i right one bit position. “Good implementations of heapsort often implement these procedures as macros or inline procedures.”

In a max-heap, the max-heap property is that for every node i other than the root, A[PARENT(i)] ≥ A[i]: the largest element is stored at the root, and the subtree rooted at a node contains values no larger than the node itself. The min-heap property is A[PARENT(i)] ≤ A[i], with the smallest element at the root. Heapsort uses max-heaps; min-heaps commonly implement priority queues.

The height of a node is the number of edges on the longest simple downward path from the node to a leaf, and the height of the heap is the height of its root. Since a heap of n elements is based on a complete binary tree, its height is Θ(lg n) (Exercise 6.1-2: exactly ⌊lg n⌋), and the basic operations on heaps take O(lg n) time. The book also warns that the heap data structure is not garbage-collected storage, which later took over the same name.

6.2 · maintaining the heap property

Let the small one sink

Picture a heap that is perfect except at one spot. Node i holds a value smaller than one of its children, but the two subtrees under it are fine max-heaps on their own. The repair is local: look at A[i] and its two children, find the largest of the three, and if that isn't A[i], swap them. The small value has moved down one level and node i is now fine. The subtree it landed in may be broken, though, so do the same thing there. The value floats down until it is at least as large as its children, or has become a leaf.

That is MAX-HEAPIFY(A, i). Each call does a constant amount of work and then calls itself on one child, so the total is one step per level: O(h) on a node of height h, at most O(lg n).

The book states it as the recurrence T(n) ≤ T(2n/3) + Θ(1). Why 2n/3? A child's subtree takes the biggest share of the nodes when the bottom level is exactly half full: then the left subtree is one level deeper than the right one. With 11 nodes the left subtree holds 7, and that share creeps toward 2/3 as the heap grows but never reaches it. Case 2 of the master theorem turns the recurrence into O(lg n).

Try it: Step through MAX-HEAPIFY(A, 2) from Figure 6.2. The blue node is i, yellow nodes are being compared, the green one is largest, and the shaded triangle is the subtree this call is responsible for. Then try Bottom half full: 11 nodes, and the root's 1 sinks all the way down. Watch the subtree at i counter: 11, then 7, which is under 2·11/3. Nothing to do calls it on a node that is already larger than its children. In Rust, the memory strip grows one stack frame per recursive call, each one borrowing the same buffer.

What the book says

MAX-HEAPIFY maintains the max-heap property. Its inputs are an array A with the heap-size attribute and an index i. When it is called, it assumes that the binary trees rooted at LEFT(i) and RIGHT(i) are max-heaps, while A[i] might be smaller than its children. It lets the value at A[i] “float down” in the max-heap so that the subtree rooted at index i obeys the max-heap property.

Each step determines the largest of A[i], A[LEFT(i)] and A[RIGHT(i)] and stores its index in largest. If A[i] is largest, the subtree rooted at node i is already a max-heap. Otherwise positions i and largest swap their contents, which makes node i and its children satisfy the property. The node indexed by largest just had its value decreased, so its subtree might now violate the property, and MAX-HEAPIFY “calls itself recursively on that subtree.”

On a subtree of size at most n, the running time is Θ(1) to fix up the relationships among A[i], A[LEFT(i)] and A[RIGHT(i)], plus the time to run MAX-HEAPIFY on a subtree rooted at one of the children. The children's subtrees each have size at most 2n/3 (Exercise 6.2-2), so T(n) ≤ T(2n/3) + Θ(1), equation (6.1). By case 2 of the master theorem, T(n) = O(lg n). Equivalently, the running time on a node of height h is O(h).

Exercise 6.2-6 observes that the procedure is efficient in constant factors except possibly for the recursive call in line 10, for which some compilers might produce inefficient code, and asks for a version with a loop instead.

6.3 · building a heap

Fix the bottom first

To turn any array into a max-heap, don't start at the top. The whole second half of the array, A[⌊n/2⌋ + 1 : n], is leaves, and a single leaf is already a max-heap. So walk backward from the last parent, ⌊n/2⌋, to the root, and call MAX-HEAPIFY on each node. When a node's turn comes, its children have higher numbers, so they were fixed earlier: exactly what MAX-HEAPIFY needs. That is BUILD-MAX-HEAP.

Its loop invariant: at the start of each iteration, every node i + 1, …, n is the root of a max-heap. It holds at the start because those nodes are leaves, each call keeps it, and when the loop ends i = 0, so node 1, the whole array, is a max-heap. Run the loop the other way, from 1 upward, and the root is repaired before the subtrees under it are ready.

The cost: about n/2 calls of O(lg n) each is O(n lg n), correct but loose. Most nodes sit near the bottom, where MAX-HEAPIFY is cheap. At most ⌈n/2h+1⌉ nodes have height h, and a call on one costs O(h), so the total is at most cn · Σ h/2h ≤ 2cn. Building a heap takes linear time.

Try it: Step through Figure 6.3. Blue is the loop's i; green rings mark the nodes that are already roots of max-heaps, which is the invariant. Each step of line 3 runs a whole MAX-HEAPIFY call. What the book says

BUILD-MAX-HEAP converts an array A[1 : n] into a max-heap by calling MAX-HEAPIFY “in a bottom-up manner.” Exercise 6.1-8 says that the elements in A[⌊n/2⌋ + 1 : n] are all leaves of the tree, so each is a 1-element heap to begin with. BUILD-MAX-HEAP goes through the remaining nodes and runs MAX-HEAPIFY on each one (Figure 6.3).

The loop invariant: at the start of each iteration of the for loop of lines 2–3, each node i + 1, i + 2, …, n is the root of a max-heap. Initialization: before the first iteration i = ⌊n/2⌋, and each node after it is a leaf, the root of a trivial max-heap. Maintenance: the children of node i are numbered higher than i, so both are roots of max-heaps, which is precisely the condition MAX-HEAPIFY(A, i) needs; the call also preserves the property for nodes i + 1, …, n, and decrementing i reestablishes the invariant. Termination: the loop makes exactly ⌊n/2⌋ iterations and ends with i = 0, so each node 1, 2, …, n is the root of a max-heap. “In particular, node 1 is.”

A simple bound is O(n lg n): O(n) calls of O(lg n) each. “This upper bound, though correct, is not as tight as it can be.” An n-element heap has height ⌊lg n⌋ and at most ⌈n/2h+1⌉ nodes of any height h (Exercise 6.3-4), and MAX-HEAPIFY on a node of height h takes O(h). Since n/2h+1 ≥ 1/2 for 0 ≤ h ≤ ⌊lg n⌋ (Exercise 6.3-2) and ⌈x⌉ ≤ 2x for x ≥ 1/2, the total is at most Σh=0⌊lg n⌋ (n/2h) ch ≤ cn Σh=0∞ h/2h ≤ cn · (1/2)/(1 − 1/2)2 = O(n), by equation (A.11). “Hence, we can build a max-heap from an unordered array in linear time.”

6.4 · the heapsort algorithm

Take the top, refill, repeat

Once the array is a max-heap, its largest value sits in A[1]. That value belongs at the very end, in A[n], so swap the two. Now forget the last cell: decrementing A.heap-size takes it out of the heap. The root's two subtrees are still max-heaps; only the new root, a small value pulled up from the bottom, may break the rule, and a single MAX-HEAPIFY(A, 1) repairs it. Do it again with heap-size n − 1, then n − 2, all the way down to 2.

That loop, after one BUILD-MAX-HEAP, is HEAPSORT. The heap shrinks from the right while a sorted run grows into the cells it gives up, so one array holds both and nothing else is needed: heapsort sorts in place, like insertion sort. The build is O(n) and each of the n − 1 MAX-HEAPIFY calls is O(lg n), so the total is O(n lg n), like merge sort but without its extra arrays.

Its loop invariant (Exercise 6.4-2): before each iteration, A[1 : i] is a max-heap holding the i smallest values, and A[i + 1 : n] holds the n − i largest, in sorted order. Input order barely matters: a sorted array is first rebuilt into a heap and then taken apart again, and a reversed one is already a max-heap but still pays for the whole loop.

Try it: Step once to run BUILD-MAX-HEAP, which gives Figure 6.4(a). Each further step either swaps the root to the end (it turns lilac: sorted and out of the heap) or lets the new root sink. Play runs it all. Then try Sorted, Reversed and Random and compare the counters with n lg n. In Rust, look at the memory strip: max_heapify is handed a shorter slice &mut a[..i] of the same buffer, so heap-size is simply that slice's length.

What the book says

HEAPSORT starts by calling BUILD-MAX-HEAP to build a max-heap on the input array A[1 : n]. Since the maximum element is stored at the root A[1], it can be put into its correct final position by exchanging it with A[n]. If the procedure then discards node n from the heap, which it can do by simply decrementing A.heap-size, the children of the root remain max-heaps, but the new root element might violate the max-heap property. Calling MAX-HEAPIFY(A, 1) restores it and leaves a max-heap in A[1 : n − 1]. The procedure repeats this for the max-heap of size n − 1 down to a heap of size 2.

HEAPSORT takes O(n lg n) time, since the call to BUILD-MAX-HEAP takes O(n) time and each of the n − 1 calls to MAX-HEAPIFY takes O(lg n) time. Exercise 6.4-2 argues correctness with the invariant that, at the start of each iteration of the for loop of lines 2–5, A[1 : i] is a max-heap containing the i smallest elements of A[1 : n], and A[i + 1 : n] contains the n − i largest elements, sorted. Exercises 6.4-3 to 6.4-5 ask about already sorted inputs and show that the worst case, and the best case for distinct elements, are both Ω(n lg n).

As the chapter's opening puts it, heapsort runs in O(n lg n) like merge sort, and like insertion sort it sorts in place: “only a constant number of array elements are stored outside the input array at any time.” So “heapsort combines the better attributes of the two sorting algorithms we have already discussed.”

Since any comparison-based sort needs Ω(n lg n) comparisons (Chapter 8), heapsort is asymptotically optimal among comparison sorts. Still, the book notes that a good implementation of quicksort (Chapter 7) usually beats it in practice.

6.5 · priority queues

The job queue that always knows who's next

A shared computer has a pile of waiting jobs, each with a priority. Whenever the processor is free, the scheduler wants the most urgent job right now; meanwhile new jobs keep arriving, and an old job sometimes becomes more urgent. A sorted list would make arrivals slow; an unsorted one would make every pick a full scan. A max-priority queue does both in O(lg n): it is a max-heap whose elements are pointers to job objects, ordered by each job's key.

Four operations. MAXIMUM reads the root in Θ(1). EXTRACT-MAX takes the root, moves the last leaf into its place and lets MAX-HEAPIFY sink it — the body of heapsort's loop. INCREASE-KEY raises one job's key and floats it up, swapping with its parent, like insertion sort's inner loop walking toward the root. INSERT adds a leaf with key −∞, then calls INCREASE-KEY to give it its real key.

The heap moves elements around, but the application holds on to its job objects. So each object carries a handle — here, its current index in the array — and every exchange must update the two handles involved. Without it, “find the index of job x” would be a linear search.

Try it: press Extract max and watch the root go to the processor and the last leaf sink. Press Insert to add the next waiting job. The selected job (yellow) starts as Figure 6.5's key-4 job: press Increase key with the slider at 15 and watch its handle i change on every exchange. Then set the slider below the job's key, or empty the queue, or fill all 12 slots, and see the book's three errors.

What the book says

A priority queue is a data structure for maintaining a set S of elements, each with an associated value called a key. A max-priority queue supports INSERT(S, x, k), MAXIMUM(S), EXTRACT-MAX(S), and INCREASE-KEY(S, x, k), where the new key k is assumed to be at least as large as x's current key. One application is scheduling jobs on a shared computer: “When a job is finished or interrupted, the scheduler selects the highest-priority job from among those pending by calling EXTRACT-MAX.” A min-priority queue (INSERT, MINIMUM, EXTRACT-MIN, DECREASE-KEY) can drive an event-driven simulator, with each event's time of occurrence as its key.

The elements of the queue correspond to application objects, so the implementation needs a way to map objects to and from array indices. One way is handles: additional information stored in the objects and heap elements, often opaque, “thereby maintaining an abstraction barrier” between the application and the priority queue. Because heap elements change locations during heap operations, relocating an element must also update the array indices in the corresponding handles; typically, the worst-case overhead for maintaining handles is O(1) per access. The alternative is a mapping inside the queue, such as a hash table, with O(1) added expected time but Θ(n) in the worst case.

MAX-HEAP-MAXIMUM runs in Θ(1) time and reports “heap underflow” on an empty heap. MAX-HEAP-EXTRACT-MAX is similar to the for loop body of HEAPSORT and runs in O(lg n) time. MAX-HEAP-INCREASE-KEY first checks that the new key will not decrease the key, then traverses a simple path toward the root, exchanging an element with its parent while the element's key is larger; the path has length O(lg n). MAX-HEAP-INSERT checks for room (“heap overflow”), adds a new leaf whose key is −∞, and calls MAX-HEAP-INCREASE-KEY to set the key to its correct value.

“In summary, a heap can support any priority-queue operation on a set of size n in O(lg n) time, plus the overhead for mapping priority queue objects to array indices.”

problem 6-1 · building a heap using insertion

Top-down or bottom-up?

You already have a priority queue with INSERT, so here is the obvious way to turn an array into a heap: start with a one-element heap and insert the other elements one at a time. That is BUILD-MAX-HEAP′. Each insertion adds a leaf and floats it up toward the root.

BUILD-MAX-HEAP works the other way round: every leaf is already a tiny heap, so it calls MAX-HEAPIFY on the nodes from ⌊n/2⌋ down to 1 and lets values sink. The two procedures don't always produce the same heap: on ⟨1, 2, 3⟩ the bottom-up build gives ⟨3, 2, 1⟩, but insertion gives ⟨3, 1, 2⟩. Both are valid max-heaps; the heap property allows many arrangements.

The real difference is cost. Most nodes of a heap are near the bottom, and sinking from there is short, which is why BUILD-MAX-HEAP is O(n). An insertion, though, floats a leaf up as far as the root. On an increasing array every new element is the largest so far and climbs the whole height, ⌊lg i⌋ levels, so BUILD-MAX-HEAP′ does Θ(n lg n) work in the worst case.

Try it: press Play on the book's array and compare the two finished trees: the red nodes are where they differ. Then pick Increasing, drag n to 15 and play again: insertion needs 34 exchanges, bottom-up only 11. Random deals a new array each time.

What the book says

“One way to build a heap is by repeatedly calling MAX-HEAP-INSERT to insert the elements into the heap.” The procedure BUILD-MAX-HEAP′(A, n) sets A.heap-size = 1 and then, for i = 2 to n, calls MAX-HEAP-INSERT(A, A[i], n). It assumes that the objects being inserted are just the heap elements.

problem 6-2 · analysis of d-ary heaps

Wider trees, shorter paths

Nothing forces a heap to be binary. In a d-ary heap every inner node has d children (except perhaps one). It still lives in a plain array, level by level: the root at index 1, its d children at 2 … d + 1, and in general the children of node i sit at d(i − 1) + 2 through di + 1, with the parent at ⌊(i − 2)/d⌋ + 1. Counting from 0, as Rust does, it is tidier: children di + 1 … di + d, parent ⌊(i − 1)/d⌋.

A wider tree is a shorter one: the height is Θ(logd n) = Θ(lg n / lg d). That helps every operation that walks up: INSERT and INCREASE-KEY compare once per level, so they cost O(logd n). EXTRACT-MAX walks down, and at each level it must look at all d children to find the largest, so it costs O(d logd n).

So d is a dial. Turn it up when inserts and key increases far outnumber extractions (the case in some graph algorithms later in the book); leave it at 2 or 4 when extractions dominate.

Try it: in Array layout, drag d from 2 to 6 and watch the same twelve keys fold into a flatter tree. problem 6-3 · young tableaus

A heap folded into a grid

Picture a 4 × 4 box of numbered tiles where every row increases to the right and every column increases downwards. That is an m × n Young tableau. Empty cells hold ∞, so they gather at the bottom right, and the tableau holds r ≤ mn real numbers. The smallest one is always in the top-left corner, just as a min-heap keeps its smallest key at the root: here each cell has two “children”, the cell to its right and the cell below.

So the heap procedures carry over. EXTRACT-MIN takes Y[1, 1], puts ∞ in its place and lets the ∞ sink: swap it with the smaller of its right and lower neighbours, then solve the smaller (m − 1) × n or m × (n − 1) problem that starts there. Each move goes right or down, so there are at most m + n − 2 of them: O(m + n). INSERT is the mirror image: put the key in the bottom-right cell and float it up or left. Insert n² numbers into an n × n tableau and extract them all again, and they come out sorted, in O(n³).

Searching is the neat part. Start at the top-right corner. If that cell is bigger than x, its whole column below is bigger too: drop the column. If it is smaller, its whole row to the left is smaller: drop the row. Each comparison throws away a row or a column, so the search ends within m + n − 1 steps.

Try it: in Extract-min, press Extract min and follow the ∞ as it sinks. In Insert, keep pressing Insert next until the tableau is full and the error line lights up. In Search, set x and press Find x: try 12, then 7, which isn't there. In Sort, Sort 16 sorts sixteen numbers with nothing but inserts and extracts. The memory strip shows the Rust Vec<Vec<u32>>: four separate row buffers.

What the book says

“An m × n Young tableau is an m × n matrix such that the entries of each row are in sorted order from left to right and the entries of each column are in sorted order from top to bottom.” Some of the entries may be ∞, which are treated as nonexistent elements, so a Young tableau can hold r ≤ mn finite numbers.

An array viewed as a nearly complete binary tree, one node per element. Not the garbage-collected memory that shares the name.
nearly complete binary tree
Every level is full except perhaps the lowest, which is filled from the left.
heap-size
How many of the array's first cells belong to the heap. The cells after it are just array.
PARENT, LEFT, RIGHT
⌊i/2⌋, 2i and 2i + 1 in the book's 1-based arrays; ⌊(i − 1)/2⌋, 2i + 1 and 2i + 2 counting from 0.
max-heap property
Every node other than the root is at most its parent, so the largest value is at the root.
min-heap
The mirror image: every parent is at most its children, and the smallest value is at the root.
height of a node
Edges on the longest path from the node down to a leaf. The heap's height is the root's: ⌊lg n⌋.
leaf
A node with no children. In an n-element heap they are nodes ⌊n/2⌋ + 1 to n.
MAX-HEAPIFY
Lets A[i] float down, swapping with its larger child, until its subtree is a max-heap. O(lg n).
BUILD-MAX-HEAP
Turns any array into a max-heap by calling MAX-HEAPIFY from ⌊n/2⌋ down to 1. O(n).
loop invariant
A statement true before every iteration of a loop, used to prove the loop correct: here, nodes i + 1 … n are heap roots.
heapsort
Build a max-heap, then swap the root to the end and repair, n − 1 times. O(n lg n).
in place
Sorting with only a constant number of elements outside the input array at any time.
priority queue
A set of elements, each with a key, that hands out the largest (or smallest) key first.
key
The value that decides an element's place in the heap, such as a job's priority.
INSERT / MAXIMUM / EXTRACT-MAX / INCREASE-KEY
The operations of a max-priority queue: add, peek at the largest, remove the largest, raise a key.
min-priority queue
Supports INSERT, MINIMUM, EXTRACT-MIN and DECREASE-KEY, for example in an event-driven simulator.
handle
Extra information kept with an object and its heap element so each can find the other, such as the element's array index.
heap underflow / overflow
The errors for taking from an empty heap and inserting into a full array.
d-ary heap
A heap whose nonleaf nodes have d children instead of two: shorter, but each node has more children to compare.
Young tableau
An m × n matrix whose rows and columns are each sorted, with ∞ marking empty cells.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

<< and >>
Bit shifts. i << 1 doubles, i >> 1 halves and rounds down: the heap's index arithmetic in one instruction.
checked_sub
Subtraction that returns None instead of panicking when a usize would go below 0, as for the root's parent.
impl Fn(…) -> …
A parameter that accepts any closure of that shape, such as the max-heap or min-heap comparison.
if as an expression
let largest = if … { l } else { i }; An if produces a value, so no ternary operator is needed.
reborrow
Passing a &mut on to a call lends it for that call only; the caller can use it again afterwards.
loop
An endless loop left only by return or break: the iterative MAX-HEAPIFY, with no stack frame per level.
(0..n / 2).rev()
A range is an iterator; rev() walks it backward. Integer division rounds down, the book's ⌊n/2⌋.
T: Ord
A trait bound: the generic code works for any totally ordered type. f64 is not Ord, because NaN compares with nothing.
&mut a[..i]
A mutable borrow of just the first i items of the same buffer. Its length plays the book's heap-size.
Option and ?
None instead of “heap underflow”; ? returns early with None when a value is missing.
BinaryHeap, Reverse
The standard library's max-heap. Wrapping keys in Reverse flips their order and makes a min-queue.
const generics
A type parameter that is a number, like D in a d-ary heap, fixed at compile time.
