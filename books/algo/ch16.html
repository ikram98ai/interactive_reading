Amortized Analysis

A data structure may spend almost nothing on most operations and a great deal on a few. Amortized analysis averages the cost over a whole sequence of operations, in the worst case and with no probability involved, to show that the rare expensive operations are paid for by the many cheap ones.

“An amortized analysis guarantees the average performance of each operation in the worst case.” — Cormen, Leiserson, Rivest & Stein

16.1 · aggregate analysis: stack operations

One big sweep, paid for by the pushes

A stack is a pile of plates. PUSH puts one on top and POP takes the top one off, one step each. Now add MULTIPOP(S, k), which sweeps the top k plates off in a single call, or the whole pile if it is shorter. One call can suddenly cost as much as the pile is tall.

Add up the worst case call by call and the news looks bad: a MULTIPOP costs up to n, a sequence may hold n of them, so n operations cost O(n2). That is true, but not tight. A plate can only be popped after it was pushed, so across the whole sequence the pops, MULTIPOP's included, never outnumber the pushes. The total cost T(n) is at most n pushes plus n pops: O(n).

Divide by n and every operation, MULTIPOP too, gets an amortized cost of O(1). This is aggregate analysis: bound the total of any sequence, then share it equally. It is a worst-case guarantee, not an average over luck.

Try it: press Push a few times, then Multipop with the slider on 4. One operation costs 4, yet the green average line hardly moves. Then press Adversary: it fills the stack and sweeps it empty, twice, the tallest sequence the O(n2) argument can imagine. Compare the long grey bar (n × the worst operation) with the short green one (what the sequence really cost). In the Rust view the memory strip shows the Vec buffer: pops never shrink it.

What the book says

The chapter opens with a gym membership whose monthly fee is spread over the days of the month, and then names the idea: in an amortized analysis you average the time of a sequence of data-structure operations over all the operations performed, so that a single expensive operation can sit in a sequence whose average cost is small. Amortized analysis differs from average-case analysis “in that probability is not involved.” An amortized analysis “guarantees the average performance of each operation in the worst case.”

In aggregate analysis you show that for all n, a sequence of n operations takes T(n) worst-case time in total. The average cost, or amortized cost, per operation is therefore T(n)/n, and that figure applies to every operation, even when the sequence mixes several types.

The stack of Section 10.1.3 has PUSH and POP, each O(1), so each is given cost 1. The new MULTIPOP(S, k) removes the k top objects, popping the entire stack if it holds fewer than k; on a stack of s objects its cost is min{s, k}. Figure 16.1 shows MULTIPOP(S, 4) and then MULTIPOP(S, 7) on a stack of six objects.

Since the stack holds at most n objects, one MULTIPOP costs O(n) and a sequence of n operations is bounded by O(n2), a correct but loose bound. The tight argument: “An object cannot be popped from the stack unless it was first pushed.” So the number of POP calls on a nonempty stack, those inside MULTIPOP included, is at most the number of PUSH operations, which is at most n. Any sequence of n operations on an initially empty stack costs O(n), and the amortized cost of all three operations is O(n)/n = O(1).

16.1 · aggregate analysis: incrementing a binary counter

The carry that rarely travels far

A binary counter is a row of bits that counts up from 0. To add 1, INCREMENT starts at the lowest bit and ripples a carry: every 1 flips to 0 and the carry moves up, until it meets a 0 and flips that to 1. Usually that is one or two flips. But 0111 1111 becomes 1000 0000, and that call flips all eight bits. The cost of an INCREMENT is the number of bits it flips.

So a k-bit counter can cost Θ(k) in one call, and n calls look like O(nk). Correct, not tight, and the same shape as MULTIPOP: not every call is the big one. Look at one bit at a time. A[0] flips on every call, A[1] on every other call, A[2] on every fourth. In n calls bit A[i] flips ⌊n/2i⌋ times.

Add those counts up: n + n/2 + n/4 + … is less than 2n. That is aggregate analysis again: the whole sequence costs O(n), so each INCREMENT has amortized cost O(1), however wide the counter is.

Try it: press Step a few times to follow one carry line by line, or Increment to run a whole call. The bars under the bits count each bit's flips; the strip at the bottom stacks them against the 2n limit. Press Run 16 to reproduce Figure 16.2, then keep pressing it: at the 16th, 32nd, 64th and 128th call the carry runs far, and the total still stays under 2n. At the 256th call the counter wraps to 0.

What the book says

The k-bit counter is an array A[0 : k − 1] of bits whose lowest-order bit is A[0] and highest-order bit A[k − 1], so that it stores x = Σ A[i]·2i. Initially x = 0. To add 1 (modulo 2k) you call INCREMENT. Each iteration of the while loop in lines 2–4 adds a 1 into position i: if A[i] = 1 the bit flips to 0 and a carry goes to position i + 1; otherwise the loop ends and, if i < k, line 6 flips a 0 to a 1. If the loop ends with i = k, the call flipped all k bits from 1 to 0. The cost of each INCREMENT is linear in the number of bits flipped.

Figure 16.2 runs an 8-bit counter from 0 to 16 with 16 INCREMENT calls, shading the bits that flip and keeping a running cost: the total after the sixteenth call is 31, less than twice the number of calls.

As with the stack, a cursory analysis gives a bound that is correct but not tight. A single INCREMENT takes Θ(k) time in the worst case, when every bit is 1, so n calls on an initially zero counter take O(nk). But not all bits flip on each call, just as not every MULTIPOP call pops many objects.

A[0] flips every call. A[1] flips only every other call, ⌊n/2⌋ times in n calls; A[2] only every fourth call, ⌊n/4⌋ times. In general, for i = 0, 1, …, k − 1, bit A[i] flips ⌊n/2i⌋ times in a sequence of n INCREMENT calls on an initially zero counter; for i ≥ k the bit does not exist. The total number of flips is Σ ⌊n/2i⌋ < n Σ 1/2i = 2n (by equation (A.7)). So n INCREMENT calls take O(n) time in the worst case, and the amortized cost per operation is O(n)/n = O(1).

16.2 · the accounting method

Charge a little extra, keep it for later

Aggregate analysis gives every operation the same average. The accounting method is pickier: it sets a price for each kind of operation, its amortized cost, which may be more or less than the operation really costs. When the price is higher, the difference is stored as credit on an object in the data structure. When it is lower, the operation pays the rest out of stored credit.

One rule keeps the books honest: the total charged must never fall below the total actually spent, so the credit never goes negative. Take the stack. Charge $2 for a PUSH: $1 pays for the push and $1 rests on the new plate. POP and MULTIPOP are charged $0, because the plate being removed carries the dollar that pays for it. Every plate always has $1 on it, so the bank cannot be negative.

The counter works the same way. Setting a bit to 1 is charged $2: $1 flips the bit and $1 stays on it. Resetting a bit to 0 is then free, since every 1-bit holds a dollar. INCREMENT sets at most one bit, so it is charged at most $2. The dollars are bookkeeping for the analysis only; the real code never stores them.

Try it: pick Stack or Counter, press the operation buttons and watch the dollars move: charged in, $1 out to pay, the rest on the object. The bank always equals the dollars on the objects. Now choose a charge of $1: nothing is left over to store, so the first POP (or the second INCREMENT) has no credit to draw on, and the bank turns coral. Try $3 too: safe, just wasteful. In the Rust view, credit is an i64 so a deficit shows as a negative number.

What the book says

In the accounting method you assign differing charges to different operations, with some charged more or less than they actually cost. The amount charged is the operation's amortized cost. When it exceeds the actual cost, you assign the difference to specific objects in the data structure as credit, which can pay for later operations whose amortized cost is less than their actual cost. This differs from aggregate analysis, in which all operations have the same amortized cost.

The amortized costs must be chosen so that the total amortized cost of any sequence of n operations is an upper bound on its total actual cost: the sum of the amortized costs is at least the sum of the actual costs, inequality (16.1). The total credit stored is the difference of the two sums, so it must be nonnegative at all times. If it ever became negative, the total amortized cost at that moment would be below the total actual cost, and would not be an upper bound.

For the stack the actual costs are PUSH 1, POP 1 and MULTIPOP min{s, k}, and the amortized costs are PUSH 2, POP 0 and MULTIPOP 0. Let $1 represent each unit of cost. Pushing a plate uses $1 for the actual push and leaves $1 of credit, placed on top of the plate, so every plate on the stack has $1 on it. A POP pays by taking the $1 off the plate; MULTIPOP is repeated POPs. The stack never has a negative number of plates, so the credit is never negative, and the total amortized cost O(n) bounds the actual cost.

For the counter the amortized cost of setting a 0-bit to 1 is $2: $1 pays to set the bit and the second $1 stays on it as credit for a later reset. At any time every 1-bit has $1 on it, so resetting costs nothing. INCREMENT sets at most one bit to 1 (line 6), so its amortized cost is at most $2; the number of 1-bits is never negative, and the total amortized cost of n INCREMENT calls, O(n), bounds the total actual cost.

The charges are for the analysis only: the chapter's introduction says they need not, and should not, appear in the code.

16.3 · the potential method: stack operations

The height of the stack pays the bill

In the accounting method every plate carries its own dollar. The potential method keeps the same prepaid work but stops pinning it to plates: the work is stored as potential energy in the whole data structure, ready to be released when an expensive operation comes along.

You pick a potential function Φ that turns the structure into a number. Here Φ is the number of plates. The amortized cost of an operation is its actual cost plus the change in potential: ĉ = c + Φ(after) − Φ(before). A PUSH costs 1 and raises Φ by 1, so ĉ = 2. A POP costs 1 and lowers Φ by 1, so ĉ = 0. MULTIPOP(k) really costs k′ = min(s, k) and lowers Φ by exactly k′, so ĉ = 0 however tall the stack was.

Add the amortized costs up and the Φ terms cancel in pairs (they telescope): Σĉ = Σc + Φ(final) − Φ(start). If Φ never falls below its starting value, the amortized total is an upper bound on the true total, so n operations cost O(n). Choose a Φ that does fall below the start and the guarantee is gone.

Try it: press Push five or six times, then Multipop with k = 4. Four plates leave and the actual cost is 4, but the tank drops by 4 too, so ĉ is 0. Press Run sequence to replay twelve operations and read the totals. Then switch Φ to −size: pushes now look free, yet the amortized total falls below the actual total, so it proves nothing.

What the book says

The potential method represents the prepaid work as “potential energy,” or just “potential,” which can be released to pay for future operations. The potential applies to the data structure as a whole rather than to specific objects within it.

Start from an initial data structure D0 and apply n operations. The ith operation has actual cost ci and turns Di−1 into Di. A potential function Φ maps each Di to a real number Φ(Di), and the amortized cost of the ith operation is ĉi = ci + Φ(Di) − Φ(Di−1) (equation 16.2). Summing, the Φ terms telescope: Σĉi = Σci + Φ(Dn) − Φ(D0) (equation 16.3).

If Φ(Dn) ≥ Φ(D0), the total amortized cost is an upper bound on the total actual cost. Since you don't always know how many operations will come, require Φ(Di) ≥ Φ(D0) for every i; the simplest way is to define Φ(D0) = 0 and show Φ(Di) ≥ 0. A positive potential difference means the operation was overcharged and the potential rises; a negative one means an undercharge, paid for by the decrease in potential. Different potential functions may give different amortized costs and still be upper bounds on the actual costs, and the best one depends on the time bounds you want.

For the stack, define Φ as the number of objects on the stack. Then Φ(D0) = 0 and Φ(Di) ≥ 0. A PUSH onto a stack of s objects has potential difference (s + 1) − s = 1, so its amortized cost is 1 + 1 = 2. A MULTIPOP that pops k′ = min{s, k} objects costs k′ and has potential difference −k′, so its amortized cost is 0, and an ordinary POP likewise. All three are O(1), so the total amortized cost of n operations is O(n), and so is the worst-case cost.

16.3 · the potential method: incrementing a binary counter

Every 1 is a wound spring

Back to the binary counter. Let the potential be b, the number of 1-bits in the counter: Φ(Di) = bi. Picture every 1 as a spring that an earlier INCREMENT wound and a later carry will release.

An INCREMENT that resets t bits to 0 and sets one bit to 1 costs at most t + 1 flips. The number of 1s changes by at most 1 − t: it gains the new 1 and loses the t that were reset. So the amortized cost is at most (t + 1) + (1 − t) = 2, however long the carry chain. The long chains release many springs at once, and those springs were wound by earlier, cheap increments.

The potential method handles a counter that does not start at 0 just as easily. If it starts with b0 ones and ends with bn, then Σc ≤ 2n − bn + b0. Since b0 ≤ k, that is still O(n) once n is at least about k: the starting springs are a one-time bill.

Try it: press Run 16 from Start at 0. The yellow bars are the actual cost of each INCREMENT and rise and fall with the carry chain, but the mint dots (ĉ) never climb above the dashed line at 2. Then pick Start at 127 (seven springs already wound) and run again: the first INCREMENT costs 8, its ĉ is still 2, and the total meets the bound exactly. Start at 255 shows the wrap-around, where no bit is set at all.

What the book says

Define the potential of the counter after the ith INCREMENT to be bi, the number of 1-bits in the counter after the ith operation. Suppose the ith INCREMENT resets ti bits to 0. Its actual cost ci is then at most ti + 1, since in addition to resetting ti bits, it sets at most one bit to 1.

If bi = 0, the ith operation reset all k bits, so bi−1 = ti = k. If bi > 0, then bi = bi−1 − ti + 1. In either case bi ≤ bi−1 − ti + 1, so the potential difference is at most 1 − ti, and the amortized cost is at most (ti + 1) + (1 − ti) = 2.

If the counter starts at 0, then Φ(D0) = 0 and Φ(Di) ≥ 0 for all i, so the total amortized cost of n INCREMENT operations is an upper bound on the total actual cost, and the worst-case cost of n INCREMENT operations is O(n).

The potential method also analyzes the counter when it does not start at 0. The counter starts with b0 1-bits and after n INCREMENT operations has bn, where 0 ≤ b0, bn ≤ k. Rewriting equation (16.3) with Φ(D0) = b0, Φ(Dn) = bn and ĉi ≤ 2 gives Σci ≤ 2n − bn + b0. Because b0 ≤ k, the total actual cost is O(n) as long as k = O(n): if at least n = Ω(k) INCREMENT operations occur, the total actual cost is O(n), no matter what initial value the counter contains.

16.4 · dynamic tables

A table that has to move house

You often don't know in advance how many items a table will hold. Reserve a block of slots and sooner or later it fills up. A table lives in one contiguous block, so the only cure is to allocate a bigger block, copy every item across and free the old block. That copy is the expensive step; dropping an item into a free slot is the cheap one.

How much bigger should the new block be? The book's rule is to double it. With insertions only, the table is then never less than half full, so at most half of the space is wasted. The load factor α(T) = num ÷ size measures this: keep it bounded below by a constant and the unused space stays a constant fraction of the total. An empty table has no slots, and its load factor is defined to be 1. Later scenes also shrink a table after deletions.

The machine runs TABLE-INSERT under three growth rules. Doubling is the book's. Growing by a factor of 1.5, or by a fixed 10 slots, are the machine's own comparison, drawn for the very same inserts. The chart plots total cost ÷ inserts so far, with a dashed line at 3, the book's bound for doubling. The fixed step copies everything again every ten inserts, so the more you insert, the worse its average gets.

Try it: pick Double ×2 and press Insert 16: the table jumps from 1 to 2, 4, 8 and 16 slots, and the copy sweeps across the new block (lines 5–9 of TABLE-INSERT). Click Insert to go one insert at a time and watch the memory strip free the old buffer. Then press Insert 100 and switch between the three rules: the table and the cost numbers change, and the +10 curve climbs while ×2 stays under 3.

What the book says

You do not always know in advance how many items a table will hold. If the space allocated turns out to be too small, the program must reallocate the table with a larger size and copy all items from the original table into the new, larger one; if many items have been deleted, it may be worthwhile to reallocate with a smaller size. The section shows that the amortized cost of insertion and deletion is only O(1), even though an operation that triggers an expansion or a contraction has a large actual cost, and that the unused space never exceeds a constant fraction of the total space.

The details of the data structure that organizes the table are unimportant: it could be a stack, a heap, a hash table or something else. The table supports TABLE-INSERT, which inserts an item occupying a single slot, and TABLE-DELETE, which removes an item and frees a slot.

The load factor α(T) of a nonempty table T is the number of items stored in the table divided by the size (number of slots) of the table. An empty table, one with no slots, has size 0 and its load factor is defined to be 1. “If the load factor of a dynamic table is bounded below by a constant, the unused space in the table is never more than a constant fraction of the total amount of space.”

Because the table must always reside in contiguous memory, expansion means allocating a new array and copying the items from the old table into it. A common heuristic allocates a new table with twice as many slots as the old one. If the only table operations are insertions, the load factor is then always at least 1/2, so the wasted space never exceeds half the total space.

TABLE-INSERT keeps three attributes: T.table points to the block of storage, T.num is the number of items and T.size the number of slots; initially T.num = T.size = 0. Counting a cost of 1 per elementary insertion (line 10, and each item copied in line 6), the actual running time is linear in that count. An expansion occurs when lines 5–9 execute. The ith insert costs i if it expands (1 for line 10 plus i − 1 copies) and 1 otherwise, and it expands only when i − 1 is an exact power of 2.

16.4.1 · table expansion

Double the shelf when it fills

A bookshelf with eight slots is full, and a ninth book arrives. You buy a shelf with sixteen slots, carry all eight books across, give the old shelf away, and only then put the new book down. That day is expensive, but the next expensive day is eight books away. A dynamic table does the same with an array: TABLE-INSERT finds the table full, allocates a table with twice as many slots, copies every item over, frees the old table, and stores the new item.

Count one unit for each item written into a slot. An insertion that finds room costs 1. The insertion that finds the table full costs i: i − 1 copies plus the new item. One insertion can cost Θ(n), but the table expands only when i − 1 is an exact power of 2, so the expensive insertions are rare: any n insertions cost less than 3n in total.

The book proves it with all three methods. Aggregate: the copying costs 1, 2, 4, 8, … add up to less than 2n. Accounting: charge $3 per insertion; $1 pays for the write, $1 stays on the new item and $1 stays on an older item, so a full table has $1 on every item to pay for moving it. Potential: Φ(T) = 2·T.num − T.size is 0 right after an expansion, grows by 2 per insertion and has reached T.size when the table is full. It is the accounting view's stored credit, kept for the table as a whole instead of on single items.

Try it: press Insert until the table is full, then once more and watch lines 5–9 run: new table, copy, free, swap. Then flip between Aggregate, Accounting and Potential: the same insertions, three ledgers. Press Insert × 8 a few times; the average cost never climbs above 3.

What the book says

Because the table must sit in contiguous memory, “the system must allocate a new array for the larger table and then copy items from the old table into the new table.” A common heuristic “allocates a new table with twice as many slots as the old one.” If the only operations are insertions, the load factor is then always at least 1/2, so the wasted space never exceeds half the table. In TABLE-INSERT, T.table points to the storage, T.num counts the items and T.size the slots; an empty table has both equal to 0.

The cost of an operation is the number of elementary insertions, in lines 6 and 10; allocating and freeing in lines 5 and 7 is dominated by the copying. Operation i costs 1 if there is room, and i if the table is full: 1 for line 10 plus i − 1 copies. That gives O(n) in the worst case for one operation and O(n2) for n, but “This bound is not tight”, because the table rarely expands.

Aggregate analysis: the ith operation costs i when i − 1 is an exact power of 2 and 1 otherwise, so the total is at most n + Σ 2j over j = 0 … ⌊lg n⌋, which is less than n + 2n = 3n. The amortized cost of one operation is at most 3.

Accounting (Figure 16.3): right after an expansion to size m the table holds m/2 items and no credit. Each call charges $3. The elementary insertion “costs $1”, another $1 stays on the item inserted, and the third $1 stays on one of the m/2 items already in the table. By the time the table is full, every item has $1 to pay for being reinserted.

Potential (Figure 16.4): Φ(T) = 2(T.num − T.size/2) is 0 after an expansion, rises by 2 per insertion, equals T.size when the table fills, and is never negative because the table is at least half full. An insertion without expansion has ΔΦ = 2 and amortized cost 1 + 2 = 3. One with an expansion has ΔΦ = 3 − i and amortized cost i + (3 − i) = 3. The first insertion is left as Exercise 16.4-1.

16.4.2 · table expansion and contraction

Shrink at a quarter, not at a half

Deleting is the mirror image of inserting. A table that is nearly empty wastes space, so it should shrink: allocate a smaller table, copy the items over, free the old one. The obvious rule mirrors doubling: halve the table as soon as a deletion leaves it less than half full.

That rule is a trap. Take a full table and insert once: it doubles and is just over half full. Delete twice: it is now less than half full, so it halves and is nearly full again. Two insertions later it doubles again. Every second operation copies Θ(n) items, so n operations cost Θ(n2). After an expansion too few deletions follow to pay for a contraction, and after a contraction too few insertions follow to pay for an expansion.

The fix is a gap between the two triggers: still double when the table is full, but halve it only when it falls below a quarter full. Either resize leaves the table about half full, a long walk from the next trigger in both directions. The potential Φ makes it precise: it is 0 at load factor ½ and climbs by 2 per insertion above half or by 1 per deletion below half, so it has built up to num by the time a resize fires. Every operation then has amortized cost at most 3.

Try it: with Halve below ½ selected, press Play: the bars spike on every second operation and the dots (amortized cost) leave the dashed line at 3. Switch to Halve below ¼ and press Play again: after the first doubling the table never resizes. Then press Insert and Delete yourself and watch the dot walk along the V.

What the book says

Table contraction is analogous to expansion: when the number of items drops too low, you “allocate a new, smaller table and then copy the items from the old table into the new one.” A good strategy keeps two properties: the load factor is bounded below by a positive constant as well as above by 1, and the amortized cost of a table operation is bounded above by a constant. The actual cost of an operation is the number of elementary insertions or deletions.

Halving the table whenever a deletion would leave it less than half full keeps the load factor from dropping below 1/2, but “it can also cause the amortized cost of an operation to be quite large.” Perform n operations on a table of size n/2, n a power of 2. The first n/2 are insertions, costing Θ(n) in all, and leave T.num = T.size = n/2. The second n/2 are insert, delete, delete, insert, insert, delete, delete, insert, insert, …: the first insertion expands the table to size n, the two deletions contract it back, and so on. Each of the Θ(n) resizes costs Θ(n), so the total is Θ(n2) and the amortized cost Θ(n).

“Allow the load factor of the table to drop below 1/2.” Keep doubling when an insertion meets a full table, but halve the table when a deletion makes it less than 1/4 full. The load factor is then at least 1/4, and it is 1/2 right after a contraction. An expansion or contraction should use up all the built-up potential, so that the potential is 0 whenever the load factor is 1/2 (Figure 16.5).

The book omits the code for TABLE-DELETE as analogous to TABLE-INSERT, and assumes that a contraction happens after the item is deleted and that T.size = 0 whenever T.num = 0. The potential is Φ(T) = 2(T.num − T.size/2) if α(T) ≥ 1/2 and T.size/2 − T.num if α(T) < 1/2 (equation 16.5): the potential of an empty table is 0 and it is never negative.

Without a resize and without crossing α = 1/2, the amortized cost of an insertion is 1 + 2 = 3 at or above 1/2 and 1 + (−1) = 0 below it, and that of a deletion is 1 + (−2) = −1 at or above 1/2 and 1 + 1 = 2 below it. A deletion that contracts has Φ before equal to size/4, the same as its actual cost, and Φ = 1 after, giving amortized cost 1. The two crossing cases cost 2 and 0, and an expansion costs 3. Since every amortized cost is bounded by a constant, any sequence of n operations takes O(n) actual time. Figure 16.6 plots num, size and Φ over a mixed sequence.

problem 16-1 · binary reflected Gray code

Counting with one change at a time

Count in binary and one step can flip many bits at once: 0111 becomes 1000 and all four bits change. A Gray code counts so that every step flips exactly one bit. The binary reflected one is built with a mirror. Take the code for k − 1 bits, write it again in reverse order, put a 1 in front of the reversed copy (and a 0 in front of the original), and join the two lists. A mirror repeats the last code of the first half as the first code of the second, so the seam differs only in the new bit.

Part (a) asks which bit flips between index i − 1 and index i. Write i in plain binary: it is the position of the lowest 1 of i. Stepping from 3 to 4 (011 to 100) the lowest 1 of 4 is bit 2, and the Gray code flips bit 2. So the whole sequence needs only one flip per step, once you can find that bit.

Part (b) asks for the whole sequence in Θ(2k) time. Finding the lowest 1 means testing bits 0, 1, 2, … of i until a 1 turns up: trailing zeros of i, plus one. That is exactly the carry chain of INCREMENT in section 16.1, so by the same aggregate argument the tests over all 2k − 1 steps add up to fewer than 2 · 2k. The scan is the whole cost; the flip itself is constant.

Try it: in Reflect, press Step to watch the mirror build the code for k = 2, 3, 4. Then switch to Count and press Play: the binary counter above flips several bits at once, the Gray code below flips one, and the scan for the lowest 1 shows which. Try k = 2 and 3 with the slider.

What the book says

“A binary Gray code represents a sequence of nonnegative integers in binary such that to go from one integer to the next, exactly one bit flips every time.” The binary reflected Gray code of the integers 0 to 2k − 1 is defined recursively. For k = 1 it is ⟨0, 1⟩. For k ≥ 2, form the code for k − 1, form its reflection, which is the sequence in reverse, add 2k−1 to each integer of the reflection, and concatenate the two sequences.

For k = 2 the reflection of ⟨0, 1⟩ is ⟨1, 0⟩, adding 2 gives ⟨3, 2⟩, and the result is ⟨0, 1, 3, 2⟩, in binary ⟨00, 01, 11, 10⟩. For k = 3 the reflection of that is ⟨2, 3, 1, 0⟩, adding 4 gives ⟨6, 7, 5, 4⟩, and the result is ⟨0, 1, 3, 2, 6, 7, 5, 4⟩, in binary ⟨000, 001, 011, 010, 110, 111, 101, 100⟩. “In the binary reflected Gray code, only one bit flips even when wrapping around from the last integer to the first.”

Part (a): index the integers from 0 to 2k − 1 and consider the ith. Going from the (i − 1)st to the ith, exactly one bit flips; show how to determine which, given the index i. Part (b): assuming that given a bit number j you can flip bit j of an integer in constant time, show how to compute the entire sequence of 2k numbers in Θ(2k) time. The book leaves both parts to the reader, so the procedures on this page are a sketch of one answer.

problem 16-2 · making binary search dynamic

A binary counter made of sorted arrays

A sorted array is perfect for binary search and awful for insertion: to make room you slide everything over, which takes time linear in its length. The problem's fix is to keep several sorted arrays instead of one. Write n in binary. For every 1 bit ni keep one sorted array Ai of exactly 2i items, and for every 0 bit keep nothing. With n = 11 = 10112 you hold arrays of 1, 2 and 8 items. Items in different arrays have no particular order relative to one another.

SEARCH runs an ordinary binary search in each full array, smallest first, until one finds the key. There are at most ⌈lg(n + 1)⌉ arrays, and the one of length 2i costs about i + 1 probes, so a search takes O(lg2 n). INSERT is the binary counter again. The new item is an array of length 1, the carry. While Ai is full, merge it with the carry into a sorted array of 2i+1 items, empty Ai and try the next level; the carry settles in the first empty slot. Like INCREMENT, one insertion can be huge (n = 2m − 1 merges everything) but each item is merged at most once per level, so insertions cost O(lg n) amortized.

DELETE is the awkward one: deleting from the middle of a sorted array leaves a hole. One way to do it: find x in Ai, take the smallest full array Aj out, move one of its items y into x's place (keeping Ai sorted), and cut the other 2j − 1 items of Aj into A0 … Aj−1. That is the binary counter run backwards. The tally shows its price: deleting from a big array rewrites that whole array.

Try it: in Insert, press Insert and watch the carry merge its way down, exactly as a counter carries; compare the moves with the shifts one big sorted array would need. In Search, click any key, or press the missing-key button and see every full array probed. In Delete, click a key in the largest array, then one in the smallest, and compare the moves.

What the book says

Binary search of a sorted array takes logarithmic search time, but the time to insert a new element is linear in the size of the array. “You can improve the time for insertion by keeping several sorted arrays.” To support SEARCH and INSERT on a set of n elements, let k = ⌈lg(n + 1)⌉ and let the binary representation of n be ⟨nk−1, nk−2, …, n0⟩.

Maintain k sorted arrays A0, A1, …, Ak−1, where the length of Ai is 2i. “Each array is either full or empty”, depending on whether ni = 1 or ni = 0. The total number of elements held in all k arrays is Σ ni2i = n. “Although each individual array is sorted, elements in different arrays bear no particular relationship to each other.”

Part (a) asks how to perform SEARCH and what its worst-case running time is. Part (b) asks how to perform INSERT and for its worst-case and amortized running times, assuming the only operations are INSERT and SEARCH. Part (c) asks how to implement DELETE and for its worst-case and amortized running times when DELETE, INSERT and SEARCH can all occur. The book leaves all three to the reader, so the procedures on this page are a sketch of one answer, and the DELETE here is one way among several.

The chapter on one page

Chapter 16 in eight cards. Each one points at the scenes that act it out.

Average without probability

An amortized analysis averages the time of a sequence of operations over all the operations performed, so one expensive operation can sit in a sequence whose average cost is small. Unlike average-case analysis no probability is involved: it guarantees the average cost of each operation in the worst case. → 16.1 Multipop stack

Aggregate: bound the total

Show that n operations take T(n) in total, and give each the amortized cost T(n)/n. A plate can be popped only after it was pushed, so n stack operations cost O(n) although one MULTIPOP costs up to n. Bit A[i] of a counter flips ⌊n/2i⌋ times in n INCREMENTs, fewer than 2n flips in all. → 16.1 Multipop stack, Binary counter

Accounting: credit on objects

Charge each operation its own amortized cost and store any overcharge as credit on objects. The total charged must stay at least the total spent, so the credit never goes negative. Stack: PUSH $2, POP and MULTIPOP $0. Counter: setting a bit $2, resetting it $0. → 16.2 Accounting

Potential: credit for the whole structure

A potential function Φ maps each state to a number, and the amortized cost is ĉi = ci + Φ(Di) − Φ(Di−1). If Φ never drops below its starting value, the amortized total bounds the actual total. For the stack, Φ is the number of objects: PUSH 2, POP 0, MULTIPOP 0. → 16.3 Potential: stack

Counting the 1-bits

With Φ equal to the number of 1-bits, INCREMENT has amortized cost at most 2. The same Φ handles a counter that does not start at 0: with b0 ones at the start the total actual cost is at most 2n − bn + b0, still O(n) when k = O(n). → 16.3 Potential: counter

Tables that grow

A dynamic table keeps its load factor α bounded below so unused space stays a constant fraction. Doubling a full table and copying everything makes a single insertion cost up to i, yet aggregate (under 3n), accounting ($3 each) and potential (Φ = 2(num − size/2)) all give amortized cost 3. → 16.4 Dynamic tables, 16.4.1 Expansion

Contract at a quarter

Halving a table as soon as it is less than half full lets a run of inserts and deletes force a Θ(n) resize on every step. Contract when it falls below 1/4 full instead, so a freshly resized table is half full, and the potential of (16.5) pays for every resize: each operation is O(1). → 16.4.2 Contraction

Beyond stacks and counters

The binary reflected Gray code counts with exactly one bit flip per step, and the bit to flip can be read from the index. Problem 16-2 keeps a set in sorted arrays of sizes 2i, one for each 1-bit of n, so that an insertion works like INCREMENT with merges in place of carries. → 16-1 Gray code, 16-2 Dynamic search

Words to know

The book's words from this chapter, in plain language.

amortized analysis
Averaging the time of a sequence of data-structure operations over all of them, to show each is cheap on average even if one is expensive. A worst-case guarantee, not a probabilistic one.
amortized cost
The price an analysis assigns to an operation. Over any sequence the amortized costs must add up to at least the actual costs.
actual cost ci
What the ith operation really takes, counted here in elementary steps: pops, bit flips, items written.
T(n)
The worst-case total cost of any sequence of n operations. Aggregate analysis divides it by n.
aggregate analysis
Bound the total cost T(n) of a sequence, then give every operation the average T(n)/n as its amortized cost, whatever its type.
accounting method
Give each type of operation its own charge. Overcharges are stored as prepaid credit on objects and pay for operations charged less than they cost.
credit
The difference between the total amortized cost and the total actual cost so far. It must never be negative.
inequality (16.1)
Σ ĉi ≥ Σ ci for every sequence of n operations: what makes the amortized costs an upper bound on the real ones.
potential method
Like the accounting method, but the prepaid work is kept as the energy of the whole data structure instead of on single objects.
potential function Φ
Maps each state Di of the data structure to a real number Φ(Di). It is usually set to 0 for the initial structure and kept nonnegative.
potential difference
Φ(Di) − Φ(Di−1). Positive: the operation was overcharged and stores energy. Negative: its cost is partly paid from stored potential.
telescoping sum
In Σ ĉi every middle potential appears once with a plus and once with a minus, so only Φ(Dn) − Φ(D0) is left.
MULTIPOP(S, k)
Pops the top k objects of a stack, or all of them if there are fewer. Its cost is min{s, k} for a stack of s objects.
INCREMENT(A, k)
Adds 1, modulo 2k, to a k-bit binary counter stored in A[0 : k − 1]. Its cost is the number of bits it flips.
dynamic table
A table that grows when it fills and may shrink when it empties, by allocating a new array and copying the items across, so that unused space stays a constant fraction.
load factor α(T)
Items stored divided by the table's size in slots. An empty table (no slots) has load factor 1.
TABLE-INSERT
Adds an item, first allocating a table of twice the size and copying every item if the table is full. T.num counts items, T.size slots.
expansion and contraction
Moving the items into a bigger table when the old one is full, or into a smaller one when the load factor drops too low.
Gray code
A list of integers in binary in which each one differs from the previous by exactly one bit. The binary reflected Gray code builds the code for k bits from the one for k − 1.
reflection
The sequence in reverse. The reflected (k − 1)-bit code with 2k−1 added to each integer, placed after the original, is the k-bit code.
sorted arrays Ai of length 2i
Problem 16-2's structure: array Ai is full or empty according to bit ni of n. Each array is sorted; different arrays are unrelated.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

&mut self methods that count
A method declared fn push(&mut self, …) in an impl block borrows the struct mutably, so it may change fields such as a cost counter. Nothing else may touch the struct meanwhile.
Vec::pop → Option, and ?
pop returns Some(x) or None on an empty Vec. Inside a function that returns Option, ? returns the None from that very line.
len vs capacity
len() counts the items; capacity() counts the slots already allocated. When a push finds the buffer full, the Vec allocates a bigger one (it grows geometrically) and moves the items across. pop never shrinks it.
&mut [bool] and [bool; 8]
A slice is a borrowed view of someone's items, with a length at run time. An array owns its items inline and its length is part of the type. A &mut Vec<bool> coerces to &mut [bool] automatically.
&& short-circuits
In i < k && a[i] the right side runs only if the left is true, so a[i] is never read at i == k. Reading past the end would panic, not return garbage.
bit operations
n >> i is ⌊n/2i⌋; x ^ y keeps the bits where they differ; count_ones() and trailing_ones() count 1-bits and the run of 1s at the low end.
signed integers for Φ and credit
A potential difference or a credit can be negative, so the listings use i64 and convert with as i64. With usize or u64 the subtraction would overflow and panic in a debug build.
Result<(), String> and ?
A check that can fail returns Err(message) instead of crashing. ? on a Result passes an Err straight up to the caller, who decides what to print.
enum variants with data, and match
enum Op { Push(i32), Pop, Multipop(usize) } lets one type be several shapes; a match picks the shape and unpacks its data. #[derive(Debug)] makes {op:?} print it.
Option slots and take()
A table of Vec<Option<u32>> uses None for an empty slot. slot.take() moves the item out and leaves None behind. Assigning a new Vec to a field drops the old one, which frees its buffer.
Vec<Vec<i32>>, mem::take, binary_search
A vector of vectors holds the sorted arrays of problem 16-2. std::mem::take(&mut v) moves a Vec out and leaves an empty one behind. binary_search returns Ok(position) if found, else Err(where it would go).
iterator chains and closures
zip, iter_mut, rev().map(…).collect() and windows(2) walk and rebuild sequences without index bookkeeping; std::array::from_fn(|i| …) builds an array from a closure of the index.
