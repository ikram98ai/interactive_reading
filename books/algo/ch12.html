Binary Search Trees

A binary search tree keeps the smaller keys to the left of every node and the larger ones to its right, so one path from the root is enough to find a key. This chapter walks, searches, inserts into and deletes from such trees in time proportional to their height, and asks how tall a tree grows when the keys arrive in random order.

“Basic operations on a binary search tree take time proportional to the height of the tree.” — Cormen, Leiserson, Rivest & Stein

12.1 · what is a binary search tree?

Every ancestor puts up a fence

Picture a family tree of numbers. Each node holds a key and three links: its left child, its right child and its parent p. A missing link is NIL. The tree itself keeps one pointer, root, to the only node whose parent is NIL. What turns this into a binary search tree is one rule for every node x. Every key in x's left subtree is ≤ x.key, and every key in its right subtree is ≥ x.key. That rule is the binary-search-tree property.

Read the rule closely: it says subtree, not child. A 7 hanging to the right of a 5 looks fine to its parent. If that 5 is the left child of a 6, though, the 7 sits in the 6's left subtree and breaks the rule. So a correct checker has to carry a fence down the tree. Going left, x.key becomes the new upper bound, and going right it becomes the new lower bound. Lay the nodes out by their position in sorted order, as every machine in this chapter does, and the property becomes a picture: a tree is a binary search tree exactly when its keys read sorted from left to right.

One set of keys fits many shapes. Figure 12.1 stores 2, 5, 5, 6, 7, 8 once with height 2 and once with height 4, and that matters, because the basic operations take time proportional to the height. A complete binary tree on n nodes has height about lg n, and a chain of n nodes has height n − 1.

Try it: press Play. IS-BST visits each node with its fence written underneath, and the node turns mint when its key fits. Then set the trap: the dashed ring marks the 5 under the 5, so press +1 twice to make it a 7 and press Play again. IS-BST stops at the 7, and the root that set the fence lights blue. Now pick children only and play it: that checker says TRUE, even though the row along the bottom isn't sorted. Last, switch to Fig. 12.1(b). The nodes slide only up and down, because their left-to-right order stays the same.

What the book says

The search tree data structure supports SEARCH, MINIMUM, MAXIMUM, PREDECESSOR, SUCCESSOR, INSERT and DELETE, so it can serve both as a dictionary and as a priority queue. “Basic operations on a binary search tree take time proportional to the height of the tree.” For a complete binary tree with n nodes they run in Θ(lg n) worst-case time, and for a linear chain of n nodes in Θ(n). Chapter 13's red-black trees guarantee a height of O(lg n), and a binary search tree built on a random set of n keys has expected height O(lg n).

The tree is a linked data structure. Besides a key and satellite data, each node has attributes left, right and p pointing to its left child, right child and parent, NIL when missing. The tree has an attribute T.root, NIL if the tree is empty, and the root is the only node whose parent is NIL.

The binary-search-tree property: let x be a node. If y is a node in the left subtree of x, then y.key ≤ x.key. If y is a node in the right subtree of x, then y.key ≥ x.key. In Figure 12.1(a) the root's key is 6, the keys 2, 5 and 5 in its left subtree are no larger than 6, and the keys 7 and 8 in its right subtree are no smaller. The same holds at every node, for example at the root's left child 5.

“Different binary search trees can represent the same set of values.” Figure 12.1(a) is a binary search tree on 6 nodes with height 2, and (b) a less efficient one with height 4 that contains the same keys.

12.1 · inorder, preorder and postorder tree walks

Left, root, right: sorted for free

Every left subtree holds the small keys and every right subtree the large ones. So a three-line recursive procedure prints a whole binary search tree in sorted order: print the left subtree, then the root, then the right subtree. That is an inorder tree walk. Print the root before both subtrees and you have a preorder walk; print it after them and you have a postorder walk. The three procedures differ in where a single line sits.

What does it cost? After the first call, every node makes exactly two recursive calls, one per child, and the empty subtrees are called too. Each of those NIL calls costs only the test x ≠ NIL. Six nodes make 2·6 + 1 = 13 calls, and the book's Theorem 12.1 proves the walk takes Θ(n) time on n nodes.

The recursion keeps its place on the call stack: one frame for each node on the path from the root to where the walk is now, plus one for a NIL call at the bottom. A tree of height h never has more than h + 2 walk frames live at once. In the Rust program each frame holds just x, an index into the node arena. The printing is a closure the caller passes in, which pushes onto a Vec it borrows.

Try it: press Play and watch the output row fill in. In Inorder each key drops straight down into its own column, because the tree is laid out in sorted order. Switch to Preorder and Postorder and play again. The calls and the stack stay the same, and only the moment of printing moves. In the memory strip a frame is pushed for every call, the 7 NIL calls included, and out gets a heap buffer only at its first push.

What the book says

“Because of the binary-search-tree property, you can print out all the keys in a binary search tree in sorted order by a simple recursive algorithm, called an inorder tree walk”. It prints the key of a subtree's root between the values in its left subtree and those in its right subtree. A preorder tree walk prints the root before the values in either subtree, and a postorder tree walk prints it after the values in its subtrees.

To print all the elements of a tree T, call INORDER-TREE-WALK(T.root). On both trees of Figure 12.1 it prints 2, 5, 5, 6, 7, 8. Its correctness follows by induction directly from the binary-search-tree property.

The walk takes Θ(n) time on an n-node tree because, “after the initial call, the procedure calls itself recursively exactly twice for each node in the tree”: once for its left child and once for its right child.

Theorem 12.1: if x is the root of an n-node subtree, then INORDER-TREE-WALK(x) takes Θ(n) time. It visits all n nodes, so T(n) = Ω(n). An empty subtree costs a constant c > 0, and with k nodes on the left, T(n) ≤ T(k) + T(n − k − 1) + d. The substitution method then shows T(n) ≤ (c + d)n + c, so T(n) = O(n).

12.2 · searching

Higher or lower, one level at a time

Searching a binary search tree is a game of higher-or-lower. Start at the root and compare the key k with x.key. If they are equal, you have found it. If k is smaller, the binary-search-tree property says k can't be anywhere in the right subtree, so go left. If it is larger, go right. Every comparison throws away a whole subtree, so the search traces a simple path down from the root and stops at the key or at a NIL. On a tree of height h, TREE-SEARCH runs in O(h) time.

TREE-SEARCH is written recursively, but each call makes at most one more call and then only passes its answer back. A recursion like that can be unrolled into a loop that moves one pointer down the tree: ITERATIVE-TREE-SEARCH. The path and the comparisons are the same. The difference is one stack frame instead of one per level, and no climb back up to hand the answer along. The book notes that on most computers the loop is the faster of the two.

The two Rust programs also show two ways to build a tree. The recursive one uses the owned form: each node owns its children through Option<Box<Node>>, every node is its own heap block, and as_deref() borrows down the chain. The iterative one uses the arena from 12.1. Its links are indices, so a node can also point back up at its parent.

Try it: press Play to search for 13, as in the book's Figure 12.2(a): 15 → 6 → 7 → 13. Each subtree the search rules out fades. Drag k to a key that isn't in the tree, such as 16, and the search ends at a NIL. Click any node to search for its key. Then switch between Recursive and Iterative and compare the stack. The recursive search pushes one frame per level and hands the answer back up through all of them; the loop keeps a single frame whose x moves.

What the book says

Binary search trees support the queries MINIMUM, MAXIMUM, SUCCESSOR, PREDECESSOR and SEARCH, each in O(h) time on a tree of height h.

Given a pointer x to the root of a subtree and a key k, TREE-SEARCH(x, k) returns a pointer to a node with key k if one exists in the subtree, and NIL otherwise. To search the whole tree T, call TREE-SEARCH(T.root, k). At each node it compares k with x.key: equal ends the search, smaller continues in the left subtree because the binary-search-tree property rules out the right one, and larger continues in the right subtree.

“The nodes encountered during the recursion form a simple path downward from the root of the tree, and thus the running time of TREE-SEARCH is O(h), where h is the height of the tree.” In Figure 12.2(a) a search for 13 follows the path 15 → 6 → 7 → 13.

Because TREE-SEARCH recurses on the left subtree or the right one but never both, the recursion can be unrolled into a while loop. On most computers that version, ITERATIVE-TREE-SEARCH, is more efficient.

12.2 · minimum and maximum

Keep turning left

Where is the smallest key? Start at a node x and follow left pointers until there is no left child. The binary-search-tree property says why that works. If x has a left subtree, every key there is ≤ x.key and every key in the right subtree is ≥ x.key, so the minimum has to be on the left. If x has no left child, nothing in its subtree is smaller than x itself. TREE-MAXIMUM is the mirror image and follows right pointers.

Neither procedure compares a single key: the shape of the tree already holds the order. The nodes they visit form a simple path down from x, so both run in O(h) time on a tree of height h, and starting lower down only shortens the path. Later procedures build on this. TREE-SUCCESSOR calls TREE-MINIMUM on a right subtree, and TREE-DELETE uses it to find the node that takes a deleted node's place.

The book assumes x is not NIL. The Rust version puts that in its type: x is a usize, not an Option<usize>, so an empty tree has to be handled before the call. root.map(…) does that and leaves None as None.

Try it: press Play. TREE-MINIMUM(15) walks 15 → 6 → 3 → 2, and at each step the right subtree it skips turns dashed, ruled out by the property. Switch to Maximum for 15 → 18 → 20. Then click any node to start there instead. The 7 has no left child, so it is the minimum of its own subtree after zero steps.

What the book says

To find an element whose key is a minimum, follow left child pointers from the root until you encounter a NIL, as in Figure 12.2(b), where the minimum 2 is found that way and the maximum 20 by following right pointers. TREE-MINIMUM(x) returns a pointer to the minimum element in the subtree rooted at x, which is assumed to be non-NIL.

The binary-search-tree property guarantees that TREE-MINIMUM is correct. If x has no left subtree, every key in its right subtree is at least as large as x.key, so the minimum in the subtree rooted at x is x.key. If x has a left subtree, no key in the right subtree is smaller than x.key and every key in the left subtree is not larger, so the minimum lies in the subtree rooted at x.left.

“The pseudocode for TREE-MAXIMUM is symmetric.” Both procedures run in O(h) time on a tree of height h since, as in TREE-SEARCH, the nodes encountered form a simple path downward from the root.

12.2 · successor and predecessor

Who comes next, without looking at a key

On a bookshelf sorted by author, the next book is simply the one to the right. In a tree the keys are not in a row, but an inorder walk still visits them in sorted order, so next still has a meaning: the successor of a node is the node the inorder walk visits right after it. The predecessor is the one just before.

There are two cases. If x has a right subtree, the walk goes there next and starts at its leftmost node: the successor is TREE-MINIMUM(x.right). If it has none, x was the last node of some left subtree, so climb: while you are a right child, keep going up; the first time you step up from a left child, that parent is the successor. If you fall off the root, x was the maximum and the answer is NIL. No key is ever compared, only pointers are followed, so each call is O(h).

Climbing needs the parent pointer x.p, and that is why the Rust version keeps its nodes in an arena: one Vec<Node> whose nodes name each other by index. With Box, a child would need two owners (its parent and its own p), which Rust does not allow. Start at the minimum and call successor n − 1 times, and you have an inorder walk that crosses every edge exactly twice: Θ(n) in total, though one call can cost h.

Try it: 15 is picked: press Play and watch x go right once, then left to 17 (Figure 12.2(c)). Click 13 and Play: it has no right subtree, so x and y climb until they come up from a left child, at 15 (Figure 12.2(d)). Click 20 to see the NIL case, then switch to Predecessor. Finally press Walk all and compare the edge counter with 2(n − 1). In Rust, the memory strip shows x and y as plain indices into the Vec.

What the book says

Given a node in a binary search tree, the successor in the sorted order determined by an inorder walk is, if all keys are distinct, the node with the smallest key greater than x.key. Regardless of whether the keys are distinct, the book defines “the successor of a node as the next node visited in an inorder tree walk.” “The structure of a binary search tree allows you to determine the successor of a node without comparing keys.” TREE-SUCCESSOR returns the successor of x, or NIL if x is the last node an inorder walk would visit.

The code has two cases. If the right subtree of x is nonempty, the successor is the leftmost node in that subtree, which line 2 finds with TREE-MINIMUM(x.right): in Figure 12.2(c) the successor of 15 is 17. Otherwise, if x has a successor y, then y is the lowest ancestor of x whose left child is also an ancestor of x (Exercise 12.2-6; every node is its own ancestor). In Figure 12.2(d) the successor of 13 is 15. Lines 4–8 find y by going up from x until reaching the root or a node that is the left child of its parent.

TREE-SUCCESSOR runs in O(h) time on a tree of height h, since it “either follows a simple path up the tree or follows a simple path down the tree.” TREE-PREDECESSOR is symmetric and also runs in O(h). Theorem 12.2: SEARCH, MINIMUM, MAXIMUM, SUCCESSOR and PREDECESSOR can each be implemented to run in O(h) time.

Exercise 12.2-5 shows that if a node has two children, its successor has no left child and its predecessor has no right child. Exercise 12.2-7 asks you to prove that an inorder walk done as TREE-MINIMUM followed by n − 1 calls to TREE-SUCCESSOR takes Θ(n) time, and 12.2-8 that k successive calls take O(k + h) time.

12.3 · insertion

Walk down to an empty spot, one step behind

A new book arrives at a library shelved as a tree. At each shelf the librarian asks one question, smaller or not?, and turns left or right, until the next turn leads nowhere. That empty spot, a NIL, is where the book goes. But by then she has stepped past the shelf the book must hang from. So a friend walks one step behind her: x searches, and the trailing pointer y remembers x's parent.

That is all of TREE-INSERT: x and y walk down one simple path, then the new node z gets y as its parent and becomes y's left or right child (or the root, if the tree was empty). It never moves an existing node, and the binary-search-tree property still holds. Cost: one comparison per level, O(h).

The catch is h. The same ten keys make a bushy tree of height 3 in one order and a linear chain of height 9 in sorted order, where every later insert walks the whole chain. Sorting by inserting into a tree and then walking it inorder (Exercise 12.3-3) is fast or slow for exactly this reason.

Try it: Step through Figure 12.3: x and y walk 12 → 18 → 15, x falls off to NIL, and 13 hangs under y. Then pick Shuffled and Sorted, press Play, and compare their heights. In Rust, watch the memory strip at the ninth push: the Vec moves to a bigger buffer, which is harmless because the code holds indices, not references.

What the book says

Insertion and deletion change the dynamic set, and the tree must change so that the binary-search-tree property continues to hold. Inserting is relatively straightforward; deleting is more complicated.

TREE-INSERT takes a binary search tree T and a node z whose key is already filled in, with z.left = NIL and z.right = NIL, and modifies T and some attributes of z so as to insert z into an appropriate position in the tree. Like TREE-SEARCH, it starts at the root and the pointer x traces a simple path downward looking for a NIL to replace with the input node z. The procedure maintains the trailing pointer y as the parent of x; the while loop of lines 3–7 moves both down, left or right by comparing z.key with x.key, until x becomes NIL.

That NIL is a left or right attribute of the node that will become z's parent, or T.root if the tree is empty. The trailing pointer is needed because by the time the procedure finds the NIL where z belongs, the search has gone one step beyond the node that needs to be changed. Lines 8–13 set the pointers that insert z. Figure 12.3 inserts 13: the path 12, 18, 15 leads to the left child of 15.

TREE-INSERT runs in O(h) time on a tree of height h. The chapter opens with the warning that the height decides everything: a complete binary tree gives Θ(lg n) worst-case time, a linear chain of n nodes Θ(n), and a tree built on a random set of n keys has expected height O(lg n).

12.3 · deletion

Who takes the empty chair?

A manager leaves a company drawn as a tree. With no reports, the desk is simply cleared. With one report, that person moves up into the desk and brings their whole team along. With two, someone must take the chair who is bigger than everyone on the left and smaller than everyone on the right: the successor, the smallest key of the right subtree. It sits at the end of a left-going path, so it has no left child, and moving it is easy.

The book builds all of this from one move, TRANSPLANT(T, u, v): u's parent now points to v instead, and v's parent pointer is fixed. It never touches v's children. TREE-DELETE then has four cases, Figure 12.4's pictures: (a) no left child, so the right child (maybe NIL) moves up; (b) only a left child, so it moves up; (c) two children and the successor y is z's right child: y moves up and takes z's left subtree; (d) y is deeper: first its right child x takes y's place, then y adopts z's right subtree, then case (c).

Every line is a constant number of pointer writes except finding y, so delete is O(h). In the Rust arena the deleted node's slot is never reused: it stays in the Vec, unreachable. A free list of dead indices would fix that.

Try it: 15, the root, is picked: it is case (d). Press Step and watch y = 17 leave its place, adopt 18, then take the root's chair. Then click 13 (case (b)), 7 (case (a)) and 6 (case (c)), pressing Play after each. Random builds another tree. In Rust, the memory strip keeps every deleted node's slot, dead.

What the book says

The overall strategy for deleting a node z has three basic cases. With no children, z's parent gets NIL in its place. With one child, that child is elevated to take z's position. With two children, z's successor y, which must lie in z's right subtree, takes z's position: the rest of z's right subtree becomes y's new right subtree and z's left subtree becomes y's new left subtree. This case is the tricky one, because it matters whether y is z's right child.

TREE-DELETE organizes these as the four cases of Figure 12.4: (a) z has no left child: replace z by its right child, which may be NIL; (b) z has a left child but no right child: replace z by its left child; (c) two children and the successor y is z's right child: replace z by y, leaving y's right child alone; (d) otherwise y lies deeper in z's right subtree: first replace y by its own right child, then replace z by y. The successor has no left child (Exercise 12.2-5).

TRANSPLANT replaces the subtree rooted at u with the subtree rooted at v: u's parent becomes v's parent, and u's parent ends up with v as its appropriate child. “TRANSPLANT allows v to be NIL instead of a pointer to a node.” It does not update v.left or v.right; that is the caller's job.

Each line of TREE-DELETE, including the TRANSPLANT calls, takes constant time except the call to TREE-MINIMUM in line 5, so TREE-DELETE runs in O(h) time. Theorem 12.3: INSERT and DELETE can each be implemented in O(h) time on a binary search tree of height h. Exercise 12.3-7 notes that y could be the predecessor instead.

problem 12-2 · radix trees

A tree that spells its keys

A dictionary puts words in order letter by letter. Compare the first letters; if they match, the next ones; and a word that runs out first, like “car” against “cart”, comes first. For bit strings that is lexicographic order: 10100 < 10110 because they first differ at position 3, and 10100 < 101000 because the first is a prefix of the second.

A radix tree, also called a trie, stores bit strings without writing them down. From the root, go left for a 0 and right for a 1: the path spells the string, so a node only has to say whether some string ends there. Nodes where no string ends (dashed in the machine) are only there to carry a path to deeper nodes.

To sort, insert every string, then walk the tree in preorder: a node before its subtrees, and the 0 side before the 1 side. Printing a node before everything below it puts a prefix before its extensions; left before right means the first differing bit decides. If the lengths add up to n, the inserts read n bits, the tree has at most n + 1 nodes, and the walk visits each once: Θ(n) in all, with no comparisons between strings at all.

Try it: press Step to read 1011 into the tree one bit at a time: the yellow node is x, and a dashed node appears wherever the path is missing. Then press Play to insert the rest and walk the tree; each string turns mint as the walk prints it. Try Prefix chain, where every string is a prefix of the next, and Random set. In Rust the memory strip shows the one String buffer s growing with push on the way down and shrinking with pop on the way back.

What the book says

For strings a = a0a1…ap and b = b0b1…bq over an ordered set of characters, a is lexicographically less than b if either (1) there is an integer j, 0 ≤ j ≤ min{p, q}, with ai = bi for all i = 0, 1, …, j − 1 and aj < bj, or (2) p < q and ai = bi for all i = 0, 1, …, p. For bit strings, 10100 < 10110 by rule 1 (with j = 3) and 10100 < 101000 by rule 2. “This ordering is similar to that used in English-language dictionaries.”

The radix tree of Figure 12.5, also known as a trie, stores the bit strings 1011, 10, 011, 100, and 0. When searching for a key, go left at a node of depth i if ai = 0 and right if ai = 1. A node's key is the simple path from the root to it, so the keys need not be stored in the nodes; the nodes whose keys are not in the tree (blue in the figure) are present only to establish a path to other nodes.

The problem: let S be a set of distinct bit strings whose lengths sum to n; show how to use a radix tree to sort S lexicographically in Θ(n) time. For Figure 12.5 the output should be 0, 011, 10, 100, 1011. The machine's insert-then-preorder method is one answer, written as a sketch.

The chapter notes explain the other name: radix trees are often called tries, which “comes from the middle letters in the word retrieval.”

problem 12-3 · average node depth in a randomly built binary search tree

Shuffle first, and the tree stays bushy

Insert keys into a binary search tree in sorted order and you get a chain: the average node depth is (n − 1)/2. Shuffle them first, with every one of the n! orders equally likely, and you get a randomly built binary search tree. Its average node depth is only O(lg n).

Measure a tree by its total path length P(T), the sum of all its nodes' depths; the average depth is P(T)/n. Hanging two subtrees under a root pushes every one of their nodes one level deeper, so P(T) = P(TL) + P(TR) + n − 1. In a random order the first key becomes the root and is equally likely to have any rank, which turns that into a recurrence for the expected total, P(n): the same recurrence as randomized quicksort's comparison count, so P(n) = O(n lg n).

That is no coincidence. Inserting a key compares it with each of its ancestors, once each. A quicksort whose pivot is always the element that was inserted first compares each element with exactly the same keys: the pivot of a subarray is the root of the matching subtree. Same comparisons, in a different order.

Try it: in Insert, press Play: each key slides down from the root, one comparison per level, and the comparison count ends equal to P(T). Switch to Quicksort and press Play on the same order: every key starts in one row, each partition leaves its pivot in place and drops the others one level, and the count ends at the same number. Sorted gives the chain; Shuffle deals a new order. In Many trees, press Play: the dots, averages over random trees, land on the recurrence's curve, far below the sorted-input line.

What the book says

A randomly built binary search tree on n keys is created by “starting with an empty tree and inserting the keys in random order,” each of the n! permutations of the keys being equally likely. The problem proves that the average depth of a node in such a tree is O(lg n), and that the technique shows a surprising similarity between building a binary search tree and running RANDOMIZED-QUICKSORT from Section 7.3.

With d(x, T) the depth of node x and the total path length P(T) the sum of d(x, T) over all nodes: (a) the average depth is (1/n) Σx∈T d(x, T) = (1/n) P(T), so it suffices to show that E[P(T)] is O(n lg n); (b) P(T) = P(TL) + P(TR) + n − 1; (c) the average total path length P(n) of a randomly built tree with n nodes satisfies P(n) = (1/n) Σi=0n−1 (P(i) + P(n − i − 1) + n − 1); (d) so P(n) = (2/n) Σk=1n−1 P(k) + Θ(n); (e) recalling the alternative analysis of randomized quicksort in Problem 7-3, P(n) = O(n lg n).

(f) “Each recursive invocation of randomized quicksort chooses a random pivot element to partition the set of elements being sorted. Each node of a binary search tree partitions the set of elements that fall into the subtree rooted at that node.” The task is to describe a quicksort whose comparisons are exactly those made by inserting the elements into a binary search tree, though perhaps in a different order. QUICKSORT-AS-BST in the machine is one answer, written as a sketch.

The chapter's introduction adds, without proof, that a binary search tree built on a random set of n keys has expected height O(lg n) too, even if you don't try to limit its height. The curve in Many trees is the recurrence of part (c) evaluated numerically; the 2 ln n line is a reference added here.

problem 12-4 · number of different binary trees

Fourteen shapes for four nodes

How many different shapes can a binary tree with n nodes take? Call the answer bn. There is one empty tree, so b0 = 1. For n ≥ 1, one node is the root and the other n − 1 split between its subtrees: k on the left and n − 1 − k on the right. Any left shape goes with any right shape, so bn = Σk=0n−1 bk bn−1−k.

These are the Catalan numbers: 1, 1, 2, 5, 14, 42, … with the closed form bn = (1/(n + 1))·C(2n, n), and they grow like 4n/(√π n3/2). For engineers there are two lessons. Every shape is the shape of exactly one binary search tree on the keys 1 to n, because an inorder walk fixes where each key goes. And the numbers outgrow machine words fast: a u64 holds bn only up to n = 36, a u128 up to 69.

The chapter on one page

Chapter 12 in eight cards. Each one points at the scenes that act it out.

Smaller left, larger right

For every node x, the keys in its left subtree are ≤ x.key and those in its right subtree are ≥ it. The rule is about whole subtrees, so a checker has to pass bounds down, not just compare children. Laid out by sorted position, a binary search tree reads in order from left to right. → 12.1 The BST property

Walk it and it's sorted

INORDER-TREE-WALK prints the left subtree, then the root, then the right subtree: the keys in sorted order. Preorder prints the root first, postorder last. There are 2n + 1 calls, the NIL ones included, so a walk takes Θ(n). → 12.1 Tree walks

One simple path down

TREE-SEARCH compares k with x.key and throws away a whole subtree each time, so it costs O(h). Its recursion unrolls into a loop with one stack frame. TREE-MINIMUM and TREE-MAXIMUM only follow left or right pointers, without comparing a single key. → 12.2 Searching, Min and max

Next, without a key

The successor is the next node of an inorder walk: the minimum of the right subtree if there is one, otherwise the first ancestor reached from a left child. Climbing needs parent pointers. Starting at the minimum, n − 1 successor calls walk the whole tree in Θ(n). → 12.2 Successor

Insert where the search falls off

TREE-INSERT walks x down to a NIL while the trailing pointer y remembers the parent, then hangs z under y. No existing node moves. The order of insertion decides the shape: sorted keys make a chain. → 12.3 Insertion

Delete by transplanting

TRANSPLANT puts one subtree where another was. TREE-DELETE has four cases: no left child, no right child, a successor that is z's right child, and a successor deeper down, which has no left child. It deletes the node z itself, so other pointers into the tree don't go stale. → 12.3 Deletion

Height is everything

Every operation here costs O(h): Θ(lg n) on a complete tree, Θ(n) on a chain. Insert the keys in random order and the average node depth is O(lg n). The proof is randomized quicksort's: the root is the first pivot. Red-black trees (Chapter 13) guarantee O(lg n) height. → 12-3 Random BSTs

Trees that spell, trees you count

A radix tree stores bit strings as paths of 0s and 1s, and a preorder walk sorts them in Θ(n) for total length n. The number of binary tree shapes with n nodes is the Catalan number (1/(n + 1))·C(2n, n), about 4n/(√π n3/2). → 12-2 Radix trees, 12-4 Counting trees

Words to know

The book's words from this chapter, in plain language.

binary search tree
A binary tree whose keys obey the binary-search-tree property. It supports SEARCH, MINIMUM, MAXIMUM, PREDECESSOR, SUCCESSOR, INSERT and DELETE.
key, satellite data
The value a node is ordered by, and whatever else the node carries along with it.
left, right, p
A node's pointers to its left child, its right child and its parent. NIL when there is none.
root
T.root points to the top node, the only node whose parent is NIL. It is NIL for an empty tree.
binary-search-tree property
Keys in a node's left subtree are ≤ its key, and keys in its right subtree are ≥ it. This holds at every node, for whole subtrees.
height
The number of edges on the longest path from the root down to a leaf. The basic operations take time proportional to it.
inorder tree walk
Visits the left subtree, then the root, then the right subtree. On a binary search tree it prints the keys in sorted order, in Θ(n).
preorder / postorder walk
Prints a subtree's root before its subtrees, or after them.
simple path
A path that never visits a node twice. A search, a minimum or an insertion follows one from the root downward, so it costs O(h).
unrolling a recursion
Replacing a recursion that makes at most one call per call by a loop, as ITERATIVE-TREE-SEARCH does: one stack frame instead of one per level.
minimum / maximum
The leftmost and the rightmost node of a subtree, reached by following only left or only right pointers.
successor / predecessor
The node visited right after or right before a given node in an inorder walk. NIL for the last or the first node.
trailing pointer
TREE-INSERT's y, which stays one step behind x so it still names the parent when x reaches NIL.
TRANSPLANT
Replaces the subtree rooted at u by the one rooted at v as a child of u's parent. It leaves v's own children to the caller.
linear chain
A tree where each node has at most one child, as sorted insertions build. Its height is n − 1, so its operations take Θ(n).
randomly built BST
A tree built by inserting n keys in an order where all n! orders are equally likely. Its average node depth is O(lg n).
total path length
P(T), the sum of all node depths. Divided by n, it is the average depth.
lexicographic order
Dictionary order: the first position where two strings differ decides, and a prefix comes before its extensions.
radix tree (trie)
A tree that stores strings as paths, going left for a 0 and right for a 1. The keys need not be stored in the nodes.
Catalan numbers
1, 1, 2, 5, 14, 42, …: bn, the number of different binary trees with n nodes, equal to (1/(n + 1))·C(2n, n).

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

arena
All nodes live in one Vec<Node> and name each other by index. That gives a node both children and a parent, which Box can't, because a child would have two owners.
Option<usize> as NIL
A link is Some(index) or None. It is Copy, so x = node.left copies it, and it takes 16 bytes: a padded tag plus the index.
Option<Box<Node>>
An owned child. A Box is never null, so None uses the null address and the whole thing is one 8-byte pointer.
as_deref / as_deref_mut
Turn &Option<Box<Node>> into Option<&Node> (or &mut), to borrow down a chain of boxes without moving anything.
while let
while let Some(l) = t.nodes[x].left { x = l; } loops for as long as the pattern matches: the book's “while x.left ≠ NIL”.
let … else
let Some(i) = x else { return true }; binds on a match and otherwise must leave the function. It's a guard for NIL in one line.
match guards
Some(n) if k < n.key => … adds a test to a pattern. The arms are tried in order, so the three cases of a search read top to bottom.
&mut impl FnMut
A parameter that accepts any closure that may change what it captured, such as one that pushes onto a Vec it borrows. The tree walk calls it without knowing what it does.
is_some_and, map, expect
Option helpers: test the value if there is one, transform it and leave None alone, or take it out and panic with a message when there is none.
two &mut into one Vec
The borrow checker won't hand out mutable references to two nodes of the same Vec at once. TRANSPLANT copies the indices it needs first.
Drop
When the owner of a Box tree goes out of scope, every box frees its own subtree. There is no garbage collector, and no leak.
checked_mul, try_fold
Arithmetic that returns None on overflow instead of wrapping or panicking, and a fold that stops at the first None: how a u128 learns its limit with Catalan numbers.
