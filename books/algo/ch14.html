Dynamic Programming

Dynamic programming solves optimization problems whose subproblems overlap: instead of recomputing the same subproblem again and again, it solves each one once and saves the answer in a table. That turns exponential-time recursions into polynomial-time algorithms, as the chapter shows on rod cutting, matrix chains, longest common subsequences and optimal search trees.

“The key strategy is to store the solution to each such subproblem rather than recompute it.” — Cormen, Leiserson, Rivest & Stein

14.1 · rod cutting

Which cuts pay the most?

A steel company buys long rods and saws them into shorter ones to sell. Every cut is free, but the price list is uneven: a 4-inch piece sells for $9, while two 2-inch pieces sell for $5 each, $10 together. So the best plan is not obvious. Where should you cut a rod of n inches?

That is the rod-cutting problem: given a rod length and a table of prices, find the greatest total revenue over all ways to cut. A rod has n − 1 spots where a saw could go, and each spot is an independent yes-or-no, so there are 2n−1 ways to cut it: 8 for four inches, 512 for ten, about 5 × 1011 for forty. Checking them all is hopeless for big rods, and the rest of this section is about doing better.

Rod cutting is the chapter's first example of dynamic programming. It suits problems where you make a set of choices to reach an optimal solution, each choice leaves subproblems of the same form, and the same subproblems come up again and again. The trick is to solve each one once and keep the answer in a table. (“Programming” here means filling a table, not writing code.) A greedy algorithm, the subject of Chapter 15, would instead take whatever looks best at each choice.

Try it: click the small circles under the rod to cut or join it, and watch the revenue add up. Can you beat $9 for four inches? Then press Show the best, or Play to watch the brute-force procedure try every pattern one after another (Step goes one pattern at a time). Slide n up to 10 and see the number of ways double with every inch.

What the book says

Part IV opens with the three techniques of Chapters 14–16. “Dynamic programming typically applies to optimization problems in which you make a set of choices in order to arrive at an optimal solution, each choice generates subproblems of the same form as the original problem, and the same subproblems arise repeatedly.” The key strategy is to store each subproblem's solution rather than recompute it, which can turn exponential-time algorithms into polynomial-time ones. Greedy algorithms also make a set of choices, but each one is made “in a locally optimal manner, resulting in a faster algorithm than you get with dynamic programming.”

“Dynamic programming, like the divide-and-conquer method, solves problems by combining the solutions to subproblems.” Divide-and-conquer splits a problem into disjoint subproblems. Dynamic programming applies when the subproblems overlap, so a divide-and-conquer algorithm does more work than necessary, while a dynamic-programming algorithm “solves each subsubproblem just once and then saves its answer in a table.” The word “programming” here “refers to a tabular method, not to writing computer code.”

Optimization problems can have many solutions, each with a value. We call a solution with the optimal (minimum or maximum) value an optimal solution, not the optimal solution, since several may reach that value. Developing a dynamic-programming algorithm takes four steps: characterize the structure of an optimal solution; recursively define its value; compute the value, “typically in a bottom-up fashion”; and construct an optimal solution from the computed information. Steps 1–3 form the basis, and step 4 can be omitted if only the value is needed.

Section 14.1 uses a steel company that buys long rods and cuts them into shorter rods, which it then sells; “Each cut is free.” Figure 14.1 gives the price pi of a rod of i inches, for i = 1 to 10: 1, 5, 8, 9, 10, 17, 17, 20, 24, 30 dollars. Given a rod of length n and these prices, find the maximum revenue rn obtainable by cutting up the rod and selling the pieces. If pn is large enough, the optimum may need no cutting at all.

For n = 4, Figure 14.2 shows all 8 ways; two 2-inch pieces earn p2 + p2 = 5 + 5 = 10, which is optimal. A rod of length n can be cut in 2n−1 ways, since there is an “independent option of cutting, or not cutting, at distance” i inches from the left end for each i = 1, …, n − 1. By inspection the optimal revenues for n = 1 to 10 are 1, 5, 8, 10, 13, 17, 18, 22, 25, 30, and n = 7 has two optimal decompositions, 1 + 6 and 2 + 2 + 3.

The values satisfy rn = max{pn, r1 + rn−1, r2 + rn−2, …, rn−1 + r1} (equation 14.1), because after the first cut the two pieces are independent instances of the same problem. A simpler form cuts off a first piece of length i and treats only the remainder as divisible: rn = max{pi + rn−i : 1 ≤ i ≤ n} (14.2), with r0 = 0.

14.1 · the naive recursion and why it explodes

The same question, asked again and again

Saw off a first piece of length i and what is left is a smaller rod-cutting problem. So the best revenue for n inches is the best, over every first piece i from 1 to n, of that piece's price plus the best revenue for the remaining n − i inches. A rod of length 0 earns nothing. Write that down as a recursive procedure and you get CUT-ROD.

It is correct, and it is hopeless. CUT-ROD(4) calls itself on 3, 2, 1 and 0. The call on 3 calls 2, 1 and 0 again, the call on 2 calls 1 and 0 again, and so on. Every call is a node of the recursion tree, and the same sizes show up in many places. If T(n) counts the calls, then T(n) = 1 + T(0) + … + T(n − 1), which comes to 2n: every extra inch doubles the work. At n = 40 that is around a trillion calls.

Look at what has not exploded. There are only n + 1 different questions, one for each size 0 to n, and the call stack never gets deeper than n + 1 frames. The time goes into overlapping subproblems: the same sizes solved repeatedly. Each leaf of the tree, by the way, is one of the 2n−1 ways to cut the rod.

Try it: press Play and watch the call tree grow depth-first (Step moves one line of CUT-ROD at a time). Then click a size under the tree, or any circle, to colour every call with that size: they are all the same question. Raise n to 7 and compare the calls with 2n. In the memory strip (Rust view) the stack stays shallow while the calls pile up.

What the book says

CUT-ROD implements equation (14.2) in a straightforward, top-down, recursive manner. It takes an array p[1 : n] of prices and an integer n and returns the maximum revenue possible for a rod of length n. For n = 0 it returns 0 in line 2. Line 3 sets q to −∞ so that the for loop of lines 4–5 correctly computes q = max{pi + CUT-ROD(p, n − i) : 1 ≤ i ≤ n}, and line 6 returns it. A simple induction on n shows this equals rn.

Code it up in your favorite language and “once the input size becomes moderately large, your program takes a long time to run.” For n = 40 it may take several minutes and possibly more than an hour, and “each time you increase n by 1, your program’s running time approximately doubles.”

The reason is that CUT-ROD solves the same subproblems over and over, calling itself again and again with the same parameter values. Figure 14.3 shows the recursion tree for n = 4: CUT-ROD(p, n) calls CUT-ROD(p, n − i) for i = 1, 2, …, n, or equivalently CUT-ROD(p, j) for each j = 0, 1, …, n − 1.

Let T(n) be the total number of calls made for a given n, which is the number of nodes in a subtree rooted at a node labeled n, counting the root. Then T(0) = 1 and T(n) = 1 + Σj=0n−1 T(j) (14.3). Exercise 14.1-1 asks you to show T(n) = 2n (14.4), so the running time is exponential in n.

In retrospect this is not so surprising, because CUT-ROD tries all possible ways of cutting up a rod of length n. There are n − 1 potential places to cut, each way cuts at some subset of them (the empty set means no cuts), and an n − 1 element set has 2n−1 subsets. Each leaf of the recursion tree is one way, so the tree has 2n−1 leaves and 2n nodes. The labels on the path from the root to a leaf are the sizes of the right-hand remainders before each cut.

14.1 · memoization and bottom-up

Write it down, then look it up

The cure for repeated work is almost embarrassingly simple: the first time you solve a subproblem, write the answer in a table. The next time you need it, read the table instead of recomputing. That costs memory, a time–memory trade-off, but the saving is dramatic. There are only n + 1 subproblems and each takes a loop of at most n steps, so the work falls from 2n to Θ(n2).

There are two ways to do it. Top-down with memoization keeps the recursion of the last scene and checks the table first: if r[n] is known, return it; otherwise compute it, save it, return it. (“Memoization” comes from memo, a note you write to look up later.) Bottom-up drops the recursion: solve the subproblems in size order, smallest first, so that when a size needs r[j − i] it is already in the table.

Both fill the same table with the same numbers in Θ(n2) time. The order differs: top-down dives to r[0] first and fills the table on the way back, solving only the sizes it actually meets; bottom-up marches from 0 to n with no call overhead, which usually means smaller constants.

Try it: in Top-down, press Play: the calls dive to r[0], the table fills on the way back, and a mint flash marks every lookup that hits a saved answer. Switch to Bottom-up and compare the order. Slide n to 10 and set the loop steps against the 1024 calls of CUT-ROD. In Rust the memo is a Vec<Option<i64>>: None plays the part of the book's −∞.

What the book says

Dynamic programming arranges for each subproblem to be solved only once: the first time you solve one, save its solution, and if you need it later, just look it up. “Saving subproblem solutions comes with a cost: the additional memory needed to store solutions.” Dynamic programming is thus an example of a time–memory trade-off, and the savings may be dramatic, here from an exponential-time algorithm to a Θ(n2) one. It runs in polynomial time when the number of distinct subproblems is polynomial in the input size and each can be solved in polynomial time.

There are usually two equivalent ways to implement it. In the first, top-down with memoization, “you write the procedure recursively in a natural manner, but modified to save the result of each subproblem (usually in an array or hash table).” The procedure first checks whether it has solved this subproblem before; if so it returns the saved value, if not it computes the value as usual and saves it. The word memoization comes from memo, since the technique records a value to be looked up later; it is not a misspelling of memorization.

The second is the bottom-up method, which relies on some natural notion of the size of a subproblem. “Solve the subproblems in size order, smallest first, storing the solution to each subproblem when it is first solved.” Then every prerequisite is already saved when you need it. The two approaches have the same asymptotic running time, “except in unusual circumstances where the top-down approach does not actually recurse to examine all possible subproblems.” “The bottom-up approach often has much better constant factors, since it has lower overhead for procedure calls.”

MEMOIZED-CUT-ROD makes a new array r[0 : n] and fills it with −∞, a convenient mark for unknown since real revenues are never negative, then calls MEMOIZED-CUT-ROD-AUX. The helper is the memoized CUT-ROD: line 1 asks whether r[n] is already known and line 2 returns it; lines 3–7 compute q the usual way, with the for loop over the position i of the first cut; line 8 saves q in r[n] and line 9 returns it.

BOTTOM-UP-CUT-ROD creates r[0 : n], sets r[0] = 0 because a rod of length 0 earns nothing, and in lines 3–7 solves sizes j = 1, …, n in increasing order. It is CUT-ROD except that line 6 reads r[j − i] directly instead of making a recursive call. Line 8 returns r[n]. The running time is Θ(n2), because the inner loop's iteration counts form an arithmetic series. MEMOIZED-CUT-ROD is also Θ(n2): a recursive call on a solved subproblem returns at once, so each size 0, 1, …, n is solved once, and the loop for size n runs n times, an arithmetic series again. (The book calls this a form of aggregate analysis, seen in Section 16.1.)

14.1 · subproblem graphs and reconstructing the solution

A map of what depends on what

Draw one vertex for every distinct subproblem, the sizes 0 to n, and an arrow from x to y whenever solving x looks at the answer for y. That is the subproblem graph. It is the recursion tree with every node of the same size merged into one vertex, so it is small: n + 1 vertices and n(n + 1)/2 edges. Every arrow points to a smaller size, so there are no cycles, and the bottom-up order is simply: visit a vertex only after everything it points to.

The graph also gives the running time. Each subproblem is solved once, and the time to solve it is about its out-degree, the number of arrows leaving it. So the total is proportional to the number of vertices plus the number of edges. For rod cutting that is Θ(n2), the same answer as before, but now you can read it off a picture.

One thing is still missing: the procedures so far return the value rn, not the cuts. The fix is to record, for every size j, which first piece gave the maximum: s[j]. EXTENDED-BOTTOM-UP-CUT-ROD stores it next to r[j], and PRINT-CUT-ROD-SOLUTION then follows the choices: print s[n], cut that piece off, and repeat on what is left.

Try it: pick n and press Play. For each size j the arrows leaving it light up one at a time, each labelled with the revenue that first piece would give; the best turns mint and its length lands in s[j]. When the table is full, click any vertex (or press Print the solution) to follow the mint arrows down to 0 and print the cuts. At the end, the edges examined equal |E|.

What the book says

“When you think about a dynamic-programming problem, you need to understand the set of subproblems involved and how subproblems depend on one another.” The subproblem graph embodies exactly this. It is a directed graph with one vertex for each distinct subproblem, and an edge from the vertex for subproblem x to the vertex for y if determining an optimal solution for x involves directly considering an optimal solution for y, for example if a top-down recursive procedure for x directly calls itself to solve y. Figure 14.4 shows it for rod cutting with n = 4: a reduced version of the recursion tree of Figure 14.3, in which all nodes with the same label are collapsed into a single vertex and all edges go from parent to child.

The bottom-up method considers the vertices in an order such that the subproblems y adjacent to a given x are solved before x. In terms of Section 20.4, that is a reverse topological sort, or a topological sort of the transpose, of the subproblem graph; no subproblem is considered until all those it depends on have been solved. Likewise, the top-down method with memoization can be viewed as a depth-first search of the subproblem graph (Section 20.3).

The size of the graph G = (V, E) helps determine the running time. Since each subproblem is solved just once, the running time is the sum of the times needed to solve each. Typically the time for a subproblem is proportional to the degree (number of outgoing edges) of its vertex, and the number of subproblems equals the number of vertices. In this common case “the running time of dynamic programming is linear in the number of vertices and edges.”

MEMOIZED-CUT-ROD and BOTTOM-UP-CUT-ROD return the value of an optimal solution but not the solution itself, a list of piece sizes. To fix that, extend the approach to “record not only the optimal value computed for each subproblem, but also a choice that led to the optimal value.” EXTENDED-BOTTOM-UP-CUT-ROD computes, for each rod size j, not only the maximum revenue rj but also sj, the optimal size of the first piece to cut off. It creates the array s in line 1 and updates s[j] in line 8.

PRINT-CUT-ROD-SOLUTION takes the prices and a rod size n, calls EXTENDED-BOTTOM-UP-CUT-ROD to get s[1 : n], and prints the complete list of piece sizes of an optimal decomposition. For the prices of Figure 14.1, the call with n = 10 returns r = 0, 1, 5, 8, 10, 13, 17, 18, 22, 25, 30 for sizes 0 to 10 and s = 1, 2, 3, 2, 2, 6, 1, 2, 3, 10 for sizes 1 to 10. PRINT-CUT-ROD-SOLUTION(p, 10) prints just 10, and a call with n = 7 prints the cuts 1 and 6, the first optimal decomposition of r7.

14.2 · matrix-chain multiplication (the problem)

The same product, ten times cheaper

Multiplying a p×q matrix by a q×r matrix takes p·q·r little multiplications, because the three loops of the textbook method run their innermost line that many times. Now take three matrices of sizes 10×100, 100×5 and 5×50. Matrix multiplication is associative, so (A1A2)A3 and A1(A2A3) are the same matrix. The bills are not: 5,000 + 2,500 = 7,500 for the first, 25,000 + 50,000 = 75,000 for the second. Ten times the work for the same answer.

That is the matrix-chain multiplication problem. The input is a chain of n matrices, where Ai is pi−1×pi, so all you need is the list of dimensions p0, p1, …, pn. Nothing gets multiplied. You only decide where the brackets go. Every full parenthesization picks a last multiplication, which cuts the chain in two, and then does the same inside each piece.

How many bracketings are there? Call the count P(n). Then P(1) = 1 and P(n) is the sum of P(k)·P(n−k) over every place k to cut: 1, 1, 2, 5, 14, 42, … It grows at least like 2n, so trying every bracketing is hopeless. The next machine finds the best one with a table.

Try it: pick a chain above the picture, then click a dot between two matrices. That dot becomes the last multiplication of its piece: the piece splits in two and its p·q·r is added to your bill. Keep splitting until every piece is one matrix, then look where your bracketing lands among all of them in the bars underneath. Best and Worst build those two for you, and a click on any bar loads that bracketing. The book tab of the code shows the multiplication being paid for; PAREN-COST is the same bill as a recursion.

What the book says

Given a chain ⟨A1, A2, …, An⟩ of n matrices, which are not necessarily square, the goal is to compute the product A1A2⋯An with the standard algorithm for rectangular matrices while minimizing the number of scalar multiplications. Matrix multiplication is associative, so all parenthesizations yield the same product. A product is fully parenthesized if it is a single matrix or the product of two fully parenthesized matrix products, surrounded by parentheses. A chain ⟨A1, A2, A3, A4⟩ can be fully parenthesized in five distinct ways.

“How you parenthesize a chain of matrices can have a dramatic impact on the cost of evaluating the product.” RECTANGULAR-MATRIX-MULTIPLY computes C = C + A·B for A of size p×q, B of size q×r and C of size p×r. Its running time is dominated by the scalar multiplications in line 4, which number pqr, so the cost of a multiplication is counted in scalar multiplications.

For dimensions 10×100, 100×5 and 5×50, the bracketing ((A1A2)A3) performs 10·100·5 = 5000 multiplications to get the 10×5 matrix A1A2, plus 10·5·50 = 2500 more, for 7500. The bracketing (A1(A2A3)) performs 100·5·50 = 25,000 plus 10·100·50 = 50,000, for 75,000. The first is ten times faster.

The problem is stated for a chain in which Ai has dimension pi−1×pi; the input is the sequence ⟨p0, p1, …, pn⟩. “The matrix-chain multiplication problem does not entail actually multiplying matrices.” The goal is only an order with the lowest cost, and the time spent finding it is typically more than paid for by the time saved when the multiplications are performed.

The number of parenthesizations satisfies P(1) = 1 and P(n) = Σ P(k)P(n−k) for k = 1, …, n−1 (14.6). A similar recurrence gives the Catalan numbers; Exercise 14.2-3 asks for a proof that this one is Ω(2n). Exhaustive search is therefore “a poor strategy”. The book then applies the four-step method: characterize the structure of an optimal solution, define its value recursively, compute the value, and construct the solution from computed information.

14.2 · filling the m and s tables

Short chains first, one diagonal at a time

Suppose the best way to multiply Ai⋯Aj makes its last multiplication after Ak. Then the cost is the best cost of the left piece, plus the best cost of the right piece, plus the price of that last multiplication, pi−1·pk·pj. You do not know k, so try every one from i to j−1 and keep the cheapest. Call the answer m[i, j] and keep the winning k in a second table, s[i, j].

There is one question for each pair i ≤ j, only Θ(n2) in all, so a table can hold every answer. The order matters: m[i, j] needs m[i, k] and m[k+1, j], which are shorter chains. So MATRIX-CHAIN-ORDER fills the table by chain length l = 2, 3, …, n: one diagonal after another, and everything a cell reads is already there. Three nested loops run at most n times each, which makes O(n3) time and Θ(n2) space.

The m table only says how much. The s table says how: PRINT-OPTIMAL-PARENS reads s[1, n] to find the last multiplication, then recurses into the two pieces.

Try it: press Step to test one split k. Two blue cells flow into the yellow one and the chips list every k tried, the cheapest so far in green; its k lands in s. Next cell finishes a cell, Play fills everything. Watch m[2, 5], the book's worked example: 13,000, 7,125 or 11,375. Then pick Print the parentheses and step through the recursion. In Rust, the strip shows each table as a Vec of row buffers, and the output string growing.

What the book says

The subproblem is to find the minimum cost of parenthesizing AiAi+1⋯Aj for 1 ≤ i ≤ j ≤ n; the pair (i, j) specifies it. Let m[i, j] be the minimum number of scalar multiplications needed to compute Ai:j, so the full problem costs m[1, n]. Then m[i, j] = 0 if i = j, and otherwise the minimum, over i ≤ k < j, of m[i, k] + m[k+1, j] + pi−1pkpj (14.7). Define s[i, j] to be a value of k at which the product is split in an optimal parenthesization.

A recursive algorithm based on (14.7) would take exponential time. “Fortunately, there aren’t all that many distinct subproblems”: one for each choice of i and j with 1 ≤ i ≤ j ≤ n, which is Θ(n2) in all. MATRIX-CHAIN-ORDER computes the optimal costs bottom-up, with an auxiliary table m[1 : n, 1 : n] for the costs and a table s[1 : n−1, 2 : n] that records which index k achieved the optimal cost. “The table s will help in constructing an optimal solution.”

“Thus, the algorithm should fill in the table m from shorter matrix chains to longer matrix chains.” The subproblem size is the chain length j − i + 1. The procedure fills the entries in order of increasing chain length; each entry depends only on entries already computed. The loops are nested three deep and each index takes at most n − 1 values, so the running time is O(n3) (Exercise 14.2-5 shows Ω(n3) too). The tables take Θ(n2) space.

Figure 14.5 shows the tables for n = 6 with dimensions 30×35, 35×15, 15×5, 5×10, 10×20, 20×25. The minimum is m[1, 6] = 15,125. For m[2, 5] the three candidates are 13,000, 7125 and 11,375, so m[2, 5] = 7125. The figure rotates the tables so the main diagonal runs horizontally; each diagonal holds the chains of one length.

Step 4 constructs a solution. Each s[i, j] records a k such that an optimal parenthesization of Ai⋯Aj splits between Ak and Ak+1, so the final multiplication for A1:n is A1:s[1,n]As[1,n]+1:n, and the earlier ones follow by recursion. The call PRINT-OPTIMAL-PARENS(s, 1, 6) prints the parenthesization (( A1(A2A3))((A4A5)A6)).

14.3 · optimal substructure

Cut out a part, paste in a better one

When should you reach for dynamic programming? The first ingredient is optimal substructure: an optimal solution to the problem contains within it optimal solutions to subproblems. Rod cutting has it: if the best way to cut a rod makes a first cut, the rest of the rod must itself be cut in the best possible way. So do matrix chains: if the best bracketing makes its last multiplication after Ak, the bracketing inside Ai…Ak must be the best one for that piece, and likewise for the other piece.

How can you be sure? The book's habit is the cut-and-paste argument. Suppose you are handed the choice that leads to an optimal solution, and look at the subproblems it leaves. Suppose one of the parts inside is not optimal. Cut it out, paste in an optimal one, and the whole gets better, although the whole was supposed to be optimal. That is a contradiction. The machine does the pasting: the whole is the price of the choice plus its parts, so a worse part makes the whole worse by exactly the same amount.

Problems differ in two ways: how many subproblems an optimal solution uses (rod cutting one, matrix chains two) and how many choices there are (n against j − i). Their product is roughly the running time, which the third view counts. Choose the subproblems with care, too: for matrix chains, pieces of the form A1…Aj are not enough, because the right piece does not start at 1. Both ends must vary, so a subproblem is a pair (i, j).

Try it: in Matrix chain or Rod cutting the optimal parts are pasted in. Click another solution under a part: the old one goes back on the shelf, the new one is pasted in, and the bar shows the whole against the optimum. Make a part worse and watch the whole lose exactly as much. Then, from the worse whole, paste the best part back (or press Paste the optimum): the whole improves, so the worse whole was never optimal. In Count the work, drag n and press Count.

What the book says

“Recall that a problem exhibits optimal substructure if an optimal solution to the problem contains within it optimal solutions to subproblems.” When a problem has it, dynamic programming might apply (Chapter 15 notes that a greedy strategy might apply too). Dynamic programming builds an optimal solution from optimal solutions to subproblems, so the range of subproblems you consider must include those used in an optimal solution.

The book finds optimal substructure by a common pattern. (1) A solution consists of making a choice, such as an initial cut in a rod or an index at which to split a matrix chain; the choice leaves one or more subproblems. (2) Suppose you are given the choice that leads to an optimal solution, without worrying how to find it. (3) Given this choice, determine which subproblems ensue and how best to characterize the space of subproblems. (4) Show that the solutions to the subproblems used within an optimal solution must themselves be optimal, by a “cut-and-paste” technique: suppose a subproblem solution is not optimal, cut it out and paste in the optimal one, and you get a better solution to the original problem, contradicting the supposition.

To characterize the space of subproblems, a good rule of thumb is to “try to keep the space as simple as possible and then expand it as necessary.” For rod cutting, rods of length i for each size i worked. For matrix-chain multiplication, restricting to products A1A2⋯Aj fails unless k always equals j − 1, since the other subproblem, Ak+1⋯Aj, does not have that form. Subproblems must vary at both ends: both i and j.

Optimal substructure varies across problem domains in two ways: how many subproblems an optimal solution uses, and how many choices there are for which subproblems to use. In rod cutting an optimal solution uses one subproblem, of size n − i, and there are n choices for i. Matrix-chain multiplication for Ai⋯Aj uses two subproblems and has j − i choices. Informally, the running time of a dynamic-programming algorithm depends on the product of two factors: the number of subproblems overall and how many choices you look at for each. Rod cutting has Θ(n) subproblems and at most n choices for each, so O(n2) time; matrix-chain multiplication has Θ(n2) subproblems with at most n − 1 choices each, so O(n3). In the subproblem graph the choices for a subproblem are the edges leaving its vertex.

The cost of a solution is usually the subproblem costs plus a cost directly attributable to the choice itself: the term pi in rod cutting, and pi−1pkpj in matrix-chain multiplication. A greedy algorithm differs: it makes the choice that looks best at the time and then solves the one resulting subproblem, instead of first solving all the related subproblems.

14.3 · overlapping subproblems and memoization vs bottom-up

The same question, asked again and again

The second ingredient is overlapping subproblems. A divide-and-conquer algorithm makes brand-new problems at every step. A dynamic-programming problem is different: its natural recursion keeps running into the same subproblems, and there are only a few distinct ones. The matrix-chain recursion is the example. To compute m[1, 4] it asks for m[3, 4] twice, for m[2, 2] five times, and every time it works the answer out from scratch.

That waste explodes. The book proves the plain recursion takes at least exponential time. The machine counts it exactly: 3 calls for 2 matrices, 9 for 3, 27 for 4, 81 for 5, so each extra matrix triples the work. Yet a chain of n matrices has only Θ(n2) different pairs (i, j). Solve each one once and remember it.

There are two ways to remember. Memoization keeps the recursion and adds a table: a subproblem's answer is stored the first time it is computed, and every later call just looks it up (MEMOIZED-MATRIX-CHAIN and LOOKUP-CHAIN). Bottom-up drops the recursion and fills the table by chain length, as before. Both run in O(n3). Bottom-up usually wins by a constant factor, since it has no recursion overhead. Memoization wins when some subproblems are never needed, because it only solves the ones the recursion reaches.

Try it: in Plain recursion press Step or Play and watch the tree of calls run, top to bottom. A blue node is the first time a subproblem is solved; a coral node is a repeat, the same work done again. Click any node to ring all the copies of its subproblem, and change n. Then try Memoized: repeats turn green (a lookup) and their subtrees are never visited. Bottom-up has no tree at all. The scoreboard compares the three for the n you chose.

What the book says

The second ingredient is that the space of subproblems must be “small” in the sense that a recursive algorithm solves the same subproblems over and over, rather than always generating new ones. Typically the total number of distinct subproblems is a polynomial in the input size. When a recursive algorithm revisits the same problem repeatedly, the optimization problem has overlapping subproblems. A divide-and-conquer approach, in contrast, usually generates brand-new problems at each step. Dynamic-programming algorithms solve each subproblem once and store the solution in a table, where it can be looked up in constant time.

For matrix-chain multiplication, MATRIX-CHAIN-ORDER repeatedly looks up subproblem solutions in lower rows of the table; for example, it references m[3, 4] four times, during the computations of m[2, 4], m[1, 4], m[3, 5] and m[3, 6]. The inefficient RECURSIVE-MATRIX-CHAIN is based directly on recurrence (14.7), and Figure 14.7 shows the recursion tree of the call RECURSIVE-MATRIX-CHAIN(p, 1, 4); some pairs of values occur many times. Its time to compute m[1, n] satisfies T(n) ≥ 2 Σ T(i) + n, and the substitution method shows T(n) = Ω(2n). There are only Θ(n2) distinct subproblems, and the bottom-up algorithm solves each exactly once; the recursive one solves each every time it reappears.

As a practical matter, store the choice made in each subproblem in a separate table. Without the s table, reconstructing which subproblems were chosen would take Θ(j − i) = ω(1) time per entry; with it, PRINT-OPTIMAL-PARENS looks each choice up in O(1) time.

Memoization keeps the top-down control structure of the natural recursive algorithm and maintains a table of subproblem solutions, each entry initially holding a special value that marks it as not yet filled in. When a subproblem is first encountered its solution is computed and stored; each later encounter simply looks it up. In MEMOIZED-MATRIX-CHAIN every entry starts at ∞, and LOOKUP-CHAIN returns m[i, j] at once if line 1 finds it below ∞. It runs in O(n3) time: there are Θ(n2) calls that compute a new entry, one per table entry, and O(n3) calls that only return a stored value, each taking O(1). Memoization turns an exponential-time algorithm into a cubic one. A footnote adds that the table can also be a hash table keyed by the subproblem parameters.

“In general practice, if all subproblems must be solved at least once, a bottom-up dynamic-programming algorithm usually outperforms the corresponding top-down memoized algorithm by a constant factor”, because it has no recursion overhead and less table overhead, and the regular access pattern can sometimes cut time or space further. On the other hand, if some subproblems need not be solved at all, the memoized solution has the advantage of solving only those that are definitely required.

14.3 · when a problem has no optimal substructure

Two best halves that fight over the same junctions

A courier must get from junction q to junction t in a small town. Four junctions, q r s t, sit on the corners of a square, and every side is a two-way street. The first job: use as few streets as possible. The second: use as many as possible without passing through any junction twice. Both sound like best-route problems, and dynamic programming only works if the best route is built from best sub-routes.

For the fewest-streets route, it is. Cut the route q → r → t at r: the front half is a shortest route from q to r, the back half a shortest route from r to t. If a better front half existed, you could cut and paste it in and beat the “shortest” route, which is absurd. The two halves also never meet again, because they share no junction except r.

For the most-streets route (the longest simple path) the same cut breaks. q → r → t is a best route, yet its front half is not the best way from q to r: q → s → t → r is longer. Worse, the two best halves use the same junctions, so gluing them together gives a walk that crosses itself. The subproblems are not independent: using a junction in one takes it away from the other. No efficient dynamic-programming algorithm is known for this problem.

Try it: with Shortest path chosen, press Play: the best halves, found on their own, rebuild a path of the same length. Switch to Longest simple path and play again: the halves come out longer, then collide. Click r or s (or use the buttons) to cut the route at the other junction.

What the book says

The book warns: “You should be careful not to assume that optimal substructure applies when it does not.” It compares two problems on a directed graph G = (V, E) with vertices u, v: the unweighted shortest path, a path with the fewest edges, and the unweighted longest simple path, a simple path with the most edges. Without the simplicity requirement the second problem is undefined, since “repeatedly traversing a cycle creates paths with an arbitrarily large number of edges.”

Shortest paths have optimal substructure. Any path p from u to v (with u ≠ v) contains an intermediate vertex w and splits into p1 from u to w and p2 from w to v, and the edge counts add. If p is shortest, a “cut-and-paste” argument shows that p1 and p2 are shortest too.

Longest simple paths do not. In Figure 14.6, q → r → t is a longest simple path from q to t, but q → s → t → r is a longer simple path from q to r, and r → q → s → t is a longer one from r to t. Combining those two gives q → s → t → r → q → s → t, “which is not simple.” So one cannot even assemble a legal solution from solutions to the subproblems. “No efficient dynamic-programming algorithm for this problem has ever been found”; the problem is NP-complete (Chapter 34).

The difference is independence: “the solution to one subproblem does not affect the solution to another subproblem of the same problem.” For longest simple paths, “using resources in solving one subproblem (those resources being vertices) renders them unavailable for the other subproblem.” For shortest paths, “by nature, the subproblems do not share resources”: a vertex x ≠ w on both halves would let you cut out the loop through w and save at least two edges, contradicting the optimality of p. The subproblems of rod cutting and matrix-chain multiplication are independent too.

14.4 · longest common subsequence

Same letters, same order, gaps allowed

Two strands of DNA, two versions of a file: how alike are they? One answer hunts for a third string whose letters appear in both, in the same order but not necessarily side by side. Take X = ⟨A, B, C, B, D, A, B⟩ and Y = ⟨B, D, C, A, B, A⟩. Leaving letters out of X gives a subsequence; one that can also be read off Y is a common subsequence. ⟨B, C, A⟩ qualifies, but ⟨B, C, B, A⟩ is longer, and nothing common is longer still: it is a longest common subsequence (LCS).

The brute-force way tries every subsequence of X. Each one is a subset of X's positions, so a string of m letters has 2m of them (128 here, over a million for 20 letters), and each must be checked against Y.

Dynamic programming needs a way to peel the problem. Look only at the last letters of two prefixes Xi and Yj. If they are equal, they can end an LCS together, and what is left is an LCS of the two shorter prefixes. If they differ, an LCS cannot use both, so one of them goes: the answer is the longer of two smaller problems. That is the optimal substructure of LCS, and the recurrence it gives for c[i, j] meets only Θ(mn) different prefix pairs.

Try it: in Subsequences, click letters of X to pick a subsequence: each pick finds its partner in Y, and the panel says whether it is common. Show an LCS lights one, and Brute force tries all 2m subsets while a counter runs. In The recurrence, click a letter in X and one in Y to choose the prefixes, then press Step: equal last letters take the diagonal, different ones try two smaller problems, and the counters show how often plain recursion repeats itself. Type your own strings in the boxes.

What the book says

Biological applications often compare the DNA of two organisms, written as strings over the four bases A, C, G, T. One measure of similarity is a third strand whose bases appear, in order but not necessarily consecutively, in both. For the book's strands S1 = ACCGGTCGAGTGCGCGGAAGCCGGCCGAA and S2 = GTCGTTCGGAATGCCGTTGCTCTGTAAA, the longest such strand is GTCGTCGGAAGCCGGCCGAA.

“A subsequence of a given sequence is just the given sequence with 0 or more elements left out.” For X = ⟨A, B, C, B, D, A, B⟩ and Y = ⟨B, D, C, A, B, A⟩ the sequence ⟨B, C, A⟩ is common but has length 3, while ⟨B, C, B, A⟩, also common, has length 4. ⟨B, D, A, B⟩ is another LCS, and there is no common subsequence of length 5 or more.

Step 1 of the method observes that each subsequence of X corresponds to a subset of the indices {1, 2, …, m}, so there are 2m of them and brute force “requires exponential time, making it impractical for long sequences.” Theorem 14.1 gives the optimal substructure. With Z an LCS of X and Y: if the last letters xm and yn are equal, then zk is that letter and Zk−1 is an LCS of Xm−1 and Yn−1; if they differ, Z is an LCS of Xm−1 and Y, or of X and Yn−1. The proofs use cut and paste: appending the common letter to a longer sub-solution would beat Z.

So you examine one or two subproblems, and the longer of the two answers wins. The problem also has overlapping subproblems: “Many other subproblems share subsubproblems.” With c[i, j] the length of an LCS of Xi and Yj, equation (14.9) says c[i, j] is 0 when i or j is 0, is c[i−1, j−1] + 1 when the last letters match, and is the larger of c[i, j−1] and c[i−1, j] otherwise. Unlike rod cutting and matrix chains, “a condition in the problem restricts which subproblems to consider.” There are only Θ(mn) distinct subproblems, so a table can fill them bottom up.

14.4 · the c table and PRINT-LCS

Fill the grid, then walk home along the arrows

The recurrence only ever asks about prefix pairs, and a pair of prefixes is a pair of lengths. So give each pair its own cell. The table c has a row for every prefix of X and a column for every prefix of Y, and row 0 and column 0 (the empty prefixes) hold 0. LCS-LENGTH fills the rest row by row. For each cell it looks at one letter from each string: equal letters take the diagonal neighbour plus one; different letters copy the larger of the neighbours above and to the left. Beside each number it leaves an arrow in a second table b, saying which neighbour it used.

Every cell costs a constant amount of work, so the whole table costs Θ(mn) instead of the brute force's 2m. The corner cell holds the length of an LCS. To get the letters, start at the corner and follow the arrows: every ↖ is a letter of the answer. PRINT-LCS recurses to the start first and prints on the way back out, so the letters appear in the right order.

Two refinements. The arrows are not essential: each number can be explained by its neighbours, so the b table can go. And if you only want the length, you never need more than two rows at a time. The price is that the letters can no longer be traced back.

Try it: press Step to compute one cell: its three neighbours light up, the rule picks a number and an arrow. Fill table does it all at once; then Play or Step to trace back from the corner, and watch the letters come out in order. Pick another pair of strings (Identical is all diagonals, Disjoint all zeros). Switch to Two rows only and watch the older rows disappear while the length survives.

What the book says

LCS-LENGTH takes X, Y and their lengths and stores the c[i, j] values in a table c[0 : m, 0 : n], computing the entries in row-major order: the first row left to right, then the second, and so on. It also maintains a table b[1 : m, 1 : n] to help in constructing an optimal solution. Intuitively, b[i, j] “points to the table entry corresponding to the optimal subproblem solution chosen” when computing c[i, j]. It returns both tables, and c[m, n] holds the length of an LCS. Each entry takes Θ(1) time, so the running time is Θ(mn). Figure 14.8 shows the tables for X = ⟨A, B, C, B, D, A, B⟩ and Y = ⟨B, D, C, A, B, A⟩; the entry in the lower right-hand corner is 4, the length of the LCS ⟨B, C, B, A⟩.

Step 4 constructs the LCS from b. Begin at b[m, n] and follow the arrows; each ↖ means that xi = yj is an element of the LCS. “This method gives you the elements of this LCS in reverse order.” The recursive PRINT-LCS “prints out an LCS of X and Y in the proper, forward order.” For the table of Figure 14.8 it prints BCBA, and it takes O(m + n) time, since each call decrements at least one of i and j.

“Improving the code”: you can eliminate the b table altogether, because each c[i, j] depends on only three other entries, and from its value you can tell in O(1) time which one was used. You can still reconstruct an LCS in O(m + n) time. This saves Θ(mn) space, but the auxiliary space for computing an LCS does not asymptotically decrease, since c takes Θ(mn) space anyway.

You can, however, reduce the space for LCS-LENGTH itself, “since it needs only two rows of table c at a time: the row being computed and the previous row.” This works if you need only the length of an LCS. If you must reconstruct the elements, the smaller table does not keep enough information to retrace the steps in O(m + n) time.

14.5 · optimal binary search trees

Put the busy words near the top

A translation program looks every word of a text up in a binary search tree. Some words, like the, are searched all the time; others, like naumachia, almost never. Each lookup costs the nodes it visits, which is depth + 1, so the busy words belong near the root. Say you know how likely each key k1 < … < kn is to be searched (probability pi), and how likely a search is to land in each gap between keys and miss: those misses end at dummy keys d0 … dn with probabilities qi. The expected search cost weights every node's depth + 1 by its probability, and an optimal binary search tree makes it as small as possible.

Neither the shortest tree nor the one with the likeliest key on top has to win, and trying every shape is hopeless, since there are exponentially many. But the problem has optimal substructure. A subtree always holds a contiguous run of keys ki … kj (and the dummies between and around them), and in an optimal tree every subtree is optimal for its own run: cut and paste again. So try each key kr in the run as root; its two subtrees are optimal trees for the keys on either side. Hanging a subtree under a new root pushes all its nodes one level deeper, which costs exactly its total probability w(i, j) more: e[i, j] = e[i, r−1] + e[r+1, j] + w(i, j).

OPTIMAL-BST fills three tables by increasing run length: e (the best cost of each run), w (its total probability, built from the run one shorter) and root (the winning r). Three nested loops make it Θ(n3), like matrix chains.

Try it: in Fill the tables, press Step: one run of keys is solved, each candidate root gets its cost, and the cheapest is written to e and root. Fill table finishes it. In Pick a root, click any root chip to see the best tree with that key on top, and Build it to watch the root table turn into that tree. The four buttons under the picture change the probabilities: with k₅ heavy the busiest key finally takes the root.

What the book says

The setting is a translation program that looks up each English word in a binary search tree keyed by the words. Given keys k1 < … < kn with search probabilities pi, and n + 1 dummy keys d0, …, dn for the values not in K (d0 for everything below k1, dn for everything above kn, with probabilities qi), the probabilities sum to 1 (equation 14.10). The cost of a search is the number of nodes examined, the depth plus 1, so the expected cost of a tree T is Σ(depth + 1)·pi + Σ(depth + 1)·qi (14.11).

Figure 14.9 gives n = 5 with p = 0.15, 0.10, 0.05, 0.10, 0.20 and q = 0.05, 0.10, 0.05, 0.05, 0.05, 0.10: tree (a) costs 2.80, tree (b), the optimal one, 2.75. This shows that an optimal tree is not necessarily one whose overall height is smallest, and “Nor does an optimal binary search tree always have the key with the greatest probability at the root.” Here k5 is the likeliest key, yet the optimal root is k2; the lowest cost with k5 at the root is 2.85. Exhaustive search needs exponentially many trees (Problem 12-4).

Step 1: every subtree contains keys in a contiguous range ki, …, kj together with the dummy keys di−1, …, dj, and in an optimal tree it must be optimal for that subproblem. “The usual cut-and-paste argument applies.” A range with no keys still holds one dummy key. This gives e[i, j] = qi−1 if j = i − 1, and otherwise the minimum over r from i to j of e[i, r−1] + e[r+1, j] + w(i, j) (14.14).

Step 3: the e and w tables run over [1 : n + 1, 0 : n] because a subtree holding only dn needs e[n + 1, n] and one holding only d0 needs e[1, 0]. The w table is a time-saver: w[i, j] = w[i, j − 1] + pj + qj (14.15) takes constant time instead of Θ(j − i). OPTIMAL-BST computes by increasing l and keeps the best r in root[i, j]. Like MATRIX-CHAIN-ORDER it runs in Θ(n3) time. Figure 14.10 shows the tables for Figure 14.9; building the tree from root is Exercise 14.5-1.

problem 14-4 · printing neatly

Where to break the lines

Pour a paragraph into lines at most M characters wide, one space between words. Every line except the last ends with some blank space, and the paragraph looks neat when those trailing gaps are small. The book prices a line by the cube of its trailing spaces, so one big gap costs far more than several small ones, and asks for the layout with the lowest total. The last line is free.

Why not just fill every line as full as it will go? Because greedy only sees the line in front of it: it can leave one huge gap to pay for later. Instead look at the last line of a best layout. It holds words i … j, and everything before it must be a best layout of the first i − 1 words. So c[j], the best cost for the first j words, is the smallest of c[i − 1] plus the cost of the line i … j, over every i where that line fits. Fill c from left to right and remember the winning i in p[j]; then read the lines off backwards.

A word and its space take at least 2 characters, so a line holds at most about M/2 words and each c[j] tries at most that many candidates: O(nM) time and Θ(n) space, far below trying all 2n−1 ways to break the paragraph.

To turn algorithm into altruistic you can copy a letter, replace one, delete one, insert one, swap two neighbours, and as the very last step throw away whatever is left of the old word. Store it, don't recompute it

Dynamic programming fits optimization problems where each choice leaves subproblems of the same form and the same subproblems keep coming back. It solves each one once and saves the answer in a table. The recipe: characterize an optimal solution, define its value recursively, compute the value (usually bottom-up), then construct the solution. → 14.1 Rod cutting

2n calls, n + 1 questions

CUT-ROD tries every first piece and recurses on the rest. Its recursion tree has 2n nodes and 2n−1 leaves, one per way to cut, yet only the sizes 0 to n ever occur. Each extra inch doubles the time. → 14.1 Naive recursion

Memoize, or fill from the bottom

Top-down keeps the recursion but checks a table first. Bottom-up solves the sizes smallest first, so every answer it needs is already there. Both fill the same table in Θ(n2) time; bottom-up usually has the smaller constants. → 14.1 Memoize it

A graph of dependencies

One vertex per subproblem, an edge x → y when x looks at y: the recursion tree with equal nodes merged. The running time is linear in |V| + |E|. Storing the best first piece s[j] next to r[j] lets PRINT-CUT-ROD-SOLUTION rebuild the cuts. → 14.1 Subproblem graph

Order matters in a matrix chain

Multiplying A1 … An can be parenthesized in Ω(2n) ways, and the cost differs wildly: 7500 against 75,000 scalar multiplications for 10×100, 100×5, 5×50. MATRIX-CHAIN-ORDER fills m and s by increasing chain length: Θ(n2) subproblems, up to n − 1 choices each, Θ(n3) time. → 14.2 Matrix chains, Filling the table

Two ingredients

Dynamic programming needs optimal substructure (an optimal solution contains optimal solutions to subproblems, shown by cut-and-paste) and overlapping subproblems (a small space that recursion revisits). Longest simple path has no optimal substructure, because its subproblems share vertices. → 14.3 Substructure, Overlap, When it fails

Common subsequences

An LCS keeps the letters of both strings in order, gaps allowed. If xi = yj, then c[i, j] = c[i − 1, j − 1] + 1, else the larger of its left and upper neighbours. LCS-LENGTH fills a Θ(mn) table with arrows; PRINT-LCS follows them back. → 14.4 LCS, LCS table

Trees, text and strings

An optimal binary search tree minimizes the expected search cost over keys and dummy keys, with tables e, w and root in Θ(n3) time. The same recipe solves the problems: longest palindrome subsequence, neat printing with the sum of cubes of trailing spaces, and edit distance with six operations. → 14.5 Optimal BST, 14-2 Palindromes, 14-4 Printing neatly, 14-5 Edit distance

Words to know

The book's words from this chapter, in plain language.

dynamic programming
Solving a problem by combining solutions to overlapping subproblems, solving each once and saving its answer in a table. “Programming” means the table, not code.
optimization problem
A problem with many solutions, each with a value, where you want one with the best (smallest or largest) value. That is an optimal solution, not the optimal one: several can tie.
the four steps
Characterize the structure of an optimal solution, define its value recursively, compute that value (typically bottom-up), construct a solution from what was computed.
rod-cutting problem
Given a rod of n inches and a price for each length, find the cuts with the greatest total revenue rn. A rod can be cut in 2n−1 ways.
recursion tree
One node per call, an edge from caller to callee. CUT-ROD's tree has 2n nodes though only n + 1 different sizes occur.
optimal substructure
An optimal solution to the problem contains optimal solutions to related subproblems, which can be solved independently.
cut-and-paste
The proof technique for optimal substructure: if a sub-solution were not optimal, cut it out, paste in a better one, and you would beat an optimum.
independent subproblems
Subproblems of one problem that do not share resources, so the solution of one does not affect the other. Shortest paths have them; longest simple paths do not.
overlapping subproblems
A small space of subproblems that a recursive algorithm meets again and again, so that solving each once pays off.
memoization
Top-down dynamic programming: write the natural recursion, but save each result and return the saved value when the subproblem comes back. From memo, not “memorization”.
bottom-up method
Solve the subproblems in size order, smallest first, storing each answer, so every prerequisite is already in the table.
time–memory trade-off
Spending memory on a table to save time on recomputing: exponential down to polynomial.
subproblem graph
A directed graph with a vertex per distinct subproblem and an edge x → y when solving x directly needs y. Its size, |V| + |E|, tracks the running time.
reconstructing a solution
Recording the choice made for each subproblem, such as s[j], so an optimal solution can be printed after the values are known.
matrix-chain multiplication
Choose the parenthesization of A1 … An that needs the fewest scalar multiplications. Matrix Ai is pi−1 × pi; the input is p0 … pn.
m[i, j] and s[i, j]
The least cost of computing Ai … Aj, and a split point k that achieves it.
subsequence
A sequence with zero or more elements left out, order kept. Unlike a substring it need not be contiguous.
longest common subsequence (LCS)
A longest sequence that is a subsequence of both X and Y. For ⟨A, B, C, B, D, A, B⟩ and ⟨B, D, C, A, B, A⟩ one is ⟨B, C, B, A⟩, length 4.
c and b tables
c[i, j] is the LCS length of the first i and first j elements; b[i, j] is the arrow saying which neighbour it came from.
optimal binary search tree
The tree over sorted keys, given each key's search probability and the probabilities of the gaps between them, with the least expected search cost.
dummy key
A leaf di standing for all searched values that fall between two keys, so unsuccessful searches have a cost too.
edit distance
The cheapest series of copy, replace, delete, insert, twiddle and kill operations that turns one string into another.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

padding slot 0
Prices and tables get one spare slot ([0, 1, 5, 8, …], a table one row and one column bigger), so p[i] is the book's pi and i - 1 never underflows a usize.
array, Vec, Vec<Vec<T>>
[i64; 11] has a fixed size and lives inline on the stack. A Vec owns a growable heap buffer, and vec![0; n + 1] fills one with zeros. A table is a Vec of row Vecs, indexed c[i][j].
&[T] and &mut [T]
A borrowed view of a run of items: a pointer and a length, no copy. &p from an array and &mut r from a Vec coerce to it.
&mut as a shared out-parameter
One mutable borrow handed down every recursive call, so all frames bump the same counter or append to the same String. *calls += 1 follows the borrow to the number.
∞ as a number
i64::MIN, u64::MAX and f64::INFINITY stand in for −∞ and ∞, and .max() and .min() pick the better value. An INF of i64::MAX / 4 leaves room to add a cost without overflow.
Option and HashMap as the memo
Vec<Option<i64>>: None means not solved yet, Some(v) a saved answer, and if let Some(v) = r[n] is the lookup. A HashMap<(usize, usize), u64> does the same for pairs: a missing key is “not computed yet”.
ranges 1..=n
a..b stops before b and a..=b includes it. (1..=j).rev() counts down, like the book's “downto”.
tuples and destructuring
A function returns (r, s), moving both Vecs out to the caller, and let (r, s) = … takes them apart. A leading underscore, as in _r, marks a value as unused on purpose.
bit masks
1u32 << k and mask >> i & 1 == 1 turn one integer into a set of yes-or-no choices. Unlike C, & binds tighter than ==.
enum + match
An arrow or an edit operation is a variant of an enum, which can even carry data, and a match without a _ arm must handle every case.
mem::swap and mem::replace
swap exchanges two values in place, so two table rows trade places in O(1) without copying their numbers. replace puts a new value in a slot and hands back the old one.
generics, closures, iterator chains
fn cheapest<T>(…, cost: impl Fn(&T) -> u64) works for any item type. .iter().map(…).sum() and (1..=10).map(|n| …).collect() replace small loops.
