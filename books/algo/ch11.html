Hash Tables

A hash table keeps a dictionary in an array about as big as the set it stores, by computing each key's slot with a hash function. Collisions can't be avoided, so the chapter resolves them with chains or by probing, chooses hash functions that behave as if random, and shows why a search then takes O(1) time on average.

“The bottom line is that hashing is an extremely effective and practical technique: the basic dictionary operations require only O(1) time on the average.” — Cormen, Leiserson, Rivest & Stein

11.1 · direct-address tables

A slot for every possible key

A coat check with numbered tickets 0 to 9 has one hook per ticket number. To find a coat nobody searches: they walk straight to hook k. That is direct addressing. When every key comes from a small universe U = {0, 1, …, m − 1}, keep an array T[0 : m − 1] with one slot per possible key. Slot k points to the element whose key is k, or holds NIL.

SEARCH, INSERT and DELETE each touch exactly one slot, so all three take O(1) time in the worst case, not just on average. The price is space. The table has |U| slots no matter how few keys K you actually store. With 32-bit keys that is 232 slots, 32 GiB of pointers, to hold perhaps four records.

In Rust a slot is an Option<Box<Record>>: None is NIL and the Box is the pointer to the element. Rust stores None as the null pointer, so the Option costs nothing extra. A slot is 8 bytes, the same as a bare pointer. The memory strip shows the table's buffer and the records it points to.

Try it: click a key in the top row, then press Insert, Search or Delete. Each one is a single jump from the key to its slot. Delete needs an element, so it only works on a key that is stored. Then switch to Huge universe and drag |U| up. You still store four records, but the table soon stops fitting in memory.

What the book says

Many applications need a dynamic set that supports only the dictionary operations INSERT, SEARCH and DELETE, such as a compiler's symbol table, whose keys are the identifiers of the program. A hash table is an effective data structure for dictionaries. Searching one can take Θ(n) time in the worst case, but under reasonable assumptions the average time is O(1). “Indeed, the built-in dictionaries of Python are implemented with hash tables.”

Direct addressing is a simple technique that works well when the universe U of keys is reasonably small. Each element has a distinct key drawn from U = {0, 1, …, m − 1}, where m is not too large. The dynamic set is an array, or direct-address table, T[0 : m − 1], in which each position, or slot, corresponds to a key in U. Slot k points to an element in the set with key k. If the set contains no element with key k, then T[k] = NIL. In Figure 11.1, U = {0, 1, …, 9} and the actual keys are K = {2, 3, 5, 8}.

DIRECT-ADDRESS-SEARCH, DIRECT-ADDRESS-INSERT and DIRECT-ADDRESS-DELETE are trivial to implement, and each takes only O(1) time. Note that DELETE takes the element x, not a key.

For some applications the table can hold the elements itself: store the object directly in the slot, and mark an empty slot with a special key. Why store the key at all? “The index of the object is its key!” But then you need some way to tell whether a slot is empty.

Section 11.2 names the downside (p. 275): if U is large or infinite, a table of size |U| may be impractical, or impossible given a typical computer's memory, and when the stored keys K are few compared with U, most of that space is wasted.

11.2 · hash tables

Ten slots, ten thousand keys

Direct addressing gave every possible key its own slot. Hashing keeps only m slots, far fewer than |U|, and computes where each key goes. A hash function h : U → {0, 1, …, m − 1} sends key k to slot h(k). We say k hashes to that slot, and h(k) is its hash value. Storage drops to Θ(|K|), and a search still takes O(1) time, but now only on average.

Because |U| > m, some keys must share a slot. That is a collision, and no choice of h avoids it: 10,000 keys into 10 slots puts at least 1,000 keys in some slot. A good h looks random, so the keys you actually store rarely meet. The ideal is independent uniform hashing. Each key gets a slot drawn uniformly at random, independently of every other key, and the same key always gets the same slot back. Such a function is also called a random oracle. It is the yardstick for the analysis. You can't build one.

The machine hashes ten prices in cents into m = 10 slots. With h(k) = k mod 10, the book's “simple, but not particularly good” example, prices that end in 0 or 5 pile into two slots. A random oracle spreads them out, yet it still collides early: with 10 slots the first collision comes, on average, at about the 4.7th key, the birthday paradox of Chapter 5. In Rust both hash functions are closures, passed to the same function as values.

Try it: press Play with k mod 10 and watch slots 0 and 5 fill up. Switch to independent uniform and press Play again. Hash again re-hashes a key that is already in: it goes back to the slot it got the first time. Run 1000 hashes the ten keys with 1,000 fresh random oracles and averages the results.

What the book says

When the set K of stored keys is much smaller than the universe U, a hash table needs much less storage than a direct-address table: Θ(|K|), while searching still takes only O(1) time. The catch is that this bound is for the average-case time, whereas for direct addressing it holds in the worst case. A footnote warns that “average-case” needs care: it can mean a distribution over the keys or a random choice of hash function, and the book emphasizes the second.

The hash function maps the universe into the slots of a hash table T[0 : m − 1], h : U → {0, 1, …, m − 1}, where m is typically much less than |U|. An element with key k hashes to slot h(k), and h(k) is the hash value of k. In Figure 11.2, keys k2 and k5 map to the same slot, so they collide. A simple, but not particularly good, hash function is h(k) = k mod m.

One idea is to make h appear random, which is the spirit of the word “to hash,” with its images of mixing and chopping. But h must be deterministic: a given input k always produces the same output h(k). Because |U| > m, at least two keys have the same hash value, and avoiding collisions altogether is impossible. So a method for resolving collisions is still needed: chaining (this section) or open addressing (Section 11.4).

An ideal hash function would give each input k an output h(k) chosen randomly and independently and uniformly from {0, 1, …, m − 1}, and every later call with the same k would return that same value. This is an independent uniform hash function, often called a random oracle, and using one is independent uniform hashing. It is an ideal theoretical abstraction that can't reasonably be implemented in practice. The book analyzes hashing under this assumption and then presents useful practical approximations to the ideal.

11.2 · collision resolution by chaining

Every slot keeps a short list

Collisions will happen, so give each slot room for more than one element. With chaining, slot j points to the head of a linked list holding every stored element whose hash value is j, and holds NIL if there is none. The book calls it a nonrecursive divide-and-conquer: h splits the n elements into m lists of about n/m each, and each list is managed on its own.

CHAINED-HASH-INSERT puts the new element at the front of its list: O(1) in the worst case, as long as the key is not already there. CHAINED-HASH-SEARCH walks the list, so it costs the list's length. CHAINED-HASH-DELETE is handed the element x itself, not its key, so with a doubly linked list it unlinks x in O(1) with no search at all.

Real Rust code rarely chains with linked nodes. Here each chain is a Vec<(u64, String)>: one contiguous buffer per slot, no allocation per element, no pointers to chase, and the cache brings neighbours in for free. Order inside a chain doesn't matter, so delete uses swap_remove, which moves the last pair into the hole in O(1). One thing is lost. Rust won't let you hold a reference to x while you change the table, so delete takes the key and searches first.

Try it: press Insert next to add the keys of Exercise 11.2-2 with h(k) = k mod 9. Each new key goes to the front of its list. Click a key to pick it, then press Search picked or Delete picked. Search a miss walks a whole list and finds nothing. Switch to Rust: each list turns into a buffer that appends at the back, and a delete fills the hole with the last pair.

What the book says

At a high level, hashing with chaining is a nonrecursive form of divide-and-conquer: the input set of n elements is divided randomly into m subsets, each of approximate size n/m. A hash function determines which subset an element belongs to, and each subset is managed independently as a list.

In Figure 11.3 each nonempty slot points to a linked list, and all the elements that hash to the same slot go into that slot's list. Slot j contains a pointer to the head of the list of all stored elements with hash value j; if there are none, it contains NIL. The lists can be singly or doubly linked. The figure shows them doubly linked because deletion may be faster when the procedure knows which list element, not just which key, to delete.

The dictionary operations use the linked-list procedures of Section 10.2. Insertion takes O(1) time in the worst case. It is fast in part because it assumes the element is not already present; to enforce that, you can search for the key first, at additional cost. Searching takes time proportional to the length of the list. Deletion takes O(1) time if the lists are doubly linked, because CHAINED-HASH-DELETE takes the element x, not its key, so no search is needed. With singly linked lists, deletion and searching would have the same asymptotic running times.

11.2 · analysis of hashing with chaining

The load factor sets the price

How long is a chain? With n elements spread over m slots, the load factor α = n/m is the average number of elements per chain. It can be below 1, exactly 1, or well above it.

The worst case is terrible. If all n keys hash to one slot, the table is a single linked list and a search takes Θ(n). Nobody uses hash tables for their worst case. Under independent uniform hashing, a missing key lands in a slot whose list has expected length α, so an unsuccessful search examines α elements on average and takes Θ(1 + α) time (Theorem 11.1). A successful search for x examines x plus the elements in front of it, which were all inserted after x. That averages 1 + α/2 − α/2n elements, again Θ(1 + α) (Theorem 11.2).

So keep n = O(m), growing the table as n grows, and α stays O(1): every dictionary operation then takes O(1) time on average. The 1 in 1 + α is the hash computation and the slot access, paid even when the chain is empty. The Rust simulation keeps only chain lengths in a Vec<usize> and divides with an explicit as f64, because Rust never converts between integers and floats on its own.

Try it: set n and m and press New fill. Search a miss and Search a hit each run one search and highlight the elements it reads. Average 1000 fills brings both measured averages onto their formulas. Then switch to Worst case, where every key lands in slot 0.

What the book says

Given a hash table T with m slots that stores n elements, the load factor α for T is n/m, the average number of elements stored in a chain. It can be less than, equal to, or greater than 1. The worst case of hashing with chaining is terrible: all n keys hash to the same slot, creating a list of length n, so searching takes Θ(n) plus the time to compute the hash function, no better than one linked list for all the elements.

The average case depends on how well h distributes the keys among the m slots. The analysis assumes independent uniform hashing: each element is equally likely to hash into any slot, independently of where the others go. That makes it universal: two distinct keys collide with probability at most 1/m. With nj the length of list T[j], n = n0 + n1 + ⋯ + nm−1 and E[nj] = α. Computing h(k) is assumed to take O(1) time, so the cost is the number of list elements examined.

Theorem 11.1: an unsuccessful search takes Θ(1 + α) time on average. A key not in the table is equally likely to hash to any slot, and the search runs to the end of a list of expected length α. Theorem 11.2: a successful search also takes Θ(1 + α) time on average, assuming the element sought is equally likely to be any of the n. Because new elements go at the front, the elements examined are 1 plus those inserted later into the same list. Indicator random variables and linearity of expectation give 1 + α/2 − α/2n, so the total is Θ(2 + α/2 − α/2n) = Θ(1 + α).

If n = O(m), then α = O(1) and searching takes constant time on average. Insertion is O(1) in the worst case, and so is deletion with doubly linked lists, so all dictionary operations take O(1) time on average. The analysis needs only uniformity and independence.

11.3.1 · static hashing: the division and multiplication methods

Keys with a pattern, and a table that notices

A good hash function should act as if every key picks a slot at random, independently of the others. Nobody can check that for real data, so a static hash function, one fixed formula, tries to produce slots that have nothing to do with any pattern in the keys. Real keys do have patterns: order numbers that go up by 8, record addresses aligned to 16 bytes, prices in whole cents.

The division method is h(k) = k mod m: one division, very fast. But if m = 2p, k mod m is just the lowest p bits of k, and keys that share their low bits all collide. In general keys that step by d can only reach the slots that are multiples of gcd(d, m), so a prime m not close to a power of 2 is the safe choice. The multiplication method, h(k) = ⌊m (kA mod 1)⌋, multiplies by a constant 0 < A < 1 and keeps the fractional part, which stirs every digit of k; there the value of m hardly matters.

Try it: press Play: 24 keys 8, 16, …, 192 go through k mod 16 and pile into just 2 of the 16 slots (watch the low 4 bits in the panel). Press m = 13 and Play again: the same keys use every slot. Switch to multiplication with m = 16, and drag stride to try other patterns.

What the book says

A good hash function satisfies (approximately) the assumption of independent uniform hashing: each key is equally likely to hash to any of the m slots, independently of where any other key has hashed. With a fixed function, that would depend on the distribution of the keys, which you typically cannot check. If the keys are known to be random reals uniformly distributed in 0 ≤ k < 1, then h(k) = ⌊km⌋ does satisfy it. A good static approach derives the hash value “independent of any patterns that might exist in the data.”

Keys in practice are short nonnegative integers that fit in a w-bit word (w typically 32 or 64), or short vectors of bounded integers such as byte strings. Static hashing uses a single, fixed hash function; the only randomness is the (usually unknown) distribution of the keys. “Although static hashing is no longer recommended,” the multiplication method is a good foundation for random hashing.

The division method: h(k) = k mod m. With m = 12 and k = 100, h(k) = 4. “The division method may work well when m is a prime not too close to an exact power of 2.” There is no guarantee of good average-case performance, and it constrains the table size to be prime.

The multiplication method: multiply k by a constant A with 0 < A < 1, take the fractional part of kA, multiply by m and take the floor: h(k) = ⌊m (kA mod 1)⌋, where kA mod 1 = kA − ⌊kA⌋. Its advantage is that “the value of m is not critical.” The book recommends random hashing instead of any fixed function. The machine's A = (√5 − 1)/2 is the constant of Exercise 11.3-4.

11.3.1 · the multiply-shift method

Three instructions and a window of bits

Floating-point kA mod 1 is slow and inexact. When the table size is a power of 2, m = 2ℓ, the multiplication method becomes pure integer work on w-bit machine words. Store A as the integer a = A · 2w. The product k · a fills two words, r1 2w + r0. The low word r0 is the fractional part of kA, written in binary, and its top ℓ bits are ⌊m (kA mod 1)⌋.

So the multiply-shift hash is ha(k) = (ka mod 2w) ≫ (w − ℓ). The mod 2w is free, because a CPU's ordinary multiply keeps only the low word anyway, and the logical right shift slides the top ℓ bits of r0 down to the bottom, filling with zeros. It is fast, but a fixed a still promises nothing about the average case. Choosing a as a random odd integer when the program starts fixes that (next scene).

Try it: press Play to watch the multiply, the subtract and the shift on a toy 16-bit machine (real words have 32 or 64 bits). Press k + 1 a few times: neighbouring keys jump to far-apart slots. Drag ℓ to resize the table. Then switch to w = 32 (book) for the book's own example, which hashes 123456 to 67.

What the book says

In practice the multiplication method is best when m = 2ℓ for an integer ℓ ≤ w, w being the number of bits in a machine word. Choose a fixed w-bit positive integer a = A 2w with 0 < A < 1, so 0 < a < 2w, and assume a key fits in one w-bit word. The product ka is a 2w-bit value r12w + r0; the ℓ-bit hash value is the ℓ most significant bits of r0 (Figure 11.4). Since r1 is ignored, a machine whose multiply returns only a w-bit product (modulo 2w) is enough.

Equation (11.2): ha(k) = (ka mod 2w) ≫ (w − ℓ), for a fixed nonzero w-bit a. ≫ is a logical right shift by w − ℓ bits, shifting zeros in on the left; it is the same as dividing by 2w−ℓ and taking the floor. The function “can be implemented with three machine instructions: multiplication, subtraction, and logical right shift.”

Example: k = 123456, ℓ = 14, m = 214 = 16384, w = 32, and a = 2654435769, following a suggestion of Knuth. Then ka = 327706022297664 = (76300 · 232) + 17612864, so r1 = 76300, r0 = 17612864, and the 14 most significant bits of r0 give ha(k) = 67.

Even though the method is fast, “it doesn’t provide any guarantee of good average-case performance.” A simple randomized variant works well on the average, when the program begins by “picking a as a randomly chosen odd integer.”

11.3.2–11.3.4 · random hashing and universal families

Beat the adversary by rolling the dice late

Publish your hash function and someone can attack it. An adversary who knows a fixed h simply picks keys that all land in the same slot, and every search crawls a chain of length n. No fixed function escapes this. The cure is random hashing: keep a whole family H of functions and pick one at random when the program starts, after the keys can no longer be chosen against it.

A family is universal if any two distinct keys collide under at most |H|/m of its functions, so the chance of a collision is at most 1/m, the same as if their slots were truly random. Then hashing with chaining handles any s operations, n = O(m) of them insertions, in Θ(s) expected time, whatever keys the adversary sends. One universal family is hab(k) = ((ak + b) mod p) mod m for a prime p: p(p − 1) functions, one per choice of a ≠ 0 and b. The faster family used in practice is multiply-shift with a random odd a, which is 2/m-universal: collisions at most twice as likely.

Try it: the adversary's 8 keys all sit in slot 0 under the published h3,4. Press Play to draw a and b at random and rehash them: the chain breaks up. Play again for another draw. Run 1000 measures how often a pair of these keys collides, and All functions counts it exactly over the whole family. Then try multiply-shift.

What the book says

If a malicious adversary chooses the keys to be hashed by some fixed hash function, it can choose n keys that all hash to the same slot, giving Θ(n) average retrieval time. “Any static hash function is vulnerable to such terrible worst-case behavior.” “The only effective way to improve the situation is to choose the hash function randomly in a way that is independent of the keys that are actually going to be stored.” As with quicksort, “randomization guarantees that no single input always evokes worst-case behavior.”

A finite family H of functions from U to {0, 1, …, m − 1} is universal if for each pair of distinct keys, the number of functions in H under which they collide is at most |H|/m. Independent uniform hashing is picking uniformly from all mn functions; every such family is universal, but not conversely (on U = {0, …, m − 1}, the family holding only the identity function is universal, since distinct keys never collide, yet each key hashes to a fixed value). Corollary 11.3: with universal hashing and chaining, an initially empty table with m slots handles any sequence of s INSERT, SEARCH and DELETE operations containing n = O(m) INSERTs in Θ(s) expected time.

Section 11.3.3 lists other properties, probabilities taken over the random pick of h: H is uniform if Pr{h(k) = q} = 1/m for every key and slot; ε-universal if distinct keys collide with probability at most ε (a universal family is 1/m-universal); d-independent if any d distinct keys land in any d given slots with probability 1/md.

Theorem 11.4: for a prime p larger than every key, the family Hpm of hab(k) = ((ak + b) mod p) mod m, with a ∈ {1, …, p − 1} and b ∈ {0, …, p − 1}, is universal; m need not be prime. Example: p = 17, m = 6 gives h3,4(8) = 5. The proof: distinct keys never collide modulo p, the pair (r1, r2) is equally likely to be any pair of distinct values, and at most (p − 1)/m of the p − 1 choices for r2 agree with r1 modulo m.

Theorem 11.5: the family of multiply-shift functions (equation (11.2)) with odd constants a is 2/m-universal. The book recommends it in practice: “It is exceptionally efficient and (although we omit the proof) provably 2/m-universal.” Often the speed of computing it more than makes up for the higher bound on collisions.

11.3.5 · hashing long inputs such as vectors or strings

Hashing a whole string, one byte at a time

Most real keys are not small numbers but strings: names, URLs, file paths, a vector of bytes of any length. They don't fit in one machine word, so the hash has to chew through the input piece by piece and still behave like a random function.

The number-theory way treats the bytes x0, …, xd−1 as the coefficients of a polynomial and evaluates it at a random point b modulo a prime p: hb(x) = (Σ xj bj) mod p, with one multiply and one add per byte (Horner's rule). Two different strings collide only when b is a root of their difference, a polynomial of degree at most d − 1, so at most d − 1 of the p choices of b are bad. The other way is a cryptographic hash such as SHA-256: 256 output bits that look random, so that changing one letter flips about half of them. With a random salt a prepended, ha(k) = SHA-256(a ‖ k) mod m is a whole family to pick from at random.

Try it: press Play to evaluate both anagrams, listen and silent, byte by byte with the same b. Every b tries all 65,521 values and marks the ones where they collide. Click any letter to change it. Then switch to SHA-256, press Play, and click one letter of the key: the changed bits light up. New salt moves the key to another slot.

What the book says

Some inputs are so long that they can't easily be encoded modulo a reasonably sized prime p, or in one word of, say, 64 bits: for example vectors of 8-bit bytes, which is how many languages store strings, possibly of arbitrary, varying length. One approach extends the universal-hashing ideas of Section 11.3.4; Exercise 11.3-6 hashes a d-tuple ⟨a0, …, ad−1⟩ of values in Zp by hb = (Σj aj bj) mod p for b ∈ Zp, and asks you to argue that this family is ε-universal for ε = (d − 1)/p.

Another is a hash function designed for cryptography: complex pseudorandom functions built for more demanding applications, but robust, widely implemented, and usable for hash tables. It takes an arbitrary byte string and returns a fixed-length output; the NIST standard SHA-256 produces 256 bits (32 bytes) for any input. Some CPUs implement rounds of the Advanced Encryption Standard as the “AES-NI” instructions: “These instructions execute in a few tens of nanoseconds, which is generally fast enough for use with hash tables.” A message authentication code such as CBC-MAC based on AES could be a useful and efficient hash function.

Cryptographic hash functions give an approximate random oracle, which is equivalent to an independent uniform hash function family. In theory a random oracle is an unachievable ideal: “a deterministic function that provides a randomly selected output for each input,” the same output each time it is asked again. In practice, families built from cryptographic hash functions are sensible substitutes.

One could define h(k) = SHA-256(k) mod m, and a family by prepending a salt string a: ha(k) = SHA-256(a ‖ k) mod m, where ‖ is concatenation. Cryptographic designs are becoming more practical as memories are arranged in hierarchies of differing capacities and speeds; Section 11.5 builds one on the RC6 encryption method.

11.4 · open addressing

Your first choice is taken? Try your second

Think of a car park with no overflow lot. Every driver has a personal list of favourite spaces: first choice, second choice, and so on through every space in the park. You park in the first free space on your list. To find your car later, you walk the same list until you reach it, and if you reach an empty space first, the car was never parked here, because you would have taken that space.

That is open addressing. Every key sits in the table itself, so there are no chains and no pointers, and the load factor α = n/m can never pass 1. The hash function takes a second input, the probe number i, and the probe sequence ⟨h(k, 0), h(k, 1), …, h(k, m − 1)⟩ must be a permutation of all m slots, so that a key can always find room while the table has any. HASH-INSERT and HASH-SEARCH both walk that sequence.

Deleting is the trap. Put NIL back in a slot and every key that once probed past that slot becomes unreachable, because the search now stops early at the hole. The fix is a tombstone: write the special value DELETED. Searches step over it, and insertions may reuse it. In Rust the three kinds of slot are one enum, and match has to handle each of them.

Try it: press Play to insert Exercise 11.4-1's nine keys and then search for 59, which retraces 59's own probes. Switch to Delete → NIL and press Play: once 4 is deleted, the search for 59 stops at the hole and wrongly reports NIL. Delete → DELETED runs the same steps with a tombstone, and the search succeeds. Then pick any k with the slider and use Insert k, Search k or Delete k. Fill the last two slots to see “hash table overflow”.

What the book says

Open addressing is a method for collision resolution that, unlike chaining, “does not make use of storage outside of the hash table itself.” Each entry holds an element of the dynamic set or NIL, so the table can “fill up” and the load factor α can never exceed 1. A new element goes to its “first-choice” location if possible, otherwise to its second choice, and so on, and different elements have different preference orders. You could store chains inside the table instead, “but the advantage of open addressing is that it avoids pointers altogether. Instead of following pointers, you compute the sequence of slots to be examined.” The memory saved buys more slots, potentially giving fewer collisions and faster retrieval.

The hash function becomes h : U × {0, 1, …, m − 1} → {0, 1, …, m − 1}, its second input being the probe number, and for every key the probe sequence ⟨h(k, 0), …, h(k, m − 1)⟩ must be a permutation of ⟨0, 1, …, m − 1⟩. HASH-INSERT assumes keys without satellite data and a key not already present; it returns the slot it used or flags an error when the table is full. HASH-SEARCH probes the same sequence the insertion examined, so it can stop unsuccessfully at an empty slot, since k would have been inserted there.

Deletion is tricky: “it would be a mistake to mark that slot as empty by simply storing NIL in it,” because a key whose insertion probed that slot and found it occupied could no longer be retrieved. Storing the special value DELETED solves this. HASH-INSERT treats such a slot as empty and may insert there, and HASH-SEARCH passes over it. But then “search times no longer depend on the load factor,” which is why chaining is often chosen when keys must be deleted. Linear probing avoids DELETED altogether (Section 11.5.1). HASH-DELETE itself is Exercise 11.4-2, so the machine's version is a sketch.

The analysis assumes independent uniform permutation hashing: each key's probe sequence is equally likely to be any of the m! permutations of ⟨0, 1, …, m − 1⟩. That is hard to implement truly, and approximations such as double hashing are used in practice. The machine uses Exercise 11.4-1's double hashing: m = 11, h1(k) = k, h2(k) = 1 + (k mod (m − 1)), and the keys 10, 22, 31, 4, 15, 28, 17, 88, 59.

11.4 · double hashing and linear probing

Two hash functions: where to start, how far to jump

Lay the table out like a clock face with 13 hours. A key starts at hour h1(k). If that hour is taken it jumps h2(k) hours clockwise, then the same distance again, and keeps going until it finds a free hour. That is double hashing: h(k, i) = (h1(k) + i·h2(k)) mod m. Two keys that start at the same hour usually jump by different amounts, so they part ways at once. With m prime there are about m2 different probe sequences, one per (start, jump) pair.

Fix the jump at 1 and you get linear probing, h(k, i) = (h1(k) + i) mod m: try the next slot, then the next, wrapping round at the end. The start decides everything, so there are only m probe sequences.

The jump must be relatively prime to m. If gcd(h2(k), m) = d > 1, the jumps come back to the start after visiting only m/d slots, and an insertion can report a full table while most of it is empty. The usual cure is a prime m with 1 ≤ h2(k) < m, or m a power of 2 with h2(k) always odd.

Try it: press Play to insert 14 into Figure 11.5's table: it jumps by 4 and lands in slot 9 on its third probe. The faint star is 14's whole probe sequence, and it passes through every slot. Switch to Linear probing, where the table is rebuilt with steps of 1, and press Play again. Then try m = 12: a jump of 4 traces a triangle, and HASH-INSERT reports overflow with 7 slots still empty. Drag k to try other keys.

What the book says

“Double hashing offers one of the best methods available for open addressing because the permutations produced have many of the characteristics of randomly chosen permutations.” It uses h(k, i) = (h1(k) + ih2(k)) mod m, where h1 and h2 are auxiliary hash functions. The first probe goes to T[h1(k)], and each later probe is offset by h2(k), modulo m. Figure 11.5 uses a table of size 13 with h1(k) = k mod 13 and h2(k) = 1 + (k mod 11): since 14 ≡ 1 (mod 13) and 14 ≡ 3 (mod 11), the key 14 goes into empty slot 9, after slots 1 and 5 are examined and found to be occupied.

For the entire table to be searched, “the value h2(k) must be relatively prime to the hash-table size m.” Either let m be an exact power of 2 and design h2 to produce only odd numbers, or let m be prime and h2 return a positive integer less than m, for example h1(k) = k mod m and h2(k) = 1 + (k mod m′) with m′ slightly less than m. With k = 123456, m = 701 and m′ = 700, the first probe goes to slot 80 and successive probes examine every 257th slot. Exercise 11.4-5: if gcd(m, h2(k)) = d ≥ 1, an unsuccessful search for k examines (1/d)th of the table before returning to slot h1(k).

When m is prime or an exact power of 2, double hashing produces Θ(m2) probe sequences, one for each (h1(k), h2(k)) pair, and it appears to perform close to the ideal of independent uniform permutation hashing, which would need all m! permutations. It cannot generate more than m2 sequences.

“Linear probing, a special case of double hashing, is the simplest open-addressing approach to resolving collisions.” It probes T[h1(k)], then the next position, on up to T[m − 1], then wraps around to T[0], T[1], and so on, never going past T[h1(k) − 1]. It is double hashing with h2(k) = 1 for all k, so h(k, i) = (h1(k) + i) mod m (equation (11.6)), and only m distinct probe sequences are possible. Section 11.5.1 returns to it.

11.4 · analysis of open-address hashing

Why a half-full table costs two probes and a 90% full one ten

Look for a key that isn't there. The first probe always happens. It lands on an occupied slot with probability n/m = α, and only then is there a second probe. That one hits a key with probability (n − 1)/(m − 1), which is a little less than α, and so on. So the chance of needing an ith probe is at most αi−1, and the expected count is at most 1 + α + α2 + ⋯ = 1/(1 − α) (Theorem 11.6). An insertion is an unsuccessful search that then stops at the empty slot, so it costs the same (Corollary 11.7).

A successful search is cheaper. Finding k retraces the probes made when k was inserted, and back then the table was emptier. The (i + 1)st key went in when α was i/m, which cost at most m/(m − i) probes. Averaged over all n keys that is at most (1/α) ln(1/(1 − α)) (Theorem 11.8): under 1.387 probes at half full, under 2.559 at 90%.

Both bounds assume independent uniform permutation hashing, where each probe sequence is a uniformly random permutation, and no deletions. The machine simulates exactly that model, with each probe going to a random slot not yet probed. The Rust program measures the same averages for a 20-slot table.

Try it: press One search. Blue cells were probed and held a key; the search stops at the first empty one, in mint. The bars are Pr{X ≥ i}, and the ticks above them are αi−1. Press Run 1000, then drag α up to 0.90 and press Sweep α: the dots follow just under the blue curve. Switch to Successful search and press Fill a table. Each key shows how many probes it took to insert, which is also what a later search for it will cost.

What the book says

The analysis is in terms of the load factor α = n/m. With open addressing at most one element occupies each slot, so n ≤ m and α ≤ 1. The analysis requires α < 1, so at least one slot is empty, and “because deleting from an open-address hash table does not really free up a slot, we assume as well that no deletions occur.” It assumes independent uniform permutation hashing: the probe sequence used to insert or search for each key is equally likely to be any permutation of ⟨0, 1, …, m − 1⟩. Of course “any given key has a unique fixed probe sequence associated with it”; what is meant is that each possible probe sequence is equally likely over the distribution of keys.

Theorem 11.6: given an open-address hash table with load factor α = n/m < 1, the expected number of probes in an unsuccessful search is at most 1/(1 − α), assuming independent uniform permutation hashing and no deletions. In the proof, X is the number of probes and Ai the event that an ith probe occurs and is to an occupied slot. Pr{X ≥ i} = (n/m)((n − 1)/(m − 1)) ⋯ ((n − i + 2)/(m − i + 2)) ≤ αi−1, and summing gives E[X] ≤ Σ αi = 1/(1 − α). The bound “has an intuitive interpretation. The first probe always occurs.” With probability about α it finds an occupied slot and a second probe happens, with probability about α2 a third, and so on. A half-full table needs at most 2 probes on average for an unsuccessful search, a 90% full one at most 10.

Corollary 11.7: inserting an element into an open-address hash table with load factor α < 1 requires at most 1/(1 − α) probes on average, because an insertion is an unsuccessful search followed by placing the key in the first empty slot found.

Theorem 11.8: with α < 1, the expected number of probes in a successful search is at most (1/α) ln(1/(1 − α)), assuming independent uniform permutation hashing with no deletions and each key equally likely to be searched for. “A search for a key k reproduces the same probe sequence as when the element with key k was inserted.” If k was the (i + 1)st key inserted, the load factor then was i/m, so the search makes at most m/(m − i) probes on average. Averaging over the n keys and bounding the harmonic sum by an integral gives the result. “If the hash table is half full, the expected number of probes in a successful search is less than 1.387. If the hash table is 90% full, the expected number of probes is less than 2.559.”

11.5.1 · linear probing

Next door is almost free

The RAM model charges the same for every probe. A real CPU doesn't. Memory arrives from main memory in cache blocks of (say) 64 bytes, so one fetch brings eight 8-byte slots at once, and touching a neighbour of a slot you just read costs almost nothing. Linear probing, h(k, i) = (h1(k) + i) mod m, always steps to the next slot, so its probes usually stay inside the block it already has. Double hashing jumps h2(k) slots at a time and usually lands in a new block.

The price is primary clustering. Keys pile up in runs of full slots, and an empty slot just after a run of i full slots is the next one filled with probability (i + 1)/m: every key that lands anywhere in the run slides to its end. Long runs grow longer. In the RAM model that is plain bad. With a memory hierarchy a run sits in one or two blocks, so a search pays for a few fetches, not one per probe.

Linear probing can even delete without a DELETED marker, because every key walks the same cyclic sequence from its own start h1(k). Empty slot q, then walk right. A key k′ at slot q′ passed the hole on its way in if g(k′, q) < g(k′, q′), where g(k, q) = (q − h1(k)) mod m is the probe number that reaches slot q. That key moves back into the hole, the hole moves to q′, and the walk stops at the first empty slot.

Try it: in Delete, press Step to run LINEAR-PROBING-HASH-DELETE on Figure 11.6, deleting 43 from slot 3. Each arc is the path a key took when it was inserted; a path through an empty slot turns coral and that key is lost. Pick Only NIL and Play again to see that happen to 93 and 92. Click any key to delete it instead, or press New keys. In Cache blocks, press Insert 8 a few times, then Search a miss, and compare slots probed with cache blocks read.

What the book says

Section 11.5 looks at two features of modern CPUs that the standard RAM model leaves out: memory hierarchies and advanced instruction sets. Memory runs from fast registers through levels of cache to main memory, each level larger and slower. “Furthermore, cache memory is organized in cache blocks of (say) 64 bytes each, which are always fetched together from main memory.” Counting slots probed is only a crude approximation, since once a cache block is in the cache, further probes to it are much faster than probes that go to main memory.

“Linear probing is often disparaged because of its poor performance in the standard RAM model. But linear probing excels for hierarchical memory models, because successive probes are usually to the same cache block of memory.” Deletion works without DELETED because all keys follow the same simple cyclic probing sequence, though from different starting points; it does not work for open addressing in general. The inverse function g(k, q) = (q − h1(k)) mod m gives the probe number that reaches slot q. If g(k′, q) < g(k′, q′), slot q was examined and found occupied when k′ was inserted, so k′ moves to q (line 10) and the search goes on for keys that should move into the slot just freed.

Figure 11.6 uses m = 10 and h1(k) = k mod 10 with keys inserted in the order 74, 43, 93, 18, 82, 38, 92. Deleting 43 from slot 3 moves 93 up to slot 3, then 92 up to slot 5. “No other keys need to be moved.”

Linear probing “exhibits a phenomenon known as primary clustering”: long runs of occupied slots build up, because an empty slot preceded by i full slots is filled next with probability (i + 1)/m. In the RAM model double hashing usually does better. In a hierarchical memory model clustering helps, as elements are often stored together in the same cache block, and the running time of HASH-INSERT, HASH-SEARCH or LINEAR-PROBING-HASH-DELETE for a key k is at most proportional to the distance from h1(k) to the next empty slot. Theorem 11.9 (Pagh et al., with a newer proof by Thorup): if h1 is 5-independent and α ≤ 2/3, searching, inserting and deleting take expected constant time, and O(1/ε2) for α = 1 − ε. The need for 5-independence “is by no means obvious.”

11.5.2 · hash functions for hierarchical memory models

A hash that never leaves the registers

Linear probing works best with a very random hash function: Theorem 11.9 asks for 5-independence. Random-looking functions sound slow, but on a machine with a memory hierarchy a few multiplications inside the CPU's fast registers cost less than one trip to main memory for a random slot. So the book builds a hash function from nothing but addition, multiplication and swapping the two halves of a word, and calls it wee because it needs only a tiny amount of memory.

One round is fa(k) = swap((2k2 + ak) mod 2w). In w-bit arithmetic the overflow just falls off the top. A change in bit i of k can only change bits i and above of the product, so the swap brings the high half down where the next round can stir it in again. Run it r times and you get fa(r), which is one-to-one for odd a: a small block cipher with key a. A t-bit key k hashes to f(r)a+2t(k + b) mod m. Adding b randomizes the input. Adding 2t to the key makes inputs of different lengths hash differently, and it is 2t rather than t so the key stays odd.

Longer inputs are chopped into w-bit words k1, …, ku, least significant first, with the last word padded with 0 bits. WEE then chains them: q starts at b, and each word is added to q and run through r rounds. Padding means "ab" and "ab" followed by a zero byte chop to the very same word. Only their lengths t differ, and through a + 2t that is enough.

Try it: in One word, press Step to follow WEE on the key 42 with a = 123, the value used in the book's timing runs. Each row shows q in hex, and its strip marks the bits that differ from a second run whose key has bit j flipped. With j = 63, one round changes a single bit. Press Play and watch rounds 2 to 4 spread the change, then try r = 1 and other values of j. In Many words, pick ab and then ab\0 (with a zero byte at the end): same chopped word, different slot. New a, b draws another member of the hash family; Reset brings back the book's.

What the book says

“This section illustrates an approach for designing efficient hash tables in a modern computer system having a memory hierarchy.” Linear probing suits a memory hierarchy because its probe sequences stay within cache blocks, but it is most efficient with a complex hash function, and a memory hierarchy means complex functions can be implemented efficiently. One option is a cryptographic hash function such as SHA-256. “Instead, we present here a simple hash function based only on addition, multiplication, and swapping the halves of a word.” It runs entirely within the fast registers, is related to the RC6 encryption algorithm, and can for practical purposes be considered a random oracle.

Let w be the (even) word size, a and b unsigned w-bit integers with a odd, and swap(x) = (x ⋙ (w/2)) + (x ⋘ (w/2)). Then fa(k) = swap((2k2 + ak) mod 2w), and fa(r) iterates it r times. For odd a and any r ≥ 0 it is one-to-one (Exercise 11.5-1); a cryptographer would view it as a simple block cipher with r rounds and key a. For a t-bit input with t ≤ w, equation (11.7) defines ha,b,t,r(k) = (f(r)a+2t(k + b)) mod m. Adding b keeps the 0-length input from having a fixed hash value; using 2t rather than t keeps the key odd. The function has no name in the literature; it is a variant the authors developed for the textbook.

“It is surprising how much efficiency can be bought with locality.” In the authors' unpublished experiments on a 2019 MacBook Pro with w = 64 and a = 123, evaluating wee took less time than probing a single randomly chosen slot: for large hash tables it was 2 to 10 times faster than one probe.

For long or variable-length inputs, chop(k) splits a t-bit key into u = ⌈t/w⌉ words, k1 holding the least-significant w bits and the unused high-order bits of ku padded with 0-bits. Given t, chop is one-to-one, and a single-word key yields a single word, so WEE is a consistent extension of (11.7). The book recommends a randomly chosen odd w-bit a, a random w-bit b, and r = 4. The family's approximate 5-independence can be argued from treating the 1-word function as a random oracle and from the security of CBC-MAC. “This definition of a cryptographically inspired hash-function family is meant to be realistic, yet only illustrative, and many variations and improvements are possible.”

problem 11-3 · slot-size bound for chaining

How long is the longest chain?

Hash n keys into a chained table with n slots, each key equally likely to land in each slot. The load factor is 1, so the average chain holds one key. But a search for an unlucky key walks the longest chain, and that one is longer. Call its length M. Problem 11-3 proves that its expected value grows like lg n / lg lg n: it does grow, but even more slowly than lg n.

The proof runs in five steps. One slot gets exactly k keys with the binomial probability Qk = C(n, k) (1/n)k (1 − 1/n)n−k. The fullest slot holds k keys only if some slot does, so by a union bound Pk = Pr{M = k} ≤ nQk. Stirling's approximation gives Qk < ek/kk, which collapses so fast that at k0 = c lg n / lg lg n it is under 1/n3, and every Pk beyond is under 1/n2. Finally M is never more than n, so E[M] ≤ Pr{M > k0} · n + Pr{M ≤ k0} · k0 = O(lg n / lg lg n).

Try it: press Play to hash n keys into n slots and see M marked. Press Run 1000: the bars become the measured Pk, and they always stay under the dots nQk from parts (a) and (b). Move n and run again. Then switch to Growth and press Run to estimate E[M] from n = 8 up to 65,536 against lg n / lg lg n and lg n.

What the book says

Given a hash table with n slots and collisions resolved by chaining, n keys are inserted, each equally likely to be hashed to each slot. M is the maximum number of keys in any slot after all the keys have been inserted, and the mission is to prove an O(lg n / lg lg n) upper bound on E[M], the expected value of M.

(a) The probability that exactly k keys hash to a particular slot is Qk = (1/n)k (1 − 1/n)n−k C(n, k). (b) With Pk the probability that M = k, show Pk ≤ nQk. (c) Show Qk < ek/kk, using Stirling's approximation, equation (3.25).

(d) Show that some constant c > 1 gives Qk0 < 1/n3 for k0 = c lg n / lg lg n, and conclude Pk < 1/n2 for k ≥ k0. (e) Argue that E[M] ≤ Pr{M > c lg n / lg lg n} · n + Pr{M ≤ c lg n / lg lg n} · c lg n / lg lg n, and conclude E[M] = O(lg n / lg lg n).

The chapter on one page

Chapter 11 in eight cards. Each one points at the scenes that act it out.

A slot per key

When the universe is small, U = {0, 1, …, m − 1}, a direct-address table gives key k slot T[k]. SEARCH, INSERT and DELETE are O(1) in the worst case. But the table has |U| slots however few keys are stored, which is wasteful at first and impossible for large universes. → 11.1 Direct addressing

Compute the slot

A hash function h : U → {0, 1, …, m − 1} cuts storage to Θ(|K|) and keeps search O(1), now on average. Since |U| > m, collisions can't be avoided. The ideal yardstick is independent uniform hashing, a random oracle. → 11.2 Hashing

Chains and α = n/m

Chaining keeps a list per slot. Insert prepends in O(1), and delete is O(1) given x in a doubly linked list. A miss reads α elements on average and a hit 1 + α/2 − α/2n: Θ(1 + α) either way, Θ(n) if every key lands in one slot. With n keys in n slots, the longest chain is expected O(lg n / lg lg n). → 11.2 Chaining, Load factor, 11-3 Longest chain

Fixed formulas

Division, k mod m, wants a prime m far from a power of 2, or keys that share low bits collide. Multiplication, ⌊m (kA mod 1)⌋, barely cares about m. Multiply-shift does it in three instructions: (ka mod 2w) ≫ (w − ℓ). → 11.3.1 Static hashing, Multiply-shift

Roll the dice at start-up

Every fixed h has n keys that all collide, and an adversary can find them. So pick h at random from a universal family, where two distinct keys collide with probability at most 1/m, such as ((ak + b) mod p) mod m, or multiply-shift with a random odd a, which is 2/m-universal. → 11.3.2 Random hashing

Strings and vectors

Long keys get hashed piece by piece. One way evaluates a polynomial at a random point modulo a prime, and two different strings then collide for only a few bad points. The other runs a cryptographic hash such as SHA-256 on a random salt plus the key, then takes the result mod m. → 11.3.5 Long inputs

Everything in the table

Open addressing probes ⟨h(k, 0), …, h(k, m − 1)⟩, a permutation of the slots, so α ≤ 1. Deleting needs a DELETED marker. Double hashing jumps by h2(k), and linear probing by 1. Expected probes are at most 1/(1 − α) for a miss and (1/α) ln(1/(1 − α)) for a hit. → 11.4 Open addressing, Double hashing, Probe counts

Count cache misses, not probes

On real memory, linear probing's neighbouring probes share a cache block, which outweighs primary clustering, and it can delete without markers by moving keys back. The wee hash mixes words with multiply, add and swap inside the registers, so it stays fast even though it looks random. → 11.5.1 Linear probing, 11.5.2 Memory-aware

chaining
Resolving collisions by keeping, in each slot, a linked list of the elements that hash there.

n/m: elements per slot on average. With chaining it can exceed 1.
unsuccessful / successful search
A search for a key that is absent, which reads its whole list, or present, which stops when it reaches the key.
static hashing
One fixed hash function for all data. It works for many inputs, but some inputs always defeat it.
division method
h(k) = k mod m.
multiplication method

random hashing
Choosing the hash function at random from a family when the program starts, independently of the keys.
universal family
A family where any two distinct keys collide with probability at most 1/m over the random choice of h. ε-universal allows ε instead of 1/m.

Any d distinct keys land in any d given slots with probability exactly 1/md.
open addressing
Every element is stored in the table itself. A key that finds its slot taken tries others, so α ≤ 1.

double hashing
h(k, i) = (h1(k) + i·h2(k)) mod m, with h2(k) relatively prime to m.
linear probing
Double hashing with a step of 1: try the next slot, wrapping around. Only m different probe sequences.
primary clustering
Linear probing's runs of full slots, which tend to grow because every key that lands in a run ends up at its end.
independent uniform permutation hashing
The open-addressing ideal: each key's probe sequence is equally likely to be any of the m! permutations.
