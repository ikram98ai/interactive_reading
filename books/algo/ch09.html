Medians and Order Statistics

The minimum, the median, the 90th percentile: each is the ith smallest of n numbers, and none of them needs the numbers sorted. This chapter finds the minimum and maximum with the fewest possible comparisons, then picks out any rank in linear time, on average with a random pivot and in the worst case with a carefully chosen one.

9.1 · minimum and maximum

Everyone but the champion loses once

Line up n distinct numbers by size. The one in place i is the i-th order statistic: the minimum is the 1st, the maximum the nth, and the median sits halfway. With odd n there is one median, at i = (n + 1)/2. With even n there are two, the lower median at n/2 and the upper at n/2 + 1, and the book's “the median” always means the lower one. The selection problem asks for the element larger than exactly i − 1 others. Sort first, then read off A[i], and it costs O(n lg n). This chapter does better.

The minimum alone is easy. MINIMUM walks the array once, keeping the smallest so far: n − 1 comparisons. It can't be done in fewer. Picture any minimum-finding algorithm as a knockout tournament where every comparison is a match and the smaller number wins. Each match makes exactly one loser, and every element except the champion has to lose at least once (otherwise it could still be the minimum). That makes n − 1 losers, so at least n − 1 matches. MINIMUM is optimal in comparisons, and the maximum works the same way.

Try it: in Order statistics, press Step twice to sort and pick, then drag i. Drag n to an odd number and the two medians become one. Switch to MINIMUM and press Play: each comparison greys out its loser. Then try Tournament. The matches come in a different order, but there are still exactly n − 1 of them.

What the book says

The ith order statistic of a set of n elements is its ith smallest element: the minimum is the first (i = 1) and the maximum the nth. Medians occur at i = ⌊(n + 1)/2⌋ and i = ⌈(n + 1)/2⌉ whatever the parity of n, and the text uses “the median” to mean the lower median. The selection problem: given a set A of n distinct numbers and an integer i with 1 ≤ i ≤ n, output the element of A that is larger than exactly i − 1 others.

Distinctness is only for convenience: “virtually everything that we do extends to the situation in which a set contains repeated values.” Sorting with heapsort or merge sort and outputting the ith element solves selection in O(n lg n) time. The chapter's algorithms are asymptotically faster.

MINIMUM(A, n) examines each element in turn and keeps track of the smallest seen so far, an upper bound of n − 1 comparisons. The maximum takes n − 1 as well.

The matching lower bound treats any algorithm for the minimum as a tournament: each comparison is a match, and the smaller element wins. “Since every element except the winner must lose at least one match, we can conclude that n − 1 comparisons are necessary to determine the minimum.” So MINIMUM is optimal with respect to the number of comparisons performed.

9.1 · simultaneous minimum and maximum

Two at a time is cheaper

A graphics program that fits a cloud of (x, y) points onto a screen needs the smallest and the largest value of each coordinate. The obvious way runs MINIMUM and then the maximum: n − 1 comparisons each, 2n − 2 in all. That is Θ(n) and asymptotically optimal, but the constant 2 can still come down.

The trick is to take the elements in pairs. Compare the two members of a pair with each other first. Now only the smaller one could be a new minimum, and only the larger one a new maximum, so 1 + 1 + 1 = 3 comparisons settle 2 elements, not 4. To start: if n is odd, the first element is both the minimum and the maximum so far. If n is even, one comparison of the first two sets both. That gives 3⌊n/2⌋ comparisons for odd n and 3n/2 − 2 for even n, so at most 3⌊n/2⌋ either way.

Try it: press Play in One at a time and watch every element meet both boxes. Then switch to In pairs and Play again: the bars at the bottom compare the two counts. Drag n between odd and even numbers to see how the start changes.

What the book says

Some applications need both the minimum and the maximum, for example a graphics program that scales a set of (x, y) data to fit a rectangular display: it must first determine the minimum and maximum value of each coordinate. Finding them independently uses n − 1 comparisons for each, 2n − 2 = Θ(n) in total.

“Although 2n − 2 comparisons is asymptotically optimal, it is possible to improve the leading constant.” Keep both the minimum and the maximum seen so far. Rather than comparing each element with both, at 2 comparisons per element, process the elements in pairs: compare the two with each other, then the smaller with the current minimum and the larger with the current maximum, 3 comparisons for every 2 elements.

The start depends on the parity of n. If n is odd, set both the minimum and the maximum to the first element and process the rest in pairs. If n is even, make 1 comparison on the first 2 elements to set the initial minimum and maximum. Odd n costs 3⌊n/2⌋ comparisons. Even n costs 1 + 3(n − 2)/2 = 3n/2 − 2. Either way the total is at most 3⌊n/2⌋. (Exercise 9.1-4 asks for the matching lower bound of ⌈3n/2⌉ − 2 comparisons in the worst case.)

9.2 · selection in expected linear time

Partition, then follow one side only

To find the 5th smallest of 15 numbers you don't need all 15 in order. RANDOMIZED-SELECT borrows quicksort's main move. It picks a random pivot and partitions the window A[p : r] so that everything smaller ends up to the pivot's left and everything larger to its right. The pivot now sits exactly where sorting would put it, and k = q − p + 1 is its rank inside the window.

Now compare i with k. If they are equal, the pivot is the answer. If i < k, the answer is on the low side. If i > k, it is on the high side, and it is the (i − k)th smallest there, because the k elements thrown away were all smaller. Quicksort goes on to sort both sides. Select keeps one, and that alone takes the expected time from Θ(n lg n) down to Θ(n).

Every call is a tail call, so the Rust version is a loop (Exercise 9.2-2). The window is a single &mut [i32] that gets narrowed inside the same Vec, with no copying and no new stack frame per round. The memory strip shows the slice's pointer sliding along the buffer.

Try it: press Step to go through RANDOMIZED-SELECT one line at a time. Line 3 plays a whole partition, with PARTITION's lines lighting up. Play replays Figure 9.1 and fills in its table. Then switch to Random pivots, pick i and press Play a few times. The pivots and the number of rounds change, but the answer never does.

What the book says

The general selection problem looks harder than finding a minimum, yet both take Θ(n) time. RANDOMIZED-SELECT is a divide-and-conquer algorithm modeled after quicksort (Chapter 7), and like quicksort it partitions the input array recursively. “But unlike quicksort, which recursively processes both sides of the partition, RANDOMIZED-SELECT works on only one side of the partition.” Quicksort's expected running time is Θ(n lg n), RANDOMIZED-SELECT's is Θ(n), assuming distinct elements. It returns the ith smallest element of A[p : r], where 1 ≤ i ≤ r − p + 1, and uses RANDOMIZED-PARTITION from Section 7.3, which swaps a randomly chosen element into A[r] and then calls PARTITION (pp. 184 and 192).

Line 1 checks for the base case, a one-element subarray, where i must be 1. Line 3 partitions A[p : r] into A[p : q − 1] and A[q + 1 : r], possibly empty, with each element of the first at most A[q] and A[q] less than each element of the second. Line 4 computes k, the number of elements on the low side plus 1 for the pivot. If i = k, the pivot is the answer. If i < k, line 8 recurses on the low side. Otherwise the answer is the (i − k)th smallest element of A[q + 1 : r]. The procedure still gives the correct result if equal elements are present, and Exercise 9.2-1 shows that it never recurses on an empty subarray.

The worst case is Θ(n2), even for the minimum: it could always partition around the largest remaining element, removing only the pivot each time, so T(n) = T(n − 1) + Θ(n). But the expected running time is linear, “and because it is randomized, no particular input elicits the worst-case behavior.”

Figure 9.1 runs it on ⟨6, 19, 4, 12, 14, 9, 15, 7, 8, 11, 3, 13, 2, 5, 10⟩ with i = 5. Five partitionings narrow (p, r, i) from (1, 15, 5) to (5, 5, 1), and the answer is the element left at p = r = 5.

9.2 · selection in expected linear time (the analysis)

Shrinking by quarters adds up to 8n

Suppose every pivot landed in the middle half, between the lower and upper quartiles. Whichever side survives, at least a quarter of the elements leave play, so at most 3/4 remain. The work is then n + 3n/4 + 9n/16 + …, a geometric series bounded by 4n. In recurrence form that is T(n) = T(3n/4) + Θ(n) = Θ(n).

Real pivots are random, so call a partitioning helpful when it leaves at most 3/4 of the elements in play. A random pivot falls in the middle half with probability at least 1/2 (Lemma 9.1), so on average it takes at most 2 tries to get a helpful one. Group the run into generations that each start with a helpful partitioning. Every set in generation k holds at most (3/4)kn elements, and a generation has at most 2 partitionings on average, each costing less than the size of its set. The expected total is less than 2n(1 + 3/4 + 9/16 + …) = 8n comparisons (Theorem 9.2).

The worst case is still there. A pivot that is always the largest element removes one element per round, and finding the minimum then costs n(n − 1)/2 comparisons, which is Θ(n2). Randomness does not remove that case. It makes it vanishingly unlikely, and no input can force it.

Try it: press Run once. Each dot is one partitioning, plotted on a log scale, and green dots are helpful. The dashed staircase is the proof's bound (3/4)kn. It steps down at every helpful dot, and every dot stays under it. Press Run 200 and watch the histogram of comparisons ÷ n pile up well left of the 8n line. Drag i to 1 and the mean drops to about 2n. Then try Always the largest.

What the book says

Intuition: if each random pivot lies in the second or third quartile, the “middle half”, then at least 1/4 of the remaining elements are ignored in all future recursive calls, whichever side the answer is on. The worst-case recurrence becomes T(n) = T(3n/4) + Θ(n), which is Θ(n) by case 3 of the master method. A random pivot falls in the middle half about half the time, a Bernoulli trial needing two trials on average, so the expected number of partitionings at most doubles and each extra one costs less than the one before.

To make this rigorous, let A(j) be the set of elements still in play after j partitionings, with A(0) = A. The jth partitioning is helpful if |A(j)| ≤ (3/4)|A(j−1)|. Lemma 9.1: a partitioning is helpful with probability at least 1/2. The proof defines the middle half of an n-element subarray as all but the smallest ⌈n/4⌉ − 1 and the greatest ⌈n/4⌉ − 1 elements. A pivot there removes at least ⌈n/4⌉ elements, leaving at most ⌊3n/4⌋. The pivot misses the middle half with probability at most 2(⌈n/4⌉ − 1)/n ≤ 1/2.

Theorem 9.2: on n distinct elements the expected running time is Θ(n). Number the helpful partitionings h0 = 0 (a dummy), h1, …, hm, so that nk = |A(hk)| ≤ (3/4)kn0. Generation k is the sets from A(hk) up to the next helpful partitioning, and Xk = hk+1 − hk counts them, with E[Xk] ≤ 2. The jth partitioning compares the pivot with the other |A(j−1)| − 1 elements, so the total is less than the sum of Xk(3/4)kn0. By linearity of expectation it is less than 2n0 times the sum of (3/4)k, which is 8n0. The first call examines all n elements, so the bound is tight: Θ(n).

The probability of a helpful partitioning is actually higher than 1/2. A partitioning is also helpful when the pivot misses the middle half but the ith smallest element happens to lie in the smaller side. The proof only uses the bound of 1/2.

9.3 · selection in worst-case linear time

A pivot you can trust

RANDOMIZED-SELECT is fast on average, but a run of unlucky pivots makes it quadratic. SELECT takes the luck out: it computes a pivot that is guaranteed to sit near the middle. The catch is that finding that pivot is itself a selection problem, so SELECT calls itself twice: once on a small set to find the pivot, and once on one side of the partition to find the answer.

First it trims: while the window A[p : r] doesn't hold a multiple of 5 elements, it moves the minimum to A[p] and steps past it (0 to 4 times). Then it reads the window as five rows of g. Each column, ⟨A[j], A[j + g], …, A[j + 4g]⟩, is a group of 5 spaced g apart in memory. Sorting every column puts every group's median in the middle row, which is the middle fifth A[p + 2g : p + 3g − 1], one contiguous stretch. SELECT on that stretch returns the median of the medians, x.

Line the groups up by their medians and the picture explains everything. The groups on x's left each have three elements no bigger than x, and the groups on its right each have three no smaller. So PARTITION-AROUND x can't leave more than about 7n/10 elements on either side, and the recursion into one side always shrinks by a fixed fraction, whatever the input.

Try it: press Step to strip the two minima, then watch the 25 numbers fold into five rows of 5 and each column sort itself. Keep stepping: the middle row gives x, the shaded corners show what is known to be ≤ x and ≥ x, and the partition sends everything back into the array. Play runs to the answer. Move i, or press New numbers; in Rust the memory strip shows one frame per call, all borrowing the same buffer.

What the book says

SELECT runs in Θ(n) time in the worst case, where RANDOMIZED-SELECT is quadratic in its worst case. But SELECT is not nearly as practical as RANDOMIZED-SELECT. “It is mostly of theoretical interest.” It also finds the answer by recursively partitioning the input, but guarantees a good split by choosing a provably good pivot. “The cleverness in the algorithm is that it finds the pivot recursively.”

Its partitioning step, PARTITION-AROUND, is the deterministic PARTITION from quicksort (Section 7.1) with the element to partition around as an extra input; like PARTITION it returns the pivot's index, and its pseudocode is omitted. SELECT takes a subarray A[p : r] of n = r − p + 1 elements and an integer i with 1 ≤ i ≤ n, and returns the ith smallest element. “The pseudocode is actually more understandable than it might appear at first.”

The while loop of lines 1–10 runs 0 to 4 times. Each pass puts the minimum of A[p : r] into A[p]; if i = 1 that minimum is the answer, and otherwise lines 9–10 drop it and look for the (i − 1)st element of A[p + 1 : r]. After the loop, the g = (r − p + 1)/5 groups are ⟨A[p], A[p + g], …, A[p + 4g]⟩, ⟨A[p + 1], A[p + g + 1], …⟩, and so on, up to the last one, which ends at A[r] (r = p + 5g − 1). Line 13 sorts each group, for example with insertion sort, so that A[j] ≤ A[j + g] ≤ A[j + 2g] ≤ A[j + 3g] ≤ A[j + 4g].

The median of each group is then A[j + 2g], so all the group medians lie in A[p + 2g : p + 3g − 1]. Line 16 finds the pivot x as the ⌈g/2⌉th smallest of them, and line 17 partitions around it, returning the index q with A[q] = x. The rest mirrors RANDOMIZED-SELECT: return the pivot if it is the answer, or recurse on A[p : q − 1] or A[q + 1 : r]. Figure 9.3 draws each sorted group as a column, with the groups ordered by their medians, to show which elements are known to be ≤ x and which ≥ x.

9.3 · selection in worst-case linear time (the analysis)

Why five, and not three

Charge SELECT line by line. Outside its recursive calls everything is linear: at most four scans to strip minima, g sorts of 5 elements at constant cost each, one partition. The pivot call (line 16) works on just the g ≤ n/5 medians. Only one of lines 23 and 24 runs, and the picture of the groups lined up by their medians caps its size: ⌈g/2⌉ medians are ≤ x, each with two more below it, so at least 3g/2 elements can't land on the high side, and the same count works for the low side. Either side keeps at most 5g − 3g/2 = 7g/2 ≤ 7n/10 elements.

That gives the recurrence T(n) ≤ T(n/5) + T(7n/10) + Θ(n). The two subproblems together are only 1/5 + 7/10 = 9/10 of the input, so each level of the recursion tree costs at most 9/10 of the level above. The levels form a shrinking geometric series, and the total is at most 10 times the top level: Θ(n). In the substitution proof the missing tenth is exactly the room that pays for the Θ(n) work.

Now try groups of 3. Then 1/3 + 2/3 = 1: nothing is lost from level to level, every level costs about n, and the best this argument proves is O(n lg n). Groups of 7 work too, with 1/7 + 5/7 = 6/7. And selection beats the Ω(n lg n) lower bound for comparison sorting because it never sorts the whole input.

Try it: press Step to charge each part of SELECT; the cost lands as a note on its line and a term in the recurrence. At line 16 the medians light up; at lines 23–24 the shaded corners show what can't cross over. Keep stepping to see the level costs and the substitution. Switch to groups of 3 and groups of 7 and compare the bars; move g to recount the picture. The Rust program runs all three on real shuffled inputs.

What the book says

Theorem 9.3. The running time of SELECT on an input of n elements is Θ(n). The proof defines T(n) as the worst-case time of SELECT on any subarray of size at most n, so T(n) is monotonically increasing. Outside the recursive calls in lines 16, 23 and 24: the while loop of lines 1–10 runs O(1) times at Θ(n) each; sorting the groups takes Θ(n), because each 5-element group takes Θ(1) time even with insertion sort and there are n/5 − 1 < g ≤ n/5 of them; partitioning takes Θ(n) (Exercise 7.1-3). The pivot call takes T(g) ≤ T(n/5); at most one of lines 23 and 24 runs, on at most 7n/10 elements.

In Figure 9.3 the yellow region holds ⌊g/2⌋ + 1 group medians and the blue region ⌈g/2⌉, each with two more elements beyond them, so both regions contain at least 3g/2 elements. The yellow elements can't fall into the low side of the partition around x and the blue ones can't fall into the high side; with 5g elements in all, the low side holds at most 5g − 3g/2 = 7g/2 ≤ 7n/10, and likewise the high side. Hence recurrence (9.1): T(n) ≤ T(n/5) + T(7n/10) + Θ(n).

By substitution, T(n) ≤ c(n/5) + c(7n/10) + Θ(n) ≤ 9cn/10 + Θ(n) = cn − cn/10 + Θ(n) ≤ cn if c is large enough that c/10 dominates the constant hidden in the Θ(n), and large enough to cover the base cases n ≤ 4. The Akra-Bazzi method of Section 4.7 would also solve it. Because line 13 alone takes Θ(n), the total is Θ(n).

Like comparison sorts, both selection algorithms learn about the order only by comparing elements, yet they are not subject to the Ω(n lg n) lower bound, “because they manage to solve the selection problem without sorting all the elements.” Exercise 9.3-1 asks you to show that groups of 7 also give linear time. Problem 9-6 shows that any odd group size greater than 3 works, and that groups of 3 give O(n lg n); that is only an upper bound, so it is not known whether groups of 3 actually run in O(n) time. Its SELECT3 repeats the groups-of-3 idea on the middle group of medians to guarantee O(n).

problem 9-1 · largest i numbers in sorted order

The top three, three ways

A leaderboard needs the top i scores out of n, best first. The obvious way sorts everything and reads the end: Θ(n lg n) comparisons, most of them spent putting the losers in order, which nobody asked for.

A max-heap does less. Building it takes only Θ(n), and each EXTRACT-MAX costs O(lg n), so the top i cost Θ(n + i lg n). The selection way is better still on paper: find the ith largest with SELECT in Θ(n), partition around it so the top i sit together, and sort only those: Θ(n + i lg i). The rest of the array is never sorted at all.

The best asymptotic bound and the fewest comparisons are not the same thing, though. SELECT's constant factor is large, so for small i the heap's linear-time build wins. Swap SELECT for RANDOMIZED-SELECT (or std's select_nth_unstable) and method (c) is cheap in practice as well.

Try it: press Play to run the three methods on ten numbers, one after another. Each ends with the top i in green at the right end; look at what happened to the rest. Change i and compare the comparison counts. Then switch to At scale and drag n and i: the bars are real comparison counts, in units of n.

a. Sort the numbers, and list the i largest. b. Build a max-priority queue from the numbers, and call EXTRACT-MAX i times. c. Use an order-statistic algorithm to find the ith largest number, partition around that number, and sort the i largest numbers.

The chapter's introduction notes that the selection problem itself can be solved in O(n lg n) time by sorting the numbers with heapsort or merge sort and then outputting the ith element of the sorted array; Sections 9.2 and 9.3 give asymptotically faster algorithms. problem 9-3 · weighted median

Where to build the post office

Seven villages lie along one road, and some send far more mail than others. Give village k a weight wk, its share of all the mail, so the weights add up to 1. The weighted median is the village xk where the road balances: the villages left of it weigh less than ½ in total, and the ones right of it weigh at most ½. In the book's example the ordinary median is 4, but the weighted median is 6, because the village at 8 alone carries 0.35. With equal weights 1/n it is just the ordinary (lower) median.

Now place the office at p to make the total weighted distance Σ wi|p − xi| as small as possible. Nudge p to the right and every bit of weight on its left gets a little farther away while every bit on its right gets closer, so the cost changes at the rate (weight left) − (weight right). Keep moving while more weight lies ahead; stop where the weight behind reaches ½. That point is the weighted median. To find it, sort by position and add up weights until the total reaches ½: O(n lg n). Or, in Θ(n), let SELECT find the plain median, add up the weight on one side, and recurse into the heavier half only.

On a city grid with Manhattan distance |x1 − x2| + |y1 − y2|, the east–west and north–south parts of the cost don't interact. Solve each axis on its own: the best office stands at the weighted median of the x's and the weighted median of the y's, often a corner where no village is.

Try it: drag the office (or use the p slider, or the arrow keys on the marker) and watch the cost curve and the left/right weights. Then press Step to run the scan: the bar below adds the weights in sorted order until it crosses ½. Try Equal weights, then 2-D (Manhattan), where you drag the office anywhere on the grid.

Problem 9-3. Consider n elements x1, …, xn with positive weights w1, …, wn such that the weights sum to 1. The weighted (lower) median is an element xk such that the weights of the elements less than xk sum to less than 1/2, and the weights of the elements greater than xk sum to at most 1/2.

For the elements 3, 8, 2, 5, 4, 1, 6 with weights 0.12, 0.35, 0.025, 0.08, 0.15, 0.075, 0.2, the median is x5 = 4 but the weighted median is x7 = 6: the elements less than 6 weigh 0.45 in total, less than 1/2, and the only greater element, x2, weighs 0.35, no greater than 1/2.

(a) Argue that the median is the weighted median when every weight is 1/n. (b) Compute the weighted median in O(n lg n) worst-case time using sorting. (c) Compute it in Θ(n) worst-case time using a linear-time median algorithm such as SELECT.

In the post-office location problem the input is n points p1, …, pn with weights w1, …, wn, and a solution is a point p, not necessarily one of the input points, that minimizes the sum of wi d(p, pi). (d) Argue that the weighted median is a best solution in one dimension, with d(a, b) = |a − b|. (e) Find the best solution in two dimensions with the Manhattan distance d(a, b) = |x1 − x2| + |y1 − y2|.

Rank without sorting

The ith order statistic is the ith smallest element. The minimum is i = 1, the maximum i = n, and the medians sit at ⌊(n + 1)/2⌋ and ⌈(n + 1)/2⌉. Sorting finds any of them in O(n lg n), and this chapter does it in Θ(n). → 9.1 Minimum

n − 1 is the floor

Pairs save a quarter

The 1st and the nth order statistics.
median
The halfway element. Odd n has one, at (n + 1)/2. Even n has a lower median at n/2 and an upper one at n/2 + 1, and “the median” means the lower.
selection problem
Given n distinct numbers and a rank i, find the one that is larger than exactly i − 1 of the others.
distinct elements
No two equal. Assumed for convenience; pairing each value with its index enforces it.
lower bound
A cost no algorithm can beat. For the minimum it is n − 1 comparisons.
tournament argument
Each comparison is a match the smaller element wins. Every element but the winner has to lose a match.
optimal
No algorithm uses fewer of the counted resource, here comparisons, in the worst case.
processing in pairs
Compare two elements with each other, then the smaller with the minimum and the larger with the maximum: 3 comparisons for 2 elements.
pivot
The element a partition splits around. It ends up in its sorted position q.
low side / high side
After partitioning, A[p : q − 1] holds elements at most the pivot and A[q + 1 : r] those larger.
randomized algorithm
One whose behavior depends partly on a random-number generator, such as a random pivot.
expected running time
The average over the algorithm's own random choices, for any fixed input.
in play
The elements still inside the current subarray A[p : r]: the set A(j) after j partitionings.
middle half
The elements between the lower and upper quartiles. A pivot from there throws out at least a quarter.
helpful partitioning
One that leaves at most 3/4 of the elements in play. A random pivot gives one with probability at least 1/2.
generation
In the proof of Theorem 9.2, a helpful partitioning plus the unhelpful ones after it: on average at most 2 partitionings.
group median
The middle element of a sorted group of 5. In SELECT they all land in the middle fifth of the subarray.
median of the medians
SELECT's pivot: the median of the group medians, found by calling SELECT recursively.
PARTITION-AROUND
PARTITION with the pivot given as an argument instead of taken from A[r].
comparison model
Algorithms that learn the order of elements only by comparing pairs. Sorting there needs Ω(n lg n), selection doesn't.
weighted median
With weights summing to 1: the element whose smaller elements weigh less than 1/2 and whose larger ones weigh at most 1/2.
post-office location problem
Pick the point that minimizes the total weighted distance to n weighted points. On a line, the weighted median solves it.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

Option<&T> from min()
a.iter().min() returns Some(&smallest), or None for an empty slice. The compiler makes you handle the empty case.
slice patterns
match pair { [x, y] => …, [x] => … } matches a slice by its length and binds its items in one step.
*count += 1
Writing through a &mut u32: the * reaches the caller's variable, so a counter can be shared without a global.
sort_by + total_cmp
f64 is not Ord, because NaN has no place in an order. Sort floats with sort_by(|a, b| a.total_cmp(b)).
FnMut closures
A closure that changes what it captured, like a comparison counter or an RNG. It must be declared mut, and impl FnMut(usize) -> usize accepts one as a parameter.
chunks_exact + remainder
Walks a slice in pieces of exactly k items. Whatever doesn't fill a piece waits in remainder().
narrowing a &mut slice
w = &mut w[..q] points the same borrow at part of the buffer. The window shrinks with no copy and no new stack frame.
#[derive(Default)]
Lets the compiler write Tally::default(), with every field set to zero.
bool as u64
true as u64 is 1, so a test can be counted. 4 * after <= 3 * before checks at most 3/4 without floating point.
[T; N] and const generics
A fixed-size array on the stack, such as a group of 5. With const Q: usize one function serves groups of 3, 5 or 7.
select_nth_unstable
The standard library's selection: it puts the kth smallest at index k, with smaller items before it and larger ones after.
BinaryHeap
The standard library's max-priority queue. BinaryHeap::from(vec) heapifies the vector's own buffer, and pop() returns an Option.
