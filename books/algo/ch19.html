Data Structures for Disjoint Sets

Some programs must keep track of which items belong together while groups keep merging: ask which group an item is in, or merge two groups. Chapter 19 builds the structure that does both, first with linked lists, then with rooted trees and two small tricks that make each operation almost constant time.

“The running time using the tree representation is theoretically superlinear, but for all practical purposes it is linear.” — Cormen, Leiserson, Rivest & Stein

19.1 · disjoint-set operations

Who belongs with whom?

Picture ten villages and a pile of road-building orders. Each time a road is finished, two regions of villages become one. At any moment you only want to know: can you drive from here to there? You could search the whole road map for every question, or you could keep a list of regions and, when a road joins two of them, merge the two entries.

That list is a disjoint-set data structure: a collection of disjoint dynamic sets, which means no village is ever in two sets and the sets change over time. Each set names one member as its representative, the captain you ask for. It may be any member, as long as it stays the same until the set changes. Three operations are all you get: MAKE-SET(x) starts a new set containing only x, FIND-SET(x) returns the representative of x's set, and UNION(x, y) merges the two sets that contain x and y.

The machine runs the book's CONNECTED-COMPONENTS on the graph of Figure 19.1: every vertex starts as a set of its own, and for every edge whose two ends have different representatives, UNION joins them. Afterwards SAME-COMPONENT answers a road question by comparing two representatives.

Try it: press Step and follow the highlighted lines: first ten MAKE-SETs, then each edge in three steps: pick it, compare the two FIND-SETs, UNION. Watch the sets counter: every UNION lowers it by exactly 1, and the last edge, (b, c), is skipped because b and c already share a representative. Then click two vertices and press SAME-COMPONENT, or Add edge to join two components yourself. Reverse order reaches the same components through different sets.

What the book says

A disjoint-set data structure maintains a collection S = {S1, S2, …, Sk} of disjoint dynamic sets. Each set is identified by a representative, some member of the set. In some applications it does not matter which member is used, only that asking twice for the representative of a set, without modifying the set in between, gives the same answer both times. Other applications need a prespecified rule, such as choosing the smallest member of a set whose elements can be ordered.

Each element is an object x. MAKE-SET(x), where x does not already belong to another set, creates a new set whose only member, and thus representative, is x. UNION(x, y) unites the sets Sx and Sy that contain x and y; the representative of the result is any member of the union, though many implementations pick the representative of one of the two. Because the sets must always be disjoint, UNION destroys Sx and Sy, and implementations often absorb the elements of one set into the other. FIND-SET(x) returns a pointer to the representative of the unique set containing x.

The running times are analyzed in two parameters: n, the number of MAKE-SET operations, and m, the total number of MAKE-SET, UNION and FIND-SET operations. So m ≥ n, the first n operations are MAKE-SETs, and since each UNION reduces the number of sets by 1, at most n − 1 UNIONs can occur.

An application is finding the connected components of an undirected graph. CONNECTED-COMPONENTS places each vertex in its own set and, for each edge (u, v), unites the sets containing u and v. By Exercise 19.1-2, after all edges are processed two vertices are in the same component if and only if they are in the same set, so SAME-COMPONENT can answer queries. When the edges are static, depth-first search computes the components faster; when edges are added dynamically, with the components updated as each edge arrives, this implementation can be more efficient than running a new depth-first search for each new edge.

19.2 · linked-list representation of disjoint sets

Every item knows its team sheet

A coach keeps each team as a chain of player cards. A card holds a name, a pointer to the next card, and a pointer back to the team's set object, a sheet that says who is first (head) and who is last (tail). The first player is the captain. To find a player's captain you follow two pointers: card to sheet, sheet to head. That is FIND-SET, and it takes the same time for a team of three or three million. MAKE-SET is just as cheap: one card, one sheet.

Merging teams is the catch. UNION(x, y) glues y's chain onto the end of x's, quickly, thanks to the tail pointer. But every card that came from y's team still points back to y's old sheet, which is about to be thrown away, so each of those pointers must be rewritten: the cost is the length of y's list.

That cost can pile up. Make n single-card teams, then merge them one after another, always gluing the long chain onto a lone card: the ith union rewrites i pointers, 1 + 2 + … + (n − 1) in all. Those 2n − 1 operations cost Θ(n2), so Θ(n) each on average.

Try it: in Figure 19.2 press Step three times: find the two set objects, splice the lists, rewrite the pointers (the yellow dots turn blue one by one). Click any cell to run FIND-SET on it. Then choose UNION(e, g) and run it again: the same seven items end up in one set, but the bars at the bottom show a different price. Switch to The worst sequence and press Play: the bars grow 1, 2, 3, …

What the book says

Each set is represented by its own linked list. The set object has attributes head, pointing to the first object in the list, and tail, pointing to the last. Each object in the list contains a set member, a pointer to the next object, and a pointer back to the set object. Within a list the objects may appear in any order. “The representative is the set member in the first object in the list.”

With this representation MAKE-SET and FIND-SET require only O(1) time. MAKE-SET(x) creates a new linked list whose only object is x; FIND-SET(x) follows the pointer from x back to its set object and returns the member in the object that head points to. In Figure 19.2(a), FIND-SET(g) returns f.

The simplest implementation of UNION takes significantly more time. UNION(x, y) appends y's list onto the end of x's list; the representative of x's list becomes the representative of the result, and the tail pointer of x's list shows where to append. UNION destroys the set object for y's list, and it must also update the pointer to the set object for each object originally on y's list, which takes time linear in the length of that list. In Figure 19.2, UNION(g, e) causes pointers to be updated in the objects for b, c, e and h.

A sequence of m operations on n objects can require Θ(n2) time: n MAKE-SET operations followed by the n − 1 UNION operations of Figure 19.3, so m = 2n − 1. The MAKE-SETs take Θ(n); the ith UNION updates i objects, so the updates form an arithmetic series, Θ(n2) in total. Each operation therefore takes Θ(n) on average: the amortized time of an operation is Θ(n).

19.2 · a simple heuristic: weighted union

Move the smaller crowd

Why did the chain of unions cost so much? Every union glued a long list onto a one-card list, and it is the glued-on list that has to rewrite its pointers. So flip it. Keep the length of each list on its set object, and always glue the shorter list onto the longer one. A card now pays for a rewrite only when it was on the shorter side.

Follow one card x. Each time its pointer is rewritten, x was in the shorter list, so the list it lands in is at least twice as long as the one it left. After one rewrite its set has at least 2 members, after two at least 4, after k at least 2k. No set has more than n members, so no card is rewritten more than ⌈lg n⌉ times, and all the unions together rewrite at most n lg n pointers.

The machine holds 16 cards. Each block above a card is one rewrite of its pointer; the dashed line is ⌈lg 16⌉ = 4. Run the chain with Simple union and the first card's tower of blocks climbs far above the line. Run it again with Weighted union and every tower stays one block high. Then try Balanced merges, where the lists are always equal and no rule can help.

Try it: press Play on the chain with Simple union and watch the red blocks pile up above the line; press Reset, switch to Weighted union and play it again. Then choose Balanced merges: both rules cost 32, which is exactly (n/2) lg n. Random deals a new sequence each time you press it; step through one and read the caption after each union.

What the book says

In the worst case the simple UNION takes Θ(n) time per call on average, because it might append a longer list onto a shorter one and must update the pointer to the set object for each member of the longer list. Suppose instead that each list also includes its length, which is maintained with constant overhead, and that UNION always appends the shorter list onto the longer, breaking ties arbitrarily. With this weighted-union heuristic a single UNION can still take Ω(n) time, if both sets have Ω(n) members.

Theorem 19.1: using the linked-list representation of disjoint sets and the weighted-union heuristic, a sequence of m MAKE-SET, UNION and FIND-SET operations, n of which are MAKE-SET operations, takes O(m + n lg n) time.

The proof bounds, for each object x, how often its pointer back to the set object is updated. Each time x's pointer is updated, x must have started in the smaller set. The first time, the resulting set has at least 2 members; the next time, at least 4; and for any k ≤ n, after ⌈lg k⌉ updates the resulting set has at least k members. Since the largest set has at most n members, each object's pointer is updated at most ⌈lg n⌉ times over all the UNION operations, so the pointer updates take O(n lg n) in total.

Updating the tail pointers and the list lengths takes Θ(1) time per UNION, so all the UNIONs take O(n lg n). Each MAKE-SET and FIND-SET takes O(1) time and there are O(m) of them, so the whole sequence takes O(m + n lg n).

19.3 · disjoint-set forests

Everyone points at their parent

Lists made FIND-SET instant and UNION slow. Trees turn that around. Give every element exactly one thing to remember: its parent. The element at the top of a tree remembers itself, and that element is the set's representative. A whole collection of such trees is a disjoint-set forest.

To find an element's set, follow parent pointers until you reach an element that is its own parent. The elements you pass through are the find path. To merge two sets, find both roots and make one root point at the other: a single pointer write, with no list copied and no element relabelled.

The catch: nothing says which root should hang under which. Merge in an unlucky order and the forest becomes a chain, and then one FIND-SET walks the whole chain. The book says it plainly: this version is no faster than linked lists, and the next two scenes fix it.

Try it: press Step to make eight one-element trees, then keep stepping through the seven UNIONs: each one is two FIND-SET walks and one pointer write. In Chain order every union hangs the old root under the next element, so the sets pile into one long path; press Find deepest and watch the walk. Then switch to Pairs order, which does the same number of unions in another order, and compare the tallest tree and the hops. In the Rust view the elements become indices, and the pointers are the cells of one Vec.

What the book says

A faster implementation of disjoint sets represents sets by rooted trees. Each node holds one member and each tree represents one set. In a disjoint-set forest, each member points only to its parent, and the root of each tree contains the representative and is its own parent.

The three operations have simple implementations. A MAKE-SET creates a tree with just one node. A FIND-SET follows parent pointers until it reaches the root, and the nodes visited on that path constitute the find path. “A UNION operation, shown in Figure 19.4(b), simply causes the root of one tree to point to the root of the other.”

Figure 19.4(a) draws the two sets of Figure 19.2 as trees: {b, c, e, h} with representative c, and {d, f, g} with representative f. Figure 19.4(b) shows the result of UNION(e, g).

“So far, disjoint-set forests have not improved on the linked-list implementation.” A sequence of n − 1 UNION operations can create a tree that is just a linear chain of n nodes. Two heuristics, union by rank and path compression, yield a running time that is almost linear in the total number m of operations.

19.3 · union by rank

Hang the short tree under the tall one

The chain appeared because UNION hung one root under the other without looking. The cure is the idea from the linked lists: put the smaller set under the bigger one, so the merged tree grows as little as possible. Common sense says to count nodes, but the book keeps something lighter that is easier to analyze.

Every node carries a rank, an upper bound on its height (the longest path down to a leaf). A fresh node has rank 0. When LINK joins two roots, the root of higher rank becomes the parent and no rank changes. Only when the ranks are equal is the parent picked arbitrarily, and then that parent's rank goes up by one.

So a tree gets taller only when two trees as tall as each other meet. That is why the right-hand forest stays shallow while the left one, which still links with a blind x.p = y, can turn into a chain. Here FIND-SET is still the plain walk; the next scene improves it.

Try it: pick an order (Chain and Pairs are the two from the last scene, Random deals new unions) and press Step. Each UNION is: walk to both roots, compare ranks (line 1 of LINK), hang one root under the other, and, if the ranks were equal, raise the winner's rank. Both forests receive the same unions. When the run is done, click any element to run FIND-SET on it in both forests and compare the hops.

What the book says

The first heuristic, union by rank, is similar to the weighted-union heuristic of the linked lists. “The common-sense approach is to make the root of the tree with fewer nodes point to the root of the tree with more nodes.” Rather than keep subtree sizes, the book adopts an approach that eases the analysis: “For each node, maintain a rank, which is an upper bound on the height of the node.”

“Union by rank makes the root with smaller rank point to the root with larger rank during a UNION operation.” MAKE-SET gives a singleton an initial rank of 0, and every FIND-SET leaves all ranks unchanged. If the two roots have unequal ranks, the root with higher rank becomes the parent of the other and no rank changes. “If the roots have equal ranks, arbitrarily choose one of the roots as the parent and increment its rank.”

The pseudocode: MAKE-SET sets x.p = x and x.rank = 0; UNION(x, y) is LINK(FIND-SET(x), FIND-SET(y)); LINK takes pointers to two roots, makes the one of greater rank the parent, and adds one to the survivor's rank when the ranks tie. This scene runs it with the plain walk-up version of FIND-SET; the book's own FIND-SET adds path compression, which the next scene turns on.

Used alone, union by rank gives a running time of O(m lg n) for a sequence of m operations, n of which are MAKE-SET, and the book notes that this bound is tight (Exercise 19.3-3).

19.3 · path compression

Tidy the path as you walk it

FIND-SET already walks from an element up to its root. Path compression asks it to leave something behind: every element it passed is re-pointed straight at the root. The first search pays full price. Afterwards everyone on that path, and everything hanging below them, is closer to the root for good.

The book writes it as a short recursion. Going up, each call asks its parent for the root (pass one). Coming back down, each call sets its own parent to the answer (pass two): x.p = FIND-SET(x.p). The recursion is the call stack: one frame per element on the find path, and the fixes happen as the frames pop.

Compression rewrites parent pointers only; ranks never change. So once finds start tidying paths, a rank is only an upper bound on the height, not the exact height. And elements that hang off the path (f, g and h below) are not re-pointed, yet they get shallower too, because their parents did.

Try it: press Step to start FIND-SET(a): five frames pile up on the way to the root e, then unwind, turning each node green as it swings to the root. Press Play to run the rest, then run it again: the same find now costs one hop. Between finds you can click any element to choose what to find next (try g). Switch to Plain walk to see the cost without compression: four hops every time. In the Rust view the strip underneath shows the call stack growing and unwinding.

What the book says

The second heuristic is also quite simple and highly effective: FIND-SET operations use it to make each node on the find path point directly to the root (Figure 19.5). “Path compression does not change any ranks.”

The FIND-SET procedure with path compression is implemented recursively. “The FIND-SET procedure is a two-pass method: as it recurses, it makes one pass up the find path to find the root, and as the recursion unwinds, it makes a second pass back down the find path to update each node to point directly to the root.” Line 2 sets x.p to the pointer the recursive call returns, and line 3 returns x.p. If x is the root, line 2 is skipped, x.p is x itself, and the recursion bottoms out.

Figure 19.5 shows a tree before FIND-SET(a), with triangles for subtrees, and the same set after: each node on the find path now points directly to the root. Exercise 19.3-2 asks for a nonrecursive version.

Used alone, path compression gives a worst-case running time of Θ(n + f · (1 + log2+f/n n)) for n MAKE-SET operations and f FIND-SET operations; the book does not prove it here.

19.3 · applying both heuristics

Two small ideas, one almost-linear machine

Each heuristic repairs a different weakness. Union by rank keeps trees from growing tall in the first place. Path compression makes a tall tree short as soon as somebody walks it. Alone, union by rank costs O(m lg n) for m operations, and compression alone is a little worse than linear. Together they cost O(m α(n)).

That α(n) is the book's name for a function that grows so slowly it is at most 4 for any n you could ever build (section 19.4 defines it). So the cost per operation is, for all practical purposes, a small constant, though mathematically still not quite constant.

The machine sends one sequence of operations through four forests at once (naive, rank only, compression only, both) and counts the parent pointers followed by FIND-SET. Each workload is the nightmare of a different variant, so you can see what each heuristic buys.

Try it: pick a workload and press Play. The bars share one scale; the dashed ticks mark m (one step per operation) and m lg n. Chain wrecks naive linking. Pairs builds perfectly balanced trees, where rank alone still pays about lg n per find and compression pays it once. Random graph is an ordinary CONNECTED-COMPONENTS run. In Rust, the table the program prints is the n = 64 run of this machine.

What the book says

“Separately, either union by rank or path compression improves the running time of the operations on disjoint-set forests, and combining the two heuristics yields an even greater improvement.”

Alone, union by rank yields a running time of O(m lg n) for a sequence of m operations, n of which are MAKE-SET, and this bound is tight (Exercises 19.4-4 and 19.3-3). For n MAKE-SET operations (hence at most n − 1 UNIONs) and f FIND-SETs, the worst-case running time using only path compression is Θ(n + f · (1 + log2+f/n n)); the book does not prove that bound here.

Combining union by rank and path compression gives a worst-case running time of O(m α(n)), where α(n) is a very slowly growing function defined in Section 19.4. In any conceivable application, α(n) ≤ 4, “and thus, its running time is as good as linear in m for all practical purposes.” “Mathematically speaking, however, it is superlinear.” Section 19.4 proves the O(m α(n)) upper bound.

The three workloads and the step counter are this page's own illustration, not the book's: they run the book's procedures and count the parent pointers FIND-SET follows. Each UNION is charged its two FIND-SETs, as in the book's pseudocode.

19.4 · analysis of union by rank with path compression

The inverse of an explosion

The chapter promises O(m α(n)) for m operations, and α(n) is a number you will never see above 4. To see why, build a ladder of ever stronger growth. Level 0 only adds one: A₀(j) = j + 1. Each level above asks the one below to repeat itself: Ak(j) means “apply Ak−1 to j, and do it j + 1 times”. Level 1 doubles (2j + 1), level 2 doubles j + 1 times, and level 3 leaves the page: A₃(1) = 2047, but A₃(2) already has about 121 million digits.

The inverse runs the ladder backwards. α(n) is the lowest level k whose Ak(1) reaches n. The rungs are 2, 3, 7, 2047 and then a number with more than 600 digits, so α(n) is 0 up to 2, 1 for 3, 2 for 4 to 7, 3 for 8 to 2047, and 4 from there up to that monster. No input a computer will ever hold climbs higher.

The proof pays for finds with a savings account, a potential, kept on every node. A node x under a parent of higher rank gets a level (the highest rung k with the parent's rank still at least Ak(x.rank)) and an iter (how many times that rung repeats before passing the parent's rank). Path compression hangs x under the root, whose rank is bigger, so for nearly every node on the path its level or iter rises and its potential falls by at least 1. On a find path of s nodes at most α(n) + 2 nodes can escape paying, so the rest of the walk is paid for.

Try it: in Ak(j), pick a cell with the two sliders (or click the table) and press Play: the chain is built by repeating the row above, and blue cells mark the entries it reads. Try A₂(2) = 23, then A₃(1) = 2047, then A₃(2) and watch it overflow. In α(n), drag n and press Play to climb the rungs. In Potential, press Play to compute level, iter and potential for each node of a find path, then see compression pay for the walk. The other two paths are in the picker.

What the book says

For integers j, k ≥ 0 the book defines Ak(j) = j + 1 if k = 0, and Ak−1 applied j + 1 times to j if k ≥ 1, using functional iteration. The parameter k is called “the level of the function A”. The function strictly increases in both j and k. Lemma 19.2 gives A₁(j) = 2j + 1 and Lemma 19.3 gives A₂(j) = 2j+1(j + 1) − 1, so A₀(1) = 2, A₁(1) = 3, A₂(1) = 7, A₃(1) = 2047, and A₄(1) is larger than 22056 = 16514, far above 1080, “the estimated number of atoms in the observable universe”.

The inverse is α(n) = min {k : Ak(1) ≥ n}: 0 for 0 ≤ n ≤ 2, 1 for n = 3, 2 for 4 ≤ n ≤ 7, 3 for 8 ≤ n ≤ 2047, and 4 for 2048 ≤ n ≤ A₄(1). Only for n above A₄(1) is α(n) > 4, so α(n) ≤ 4 for all practical purposes.

The proof first collects properties of ranks. Lemma 19.4: a node's rank is at most its parent's rank, strictly if it is not a root; a rank starts at 0, grows until the node stops being a root, and then never changes; and a parent's rank only goes up. Along any simple path toward a root, ranks strictly increase. Lemma 19.6: every rank is at most n − 1 (the exercises tighten this to ⌊lg n⌋). Lemma 19.7 lets the analysis treat each UNION as two FIND-SETs and a LINK.

The potential of node x is α(n)·x.rank if x is a root or has rank 0, and otherwise (α(n) − level(x))·x.rank − iter(x), where level(x) = max {k : x.p.rank ≥ Ak(x.rank)} and iter(x) = max {i : x.p.rank ≥ Alevel(x)(i)(x.rank)}. The book shows 0 ≤ level(x) < α(n) and 1 ≤ iter(x) ≤ x.rank when x.rank ≥ 1, and that a potential is never negative and never above α(n)·x.rank.

MAKE-SET costs O(1) amortized and LINK O(α(n)), because only the new parent's potential can rise, by at most α(n). For a FIND-SET whose find path has s nodes, no potential rises and at least max {0, s − (α(n) + 2)} nodes lose at least 1, so its amortized cost is O(α(n)). Theorem 19.14 follows: m operations, n of them MAKE-SET, take O(m α(n)) time. The procedures under the machine for A, the inverse, level, iter and the potential are sketches of those definitions, and the find paths and n = 2047 are the machine's own; FIND-SET is the book's.

problem 19-1 · offline minimum

Answering before the questions arrive

A ticket booth hands out numbered tickets 1 to n, and now and then the clerk calls the lowest number still waiting. You get the day's whole log in advance, and all you want to know is which number each call returns. You could replay the log with a heap. Or you can use the fact that you already know the future.

Cut the log at every call: I1, E, I2, E, …, E, Im+1, where E is an EXTRACT-MIN and each Ij is the (possibly empty) run of INSERTs before it. Put the keys of Ij into a set Kj. Now take the keys in increasing order. Key i is the smallest one left, so the first unanswered E after it was inserted returns it: that is the E at the end of the set that holds i. OFFLINE-MINIMUM finds that j, records extracted[j] = i (unless j = m + 1, which no E follows), and then merges Kj into the next set that still exists, because the keys of block j that were not returned wait for the next call.

Finding the set of i and merging two sets are FIND-SET and UNION, so the sets live in a disjoint-set forest with this chapter's two heuristics. One twist: the merged set must be called Kl, yet its root may be either old root, so every root carries a name (the same trick as the ancestor attribute in Problem 19-3). With n finds and at most m unions on m + 1 elements, the run is near-linear in n + m.

Try it: press Play on the book's log. The tape on top is the sequence; key i lights up inside its set, its answer drops into extracted, and the set melts into the next one. Then try Inserts first: one set carries all nine keys along while the calls answer 1, 2, 3, … Try Insert, extract, then Random (press it again for another log). In Rust the indices count from 0, so K7 becomes K6.

What the book says

In the offline minimum problem you maintain a dynamic set T of elements from {1, 2, …, n} under INSERT and EXTRACT-MIN. The input is a sequence S of n INSERT and m EXTRACT-MIN calls, where each key is inserted exactly once. The goal is to fill an array extracted[1 : m] so that extracted[i] is the key returned by the ith EXTRACT-MIN. The problem is “offline” because you may process the entire sequence before determining any returned key.

Part (a) asks for the array for the sequence 4, 8, E, 3, E, 9, 2, 6, E, E, E, 1, 7, E, 5, where each INSERT(i) is written as the value i and each EXTRACT-MIN as E. To develop an algorithm, break S into homogeneous subsequences I1, E, I2, E, I3, …, Im, E, Im+1, put the keys inserted by each Ij into a set Kj (empty if Ij is), and run OFFLINE-MINIMUM.

Part (b) asks you to argue that the array returned is correct. Part (c) asks you to describe an efficient implementation of OFFLINE-MINIMUM with a disjoint-set data structure and to give as tight a bound as you can on its worst-case running time. The pseudocode under the machine is the book's; the second listing is one possible answer to part (c), and the other logs are the machine's own.

problem 19-3 · Tarjan's offline lowest-common-ancestors algorithm

Who is the closest common boss?

In a company tree, the lowest common ancestor of two people is their closest shared boss: the deepest node that sits above both. Suppose you are handed the whole tree and a list of pairs, and you may answer in any order. That is the offline problem, and one walk through the tree answers every pair.

Walk the tree depth first, and keep disjoint sets as you go. When LCA(u) starts, u gets a set of its own whose ancestor label is u. When a child's visit returns, the child's whole set is merged into u's, and the label is set to u again: everyone finished below u now reports u as the node they hang from. When u is done it turns BLACK, and for each partner v that is already BLACK the answer is v's label, FIND-SET(v).ancestor. The partner's label is the deepest node still open on the walk that sits above v, and that is exactly the lowest common ancestor.

Each pair is answered once, at the moment its second member finishes. And when a call starts, the number of sets equals the number of calls already open above it, which is the depth of that node (the memory strip below shows those frames). The label lives on the set's root, which is not the same thing as the root's own name: UNION may make either old root the new root, so the label is set again after every union.

Try it: press Play and watch the yellow node walk. Black nodes are finished; the small “→ b” beside one is its set's ancestor label. Note the pair whose members are ancestor and descendant: it is answered when the ancestor finishes.

What the book says

The lowest common ancestor of two nodes u and v in a rooted tree T is the node w that is an ancestor of both and has the greatest depth in T. In the offline lowest-common-ancestors problem you are given a rooted tree T and an arbitrary set P of unordered pairs of nodes, and you wish to determine the lowest common ancestor of each pair in P.

The LCA procedure performs a tree walk of T with the initial call LCA(T.root), assuming every node is colored WHITE before the walk. Its lines 1–2 create a set for u with ancestor u; for each child v it recurses on v, unions u with v and sets the ancestor of the merged set to u again; then it colors u BLACK and, for each node v with {u, v} in P, prints FIND-SET(v).ancestor if v is BLACK.

The problem asks you to argue that line 10 executes exactly once for each pair; that at the time of the call LCA(u) the number of sets in the disjoint-set data structure equals the depth of u in T; to prove that LCA prints the lowest common ancestor of u and v for each pair; and to analyze the running time of LCA assuming the disjoint-set implementation of Section 19.3. The tree, the pairs and the node names in the machine are its own.

The chapter on one page

Chapter 19 in eight cards. Each one points at the scenes that act it out.

Groups that merge

A disjoint-set data structure keeps a collection of disjoint dynamic sets, each named by a representative, with three operations: MAKE-SET(x), FIND-SET(x) and UNION(x, y). Of m operations, n are MAKE-SETs, so m ≥ n, and at most n − 1 UNIONs can occur. CONNECTED-COMPONENTS turns every edge into a test and maybe a UNION; SAME-COMPONENT is two FIND-SETs. → 19.1 Disjoint-set operations

Lists: cheap find, costly union

With one linked list per set, a set object with head and tail, and a back-pointer in every object, MAKE-SET and FIND-SET are O(1). UNION appends one list to the other but must rewrite one back-pointer for each object of the appended list. n MAKE-SETs and n − 1 UNIONs, as in Figure 19.3, cost Θ(n2). → 19.2 Linked-list representation

Append the shorter list

Keep each list's length and always append the shorter onto the longer. An object's pointer is rewritten only when its set at least doubles in size, so no object is rewritten more than ⌈lg n⌉ times. Theorem 19.1: m operations take O(m + n lg n). → 19.2 Weighted union

Trees that point upward

In a disjoint-set forest each node points only at its parent, and the root is the representative. MAKE-SET builds a one-node tree, FIND-SET follows parent pointers up the find path, and UNION hangs one root under the other. On its own this is no faster than lists: n − 1 UNIONs can build a chain of n nodes. → 19.3 Disjoint-set forests

Union by rank

A node's rank is an upper bound on its height. LINK makes the root of smaller rank a child of the root of larger rank and leaves both ranks alone; when the ranks are equal it picks one root as parent and raises that rank by one. Alone, union by rank gives O(m lg n). → 19.3 Union by rank

Path compression

FIND-SET recurses up to the root and, as the recursion unwinds, points every node on the find path straight at the root. It changes no ranks, and the next FIND-SET on the same node is nearly free. Compression alone also helps, but its bound is weaker. → 19.3 Path compression

Almost linear

Both heuristics together run m operations in O(m α(n)). α is the inverse of the explosively growing Ak(j): A3(1) = 2047 and A4(1) is much greater than 1080, so α(n) ≤ 4 in any conceivable application. The proof uses the potential method, with each node's rank, level and iter. → 19.3 Applying both heuristics, 19.4 The analysis

Two jobs for the sets

Offline minimum answers every EXTRACT-MIN of a known sequence by merging each spent set of keys into the next one. Tarjan's offline lowest-common-ancestors algorithm walks a tree depth-first and keeps an ancestor label in each set, so each pair is answered the moment its second node is finished. → 19-1 Offline minimum, 19-3 Tarjan's LCA

Words to know

The book's words from this chapter, in plain language.

disjoint-set data structure
Keeps a collection of disjoint dynamic sets: no element is in two sets, and the sets change as unions happen.
representative
One member chosen to name its set. Asking twice without changing the set must give the same answer; some applications also fix a rule, such as the smallest member.
MAKE-SET(x)
Creates a new set whose only member, and so representative, is x. It must not already be in another set.
FIND-SET(x)
Returns the representative of the one set that contains x.
UNION(x, y)
Unites the sets containing x and y and destroys the two old sets. The new representative is a member of either.
n and m
n counts the MAKE-SET operations, m all operations. So m ≥ n, and since each UNION removes one set, at most n − 1 UNIONs occur.
connected component
A maximal group of vertices that can reach each other along edges. CONNECTED-COMPONENTS finds them with the disjoint-set operations, and SAME-COMPONENT answers whether two vertices share one.
set object, head, tail
In the list representation, the record for a set. Its head points to the first object in the list (the representative) and its tail to the last.
back-pointer
The pointer in each list object to its set object. FIND-SET follows it, and UNION must rewrite it for every appended object.
weighted-union heuristic
Keep each list's length and always append the shorter list onto the longer, breaking ties arbitrarily.
disjoint-set forest
Sets as rooted trees, one node per member, each node pointing to its parent. The root contains the representative and is its own parent.
find path
The nodes visited by FIND-SET on the way from a node up to the root of its tree.
LINK(x, y)
The subroutine of UNION that takes two roots and makes one the parent of the other.
rank
An integer kept in each node, an upper bound on its height. It starts at 0 and changes only in LINK, when two roots of equal rank meet.
union by rank
The root with smaller rank becomes a child of the root with larger rank. On its own it gives O(m lg n).
path compression
FIND-SET makes each node on the find path point directly to the root. A two-pass method: up the path, then back down as the recursion unwinds.
inverse Ackermann function α(n)
The lowest level k for which Ak(1) ≥ n. It grows so slowly that α(n) ≤ 4 for every practical n.
Ak(j)
A function that grows extremely fast: A0(j) = j + 1, and Ak(j) applies Ak−1 to j, j + 1 times. The parameter k is its level.
level and iter
For a nonroot node x with positive rank: level(x) is the greatest k with Ak(x.rank) ≤ x.p.rank, and iter(x) how many times Alevel can be applied before passing the parent's rank.
potential method
An amortized analysis in which a potential stored in the data structure pays for expensive operations. Here it sums a potential over all nodes of the forest.
offline problem
The whole sequence of operations is known in advance, so the answers may be worked out in any order.
offline minimum
Given a sequence of INSERTs and EXTRACT-MINs on keys 1 … n, find which key each EXTRACT-MIN returns, by merging the sets of keys that lie between the EXTRACT-MINs.
lowest common ancestor
Of two nodes in a rooted tree: the deepest node that is an ancestor of both.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

indices instead of pointers
The book's objects and parent pointers become numbers: element x is slot x, and x.p is parent[x], another usize. Nothing owns anything, so no Box or Rc is needed and a UNION is one write.
trait and D: DisjointSets
A trait lists the methods a type must offer. A function that takes D: DisjointSets works with any structure that has them; the compiler makes one copy per type, with no run-time lookup.
&mut self on a read
A method that only looks takes &self. FIND-SET with path compression rewrites parents while it looks, so it must take &mut self: a read that mutates.
Vec<Vec<usize>>, append and mem::take
One Vec per list. take moves a list out of its slot and leaves an empty Vec behind; append moves all its items onto another Vec. Nothing is cloned.
two fields, two borrows
Reading self.lists while writing self.set is fine, because they are different fields. A call such as sets.label[sets.find(x)] is not: find needs &mut while sets.label is still borrowed, so the root goes in a variable first.
std::mem::swap
Exchanges the values behind two &mut references without copying either, like the book's swap.
match on cmp
a.cmp(&b) returns an Ordering: Less, Equal or Greater. A match must cover all three, so LINK's three cases cannot lose a branch.
Option, checked_add and ?
Where the Ackermann function overflows u64, checked_* returns None instead of wrapping, and ? passes that None up at once. None then plays the role of "too big to count".
BTreeMap, BinaryHeap and Reverse
entry(k).or_default().push(v) groups values under sorted keys. BinaryHeap is a max-heap; wrapping keys in Reverse makes it a min-priority queue.
closures and iterator chains
.map(…).max(), .sum(), .step_by(k) and collect::<Option<Vec<_>>>() replace hand-written loops. A move closure owns the state it changes, such as a random-number seed.
lifetimes in a struct, &mut returned
struct Walk<'a> holds borrowed tables and promises they outlive it. A method can return &mut usize, a place to read or assign, such as the ancestor label of a set.
u8 for a rank
A rank never exceeds lg n, so one byte holds it for any set that fits in memory, and u8 arithmetic would panic in a debug build rather than wrap silently.
