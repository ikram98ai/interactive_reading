Minimum Spanning Trees

To join a set of points with the least cable, you want a set of edges that connects everything, has no loop, and weighs as little as possible. Chapter 21 grows that minimum spanning tree one edge at a time, always adding an edge that a cut proves safe, and turns the idea into Kruskal's and Prim's algorithms.

21 · the minimum-spanning-tree problem

The cheapest way to join everything

An electronics designer has nine pins to wire together so that current can pass between any two of them, through other pins if need be. Any two pins can be joined by a wire, and each possible wire has a cost: the amount of wire it takes. Model the pins as the vertices of a connected, undirected graph, the possible wires as its edges, and each edge's cost as its weight w(u, v). The designer wants everything joined with as little wire as possible.

A set of wires with a loop in it wastes wire: cut any wire on the loop and everything is still joined. So the best set has no loop. A loop-free set that joins every pin is a tree, and because it reaches every vertex it is a spanning tree: it “spans” the graph. Nine pins always give exactly eight wires, so the choice is never how many wires to use, only which eight. The spanning tree whose weights add up to the least is a minimum spanning tree.

The best tree need not be the only one. Here the edges (b, c) and (a, h) both weigh 8, so a minimum tree that uses one of them can swap it for the other and stay minimum. Trying every set of eight edges would find a best tree, but the rest of the chapter does it far more cleverly: it grows a tree one edge at a time, always adding an edge that is sure to belong to some minimum tree.

Try it: click an edge to put it into your tree T (blue), and click it again to take it out. Try to close a loop: the machine refuses and shows the loop. Watch pieces fall from 9 towards 1 and weight climb, then compare with the minimum, 37. Press Play to add edges in random order (press it again for another order), or Book's tree and then Swap to see two different trees that both weigh 37.

What the book says

The chapter opens with a wiring problem. To interconnect a set of n pins, a designer can use an arrangement of n − 1 wires, each connecting two pins, and of all such arrangements the one that uses the least wire is usually the most desirable. The book models this with a connected, undirected graph G = (V, E), where V is the set of pins, E the set of possible interconnections between pairs of pins, and a weight w(u, v) the cost of connecting u and v.

The goal is an acyclic subset T ⊆ E that connects all of the vertices and whose total weight w(T) = Σ w(u, v), summed over the edges (u, v) of T, is minimized. Since T is acyclic and connects all of the vertices, it must form a tree, which the book calls a spanning tree since it “spans” the graph G. Determining the tree T is the minimum-spanning-tree problem. A footnote explains that “minimum spanning tree” is a shortened form of “minimum-weight spanning tree”, and that there is no point in minimizing the number of edges in T, since all spanning trees have exactly |V| − 1 edges (Theorem B.2).

Figure 21.1 shows a connected graph with its weights and a minimum spanning tree in blue, of total weight 37. That tree is not unique: removing the edge (b, c) and replacing it with the edge (a, h) yields another spanning tree with weight 37. The machine starts from this graph.

The chapter studies two ways to solve the problem. Kruskal's algorithm and Prim's algorithm both run in O(E lg V) time; Prim's reaches that bound with a binary heap as its priority queue, and with Fibonacci heaps it runs in O(E + V lg V), which is better than O(E lg V) whenever |E| grows asymptotically faster than |V|. Both are greedy algorithms in the sense of Chapter 15: a greedy strategy does not generally find globally optimal solutions, but for this problem the book can prove that certain greedy strategies do yield a spanning tree with minimum weight. Because the chapter focuses on trees in terms of their edges, the vertices of a tree T are implicitly those that some edge of T is incident on.

21.1 · the generic minimum-spanning-tree method

Grow the tree one safe edge at a time

Suppose a wise friend could tell you, for any wires you have already chosen, a next wire that is certain to belong to some cheapest tree. Then the cheapest tree would be easy to build: keep a set A of chosen edges, ask for such a wire, add it, and repeat. The book's GENERIC-MST is exactly this loop. What it keeps true all the way through is its loop invariant: before every iteration, A is a subset of some minimum spanning tree.

An edge that can join A without spoiling that promise is safe for A. At the start A is empty, so the promise holds trivially; every safe edge keeps it true; and everything in A belongs to a minimum spanning tree, so when A finally spans the graph it is one. The loop runs exactly |V| − 1 times, one edge a round.

The tricky part is line 3, finding a safe edge. This machine cheats on purpose: it has already tried every set of eight edges of the graph, so it knows every minimum tree and can say exactly which edges are safe. Notice what “safe” depends on: not only the edge, but the edges already in A. At the start (b, c) and (a, h) are both safe; once A holds one of them, the other is not.

Try it: press Step and watch line 3: every safe edge lights up, one is picked and added. Then click edges yourself. Click (b, h), which is in no cheapest tree, and it is refused. Click (a, h), then try (b, c). Press Show safe edges to see the safe set shrink. Finally switch to Any edge and force an unsafe edge in: both cards turn red, because no minimum tree holds A any more, and the finished tree is heavier than 37.

What the book says

The input is a connected, undirected graph G = (V, E) with a weight function w : E → ℝ, and the goal is a minimum spanning tree. Both algorithms in the chapter use a greedy approach, captured by the procedure GENERIC-MST, which grows the tree one edge at a time. The generic method manages a set A of edges, maintaining a loop invariant: prior to each iteration, A is a subset of some minimum spanning tree.

Each step determines an edge (u, v) that the procedure can add to A without violating the invariant, in the sense that A ∪ {(u, v)} is also a subset of a minimum spanning tree. Such an edge is called a safe edge for A, since it can be added safely. Initialization: after line 1, A trivially satisfies the invariant. Maintenance: the loop in lines 2–4 maintains it by adding only safe edges. Termination: all edges added to A belong to a minimum spanning tree, so the set returned in line 5 must be a minimum spanning tree.

A safe edge always exists when line 3 runs. By the invariant there is a spanning tree T with A ⊆ T; inside the loop A is a proper subset of T, so there is an edge (u, v) ∈ T, not in A, that is safe for A. Finding it is the hard part, and Theorem 21.1, in the next scene, gives the rule that recognizes safe edges.

As the method proceeds, A is always acyclic, since it is a subset of a minimum spanning tree and a tree may not contain a cycle. The graph GA = (V, A) is a forest whose components are trees, some with a single vertex; when the method begins, A is empty and the forest contains |V| trees. Any safe edge connects distinct components of GA, since A ∪ {(u, v)} must be acyclic. The loop runs |V| − 1 times because each iteration finds one of the |V| − 1 edges of a minimum spanning tree and reduces the number of trees by 1.

21.1 · cuts, light edges and safe edges

Split the graph in two: the lightest crossing edge is safe

Here is a way to recognize a safe edge without trying every tree. Choose any group of vertices S and call all the others V − S. That split is a cut. An edge crosses the cut if one end is in S and the other is not, like a bridge between two islands. Of the crossing edges the cheapest is a light edge; if several tie, each is light.

One condition keeps the cut honest: it must respect A, which means no edge already in A crosses it, so every piece of A stays on one island. Then Theorem 21.1 says a light edge crossing the cut is safe for A. Why? Take a minimum tree T that holds A but lacks the light edge (u, v). Adding (u, v) to T closes a cycle, and since u and v are on opposite sides, the cycle crosses the cut again on some edge (x, y), which is not in A because the cut respects A. Swap them, a cut-and-paste: the new tree weighs w(T) − w(x, y) + w(u, v), which is no more, because (u, v) is light.

A special case matters most, Corollary 21.2: take any tree C in the forest that A forms and cut it off from the rest. The cheapest edge leaving C is safe. Both algorithms of the next section are this idea: Prim grows one tree and always takes its cheapest outgoing edge; Kruskal takes the cheapest edge that links any two trees.

Try it: in Pick a cut click vertices to move them in or out of S (yellow). Dashed red edges cross the cut, the green one is light. Press Step to watch LIGHT-EDGE scan the edges. Switch to A's component and click a vertex to cut off its whole tree. Then press A = only (b, c), pick the cut {a, b}, and see a cut that crosses A: its light edge (a, h) is not safe. In Cut and paste press Step to watch the swap from the proof.

What the book says

A cut (S, V − S) of an undirected graph G = (V, E) is a partition of V. An edge (u, v) ∈ E crosses the cut if one of its endpoints belongs to S and the other to V − S. A cut respects a set A of edges if no edge in A crosses the cut. An edge is a light edge crossing a cut if its weight is the minimum of any edge crossing the cut; there can be more than one light edge in the case of ties. More generally, an edge is a light edge satisfying a given property if its weight is the minimum of any edge satisfying the property. Figure 21.2 shows a cut of the graph of Figure 21.1 in which (d, c) is the unique light edge and the cut respects the blue subset A.

Theorem 21.1. Let G = (V, E) be a connected, undirected graph with a real-valued weight function w on E. Let A be a subset of E included in some minimum spanning tree for G, let (S, V − S) be any cut of G that respects A, and let (u, v) be a light edge crossing (S, V − S). Then the edge (u, v) is safe for A.

The proof uses a cut-and-paste technique. Let T be a minimum spanning tree that includes A, and assume T does not contain (u, v), since otherwise we are done. The edge (u, v) forms a cycle with the edges on the simple path p from u to v in T (Figure 21.3). At least one edge of T on p crosses the cut; call it (x, y). It is not in A, because the cut respects A. Removing it breaks T into two components, and adding (u, v) reconnects them into T′ = (T − {(x, y)}) ∪ {(u, v)}. Since (u, v) is light and (x, y) crosses the same cut, w(u, v) ≤ w(x, y), so w(T′) = w(T) − w(x, y) + w(u, v) ≤ w(T). As T is minimum, T′ is too, and A ∪ {(u, v)} ⊆ T′, so (u, v) is safe.

Corollary 21.2. Let A be a subset of E included in some minimum spanning tree for G, and let C = (VC, EC) be a connected component (tree) in the forest GA = (V, A). If (u, v) is a light edge connecting C to some other component in GA, then (u, v) is safe for A. The proof is one line: the cut (VC, V − VC) respects A, and (u, v) is a light edge for this cut. The two algorithms of Section 21.2 use this corollary.

21.2 · Kruskal's algorithm

Cheapest road first, unless it loops

A county wants to link nine villages with as little new road as possible. Kruskal's rule is almost too simple: write down every possible road, cheapest first, and walk down the list. Build a road if it joins two villages that are not yet connected. Skip it if they already are, because a second route between them would only add cost.

Each village starts as a tiny forest of its own. The question “already connected?” is what disjoint sets (chapter 19) answer: FIND-SET(u) names the representative of u's tree, and two vertices share a tree exactly when their representatives match. If they differ, the road goes into the edge set A and UNION merges the two trees. That is MST-KRUSKAL. It is correct because the road it picks is the cheapest one leaving the tree it joins, which is the light-edge rule of section 21.1.

The sort costs O(E lg E) and the disjoint-set work is cheaper, so the total is O(E lg V). Ties matter for which tree you get, not for its weight: Figure 21.1 has two edges of weight 8, and either order yields weight 37.

Try it: press Step and watch lines 6–7. The pointer sits on one edge of the sorted row, and the two FIND-SETs are compared. Accepted edges turn blue and their vertices share a colour; a ring marks each set's representative. Edge g–i (weight 6) is refused: g and i already sit in one set. Then switch to a–h first (a different tree, still 37), and to Not sorted, which runs the same loop without line 5: the tree gets heavier.

What the book says

Kruskal's algorithm finds a safe edge to add to the growing forest by finding, of all the edges that connect any two trees in the forest, an edge (u, v) with the lowest weight. Since (u, v) must be a light edge connecting one tree to some other tree, Corollary 21.2 implies that it is a safe edge. It qualifies as a greedy algorithm because at each step it adds to the forest an edge with the lowest possible weight.

Like the connected-components algorithm of Section 19.1, MST-KRUSKAL uses a disjoint-set data structure to maintain several disjoint sets of elements. Each set contains the vertices in one tree of the current forest. FIND-SET(u) returns a representative element from the set that contains u, so to decide whether u and v belong to the same tree, test whether FIND-SET(u) equals FIND-SET(v). To combine trees, the procedure calls UNION.

Lines 1–3 initialize A to the empty set and create |V| trees, one containing each vertex. The for loop in lines 6–9 examines edges in order of weight, from lowest to highest. If the endpoints of an edge belong to the same tree, the edge cannot be added to the forest without creating a cycle, and it is ignored. Otherwise the two vertices belong to different trees: line 8 adds the edge to A, and line 9 merges the vertices in the two trees.

The running time depends on the disjoint-set implementation; the book assumes the disjoint-set forest of Section 19.3 with union by rank and path compression. Creating the list of edges in line 4 takes O(V + E) time, which is O(E) because G is connected, and the sort in line 5 takes O(E lg E). The loop performs O(E) FIND-SET and UNION operations, which together with the |V| MAKE-SET operations take O(E α(V)) time. Since |E| < |V|², lg|E| = O(lg V), so the total running time is O(E lg V).

Exercise 21.2-1 notes that Kruskal's algorithm can return different spanning trees for the same input graph, depending on how it breaks ties when the edges are sorted, and asks the reader to show that every minimum spanning tree can be produced by some sort order. The machine's edge list, the Not sorted run and its total of 43 are my own illustration, not the book's figure.

21.2 · Prim's algorithm

One tree, always growing

Kruskal grows many little forests at once. Prim works like a telephone company laying cable outward from head office: start at one vertex, the root, and at every step connect the nearest outsider, the vertex that can be hooked to the network by the cheapest single edge. The network is always one connected piece.

To find that outsider quickly, every vertex still outside carries a key, the weight of the lightest edge joining it to the tree so far (∞ if none), and a parent π, the tree vertex at the other end of that edge. The outsiders wait in a min-priority queue Q. EXTRACT-MIN pulls out the smallest key and that vertex joins the tree; then each of its neighbours still in Q is checked, and if the new edge is lighter than the neighbour's key, key and parent are updated and DECREASE-KEY tells the queue. The tree and Q always form a cut, and the vertex pulled out hangs on a light edge across it, so the choice is safe.

Rust's standard BinaryHeap has no DECREASE-KEY. The Rust twin pushes a second entry with the better key and ignores the stale one when it finally surfaces. The memory strip under the machine shows those stale entries piling up.

Try it: press Step. One step pulls the cheapest vertex out of Q (a tag flies to its place in the tree); the next scans that vertex's neighbours and decreases keys, and a cell slides left when its key drops. Follow h: ∞, then 8, then 7, then 1. When two keys tie (c and h are both 8) the machine takes the earlier letter. Pick another root in the row of letters before you start (try e): the total stays 37, but a different tree grows.

What the book says

Like Kruskal's algorithm, Prim's algorithm is a special case of the generic method of Section 21.1, and it operates much like Dijkstra's algorithm for shortest paths (Section 22.3). The edges in the set A always form a single tree. As Figure 21.5 shows, the tree starts from an arbitrary root vertex r and grows until it spans all the vertices in V. Each step adds to the tree A a light edge that connects A to an isolated vertex, one on which no edge of A is incident. By Corollary 21.2 this rule adds only edges that are safe for A, so when the algorithm terminates the edges in A form a minimum spanning tree.

The inputs are the connected graph G and the root r. To select a new edge efficiently, the algorithm maintains a min-priority queue Q of all vertices that are not in the tree, based on a key attribute. For each vertex v, v.key is the minimum weight of any edge connecting v to a vertex in the tree, and by convention v.key = ∞ if there is no such edge. The attribute v.π names the parent of v in the tree. The algorithm implicitly maintains A as {(v, v.π) : v ∈ V − {r} − Q}.

Lines 1–7 set the key of each vertex to ∞ (except the root, whose key is 0 so that it is the first vertex processed), set every parent to NIL, and insert each vertex into Q. Line 9 identifies a vertex u in Q incident on a light edge that crosses the cut (V − Q, Q); removing u from Q adds it to the tree. The for loop of lines 10–14 updates the key and π of every vertex v adjacent to u but not in the tree. Whenever line 13 updates v.key, line 14 calls DECREASE-KEY to inform the queue.

The running time depends on how Q is implemented. With a binary min-heap (Chapter 6), including a way to map between vertices and their heap elements, the while loop executes |V| times, each EXTRACT-MIN takes O(lg V) time, and the for loop executes O(E) times altogether, since the sum of the lengths of all adjacency lists is 2|E|. The test for membership in Q in line 11 takes constant time if you keep a bit for each vertex. Each DECREASE-KEY takes O(lg V), so the total is O(V lg V + E lg V) = O(E lg V), asymptotically the same as Kruskal's. With a Fibonacci heap it improves to O(E + V lg V).

The Rust twin's lazy deletion (a second heap entry instead of DECREASE-KEY) is my own adaptation, not the book's; so is the tie rule that takes the earlier letter. Figure 21.5 notes that in its second step the algorithm may add either edge (b, c) or edge (a, h), since both are light edges crossing the cut.

21.2 · running times: Kruskal vs Prim

Two ways to pay for the same tree

Both algorithms return a tree of the same total weight, so the contest is about cost. Kruskal pays for a sort up front, then puts one question to the disjoint-set forest for every edge. Prim pays for a priority queue: an EXTRACT-MIN for every vertex and, whenever a neighbour's key improves, a DECREASE-KEY. With a binary heap each of those costs about lg V, and both algorithms come to O(E lg V).

A Fibonacci heap changes Prim's bill: DECREASE-KEY costs only O(1) amortized, so Prim drops to O(E + V lg V). That beats E lg V once the number of edges grows faster than the number of vertices, so a dense graph is where it shows. The machine counts the work of both algorithms on a graph you choose, and computes the two bounds next to the counts.

The counts are honest but they are mine: a merge sort for line 5, and a binary heap with a position table for Q. Notice how far the measured Prim bars stay below E lg V. The bound charges every edge a DECREASE-KEY; on random weights only some edges improve a key.

Try it: press Play and watch each count being added up while its line lights in the code. Then choose Dense graph: Kruskal's sort comparisons grow with E, Prim's heap steps hardly move, the adjacency scans grow with E, and the Fibonacci bound is several times shorter than E lg V. Drag the two sliders to make your own graph, and press New graph for fresh random weights.

What the book says

The chapter opens with the summary: both Kruskal's and Prim's algorithm run in O(E lg V) time. Prim's algorithm achieves this bound with a binary heap as its priority queue. With Fibonacci heaps it runs in O(E + V lg V) time, which is better than O(E lg V) whenever |E| grows asymptotically faster than |V|.

For Kruskal's algorithm, the book assumes the disjoint-set forest of Section 19.3 with union by rank and path compression. Creating the list of edges takes O(E) time and sorting it O(E lg E). The loop in lines 6–9 performs O(E) FIND-SET and UNION operations, which together with the |V| MAKE-SET operations take O(E α(V)) time. Since α(|V|) = O(lg V) = O(lg E), the total is O(E lg E), and since |E| < |V|² it restates as O(E lg V).

For Prim's algorithm with a binary min-heap, the BUILD-MIN-HEAP procedure can perform lines 5–7 in O(V) time, and it is not even needed: put the key of r at the root and, because all other keys are ∞, they can go anywhere else. The while loop executes |V| times and each EXTRACT-MIN takes O(lg V), giving O(V lg V) in all. The for loop in lines 10–14 executes O(E) times altogether, each DECREASE-KEY takes O(lg V), and the total is O(V lg V + E lg V) = O(E lg V), asymptotically the same as Kruskal's.

In a Fibonacci heap holding |V| elements, EXTRACT-MIN takes O(lg V) amortized time while INSERT and DECREASE-KEY take O(1) amortized time each, so Prim's algorithm improves to O(E + V lg V). Exercise 21.2-3 asks whether this is asymptotically faster than the binary heap for a sparse graph, |E| = Θ(V), and for a dense graph, |E| = Θ(V²), and how |E| and |V| must be related for it to win.

problem 21-1 · second-best minimum spanning tree

Runner-up: one swap away

When every edge weight is different, the cheapest way to wire a graph is one single tree. The runner-up is the cheapest tree that is not that one, and you do not have to search all trees for it: it differs from the best tree by exactly one swap. Pick a link that is outside the best tree and add it. The tree now has exactly one loop, made of the new link and the tree path between its ends. To get a tree back you must drop a link from that loop, and the cheapest choice is the heaviest link on the path.

So each outside edge (x, y) has a price for the swap: w(x, y) minus the heaviest weight on the tree path from x to y. The second-best minimum spanning tree is the swap with the smallest price. The lightest outside edge need not win, because it may only be able to knock out a light edge.

Pricing each edge by walking its path would be slow. Instead fill a table first: max[u, v] is the heaviest edge on the tree path between u and v. One walk through the tree from each vertex fills one row, carrying the heaviest edge seen so far: V walks of V steps, O(V2) in all. After that every outside edge costs one lookup. The best tree is unique, but the runner-up may not be: two swaps can cost the same.

Try it: press Play. Six walks fill the table, one row per start vertex (the lilac one), and each vertex shows the heaviest weight on its path from the start. Then every outside edge (yellow) lights the tree path it would close into a loop (green), the heaviest edge on that path is marked for removal (red dashes), and a chip prices the swap. Next source fills one row at a time. Switch to A tie to see two swaps with the same price, or Random weights for a new graph. In the Rust view the memory strip shows the table as a Vec of six row Vecs and the call stack as the path from the start vertex.

What the book says

The problem takes an undirected, connected graph G = (V, E) with weight function w, where |E| ≥ |V| and all edge weights are distinct. If 𝒯 is the set of all spanning trees of G and T is a minimum spanning tree, a second-best minimum spanning tree is a spanning tree T′ whose weight is the minimum of the weights of the trees in 𝒯 − {T}.

Part (a) asks you to show that the minimum spanning tree is unique, but that the second-best one need not be. Part (b) asks you to prove that G contains an edge (u, v) in T and an edge (x, y) not in T such that (T − {(u, v)}) ∪ {(x, y)} is a second-best minimum spanning tree: one swap is enough.

Part (c): for any spanning tree T and any two vertices u and v, let max[u, v] denote an edge of maximum weight on the unique simple path between u and v in T. Describe an O(V2)-time algorithm that, given T, computes max[u, v] for all pairs. Part (d) asks for an efficient algorithm for the second-best minimum spanning tree.

The book gives no pseudocode for any part. The two procedures in the code panel are this page's sketch of (c) and (d); the graphs and weights are the machine's own, and the proofs of (a) and (b) are left to the reader, as in the book.

problem 21-4 · bottleneck spanning tree

Only the longest bridge counts

Suppose you must link eight islands with bridges, and what decides the cost is the single longest span, the one your crane has to reach. A spanning tree whose heaviest edge is as light as possible is a bottleneck spanning tree, and that heaviest weight is its value. The total weight does not matter.

Ask a yes-or-no question instead: can every island be reached using only edges of weight at most b? Cross out the heavier edges and run a breadth-first search from any vertex. If it reaches everything, the answer is yes, and the test costs O(V + E). Raising b can only turn a no into a yes, so the bottleneck value is the smallest b that says yes, and it is always one of the edge weights. That means you can binary-search the sorted list of weights.

A minimum spanning tree is always a bottleneck tree: press Show MST and its heaviest edge lands exactly on the value. The book wants linear time, and hints at contracting sets of edges. The idea: test the median weight. If the graph is connected, throw away every heavier edge; if not, merge each piece of the lighter edges into one vertex. Either way half of the edges leave play, so the rounds cost E + E/2 + E/4 + … = O(E). The edges in play counter shows that halving.

Try it: in Test a threshold set the slider to 7 and press Play: the search sees one cluster of four vertices and stops. Raise it to 9 and play again. Then press Show MST. Switch to Halve the weights and press Play: four tests find the value. Shuffle weights deals a new graph (the Rust program keeps the starting weights). In the Rust view the memory strip shows the queue as a ring buffer.

What the book says

A bottleneck spanning tree T of an undirected graph G is a spanning tree of G “whose largest edge weight is minimum over all spanning trees of G.” The value of the bottleneck spanning tree is the weight of the maximum-weight edge in T.

Part (a) asks you to argue that a minimum spanning tree is a bottleneck spanning tree, which shows that finding a bottleneck spanning tree is “no harder than finding a minimum spanning tree.” The remaining parts show how to find one in linear time.

Part (b) asks for a linear-time algorithm that, given a graph G and an integer b, determines whether the value of the bottleneck spanning tree is at most b. Part (c) uses that algorithm as a subroutine in a linear-time algorithm for the problem; the hint is to use a subroutine that contracts sets of edges, as in the MST-REDUCE procedure of Problem 21-2.

The book gives no pseudocode for this problem. The two procedures in the code panel are this page's sketch of (b) and of a binary-search way to use it; the halving with contraction is described in the text above but not coded. The graph and its weights are the machine's own.

The chapter on one page

Chapter 21 in eight cards. Each one points at the scenes that act it out.

The cheapest way to join everything

Given a connected, undirected graph G = (V, E) with a weight w(u, v) on each edge, find an acyclic set T ⊆ E that connects all of the vertices and minimizes w(T), the sum of its weights. Such a T is a tree, a spanning tree, and every spanning tree has exactly |V| − 1 edges. Figure 21.1's best tree weighs 37 and is not unique: replacing (b, c) by (a, h) gives another. → 21 The minimum-spanning-tree problem

Grow it one safe edge at a time

GENERIC-MST keeps an edge set A and the loop invariant that prior to each iteration A is a subset of some minimum spanning tree. An edge is safe for A if adding it keeps that true. Initialization, maintenance and termination follow at once; the loop runs |V| − 1 times, and the forest (V, A) loses one tree per iteration. The tricky part is line 3, finding a safe edge. → 21.1 Generic method

Cuts, light edges, and a safe rule

A cut (S, V − S) partitions the vertices; an edge crosses it if its ends are on different sides, and the cut respects A if no edge of A crosses. A light edge is a crossing edge of least weight. Theorem 21.1: a light edge crossing a cut that respects A is safe, by cut and paste: swap it for an edge of the cycle that crosses the cut. Corollary 21.2: for any tree of the forest (V, A), a light edge leaving it is safe. → 21.1 Cuts, light edges and safe edges

Kruskal: the cheapest edge that joins two trees

MST-KRUSKAL makes every vertex a one-vertex set, sorts the edges by weight, and takes each in turn: if FIND-SET(u) ≠ FIND-SET(v) the edge joins two trees, so it goes into A and UNION merges them; otherwise it would close a cycle and is skipped. Sorting costs O(E lg E), the disjoint-set work O(E α(V)), and the total is O(E lg V). → 21.2 Kruskal's algorithm

Prim: one tree, always growing

MST-PRIM(G, w, r) grows a single tree from a root r. Every vertex outside carries v.key, the lightest edge joining it to the tree (∞ if none), and a parent v.π; they wait in a min-priority queue Q. EXTRACT-MIN adds the nearest vertex, then DECREASE-KEY records better keys for its neighbours. At the end A = {(v, v.π) : v ∈ V − {r}}. → 21.2 Prim's algorithm

Kruskal and Prim in time

Kruskal runs in O(E lg V). Prim with a binary min-heap does |V| EXTRACT-MINs and O(E) DECREASE-KEYs at O(lg V) each, also O(E lg V); with a Fibonacci heap, whose INSERT and DECREASE-KEY are O(1) amortized, it improves to O(E + V lg V), better whenever |E| grows asymptotically faster than |V|. Different trees are possible, but both return the same minimum weight. → 21.2 Kruskal vs Prim

Runner-up: one swap away

Problem 21-1: with distinct weights the minimum spanning tree is unique, but the second-best need not be. Some edge of T and some edge outside it can be swapped to give a second-best tree. A table max[u, v], the heaviest edge on the tree path from u to v, fills in O(V2) time, and then every outside edge is priced by one lookup. → 21-1 Second-best minimum spanning tree

Only the heaviest edge counts

Problem 21-4: a bottleneck spanning tree is a spanning tree whose largest edge weight is least over all spanning trees. Every minimum spanning tree is one, so finding it is no harder than finding a minimum spanning tree. Asking whether the value is at most b takes one search of the graph without the heavier edges, and the book then asks for a linear-time algorithm, with contraction as a hint. → 21-4 Bottleneck spanning tree

Words to know

The book's words from this chapter, in plain language.

weight w(u, v), w(T)
The cost of one edge, such as the amount of wire it needs. The weight of an edge set T is the sum over its edges.
tree, forest
A tree is a connected graph with no cycle. A forest has no cycle either, but may be in several pieces; each connected piece is a tree.
spanning tree
A tree that “spans” the graph: it connects all of the vertices, and it has exactly |V| − 1 edges.
minimum spanning tree
A spanning tree of least total weight. It is short for minimum-weight spanning tree, and it need not be unique when weights tie.
GA = (V, A)
The graph with all the vertices and only the chosen edges. It is a forest whose trees are the pieces built so far; at the start it has |V| one-vertex trees.
greedy algorithm
One that makes the choice that looks best at the moment. It does not always find the best answer, but for minimum spanning trees certain greedy rules provably do.
GENERIC-MST
The method that grows A one edge at a time by finding an edge that is safe for A. Kruskal and Prim are two ways to do line 3.
loop invariant
A statement true before every iteration. For GENERIC-MST: A is a subset of some minimum spanning tree.
safe edge
An edge (u, v) such that A ∪ {(u, v)} is also a subset of some minimum spanning tree. It depends on A, not only on the edge.
cut (S, V − S)
A partition of the vertices into two sets.
crosses
An edge crosses a cut when one endpoint is in S and the other is in V − S.
respects
A cut respects A when no edge of A crosses it.
light edge
A crossing edge whose weight is the least of all crossing edges. There can be several if weights tie.
cut and paste
The proof technique of Theorem 21.1: build a new tree T′ from T by removing one edge and adding another, then show T′ is no heavier.
Theorem 21.1, Corollary 21.2
A light edge of a cut that respects A is safe; and a light edge between a tree of GA and another tree is safe.
MST-KRUSKAL
Sorts the edges by weight and adds each edge that joins two different trees, using FIND-SET and UNION on the vertices.
disjoint-set data structure
Chapter 19's structure for sets that merge. Kruskal uses one set per tree: FIND-SET names a tree's representative and UNION merges two trees.
MST-PRIM
Grows one tree from a root r by repeatedly adding the vertex joined to the tree by the cheapest edge.
v.key and v.π
In Prim's algorithm, the weight of the lightest edge connecting v to the tree (∞ if there is none) and the vertex at the tree end of that edge, v's parent.
min-priority queue
A set from which EXTRACT-MIN removes the element with the smallest key and DECREASE-KEY lowers a key. Prim keeps the vertices not yet in the tree in one.
Fibonacci heap
A heap with O(lg V) amortized EXTRACT-MIN and O(1) amortized INSERT and DECREASE-KEY, which brings Prim to O(E + V lg V).
second-best minimum spanning tree
A spanning tree of least weight among all spanning trees except the minimum one. Problem 21-1 shows it differs from the minimum tree by one edge swap.
max[u, v]
An edge of maximum weight on the unique simple path between u and v in a tree. All the values can be found in O(V2) time.
bottleneck spanning tree
A spanning tree whose largest edge weight is least over all spanning trees; that weight is its value. Every minimum spanning tree is one.
Borůvka's algorithm
The oldest minimum-spanning-tree algorithm (1926). In the chapter notes it is described as O(lg V) iterations of the contraction procedure MST-REDUCE from Problem 21-2.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

an edge as a tuple, type
type Edge = (usize, usize, u32) names a tuple (u, v, weight). A loop can split it where it stands: for &(u, v, w) in &edges copies each tuple out of the borrowed list and gives its three parts names.
enum and match for outcomes
When a step can end three ways, such as refused, added or spanning, an enum says so, and a match must cover every case. An arm can carry an if guard, and continue is allowed as an arm.
&mut self and iter_mut
A method that changes its struct takes &mut self. iter_mut() lends a &mut to each slot of a Vec in turn, so *p = new rewrites it in place.
a u32 as a set of edges
Bit i of an integer says whether edge i is in the set: set >> i & 1 reads it, a | 1 << e adds one, count_ones() is the size. Fourteen edges fit in one machine word, so trying every subset is a loop over numbers.
Option and its helpers
Option<Edge> is the book's NIL made safe: None when there is no light edge. map_or(true, …) treats None as true, .expect("…") unwraps or panics with a message, and if let Some(x) = … runs only for a value. A Vec<Option<usize>> holds the parents v.π.
closures over references: |&&m|
iter() lends &T and filter lends a reference to that, so a closure over u32s binds |&&m| to get the number. sort_by_key(|e| e.2) sorts edges by their weight field, and .all(|&s| s) asks whether every flag is true.
union–find with usize indices
Chapter 19's forest again: struct Dsu holds parents as Vec<usize> indices, so a UNION is one write. std::mem::swap(&mut a, &mut b) exchanges two values without copying; take(a) moves a Vec out and leaves an empty one behind.
BinaryHeap, Reverse and u32::MAX
std's heap is a max-heap with no DECREASE-KEY. Reverse flips it into a min-heap, and Prim pushes a second entry with the better key and skips the stale one when it pops. u32::MAX stands in for ∞. A hand-built heap keeps a position table so DECREASE-KEY can find a vertex.
adjacency lists and queues
Vec<Vec<(usize, u32)>> holds a (neighbour, weight) list per vertex, and vec![vec![0; n]; n] a table of rows, each its own heap buffer. VecDeque is a queue: while let Some(u) = queue.pop_front() stops when it is empty.
borrow a slice, copy with to_vec()
A function that takes &[Edge] only borrows the caller's list. To sort without disturbing it, it first makes its own copy with to_vec(); split_off cuts a Vec in two.
a counter lent down the calls
cmps: &mut u64 lends one counter to every recursive call, so each level adds to the same total. #[derive(Default)] builds a struct of counters that all start at 0, and a tuple returns the tree and its counts together.
const arrays and binary search
A const array such as [Edge; 14] is part of the program, and a recursive walk can fill a table through one &mut slice. A binary search keeps lo and hi indices and halves the range each time.
