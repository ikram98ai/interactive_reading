The chapter in six stops

Each stop uses the same three numbers. Learn them now, and the rest of the chapter gets much easier.

  1. Say what may run togetherYou mark which jobs are allowed to run at the same time. A scheduler decides who actually does what.
  2. Draw the runAny parallel run can be drawn as boxes and arrows. Two numbers read off that picture predict how fast it can ever go.
  3. Find the limitMore processors help until the longest chain of waiting gets in the way. Past that point, adding more does almost nothing.

26 · task-parallel programming

Who does which job?

Don't decide who does which job. Say which jobs may run together, and let a scheduler keep everyone busy.

Nine jobs are waiting. They take 7, 5, 4, 1, 1, 2, 1, 2 and 1 minutes. You have three workers, so those 24 minutes of work could finish in 8. How you hand the jobs out decides how close you get.

Split them up front, three jobs each, and the first worker gets all the long ones. It finishes at minute 16, while the others sat idle from minute 4. That is programming with threads: you divide the job yourself, and keeping things balanced is your problem.

Now hand out each job only when someone is free. A scheduler does that for you, and you finish at minute 9. That is the idea of task-parallel programming: you only say what may run together. You never say who runs it.

Why this works: when you write the program, you can't know how long each job will take. The scheduler doesn't need to know either. It just sees who is free right now.

Try it: press Next to hand out the jobs one at a time. Then switch to A scheduler at the top and watch the same nine jobs finish 7 minutes sooner.

What the book says

Parallel computers are ubiquitous. Multicores contain several processing cores, each able to access any location in a common shared memory. Clusters join multicores with a network and have distributed memory, but shared-memory programming tends to be conceptually easier, so the chapter focuses on multicores.

Programming a shared-memory parallel computer directly with threads tends to be difficult and error-prone. One reason is that it can be complicated to dynamically partition the work so each thread receives about the same load.

Task-parallel platforms add a layer of software on top of threads. The programmer identifies what may run in parallel, “processor-oblivious”, and the platform's scheduler load-balances the tasks across the processors.

Fork-join parallelism, the most basic kind of task-parallel algorithm, is typically embodied in two features: spawning and parallel loops. The pseudocode needs just three added keywords: parallel, spawn and sync. The book states this section in words; the listing below is our own short sketch of the two ways to hand out jobs, and the nine jobs are our own example.

26.1 · parallel keywords

Spawn and sync

One word says "this may run at the same time". Another says "wait for it here". The program's meaning stays the same.

In the Fibonacci numbers, each one adds the two before it: 0, 1, 1, 2, 3, 5. Count from 0, so number 3 is the 2. To get it, compute number 2 and number 1, then add. Those two calculations don't touch each other's data, so they could happen at the same time.

So we add two words. spawn starts a call and lets the caller (the parent) carry on while the spawned call (its child) works. sync makes the parent wait until its children finish, so that it is safe to use their answers.

Here is the part people miss: spawn gives permission. It doesn't order anything to run at the same time. With one processor the jobs run one after another, and the answer is still right. Delete the two words and you have the ordinary program, which the book calls the serial projection.

Read the pseudocode
x = spawn P-FIB(n − 1)
spawn
Start this call. You may carry on with the next line while it runs.
x
Where the child's answer lands. Don't read it before the sync.
sync
Stop here until every child you spawned has finished.

With numbers: P-FIB(3) spawns P-FIB(2), which will give x = 1. It calls P-FIB(1) itself, which gives y = 1. After the sync it returns 1 + 1 = 2.

Easy to mix up: a spawn isn't a command to use another processor. It only says that nothing breaks if another processor helps. The scheduler decides what really happens, at run time.

Try it: step through One processor, then Two processors. The answer is the same, but the running time drops from 9 to 6. Then pick Forget the sync, and watch P-FIB(3) add up a number that hasn't arrived yet.

What the book says

FIB(n) makes two recursive calls and has running time Θ(φn), which is exponential. It is a poor way to compute Fibonacci numbers, but it warms up the concepts: two parallel tasks that operate on entirely different data each produce the same outcomes as when run serially.

P-FIB adds spawn and sync. Deleting them gives the serial projection, FIB apart from the name. The parent may continue to execute in parallel with its spawned child. Nested spawns create a potentially vast tree of subcomputations.

The keywords express the logical parallelism of the computation. At runtime, a scheduler determines which subcomputations actually run in parallel.

A procedure cannot safely use the values returned by its spawned children until after it executes a sync. It is convenient to assume that every procedure executes a sync implicitly before it returns.

26.1 · a graph model for parallel execution

A run, drawn as a picture

Draw each stretch of work as a circle, and add an arrow wherever one stretch must finish before another can start.

P-FIB(4) makes 9 calls. Inside each call, some stretches of code run straight through, with no spawn, sync, call or return. Each such stretch is one circle, called a strand. An arrow from one strand to another means "this must finish first".

The whole picture is called a trace. It holds no clock and no processors. It only shows what has to come before what, which makes it the same however many processors you have.

The arrows tell you how the code was written. A strand with two arrows leaving it did a spawn. A strand with several arrows coming in is waiting at a sync. If arrows lead from one strand to another, the two are in series, so their order is fixed. If no arrows lead either way, they are in parallel: they may run at the same time, and either may go first.

Why this helps: once you have the picture, questions about speed become questions about circles and arrows. That is the next machine.

Try it: press Next to build the picture one call at a time. Then pick Series or parallel? and click any two circles to see how they relate.

What the book says

The execution of a parallel computation can be viewed as a directed acyclic graph G = (V, E), called a (parallel) trace, and also called a computation dag in the literature. Vertices are executed instructions, and an edge (u, v) means instruction u had to execute before v.

A chain of instructions with no parallel or procedural control is grouped into a single strand. A call adds an edge to the child's first strand, and the child's last strand has an edge to the caller's next strand. A spawn adds a second edge, because the parent's next strand can continue at once, and the child's last strand has an edge to the strand immediately after the sync.

If a directed path runs from u to v, the strands are (logically) in series. If no path runs either way, they are (logically) in parallel.

Analyses assume an ideal parallel computer: processors of equal power, a sequentially consistent shared memory, and no scheduling cost. Sequential consistency means memory behaves as if exactly one instruction executes at a time, in a linear order that preserves each processor's own order.

26.1 · performance measures

Work and span

Two numbers from the picture set the limits: how much there is to do, and the longest chain that must happen in order.

Say each circle in P-FIB(4) takes one second. Count all the circles and you get 17. That is the work: 17 seconds, if one processor does everything. We write it T₁.

Now give yourself unlimited processors. Are you done in one second? No, because of the arrows. Follow the longest chain of arrows from start to finish: it has 8 circles, and they must run one after another. That is the span: 8 seconds, however many processors you own. We write it T∞. The longest chain itself is the critical path.

The third number is the running time, TP: how long it really takes on P processors. Work and span come from the picture alone. Only the running time depends on how many processors you have and how they are used.

Read the maths
T₁ = every strand's time, added up
T∞ = strand times along the longest chain
T₁
Work. The little 1 means "on one processor".
T∞
Span. The ∞ means "on unlimited processors".
TP
Running time on P processors.

With numbers: P-FIB(4) has 17 strands of 1 second each, so T₁ = 17. Its longest chain has 8 strands, so T∞ = 8.

Easy to mix up: span isn't "the time on a fast machine" and work isn't "the time now". Slow down one strand and work always grows, but span grows only if that strand ends up on the longest chain.

Try it: step through Work, then Span. Then pick Slow a strand and click circles to make them take 3 seconds. Find one that raises the work but leaves the span alone.

What the book says

The work of a task-parallel computation is the total time to execute the entire computation on one processor: the sum of the times taken by each strand. If each strand takes unit time, the work is the number of vertices in the trace.

The span is the fastest possible time on an unlimited number of processors. It is the sum of the times along a longest path in the trace, where each strand is weighted by its execution time. Such a longest path is called the critical path.

The trace of Figure 26.2 has 17 vertices in all and 8 vertices on its critical path, so if each strand takes unit time, its work is 17 time units and its span is 8 time units.

The running time on P processors is written TP. The work is T1, and the span is T∞. The actual running time depends on the work, the span, how many processors are available and how the scheduler allocates strands. The book states work and span as definitions; the listing below writes them as short procedures.

26.1 · performance measures: the two laws

Two limits on running time

However clever you are, you can't finish faster than the work shared equally, and you can't finish faster than the longest chain.

P-FIB(4) has 17 seconds of work and a span of 8. Could 2 processors finish in 6 seconds? In 6 seconds they can do at most 12 seconds of work, and there are 17 to do. So no. That is the work law.

Could 100 processors finish in 3 seconds? They have more than enough muscle, but 8 strands must still run one after another, and those take 8 seconds. So no. That is the span law.

Both limits hold at once, so the running time can't be below the larger of the two. While work is the bigger limit, more processors help. Once the span is the bigger limit, the floor stops moving.

Read the maths
TP ≥ T₁ / P (work law)
TP ≥ T∞ (span law)
P
How many processors you have.
T₁ / P
The work, if it could be shared out perfectly evenly.
T∞
The longest chain, which can't be shared at all.

With numbers: T₁ = 17 and T∞ = 8. On 2 processors, 17 ÷ 2 = 8.5, so the running time is at least 8.5. On 4 processors, 17 ÷ 4 = 4.25 but the span is still 8, so it is at least 8.

Why the work law holds: in one step, P processors do at most P units of work. Why the span law holds: a machine with unlimited processors could always pretend to have just P, so P processors can never beat it.

Try it: press Next to add each law to the chart, then walk up through the processor counts. Then raise work to 64 and lower span to 4, and see how far right the curve keeps falling.

What the book says

The work and span provide lower bounds on the running time TP of a task-parallel computation on P processors.

In one step, an ideal parallel computer with P processors can do at most P units of work, and thus in TP time it can perform at most PTP work. Since the total work to do is T1, we have PTP ≥ T1. Dividing by P yields the work law (26.2): TP ≥ T1/P.

A P-processor ideal parallel computer cannot run any faster than a machine with an unlimited number of processors, which can emulate it by using just P of its processors. Thus the span law (26.3): TP ≥ T∞.

The book states the laws as inequalities; the listing below writes them as a short procedure.

26.1 · performance measures: speedup

Speedup and parallelism

Dividing the total effort by the longest chain tells you how many processors a job can really use. Beyond that, the extras mostly wait.

P-FIB(4) has 17 seconds of work and a span of 8. Divide them: 17 ÷ 8 = 2.125. That single number says that P-FIB(4) can never run more than 2.125 times faster, even on a million processors. The number is called its parallelism.

Speedup means how many times faster P processors are than one. The ideal is a speedup of P. But once P passes the parallelism, you can't get that any more. Bigger jobs have more parallelism: P-FIB(20) has over a thousand.

Read the maths
speedup = T₁ / TP
parallelism = T₁ / T∞
slackness = parallelism / P
speedup
How many times faster than one processor. At most P, and at most the parallelism.
parallelism
The average amount of work that can run side by side, for each step along the longest chain.
slackness
How much parallelism you have per processor. Below 1, there isn't enough to go around.

With numbers: on 4 processors, P-FIB(4) has slackness 2.125 ÷ 4 ≈ 0.53, so a speedup of 4 is impossible. P-FIB(20) has parallelism about 1094, so on 100 processors its slackness is about 11.

Why it is a ceiling: the span law says the running time is at least T∞. So T₁ ÷ TP can't be more than T₁ ÷ T∞, however large P gets.

Try it: pick a job at the top, then press Next to multiply the processors by 4 each time. Watch the amber line go flat. Move the P slider to start from any processor count.

What the book says

The speedup on P processors is T1/TP, and by the work law it is at most P. Linear speedup means T1/TP = Θ(P), and perfect linear speedup means T1/TP = P.

The ratio T1/T∞ is the parallelism. As a ratio, it is the average amount of work that can be performed in parallel for each step along the critical path. As an upper bound, it gives the maximum possible speedup on any number of processors. Once the number of processors exceeds it, the computation cannot possibly achieve perfect linear speedup.

For P-FIB(4), T1/T∞ = 17/8 = 2.125, so achieving much more than double the performance is impossible.

The (parallel) slackness on P processors is (T1/T∞)/P. If it is less than 1, perfect linear speedup is impossible, and extra parallelism can have a great impact. If it is greater than 1, the work per processor is the limiting constraint. Once the slackness is much greater than 1, additional parallelism shows diminishing returns.

26.1 · scheduling

A greedy scheduler

If you never leave a processor idle while a job is ready, you land within a factor of two of the best possible time.

Someone must decide, at each moment, which strands run where. A greedy scheduler has one rule: if a strand is ready and a processor is free, run it. It doesn't plan ahead. It doesn't even know what comes next.

Each time step is one of two kinds. In a complete step, at least P strands are ready, so every processor is busy. In an incomplete step, fewer than P are ready, so all of them run, and some processors have nothing to do.

Here is why that is enough. Complete steps do P units of work each, and only so much work exists. Incomplete steps run every ready strand, so each one shortens the longest remaining chain by 1, and only so much chain exists. Every step is one kind or the other, so the two counts add up.

Read the maths
TP ≤ T₁ / P + T∞
T₁ / P
The most complete steps there can ever be.
T∞
The most incomplete steps there can ever be.

With numbers: P-FIB(4) on 2 processors: T2 ≤ 17 ÷ 2 + 8 = 16.5. The floor from the two laws is 8.5. The machine lands in between.

Why this is within a factor of 2: the true best time is at least the larger of T₁ / P and T∞. The sum of two numbers is never more than twice the larger one.

Try it: pick a processor count at the top and press Next. Each column of the chart is one time step, marked C for complete or I for incomplete. Compare the Cs on 2 processors with the Cs on 4.

What the book says

The programming model provides no way to say which strands execute on which processors; the runtime system's scheduler maps the unfolding computation onto them. It must operate online, without knowing in advance when procedures will be spawned or finish, and a good one operates in a distributed fashion. For simplicity the book analyzes an online centralized scheduler.

Greedy schedulers assign as many strands to processors as possible in each time step. A complete step has at least P strands ready; an incomplete step has fewer than P.

Theorem 26.1: on an ideal parallel computer with P processors, a greedy scheduler executes a computation with work T1 and span T∞ in time TP ≤ T1/P + T∞. Complete steps number at most T1/P, and every incomplete step decreases the span of the remaining trace by 1.

Corollary 26.2: the running time is within a factor of 2 of optimal. Corollary 26.3: if the parallel slackness is much greater than 1, then TP ≈ T1/P, a speedup of approximately P. As a rule of thumb, a slackness of at least 10 generally suffices. Which ready strands to pick on a complete step is left open; here we take the ones the serial program would reach first, and the theorem holds for any choice.

26.1 · analyzing parallel algorithms

Adding up work and span

Jobs in a row add their waiting. For jobs side by side, you only count the longer one. The total effort always adds.

Say job A has work 6 and span 4, and job B has work 5 and span 3. Run A and then B, and you have work 11 and span 7. Nothing surprising: the waits line up end to end.

Now run them side by side. The work is still 11, because the same things get done. But the span is only 4, the longer of the two. While the longer job runs, the shorter one has plenty of time to finish alongside it.

Any fork-join program is built from these two moves. So finding the work is the old job of timing the ordinary program, and the span follows from the same structure. For P-FIB, the work grows about 1.6 times with each step up in n, while the span only grows by 2.

What the book says

Analyzing the work amounts to analyzing the running time of an ordinary serial algorithm, namely the serial projection. Analyzing the span is the new thing that parallelism engenders.

If two traces are joined in series, their spans add. If they are joined in parallel, the span of their composition is the maximum of the spans of the two traces. In both cases the work is the sum of their work (Figure 26.3). The trace of any fork-join parallel computation can be built up from single strands by series-parallel composition.

The work of P-FIB(n) is Θ(φn). Its span obeys T∞(n) = max{T∞(n − 1), T∞(n − 2)} + Θ(1) = T∞(n − 1) + Θ(1), so T∞(n) = Θ(n).

The parallelism is Θ(φn/n), which grows dramatically as n gets large. Blocks A and B and the unit-strand counts here are our own examples; the book's bounds are asymptotic. The listing writes the composition rules as procedures.

26.1 · parallel loops

Parallel loops

A parallel loop isn't started all at once. Its range gets cut in half again and again, and each half may run on its own.

Multiplying a matrix by a vector means working out 8 separate answers, y1 to y8, when the matrix has 8 rows. Each answer has its own place in memory, so all eight could be worked out at once. We write that as parallel for.

Behind the scenes, nothing launches all 8 rounds in one go. The compiler turns the loop into a function. It cuts the range 1 to 8 into 1 to 4 and 5 to 8, spawns one half, works on the other, and repeats. This is recursive spawning.

Cutting in half takes few levels: 8 rounds need 3, and a thousand rounds need about 10. So the splitting adds very little to the span. Each split is a little extra work, and it can pay to stop early. To coarsen a loop is to run several rounds in one leaf. That means fewer splits, but also less parallelism.

Read the maths
T∞(n) = Θ(lg n) + max iter∞(i)
n
The number of rounds in the loop.
lg n
How many times you can halve n before reaching 1: the levels of cutting.
iter∞(i)
The span of round i. Only the slowest round counts, since they run side by side.

With numbers: P-MAT-VEC with n = 8 has 3 levels of cutting, and each round takes 8 additions. So the span is about 3 + 8 = 11, while the work is about 8 × 8 = 64.

Why the splitting barely costs any work: a tree that ends in 8 leaves has only 7 splits. So the total splitting is smaller than the real work in the leaves.

Try it: press Next to cut the range level by level. Then pick 2 rounds per leaf and 4 rounds per leaf, and watch the work drop slightly while the span climbs. Drag n to see other sizes.

What the book says

The parallel keyword precedes the for keyword. P-MAT-VEC computes y = y + Ax by computing all entries of y in parallel.

Compilers can implement parallel loops by recursive spawning. P-MAT-VEC-RECURSIVE spawns the first half of the iterations in parallel with the second half and then executes a sync, creating a binary tree of parallel execution (Figure 26.4).

The work of P-MAT-VEC on an n × n matrix is Θ(n2). Recursive spawning increases the work, but not asymptotically: the tree is a full binary tree, so the number of internal nodes is one less than the number of leaves.

A parallel loop with n iterations has span Θ(lg n) + max{iter∞(i)}. For P-MAT-VEC that is Θ(n) + Θ(lg n) = Θ(n), so the parallelism is Θ(n).

Platforms sometimes coarsen the leaves, executing several iterations in a single leaf. This optimization comes at the expense of reducing the parallelism, though with enough slackness near-perfect linear speedup won't be sacrificed. The exact counts here (1 per split, 1 per addition) and the matrix are our own.

26.1 · race conditions

Two processors, one number

If two jobs running together both change the same number, one change can vanish, and the bug may show up only rarely.

Set x to 0, then add 1 to it twice, in parallel. It looks as if x must end at 2. But "add 1" isn't one action. A processor loads x into a private spot called a register, adds 1 there, and stores the result back.

Now suppose both processors load before either one stores. Both see 0. Both work out 1. Both store 1. One update is lost, and the program prints 1. That is a determinacy race: two parallel instructions touch the same place in memory, and at least one of them writes to it.

Why is it so nasty? The result depends on timing, so a program can pass tests for days and then fail in the field. The book names two famous cases: the Therac-25 radiation machine and the 2003 blackout. The cure is to keep parallel strands mutually noninterfering: they may share what they only read, but not what they change. Then the program is deterministic: the same input gives the same result, every time.

Easy to mix up: in this tiny example, 18 of the 20 orders go wrong, because the whole strand is the risky part. A real program runs a great deal of code around its few risky lines, so most orders of the whole program come out fine. That is why the book says races are hard to catch: most runs look correct.

Try it: press Next through the book's bad order. Then click any tile at the bottom to try another of the 20 orders. Finally pick The fix, where each strand writes to its own place: all 20 tiles turn green.

What the book says

A parallel algorithm is deterministic if it always does the same thing on the same input, and nondeterministic if its behavior might vary from run to run. A determinacy race occurs when two logically parallel instructions access the same memory location and at least one of the instructions modifies the value stored in the location.

Figure 26.5 shows RACE-EXAMPLE printing 1 instead of 2. By sequential consistency, the parallel execution behaves like an interleaving of the two processors' instructions. Either trivial order prints 2. Generally, most instruction orderings produce correct results, but some generate improper results, so races can be extremely hard to test for.

Famous race bugs include the Therac-25 radiation therapy machine, which killed three people and injured several others, and the Northeast Blackout of 2003, which left over 50 million people in the United States without power.

Parallel strands should be mutually noninterfering: they only read, and do not modify, any memory locations accessed by both of them. P-MAT-VEC-WRONG parallelizes the inner loop to reach Θ(lg n) span, but it races when updating yi. Index variables of parallel loops do not cause races.

Some programs are intentionally nondeterministic and use mutual-exclusion locks and other synchronization; the book insists on an absence of determinacy races in the algorithms it develops. The fix shown here, one variable per strand, is our own small example of that rule.

26.1 · a chess lesson

The speedup that wasn't

A change that made a program faster on a small machine would have made it slower on the big one. Two numbers predicted it.

A team was building a chess program. They tested on a 32-processor computer, but the real target was a 512-processor supercomputer they could rarely use. One day, a clever change cut the test from 65 seconds to 40. A clear win, it seemed.

Instead of cheering, they looked at the work and the span. The change halved the work, from 2048 to 1024. But it raised the span from 1 to 8. On 32 processors the work still dominates, so halving it wins. On 512 processors, the work per processor is tiny, and the span is what's left.

Estimate the running time at 512 processors: the original takes 5 seconds, and the "improved" one takes 10. They threw the change out, without ever running it on the big machine.

What the book says

This true story occurred during the development of one of the first world-class parallel chess-playing programs, and the timings have been simplified for exposition. The program was developed on a 32-processor computer but designed to run on a supercomputer with 512 processors.

An optimization reduced the running time on an important benchmark from T32 = 65 seconds to T′32 = 40 seconds. The original version had work T1 = 2048 seconds and span T∞ = 1 second. With the optimization, the work becomes T′1 = 1024 seconds and the span becomes T′∞ = 8 seconds.

Treating inequality (26.4) as the equation TP = T1/P + T∞, the first version runs in T512 = 5 seconds and the second in T′512 = 10 seconds. The optimized version's span becomes the dominant term on 512 processors. They abandoned the optimization.

The moral of the story is that work/span analysis, and measurements of work and span, can be superior to measured running times alone in extrapolating an algorithm's scalability. 26.2 · parallel matrix multiplication: with parallel loops

Every entry at once

Each entry of the answer has its own place in memory, so all the entries can be worked out at the same time.

Multiplying two 3 × 3 matrices fills 9 entries, and each entry is a sum of 3 products. That is 27 multiply-and-adds, so one processor needs 27 rounds. But no entry needs any other entry. So we write parallel in front of the two outer loops. Now 9 entries can each do their first product in the same moment, then their second, then their third.

The inner loop has to stay an ordinary loop. All its rounds add to the same entry. Adding to one place at the same time is the lost update from the race machine.

26.2 · parallel matrix multiplication: divide and conquer

Eight smaller products, side by side

Cut each matrix in four, run eight smaller products side by side, and add. The waiting shrinks to a tiny part of the job.

Cut each matrix into four quarters and you can multiply using quarter-size pieces: eight smaller products, then add them up. Spawn all eight, and they run side by side. So the span only has to count one of them, plus the adding.

One catch. Two of the products belong in the top-left quarter of C: A₁₁·B₁₁ and A₁₂·B₂₁. If both added into C at once, that would be a race. So the second product of each pair goes into a temporary matrix D. After the sync, a parallel loop adds D into C.

Merge sort, first try

Sorting the two halves together is easy, but the final merge still walks every item in turn, and that slow walk limits everything.

Merge sort already splits its job in two. So just spawn both halves! Each half sorts at the same time as the other, and it looks as if we are done.

Now follow the longest chain on 8 numbers. Four small merges run side by side, and each takes 2 steps. Then two merges, each taking 4. Then one merge of all 8, which takes 8 steps, on its own, with nothing to share. That last merge alone is more than half the span.

26.3 · parallel merge sort: the split point

Finding the split point

In a sorted list, you can find where a value belongs in a handful of looks, without walking the whole list.

Merging can be cut in two if we can split both sorted lists around one value x. Say x is 10, and the sorted list is 2, 5, 7, 9, 12, 15, 20, 23. The place where 10 would fit is between 9 and 12. Everything to the left is at most 10, and everything from there on is at least 10. That place is the split point.

You don't have to look at every number. Look at the middle. If x is at most that number, the split point is at the middle or to its left. If not, it is to the right. Each look throws away half of what's left. Eight numbers need at most 4 looks, and a million need about 20.

Why this matters: the merge's bottleneck was walking everything in order. This search replaces that walk with a few looks, so the merge can split its job quickly.

Easy to mix up: this procedure has no parallelism at all. Its work and span are the same number. It is fast because there is so little to do, not because anyone helps.

Try it: press Next and watch the range shrink. Then drag x to 1 or 30. The split point can land at the very start, or just past the end.

What the book says

FIND-SPLIT-POINT(A, p, r, x) takes as input a sorted subarray A[p : r] and a key x. It returns a split point: an index q in the range p ≤ q ≤ r + 1 such that all the elements in A[p : q − 1] (if any) are at most x and all the elements in A[q : r] (if any) are at least x.

Each time through the while loop, line 5 compares the middle element of the range with the search key, and lines 6 and 7 narrow the range. When the range has been narrowed to a single index, line 8 returns it.

Because FIND-SPLIT-POINT contains no parallelism, its span is just its serial running time, which is also its work. Each iteration halves the search range, so it runs in Θ(lg n) worst-case time, and the procedure has work and span Θ(lg n). The sorted list here is our own example.

26.3 · parallel merge sort: parallel merging

Merging in parallel

Pick the middle of the longer list, find where it splits the other, and you get two smaller merges that can run side by side.

You have two sorted lists. Take the middle value of the longer one and call it x, the pivot. Use the search from the last machine to find where x splits the other list. Now everything goes into one of two groups: at most x, or at least x.

Count how many are in the first group, and you know exactly where x belongs in the output. Put it there. What is left is two smaller merges: the small groups go to the left of x, and the large groups go to the right. They never touch the same output cells, so they can run side by side, and each of them does the same thing again.

No walk across everything remains. Each call does one search and places one value. Why pick from the longer list? It guarantees that neither of the two smaller merges gets more than three quarters of the items, so the recursion stays balanced.

With a parallel merge, merge sort does the same work as before, but the longest chain shrinks from enormous to tiny.

Naive against parallel merging

The chapter on one page

The key ideas, in order.

Say "may", not "must"

spawn gives permission to run at the same time. sync waits for the children. A scheduler decides what really runs where.

Three separate numbers

Work is every job added up. Span is the longest chain. Running time depends on how many processors you have, and the other two don't.

Two floors under the time

You can't beat work ÷ P, and you can't beat span. Whichever is bigger is your floor.

Parallelism is the ceiling

Work ÷ span is the most speedup you can ever get. Past that many processors, the extras mostly sit idle.

Greedy is good enough

Never leaving a processor idle when a job is ready gives a time of at most work ÷ P + span, within a factor of 2 of the best possible.

Series adds, parallel takes the larger

Work always adds. Span adds for jobs in a row, and takes the larger for jobs side by side.

Races hide

If two parallel jobs touch the same memory and one of them writes, the answer can depend on luck. Keep what parallel jobs write separate.

Attack the longest chain

Matrix multiply and merge sort gain the most when the slow serial step on the longest chain gets divided too, like the final merge.

Words to know

The book's words from this chapter, in plain language.

thread
A separate line of execution that shares memory with other threads. The operating system decides when it runs on a core.
scheduler
The part of the system that decides which job runs on which processor, and when.
task-parallel
A way of programming where you only say which jobs may run together, and a scheduler handles the rest.
spawn
Start a function call, and allow the caller to carry on at the same time. It gives permission, not an order.
sync

parent / child
The call that runs a spawn, and the call it spawned.

The ordinary one-at-a-time program you get by deleting the words spawn, sync and parallel.
strand
A stretch of instructions with no spawn, sync, call or return inside. It is one circle in the picture of a run.
trace
The picture of one run: strands as circles, and an arrow wherever one strand has to finish before another can start.
in series / in parallel
Two strands are in series if arrows lead from one to the other. If no arrows connect them either way, they are in parallel.
sequential consistency
A promise about memory: the result always looks as if instructions ran one at a time, in some order that keeps each processor's own order.
work
The time for every strand added up, which is how long one processor would take. Written T₁.
span
The time along the longest chain of strands, which is how long unlimited processors would take. Written T∞.

How long a run really takes on P processors. Written TP.
critical path
A longest chain in the trace. Its length is the span.
work law
Running time is at least work ÷ P, because P processors do at most P units of work per step.
span law
Running time is at least the span, because no number of processors can beat unlimited processors.
speedup
How many times faster P processors are than one: T₁ ÷ TP.
parallelism
Work ÷ span. The largest speedup possible on any number of processors.
slackness
Parallelism ÷ P. Above 1 there is more parallel work than processors. Below 1, perfect speedup is impossible.
greedy scheduler
A scheduler that never leaves a processor idle if some strand is ready to run.
complete step
A time step with at least P strands ready, so every processor is busy.
incomplete step
A time step with fewer than P strands ready, so every ready strand runs and some processors sit idle.

deterministic
Always does the same thing on the same input, however the instructions happen to be scheduled.

Parallel strands that only read, and never change, the memory they share.
