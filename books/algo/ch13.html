Red-Black Trees

A binary search tree is only as fast as it is short, and keys that arrive in sorted order stretch it into a list. A red-black tree spends one bit per node on a colour, and a few recolourings and rotations per update, to keep searches, insertions and deletions at O(lg n) even in the worst case.

“By constraining the node colors on any simple path from the root to a leaf, red-black trees ensure that no such path is more than twice as long as any other, so that the tree is approximately balanced.” — Cormen, Leiserson, Rivest & Stein

13.1 · properties of red-black trees

Five rules that keep a tree in shape

Chapter 12's binary search trees are fast only while they stay short. Feed one keys in sorted order and it grows into a linked list. A red-black tree is a binary search tree with one extra bit in every node, its color, and five rules about where each colour may sit. Those rules keep every path from the root down to a leaf within a factor of two of every other one, so the tree stays roughly balanced.

The rules: (1) every node is red or black; (2) the root is black; (3) every leaf is black; (4) a red node has two black children; (5) from any node, every path down to a leaf passes the same number of black nodes. The “leaves” here are the empty NIL pointers under the key-holding internal nodes, so a node with one child still has a leaf on its other side.

Code doesn't keep a separate NIL for every leaf. One black sentinel object, T.nil, stands for all of them and for the root's parent too. A missing child is then an ordinary node whose colour you can read, so x.left.color never needs a null check. Drawings leave the leaves out, as the rest of the chapter does.

Try it: click a node to flip its colour and watch the five checks under the picture. Paint 15 black: property 5 breaks at 16, and its two unequal paths light up. Paint it back and paint the root 26 red: only property 2 complains, because the root sits on every path. Most other flips break property 5 too, since they change the black count of every path through that node. Pick One T.nil and click the sentinel itself. Then press Run checker to watch CHECK-BH compute black counts from the bottom up and stop at the first broken rule.

What the book says

Chapter 12 showed that a binary search tree of height h supports the basic dynamic-set operations in O(h) time. If the height is large, “the set operations may run no faster than with a linked list.” Red-black trees are one of many search-tree schemes that are balanced to guarantee O(lg n) time in the worst case.

A red-black tree is a binary search tree with “one extra bit of storage per node: its color, which can be either RED or BLACK.” Each node has the attributes color, key, left, right and p. A missing child or parent is NIL: think of the NILs as pointers to leaves (external nodes), and of the key-bearing nodes as internal nodes. By constraining the colours on any simple path from the root to a leaf, red-black trees ensure “that no such path is more than twice as long as any other, so that the tree is approximately balanced.”

The red-black properties: 1. Every node is either red or black. 2. The root is black. 3. Every leaf (NIL) is black. 4. If a node is red, then both its children are black. 5. For each node, all simple paths from the node to descendant leaves contain the same number of black nodes.

To handle boundary conditions, a single sentinel T.nil represents NIL: an object with the same attributes as an ordinary node, colour BLACK, its p, left, right and key arbitrary. Every pointer to NIL, including the root's parent, points to it. A distinct sentinel for each NIL would give every NIL a well-defined parent, but “That approach needlessly wastes space, however.” The rest of the chapter omits the leaves in its drawings (Figure 13.1(c)).

13.1 · black-height and lemma 13.1

Why the height stays logarithmic

Pick a node x and count the black nodes on a path from just below x down to a leaf, the leaf included. Property 5 says every such path gives the same count, so the count belongs to the node: its black-height, bh(x). The black-height of the tree is the root's.

Two facts squeeze the height. A subtree whose root has black-height b holds at least 2b − 1 internal nodes: each child has black-height at least b − 1, so each child's subtree holds at least 2b−1 − 1, and two of those plus x make 2b − 1. And since a red node never has a red child, at least half the nodes on any path below the root are black, so a path of length h needs bh(root) ≥ h/2.

Together: n ≥ 2h/2 − 1, which is h ≤ 2 lg(n + 1). No path is more than twice as long as the shortest one, so SEARCH, MINIMUM, MAXIMUM, SUCCESSOR and PREDECESSOR, each O(h) on any search tree, are O(lg n) here. Height counts the steps from the root down to a leaf T.nil, as the proof does.

Try it: press Play to run SUBTREE-FACTS from the root. It returns black-height, size and height from the bottom up, and each node's black-height appears beside it. Click any node to make it x, then play again on its subtree. Then pick Tallest legal tree and drag the slider: the long path alternates black and red, the short one is all black, and the height still stays under 2 lg(n + 1).

What the book says

The black-height bh(x) is “the number of black nodes on any simple path from, but not including, a node x down to a leaf.” By property 5 it is well defined, since all descending simple paths from the node have the same number of black nodes. The black-height of a red-black tree is the black-height of its root.

Lemma 13.1: a red-black tree with n internal nodes has height at most 2 lg(n + 1). The proof first shows, by induction on the height of x, that the subtree rooted at x contains at least 2bh(x) − 1 internal nodes. Height 0 means x is T.nil, and 20 − 1 = 0. Otherwise each child has black-height bh(x) − 1 if it is black or bh(x) if it is red, so the subtree holds at least 2(2bh(x)−1 − 1) + 1 = 2bh(x) − 1.

By property 4, at least half the nodes on any simple path from the root to a leaf, not including the root, must be black. So the root's black-height is at least h/2, and n ≥ 2h/2 − 1. Moving the 1 and taking logarithms gives lg(n + 1) ≥ h/2, or h ≤ 2 lg(n + 1). Exercise 13.1-5 asks you to show that the longest simple path from a node to a descendant leaf is at most twice as long as the shortest.

So SEARCH, MINIMUM, MAXIMUM, SUCCESSOR and PREDECESSOR run in O(lg n) on a red-black tree. TREE-INSERT and TREE-DELETE from Chapter 12 also run in O(lg n) on one, but they do not necessarily maintain the red-black properties.

13.2 · rotations

Twist one link, keep the order

Inserting or deleting a key can break the red-black rules, and recolouring alone can't always repair them: sometimes the shape has to change. The tool for that is the rotation, a local move that rewires a handful of pointers and keeps the binary-search-tree property intact.

A left rotation on a node x needs x's right child y. It twists the link between them: y moves up into x's place, x becomes y's left child, and y's old left subtree β moves across to become x's right subtree. The subtrees α (under x, on the left) and γ (under y, on the right) keep their parents. A right rotation on y is the mirror image, and undoes it.

From left to right the keys still read α < x < β < y < γ, so an in-order walk lists them the same before and after. The machine gives every key its own in-order column, which makes this visible: a rotation only moves nodes up and down. At most six pointers change, however big the tree is, so a rotation takes O(1) time.

Try it: press Play to run LEFT-ROTATE(T, x) on Figure 13.3, one line at a time. Halfway through, 14 briefly has two parents, and after line 11 an edge points upward until the picture settles. Press Play again to rotate back. Then click any edge to rotate around it (a right child rotates left, a left child rotates right), or use Step. In the Rust view the memory strip shows the arena: every “pointer” is a usize index into one Vec, copied out before each write.

What the book says

TREE-INSERT and TREE-DELETE take O(lg n) time on a red-black tree, but because they modify the tree, “the result may violate the red-black properties.” Restoring them means changing colours and pointers. The pointer structure changes through rotation, “which is a local operation in a search tree that preserves the binary-search-tree property.”

A left rotation on x needs a right child y that is not T.nil. It changes the subtree rooted at x by “twisting” the link between x and y to the left: y becomes the new root of the subtree, with x as its left child and y's original left child β as x's right child. LEFT-ROTATE assumes x.right ≠ T.nil and that the root's parent is T.nil.

In Figure 13.2, the keys in α precede x.key, which precedes the keys in β, which precede y.key, which precedes the keys in γ. RIGHT-ROTATE(T, y) is the inverse operation, and its code is symmetric. Both run in O(1) time. “Only pointers are changed by a rotation, and all other attributes in a node remain the same.”

Figure 13.3 runs LEFT-ROTATE on a binary search tree: inorder tree walks of the input and the modified tree produce the same listing of keys. Exercise 13.2-2 asks you to show that an n-node binary search tree has exactly n − 1 possible rotations, and 13.2-4 that any n-node binary search tree can be turned into any other with O(n) rotations.

13.3 · insertion

Drop it in, painted red

A new key enters a red-black tree exactly the way it entered a plain search tree in Chapter 12. A pointer x walks down from the root, turning left when the new key is smaller and right otherwise, while a second pointer y trails one step behind. When x falls off the bottom onto the sentinel, y is the parent, and the new node z hangs there as a leaf whose two children are T.nil.

Then comes the one real decision: the colour. A black z would put one extra black node on every path through it, so every ancestor of z would see unequal black counts (property 5), a fault spread across the whole path. A red z adds no black at all, so the black counts stay as they were. The worst a red z can do is local: it is a red root (property 2), or it sits under a red parent (property 4).

That is RB-INSERT: TREE-INSERT with T.nil in place of NIL, both children of z set to T.nil, z coloured red, and then one call to RB-INSERT-FIXUP to repair a broken property 2 or 4. The descent visits one node per level, so it costs O(lg n).

Try it: press Step and watch x walk down with y one step behind, then Play to finish the key. Once z is red, the strip at the bottom checks all five properties: 4 lands under a red 5 and breaks property 4. Press Play again: the fixup runs in one jump (the next scene takes it apart), and 13 lands under a black 14 and breaks nothing. Start empty inserts the keys of Exercise 13.3-2, and the very first one is a red root. What if z is black? shows why the book refuses: every node above z ends up with unequal black counts. In Rust, the memory strip shows z pushed onto the end of the arena; when the buffer is full the Vec moves to a bigger one, and the indices x, y, z still name the same nodes.

What the book says

To insert a node into a red-black tree with n internal nodes in O(lg n) time and keep the red-black properties, the book slightly modifies TREE-INSERT from page 321. RB-INSERT inserts node z as if the tree were an ordinary binary search tree, then colors z red; to guarantee that the properties are preserved, the auxiliary procedure RB-INSERT-FIXUP recolors nodes and performs rotations. The key of z is assumed to be filled in already. Exercise 13.3-1 asks why z is made red rather than black.

TREE-INSERT and RB-INSERT differ in four ways: every NIL in TREE-INSERT becomes T.nil; lines 14–15 set z.left and z.right to T.nil, to maintain the proper tree structure; line 16 colors z red; and, because that may violate a red-black property, line 17 calls RB-INSERT-FIXUP(T, z) to restore them.

Which properties can fail at that call? Properties 1 and 3 still hold, since both children of the new red node are the sentinel. Property 5 holds too, because z replaces the (black) sentinel and is red with sentinel children. “Thus, the only properties that might be violated are property 2, which requires the root to be black, and property 4, which says that a red node cannot have a red child.” Property 2 is violated if z is the root, and property 4 if the parent of z is red.

Since the height of a red-black tree on n nodes is O(lg n), lines 1–16 of RB-INSERT take O(lg n) time.

13.3 · RB-INSERT-FIXUP's three cases

Two reds in a row, three ways out

After the insert, at most one rule is broken, and the broken spot is always at z: either z and its parent are both red, or z is a red root. RB-INSERT-FIXUP keeps that promise as a loop invariant while it pushes the trouble up the tree. Each pass looks at three nodes around z: its parent, its grandparent (black, because the parent is red), and its uncle y, the grandparent's other child.

Case 1, the uncle is red: just recolour. Parent and uncle turn black and the grandparent turns red, so every path keeps its black count. The trouble, if any is left, has moved up two levels to the grandparent, which becomes the new z. Case 2, the uncle is black and z is an inner child: one rotation at the parent turns it into case 3 without changing any black count. Case 3, the uncle is black and z is an outer child: make the parent black and the grandparent red, rotate the grandparent the other way, and no two reds touch any more. The loop ends.

So the loop goes round again only after case 1, climbing two levels each time: O(lg n) passes. Cases 2 and 3 end it, so one insert does at most two rotations. Lines 17–29 are the same three cases in a mirror, for a parent that is a right child, and line 30 paints the root black, which is the only repair property 2 ever needs.

Try it: Step through Fig. 13.4: case 1 lifts z from 4 to 7, case 2 rotates 2 down, case 3 rotates 11 down, and the loop stops. The three chips at the bottom check the invariant every time line 1 is tested. Case 1 twice climbs all the way to the root, and only line 30 fixes it. Case 3 goes straight to the rotation; its uncle is T.nil, because a fresh leaf never has a real black uncle. Mirror runs lines 24–29. Zigzag inserts 1, 10, 2, 9, … , the order that turns a plain search tree into a zigzag chain: watch the rotation counter, never above 2 per key. In Rust, the memory strip shows that a rotation moves no node; it rewrites a few usize links.

What the book says

The while loop of lines 1–29 maintains a three-part invariant at the start of each iteration: (a) node z is red; (b) if z.p is the root, then z.p is black; (c) if the tree violates any of the red-black properties, it violates at most one of them, either property 2 (because z is the root and is red) or property 4 (because both z and z.p are red), but not both. Part (b) guarantees that the grandparent z.p.p exists whenever the loop body runs.

Case 1, the uncle y is red: the grandparent is black, and its blackness transfers down one level to both z.p and y; the grandparent becomes red, which maintains property 5, and the loop repeats with z.p.p as the new z, two levels up. If that creates a new violation of property 4, it is only between the new z and its parent.

Cases 2 and 3, the uncle is black. In case 2, z is a right child, and a left rotation immediately transforms the situation into case 3, in which z is a left child; since z and z.p are both red, the rotation affects neither the black-heights nor property 5. Case 3 performs some color changes and a right rotation, which preserve property 5. “At this point, there are no longer two red nodes in a row.” The loop then terminates, because z.p is black.

If only case 1 occurs, z moves toward the root, so eventually z.p is black (when z is the root, z.p is the sentinel, which is black). At termination only property 2 can fail, and line 30 restores it. The while loop repeats only in case 1, so it runs O(lg n) times and RB-INSERT takes O(lg n) in total. Moreover, it “never performs more than two rotations, since the while loop terminates if case 2 or case 3 is executed.” Lines 17–29 handle a parent that is a right child, with “right” and “left” exchanged.

13.4 · deletion

Pull one node out, and someone must fill the hole

Deleting starts as the plain search-tree deletion of chapter 12. If the doomed node z has at most one child, that child moves up into z's place. If it has two, its successor y (the leftmost node of z's right subtree) is cut out and moved into z's position, and takes z's colour along with it. Either way exactly one node, y, leaves its old spot, and its only child x slides up into that spot. x may be the sentinel T.nil. Every “put this subtree where that one was” move is RB-TRANSPLANT.

So the colour to remember is y's, before anything moves: y-original-color. A red y breaks nothing. Removing it changes no black count, it can't leave two reds touching, and a red node was never the root. A black y leaves every path through its old spot one black short (property 5). It may also leave x and its new parent both red (property 4), or put a red x at the root (property 2).

The book's trick is to give y's blackness to x as an extra black: count x twice and property 5 holds again. Now x is “doubly black” or “red-and-black”, which breaks property 1 instead, and RB-DELETE-FIXUP (the next machine) has to push that extra black out of the tree. The fixup looks at x.p even when x is T.nil. That is why RB-TRANSPLANT sets v.p even when v is the sentinel, and why line 16 sets x.p = y.

Try it: pick a deletion above the tree (black leaf, one child, y = z.right, y deeper) and press Step to walk through RB-DELETE one line at a time. z is ringed yellow and y blue; when x is T.nil it shows up as a small black square. At line 21 the checklist shows what broke, and line 22 runs the fixup in one go. Then tap any node to delete it next. In the Rust view, watch the memory strip: when x is the sentinel, slot 0's p gets written.

What the book says

Deletion takes O(lg n) time, like the other basic operations. “Deleting a node from a red-black tree is more complicated than inserting a node.” It builds on TREE-DELETE. RB-TRANSPLANT replaces the subtree rooted at node u by the subtree rooted at node v. It differs from TRANSPLANT in two ways: line 1 references the sentinel T.nil instead of NIL, and the assignment to v.p in line 6 occurs unconditionally: “the procedure can assign to v.p even if v points to the sentinel.”

When the node z being deleted has at most one child, y is z. When z has two children, y is z's successor, which has no left child; it moves into z's position and takes on z's color. “In either case, node y has at most one child: node x, which takes y's place in the tree.” Node x is T.nil if y has no children. Lines 2 and 10 save y-original-color right after each assignment to y. Line 16 is needed when y is z's right child and y's right child is T.nil, because RB-DELETE-FIXUP relies on x.p being y even if x is T.nil.

If y was red, the properties still hold: no black-heights change, no red nodes become adjacent, and y could not have been the root. If y was black, three problems may arise. A red child of y may become the new root (property 2). Both x and its new parent may be red (property 4). And moving y “causes any simple path that previously contained y to have one less black node” (property 5).

The fix for property 5: when the black node y is removed or moved, its blackness transfers to x, giving it an extra black. But then x is neither red nor black, which violates property 1. It is either “doubly black” or “red-and-black”, contributing 2 or 1 to the count of black nodes on paths through it. Its color attribute stays RED or BLACK: “the extra black on a node is reflected in x's pointing to the node rather than in the color attribute.”

13.4 · RB-DELETE-FIXUP's four cases

Passing the extra black up, or absorbing it

After a black node leaves, x carries an extra black, drawn here as a ring. RB-DELETE-FIXUP's loop moves that ring up the tree until one of three things happens. x reaches a red node, which is then “red-and-black”, so line 44 simply paints it black. Or x reaches the root, where the extra black can vanish because every path loses one black together. Or a rotation and a few recolourings soak it up and the loop stops. Inside the loop x is always a doubly black non-root, and its sibling w is never T.nil: w's side has to hold as many blacks as x's doubled count.

With x a left child, there are four cases. Case 1, w red: swap the colours of w and x.p and rotate left at x.p, which gives x a black sibling and turns it into case 2, 3 or 4. Case 2, w black with two black children: take one black off both x and w (w turns red) and hand it to x.p, which becomes the new x. Case 3, w black with a red left child and a black right child: swap the colours of w and w.left and rotate right at w, and you have case 4. Case 4, w black with a red right child: three recolourings and a left rotation at x.p absorb the extra black, and x = T.root ends the loop. When x is a right child, lines 24–43 do the mirror image.

Each case keeps the black count, including x's extra one, the same from the top of the picture down to every subtree, so property 5 is never at risk. Only case 2 repeats, and it rotates nothing, so the loop runs O(lg n) times. Cases 1, 3 and 4 finish after a constant amount of work: at most three rotations in all (case 1, then 3, then 4).

Try it: pick a starting tree above and press Step. The first step deletes the yellow node with RB-DELETE and puts the ring on x. Each further Step runs one line of RB-DELETE-FIXUP, with w in blue and the case named top left. case 2 climbs all the way to the root; 1→3→4 uses all three rotations; mirror runs lines 24–43. When a run ends, tap any node to delete it from the current tree.

What the book says

RB-DELETE-FIXUP restores properties 1, 2, and 4. The goal of the while loop in lines 1–43 is to move the extra black up the tree until x points to a red-and-black node, in which case line 44 colors x (singly) black; or x points to the root, “in which case the extra black simply vanishes”; or, having performed suitable rotations and recolorings, the loop exits. Lines 3–22 handle x as a left child and lines 24–43 the symmetric situation. The cases are not mutually exclusive.

Within the while loop, x always points to a nonroot doubly black node, and its sibling w cannot be T.nil: otherwise the number of blacks on the simple path from x.p to the leaf w would be smaller than the number on the path from x.p to x. RB-DELETE always assigns to x.p before calling RB-DELETE-FIXUP, even when x is T.nil, because the fixup references x's parent in several places.

In each case, the transformation preserves the number of black nodes (including x's extra black) from the root of the subtree shown to the roots of each of the subtrees α, β, …, ζ. Case 1 (w red, so w has black children) switches the colors of w and x.p and left-rotates on x.p, converting into case 2, 3, or 4. Case 2 (w black, both children black) removes one black from both x and w, leaving w red, and x.p takes on the extra black. “If case 2 enters through case 1, the new node x is red-and-black, since the original x.p was red.” Case 3 (w black, w.left red, w.right black) switches the colors of w and w.left and right-rotates on w, falling through into case 4. Case 4 (w black, w.right red) changes some colors and left-rotates on x.p, so that the extra black vanishes; line 22 sets x to the root.

Without the fixup, RB-DELETE takes O(lg n) time. Cases 1, 3, and 4 lead to termination after a constant number of color changes and at most three rotations. Case 2 is the only case in which the loop can repeat, and then x moves up the tree at most O(lg n) times, performing no rotations. “Thus, the procedure RB-DELETE-FIXUP takes O(lg n) time and performs at most three rotations, and the overall time for RB-DELETE is therefore also O(lg n).”

problem 13-1 · persistent dynamic sets

Every old version, almost for free

An editor with unlimited undo, a database that answers “what did this look like yesterday?”, a version-control system: each one has to keep the old versions of a set while it keeps changing. A set that keeps its past is persistent. The obvious way is to copy the whole set on every change, which costs Θ(n) time and space per update.

A search tree can do much better. Inserting a key changes only the nodes on the search path, from the root down to the new leaf. So copy just those nodes (COPY-NODE), let each copy point at the old subtrees it did not change, and give the new version its own root. Inserting 5 into the book's tree copies 4, 8 and 7, adds 5, and shares 3, 2 and 10 with the old version. That is path copying: h + 1 new nodes and O(h) time for a tree of height h. Every old root still sees exactly its own version, because no existing node is ever written.

It only works if nodes have no parent pointer. A shared node such as 3 would need its p to point at both the old 4 and the new 4, which one field can't do, so 3 must be copied too, then its children, and so on down: every insert copies all n nodes. Without parents, and with a balanced tree such as a red-black tree to keep h = O(lg n), each update costs O(lg n) time and space. In Rust the sharing is literal: each node is an Rc, and its strong count says how many parents and roots point at it.

Press Play again for 9, 1 and 6. Click the version chips under the tree to compare any version with the one before it; “rc 2” marks a node two parents share. Then switch to With parent pointers and insert again: every node turns blue.

What the book says

Sometimes an algorithm needs to keep past versions of a dynamic set as it is updated; such a set is called persistent. Copying the entire set whenever it changes works, but can slow a program down and consume a lot of space. Consider a persistent set with INSERT, DELETE and SEARCH, implemented with binary search trees as in Figure 13.8(a), keeping a separate root for every version.

To insert key 5, create a new node with key 5. It becomes the left child of a new node with key 7, since the existing node with key 7 cannot be modified. The new 7 becomes the left child of a new node with key 8, whose right child is the existing 10, and the new 8 becomes the right child of a new root r′ with key 4, whose left child is the existing 3. Only part of the tree is copied; the rest is shared with the original (Figure 13.8(b)). Each node has the attributes key, left and right but no parent.

problem 13-2 · join operation on red-black trees

Two trees and one key between them

Two shelves of sorted books, and one more book that belongs exactly between them: every key in T₁ ≤ x ≤ every key in T₂. The join operation turns T₁, x and T₂ into one red-black tree. Re-inserting every key would take O(n lg n); the join does it in O(lg n) by touching a single path.

Say T₁ has the larger black-height. Walk down its right spine, the path of right children from the root, counting as you go: stepping onto a black node lowers the black-height by one, stepping onto a red one doesn't. Stop at the black node y whose black-height equals T₂'s; it is the one with the largest key among such nodes. Now y's subtree and T₂ are equally “tall” in black nodes, so x can take y's place with y's subtree on its left and T₂ on its right. Search order holds because everything in y's subtree is ≤ x ≤ everything in T₂.

Colour x red. Its children are two black roots of equal black-height, so properties 1, 3 and 5 hold. What can break is property 2 (if x became the root) or property 4 (if x's new parent is red), which is exactly the situation right after RB-INSERT. So RB-INSERT-FIXUP finishes the job in O(lg n). If T₂ is taller, everything mirrors: walk down T₂'s left spine.

A stricter balance rule

Red-black trees allow one path to be twice as long as another. The older AVL tree is stricter: at every node, the heights of the left and right subtrees differ by at most 1. Each node stores its own height x.h (a leaf has height 0, and NIL counts as −1), so the difference, the balance, is one subtraction away.

Why the height stays O(lg n): the thinnest AVL tree of height h has one subtree of height h − 1 and one of height h − 2, both as thin as possible. Its size grows like the Fibonacci numbers, at least Fh nodes, and Fh grows like φh with φ ≈ 1.618. Turned around, h ≤ about 1.44 lg n, tighter than the red-black bound of 2 lg(n + 1).

To insert, walk down as in a plain search tree and hang the new node at the bottom. Then, on the way back up, call BALANCE on every node of the path: refresh its height and, if one side is now 2 taller, rotate. If the too-tall grandchild is on the outside (left of left, right of right), one rotation fixes it; if it is on the inside, a double rotation first rotates the child, then the node. There are no parent pointers, so each rotation simply returns the new root of its subtree. The whole insertion is O(lg n), and the counter shows that no insertion needs more than one single or double rotation: a rebalanced subtree is back at the height it had before.

What the book says

An AVL tree is a binary search tree that is height balanced: for each node x, the heights of the left and right subtrees of x differ by at most 1. To implement one, maintain an extra attribute h in each node such that x.h is the height of node x; T.root points to the root, as for any other binary search tree.

The chapter on one page

Chapter 13 in eight cards. Each one points at the scenes that act it out.

One bit, five rules

A red-black tree is a binary search tree whose nodes are red or black. The root and every leaf are black, a red node has black children, and every path from a node down to a leaf meets the same number of black nodes. One sentinel T.nil plays every leaf and the root's parent. → 13.1 Five rules

Never more than 2 lg(n + 1)

A subtree with black-height b holds at least 2b − 1 nodes, and at least half of any path below the root is black. So the height is at most 2 lg(n + 1), and searching, minimum, maximum, successor and predecessor all take O(lg n). → 13.1 Why it's balanced

Rotate: O(1), order kept

LEFT-ROTATE lifts x's right child y into x's place and hands y's left subtree β to x. RIGHT-ROTATE undoes it. A few pointers change and nothing else, and α < x < β < y < γ still holds. → 13.2 Rotations

Insert red

RB-INSERT is TREE-INSERT with T.nil for NIL, then colours the new node red. A red node adds no black to any path, so only property 2 (a red root) or property 4 (a red parent) can break, both right at z. → 13.3 Insertion

Three cases, two rotations

A red uncle: recolour and move z up two levels (case 1). A black uncle: at most one rotation to straighten the zigzag (case 2), then a recolour and a rotation that end the loop (case 3). O(lg n) time, at most two rotations. → 13.3 Fixing up

Remember y's colour

RB-DELETE removes or moves one node y and slides its child x into y's spot, even when x is T.nil, whose parent is then set on purpose. A red y breaks nothing. A black one leaves paths a black short, so x takes an extra black. → 13.4 Deletion

Push the extra black away

RB-DELETE-FIXUP looks at x's sibling w: four cases. Only case 2 repeats, moving the extra black up a level with no rotation. Cases 1, 3 and 4 finish in constant work, for at most three rotations. → 13.4 Extra black

Beyond the basics

Copying only the search path makes a persistent set, O(lg n) per version when the tree is balanced and has no parent pointers. Joining two trees around a middle key walks one spine in O(lg n). AVL trees balance by heights instead of colours. → 13-1 Persistent sets, 13-2 Join, 13-3 AVL trees

Words to know

The book's words from this chapter, in plain language.

balanced search tree
A search tree that keeps its height O(lg n), so the basic dynamic-set operations are O(lg n) in the worst case.
red-black tree
A binary search tree with a colour bit in every node and five rules about the colours, which keep it approximately balanced.
red-black properties
Every node is red or black; the root is black; every leaf is black; a red node's children are black; from each node, every path down to a leaf has the same number of black nodes.
internal node / leaf
Internal nodes hold the keys. Leaves (external nodes) are the NILs hanging below them.
sentinel T.nil
One black object that stands for every NIL leaf and for the root's parent, so code can read a missing child's colour or parent.
black-height bh(x)
The number of black nodes on any path from x, not counting x itself, down to a leaf. The tree's black-height is the root's.
Lemma 13.1
A red-black tree with n internal nodes has height at most 2 lg(n + 1).
rotation
A local change of a few pointers that moves one node up and its parent down, keeping the binary-search-tree property. O(1) time.
left / right rotation
LEFT-ROTATE(T, x) lifts x's right child; RIGHT-ROTATE(T, y) lifts y's left child. Each undoes the other.
uncle
The sibling of a node's parent. Its colour decides which case of RB-INSERT-FIXUP runs.
RB-INSERT-FIXUP
The loop after an insert that recolours and rotates until no red node has a red parent, then paints the root black.
loop invariant (fixup)
During the fixup at most one property is broken: 2, because z is a red root, or 4, because z and its parent are both red.
RB-TRANSPLANT
Replaces the subtree at u by the subtree at v, and sets v.p even when v is T.nil.
y-original-color
The colour of the node RB-DELETE removes or moves, saved before anything changes. Only black means the fixup must run.
extra black
The blackness a removed black node passes to x, so that property 5 still counts right. It lives in the pointer x, not in a colour field.
doubly black / red-and-black
What x is while it carries the extra black: a black node counted twice, or a red node counted once.
sibling w
x's parent's other child. Its colour and its children's colours pick the case of RB-DELETE-FIXUP.
persistent set
A dynamic set that keeps every past version while it is updated.
path copying
Copying only the nodes on the path to the change and sharing the rest, so a new version costs O(h) nodes.
join
Combines two sets and a key that sits between them, every key of the first ≤ x ≤ every key of the second, into one set.
AVL tree
A height-balanced binary search tree: at every node the two subtrees' heights differ by at most 1.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

arena + usize links
Every node lives in one Vec<Node> and p, left, right are indices into it. Index 0 is T.nil, so a missing child is the number 0 and no Option is needed.
#[derive(Clone, Copy, PartialEq, Debug)]
Asks the compiler to write the code for copying, == and {:?} printing, so color == Red just works.
Copy enum + exhaustive match
enum Color { Red, Black } leaves no room for a third colour, and a match on it without a _ arm must handle both.
copy the index, then write
let y = self.nodes[x].right; copies a usize and keeps no borrow. Writing nodes[nodes[y].right].p = y in one go is error E0502.
&self vs &mut self
A checker borrows the tree to read; a rotation or fixup borrows it mutably, and nothing else may touch it meanwhile.
Result + ?
The property checkers return Ok(black-height) or Err(which rule broke). ? passes an Err straight up to the caller.
tuples and destructuring
let (b, n, h) = facts(x); returns three values at once; let Node { key, color, .. } = n; takes a struct apart; match (c1, c2) tests two colours together.
struct update syntax
Node { p, ..old } builds a node from old's fields with only p changed.
Rc and Rc::clone
A shared, read-only pointer with a count. Cloning it copies a pointer, not the node, which is how persistent versions share subtrees.
as conversions
n as f64 turns an integer into a float for log2(); flag as u32 turns a bool into 0 or 1.
ilog2
n.ilog2() is ⌊lg n⌋ in integer arithmetic, with no rounding errors from floats.
closures that borrow
let k = |i| t.nodes[i].key; reads the tree it captured. While it lives, the tree can't be borrowed mutably.
