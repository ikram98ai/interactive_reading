part v · advanced data structures and augmenting

One extra number per node

Most programs get by with a textbook structure: a hash table, a linked list, a search tree. But sometimes the textbook structure is almost right, and the one question you need answered is just out of reach: how many keys are in this subtree? How tall is it? What do its keys add up to? You could walk the whole tree for every answer. Or you could keep the answer inside the tree.

To augment a data structure is to store extra information in it and write new operations that use that information. The catch is that the ordinary operations, such as insert, now have to keep the extra information true. The machine shows why that is often cheap: a node's extra number is computed from the node and its two children, so when a leaf is added only the nodes on the path up to the root can go stale.

This is the idea of Part V, advanced data structures. Chapter 17 augments red-black trees twice, once to find the ith smallest key and once to find overlapping intervals; the chapters after it turn to B-trees (Chapter 18) and disjoint sets (Chapter 19).

Try it: pick a field above the tree (size, height or sum) and press Fill the field: the numbers appear from the leaves upward, each parent reading its two children. Then press Add key 33, and again for the next keys: the path from the new leaf to the root turns coral (stale), then blue as each node is recomputed. Count the blue nodes against the whole tree. In the Rust view, one combine method keeps all three fields.

What the book says

Part V “returns to studying data structures that support operations on dynamic sets, but at a more advanced level than Part III.” Chapter 17 shows how to augment red-black trees, adding information in each node, to support dynamic-set operations beyond those of Chapters 12 and 13: first to maintain order statistics, then, in a different way, intervals of real numbers. It includes a theorem giving sufficient conditions for when a red-black tree can be augmented while keeping the O(lg n) running times of insertion and deletion. Chapter 18 presents B-trees, balanced search trees designed to be stored on disks, and Chapter 19 examines data structures for disjoint sets, whose operations run in O(m α(n)) time for a sequence of m operations, with α(n) at most 4 in any conceivable application.

The part's topics are not the only advanced data structures. The introduction lists Fibonacci heaps, dynamic trees, splay trees, persistent data structures, van Emde Boas trees and fusion trees for restricted universes of keys, and dynamic graph data structures.

Chapter 17 begins: “Rarely will you need to create an entirely new type of data structure, though.” More often, it continues, you can augment a textbook data structure by storing additional information in it, and then program new operations that support your application. “Augmenting a data structure is not always straightforward, however,” because the added information must be updated and maintained by the ordinary operations on the data structure.

The chapter's roadmap: Section 17.1 describes a structure that supports general order-statistic operations on a dynamic set, quickly finding the ith smallest number or the rank of a given element. Section 17.2 abstracts the process of augmenting and gives a theorem for red-black trees. Section 17.3 uses it to design a data structure for a dynamic set of intervals, such as time intervals, that quickly finds an interval overlapping a query interval.

17.1 · order-statistic trees

A size tag on every node

Picture twenty books on a shelf, sorted by title, and a question that keeps coming up: which book is seventeenth from the left? A search tree can find any title quickly, but it can't say how many books come before it without counting them. So we stick one small tag on every node of the tree, saying how many nodes hang below it, itself included.

The tag follows one rule. A node's size is the size of its left subtree, plus the size of its right subtree, plus one for itself, and a missing child counts as 0. In a search tree every subtree is an unbroken stretch of the sorted keys, so a node of size 7 covers exactly 7 neighbours in sorted order. A rank is a position in that sorted order.

An order-statistic tree is nothing more than a red-black tree with this one extra attribute in each node. Keys may repeat, so rank means the position in an inorder walk: Figure 17.1's two 14s have ranks 5 and 6.

Try it: click any node. In the sorted row below, its subtree lights up as one unbroken stretch: the left part blue, the right part mint, the node itself yellow. Then press Insert 24 and watch the new leaf walk down from the root, making every node it passes one bigger. Step runs it one line at a time, and Reset takes the new keys out again. In the Rust view the sizes are plain usize fields in an arena, and index 0 plays T.nil with size 0, so no line of code needs an if for a missing child.

What the book says

Section 17.1 modifies red-black trees so that any order statistic of a dynamic set, and the rank of an element, can be found in O(lg n) time. Chapter 9 found an order statistic in O(n) time in an unordered set. Figure 17.1 shows a data structure for this: an order-statistic tree T is “simply a red-black tree with additional information stored in each node.”

Each node x keeps the usual attributes x.key, x.color, x.p, x.left and x.right, along with a new attribute x.size: the number of internal nodes in the subtree rooted at x, including x itself but not including any sentinels. If the sentinel's size is defined to be 0, that is, T.nil.size = 0, then x.size = x.left.size + x.right.size + 1.

Keys need not be distinct. Figure 17.1 has two keys with value 14 and two with value 21. When equal keys are present the notion of rank is not well defined, so the book defines the rank of an element as the position at which it would be printed in an inorder walk of the tree. In Figure 17.1 the key 14 stored in a black node has rank 5, and the key 14 stored in a red node has rank 6.

The section then shows two queries that use size (OS-SELECT and OS-RANK) and how insertion and deletion keep the sizes right, all in O(lg n) time.

17.1 · retrieving the element with a given rank

Throw away a whole side at every step

You want the seventeenth book from the left. Stand at the root and ask one question: how many books are in the left subtree? Say 12. Then the root itself is the thirteenth, so the seventeenth is on the right, and there it is the fourth (17 − 13). One question threw away thirteen books, and the same trick works at every node below.

That is OS-SELECT. At node x, compute r = x.left.size + 1, the rank of x inside its own subtree, and compare it with the wanted rank i. Equal: x is the answer. Smaller: go left with the same i. Larger: go right and look for the (i − r)th. Each step goes one level down, so the cost is the height of the tree, O(lg n) for a red-black tree.

The book writes it recursively, and the machine runs it that way first. Exercise 17.1-3 asks for a loop instead, and the second mode is a sketch of one.

Try it: drag rank i and press Play, or click any node to ask for its own rank. In the sorted row, the lit block is the subtree still in play, mint cells are x.left.size, and the blue cell is where rank i lives; the block shrinks around it. Start with i = 17, the book's example, then try 5 and 6 (the two 14s). In the Rust view the strip shows the stack: the recursion keeps one frame per level, each with its own i, while the loop keeps one frame and overwrites it.

What the book says

OS-SELECT(x, i) returns a pointer to the node containing the ith smallest key in the subtree rooted at x; to find it in an order-statistic tree T, call OS-SELECT(T.root, i). Line 1 computes r, the rank of x within the subtree rooted at x: the value of x.left.size is the number of nodes that come before x in an inorder tree walk of that subtree, so x.left.size + 1 is x's rank there.

If i = r, then x is the ith smallest element, and line 3 returns x. If i < r, the ith smallest resides in x's left subtree, and line 5 recurses on x.left. If i > r, it resides in the right subtree. The subtree rooted at x contains r elements that come before x's right subtree in an inorder walk, so the ith smallest of the subtree rooted at x is the (i − r)th smallest of the subtree rooted at x.right, and line 6 recurses on that.

Worked example on Figure 17.1: the search for the 17th smallest element starts at the root, 26, with i = 17. The size of 26's left subtree is 12, so its rank is 13, and the node with rank 17 is the 17 − 13 = 4th smallest in 26's right subtree. At 41, i = 4 and the left subtree has size 5, so its rank is 6, and the search goes into 41's left subtree. At 30 the rank within its subtree is 2, so the search looks for the 4 − 2 = 2nd smallest in the subtree rooted at 38. Its left subtree has size 1, which means it is the second smallest, and the procedure returns the node with key 38.

Because each recursive call goes down one level, the total time is at worst proportional to the height of the tree. Since the tree is a red-black tree, its height is O(lg n), so OS-SELECT takes O(lg n) time for a dynamic set of n elements. Exercise 17.1-3 asks the reader to write a nonrecursive version.

17.1 · determining the rank of an element

Climb up and count what you pass

Now the reverse question: you hold a node, and want to know its place in the sorted order. Inside its own little subtree the node is easy to place: it comes right after everything in its left subtree. To place it in the whole tree, climb. Whenever you step up out of a right child, the parent and the parent's whole left subtree lie to your left, so add them. Stepping up out of a left child adds nothing, since the parent and its right subtree come later.

That is OS-RANK. It keeps r, the rank of x inside the subtree rooted at y, while y climbs from x to the root. Each pass is one parent pointer and one size lookup, so the cost is the height again, O(lg n). It needs each node to know its parent, which red-black trees store as x.p.

The sorted row shows the idea: the lit block is y's subtree, the numbers under it are ranks inside that block, and the blue cell, x, always sits at position r.

Try it: press Play for the book's example, the node 38, or click any node. The little table is the book's: y and r at the top of each pass. When y is a right child the block grows leftwards, the new cells flash mint, and r jumps; otherwise it grows rightwards and r stays. Try x = 3, which is a left child all the way up, and x = 47, a right child all the way. In the Rust view, a parent link is just another usize index.

What the book says

Given a pointer to a node x in an order-statistic tree T, OS-RANK returns the position of x in the linear order determined by an inorder tree walk of T. You can think of the rank of x as the number of nodes preceding x in an inorder tree walk, plus 1 for x itself.

OS-RANK maintains this loop invariant: at the start of each iteration of the while loop, r is the rank of x.key in the subtree rooted at node y. Initialization: line 1 sets r to the rank of x.key within the subtree rooted at x, and line 2 sets y = x. Maintenance: line 6 moves y to y.p. If y is a left child, neither y.p nor any node in y.p's right subtree precedes x, so r is left alone. Otherwise y is a right child, all the nodes in y.p's left subtree precede x, as does y.p itself, and line 5 adds y.p.left.size + 1 to r. Termination: each iteration moves y toward the root, and when y = T.root the subtree rooted at y is the entire tree.

On Figure 17.1, finding the rank of the node with key 38 gives the values of y.key and r at the top of the while loop: iteration 1: 38 and 2; iteration 2: 30 and 4; iteration 3: 41 and 4; iteration 4: 26 and 17. The procedure returns the rank 17.

Each iteration of the while loop takes O(1) time, and y goes up one level with each iteration, so the running time is at worst proportional to the height of the tree: O(lg n) on an n-node order-statistic tree.

17.1 · maintaining subtree sizes

Fix the counters on the way

A counter is only worth having while it is true. Every insert and delete changes how many nodes hang below some of the nodes, so the sizes must be repaired as part of the operation, without making it slower than its O(lg n). A red-black insert has two phases: a walk down to the spot where the new node goes, then a walk back up that recolours and, at most twice, rotates.

Phase one is plain bookkeeping. The new node will end up below every node on the path, so each node you pass adds 1 to its size, and the new node itself starts at 1. Phase two is where the care goes: recolouring touches no size at all, and a rotation moves one node up and one node down while the three subtrees hanging off them keep exactly the same members. Only the two nodes on the rotated link now hold a wrong number, and two lines fix them: the node that moved up takes the size of the node it replaced, and the node that moved down is recomputed from its children.

Deleting mirrors it. Before the node leaves, walk from the lowest node that moves up to the root, subtracting 1 from every size on the way; whoever takes the deleted node's place takes its colour and its size. The fixup's rotations (at most three) get the same two-line repair. A path costs O(lg n) and a rotation costs O(1), so the whole operation is still O(lg n).

Try it: Insert is set to key 39: press Play. Four sizes go up by 1 on the way down, the red leaf starts at 1, recolouring needs no size change, and the rotation leaves two coral numbers until lines 13 and 14 repair them. Then press Reset, turn on Skip lines 13–14 and play it again: the tree is still a valid red-black tree, but two sizes lie, and the OS-SELECT misses tile counts the ranks the sizes now steer wrongly (try Rotate with the skip on). In Delete, click a node and press Play. In Rotate, click an edge. The strip below the code shows the size cells of the Rust arena that get written.

What the book says

Once every node holds its size, OS-SELECT and OS-RANK are quick, but the work would be for naught if the basic modifying operations of red-black trees could not maintain the attribute efficiently. Insertion has two phases: the first goes down the tree from the root, inserting the new node as a child of an existing node, and the second goes up, changing colours and performing rotations.

In the first phase, the sizes are maintained by incrementing x.size for each node x on the simple path from the root toward the leaves, and the new node gets a size of 1. That path has O(lg n) nodes, so the extra cost is O(lg n).

In the second phase, the only structural changes are caused by rotations, of which there are at most two. A rotation is a local operation: “only two nodes have their size attributes invalidated.” The link around which the rotation is performed is incident on these two nodes. The book adds two lines to LEFT-ROTATE: line 13, y.size = x.size, and line 14, x.size = x.left.size + x.right.size + 1; the change to RIGHT-ROTATE is symmetric (Figure 17.2). The second phase therefore costs only O(1) extra, and the total for insertion remains O(lg n).

Deletion also has two phases. The first operates on the underlying search tree: it removes one node z and could move at most two other nodes (y and x in Figure 12.4). To update the sizes, traverse a simple path from the lowest node that moves, starting from its original position, up to the root, decrementing size at each node on it; the path has length O(lg n). The second phase causes at most three rotations and no other structural change, and they are handled the same way as for insertion. So insertion and deletion, including the size attribute, both take O(lg n).

17.2 · how to augment a data structure

Four steps and one test

Augmenting means hanging one extra fact on every node of a structure you already trust, so that a new kind of question becomes cheap. The book breaks the job into four steps: choose an underlying data structure, decide what extra information each element keeps, verify that the ordinary operations can maintain it, and develop the new operations it makes fast. Step 3 is where designs die: the field has to stay true through every change that insert and delete make, without slowing them down.

For a red-black tree, step 3 has a clean test, Theorem 17.1. If the field at a node is computable, in O(1), from that node, its left child and its right child (and their fields), then insert and delete can keep it right in O(lg n). The reason is a ripple: changing a node's field can only disturb its ancestors, a red-black tree has O(lg n) of those on any path, and the fixup does at most two rotations for an insert and three for a delete. Size passes. So do height, minimum and sum, which the machine adds as toy examples.

What fails? A field that looks beyond the children. Store each node's rank in the whole tree and OS-SELECT would be quick, but inserting a new smallest key bumps the rank of every node. Store each node's depth and a single rotation at the root changes the depth of every node outside one subtree. Those are the two fields for which the machine's third box turns red.

Try it: keep size selected and press Insert a new smallest key. The tree changes at once, and every stored number that is now wrong turns coral. Press Play: UPDATE-UP climbs from the new node to the root and rebuilds each number from the node's two children only. Then try Rotate the root (two numbers go stale). Switch to rank and insert again: every number goes stale, and no child can supply the answer. depth breaks on the rotation instead. The four tiles keep score of the stale numbers per edit.

What the book says

Augmenting a basic data structure to support extra functionality happens quite often in algorithm design. The process has four steps: choose an underlying data structure; determine additional information to maintain in it; verify that the additional information can be maintained for the basic modifying operations on the underlying structure; and develop new operations. You will rarely be able to follow the steps in order: most design work contains trial and error, and progress on all steps usually proceeds in parallel. There is no point in determining the information and developing operations (steps 2 and 4) if you cannot maintain the information efficiently.

Section 17.1 followed the steps. Red-black trees were chosen because they efficiently support other dynamic-set operations on a total order, such as MINIMUM, MAXIMUM, SUCCESSOR and PREDECESSOR; the size attribute was added; and insertion and deletion can maintain it in O(lg n); then OS-SELECT and OS-RANK were developed. Generally the additional information makes operations more efficient, and sometimes it is pointer information rather than data (Exercise 17.2-1). Ideally you update only a few elements: if each node stored its rank in the tree, OS-SELECT and OS-RANK would run quickly, but inserting a new minimum element might change this information in every node of the tree.

Theorem 17.1 (Augmenting a red-black tree): let f be an attribute that augments a red-black tree T of n nodes, suppose that the value of f at each node x depends only on the information in nodes x, x.left and x.right (possibly including x.left.f and x.right.f), and that x.f can be computed from this information in O(1) time. Then insertion and deletion can maintain the values of f in all nodes of T without asymptotically affecting their O(lg n) running times.

The proof's main idea is that a change to f in a node x reaches only the ancestors of x: updating x.f may require x.p.f to change, then x.p.p.f, and so on up to T.root, after which nothing else depends on it. With height O(lg n), one change costs O(lg n). Insertion's first phase therefore costs O(lg n); its second phase does at most two rotations, each changing two nodes and costing O(lg n) to propagate. Deletion does at most three rotations. In many cases, such as size, the cost after a rotation is only O(1). But if each operation needed Θ(lg n) rotations and each rotation walked to the root, one operation could cost Θ(lg2 n); that is why the constant number of rotations matters.

17.3 · interval trees

Bars on a line, a max in every node

A calendar of bookings, a timeline of events, a queue of jobs: each is a set of intervals, a stretch from a low end to a high end, and the usual question is which of them overlaps a given one. The book uses closed intervals [low, high], which include both ends, so [4, 9] and [9, 12] share the point 9. Two intervals overlap exactly when each starts no later than the other ends: i.low ≤ i′.high and i′.low ≤ i.high.

Any two intervals fall into exactly one of three cases, the interval trichotomy: they overlap, or the first lies wholly to the left of the second (i.high < i′.low), or wholly to the right (i′.high < i.low). So failing the overlap test always means one interval is clear of the other on one side. That fact is what makes a fast search possible in the next scene.

An interval tree is a red-black tree of intervals, keyed on the low end, so an in-order walk lists them sorted by low. The augmentation, step 2 of the recipe, is one number per node: x.max, the largest endpoint anywhere in the subtree under x. It passes the test of step 3 at once, because x.max = max{x.int.high, x.left.max, x.right.max}. Change one interval's high end and only the maxes on the path above it can go stale.

Try it: in Overlap or not, drag any end of the two bars (arrow keys work on a focused end), or press a preset. The two tests and the verdict follow, and the lines that ran are lit. Try Touching: closed ends count as overlap. Switch to Interval tree, the ten intervals of Figure 17.4. Click a node or a bar and a dashed line marks that node's x.max on the axis. Then press Shrink (the interval [25,30] is selected at the start), or drag its right end left: the maxes above it turn coral, because the tree has not been told yet. Press Play and UPDATE-MAX climbs and repairs them; the root's max drops from 30 to 26.

What the book says

Intervals are convenient for representing events that each occupy a continuous period of time: you could query a database of time intervals to find which events occurred during a given interval. The section assumes closed intervals; extending the results to open and half-open intervals is conceptually straightforward. An interval [t1, t2] is represented as an object i with attributes i.low = t1 (the low endpoint) and i.high = t2 (the high endpoint). Intervals i and i′ overlap if i ∩ i′ ≠ ∅, that is, if i.low ≤ i′.high and i′.low ≤ i.high.

Any two intervals satisfy the interval trichotomy (Figure 17.3): exactly one of three properties holds. (a) i and i′ overlap; there are four situations, and in each, i.low ≤ i′.high and i′.low ≤ i.high. (b) i is to the left of i′, that is, i.high < i′.low. (c) i is to the right of i′, that is, i′.high < i.low.

An interval tree is a red-black tree that maintains a dynamic set of elements, each containing an interval x.int. It supports INTERVAL-INSERT(T, x), INTERVAL-DELETE(T, x), and INTERVAL-SEARCH(T, i), which returns a pointer to an element whose interval overlaps i, or the sentinel T.nil if there is none. The four-step method of Section 17.2 guides the design. Step 1: a red-black tree is the underlying structure, each node contains an interval, and the key of x is its low endpoint, so an in-order walk lists the intervals in sorted order by low endpoint.

Step 2: each node x also contains a value x.max, the maximum value of any interval endpoint stored in the subtree rooted at x. Step 3: x.max is determined in O(1) time from the interval x.int and the max values of x's children, as x.max = max{x.int.high, x.left.max, x.right.max}. By Theorem 17.1, insertion and deletion therefore run in O(lg n) time, and Exercise 17.2-3 or 17.3-1 shows how to update all the max attributes that change after a rotation in just O(1) time. Figure 17.4 shows ten intervals and the interval tree that represents them.

17.3 · searching for an overlapping interval

Follow the maximum

You keep a diary of meetings in a search tree ordered by start time, and every branch carries a note: the latest finishing time of any meeting hanging below it. A friend asks whether anything is on between 22 and 25 o'clock. Reading every meeting would take forever; reading one path from the top to the bottom is enough.

At each meeting x you ask one question: does it overlap the query i? If yes, you are done. If not, you glance at the note on x's left branch. If that note is at least i.low, someone on the left reaches far enough, so go left. Otherwise nobody on the left even reaches the start of i, so go right. That is INTERVAL-SEARCH: a loop of constant-time steps down a tree of height O(lg n).

The surprise is that going left is safe even when the left branch holds no overlap. The note came from some interval i′ on the left that ends at or after i.low yet misses i, so i lies wholly to the left of i′. Everything on the right starts at x.low or later, which is even further right, so the right branch has nothing either. That is Theorem 17.2. Compare it with the tempting rule that only compares low endpoints, like a plain search tree: it can walk straight past an overlap.

Try it: press Play to run the search for i = [22, 25] on Figure 17.4, and watch each test light up on the strip under the tree. Press Miss 11–14 and Play for a search that ends at NIL. The mint-tinted nodes are the ones that really overlap i. Drag the yellow bar (or its ends) or use the sliders to move i. Then press Point 22, switch to Key-only rule and Play: the search misses an overlap that the max rule finds.

What the book says

The only new operation is INTERVAL-SEARCH(T, i), which finds a node in tree T whose interval overlaps interval i, or returns a pointer to the sentinel T.nil if there is none. The search starts at the root and proceeds downward. It stops when it finds an overlapping interval or reaches T.nil. Each iteration of the loop takes O(1) time and the height of an n-node red-black tree is O(lg n), so the procedure takes O(lg n) time.

On Figure 17.4, the search for i = [22, 25] starts at the root [16, 21], which does not overlap i. Since x.left.max = 23 is greater than i.low = 22, it goes left to [8, 9], which does not overlap either. Now x.left.max = 10 is less than 22, so it goes right, and the interval [15, 23] there overlaps i and is returned. For the unsuccessful search for [11, 14], the path goes root, [8, 9], then right to [15, 23], whose left child is T.nil, so the search goes right again, the loop ends and T.nil is returned.

Theorem 17.2 says that any execution of INTERVAL-SEARCH either returns a node whose interval overlaps i, or returns T.nil and the tree contains no interval that overlaps i. The proof shows that whether the search goes left in line 4 or right in line 5, it heads toward an overlapping interval if one exists. If it goes right, then x.left = T.nil or x.left.max < i.low, so every interval i′ in the left subtree has i′.high ≤ x.left.max < i.low, and by the interval trichotomy it does not overlap i.

If it goes left and the left subtree has no overlap, then x.left.max ≥ i.low and the left subtree contains an interval i′ with i′.high = x.left.max ≥ i.low. Since i′ does not overlap i, the trichotomy gives i.high < i′.low. Because the tree is keyed on low endpoints, i′.low ≤ x.int.low ≤ i″.low for any interval i″ in the right subtree. So i.high < i″.low, and the right subtree has no overlap either: “the search always proceeds in a safe direction”.

problem 17-1 · point of maximum overlap

The busiest moment

Draw n meetings as bars on a timeline. Which moment has the most meetings going on at once? That is the point of maximum overlap. Coverage only changes where a bar starts or stops, so a best point can always be found at an endpoint of one of the intervals: only 2n candidates need a look.

Give every left endpoint the value +1 (a meeting starts) and every right endpoint −1 (it ends), and walk the endpoints in order with a running total. The total is the number of bars over you, and its peak is the answer. Intervals are closed, so a bar still covers its own right end: where one ends and another begins they overlap, and at equal positions the +1 must come first.

Part (b) wants more than one sweep: INTERVAL-INSERT, INTERVAL-DELETE and FIND-POM, each in O(lg n). Keep the endpoints in a red-black tree and augment each node with two numbers that come from its children: the sum of the ±1 values below it and the highest running total inside its subtree. A change at one endpoint then touches only its ancestors (Theorem 17.1), and FIND-POM just reads the root.

Try it: in Sweep, press Play: the line walks the sorted events and the count under each event is how many bars are open. Then press −1 first (wrong) and Play again: touching bars close too early and the sweep misses the true peak. Switch to Tree and press Insert next interval five times: only the nodes on the path from each new endpoint to the root change their numbers. New intervals deals a fresh instance.

What the book says

Problem 17-1 asks you to keep track of a point of maximum overlap in a set of intervals: “a point with the largest number of intervals in the set that overlap it”.

Part (a) asks you to show that there is always a point of maximum overlap that is an endpoint of one of the intervals. Part (b) asks you to design a data structure that efficiently supports INTERVAL-INSERT, INTERVAL-DELETE, and FIND-POM, which returns a point of maximum overlap.

The hint: “Keep a red-black tree of all the endpoints.” Associate a value of +1 with each left endpoint and a value of −1 with each right endpoint, and augment each node of the tree with some extra information to maintain the point of maximum overlap.

The book leaves the extra information to the reader. The machine uses one standard choice, not taken from the book: each node stores the sum of the values in its subtree and the largest running total inside it, together with the endpoint where that total is reached. Both are computed from the node and its two children, so Theorem 17.1 keeps insertion and deletion at O(lg n).

Counting out the circle

n people stand in a circle. Starting from a chosen person you count around, and the m-th person leaves; counting carries on from the next person, and so on until the circle is empty. The order in which people leave is the Josephus permutation. For seven people and m = 3 it is ⟨3, 6, 2, 7, 5, 1, 4⟩.

Walking round the circle is fine when m is a small constant (part a). When m can be large it wastes effort: all you need is where the m-th person is. If the k people still standing were in a row, counting from position j lands on ((j + m − 2) mod k) + 1, a jump of arithmetic. An array can index that spot at once, but removing from the middle shifts everyone after it, so each person costs O(n) and the whole circle O(n2).

Part (b) asks for O(n lg n). Keep the people in an order-statistic tree: OS-SELECT(T.root, j) finds the j-th person still standing in O(lg n) by comparing j with x.left.size + 1, and deleting that node costs O(lg n) too, with the sizes on its path dropping by one.

Try it: press Play in Array mode. A counter walks m people round the circle, the formula lands on the same person, and everyone behind them in the buffer shifts. Then switch to Tree and Play again: OS-SELECT descends from the root, and deleting the node drops the sizes along its path. The last two tiles run the same m on 1000 people. Move the sliders for other circles; seven people and m = 3 is the book's example.

What the book says

Problem 17-2 defines the Josephus problem like this. A group of n people form a circle, and a positive integer m ≤ n is given. Beginning with a designated first person, proceed around the circle, removing every m-th person. After each person is removed, counting continues around the circle that remains, until nobody remains.

The order in which the people are removed from the circle defines the (n, m)-Josephus permutation of the integers 1, 2, …, n. For example, the (7, 3)-Josephus permutation is ⟨3, 6, 2, 7, 5, 1, 4⟩.

Part (a): suppose that m is a constant, and describe an O(n)-time algorithm that, given an integer n, outputs the (n, m)-Josephus permutation. Part (b): suppose that m is not necessarily a constant, and describe an O(n lg n)-time algorithm that, given integers n and m, outputs the permutation.

The book gives no solution here. The machine's two modes are one reading of the problem, not taken from the book: the index formula applied to an array, and the same formula with OS-SELECT and a tree delete from Section 17.1. The second procedure in the Tree listing is the book's OS-SELECT.

The chapter on one page

Chapter 17 in eight cards. Each one points at the scenes that act it out.

Store a little more

Rarely do you need a brand-new data structure. Usually you augment a textbook one: store additional information in it and program new operations on top. The catch is that the ordinary operations must keep the new information true. → Part V · Augmenting

A size in every node

An order-statistic tree is a red-black tree with one more attribute, x.size = x.left.size + x.right.size + 1, where T.nil.size = 0. Every subtree is an unbroken stretch of the sorted keys, and the rank of an element is its position in an inorder walk, so equal keys still get different ranks. → 17.1 Order-statistic trees

Pick by rank, rank by climbing

OS-SELECT compares i with r = x.left.size + 1 and goes left, right with i − r, or stops. OS-RANK starts at x and climbs, adding y.p.left.size + 1 whenever it leaves a right child. Each does one step per level: O(lg n). → 17.1 OS-SELECT, OS-RANK

Repair one path

Insertion adds 1 to every size on the way down, and the at most two rotations leave only two nodes wrong, fixed by two extra lines in LEFT-ROTATE. Deletion subtracts 1 along a path up from the lowest node that moves, and its at most three rotations get the same repair. Both stay O(lg n). → 17.1 Keeping sizes

Four steps, one theorem

Choose the underlying structure, decide what to store, check that it can be maintained, then develop the new operations. Theorem 17.1: if a field depends only on a node and its two children, insertion and deletion keep it right in O(lg n). A stored rank fails: a new minimum changes every node. → 17.2 The recipe

Intervals with a max

Closed intervals [low, high] overlap when i.low ≤ i′.high and i′.low ≤ i.high; otherwise one is wholly left of the other. An interval tree is a red-black tree keyed on low, with x.max = max{x.int.high, x.left.max, x.right.max}. → 17.3 Interval trees

Follow the max

INTERVAL-SEARCH walks one path: if x.left.max ≥ i.low go left, otherwise right. By Theorem 17.2 that never misses an overlap, because if the left side has none, the right side has none either. One constant-time step per level: O(lg n). → 17.3 INTERVAL-SEARCH

Two problems, same tools

A point of maximum overlap can always be an endpoint: give left ends +1 and right ends −1, and an augmented tree keeps the best running total under insertions and deletions. The Josephus permutation takes O(n lg n) when each removal is one OS-SELECT and one delete. → 17-1 Max overlap, 17-2 Josephus

Words to know

The book's words from this chapter, in plain language.

augmenting a data structure
Storing additional information in a known structure and programming new operations that use it, while the ordinary operations keep it up to date.
dynamic set
A set of keys that changes over time through insertions and deletions, and answers queries between them.
order statistic
The ith order statistic of a set is the element with the ith smallest key.
rank
An element's position in the linear order of the set. With equal keys, the position in an inorder walk of the tree.
order-statistic tree
A red-black tree whose nodes also store x.size, so that the ith smallest key and any element's rank cost O(lg n).
x.size
The number of internal nodes in the subtree rooted at x, including x, not counting sentinels. x.size = x.left.size + x.right.size + 1.
inorder walk
Visiting a tree's left subtree, then the node, then the right subtree. In a search tree it lists the keys in sorted order.
OS-SELECT(x, i)
Returns the node with the ith smallest key in the subtree rooted at x, by comparing i with x.left.size + 1 and going down one side.
OS-RANK(T, x)
Returns the position of x in an inorder walk, by climbing from x to the root and adding what lies to the left.
loop invariant of OS-RANK
At the start of each pass, r is the rank of x.key in the subtree rooted at y.
maintaining the sizes
Insertion adds 1 to each size on the path down and repairs two nodes per rotation; deletion subtracts 1 along a path up. O(lg n) in all.
the four steps
Choose an underlying data structure; determine the additional information; verify it can be maintained by the basic modifying operations; develop the new operations.
Theorem 17.1
If a field f of each node depends only on that node, its left child and its right child, and is computable from them in O(1) time, a red-black tree can maintain it through insertion and deletion in O(lg n).
closed interval
A stretch [t1, t2] that includes both endpoints, stored as i.low and i.high.
overlap
Intervals i and i′ overlap if they share a point: i.low ≤ i′.high and i′.low ≤ i.high.
interval trichotomy
Any two intervals either overlap, or the first lies wholly to the left of the second, or wholly to the right. Exactly one holds.
interval tree
A red-black tree of intervals, keyed on the low endpoint, with x.max in each node.
x.max
The largest interval endpoint in the subtree rooted at x: the maximum of x.int.high, x.left.max and x.right.max.
INTERVAL-SEARCH(T, i)
Walks one path down from the root and returns a node whose interval overlaps i, or T.nil if there is none.
Theorem 17.2
Any run of INTERVAL-SEARCH returns a node whose interval overlaps i, or returns T.nil and the tree has no overlapping interval.
point of maximum overlap
A point covered by the largest number of intervals of the set. One always exists at an endpoint of some interval.
Josephus permutation
The order in which people are removed from a circle of n when every mth person, counting on around what remains, is removed.

Rust words from the code panels

For readers coming from another language. Each one shows up in a listing above.

arena + index 0 as T.nil
All nodes live in one Vec<Node> and links are usize indices into it. Slot 0 is the sentinel, with size 0, so left.size + right.size + 1 needs no if for a missing child.
Option<usize> as T.nil
Where a link may be absent, None plays the sentinel. while let Some(k) = x loops for as long as there is a node, and the compiler makes you handle the None case.
usize and i32
Sizes and indices are usize, which cannot be negative: i - r is safe only because i > r, and size -= 1 on 0 panics in a debug build. Where a value may be −1, such as an empty subtree's height, use i32.
match i.cmp(&r)
cmp returns an Ordering: Less, Equal or Greater. A match must cover all three, so the book's if / elseif / else cannot lose a branch.
#[derive(Clone, Copy, Default, Debug)]
Asks the compiler to write copying, an all-zeros default, and {:?} printing. A small Copy struct such as a node or an interval can be read out of the Vec by value, so no borrow of the arena is still alive when you write to it.
trait and generic impl
trait Augment says how a field is combined from a node's children. impl<A: Augment> Tree<A> is one tree for every such field, compiled once per field type, with no runtime lookup.
match on a tuple, _ and guards
match (a < b, c < d) tests two conditions at once; _ means don't care; an if after a pattern is a guard that must also hold for the arm to fire.
flatten and reduce
An Option is iterable, so flatten() over a list of them drops the Nones. reduce(f) folds what is left into one value, with no starting value needed.
sort_by_key with a tuple
Tuples compare field by field, so a key such as (x, -v) sorts by position first and, at equal positions, puts the +1 before the −1.
iterator chains and closures
.filter(|&x| …).count(), .all(…), .any(…) and .map(…).collect() replace hand-written loops that count, test or build a list. The closure between the bars can borrow what is around it.
Vec::remove
v.remove(j) takes element j out and shifts every later one left: O(n) per call, which is why the tree wins for the Josephus permutation.
assert! and size_of
assert! turns a precondition, such as 1 ≤ i ≤ x.size, into a check that panics instead of looping on. std::mem::size_of::<Node>() prints the real size in bytes, so the cost of the extra field is visible.
