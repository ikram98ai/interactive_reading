3.1 · a historical perspective

One family of chips, many years long

The processor in a new laptop still understands programs written for a chip from 1978. Each new model added instructions, but it kept the old ones. That promise is called backward compatibility.

The book measures the growth by transistor count: a few tens of thousands, then millions, then more than a billion. The instructions a compiler emits got wider too, from 16-bit moves to 64-bit moves to packed floating-point adds.

The code panel is a few lines of Rust that rustc compiled today. fn starts a function, pub makes it visible outside its file, and #[no_mangle] is an attribute, a note to the compiler, asking it to keep the plain name so the listing says store16. u16 is a 2-byte unsigned integer, and p: &mut u16 is a mutable reference: an address Rust has checked is valid and not shared, so *p = v may write through it. In max32, if a > b { a } else { b } is an expression with a value, so it can be the function’s answer. In add8, [i32; 8] is an array of eight i32 values and for i in 0..8 runs i from 0 up to 7.

Try it: Tap a chip, or press Next chip. Then jump to 8086 and Haswell and read the one instruction each era added to the story. The code panel highlights where today’s 64-bit rustc output still uses it.

What the book says

The book lists Intel processors by the transistors it took to build them. The 8086 (1978, 29 K transistors) is a 16-bit microprocessor. Its 8088 variant, with an 8-bit external bus, was the heart of the original IBM personal computers. Those machines came with 32,768 bytes of memory. Addresses were 20 bits long (1,048,576 bytes addressable), and the operating system reserved 393,216 bytes, leaving a 655,360-byte space.

The i386 (1985, 275 K transistors) expanded the architecture to 32 bits and the flat addressing model used by Linux. It was the first machine in the series that could fully support a Unix operating system. The PentiumPro (1995, 5.5 M transistors) introduced the P6 microarchitecture and a class of conditional move instructions.

The Pentium 4E (2004, 125 M transistors) added EM64T, Intel’s implementation of a 64-bit extension to IA32 developed by Advanced Micro Devices (AMD), which the book calls x86-64. The Core i7 Haswell (2013, 1.4 G transistors) extended AVX to AVX2. A program compiled for an earlier chip in this line still runs.

3.2 · compiling into machine code

One command, four workers

You type one line. Four programs run in a row, and only the last one writes the file the processor can run.

The book’s gcc runs four separate programs. Rust’s rustc is a driver too, with a different crew: there is no preprocessor, the front end checks the types and the borrows, LLVM (the code generator inside rustc) writes the assembly and the object file itself, and then rustc hands the pieces to a linker.

The book asks gcc for -Og so the assembly stays close to the C. This page asks rustc for -C opt-level=1. At the default, 0, rustc stores values to the stack and loads them back (multstore’s dest makes that round trip), so listings get longer; levels 2 and 3 may unroll loops and switch to vector instructions until the shape is hard to recognize. Where a scene needs another level, its code panel says so.

Try it: Press Step and watch the result travel from one worker to the next. Reset puts the line back at the start. The code panel highlights the worker that just ran.

What the book says

gcc is a compiler driver. For a command such as gcc -Og -o p p1.c p2.c it runs the preprocessor (cpp), the compiler (cc1), the assembler (as), and the linker (ld). The preprocessor handles directives that begin with #. The compiler writes assembly. The assembler writes relocatable object code. The linker merges the object files and library code and fills in addresses.

The book generates code with gcc -Og. At this level the generated code follows the structure of the original C. Optimization levels -O1 and -O2 can transform the code so thoroughly that the mapping back to the source is hard to follow.

The finished file is what the processor runs. Everything before it is a tool for people, or a file the next tool still has to finish.

3.2.1 · machine-level code

A contract the hardware must keep

The chip may overlap work inside, but the program is allowed to pretend that one instruction finishes before the next one starts. That pretend-machine is the instruction set architecture.

The state a programmer does not usually see is small: a program counter, sixteen registers, a few condition codes, and a giant array of bytes called memory.

The code panel is one line of Rust, *x += y, and the single instruction rustc made from it. That one instruction uses all four pieces of state.

Try it: Press Step to fetch, read the registers, read memory, and write the sum. Reset returns to the idle machine. The highlighted line is the instruction being carried out.

What the book says

The instruction set architecture defines the processor state, the format of the instructions, and the effect of each instruction. The hardware may execute parts of several instructions at once, but it must produce the same results as a processor that completes one instruction before starting the next.

The visible state is the program counter (called %rip on x86-64), a register file of 16 named locations, condition codes that record recent arithmetic, and memory. Memory is a large byte-addressable array. Virtual addresses give each program its own view of that array.

Current 64-bit machines can use up to 256 terabytes (2^48 bytes) of memory, and could be extended toward 16 exabytes (2^64 bytes). A 32-bit machine can only make use of around 4 gigabytes (2^32 bytes).

The assembly listing is for people. The file the assembler writes is a string of bytes. Fourteen of them are the whole function.

A tool called a disassembler reads those bytes backward and prints something that looks like assembly again. After the linker runs, four of the bytes change: the call finally learns how far to jump.

3.2.3 · notes on formatting

Two spellings of the same instruction

rustc’s assembly and the book’s listings both use ATT format: the source is written first, registers wear a %, and a letter at the end of the instruction says how many bytes move. LLVM even adds the letter where the book leaves it off, writing callq and retq.

Intel’s manuals write the destination first, and they do not put a % on the register. It is the same instruction. Only the spelling changed.

Try it: Use the switch for Annotated, Raw .s, and Intel. Press Show the call while you are on the annotated listing. The code panel is the file that switch selected.

What the book says

The book shows assembly in ATT format, the form produced by gcc. A register name is prefixed by %, and an immediate is prefixed by $. The last letter of many instruction names is a size: b, w, l, or q. The source operand is written before the destination.

The raw output of gcc -Og -S also contains assembler directives, lines that begin with a period. The book’s annotated listings omit those and add a comment on each instruction.

gcc -Og -S -masm=intel asks for Intel format. The operands are reversed, the % signs disappear, and the size is written differently. The book uses ATT unless it says otherwise.

3.3 · data formats

How many bytes, and which letter

Every type the compiler moves has a size in bytes, and the instruction name grows a letter to match: b, w, l, or q. Rust writes the size into the type’s name: i32 is a 32-bit (4-byte) signed integer, u8 is an unsigned byte, and f64 is an 8-byte floating-point number. In put_ref, 'a is a lifetime: a name that tells the compiler the reference v must stay valid as long as the reference stored through p.

One letter is a trick. On integer instructions, l means 4 bytes. On floating-point instructions, l means an 8-byte double. The rest of the instruction tells you which meaning you are looking at.

Try it: Press Next type, or tap a row, or press f64. The bar is the width. The code panel highlights the move that carries that type.

What the book says

Figure 3.1 gives the sizes used by gcc on x86-64. char is 1 byte (suffix b). short is 2 bytes, which Intel calls a word (suffix w). int is 4 bytes, a double word (suffix l). long and any pointer are 8 bytes, a quad word (suffix q).

float is 4 bytes, moved by instructions with suffix s. double is 8 bytes, moved by instructions with suffix l. The suffix l also means a 4-byte integer on instructions such as movl, but the floating-point forms are separate instructions, so the two meanings do not collide.

Most instructions that move or compute on these sizes encode the size in the name. A pointer is an address, 8 bytes on this machine, moved with movq.

3.4 · the register file

Sixteen slots, each with more than one name

The processor keeps sixteen 64-bit slots close at hand. %rax is the same slot as %eax, %ax, and %al. The short names mean “only the low part.”

A 4-byte write is special: it stores the new bytes and clears the top half. A 1-byte or 2-byte write leaves the other bytes alone. That is why there is no instruction that zero-extends a 4-byte move. movl already did it.

The code panel shows three tiny Rust functions. x as u32 is a cast: it keeps the low 4 bytes of x. !0xffff flips every bit of 0xffff, so x & !0xffff clears the low 2 bytes. A name that starts with _, like _x, tells Rust the argument is unused on purpose.

Try it: Tap a register name to see its four names and its job. Then press Write 4 bytes, Write 2 bytes, and Write 8 bytes. Each runs one of the Rust functions on the slot you picked; the eight boxes are its bytes, high byte on the left, and the ones just written turn green.

What the book says

x86-64 has 16 general-purpose registers holding 64 bits each. The names %rax through %rsp are the historic ones, and %r8 through %r15 were added with the 64-bit extension. Each register also has names for its low 32, 16, and 8 bits.

Writing the 32-bit form, such as movl, sets the low 4 bytes and forces the high 4 bytes to 0. Writing the 8-bit or 16-bit form leaves the remaining bytes unchanged. There is no movzlq, because movl already zero-extends into the 64-bit register.

Some names have fixed jobs in the calling convention: %rsp is the stack pointer, %rax carries a return value, and the argument registers are assigned in a set order. The picture’s role labels follow that convention.

3.4.1 · operand specifiers

Where an instruction is allowed to look

An instruction can take a value from a register, from a constant written in the instruction itself, or from memory. Memory is named with a little formula: a number, plus a register, plus another register times 1, 2, 4, or 8.

Practice Problem 3.1 is that formula on a tiny memory. %rax holds 0x100, so (%rax) means “the byte at 0x100,” not the number 0x100.

The code panel shows where rustc used each form. struct Pair { pub a: i64, pub b: i64 } defines a type with two named 8-byte fields, and p.b reads the second one. &i64, without mut, is a shared reference: reading only. [i32; 64] is an array of 64 i32 values, and usize is the unsigned integer Rust uses for indexes, 8 bytes on this machine. Rust checks every array index, but i & 63 can never pass 63, so the compiler drops the check.

Try it: Press the operand buttons. The lit box is the place that was read, and the code panel highlights the line where rustc used the same form. Start from (%rax), then try $0x108 and 0xFC(,%rcx,4).

What the book says

The three kinds of operands are immediate (a constant, written with $), register, and memory. A memory operand has the general form Imm(rb, ri, s): the effective address is Imm + R[rb] + R[ri] × s, where the scale s is 1, 2, 4, or 8. Any of those pieces except the scale may be omitted.

Practice Problem 3.1 stores 0xFF, 0xAB, 0x13, and 0x11 at addresses 0x100, 0x104, 0x108, and 0x10C. %rax holds 0x100, %rcx holds 1, and %rdx holds 3. Absolute address 0x104 reads 0xAB. The immediate $0x108 is the number itself, not a load.

9(%rax,%rdx) is 9 + 0x100 + 3 = 0x10C. 260(%rcx,%rdx) is 264, which is 0x108. 0xFC(,%rcx,4) is 0xFC + 4 = 0x100. (%rax,%rdx,4) is 0x100 + 12 = 0x10C.

3.4.2 · data movement

A move may touch memory once

movq can copy a constant into a register, a register into a register, a register into memory, or memory into a register. It cannot copy memory straight into memory.

The width letters matter. movl writes four bytes and clears the top of the register. movb writes one byte and leaves the other seven exactly as they were.

Try it: On legal moves, set the source and the destination to memory. Then switch to width and press movl $0xaabbccdd and movb $0x7f. The code panel marks the line that matches.

What the book says

The data-movement instruction movq allows an immediate, a register, or one memory operand. Both operands cannot be memory. A copy from memory to memory is done through a register.

movl stores 4 bytes and sets the upper 4 bytes of a 64-bit register to 0. movb and movw update only the bytes they name. movzbq zero-extends a byte into a quad word, and movsbq sign-extends one.

The width picture starts from the bit pattern 0x1122334455667788. After movl of 0xaabbccdd the register holds 0x00000000aabbccdd. After a one-byte write, only the low byte has changed.

3.4.3 · an example

Swap, and hand back the old value

Kenji’s box holds 4. Lucia wants to put 3 in the box and keep the old 4. One function does both jobs.

The pointer arrives in %rdi and the new value arrives in %rsi. The function reads through the pointer, writes the new value through the same pointer, and leaves the old value in %rax, which is how a function returns a number.

In the Rust, xp: &mut i64 is that pointer as a mutable reference. The last line, x with no semicolon, is the value the function hands back. (The standard library’s std::mem::replace(xp, y) does this whole job in one call.)

Try it: Press Step three times. The arrows are the loads and stores. Reset puts 4 back in the box. The code panel has the Rust and rustc’s assembly, the same three instructions the book’s gcc made; the highlighted line is the step you are on.

What the book says

The book’s exchange takes a pointer xp and a value y. It saves the value xp points at, stores y through xp, and returns the old value. With a = 4 and b = 3, a call that passes the address of a and the value of b leaves a equal to 3 and returns 4, which the caller stores in b.

The compiled form is movq (%rdi), %rax, then movq %rsi, (%rdi), then ret. The first instruction both reads memory and sets the return value. No extra register is required.

A pointer in this code is just an address sitting in a register. The C type says what size to read. The machine sees the address.

3.4.4 · push and pop

Two short instructions for the stack

The stack is a pile of 8-byte slots. The top is the lowest address. %rsp points at that top.

pushq subtracts 8 from %rsp and then stores a register there. popq reads that slot and adds 8 back. You could write the same work as a subtract plus a move, but pushq fits in one byte. After popq, the old value is still sitting in memory until something else writes there.

rustc’s multstore from 3.2.2 is the example: it borrows %rbx, so it pushes the caller’s value first and pops it back at the end.

Try it: Press Step three times: push the caller’s 0x123, reuse %rbx, then pop 0x123 back. Reset restores %rsp to 0x108. The lower box is the top of the stack.

What the book says

Figure 3.9 starts with %rsp equal to 0x108 and %rax equal to 0x123. pushq %rax sets %rsp to 0x100 and writes 0x123 at that address. popq %rdx reads 0x123 into %rdx and sets %rsp back to 0x108.

The value 0x123 remains at address 0x100 after the pop. Popping does not erase memory. It only moves the stack pointer.

pushq is encoded in 1 byte. The two-instruction form subq $8, %rsp and movq %rax, (%rsp) takes 8 bytes. The machine treats them as the same state change.

3.5.1 · load effective address

An add that pretends to be an address

leaq uses the memory formula but does not read memory. It writes the address it computed into a register. Compilers use that as a cheap multiply-and-add.

(%rdi,%rdi,4) is x + 4x when %rdi holds x. That is 5x, and no memory was touched; rustc then adds the 7 with an addq. A longer recipe, three leaq instructions, computes x + 4y + 12z with no multiply instruction at all.

In Rust, 5 * x + 7 on an i64 is checked for overflow when overflow checks are on, which rustc does by default only at opt-level 0: there an overflow stops the program with a panic, a deliberate crash with a message. At opt-level 1 the checks are off, the result wraps around, and a plain leaq is allowed. Overflow is never undefined behaviour in Rust.

Try it: Move the sliders, or press x = 3. Switch to scale() to see the three-instruction recipe. The code panel shows the leaq lines and the value they just wrote.

What the book says

leaq computes an effective address and stores it in a register. The destination must be a register. The instruction does not load from memory, and it does not set the condition codes.

The book’s example leaq 7(%rdx,%rdx,4), %rax computes 5x + 7 when %rdx holds x. Scale factors of 1, 2, 4, and 8 are the ones the machine can do in the address formula.

The function scale computes x + 4y + 12z with three leaq instructions: one for x + 4y, one for 3z, and one that adds four times that 3z. The compiler prefers this to an integer multiply when the factors are small.

3.5.2 · unary and binary

The second operand is the one that changes

In ATT spelling, subq %rsi, %rax means “subtract %rsi from %rax,” not the other way around. The destination is written last. That is what rustc makes from x - y, after copying x into %rax.

A unary instruction has one operand, and that operand is both the source and the destination. incq (%rdi) adds one to the value in memory at the address in %rdi: rustc’s whole translation of *count += 1. Two memory operands are still forbidden.

Try it: Press Run subq, then incq (%rdi). Reset puts the numbers back. The code panel is the instruction that just ran.

What the book says

Binary operations such as addq, subq, and xorq read the source and the destination and write the destination. In ATT format the source is first. subq %rax, %rdx performs %rdx ← %rdx − %rax.

Unary operations such as incq and decq update their only operand. That operand may be a register or a memory location. It may not be two memory locations, because no instruction here has two memory operands.

incq and decq update the other condition codes but leave the carry flag unchanged. The picture’s memory cell starts at 41 so the increment is easy to see.

3.5.3 · shift operations

The bit that falls off, and the bit that comes in

A left shift brings a 0 in on the right. A right shift has a choice: shr brings in a 0, and sar copies the sign bit so a negative number stays negative.

The shift amount is either a constant or the register %cl. The book says an 8-bit shift uses only the low 3 bits of %cl. The chip actually keeps the low 5 bits for 8-, 16- and 32-bit shifts and 6 bits for 64-bit ones, so %cl equal to 0xFF means “shift by 31,” and a byte shifted that far is 0.

In Rust the type picks the instruction: >> on a signed type such as i8 is arithmetic (sar), on an unsigned type such as u8 logical (shr). A plain x << n with n of 8 or more is an overflow, which panics when overflow checks are on. x.wrapping_shl(n) is a method, a function called with a dot, that promises to shift by n mod 8 for a u8, so rustc adds an and to get there.

Try it: Press sal 1, sar 1, and shr 1. Then press sal by %cl to use the masked amount. Reset restores 11000001. The code panel names the instruction.

What the book says

sal and shl are the same left shift. sar is an arithmetic right shift: the sign bit is copied into the vacated bit. shr is a logical right shift: a 0 enters from the left.

The shift amount is an immediate or the single register %cl. The processor masks the amount to the low 3 bits for an 8-bit shift, the low 4 bits for a 16-bit shift, the low 5 bits for a 32-bit shift, and the low 6 bits for a 64-bit shift. So salb with %cl equal to 0xFF shifts by 7.

The picture is an 8-bit illustration, so a carry is easy to see. Its masks are not the book’s: Intel’s manual says the count is masked to 5 bits (6 bits for a 64-bit operand) whatever the data size, so salb with %cl equal to 0xFF shifts by 31. The book’s 3-bit and 4-bit rules for 8-bit and 16-bit shifts are an error in the book.

3.5.4 · discussion

Most arithmetic does not care about signed

Add, subtract, and, and xor do the same thing to the bits whether you think of them as signed or unsigned. The right shift is the exception, which is why it has two instructions.

The book’s arith example is a short straight-line function. In rustc’s version: an xor, a shift and a leaq that together make 48z, a mask, and a subtract. leaq is doing arithmetic again, and it still does not touch the condition codes. 3.5.5 · special arithmetic

A product that needs two registers

Multiplying two 64-bit numbers can take 128 bits. mulq writes that full product in %rdx and %rax together. The book calls those 16 bytes an oct word. Rust has a 16-byte integer type, u128, so a as u128 * b as u128 asks for exactly that product.

Division needs the same pair as the dividend. idivq writes the quotient in %rax and the remainder in %rdx. If you still needed what used to be in %rdx, you have to save it first. The remainder takes the sign of the dividend. Before it divides, Rust checks two cases: dividing by zero panics, and so does i64::MIN / −1, whose answer does not fit in an i64. A function can hand back two values as a tuple, (i64, i64).

Try it: On mulq, press Show product. Switch to idivq and press Step divide, then y = 0. The code panel is the instruction that just wrote %rdx and %rax.

What the book says

The one-operand mulq multiplies %rax by its operand and writes the full 128-bit product in %rdx:%rax. The two-operand imulq keeps only the low 64 bits, which is what a C multiplication of 64-bit values does.

Signed division uses cqto to sign-extend %rax into %rdx, then idivq. The quotient is left in %rax and the remainder in %rdx. The remainder has the sign of the dividend.

The book’s remdiv receives the destination pointer qp in %rdx. Because idivq will overwrite %rdx, the function first copies qp to %r8. The picture divides −7 by 2: the quotient is −3 and the remainder is −1, and −3 × 2 + (−1) = −7.

3.6.1 · condition codes

Four lamps the last operation left on

After an add, the processor does not only store the sum. It also sets four flags. CF means the unsigned sum did not fit. ZF means the stored bits are all zero. SF means the top bit is 1, so the result looks negative. OF means the signed sum did not fit.

leaq does not touch the lamps. inc and dec update the others but leave CF as it was. This picture uses 4-bit numbers so a carry is easy to see; the real flags watch 8, 16, 32, or 64 bits.

Rust lets you read two of the lamps. a.overflowing_add(b) returns a pair: the wrapped sum and a bool that says whether it overflowed. For a u64 that bool is the carry flag; for an i64 it is the overflow flag.

Try it: Drag the two sliders, or press 9 + 12 and 8 + 8. Then press leaq. The code panel is the operation whose flags you are looking at.

What the book says

The condition codes include CF, ZF, SF, and OF. CF is the carry out of unsigned addition. ZF is set when the result is zero. SF is a copy of the most significant bit. OF is set when signed overflow occurs, which is not the same event as unsigned carry.

Most arithmetic instructions set the codes. leaq does not. inc and dec set ZF, SF, and OF but leave CF unchanged, which matters when a loop is using CF for something else.

The four-bit adder is an illustration of those rules, not a figure from the book. 9 + 12 needs five bits unsigned and also leaves the signed 4-bit range. 8 + 8 also carries out (16 needs five bits) and leaves 0000 behind, so ZF is set too, and as signed values −8 + −8 = −16 leaves the signed range.

3.7.6 · recursive procedures

Each call gets its own copy of n

A recursive function calls itself. Each call needs its own n. At opt-level 0, rustc keeps each call’s n in that call’s own stack frame, at 8(%rsp).

3.9.3 · data alignment

3.10.1 · understanding pointers

The type lives in the compiler

A pointer’s value is an address. Its type, the story about what sits at that address, is used by the compiler and then thrown away. The machine code does not store the type.

The book’s C pointers are raw pointers in Rust, written *mut i32: addresses the compiler does not check. What the book says

The book treats a pointer as an address, and the pointer type as a C abstraction that says how to interpret the object at that address. Different pointer types can hold the same address bits.

3.10.3 · out-of-bounds memory references and buffer overflow

A copy that does not know when to stop

The book’s echo stores a line in an 8-byte array with C’s gets, which keeps copying until it sees a newline and never asks how big the array is. C does not check array bounds, so the extra characters land on whatever sits above the array, including the return address.

Safe Rust cannot do that: every index is checked. To show the danger we have to step outside with unsafe. copy_unchecked is an unsafe fn: its /// # Safety section says src must fit in buf’s 8 bytes, so main may call it only inside unsafe { … }. It writes through a raw pointer with no length attached, and LLVM turned its loop into one memcpy of the whole input. rustc made a 24-byte frame with subq $24, %rsp and put buf at 8(%rsp). Characters 0 through 7 land in buf; the return address sits 16 bytes above the start of buf, so character 16 starts to overwrite it.

Rust has no gets. echo.rs starts with use std::io::stdin, which brings the standard library’s stdin into scope. read_line puts the line in a String, which grows to fit, and .unwrap() stops the program if reading fails. The for loop walks the bytes with their positions (enumerate), and buf[i] is checked: the ninth byte stops the program with index out of bounds: the len is 8 but the index is 8, a panic, before a single byte lands outside buf. &buf[..n] is the first n bytes, String::from_utf8_lossy turns them into text, and println! prints it. In echo_unsafe.rs, std::env::args().nth(1) is the first word typed after the program’s name (unwrap_or_default gives an empty string if there is none), and black_box(&mut buf) makes LLVM keep buf in memory, in this frame, instead of optimizing it away.

The unsafe { … } around the call is main’s promise that the input fits, and the block inside copy_unchecked relies on it. The compiler cannot check that promise, and a long input breaks it: then the program’s behaviour is undefined. That is the lesson: in Rust an overflow like the book’s can only happen inside code marked unsafe.

Try it: Press Type a char until the return address changes, or press Overwrite return. Reset empties the buffer. The code panel marks the memcpy; the echo.rs tab is the safe version and its real panic.

What the book says

C does not check array bounds. The book’s echo allocates an 8-byte char array, buf, and calls gets. The compiled form subtracts 24 from %rsp, so the return address is 24 bytes above buf.

Characters 0 through 7 stay inside buf. The book’s figure marks bytes 8 through 23 as unused padding and bytes 24 through 31 as the return address. A longer string overwrites the return address, and ret transfers control to that forged address.

The same pattern is why strcpy, strcat, and sprintf are dangerous when the source can be longer than the destination. The picture types the letter A so the overrun is visible; the book’s attack string would be exploit bytes plus a forged return address.

3.10.4 · thwarting buffer overflow attacks

Three ways to spoil the trick

The book’s fix in C is fgets, which takes a limit, so the copy can be stopped. Rust’s checked indexing plays that part in echo.rs. Three other defenses assume someone still overflowed the buffer, for instance with unsafe code.

A canary is a random value stored between the buffer and the return address and checked before ret. Stable rustc does not add one: stack protection exists only on the nightly compiler, as -Z stack-protector. Stack randomization moves the stack so a guessed address is probably wrong; rustc builds position-independent executables, so on Linux the code moves too. The NX bit lets the stack be written and forbids executing it, so bytes that landed there cannot run; our binary’s stack is marked RW, not executable. aslr.rs prints two addresses: {:p} formats an address, &local is on the stack, and main as fn() turns main into a function pointer, whose value is where its code was loaded.

Try it: Press Type until the write passes the buffer. Switch Canary, ASLR, and NX and type again. Reset clears the write but leaves the switches. The code panel shows our real checks of the binary.

What the book says

The book recommends a bounded copy such as fgets in place of gets. Three further defenses remain useful when a program still has an overflow.

A stack protector stores a canary between the buffer and the return address, loaded from %fs:40, and checks it before returning. gcc skipped that guard in the book’s demo only when asked with -fno-stack-protector. Stack randomization, a form of ASLR, moves stack addresses. On the book’s 32-bit measurements the range was about 2^23. A 256-byte nop sled against that range still leaves 2^15, or 32,768, guesses. A 64-bit system’s range is nearly 2^32.

The processor’s NX bit, which AMD introduced, marks memory not executable. The stack can stay readable and writable while the processor refuses to run instructions stored there.

3.10.5 · supporting variable-size stack frames

When the frame size is not known yet

Most frames are a fixed size, and the compiler never needs a frame pointer. The book’s example is a C function that puts an array whose length is an argument on the stack: %rsp moves by an amount known only at run time, and locals still need a stable address, so gcc keeps one in %rbp.

Stable Rust has no such arrays: an array’s length is fixed when the program is compiled, and a run-time length means a Vec, whose elements live on the heap, so the frame keeps its size. Rust still meets the same problem another way. struct Line(pub [u8; 64]) is a tuple struct, whose one field has no name, so l.0 is that field. #[repr(align(64))] asks for a type that starts on a 64-byte boundary; the caller’s %rsp can end anywhere, so rustc rounds %rsp down, and the frame’s size is again known only at run time. It saves the old %rbp, copies %rsp into %rbp, and restores both at the end.

Try it: Drag k, which moves the caller’s %rsp by 8 bytes at a time, or press k = 4. Watch the gap and the frame size change while %rbp stays the fixed point. The code panel marks the rounding and the restore.

What the book says

When a frame’s size depends on a runtime value, gcc uses %rbp as a frame pointer. The prologue is pushq %rbp and movq %rsp, %rbp. A local such as i is addressed from %rbp, at −8(%rbp), so it stays put while %rsp moves.

The book’s vframe allocates an array of n longs. It computes the byte count with leaq 22(,%rdi,8), %rax and andq $-16, %rax, which rounds up to a multiple of 16, then subtracts that from %rsp.

3.11.1 · floating-point movement and conversion

Floats live in a different set of registers

Floating-point values do not use %rax. They use the XMM registers. A double occupies the low 8 bytes of a 16-byte XMM register.

The book’s gcc targets AVX, so its instruction names start with v. rustc’s default target uses the older SSE2 forms that every x86-64 chip has: movsd copies one double between memory and a register, movaps copies a whole XMM register, cvtsi2sd turns an integer into a double, and cvttsd2si turns a double back into an integer by truncating toward zero.

In Rust, x as i64 on an f64 is defined for every input: a value too big for an i64 becomes the nearest limit, and NaN, “not a number”, becomes 0. So rustc adds two checks after the conversion.

Try it: Press Step through the load, the register copy, and the two conversions. Reset clears the XMM registers. The code panel highlights the instruction that just wrote.

What the book says

Scalar floating-point data lives in the XMM registers. movss and movsd (and the AVX forms vmovss and vmovsd) move a single float or double between memory and the low bytes of an XMM register. The memory operand need not be aligned, though alignment is recommended.

To copy between two XMM registers, gcc uses vmovaps for single precision and vmovapd for double precision, moving the whole register.

vcvtsi2sd converts an integer to a double. vcvttsd2si converts a double to an integer, truncating toward zero. The picture turns the integer 7 into the double 7.0, then the double 2.9 into the integer 2.

3.11.2 · floating-point code in a procedure

Two counting systems at once

Integer arguments and floating arguments are numbered separately. The next integer goes to the next integer register. The next float goes to the next XMM register.

That is why f1(i32, f64, i64) and f2(f64, i32, i64) put the f64 in %xmm0 and the two integers in %edi and %rsi either way. A floating result comes back in %xmm0. Every XMM register is caller-saved.

3.11.6 · floating-point comparison operations

A comparison that can fail on both sides

ucomisd compares two doubles and sets ZF, CF, and the parity flag PF. Ordinary comparisons set ZF and CF. PF is the extra lamp, and it comes on when either value is not a number.

When PF is on, <, <=, >, >= and == are all false, in Rust just as in the book’s C, and != is true. That includes x == x: a NaN is not equal to itself. The unordered case is how the machine reports a NaN.

rustc found a shortcut for x < y: it compares y with x and uses seta, which is false whenever ZF or CF is set. A NaN sets both, so the answer is false without a separate PF test.

3.11.7 · observations

Same idea as integer code, wider registers

Floating-point machine code looks familiar: values sit in registers, and an instruction does one operation. The registers are XMM or YMM, and there are many more instruction names.

The extra speed the book points at is packed arithmetic. One instruction can add two doubles in an XMM register, or four in a YMM register. A scalar add does them one at a time. rustc uses packed adds by itself when it can: at opt-level 3 it turned a four-element loop into two addpd, and with -C target-cpu=x86-64-v3 into one vaddpd on a YMM register.

Packed instructions apply one operation to several values at once. An XMM register holds two doubles. A YMM register, introduced with AVX on Sandy Bridge and extended by AVX2 on Haswell, holds four.

Words to know

The chapter’s grown-up words, in plain language.

ISA
The contract: registers, instruction formats, and the result of each instruction, as if they ran one at a time.
PC / %rip
The program counter. It holds the address of the next instruction.
word, dword, qword
Intel’s names for 2, 4, and 8 bytes. An i64 and a pointer on this machine are quad words.
immediate
A constant written inside the instruction, marked with $ in ATT format.
effective address
The address a memory operand computes: a constant, plus a base, plus an index times 1, 2, 4, or 8.
condition codes
CF, ZF, SF, and OF: carry, zero, sign, and overflow, left behind by arithmetic.
PC-relative
A jump that stores a distance from the next instruction, so the code can be moved without rewriting the distance.
cmov
A move that happens only when a condition is true. Both values are computed; there is no guess.
stack frame
The slice of stack one call uses: return address, saved registers, locals, and outgoing arguments.
callee-saved
A register the called function must restore. On this machine: %rbx, %rbp, and %r12 through %r15.
jump table
A list of code addresses (in rustc’s, distances from the table to the code). One indirect jump selects a match arm or switch case.
row-major
A grid stored one row at a time, so a[i][j] is at the start plus the element size times (columns × i + j).
alignment
The rule that a K-byte object wants an address that is a multiple of K. Compilers insert padding to get it.
bounds check
The compare-and-jump rustc puts before an index such as a[i], so an index past the end panics instead of reading a neighbour’s memory.
unsafe
A Rust block or function where the programmer, not the compiler, promises the rules hold: needed to dereference raw pointers or read union fields.
#[repr(C)]
An attribute that asks rustc to lay a struct out in C’s order with C’s padding, as the book describes.
canary
A random value parked between a buffer and the return address, checked before the function returns.
NX
A bit that marks memory not executable, so bytes written onto the stack cannot be run.
XMM / YMM
Registers for floating-point values. An XMM holds two doubles; a YMM holds four.
