Separate notebooks of code become one program. The glue can be applied when you compile, when you load, or while the program is already running.

“Linking is the process of collecting and combining various pieces of code and data into a single file that can be loaded (copied) into memory and executed.” — Bryant & O’Hallaron

Rust setup: what the listings assume

The book compiles C with gcc into ELF object files. This page’s listings are Rust, and linking is about raw names and addresses, so they use a few tools everyday Rust rarely needs. *const i32 and *mut i32 are raw pointers: plain addresses, like C’s pointers, that Rust’s borrow checker (the part of the compiler that tracks who may use a value, and when) does not follow. &raw const X takes one. static is a global value with a fixed address; static mut is one any code may change, so touching it needs unsafe { }, a block where you, not the compiler, promise the code is right. as converts one number or pointer type to another, c"…" is a C string, ending in a zero byte, and println! prints a line (the ! marks a macro, code that writes code). An unsafe fn is a function whose caller must keep a promise the compiler cannot check, and the /// doc comment above it has a # Safety section that spells that promise out. Everyday Rust would use Vec (a growable array), references, and safe functions instead.

7.1 · compiler drivers

A receptionist who calls the specialists

In the book, Mei types one line, gcc -Og -o prog main.c sum.c, and gcc quietly runs four programs: the C preprocessor, the compiler, the assembler, and the linker ld. A program that only calls other programs is a compiler driver, a receptionist.

Our twins are main.rs and sum.rs. rustc is a driver too, with fewer visits. There is no separate preprocessor: rustc’s own macro expander handles things like println!. rustc checks the program and hands LLVM a low-level form of it called LLVM IR, close to assembly with types added, and LLVM writes the machine code straight into an object file, main.o. No assembler program runs, though --emit=asm shows the same code as text.

For the last step rustc phones the system’s C driver, cc, with a long argument list: our objects, the standard library’s archives, libc, and -fuse-ld=lld. So the linker that actually runs is rust-lld, the copy of LLVM’s linker that ships with Rust. Since Rust 1.90 it is the default on x86-64 Linux.

The two files meet only in the linker. So main.rs declares sum in an extern "C" block, a promise that some other object file defines it, and calls it inside unsafe { }, because the compiler cannot check another file’s code. ARRAY.as_ptr() hands sum a raw pointer to the array’s first element, the way C passes an array. #![no_main] tells rustc not to write its own main: this file defines the plain C-style main itself, as the book’s does. 7.9 shows what rustc writes when you leave it out. Typing ./prog is a later trip, the loader’s.

Try it: Press Step. The real commands under the picture light up as each program works. The last line is prog’s exit status, 3, the sum of 1 and 2. main.rs and sum.rs are one tab away.

What the book says

Figure 7.1 is the running example. main.c declares sum, defines a global two-element array holding 1 and 2, and returns the sum of that array. sum.c adds the n elements. The discussion is an x86-64 system running Linux and using ELF. Concepts are the same on other systems; details vary.

The driver command is gcc -Og -o prog main.c sum.c. It runs cpp to make /tmp/main.i, then cc1 /tmp/main.i -Og -o /tmp/main.s, then as -o /tmp/main.o /tmp/main.s, the same path for sum.o, then ld -o prog with system object files plus the two .o files. In some versions of gcc the preprocessor is integrated into the driver. gcc -v shows the real argument lists.

./prog is not a built-in shell command, so the shell invokes the loader, which copies the code and data into memory and transfers control to the beginning of the program.

7.2 · static linking

Two jobs, then the glue

Amara compiled main.rs on Monday and sum.rs on Tuesday, each with rustc --emit=obj, which stops before linking. Each .o file is a stack of sections, named runs of bytes. rustc gives every function and every static its own little section: main’s instructions are in .text.main, and ARRAY’s eight bytes are in .rodata.array, read-only data: the Rust Reference lets a static that nothing can change go in read-only memory. The static linker reads those stacks and writes one executable.

Job one is symbol resolution: every name that is used must be tied to exactly one definition. Job two is relocation: the sections were born at address 0, so the linker slides them to real addresses and rewrites the blanks LLVM left in the code.

The linker is not a second compiler. It concatenates blocks of bytes, picks run-time homes, and patches a few numbers. rustc and LLVM already did the thinking.

Try it: Press Step. First the name sum finds its definition. Then the blocks slide into prog and pick up the addresses rust-lld really gave them.

What the book says

Static linkers such as the Linux ld program take relocatable object files and command-line arguments and generate a fully linked executable that can be loaded and run. Instructions are in one section, initialized global variables in another, uninitialized variables in a third.

Symbol resolution associates each symbol reference with exactly one symbol definition. A symbol is a function, a global variable, or a static variable. Relocation then gives each definition a memory location and modifies references so they point there. “The linker blindly performs these relocations using detailed instructions, generated by the assembler, called relocation entries.”

“Object files are merely collections of blocks of bytes.” A linker concatenates blocks, decides on run-time locations, and modifies locations inside the code and data. “Linkers have minimal understanding of the target machine.”

7.3 · object files

Three kinds of package

Not every binary file is ready to run. A relocatable file can still be combined with others at compile time. An executable can be copied into memory and started. A shared object can be loaded and linked later, at load time or run time.

Compilers and assemblers make the relocatable ones, including shared objects. Linkers make executables. On disk the bytes are an object file; the same sequence of bytes is an object module. The book uses both names.

The recipe for arranging those bytes has changed names over the years: early Unix a.out, Windows PE, Mac OS-X Mach-O, and ELF on modern x86-64 Linux. The ideas underneath are the same.

Rust makes all three. rustc --emit=obj writes a relocatable file, plain rustc writes an executable, and rustc --crate-type=cdylib writes a shared library that programs in other languages can load. Rust also has a package of its own, the rlib: an ar archive holding the crate’s object files plus a lib.rmeta file, the metadata rustc reads when another crate uses this one. (A crate is Rust’s unit of compiling and linking: one library or one program.)

Try it: Tap a package. The picture shows who builds it and who consumes it. The listing underneath is the rustc command for that form and what file said about the result.

What the book says

A relocatable object file contains binary code and data that can be combined with other relocatable object files at compile time. An executable object file can be copied directly into memory and executed. A shared object file is a special relocatable object file that can be loaded and linked dynamically, at either load time or run time.

Compilers and assemblers generate relocatable object files, including shared object files. Linkers generate executable object files. An object module is a sequence of bytes; an object file is that module stored on disk. The book uses the terms interchangeably.

The first Unix systems from Bell Labs used the a.out format. Executables are still called a.out files. Windows uses the Portable Executable (PE) format. Mac OS-X uses the Mach-O format. Modern x86-64 Linux and Unix systems use ELF.

7.4 · relocatable object files

A sandwich with a label on each filling

Diego opens the main.o rustc made. Its first 16 bytes are 7f 45 4c 46 02 01 01 00…: the letters ELF, then 64-bit words, then little-endian bytes. The rest of the ELF header says “relocatable, x86-64,” and that the table of contents, 11 section headers of 64 bytes each, starts 528 bytes into the file. Between the header and that table are the fillings.

Instructions live in .text; rustc names each function’s piece after it, so main is in .text.main. Read-only data lives in .rodata, and that is where ARRAY went. A static mut with a nonzero starting value lives in .data. Zeros live in .bss, which is a trick: the file stores a size, not the zero bytes. Better save space. Names live in .symtab. Sticky notes for the linker live in .rela.text… and .rela.data…; x86-64 ELF always uses the rela kind, whose notes carry their own addend.

Compile with -g and debugging sections appear: in our main.o they are .debug_info, .debug_line, .debug_abbrev, .debug_str and .debug_aranges. .debug_line does the job of the book’s .line: it maps source lines to machine instructions (in ours, main.rs line 15 to main’s first byte). Without -g they are simply not in the file. .symtab is there either way, unless someone runs strip.

Try it: Tap a filling. The listing shows the line of Rust that lands there, or the real readelf row. Then press -g and watch the debugging sections show up.

What the book says

Figure 7.3: the ELF header begins with a 16-byte sequence that describes word size and byte ordering. The rest holds the header size, the object file type, the machine type, and the file offset, size, and number of entries in the section header table. Each section has a fixed-size entry in that table.

.text is compiled machine code. .rodata holds printf format strings and switch jump tables. .data holds initialized global and static variables. Local variables live on the stack and do not appear in .data or .bss. “This section occupies no actual space in the object file; it is merely a placeholder.” The name .bss comes from the IBM 704 “block started by symbol” directive, circa 1957. A mnemonic: “Better Save Space!”

.symtab is present unless removed with strip, and you do not need -g to get it. It has no local variables. .rel.text lists locations in .text to modify; calls to local functions usually need none. .rel.data covers initialized globals whose value is an address. .debug and .line exist only with -g. .strtab is the null-terminated strings those tables name.

7.5 · symbols and symbol tables

The roster is not the lockers

Every relocatable module has a roster of names. Some names it defines and is willing to share. Some names it uses but does not define — those are externals. Some names it marks static, so they stay inside the file. Those local linker symbols are not the same thing as a local variable. In C you ask for one with the word static. Rust flips C’s default: an item is private to its module unless you mark it pub, and in local.rs rustc made the private bump and HITS LOCAL rows.

Kenji’s swap and Lucia’s m are Practice Problem 7.1. buf is borrowed from Lucia. bufp0 starts as the address of buf. swap is a global function. temp lives on the stack (or in a register) and gets no row at all. In the book’s C, bufp1 has no starting value, so gcc parks it in COMMON. Rust will not leave a static without a value, so the twin starts bufp1 as a null pointer: all zero bytes, so rustc put it in .bss. #[link_name = "buf"] lets the Rust name BUF stand for the symbol buf.

If two functions in one C file each declare a static local named x (one that keeps its value between calls), the compiler cannot put either on the stack. gcc gives each a spot in .data or .bss and invents two roster names, x.1 and x.2. A Rust static inside a function is the same kind of thing, and rustc spells the whole path into the name: nm printed …7statics1f1X and …7statics1g1X, and nm -C reads them back as statics::f::X and statics::g::X.

Try it: Switch the three views. In the roster, tap a name from swap.o. temp stays off the list. In the third view, watch one spelling of X become two linker names.

What the book says

Three kinds of symbols in module m: global symbols defined by m (nonstatic C functions and global variables); externals referenced by m but defined elsewhere; and local symbols (static functions and globals). “It is good programming practice to protect your variables and functions with the static attribute wherever possible.” Local linker symbols are not local program variables. The .symtab has no nonstatic locals; those live on the stack.

Figure 7.4, Elf64_Symbol: name (string-table offset), 4-bit type and binding, section, value (section offset in a relocatable file, absolute address in an executable), size. Pseudosections that have no section-header entry: ABS (do not relocate), UNDEF (referenced here, defined elsewhere), COMMON (uninitialized, not yet allocated; value is alignment, size is the minimum). They exist only in relocatable files. Modern gcc: COMMON is uninitialized globals; .bss is uninitialized statics and globals or statics initialized to zero. That split exists because of the rules in Section 7.6.

7.6 · symbol resolution

A name the linker cannot find

Inside one file, resolution is easy. The compiler allows only one definition of each local symbol, and it gives static locals unique names. The linker just follows the roster.

A global is harder. If the compiler sees foo used but not defined, it shrugs and leaves a blank. The book’s linkerror.c compiles, then the linker searches every input module, finds no foo, and stops. The Rust twin, linkerror.rs, fails the same way: rustc compiles it, then rust-lld reports undefined symbol: foo, referenced by linkerror::main.

C++ and Java can have several functions with the same spelling and different arguments, so their compilers mangle each one into a unique linker name. rustc mangles every name too, unless no_mangle or export_name says otherwise, for a different reason: two modules or two crates may each have a bar, and the linker needs one string per item. rustc 1.100 uses Rust’s own v0 scheme. A v0 name starts with _R and writes each piece of the path as its length, then its letters: 6mangle, 3Foo, 3bar. The short code after Cs tells this build of crate mangle apart from any other crate with that name.

Try it: On the first view, press Link and read the real error under the listing. On the second, the local name resolves inside the file. On the third, press Mangle and see what nm printed for the two bars.

What the book says

The linker associates each reference with exactly one symbol definition from the symbol tables of its input relocatable object files. Local references are straightforward: one definition per local symbol per module, and unique names for static locals. For a global the compiler does not see defined, it assumes another module defines it, emits a symbol-table entry, and leaves the reference for the linker.

If no input module defines the symbol, the linker prints an error and terminates. gcc -Wall -Og -o linkerror linkerror.c compiles, then the linker reports undefined reference to foo from .text+0x7.

C++ and Java overloaded methods share a source name and differ in their parameter lists. The compiler encodes each method and parameter list into a unique linker name. That encoding is mangling; the inverse is demangling. Class Foo is encoded as 3Foo. Foo::bar(int, long) is encoded as bar__3Fooil.

7.6.1 · duplicate global names

One strong name quietly wins

In C, every global is stamped strong or weak at compile time. Functions and initialized globals are strong. Uninitialized globals are weak. The Linux linker then uses three rules. Two strongs with the same name: error. One strong and any number of weaks: keep the strong, say nothing. Several weaks: pick any of them. In the book, Omar’s file gives x the value 15213, Priya’s declares an x with no value and stores 15212 in it, and the program prints x = 15212. Priya wrote Omar’s variable, and nobody was told.

Rust closes most of these doors. (Each twin puts both files in one program as two mods, modules, so rustc sees them together.) A Rust static must have a value, so stable Rust has no way to write a weak one: Priya’s x does not compile. Two exported statics with one name are a compile error; the Rust Reference says no_mangle must be written unsafe for exactly this reason, because a plain name can collide with another.

Types make the C case nastier. Omar’s strong x is a 4-byte int, and Priya declares x as an 8-byte double. Storing minus zero writes 8 bytes and smears the neighbour y. A Rust module that reaches another module’s static by its path gets the real type, so that store is a type error. The way back to the book’s bug is an unsafe extern block, which the Reference compares to an unchecked import: declare x as an f64 there, link it against foo5.o, and the twin prints the book’s line. rust-lld put y 4 bytes after x, at 0x2512e4, and printed no warning at all.

Try it: Pick a pair and press Link. The listing is the Rust twin, and the black box is what rustc really printed. For the int/double pair, press again to watch the store write eight bytes across x and y.

What the book says

Functions and initialized global variables get strong symbols. Uninitialized global variables get weak symbols. Rule 1: multiple strong symbols with the same name are not allowed. Rule 2: one strong and multiple weaks, choose the strong. Rule 3: multiple weaks, choose any. foo1.c and bar1.c both define main and the link fails. foo2.c and bar2.c both define an initialized x of 15213, and the link fails the same way.

foo3.c defines a strong x of 15213 and calls f. bar3.c defines a weak x, and f sets it to 15212. gcc -o foobar3 foo3.c bar3.c gives no multiply-defined warning, and ./foobar3 prints x = 15212. Two weak definitions (foo4.c, bar4.c) are rule 3.

foo5.c defines int y as 15212 and int x as 15213. bar5.c declares a double x and assigns it minus zero. On x86-64/Linux a double is 8 bytes and an int is 4. The book’s addresses are x at 0x601020 and y at 0x601024, so the assignment overwrites both. The link warns that alignment 4 of x is smaller than 8, then ./foobar5 prints x = 0x0 y = 0x80000000. gcc -fno-common errors on multiply-defined globals. -Werror turns warnings into errors. A weak global is assigned to COMMON because the compiler cannot yet know which definition will win; a zero-initialized global is strong, so it can go in .bss.

7.6.2 · linking with static libraries

A shelf that lends only the books you name

ISO C has a huge box of functions: printf, strcpy, sin, and hundreds more. Putting every one of them into every program would waste disk and memory. On the book’s system libc.a is about 5 MB and libm.a is about 2 MB. Making the compiler invent the functions itself would mean a new compiler every time the library changed. Handing the programmer a directory of loose .o files means a long, fragile command line.

A static library is the compromise. Related .o files are packed into one archive (.a). At link time the linker copies only the members the program actually references.

Leila compiles addvec.rs and multvec.rs to objects and packs them with ar rcs libvector.a addvec.o multvec.o. Her main2.rs calls addvec only, and rustc main2.rs -L . -l static=vector links it. nm prog2c finds addvec and addcnt, and no multvec: that member stayed on the shelf.

Rust’s own libraries arrive the same way. The link line in 7.1 hands cc nineteen .rlib files, from libstd to libcompiler_builtins, and an rlib is an ar archive with one object file per codegen unit (the pieces rustc splits a crate into, so LLVM can work on them in parallel). And when C code wants Rust, --crate-type=staticlib packs our two functions and all of std into one archive: 337 members, 23.6 MB.

One twist: rustc links with --gc-sections, and every function sits in its own section, so the linker also throws away unused sections inside the files it does copy. Merge both objects into one big vector.o and the normal build still drops multvec; only with --no-gc-sections do you see the book’s waste.

Try it: Switch the three ways to ship a library, then press Link. In the loose-files view, turn addvec.o off and see the real error.

What the book says

ISO C99 functions such as atoi, printf, scanf, strcpy, and rand live in libc.a. sin, cos, and sqrt live in libm.a. One approach, used by Pascal for a small set of functions, is for the compiler to generate them directly. That is not feasible for C. A single libc.o linked with gcc main.c /usr/lib/libc.o would copy the whole collection into every executable. On the book’s system libc.a is about 5 MB and libm.a is about 2 MB. Separate .o files in a directory force the programmer to name each one.

An archive is concatenated relocatable object files plus a header describing each member. Figure 7.6: addvec increments addcnt and adds two vectors element by element; multvec increments multcnt and multiplies. gcc -c addvec.c multvec.c then ar rcs libvector.a addvec.o multvec.o.

Figure 7.7, main2.c, calls addvec on the two-element vectors 1, 2 and 3, 4, with the result in z. gcc -static -o prog2c main2.o ./libvector.a, or -L. -lvector. -static asks for a fully linked executable with no further load-time linking. -lvector means libvector.a. The linker copies addvec.o and printf.o (and other C run-time modules). It does not copy multvec.o. The driver already passes libc.a.

7.6.3 · how linkers use static libraries

The librarian reads the list from left to right

While it scans the command line, the linker keeps three sets. E is the object files it will merge. U is names it has seen used but not yet defined. D is names it has already defined. An ordinary .o always joins E. An archive member joins only if it defines something still in U. Members that never help are thrown away.

Order matters to that algorithm. We put sum.o in an archive, libsum.a, and linked it with our main.o using GNU ld, the linker the book uses. Archive last works. Archive first fails: the archive is read while U is still empty, so nothing is kept, and then main.o adds sum to U with nobody left to define it. ld printed undefined reference to `sum'. “The general rule for libraries is to place them at the end of the command line.”

Here is a Rust surprise. rust-lld, the linker rustc uses, does not forget an archive once it has passed it, so the same archive-first link succeeds. Ask it with --warn-backrefs and it tells you it had to look backwards. Code that links with rustc today can still fail under GNU ld, so the rule is worth keeping.

If libraries call each other in a circle, one copy at the end is not enough for GNU ld. The book’s pattern is libx.a liby.a libx.a: the second libx.a resolves the name that liby.a added to U after the first scan.

Try it: Press Step and watch E, U, and D. Then flip to archive-first and to the circle that needs libx.a twice. The sets are doing GNU ld’s real scan, not a scripted slide; the listing shows what each linker printed.

What the book says

The linker scans relocatable object files and archives left to right, in command-line order. The driver turns .c files into .o files first. It maintains E (files to merge), U (unresolved symbols), and D (symbols defined so far). All three start empty. An object file is added to E, and U and D are updated from its references and definitions. An archive member is added only when it resolves a symbol in U, repeating until U and D stop changing. Other members are discarded.

If U is nonempty at the end, the linker prints an error. gcc -static ./libvector.a main2.c fails with undefined reference to addvec, because U is empty while the archive is scanned. “The general rule for libraries is to place them at the end of the command line.”

If foo.c calls functions in libx.a and libz.a that call functions in liby.a, the command is gcc foo.c libx.a libz.a liby.a. If the dependence is a cycle, the library is repeated: gcc foo.c libx.a liby.a libx.a. Practice Problem 7.3: p.o then libx.a; then also liby.a; and, when each archive needs the other, p.o libx.a liby.a libx.a.

7.7 · relocation

Slide the blocks, then give them street numbers

Resolution is finished: every reference has exactly one definition, and the linker knows how big every section is. Relocation is two moves, not one.

First it merges sections of the same type. .text.main from main.o, .text.sum from sum.o, and many pieces of the standard library all become one .text. .rodata.array joins the one .rodata. Then it assigns a run-time address to each merged section and to each symbol. After this move, every instruction and every global has a unique address.

In our prog, rust-lld put .text at 0x20fc40, main at 0x20fd30 and sum far away at 0x2475a0, with library code in between. array is the very first thing in .rodata, at 0x2011b0.

Second, it walks the relocation entries and rewrites the references inside those sections so they point at the new addresses. That second move is the next two scenes. This one is only the merge and the street numbers.

Try it: Press Step. Watch main and sum land in one code block, and array land in the read-only block, at the addresses nm prog printed.

What the book says

After symbol resolution, each reference is tied to exactly one definition, and the linker knows the sizes of the code and data sections. Relocation has two steps.

Relocating sections and symbol definitions: the linker merges all sections of the same type into one aggregate section. The .data sections of the input modules become the .data section of the executable. It then assigns run-time addresses to the aggregate sections, to each input section, and to each symbol. Every instruction and global variable then has a unique run-time address.

Relocating symbol references: the linker modifies every reference in the code and data so it points at the correct address, using relocation entries stored in the relocatable modules.

7.7.1 · relocation entries

A sticky note on every blank

When LLVM writes the jump to sum, it does not know where sum will live. It writes zeros and a relocation entry: where the blank is, which symbol it should point at, how to compute the number, and a constant addend. The listing writes that entry as a Rust struct, a record with named fields; #[repr(C)] keeps the fields in order, so the struct is byte for byte the 24-byte entry in the file.

Our main.o has two notes in .rela.text.main. The mov that wants the address of array is type R_X86_64_32, an absolute address, exactly as in the book. The book’s main calls sum; ours ends with jmp sum, because main returns whatever sum returns, so LLVM lets sum return straight to main’s caller (a tail call). Its note is R_X86_64_PLT32 with addend −4.

LLVM used PLT32 for every jump and call to a function in this page’s objects. The rule is “PLT entry + addend − place”. sum sits in our own executable and needs no PLT entry (7.12), so the linker uses sum itself, and the sum is the same as the book’s R_X86_64_PC32: a distance from the next instruction.

What the book says

Whenever the assembler meets a reference whose ultimate location is unknown, it generates a relocation entry. Code entries go in .rel.text. Data entries go in .rel.data. Figure 7.9, Elf64_Rela: offset (section offset of the reference), type (32 bits), symbol (32 bits, a symbol-table index), and addend (a signed constant).

7.7.2 · relocating symbol references

Fill the blank with a distance, or with an address

rust-lld already chose homes: main’s section at 0x20fd30, sum at 0x2475a0, array at 0x2011b0. Figure 7.10 is the recipe. For a PC-relative blank it writes ADDR(symbol) + addend − refaddr. For an absolute blank it writes ADDR(symbol) + addend.

The jump’s blank sits 0xb bytes into main, at 0x20fd3b. The arithmetic is 0x2475a0 + (−4) − 0x20fd3b = 0x37861, so the instruction becomes e9 61 78 03 00. At run time the PC is already the next instruction, 0x20fd3f, and 0x20fd3f + 0x37861 lands on sum.

The mov is simpler. Addend 0, so the blank becomes 0x2011b0, stored little-endian as b0 11 20 00. objdump -d prog shows exactly those bytes. After both patches, the loader can map the bytes and run them with no further edits.

7.8 · executable object files

A packing list for two memory segments

A fully linked ELF executable looks like a relocatable file with two extras. The ELF header now stores the entry point, the address of the first instruction. A program header table maps contiguous chunks of the file onto contiguous chunks of memory. There is no .rel.text anymore. The blanks are already filled.

The book’s Figure 7.14 has two LOAD rows, code and data. readelf -l on our prog shows four. rust-lld gave read-only data (.rodata, the ELF header) a segment of its own, marked R, so it cannot be run as code. The code segment, R E, starts at 0x20fc40 and is 0x37a10 bytes both in the file and in memory. A third segment, RW, holds the GOT and other tables the dynamic linker fills in and then locks read-only, because rustc asks for “full RELRO” by default. The last, RW, is .data and .bss: 0xa00 bytes from the file, 0xa76 in memory. The extra 0x76 bytes are .bss, zeros made at run time.

For every segment the linker must pick a start address vaddr so that vaddr mod align equals off mod align. Here align is 0x1000, one 4 KB page. For the data segment both sides come out to 0x5f8. That alignment is what lets the loader later map file pages onto memory pages. Chapter 9 explains why.

Try it: Tap a segment. Press Check alignment and watch both remainders come out the same.

7.9 · loading executable object files

The loader jumps to _start, not to main

Hana types ./prog. The shell does not know that name, so it calls the loader. Any Linux program can do the same with execve. The loader copies the code and data segments into a run-time memory image and jumps to the entry point.

That entry point is _start, from the C start-up file crt1.o, even in a Rust program. readelf -h prog gives the entry as 0x20fc40, and nm says that is _start. Its code loads the address of main and calls __libc_start_main in libc, which sets up the world, calls main, and deals with the return value.

Our main.rs wrote that C-style main itself. An ordinary Rust program’s fn main is not it. Build a plain hello.rs and nm shows two: a plain main, which rustc wrote for you, and hello::main, yours. rustc’s main hands yours to the standard library’s start-up code, std::rt::lang_start, which prepares things such as the main thread’s name and catches a panic before it escapes. So the walk is _start → __libc_start_main → main → lang_start → your main.

The book’s picture of memory puts code at the bottom, then data, then a heap that grows up when you call malloc, then a gap for shared libraries, then a stack that grows down from just under 2^48. Above that is the kernel. Our non-PIE prog starts at 0x200000, the address rust-lld chose, instead of the book’s 0x400000. The drawing is a simplification. The aside says the loader does not really copy. It maps pages, and the bytes move from disk only when the CPU touches them. ASLR slides the stack, the heap, and the shared libraries each run. Their order stays the same.

Try it: Press Step to fill the image and walk from _start to main. Switch to the aside: nothing is copied until a page is touched.

What the book says

linux> ./prog makes the shell invoke the loader, because prog is not a built-in command. Any Linux program can call the loader through execve (Section 8.4.6). Loading copies the executable’s code and data into memory and jumps to the entry point.

Figure 7.15, not to scale, and with alignment gaps and ASLR omitted: code starts at 0x400000, then the read/write segment (.data, .bss), then the run-time heap created by malloc and growing up via brk, then a memory-mapped region for shared libraries, then the user stack growing down from the largest legal user address. Kernel memory begins at 2^48 and is invisible to user code. The loader then jumps to _start in crt1.o. _start calls __libc_start_main in libc.so, which initializes the environment, calls main, and if necessary returns to the kernel.

The aside: each program runs in a process with its own virtual address space. The shell forks a child; the child calls execve. The loader deletes the old segments and creates code, data, heap, and stack segments. Heap and stack start as zero. Code and data are initialized by mapping pages to page-size chunks of the file. Aside from some header information, nothing is copied at load time. A copy happens later, when the CPU references a mapped page.

7.10 · dynamic linking with shared libraries

One cookbook, many kitchens

A static library still has two problems. To pick up a fix, every program must be relinked. And every program carries its own copy in memory. Rust lives with this on purpose: rustc links the standard library statically by default, so each Rust program has its own copy of println!’s machinery. But libc is shared: readelf -d on any of our programs lists libc.so.6 as NEEDED.

A shared library (.so on Linux, a DLL on Microsoft systems) is loaded at an arbitrary address and linked in memory by the dynamic linker. It is shared twice: one .so file on disk for every program that names it, and one copy of its .text in memory for every process that runs it. Each process still gets its own writable data.

Leila builds libvector.so with rustc --crate-type=cdylib, a C-style shared library, and links prog2l against it with -l dylib=vector. The library’s code is not copied in; prog2l gets a NEEDED note and the symbol and relocation entries the dynamic linker will need. At load time the loader finds the .interp section, /lib64/ld-linux-x86-64.so.2, runs that dynamic linker, and it places libvector.so and libc.so.6 and patches the references. From then on, those addresses stay put.

Try it: On “why share,” press Show copies. On “build prog2l,” press Step: the .so stays out of the executable until the dynamic linker runs.

What the book says

Static libraries must be explicitly relinked when they change. Also, code for printf and scanf is duplicated in the text segment of every running process. A shared library is an object module that can be loaded at an arbitrary memory address and linked with a program in memory, at run time or load time. This is dynamic linking, done by a dynamic linker. On Linux the suffix is .so. Microsoft operating systems call them DLLs.

Shared in two ways: exactly one .so file on a file system, whose code and data are shared by every executable that references the library (instead of being copied in, as with a static library); and a single in-memory copy of the .text section, shared by different running processes (Chapter 9). gcc -shared -fpic -o libvector.so addvec.c multvec.c builds the library. -fpic asks for position-independent code. gcc -o prog2l main2.c ./libvector.so creates a partially linked executable. No code or data from libvector.so is copied into prog2l. The linker copies relocation and symbol table information.

When the loader runs prog2l, it notices the .interp section, whose contents are the path of the dynamic linker (ld-linux.so). The dynamic linker relocates libc.so and libvector.so into memory segments and relocates references in prog2l to symbols they define, then passes control to the application. After that, the shared libraries’ locations do not change during the run.

7.11 · loading shared libraries from applications

Ask for a library while the program is already running

Load-time linking happens before main. A program can also call the dynamic linker itself, in the middle of a run, for a library it never named at compile time.

Nadia’s program (dll.c in the book, dll.rs here) asks dlopen for ./libvector.so with the flag RTLD_LAZY, then asks dlsym for addvec, then calls it on the vectors 1, 2 and 3, 4. The sum lands in z as 4, 6. dlclose unloads the library if nobody else is using it. dlerror explains a failure. Plain rustc dll.rs builds it: rustc’s link line already carries -ldl.

In Rust, dlsym hands back a bare address, and std::mem::transmute (reinterpret these bits as another type) turns it into a function pointer we can call. That is the riskiest line on the page: if the library’s addvec took other arguments, nothing would catch it. On Linux the twin loaded our Rust-built libvector.so and printed z = [4 6]. With the file moved away, dlerror said ./libvector.so: cannot open shared object file: No such file or directory.

That is also how a busy web server can avoid fork and execve for every custom page. It keeps each page’s function in a shared library, loads it on the first request, and later requests are an ordinary call. The function stays cached. Java’s JNI does the same kind of thing: the interpreter dlopens a .so of native code.

What the book says

Windows applications ship updates this way. High-performance web servers package each dynamic-content function in a shared library and call it directly, instead of fork and execve of a CGI program. The function stays cached, so the next request is a function call. Functions can be updated without stopping the server.

dlopen loads and links filename and returns a handle, or NULL. Symbols are resolved using libraries previously opened with RTLD_GLOBAL. With -rdynamic, the executable’s globals are available too. The flag includes RTLD_NOW (resolve immediately) or RTLD_LAZY (defer until the code runs), optionally ored with RTLD_GLOBAL. dlsym returns a symbol’s address or NULL. dlclose unloads the library if no other shared library is still using it, returning 0 or −1. dlerror returns the most recent error string, or NULL.

7.12 · position-independent code

A library that can sit on any shelf

If every shared library had a reserved street number, the loader’s job would be easy and the address space would rot. Unused libraries would still own their chunk. A new version that no longer fits would need a new chunk. Hundreds of libraries would leave the map full of holes that are free and still useless. And every machine would need the same assignment.

Position-independent code can be loaded anywhere without the linker rewriting the code bytes. Then one copy of the code segment can be mapped into as many processes as you like. Each process still gets its own read/write data. gcc needs -fpic for this. For rustc it is the default, -C relocation-model=pic. We tried building libvector.so from our static-model code instead, and rust-lld refused: relocation R_X86_64_PC32 cannot be used against symbol 'addcnt'; recompile with -fPIC.

References inside the same executable are already fine: PC-relative addressing, patched once by the static linker. References to globals and functions that live in a shared module need the GOT and the PLT, which are the next two scenes.

Try it: Press Add library. In the reserved-slot world the newcomer has nowhere to sit. In the PIC world it takes the next free place, and both processes share its code.

What the book says

One approach would assign each shared library a dedicated chunk of the address space and always load it there. That wastes space for libraries a process does not use, is hard to keep from overlapping, breaks when a library no longer fits its chunk, and fragments the address space into unusable holes. The assignment would also differ from system to system.

Modern systems compile shared-module code so it can be loaded anywhere without being modified by the linker. A single copy of the code segment can then be shared by an unlimited number of processes. Each process still gets its own copy of the read/write data segment. Code that needs no relocations is position-independent code (PIC). gcc -fpic generates it. Shared libraries must always be compiled with this option.

On x86-64, references to symbols in the same executable need no special PIC treatment: they use PC-relative addressing and are relocated by the static linker when the object file is built. References to external procedures and to global variables defined by shared modules need the techniques in the rest of the section.

7.12 · PIC data references

The distance stays. The address lives in the GOT.

No matter where a shared module is loaded, its data segment stays the same distance from its code segment. So the distance from an instruction to a slot in the data segment is a constant, even though the absolute addresses are not.

In the book, the compiler builds a global offset table at the start of the data segment. (In our libvector.so, rust-lld laid out .got from LLVM’s notes, just after .dynamic.) Each global the module uses gets an 8-byte slot. At load time the dynamic linker fills those slots with absolute addresses. The code does not change. It loads a slot with a PC-relative mov, then uses the address it found.

Our Rust libvector.so does exactly the book’s trick. ADDCNT += 1 became mov 0x3a1d1(%rip), %rax then incl (%rax). The mov ends at 0x12bb7, and 0x12bb7 + 0x3a1d1 = 0x4cd88, a GOT slot. readelf -r shows the note the dynamic linker obeys at load time: R_X86_64_GLOB_DAT addcnt, “write the address of addcnt here.” Move the whole library and the distance is still 0x3a1d1. Only the value stored in the slot changes.

Like gcc, rustc goes through the GOT even though addcnt lives in this very library, because an exported name could be replaced by another library’s definition at run time (7.13 does exactly that to malloc).

Try it: Press Step to run the two instructions. Then Move library: the code bytes stay the same, the gap stays 0x3a1d1, and the slot points at addcnt in its new place.

What the book says

No matter where an object module is loaded, the data segment is always the same distance from the code segment. The distance between any instruction and any variable in the data segment is a run-time constant.

Compilers create a global offset table (GOT) at the beginning of the data segment, with an 8-byte entry for each global object the module references. The compiler also generates a relocation record for each GOT entry. At load time the dynamic linker fills each entry with the object’s absolute address. Each object module that references global objects has its own GOT.

Figure 7.18: addvec in libvector.so executes mov 0x2008b9(%rip), %rax so that %rax becomes *GOT[3], which is &addcnt, then addl $0x1, (%rax). The distance 0x2008b9 between GOT[3] and the addl is a run-time constant. The compiler uses the GOT even for addcnt, which this module itself defines, because that is the general solution when the variable might live in another shared module.

7.12 · PIC function calls

The first call pays. The rest are one jump.

A call to a function in a shared library cannot bake the function’s address into the code. That would mean rewriting the code segment, and then it could not be shared. Patching every function at load time would also be wasteful: a program uses a handful of the thousands of functions in libc.so.

Lazy binding waits until the first real call. The procedure linkage table is a row of 16-byte stubs in the code segment. PLT[0] jumps into the dynamic linker. Our stub for addvec is PLT[1] at 0x24bc30. Its GOT slot, GOT[3] at 0x250bc0, starts out holding 0x24bc36, the next instruction inside that stub, not addvec.

The first call bounces stub → GOT → back into the stub → PLT[0] → dynamic linker. The linker writes the address of addvec into GOT[3] and jumps there. The next call is stub → GOT → addvec, one indirect jump. We watched it happen: with LD_DEBUG=bindings, the dynamic linker’s line binding … normal symbol `addvec' came out between our “first call” and “second call”.

That is not Rust’s default. rustc asks for full RELRO (-z now): every function is bound before main starts and the GOT is then made read-only, which closes a door attackers like. With PIC code on x86-64 it even skips the PLT: prog2l calls call *0x3dd3f(%rip), straight through a GOT slot. To get the book’s lazy PLT we built with -C relro-level=partial.

Try it: Press Step through the first call. Watch GOT[3] change from 0x24bc36 to the address of addvec. Press Step again: the second call skips the linker. Then switch to “Rust default”.

What the book says

The compiler cannot predict the run-time address of a shared-library function. A relocation record on the call would force the dynamic linker to modify the caller’s code segment, which is not PIC. Lazy binding defers the binding until the first call. A typical program calls only a handful of the hundreds or thousands of functions in libc.so, so the linker skips the rest at load time. The first call has a nontrivial cost. Each later call is a single instruction plus a memory reference.

The PLT is an array of 16-byte code entries in the code segment. PLT[0] jumps into the dynamic linker. PLT[1] (not shown) invokes __libc_start_main. Entries from PLT[2] invoke user-called functions: PLT[2] is addvec, PLT[3] is printf. The GOT is 8-byte addresses in the data segment. GOT[2] is the dynamic linker’s entry in ld-linux.so. Initially each function’s GOT entry points at the second instruction of its PLT entry. GOT[4] starts as 0x4005c6.

7.13 · library interpositioning

Stand in the doorway and take a note

Ines wants a diary of every malloc and free. She writes a wrapper with the same shape as the real function. The wrapper does its own work, calls the real function, and returns whatever that returned. The caller thinks it called malloc.

Linux can arrange that trick at three times. Compile time needs the source, so the preprocessor can rewrite the call. Link time needs the relocatable .o files, so the linker can rename the symbol. Run time needs only the executable: a shared library is placed first in the search.

The next three scenes open those three doorways. This one is the idea they share. The book’s int.c asks malloc for 32 bytes, then frees them. Its twin, int.rs, calls the same C malloc on purpose, because that is the function we want to intercept. Everyday Rust would use Vec or Box (one value on the heap) and never call malloc by hand. (Which allocator those use is officially unspecified; in our builds the standard library’s own allocations went to libc’s malloc, and the wrappers below caught them too.) int.rs prints the pointer it got: our first version did not, and LLVM simply deleted the unused malloc and free, leaving nothing to trace.

What the book says

Library interpositioning lets you intercept calls to shared library functions and run your own code instead. You can count calls, trace arguments and return values, or replace the function.

You write a wrapper whose prototype matches the target. Some interpositioning mechanism makes the system call the wrapper instead. The wrapper typically runs its own logic, calls the target, and passes the return value back.

Interpositioning can happen at compile time, at link time, or at run time as the program is loaded. The running example, Figure 7.20(a), is int.c: malloc(32) then free(p). The goal is to trace those calls.

7.13.1 · compile-time interpositioning

The compiler picks which malloc the name means

In the book, a local header tells the C preprocessor: whenever you see malloc(size), pretend the programmer wrote mymalloc(size). The flag -I. makes the preprocessor find that header first. The wrapper itself is compiled without it, so its own call to malloc is not rewritten into a call to itself. Forget the flag and the trace stays empty.

Rust has no preprocessor that rewrites calls, but it can choose, when it compiles, what a name means. In intc.rs, #[cfg(trace)] keeps a line only when rustc is given --cfg trace, and use … as malloc makes the name malloc mean mymalloc. The code in main never changes. The wrapper reaches the real function by its full path, sys::malloc (sys is a module holding libc’s declarations), so it never calls itself.

7.13.2 · link-time interpositioning

The linker renames the symbol

This time the source is left alone. int.rs still calls malloc. The wrappers live in their own object, trace_malloc.o, and rustc passes the linker two extra arguments: -C link-arg=-Wl,--wrap=malloc, and the same for free. -Wl, means “hand this on to the linker”, so rust-lld sees --wrap=malloc.

That flag means: a reference to malloc is resolved as __wrap_malloc, and a reference to __real_malloc is resolved as the real malloc. The wrapper calls __real_malloc, prints, and returns. #[unsafe(no_mangle)] keeps the name __wrap_malloc plain so the linker can match it. Without the flag, the call goes straight to libc and the diary stays blank.

./intl printed malloc(32) = 0x5555555a99e0 and the matching free, and two more lines before main even started: malloc(4) and malloc(544). Those come from the Rust standard library, which was linked into the same executable, so --wrap renamed its malloc references too. You needed the object files. You did not need to rewrite the source.

What the book says

The static linker’s --wrap f flag resolves references to f as __wrap_f, and references to __real_f as f. Figure 7.21, under LINKTIME, declares __real_malloc and __real_free. __wrap_malloc calls __real_malloc and prints the size and the pointer. __wrap_free calls __real_free and prints.

7.13.3 · run-time interpositioning

A library that cuts in line

Compile-time wrapping needs source. Link-time wrapping needs .o files. LD_PRELOAD needs only the executable. If that variable names shared libraries, ld-linux.so searches them first, before libc.so, whenever it resolves an undefined reference.

The run-time wrapper is itself named malloc. It asks dlsym, with the special handle RTLD_NEXT, for the next malloc down the line — libc’s — then calls that and prints. The Rust twin, mymalloc.rs, defines malloc and free with #[unsafe(no_mangle)] and uses transmute to call the address dlsym returns; type Malloc gives that function-pointer type a name. It is built with rustc --crate-type=cdylib mymalloc.rs. The program is the plain int.rs, built with nothing special, and run as LD_PRELOAD=./mymalloc.so ./intr.

On Linux it printed our malloc(32), but only after eleven lines from libc and Rust’s start-up code, most of which our earlier doorways never saw: this one catches every malloc in the process. The same variable works on a program you did not write. LD_PRELOAD=./mymalloc.so /usr/bin/uptime printed 13 malloc lines and the clock. Turn the variable off and uptime is quiet again.

Try it: Run ./intr with preload on and off. Then run uptime. The search list puts mymalloc.so ahead of libc.so only while the variable is set.

What the book says

If LD_PRELOAD is a list of shared-library pathnames separated by spaces or colons, the dynamic linker searches those libraries first when resolving undefined references. You can interpose on any function in any shared library, including libc.so, for any executable.

Figure 7.22, under RUNTIME and _GNU_SOURCE: malloc looks up the next malloc with dlsym and RTLD_NEXT, calls it, and prints the size and the pointer. free returns immediately on a null pointer, otherwise dlsym(RTLD_NEXT, "free") and prints. Build with gcc -DRUNTIME -shared -fpic -o mymalloc.so mymalloc.c -ldl and gcc -o intr int.c.

From bash: LD_PRELOAD="./mymalloc.so" ./intr prints malloc(32) = 0x1bf7010 and free(0x1bf7010). The same prefix on /usr/bin/uptime traces mallocs including malloc(568) = 0x21bb010 and then prints 20:47:36 up 85 days, 6:04, 1 user, load average: 0.10, 0.04, 0.05. csh and tcsh use setenv.

7.14 · tools for object files

Eight ways to open the binary

The GNU binutils package is on every Linux system, and it is how you look inside the files this chapter has been building. Each tool answers one question.

ar packs and lists archive members. strings pulls out the readable text. strip deletes the symbol table. nm lists symbols. size lists section sizes. readelf shows the whole ELF structure, including what size and nm show. objdump can show everything, and its party trick is disassembling .text. ldd is separate: it lists the shared libraries an executable will need when it runs.

Every output below is what the tool printed on this page’s own Rust-built files — main.o, libvector.a, prog, prog2l — trimmed to the lines that matter. A few are worth a second look. size counts array as text, because rustc put it in read-only data. strip took prog from 4,448,360 bytes to 301,608: most of the file was the standard library’s debugging information, and the program still ran. nm -C and objdump -C turn v0 names back into Rust paths.

Try it: Pick a tool and press Run. strip really removes the roster from the picture. Run nm afterwards and the names are gone until you press Reset.

What the book says

GNU binutils runs on every Linux platform. ar creates static libraries and inserts, deletes, lists, and extracts members. strings lists printable strings in an object file. strip deletes symbol table information. nm lists the symbols in an object file’s symbol table. size lists the names and sizes of the sections. readelf displays the complete structure of an object file, including the ELF header, and subsumes size and nm.

objdump can display all of the information in an object file. Its most useful function is disassembling the binary instructions in .text. Linux also provides ldd, which lists the shared libraries that an executable needs at run time.

What the summary says

Linking happens at compile time, load time, and run time. Object files are relocatable, executable, or shared. The two tasks are symbol resolution and relocation. Loaders map executables into memory. Partially linked executables are finished by a dynamic linker.

Words to know

The chapter’s grown-up words, in one sentence each.

compiler driver
A program that runs the others for you: gcc, and rustc, which calls LLVM and then cc and rust-lld.
relocatable object file
Code and data that can still be combined with other files at compile time.
executable
A fully linked file the loader can map into memory and run.
shared object
A .so, or a Windows DLL, loaded and linked at load time or run time.
ELF
The object-file format on modern x86-64 Linux and Unix.
.text / .rodata / .data / .bss
Instructions, read-only data, changeable initialized data, and zeros that take no space on disk.
symbol
A function, a global, or a static variable, as the linker sees it.
strong / weak
In C, a function or initialized global, versus a global with no value. Every Rust static has a value, so it is strong.
COMMON
Where gcc parks an uninitialized C global until the linker picks a winner. A Rust static always has a value, so our builds never made one.
static library
An archive of .o files. The linker copies only the members it needs.
mangling
Spelling a name with its path (and, in C++, its argument types) so the linker sees one unique string. Rust’s v0 names start with _R.
crate
Rust’s unit of compiling and linking: one library or one program.
rlib
Rust’s library package: an ar archive of object files, one per codegen unit, plus metadata for rustc.
cdylib / staticlib
A Rust crate built as a C-style .so, or as a .a that also holds all of std.
extern block
Rust declarations of functions or statics defined in another object file. rustc cannot check them, so using them is unsafe.
relocation entry
A note with an offset, a type, a symbol, and an addend, telling the linker how to fill a blank. x86-64 keeps them in .rela sections.
PC-relative
A distance from the next instruction. R_X86_64_PC32 is this kind, and so is R_X86_64_PLT32 when no PLT entry is needed.
loader
Operating-system code, reached through execve, that maps the executable and jumps to _start.
dynamic linker
ld-linux-x86-64.so.2, which finishes shared-library addresses at load time, or when you call dlopen.
PIC
Code that can be loaded at any address without rewriting its own bytes.
GOT
A table of 8-byte addresses in the data segment that the dynamic linker fills in.
PLT
16-byte stubs in the code segment that bind a function on its first call.
RELRO
Making the GOT read-only once it is filled. rustc asks for full RELRO, which binds every function before main.
interpositioning
A wrapper that runs instead of a library function, then usually calls it.
LD_PRELOAD
Shared libraries the dynamic linker searches before libc.so.
