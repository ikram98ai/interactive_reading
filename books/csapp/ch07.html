Linking

Separate notebooks of code become one program. The glue can be applied when you compile, when you load, or while the program is already running.

“Linking is the process of collecting and combining various pieces of code and data into a single file that can be loaded (copied) into memory and executed.” — Bryant & O’Hallaron

New here? Every section below is one little machine. Read the story, then press the buttons. Under each picture is the code that machine is using: the highlighted line is the step you are on, and the small tags are live values. Press C or Rust. Shell commands, assembly, and ELF dumps stay as the book shows them. You cannot break it.

Rust setup: what the listings assume

The book’s C listings are compiled by gcc into ELF object files. Rust reaches the same linker, but it mangles names and keeps items private unless you ask, so these listings export the symbols the scenes talk about. Where C behaves in a way Rust cannot (weak symbols, merged duplicates), the Rust listing shows what happens instead.

//   #[unsafe(no_mangle)]              a function or static keeps its own name
//   #[unsafe(export_name = "array")]  export ARRAY under the C name `array`
// Plain Rust items are private and mangled (f::X), unlike C globals.
// Rust has no weak symbols and no COMMON: C's `int x;` becomes a strong
// definition, so two files that both define x fail at link time.

    fn free(ptr: *mut u8);

    fn dlerror() -> *const c_char;
    fn dlclose(handle: *mut c_void) -> c_int;

7.1 · compiler drivers

A receptionist who calls four specialists

Mei types one line: gcc -Og -o prog main.c sum.c. She thinks one program did all the work. gcc is a compiler driver, a receptionist. It calls the preprocessor, the compiler, the assembler, and the linker, then goes home.

Each specialist leaves a new file. main.c becomes main.i, then main.s, then a binary main.o. The same walk happens for sum.c. Only then does ld glue the object files, plus system files, into prog.

Typing ./prog is a later trip. The shell asks the operating system’s loader to copy that file into memory and start it. Linking already finished.

Try it: Press Step. The command under the picture highlights the specialist who is working, and main.c or sum.c stays one tab away.

What the book says

Figure 7.1 is the running example. main.c declares sum, defines array[2] = {1, 2}, and returns sum(array, 2). sum.c adds the n elements. The discussion is an x86-64 system running Linux and using ELF. Concepts are the same on other systems; details vary.

The driver command is gcc -Og -o prog main.c sum.c. It runs cpp to make /tmp/main.i, then cc1 /tmp/main.i -Og -o /tmp/main.s, then as -o /tmp/main.o /tmp/main.s, the same path for sum.o, then ld -o prog with system object files plus the two .o files. In some versions of gcc the preprocessor is integrated into the driver. gcc -v shows the real argument lists.

./prog is not a built-in shell command, so the shell invokes the loader, which copies the code and data into memory and transfers control to the beginning of the program.

7.2 · static linking

Two jobs, then the glue

Amara compiled main.c on Monday and sum.c on Tuesday. Each .o file is a stack of sections: one run of bytes for instructions, one for initialized globals, one for zeros. The static linker ld reads those stacks and writes one executable.

Job one is symbol resolution: every name that is used must be tied to exactly one definition. Job two is relocation: the sections were born at address 0, so the linker slides them to real addresses and rewrites the blanks the assembler left.

The linker is not a second compiler. It concatenates blocks of bytes, picks run-time homes, and patches a few numbers. The compilers and assemblers already did the thinking.

Try it: Press Step. First the name sum finds its definition. Then the blocks slide into prog and pick up addresses from the chapter’s later figure.

What the book says

Static linkers such as the Linux ld program take relocatable object files and command-line arguments and generate a fully linked executable that can be loaded and run. Instructions are in one section, initialized global variables in another, uninitialized variables in a third.

Symbol resolution associates each symbol reference with exactly one symbol definition. A symbol is a function, a global variable, or a static variable. Relocation then gives each definition a memory location and modifies references so they point there. “The linker blindly performs these relocations using detailed instructions, generated by the assembler, called relocation entries.”

“Object files are merely collections of blocks of bytes.” A linker concatenates blocks, decides on run-time locations, and modifies locations inside the code and data. “Linkers have minimal understanding of the target machine.”

7.3 · object files

Three kinds of package

Not every binary file is ready to run. A relocatable file can still be combined with others at compile time. An executable can be copied into memory and started. A shared object can be loaded and linked later, at load time or run time.

Compilers and assemblers make the relocatable ones, including shared objects. Linkers make executables. On disk the bytes are an object file; the same sequence of bytes is an object module. The book uses both names.

The recipe for arranging those bytes has changed names over the years: early Unix a.out, Windows PE, Mac OS-X Mach-O, and ELF on modern x86-64 Linux. The ideas underneath are the same.

Try it: Tap a package. The picture shows who builds it and who consumes it. The listing underneath is the command that produces that form.

What the book says

A relocatable object file contains binary code and data that can be combined with other relocatable object files at compile time. An executable object file can be copied directly into memory and executed. A shared object file is a special relocatable object file that can be loaded and linked dynamically, at either load time or run time.

Compilers and assemblers generate relocatable object files, including shared object files. Linkers generate executable object files. An object module is a sequence of bytes; an object file is that module stored on disk. The book uses the terms interchangeably.

The first Unix systems from Bell Labs used the a.out format. Executables are still called a.out files. Windows uses the Portable Executable (PE) format. Mac OS-X uses the Mach-O format. Modern x86-64 Linux and Unix systems use ELF.

7.4 · relocatable object files

A sandwich with a label on each filling

Diego opens main.o. The first 16 bytes say how big a word is and which way the bytes face. The rest of the ELF header says “relocatable, x86-64,” and where the table of contents sits. Between the header and that table are the fillings.

Instructions live in .text. Read-only constants live in .rodata. Initialized globals live in .data. Zeros live in .bss, which is a trick: the file stores a size, not the zero bytes. Better save space. Names live in .symtab. Sticky notes for the linker live in .rel.text and .rel.data.

Compile with -g and two more fillings appear: .debug and .line. Without -g they are simply not in the file. .symtab is there either way, unless someone runs strip.

Try it: Tap a filling. The listing highlights the lines of Figure 7.1 that land there. Then press -g and watch .debug and .line show up.

What the book says

Figure 7.3: the ELF header begins with a 16-byte sequence that describes word size and byte ordering. The rest holds the header size, the object file type, the machine type, and the file offset, size, and number of entries in the section header table. Each section has a fixed-size entry in that table.

.text is compiled machine code. .rodata holds printf format strings and switch jump tables. .data holds initialized global and static variables. Local variables live on the stack and do not appear in .data or .bss. “This section occupies no actual space in the object file; it is merely a placeholder.” The name .bss comes from the IBM 704 “block started by symbol” directive, circa 1957. A mnemonic: “Better Save Space!”

.symtab is present unless removed with strip, and you do not need -g to get it. It has no local variables. .rel.text lists locations in .text to modify; calls to local functions usually need none. .rel.data covers initialized globals whose value is an address. .debug and .line exist only with -g. .strtab is the null-terminated strings those tables name.

7.5 · symbols and symbol tables

The roster is not the lockers

Every relocatable module has a roster of names. Some names it defines and is willing to share. Some names it uses but does not define — those are externals. Some names it marks static, so they stay inside the file. Those local linker symbols are not the same thing as a local variable.

Kenji’s swap.c and Lucia’s m.c are Practice Problem 7.1. buf is borrowed from Lucia. bufp0 is an initialized pointer. bufp1 has no initializer, so gcc parks it in COMMON. swap is a global function. temp lives on the stack and gets no row at all.

If two functions in one file each say static int x, the compiler cannot put either on the stack. It allocates .data or .bss and invents two roster names, x.1 and x.2.

Try it: Switch the three views. In the roster, tap a name from swap.c. temp stays off the list. In the third view, watch one spelling of x become two linker names.

What the book says

Three kinds of symbols in module m: global symbols defined by m (nonstatic C functions and global variables); externals referenced by m but defined elsewhere; and local symbols (static functions and globals). “It is good programming practice to protect your variables and functions with the static attribute wherever possible.” Local linker symbols are not local program variables. The .symtab has no nonstatic locals; those live on the stack.

Figure 7.4, Elf64_Symbol: name (string-table offset), 4-bit type and binding, section, value (section offset in a relocatable file, absolute address in an executable), size. Pseudosections that have no section-header entry: ABS (do not relocate), UNDEF (referenced here, defined elsewhere), COMMON (uninitialized, not yet allocated; value is alignment, size is the minimum). They exist only in relocatable files. Modern gcc: COMMON is uninitialized globals; .bss is uninitialized statics and globals or statics initialized to zero. That split exists because of the rules in Section 7.6.

readelf on main.o: main is a 24-byte FUNC GLOBAL in Ndx 1 (.text) at value 0; array is an 8-byte OBJECT GLOBAL in Ndx 3 (.data) at value 0; sum is NOTYPE GLOBAL UND. 7.6 · symbol resolution

A name the linker cannot find

Inside one file, resolution is easy. The compiler allows only one definition of each local symbol, and it gives static locals unique names. The linker just follows the roster.

A global is harder. If the compiler sees foo used but not defined, it shrugs and leaves a blank. The compiler of linkerror.c succeeds. The linker then searches every input module, finds no foo, and stops with undefined reference to foo.

C++ and Java can have several functions with the same spelling and different arguments. The compiler mangles each combination into a unique linker name. Foo::bar(int, long) becomes bar__3Fooil. The linker never sees the overload. It sees a different string.

Try it: On the first view, press Link and read the error under the listing. On the second, the local name resolves inside the file. On the third, press Mangle.

What the book says

The linker associates each reference with exactly one symbol definition from the symbol tables of its input relocatable object files. Local references are straightforward: one definition per local symbol per module, and unique names for static locals. For a global the compiler does not see defined, it assumes another module defines it, emits a symbol-table entry, and leaves the reference for the linker.

If no input module defines the symbol, the linker prints an error and terminates. gcc -Wall -Og -o linkerror linkerror.c compiles, then the linker reports undefined reference to foo from .text+0x7.

C++ and Java overloaded methods share a source name and differ in their parameter lists. The compiler encodes each method and parameter list into a unique linker name. That encoding is mangling; the inverse is demangling. Class Foo is encoded as 3Foo. Foo::bar(int, long) is encoded as bar__3Fooil.

7.6.1 · duplicate global names

One strong name quietly wins

At compile time every global is stamped strong or weak. Functions and initialized globals are strong. Uninitialized globals are weak. Linux then uses three rules. Two strongs with the same name: error. One strong and any number of weaks: keep the strong, say nothing. Several weaks: pick any of them.

Omar’s foo3.c sets int x = 15213. Priya’s bar3.c says bare int x and, inside f, stores 15212. The link succeeds. The program prints x = 15212. Priya wrote Omar’s variable.

Types make it nastier. A strong int x next to a weak double x still keeps the strong name, but x = -0.0 writes 8 bytes. On the book’s layout that smears the neighbour y, and the printout is x = 0x0 y = 0x80000000. The linker only warned about alignment.

Try it: Pick a pair and press Link. For the int/double pair, press again to watch f write eight bytes across x and y.

What the book says

Functions and initialized global variables get strong symbols. Uninitialized global variables get weak symbols. Rule 1: multiple strong symbols with the same name are not allowed. Rule 2: one strong and multiple weaks, choose the strong. Rule 3: multiple weaks, choose any. foo1.c and bar1.c both define main and the link fails. foo2.c and bar2.c both define int x = 15213 and the link fails the same way.

foo3.c defines strong x = 15213 and calls f. bar3.c defines weak x and sets x = 15212. gcc -o foobar3 foo3.c bar3.c gives no multiply-defined warning, and ./foobar3 prints x = 15212. Two weak definitions (foo4.c, bar4.c) are rule 3.

foo5.c has int y = 15212 and int x = 15213. bar5.c has double x and assigns x = -0.0. On x86-64/Linux a double is 8 bytes and an int is 4. The book’s addresses are x at 0x601020 and y at 0x601024, so the assignment overwrites both. The link warns that alignment 4 of x is smaller than 8, then ./foobar5 prints x = 0x0 y = 0x80000000. gcc -fno-common errors on multiply-defined globals. -Werror turns warnings into errors. A weak global is assigned to COMMON because the compiler cannot yet know which definition will win; a zero-initialized global is strong, so it can go in .bss.

7.6.2 · linking with static libraries

A shelf that lends only the books you name

ISO C has a huge box of functions: printf, strcpy, sin, and hundreds more. Putting every one of them into every program would waste disk and memory. On the book’s system libc.a is about 5 MB and libm.a is about 2 MB. Making the compiler invent the functions itself would mean a new compiler every time the library changed. Handing the programmer a directory of loose .o files means a long, fragile command line.

A static library is the compromise. Related .o files are packed into one archive (.a). At link time the linker copies only the members the program actually references.

Leila builds libvector.a from addvec.o and multvec.o. Her main2.c calls addvec only. The executable receives addvec.o and printf.o from libc.a. multvec.o stays on the shelf.

Try it: Switch the three ways to ship a library, then press Link. Only the archive copies addvec and leaves multvec behind.

What the book says

ISO C99 functions such as atoi, printf, scanf, strcpy, and rand live in libc.a. sin, cos, and sqrt live in libm.a. One approach, used by Pascal for a small set of functions, is for the compiler to generate them directly. That is not feasible for C. A single libc.o linked with gcc main.c /usr/lib/libc.o would copy the whole collection into every executable. On the book’s system libc.a is about 5 MB and libm.a is about 2 MB. Separate .o files in a directory force the programmer to name each one.

An archive is concatenated relocatable object files plus a header describing each member. Figure 7.6: addvec increments addcnt and stores x[i] + y[i]; multvec increments multcnt and multiplies. gcc -c addvec.c multvec.c then ar rcs libvector.a addvec.o multvec.o.

Figure 7.7, main2.c, calls addvec(x, y, z, 2) with {1, 2} and {3, 4}. gcc -static -o prog2c main2.o ./libvector.a, or -L. -lvector. -static asks for a fully linked executable with no further load-time linking. -lvector means libvector.a. The linker copies addvec.o and printf.o (and other C run-time modules). It does not copy multvec.o. The driver already passes libc.a.

7.6.3 · how linkers use static libraries

The librarian reads the list from left to right

While it scans the command line, the linker keeps three sets. E is the object files it will merge. U is names it has seen used but not yet defined. D is names it has already defined. An ordinary .o always joins E. An archive member joins only if it defines something still in U. Members that never help are thrown away.

Order matters. gcc -static ./libvector.a main2.c looks at the archive while U is still empty, so it keeps nothing from the shelf. Later main2.o adds addvec to U, and nobody is left to define it. “The general rule for libraries is to place them at the end of the command line.”

If libraries call each other in a circle, one copy at the end is not enough. The book’s pattern is gcc foo.c libx.a liby.a libx.a: the second libx.a resolves the name that liby.a added to U after the first scan.

Try it: Press Step and watch E, U, and D. Then flip to archive-first and to the circle that needs libx.a twice. The sets are doing the real scan, not a scripted slide.

What the book says

The linker scans relocatable object files and archives left to right, in command-line order. The driver turns .c files into .o files first. It maintains E (files to merge), U (unresolved symbols), and D (symbols defined so far). All three start empty. An object file is added to E, and U and D are updated from its references and definitions. An archive member is added only when it resolves a symbol in U, repeating until U and D stop changing. Other members are discarded.

If U is nonempty at the end, the linker prints an error. gcc -static ./libvector.a main2.c fails with undefined reference to addvec, because U is empty while the archive is scanned. “The general rule for libraries is to place them at the end of the command line.”

If foo.c calls functions in libx.a and libz.a that call functions in liby.a, the command is gcc foo.c libx.a libz.a liby.a. If the dependence is a cycle, the library is repeated: gcc foo.c libx.a liby.a libx.a. Practice Problem 7.3: p.o then libx.a; then also liby.a; and, when each archive needs the other, p.o libx.a liby.a libx.a.

7.7 · relocation

Slide the blocks, then give them street numbers

Resolution is finished: every reference has exactly one definition, and the linker knows how big every section is. Relocation is two moves, not one.

First it merges sections of the same type. All the .text blocks become one .text. All the .data blocks become one .data. Then it assigns a run-time address to each merged section and to each symbol. After this move, every instruction and every global has a unique address.

Second, it walks the relocation entries and rewrites the references inside those sections so they point at the new addresses. That second move is the next two scenes. This one is only the merge and the street numbers.

Try it: Press Step. Watch main and sum land in one code block, and array land in the data block, at the addresses Figure 7.12 will use.

What the book says

After symbol resolution, each reference is tied to exactly one definition, and the linker knows the sizes of the code and data sections. Relocation has two steps.

Relocating sections and symbol definitions: the linker merges all sections of the same type into one aggregate section. The .data sections of the input modules become the .data section of the executable. It then assigns run-time addresses to the aggregate sections, to each input section, and to each symbol. Every instruction and global variable then has a unique run-time address.

Relocating symbol references: the linker modifies every reference in the code and data so it points at the correct address, using relocation entries stored in the relocatable modules.

7.7.1 · relocation entries

A sticky note on every blank

When the assembler writes call sum, it does not know where sum will live. It writes zeros and a relocation entry: where the blank is, which symbol it should point at, how to compute the number, and a constant addend.

Notes for code go in .rel.text. Notes for data go in .rel.data. Figure 7.11 has two notes in main. The mov that wants &array is type R_X86_64_32, an absolute address. The call to sum is type R_X86_64_PC32, a distance from the next instruction, with addend −4.

ELF defines 32 relocation types. The book cares about these two, which are enough for the small code model: code and data together smaller than 2 GB. Bigger programs can ask for -mcmodel=medium or -mcmodel=large. The book does not cover those.

Try it: Tap the call or the mov. The four fields of Elf64_Rela fill in, and that line lights up in the disassembly.

What the book says

Whenever the assembler meets a reference whose ultimate location is unknown, it generates a relocation entry. Code entries go in .rel.text. Data entries go in .rel.data. Figure 7.9, Elf64_Rela: offset (section offset of the reference), type (32 bits), symbol (32 bits, a symbol-table index), and addend (a signed constant).

R_X86_64_PC32 relocates a 32-bit PC-relative address. The CPU adds that value to the PC, which is the address of the next instruction. R_X86_64_32 relocates a 32-bit absolute address, used directly as the effective address. These two types support the x86-64 small code model, the gcc default, which assumes the executable’s code and data are smaller than 2 GB. -mcmodel=medium and -mcmodel=large exist for larger programs; the book does not discuss them.

Figure 7.11, from objdump -dx main.o: at offset 0x9 a mov $0x0, %edi with entry R_X86_64_32 array; at offset 0xe a callq with entry R_X86_64_PC32 sum-0x4. Relocation entries and instructions live in different sections; objdump prints them together. For the call, r.offset = 0xf, r.symbol = sum, r.type = R_X86_64_PC32, r.addend = -4.

7.7.2 · relocating symbol references

Fill the blank with a distance, or with an address

The linker already chose homes: .text at 0x4004d0, sum at 0x4004e8, array at 0x601018. Figure 7.10 is the recipe. For a PC-relative blank it writes ADDR(symbol) + addend − refaddr. For an absolute blank it writes ADDR(symbol) + addend.

The call’s reference sits at 0x4004df. The arithmetic is 0x4004e8 + (−4) − 0x4004df = 0x5. The instruction becomes e8 05 00 00 00. At run time the PC is already the next instruction, 0x4004e3, and 0x4004e3 + 0x5 lands on sum.

The mov is simpler. Addend 0, so the blank becomes 0x601018, stored little-endian as 18 10 60 00. After both patches, the loader can copy the bytes and run them with no further edits.

Try it: Press Step on the call. The listing follows Figure 7.10 line by line and pins the running total on the formula. Switch to array for the absolute patch.

What the book says

Figure 7.10 iterates over each section s and each relocation entry r. refptr = s + r.offset. For R_X86_64_PC32, refaddr = ADDR(s) + r.offset and *refptr = (unsigned)(ADDR(r.symbol) + r.addend − refaddr). For R_X86_64_32, *refptr = (unsigned)(ADDR(r.symbol) + r.addend).

For the call, ADDR(.text) = 0x4004d0 and ADDR(sum) = 0x4004e8. refaddr = 0x4004d0 + 0xf = 0x4004df. *refptr = 0x4004e8 + (−4) − 0x4004df = 0x5. The relocated instruction is 4004de: e8 05 00 00 00 callq 4004e8. At run time the call is at 0x4004de and the PC is 0x4004e3. The CPU pushes the PC and sets PC ← 0x4004e3 + 0x5 = 0x4004e8.

For array, r.offset = 0xa, addend 0, ADDR(array) = 0x601018, so the reference becomes 0x601018. The instruction is 4004d9: bf 18 10 60 00 mov $0x601018, %edi. Figure 7.12 shows the relocated .text and the eight data bytes 01 00 00 00 02 00 00 00 at 0x601018. 7.8 · executable object files

A packing list for two memory segments

A fully linked ELF executable looks like a relocatable file with two extras. The ELF header now stores the entry point, the address of the first instruction. A program header table maps contiguous chunks of the file onto contiguous chunks of memory. There is no .rel.text anymore. The blanks are already filled.

Figure 7.14 has two LOAD rows. The code segment is read and execute, starts at 0x400000, and is 0x69c bytes both in the file and in memory. The data segment is read and write, starts at 0x600df8, takes 0x228 bytes from the file and 0x230 bytes in memory. The extra 8 bytes are .bss, filled with zeros at run time.

The linker must pick a start address vaddr so that vaddr mod align equals off mod align. For the data segment both sides equal 0xdf8. That alignment is what lets the loader later map file pages onto memory pages. Chapter 9 explains why.

Try it: Tap a segment. Press Check alignment on the data segment and watch both remainders come out to 0xdf8.

What the book says

Figure 7.13: an executable has an ELF header, a segment header table (program header table), sections including .init, and a section header table. .init defines _init, called from the startup code. The file is fully relocated, so it needs no .rel sections. Symbol tables and debugging info are not loaded into memory. The entry point is the address of the first instruction.

Figure 7.14, for prog: the first LOAD has off 0, vaddr 0x400000, filesz 0x69c, memsz 0x69c, flags r-x, align 2**21. 7.9 · loading executable object files

The loader jumps to _start, not to main

Hana types ./prog. The shell does not know that name, so it calls the loader. Any Linux program can do the same with execve. The loader copies the code and data segments into a run-time memory image and jumps to the entry point.

That entry point is always _start, from crt1.o, the same for every C program. _start calls __libc_start_main, which sets up the world, calls main, and deals with the return value. The picture in the book puts code at 0x400000, then data, then a heap that grows up when you call malloc, then a gap for shared libraries, then a stack that grows down from just under 2^48. Above that is the kernel.

The drawing is a simplification. The aside says the loader does not really copy. It maps pages, and the bytes move from disk only when the CPU touches them. There is also a gap between code and data because of alignment, and ASLR slides the stack, the heap, and the shared libraries each run. Their order stays the same.

Try it: Press Step to fill the image and walk _start → __libc_start_main → main. Switch to the aside: nothing is copied until a page is touched.

What the book says

linux> ./prog makes the shell invoke the loader, because prog is not a built-in command. Any Linux program can call the loader through execve (Section 8.4.6). Loading copies the executable’s code and data into memory and jumps to the entry point.

Figure 7.15, not to scale, and with alignment gaps and ASLR omitted: code starts at 0x400000, then the read/write segment (.data, .bss), then the run-time heap created by malloc and growing up via brk, then a memory-mapped region for shared libraries, then the user stack growing down from the largest legal user address. Kernel memory begins at 2^48 and is invisible to user code. The loader then jumps to _start in crt1.o. _start calls __libc_start_main in libc.so, which initializes the environment, calls main, and if necessary returns to the kernel.

The aside: each program runs in a process with its own virtual address space. The shell forks a child; the child calls execve. The loader deletes the old segments and creates code, data, heap, and stack segments. Heap and stack start as zero. Code and data are initialized by mapping pages to page-size chunks of the file. Aside from some header information, nothing is copied at load time. A copy happens later, when the CPU references a mapped page.

7.10 · dynamic linking with shared libraries

One cookbook, many kitchens

A static library still has two problems. To pick up a fix, every program must be relinked. And almost every C program has its own copy of printf in memory. Hundreds of processes means hundreds of copies.

A shared library (.so on Linux, a DLL on Microsoft systems) is loaded at an arbitrary address and linked in memory by the dynamic linker. It is shared twice: one .so file on disk for every program that names it, and one copy of its .text in memory for every process that runs it. Each process still gets its own writable data.

Building prog2l does not copy libvector.so into the executable. It copies relocation and symbol-table notes. At load time the loader sees a .interp section, runs ld-linux.so, and that program places libc.so and libvector.so and patches the references. From then on, those addresses stay put.

Try it: On “why share,” press Run and count copies of printf. On “build prog2l,” press Step: the .so stays out of the executable until ld-linux.so runs.

What the book says

Static libraries must be explicitly relinked when they change. Also, code for printf and scanf is duplicated in the text segment of every running process. A shared library is an object module that can be loaded at an arbitrary memory address and linked with a program in memory, at run time or load time. This is dynamic linking, done by a dynamic linker. On Linux the suffix is .so. Microsoft operating systems call them DLLs.

Shared in two ways: exactly one .so file on a file system, whose code and data are shared by every executable that references the library (instead of being copied in, as with a static library); and a single in-memory copy of the .text section, shared by different running processes (Chapter 9). gcc -shared -fpic -o libvector.so addvec.c multvec.c builds the library. -fpic asks for position-independent code. gcc -o prog2l main2.c ./libvector.so creates a partially linked executable. No code or data from libvector.so is copied into prog2l. The linker copies relocation and symbol table information.

When the loader runs prog2l, it notices the .interp section, whose contents are the path of the dynamic linker (ld-linux.so). The dynamic linker relocates libc.so and libvector.so into memory segments and relocates references in prog2l to symbols they define, then passes control to the application. After that, the shared libraries’ locations do not change during the run.

7.11 · loading shared libraries from applications

Ask for a library while the program is already running

Load-time linking happens before main. A program can also call the dynamic linker itself, in the middle of a run, for a library it never named at compile time.

Nadia’s dll.c calls dlopen("./libvector.so", RTLD_LAZY), then dlsym to get addvec, then calls it on {1,2} and {3,4}. The sum lands in z as {4,6}. dlclose unloads the library if nobody else is using it. dlerror explains a failure. The build line is gcc -rdynamic -o prog2r dll.c -ldl.

That is also how a busy web server can avoid fork and execve for every custom page. It keeps each page’s function in a shared library, loads it on the first request, and later requests are an ordinary call. The function stays cached. Java’s JNI does the same kind of thing: the interpreter dlopens a .so of native code.

Try it: Step through dll.c and watch z fill in. Then switch to the server: send the same request twice. The CGI path forks every time. The dlopen path loads once.

What the book says

An application can ask the dynamic linker to load and link arbitrary shared libraries while it is running, without having linked against them at compile time. Windows applications ship updates this way. High-performance web servers package each dynamic-content function in a shared library and call it directly, instead of fork and execve of a CGI program. The function stays cached, so the next request is a function call. Functions can be updated without stopping the server.

dlopen loads and links filename and returns a handle, or NULL. Symbols are resolved using libraries previously opened with RTLD_GLOBAL. With -rdynamic, the executable’s globals are available too. The flag includes RTLD_NOW (resolve immediately) or RTLD_LAZY (defer until the code runs), optionally ored with RTLD_GLOBAL. dlsym returns a symbol’s address or NULL. dlclose unloads the library if no other shared library is still using it, returning 0 or −1. dlerror returns the most recent error string, or NULL.

7.12 · position-independent code

A library that can sit on any shelf

If every shared library had a reserved street number, the loader’s job would be easy and the address space would rot. Unused libraries would still own their chunk. A new version that no longer fits would need a new chunk. Hundreds of libraries would leave the map full of holes that are free and still useless. And every machine would need the same assignment.

Position-independent code can be loaded anywhere without the linker rewriting the code bytes. Then one copy of the code segment can be mapped into as many processes as you like. Each process still gets its own read/write data. gcc -fpic asks for this. Shared libraries must be built that way.

References inside the same executable are already fine: PC-relative addressing, patched once by the static linker. References to globals and functions that live in a shared module need the GOT and the PLT, which are the next two scenes.

Try it: Press Add library. In the reserved-slot world the newcomer has nowhere to sit. In the PIC world it takes the next free place, and both processes share its code.

What the book says

One approach would assign each shared library a dedicated chunk of the address space and always load it there. That wastes space for libraries a process does not use, is hard to keep from overlapping, breaks when a library no longer fits its chunk, and fragments the address space into unusable holes. The assignment would also differ from system to system.

Modern systems compile shared-module code so it can be loaded anywhere without being modified by the linker. A single copy of the code segment can then be shared by an unlimited number of processes. Each process still gets its own copy of the read/write data segment. Code that needs no relocations is position-independent code (PIC). gcc -fpic generates it. Shared libraries must always be compiled with this option.

On x86-64, references to symbols in the same executable need no special PIC treatment: they use PC-relative addressing and are relocated by the static linker when the object file is built. References to external procedures and to global variables defined by shared modules need the techniques in the rest of the section.

7.12 · PIC data references

The distance stays. The address lives in the GOT.

No matter where a shared module is loaded, its data segment stays the same distance from its code segment. So the distance from an instruction to a slot in the data segment is a constant, even though the absolute addresses are not.

The compiler builds a global offset table at the start of the data segment. Each global the module uses gets an 8-byte slot. At load time the dynamic linker fills those slots with absolute addresses. The code does not change. It loads a slot with a PC-relative mov, then uses the address it found.

In Figure 7.18, addvec does mov 0x2008b9(%rip), %rax and then addl $0x1, (%rax). That adds one to addcnt. The constant 0x2008b9 is the distance to GOT[3]. Move the whole library and the distance is still 0x2008b9. Only the value stored in the slot changes.

Try it: Press Step to run the two instructions. Then Move library: the code bytes stay the same, the gap label stays 0x2008b9, and GOT[3] points at addcnt in its new place.

What the book says

No matter where an object module is loaded, the data segment is always the same distance from the code segment. The distance between any instruction and any variable in the data segment is a run-time constant.

Compilers create a global offset table (GOT) at the beginning of the data segment, with an 8-byte entry for each global object the module references. The compiler also generates a relocation record for each GOT entry. At load time the dynamic linker fills each entry with the object’s absolute address. Each object module that references global objects has its own GOT.

Figure 7.18: addvec in libvector.so executes mov 0x2008b9(%rip), %rax so that %rax becomes *GOT[3], which is &addcnt, then addl $0x1, (%rax). The distance 0x2008b9 between GOT[3] and the addl is a run-time constant. The compiler uses the GOT even for addcnt, which this module itself defines, because that is the general solution when the variable might live in another shared module.

7.12 · PIC function calls

The first call pays. The rest are one jump.

A call to a function in a shared library cannot bake the function’s address into the code. That would mean rewriting the code segment, and then it could not be shared. Patching every function at load time would also be wasteful: a program uses a handful of the thousands of functions in libc.so.

Lazy binding waits until the first real call. The procedure linkage table is a row of 16-byte stubs in the code segment. PLT[0] jumps into the dynamic linker. PLT[2] is addvec. The matching GOT[4] starts out pointing at the next instruction inside that stub, 0x4005c6, not at addvec.

The first call bounces stub → GOT → back into the stub → PLT[0] → dynamic linker. The linker writes &addvec into GOT[4] and jumps there. The next call is stub → GOT → addvec, one indirect jump.

Try it: Press Step through the first call. Watch GOT[4] change from 0x4005c6 to &addvec. Press Step again: the second call skips the linker.

What the book says

The compiler cannot predict the run-time address of a shared-library function. A relocation record on the call would force the dynamic linker to modify the caller’s code segment, which is not PIC. Lazy binding defers the binding until the first call. A typical program calls only a handful of the hundreds or thousands of functions in libc.so, so the linker skips the rest at load time. The first call has a nontrivial cost. Each later call is a single instruction plus a memory reference.

The PLT is an array of 16-byte code entries in the code segment. PLT[0] jumps into the dynamic linker. PLT[1] (not shown) invokes __libc_start_main. Entries from PLT[2] invoke user-called functions: PLT[2] is addvec, PLT[3] is printf. The GOT is 8-byte addresses in the data segment. GOT[2] is the dynamic linker’s entry in ld-linux.so. Initially each function’s GOT entry points at the second instruction of its PLT entry. GOT[4] starts as 0x4005c6.

Figure 7.19(a), first call: (1) call PLT[2] at 0x4005c0; (2) jmpq *GOT[4] returns to pushq $0x1 in the same stub; (3) push the id 0x1 and jump to PLT[0] at 0x4005a0; (4) PLT[0] pushes *GOT[1] and jumps through *GOT[2] into the dynamic linker, which overwrites GOT[4] with &addvec and transfers to addvec. Figure 7.19(b): the same indirect jump through GOT[4] now goes straight to addvec.

7.13 · library interpositioning

Stand in the doorway and take a note

Ines wants a diary of every malloc and free. She writes a wrapper with the same shape as the real function. The wrapper does its own work, calls the real function, and returns whatever that returned. The caller thinks it called malloc.

Linux can arrange that trick at three times. Compile time needs the source, so the preprocessor can rewrite the call. Link time needs the relocatable .o files, so the linker can rename the symbol. Run time needs only the executable: a shared library is placed first in the search.

The next three scenes open those three doorways. This one is the idea they share. int.c does malloc(32) and free(p). The trace appears only if a wrapper is standing in the path.

Try it: Pick a doorway, then press Call malloc. The files on the desk change with the doorway. The trace appears underneath.

What the book says

Library interpositioning lets you intercept calls to shared library functions and run your own code instead. You can count calls, trace arguments and return values, or replace the function.

You write a wrapper whose prototype matches the target. Some interpositioning mechanism makes the system call the wrapper instead. The wrapper typically runs its own logic, calls the target, and passes the return value back.

Interpositioning can happen at compile time, at link time, or at run time as the program is loaded. The running example, Figure 7.20(a), is int.c: malloc(32) then free(p). The goal is to trace those calls.

7.13.1 · compile-time interpositioning

The preprocessor rewrites the call

A local header malloc.h says: whenever you see malloc(size), pretend the programmer wrote mymalloc(size). Same for free. The wrappers live in mymalloc.c. They call the real functions, print a line, and return.

The trick is -I. That tells the preprocessor to look in the current directory before the system headers. int.c is compiled with that flag, so it picks up the local header. mymalloc.c is compiled with -DCOMPILETIME and the ordinary system malloc.h, so the wrapper’s own call to malloc is not rewritten into a call to itself.

Forget -I. and the system header wins. The source still says malloc, the wrapper is never called, and the trace stays empty. With the flag, ./intc prints malloc(32)=0x9ee010 and free(0x9ee010).

Try it: Leave -I. on and press Preprocess. The call in the listing changes to mymalloc. Turn the flag off and the call stays malloc.

What the book says

7.13.2 · link-time interpositioning

The linker renames the symbol

This time the source is left alone. int.o still mentions malloc. The link line carries -Wl,--wrap,malloc and the same for free. -Wl passes the rest to ld, and each comma becomes a space, so the linker sees --wrap malloc.

That flag means: a reference to malloc is resolved as __wrap_malloc, and a reference to __real_malloc is resolved as the real malloc. The wrapper calls __real_malloc, prints, and returns. Without the flag, int.o’s malloc goes straight to libc and the diary stays blank.

./intl prints malloc(32) = 0x18cf010 and free(0x18cf010). You needed the .o files. You did not need to rewrite the source.

Try it: Press Link with the wrap flag on, then off. The arrows in the picture show which name each reference becomes.

What the book says

The static linker’s --wrap f flag resolves references to f as __wrap_f, and references to __real_f as f. Figure 7.21, under LINKTIME, declares __real_malloc and __real_free. __wrap_malloc calls __real_malloc and prints malloc(%d) = %p. __wrap_free calls __real_free and prints.

7.13.3 · run-time interpositioning

A library that cuts in line

Compile-time wrapping needs source. Link-time wrapping needs .o files. LD_PRELOAD needs only the executable. If that variable names shared libraries, ld-linux.so searches them first, before libc.so, whenever it resolves an undefined reference.

The run-time wrapper is itself named malloc. It calls dlsym(RTLD_NEXT, "malloc") to find the next malloc down the line — libc’s — then calls that and prints. Build the wrapper with gcc -DRUNTIME -shared -fpic -o mymalloc.so mymalloc.c -ldl. Build the program with a plain gcc -o intr int.c. Run it as LD_PRELOAD="./mymalloc.so" ./intr.

The same variable works on a program you did not write. LD_PRELOAD="./mymalloc.so" /usr/bin/uptime prints a stream of malloc lines and then the clock. Turn the variable off and uptime is quiet again.

Try it: Run ./intr with preload on and off. Then run uptime. The search list puts mymalloc.so ahead of libc.so only while the variable is set.

What the book says

If LD_PRELOAD is a list of shared-library pathnames separated by spaces or colons, the dynamic linker searches those libraries first when resolving undefined references. You can interpose on any function in any shared library, including libc.so, for any executable.

7.14 · tools for object files

Eight ways to open the binary

The GNU binutils package is on every Linux system, and it is how you look inside the files this chapter has been building. Each tool answers one question.

ar packs and lists archive members. strings pulls out the readable text. strip deletes the symbol table. nm lists symbols. size lists section sizes. readelf shows the whole ELF structure, including what size and nm show. objdump can show everything, and its party trick is disassembling .text. ldd is separate: it lists the shared libraries an executable will need when it runs.

What the book says

objdump can display all of the information in an object file. Its most useful function is disassembling the binary instructions in .text. Linux also provides ldd, which lists the shared libraries that an executable needs at run time.
