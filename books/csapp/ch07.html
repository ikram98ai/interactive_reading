Linking

Two notebooks become one running program. A quiet program called the linker does the gluing — and if two pages claim the same name, the glue can go wrong without a peep.

“Linking is the process of collecting and combining various pieces of code and data into a single file that can be loaded (copied) into memory and executed.”

New here? Read the short story, then press the buttons on the picture. You cannot break it. The book’s exact file names and figure numbers live under “What the book says.”

Big idea 1 · compiler drivers

A receptionist who calls four specialists

Mei types one line: gcc -Og -o prog main.c sum.c. She thinks one program did everything. Really a compiler driver is a receptionist. It calls the preprocessor, the compiler, the assembler, and the linker, in that order, then goes home.

Each specialist leaves a new file on the desk. main.c becomes main.i, then main.s, then a binary main.o. The same walk happens for sum.c. Only then does the linker glue the object files into prog.

When she types ./prog, the shell asks the operating system’s loader to copy that file into memory and start it. Linking already happened. Loading is a later trip.

Try it: Press Step. Watch Figure 7.1’s main.c walk through cpp, cc1, and as, then meet sum.o at ld.

What the book says

Figure 7.1 is the running example: main.c declares int sum(int *a, int n), defines int array[2] = {1, 2}, and returns sum(array, 2). sum.c adds the n elements. The discussion is x86-64 Linux using ELF-64 (called ELF in the chapter). Concepts are the same on other systems; details vary.

The driver command is gcc -Og -o prog main.c sum.c. It runs cpp to make /tmp/main.i, then cc1 … -Og … -o /tmp/main.s, then as … -o /tmp/main.o /tmp/main.s, the same path for sum.o, then ld -o prog [system object files and args] /tmp/main.o /tmp/sum.o. In some versions of gcc the preprocessor lives inside the driver.

./prog is not a built-in shell command, so the shell invokes the loader, which copies code and data into memory and transfers control to the start of the program. Run gcc -v if you want to see the real argument lists.

gcc -Og -o prog main.c sum.cmain.c

        Big idea 2 · static linking
        
Two notebooks glued into one book

        
Amara compiled main.c on Monday and sum.c on Tuesday. Each .o file is a notebook of sections — one run of bytes for instructions, one for initialized globals, one for zeros. The static linker ld reads those notebooks and writes a single executable.

        
It has two jobs. First it matches every name that is used with exactly one place that defines it — symbol resolution. Then it slides the sections to real addresses and rewrites the blanks the assembler left — relocation.

        
The linker is not a second compiler. It concatenates blocks of bytes and patches a few numbers. The compilers and assemblers already did the thinking.

        
Try it: Press Step. First the sum name finds its definition. Then the sections get run-time addresses from Figure 7.12.

        

          What the book says
          

            
Static linkers such as Linux ld take relocatable object files and command-line arguments and emit a fully linked executable. Instructions live in one section, initialized globals in another, uninitialized variables in a third.

            
Step 1, symbol resolution: each symbol is a function, a global variable, or a C static variable, and each reference is associated with exactly one definition. Step 2, relocation: compilers and assemblers emit sections that start at address 0. The linker assigns a memory location to each definition and rewrites references. “The linker blindly performs these relocations using detailed instructions, generated by the assembler, called relocation entries.”

            
“Object files are merely collections of blocks of bytes.” A linker concatenates blocks, chooses run-time locations, and modifies locations inside the code and data. “Linkers have minimal understanding of the target machine.”

        Big idea 3 · object files
        
A sandwich with a label on each filling

        
Diego opens main.o. It is not a text file. It is an ELF sandwich: a header that says “this is a relocatable x86-64 object,” then fillings, then a table that says where each filling starts. Three kinds of sandwich exist — relocatable, executable, and shared.

        
Instructions sit in .text. Initialized globals sit in .data. Uninitialized globals, and anything initialized to zero, sit in .bss. That last filling is a trick: it takes no disk space. The file just promises “leave me this many zero bytes in memory.”

        
A roster of names lives in .symtab. Notes for the linker — “please patch this call later” — live in .rel.text. Local C variables do not appear. They will live on the stack when the program runs.

        
Try it: Tap a section, or press Next section. Read what that filling is for. Notice that .bss is a placeholder.

        

          What the book says
          

            
Three forms: a relocatable object file can be combined at compile time; an executable can be copied into memory and run; a shared object can be loaded and linked at load time or run time. Compilers and assemblers emit relocatable files (including shared objects); linkers emit executables. Early Unix used a.out (the name stuck); Windows uses PE; Mac OS-X uses Mach-O; modern x86-64 Linux and Unix use ELF.

            
Figure 7.3: the ELF header begins with a 16-byte sequence for word size and byte ordering, then type, machine, and the section-header-table offset. Typical sections: .text, .rodata (printf format strings, switch jump tables), .data, .bss, .symtab, .rel.text, .rel.data, .debug and .line (only with -g), and .strtab. “This section occupies no actual space in the object file; it is merely a placeholder.”

            
.bss was the IBM 704 “block started by symbol” directive, circa 1957. A mnemonic: “Better Save Space!” Every relocatable file has a .symtab unless someone ran strip; it does not list ordinary local variables, and you do not need -g to get it.

        Big idea 4 · symbols and symbol tables
        
The class roster is not the same as the lockers

        
Kenji writes swap.c. Lucia writes m.c with a global buf[2] = {1, 2} and calls swap. The linker’s roster for Kenji’s file has public names, names he borrowed, and names he marked static so they stay in his classroom.

        
Those local linker symbols are not the same as a local variable like temp. temp lives on the stack. It never gets a row in .symtab. But if two functions in one file each write static int x, the compiler invents unique roster names — x.1 and x.2 — and parks them in .data or .bss.

        
Try it: Tap a name from Practice Problem 7.1. Switch to static locals to see x.1 and x.2. temp has no row.

        

          What the book says
          

            
Three kinds of linker symbols in module m: globals defined by m (nonstatic C functions and globals); externals referenced by m but defined elsewhere; and local linker symbols (C functions and globals declared static). “It is good programming practice to protect your variables and functions with the static attribute wherever possible.”

            
Figure 7.4 Elf64_Symbol: name (string-table offset), 4-bit type and binding, section, value (section offset in a relocatable file, absolute address in an executable), size. Pseudosections: ABS, UNDEF, COMMON (value = alignment, size = minimum). Modern gcc: COMMON = uninitialized globals; .bss = uninitialized statics and globals or statics initialized to zero. That split exists because of the resolution rules in Section 7.6.

            
readelf on main.o: main is a 24-byte FUNC GLOBAL in Ndx=1 (.text) at value 0; array is an 8-byte OBJECT GLOBAL in Ndx=3 (.data) at value 0; sum is NOTYPE GLOBAL UND. Figure 7.5 / Practice 7.1: in swap.o, buf is extern from m.o .data; bufp0 global .data; bufp1 global COMMON; swap global .text; temp has no entry.

        Big idea 5 · symbol resolution
        
Two lockers, one name — or a librarian who skips unread books

        
Omar writes int x = 15213. Priya writes a bare int x in another file and, in f, stores 15212. The compiler is fine. The linker sees one strong name (initialized) and one weak name (uninitialized), quietly keeps Omar’s, and Priya’s write still hits that same x. The printout is 15212. No error in the default case.

        
Two strong names with the same spelling — two mains, or two int x = 15213s — is a hard error. Two weaks: the linker picks either. Different types make it nastier: an int x next to a double x can smear a neighbour.

        
Libraries are a second trap. A .a archive is a shelf of object files. The linker walks the command line left to right and only pulls a member that defines a name it still needs. Put the archive before the file that uses addvec, and the shelf is empty of requests — so nothing is pulled, and addvec stays undefined.

        
Try it: On strong / weak, pick a pair of modules and press Link. On archive, Step the left-to-right walk, then flip the order and watch it fail.

        

          What the book says
          

            
Functions and initialized globals are strong; uninitialized globals are weak. Rule 1: multiple strong symbols with the same name are not allowed. Rule 2: strong plus weaks → choose the strong. Rule 3: several weaks → choose any. foo3.c / bar3.c print x = 15212 with no multiply-defined warning. foo5.c (int y = 15212; int x = 15213) plus bar5.c (double x; x = -0.0) can print x = 0x0 y = 0x80000000 after an alignment warning. Use -fno-common or -Werror.

            
ISO C99’s atoi, printf, strcpy, rand live in libc.a (about 5 MB); sin, cos, sqrt live in libm.a (about 2 MB). A single libc.o would waste disk and memory. Figure 7.6–7.8: ar rcs libvector.a addvec.o multvec.o, then gcc -static -o prog2c main2.o ./libvector.a (or -L. -lvector). Only addvec.o is copied; multvec.o is not. The driver already passes libc.a.

            
Left-to-right scan: sets E (files to merge), U (unresolved), D (defined). An archive member is pulled only if it resolves something in U, iterating to a fixed point. “The general rule for libraries is to place them at the end of the command line.” gcc -static ./libvector.a main2.c fails: U is empty while the archive is scanned, so addvec is never resolved.

A strong name beats a weak one. An archive only donates members that settle a name the linker still needs.

      

    

  


  

    

      

        Big idea 6 · relocation
        
Fill in the street number once you know the block

        
Soren’s assembler wrote callq with four zero bytes after the opcode. It did not know where sum would live. It left a sticky note: “this is a 32-bit PC-relative reference to sum, starting at offset 0xf, addend −4.”

        
After resolution, the linker knows the run-time addresses. It merges same-named sections, assigns each a home, then patches every sticky note. For a PC-relative call the new number is ADDR(sum) + addend − refaddr. Here that is 0x5, so the CPU will land on sum.

        
An absolute reference is simpler: write ADDR(array) itself. That is how %edi gets &array at 0x601018.

        
Try it: Press Relocate on the sum call. Switch to the array move and do it again. The formula sits in the picture.

        

          What the book says
          

            
Relocation: (1) merge sections of the same type and assign run-time addresses; (2) rewrite references using relocation entries (.rel.text, .rel.data). Figure 7.9 Elf64_Rela: offset, type, symbol, addend. ELF defines 32 relocation types; the chapter uses two. R_X86_64_PC32 is a 32-bit PC-relative address (PC is the next instruction). R_X86_64_32 is a 32-bit absolute address. Both support the small code model (code plus data smaller than 2 GB), gcc’s default.

            
Figure 7.10: *refptr = ADDR(r.symbol) + r.addend - refaddr for PC32, with refaddr = ADDR(s) + r.offset; for type 32, *refptr = ADDR(r.symbol) + r.addend. Figure 7.11 main.o: call at offset 0xe, opcode 0xe8, r.offset = 0xf, symbol sum, PC32, addend −4. With ADDR(.text) = 0x4004d0 and ADDR(sum) = 0x4004e8, refaddr = 0x4004df and the field becomes 0x5. At run time PC is 0x4004e3; PC + 0x5 = 0x4004e8.

            
The array move: opcode 0xbf, r.offset = 0xa, type 32, addend 0, ADDR(array) = 0x601018. Figure 7.12 is the relocated .text and .data. After that, the loader can copy the bytes with no further patches.

        Big idea 7 · executables and loading
        
A moving truck with a packing list

        
Yara’s prog is a finished book. The ELF header now stores an entry point. There is a new program header table — a packing list that maps file chunks onto memory segments. Relocation notes are gone. The file is meant to be copied, not patched again.

        
The list has two LOAD rows. Code (read and execute) starts at 0x400000. Data (read and write) starts at 0x600df8. Eight extra bytes in memory are .bss zeros that were never stored on disk.

        
The loader builds a memory picture: code, data, a heap that grows up, a hole for shared libraries, a stack that grows down from just below 248 − 1, and the kernel above 248. Then it jumps not to main but to _start.

        
Try it: Press Step. Watch the two LOAD segments land, then the jump to _start. The other mode is the packing list itself.

        

          What the book says
          

            
Figure 7.13: an executable looks like a relocatable file plus a segment header table, an .init section (_init), and no .rel sections. The ELF header includes the entry point. Figure 7.14 for prog: code LOAD off 0, vaddr 0x400000, filesz = memsz = 0x69c, flags r-x, align 221. Data LOAD off 0xdf8, vaddr 0x600df8, filesz 0x228, memsz 0x230, flags rw-. The extra 8 bytes are .bss. The linker chooses vaddr so vaddr mod align = off mod align (here both sides are 0xdf8). That helps virtual memory map file pages.

            
Figure 7.15: on Linux x86-64 the code segment starts at 0x400000, then data, then the heap via malloc, then a region for shared modules. The user stack starts below 248 − 1 and grows down. Kernel memory starts at 248. The picture hides alignment gaps and ASLR; the linker randomizes stack, shared-library, and heap addresses, but relative order stays the same.

            
The shell runs ./prog via the loader (execve). The loader copies chunks using the program header table, then jumps to _start in crt1.o — the same for every C program. _start calls __libc_start_main in libc.so, which sets up the environment, calls main, and handles the return. The book’s “copy” story is the conceptual one; Chapter 9 will replace it with page mapping.

Two LOAD rows become two memory segments. Control starts at _start, not at main.

      

    

  


  

    

      

        Big idea 8 · shared libraries
        
One cookbook on a public shelf

        
If every kitchen photocopies the whole standard cookbook, the house runs out of shelves. A shared library (.so on Linux, DLL on Windows) is one book on a public shelf. Executables keep a note, not a copy. At load time a dynamic linker finishes the glue.

        
Nadia builds libvector.so with -shared -fpic, then prog2l from main2.c. None of the library’s code is copied into prog2l. The loader sees a .interp path — ld-linux.so — and runs that first. It parks libc.so and libvector.so in memory and patches prog2l’s references. After that the addresses stay put.

        
A running program can also fetch a library later: dlopen, dlsym, call, dlclose. Web servers use that to add a page-builder without restarting.

        
Try it: Step the load-time walk for prog2l. Switch to dll.c and Step dlopen → dlsym → addvec → dlclose.

        

          What the book says
          

            
Static libraries still waste memory (every process copies printf) and need a relink after an update. A shared library can be loaded at an arbitrary address at load time or run time. Linux suffix .so; Microsoft DLLs. One .so file is shared by every executable that references it, and one in-memory .text can be shared by processes (Chapter 9).

            
Build: gcc -shared -fpic -o libvector.so addvec.c multvec.c. Link: gcc -o prog2l main2.c ./libvector.so. No code or data from the .so is copied into prog2l — only relocation and symbol-table info. The loader maps prog2l, sees .interp (e.g. ld-linux.so), and runs the dynamic linker, which relocates libc.so, libvector.so, and references in prog2l, then passes control to the app.

            
Figure 7.17 dll.c: dlopen("./libvector.so", RTLD_LAZY), dlsym(handle, "addvec"), call, dlclose. Flags: RTLD_NOW or RTLD_LAZY, optionally or-ed with RTLD_GLOBAL; -rdynamic exports the executable’s globals. Also dlerror. Uses the book names: Windows updates, high-performance Web servers (versus fork/execve CGI), and Java Native Interface (JNI) via a similar dlopen.

          

        

      

      

        
Figure 7.16–7.17 · .so then dlopen

        

        

        
The executable keeps notes, not a photocopy. ld-linux.so finishes the addresses when the program is loaded — or when Nadia calls dlopen.

      

    

  


  

    

      

        Big idea 9 · position-independent code
        
A library that works at any street number

        
If every shared cookbook needed a reserved address, the city map would fragment. So the code is compiled to sit anywhere without being rewritten. That is position-independent code (PIC). -fpic is required for shared libraries.

        
Hiro’s trick: no matter where you drop the module, the data segment stays a fixed distance from the code. A global offset table (GOT) at the start of data holds 8-byte addresses. addvec loads &addcnt from GOT[3] with a PC-relative offset — 0x2008b9 in the book’s picture — then increments through that pointer.

        
Calls into another shared module must not patch the code either. A procedure linkage table (PLT) plus lazy binding waits until the first call. The first time, GOT[4] still points back into the PLT, and the dynamic linker fills in &addvec. After that, one indirect jump is enough.

        
Try it: On GOT, press Step to increment addcnt through the table. On PLT, Step the first call (four hops), then the next call (two hops).

        

          What the book says
          

            
Reserved address chunks for each library waste space and fragment. PIC code needs no load-time patches in the code segment, so many processes can share one copy (each still gets its own data). Same-module references can use PC-relative addressing and be relocated by the static linker. External procedures and globals in shared modules need GOT / PLT.

            
Figure 7.18: the GOT sits at the beginning of the data segment; one 8-byte entry per referenced global; the dynamic linker fills absolute addresses at load time. addvec does mov 0x2008b9(%rip), %rax then addl $0x1, (%rax). The compiler uses the GOT even for addcnt defined in the same .so, as the general solution.

            
Figure 7.19: the PLT is 16-byte code entries in the code segment. PLT[0] jumps into the dynamic linker; PLT[1] is __libc_start_main; PLT[2] is addvec. GOT[2] is the dynamic-linker entry; GOT[4] matches PLT[2] and initially points at the second instruction of that PLT entry. First call: call PLT[2] → jmp *GOT[4] (back into PLT[2]) → push id 0x1 → PLT[0] → linker overwrites GOT[4]. Later calls: jmp *GOT[4] goes straight to addvec.

          

        

      

      

        
Figure 7.18–7.19 · GOT and PLT

        

        

        
Code never moves its own bytes. The GOT holds addresses; the PLT fills one of them on the first call.

      

    

  


  

    

      

        Big idea 10 · library interpositioning
        
Stand in the doorway and take a note

        
Fatima wants a trace of every malloc(32) and free in the book’s tiny int.c. She writes a wrapper with the same prototype, does her own work, then calls the real function. The trick is making the system knock on her door first.

        
Three doors. At compile time a local malloc.h #defines the names, and -I. makes the preprocessor see that header first. At link time --wrap malloc turns calls into __wrap_malloc and lets her reach the real one as __real_malloc. At run time she builds mymalloc.so and sets LD_PRELOAD so the dynamic linker searches her library first — even for /usr/bin/uptime.

        
Try it: Pick compile, link, or run, then press Call malloc. The wrapper always prints; only the doorway changes.

        

          What the book says
          

            
Figure 7.20 int.c calls malloc(32) and free. Compile-time: local malloc.h maps those names to mymalloc / myfree; gcc -DCOMPILETIME -c mymalloc.c then gcc -I. -o intc int.c mymalloc.o. Trace: malloc(32)=0x9ee010 then free(0x9ee010).

            
Link-time: --wrap f resolves f as __wrap_f and __real_f as f. gcc -Wl,--wrap,malloc -Wl,--wrap,free -o intl int.o mymalloc.o (-Wl, passes options, commas become spaces). Trace: malloc(32) = 0x18cf010.

            
Run-time: LD_PRELOAD is a space- or colon-separated list of .so pathnames searched first by ld-linux.so. Build gcc -DRUNTIME -shared -fpic -o mymalloc.so mymalloc.c -ldl; run LD_PRELOAD="./mymalloc.so" ./intr (bash) or the setenv form in csh/tcsh. Wrappers use dlsym(RTLD_NEXT, "malloc"). The same preload traces /usr/bin/uptime. Compile-time needs source; link-time needs .o files; run-time needs only the executable.

Same wrapper idea, three doorways. Compile rewrites the source; link renames symbols; run time puts a .so first in line.

Words to know
The chapter’s grown-up words, in plain language.

      

        
compiler driver
The front desk (gcc) that runs cpp, cc1, as, and ld for you.

        
relocatable .o
Code and data that can be combined with other .o files at compile time.

        
executable
A fully linked file the loader can copy into memory and run.

        
shared object
A .so (or Windows DLL) loaded and linked at load time or run time.

        
ELF
The object-file format on modern x86-64 Linux and Unix.

        
.text / .data / .bss
Instructions; initialized globals; zeros that take no disk space.

        
strong / weak
Initialized functions and globals vs uninitialized globals. Three clash rules.

        
COMMON
A relocatable-file parking spot for uninitialized globals, until the linker picks a winner.

        
relocation entry
The assembler’s sticky note: offset, type, symbol, addend.

        
PC-relative
An offset from the next instruction. R_X86_64_PC32 uses this.

        
GOT
A table of 8-byte addresses at the start of the data segment.

        
PLT
16-byte trampolines in the code segment that lazy-bind calls.

        
PIC
Code that can be loaded at any address without rewriting its bytes.

        
loader
OS code (via execve) that maps the executable and jumps to _start.

        
interpositioning
A wrapper that runs instead of a library function, then often calls it.

        
LD_PRELOAD
Shared libraries the dynamic linker searches before libc.so.
