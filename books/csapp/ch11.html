Network Programming

A browser and a server are two programs passing notes. The notes are packets, the conversation is a connection, and the shop that answers is a few hundred lines of C.

“all network applications are based on the same basic programming model, have similar overall logical structures, and rely on the same programming interface.” — Bryant & O’Hallaron

11.1 · the client-server programming model

Ask the shop, get a parcel back

Amara’s browser wants a page. Kenji’s program owns a shelf of files. She sends a note. He reads a file. He sends the file back. She draws it. That four-beat loop is a transaction.

The shop and the customer are processes, not buildings. One laptop can run both. The dance does not change. And this is not a database transaction: nothing here is all-or-nothing.

Try it: press Step. Watch the request leave Amara, the disk file arrive at Kenji, the response fly home, and the matching line of the sketch light up.

What the book says

Every network application is based on the client-server model: a server process and one or more client processes. A server manages some resource and provides a service by manipulating it. A Web server manages disk files; an FTP server stores and retrieves files; an email server reads and updates a spool file.

Figure 11.1 is four steps. The client sends a request. The server interprets it and manipulates its resources. The server sends a response and waits for the next request. The client receives the response and manipulates it — a browser displays the page.

“Client-server transactions are not database transactions and do not share any of their properties, such as atomicity.” Here a transaction is simply a sequence of steps. Clients and servers are processes, not hosts. One host can run many of each, and a transaction can stay on one host or cross the Internet. The model is the same either way.

11.2 · networks

Just another plug on the I/O bus

To a computer, the network is not a cloud. It is another I/O device: a plug that can swallow bits or spit them out. The plug is a network adapter on the I/O bus.

When a frame arrives, the adapter copies it into main memory by DMA. The CPU does not carry those bytes itself. Sending is the same road, backwards.

Try it: press Receive and watch the bytes go adapter → memory while the CPU stays idle. Then Send the other way.

What the book says

To a host, a network is just another I/O device that serves as a source and sink for data (Figure 11.2). An adapter plugged into an expansion slot on the I/O bus provides the physical interface. Data received from the network are copied from the adapter across the I/O and memory buses into memory, typically by a DMA transfer. Data can also be copied from memory to the network.

Physically, a network is hierarchical by geographical proximity. The lowest level is a LAN spanning a building or campus. The most popular LAN technology is Ethernet, developed in the mid-1970s at Xerox PARC, evolving from 3 Mb/s to 10 Gb/s.

11.2 · Ethernet segments

Everyone hears the shout, one kid reads it

A cheap Ethernet is wires plus a hub. Lucia shouts a frame “for Omar.” The hub copies every bit onto every wire. Priya hears it too, and ignores it. Only Omar’s adapter, whose 48-bit name is on the frame, actually reads it.

A bridge is nosier and wiser. It learns who lives on which port. If A and B share a segment, bridge X throws the frame away. If C is across the building, X copies the frame only toward the port that leads to C.

Try it: send A → B, then A → C, on the hub. Switch to the bridge and send both again.

What the book says

An Ethernet segment (Figure 11.3) is wires, usually twisted pairs, and a hub. Segments typically span a room or a floor. Each wire has the same maximum bit bandwidth, typically 100 Mb/s or 1 Gb/s. “A hub slavishly copies every bit that it receives on each port to every other port. Thus, every host sees every bit.”

Each adapter has a globally unique 48-bit address in nonvolatile memory. A frame’s header identifies source, destination, and length, then a payload. Every host adapter sees the frame, but only the destination host actually reads it.

Bridges join segments into a bridged Ethernet (Figure 11.4). In the book’s picture the bridge–bridge wire is 1 Gb/s and the hub–bridge wires are 100 Mb/s. Bridges learn which hosts are reachable from which ports and copy a frame only when necessary. If host A sends to host B on the same segment, bridge X throws the frame away. If A sends to host C on a different segment, X copies only toward bridge Y, which copies only toward C’s segment.

11.2 · internets

A letter, then a new envelope at the depot

Two neighbourhoods speak different wire languages. A router sits between them. Yara’s program hands bytes to the kernel. The kernel wraps them in an internet packet, then in a local frame addressed only to the router — a parcel inside a parcel. That wrapping is encapsulation.

At the depot the old street envelope comes off. A new one, written in the next neighbourhood’s script, goes on. The inner address, host B, never changes. Lowercase internet means any mesh of LANs and WANs. Uppercase Internet is the global IP one.

Try it: step the eight hops of Figure 11.7. The payload stays the same. Only the outer frame header swaps.

What the book says

To simplify LAN pictures, the book draws hubs, bridges, and wires as one horizontal line (Figure 11.5). Routers connect incompatible LANs, and also WANs such as high-speed point-to-point phone links, into an internet (Figure 11.6: two LANs, two WANs, three routers). “We will always use lowercase internet to denote the general concept, and uppercase Internet to denote a specific implementation — namely, the global IP Internet.”

Protocol software on each host and router gives two things the wires do not share: a uniform naming scheme, and packets. A packet has a header (size and source and destination host addresses) and a payload. Figure 11.7 walks eight steps from a client on host A (LAN1) to a server on host B (LAN2). The LAN1 frame’s payload is an internet packet, whose payload is the user data. “This kind of encapsulation is one of the fundamental insights of internetworking.”

The router reads the destination internet address, indexes a routing table, strips the LAN1 frame header, and prepends a LAN2 frame header addressed to host B. Host B strips both headers and, when the server reads, copies the data into the server’s virtual address space. The book leaves open different maximum frame sizes, how routers learn routes, topology changes, and lost packets.

11.3 · the global IP Internet

One family of protocols, three promises

The global IP Internet has been around, in some form, since 1969. From a programmer’s chair it is stable: your code calls the sockets interface, those calls trap into the kernel, and kernel TCP/IP talks to the adapter.

IP names hosts and sends datagrams, and it does not care if one is lost. UDP would carry that same best-effort idea from process to process; the book sets UDP aside. TCP builds a reliable two-way connection on top of IP. The chapter treats TCP/IP as one protocol and stays on IPv4.

Try it: send a datagram and drop it. IP shrugs. Send the same bytes as a TCP stream and the lost one is repaired. The IPv6 note is the book’s aside, not a second protocol tour.

What the book says

Figure 11.8: user code sits on the sockets interface (system calls), which traps into TCP/IP kernel code, which meets the adapter at the hardware interface. Clients and servers also use Unix I/O. TCP/IP is supported by almost every modern computer system.

IP provides naming and delivery of datagrams from host to host, and “makes no effort to recover if datagrams are lost or duplicated.” UDP extends IP so datagrams can go from process to process. TCP builds reliable full-duplex connections on IP. The book treats TCP/IP as one monolithic protocol and does not discuss UDP.

From a programmer’s perspective the Internet is a worldwide collection of hosts with three properties: hosts map to 32-bit IP addresses; those addresses map to Internet domain names; a process can communicate with a process on any other host over a connection.

IPv4 is the original 32-bit protocol. In 1996 the IETF proposed IPv6, with 128-bit addresses. As of 2015, only 4 percent of users accessed Google services using IPv6, so the chapter focuses on IPv4. The client and server techniques later in the chapter use modern interfaces that are independent of any particular protocol.

11.3.1 · IP addresses

The postcard always writes the big end first

An IPv4 address is a 32-bit unsigned integer stuffed in a struct, in_addr, because the early sockets designers did it that way and it is too late to change. People write it dotted: 128.2.194.242. That is hex 0x8002c2f2.

Chips disagree about which byte of a word comes first. The wire picked one order: network byte order, big-endian. htonl and htons pack host integers for the packet. ntohl and ntohs unpack them. There is no 64-bit pair.

Try it: step through the book’s addresses, including Practice Problem 11.1. Flip host order and network order. Then pack port 80 with htons.

What the book says

Figure 11.9: struct in_addr { uint32_t s_addr; } with the address always in network (big-endian) byte order, even on a little-endian host. 128.2.194.242 is 0x8002c2f2. hostname -i on the book’s host printed 128.2.210.175.

htonl and ntohl convert 32-bit values; htons and ntohs convert 16-bit values. inet_pton and inet_ntop convert dotted-decimal strings and binary addresses (“p” presentation, “n” network). They return 1, 0, or −1 (inet_pton) and a pointer or NULL (inet_ntop). They also accept AF_INET6, which the book does not cover.

Practice Problem 11.1 asks for a dotted-decimal ↔ hex table. The solution pairs 107.212.122.205 with 0x6BD47ACD, 64.12.149.13 with 0x400C950D, 107.212.96.29 with 0x6BD4601D, 0x00000080 with 0.0.0.128, 0xFFFFFF00 with 255.255.255.0, and 0x0A010140 with 10.1.1.64.

11.3.2 · Internet domain names

A name you can say, a number the wire uses

People remember whaleshark.ics.cs.cmu.edu. Programs dial 128.2.210.175. The map used to be one file, HOSTS.TXT. Since 1988 it is a worldwide database: DNS.

A name is a path in a tree: unnamed root, then ICANN’s first-level names (com, edu, …), then cmu.edu, then whatever CMU invents underneath. Some names share one number. Some share a handful. Some legal names, like edu, have no address at all. And every host answers to localhost at 127.0.0.1.

Try it: look up the book’s names. twitter.com returns four addresses. edu returns no answer.

What the book says

A domain name is words (letters, numbers, dashes) separated by periods. Figure 11.10: an unnamed root, first-level names defined by ICANN (com, edu, gov, org, net), then second-level names such as cmu.edu, assigned first-come first-serve. An organisation that owns a second-level name may create cs.cmu.edu and so on. The figure also shows whaleshark at 128.2.210.175, a www at 128.2.131.66, and amazon’s www at 176.32.98.166.

Until 1988 the mapping lived in HOSTS.TXT. Since then it is DNS. Each host entry maps a set of names to a set of IP addresses. localhost always maps to the loopback address 127.0.0.1. whaleshark.ics.cs.cmu.edu maps to 128.2.210.175. cs.mit.edu and eecs.mit.edu both map to 18.62.1.6. www.twitter.com and twitter.com share 199.16.156.6, 199.16.156.70, 199.16.156.102, and 199.16.156.230. nslookup edu and ics.cs.cmu.edu print “No answer.”

The Internet Domain Survey counted about 20,000 hosts in 1987 and over 1,000,000,000 by 2015.

11.3.3 · Internet connections

A private phone line, both can talk

Once two processes agree to talk, they have a connection: one pair of ends, both directions at once, and the bytes arrive in the order they were sent — unless a backhoe cuts the cable.

Each end is a socket named address:port. The server usually sits on a well-known door (Web is 80, named http; email is 25, named smtp). The client gets a spare door the kernel picks — an ephemeral port. The pair of names is the connection’s ID. These software ports are not the hardware ports on a hub.

Try it: read the book’s socket pair, then send HELLO. Drop the third letter: IP loses it; TCP still delivers H E L L O.

What the book says

A connection is point-to-point, full duplex, and reliable: “the stream of bytes sent by the source process is eventually received by the destination process in the same order it was sent,” barring a catastrophe such as a cable cut by a careless backhoe operator.

A socket address is an IP address plus a 16-bit port, written address:port. The client port is an ephemeral port assigned by the kernel. Web servers typically use port 80 (well-known name http in /etc/services); email uses port 25 (smtp). A connection is the socket pair (cliaddr:cliport, servaddr:servport). Figure 11.11’s pair is (128.2.194.242:51213, 208.216.181.15:80).

11.4 · the sockets interface

A road map both sides can follow

The sockets interface is a handful of functions plus ordinary Unix I/O. Berkeley researchers built it in the early 1980s and shipped it in Unix 4.2BSD, so thousands of people suddenly had TCP/IP.

Figure 11.12 is the whole dance on one page. The server prepares a door and waits. The client knocks. Then both sides read and write until one closes, and the other sees EOF.

Try it: step the road map. The highlighted call is the one the picture is on. Client calls are on the left file; server calls are on the right.

What the book says

The sockets interface is used with the Unix I/O functions to build network applications. It exists on Unix variants and on Windows and Macintosh systems. Figure 11.12 is the road map: the server side runs getaddrinfo, socket, bind, listen, then blocks in accept; the client runs getaddrinfo, socket, and connect. After the connection, both sides use rio_readlineb and rio_writen, then close. The helpers open_clientfd and open_listenfd wrap the open sequence.

EOF on a connection is not a character. It is a condition the kernel detects. For a connection, EOF happens when the other process closes its end. The reader finds out by getting a zero return from read.

11.4.1 · socket address structures

Sixteen bytes, and a cast the old C required

To the kernel, a socket is an end of a conversation. To your program, it is just an open file with a descriptor. The address that goes with an Internet socket is 16 bytes: family, port, IP address, and padding.

connect, bind, and accept were written before void * existed, so they take a generic sockaddr *. You keep a sockaddr_in and cast it. The book’s typedef for that cast is SA. The _in means internet, not input.

Try it: pack the book’s server address 208.216.181.15 and port 80 into the 16 bytes. The last eight bytes stay zero.

What the book says

Figure 11.13: sockaddr_in has sin_family (always AF_INET for these programs), sin_port (16-bit, network byte order), sin_addr (32-bit, network byte order), and sin_zero[8] so the struct matches sizeof(struct sockaddr). The generic sockaddr has sa_family and sa_data[14].

The book follows Stevens and defines typedef struct sockaddr SA, then casts sockaddr_in * to SA * at the calls.

11.4.2 · the socket function

A door that is not open yet

socket asks the kernel for a new descriptor. For a connection you would call it with AF_INET, SOCK_STREAM, and protocol 0. Better code lets getaddrinfo fill those three arguments so the same source works for more than one IP version.

The descriptor comes back only partially opened. You cannot read or write it yet. A client finishes the job with connect. A server finishes it with bind and listen.

Try it: press socket(). Descriptor 3 appears next to stdin, stdout, and stderr. Then press try to read — it is not ready.

What the book says

socket(domain, type, protocol) returns a nonnegative descriptor, or −1 on error. A connection end point can be created with Socket(AF_INET, SOCK_STREAM, 0): AF_INET means 32-bit IP addresses, SOCK_STREAM means a connection. The best practice is to let getaddrinfo generate those arguments (Section 11.4.8).

The descriptor is only partially opened and cannot yet be used for reading and writing. How you finish opening it depends on whether you are a client or a server.

11.4.3 · the connect function

Knock, and wait until the door opens

A client finishes opening its socket by calling connect with the server’s address. The call blocks. It returns 0 when the connection exists, or −1 if it never will.

On success the kernel has filled in the client’s own address and an ephemeral port. The connection is the pair (x:y, server address:server port). The descriptor is finally ready for read and write.

Try it: press connect() and watch the call block, then wake up holding the book’s socket pair. Press no server to see the −1.

What the book says

connect(clientfd, addr, addrlen) attempts a connection to the socket address addr, with addrlen equal to sizeof(sockaddr_in). It blocks until the connection is established or an error occurs. On success clientfd is ready for reading and writing, and the connection is the socket pair (x:y, addr.sin_addr:addr.sin_port), where x is the client’s IP address and y is the ephemeral port.

As with socket, the best practice is to let getaddrinfo supply the address arguments.

11.4.4 · the bind function

Nail the shop’s address onto the door

Servers use the rest of the calls. bind asks the kernel to associate a socket address — an IP address and a port — with the descriptor socket just returned.

Until that call, the descriptor has no public name. After it, clients can aim at that address. The best practice, again, is to let getaddrinfo build the address, often the wildcard that means “any address of this host.”

Try it: press bind() and watch port 80 stick to descriptor 3. Press address taken to see bind fail.

What the book says

bind, listen, and accept are how servers establish connections. bind(sockfd, addr, addrlen) asks the kernel to associate the server’s socket address with sockfd. addrlen is sizeof(sockaddr_in). It returns 0, or −1 on error. As with socket and connect, the best practice is to let getaddrinfo supply the arguments.

11.4.5 · the listen function

Turn the door from a visitor into a shop

By default the kernel assumes a new socket is active: it will be a client and will call connect. A server calls listen to say “this one waits.” The socket becomes a listening socket.

The second argument, backlog, is a hint about how many connection requests to queue before refusing more. The book usually passes a large hint, such as 1,024. Fill a tiny queue here and the next knock is turned away.

Try it: press listen(), then knock until the queue is full. The next client is refused. accept one frees a slot.

What the book says

Clients are active; servers are passive. listen(sockfd, backlog) converts sockfd from an active socket into a listening socket that can accept connection requests. The backlog is a hint about how many outstanding requests the kernel should queue before it refuses more. The exact meaning needs more TCP/IP than the chapter covers. The book typically sets it to a large value, such as 1,024.

11.4.6 · the accept function

The shop door stays; each guest gets a table

The server blocks in accept on the listening descriptor. In the book’s picture that is descriptor 3, because 0, 1, and 2 are the standard files. Amara’s connect wakes it up. accept returns a new descriptor, connfd 4, just for her, and fills in her socket address.

The listening descriptor lives as long as the server. The connected one lasts for one client. That split is why a later chapter can fork a process per client and keep accepting on the old door.

Try it: step Figure 11.14. Then accept a second client and see listenfd 3 still waiting while connfd changes.

What the book says

accept(listenfd, addr, addrlen) waits for a connection request on the listening descriptor, fills in the client’s socket address, and returns a connected descriptor. The listening descriptor is created once and exists for the lifetime of the server. The connected descriptor is created for each accepted client and exists only while the server services that client.

Figure 11.14: the server blocks in accept on listenfd (descriptor 3). The client blocks in connect. accept returns connfd 4, the connection is between clientfd and connfd, and both calls return. The aside points out why the split exists: a concurrent server can fork a child that talks on the connected descriptor while the parent keeps accepting on the listening one. Chapter 12 builds those servers.

11.4.7 · host and service conversion

A list of addresses, then free it

getaddrinfo turns a name like twitter.com and a service like http into a linked list of addrinfo structs. Each one already holds the arguments socket and connect want. You walk the list until one works. Then you call freeaddrinfo, or the list leaks.

getnameinfo is the reverse: a socket address becomes a host string and a service string. hostinfo in Figure 11.17 uses both, restricted to IPv4 connections, and prints dotted-decimal addresses because it passes NI_NUMERICHOST.

Try it: run hostinfo on twitter.com and watch the four addresses print. Then run it again and skip freeaddrinfo.

What the book says

getaddrinfo replaces gethostbyname and getservbyname. It is reentrant and protocol-independent. Given host and service, it returns a list of addrinfo structures (Figure 11.15), each pointing at a socket address. A client tries each until socket and connect succeed; a server tries each until socket and bind succeed. Nonzero errors become strings via gai_strerror. At least one of host and service must be set.

Hints (Figure 11.16) may set ai_family, ai_socktype, ai_protocol, and ai_flags; everything else is zeroed with memset. Useful flags: AI_ADDRCONFIG, AI_CANONNAME, AI_NUMERICSERV, and AI_PASSIVE (server; host NULL; wildcard address). ai_family, ai_socktype, and ai_protocol pass straight to socket; ai_addr and ai_addrlen pass straight to connect or bind.

getnameinfo is the inverse, replacing gethostbyaddr and getservbyport. NI_NUMERICHOST asks for a numeric address; NI_NUMERICSERV asks for a port number instead of a name from /etc/services. Figure 11.17’s hostinfo, run on twitter.com, prints 199.16.156.102, 199.16.156.230, 199.16.156.6, and 199.16.156.70.

11.4.8 · open_clientfd and open_listenfd

Walk the list until one call works

The raw calls are a lot to type. open_clientfd(hostname, port) wraps them for a client: get the list, try socket then connect, close and continue on failure, free the list, return a descriptor that is ready for Unix I/O — or −1 if every candidate failed.

open_listenfd(port) does the server version with AI_PASSIVE, so the address is the wildcard. It also sets SO_REUSEADDR. Without that, a restarted server refuses connections for about 30 seconds, which makes debugging miserable. Then it calls listen.

Try it: walk a client list where the first socket fails and the second connect fails. Switch to the server and see the wildcard bind, then the 30-second trap if you forget the socket option.

11.4.9 · echo client and server

Read a line, write it back, stop on zero

The echo client connects, then loops: read a line from the keyboard, write it to the server, read the echo, print it. Ctrl+D makes fgets return NULL. The client closes its descriptor. That close is how the server learns about EOF — rio_readlineb returns 0. There is no EOF character.

The server is iterative: accept, echo until EOF, close connfd, then accept the next client. A second client waits in line. The address buffer is a sockaddr_storage, big enough for any kind of socket address, so the code stays protocol-independent.

Try it: send hello. Watch the server count the bytes. Press Ctrl+D. Then send a line while the first client is still connected — the second client waits.

What the book says

11.5.1 · Web basics

A page that can point at another shop

A browser opens a connection, asks for some content, reads the reply, and the server closes. What makes the Web different from a plain file fetch is HTML. Tags tell the browser how to draw. <b> means bold. An <a href> is a pointer that can name a file on any host.

What the book says

HTML tags describe the page. <b> Make me bold! </b> is boldface. A hyperlink such as <a href="http://www.cmu.edu/index.html">Carnegie Mellon</a> highlights the text and, on a click, requests index.html from the CMU server.

11.5.2 · Web content

A file, or the output of a program

Content is bytes plus a MIME type: text/html, image/jpeg, and so on. Static content is a disk file the server sends back. Dynamic content is whatever a program prints when the server runs it.

A URL names that file. The browser uses the prefix — scheme, host, port — to find the server. The server uses the suffix. The leading slash is not the Linux root; it is the server’s home for that kind of content. A bare / becomes a default home page. A ? starts arguments, split by &.

Try it: split the book’s two URLs. One is a static HTML file on port 80. One is the adder program with arguments 15000 and 213.

What the book says

Figure 11.23 lists MIME types including text/html, text/plain, application/postscript, image/gif, image/png, and image/jpeg. Static content is a disk file; dynamic content is the output of an executable.

The URL http://www.google.com:80/index.html names /index.html on www.google.com, port 80. The port is optional and defaults to 80. http://bluefish.ics.cs.cmu.edu:8000/cgi-bin/adder?15000&213 names an executable with argument strings 15000 and 213. The client uses the prefix to find the server; the server uses the suffix to find the file and to decide static versus dynamic. There is no universal rule; a classic one is a directory such as cgi-bin for executables. The leading slash is the content home, not the Linux root — a server might keep static files in /usr/httpd/html and dynamic files in /usr/httpd/cgi-bin. The suffix / expands to a default such as /index.html.

11.5.3 · HTTP transactions

A note that starts GET, a reply that starts 200

HTTP is text lines over a connection, each line ending in \r\n. You can type them with telnet. A request is a request line (method URI version), headers, and a blank line. HTTP/1.1 insists on a Host header so a proxy knows whose copy to fetch. HTTP/1.0 does not.

The reply is a status, headers such as Content-Type and Content-Length, a blank line, then the body. The chapter’s workhorse method is GET. Other methods exist; Tiny will answer 501 if you try one.

Try it: step the book’s telnet to www.aol.com. Then press a status code and read what the book says it means.

What the book says

Figure 11.24: telnet www.aol.com 80 reaches 205.188.146.23. The client sends GET / HTTP/1.1 and Host: www.aol.com, then a blank line. The server replies HTTP/1.0 200 OK, five response headers including Content-Type: text/html and Content-Length: 42092, then HTML, then closes. Telnet appends \r\n to each line. The Host header is “required in HTTP/1.1 requests, but not in HTTP/1.0 requests.” It tells a proxy the origin server’s domain name.

Methods include GET, POST, OPTIONS, HEAD, PUT, DELETE, and TRACE. The chapter discusses GET. A request line is method URI version. The URI is the URL suffix (a proxy must send the whole URL). HTTP/1.1 adds caching, security, and persistent connections; HTTP/1.0 clients and servers ignore unknown HTTP/1.1 headers. 11.5.4 · serving dynamic content

The child prints, and stdout is the client

CGI is the set of rules for dynamic content. GET arguments ride in the URI. The server forks, sets QUERY_STRING to 15000&213, points the child’s standard output at the connected descriptor with dup2, and execves the adder. Anything the child prints goes straight to the browser.

11.6 · the serve_static function

Map the file, send the bytes, unmap it

get_filetype looks at the suffix: .html, .gif, .png, .jpg, or else text/plain. Tiny then writes HTTP/1.0 200 OK, Server: Tiny Web Server, Connection: close, the length, the type, and a blank line.

The body is not read with a loop in this version. mmap places the file in memory, the file descriptor is closed, rio_writen sends those bytes, and munmap gives the mapping back. Forget either close and a long-running server leaks.

Try it: serve each suffix. Then serve once more and skip munmap — the leak counter climbs.

What the book says

Figure 11.34 sends response headers, then the file. mmap maps the first filesize bytes of the open file into a private read-only area. The descriptor is closed immediately so it is not leaked. rio_writen copies filesize bytes from that area to the client. munmap frees the area; skipping it is also a leak. get_filetype maps .html to text/html, .gif to image/gif, .png to image/png, .jpg to image/jpeg, and anything else to text/plain.

11.6 · the serve_dynamic function

The parent waits; the child becomes the program

serve_dynamic writes only the status line and Server: Tiny Web Server. The CGI program must send the rest. The child sets QUERY_STRING, dup2s the connection onto stdout, and execves the program with an empty argument list. The parent blocks in wait so it can reap the child.

If the browser hits Stop, the first write to that socket can still succeed. The second write delivers SIGPIPE, whose default action kills the process. Caught or ignored, the write returns −1 and errno is EPIPE, reported as “Broken pipe.” Tiny does not catch it.

Try it: run the adder path. Then press browser Stop and watch the second write hit SIGPIPE.

What the book says

Figure 11.35 writes HTTP/1.0 200 OK and the Server header, then Fork. The child calls setenv("QUERY_STRING", cgiargs, 1), Dup2(fd, STDOUT_FILENO), and Execve(filename, emptylist, environ). A real server would set the other CGI variables too. The parent Waits. Because the child shares the open files and the environment from before execve, CGI output on stdout reaches the client with no further help from the parent. The book notes this is less robust than it might be: the 200 is sent before the CGI program has a chance to fail.

If the client has already closed (the Stop button), the first write returns normally and the second causes SIGPIPE, whose default action terminates the process. If SIGPIPE is caught or ignored, that write returns −1 with errno set to EPIPE. perror reports “Broken pipe.” Tiny does not catch SIGPIPE.

Words to know

The chapter’s words, in one plain sentence each.

transaction
Request, server work, response, client work. Not a database transaction.
host
A machine. Clients and servers are processes that may share a host or not.
adapter
The I/O card that moves frames between the network and memory, often by DMA.
frame
A chunk of bits on one LAN, with a header that names the source and destination adapters.
hub / bridge
A hub copies every bit to every port. A bridge learns and copies only when it must.
internet / Internet
Lowercase: any mesh of LANs and WANs plus routers. Uppercase: the global IP one.
packet / datagram
A header plus a payload. An IP datagram is best-effort: it may be lost or duplicated.
encapsulation
A packet stuffed inside a frame. The next hop peels the outer header and writes a new one.
network byte order
Big-endian. What IP addresses and ports use on the wire and inside the socket structs.
domain name
A path in the DNS tree, such as whaleshark.ics.cs.cmu.edu.
connection
A reliable, full-duplex, point-to-point byte stream between two processes.
socket pair
The two socket addresses that uniquely name a connection.
ephemeral port
The 16-bit number the kernel assigns the client for one connection.
listening / connected
listenfd is the long-lived door. connfd is the per-client descriptor accept returns.
getaddrinfo
Turns a host and a service into a list of socket addresses any IP version can use.
iterative server
A server that finishes one client before accepting the next. Echo and Tiny are both iterative.
EOF
Not a character. On a connection, read returns 0 because the peer closed its end.
URI / URL
The URI is the suffix the server sees. The URL is the whole name, including host and port.
MIME type
A label on a byte sequence, such as text/html or image/jpeg.
CGI
Rules for dynamic content: arguments in QUERY_STRING, output on stdout.
Tiny
The book’s iterative HTTP/1.0 GET server, about 250 lines, static files and CGI.
