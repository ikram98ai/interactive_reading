Network Programming

A browser and a server are just two programs passing notes. The notes travel as packets, the conversation is a connection, and the language they agree on is HTTP.

“all network applications are based on the same basic programming model, have similar overall logical structures, and rely on the same programming interface.”

11.1 · the client-server model

Ask the shop, get a parcel back

Amara’s browser wants a page. Kenji’s program owns a shelf of files. She sends a note. He reads a file. He sends the file back. She draws it on the screen. That four-beat loop is a transaction.

The shop and the customer are processes, not buildings. One laptop can run both. Two laptops can split them. The dance does not change.

Try it: Step the four beats of Figure 11.1. Watch the request leave Amara, Kenji touch the disk, and the page fly home.

What the book says

Figure 11.1 is a four-step client-server transaction: the client sends a request; the server interprets it and manipulates a resource; the server sends a response; the client receives it. A Web server reads a disk file; an FTP server stores and retrieves files; an email server updates a spool file.

“Client-server transactions are not database transactions and do not share any of their properties, such as atomicity.” Here a transaction is only a sequence of steps.

Clients and servers are processes, not hosts. One host can run many of each. The model is the same whether they share a machine or sit on opposite sides of the Internet.

11.2 · networks and Ethernet

Everyone hears the shout, one kid reads it

To a computer, the network is just another I/O gadget — a plug that can swallow bits or spit them out. The plug is a network adapter with a 48-bit name burned in.

On a cheap Ethernet, a hub copies every bit to every wire. Lucia shouts “for Omar.” Priya hears it too, and ignores it. A bridge is nosier and wiser: it learns who lives on which wire and only copies when the shout must cross.

Try it: Send a frame from A to B, then from A to C. Switch to the bridge and watch it throw a same-segment frame away.

What the book says

Figure 11.2: data arrive by DMA from the adapter across the I/O and memory buses. Ethernet began at Xerox PARC in the mid-1970s and grew from 3 Mb/s to 10 Gb/s. A segment (Figure 11.3) is wires plus a hub, typically 100 Mb/s or 1 Gb/s.

“A hub slavishly copies every bit that it receives on each port to every other port.” Each adapter has a globally unique 48-bit address. “Every host adapter sees the frame, but only the destination host actually reads it.”

Figure 11.4: bridges join segments into a bridged Ethernet. Bridge–bridge wires can run at 1 Gb/s while hub–bridge wires stay at 100 Mb/s. If host A sends to host B on the same segment, bridge X throws the frame away. If A sends to host C, X copies only toward bridge Y.

Frames on a wire
A hub floods. A bridge copies only when the destination lives on another port.
11.2–11.3 · internets and IP

A letter, then a new envelope at the depot

Two neighbourhoods speak different wire languages. A router sits between them. Yara’s program hands bytes to the kernel. The kernel wraps them in an internet packet, then in a local frame addressed to the router — a parcel inside a parcel.

At the depot the old street envelope comes off. A new one, written in the next neighbourhood’s script, goes on. The inner address never changes. That is how a datagram hops a mix of LANs and WANs.

Try it: Step the wrap at host A, the hop at the router, and the unwrap at host B. The payload stays the same; only the outer header swaps.

What the book says

An internet (lowercase) is LANs and WANs joined by routers. The protocol gives a uniform naming scheme and bundles bits into packets: a header with size and addresses, plus a payload. Figure 11.7 walks eight steps from host A on LAN1 to host B on LAN2. The LAN1 frame payload is an internet packet. “This kind of encapsulation is one of the fundamental insights of internetworking.”

The router indexes a routing table, strips FH1, and prepends FH2. Host B strips both headers and copies the data into the server’s address space.

IP sends 32-bit-addressed datagrams and “makes no effort to recover if datagrams are lost or duplicated.” UDP extends that host-to-host service to processes. TCP builds reliable full-duplex connections on IP. The book treats TCP/IP as one protocol and does not discuss UDP. IPv6’s 128-bit addresses existed, but as of 2015 only 4 percent of users reached Google over IPv6, so the chapter stays on IPv4.

The internet header names host B. The frame header only has to reach the next hop.
11.3.3 · connections and ports

A private phone line, both can talk

Once two processes agree to talk, they have a connection: one pair of ends, both directions at once, and the bytes arrive in the order they were sent — unless a backhoe cuts the cable.

Each end is a socket named address:port. The server usually sits on a well-known door (Web is 80, email is 25). The client gets a spare door the kernel picks — an ephemeral port. The pair of names is the connection’s ID.

Try it: Read the book’s socket pair, then send HELLO. Drop the third letter: IP loses it; TCP still delivers H E L L O.

What the book says

A connection is point-to-point, full duplex, and reliable: “the stream of bytes sent by the source process is eventually received by the destination process in the same order it was sent.”

A socket address is an IP address plus a 16-bit port, written address:port. Web servers typically use port 80 (http in /etc/services); email uses port 25 (smtp). The client port is assigned automatically. Figure 11.11’s socket pair is (128.2.194.242:51213, 208.216.181.15:80).

IP datagrams can be lost or duplicated. TCP is the protocol that turns that unreliable hop-by-hop service into a reliable byte stream between processes. Software ports are not the hardware ports on a hub or router.

Socket pair · then a stream
The connection is the pair of socket addresses. The stream is the bytes that ride it.
11.3.2 · domain names

A name you can say, a number the wire uses

People remember whaleshark.ics.cs.cmu.edu. Programs dial 128.2.210.175. The phone book that maps one to the other used to be a single file called HOSTS.TXT. Since 1988 it is a worldwide database: DNS.

Some names share one number. Some names share a handful of numbers. Some perfectly legal names — like edu — have no address at all. And every host answers to localhost at 127.0.0.1, which is handy when the client and server are roommates.

Try it: Look up the book’s names. twitter.com returns four addresses; edu returns none.

What the book says

Figure 11.10: an unnamed root, then ICANN first-level names (com, edu, gov, org, net), then second-level names such as cmu.edu. An organisation that owns a second-level name may create cs.cmu.edu and so on.

localhost always maps to the loopback address 127.0.0.1. whaleshark.ics.cs.cmu.edu maps one-to-one to 128.2.210.175. cs.mit.edu and eecs.mit.edu both map to 18.62.1.6. www.twitter.com and twitter.com share 199.16.156.6, .70, .102, and .230. nslookup edu and ics.cs.cmu.edu print “No answer.”

Until 1988 the map lived in HOSTS.TXT. The Internet Domain Survey counted about 20,000 hosts in 1987 and over 1,000,000,000 by 2015.

11.4 · the sockets interface

Open the shop, then wait by the door

Kenji opens a socket — to the kernel that is just another file descriptor. He pins it to port 80 (bind), hangs a “we are a shop” sign (listen), and blocks in accept. That listening descriptor stays for the life of the server.

Amara opens her own socket and connects. Accept wakes up and hands Kenji a new descriptor, connfd, just for her. The old door keeps waiting for the next customer. That split is why a later chapter can serve many clients at once.

Try it: Step Figure 11.14. The shop is listenfd 3; the private counter is connfd 4.

What the book says

Berkeley sockets arrived in the early 1980s in Unix 4.2BSD. Figure 11.12 is the road map: the server calls socket, bind, listen, accept; the client calls socket and connect. Helpers open_listenfd and open_clientfd wrap getaddrinfo so the same C works for any IP version.

listen turns an active socket into a listening socket. The backlog is a hint; the book typically uses 1,024. Figure 11.14: the server blocks in accept on listenfd (descriptor 3; 0–2 are the standard files). The client blocks in connect. accept returns connfd 4. The listening descriptor lives for the server’s lifetime; the connected one lasts for one client.

The echo server in Figure 11.20–11.22 is iterative: one client at a time. Chapter 12 builds concurrent servers. EOF on a connection is not a character; it is the kernel reporting that the peer closed its end.

11.3.1 · 11.4.1 · addresses and byte order

The postcard always writes the big end first

An IPv4 address is a 32-bit unsigned integer. Humans write it dotted: 128.2.194.242. That is hex 0x8002c2f2. Different chips store a 32-bit word in opposite byte orders, so the Internet picked one: network byte order, which is big-endian.

htonl and htons pack host integers for the wire. ntohl and ntohs unpack them. A sockaddr_in is 16 bytes: family AF_INET, a 16-bit port, a 32-bit address (both already in network order), and eight pad bytes so it matches a generic sockaddr.

Try it: Flip host order versus network order for 128.2.194.242, then pack port 80 with htons.

What the book says

Figure 11.9: struct in_addr { uint32_t s_addr; } — always network (big-endian) byte order. 128.2.194.242 is 0x8002c2f2. hostname -i on the book’s host printed 128.2.210.175. Convert with inet_pton / inet_ntop (“p” = presentation, “n” = network). They also accept AF_INET6, which the book does not cover.

htonl / ntohl convert 32-bit values; htons / ntohs convert 16-bit values. There are no 64-bit twins. Practice 11.1 asks you to fill a dotted-decimal ↔ hex table, including 0x00000080, 0xFFFFFF00, and 0x0A010140.

Figure 11.13: sockaddr_in has sin_family (always AF_INET), sin_port, sin_addr, and sin_zero[8]. The “_in” suffix means internet, not input. Sockets calls take a generic sockaddr *; the book typedefs it SA.

0x8002c2f2 · then sockaddr_in
The wire is big-endian. A little-endian host must swap before it copies an address into a packet.
11.5 · Web servers

A note that starts GET, a reply that starts 200

Mateo types in a browser. Under the paint, the browser opens a connection and writes text: a request line GET / HTTP/1.1, then headers, then a blank line. HTTP/1.1 insists on a Host header so a proxy knows whose copy to fetch.

The server answers with a status (200 OK, or 404, or 501), a Content-Type such as text/html, a length, a blank line, then the body. Static content is a file. Dynamic content is the output of a program, often a CGI child that reads QUERY_STRING.

Try it: Step the book’s telnet to www.aol.com, then the adder CGI that prints 15000 + 213 = 15213.

What the book says

Figure 11.24: telnet www.aol.com 80 reaches 205.188.146.23. The client sends GET / HTTP/1.1 and Host: www.aol.com, then a blank line. Each line ends in \r\n. The server replies HTTP/1.0 200 OK, Content-Type: text/html, Content-Length: 42092, then HTML, then closes. The Host header is “required in HTTP/1.1 requests, but not in HTTP/1.0 requests.”

A request line is method URI version. Methods include GET, POST, OPTIONS, HEAD, PUT, DELETE, and TRACE; the chapter discusses GET. Figure 11.25: 200 OK, 301, 400, 403, 404, 501, 505. Figure 11.23 lists MIME types including text/html, text/plain, image/gif, image/png, and image/jpeg.

URL http://www.google.com:80/index.html — port 80 is optional. Dynamic example: http://bluefish.ics.cs.cmu.edu:8000/cgi-bin/adder?15000&213. Figure 11.28: Tiny plus adder return 115 bytes of HTML, “The answer is: 15000 + 213 = 15213”. The child sets QUERY_STRING and dup2s stdout onto the connected descriptor.

        11.6 · the Tiny Web server
        
Two hundred and fifty lines, one GET at a time

        
Tiny is Kenji’s shop in 250 lines of C. It listens, accepts, calls doit, and closes. doit reads the request line. If the method is not GET, it answers 501 and goes back to the door.

        
A URI with cgi-bin is dynamic: fork, set QUERY_STRING, point stdout at the client, execve. Anything else is a file under the current directory; a trailing slash becomes ./home.html. Missing file: 404. No read or execute permission: 403.

        
Try it: Fire the book’s adder GET, a static home page, a POST (501), and a missing file (404).

Words to know
The chapter’s grown-up words, in plain language.

      

        
transaction
Request, server work, response, client work. Not a database transaction.

        
adapter
The I/O card with a 48-bit Ethernet address that moves frames to memory, often by DMA.

        
hub / bridge
A hub copies every bit to every port. A bridge learns and copies only when it must.

        
internet / Internet
Lowercase: any mesh of LANs and WANs plus routers. Uppercase: the global IP one.

        
datagram
An IP packet. Best-effort: it may be lost or duplicated.

        
encapsulation
A packet stuffed inside a frame. The next hop peels the outer header and writes a new one.

        
domain name
A path in the DNS tree, such as whaleshark.ics.cs.cmu.edu.

        
connection
A reliable, full-duplex, point-to-point byte stream between two processes.

        
socket pair
The two socket addresses that uniquely name a connection.

        
ephemeral port
The 16-bit number the kernel assigns the client for one connection.

        
network byte order
Big-endian. What s_addr and sin_port always use.

        
listenfd / connfd
The long-lived shop door versus the per-client table.

        
URI / URL
URI is the suffix the server sees (/index.html). URL is the whole thing, including host and port.

        
MIME type
A label on a byte sequence, such as text/html or image/jpeg.

        
CGI
Rules for dynamic content: arguments in QUERY_STRING, output on stdout.

        
Tiny
The book’s iterative HTTP/1.0 GET server, about 250 lines, static and CGI.
