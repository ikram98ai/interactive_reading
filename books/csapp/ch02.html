A computer only stores zeros and ones. The same switches can be a letter, a counting number, a negative number, or a rough real number — and the arithmetic can surprise you, because there are never enough bits.

2.1 · information storage

Mailboxes, not loose switches

A machine does not let a program touch one bit at a time. The smallest box you can address is a byte: eight bits. Memory looks to the program like one long row of those boxes. That picture is called virtual memory.

Every box has a number, its address. The whole set of possible numbers is the virtual address space. A pointer is just the address of the first byte of some object. In Rust, &x borrows x: it gives you a reference, an address the compiler checks, and the compiler makes sure x outlives it. The compiler remembers the type. The machine code it emits does not: it only sees a block of bytes.

The listing turns that reference into a raw pointer to single bytes, a bare address the compiler does not check. raw.add(i) moves it i bytes along, and * reads the byte there. Reading through a raw pointer is only allowed inside an unsafe block, which means “Rust cannot check this, and I promise it is fine.” Everyday Rust gets the same four bytes safely with x.to_ne_bytes(). The raw pointer is here because the book’s point is that the machine sees bare bytes.

Run on x86-64 Linux, the four bytes come out 67 45 23 01: the low end of the number first. The next scene explains why. Tap a box past the fourth and the promise breaks: reading outside x is undefined behaviour, a program Rust’s rules give no meaning at all.

Try it: tap a mailbox. Then switch the glasses between “the compiler’s i32” and “the machine’s bytes.” The pointer never moves. Only the story does.

What the book says

Most computers use blocks of 8 bits, or bytes, as the smallest addressable unit. A machine-level program views memory as a very large array of bytes, called virtual memory. Every byte is identified by a unique address, and the set of all possible addresses is the virtual address space. Chapter 9 shows that this image is built from DRAM, flash, disk, hardware, and the operating system.

A pointer’s value is the virtual address of the first byte of a block of storage. The C compiler associates type information with each pointer so it can generate different code for different types. The machine-level program it generates has no information about data types. It treats each program object as a block of bytes, and the program itself as a sequence of bytes.

2.1.1 · hexadecimal notation

Four bits, one nickname

A byte written as 11010100 is noisy. Written as 212, the bits disappear. Hexadecimal splits the difference: base 16, digits 0–9 and then A–F. Each digit is exactly four bits.

Two hex digits are one byte, from 00 to FF. Rust writes them with a lowercase 0x in front (and binary with 0b). The digits may be either case, so 0xFA1D37B and 0xfa1d37b are the same number, and an underscore may split a long one: 0xFA1_D37B. The book’s C also accepts a capital 0X; rustc refuses it with “invalid base prefix for number literal.” Binary and hex convert one digit at a time. Decimal needs real division.

Try it: flip switches and watch each group of four become one hex digit. Then open Divide by 16 and step decimal 314,156 down to 0x4CB2C. In Rust, println!("{:#X}", x) does those divisions for you: println! prints a line, and {:#X} asks for hex with 0x.

What the book says

A byte ranges from 00000000 to 11111111 in binary, and from 0 to 255 in decimal. Hexadecimal uses digits 0 through 9 and characters A through F. Figure 2.2 is the chart. In C, constants starting with 0x or 0X are hexadecimal, and the letters may be upper- or lowercase. “Converting between binary and hexadecimal is straightforward, since it can be performed one hexadecimal digit at a time.”

The book’s running example expands 0x173A4C into 0001 0111 0011 1010 0100 1100. The other way, 1111001010110110110011 is padded on the left and becomes 0x3CADB3. Decimal 314,156 converts by repeated division by 16, remainders C, 2, B, C, 4, so 0x4CB2C. Powers of two are easy: 211 = 2048 = 0x800.

2.1.2 · data sizes

A word is how wide a pointer is

Every computer has a word size: the nominal size of a pointer. A 32-bit word can name at most 4 gigabytes of addresses. A 64-bit word can name 16 exabytes. That is the real reason the word got wider.

In the book’s C, a type is a request for “this many bytes,” and the answer depends on the compiler: int stays 4 bytes in a 64-bit program, while long and pointers grow from 4 to 8. Stuffing a pointer into an int worked for years, and then it didn’t. Rust puts the width in the name: i32 is 4 bytes everywhere. Only pointers and the pointer-sized usize grow, and std::ffi::c_long stands for C’s long when Rust talks to C. The program, not the machine, decides: the book compiles with gcc -m32 or gcc -m64, and rustc picks a --target.

Try it: switch 32-bit and 64-bit. Watch which bars grow, and read the lines that change with them. println! prints a line, filling each {} with a value, and size_of::<T>() counts the bytes in a type T.

What the book says

For a w-bit word, virtual addresses range from 0 to 2w − 1, so the program can touch at most 2w bytes. A 32-bit word limits that to 4 gigabytes. A 64-bit word yields 16 exabytes. Most 64-bit machines can also run programs compiled for 32-bit machines. gcc -m32 prog.c runs on either; gcc -m64 prog.c runs only on a 64-bit machine. The book therefore talks about 32-bit programs and 64-bit programs, not machines.

Figure 2.3: char 1, short 2, int 4, long 4 or 8, int32_t 4, int64_t 8, char * 4 or 8, float 4, double 8. ISO C99 added the fixed-size types so the size does not depend on the compiler. “Many programmers historically assumed that an object declared as type int could be used to store a pointer. This works fine for most 32-bit programs, but it leads to problems for 64-bit programs.”

2.1.3 · addressing and byte ordering

Which end of the egg?

A four-byte i32 at address 0x100 occupies 0x100 through 0x103. The address of the object is always the smallest of those. The only fight is which byte sits there.

Little endian puts the least significant byte first. Big endian puts the most significant byte first. Intel machines, and the phones you know, are little-endian. The names come from Swift’s argument about which end of an egg to crack. There is no technical winner. Networks, disassembly, and casts are where you notice.

Rust lets you choose the order out loud. x.to_le_bytes() gives the four bytes little-endian and x.to_be_bytes() big-endian, on any machine; to_ne_bytes gives this machine’s own order, and from_le_bytes and its twins turn bytes back into a number. Code that sends numbers over a network names the order, so it reads the same everywhere.

Try it: park 0x01234567 both ways. Then press show_int(12345) and watch the little-endian order print the low byte first, while the big-endian order (the book’s Sun) prints it last.

What the book says

A multi-byte object is stored as a contiguous sequence of bytes, and its address is the smallest address used. For x = 0x01234567 at 0x100, big endian stores 01 23 45 67 and little endian stores 67 45 23 01.

Figure 2.4 is show_bytes. Figure 2.6 runs it on 12,345, which is 0x00003039. Linux 32, Windows, and Linux 64 print 39 30 00 00. Sun prints 00 00 30 39. The float 12,345.0 is 0x4640E400, same bytes, reversed on the Sun. Pointer bytes differ completely, and Linux 64 uses 8-byte addresses.

Byte order shows up when binary data cross a network (Chapter 11), when you read a disassembly such as 4004d3: 01 05 43 0b 20 00, and when a cast or union peeks at the raw bytes.

2.1.4 · representing strings

Letters do not flip

In the book’s C, a string is a row of characters with a zero byte, the null, at the end, and code finds the end by searching for it. A Rust &str is a pointer and a length instead, so it needs no terminator. Its bytes are always UTF-8, which spends one byte on each ASCII character. The digit character 1 is not the number 1. It is the byte 0x31.

For text that must go to C, Rust has C string literals: c"12345" adds the null for you. Print its bytes and you get 31 32 33 34 35 00, the book’s output. Byte order never reverses a string, because each character is already one byte. Text travels more calmly than integers do.

Try it: pick a string. c"12345" and c"Hi" end in a null. The practice problem’s "mnopqr", an ordinary &str read with as_bytes(), has none.

What the book says

A string in C is an array of characters terminated by the null character, value 0. The most common encoding is ASCII. show_bytes on "12345" with length 6 prints 31 32 33 34 35 00. The ASCII code for decimal digit x is 0x3x. The same bytes appear on any ASCII system, independent of byte ordering and word size. Text data are more platform independent than binary data.

Practice Problem 2.7 asks what show_bytes prints for "mnopqr" with strlen, which does not include the null. Letters a through z are 0x61 through 0x7A. The Unicode aside notes that UTF-8 keeps those same single-byte codes, and that Java strings use Unicode.

2.1.5 · representing code

The same recipe, different bytes

From the machine’s point of view a program is just another sequence of bytes. Compile one tiny function, sum, with rustc for four targets and you get four different byte strings. Same source. Incompatible instructions. Every byte on this stage is rustc’s own, read back from the object file with objdump.

Even the same processor can disagree when the operating system changes. x86-64 Linux and x86-64 Windows both answer with one lea and a ret, but Windows hands the function its arguments in different registers, so one byte of the lea differs: 37 becomes 11. Binary code is seldom portable. The build matters too: a debug build checks the add for overflow, and the same four-byte function grows to 31 bytes.

Try it: switch targets. The Rust in the code panel stays put. The bytes on the stage change. #[no_mangle] above the function only keeps its plain name, sum, in the object file, so the tools can find it, and pub lets code outside this file call it.

What the book says

The sample function, sum, takes two int arguments and returns their sum. Compiled, its bytes are: Linux 32 55 89 e5 8b 45 0c 03 45 08 c9 c3; Windows 55 89 e5 8b 45 0c 03 45 08 5d c3; Sun 81 c3 e0 08 90 02 00 09; Linux 64 55 48 89 e5 89 7d fc 89 75 f8 03 45 fc c9 c3.

Different machine types use different and incompatible instructions and encodings. Identical processors running different operating systems are not binary compatible. A program, from the perspective of the machine, is simply a sequence of bytes.

2.1.6 · introduction to Boolean algebra

Four questions you can ask two bits

George Boole’s algebra is the math of 0 and 1. AND is 1 only when both are 1. OR is 1 when either is 1. XOR is 1 when they differ. NOT flips the one bit you hand it. Rust writes them &, |, ^ and !; the book writes NOT as ~.

The same four questions work on whole rows of bits, one column at a time. The book’s example: 0110 AND 1100 is 0100. And a ^ a is always all zeros — every pattern is its own inverse. That is the trick behind the swap in the next section. The same bits can also mean a set, or a mix of red, green, and blue light.

Try it: flip bits in the book’s two patterns. Then open RGB and mix the three lights. Complement flips every light that is on.

What the book says

Binary values are encoded as 0 and 1. Boolean algebra, from George Boole, is the algebraic treatment of logic. Figure 2.7 defines NOT, AND, OR, and exclusive-OR. The book’s symbols match C: ~, &, |, and ^.

The operations extend to bit vectors one bit at a time. With a = [0110] and b = [1100], AND is [0100], OR is [1110], XOR is [1010], and NOT b is [0011]. In the Boolean ring, every value is its own inverse: a ^ a = 0. Bit vectors also encode sets, and Practice Problem 2.9 mixes red, green, and blue light into eight colors. Claude Shannon connected this algebra to networks of relays.

2.1.7 · bit-level operations in C

A mask, a swap, a zero in the middle

Rust, like the book’s C, applies those four operations to every bit of an integer. The book’s byte examples: NOT 0x41 is 0xBE (in Rust, !0x41u8, where the u8 ending makes 0x41 a byte), and 0x69 & 0x55 is 0x41. A mask is a pattern that keeps or sets the bits you name. x & 0xFF keeps the low byte.

Because a ^ a is 0, you can swap two numbers with no third variable. The swap takes two &mut borrows, addresses it may write through, and *x reaches the value behind one. The trick has a bite. The book’s C reverses an odd-length array by swapping toward the middle, and its loop also runs when the two ends meet, so the center element is XORed with itself and becomes 0. Rust will not compile that loop at all. Two &mut borrows into one array at once are error E0499, because the compiler cannot tell the two elements apart. split_at_mut cuts the array into two parts that cannot overlap, and the Rust loop stops before the ends meet. Real code calls a.swap(i, j) or a.reverse(); the XOR trick is the book’s puzzle.

Try it: run the book’s 0x69 and 0x55 through each operator. Then step the XOR swap, and reverse [1, 2, 3, 4, 5].

What the book says

C’s bitwise OR, AND, NOT and XOR apply to any integral type. For one byte: NOT 0x41 is 0xBE, NOT 0x00 is 0xFF, 0x69 AND 0x55 is 0x41, and 0x69 OR 0x55 is 0x7D. The best method is to expand to binary, operate, and convert back.

Practice Problem 2.10 is inplace_swap, three XOR steps and no temporary. Practice Problem 2.11 uses it to reverse an array. Even length works. Odd length sets the middle element to 0, because the last swap is a value with itself. A mask example: 0x89ABCDEF AND 0xFF yields 0x000000EF. NOT 0 is a mask of all ones at any word size.

2.1.8 · logical operations in C

A yes-or-no, not a bit walk

In the book’s C, the logical operators AND, OR and NOT accept any integer: nonzero counts as true, zero as false, and the answer is 1 or 0. So in C the logical AND of 0x69 and 0x55 is 1, while the bitwise AND is 0x41. Rust’s &&, || and ! work on a bool, a plain true or false. Hand && two i32s and rustc stops with error E0308, “expected `bool`, found `i32`.” You write the test, a != 0, yourself.

They also stop early. If the first side of && is false, the second side never runs. That is why a != 0 && 5 / a != 0 never divides by zero. Without the test, Rust would not quietly divide: 5 / a with a = 0 panics: the program stops with the message “attempt to divide by zero.” The book’s other example tests a pointer before following it. In Rust a value that might be missing is an Option, either Some(value) or None, and you have to check which before you use it.

Try it: set a to 0 and press Step. The division is painted as skipped. Set a to 0x55 and both sides run. Compare with a single &.

What the book says

Logical operators treat any nonzero argument as true and 0 as false, and they return 1 or 0. The book’s table: logical NOT of 0x41 is 0x00, logical NOT of 0x00 is 0x01, a double NOT of 0x41 is 0x01, and both the logical AND and the logical OR of 0x69 and 0x55 are 0x01. A bitwise operation matches its logical twin only when the arguments are restricted to 0 and 1.

Logical AND and OR do not evaluate their second argument if the first argument already decides the result. So testing a before dividing 5 by a never causes a division by zero, and testing a pointer before following it never dereferences a null pointer.

2.1.9 · shift operations in C

Shove the bits, then mind the parentheses

A left shift drops bits off the left and fills the right with zeros. A right shift is two different machines. Logical fills with zeros. Arithmetic copies the top bit, which keeps a negative number negative. The book’s C almost always uses the arithmetic one for signed data, and must use the logical one for unsigned data. Java writes them as >> and >>>. Rust picks by type: >> is arithmetic on the signed i8 to i64, and logical on the unsigned u8 to u64.

Two traps. In C, shifting a 32-bit int by 32 or more is undefined, even if your laptop happens to take the amount mod 32. Rust defines it. rustc rejects a shift it can see is that big (“this arithmetic operation will overflow”). A debug build, rustc’s default with no optimisation, panics on one computed while running (“attempt to shift left with overflow”). A release build, compiled with optimisation, skips that check and takes the amount mod 32, so x << 32 gives back x. checked_shl or wrapping_shl say which answer you want in every build. Bits that fall off the end are not overflow: 200u8 << 1 is simply 144. Second, 1<<2+3<<4 is 512, not 52, in both languages, because + binds tighter than <<.

Try it: shift the book’s two bytes by 4, logical and arithmetic. Open Precedence and watch 512 appear where 52 was intended. Then open Shift ≥ 32 for the book’s three oversized shifts.

What the book says

x << k drops the top k bits and fills the right with zeros. Shifts associate left to right. A logical right shift fills with zeros. An arithmetic right shift fills with copies of the most significant bit. For an 8-bit argument, [01100011] << 4 is [00110000], and [10010101] >> 4 is [00001001] logically and [11111001] arithmetically.

The C standards do not say which right shift signed data must use. In practice almost every compiler uses arithmetic for signed data, and unsigned right shifts must be logical. Java defines >> as arithmetic and >>> as logical. Shifting a 32-bit int by 32, 36, or 40 is undefined in C. The expression 1<<2 + 3<<4 equals (1 << (2+3)) << 4, which is 512, rather than the intended 52.

2.2 · integer representations

Two ways to read the same switches

From here the book gives integers two encodings. Unsigned only counts upward from zero. Two’s complement uses the same bits for negatives, zero, and positives. They are not rival machines. The adder you will meet later barely cares which story you picked.

Figure 2.8 is the phrase book: B2U, B2T, TMin, UMax, and the little operations +u, +t, *u, *t. The subscript w is the number of bits. Tap a name and the four-bit picture shows what that name points at.

Try it: press each symbol. The bits stay [1011]. Only the name of the reading changes.

What the book says

Section 2.2 describes two ways bits encode integers: one for nonnegative numbers, and one that can be negative, zero, or positive. They are strongly related in their mathematics and in their machine-level implementations. Expanding or shrinking an encoded integer to a different length is part of the same story.

Figure 2.8 lists the notation used for the rest of the chapter. B2Uw and B2Tw turn a bit vector into an unsigned or two’s-complement number. U2Bw and T2Bw go the other way. T2Uw and U2Tw keep the bits and change the interpretation. TMinw, TMaxw, and UMaxw are the extreme values. The operations +u, +t, *u, *t, and the two negations are defined on later pages.

2.2.1 · integral data types

The negative side is one longer

Integer types are finite rulers. The book’s Figures 2.9 and 2.10 list C’s typical rulers for 32-bit and 64-bit programs, where C’s long is the one that moves. Rust’s rulers are in the names: i8, i16, i32, i64 and i128 are signed, u8 to u128 unsigned, and the number is the bit count on every target. Only the pointer-sized isize and usize move. Every signed ruler is lopsided: the most negative value is one past the most positive.

The book’s Figure 2.11 is what the C standard actually promises, which is smaller and, except for C’s fixed-size types, symmetric. A C int is only guaranteed to reach 32,767. Rust has no such hedge. i32::MIN and i32::MAX name its exact ends, −2,147,483,648 and 2,147,483,647. When Rust talks to C, std::ffi::c_int and c_long stand for whatever C’s int and long are on that target.

Try it: switch the 32-bit program, the 64-bit program, and the C minimum. Watch isize and usize jump while i32 stays put, and watch C’s guaranteed int shrink.

What the book says

Figure 2.9, 32-bit programs: signed char −128…127, unsigned char 0…255, short −32,768…32,767, int and long −2,147,483,648…2,147,483,647, unsigned 0…4,294,967,295. int64_t reaches −9,223,372,036,854,775,808. Figure 2.10 is the same except long and unsigned long grow to the 64-bit range.

2.2.2 · unsigned encodings

Each switch is a power of two

B2U is ordinary binary. Bit i, if it is on, adds 2i. Four bits can name every integer from 0 to 15, and each integer once. That two-way match is a bijection. The top of the ruler is UMax = 2w − 1.

Figure 2.12 draws the weights as bars. [0001] is 1, [0101] is 5, [1011] is 11, [1111] is 15. Nothing is negative. Nothing is skipped.

Try it: flip the four switches, or jump to the figure’s four examples. The total under the bars is B2U.

What the book says

Equation 2.1 defines B2Uw(x) as the sum of xi 2i. Figure 2.12 works four cases: [0001] = 1, [0101] = 5, [1011] = 11, [1111] = 15. UMaxw is 2w − 1. For w = 4 that is 15.

Every number from 0 to 2w − 1 has exactly one w-bit encoding. The book’s principle: function B2Uw is a bijection. There is only one unsigned 4-bit form of 11, namely [1011].

2.2.3 · two’s-complement encodings

The left switch pulls downward

Keep every weight except the top one. Bit w−1 is now worth −2w−1, not +2w−1. That is the sign bit. Four bits that meant 0…15 now mean −8…7.

[1011] was 11. It is now −8+2+1 = −5. The most negative pattern, [1000], is TMin = −8. The most positive, [0111], is TMax = 7. There is no +8. Zero sits on the nonnegative side, so the ruler is one step longer below zero. All-ones is −1.

Try it: flip the sign bit and watch the unsigned total jump up while the signed total falls through the floor. Press Negate to see !x + 1: flip every bit, then add one.

What the book says

Equation 2.3 defines B2Tw(x) as −xw−1 2w−1 plus the usual sum of the lower bits. Figure 2.13 uses the same four patterns as Figure 2.12. [1011] is −5. TMinw = −2w−1 and TMaxw = 2w−1 − 1. Figure 2.14 records |TMin| = TMax + 1, and UMax = 2 TMax + 1.

Both mappings are bijections. The pattern of all ones is −1. The pattern 100…0 is TMin. An alternative the book mentions, and almost nobody uses, is ones’ complement or sign-magnitude. Negating a two’s-complement value is equivalent to complementing the bits and adding 1, which the negation section makes precise.

2.2.4 · conversions between signed and unsigned

Keep the bits. Add 2w if you must.

Casting between signed and unsigned, on almost every machine, does not touch the bits. It only changes the function you use to read them. That is T2U one way and U2T the other.

If the number was already in range, nothing numerical happens. If it was negative, T2U adds 2w. So −1, the all-ones pattern, becomes UMax. TMin becomes 2w−1, which is just past TMax. On 16 bits, −12,345 becomes 53,191, because 65,536 − 12,345 = 53,191.

In Rust the cast is as, and between two integer types of the same size it does exactly this: nothing to the bits. -1i8 as u8 is 255, -1i32 as u32 is 4,294,967,295, and as back gives −1 again. It never panics, in any build. When you want a check instead, u8::try_from(t) returns an error for a negative t.

Try it: step −1, TMin, and −12,345. The bit row does not move. The decimal reading does.

What the book says

The principle for T2Uw(x): if x is negative, the unsigned reading is x + 2w; otherwise it is x. U2Tw(u) subtracts 2w when u is greater than TMax. “Most systems follow the rule that the underlying bit representation does not change.”

T2Uw(−1) = UMaxw. T2Uw(TMinw) = 2w−1 = TMaxw + 1. From Figure 2.15, T2U16(−12,345) = 65,536 − 12,345 = 53,191.

2.2.5 · signed versus unsigned in C

One unsigned side, and the comparison flips

The book’s C converts for you, with a cast or without one. Its printf does not even check the type: printing −1 with the unsigned format prints 4294967295 in a 32-bit program, the bits of −1 read as unsigned.

The sharp edge is a comparison. In C, if either side is unsigned, the other side is cast to unsigned too, silently. So −1 is less than 0, but −1 is not less than an unsigned 0. Figure 2.19 marks the surprising rows with a star. Rust never converts silently. Compare an i32 with a u32 and rustc stops with error E0308, “expected `i32`, found `u32`.” You write as u32 yourself, so the surprise is in plain sight, and rustc even warns that the answer is fixed: “comparison is useless due to type limits.”

Try it: press each row of the figure. The code panel shows the cast Rust makes you write, and the true or false that comes out.

What the book says

Constants are signed unless you add the suffix U or u. “Most systems follow the rule that the underlying bit representation does not change.” The book’s printf example, compiled as a 32-bit program, prints x = 4294967295 = -1 and u = 2147483648 = -2147483648.

“When either operand of a comparison is unsigned, the other operand is implicitly cast to unsigned.” Figure 2.19: −1 less than 0 is 1; −1 less than an unsigned 0 is 0; and an unsigned 2,147,483,647 greater than −2,147,483,647−1 is 0. The book writes TMin32 as −2,147,483,647−1 because of a quirk explained in the web aside, matching how limits.h defines INT_MIN as minus INT_MAX, minus 1.

2.2.6 · expanding the bit representation

New bits on the left must not change the number

Growing a value into a wider type should keep the same number. Unsigned growth is zero extension: the new high bits are 0. Signed growth is sign extension: the new high bits are copies of the sign bit, so −5 stays −5.

Fill a negative 16-bit number with zeros instead and it becomes a huge positive 32-bit one. That is the whole bug. The numeric value is preserved exactly when the fill matches the encoding.

Rust’s as picks the fill from the type it starts with: u8 as u32 zero-extends and i8 as i32 sign-extends. When the size and the sign both change, the size changes first. -5i8 as u32 sign-extends to 32 bits and then reads them unsigned: 4,294,967,291. The book’s C follows the same order: its short −12,345 converted to unsigned is 4,294,954,951, and so is -12345i16 as u32.

Try it: widen [1011]. Zero-fill reads it as 11. Sign-fill reads it as −5. Both are right — for different types.

What the book says

Converting to a larger data type should always be possible. For an unsigned number, zero extension adds leading zeros and B2U of the short vector equals B2U of the long one. For two’s complement, sign extension repeats the most significant bit. The numeric value is unchanged.

The book’s pictures show a negative value staying negative only when the new bits copy the sign. Casting a short to an int in C does this sign extension for you. When a short −12,345 is converted to unsigned, the program first changes the size and then the type, giving 4,294,954,951 rather than 53,191, and the C standards require that order. The next section is what happens when the destination is smaller instead of larger.

Throw away the high bits

Shrinking keeps the low k bits and drops the rest. For unsigned numbers that is exactly “mod 2k”. For two’s complement you do the same mod, then re-read the top of those remaining bits as a sign.

The book’s example: the 32-bit 53,191 truncated to 16 bits is −12,345. In Rust, as to a narrower type such as i16 does exactly this: it keeps the low bits. 2.2.8 · advice on signed versus unsigned

The bug you cannot see in the source

The dangerous casts are the quiet ones. The book’s sum_elements takes an unsigned length. Called with 0, its loop test computes 0 − 1 in unsigned arithmetic, which wraps to a gigantic number, and the loop walks off the end of the array. In Rust a length is a usize, the unsigned size type. A plain 0 − 1 on it panics in a debug build (“attempt to subtract with overflow”) instead of carrying on. The listing asks for C’s silent wrap on purpose with wrapping_sub, as a release build would do anyway, and Rust still stops the loop the moment it reaches a[3], one past the end, because it checks every index before using it.

strlonger subtracts two unsigned string lengths. If the first string is shorter, the subtraction wraps to a huge value, and that value is greater than 0. The function says “longer” when it means “shorter.” Comparing the lengths directly does not wrap, in either language.

The book’s getpeername aside is the same mismatch with a security price. FreeBSD’s kernel took a signed length from the user, kept the smaller of it and its buffer size, and handed that to memcpy, whose length is unsigned. A negative length became a gigantic copy that could read private kernel memory. Rust will not mix the two types: the book’s signature, written in Rust, fails with error E0308, “expected `usize`, found `i32`.” The fix is the book’s own: make every length a size. In Rust, take it from the buffer itself. (In the listing, const names a fixed value, static is one array that lasts as long as the program, and [u8; N] is an array of N bytes.)

Try it: run all three bugs, then press Fixed. The book’s advice is not “never use unsigned.” It is “know when a size wants to be unsigned, and when a subtraction does not.”

What the book says

Practice Problem 2.25 is sum_elements. With length equal to 0 it should return 0.0. Instead length-1 wraps, and the loop accesses past the array. Practice Problem 2.26 is strlonger, which returns whether the length of s minus the length of t is greater than 0. Those lengths have type size_t, which is unsigned. When s is shorter, the subtraction wraps and the comparison succeeds.

The book notes that few languages other than C have unsigned integers; Java has only signed ones, an arithmetic >>, and a logical >>>. Unsigned is still the right tool for raw bits, for addresses, and for modular arithmetic. The bugs come from implicit casts, especially around subtraction and comparison.

The aside on getpeername (at the start of 2.3.1) is a 2002 FreeBSD bug. copy_from_kernel took a signed maxlen, copied the smaller of it and the 1,024-byte kernel buffer, and passed that length to memcpy, whose length parameter is the unsigned size_t. A negative maxlen became a very large positive count, so a caller could read kernel memory it was not allowed to see. The fix declares maxlen, the local length, and the return value as size_t.

2.3 · integer arithmetic

Positive plus positive can be negative

The opening of the chapter multiplies four positive ints, 200 × 300 × 400 × 500, and gets −884,901,888. Every parenthesization gets that same wrong number. Integer multiply on a computer is associative. It is just associative around the wrong answer. Write that constant product in Rust and it will not compile: rustc reports “this arithmetic operation will overflow.” wrapping_mul asks for the low 32 bits on purpose, and gives the book’s number.

Addition has its own version of the surprise. x < y and x - y < 0 can disagree, because the subtraction overflows. On an i8, TMin (−128) is less than 1, but TMin − 1 wraps to 127.

In the book’s C, overflows are not signaled as errors: the wrong number just carries on. Rust says exactly what happens. In a debug build every +, - and * is checked, and an overflow panics. In a release build the checks are off and the result wraps, two’s-complement style, which Rust still counts as a bug in your program. When you mean one answer in every build, you say which: wrapping_mul keeps the low bits, checked_mul returns an Option, either Some(value) or None, saturating_mul stops at the ruler’s end, and overflowing_mul returns the wrapped value with a true-or-false. The same four families exist for add, subtract, negate and shift.

Try it: run the four-factor product, then the i8 comparison. Same idea, smaller ruler. Then open Rust’s six answers and press Run it to step through every way Rust can multiply 24,000,000 by 500.

What the book says

On a machine with a 32-bit int, 200 * 300 * 400 * 500 yields −884,901,888. Multiplication is associative and commutative, so (500 * 400) * (300 * 200) and the other parenthesizations yield that same value.

Section 2.3 opens by noting that adding two positive numbers can yield a negative result, and that x < y can differ from x - y < 0. Both are artifacts of finite computer arithmetic. The following subsections say exactly when unsigned and two’s-complement addition and multiplication wrap.

2.3.1 · unsigned addition

A clock with 2w hours

Two w-bit unsigned numbers add to something that may need w+1 bits. The computer keeps w. The result is the true sum mod 2w. On four bits, 9 + 12 = 21, and 21 mod 16 is 5.

You can detect the wrap without a fifth bit: it overflowed exactly when the stored sum is smaller than either addend. 5 < 9, so yes. The book’s C does not signal it. Rust does in a debug build, where a plain + that wraps panics, and its standard library does in every build: checked_add returns None when the sum would wrap, and overflowing_add hands back the stored sum together with a true-or-false “it wrapped.” The book puts its getpeername aside here; this page runs it in 2.2.8, beside the other signed-versus-unsigned bugs.

Try it: add on the 16-hour clock. Cross 15 and watch the overflow pill light, because the stored sum dropped below x.

What the book says

For 0 ≤ x, y < 2w, the true sum can be as large as 2w+1 − 2. Figure 2.21 plots that for w = 4: arguments 0…15, sums 0…30. Unsigned addition keeps the sum modulo 2w. It overflows if and only if the stored sum s satisfies s < x (or equally s < y).

2.3.2 · two’s-complement addition

The same adder, a different overflow rule

Two’s-complement addition uses the identical bit adder. Truncate the sum to w bits. The difference is only how you notice trouble. Positive overflow: both addends positive, stored sum not positive. Negative overflow: both negative, stored sum not negative.

On four bits, 5 + 5 = 10, which does not fit in −8…7, so the bits read as −6. And −5 + −5 = −10 becomes +6. In range, −3 + 5 is just 2. Figure 2.25 is this picture.

Try it: the three cases are buttons. The bit sum is the same procedure every time. Only the verdict changes.

What the book says

The bit-level representation of a two’s-complement sum is binary addition, truncated to w bits. Positive overflow happens if and only if x > 0, y > 0, and s ≤ 0. Negative overflow happens if and only if x < 0, y < 0, and s ≥ 0. When the true sum is below TMin, the stored result is 2w too high. When it is above TMax, the stored result is 2w too low.

2.3.3 · two’s-complement negation

Flip the bits and add one — except once

The additive inverse of x is the number you add to x to get zero. On this ruler that is usually −x, and the bits of −x are the complement plus one. The book writes that ~x + 1; Rust writes !x + 1. Try 5: 0101, complement 1010, plus one is 1011, which is −5. And −5 + 5 wraps to 0.

TMin is the exception. −(−8) would be +8, and +8 is not on a four-bit ruler. Complement of 1000 is 0111, plus one is 1000 again. TMin is its own negation. Rust treats that as an overflow: -x with x = i32::MIN panics in a debug build (“attempt to negate with overflow”). wrapping_neg gives back TMin, the book’s answer, and checked_neg gives None.

What the book says

Two’s-complement negation of x is ~x + 1 at the bit level. For every x other than TMin, that result is the ordinary −x, and x + (−x) = 0 inside the word. The principle the book states: −t TMinw = TMinw. TMin is its own additive inverse, because the positive value 2w−1 cannot be represented.

2.3.5 · two’s-complement multiplication

Same bits as the unsigned product

Here is the gift of two’s complement. Multiply the bit patterns as if they were unsigned, keep the low w bits, and you already have the two’s-complement product. The circuitry does not branch.

The reading can still surprise you. −5 × −5 = 25, which on four bits is the bits of 9, read as −7. And the chapter’s 200 × 300 × 400 × 500 is this same truncation on 32 bits: the low half of a positive product, read with a sign bit, is negative.

The book’s XDR aside is this truncation with a security price. Sun’s library computed a buffer size as count × size. With 1,048,577 elements of 4,096 bytes in a 32-bit program, the product wraps to 4,096, so it allocated 4,096 bytes and then copied over four gigabytes into them. Rust’s checked_mul returns None instead of a wrong size, and a match, which runs the one arm that fits the value, handles each case: allocate, or refuse. Rust’s own growable array, Vec, makes this check for you: Vec::<u32>::with_capacity(usize::MAX) panics with “capacity overflow” rather than allocate too little.

Try it: multiply −5 by −5. The unsigned machine and the signed machine drop the same bits. Then run the 32-bit product, and the XDR size.

What the book says

The bit-level result of two’s-complement multiplication equals the bit-level result of unsigned multiplication on the same bit vectors. The low-order w bits are the product modulo 2w, then interpreted with U2T if you want the signed value. Figure 2.27 shows three-bit cases of both.

2.3.6 · multiplying by constants

A shift is a multiply, until bits fall off

Left shift by k is multiplication by 2k, for unsigned and for two’s complement, including when it overflows. Compilers prefer shifts because, on the book’s Haswell reference machine, an integer multiply costs 3 cycles and a shift costs 1. Historically multiply cost 10 or more.

So x * 14 becomes (x<<3) + (x<<2) + (x<<1), since 14 = 8+4+2. Even better, 14 = 16−2, so (x<<4) - (x<<1). Both match the multiply even if the product wraps.

rustc does this rewrite too, through LLVM, the code generator it is built on. Compile x.wrapping_mul(14) with -C opt-level=1 (basic optimisation, and no debug overflow checks) and the machine code has no multiply at all: a shift, an lea and a subtract, the book’s second form. x.wrapping_mul(3) becomes one lea (%rdi,%rdi,2), which is x + 2x.

Try it: compute 3 × 14 both ways on a u8, then push x until the product wraps. The shift form wraps with it. Then open rustc’s code and follow x through the four real instructions.

What the book says

Shifting the 4-bit pattern [1011] (the number 11) left by 2 gives [101100], which is 44 = 11 × 4. Truncating back to 4 bits gives [1100], the value 12, and 44 mod 16 is 12. For a fixed word, x << k equals x multiplied by 2k in unsigned or two’s-complement arithmetic.

Because multiply is slower — 3 clock cycles on the Intel Core i7 Haswell, against 1 for a shift or an add — compilers rewrite x*14 as (x<<3)+(x<<2)+(x<<1) or as (x<<4)-(x<<1). The results match even on overflow. A single lea can compute (a<<k)+b for small k, so 3*a is (a<<1)+a.

Integer division rounds toward zero. An unsigned >> k already does that, because a logical right shift of a nonnegative number is floor of the division. Figure 2.28: 12,340 shifted right by 4 is 771, and 12,340 / 16 is 771.25.

2.3.8 · final thoughts on integer arithmetic

Modular, and still mostly well behaved

What the machine calls integer math is modular arithmetic. The ring is small, so some familiar sentences fail. x*x >= 0 is not always true. x>0 || -x>=0 fails at TMin, whose negation is itself.

A lot still holds: associativity, commutativity, distributivity. That is why a compiler may rewrite 7*x as (x<<3)-x and promise the same bits, overflow included. Practice Problem 2.44 is a list of sentences. Some are always true. Some have a counterexample.

Try it: pick a sentence and sweep x. The line in the code panel turns green when the sentence holds and red when this x breaks it. The Rust uses wrapping_mul and wrapping_neg to get the machine’s modular answers; a plain * would panic in a debug build.

What the book says

Computer “integer” arithmetic is modular. Two’s complement lets addition, subtraction, multiplication, and even division share most of their bit-level behavior with the unsigned forms. Unsigned surprises, including constants and library types such as size_t, are a common source of bugs.

Practice Problem 2.44 asks which expressions are true for all 32-bit two’s-complement x and y. Among them: x*x >= 0 is not, and x>0 || -x>=0 fails when x is TMin. The summary later notes that associativity, commutativity, and distributivity still hold, which is what justifies replacing 7*x by (x<<3)-x, and that ~x+1 equals -x except at TMin.

2.4 · floating point

A significand, and a power of two

Integers are exact and short-ranged. Many programs need tiny fractions and enormous magnitudes. A floating-point number is a rational of the form V = x × 2y: a significand, and a scale. Move the scale and the gaps between neighbors grow.

Until about 1985 every maker invented its own version, and often favored speed over accuracy. IEEE Standard 754, with William Kahan’s design at its core, made one format that scientific code can trust from machine to machine.

Try it: slide the scale. The same two significand steps land farther apart as the power of two grows. That spreading is the whole idea, before the bit fields.

What the book says

A floating-point representation encodes rationals of the form V = x × 2y. It is for numbers with very large magnitude, numbers very close to 0, and as an approximation to real arithmetic. Before the 1980s each manufacturer defined its own format and often treated accuracy as secondary to speed.

Around 1985, IEEE Standard 754 replaced that variety. The effort began in 1976 for Intel’s 8087. Intel hired William Kahan of the University of California, Berkeley. The IEEE committee adopted a standard close to his. Virtually all computers now support IEEE floating point. The aside notes that IEEE, the Institute of Electrical and Electronics Engineers, also publishes the 802.11 wireless standard.

2.4.2 · IEEE floating-point representation

Sign, exponent, fraction

The bits split into three fields. s is the sign. exp is a biased exponent. frac is the fraction. Single precision is 1 + 8 + 23 bits, bias 127. Double is 1 + 11 + 52, bias 1023.

If exp is all zeros, the number is denormalized: no hidden 1, so the tiniest values, including ±0, can be stored. If exp is all ones, you have ±infinity or a NaN. Otherwise the number is normalized: a hidden leading 1, and the real exponent is exp minus the bias.

What the book says

2.4.4 · rounding

What to do with $1.50

Most real numbers sit between two values the format can store. Rounding picks one. The IEEE default is round-to-even: pick the nearest, and if you are exactly halfway, pick the one whose last digit is even. So $1.40 goes to $1, $1.60 goes to $2, and both $1.50 and $2.50 go to $2.

The other three modes are bounds. Toward zero. Down (toward −∞). Up (toward +∞). Always rounding halves the same direction would bias an average. Even rounding goes up about half the time and down about half the time.

Rust’s f32 and f64 round every +, -, * and / to even, as IEEE says. To round a number to a whole one yourself, each mode has a method: round_ties_even, trunc, floor and ceil. Watch out for the one called plain round: it sends ties away from zero, so 2.5f64.round() is 3, not 2.

Try it: press each dollar amount. The four modes answer together. $1.50 is the row where they disagree.

What the book says

Figure 2.37 rounds to the nearest dollar. Round-to-even, also called round-to-nearest, is the default: $1.40 → $1, $1.60 → $2, $1.50 → $2, $2.50 → $2, $−1.50 → $−2. Round-toward-zero gives $1, $1, $1, $2, $−1. Round-down gives $1, $1, $1, $2, $−2. Round-up gives $2, $2, $2, $3, $−1.

The even rule avoids a statistical bias in averages. The same idea applies past the decimal point: 1.2350000 and 1.2450000 both round to 1.24 when the target is hundredths, because 4 is even. In binary, a 0 in the last kept bit is even and a 1 is odd. The mode matters for a pattern whose remainder begins with 1 followed by all zeros — a perfect tie.

2.4.5 · floating-point operations

Round the exact answer — and order matters

The rule is simple to say. Compute the exact real result, then round it to a value the format can hold. Specials have their own manners: 1/+0 is +∞, 1/−0 is −∞, and ∞ − ∞ is NaN.

Addition and multiplication are commutative. They are not associative. In single precision, (3.14+1e10)-1e10 is 0.0, and 3.14+(1e10-1e10) is 3.14. And (1e20*1e20)*1e-20 overflows to +∞, while the other association stays 1e20. A compiler that reassociates a+b+c can change the answer, so compilers mostly refuse. Rust promises more than “mostly”: each f32 or f64 operation gives the result IEEE 754 specifies, so rustc may not regroup your sum or fuse a multiply and an add behind your back.

Try it: run the three single-precision expressions. The two associations are different code paths. Watch which one loses the small number, and which one hits infinity.

What the book says

The result of an operation is Round(x ⊙ y), the exact real result then rounded. 1/−0 yields −∞ and 1/+0 yields +∞. Floating-point addition is commutative, and x + (−x) is 0 except for infinities (∞ − ∞ is NaN) and NaNs. It is not associative. With single precision, (3.14+1e10)−1e10 evaluates to 0.0, while 3.14+(1e10−1e10) evaluates to 3.14.

Multiplication is commutative and has identity 1.0, and it is not associative: (1e20*1e20)*1e-20 evaluates to +∞, while 1e20*(1e20*1e-20) evaluates to 1e20. It does not distribute: 1e20*(1e20−1e20) is 0.0, while 1e20*1e20 − 1e20*1e20 is NaN. Monotonicity does hold, for values other than NaN. A compiler that computes t = b+c and then x = a+t may not match x = a+b+c.

Single precision, two associations
2.4.6 · floating point in C

Casts that round, and one that overflows

C’s float and double are single and double precision on machines that follow IEEE, rounding to even. But C itself does not promise IEEE, nor a portable way to name infinity or change the rounding mode. Rust’s f32 and f64 are IEEE single and double by definition, the standard library names the specials (f64::INFINITY, f64::NAN), and the rounding mode is always round-to-even: Rust has no way to switch it.

Casts have house rules, and in Rust every one of them is an as whose answer the language defines. An i32 to f32 cannot overflow, but it can round: 16777217 as f32 (that is 224+1) is 16,777,216. An i32 or an f32 to f64 keeps the value (a wider i64 can round, since f64 keeps only 53 significant bits). f64 as f32 can round, or overflow to infinity: 1e300 as f32 is inf. Float to int rounds toward zero, so 1.999 becomes 1 and −1.999 becomes −1.

The edge is a value that does not fit. The book’s C, on an Intel-compatible chip, turns +1e10 into the “integer indefinite” bit pattern: TMin, a negative number from a positive input. Rust’s as saturates instead, stopping at the nearest end of the ruler: 1e10 as i32 is i32::MAX, -1e10 as i32 is i32::MIN, and NaN becomes 0. It never panics. (Before Rust 1.45 such a cast was undefined behaviour.) A saturated answer still looks like a real number, so when the value might not fit, test it first.

Try it: run each cast. The code panel is the expression, and the note is what comes back.

What the book says

float and double are the two C floating types. On IEEE machines they are single and double precision, rounded to even. The standards do not require IEEE, so there is no portable way to change the rounding mode or to name −0, +∞, −∞, or NaN. gcc defines INFINITY and NAN when the program defines _GNU_SOURCE and includes the math.h header.

Assuming a 32-bit int: int to float may round but cannot overflow; int or float to double preserves the value; double to float may overflow to ±∞ or round; float or double to int rounds toward zero. 1.999 becomes 1 and −1.999 becomes −1. A conversion that cannot produce a reasonable integer yields the bit pattern [10…00], TMin, on Intel-compatible processors. The book’s example is casting +1e10 to int, which turns a positive value into that negative pattern.

A 16-bit box, and a faster rocket

The chapter’s last picture is not a formula. On 4 June 1996, 37 seconds after liftoff, Ariane 5 veered, broke up, and exploded. Satellites worth $500 million were aboard.

The navigation computer had converted a 64-bit floating-point horizontal velocity into a 16-bit signed integer. The value overflowed. Instead of a velocity, it sent a diagnostic bit pattern. Ariane 4’s software had been checked against speeds that fit in 16 bits. Ariane 5 was more than five times faster in that measurement, and the old assumption was reused without being rechecked.

Rust’s v as i16 would not report the overflow at all: it saturates, so 80,000.0 becomes 32,767, a believable and wrong speed. The listing’s careful version returns an Option: None when the value does not fit, so the caller must decide what to do. Its last line, fits.then_some(v as i16), turns the true-or-false fits into Some(v as i16) when it is true and None when it is false.

Try it: keep the velocity inside a signed 16-bit range, then push it past 32,767. The cast stops being a speed.

What the book says

The summary gathers the chapter: bits and bytes, 32-bit versus 64-bit programs, two’s complement, IEEE 754, casts that keep the bits, and arithmetic that overflows or underflows. Integer arithmetic stays associative, commutative, and distributive even though x*x can be negative. The seesaws from this chapter

Every encoding spends its bits on something. Push one side and the other gives way.

Hex

One digit names four bits. Easy to read a dump.

vs

Decimal

Comfortable for people. Hides the bits, and needs division to convert.

32-bit program

Pointers are 4 bytes, the size of an i32. The address space stops at 4 GB.

vs

64-bit program

A huge address space. Pointers are 8 bytes; an i32 stays 4.

Little endian

Low byte at the low address. What Intel, Linux, Windows, Android, and iOS store.

vs

Big endian

High byte first, the way we write numbers. The Sun in Figure 2.6.

Unsigned

0 through 2w−1, a perfect circle. One unsigned operand can quietly change a comparison.

vs

Two’s complement

Negatives included. The range is lopsided: TMin has no positive twin.

Integer arithmetic

Exact, and associative, inside a small range. Overflow wraps, and a product of positives can be negative.

vs

Floating point

A huge range, only approximate. Overflow becomes infinity. Addition is not associative.

vs

Guaranteed bounds. Useful, and not the default.

Words to know

The chapter’s grown-up words, in one plain sentence each.

byte / address
Eight bits, the smallest box a program can name. The address is that box’s number.
word
The nominal size of a pointer: 4 bytes in a 32-bit program, 8 in a 64-bit one.
hexadecimal
Base 16. One digit, 0–F, names exactly four bits. Rust writes it 0x…, as C does.
little / big endian
Least-significant byte at the lowest address, or most-significant byte first.
ASCII / null / UTF-8
ASCII is the usual one-byte character codes; UTF-8, Rust’s text encoding, keeps them as single bytes. A C string ends with a null byte of value 0; a Rust &str stores its length instead.
mask
A bit pattern used with & or | to keep, clear, or set chosen bits.
logical vs bitwise
Rust’s && || ! take true or false, and && || can stop early. & | ^ and ! on an integer walk every bit. (C’s logical operators take integers, and C writes bitwise NOT as ~.)
arithmetic right shift
Fill the vacated left bits with copies of the sign bit.
B2U / UMax
Ordinary binary. The biggest value on w bits is 2w − 1.
B2T / TMin / TMax
Two’s complement. The top bit weighs −2w−1. Range TMin … TMax, one step longer on the negative side.
T2U / U2T
Keep the bits, change the reading. A negative x becomes x + 2w.
sign extension
When a signed value grows, copy the sign bit into the new high bits.
overflow
The true result does not fit. Unsigned and two’s-complement wrap. Floats become infinity.
panic
Rust stopping the program with a message instead of carrying on with a wrong value: an index past the end, or an overflow in a debug build.
debug / release build
rustc’s default build has no optimisation and checks every integer overflow; an optimised build skips those checks, and an overflow wraps.
wrapping / checked / saturating / overflowing
Rust methods that pick the overflow answer on purpose, in every build: keep the low bits, return None, stop at MIN or MAX, or return the wrapped value with a true-or-false.
as
Rust’s cast. Between integers it keeps, truncates or extends the bits; float to integer rounds toward zero and saturates; it never panics.
raw pointer / unsafe
A bare address the compiler does not check. Reading through one needs an unsafe block, the programmer’s promise that the read is valid.
undefined behaviour
A program Rust’s rules give no meaning to, such as reading outside an object through a raw pointer. Safe Rust cannot produce it.
IEEE 754
The standard that packs a sign, an exponent, and a fraction into V = (−1)s × M × 2E.
denormalized / NaN
Exponent all zeros: no hidden 1, including ±0. Exponent all ones and a nonzero fraction: not a number.
round-to-even
The default: round to nearest, and break a tie toward the even last digit.
