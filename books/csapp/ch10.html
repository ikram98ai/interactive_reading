System-Level I/O

Input copies bytes from a device into memory. Output copies bytes the other way. Linux makes every device look like a file, so one small set of calls serves the disk, the keyboard, and the network.

“All I/O devices, such as networks, disks, and terminals, are modeled as files, and all input and output is performed by reading and writing the appropriate files.”

10.1 · Unix I/O

A ticket, not the drawer

A Linux file is a sequence of m bytes. Opening one asks the kernel for a small nonnegative integer, the descriptor. Priya stores that number. The kernel stores everything else, including a file position k that starts at 0.

A new process already holds three descriptors: 0 standard input, 1 standard output, 2 standard error. A read of n bytes copies from k and then sets k to k+n. If k is already past the last byte, the read returns 0. That condition is end-of-file. There is no EOF character hiding in the file. Close puts the descriptor back in the pool. Exit closes whatever is left.

Try it: press Open foo.txt. The lowest free number is 3. Then Read 4 twice, and once more for EOF. Watch the same line light up in both listings.

What the book says

Opening a file asks the kernel to open the corresponding file. “The kernel keeps track of all information about the open file. The application only keeps track of the descriptor.” unistd.h names descriptors 0, 1, and 2 STDIN_FILENO, STDOUT_FILENO, and STDERR_FILENO.

The kernel maintains a file position k, initially 0. A read copies n > 0 bytes starting at k and then increments k by n. When k ≥ m, the application detects end-of-file. “There is no explicit EOF character at the end of a file.” Close frees the kernel structures and restores the descriptor to the pool. Process termination closes every open file.

10.2 · files

A type, a place, and bytes

Kenji’s tree hangs from one root, /. A regular file holds bytes. A directory is a list of names, and it always contains . (itself) and .. (its parent). A socket is a file used to talk to another process across a network. The kernel does not have a separate text type and binary type. Programs invent that distinction.

A Linux text line ends with one byte, newline, value 0x0a. Windows and HTTP end a line with 0x0d 0x0a. Open that file on Linux and each line shows a ^M. An absolute pathname starts with /. A relative pathname starts from the process’s current working directory.

Try it: tap a file, then change cwd and read the pathname the listing prints. Switch to end of line and compare one Linux newline with a Windows pair.

What the book says

A regular file contains arbitrary data. Applications distinguish text files from binary files. “To the kernel there is no difference between text and binary files.” A Linux text line ends with '\n', the ASCII line feed, numeric value 0x0a. MS Windows and HTTP use '\r\n' (0x0d 0x0a).

A directory is an array of links. Each contains at least . and ... Figure 10.1 includes /home/droh/hello.c, /usr/include/stdio.h, /bin/bash, and /dev/tty1. An absolute pathname starts with a slash. If the cwd is /home/droh, the relative name of hello.c is ./hello.c. If the cwd is /home/bryant, it is ../droh/hello.c. Named pipes, symbolic links, and character and block devices are beyond the chapter’s scope.

10.3 · opening and closing files

The lowest free number

open returns a descriptor, or −1. It never skips a hole. Mei already holds 0, 1, and 2, so the first open returns 3. She closes 3. The next open — even of a different file — returns 3 again. Closing a descriptor that is already closed is an error.

The flags say how she will use the file: read, write, or both, plus O_CREAT, O_TRUNC, and O_APPEND. Append sets the position to the end before each write. A new file’s permission bits are mode & ~umask. The umask crosses out bits the process refuses to grant.

Try it: step Practice Problem 10.1. Then umask, and watch group-write and other-write disappear. Then O_APPEND and write one Z.

What the book says

open(filename, flags, mode) returns a new descriptor or −1. “The descriptor returned is always the smallest descriptor that is not currently open in the process.” Access flags: O_RDONLY, O_WRONLY, O_RDWR. Extra flags, or-ed in: O_CREAT, O_TRUNC, O_APPEND.

Figure 10.2 lists the permission bits. New-file bits are mode & ~umask. With DEF_MODE granting read and write to user, group, and other, and DEF_UMASK equal to S_IWGRP|S_IWOTH, the owner can read and write and everyone else can only read. close returns 0 or −1. Practice Problem 10.1 prints fd2 = 3.

10.4 · reading and writing files

Fewer bytes is not a failure

read copies at most n bytes from the current position into memory. It returns −1 on error, 0 on EOF, otherwise the number of bytes it actually moved. write is the same idea toward the device. A return smaller than n is a short count. It is not an error.

On a disk, reads come up short only at the end, and writes do not come up short at all. On a terminal, each read returns one typed line. On a socket, buffering and delay can hand back any number, and a write can go short too. size_t is unsigned. ssize_t is signed, because the call must be able to return −1.

Try it: on disk EOF, ask for 50 from a 20-byte file. Then a terminal line, then a socket that dribbles.

What the book says

read returns −1 on error, 0 on EOF, otherwise the number of bytes transferred. Figure 10.3 copies standard input to standard output one byte at a time. lseek can move the position; it is beyond the chapter’s scope.

“Such short counts do not indicate an error.” They happen at EOF (20 bytes left, a 50-byte request, so the next read returns 20 and the one after returns 0), from a terminal (one text line per read), and on sockets because of buffering and delay. In practice disk reads short only at EOF, and disk writes do not short. On x86-64, size_t is an unsigned long and ssize_t is a long. The possibility of returning −1 halves the maximum size of a read.

10.5.1 · Rio unbuffered

Stay until the count is met

Rio is a small package that deals with short counts for you. The unbuffered pair, rio_readn and rio_writen, copies straight between memory and a descriptor. No private buffer. That is the right tool for binary data on a network.

rio_readn may return a short count only when it hits EOF. rio_writen never returns a short count: it loops until every byte is written, or a real error occurs. If a signal handler interrupts the system call, errno is EINTR and the function simply tries again. The two calls may be interleaved on the same descriptor.

Try it: press Step and watch nleft fall 8, 5, 2, 0. Press Signal before a read and see the retry leave nleft alone. Then switch to rio_writen.

What the book says

Applications that must be robust call read and write until every requested byte has moved. Rio does that loop. Unbuffered rio_readn and rio_writen transfer directly between memory and a file. “The rio_readn function can only return a short count if it encounters EOF.” rio_writen never returns a short count. Both restart after EINTR. They may be interleaved on the same descriptor.

The package is inspired by Stevens’s readn and writen. The picture below is a teaching sketch of that loop, with a tiny transfer of 8 bytes so each subtraction fits on the stage. The book’s listing is Figure 10.4.

10.5.2 · Rio buffered input

One kernel read, then serve from the drawer

Reading a file one byte at a time with read traps into the kernel for every byte. rio_readinitb ties a descriptor to a rio_t: a descriptor, an unread count, a pointer, and a buffer. The book sizes that buffer at 8192 bytes. This picture uses 8 so you can see it refill.

When the buffer is empty, an internal read fills it. A short fill is fine. rio_readlineb then copies until newline, and adds a terminating zero. rio_readnb is the buffered cousin of rio_readn. Those two may share a descriptor. Do not mix them with unbuffered rio_readn: the kernel position has already moved past bytes still sitting in the buffer.

Try it: Init, then Read a line twice. The second line does not call the kernel. Then press Unbuffered read and watch it skip the bytes still in the drawer.

What the book says

rio_readinitb associates a descriptor with a rio_t and sets the unread count to 0. rio_readlineb copies the next text line, including the newline, NUL-terminates it, and reads at most maxlen-1 bytes. rio_readnb transfers raw bytes from the same buffer. Figure 10.5 is cpfile: init, then readline and writen.

Internal rio_read refills when rio_cnt <= 0. A short fill is not an error. It then copies min(n, rio_cnt) bytes. Buffered calls must not be interleaved with unbuffered rio_readn on the same descriptor. The buffered pair is thread-safe, which fixes the static buffer in Stevens’s readline.

10.6 · reading file metadata

Read the card, not the book

Fatima wants the size of a file, and whether she may read it, without opening it. stat and fstat fill a struct stat. That record is the file’s metadata. Standard I/O has no call for this. It is one reason Unix I/O exists at all.

Two facts share st_mode: the type, and the permission bits. S_ISREG, S_ISDIR, and S_ISSOCK read the type. st_mode & S_IRUSR asks whether the owner may read. st_size is the length in bytes. The chapter needs those two members later for a Web server. The rest of the struct is beyond its scope.

Try it: pick a file, then press Step. The highlighted branch is the one statcheck actually takes. secret is a regular file the owner cannot read.

What the book says

stat(filename, &buf) and fstat(fd, &buf) fill a struct stat (Figure 10.9). The chapter needs st_mode and st_size. st_mode encodes both the permission bits of Figure 10.2 and the file type of Section 10.2.

Macros: S_ISREG, S_ISDIR, S_ISSOCK. Figure 10.10 prints type: regular, directory, or other, and read: yes or no from st_mode & S_IRUSR. The standard I/O library provides no way to read this metadata.

10.7 · reading directory contents

A stream of names

Nia opens a directory the way she would open a book of names: opendir returns a stream, readdir returns the next entry, closedir puts it away. Each struct dirent has two fields you can count on: d_ino and d_name.

The awkward part is the end. readdir returns NULL both when the stream is finished and when something went wrong. The only way to tell is to set errno to 0 before the call. NULL with errno still 0 means “no more entries.” NULL with errno changed means an error.

Try it: press Step. You should see ., .., and hello.c, then a quiet NULL. Press Force an error to see the other NULL.

What the book says

Applications read a directory with opendir, readdir, and closedir. Only d_ino and d_name are standard across systems. readdir returns NULL at the end or on error. “The only way to tell the difference is to check whether errno has changed.” Figure 10.11 sets errno = 0 before the loop and tests it after.

10.8 · sharing files

Three tables, one question: whose bookmark?

The kernel keeps three related tables. Each process has a descriptor table. Each open descriptor points at an entry in the process-wide file table, which holds the position and a reference count. That entry points at a v-node, which holds most of the stat facts, including size and type.

Yuki opens foobar.txt twice. Two descriptor slots, two file-table entries, one v-node. Each entry has its own position, so both reads return f. If she forks instead, Sofia gets a copy of the descriptor table but shares the file-table entry. One position. Sofia reads f, Yuki’s next read is o. Both must close before the reference count hits zero and the kernel deletes the entry.

Try it: on two opens, read fd1 and then fd2. Both say f. On fork, let the child read first. The parent gets o.

What the book says

Figure 10.12: descriptors 1 and 4 name two different files — no sharing. Figure 10.13: two descriptors, same disk file, two file table entries. “The key idea is that each descriptor has its own distinct file position.” Practice Problem 10.2 therefore prints c = f.

Figure 10.14: after fork, parent and child share the open file table entries, so they share the file position, and each reference count becomes 2. Practice Problem 10.3: the child reads the first byte of foobar, the parent reads the second, and the output is c = o.

10.9 · I/O redirection

Point descriptor 1 at a different file

The shell command ls > foo.txt sends a listing into a file. The book’s nickname for > is the right hoinky. The call underneath is dup2(oldfd, newfd): copy descriptor-table slot oldfd onto slot newfd. If newfd was already open, dup2 closes it first.

Start with fd 1 as the terminal (file A) and fd 4 as a disk file (file B). After dup2(4, 1) both slots point at B, A’s file-table entry is deleted, and B’s reference count is 2. Anything written to standard output now lands in the notebook. Practice Problem 10.5 uses the same trick on two opens of foobar.txt: after the copy, the next read is o, not f.

Try it: press dup2(4, 1) and watch fd 1 leave the terminal. Then step Practice Problem 10.5.

What the book says

dup2(oldfd, newfd) copies descriptor table entry oldfd to newfd, closing newfd first if it was open. Figure 10.15 is that picture: both descriptors point at file B, and B’s reference count is 2. Practice Problem 10.4 redirects standard input with dup2(5, STDIN_FILENO).

Practice Problem 10.5: two opens of foobar.txt, Read(fd2), Dup2(fd2, fd1), Read(fd1). fd1 now shares fd2’s file position, already past the first byte, so the output is c = o.

10.10 · standard I/O

A FILE is a descriptor plus a buffer

ANSI C gives you a higher layer: fopen, fclose, fread, fwrite, fgets, scanf, printf. An open file at this layer is a stream, a pointer to a FILE. Every C program starts with stdin, stdout, and stderr, which are descriptors 0, 1, and 2 in disguise.

A FILE holds a descriptor and a buffer. The first getc may fill that buffer with one read. Later getc calls stay in user space. Streams are full duplex, but there is a rule: input after output needs an fflush or a seek, and output after input needs a seek, unless the input hit EOF. A socket cannot seek.

Try it: press getc and count kernel reads. Then switch to direction and step until a socket makes fseek illegal.

What the book says

The standard I/O library models an open file as a stream, a pointer to a FILE. A FILE is a descriptor plus a stream buffer, filled by one read so later character calls stay in user space. Figure 10.16 draws this layer, and Rio, sitting on top of Unix I/O.

Input functions following output functions need fflush, fseek, fsetpos, or rewind first. Output functions following input functions need a seek, unless the input hit EOF. lseek is illegal on a socket, so that second restriction cannot be worked around there.

10.11 · which I/O functions should I use?

Three guidelines

Noor has three toolboxes and three rules. G1: use standard I/O whenever you can — disk files and terminals. G2: do not use scanf or rio_readlineb on a binary file. A 0x0a byte in a picture is not a newline. G3: use Rio for sockets.

The socket trap is specific. People open one descriptor twice with fdopen, once to read and once to write, because they cannot seek between directions. The first fclose closes the descriptor. The second fclose closes it again. The book’s way around it: format with sprintf and send with rio_writen; read a line with rio_readlineb and parse with sscanf.

Try it: tap disk text, binary, or socket. Then socket trap and step both fclose calls.

What the book says

G1: “Use the standard I/O functions whenever possible.” They are the method of choice on disk and terminal devices. Most C programmers use them exclusively, except possibly stat, which has no standard I/O counterpart. G2: do not use scanf or rio_readlineb to read binary files. G3: “Use the Rio functions for I/O on network sockets.”

Opening two streams with fdopen on the same socket and calling fclose on both closes the same descriptor twice — a recipe for disaster in a threaded program (Section 12.7.4). Format in memory with sprintf and send with rio_writen. Read a line with rio_readlineb and parse with sscanf.

Words to know

The chapter’s grown-up words, in plain language.

descriptor
A small nonnegative integer that names an open file in this process. 0, 1, and 2 start out taken.
file position
The byte offset k where the next read or write begins. It lives in the kernel, not in your variable.
EOF
A read when k is past the last byte. Returns 0. There is no end-of-file character in the file.
short count
Fewer bytes than you asked for. Not an error. Normal at EOF, on a terminal, and on a socket.
umask
Permission bits the process refuses to grant. A new file’s mode is mode & ~umask.
Rio
Robust I/O. Unbuffered rio_readn and rio_writen, and buffered rio_readlineb and rio_readnb.
rio_t
The buffered reader’s private drawer: descriptor, unread count, pointer, and an 8192-byte buffer.
EINTR
A system call was interrupted by a signal. Rio sets the count to 0 and tries again.
metadata
Facts about a file from stat or fstat — type, size, permissions — without reading the bytes.
descriptor table
Per process. Each open slot points at one file-table entry.
file table
Shared. Holds the file position, a reference count, and a pointer to a v-node.
v-node
Shared. Holds most of the stat information for one file, including type and size.
dup2
Copy one descriptor-table slot onto another. How the shell implements > and <.
stream
A FILE* : a descriptor plus a buffer, so later getc calls can stay in user space.
current working directory
The process’s location in the tree. Relative pathnames start here.
