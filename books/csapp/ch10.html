10.1 · Unix I/O

A ticket, not the drawer

Priya walks into a post office. Every window — the letter slot, the counter screen, even the phone line to another town — is the same kind of drawer. She does not carry the drawer. She carries a small numbered ticket. That ticket is a descriptor.

A new program already holds three tickets: 0 for what she types, 1 for what she prints, 2 for complaints. The clerks (the kernel) remember where each ticket points, and how far through the pile they have read. That “how far” is the file position.

Try it: Press Open foo.txt to get ticket 3. Then Read 4 and watch the file position climb. Close puts 3 back in the pool.

What the book says

A Linux file is a sequence of m bytes. Opening a file asks the kernel for a small nonnegative integer, the descriptor. “The kernel keeps track of all information about the open file. The application only keeps track of the descriptor.”

Each process created by a Linux shell begins with standard input (descriptor 0), standard output (1), and standard error (2). unistd.h names them STDIN_FILENO, STDOUT_FILENO, and STDERR_FILENO.

The kernel keeps a file position k, initially 0. A read of n>0 bytes starts at k and then sets k ← k+n. If k ≥ m, the application sees end-of-file. There is no explicit EOF character at the end of a file. Close frees the kernel structures and returns the descriptor to the pool. Process exit closes every open file.

10.2 · 10.7 · files and directories

Houses, street signs, phone lines

Kenji’s town map has one root street named /. A house holds a story — a regular file. A street sign is a list of names, each name pointing at another place. That list is a directory. A phone line to another town is a socket.

Every directory keeps two special names: . (this street) and .. (the street above). Kenji’s current working directory is where he is standing, so the same house has two addresses: one from the root, and one from here.

Try it: Tap a file to see its type and both pathnames. Switch cwd with the buttons. Then pick readdir and Step through ., .., and hello.c.

What the book says

A regular file holds arbitrary data. Applications distinguish text files (ASCII or Unicode) from binary files. “To the kernel there is no difference between text and binary files.” A Linux text line ends with a newline '\n', the ASCII line feed, numeric value 0x0a. Linux and Mac OS X use that byte; MS Windows and HTTP use the sequence '\r\n' (0xd 0xa).

A directory is an array of links from filename to file. Each directory contains at least . and ... Figure 10.1 is a slice of the hierarchy: /home/droh/hello.c, /usr/include/stdio.h, /bin/bash, /dev/tty1. An absolute pathname starts with a slash. A relative pathname starts from the current working directory: from /home/droh the relative name of hello.c is ./hello.c.

Sockets talk to another process across a network (Section 11.4). Named pipes, symbolic links, and character and block devices are beyond the chapter’s scope.

Applications walk a directory with opendir, readdir, and closedir. Each struct dirent has d_ino and d_name — the only two members standard across systems. readdir returns NULL at the end or on error; the only way to tell is to check whether errno changed. Figure 10.11 is the loop.

10.3 · opening and closing

Always the lowest empty locker

Mei asks for a locker. The attendant never skips. Lockers 0, 1, and 2 are already taken, so the first open hands her 3. She gives 3 back. The next open — even for a different file — hands her 3 again.

When she creates a new notebook, two stamps decide who may touch it: the mode she asked for, and her process umask, which crosses out bits she does not want the group or the world to have.

Try it: Step Practice Problem 10.1: open foo.txt, close it, open baz.txt. Then switch to umask and watch mode & ~umask knock out group-write and other-write.

What the book says

open(filename, flags, mode) returns a new descriptor or −1. “The descriptor returned is always the smallest descriptor that is not currently open in the process.” Access flags: O_RDONLY, O_WRONLY, O_RDWR. Extra write flags, or-ed in: O_CREAT (create a truncated empty file if missing), O_TRUNC, O_APPEND (seek to the end before each write).

Figure 10.2 lists the permission bits in sys/stat.h (S_IRUSR … S_IXOTH). New-file bits are mode & ~umask. With DEF_MODE = S_IRUSR|S_IWUSR|S_IRGRP|S_IWGRP|S_IROTH|S_IWOTH and DEF_UMASK = S_IWGRP|S_IWOTH, the owner can read and write and everyone else can only read.

close returns 0 or −1. Closing a descriptor that is already closed is an error. Practice Problem 10.1 prints fd2 = 3: the first Open returns 3, Close frees it, the next Open returns 3 again.

        10.4 · reading and writing
        
Asked for fifty, got twenty

        
Omar asks the clerk for 50 letters. The pigeonhole has 20 left. He gets 20 — not a scolding. That smaller pile is a short count. He asks again and gets 0. The drawer is empty. That empty is EOF. Nobody hid a special end-mark character in the file.

        
On a disk this almost only happens at the end. On a keyboard, each read brings one typed line. On a network socket, delays and buffers can hand back any number of bytes, and a write can go short too.

        
Try it: On disk EOF, press read(50) twice. Then switch to socket and step the short deliveries. Slide the request size if you like.

        

          What the book says
          

            
read(fd, buf, n) copies at most n bytes from the current file position. It returns −1 on error, 0 on EOF, otherwise the number of bytes actually transferred. write is the same idea in the other direction. Figure 10.3 copies standard input to standard output one byte at a time. lseek can move the position; it is beyond the chapter’s scope.

            
“Such short counts do not indicate an error.” They happen (1) at EOF — 20 bytes left, 50-byte chunks, so the next read returns 20 and the one after that returns 0; (2) on a terminal, one text line per read; (3) on network sockets, from internal buffering and long delays; also on Linux pipes, which are beyond our scope.

            
In practice you will never encounter short counts when you read from disk files except on EOF, and you will never encounter short counts when you write to disk files. Robust network programs must loop until every requested byte has moved. On x86-64, size_t is an unsigned long and ssize_t is a long: read must be able to return −1, which halves the maximum size of a read.

        10.5 · the Rio package
        
Keep asking until the pile is complete

        
Aisha needs 8 letters from a slow line. Raw read may hand her 3 and walk away. If she treats that as “done,” the other 5 never arrive. rio_readn stays at the window and asks again until she has all 8, or the line hangs up. rio_writen never shrugs and sends fewer.

        
For text lines she uses a second trick: fill a private drawer once, then serve characters from that drawer. That drawer is a rio_t buffer. The book sizes it at 8192 bytes. We draw a tiny one so you can see the refill.

        
Try it: On rio_readn, press Ask for 8 on both sides. Raw stops at 3. Rio keeps going. Then switch to readlineb and step two lines out of one refill.

        

          What the book says
          

            
Rio (Robust I/O) hides short counts. Unbuffered rio_readn / rio_writen transfer directly between memory and a file — useful for binary data on networks. “The rio_readn function can only return a short count if it encounters EOF.” rio_writen never returns a short count. Both restart read / write after EINTR. They may be interleaved on the same descriptor.

            
Buffered input: rio_readinitb ties a descriptor to a rio_t (rio_fd, rio_cnt, rio_bufptr, rio_buf[RIO_BUFSIZE] with RIO_BUFSIZE 8192). rio_readlineb copies the next text line, including the newline, and adds a NULL; it reads at most maxlen-1 bytes and truncates longer lines. rio_readnb is a buffered rio_readn. The two buffered calls may interleave; do not mix them with unbuffered rio_readn on the same descriptor. They are thread-safe. Figure 10.5 is cpfile: Rio_readinitb, then Rio_readlineb / Rio_writen.

            
Internal rio_read refills the buffer with read when empty (a short fill is fine), then copies min(n, rio_cnt). Rio is inspired by Stevens’s readn, writen, and readline; the buffered pair fixes the static-buffer thread-safety problem and the fact that Stevens’s buffered readline and unbuffered readn cannot be used together on the same descriptor.

        10.6 · file metadata
        
Ask the card catalogue, do not open the book

        
Fatima wants to know how big a notebook is, and whether she may read it, without opening it. She asks the librarian for the card. That card is the file’s metadata. Standard I/O has no such catalogue.

        
Two questions live in one stamp called st_mode: what kind of file is this, and who may touch it? Macros such as S_ISREG read the kind. A bit such as S_IRUSR reads “may the owner read?”

        
Try it: Tap foobar.txt, the directory, or the socket. Watch statcheck print the type and the owner-read bit.

        

          What the book says
          

            
stat(filename, &buf) and fstat(fd, &buf) fill a struct stat (Figure 10.9). The chapter needs st_mode and st_size for the Web servers in Section 11.5; the other members are beyond its scope. st_size is the file size in bytes. st_mode encodes both the permission bits of Figure 10.2 and the file type of Section 10.2.

            
Macros in sys/stat.h: S_ISREG(m) regular file, S_ISDIR(m) directory, S_ISSOCK(m) network socket. Figure 10.10 statcheck prints type: regular|directory|other and read: yes|no by testing stat.st_mode & S_IRUSR.

            
The chapter introduction notes that the standard I/O library provides no way to access file metadata such as file size or file creation time — one reason to learn Unix I/O at all.

        10.8 · sharing files
        
Two tickets, one bookmark or two

        
Yuki opens foobar.txt twice. She now holds two tickets. Each ticket has its own bookmark, so both reads start at f. Open twice, and you get two bookmarks.

        
If she instead forks a helper, Sofia, they share one bookmark. Sofia reads f and the bookmark slides. Yuki’s next read is o. Parent and child must both close their tickets before the kernel throws the bookmark away. That leftover count is the reference count.

        
Try it: On two opens, press Read fd1 then Read fd2. Both say f. Switch to fork, Child reads, then Parent reads. The parent gets o.

        

          What the book says
          

            
The kernel uses three tables. Each process has its own descriptor table; an open entry points into the file table. The file table is shared by all processes: current file position, a reference count of descriptors that point at the entry, and a pointer into the v-node table. Closing decrements the reference count; the kernel deletes the file table entry when the count hits zero. The v-node table is also shared and holds most of the stat information, including st_mode and st_size.

            
Figure 10.12: descriptors 1 and 4 name two different files — no sharing. Figure 10.13: two descriptors, same disk file, two file table entries. “The key idea is that each descriptor has its own distinct file position.” That is what two calls to open on the same name do. Practice Problem 10.2 therefore prints c = f.

            
Figure 10.14: after fork, the child gets a copy of the parent’s descriptor table. They share the open file table entries, so they share the file position, and each reference count becomes 2. Both must close before the kernel deletes the entry. Practice Problem 10.3: the child reads the first byte of foobar, the parent reads the second, and the output is c = o.

        10.9 · I/O redirection
        
Point the window at a notebook

        
Luca’s shell can say “print the class list into a notebook, not the window”: ls > foo.txt. The book nicknames that > a right hoinky. The trick behind it is dup2: copy ticket 4 onto ticket 1.

        
Ticket 1 used to mean the terminal. After dup2(4,1) it means the disk file that 4 already named. The old terminal entry is closed. From then on, anything written to standard output lands in the notebook. A Web server does the same kind of swap when it runs a CGI program.

        
Try it: Press dup2(4,1) and watch fd 1 join file B. Then switch to Practice 10.5 and step: after the redirect, the next read is o, not f.

        

          What the book says
          

            
Linux shells associate standard input and output with disk files. Example: ls > foo.txt. A Web server performs a similar redirection for a CGI program (Section 11.5). dup2(oldfd, newfd) copies descriptor table entry oldfd onto newfd. If newfd was already open, then dup2 closes newfd before it copies oldfd.

            
Start from Figure 10.12: descriptor 1 is file A (a terminal), descriptor 4 is file B (a disk file), both reference counts 1. After dup2(4,1) (Figure 10.15) both descriptors point at B, A’s file table and v-node entries are deleted, and B’s reference count is 2. Practice Problem 10.4 redirects standard input with dup2(5,0) or dup2(5, STDIN_FILENO).

            
Practice Problem 10.5: two opens of foobar.txt, Read(fd2), Dup2(fd2, fd1), Read(fd1). Because fd1 now shares fd2’s file table entry, the second read is the second byte. The output is c = o.

        10.10 · 10.11 · standard I/O and advice
        
Three toolboxes, one stove

        
Under the floor is Unix I/O — open, read, write, close, stat. On top sit two nicer boxes. Standard I/O is the everyday restaurant: fopen, printf, fgets. Rio is the reliable takeaway for a wobbly network line.

        
Noor’s rule of thumb: homework files and the terminal? Standard I/O. A socket? Rio. A binary file? Never a line-reader — a 0xa byte in a picture is not a newline. Standard I/O and sockets also fight: you cannot lseek a socket, and closing two FILE streams on the same descriptor closes it twice.

        
Try it: Tap disk text, binary, or socket and see which box lights up. Then switch to socket trap and step the two-fclose disaster versus the Rio path.

        

          What the book says
          

            
The standard I/O library (libc) offers fopen / fclose, fread / fwrite, fgets / fputs, scanf / printf. An open file is a stream: a pointer to a FILE. Every ANSI C program begins with stdin, stdout, and stderr (descriptors 0, 1, 2). A FILE is a descriptor plus a stream buffer, filled by one read so later getc calls stay in user space. Figure 10.16 stacks standard I/O and Rio on top of Unix I/O.

            
G1: “Use the standard I/O functions whenever possible.” They are the method of choice on disk and terminal devices. Most C programmers use them exclusively, except possibly stat, which has no standard I/O counterpart. G2: do not use scanf or rio_readlineb to read binary files — those files may be littered with 0xa bytes that are not line endings. G3: “Use the Rio functions for I/O on network sockets.”

            
Streams are full duplex, but input after output needs fflush, fseek, fsetpos, or rewind; output after input needs one of the seek functions unless the input hit EOF. lseek is illegal on a socket, so the second restriction cannot be worked around. Opening two streams with fdopen and calling fclose on both closes the same socket descriptor twice — a recipe for disaster in a threaded program (Section 12.7.4). Format in memory with sprintf and send with rio_writen; read a line with rio_readlineb and parse with sscanf.

Words to know
The chapter’s grown-up words, in plain language.

      

        
descriptor
A small nonnegative integer that names an open file in this process. 0, 1, and 2 are already taken.

        
Unix I/O
The kernel’s uniform interface: open, close, read, write, and friends, for every kind of file.

        
file position
The byte offset k where the next read or write will start. Seek can move it.

        
EOF
End-of-file: a read when k is past the last byte. Returns 0. No special end character.

        
short count
Fewer bytes than you asked for. Not an error. Common on sockets and at EOF.

        
Rio
Robust I/O: wrappers that loop on short counts. rio_readn, rio_writen, rio_readlineb, rio_readnb.

        
rio_t
The buffered reader’s private drawer: descriptor, unread count, pointer, and a 8192-byte buffer.

        
metadata
Facts about a file (size, type, permissions) from stat or fstat, without reading the data.

        
descriptor table
Per process. Each open slot points at one file table entry.

        
file table
Shared. Holds the file position, a reference count, and a pointer to a v-node.

        
v-node
Shared. Holds most of the stat information for one disk file, including type and size.

        
dup2
Copy one descriptor table slot onto another. The usual implementation of > and <.

        
stream
A FILE* in standard I/O: a descriptor plus a buffer, so getc is cheap after the first read.

        
umask
Bits the process refuses to grant when it creates a file. New mode is mode & ~umask.
