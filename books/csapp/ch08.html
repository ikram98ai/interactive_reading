Exceptional Control Flow

From the moment a processor powers on, the program counter walks a sequence of instruction addresses. Most steps are smooth. A jump, a timer, a finished child, or a bad divide can yank that walk somewhere else — and those yanks are how one machine runs many programs.

“In general, we refer to these abrupt changes as exceptional control flow (ECF).”

8.1 · exceptions

Three ways the next address is chosen

The program counter holds the address of an instruction. If the next address is simply “just after this instruction,” the book calls that a smooth transfer. Nothing surprising happened.

A jump, a call, or a return is already an abrupt change — but the program itself asked for it. An exception is the other kind of abrupt change: some change in the processor’s state, called an event, yanks the walk into code the running program did not choose.

Try it: step the same three instructions three ways. Smooth adds the instruction’s length. Jump leaps to a label. Exception ignores both and lands in the kernel.

What the book says

From power-on until shutdown, the program counter takes a sequence of values a0, a1, …, an−1, each the address of an instruction. A transition from ak to ak+1 is a control transfer. It is smooth when the next instruction sits next to the current one, and abrupt otherwise. Jumps, calls, and returns are abrupt transfers that the program requested. Exceptions are abrupt transfers in response to a change in processor state.

8.1.1 · exception handling

A number, a table, a handler

Each event has a number. The processor does not “know” what to do. It treats that number as an index into the exception table, a jump table whose start address lives in a special register. Entry k holds the address of the handler for exception k.

The handler runs in kernel mode. When it finishes it has three choices: go back to the instruction that was running (Icurr), go to the one that would have been next (Inext), or never return.

Try it: pick an exception number and press Dispatch. Watch the table index light up, then choose where the handler returns.

What the book says

Exception handling needs a tight handshake of hardware and software. Each possible exception number k has a handler. At boot the operating system writes those addresses into the exception table. When an event occurs, the processor looks up entry k and transfers control there — an indirect call through the table (Figures 8.2 and 8.3).

It resembles a procedure call, with extras: the return address may be Icurr or Inext depending on the class; x86-64 also pushes the flags; a transfer from user mode pushes onto the kernel stack; and the handler runs in kernel mode. A return-from-interrupt instruction pops that state and can drop back to user mode.

8.1.2 · classes of exceptions

The return rule is the whole difference

Exceptions come in four classes. An interrupt arrives from outside, on a pin, in the middle of whatever instruction was running — a timer or a disk. The handler always returns to the next instruction.

A trap is intentional, like a system call, and also returns to the next instruction. A fault is a possibly fixable error: the handler may retry the same instruction. An abort is fatal. It does not come back.

Try it: press each class. The picture shows who caused it, and whether the walk resumes at Icurr, at Inext, or not at all.

What the book says

Figure 8.4: interrupts are asynchronous (an I/O pin) and return to the next instruction (Figure 8.5). Traps are synchronous and intentional — the system-call instruction — and also return to the next instruction (Figure 8.6). Faults are potentially recoverable errors; the handler may re-execute the faulting instruction (Figure 8.7). Aborts are unrecoverable and never return (Figure 8.8).

8.1.3 · exceptions in Linux/x86-64 systems

Divide, page fault, syscall, machine check

On x86-64, numbers 0–31 belong to the processor architects and 32–255 to the operating system. A few of them show up constantly: divide error (0), general protection fault (13), page fault (14), and machine check (18).

Linux does not try to repair a divide by zero or a protection fault. The shell reports them as “Floating exception” and “Segmentation fault.” A page fault is the famous restart: the handler maps the missing page and runs the same instruction again. System calls are traps. The number goes in %rax, the arguments in the argument registers, and a return between −4095 and −1 means −errno.

Try it: fire each example. The code panel follows the syscall hello, or the instruction that faulted.

What the book says

Figure 8.9: exception 0 is a divide error (fault), 13 a general protection fault, 14 a page fault, 18 a machine check (abort). Linux treats divide errors and general protection faults as fatal. A page fault — typically a 4 KB page — is repaired and Icurr is re-executed.

8.2 · processes

Two polite illusions

A process is an instance of a program in execution. The kernel uses exceptions to give every process two illusions: it has the processor to itself, and it has memory to itself.

The first illusion is a logical control flow. The second is a private address space. The rest of this section takes them apart. This machine just shows the trick: three programs, one processor, each convinced it is alone.

Try it: press Run a slice. The program on the CPU changes. Each program’s own “I am running” counter only moves on its turn.

What the book says

“The classic definition of a process is an instance of a program in execution.” Processes are the most successful idea the kernel builds out of exceptions. Each process appears to have exclusive use of the processor and exclusive use of the address space. Those two illusions are logical control flow and private address space.

8.2.1 · logical control flow

Your steps, with other people’s time cut out

A logical control flow is the sequence of instructions this process executes. On the physical timeline those instructions are broken into slices, with other processes in the gaps. From inside the process, the gaps are invisible: its program counter just keeps walking its own code.

Figure 8.12 is the picture: A runs, then B runs to completion, then a bit of C, then A finishes, then C finishes. A’s flow is two slices. A never sees B’s instructions.

Try it: step the physical timeline. The code panel has three files. Only the running process’s line advances.

What the book says

Figure 8.12 draws each process as vertical bars on a time axis. A single logical flow can be several bars with other processes in between. The key idea is that processes take turns. Each turn is a time slice; the kernel’s preemption is also called multitasking or time slicing. A process’s logical control flow is the sequence of its own program-counter values, not the values of the physical processor while someone else runs.

8.2.2 · concurrent flows

Overlap in time, or overlap on two cores

Two flows are concurrent when their lifetimes overlap: one has started and the other has not yet finished. They do not have to run on two cores. A and B in Figure 8.12 are concurrent. B and C are not, because B finishes before C starts.

Parallel is stricter. The flows run at the same time on different cores or different computers. Concurrent on one core is real; it is just not parallel.

Try it: drag the start and end times. The pair table answers Practice Problem 8.1’s question. Then switch cores: overlap becomes parallel only when two cores exist.

What the book says

A logical flow whose execution overlaps another in time is a concurrent flow; the two processes run concurrently. In Figure 8.12, A overlaps B, and A overlaps C; B finishes before C starts, so B and C do not. Parallel flows are concurrent flows running on different cores or computers. Practice Problem 8.1 asks the same overlap question for A on [1, 3], B on [2, 5], and C on [4, 6].

8.2.3 · private address space

Same number, different byte

Every process sees the same tidy map. On x86-64 Linux the code segment begins at 0x400000. Above it sit data, a heap that grows up, a gap, shared libraries, a stack that grows down, and — at the very top — kernel memory the process is not allowed to touch.

The addresses are private. Byte 0x400000 in process A is not byte 0x400000 in process B. The hardware translates each process’s addresses into different physical memory.

Try it: tap a region. The code line that lives there lights up. Then press Same address, two processes and watch one virtual address name two different bytes.

What the book says

Figure 8.13: the bottom of the user space holds code and data loaded from the executable, then the run-time heap, a shared-library region, and the user stack. The kernel occupies the top of the space, up to 248−1 on this machine. User code cannot read or write that region. The same virtual address in two processes refers to different physical memory — that privacy is the address-space illusion.

8.2.4 · user and kernel modes

A mode bit, and one legal way through it

A mode bit in a control register says how much the running code is allowed to do. User mode cannot execute privileged instructions and cannot touch kernel memory. Kernel mode can.

The only way for user code to enter kernel mode is an exception — usually a system call. A program that wants kernel facts the polite way reads /proc (or /sys), which the kernel exports as text files. Reaching into a kernel address directly is a protection fault.

Try it: run an ordinary add, a privileged halt, a peek at kernel memory, and a read of /proc/cpuinfo. Only the last one is a legal question.

What the book says

The mode bit limits which instructions a process may execute and which addresses it may touch. Kernel mode may use privileged instructions and the whole address space. User mode may not. Switching from user to kernel mode happens only through an exception such as a system call, a fault, or an interrupt. The /proc filesystem exposes kernel data as readable text — CPU type in /proc/cpuinfo, a process’s segments in /proc/<pid>/maps. Linux 2.6 added /sys for buses and devices.

8.2.5 · context switches

Save this process, restore that one

A context switch is exceptional control flow one level up. The kernel saves the current process’s context — program counter, registers, and the rest of what it needs to resume — restores another process’s context, and passes control to it.

Figure 8.14 is the classic reason: process A calls read and the disk will take tens of milliseconds. The kernel switches to B while the disk works. A disk interrupt later switches back to A, just after read returns. A timer interrupt, often every 1 ms or 10 ms, does the same trick when nobody is waiting on I/O.

Try it: step A’s read. Watch the saved context sit on the shelf while B runs, then come back.

What the book says

The kernel implements multitasking with context switches, built on the exception mechanism. The kernel saves the current context, restores a previously saved one, and transfers control. Figure 8.14: A’s read traps into the kernel; the kernel switches to B for the long disk wait; a disk interrupt switches back so A continues at the instruction after read.

8.4 · process control

Running, stopped, or gone

From the moment it is created until it is reaped, a process is in one of three states. Running means it is either on a CPU or waiting for a turn. Stopped means it is suspended until something continues it. Terminated means it has stopped forever — it will never run another instruction — but it still exists until its parent collects it.

Stop signals include SIGSTOP, SIGTSTP (Ctrl+Z), SIGTTIN, and SIGTTOU. SIGCONT runs a stopped process again. Termination comes from a fatal signal, a return from main, or a call to exit.

Try it: walk the three states. Illegal jumps — terminated back to running — are refused.

What the book says

A process is running, stopped, or terminated. Stopped processes were suspended by a signal (SIGSTOP, SIGTSTP, SIGTTIN, or SIGTTOU) and stay stopped until SIGCONT. A process terminates because it received a signal whose default action is to terminate, because it returned from main, or because it called exit. The following subsections are the system calls that create, wait for, pause, and replace processes.

8.4.1 · obtaining process IDs

Every process wears a positive number

Each process has a unique positive PID. getpid returns your own. getppid returns your parent’s. Both return a pid_t.

The parent does not change when you merely call these functions. It changes when the parent dies — the child is adopted, usually by init, PID 1.

Try it: step a parent and the child it creates. Each box prints the two ids. Then remove the parent and watch getppid in the child become 1.

What the book says

Every process has a unique nonzero PID. getpid returns the caller’s PID. getppid returns the parent’s PID. The type of both is pid_t, defined in the system headers the book includes through csapp.h.

8.4.2 · creating and terminating processes

Called once, returns twice

fork creates a child that is almost a copy of the parent: same code, same data at that instant, same open files. It is called once and returns twice. The child receives 0. The parent receives the child’s PID. On error the parent receives −1 and there is no child.

After the copy, the address spaces diverge. In the book’s example x starts at 1. The child increments its copy and prints 2. The parent decrements its copy and prints 0. They share the screen, so both lines appear. Two nested forks with no if create four processes, and four hellos can appear in any order.

Try it: step the private-x example. Then switch to Four hellos and run processes in different orders. The set of lines stays the same; the order does not.

What the book says

fork returns 0 to the child, the child’s PID to the parent, and −1 on error. “The fork function is interesting (and often confusing) because it is called once but it returns twice.” The child is a duplicate: identical address space, identical file descriptors, and an independent copy of the variables from then on.

8.4.3 · reaping child processes

Finished, still wearing the name tag

A terminated process that has not been reaped is a zombie. It is not running, but the kernel keeps a small record — the PID and the exit status — until the parent collects it with waitpid.

If the parent dies first, init (PID 1) adopts the orphans and reaps them. A long-running program such as a shell must not rely on that. waitpid(-1, …) reaps any child, in whatever order they finish. Storing the PIDs and waiting for each one makes the order deterministic. WNOHANG returns 0 instead of blocking when nobody has exited yet.

Try it: let both children exit, look at the zombies, then reap. Switch to creation order, or to “parent exits first.”

What the book says

A terminated unreaped process is a zombie. The kernel keeps it until the parent reaps it and reads the exit status. If the parent terminates first, init (PID 1) adopts the orphans. waitpid(pid, statusp, options) returns the child’s PID, or 0 with WNOHANG, or −1 on error. pid > 0 waits for that child; pid == -1 waits for any. wait(&status) is waitpid(-1, &status, 0).

Figure 8.18 (N = 2) reaps in no particular order; the sample run shows child 22966 with status 100, then 22967 with 101. Figure 8.19 stores the PIDs and waits in creation order. Either order is correct. WIFEXITED and WEXITSTATUS read a normal exit. No children means ECHILD; an interrupting signal means EINTR.

8.4.4 · putting processes to sleep

Sleep for three seconds, or until a signal

sleep(secs) suspends the caller. It returns 0 if the whole interval elapsed. If a signal wakes it early, it returns the number of seconds still left.

pause sleeps until some signal arrives, and always returns −1. It does not take a duration. A signal you are not catching may kill the process instead of waking it into your code — that story continues in 8.5.

Try it: run a 3-second sleep with no signal, then interrupt it at 1 second. Then pause and deliver SIGALRM.

8.4.5 · loading and running programs

Same process, different program

execve loads a new program into the current process. On success it does not return: the code, data, heap, and stack are gone, replaced by the new program, which starts at its main. The PID stays. Open file descriptors stay.

The new main receives argc, argv, and envp. By convention argv[0] is the program name. The list ends with NULL. The environment is the same shape: strings like USER=ada, also NULL-terminated. getenv, setenv, and unsetenv edit that array.

Try it: press execve. Watch the program name change and the PID stay. On failure the call returns −1 and the old program continues.

What the book says

8.4.6 · using fork and execve to run programs

A shell is a loop around those two calls

The book’s simple shell prints a prompt, reads a line, and evaluates it. A blank line does nothing. quit is a builtin: the shell handles it itself. Anything else is a program name.

The shell forks. The child execves the program. If the line did not end with &, the parent waits — a foreground job. If it did, the parent prints the PID and takes another command — a background job. This shell does not reap background children. They become zombies when they exit. Signals, in the next section, are how a real shell notices.

Try it: run quit, a foreground ls, and ls &. Step eval and watch which branch the code takes.

What the book says

Figures 8.23–8.25 are a tiny shell. main prints a prompt and calls eval. parseline builds argv and reports whether the job is background. Builtins such as quit run in the shell process. Otherwise the shell forks, the child calls execve, and the parent calls waitpid only for a foreground job. Background children are not reaped by this version.

8.5 · signals

A small message from the kernel

A signal is a tiny message that the kernel delivers to a process because something exceptional happened. Linux has 30 types. Some are hardware faults turned into software events: divide by zero becomes SIGFPE (8), an illegal instruction becomes SIGILL (4), a bad memory reference becomes SIGSEGV (11).

Others are higher-level. Ctrl+C is SIGINT (2) to the foreground group. SIGKILL (9) forces termination. A child that stops or exits causes SIGCHLD (17) in the parent.

Try it: press an event. The kernel stamps the matching signal number onto the destination process.

What the book says

A signal is a form of exceptional control flow, higher level than an exception and lower level than a nonlocal jump. Figure 8.26 lists the 30 Linux signals and each default action. The kernel tells a user process about certain exceptions by sending a signal: SIGFPE for divide-by-zero, SIGILL for an illegal instruction, SIGSEGV for an illegal memory reference. Ctrl+C sends SIGINT to the foreground process group. SIGKILL forcibly terminates. A child’s stop or termination sends SIGCHLD to the parent.

8.5.1 · signal terminology

Pending is a bit, not a counter

Sending and receiving are different moments. The kernel sends (delivers) a signal by updating state in the destination process. The process receives it later, when it is forced to react.

Two bit vectors live in the process context. Pending means “at least one of this type has arrived and not yet been received.” A second signal of the same type, while the first is still pending, is thrown away. Blocked means “do not receive this yet.” A blocked signal can sit pending until the process unblocks it. It is still received at most once.

Try it: send SIGINT twice. Block it, send again, then unblock. The code’s bit comments update with the picture.

What the book says

A signal is sent when the kernel records it in the destination’s context, either because the kernel noticed an event or because some process called kill. It is received when the destination is forced to react. A pending signal is received at most once. For each process the kernel keeps the set of pending signals and the set of blocked signals. A blocked pending signal stays pending until the signal is unblocked.

8.5.2 · sending signals

One pid, or a whole group

Processes live in process groups. A child normally joins its parent’s group. A shell puts each job in its own group, so Ctrl+C can hit the foreground job and not the shell, and not the background jobs.

/bin/kill -9 15213 sends SIGKILL to one PID. A negative PID means the group: kill -9 -20 hits every member of group 20. alarm(secs) asks the kernel to send you SIGALRM later. SIGKILL and SIGSTOP cannot be caught or ignored.

The /bin/kill program sends an arbitrary signal. kill(pid, sig) does it from a program (Figure 8.29). If pid is positive, the signal goes to that process. If pid is negative, it goes to every process in group |pid|. 8.5.3 · receiving signals

Default, ignore, or catch

When a process receives a pending unblocked signal, it does one of three things. The default action is often “terminate.” It can ignore the signal. Or it can catch it by running a handler the program installed, then resume.

A handler can itself be interrupted by a different signal. Figure 8.31 shows handler S running, then handler T, then S again, then the main program. SIGKILL and SIGSTOP still cannot be caught or ignored.

8.5.4 · blocking and unblocking signals

Hold the bit, then let it through

sigprocmask changes the blocked set. While SIGINT is blocked, sending it sets the pending bit and does not run the handler. Unblocking receives it — once, even if it was sent twice.

There is also an implicit block. While a handler for signal s runs, s is blocked, so the same signal does not nest inside its own handler. A different signal still can. That is why Figure 8.31’s handlers are for two different signals.

Try it: block, send twice, unblock. Then run the handler and send the same signal again before it returns.

What the book says

Applications use sigprocmask to block and unblock signals explicitly (Figure 8.32). The helpers sigemptyset, sigfillset, sigaddset, and sigdelset build the sets. The kernel also blocks the signal currently being handled, so a handler is not recursively interrupted by another instance of the same signal unless the program asks for that. Other signal types are not implicitly blocked.

8.5.5 · writing signal handlers

Tiny, safe, and ready for more than one

A handler shares the process with the main program, and it can run between any two instructions. That makes it a hard place to write code. Keep it short. Save and restore errno. Only call functions that are async-signal-safe: write, waitpid, and _exit are; printf, malloc, and exit are not. The book’s Sio_puts is a safe print.

Pending bits do not count. If three children exit before the parent receives SIGCHLD, one bit is set. A handler that reaps a single child leaves the others as zombies. A handler that loops on waitpid until it returns −1 reaps all of them.

Try it: compare the unsafe printf handler with Sio_puts. Then exit three children and reap one versus reap-in-a-loop.

8.5.6 · synchronizing flows to avoid nasty concurrency bugs

The child can finish before you write its name down

A shell keeps a list of jobs. The parent forks, then adds the child to the list. The SIGCHLD handler deletes the job after it reaps the child. If the child exits in the crack — after fork returns, before addjob — the handler deletes nothing, and addjob then records a job that will never be removed.

You can run this a billion times and miss it. The fix blocks SIGCHLD before fork and unblocks only after addjob. The child inherits that blocked set, so the child must unblock before execve.

Try it: run the race with a fast child, then run the blocked version. The job list is the picture; the code highlights the window.

8.5.7 · explicitly waiting for signals

Spin, pause forever, or sigsuspend

Sometimes the main program must wait until a handler has run. A spin loop while (!pid); is correct and wasteful. Putting pause in that loop looks kinder, and it has a race: if SIGCHLD arrives after the test and before pause, pause sleeps forever. sleep(1) in the loop is merely slow.

sigsuspend replaces the blocked set and waits for a signal as one atomic step, then restores the mask when it returns. The signal cannot sneak into the gap.

Try it: deliver the signal in the gap. Spin still finishes. Pause gets stuck. sigsuspend wakes up.

8.6 · nonlocal jumps

Called once, returns again from somewhere else

setjmp saves the calling environment — program counter, stack pointer, registers — and returns 0. longjmp restores that environment and makes the original setjmp return again, this time with a nonzero value. It is the C version of a jump that skips stack frames. Use it as the test of a switch, not as rc = setjmp(env).

From a signal handler, the signal-aware pair is sigsetjmp / siglongjmp. The book’s restart program installs the handler only after the first sigsetjmp, so the bookmark exists before Ctrl+C can fire. Skipping frames can leak anything those frames meant to free. C++ and Java exceptions are a more structured version of this idea.

Try it: step main → foo → bar and jump back with code 2. Then switch to the Ctrl+C restart loop.

What the book says

setjmp is called once and returns multiple times. longjmp(env, retval) restores the environment and makes that setjmp return retval, or 1 if retval was 0. 8.8 · summary

The same idea at three heights

Exceptional control flow is how a computer does more than one thing. At the bottom, hardware exceptions yank the processor into a handler. In the middle, the kernel uses that mechanism to build processes, switches, and signals. At the top, an application catches signals or jumps nonlocally back to a bookmark.

Concurrency in this chapter is mostly one core taking turns. Chapter 12 comes back when several flows really share data on purpose.

Try it: tap a layer. The code changes to the program that lives at that height.

What the book says

ECF occurs at every level and is a basic mechanism for concurrency. Hardware exceptions are interrupts, traps, faults, and aborts. The kernel uses them to provide processes: logical control flows and private address spaces. Applications create children, wait for them, run new programs, and catch signals. Signal handling is subtle. Nonlocal jumps are the application-level form of the same abrupt transfer.

An event indexes a jump table. Entry k is the handler for exception number k.

Async and always Inext; intentional and always Inext; maybe restart Icurr; never return.

Lifetimes overlap in time, versus actually running at once on different cores.

User mode or kernel mode. User code enters the kernel only through an exception.

Save this process’s context, restore another’s, and pass control.

The reason a system call returned −1. A capitalized wrapper checks it for you.

Terminated but not yet collected. waitpid collects it. PID 1 adopts orphans.

Called once, returns twice. Versus called once and, on success, never returns.

Two bit vectors. At most one pending signal of each type. Blocked means “not yet.”

The set of processes a single Ctrl+C or a negative kill pid can hit together.
