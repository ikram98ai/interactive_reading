Exceptional Control Flow

The chip likes to walk to the next instruction. A timer, a disk, or a finished child can yank that walk somewhere else — and that yank is how many programs share one machine.

“In general, we refer to these abrupt changes as exceptional control flow (ECF).”

Big idea 1 · exceptions

A smooth walk, then a yank to the drill sheet

Imani walks the school corridor locker by locker. That is a smooth control flow: each step’s address sits next to the last one. A jump, a call, or a return is already a hitch — but it still comes from her own program.

Then the alarm panel flashes. She does not go to the next locker. The hardware looks up a number in a wall chart — the exception table — and sends her to a drill sheet written by the office, not by her. After the drill she might return to this locker, the next one, or not at all.

Try it: Pick an event, then press Step. Watch the number index the table and the handler choose a return.

What the book says

“An exception is an abrupt change in the control flow in response to some change in the processor’s state.” The change is an event. The processor makes an indirect call through a jump table called the exception table, whose start sits in the exception table base register. Entry k holds the handler for exception number k.

There are up to 256 exception types. Numbers 0 to 31 are defined by the Intel architects; 32 to 255 are defined by the operating system. After the handler runs, it either returns to Icurr (the instruction that was running), returns to Inext (the one that would have run next), or aborts.

An exception is like a procedure call, with extras: the return address is Icurr or Inext depending on the class; x86-64 also pushes EFLAGS; transfers from a user program push onto the kernel’s stack; and the handler runs in kernel mode. A special “return from interrupt” instruction restores user mode if needed.

Big idea 2 · four classes

Doorbell, librarian, trip, collapse

Mateo sorts four kinds of yanks. A doorbell can ring in the middle of any step — that is an interrupt, and when the helper finishes he always goes to the next step, as if nothing happened.

Asking the librarian on purpose is a trap: a system call. Tripping on a missing page is a fault — if the office can fetch the page, Mateo retries the same step. If the building’s memory chips lie, that is an abort. He does not come back.

Try it: Press Interrupt, Trap, Fault, or Abort. The return target changes with the class — and Linux treats a divide-by-zero fault as fatal.

What the book says

Figure 8.4: an interrupt is async (I/O pin) and always returns to the next instruction. A trap is sync and intentional — also always to Inext. A fault is a potentially recoverable error and might return to the current instruction. An abort is a nonrecoverable error and never returns.

Figure 8.9 on x86-64: exception 0 is a divide error (fault); 13 is a general protection fault; 14 is a page fault; 18 is a machine check (abort). Linux does not recover from divide errors or general protection faults. Shells typically report them as “Floating exceptions” and “Segmentation faults.” A page fault (typically a 4 KB page) is the classic restart: the handler maps the page and re-executes Icurr.

Traps implement system calls. Figure 8.10: write is 1, fork is 57, execve is 59, _exit is 60. Arguments travel in %rax (the number) then %rdi, %rsi, %rdx, %r10, %r8, %r9. A negative return in %rax between −4,095 and −1 is an error corresponding to negative errno. Figure 8.11’s hello uses syscall 1 then syscall 60.

Big idea 3 · processes

One swing, three private desks

Priya, Yusuf, and Sofia share one swing. Each turn looks, to that kid, like the whole afternoon. That sequence of their own steps is a logical control flow. The grown-up with the stopwatch is the kernel: a slice for you, a slice for someone else.

Each kid also has a private desk. A byte at “address 12” on Priya’s desk is not Sofia’s byte 12. Code starts at a familiar door, 0x400000. The top of the building is the office — kernel memory — and a kid in user mode who walks up there hits a protection fault.

Try it: Step the three flows and watch who overlaps. Then switch to the address map and press Touch kernel.

What the book says

“The classic definition of a process is an instance of a program in execution.” A process gives two illusions: exclusive use of the processor (a logical control flow) and exclusive use of memory (a private address space). Figure 8.12 interleaves A, then B to completion, then C, then A to completion, then C. A and B run concurrently, as do A and C; B and C do not, because B finishes before C starts.

Concurrent means the flows overlap in time, even on one core. Parallel means they run on different cores or machines. A time slice is one turn; multitasking is also called time slicing. A context switch saves the current context, restores another, and passes control. Timers typically interrupt every 1 ms or 10 ms. Figure 8.14: A’s read traps, the kernel switches to B while the disk works (tens of milliseconds), then a disk interrupt switches back to A just after read.

Figure 8.13: on x86-64 Linux the code segment begins at 0x400000; the kernel occupies the top of the 248−1 space. User mode cannot execute privileged instructions or touch kernel memory. The only way into kernel mode is an exception. The /proc filesystem exports kernel data as text files; Linux 2.6 added /sys.

Each process takes turns on the processor and keeps its own addresses.
Big idea 4 · fork

Photocopy the desk, then change only your cup

Yusuf hits the copier once. Suddenly there are two desks, two pencil cups, two walks. The function was called once and came back twice: the new kid is told “you are 0,” and the original is told the new kid’s real number.

Both cups start with 1 marble. The child adds one and prints 2. The parent takes one and prints 0. The cups do not sync, because the address spaces are copies, not the same room. They do share the already-open screen, so both lines appear.

Try it: Step Figure 8.15. Then switch to the nested graph: two forks in the source become four hellos.

What the book says

getpid and getppid return a pid_t. A process is running, stopped (SIGSTOP, SIGTSTP, SIGTTIN, SIGTTOU until SIGCONT), or terminated (a fatal signal, return from main, or exit). fork returns 0 to the child, the child’s PID to the parent, and −1 on error. “The fork function is interesting (and often confusing) because it is called once but it returns twice.”

Figure 8.15: x starts at 1; after fork the child does ++x and prints child : x=2, the parent does --x and prints parent: x=0. Figure 8.16 is that process graph. Figure 8.17 nests two Fork calls and runs four processes, each printing hello, in any topological order. We never assume an interleaving.

Unix-level functions return −1 and set errno. The book’s unix_error helper and the capitalised wrappers (Fork calls fork and dies on error) live in csapp.c / csapp.h, following Stevens. The rest of the book calls the lowercase names in the prose and the wrappers in the listings.

        Big idea 5 · waitpid
        
Finished, still wearing the name tag

        
Sofia sends two helpers out. They finish, stand by the door, and keep their name tags. Until she collects a tag, each helper is a zombie: not running, but not gone. The office still stores a little card for them.

        
If Sofia herself leaves, a clerk called init — PID 1, there since start-up — adopts the leftovers. A long-running shell should not rely on that. She calls waitpid, reads the exit status, and the card disappears.

        
Try it: Step until both children are zombies, then reap. Switch to “in order” to force 22966 before 22967.

        

          What the book says
          

            
“A terminated process that has not yet been reaped is called a zombie.” The kernel keeps it until the parent reaps it (and reads the exit status). If the parent dies first, init (PID 1) adopts the orphans and reaps them. waitpid(pid, statusp, options) returns the child’s PID, or 0 with WNOHANG, or −1 on error. pid > 0 waits for that child; pid = −1 waits for any child. wait(&status) is waitpid(-1, &status, 0).

            
WNOHANG is 1, WUNTRACED is 2. WIFEXITED / WEXITSTATUS read a normal exit. No children means −1 and errno = ECHILD; an interrupting signal means EINTR.

            
Figure 8.18 (N = 2) has each child exit(100+i). On the authors’ box: child 22966 terminated normally with exit status=100 then 22967 with 101 — “in no particular order.” Figure 8.19 stores the PIDs and waitpid’s each in creation order so the printout is deterministic. Either order is equally correct; never assume one.

        Big idea 6 · execve
        
Same locker number, a new pile of books

        
Hiro does not get a new locker. He empties this one and loads a different course. That is execve: a new program in the same process. The PID stays put. Open files stay open. If the load works, the call never comes back.

        
A shell does both tricks: fork a copy, then execve the user’s program in the copy, then waitpid if the job is in the foreground. A trailing & means “do not wait.” The book’s tiny shell forgets to reap those background kids — that needs signals.

        
Try it: Press Run execve and watch ls overlay the process. Switch to shell to fork, exec, and wait.

        

          What the book says
          

            
execve(filename, argv, envp) “is called once and never returns” if it succeeds (−1 on error). argv[0] is the executable’s name by convention. Figure 8.20: argv holds ls, -lt, /user/include, then NULL. Figure 8.21: PWD=/usr/droh, PRINTER=iron, USER=droh. main receives argc in %rdi, argv in %rsi, envp in %rdx. getenv / setenv / unsetenv edit that array.

            
fork runs the same program in a new child. execve loads a new program in the current process: same PID, inherited file descriptors, overwritten address space. Figure 8.23–8.25’s shellex prints > , parses a line, runs the quit builtin, or Fork + execve + waitpid for a foreground job. A final & is background. The simple shell does not reap background children.

        Big idea 7 · pending and blocked
        
A flag that does not stack

        
Amara has three mail flags. The office can raise a flag (the signal is pending). A latch can hold it so she does not look yet (blocked). When she returns from the office to her own walk, the kernel checks: pending, and not blocked? Then she must deal with it.

        
Two letters of the same kind do not queue. If SIGCHLD is already up, the next SIGCHLD is tossed. Ctrl+C raises SIGINT for everyone in the front-row group, not just one desk.

        
Try it: Send SIGINT or SIGCHLD. Block, then send again. Switch to groups and press Ctrl+C — only group 20 lights up.

        

          What the book says
          

            
Linux has 30 signal types (Figure 8.26). The kernel exposes hardware faults as signals: SIGFPE (8) for divide-by-zero, SIGILL (4) for an illegal instruction, SIGSEGV (11) for a bad memory reference. Typing Ctrl+C sends SIGINT (2) to every process in the foreground process group; Ctrl+Z sends SIGTSTP (20). kill / SIGKILL (9) forcibly terminates. A child’s stop or exit sends SIGCHLD (17) to the parent.

            
“At any point in time, there can be at most one pending signal of a particular type.” Subsequent signals of that type are discarded, not queued. The kernel keeps a pending bit vector and a blocked bit vector (the signal mask). Receipt happens when the kernel is about to return p to user mode and pending & ~blocked is nonempty — typically the smallest k.

            
Every process is in one process group. Default: a child shares its parent’s group. setpgid(0, 0) in process 15213 makes group 15213. /bin/kill -9 15213 kills that PID; a negative PID kills the group. Figure 8.28: shell 10/10, foreground job 20/20 with children 21 and 22, background 32 and 40. SIGKILL and SIGSTOP cannot be caught or ignored.

        Big idea 8 · handlers
        
A helper who must not use the lobby phone

        
Kenji pins a helper to the SIGINT hook. Ctrl+C no longer kills him by default — the helper runs, then (usually) he continues. If that helper shouts through the lobby phone — printf — it can tangle with Kenji’s own phone call. The safe window is write, or the book’s Sio helpers.

        
Three children finish while the helper is still tidying. The SIGCHLD flag can only be up or down. The third “child done” is lost. The helper must loop on waitpid until the room is empty, not count the bells.

        
Try it: Catch SIGINT the unsafe way, then the Sio way. Switch to SIGCHLD and play signal1 (a leftover zombie) versus signal2 (all reaped).

        

          What the book says
          

            
Figure 8.30 installs signal(SIGINT, handler) and pause()s; the handler printf’s “Caught SIGINT!” and exit(0). That printf is not async-signal-safe. Figure 8.33’s safe list includes write, waitpid, and _exit — not printf, sprintf, malloc, or exit. Figure 8.35 uses Sio_puts and _exit. Guidelines: keep handlers tiny; save and restore errno; block signals around shared data; declare shared vars volatile; use volatile sig_atomic_t for flags.

            
Figure 8.36’s signal1 reaps one child per SIGCHLD. On the authors’ box the children are 14073, 14074, 14075; only two handlers run and 14075 stays <defunct>. “Signals cannot be used to count the occurrence of events in other processes.” Figure 8.37’s handler2 loops while (waitpid(-1, NULL, 0) > 0) and reaps 15237–15239.

            
Older Unix restores the default action after a catch, and slow calls (read, wait, accept) may return EINTR. The book’s Signal wrapper uses sigaction with SA_RESTART. Figure 8.39 races addjob against deletejob; Figure 8.40 blocks SIGCHLD around fork and addjob. sigsuspend is the race-free wait; a pause after the while test can sleep forever.

        Big idea 9 · nonlocal jumps
        
A bookmark that skips the stairs

        
Lucia leaves a bookmark in main, then walks into foo and on into bar. If bar finds a mess, she does not climb the stairs back one door at a time. She snaps to the bookmark. That is a nonlocal jump: setjmp saves the room, longjmp restores it.

        
The tidy-up on those stairs never runs — a leak if she had hung coats there. Another use: a SIGINT helper that longjmp’s back to “restart” instead of returning into the middle of the loop.

        
Try it: Press error2 (the book’s default) and watch the snap to case 2. Then switch to restart and press Ctrl+C.

        

          What the book says
          

            
setjmp(env) saves the calling environment (PC, stack pointer, registers) and returns 0. longjmp(env, retval) restores it and makes that setjmp return retval (nonzero). “The setjmp function is called once but returns multiple times.” Do not write rc = setjmp(env); use it as a switch test. Skipping intermediate frames can leak anything those frames meant to free.

            
Figure 8.43: error1 = 0, error2 = 1, so the run takes bar’s longjmp(buf, 2) and prints “Detected an error2 condition in foo.” Figure 8.44 uses sigsetjmp / siglongjmp so a SIGINT handler can restart: “starting”, then “processing…”, then after Ctrl+C “restarting”. Install the handler only after sigsetjmp, or the handler might run before env exists. Call only safe functions on the restart path; in the example, exit is unreachable.

            
C++ and Java catch / throw are higher-level cousins of setjmp / longjmp. A catch in a try is akin to setjmp; a throw is similar to longjmp.

The seesaws from this chapter
Each row is a choice the hardware, the kernel, or a careful parent process makes.

      

        
Smooth walk
Ik then Ik+1 sit next to each other in memory.
vs
ECF
An event yanks the PC into a handler, another process, or a bookmark.

        
User mode
No privileged ops, no kernel addresses. A touch is a protection fault.
vs
Kernel mode
The handler may use every resource. Return-from-interrupt drops the bit.

        
fork
New process, same program, two returns. Child sees 0.
vs
execve
Same process, new program, same PID. Success never returns.

        
waitpid(-1)
Reap any child. Order is a property of this run.
vs
waitpid(pid)
Reap in the order you stored. Still equally correct either way.

        
printf in a handler
Convenient, not async-signal-safe. Can tangle with the main flow.
vs
write / Sio
The book’s safe door. _exit, not exit.

        
Reap one SIGCHLD
A pending bit is not a counter. A child can stay a zombie.
vs
while waitpid
Each catch empties the room. Existence meant at least one.

        
pause after a test
The signal can arrive in the crack. You sleep forever.
vs
sigsuspend
Unblock and sleep as one step. Then the bookmark of blocked bits returns.

Words to know
The chapter’s grown-up words, in plain language.

      

        
ECF
Any abrupt change in the walk of the program counter, at hardware, kernel, or app level.

        
exception
Hardware + kernel: an event looks up a handler in a table and yanks the PC there.

        
exception table
A jump table. Entry k is the handler for exception number k.

        
interrupt
Async yank from an I/O pin. Always returns to the next instruction.

        
trap / syscall
Intentional sync yank. The door from user code into the kernel. Always to Inext.

        
fault
A maybe-fixable error. The handler may restart Icurr (page fault) or abort (Linux divide).

        
abort
Fatal hardware error. The handler never returns to the program.

        
process
An instance of a program in execution: a logical flow plus a private address space.

        
context switch
Save this process, restore another, pass control. Built on exceptions.

        
zombie
Terminated, not yet reaped. Still occupies a kernel slot until waitpid.

        
fork
Called once, returns twice: 0 in the child, the child’s PID in the parent.

        
execve
Load a new program in this process. Same PID. Does not return on success.

        
pending / blocked
Two bit vectors. At most one pending signal of each type. Blocked means “not yet.”

        
signal handler
User function that runs when a caught signal is received. Shares the process.

        
async-signal-safe
OK to call from a handler. write is; printf, malloc, and exit are not.

        
setjmp / longjmp
Save a calling environment; snap back to it from a deeper function or a handler.
