1.1 · information is bits + context

The same beads, a different necklace

Your program starts as a text file named hello.c. Inside the computer it is not letters. It is a row of bits — zeros and ones — grouped into 8-bit bytes. Each byte is a number from 0 to 255.

Most computers use the ASCII table to match numbers with characters: 35 means #, 105 means i, and the invisible “start a new line” character is 10. A file made only of ASCII characters is a text file. Every other file is a binary file.

Here is the surprise: nothing inside the bytes says what they mean. The same four bytes can be a word, a whole number, a decimal number, or an instruction for the processor. Only the context — how a program chooses to read them — decides.

Try it: press Next byte (or tap any cell) and watch the same character light up in the code panel. C | Rust changes which source those bytes come from. Then switch to Same bytes, four meanings and slide the green window: four readers, four answers, one set of switches.

What the book says

A source program is a sequence of bits, each with a value of 0 or 1, organized in 8-bit chunks called bytes; each byte represents some text character. Most systems use the ASCII standard, which gives each character a unique byte-size integer value. In Figure 1.2 the first byte of hello.c is 35 (#), the second is 105 (i), and each text line ends with the invisible newline character \n, value 10.

“All information in a system—including disk files, programs stored in memory, user data stored in memory, and data transferred across a network—is represented as a bunch of bits.” “The only thing that distinguishes different data objects is the context in which we view them.” The same bytes might be an integer, a floating-point number, a character string, or a machine instruction.

Machine representations of numbers are finite approximations of integers and real numbers, so they can behave in unexpected ways. That is the subject of Chapter 2.

1.2 · programs are translated by other programs

Four workers on a translation line

People can read hello.c. The processor cannot. Every C statement first has to be translated into low-level machine-language instructions, packed into an executable object file on the disk.

One command does it: gcc -o hello hello.c. The compiler driver gcc runs four programs in a row, together called the compilation system. The preprocessor pastes in header files. The compiler writes assembly language. The assembler turns that into machine-code bytes in a relocatable object file. The linker merges in library code such as printf and writes the finished executable.

Try it: press Step to run one worker at a time and read each new file in the code panel. Then choose library missing and run the line again — that error message is one every C programmer meets.

What the book says
  • Preprocessor (cpp): modifies the program according to directives that begin with #. #include <stdio.h> reads the system header file stdio.h and inserts it into the program text. The result, typically with the .i suffix, is another C program.
  • Compiler (cc1): translates hello.i into hello.s, an assembly-language program. “Assembly language is useful because it provides a common output language for different compilers for different high-level languages.”
  • Assembler (as): translates hello.s into machine-language instructions packaged as a relocatable object program in hello.o. The book calls it “a binary file containing 17 bytes to encode the instructions for function main”; viewed in a text editor it looks like gibberish.
  • Linker (ld): the printf function lives in a separate precompiled object file, printf.o, which must be merged with hello.o. The result is the executable object file hello, ready to be loaded into memory and run.

Figure 1.3 marks hello.c, hello.i and hello.s as text and hello.o, printf.o and hello as binary. In the book’s listing of hello.s, the call appears as call puts.

1.3 · it pays to understand how compilation systems work

Three kinds of trouble

For hello.c you can trust the compiler blindly. For bigger programs the book gives three reasons to know what it is doing.

Speed. Two loops that compute the same sum can run at very different speeds: one keeps its running total in a fast register, the other has to write it back to memory on every pass.

Link-time errors. The linker must find exactly one definition for every name a program uses. None, or two, and the build fails. Security. If a program copies more characters into a small array than it can hold, the extra bytes spill onto whatever sits next to it on the stack — including the address the function will return to. That is a buffer overflow.

Try it: race the two loops and count the trips to memory. Switch to Linker and break the build two different ways. Switch to Stack overflow, drag the slider past 23 characters, then press Return from echo.

What the book says

Optimizing program performance. We do not need to know the compiler’s inner workings, but good coding decisions need a basic understanding of machine-level code. Among the book’s questions: is a switch always more efficient than a sequence of if-else statements, how much overhead does a function call add, and “Why does our loop run so much faster if we sum into a local variable instead of an argument that is passed by reference?” (Chapters 3, 5 and 6.)

Understanding link-time errors. For example, “what does it mean when the linker reports that it cannot resolve a reference?” and “What happens if you define two global variables in different C files with the same name?” Some linker errors do not appear until run time. (Chapter 7.)

Avoiding security holes. “For many years, buffer overflow vulnerabilities have accounted for many of the security holes in network and Internet servers.” A first step in secure programming is to understand how data and control information are stored on the program stack. (Chapter 3.)

1.4 · processors read and interpret instructions stored in memory

The shell: a program that runs programs

hello is now an executable file sitting on the disk. To run it on a Unix system you type its name to a shell: linux> ./hello.

A shell is just another program, a command-line interpreter. It prints a prompt, waits for you to type a line, and then does what the line says. If the first word is one of its own built-in commands, it does the job itself. Otherwise it treats the word as the name of an executable file: it loads the file, runs it, and waits for it to finish before printing the next prompt.

Try it: press the command buttons. Follow the loop around the flowchart and the matching line of the shell’s code. Try a built-in (cd, pwd), a real program (./hello), and a typo.

What the book says

“The shell is a command-line interpreter that prints a prompt, waits for you to type a command line, and then performs the command.”

If the first word of the command line is not a built-in shell command, the shell assumes it names an executable file that it should load and run. For ./hello, the shell loads and runs hello and waits for it to terminate; hello prints its message and terminates; the shell prints a prompt and waits for the next command line.

The book writes its own simple shell in Chapter 8. The shell code here is a sketch in the same spirit, with helper names that say what each step does.

1.4.1 · hardware organization · buses and I/O devices

The city under the keyboard

Inside the box, the parts are joined by buses: bundles of wires that carry bytes back and forth. A bus moves one fixed-size chunk at a time, called a word. How many bytes make a word — the word size — differs between machines. Most today use 4 bytes (32 bits) or 8 bytes (64 bits).

I/O devices connect the computer to the outside world: a keyboard and mouse for input, a display for output, a disk to keep programs and data. Each plugs into the I/O bus through a controller (chips on the device or on the main circuit board) or an adapter (a card in a slot). Either way, its job is to pass bytes between the bus and the device.

Try it: tap any part of the machine to learn what it does. Then send the 16-byte message across the bus with 4-byte words, and again with 8-byte words. Count the trips.

What the book says

Figure 1.4 shows the hardware organization of a typical system, modeled after recent Intel systems. Buses are electrical conduits that carry bytes between the components. “Buses are typically designed to transfer fixed-size chunks of bytes known as words.” Most machines today have word sizes of either 4 bytes (32 bits) or 8 bytes (64 bits); the book does not assume a fixed word size and says what a “word” means wherever it matters.

The example system has four I/O devices: a keyboard and mouse for input, a display for output, and a disk drive for long-term storage. Initially the executable hello program resides on the disk. Each device connects to the I/O bus by a controller (chip sets in the device itself or on the motherboard) or an adapter (a card that plugs into a slot on the motherboard). “The distinction between the two is mainly one of packaging.”

In the figure, the CPU’s bus interface, the I/O bridge and main memory are joined by the system bus and the memory bus; the I/O bus leaves the bridge with expansion slots for other devices such as network adapters.

1.4.1 · hardware organization · main memory

One long street of numbered boxes

Main memory holds the program and the data it is working on while the processor runs it. Physically it is a set of DRAM chips. Logically it is simple: one long row of bytes, each with its own address, starting at 0.

A C variable takes several neighbouring bytes, and how many depends on its type. On an x86-64 machine running Linux, a short takes 2 bytes, an int or a float takes 4, and a long or a double takes 8. The program’s instructions live in memory too — and they are not all the same length.

Try it: press Declare next to put the next variable from the code into memory and see which bytes it fills. Tap a variable to find its line. Then switch to Instructions and step through hello’s main as bytes of different lengths.

What the book says

“The main memory is a temporary storage device that holds both a program and the data it manipulates while the processor is executing the program.” Physically, it is a collection of dynamic random access memory (DRAM) chips.

“Logically, memory is organized as a linear array of bytes, each with its own unique address (array index) starting at zero.” Each machine instruction can consist of a variable number of bytes.

The sizes of data items depend on their C type. On an x86-64 machine running Linux, short requires 2 bytes, int and float 4 bytes, and long and double 8 bytes. Chapter 6 explains DRAM.

1.4.1 · hardware organization · processor

The world’s most patient worker

The processor, or CPU, is the engine that runs instructions stored in main memory. At its heart is a word-size register called the program counter (PC). It always holds the address of some instruction.

From power-on to power-off the processor repeats one loop: read the instruction the PC points at, work out what its bits mean, do that simple job, then update the PC — usually to the next instruction, sometimes somewhere else.

The jobs are few. Load copies memory into a register. Store copies a register into memory. Operate sends two registers through the ALU and keeps the answer. Jump writes a new address into the PC. That simple story is the instruction set architecture. The real chip — its microarchitecture — is far more complicated underneath.

Try it: press Step to run one instruction of this toy program and watch the PC, the registers and memory change. Then press Power on: the same six instructions, forever, making Fibonacci numbers.

What the book says

The CPU is the engine that interprets (executes) instructions stored in main memory. “At its core is a word-size storage device (or register) called the program counter (PC).” At any time the PC contains the address of some machine-language instruction in main memory.

“From the time that power is applied to the system until the time that the power is shut off, a processor repeatedly executes the instruction pointed at by the program counter and updates the program counter to point to the next instruction.” The next instruction may or may not be contiguous in memory.

The simple operations revolve around main memory, the register file (a small storage device of word-size registers, each with its own name) and the ALU, which computes new data and address values. Examples: load (memory → register), store (register → memory), operate (two registers → ALU → register) and jump (a word from the instruction → PC).

The instruction set architecture describes the effect of each machine-code instruction; the microarchitecture describes how the processor is actually implemented, with far more complex mechanisms to speed things up (Chapters 3, 4 and 5).

1.4.2 · running the hello program

Three trips across the machine

Now put the parts together. The shell is running, waiting. As you type ./hello, the shell reads each character into a register and then stores it in memory.

When you hit enter, the shell loads the hello file: its code and data — including the string hello, world\n — are copied from disk into main memory. This copy uses direct memory access (DMA): the bytes go straight from the disk to memory without passing through the processor.

Then the processor runs hello’s main. Its instructions copy the bytes of hello, world\n from memory into the register file, and from there to the display.

Try it: press Next to type one key at a time, then Enter, then run. Watch the two counters: which bytes had to squeeze through the CPU, and which went around it?

1.5 · caches matter

Snacks in your pocket beat snacks in the shop

Look back at hello: the machine spent most of its effort copying — disk to memory, memory to processor, memory to display. Copying is overhead, so designers work hard to make it fast.

Physics gets in the way: bigger storage is slower, and faster storage costs more to build. A disk might hold 1,000 times more than main memory but take 10,000,000 times longer to read a word. The register file holds only a few hundred bytes, yet the processor reads it almost 100 times faster than memory.

So designers put small, fast cache memories made of SRAM in between: an L1 cache nearly as fast as the registers, a bigger L2, sometimes an L3. They work because of locality: programs tend to use data and code in small neighbourhoods. When a cache fetches from memory it grabs a whole cache line of neighbours at once.

Try it: add up the same 4 × 4 table two ways. Row by row, each slow trip to memory brings three neighbours you need next. Column by column, every single read misses. Same answer, very different time.

What the book says

A system spends a lot of time moving information from one place to another, and much of that copying is overhead. Because of physical laws, larger storage devices are slower than smaller ones, and faster devices cost more. A typical disk might be 1,000 times larger than main memory, but it might take the processor 10,000,000 times longer to read a word from disk than from memory.

A register file stores only a few hundred bytes versus billions in main memory, but the processor can read it almost 100 times faster, and this processor–memory gap keeps growing.

An L1 cache on the processor chip holds tens of thousands of bytes and is nearly as fast as the register file. An L2 cache with hundreds of thousands to millions of bytes is connected by a special bus; it might take 5 times longer to reach than L1, but is still 5 to 10 times faster than main memory. Both are SRAM; newer systems add an L3. Caches exploit locality, the tendency for programs to access data and code in localized regions.

“application programmers who are aware of cache memories can exploit them to improve the performance of their programs by an order of magnitude.”

1.6 · storage devices form a hierarchy

Every shelf is a cache for the shelf below

Putting a small, fast store in front of a big, slow one is not a one-off trick. It is used all the way down: registers, L1, L2, L3, main memory, the local disk, and even disks on other machines across a network.

Go down the pyramid and storage gets bigger, slower and cheaper per byte. Go up and it gets smaller, faster and costlier. The big idea: each level is a cache for the level below it. Ask for a word and the fastest shelf is checked first. On a miss, it asks the shelf below — and on the way back up, every shelf keeps a copy, throwing out the word it used longest ago if it is full.

Try it: ask for H. Nobody near the top has it, so it climbs all the way up from remote storage. Ask for H again. Then ask for other letters and watch the small shelves make room.

What the book says

Figure 1.9: L0 registers, L1–L3 caches (SRAM), L4 main memory (DRAM), L5 local secondary storage (local disks), L6 remote secondary storage (distributed file systems, Web servers). As we move from the top to the bottom, devices become slower, larger, and less costly per byte.

“The main idea of a memory hierarchy is that storage at one level serves as a cache for storage at the next lower level.” The register file is a cache for L1; L1 and L2 are caches for L2 and L3; L3 is a cache for main memory, which is a cache for the disk. On some networked systems with distributed file systems, the local disk is a cache for data stored on the disks of other systems.

The shelf sizes and the rule for throwing things out in this machine are toy choices; Chapter 6 covers the real ones.

1.7 · the operating system manages the hardware

Nobody touches the hardware but the OS

When the shell loaded hello and when hello printed its message, neither program touched the keyboard, display, disk or memory directly. They asked the operating system, a layer of software between every application and the hardware.

The OS has two jobs. It protects the hardware from runaway programs. And it gives programs simple, uniform ways to use devices that are complicated and wildly different underneath. It does both with three abstractions: files, virtual memory, and processes.

Try it: press Ask the OS to print the proper way. Then press Poke the hardware and watch the OS stop it. Tap each abstraction to see which hardware it stands for.

What the book says

Neither the shell nor hello accessed the keyboard, display, disk or main memory directly; they relied on services provided by the operating system, a layer of software between the application and the hardware (Figure 1.10). “All attempts by an application program to manipulate the hardware must go through the operating system.”

Its two primary purposes: “(1) to protect the hardware from misuse by runaway applications and (2) to provide applications with simple and uniform mechanisms for manipulating complicated and often wildly different low-level hardware devices.”

1.7.1 · processes

Two programs, one processor, nobody notices

When hello runs, it seems to have the whole machine to itself: the processor runs its instructions one after another, and its code and data look like the only things in memory. That illusion is a process, the operating system’s idea of a running program.

Really, several processes take turns. The OS keeps each one’s context — its PC, its register values, its memory — and performs a context switch: save the current process’s context, restore another’s, hand over the processor. The new process picks up exactly where it left off.

The switching is done by the kernel, the part of the OS that always stays in memory. A program calls into it with a system call, such as read. The kernel is not a process of its own; it is code and data the system uses to manage all of them.

Try it: step Process A until it calls read. Disks are slow, so the kernel parks A and lets B run. Press Disk finishes whenever you like: the kernel parks B, and A carries on from the very next line.

What the book says

The OS provides the illusion that a program has exclusive use of the processor, main memory and I/O devices. “A process is the operating system’s abstraction for a running program.” Processes run concurrently: the instructions of one process are interleaved with the instructions of another, through a mechanism called context switching.

The context includes the current values of the PC, the register file, and the contents of main memory. A context switch saves the context of the current process, restores the context of the new one, and passes control to it; the new process picks up exactly where it left off. Figure 1.12 shows process A calling read, the kernel switching to process B, and a disk interrupt switching back so A returns from read.

For hello, the shell invokes a system call; the OS saves the shell’s context, creates a hello process and its context, and passes control to it; after hello terminates, the OS restores the shell. The kernel is the portion of the OS that is always resident in memory. “Note that the kernel is not a separate process.”

1.7.2 · threads

Two workers, one notebook

A process can hold more than one flow of control. Each flow is a thread. Threads run inside the same process, so they share its code and its global data.

That makes teamwork easy. Two threads can each add up half of a list and write their answers into one shared array, and the main program simply reads it. Two separate processes each get a private copy of everything, so their answers never reach each other without extra work.

Try it: run the sum with 2 threads, then switch to 2 processes and run it again. Same code, same numbers — but only one of them prints 31.

What the book says

“Although we normally think of a process as having a single control flow, in modern systems a process can actually consist of multiple execution units, called threads, each running in the context of the process and sharing the same code and global data.”

Threads matter because network servers need concurrency, because “it is easier to share data between multiple threads than between multiple processes”, and because threads are typically more efficient than processes. Multi-threading can also make programs run faster when multiple processors are available (Section 1.9.2). Chapter 12 teaches threaded programming.

The fork call in the process version is a Chapter 8 tool; here it simply makes a child process that is a copy of its parent.

1.7.3 · virtual memory

Every program believes it owns the whole notebook

Virtual memory gives each process the illusion that it has main memory all to itself. Every process sees the same tidy layout: its virtual address space.

From address 0 upward: the program’s code and global data, loaded from the executable file; the heap, which grows and shrinks as the program calls malloc and free; an area for shared libraries such as the C library; the user stack, which grows with every function call; and at the very top, kernel memory the program may not touch.

Behind the illusion, a process’s memory is kept on disk and main memory acts as a cache for it. Hardware translates every address the processor uses.

Try it: press malloc and Call f() and watch the heap and the stack grow toward each other. Tap any area to use it: if its page is not in main memory yet, it is copied in from the disk first. Then try to touch kernel memory.

What the book says

“Virtual memory is an abstraction that provides each process with the illusion that it has exclusive use of the main memory.” Each process has the same uniform view, its virtual address space (Figure 1.13, for Linux). Addresses increase from the bottom to the top.

  • Program code and data: code begins at the same fixed address for all processes, followed by global C variables, initialized from the executable file.
  • Heap: expands and contracts at run time with calls such as malloc and free.
  • Shared libraries: near the middle, code and data for libraries such as the C standard library.
  • Stack: at the top of user space; it grows with each function call and contracts on return.
  • Kernel virtual memory: applications may not read or write it or call kernel functions directly.

“The basic idea is to store the contents of a process’s virtual memory on disk and then use the main memory as a cache for the disk.” Hardware translates every address the processor generates (Chapter 9).

1.7.4 · files

A file is a sequence of bytes. Full stop.

To a Unix program, a file is just a sequence of bytes. And every I/O device — disks, keyboards, displays, even networks — is treated as a file.

So all input and output works the same way: reading and writing files with a small set of system calls called Unix I/O. A program that copies a disk file never needs to know what kind of disk it is on, and the same program keeps working on machines with completely different disks.

Try it: choose where the bytes come from and where they go, then press Copy. Watch the code: only the first two lines change. The read–write loop is the same for every device.

What the book says

“A file is a sequence of bytes, nothing more and nothing less.” Every I/O device, including disks, keyboards, displays, and even networks, is modeled as a file. All input and output is performed by reading and writing files with a small set of system calls known as Unix I/O.

This gives applications a uniform view of all the varied I/O devices. Programmers who manipulate the contents of a disk file are “blissfully unaware of the specific disk technology”, and the same program runs on systems that use different disk technologies. Chapter 10 covers Unix I/O.

1.8 · systems communicate with other systems using networks

The network is just another gadget

So far the computer has been alone. In practice, systems are linked by networks. To one machine, a network is just another I/O device: copy bytes from main memory to the network adapter and they flow to another machine instead of to a local disk.

The book runs hello on a faraway machine with telnet. A client on your machine sends what you type to a server on the other machine. A shell there runs hello, and the output travels back to your screen. This client–server exchange is the shape of email, the Web, and almost every network program.

Try it: walk the five steps of Figure 1.15. Watch the code: the client and server move bytes with the same read and write calls you just used for files.

What the book says

From the point of view of an individual system, a network can be viewed as just another I/O device (Figure 1.14). “When the system copies a sequence of bytes from main memory to the network adapter, the data flow across the network to another machine, instead of, say, to a local disk drive.” Email, instant messaging, the World Wide Web, FTP, and telnet all copy information over a network.

1.9 important themes · 1.9.1 Amdahl’s law

A 3× faster oven doesn’t make dinner 3× faster

The tour ends with ideas that run through every part of a computer system — which is more than hardware: it is hardware and systems software working together. The first idea is Gene Amdahl’s: when you speed up one part, how much faster does the whole thing get?

It depends on how big that part was and how much you sped it up. If a part takes a fraction α of the time and you make it k times faster, the speedup of the whole is S = 1 / ((1 − α) + α/k). The book’s example: make 60% of the work 3× faster and the whole job is only 1.67× faster. Even making that 60% take no time at all gives just 1 / (1 − α) = 2.5×.

Try it: drag α and k and watch the curve flatten against its ceiling. Then switch to Potato truck, the book’s practice problem, and push the truck faster through Montana.

What the book says

A system is a collection of intertwined hardware and systems software that must cooperate to run application programs. Section 1.9 closes the tour with concepts that cut across all of it.

If a part takes a fraction α of the time Told and is sped up by a factor k, then Tnew = Told[(1 − α) + α/k] and the speedup S = Told/Tnew = 1/((1 − α) + α/k). With α = 0.6 and k = 3, S = 1.67×. Setting k to ∞ gives S∞ = 1/(1 − α); for α = 0.6 that is 2.5×. The major insight: “to significantly speed up the entire system, we must improve the speed of a very large fraction of the overall system.”

Practice 1.1: potatoes from Boise to Minneapolis, 2,500 km at 100 km/hr is 25 hours. If 1,500 km (Montana) can be driven at 150 km/hr, the trip takes 10 + 10 hours: 1.25×. For 1.67× the trip must take 15 hours, so Montana in 5 hours: 300 km/hr. Practice 1.2: a 4× target with α = 0.9 needs k = 6.

The book’s aside recommends expressing a performance improvement as the ratio Told/Tnew with a “×” suffix, because percentages are ambiguous.

1.9.2 · concurrency and parallelism · thread-level

A juggler, four cooks, and a cook with two pans

We always want computers to do more, and to go faster. Both improve when the processor does more things at once. Concurrency means many activities at the same time; parallelism means using concurrency to finish sooner.

For decades a single processor faked it — a uniprocessor switching quickly between programs, like a juggler. A multi-core chip has several real processors, called cores, on one chip. Hyperthreading gives one core spare copies of some hardware, such as program counters and register files, so it can choose which thread to run on every single cycle — and keep busy with one thread while another waits for memory.

Try it: run the same four threads on each machine. The uniprocessor has to switch, and sits idle during every wait. Four cores finish fast. Two hyperthreaded cores fill each other’s waits and get surprisingly close.

What the book says

Concurrency is the general concept of a system with multiple, simultaneous activities; parallelism is the use of concurrency to make a system run faster. Traditionally concurrent execution was only simulated, by one computer rapidly switching among its processes, “much as a juggler keeps multiple balls flying through the air.” That configuration is a uniprocessor system; multiple processors under the control of a single operating system kernel form a multiprocessor system (Figure 1.16).

Figure 1.17: four cores on one chip, each with its own L1 (split into an i-cache and a d-cache) and L2 cache, sharing the L3 cache and the interface to main memory.

Hyperthreading duplicates some CPU hardware, such as program counters and register files. “Whereas a conventional processor requires around 20,000 clock cycles to shift between different threads, a hyperthreaded processor decides which of its threads to execute on a cycle-by-cycle basis.” If one thread waits for data to be loaded into a cache, the CPU can run another. The Intel Core i7 runs two threads per core, so a four-core system executes eight threads in parallel.

Multiprocessing helps in two ways: less simulated concurrency, and a single application runs faster — but only if it is expressed as multiple threads that can run in parallel.

1.9.2 · concurrency and parallelism · instruction-level

An assembly line inside the processor

Zoom into one core. Modern processors work on several instructions at once: instruction-level parallelism. Early chips such as the 1978 Intel 8086 needed 3 to 10 clock cycles for every instruction. Recent processors keep up 2 to 4 instructions per cycle.

The main trick is a pipeline. Running an instruction is split into steps, the hardware is built as a row of stages, and each stage works on a different instruction at the same moment — like a car wash with five bays. A simple pipeline gets close to 1 instruction per cycle. Superscalar processors beat 1 per cycle.

Try it: run the same eight instructions three ways and compare the clock: one at a time, pipelined, then two at a time. Use Step one cycle to see which instruction sits in which stage.

What the book says

Modern processors can execute multiple instructions at one time, a property known as instruction-level parallelism. The 1978-vintage Intel 8086 required multiple (typically 3–10) clock cycles per instruction; more recent processors sustain 2–4 instructions per clock cycle. Any given instruction may take 20 cycles or more from start to finish, but the processor can process as many as 100 instructions at a time.

With pipelining, the actions of an instruction are partitioned into steps and the hardware is organized as a series of stages that operate in parallel on different parts of different instructions. “We will see that a fairly simple hardware design can sustain an execution rate close to 1 instruction per clock cycle.” Processors that sustain faster than 1 instruction per cycle are superscalar; most modern processors are (Chapters 4 and 5).

The five stage names and the independent instructions here are a toy; Chapter 4 builds a real pipeline and handles instructions that depend on each other.

1.9.2 · concurrency and parallelism · SIMD

One instruction, eight answers

At the lowest level, special hardware lets one instruction do many operations at once: single-instruction, multiple-data (SIMD) parallelism. Recent Intel and AMD processors can add 8 pairs of float numbers with a single instruction.

This is mostly for pictures, sound and video, where the same sum is done to thousands of values. Compilers sometimes find SIMD chances by themselves, but the book says a more reliable way is to use the special vector data types that compilers such as gcc provide.

Try it: brighten eight pixels of a photo. First with the plain loop: eight add instructions, one lane at a time. Then switch to the vector type: one instruction, all eight lanes together.

What the book says

Many modern processors have special hardware that allows a single instruction to cause multiple operations to be performed in parallel: single-instruction, multiple-data (SIMD) parallelism. Recent generations of Intel and AMD processors have instructions that can add 8 pairs of single-precision floating-point numbers (C data type float) in parallel.

These instructions are provided mostly to speed up applications that process image, sound, and video data. “Although some compilers attempt to automatically extract SIMD parallelism from C programs, a more reliable method is to write programs using special vector data types supported in compilers such as gcc.” The book describes this style in Web Aside OPT:SIMD and Chapter 5.

1.9.3 · the importance of abstractions in computer systems

A simple face on a complicated machine

Good programmers hide messy code behind a small, simple API, so other people can use it without reading the insides. Computer systems do the same trick at every level.

The instruction set architecture lets machine code act as if the processor runs one instruction at a time, even though the hardware runs many at once. Because that promise never changes, a cheap processor and an expensive one can run the very same machine code. The OS adds files, virtual memory and processes. And a virtual machine stands for a whole computer — operating system, processor and programs — so one box can run programs made for several different operating systems.

Try it: tap each abstraction in Figure 1.18 to see what it hides. Then switch to Same code, two chips and race one piece of machine code on a budget chip and a fancy one: different speed, identical answer.

What the book says

“The use of abstractions is one of the most important concepts in computer science.” Good practice is to give a set of functions a simple application program interface (API) so programmers can use them without delving into their inner workings.

On the processor side, the instruction set architecture abstracts the actual hardware: “With this abstraction, a machine-code program behaves as if it were executed on a processor that performs just one instruction at a time.” The hardware executes many instructions in parallel, but always consistently with the sequential model, so different processor implementations can run the same machine code while offering a range of cost and performance.

On the operating system side: files abstract I/O devices, virtual memory abstracts program memory, and processes abstract a running program. The virtual machine abstracts the entire computer, including the operating system, the processor, and the programs. IBM introduced it in the 1960s; it helps run programs designed for multiple operating systems (such as Microsoft Windows, Mac OS X, and Linux) or different versions of one (Figure 1.18).

The abstractions, one line each

Each name is a promise: “you can pretend the messy part looks like this.”

Instruction set architecture

Promises one instruction at a time, in order. Really many run at once — always with the same result.

Files

Promise that a disk, a keyboard, a display and a network are all just bytes you read and write.

Virtual memory

Promises your program has all of memory to itself, in the same tidy layout every time.

Processes

Promise your program is the only one running, with the processor to itself.

Virtual machine

Promises a whole computer — OS, processor and programs — living inside another computer.

Words to know

Grown-up words from the tour, in plain language.

bit / byte
A bit is a 0 or a 1. Eight bits make a byte, a number from 0 to 255.
ASCII / text file
The agreement that says which number means which character. A text file holds only ASCII; every other file is binary.
context
How a program chooses to read some bytes: as text, a number, or an instruction.
compilation system
Preprocessor, compiler, assembler and linker working as a team, usually started by gcc.
relocatable / executable
A .o file whose blanks still need filling by the linker, versus a finished program ready to load.
shell / built-in
A program that reads command lines and runs them. A built-in is a command the shell does itself instead of loading a file.
bus / word
Wires that carry a fixed-size chunk of bytes. That chunk is a word, usually 4 or 8 bytes.
controller / adapter
What connects a device to the I/O bus: chips on the device or board, or a card in a slot.
DRAM / address
The chips main memory is made of, and the number that names one byte in it.
PC / register file / ALU
The program counter holds the next instruction’s address; registers are named word-size boxes; the ALU does the arithmetic.
ISA vs microarchitecture
What each instruction promises to do, versus the clever hardware that actually does it.
DMA
Direct memory access: a device copies bytes into memory without going through the CPU.
cache / SRAM / locality
A small fast store (SRAM) in front of big slow memory. It works because programs keep using nearby data.
memory hierarchy
Storage stacked from small and fast to big and slow, each level a cache for the next.
operating system
The software layer every program must go through to use the hardware.
process / context switch
A running program’s illusion of owning the machine, and the save-and-restore that lets processes take turns.
kernel / system call
The always-in-memory part of the OS, and the special instruction a program uses to ask it for help.
thread
An extra flow of control inside a process, sharing its code and global data.
virtual address space
The private-looking layout every process sees: code, data, heap, shared libraries, stack, kernel.
file / Unix I/O
A sequence of bytes. Disks, keyboards, displays and networks are all files, used through a few system calls.
client / server
The program that asks, and the program that answers, usually on different machines.
Amdahl’s law
S = 1 / ((1 − α) + α/k). Speeding up a small slice cannot save the whole job.
concurrency / parallelism
Many things at once, versus using that overlap to finish sooner.
multi-core / hyperthreading
Several processors on one chip, or one core that can switch between threads every cycle.
pipeline / superscalar
Stages that overlap instructions like a car wash; and chips that finish more than one instruction per cycle.
SIMD / vector type
One instruction doing the same sum on many values; and the C type that asks for it.
buffer overflow
Writing past the end of an array and scribbling on what comes next — sometimes the return address.
abstraction / API
A simple face over complicated insides, and the set of functions that forms it.
virtual machine
An abstraction of a whole computer, so one box can host several operating systems.
