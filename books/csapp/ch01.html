1.1 · information is bits + context

The same beads, a different necklace

Your program starts as a text file named hello.c. Inside the computer it is not letters. It is a row of bits — zeros and ones — grouped into 8-bit bytes. Each byte is just a number from 0 to 255.

English text usually uses the ASCII table: 35 means #, 105 means i, and the invisible “go to the next line” is 10. A file made only of ASCII is a text file. Everything else is a binary file.

Here is the surprise: nothing in those numbers says what they mean. The same four bytes can be a word, a whole number, a decimal, or an instruction. Only the context — how you choose to read them — decides.

Try it: tap any byte to see its eight switches. Then slide the green window and watch four machines read the same four bytes four different ways.

What the book says

A source program is a sequence of bits organized in 8-bit bytes. Figure 1.2 shows the ASCII values for hello.c: the first byte is 35 (#), the second is 105 (i), and each line ends with newline 10.

“All information in a system — including disk files, programs stored in memory, user data stored in memory, and data transferred across a network — is represented as a bunch of bits. The only thing that distinguishes different data objects is the context in which we view them.”

Machine numbers are finite approximations of integers and reals. That is why they can behave in unexpected ways (Chapter 2).

1.2 · programs are translated by other programs

Four workers on a translation line

Humans can read hello.c. The processor cannot. A compiler driver such as gcc -o hello hello.c runs four other programs, together called the compilation system.

The preprocessor pastes in headers. The compiler writes assembly. The assembler turns that into a relocatable object file (hello.o) — 17 bytes for main in the book’s example. The linker glues in library code such as printf.o and writes the executable.

Step through each station. Then take printf.o away and see the error every programmer meets sooner or later.

What the book says
  • Preprocessor (cpp): hello.c → hello.i. Lines starting with # are expanded. #include <stdio.h> inserts the header.
  • Compiler (cc1): hello.i → hello.s, an assembly-language program. Assembly is a common output language for C, Fortran, and others.
  • Assembler (as): hello.s → hello.o, a relocatable object program. Opening it in a text editor looks like gibberish.
  • Linker (ld): merges hello.o with precompiled objects such as printf.o into the executable hello.

In the book’s assembly, printf("hello, world\n") became call puts — the compiler may pick a simpler library function when the result is the same.

gcc -o hello hello.c

        1.3 · it pays to understand compilation systems
        
Three kinds of trouble

        
For hello.c you can ignore the compiler. For real programs, three kinds of trouble show up if you do.

        
Performance: is a switch faster than if? Why does summing into a local variable beat summing through a pointer? The answers live in the machine code (Chapters 3, 5, 6).

        
Link-time errors: “undefined reference,” two globals with the same name, library order on the command line — some of these only explode at run time (Chapter 7).

        
Security: a too-long name written into a too-small stack buffer can overwrite the return address. That is a buffer overflow. Understanding the stack is the first defence (Chapter 3).

        
Flip the cards and poke each kind of trouble. On the overflow card, drag the slider past 8 characters.

        

          What the book says
          

            
Coding decisions still need a feel for machine-level translation: switch vs if-else, call overhead, pointers vs array indexes, summing into a local vs a by-reference argument.

            
Linker questions: unresolved references, static vs global variables, two globals with the same name, static vs dynamic libraries, library order, and errors that appear only at run time.

            
“For many years, buffer overflow vulnerabilities have accounted for many of the security holes in network and Internet servers.” A first step in secure programming is understanding how data and control information sit on the program stack.

        1.4.1 · hardware organization
        
The city under the keyboard

        
You type ./hello in a shell. The shell is just another program: it prints a prompt, reads a line, and if the word is not a built-in command it loads that file and waits for it to finish.

        
Inside, everything is connected by buses — electrical roads that carry chunks of bytes called words (4 or 8 bytes). Main memory is one long row of numbered boxes in DRAM. The CPU reads and obeys instructions. The disk, keyboard and display are I/O devices, each plugged in through a controller or adapter.

        
Run the three steps of ./hello. Watch step 2 closely: the file goes straight from disk to memory without passing through the CPU. That shortcut is DMA — direct memory access.

        

          What the book says
          

            
Figure 1.4: buses transfer fixed-size words. I/O devices connect via controllers (on the device or motherboard) or adapters (cards in slots). An I/O bridge joins the system bus to the memory bus and the I/O bus.

            
Main memory is a linear array of bytes starting at address 0, built from DRAM. On x86-64 Linux, short is 2 bytes, int and float are 4, long and double are 8.

            
Running hello: keystrokes go keyboard → register → memory. Hitting enter makes the shell copy the executable from disk to memory. DMA lets those bytes travel disk → memory without going through the CPU. Then main copies hello, world\n memory → register → display.

        1.4 · processors read instructions stored in memory
        
The world’s most patient worker

        
From the moment the power goes on until it goes off, the processor does the same tiny loop, billions of times a second: look at the address in the program counter (PC), fetch the instruction there, do what it says, then move the PC on.

        
There are only a handful of jobs an instruction can ask for: load (copy memory → register), store (copy register → memory), operate (send two registers to the ALU and keep the answer), and jump (write a new address into the PC).

        
That simple story is the instruction set architecture. The real chip (the microarchitecture) is much sneakier — Chapter 4.

        
Step through a five-instruction program. Watch the PC, the registers and memory change, one cycle at a time.

        

          What the book says
          

            
At the core of the CPU is a word-size register called the program counter, which always points at some machine-language instruction in main memory. The register file is a small storage device of named word-size registers. The ALU computes new data and address values.

            
The processor appears to follow this simple sequential model — its instruction set architecture. In reality its microarchitecture runs many instructions at once, but always in a way that matches the simple story.

        1.5 · caches matter
        
Snacks in your pocket beat snacks in the shop

        
A computer spends most of its life copying things. Physics is rude: bigger storage is slower storage. Registers are lightning-fast but tiny. Main memory is huge but far away. A disk may be 1,000× larger than memory and 10,000,000× slower to read a word.

        
So designers slip small fast caches (SRAM) between the processor and memory. An L1 is almost as fast as registers. An L2 is still 5–10× faster than DRAM. Newer chips add L3. This works because of locality: programs keep coming back to the same little patch of data.

        
Run the same 16 reads in order, then jumping around. Same work, wildly different time — because each miss also fetches the neighbours.

        

          What the book says
          

            
The processor reads from the register file almost 100 times faster than from memory, and this processor–memory gap keeps growing. L1 on the processor chip holds tens of thousands of bytes at nearly register speed. L2 holds hundreds of thousands to millions of bytes; reaching it may take 5 times longer than L1 but is still 5–10 times faster than main memory.

            
“Application programmers who are aware of cache memories can exploit them to improve the performance of their programs by an order of magnitude.”

        1.6 · storage devices form a hierarchy
        
Every shelf is a cache for the shelf below

        
The cache trick is not used once — it is used all the way down. Registers cache L1. L1 caches L2. L2 caches L3. L3 caches main memory. Main memory caches the disk. On a networked machine, your disk caches files that really live on another computer.

        
Go down the pyramid and storage gets bigger, slower and cheaper per byte. Go up and it gets smaller, faster and pricier.

        
Ask for a byte that nobody has yet. Watch it climb, leaving a copy on every shelf. Then ask again.

        

          What the book says
          

            
Figure 1.9: L0 registers, L1/L2/L3 caches, L4 main memory, L5 local disks, L6 remote storage such as distributed file systems and web servers.

            
“The main idea of a memory hierarchy is that storage at one level serves as a cache for storage at the next lower level.”

        1.7.1–1.7.2 · the OS manages the hardware
        
Two cooks, one stove

        
hello never touches the keyboard, disk or memory itself. It asks the operating system, a layer between apps and hardware. The OS has two jobs: protect the hardware from runaway programs, and give every program a simple way to use wildly different devices.

        
A process is the illusion that your program is the only one running. The OS juggles many processes by context switching — save this process’s PC, registers and memory image, restore the next one’s, jump. The kernel is the OS code that always stays in memory. It is not a process; it is the toolbox that manages them.

        
A process can also contain several threads: extra flows that share the same code and globals. Threads are cheaper to switch and easier to share data with than whole processes.

        
Step the shell → hello story. Watch the kernel freeze one program mid-sentence and hand the processor to the other.

        

          What the book says
          

            
Three fundamental OS abstractions (Figure 1.11): files abstract I/O devices, virtual memory abstracts memory and disk, processes abstract the processor, memory, and I/O.

            
The shell invokes a system call. The OS saves the shell, creates a hello process, and later restores the shell. A disk interrupt during a read can switch to another process and later return. “Note that the kernel is not a separate process. Instead, it is a collection of code and data structures that the system uses to manage all the processes.”

        1.7.3 · virtual memory
        
Every program believes it owns the whole notebook

        
Virtual memory gives each process the same uniform picture, a virtual address space. In the book’s picture, high addresses sit at the top.

        
From the top: kernel memory that user code must not touch, the user stack that grows on each function call, shared libraries such as the C library, the heap that malloc and free grow and shrink, then globals and code loaded from the executable. Code starts at the same fixed address in every process.

        
The trick: the process’s memory really lives on disk, and main memory is a cache for that disk. Hardware translates every address the CPU issues (Chapter 9).

        
Call malloc, call a function, return. Watch the heap climb and the stack drop — they grow toward each other but never collide here.

        

          What the book says
          

            
Linux reserves the top of the address space for kernel code and data shared by all processes. The lower region is the user’s process. Code begins at a fixed address, then global data, then the heap, then a mapped region for shared libraries, then the user stack at the top of user space, then kernel virtual memory.

            
Applications cannot read, write, or call into the kernel area; they must invoke the kernel. Virtual memory stores a process’s contents on disk and uses main memory as a cache.

        1.7.4 · files
        
A file is a sequence of bytes. Full stop.

        
Disks, keyboards, displays, even networks are modelled as files: a sequence of bytes, nothing more. All input and output goes through a small set of system calls called Unix I/O.

        
That is why the same program can talk to a spinning disk, an SSD, or a socket without rewriting. The messy device details hide behind one idea.

        
Read from each device with the same button. The bytes take different roads; the API does not change.

        

          What the book says
          

            
“A file is a sequence of bytes, nothing more and nothing less.” Every I/O device — disks, keyboards, displays, networks — is modelled as a file. All input and output is performed by reading and writing files using Unix I/O system calls.

            
Programmers who manipulate a disk file can stay unaware of the disk technology. Chapter 10 covers Unix I/O.

        1.8 · systems communicate using networks
        
The network is just another gadget

        
From one machine’s point of view a network is just another I/O device. Copy bytes to the network adapter and they show up in someone else’s memory instead of on your disk.

        
The book runs hello through telnet: you type on a local client, the string crosses the network to a remote shell, that shell runs hello, and hello, world travels back to your display. That client–server exchange is the shape of email, the web, and almost every network app (Chapter 11).

        1.9.1 · Amdahl’s law
        
Making the oven 3× faster does not make dinner 3× faster

        
Amdahl’s law (Gene Amdahl): if a fraction α of the time is sped up by a factor k, the whole-system speedup is

        
S = 1 / ((1 − α) + α/k)

        
The book’s example: speed up 60% of the work by 3×. You only get 1.67× overall. Even if that 60% became instant (k → ∞), you would still only get S∞ = 1/(1 − α) = 2.5×. To make the system much faster you must improve a large fraction of it.

        
Drag α and k. Then try the book’s potato truck (Boise → Minneapolis) and the engine that must hit 4×.

        

          What the book says
          

            
Tnew = Told[(1 − α) + α/k], so S = Told/Tnew = 1 / ((1 − α) + α/k). Report improvements as a ratio with a × suffix (“2.2×”), not as an ambiguous percentage.

            
Practice 1.1 — 2,500 km at 100 km/h is 25 hours. Montana is 1,500 km (α = 0.6). Raising Montana to 150 km/h (k = 1.5) gives 10 + 10 = 20 hours, 1.25×. To reach 1.67× you need the whole trip in 15 hours, so Montana in 5 hours = 300 km/h.

            
Practice 1.2 — want S = 4 with α = 0.9. Solving gives k = 6. If 10% cannot be improved, no finite k on the other 90% can beat S∞ = 10×.

        1.9.2 · concurrency and parallelism
        
Juggler, four cooks, conveyor belt, eight spoons

        
Concurrency means many activities at once. Parallelism is using that to go faster. The book stacks three levels.

        
Thread-level: a uniprocessor simulates concurrency by juggling. A multi-core chip puts several cores on one package (each with its own L1/L2; L3 and memory are shared). Hyperthreading gives one core extra PCs and register files so it can switch threads every cycle — a Core i7 core runs 2 threads, so 4 cores run 8.

        
Instruction-level: old chips needed 3–10 cycles per instruction. A simple pipeline can finish about 1 instruction per cycle. Superscalar designs issue several at once and can sustain 2–4 instructions per cycle.

        
SIMD: one instruction adds 8 floats at once. Handy for pictures, sound, and video.

        
Switch the model. Same idea, five hardware stories. Nothing in these pictures sits on top of anything else — each piece has its own lane.

        

          What the book says
          

            
A conventional context switch costs ~20,000 cycles. A hyperthreaded core picks a thread every cycle, so when one thread waits on a cache the other can use the ALU.

            
Pipelining splits instruction execution into stages that operate in parallel on different instructions. A simple pipeline can approach 1 instruction per cycle; superscalar processors sustain more. SIMD instructions on recent Intel/AMD chips can add 8 pairs of floats in parallel.

        1.9.3 · the importance of abstractions
        
A simple face on a complicated machine

        
Good code hides its insides behind a small API. Computer systems do the same, at every floor.

        
The instruction set architecture pretends the CPU executes one instruction at a time, in order — even though the chip is a circus of parallel tricks. That is why the same machine code runs on cheap and fancy processors.

        
The OS adds files, virtual memory, and processes. On top sits a newer idea IBM started in the 1960s: the virtual machine, a whole computer you can stack so one box can host several operating systems at once.

        
Peel a layer. The name you are standing on stays simple. The machinery underneath is named in the caption, not piled on the picture.

        

          What the book says
          

            
Figure 1.18: instruction set architecture abstracts the processor; files abstract I/O; virtual memory abstracts program memory; processes abstract a running program; a virtual machine abstracts the entire computer, including the OS.

            
Keeping one sequential execution model lets different processor implementations offer a range of cost and performance while running the same machine code.

Words to know
Grown-up words from the tour, in plain language.

      

        
bit / byte
A bit is a 0 or a 1. Eight of them make a byte, a number from 0 to 255.

        
ASCII / text file
The agreement that says which number means which letter. A text file is only ASCII; anything else is binary.

        
compilation system
Preprocessor, compiler, assembler, and linker working as a team, usually driven by gcc.

        
relocatable / executable
A .o piece that still needs linking, versus a finished program ready to load.

        
shell
A program that reads a command line and runs it — itself just another process.

        
bus / word
Wires that carry a fixed-size chunk of bytes. That chunk is a word: often 4 or 8 bytes.

        
PC / register file / ALU
The program counter points at the next instruction. Registers are named word-size boxes. The ALU does the arithmetic.

        
ISA vs microarchitecture
The promised behaviour of each instruction, versus the clever hardware that actually implements it.

        
DMA
Direct memory access: disk (or other I/O) copies into memory without bothering the CPU.

        
cache / SRAM / DRAM / locality
A small fast staging area (SRAM) in front of big slow memory (DRAM). Works because programs reuse nearby data.

        
process / context / kernel
A running program’s illusion of owning the machine. Context is the saved state. The kernel is the always-resident OS code that switches them.

        
thread
An extra flow of control inside a process, sharing code and globals.

        
virtual address space
The fake notebook every process sees: code, data, heap, shared libraries, stack, kernel.

        
file / Unix I/O
A sequence of bytes. Disks, keyboards, displays, and networks are all files, reached with a few system calls.

        
buffer overflow
Writing past the end of a box in memory and scribbling on what comes next — often the return address.

        
Amdahl’s law
S = 1 / ((1 − α) + α/k). Speeding up a small slice cannot save the whole job.

        
concurrency / parallelism
Many things at once, versus using that overlap to finish sooner.

        
multi-core / hyperthreading
Several CPUs on one chip, or one CPU with extra PCs so it can interleave two threads every cycle.

        
pipeline / superscalar / SIMD
Stages overlapping instructions; more than one instruction per cycle; one instruction doing the same op on many values.

        
virtual machine
An abstraction of a whole computer, so one box can host several operating systems.
