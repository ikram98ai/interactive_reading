Concurrent Programming

One slow visitor should not freeze the whole shop. Logical flows can overlap in time — as processes, as one process juggling descriptors, or as threads in a single kitchen.

“A concurrent program consists of a collection of logical flows that overlap in time.” — Bryant & O’Hallaron, §12.8

New here? Every numbered section below is one little machine. Read the short story, then press the buttons. Under each picture are the listings: Rust code for what the picture acts out (the book’s own code is C; this page shows the same ideas in Rust), any assembly (rustc’s own, for x86-64 Linux), and picture, the rules the drawing itself follows. The highlighted line is what just happened. You cannot break it.

A few words of Rust read the same everywhere below: fn starts a function, let makes a variable (let mut one that may change), a name with ! such as println! is a macro, and // starts a comment. i32, u32 and u64 are 32- and 64-bit integers (u: unsigned, never negative), and bool is true or false. pub lets other modules use an item. loop { … } repeats forever; for i in 0..n runs with i = 0, 1, …, n−1, and _ in place of a name means the value is not used. New words get a gloss where they first appear.

Rust setup: what the listings assume

The listings are short pieces of programs. They all assume the block below: the use lines that bring std’s names in, and three things std does not have. There is no fork and no select in std, so two small wrappers call the C library. A function declared in an extern block is unsafe to call, so the call sits in unsafe: a block the Rust compiler cannot check, so a person has to. And there is no semaphore in std, so Sem builds the book’s P and V from what std does have: a Mutex and a Condvar.

A Rust note: the book’s C lets two threads write one plain global, and that is how it loses updates. Safe Rust refuses to compile that: a type may cross to another thread only if it is Send, and be shared only if it is Sync (Section 12.7.1 explains both). This page quotes the real compiler errors, then shows the fix: a Mutex, an atomic, or giving each thread its own data. Safe Rust does not stop every concurrency bug, though: lost updates through atomics (12.5) and deadlock (12.7.5) still compile.

// The listings are short pieces of programs. They assume these
// `use` lines, which bring std's names into scope.
use std::cell::Cell; // a value you may change through &, no lock
use std::collections::VecDeque; // a queue: push at the back, pop at the front
use std::env; // the environment: env::set_var
use std::io::{self, Read, Write};
use std::net::{TcpListener, TcpStream};
use std::ops::Range; // start..end, a run of numbers
use std::os::fd::AsRawFd; // .as_raw_fd(): the descriptor number
use std::process::exit;
use std::rc::Rc; // a shared count with no lock (12.7.1)
use std::sync::atomic::{AtomicBool, AtomicI32, AtomicU32, AtomicU64};
use std::sync::atomic::Ordering::SeqCst; // strictest, easiest to reason about
use std::sync::{mpsc, Condvar, Mutex, Once, RwLock};
use std::thread;

// std has no fork and no select. These two call the C library
// directly. Functions in an extern block are unsafe to call:
// Rust can't check them, so the call goes in `unsafe`.
extern "C" {
    #[link_name = "fork"]
    fn c_fork() -> i32;
    #[link_name = "select"]
    fn c_select(n: i32, r: *mut FdSet, w: *mut FdSet,
                e: *mut FdSet, timeout: *mut u8) -> i32;
}
// 0 in the child; the child's pid in the parent
pub fn fork() -> i32 { unsafe { c_fork() } }

pub const STDIN: i32 = 0;
// a set of descriptors, laid out like Linux's fd_set: 1024 bits
#[repr(C)]
#[derive(Clone, Copy, Default)] // Copy: `a = b` copies it; Default: empty
pub struct FdSet([u64; 16]);
impl FdSet {
    pub fn new() -> FdSet { FdSet([0; 16]) }
    // `as usize` converts the number to an index type
    pub fn insert(&mut self, fd: i32) {
        self.0[fd as usize / 64] |= 1 << (fd % 64);
    }
    pub fn contains(&self, fd: i32) -> bool {
        self.0[fd as usize / 64] >> (fd % 64) & 1 == 1
    }
}
// sleep until a descriptor in `set` can be read; keep only those
pub fn select_read(set: &mut FdSet) {
    let none: *mut FdSet = std::ptr::null_mut(); // "no set"
    unsafe { c_select(1024, set, none, none, std::ptr::null_mut()) };
}

// std has no semaphore either. This is the book's P and V, built
// from a Mutex (a lock) and a Condvar (a place to sleep and wake).
// A Condvar can wake for no reason, so P re-checks n in a loop.
pub struct Sem { n: Mutex<u32>, wake: Condvar }
impl Sem {
    // const fn: usable in a `static`, before main starts
    pub const fn new(n: u32) -> Sem {
        Sem { n: Mutex::new(n), wake: Condvar::new() }
    }
    pub fn p(&self) { // wait until n > 0, then subtract 1
        let mut n = self.n.lock().unwrap();
        while *n == 0 { n = self.wake.wait(n).unwrap(); }
        *n -= 1;
    }
    pub fn v(&self) { // add 1, then wake one sleeper
        *self.n.lock().unwrap() += 1;
        self.wake.notify_one();
    }
}

// their bodies don't matter here.

12.1 · concurrent programming with processes

Two clerks from one fork

Jonah is the only clerk. A process is a logical flow the kernel schedules. The simplest way to get a second flow is fork. The child is a copy of Jonah at that instant, and from then on the two overlap in time.

The call returns twice. The child sees 0. The parent sees the child’s pid. That is the whole trick: one call, two flows, two different answers. std has no fork, so the fork() here is a small wrapper that calls the C library’s (see the Rust setup above).

Try it: press Fork. Watch the one bar split into two that overlap, and read the return value on the highlighted line.

What the book says

Logical control flows are concurrent if they overlap in time. The simplest way to build a concurrent program is with processes, using fork, exec, and waitpid. A natural server accepts a connection in the parent and creates a new child to service each client.

Because processes have separate virtual address spaces, flows that want to communicate must use an explicit IPC mechanism. The kernel schedules each process.

12.1.1 · a concurrent server based on processes

A new clerk for every customer

Priya listens on descriptor 3. When Omar connects, Accept hands her descriptor 4. She forks. The child closes the listening copy. Priya closes her copy of 4. Both copies pointed at the same file-table entry, so the connection stays up until the last copy closes. In Rust, dropping a TcpStream closes this process’s copy of its descriptor: drop(conn) does it at once, and leaving a value’s scope does it too.

Children exit. Linux does not queue SIGCHLD, so the handler loops on waitpid with WNOHANG and reaps every zombie that is already ready. In server.rs, io::Result is a value that is either Ok or an error, and ? after a call hands any error straight back to the caller.

Try it: Step through the two clients. Then flip to forget drop and watch the file-table count stick at 2.

What the book says

The listening descriptor starts as 3. The first connected descriptor is 4, the next is 5. The child closes its copy of the listening descriptor. The parent must close its copy of the connected descriptor. Otherwise the reference count in the socket’s file table entry never drops to zero while the server runs, and the leak can consume the available memory.

The SIGCHLD handler loops on waitpid, for any child and with WNOHANG, because signals are blocked while the handler runs and Linux signals are not queued. When a process terminates, the kernel closes its descriptors — so a parent that eventually exits would not leak. This parent loops forever, so closing connfd in the parent is what keeps the count honest. Practice 12.2 is that exit-time cleanup.

12.1.2 · pros and cons of processes

Separate houses, shared key rack

File tables are shared. Address spaces are not. Amina’s child can scribble on its own copy of x and Amina’s x stays put. That is the advantage: one process cannot accidentally overwrite another’s virtual memory.

The disadvantage is the same wall. To hand the number across, they need an explicit IPC mechanism, and process control plus IPC is slow compared with a thread switch. In share.rs the pipe is std’s io::pipe, and to_ne_bytes turns x into its four bytes.

Try it: press Child writes x. Then Send on a pipe so the parent actually receives 7.

What the book says

Processes have a clean model for sharing state between parents and children: file tables are shared and user address spaces are not. Separate address spaces are both an advantage and a disadvantage. It is impossible for one process to accidentally overwrite the virtual memory of another process.

To share other state they must use explicit IPC. Process-based designs also tend to be slower because the overhead for process control and IPC is high.

12.2 · I/O multiplexing

One pair of eyes, many doors

Mei does not fork. She builds a read set with stdin (0) and the listening descriptor (3), copies it, and calls select. The kernel sleeps her until a 1-byte read on one of those descriptors would not block.

select overwrites the set, so she copies the read set into a fresh ready set every loop; in Rust, let mut ready = read_set; makes that copy. If she then calls echo until the client hangs up, typed commands sit unread the whole time.

Try it: connect a client, then Type stdin while echo is still running. EOF lets the command through.

What the book says

I/O multiplexing is concurrent programming where the application explicitly schedules its own logical flows inside a single process. Flows are state machines. select manipulates fd_set values. The n argument is one past the highest descriptor of interest, so the book passes listenfd+1.

A descriptor is ready for reading when a request to read 1 byte from it would not block. Because select modifies the set, the server copies the permanent read set into ready_set on every iteration. The first server still calls echo until EOF, so a command on stdin waits.

12.2.1 · an event-driven server

One line, then back to the desk

Nia keeps a pool of connected descriptors. Each client is a state machine: waiting, reading a line, echoing, or closed. check_clients reads one text line from each ready descriptor and returns to select.

The grain of that loop is a whole line. A client that sends hel and then stops leaves Nia blocked inside the read. Ada and Bo cannot move until that line finishes.

Try it: give Ada a full line. Then send Bo a partial line and watch the others freeze. Flip to finer buffer — each client keeps its own unfinished text, and select runs again.

What the book says

The event-driven server is a pool of client descriptors, with init_pool, add_client, and check_clients. Each logical flow is a state machine. On each ready descriptor the server reads one text line. pool.nready is reloaded from select’s return value so the scan can stop once every ready descriptor has been handled.

The granularity of concurrency is the number of instructions needed to read an entire text line. A client that sends only a partial line and then halts stalls every other flow. Handling partial lines is a nontrivial change. A process-based server gets that isolation automatically.

12.2.2 · pros and cons of I/O multiplexing

You are the scheduler

Omar’s event loop can serve a preferred client first. Every flow sees the whole address space, so sharing is just a variable. One process means gdb works the ordinary way, and a new flow does not cost a process context switch.

The bill: about three times the code of the process server, a partial line can stall everyone, and the design cannot fill a multi-core chip. One core runs the loop. The others sit idle.

Try it: press Prefer Ada, then Partial line, then Four cores.

What the book says

Event-driven designs give the programmer more control — preferred service for some clients is hard in a process server. One process means every flow can see the whole address space, the server can be debugged with gdb, and scheduling a flow does not take a process context switch. The event-driven echo server is about three times as much code as the process server.

Finer granularity makes the code harder still. A malicious partial line stalls every flow. Event-based designs also cannot fully utilize multi-core processors. An aside notes that Node.js, nginx, and Tornado still use this style because of the performance advantage over processes and threads.

12.3 · concurrent programming with threads

Scheduled like a process, shared like select

A thread is a logical flow that runs inside a process. The kernel schedules it and knows it by an integer ID, the way it knows a process. Unlike a process, it does not get a private address space. Code, data, heap, shared libraries, and open files are the process’s, seen by every thread.

That is the hybrid. Try to publish a counter: the process child cannot see the parent’s copy. The select loop and the peer thread both can. In Rust, a number that threads share must say so: CNT is an atomic, and store(1, SeqCst) writes it so every thread sees it. SeqCst is the strictest ordering and the easiest to reason about, and this page always uses it.

Try it: press Publish cnt = 1 on each column.

What the book says

Threads are a hybrid of the other two approaches, scheduled by the kernel like process flows and sharing the same virtual address space like I/O multiplexing flows. Each thread has its own thread context: a TID, stack, stack pointer, program counter, general-purpose registers, and condition codes.

All threads in a process share that process’s virtual address space. Programs in the book so far have been one thread per process. Modern systems let several threads run concurrently in one process.

12.3.1 · thread execution model

Peers, not a family tree

Every process starts as one main thread. It creates a peer. A context switch — a slow system call, or the interval timer — moves the CPU to the peer, then back. The peer’s context is smaller than a process context, so the switch is faster.

Threads are a pool of peers, not a parent-child tree. Any thread can wait for any other, given its handle. (The book’s Pthreads can also cancel a thread; std cannot.) The main thread is special only because it ran first.

In Rust, thread::spawn(work) starts a peer and returns its handle. join() waits for that peer and returns a Result: Ok with what the peer returned, or Err if it panicked. unwrap() takes the Ok value, and panics on an Err.

Try it: press Play switches. Then tap a context chip: private pocket, or shared house.

What the book says

The main thread creates a peer and the two run concurrently. Control passes by a context switch, either because the running thread makes a slow system call such as read or sleep, or because the interval timer interrupts it. A thread context switch is faster than a process context switch because a thread context is much smaller.

Threads are not organized in a rigid parent-child hierarchy. They form a pool of peers. Any thread can kill any peer or wait for any peer. Each peer can read and write the same shared data.

12.3.2 · Posix threads

One pointer in, one pointer out

Posix threads, from 1995, are about 60 functions. In the book’s C, a thread routine takes one untyped pointer and returns one, so Luis puts a name and an id in a struct and passes its address. In Rust, thread::spawn takes a closure: a small unnamed function, written || body, that carries values with it. move makes the closure own them, so the struct travels into the peer whole and typed.

A struct is a named group of fields. "Luis".to_string() turns the text into an owned String the struct can keep. The peer prints both fields. Main joins the peer’s handle; then main returns, and the process ends.

Try it: press Run and watch the struct travel into the peer. The highlighted line is the call in flight.

What the book says

Pthreads was adopted in 1995 and is available on all Linux systems. It defines about 60 functions to create, kill, and reap threads, to share data safely, and to notify peers about changes in system state.

The thread routine takes one generic pointer and returns one generic pointer. Multiple arguments go in a structure; the caller passes a pointer to that structure. Multiple return values come back the same way. In the hello program, main calls Pthread_create, Pthread_join, then exit. The peer prints and returns a null pointer.

12.3.3 · creating threads

tid is filled in on the way back

In the book, Chen calls pthread_create with no attributes — the book’s examples never change the defaults — and it returns 0 on success. Rust’s thread::Builder::new().spawn(f) is the version that can report failure: it returns a Result, Ok(handle) or Err(error), and ? passes an Err up. (Plain thread::spawn panics instead.) When it returns Ok, the new peer exists (it may not have run yet), and the handle knows its id.

The peer does not read Chen’s variable. It asks thread::current().id() and gets the same id.

Try it: press Create. Compare the two IDs in the caption and on the code notes.

What the book says

pthread_create runs thread routine f in a new thread with input argument arg. The attr argument changes default attributes; the book always passes NULL. On return, tid contains the new thread’s ID. The function returns 0 on success and a nonzero error code otherwise.

The new thread learns its own ID by calling pthread_self, which returns the thread ID of the caller.

12.3.4 · terminating threads

Four ways a cook leaves

A peer can just return from its function. In the book’s C it can also call pthread_exit, and if main calls pthread_exit, main waits until every peer has finished before the process ends. Rust has no such call. When main returns the whole process ends, so main joins every peer first.

exit(0) is different: it kills the process and every thread in it, immediately. The book’s pthread_cancel lets one thread terminate another. std has no cancel, so main sets a stop flag, an AtomicBool (a true/false threads can share), and peer B checks it and returns.

Try it: press one ending. Reset between them. Watch who is still standing.

What the book says

A thread terminates implicitly when its top-level thread routine returns, or explicitly by calling pthread_exit. If the main thread calls pthread_exit, it waits for the other peers to terminate and then terminates the main thread and the process with return value thread_return.

Some peer calling the Linux exit function terminates the process and all of its threads. Another peer can terminate a chosen thread by calling pthread_cancel with that thread’s ID. pthread_cancel returns 0 on success.

12.3.5 · reaping terminated threads

You may wait for this one, not for anyone

Peer 2 finishes first. Its stack is still allocated, because a joinable thread is not reaped until someone joins it. Malik calls p0.join() on peer 0, who is still working. He blocks — even though peer 2 is already done.

There is no “join whoever finishes next,” in std or in the book’s Pthreads, where Stevens calls that a bug in the specification. join returns what the thread returned, inside a Result, and frees the peer’s memory resources. In join.rs, [0, 1, 2].map(|i| …) turns three numbers into three handles; |i| is a closure that takes i.

Try it: press Peer 2 finishes, then Join peer 0 (you wait), then Join peer 2 (the stack goes).

What the book says

pthread_join blocks until thread tid terminates, stores the pointer returned by the thread routine where thread_return points, and reaps the memory resources held by that thread.

Unlike wait, pthread_join can wait only for a specific thread. There is no way to wait for an arbitrary thread. Stevens argues that this is a bug in the specification.

12.3.6 · detaching threads

The stack that nobody comes back for

A new thread is joinable. Its stack stays until another thread joins it. A detached thread cannot be joined. When it terminates, the system frees the stack itself.

A server that creates a peer per connection should not sit in join. In the book’s C, the peer detaches itself by handing its own ID to pthread_detach. In Rust you detach by dropping the handle, or by never keeping it. The leak is to keep every handle in a Vec (a growable array) and never join one: each finished peer then keeps its stack.

Try it: finish a joinable peer and see the stack remain. Switch to detached, finish, and the stack is gone. Then server leak: press New client a few times.

What the book says

A joinable thread can be reaped and killed by other threads. Its memory resources, such as the stack, are not freed until it is reaped. A detached thread cannot be reaped or killed by other threads. Its resources are freed automatically when it terminates. Threads are created joinable.

Each joinable thread should be reaped or detached, or the process leaks. A high-performance Web server that starts a peer per connection should have that peer detach itself, because the server should not wait for each connection thread. The peer passes its own ID, from pthread_self, to pthread_detach.

12.3.7 · initializing threads

The first caller does the setup

Three peers all need a shared counter’s mutex initialized. If each one tests a ready flag and then calls init, more than one of them can pass the test before any of them sets the flag. Ravi uses std’s Once: call_once(init) runs init the first time and does nothing after. The book’s C does this with pthread_once.

INIT is a static: one value for the whole program, shared by every peer. A caller that arrives while init is still running waits for it to finish. The book’s echo byte counter uses pthread_once in Section 12.5.5.

Try it: press Three threads on Once, then on plain if.

What the book says

pthread_once takes a once_control variable and an init_routine with no arguments. once_control is global or static and is initialized to PTHREAD_ONCE_INIT. The first call with that control invokes init_routine. Later calls with the same control do nothing. The function always returns 0.

It is the tool for dynamically initializing global state that several threads share. The echo_cnt example in Section 12.5.5 initializes its mutex this way.

12.3.8 · a concurrent server based on threads

A private card for each descriptor

Leila’s main thread accepts, then creates a peer. In the book’s C, the obvious bug is passing the address of connfd, one stack slot. The next accept overwrites it before the peer reads it, and two peers then speak on the same descriptor. The book’s fix is a malloc’d int per connection, which the peer must free, and a peer that must detach, or the server leaks.

In Rust, move hands the connection itself to the peer. The peer owns it and closes it when echo returns; main cannot touch it again. Try the C bug in Rust (borrow.rs) and rustc refuses: the closure may outlive the function, but it borrows conn. The handle is dropped at once, so the peer is detached and nothing leaks.

Try it: spawn two clients on move, then on borrow to watch the book’s C race.

What the book says

The thread server has the same shape as the process server: accept, then hand the client to a new flow. Passing the address of connfd races the next accept. Each connected descriptor is stored in its own allocated block, and that pointer is the argument to pthread_create.

The peer detaches so its stack can be reclaimed without an explicit join, frees the block, echoes, and closes. Practice 12.5: deleting the detach or the free can leak. The threads are not reaped, so detach is what returns the stack; the free is what returns the block main allocated.

12.4 · shared variables in threaded programs

Three questions before you call it shared

Threads make sharing look easy, and that is the trap. Noor does not ask “is the name CNT shared?” She asks three questions, in order: what is the memory model, how are instances of this variable mapped onto memory, and how many threads reference each instance.

A variable is shared only when at least one of its instances is referenced by more than one thread. CNT in sharing.rs is static, so there is one instance, and both peers add to it. It is an atomic, and fetch_add adds 1 in one indivisible step.

Try it: press Next question until the three answers line up for CNT.

What the book says

From the programmer’s point of view, an attractive part of threads is how easily they share program variables. Sharing is also tricky. To know whether a variable is shared you work through three questions: the threads memory model, how instances of the variable are mapped to memory, and how many threads reference each of those instances.

The running example is sharing.c: a global ptr, a msgs array on main’s stack, a static cnt inside the thread routine, and a per-peer myid.

12.4.1 · threads memory model

Pockets are private. The house is not.

Each thread owns its registers: the program counter, the condition codes, and the general-purpose registers. Samir’s %rax can hold 7 while the peer’s %rax holds 3. Neither can open the other’s pocket. (%rax is the register rustc uses for the counter in Section 12.5; the book’s listing uses %rdx.)

Virtual memory is always shared. Stacks are usually private in practice, but nothing stops a peer from following a pointer onto main’s stack. The model does not protect them. In Rust that pointer is a reference (&), and thread::scope is the safe way to lend one to a peer.

Try it: tap %rax, then cnt, then try the other pocket.

What the book says

Each thread has its own thread context: TID, stack, stack pointer, program counter, condition codes, and general-purpose register values. Registers are never shared. Each thread shares the rest of the process virtual memory, so virtual memory is always shared.

Separate stacks make automatic locals private in the usual case. They are not protected. A peer that is handed a pointer can read another thread’s stack.

12.4.2 · mapping variables to memory

How many boxes does this name get?

A global, or a local declared static, has exactly one instance, in the read/write data of the process. A local automatic has one instance per thread, on that thread’s stack. The book writes them myid.p0 and myid.p1.

Farah flips the storage class and watches the boxes appear: one cupboard, or a counter on every cook’s station.

Try it: switch global, static local, and automatic.

What the book says

Global variables and local static variables each have a single instance in the read/write data area. Local automatic variables have one instance per thread, living on that thread’s stack.

The book’s notation distinguishes the instances: tid.m for main’s tid, myid.p0 and myid.p1 for the two peers. The mapping is what the next section uses to decide sharing.

12.4.3 · shared variables

Shared means one instance, two readers

The rule is exact. Variable v is shared if and only if one of its instances is referenced by more than one thread. In sharing.rs, CNT and msgs qualify. i, each myid, and ptr do not.

msgs is the surprise. It lives on main’s stack, which sounds private, but ptr = &msgs is a reference to it (a way to read it without copying it), and both peers read through their copies of ptr. thread::scope allows that: it waits for its peers before main’s locals can go away. In the book’s C, ptr is a global, so it is shared too; here move gives each peer its own copy.

Try it: tap a name. The three threads light up only if they touch that instance.

What the book says

A variable v is shared if and only if one of its instances is referenced by more than one thread. Practice 12.6: ptr, cnt, and msgs are shared; i and myid are not.

cnt has a single static instance that both peers increment. msgs is an automatic on main’s stack, and it is still shared because ptr aliases it. Each myid instance is referenced only by its own peer. The solution notes that a static like cnt is shared only with threads that can see that function’s scope.

12.5 · synchronizing threads with semaphores

The counter that will not sit still

Two peers each add 1 to CNT, a million times. The answer should be 2,000,000. The book’s C, with no synchronization, printed BOOM three times on its Linux system: 1445085, 1915220, 1404746.

Safe Rust will not compile the book’s version. With a plain let mut cnt, each thread needs &mut cnt, a writable borrow, and rustc allows only one at a time: error E0499. A static mut compiles only inside unsafe (without it, error E0133), because two threads writing it is a data race, and a data race is undefined behaviour. The unsafe.rs tab shows what rustc did with it: since it may assume no race happens, it turned the whole loop into one addq that adds niters, a million, at once. Our runs printed OK. That is luck, not correctness.

badcnt.rs is the race in safe Rust. CNT is an atomic (a number threads may share), but the thread loads it and then stores 1 more: two steps. Each step is atomic, so there is no data race and no undefined behaviour, yet updates still vanish. That is a race condition, and safe Rust does not prevent those. rustc compiles the loop to the book’s three instructions (badcnt.s): L movq loads cnt into %rax, U incq adds 1, S xchgq stores it back. If the second thread loads before the first stores, both store the same number and a tick disappears. Our runs printed BOOM! cnt=1040940, then 1019173, then 1055369 (Linux on arm64; the count changes every run).

The fix is atomic.rs: fetch_add does load, add, and store as one indivisible step. On x86-64 rustc compiles it to one instruction with a lock prefix, which keeps every other core off that memory until it is done (atomic.s). It printed OK cnt=2000000 every time. thread::scope runs threads that may borrow local values, and waits for all of them before it returns.

Try it: step the correct order, then the lost update, and watch the highlighted line in badcnt.s. Sample runs cycles our three BOOM results. The atomic.s tab is the one-instruction fix.

What the book says

badcnt.c creates two threads that each increment a global cnt niters times, with no synchronization. For niters of 1000000 the book’s runs print BOOM! cnt=1445085, cnt=1915220, and cnt=1404746.

The loop splits into Hi, Li, Ui, Si, and Ti. Li loads cnt into %rdx, Ui increments that register, Si stores it back. (Figure 12.17 prints Ui and Si with %eax; the text says both work on %rdx.) Head and tail touch only local stack data. Figure 12.18(a) finishes at cnt = 2. Figure 12.18(b) has both threads load 0, and both store 1. In general there is no way to predict whether the operating system will choose a correct ordering.

12.5.1 · progress graphs

Right or up. Never diagonal.

Yuki draws one axis per thread. A point is how far each thread has got. A legal step is right (thread 1 finishes an instruction) or up (thread 2 does). Two instructions never complete at the same instant, so there is no diagonal. Threads never run backward.

The critical section for cnt is L, U, S: in rustc’s badcnt.s, the movq, incq and xchgq lines. Where the two critical sections overlap is the unsafe region. The states on the perimeter are still safe. A trajectory that only skirts the region updates the counter. A trajectory that touches the interior loses an update.

Try it: play the safe path, then the unsafe path. The coral square is the unsafe region.

What the book says

A progress graph models n concurrent threads as a trajectory in an n-dimensional space. Axis k is the progress of thread k. The origin is the state where nobody has completed an instruction. Legal transitions move right or up, to an adjacent point. Diagonal, down, and left are illegal.

Instructions Li, Ui, and Si are the critical section for cnt. Their intersection is the unsafe region. It abuts, but does not include, the perimeter states. A trajectory that skirts the region is safe and updates the counter. A trajectory that touches the interior is unsafe. Any concurrent program that shares global data needs its threads forced onto safe trajectories.

12.5.2 · semaphores

A nonnegative integer with two moves

Dijkstra’s semaphore is a global integer that threads may touch only with P and V. P: if it is nonzero, decrement and return; if it is zero, sleep until a V wakes you, then decrement. V: add 1, and if anyone is asleep in P, wake exactly one of them. That thread finishes its P by decrementing.

The names are Dutch: proberen, to test, and verhogen, to increment. The invariant is s ≥ 0. A binary semaphore is only 0 or 1. A counting semaphore can be larger — here it starts at 2, so two P’s succeed before anyone sleeps.

std has no semaphore. (A nightly-only one was deprecated in Rust 1.7 and then removed.) Rust code reaches for what std does offer: a Mutex to keep others out, a Condvar to sleep until something changes, atomics for a single shared number, and channels to hand work over. This page builds the book’s semaphore from the first two (the semaphore.rs tab). The Mutex guards the count, and the Condvar is where P sleeps until V wakes it. wait can return with no V at all, so P tests the count in a while loop. One difference from the book: when V wakes a sleeper, the count is not saved for that thread. The woken thread has to lock the Mutex again, and a thread just arriving at P can get there first and take the count, so the woken one finds 0 and sleeps again. Dijkstra’s V hands the count straight to the thread it wakes. impl Sem holds its methods, and &self means a method that borrows the semaphore it is called on.

Try it: press P until a thread sleeps, then V to wake exactly one. Flip to binary and the start value is 1.

What the book says

A semaphore s is a global variable with a nonnegative integer value, manipulated only by P and V. If s is nonzero, P decrements s and returns immediately. If s is zero, P suspends the thread until a V makes s nonzero and restarts it; the restarted P then decrements s. V increments s by 1. If any threads are blocked in P, V restarts exactly one of them, which then completes its P by decrementing s.

The names come from the Dutch proberen (to test) and verhogen (to increment). The book’s wrappers are P for sem_wait and V for sem_post. sem_init, with 0 as its middle argument, initializes a semaphore shared by the threads of this process. A binary semaphore is 0 or 1. The invariant s is never negative.

12.5.3 · semaphores for mutual exclusion

A moat around the unsafe square

A mutex is a binary semaphore that starts at 1, used so only one thread is inside the critical section. P locks. V unlocks. The invariant s ≥ 0 draws a forbidden region that wraps the unsafe square. No legal path can step in.

Rust’s Mutex holds the data it guards. CNT.lock() waits for the lock and returns a guard, the only way to reach the number; *cnt means the number inside it, and dropping the guard unlocks. lock() returns a Result: it is an Err if another thread panicked while holding the lock (the lock is then “poisoned”), so unwrap() is there. goodcnt.rs locks around the increment. The book’s C version printed OK cnt=2000000, and so did each of our runs of the Rust one. bad.rs is the plain-variable badcnt: it compiles only with unsafe, and the race is then undefined behaviour.

Try it: walk no mutex into the coral square. Then with mutex — the path is pushed outside, and cnt ends at 2.

What the book says

Mutual exclusion means each thread has exclusive access to the shared variable while it executes its critical section. A binary semaphore used this way is a mutex, initially 1. P is the lock, V is the unlock. The semaphore operations are indivisible, so the test-and-decrement cannot interleave with another P or V.

On the progress graph the invariant s ≥ 0 carves a forbidden region that encloses the unsafe region. Trajectories may not enter it. goodcnt, with the mutex around the increment and niters of 1000000, prints OK cnt=2000000.

12.5.4 · scheduling shared resources

Empty plates, and a catalog

A mutex stops two cooks from grabbing the same plate. It does not wake a cook who is waiting for a plate to appear. The book’s bounded buffer uses three semaphores: slots starts at n, items starts at 0, and mutex starts at 1. Rust code builds the same thing from what std offers: one Mutex around the queue, and two condition variables, Condvars, places to sleep until something changes. Insert locks, sleeps on not_full while every slot is used, pushes, and wakes one sleeper on not_empty. Remove is the mirror.

In sbuf.rs the queue is a VecDeque: push at the back, pop at the front. wait(buf) hands the lock back while it sleeps and takes it again before it returns. It can also wake for no reason, so the test is a while, not an if. pop_front gives an Option, Some(item) or None, and unwrap takes the item. <T> lets the buffer hold any kind of item. std also has this buffer ready-made: mpsc::sync_channel(4) is a bounded channel whose send sleeps while it is full (channel.rs).

The same section’s other pattern is readers-writers. Many readers may look at once. A writer needs the object alone. The first solution favours readers: a waiting writer does not stop a new reader. Hold that open and the writer starves. readers.rs builds the book’s version by hand. W has to be our Sem, not a Mutex: one reader takes it and another gives it back, and a MutexGuard is not Send, so it can never be unlocked on another thread. std’s ready-made readers-writers lock is RwLock (rwlock.rs): read() lets many in, write() waits to be alone. Which side it favours is not promised: std says it depends on the operating system.

Try it: fill the window, then remove one. Switch to readers and keep sending readers while a writer waits.

What the book says

sbuf is a bounded FIFO: buf, n, front, rear, plus mutex, slots, and items. slots is initialized to n and items to 0. Empty means front == rear. The first item is buf[(front+1)%n]. Insert and remove both hold mutex around the index update. Practice 12.9: with n > 1 even one producer and one consumer need the mutex, because the index updates race. With n = 1 the mutex can be omitted, including for several producers and several consumers, because a full buffer and an empty buffer each block one side.

The first readers-writers problem favours readers. readcnt starts at 0; mutex and w start at 1. Only the first reader locks w; only the last reader unlocks it. A stream of readers can leave a writer blocked forever — starvation. The second problem favours writers. Either correct solution can starve someone. Practice 12.10: if V wakes the most recent waiter, a departing writer may restart another writer instead of a waiting reader.

12.6 · using threads for parallelism

Same sum, three places to put it

A parallel program is a concurrent program that actually runs on more than one processor. Idris sums 0 … 231−1. If every add locks a global gsum, the book’s C took 68.00 seconds with one thread on its four-core machine, and 719.00 with four. The lock costs more than the add.

Give each thread its own slot of psum, lent as &mut u64 (a writable borrow no other thread can have), and the lock leaves the hot loop: the book measured 7.26, 3.64, 1.91 seconds. Add into a stack local and store once: 1.06, 0.54, 0.28. Past four threads the four cores are already busy, and extra threads just context-switch. Speedup is T1/Tp. Efficiency is that speedup divided by the number of cores.

Every number here is the book’s measurement of its C version; our Rust measurement is pending. The Rust programs are written and wait for a real x86-64 Linux machine. One Rust surprise came out of writing them: built with rustc -C opt-level=3, array.rs and local.rs have no loop left at all. LLVM, rustc’s code generator, replaces the sum of a range with a formula. So the benchmarks pass each i through std::hint::black_box, an identity function the compiler is asked to assume could do anything, and the loop stays.

Try it: switch the recipe, then tap a thread count. The seconds are the book’s measurements of its C programs.

What the book says

Parallel programs are the concurrent programs that run on multiple processors. psum-mutex protects gsum += i with P and V. On n = 2^31 and four cores the times are 68.00, 432.00, 719.00, 552.00, and 599.00 seconds for 1, 2, 4, 8, and 16 threads. Synchronization overhead is expensive and should be avoided if possible.

Absolute speedup uses a sequential T1; relative speedup uses the parallel program on one core. After t > 4, time ticks up from context switches. Weak scaling grows the problem with the machine; strong scaling keeps the problem fixed. The psum numbers are strong scaling.

12.7 · other concurrency issues

Three failures sequential code never has

Once threads share data, new bugs show up. Naomi sorts them into three piles the rest of the section takes apart: a function that is not safe to call twice at once, a program that is correct only if one thread wins a race, and a pair of locks that wait for each other forever.

These are not only thread bugs. Any concurrent flows that share a resource can hit the same three. Rust’s compiler catches part of the first two: in safe code it rejects any program where two threads could access the same memory at once, at least one of them writing, without synchronization (a data race). It does not check timing or lock order, so wrong answers from a badly ordered program, and deadlocks, still compile.

Try it: run each pile. The picture shows the failure in one step. The subsections below take them apart.

What the book says

Synchronizing shared data is harder than mutual exclusion and producer-consumer. The section is a survey of issues that do not arise in ordinary sequential programs. The discussion is in terms of threads, and the same issues show up when any concurrent flows share resources.

The three topics that follow are thread safety, races, and deadlocks. A thread-safe function always produces the correct result when called repeatedly from multiple concurrent threads. A race is a correctness dependency on one flow reaching a point before another. A deadlock is a flow waiting for an event that will never happen.

12.7.1 · thread safety

Four ways a function lies under threads

A function is thread-safe if repeated concurrent calls still get the right answer. The book names four overlapping classes of functions that are not. Rust’s compiler checks two marker traits that catch much of this. A type is Send if a value of it may move to another thread, and Sync if it may be shared: T is Sync exactly when &T is Send. rustc works both out from a type’s fields. thread::spawn accepts only a closure that is Send, and every static that is not mut must be Sync (sendsync.rs quotes the errors).

Class 1 forgets to protect a shared variable. In Rust that does not compile: a static Cell (a value you may change through a shared reference, with no lock) is not Sync, and a static mut needs unsafe. Wrap it in a Mutex, or use an atomic, and callers do not change. Class 2 keeps state across calls, like rand and its seed. A Mutex makes it compile with no data race, but the threads still share one sequence. The only fix is the book’s: rewrite it so the caller passes the state.

Class 3 returns a pointer to a static buffer, like ctime. Safe Rust cannot hand out a writable reference into one shared static, so Rust functions return an owned String: each caller gets its own. Lock-and-copy still works. Class 4 calls an unsafe function. If that callee is class 1 or 3, a mutex at the call can save you; if it is class 2, you have to rewrite the callee. In Rust a function whose rules the caller must keep is declared unsafe fn, and keeping those rules is your job. std has two of this kind: env::set_var and env::remove_var, because outside Windows (Linux included) other threads may read the environment at the same moment. (The 2024 edition makes you write unsafe at the call.)

Try it: tap a class. The caption says what goes wrong and what rustc does about it; fix.rs shows the repair.

What the book says

A function is thread-safe if and only if it always produces correct results when called repeatedly from multiple concurrent threads. Class 1 does not protect shared variables. P and V fix it without changing callers, at the cost of synchronization. Class 2 keeps state across invocations. rand is the example. The fix is a rewrite so the caller passes the state; every call site changes.

Class 3 returns a pointer to a static variable. ctime and gethostbyname are the examples. One thread’s result is overwritten by the next. The fixes are a rewrite that stores into caller memory, or lock-and-copy: lock a mutex, call the function, copy the result to private memory, unlock. A wrapper hides that from the rest of the program. Class 4 calls an unsafe function. If the callee is class 2, the caller cannot be made safe without rewriting the callee. If the callee is class 1 or 3, protecting the call site and the resulting shared data with a mutex is enough. Figure 12.38 is ctime_ts, the lock-and-copy wrapper.

12.7.2 · reentrancy

Thread-safe, and touching nothing shared

Reentrant and thread-safe are not synonyms. Reentrant functions are the thread-safe ones that do not reference any shared data. They need no lock, so they are usually faster. rand_r takes the seed pointer from the caller. That is how you turn a class 2 function into a safe one: make it reentrant. In rand_r.rs the seed arrives as &mut u32, borrowed from the caller. wrapping_mul and wrapping_add let the number wrap around on overflow, as C’s unsigned arithmetic does.

If every argument is passed by value and every datum is a local automatic, the function is explicitly reentrant. If it takes pointers, it is only implicitly reentrant — safe when the caller passes pointers to nonshared data. In the book’s C, hand rand_r one shared seed and the two threads scramble it again. Safe Rust won’t let two threads hold &mut to one seed at once: a &mut borrow is exclusive, so the shared-seed version fails with error E0499. So in Rust the caller’s slip that makes rand_r only implicitly reentrant becomes a compile error, not a scrambled seed.

Try it: run rand, locked, rand_r private, and shared seed.

What the book says

Reentrant functions do not reference any shared data when called by multiple threads. They are a proper subset of the thread-safe functions. They are typically more efficient than non-reentrant thread-safe functions because they need no synchronization. The only way to make a class 2 function thread-safe is to rewrite it so it is reentrant. rand_r replaces the static seed with a pointer argument.

A function whose arguments are all passed by value, and whose data references are all local automatics, is explicitly reentrant. Allow pointers and it is implicitly reentrant: reentrant only if callers pass pointers to nonshared data. The book uses reentrant for both. Practice 12.12: rand_r is implicitly reentrant because a caller can pass a pointer to shared state.

12.7.4 · races

Four nametags, one sticky note

A race is when the program is correct only if one thread reaches point x before another reaches point y. In the book’s C, Ada passes the address of one loop variable i to four peers. She assumes each peer reads its own number before the loop adds 1 to i. The kernel promises no such trajectory. The book’s run printed 1, 3, 2, 3.

The book’s fix gives each peer its own malloc’d int, which the peer frees; that run printed 0, 1, 2, 3. In Rust, the borrow of i does not compile (race.rs: the closure may outlive the function). move copies i into each peer instead, so every peer has its own, and there is nothing to free.

Try it: spawn on race, then on norace. Delay peer 0 to make the book’s shared i even later.

What the book says

A race occurs when correctness depends on one thread reaching point x in its control flow before another thread reaches point y. Threaded programs must work for any feasible trajectory. race.c passes the address of i to four peers. The race is main’s next increment of i against the peer reading i through that pointer into myid. The book’s run printed Hello from thread 1, 3, 2, and 3.

12.7.5 · deadlocks

Each holds the key the other needs

Nadia locks S then T. Omar locks T then S. Some trajectories slip through. Some reach state d, where each holds one mutex and waits for an unlock that cannot happen. The overlapping forbidden regions are the deadlock region. A trajectory can enter. It cannot leave.

The repair is a total order. Both lock S then T, and release in reverse. The forbidden rectangles no longer overlap. A different trap, Practice 12.15, needs no crossed order: semaphore S starts at 1, T starts at 0, and both threads do P on S, V on S, then P on T. Every trajectory dies on T. Start T at 1 and it is gone. Rust drops local variables, lock guards included, in the reverse of the order they were declared, which is the release order the rule wants.

Deadlock is possible in safe Rust. cross.rs uses only std’s Mutex, with no unsafe, and rustc compiles it without a warning: the compiler rules out data races, not waiting forever. Our run of it, with a 50 ms sleep between each thread’s two locks so both take their first one, printed nothing and hung until timeout killed it after 5 seconds. Locking a Mutex twice on one thread is a smaller trap: std leaves the result unspecified except that the second call never returns, and ours hung too.

Try it: walk into d. Then lock order. Then T = 0.

What the book says

Opposite lock order makes the forbidden regions overlap. The overlap contains a deadlock state d and a deadlock region. Trajectories can enter deadlock regions, but they can never leave. A run of lucky schedules can hide it; the next machine, or the next schedule, traps you.

Mutex lock ordering rule: given a total ordering of all mutexes, a program is deadlock-free if each thread acquires its mutexes in order and releases them in reverse order. Practice 12.15 is a different trap. With s = 1 and t = 0, both threads doing P(s) V(s) P(t) V(t) always deadlock, because every feasible trajectory is eventually trapped. Initializing t to 1 removes it. Progress graphs are a uniprocessor picture; a multiprocessor can sit in states no trajectory names. The advice in the book stays: synchronize shared variables anyway.

12.8 · summary

Which machine fits this job?

The chapter’s concurrent program is a set of logical flows that overlap in time, built three ways: processes, I/O multiplexing, and threads. Semaphores then do two jobs — mutual exclusion, and scheduling of shared resources such as a bounded buffer or a readers-writers object. The prethreaded server uses both. Rust’s std has no semaphore, so on this page those jobs go to a Mutex, Condvars, atomics and channels.

Functions the threads call must be thread-safe. Reentrant functions are the subset that touch no shared data. Races come from assuming a schedule. Deadlock is waiting for an event that will never happen. In safe code, rustc’s borrow rules together with Send and Sync rule out data races; races of timing, and deadlocks, are still yours to prevent.

Try it: tap a job. The picture names the approach the chapter would reach for, and highlights that sketch.

What the book says

Processes are scheduled by the kernel and need explicit IPC to share data. Event-driven programs build their own flows as state machines and schedule them with I/O multiplexing; sharing is easy because there is one address space. Threads are the hybrid: kernel-scheduled, and sharing the process address space.

P and V provide mutual exclusion and also schedule resources such as the bounded buffers in producer-consumer systems and the shared objects in readers-writers systems. A prethreaded echo server uses both. Functions called by threads must be thread-safe. The book identifies four classes of thread-unsafe functions. Reentrant functions are the proper subset of thread-safe functions that do not access any shared data, and they often need no synchronization. Races come from incorrect assumptions about scheduling. Deadlocks come from waiting for an event that will never happen.

Words to know

The chapter’s words, in plain language.

concurrent
Logical flows overlap in time. They might take turns on one core or run on several.
parallel
A concurrent program that runs on more than one processor so the job finishes sooner.
process server
The parent accepts and forks a child per client. Each side closes the descriptors it does not need.
IPC
The explicit channel processes use to share state, because their address spaces are separate.
select
Sleep until any descriptor in a set would not block on a 1-byte read.
ready set
What select writes back. Copy the permanent read set first, because select overwrites it.
state machine
The event-driven model of one client: the main loop moves it from state to state as data arrives.
granularity
How many instructions one logical flow runs before another can proceed. A whole line is coarse.
thread
A kernel-scheduled flow inside one process. Own stack, TID, and registers. Shared virtual memory.
peer
Any thread in the process. There is no parent-child tree. Any thread that holds a peer’s handle can join it.
Pthreads
The book’s 1995 Posix C thread library, about 60 calls. Rust’s std::thread sits on top of it on Linux.
closure
A small unnamed function, written |args| body. move makes it own the values it uses, so it can travel to another thread.
JoinHandle
What thread::spawn returns. join() waits for that thread; dropping the handle detaches it.
joinable / detached
A joinable thread’s stack waits for a join. A detached thread’s stack is freed when it returns.
Once
call_once runs an initializer the first time and skips it after that. The book’s C does this with pthread_once.
shared variable
Some instance of it is referenced by more than one thread.
critical section
The instructions that touch a shared variable and must not interleave with another thread’s.
progress graph
One axis per thread. Legal steps are right or up. Unsafe and forbidden regions live inside.
P / V
Dijkstra’s proberen and verhogen. P waits while the semaphore is 0, then decrements. V increments and wakes one waiter. std has no semaphore; Sem on this page builds one.
mutex
A lock for mutual exclusion; in the book, a binary semaphore that starts at 1. Rust’s Mutex holds the data too: lock() gives a guard, and dropping the guard unlocks.
atomic
A number threads can share safely, such as AtomicU64. fetch_add does load, add, store as one indivisible step; on x86-64 rustc makes it one lock-prefixed instruction.
data race
Two threads touch the same memory at once, at least one writes, and at least one of the accesses is unsynchronized (not atomic, not under a lock). Undefined behaviour in Rust, so safe Rust rejects it.
Send / Sync
Send: a value may move to another thread. Sync: it may be shared between threads; precisely, T is Sync exactly when &T is Send. rustc works both out; thread::spawn needs Send, and every static that is not mut must be Sync.
Condvar
A place to sleep until another thread changes something. wait unlocks the Mutex while it sleeps and can wake for no reason, so test in a loop.
unsafe
A Rust block where the compiler cannot check the rules, so the programmer must. Reading or writing a static mut, or calling an unsafe fn, needs one. A data race inside one is undefined behaviour.
sbuf
A bounded FIFO. The book’s has a mutex and two semaphores, slots and items; this page’s has a Mutex and two Condvars. std’s sync_channel(n) is a ready-made one.
readers-writers
Many readers may share an object. A writer needs it alone. First and second solutions pick who can starve.
prethreading
Create the worker threads once. The main thread queues connected descriptors for them.
speedup / efficiency
Sp = T1/Tp. Ep = Sp/p, usually written as a percent of the cores you actually used.
thread-safe
Concurrent calls still get the correct result. Four classes of functions fail this.
lock-and-copy
Lock, call a class 3 function, copy the static result into private memory, unlock.
reentrant
Thread-safe and touching no shared data. Explicit if it uses only by-value arguments and locals. Implicit if pointers must aim at private data.
race
The program is right only if one flow beats another to a point. The kernel will not promise that. Safe Rust can still have races; it only rules out data races.
deadlock
Flows wait for an event that cannot happen. On the progress graph, you can enter that region and you cannot leave. Safe Rust compiles it.
