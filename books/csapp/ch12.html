Concurrent Programming

One slow visitor should not freeze the whole shop. The book shows three ways to keep several jobs in the air at once — and how they trip over each other when they share a counter.

“A concurrent program consists of a collection of logical flows that overlap in time.”

New here? Read the short story, then press the buttons on the picture. You cannot break it. The book’s exact names — P, V, sbuf, select — live under “What the book says.”

12.1 · processes

A new clerk for every customer

Priya runs a tiny post office. She stands at the front desk and waits. When Omar walks in, she does not serve him herself. She forks a helper — a child who looks just like her — and that child walks Omar to a window. Priya goes back to the door.

The helper gets a copy of every key Priya was holding. So Priya must hang up the key to Omar’s window, and the helper must hang up the key to the front door. Leave a key on the hook and the window never really closes.

Try it: Step through Figures 12.1–12.4. Then flip to “forget Close” and watch the file-table count stick.

What the book says

Figure 12.5 is echoserverp.c: the parent Accepts, Forks a child, and the child calls echo from Figure 11.22. The listening descriptor starts as 3; the first connected descriptor is 4, the second is 5. A SIGCHLD handler loops on waitpid(-1, 0, WNOHANG) because Linux signals are not queued.

Parent and child must each Close their copy of connfd (lines 33 and 30). “Otherwise, the file table entry for connected descriptor 4 will never be released, and the resulting memory leak will eventually consume the available memory and crash the system.” The connection dies only when the file-table reference count hits zero.

Separate virtual address spaces are the point: “It is impossible for one process to accidentally overwrite the virtual memory of another process.” Sharing then needs explicit IPC. Unix IPC (pipes, FIFOs, System V shared memory and semaphores) is out of scope; the book points at Kerrisk.

Priya listens on descriptor 3. Each customer gets a child and its own connected descriptor.
12.2 · I/O multiplexing

One pair of eyes, many doors

Mei sits at the school desk. The street door and the keyboard both want her. If she waits only at the door, typed notes pile up. If she waits only on the keyboard, visitors stand in the rain. She asks the kernel: “Wake me when any of these doors has a letter.” That ask is select.

The catch: if she then walks a visitor all the way home, the keyboard goes silent until that walk ends. A finer loop reads one line and comes straight back to the desk.

Try it: Flip between “until EOF” and “one line.” Type at stdin while a client is talking. See who gets ignored.

What the book says

Figure 12.6 puts STDIN_FILENO (0) and listenfd (3) in a read_set, then Select(listenfd+1, &ready_set, NULL, NULL, NULL). “A descriptor k is ready for reading if and only if a request to read 1 byte from that descriptor would not block.” Because select overwrites the set, the book copies ready_set = read_set every time.

That server still calls echo until EOF, so a stdin command waits. Figure 12.8 is the event-driven fix: a pool of clientfd[FD_SETSIZE], init_pool, add_client, check_clients. Each flow is a state machine (Figure 12.7) that reads one text line per ready descriptor. byte_cnt counts every received byte.

One process means shared memory and gdb. No process context switch. The cost: about three times the code of Figure 12.5, and a client that sends a partial line can stall every other flow. Event-driven designs also cannot fully use multi-core chips. An aside names Node.js, nginx, and Tornado as modern examples.

select blocks until stdin or the listening descriptor is ready. Then Mei looks at the ready set.
12.3 · threads

Peer cooks in one kitchen

A thread is a cook in someone else’s kitchen. The kernel still picks who stirs, like a process. But every cook sees the same fridge, the same counters, the same open files. That is the hybrid: kernel-scheduled, one address space.

Diego’s first recipe is tiny: the main cook creates a peer, the peer prints hello, main joins and exits. The server recipe is the same shape as the process server, except the peer must detach itself and the connected descriptor cannot be a pointer into main’s stack.

Try it: Play hello.c, then switch to the echo server and spawn two peers. Watch the malloc block travel.

What the book says

A thread has its own TID, stack, stack pointer, program counter, registers, and condition codes. Peers share the process’s text, data, heap, libraries, and open files. They form a pool, not a parent-child tree: any thread can wait for or cancel any peer. Context switches are cheaper than process switches.

Posix threads (Pthreads), 1995, define about 60 functions. Figure 12.13 is hello.c: Pthread_create, Pthread_join, then exit. A thread ends by returning, by pthread_exit (main waits for peers), by exit (kills the process), or by pthread_cancel. pthread_join waits for one specific TID — Stevens calls that a specification bug. Detached threads (default is joinable) free their stacks themselves; a server peer should Pthread_detach(pthread_self()).

Figure 12.14 echoservert.c mallocs each connfd so the next Accept cannot race the peer’s dereference. Passing &connfd is the race of Section 12.7.4. The peer detaches, Frees the block, then echos.

Main creates a peer. They share one process and take turns on the CPU.
12.4 · shared variables

Which cubbies do both cooks see?

Noor draws a map of the kitchen. Registers are each cook’s own pockets — nobody else can reach in. The rest of the house is one house. A name on the wall (global) is one box. A name written inside a recipe without static is a box on that cook’s own counter. Write static inside the recipe and there is still only one box, in the shared cupboard.

The trick: a counter box can still be shared if someone else holds a pointer to it. Noor’s msgs lives on main’s stack, but the global ptr points at it, so both peers read it.

Try it: Tap a variable. The book’s table lights up: who touches that instance?

What the book says

Figure 12.15 sharing.c: global char **ptr, main’s msgs[N] with “Hello from foo” and “Hello from bar”, two peers, local myid, and static int cnt = 0. “Thus, registers are never shared, whereas virtual memory is always shared.” Stacks are usually private, but not protected — line 26 reads main’s stack through ptr.

Mapping: one instance of each global and each local static, in the read/write area. One instance of each local automatic, per thread stack — written tid.m, myid.p0, myid.p1. “We say that a variable v is shared if and only if one of its instances is referenced by more than one thread.”

Practice 12.6: ptr, cnt, and msgs are shared; i and myid are not. cnt has one instance that both peers increment.

A variable is shared only when more than one thread touches the same instance.
12.5.1–12.5.3 · semaphores

Two chalk hands, one number

Aisha and Tomas share a chalkboard that starts at 0. Each should add 1, a million times. The answer should be two million. On the book’s Linux box the board says 1445085, then 1915220, then 1404746. Different every run. That is badcnt.c.

Each “add 1” is really load, plus, store. If Tomas loads before Aisha stores, both write 1 and a tick vanishes. The picture of every interleaving is a progress graph. The square where both are mid-update is unsafe. A semaphore named mutex — P before the add, V after — builds a forbidden moat around that square so no legal path can step in.

Try it: Play the unsafe path and watch cnt stick at 1. Then switch on the mutex and walk the same idea safely.

What the book says

Figure 12.16: two threads, each does cnt++ niters times. Figure 12.17 splits the loop into Hi Li Ui Si Ti. Figure 12.18(a) ends at cnt = 2; 12.18(b) both store 1. “In general, there is no way for you to predict whether the operating system will choose a correct ordering for your threads.”

Figure 12.19–12.21: legal moves are right or up, never diagonal. (L, U, S) is the critical section. Their intersection is the unsafe region (perimeter states are safe). Dijkstra’s semaphore s is a nonnegative integer touched only by P and V. “The names P and V come from the Dutch words proberen (to test) and verhogen (to increment).”

The book’s wrappers: sem_wait is P, sem_post is V; sem_init(sem, 0, value). A binary semaphore used this way is a mutex. Figure 12.22: the invariant s ≥ 0 carves a forbidden region that encloses the unsafe region. goodcnt with niters = 1000000 prints OK cnt=2000000.

Figure 12.18–12.22 · badcnt
Each axis is one thread. A path that cuts the coral square loses an increment.
12.5.4 · producer-consumer

A window with n plates

The bakery has a window that holds four plates. Yuki bakes and sets a plate in the next empty slot. Soren takes a plate from the front. If the window is full, Yuki waits. If it is empty, Soren waits. A lock on the window stops them from moving the same plate at once — but the lock alone cannot wake a waiter. That is what the extra counters are for.

The book’s package is sbuf: one mutex, a slots count, an items count. Insert is P(slots), P(mutex), write, V(mutex), V(items). Remove is the mirror.

Try it: Insert until the window is full, then try one more. Remove to wake the baker. Then watch a prethreaded server use the same buffer for descriptors.

What the book says

Figure 12.24 sbuf_t: buf, n, front, rear, plus mutex, slots, items. Empty when front == rear. First item is buf[(front+1)%n]; last is buf[rear%n]. Figure 12.25: Sem_init(&sp->slots, 0, n) and items starts at 0. Insert and remove both lock mutex around the index update.

Practice 12.9: with n > 1 even one producer and one consumer need the mutex (the index updates race). With n = 1 the mutex can be skipped — including when there are several producers and several consumers. The book’s prethreaded server (Figure 12.27–12.28) uses this as a descriptor queue: NTHREADS 4, SBUFSIZE 16. The main thread sbuf_inserts connfd; workers sbuf_remove and call echo_cnt.

echo_cnt (Figure 12.29) protects a static byte_cnt with its own mutex, initialized once via Pthread_once. Other sync tools named in an aside: Java monitors, and Pthreads mutex plus condition variables.

Figure 12.24–12.28 · sbuf
slots counts empty plates. items counts cakes. mutex is the lock on the window itself.
12.5.4 · readers-writers

Many may look; only one may ink

The library catalog is one book. Any number of people may read a page at once. The moment someone wants to write a new seat number — the book’s airline picture — they need the catalog alone. Readers share. Writers exclude everyone.

The first readers-writers rule is kind to readers: a waiting writer does not stop a new reader from walking in. Hold that door open long enough and the writer never sits down. That wait-forever is starvation.

Try it: Send two readers in. The writer blocks. Keep adding readers and the writer stays outside. Drain them, and the writer finally inks the page.

What the book says

Figure 12.26 solves the first readers-writers problem (favours readers). readcnt starts at 0; mutex and w start at 1. A writer does P(&w) … V(&w). Only the first reader locks w; only the last reader unlocks it. Other readers ignore w while readcnt > 0.

The second problem favours writers: once a writer is ready, it writes as soon as possible, and a later reader waits. Either correct solution can starve someone. In Figure 12.26 a stream of readers can leave a writer blocked forever. Practice 12.10 notes the priority is weak: a departing writer might restart another writer instead of a waiting reader.

The book’s everyday pictures: an airline reservation system (many inspect seats; a booking needs exclusive access) and a multithreaded caching Web proxy (many fetch; a cache fill is exclusive).

The first reader locks w. Extra readers just bump readcnt. A writer needs w alone.
12.6 · parallelism

Four cores, one sum, three recipes

Amara wants the sum 0 + 1 + … + (231 − 1). She splits the range across cooks. Recipe 1: every add writes the same global gsum behind a mutex. On the book’s four-core box, one thread takes 68 seconds. Two threads take 432. Four take 719. The lock costs more than the add.

Recipe 2: each cook writes psum[myid] — no lock. 7.26 s, then 3.64, then 1.91. Recipe 3: add into a local sum, store once. 1.06 s, 0.54 s, 0.28 s. After four threads the curve flattens: only four cores, and extra threads just swap.

Try it: Switch recipes and thread counts. The bars are the book’s seconds, not a guess.

What the book says

Parallel programs are the concurrent programs that actually run on multiple processors (Figure 12.30). psum-mutex (Figure 12.31 and Figure 12.32) protects gsum += i with P and V. On n = 231 and four cores the times are 68, 432, 719, 552, 599 seconds for 1, 2, 4, 8, 16 threads. “Synchronization overhead is expensive and should be avoided if possible.”

psum-array writes psum[myid]: 7.26, 3.64, 1.91, 1.85, 1.84 s. psum-local (Figure 12.34) uses a stack sum, then one store: 1.06, 0.54, 0.28, 0.29, 0.30 s (Figure 12.35).

Figure 12.36 (strong / relative speedup, cores p = 1, 2, 4, 4, 4): Sp = 1, 1.9, 3.8, 3.7, 3.5 and Ep = 100%, 98%, 95%, 91%, 88%. Absolute speedup uses a sequential T1; relative uses the parallel code on one core. Weak scaling grows the problem with the machine. After t > 4, time ticks up from context switches — so they often run one thread per core.

Same sum, three ways to share. The seconds are from the book’s four-core run.
12.7.4 · races

Four nametags, one sticky note

Kenji writes 0, 1, 2, 3 on a single sticky note, and each time he creates a peer he points at that same note. He thinks each peer will read “its” number. The kernel does not promise that. On the book’s machine the four hellos come back 1, 3, 2, 3 — two of them stole the same name, and 0 never appeared.

The fix is the same one the thread server used: give each peer its own little heap card, then let the peer free it. Correctness must not depend on who reaches the note first.

Try it: Run the race. Then switch to norace and spawn again. You can also delay a peer so it reads late on purpose.

What the book says

“A race occurs when the correctness of a program depends on one thread reaching point x in its control flow before another thread reaches point y.” Figure 12.42 race.c passes &i to four peers. The race is the next i++ versus myid = *((int *)vargp). Their run printed Hello from thread 1, 3, 2, 3.

Figure 12.43 norace.c does ptr = Malloc(sizeof(int)); *ptr = i; and the peer Frees the block. That run printed 0, 1, 2, 3. Freeing in the main thread right after Pthread_create would be another race (Practice 12.13). Practice 12.14’s no-malloc alternative is Pthread_create(..., (void *)i) and myid = (int)vargp — the caveat is pointer width versus int, not an id array.

Nearby in 12.7: a function is thread-safe if concurrent calls always get the right answer. Four unsafe classes; rand / ctime / gethostbyname are the working examples. Reentrant functions share no data — a proper subset of thread-safe (Figure 12.39). Linux *_r names (rand_r, ctime_r) are the usual repair.

Main passes &i. If a peer is late, it copies someone else’s id.
12.7.5 · deadlock

Two doors, each holding the other’s key

Lucia needs lock s then lock t. Omar needs lock t then lock s. Sometimes they slip past each other. Sometimes each holds one key and waits for a V that will never come. The progress graph grows a deadlock region: once you step in, every legal move is a wall. You can enter. You cannot leave.

The book’s repair is a total order. Both people take s first, then t, and put them back in reverse. The forbidden rectangles no longer overlap, and the trap disappears.

Try it: Walk the unlucky path into state d. Reset. Switch to lock order and the same two people cannot get stuck.

What the book says

Figure 12.44: two mutexes, opposite P order. Overlapping forbidden regions create deadlock state d and a deadlock region. “Trajectories can enter deadlock regions, but they can never leave.” A thousand lucky runs can hide it; the next machine, or the next schedule, traps you.

“Mutex lock ordering rule: Given a total ordering of all mutexes, a program is deadlock-free if each thread acquires its mutexes in order and releases them in reverse order.” Figure 12.45 locks s then t in both threads.

Practice 12.15 is a different trap: s = 1, t = 0 and both threads do P(s) V(s) P(t) V(t). They always deadlock on t. Raising the initial t to 1 removes it. Progress graphs, the book warns, are a uniprocessor picture; multiprocessor memory can sit in states no trajectory names. The advice stays: synchronize shared variables anyway.

Figure 12.44–12.45 · two mutexes
Opposite lock order can trap a path. Same order, reverse unlock, and the trap is gone.

The seesaws from this chapter

Each row is a choice the book actually makes you face. Homework and the bibliographic notes stay in the paper book.

Processes

Kernel-scheduled. Separate address spaces. IPC to share. Higher overhead.

vs

Threads

Kernel-scheduled. One address space. Easy sharing, easy races.

I/O multiplexing

You schedule the state machines. One process, gdb, no fork. Partial lines hurt.

vs

A child or a peer per client

The kernel isolates a stuck client. Creating a flow each time costs.

Parent keeps connfd

File-table refcount never hits 0. The leak can eat the machine.

vs

Parent Close(connfd)

Child still holds a copy. The connection can finish.

badcnt / psum-mutex

Every update takes P and V. Wrong interleavings, or 719 s.

vs

goodcnt / psum-local

Mutex around the real critical section — or don’t share the hot variable.

First readers-writers

Readers never queue behind a waiting writer. Writers can starve.

vs

Second readers-writers

A ready writer goes next. Readers can starve.

Pass &i

A race. The book printed 1, 3, 2, 3.

vs

Opposite lock order

Forbidden regions overlap. State d is a trap.

Words to know

The chapter’s grown-up words, in plain language.

concurrent
Logical flows overlap in time. They might take turns on one core or run on several.
process server
Parent accepts, forks a child, both close the descriptors they no longer need.
select
Ask the kernel to sleep until any descriptor in a read set would not block on a 1-byte read.
ready set
What select writes back: the subset that is actually ready. Copy the read set first.
thread
A kernel-scheduled flow inside one process. Own stack and TID; shared virtual memory.
Pthreads
The 1995 Posix C interface: create, join, detach, cancel, once, and about 60 calls in all.
shared variable
Some instance of it is referenced by more than one thread.
critical section
The load/update/store of a shared variable that must not interleave with another thread’s.
progress graph
One axis per thread. Legal steps are right or up. Unsafe and forbidden regions live inside.
P / V
Dijkstra’s proberen and verhogen. P waits for a positive semaphore and decrements; V increments and wakes one waiter.
mutex
A binary semaphore used for mutual exclusion. P locks, V unlocks.
sbuf
Bounded FIFO with mutex, slots, and items. The prethreaded server queues connfd here.
readers-writers
Many readers may share; a writer needs the object alone. First vs second problem is who waits.
speedup / efficiency
Sp = T1/Tp. Ep = Sp/p, usually as a percent.
race
The program is only right if one flow beats another to a point. The kernel will not promise that.
deadlock
A set of flows waits for a V that cannot happen. Enter the region and you cannot leave.
thread-safe
Repeated concurrent calls still get the correct result.
reentrant
Thread-safe and touching no shared data. Often no lock, so often faster.
