Concurrent Programming

One slow visitor should not freeze the whole shop. Logical flows can overlap in time — as processes, as one process juggling descriptors, or as threads in a single kitchen.

“A concurrent program consists of a collection of logical flows that overlap in time.” — Bryant & O’Hallaron, §12.8

The picture tab stays the rules of the drawing. The highlighted line is what just happened. You cannot break it.

Rust setup: what the listings assume

The book’s C listings rely on POSIX headers and csapp.c. The Rust listings are fragments too, and they rely on this block: thread functions must be extern "C" (the C calling convention pthread_create expects), sem_t and fd_set need their real sizes, and C’s macros become functions.

A Rust note: two threads writing one static mut (as in cnt) is undefined behaviour in Rust, not just a lost update. This chapter copies the book’s C to show the raw mechanism. Ordinary Rust uses std::thread with Mutex or atomics, and the compiler rejects the unsynchronised version.

use std::ffi::{c_char, c_int};
use std::ptr::{null, null_mut};

const STDIN_FILENO: c_int = 0;
const STDOUT_FILENO: c_int = 1;
const SIGCHLD: c_int = 17;                    // Linux
type Thread = extern "C" fn(*mut u8) -> *mut u8;   // what pthread_create wants: C ABI

// Linux x86-64 sizes. A sem_t is 32 bytes and an fd_set is 1024 bits;
// a one-word `i32` here would let sem_init and select write past it.
#[repr(C, align(8))] struct SemT([u8; 32]);
#[repr(C)] #[derive(Clone, Copy)] struct FdSet([u64; 16]);

unsafe extern "C" {
    // no pointers, so safe to call:
    pub safe fn fork() -> c_int;
    pub safe fn close(fd: c_int) -> c_int;
    pub safe fn pthread_self() -> usize;
    pub safe fn pthread_detach(tid: usize) -> c_int;
    fn pthread_create(tid: *mut usize, attr: *const u8, f: Thread, arg: *mut u8) -> c_int;
    fn pthread_join(tid: usize, ret: *mut *mut u8) -> c_int;
    fn pthread_exit(ret: *mut u8) -> !;
    fn pthread_cancel(tid: usize) -> c_int;
    fn pthread_once(once: *mut c_int, init: extern "C" fn()) -> c_int;
    fn sem_init(s: *mut SemT, pshared: c_int, value: u32) -> c_int;
    fn signal(sig: c_int, handler: extern "C" fn(c_int));
    fn pipe(fds: *mut c_int) -> c_int;
    fn read(fd: c_int, buf: *mut u8, n: usize) -> isize;
    fn write(fd: c_int, buf: *const u8, n: usize) -> isize;
    fn accept(fd: c_int, addr: *mut u8, len: *mut u32) -> c_int;
    fn select(n: c_int, r: *mut FdSet, w: *mut FdSet, e: *mut FdSet, timeout: *mut u8) -> c_int;
    fn malloc(n: usize) -> *mut u8;
    fn free(p: *mut u8);
    fn strcpy(dst: *mut c_char, src: *const c_char) -> *mut c_char;
    fn ctime(t: *const i64) -> *mut c_char;
    // from the book's csapp.c: the P and V semaphore operations
    fn P(s: *mut SemT);
    fn V(s: *mut SemT);
    fn open_listenfd(port: *const c_char) -> c_int;
}
// FD_ZERO / FD_SET / FD_ISSET are C macros; in Rust they are plain functions
unsafe fn fd_zero(s: *mut FdSet) { unsafe { (*s).0 = [0; 16] } }
unsafe fn fd_set(fd: c_int, s: *mut FdSet) { unsafe { (*s).0[fd as usize / 64] |= 1 << (fd % 64) } }
unsafe fn fd_isset(fd: c_int, s: *const FdSet) -> bool { unsafe { (*s).0[fd as usize / 64] >> (fd % 64) & 1 != 0 } }

12.1 · concurrent programming with processes

Two clerks from one fork

Jonah is the only clerk. A process is a logical flow the kernel schedules. The simplest way to get a second flow is fork. The child is a copy of Jonah at that instant, and from then on the two overlap in time.

The call returns twice. The child sees 0. The parent sees the child’s pid. That is the whole trick: one call, two flows, two different answers.

Try it: press Fork. Watch the one bar split into two that overlap, and read the return value on the highlighted line.

What the book says

Logical control flows are concurrent if they overlap in time. The simplest way to build a concurrent program is with processes, using fork, exec, and waitpid. A natural server accepts a connection in the parent and creates a new child to service each client.

Because processes have separate virtual address spaces, flows that want to communicate must use an explicit IPC mechanism. The kernel schedules each process.

12.1.1 · a concurrent server based on processes

A new clerk for every customer

Priya listens on descriptor 3. When Omar connects, Accept hands her descriptor 4. She forks. The child closes the listening copy. Priya closes her copy of 4. Both copies pointed at the same file-table entry, so the connection stays up until the last copy closes.

Children exit. Linux does not queue SIGCHLD, so the handler loops on waitpid with WNOHANG and reaps every zombie that is already ready.

Try it: Step through the two clients. Then flip to forget Close and watch the file-table count stick at 2.

What the book says

The listening descriptor starts as 3. The first connected descriptor is 4, the next is 5. The child closes its copy of the listening descriptor. The parent must close its copy of the connected descriptor. Otherwise the reference count in the socket’s file table entry never drops to zero while the server runs, and the leak can consume the available memory.

The SIGCHLD handler loops on waitpid(-1, NULL, WNOHANG) because signals are blocked while the handler runs and Linux signals are not queued. When a process terminates, the kernel closes its descriptors — so a parent that eventually exits would not leak. This parent loops forever, so the Close in the parent is what keeps the count honest. Practice 12.2 is that exit-time cleanup.

12.1.2 · pros and cons of processes

Separate houses, shared key rack

File tables are shared. Address spaces are not. Amina’s child can scribble on its own copy of x and Amina’s x stays put. That is the advantage: one process cannot accidentally overwrite another’s virtual memory.

The disadvantage is the same wall. To hand the number across, they need an explicit IPC mechanism, and process control plus IPC is slow compared with a thread switch.

Try it: press Child writes x. Then Send on a pipe so the parent actually receives 7.

What the book says

Processes have a clean model for sharing state between parents and children: file tables are shared and user address spaces are not. Separate address spaces are both an advantage and a disadvantage. It is impossible for one process to accidentally overwrite the virtual memory of another process.

To share other state they must use explicit IPC. Process-based designs also tend to be slower because the overhead for process control and IPC is high.

Bryant & O’Hallaron, 3rd ed., pp. 1011–1013 · 12.1.2

12.2 · I/O multiplexing

One pair of eyes, many doors

Mei does not fork. She builds a read set with stdin (0) and the listening descriptor (3), copies it, and calls select. The kernel sleeps her until a 1-byte read on one of those descriptors would not block.

select overwrites the set, so she copies ready_set = read_set every loop. If she then calls echo until the client hangs up, typed commands sit unread the whole time.

Try it: connect a client, then Type stdin while echo is still running. EOF lets the command through.

What the book says

I/O multiplexing is concurrent programming where the application explicitly schedules its own logical flows inside a single process. Flows are state machines. select manipulates fd_set values. The n argument is one past the highest descriptor of interest, so the book passes listenfd+1.

A descriptor is ready for reading when a request to read 1 byte from it would not block. Because select modifies the set, the server copies the permanent read set into ready_set on every iteration. The first server still calls echo until EOF, so a command on stdin waits.

12.2.1 · an event-driven server

One line, then back to the desk

Nia keeps a pool of connected descriptors. Each client is a state machine: waiting, reading a line, echoing, or closed. check_clients reads one text line from each ready descriptor and returns to select.

The grain of that loop is a whole line. A client that sends hel and then stops leaves Nia blocked inside the read. Ada and Bo cannot move until that line finishes.

Try it: give Ada a full line. Then send Bo a partial line and watch the others freeze. Flip to finer buffer — each client keeps its own unfinished text, and select runs again.

What the book says

The event-driven server is a pool of client descriptors, with init_pool, add_client, and check_clients. Each logical flow is a state machine. On each ready descriptor the server reads one text line. pool.nready is reloaded from select’s return value so the scan can stop once every ready descriptor has been handled.

The granularity of concurrency is the number of instructions needed to read an entire text line. A client that sends only a partial line and then halts stalls every other flow. Handling partial lines is a nontrivial change. A process-based server gets that isolation automatically.

12.2.2 · pros and cons of I/O multiplexing

You are the scheduler

Omar’s event loop can serve a preferred client first. Every flow sees the whole address space, so sharing is just a variable. One process means gdb works the ordinary way, and a new flow does not cost a process context switch.

The bill: about three times the code of the process server, a partial line can stall everyone, and the design cannot fill a multi-core chip. One core runs the loop. The others sit idle.

Try it: press Prefer Ada, then Partial line, then Four cores.

What the book says

Event-driven designs give the programmer more control — preferred service for some clients is hard in a process server. One process means every flow can see the whole address space, the server can be debugged with gdb, and scheduling a flow does not take a process context switch. The event-driven echo server is about three times as much code as the process server.

Finer granularity makes the code harder still. A malicious partial line stalls every flow. Event-based designs also cannot fully utilize multi-core processors. An aside notes that Node.js, nginx, and Tornado still use this style because of the performance advantage over processes and threads.

Bryant & O’Hallaron, 3rd ed., p. 1021 · 12.2.2

12.3 · concurrent programming with threads

Scheduled like a process, shared like select

A thread is a logical flow that runs inside a process. The kernel schedules it and knows it by an integer ID, the way it knows a process. Unlike a process, it does not get a private address space. Code, data, heap, shared libraries, and open files are the process’s, seen by every thread.

That is the hybrid. Try to publish a counter: the process child cannot see the parent’s copy. The select loop and the peer thread both can.

Try it: press Publish cnt = 1 on each column.

What the book says

Threads are a hybrid of the other two approaches, scheduled by the kernel like process flows and sharing the same virtual address space like I/O multiplexing flows. Each thread has its own thread context: a TID, stack, stack pointer, program counter, general-purpose registers, and condition codes.

All threads in a process share that process’s virtual address space. Programs in the book so far have been one thread per process. Modern systems let several threads run concurrently in one process.

Bryant & O’Hallaron, 3rd ed., pp. 1021–1022 · 12.3

12.3.1 · thread execution model

Peers, not a family tree

Every process starts as one main thread. It creates a peer. A context switch — a slow system call, or the interval timer — moves the CPU to the peer, then back. The peer’s context is smaller than a process context, so the switch is faster.

Threads are a pool of peers, not a parent-child tree. Any thread can wait for any other thread, or cancel it. The main thread is special only because it ran first.

Try it: press Play switches. Then tap a context chip: private pocket, or shared house.

What the book says

The main thread creates a peer and the two run concurrently. Control passes by a context switch, either because the running thread makes a slow system call such as read or sleep, or because the interval timer interrupts it. A thread context switch is faster than a process context switch because a thread context is much smaller.

Threads are not organized in a rigid parent-child hierarchy. They form a pool of peers. Any thread can kill any peer or wait for any peer. Each peer can read and write the same shared data.

12.3.2 · Posix threads

One pointer in, one pointer out

Posix threads, from 1995, are about 60 functions. A thread routine has one shape: it takes a void * and returns a void *. Luis wants to pass a name and an id, so he puts both in a struct and passes a pointer to it.

The peer unpacks the struct, prints both fields, and returns NULL. Main joins that one TID, then exit ends the process.

Try it: press Run and watch the struct travel into the peer. The highlighted line is the call in flight.

What the book says

Pthreads was adopted in 1995 and is available on all Linux systems. It defines about 60 functions to create, kill, and reap threads, to share data safely, and to notify peers about changes in system state.

The thread routine takes one generic pointer and returns one generic pointer. Multiple arguments go in a structure; the caller passes a pointer to that structure. Multiple return values come back the same way. In the hello program, main calls Pthread_create, Pthread_join, then exit. The peer prints and returns NULL.

tid is filled in on the way back

The peer does not read Chen’s variable. It calls pthread_self and gets the same number.

12.3.4 · terminating threads

Four ways a cook leaves

A peer can just return from its thread routine. Or it can call pthread_exit. If main calls pthread_exit, main waits until every peer has finished, and then the process ends.

exit is different: it kills the process and every thread in it, immediately. pthread_cancel lets one peer terminate another by TID.

Try it: press one ending. Reset between them. Watch who is still standing.

What the book says

A thread terminates implicitly when its top-level thread routine returns, or explicitly by calling pthread_exit. If the main thread calls pthread_exit, it waits for the other peers to terminate and then terminates the main thread and the process with return value thread_return.

Some peer calling the Linux exit function terminates the process and all of its threads. Another peer can terminate a chosen thread by calling pthread_cancel with that thread’s ID. pthread_cancel returns 0 on success.

12.3.5 · reaping terminated threads

You may wait for this one, not for anyone

Peer 2 finishes first. Its stack is still allocated, because a joinable thread is not reaped until someone joins it. Malik calls pthread_join on peer 0, who is still working. He blocks — even though peer 2 is already done.

There is no “join whoever finishes next.” Stevens calls that a bug in the specification. Join also copies out the void * the routine returned, then frees the peer’s memory resources.

Try it: press Peer 2 finishes, then Join peer 0 (you wait), then Join peer 2 (the stack goes).

What the book says

pthread_join blocks until thread tid terminates, stores the pointer returned by the thread routine where thread_return points, and reaps the memory resources held by that thread.

Unlike wait, pthread_join can wait only for a specific thread. There is no way to wait for an arbitrary thread. Stevens argues that this is a bug in the specification.

12.3.6 · detaching threads

The stack that nobody comes back for

A new thread is joinable. Its stack stays until another thread joins it. A detached thread cannot be joined or cancelled. When it terminates, the system frees the stack itself.

A server that creates a peer per connection should not sit in join. The peer calls pthread_detach(pthread_self()) before it does the work. Skip that, and every finished peer leaks a stack.

Try it: finish a joinable peer and see the stack remain. Reset, detach, finish, and the stack is gone. Then Serve 3 without detaching.

What the book says

A joinable thread can be reaped and killed by other threads. Its memory resources, such as the stack, are not freed until it is reaped. A detached thread cannot be reaped or killed by other threads. Its resources are freed automatically when it terminates. Threads are created joinable.

Each joinable thread should be reaped or detached, or the process leaks. A high-performance Web server that starts a peer per connection should have that peer detach itself, because the server should not wait for each connection thread. pthread_detach(pthread_self()) is the call.

Bryant & O’Hallaron, 3rd ed., pp. 1025–1026 · 12.3.6

12.3.8 · a concurrent server based on threads

A private card for each descriptor

Leila’s main thread accepts, then creates a peer. The obvious bug is passing &connfd, a pointer at one stack slot. The next Accept overwrites it before the peer reads it. Two peers then speak on the same descriptor.

The fix is a malloc’d int per connection. The peer detaches, frees that block, echoes, and closes. Delete the detach or the free and the server leaks — unlike the process server, where the parent’s missing Close is cleaned up only at process exit, and this loop never exits either.

Try it: spawn two clients on malloc, then on &connfd.

What the book says

The thread server has the same shape as the process server: accept, then hand the client to a new flow. Passing &connfd races the next accept. Each connected descriptor is stored in its own allocated block, and that pointer is the argument to pthread_create.

The peer detaches so its stack can be reclaimed without an explicit join, frees the block, echoes, and closes. Practice 12.5: deleting the detach or the free can leak. The threads are not reaped, so detach is what returns the stack; the free is what returns the block main allocated.

12.4 · shared variables in threaded programs

Three questions before you call it shared

Threads make sharing look easy, and that is the trap. Noor does not ask “is the name cnt shared?” She asks three questions, in order: what is the memory model, how are instances of this variable mapped onto memory, and how many threads reference each instance.

A variable is shared only when at least one of its instances is referenced by more than one thread. cnt in the thread routine is static, so there is one instance, and both peers increment it.

Try it: press Next question until the three answers line up for cnt.

What the book says

From the programmer’s point of view, an attractive part of threads is how easily they share program variables. Sharing is also tricky. To know whether a variable is shared you work through three questions: the threads memory model, how instances of the variable are mapped to memory, and how many threads reference each of those instances.

The running example is sharing.c: a global ptr, a msgs array on main’s stack, a static cnt inside the thread routine, and a per-peer myid.

12.4.1 · threads memory model

Pockets are private. The house is not.

Each thread owns its registers: the program counter, the condition codes, and the general-purpose registers. Samir’s %rdx can hold 7 while the peer’s %rdx holds 3. Neither can open the other’s pocket.

Virtual memory is always shared. Stacks are usually private in practice, but nothing stops a peer from following a pointer onto main’s stack. The model does not protect them.

Try it: tap %rdx, then cnt, then try the other pocket.

What the book says

Each thread has its own thread context: TID, stack, stack pointer, program counter, condition codes, and general-purpose register values. Registers are never shared. Each thread shares the rest of the process virtual memory, so virtual memory is always shared.

Separate stacks make automatic locals private in the usual case. They are not protected. A peer that is handed a pointer can read another thread’s stack.

12.4.2 · mapping variables to memory

How many boxes does this name get?

A global, or a local declared static, has exactly one instance, in the read/write data of the process. A local automatic has one instance per thread, on that thread’s stack. The book writes them myid.p0 and myid.p1.

Global variables and local static variables each have a single instance in the read/write data area. Local automatic variables have one instance per thread, living on that thread’s stack.

The book’s notation distinguishes the instances: tid.m for main’s tid, myid.p0 and myid.p1 for the two peers. The mapping is what the next section uses to decide sharing.

12.4.3 · shared variables

Shared means one instance, two readers

The rule is exact. Variable v is shared if and only if one of its instances is referenced by more than one thread. ptr, cnt, and msgs qualify. i and each myid do not.

msgs is the surprise. It lives on main’s stack, which sounds private, but the global ptr points at it, and both peers read through that pointer.

12.5 · synchronizing threads with semaphores

The counter that will not sit still

Two peers each add 1, a million times. The answer should be 2,000,000. On the book’s Linux system the program prints BOOM three times: 1445085, then 1915220, then 1404746.

cnt++ is not one step. It is load, update, store. If the second thread loads before the first stores, both write 1 and a tick disappears. You cannot predict which ordering the kernel will pick.

Try it: step the correct order, then the lost update. Sample runs cycles the book’s three results.

What the book says

12.5.1 · progress graphs

Right or up. Never diagonal.

Yuki draws one axis per thread. A point is how far each thread has got. A legal step is right (thread 1 finishes an instruction) or up (thread 2 does). Two instructions never complete at the same instant, so there is no diagonal. Threads never run backward.

The critical section for cnt is L, U, S. Where the two critical sections overlap is the unsafe region. The states on the perimeter are still safe. A trajectory that only skirts the region updates the counter. A trajectory that touches the interior loses an update.

Try it: play the safe path, then the unsafe path. The coral square is the unsafe region.

What the book says

A progress graph models n concurrent threads as a trajectory in an n-dimensional space. Axis k is the progress of thread k. The origin is the state where nobody has completed an instruction. Legal transitions move right or up, to an adjacent point. Diagonal, down, and left are illegal.

Instructions Li, Ui, and Si are the critical section for cnt. Their intersection is the unsafe region. It abuts, but does not include, the perimeter states. A trajectory that skirts the region is safe and updates the counter. A trajectory that touches the interior is unsafe. Any concurrent program that shares global data needs its threads forced onto safe trajectories.

12.5.2 · semaphores

A nonnegative integer with two moves

Dijkstra’s semaphore is a global integer that threads may touch only with P and V. P: if it is nonzero, decrement and return; if it is zero, sleep until a V wakes you, then decrement. V: add 1, and if anyone is asleep in P, wake exactly one of them. That thread finishes its P by decrementing.

The names are Dutch: proberen, to test, and verhogen, to increment. The invariant is s ≥ 0. A binary semaphore is only 0 or 1. A counting semaphore can be larger — here it starts at 2, so two P’s succeed before anyone sleeps.

Try it: press P until a thread sleeps, then V to wake exactly one. Flip to binary and the start value is 1.

What the book says

A semaphore s is a global variable with a nonnegative integer value, manipulated only by P and V. If s is nonzero, P decrements s and returns immediately. If s is zero, P suspends the thread until a V makes s nonzero and restarts it; the restarted P then decrements s. V increments s by 1. If any threads are blocked in P, V restarts exactly one of them, which then completes its P by decrementing s.

The names come from the Dutch proberen (to test) and verhogen (to increment). The book’s wrappers are P for sem_wait and V for sem_post. sem_init(sem, 0, value) initializes a semaphore shared by threads of this process. A binary semaphore is 0 or 1. The invariant s is never negative.

12.5.3 · semaphores for mutual exclusion

A moat around the unsafe square

A mutex is a binary semaphore that starts at 1, used so only one thread is inside the critical section. P locks. V unlocks. The invariant s ≥ 0 draws a forbidden region that wraps the unsafe square. No legal path can step in.

goodcnt puts P and V around cnt++. With a million iterations per thread it prints OK and cnt=2000000. The same two instructions that lost an update now run one thread at a time.

Try it: walk no mutex into the coral square. Then with mutex — the path is pushed outside, and cnt ends at 2.

What the book says

Mutual exclusion means each thread has exclusive access to the shared variable while it executes its critical section. A binary semaphore used this way is a mutex, initially 1. P is the lock, V is the unlock. The semaphore operations are indivisible, so the test-and-decrement cannot interleave with another P or V.

On the progress graph the invariant s ≥ 0 carves a forbidden region that encloses the unsafe region. Trajectories may not enter it. goodcnt, with the mutex around the increment and niters of 1000000, prints OK cnt=2000000.

12.5.4 · scheduling shared resources

Empty plates, and a catalog

A mutex stops two cooks from grabbing the same plate. It does not wake a cook who is waiting for a plate to appear. The bounded buffer uses three semaphores: slots starts at n, items starts at 0, and mutex starts at 1. Insert is P(slots), P(mutex), write, V(mutex), V(items). Remove is the mirror.

The same section’s other pattern is readers-writers. Many readers may look at once. A writer needs the object alone. The first solution favours readers: a waiting writer does not stop a new reader. Hold that open and the writer starves.

Try it: fill the window, then remove one. Switch to readers-writers and keep sending readers while a writer waits.

What the book says

sbuf is a bounded FIFO: buf, n, front, rear, plus mutex, slots, and items. slots is initialized to n and items to 0. Empty means front == rear. The first item is buf[(front+1)%n]. Insert and remove both hold mutex around the index update. Practice 12.9: with n > 1 even one producer and one consumer need the mutex, because the index updates race. With n = 1 the mutex can be omitted, including for several producers and several consumers, because a full buffer and an empty buffer each block one side.

The first readers-writers problem favours readers. readcnt starts at 0; mutex and w start at 1. Only the first reader locks w; only the last reader unlocks it. A stream of readers can leave a writer blocked forever — starvation. The second problem favours writers. Either correct solution can starve someone. Practice 12.10: if V wakes the most recent waiter, a departing writer may restart another writer instead of a waiting reader.

12.6 · using threads for parallelism

Same sum, three places to put it

A parallel program is a concurrent program that actually runs on more than one processor. Idris sums 0 … 231−1. If every add locks a global gsum, one thread takes 68.00 seconds on the book’s four-core machine and four threads take 719.00. The lock costs more than the add.

Write psum[myid] and the lock leaves the hot loop: 7.26, 3.64, 1.91 seconds. Add into a stack local and store once: 1.06, 0.54, 0.28. Past four threads the four cores are already busy, and extra threads just context-switch. Speedup is T1/Tp. Efficiency is that speedup divided by the number of cores.

Try it: switch the recipe, then tap a thread count. The seconds are the book’s, not a guess.

What the book says

Parallel programs are the concurrent programs that run on multiple processors. psum-mutex protects gsum += i with P and V. 12.7 · other concurrency issues

Three failures sequential code never has

Once threads share data, new bugs show up. Naomi sorts them into three piles the rest of the section takes apart: a function that is not safe to call twice at once, a program that is correct only if one thread wins a race, and a pair of locks that wait for each other forever.

These are not only thread bugs. Any concurrent flows that share a resource can hit the same three.

Try it: run each pile. The picture shows the failure in one step. The subsections below take them apart.

What the book says

Synchronizing shared data is harder than mutual exclusion and producer-consumer. The section is a survey of issues that do not arise in ordinary sequential programs. The discussion is in terms of threads, and the same issues show up when any concurrent flows share resources.

The three topics that follow are thread safety, races, and deadlocks. A thread-safe function always produces the correct result when called repeatedly from multiple concurrent threads. A race is a correctness dependency on one flow reaching a point before another. A deadlock is a flow waiting for an event that will never happen.

12.7.1 · thread safety

Four ways a function lies under threads

A function is thread-safe if repeated concurrent calls still get the right answer. The book names four overlapping classes of unsafe functions. Class 1 forgets to protect a shared variable — wrap it in P and V; callers do not change. Class 2 keeps state across calls, like rand and its seed. The only fix is to rewrite it so the caller passes the state.

Class 3 returns a pointer to a static buffer, like ctime. Rewrite it, or lock, copy the result into private storage, and unlock. Class 4 calls an unsafe function. If that callee is class 1 or 3, a mutex at the call can save you. If it is class 2, you have to rewrite the callee.

Try it: tap a class. The picture runs the failure, and the code shows the repair the book allows.

What the book says

A function is thread-safe if and only if it always produces correct results when called repeatedly from multiple concurrent threads. Class 1 does not protect shared variables. P and V fix it without changing callers, at the cost of synchronization. Class 2 keeps state across invocations. rand is the example. The fix is a rewrite so the caller passes the state; every call site changes.

Class 3 returns a pointer to a static variable. ctime and gethostbyname are the examples. One thread’s result is overwritten by the next. The fixes are a rewrite that stores into caller memory, or lock-and-copy: lock a mutex, call the function, copy the result to private memory, unlock. A wrapper hides that from the rest of the program. Class 4 calls an unsafe function. If the callee is class 2, the caller cannot be made safe without rewriting the callee. If the callee is class 1 or 3, protecting the call site and the resulting shared data with a mutex is enough. Figure 12.38 is ctime_ts, the lock-and-copy wrapper.

12.7.2 · reentrancy

Thread-safe, and touching nothing shared

Reentrant and thread-safe are not synonyms. Reentrant functions are the thread-safe ones that do not reference any shared data. They need no lock, so they are usually faster. rand_r takes the seed pointer from the caller. That is how you turn a class 2 function into a safe one: make it reentrant.

If every argument is passed by value and every datum is a local automatic, the function is explicitly reentrant. If it takes pointers, it is only implicitly reentrant — safe when the caller passes pointers to nonshared data. Hand rand_r one shared seed and the two threads scramble it again.

Try it: run rand, locked rand, rand_r private, and rand_r shared seed.

What the book says

Reentrant functions do not reference any shared data when called by multiple threads. They are a proper subset of the thread-safe functions. They are typically more efficient than non-reentrant thread-safe functions because they need no synchronization. The only way to make a class 2 function thread-safe is to rewrite it so it is reentrant. rand_r replaces the static seed with a pointer argument.

A function whose arguments are all passed by value, and whose data references are all local automatics, is explicitly reentrant. Allow pointers and it is implicitly reentrant: reentrant only if callers pass pointers to nonshared data. The book uses reentrant for both. Practice 12.12: rand_r is implicitly reentrant because a caller can pass a pointer to shared state.

12.7.4 · races

Four nametags, one sticky note

A race is when the program is correct only if one thread reaches point x before another reaches point y. Ada passes &i into four peers. She assumes each peer reads its own number before the next i++. The kernel promises no such trajectory. The book’s run printed 1, 3, 2, 3.

Give each peer its own malloc’d int, and the peer frees it. That run printed 0, 1, 2, 3. Freeing the block in main right after create is another race. Passing the integer itself through the void * avoids malloc; the caveat is that an int must fit in a pointer.

Try it: spawn on race, then on norace. Delay peer 0 to make the shared note even later.

What the book says

A race occurs when correctness depends on one thread reaching point x in its control flow before another thread reaches point y. Threaded programs must work for any feasible trajectory. race.c passes &i to four peers. The race is the next i++ against myid = *((int *)vargp). The book’s run printed Hello from thread 1, 3, 2, and 3.

norace.c allocates an int, stores i, and passes that pointer. The peer frees the block. That run printed 0, 1, 2, 3. Freeing in the main thread immediately after pthread_create is another race. An alternative with no malloc passes (void *)(long)i and recovers it with a cast. The peer must not free anything it does not own.

12.7.5 · deadlocks

Each holds the key the other needs

Nadia locks s then t. Omar locks t then s. Some trajectories slip through. Some reach state d, where each holds one mutex and waits for a V that cannot happen. The overlapping forbidden regions are the deadlock region. A trajectory can enter. It cannot leave.

The repair is a total order. Both acquire s then t, and release in reverse. The forbidden rectangles no longer overlap. A different trap, Practice 12.15, needs no crossed order: s starts at 1, t starts at 0, and both threads do P(s) V(s) P(t). Every trajectory dies on t. Initialize t to 1 and it is gone.

Try it: walk into d. Then lock order. Then t starts at 0.

What the book says

Opposite lock order makes the forbidden regions overlap. The overlap contains a deadlock state d and a deadlock region. Trajectories can enter deadlock regions, but they can never leave. A run of lucky schedules can hide it; the next machine, or the next schedule, traps you.

Mutex lock ordering rule: given a total ordering of all mutexes, a program is deadlock-free if each thread acquires its mutexes in order and releases them in reverse order. Practice 12.15 is a different trap. With s = 1 and t = 0, both threads doing P(s) V(s) P(t) V(t) always deadlock, because every feasible trajectory is eventually trapped. Initializing t to 1 removes it. Progress graphs are a uniprocessor picture; a multiprocessor can sit in states no trajectory names. The advice in the book stays: synchronize shared variables anyway.

12.8 · summary

Which machine fits this job?

The chapter’s concurrent program is a set of logical flows that overlap in time, built three ways: processes, I/O multiplexing, and threads. Semaphores then do two jobs — mutual exclusion, and scheduling of shared resources such as a bounded buffer or a readers-writers object. The prethreaded server uses both.

Functions the threads call must be thread-safe. Reentrant functions are the subset that touch no shared data. Races come from assuming a schedule. Deadlock is waiting for an event that will never happen.

Try it: tap a job. The picture names the approach the chapter would reach for, and highlights that sketch.

What the book says

Processes are scheduled by the kernel and need explicit IPC to share data. Event-driven programs build their own flows as state machines and schedule them with I/O multiplexing; sharing is easy because there is one address space. Threads are the hybrid: kernel-scheduled, and sharing the process address space.

P and V provide mutual exclusion and also schedule resources such as the bounded buffers in producer-consumer systems and the shared objects in readers-writers systems. A prethreaded echo server uses both. Functions called by threads must be thread-safe. The book identifies four classes of thread-unsafe functions. Reentrant functions are the proper subset of thread-safe functions that do not access any shared data, and they often need no synchronization. Races come from incorrect assumptions about scheduling. Deadlocks come from waiting for an event that will never happen.

Words to know

The chapter’s words, in plain language.

concurrent
Logical flows overlap in time. They might take turns on one core or run on several.
parallel
A concurrent program that runs on more than one processor so the job finishes sooner.
process server
The parent accepts and forks a child per client. Each side closes the descriptors it does not need.
IPC
The explicit channel processes use to share state, because their address spaces are separate.
select
Sleep until any descriptor in a set would not block on a 1-byte read.
ready set
What select writes back. Copy the permanent read set first, because select overwrites it.
state machine
The event-driven model of one client: the main loop moves it from state to state as data arrives.
granularity
How many instructions one logical flow runs before another can proceed. A whole line is coarse.
thread
A kernel-scheduled flow inside one process. Own stack, TID, and registers. Shared virtual memory.
peer
Any thread in the process. There is no parent-child tree. Any peer can join or cancel any other.
Pthreads
The 1995 Posix C interface. A thread routine is void *(*)(void *). About 60 calls.
joinable / detached
Joinable stacks wait for pthread_join. Detached stacks are freed when the thread returns.
pthread_once
Runs an initializer on the first call with a given once_control, and skips it after that.
shared variable
Some instance of it is referenced by more than one thread.
critical section
The instructions that touch a shared variable and must not interleave with another thread’s.
progress graph
One axis per thread. Legal steps are right or up. Unsafe and forbidden regions live inside.
P / V
Dijkstra’s proberen and verhogen. P waits while the semaphore is 0, then decrements. V increments and wakes one waiter.
mutex
A binary semaphore used for mutual exclusion, initially 1. P locks, V unlocks.
sbuf
A bounded FIFO with mutex, slots, and items.
readers-writers
Many readers may share an object. A writer needs it alone. First and second solutions pick who can starve.
prethreading
Create the worker threads once. The main thread queues connected descriptors for them.
speedup / efficiency
Sp = T1/Tp. Ep = Sp/p, usually written as a percent of the cores you actually used.
thread-safe
Concurrent calls still get the correct result. Four classes of functions fail this.
lock-and-copy
Lock, call a class 3 function, copy the static result into private memory, unlock.
reentrant
Thread-safe and touching no shared data. Explicit if it uses only by-value arguments and locals. Implicit if pointers must aim at private data.
race
The program is right only if one flow beats another to a point. The kernel will not promise that.
deadlock
Flows wait for an event that cannot happen. On the progress graph, you can enter that region and you cannot leave.
