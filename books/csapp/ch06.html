6.1.1 · random-access memory

A seesaw, a leaky cup, a chip that remembers the dark

SRAM stores a bit in a bistable cell of six transistors. Left or right, it stays there for as long as the power is on. That speed is why caches are SRAM. DRAM stores the bit as charge on a tiny capacitor, one transistor per bit. Leakage empties it in about 10 to 100 milliseconds, so the memory system must refresh every bit by reading it and writing it back.

A DRAM chip is a grid of supercells. To save pins, the controller sends the row first (RAS), which copies a whole row into an internal buffer, then the column (CAS). Several chips sit side by side on a module so one address returns a wide word. The CPU reaches that word over the memory bus: it drives an address, and the memory drives the data back.

Cut the power and both SRAM and DRAM forget. ROM and flash keep their bits in the dark. That is the firmware the machine can run before any disk is awake.

Try it: flip the SRAM bit, watch the DRAM cup drain, then cut the power — the ROM cell is the one that remains. Step a RAS/CAS read of supercell (2, 1). Then load A[2] and watch eight chips return one word.

What the book says

SRAM: 6 transistors per bit, relative access 1×, persistent while powered, about 1,000× the cost of DRAM, used for cache. DRAM: 1 transistor and a capacitor of about 30 femtofarads, access about 10×, must be refreshed, used for main memory and frame buffers.

A 16 × 8 DRAM has 16 supercells of 8 bits, arranged 4 × 4. Reading (2, 1) sends RAS = 2, then CAS = 1. A DIMM wires chips in parallel so they answer with a wider word. A memory read puts the address on the system bus, the I/O bridge forwards it on the memory bus, and main memory sends the word back. Enhanced DRAMs (SDR, DDR, and their kin) change the interface around the same capacitor cell.

6.1.2 · disk storage

Slide the arm, wait for the sector, then pour

A rotating disk is a stack of platters. Each surface is rings called tracks, cut into sectors of typically 512 bytes. Tracks at the same radius form a cylinder. The arm seeks to the right track, the platter spins until the sector arrives, then the bits stream off the head.

On the book’s example — 7,200 RPM, average seek 9 ms, 400 sectors per track — rotation is about 4 ms and the sector transfer is about 0.02 ms. Access time is 13.02 ms, and almost all of it is the wait before the first byte. The next sector on that track is nearly free. A random sector pays the wait again.

The CPU does not bit-bang the platter. It writes a command, the controller does the seek, and then DMA copies the sector into memory and raises an interrupt. The OS sees a sequence of logical blocks; the controller maps them to a surface, track, and sector.

Try it: step one sector through seek, rotation, transfer, and DMA. Then read four sectors in order, and four sectors at random, and compare the clocks.

What the book says

Average seek is typically 3 to 9 ms. Average rotation is half a turn. Transfer of one sector is a thin slice of a turn. Tavg rotation at 7,200 RPM is about 4 ms; Tavg transfer for 512 bytes at 400 sectors/track is about 0.02 ms. Twice the seek time is a handy estimate of a random access.

A 64-bit word is roughly 4 ns in SRAM and 60 ns in DRAM. A disk access of about 10 ms is tens of thousands of times a DRAM access. After the command, the controller can DMA the sector and interrupt the CPU.

6.1.3 · solid state disks

Write a page; to change it, erase the block

Flash is not a platter. Data moves in pages (often 512 bytes to 4 KB), and pages are grouped into blocks of 32 to 128 pages. A read fetches a page. A write can program a page only after that whole block has been erased, which sets every bit to 1.

A second write to a live page copies any neighbours worth keeping into a fresh erased block, then erases the old one. Erase is on the order of a millisecond. A block wears out after roughly 100,000 repeated writes, so the drive spreads erases around. The flash translation layer still presents ordinary logical blocks to the operating system.

Try it: tap a page. Write an erased page, then write a live page and watch the block erase first. The code panel follows the same branch.

What the book says

An SSD packages flash chips plus a translation layer behind a disk slot such as SATA or USB. “A page can be written only after the entire block to which it belongs has been erased.” A block wears out after roughly 100,000 writes.

One commercial drive in the book: sequential read about 550 MB/s and write about 470 MB/s; random reads faster than random writes; sequential access around 50 μs read and 60 μs write for 4 KB. Random writes pay the erase and the copy of sibling pages. Wear-leveling spreads that cost. SSDs cost more per byte than rotating disks and have no moving arm.

6.1.4 · storage technology trends

Density got cheap. Latency did not keep up.

From 1985 to 2015, SRAM access time and SRAM cost each improved by about 100×. DRAM cost per megabyte fell by about 44,000×, while DRAM access time improved by only about 10×. Disk cost per gigabyte fell by millions of times; minimum seek time improved by about 25×.

CPU cycle time over that same stretch improved by about 500×, and the effective cycle time — one core’s cycle, divided by the number of cores — by about 2,000×. The gap those bars open is why a hierarchy exists: the processor raced ahead of DRAM and disk, and caches are the bridge.

Try it: drag the year. The bars are “how many times better than 1985,” on a log scale. The code under the picture is a compute loop beside a memory loop — the second one is where the gap shows up.

What the book says

The survey behind the trend figure: SRAM $/MB from about 2,900 (1985) to 25 (2015), access from 150 ns to 1.3 ns. DRAM $/MB from about 880 to 0.02, access from 200 ns to 20 ns, typical size from a fraction of a megabyte to 16 GB. Disk $/GB from about 100,000 to 0.03, minimum seek from 75 ms to 3 ms.

CPU cycle time from 166 ns (80286) to 0.33 ns (2015 Core i7). Around 2003 the curve splits: single-core cycle time stalled, and chips gained cores instead. Effective cycle time fell further. It is much easier to increase density than to decrease access time.

6.2.1 · locality of references to program data

Come back soon, or knock on the next door

Temporal locality: a location you just used is likely to be used again soon. A running total in a scalar has it. Each element of a vector, visited once, does not.

Spatial locality: a neighbour is likely to be next. Walking v[i] with i++ is stride-1, the order the ints occupy in memory. Walking a two-dimensional array down a column hops N ints each time. Same additions, a worse stride.

Try it: step sumvec, then the row walk, then the column walk. The highlighted line is the reference, and the tag says which kind of locality just paid off.

What the book says

A program with good temporal locality reuses a memory location many times in the near future. Spatial locality is the neighbour rule. In the vector sum, sum is temporal and has no spatial locality; v with stride 1 is spatial and each element is touched once.

The row-wise double loop matches C’s row-major layout. The column-wise loop is stride-N. On the authors’ machine, matrix kernels with the same arithmetic and different locality varied by almost 40×.

6.2.2 · locality of instruction fetches

The loop body is fetched again, in order

Instructions are data too. The program counter walks them in address order, so a straight-line basic block has excellent spatial locality. A loop then jumps back and fetches that same block again. That is temporal locality in the instruction stream.

Code is rarely rewritten while it runs, so the instruction working set of a loop is small and stable. An instruction cache can keep it hot even while data is thrashing.

Try it: step the program counter around the five-instruction loop. Watch the jump return to cmp, and the fetch counts climb.

What the book says

Instruction fetches have spatial locality because the CPU executes instructions in sequence, and temporal locality because loops reuse the same instructions. Programs almost never write their own instruction memory at run time, so the instruction stream is a friendly client of the cache.

6.2.3 · summary of locality

Two questions about the next reference

Every reference pattern in this chapter answers the same pair of questions. Will this address be used again soon? Will the next address be nearby? Loops give both answers to the instruction stream. Stride-1 data gives the second. A scalar accumulator gives the first. A large stride gives neither.

Programs that say yes to at least one of those questions draw more of their bytes from the fast shelves. That is the whole reason a hierarchy can feel as quick as its top and as roomy as its bottom.

Try it: tap a pattern. The meters are temporal and spatial locality, and the code panel switches to the snippet that produces them.

What the book says

Locality is the reason hierarchies work: a well-written program touches the storage at one level more often than the level below, so the lower level can be slower, larger, and cheaper per bit. Data references and instruction references both count.

6.3 · the memory hierarchy

Each shelf is a cache for the one below

Registers hold the words the compiler kept close. SRAM caches stage blocks of main memory. Main memory stages pages from disk. A local disk can stage files from other machines. Go down and storage gets bigger, slower, and cheaper per byte. Go up and it shrinks and speeds up.

The effect, when locality is present, is a pool that costs like the bottom and serves data at a rate like the top. A miss at one shelf is a request to the shelf below, which may itself miss, until some level has the block.

Try it: tap a level to read its job and latency. Press Fetch and watch block 12 climb, leaving a copy on every shelf it passes.

What the book says

From the top: registers, L1–L3 SRAM, DRAM main memory, local disks, then remote storage such as network file systems. “The overall effect is a large pool of memory that costs as much as the cheap storage near the bottom of the hierarchy but that serves data to programs at the rate of the fast storage near the top.”

Sample hit times in the book’s survey: registers 0 cycles, L1 about 4, L2 about 10, L3 about 50, main memory about 200, disk cache about 100,000, network or browser cache on the order of millions to billions of cycles. SSDs sit between DRAM and rotating disk.

6.3.1 · caching in the memory hierarchy

A small shelf of copies, indexed by block number

Level k is smaller and faster than level k+1. It holds a subset of the blocks from below. Ask level k first. The block is there: a hit, served at the fast time. The block is absent: a miss. The level fetches the block from below, which may evict a victim, and then the request is a hit.

In the simple picture, block i is placed in slot i mod 4. Adjacent blocks land in different slots. Blocks 4 and 8 both want slot 0, so one of them has to leave even though other slots are full of unrelated blocks. That fight, with room still left in the cache, is a conflict miss. The very first touch of a block is a cold miss. A working set bigger than the shelf is a capacity miss.

Try it: step the book’s shelf — blocks 4, 9, 14, 3 — then 4 hits, 8 evicts that copy, and the next 4 is the conflict on slot 0. Or tap any block yourself.

What the book says

The cache at level k holds copies of blocks from level k+1. Hits are served from k. A miss copies the block in, possibly replacing another. Placement of the form “block i lives in slot i mod n” is the direct-mapped idea in miniature. The book’s picture holds blocks 4, 9, 14, and 3 in a four-slot cache above a sixteen-block memory.

Cold misses fill an empty cache. Conflict misses happen when placement piles live blocks onto one slot while other slots sit idle. Capacity misses happen when the working set is simply larger than the cache. The block size is the transfer unit between that pair of levels: words near the registers, cache lines in the SRAM caches, pages between disk and memory.

6.3.2 · summary of memory hierarchy concepts

Somebody has to decide what stays

The shape is the same at every level: a smaller store caches a larger one, in blocks, with a hit time and a miss penalty. What changes is who manages it. The compiler chooses registers. Hardware chooses the SRAM caches and the TLB. The operating system and the MMU choose which pages stay in DRAM. Client software chooses which remote files stay on the local disk. A browser chooses which pages stay on that disk.

Your C source looks the same in every row. The highlighted line is served by a different manager, with a different latency, depending on which shelf actually holds the bytes.

6.4.1 · generic cache memory organization

Sets, lines, blocks, and three fields in the address

A cache has S = 2s sets. Each set has E lines. Each line holds one block of B = 2b bytes, plus a valid bit and a tag. The data capacity, ignoring tags and valid bits, is C = S × E × B.

An m-bit address splits into t tag bits, s set-index bits, and b block-offset bits, with t = m − (s + b). Finding a byte is three steps: the index selects the set, the tag is compared with the valid lines in that set, and the offset picks the byte inside the block.

Try it: change S, E, B, and the address. The colored bits are the live split, and the code panel’s tags show the set, tag, and offset the hardware would compute.

What the book says

Parameters: m address bits, S = 2s sets, E lines per set, B = 2b bytes per block, t = m − (s + b) tag bits. C = B × E × S counts data bytes only. A line is valid bit + tag + block. A set is E lines. People often say “line size” when they mean block size.

A reference selects the set, matches a valid tag, then extracts the word at the block offset. Direct-mapped means E = 1. Set-associative means 1 < E < C/B. Fully associative means E = C/B, a single set.

6.4.2 · direct-mapped caches

One line per set, so the tag must match

E = 1. The set index chooses exactly one line. If the valid bit is set and the tag matches, the offset byte is returned. Otherwise the line is replaced with the block from memory. There is no choice of victim: the resident block leaves.

The book’s toy is (S, E, B, m) = (4, 1, 2, 4). Reads of 0, then 1, hit the same block. 13 fills another set. 8 lands in set 0 and evicts block 0. Reading 0 again misses even though three sets are empty. That second miss is a conflict. The first touch of 8 was still cold.

The index uses the middle bits, not the high bits. High bits would park neighbouring blocks in the same set, and a stride-1 scan would thrash a cache that still had empty sets.

Try it: step the toy trace, or press an address from 0 to 15. Then switch to index bits and scan blocks 0–3 with the low bits, then with the high bits.

What the book says

Worked cache (4, 1, 2, 4). Address bits are t | ss | b with one tag bit, two index bits, one offset bit. The trace 0, 1, 13, 8, 0 is miss, hit, miss, miss, miss. The last miss is the conflict: address 8 replaced the block that address 0 needs, and the other sets never entered the fight.

Indexing with the middle bits spreads consecutive blocks across sets. Indexing with the high bits maps a run of consecutive blocks onto one set. The set-selection bits are the ones just above the block offset.

6.4.3 · set associative caches

E lines in the set, so two rivals can both stay

A set-associative cache gives each set E lines, with 1 < E. The index still picks one set. Inside the set, every valid tag is checked. Any of the E lines may hold the block. When they are all full, a replacement policy — often least recently used — picks the victim.

Addresses 0 and 8 both mapped to set 0 in the direct-mapped toy, and they kicked each other out. Give that set two lines and both blocks sit there. The reread of 0 hits. A third block that wants the same set, such as 4, is the one that finally evicts somebody.

Try it: step 0, 8, 0, 4 on a two-way cache with two sets. The code tags say hit, fill, or which line LRU dropped.

What the book says

Line matching in an E-way set compares the tag against all E lines in the selected set. A hit is any valid match. A miss with a free line fills it. A miss with a full set replaces one line. LRU, LFU, and random are the usual policies; LRU needs a little state per line.

Raising E removes conflicts that were only a placement accident. It costs extra tag comparators, extra state, and a slower hit path. The Core i7 uses E = 8 in L1 and L2 and E = 16 in L3.

Bryant & O’Hallaron, 3rd ed., §6.4.3 Set Associative Caches

S = 2 · E = 2 · B = 2 · m = 4cold
Set 0 has room for both block 0 and block 4 (addresses 0 and 8).
6.4.4 · fully associative caches

One set. Any line can hold any block.

A fully associative cache is the case E = C/B: a single set, and every line is a candidate. There is no index field. The tag is everything above the block offset, and a lookup compares it with every line.

Conflicts of the “wrong slot” kind disappear. Misses that remain after the cache is warm are capacity misses: the working set has more blocks than there are lines. The machine below holds four lines. The fifth distinct block evicts the least recently used one. Small fully associative memories show up in real chips as things like a TLB, where E is tiny enough that searching every line is cheap.

Try it: step blocks 0, 2, 4, 6 into an empty cache, then block 8. The last step is the capacity miss. Reading 0 afterward misses too, because 0 was the victim.

What the book says

Fully associative placement puts a block in any line. Matching searches the entire cache. Replacement is explicit, because there is no single “home” slot to overwrite. The organization is used when the number of lines is small.

A capacity miss is independent of the placement function: even a fully associative cache misses when the working set does not fit. Cold misses still happen on the first touch of each block.

6.4.5 · issues with writes

Update downstairs now, or pin a dirty note

A write hit updates the cache’s copy. Write-through also writes the word to the next level immediately. Simple, and every store uses the bus. Write-back marks the line dirty and writes the block downstairs only when the line is evicted. Locality makes that a large saving in bus traffic, at the cost of the dirty bit and a flush on replacement.

A write miss has a second choice. Write-allocate loads the block, then updates it, hoping the program will touch that block again. No-write-allocate writes the word straight to the next level and leaves the cache alone. Write-through caches are usually no-write-allocate. Write-back caches are usually write-allocate. When you write cache-friendly code, assume write-back plus write-allocate: it tries to exploit the same locality as a read.

Try it: store to A (a hit) and to C (a miss) under both pairings, then evict. Only the dirty line travels on eviction.

What the book says

Write-through updates the next level on a write hit. Write-back defers that update until eviction and keeps a dirty bit per line. Write-allocate fetches the block on a write miss. No-write-allocate bypasses the cache and writes the next level directly.

The suggested mental model is write-back, write-allocate: lower levels already use write-back (virtual memory uses it exclusively), modern chips use write-back widely, and the policy is symmetric with reads. Write-through can hide behind a write buffer. Write-back leaves more bus bandwidth for DMA.

6.4.6 · anatomy of a real cache hierarchy

Instructions and data, side by side, then a shared L3

Real caches hold instructions as well as data. An i-cache holds instructions, a d-cache holds data, and a unified cache holds both. Splitting L1 lets the processor read an instruction and a data word in the same cycle. The i-cache is read-only, so it is simpler. Data references cannot kick instructions out of L1, or the other way around.

On the Core i7 in the book, each core has a private 32 KB L1 i-cache, a private 32 KB L1 d-cache, and a private 256 KB unified L2. All four cores share an 8 MB unified L3 on the same chip. Every SRAM cache in that picture is on the processor package. Main memory is the next shelf down.

Try it: tap a cache for its size, associativity, block size, and hit time. Then issue one loop iteration and watch the instruction and the array element arrive together.

What the book says

Core i7: L1 i-cache and L1 d-cache each 32 KB, 8-way, 64-byte blocks, 64 sets, 4-cycle access. L2 unified 256 KB, 8-way, 64-byte blocks, 512 sets, 10 cycles. L3 unified 8 MB, 16-way, 64-byte blocks, 8,192 sets, 40 to 75 cycles, shared by the cores. All of that SRAM is on the CPU chip.

Separate L1 caches allow a simultaneous instruction fetch and data load, can be tuned differently, and keep instruction and data references from conflicting with each other. The cost is that a byte used as both code and data cannot be shared inside one L1.

6.4.7 · performance impact of cache parameters

Bigger, wider, and more ways — each one spends something

Miss rate is misses divided by references. Hit rate is one minus that. Hit time is how long a hit takes. Miss penalty is the extra time a miss costs — on the order of 10 cycles from L2, 50 from L3, 200 from DRAM.

A larger cache raises the hit rate and tends to raise the hit time, which is why L1 is smaller than L2, and L2 smaller than L3. A larger block exploits spatial locality, but for a fixed capacity it means fewer lines, and the miss penalty grows because more bytes move. Higher associativity cuts conflict misses and makes the hit path heavier: more tags, more LRU state, a slower victim choice. L1 on the Core i7 is 8-way; L3 is 16-way, where the miss penalty is large enough to justify the extra logic. Write-back, farther down the hierarchy, spends bandwidth on fewer transfers.

Try it: three toys. Size: a 6-block working set in 2, 4, or 8 lines. Block: eight stride-1 ints with 4-, 16-, or 32-byte blocks. Associativity: addresses 0 and 8 sharing a set, with E = 1, 2, or 4.

What the book says

Miss rate = misses / references. Hit rate = 1 − miss rate. Hit time includes set selection, line matching, and word extraction. Miss penalty from L2 is about 10 cycles, from L3 about 50, from main memory about 200.

Larger caches: higher hit rate, slower hit. Larger blocks: better spatial hits, fewer lines, larger transfer. Higher E: fewer conflict misses, more tag bits and a longer hit time. The Core i7 compromise is 64-byte blocks, 8-way L1 and L2, 16-way L3. Write-back becomes more attractive as transfer time grows.

6.5 · writing cache-friendly code

Walk the row the array already lives in

Miss rate follows locality, and running time follows miss rate. The references that matter are the ones in the inner loop. A stride-k scan of words, with block size B, misses about min(1, word size × k / B) times per reference. Stride 1 is the friendly end of that formula: one miss, then B/4 − 1 hits, for 4-byte ints.

C stores a row-major array so that a[i][j] and a[i][j+1] are neighbours. An inner loop on j is stride-1. An inner loop on i is stride-N. If the array is larger than the cache, the column walk misses on every access. The book measured the row version about 25× faster than the column version for large arrays.

Try it: walk the 4 × 4 grid by rows, then by columns. The cache holds one 16-byte block, exactly one row of ints. The highlighted statement is the access, tagged hit or miss.

What the book says

Focus on the inner loops of the core functions. For a stride-1 sumvec of ints with B = 16 and a cold cache, the pattern is miss, hit, hit, hit. sumarrayrows repeats that per row. sumarraycols is stride-N. When the array fits, even the column walk can warm up; when it does not, every a[i][j] misses.

On the authors’ desktop, the row-wise sum ran about 25 times faster than the column-wise sum once the arrays were large.

6.6.1 · the memory mountain

Throughput is a mountain, not a number

Read throughput depends on two things at once: how big the working set is, and the stride you walk it with. Plot them and you get a mountain. High ridges are working sets that fit in L1, L2, or L3. The slope down the side is spatial locality getting worse as the stride grows. The floor is main memory.

On the Haswell Core i7 in the book, the L1 peak is over 14 GB/s and the memory floor is about 900 MB/s — more than an order of magnitude on the same machine, same load instruction. A stride-1 scan stays near 12 GB/s even past L2, because the prefetcher recognizes the pattern and pulls the next line early. At a stride of one cache line, that help runs out.

What the book says

6.6.2 · rearranging loops to increase spatial locality

Six multiply loops, one arithmetic, three miss rates

All six matrix products compute C[i][j] += A[i][k] * B[k][j]. They differ only in which index is in the inner loop. With 8-byte doubles and 32-byte blocks, a stride-1 reference misses about 0.25 times per iteration, a stride-n reference misses every time, and a reference that does not change in the inner loop can live in a register.

Inner k (ijk, jik) is class AB: A by rows, B by columns, 1.25 misses. Inner i (jki, kji) is class AC: two column scans, 2.00 misses. Inner j (kij, ikj) is class BC: B and C by rows, 0.50 misses. For large n the fastest pair ran almost 40× faster than the slowest pair, with the same floating-point work. Miss rate predicted that better than the raw number of memory operations did.

What the book says

Class AB (ijk, jik): 0.25 + 1.00 + 0 = 1.25 misses per inner iteration. Class AC (jki, kji): two stride-n loads, 2.00 misses. Class BC (kij, ikj): two stride-1 streams, 0.50 misses, even though the inner loop also stores C.

Pairs with the same miss count measured almost the same. For large n, kij and ikj stayed flat — the prefetcher kept up with the stride-1 pattern even when the arrays were far larger than SRAM. The fastest version was almost 40× the slowest.

6.6.3 · exploiting locality in your programs

Finish the work while the bytes are still here

The mountain says the effective memory rate is not one number. It swings by orders of magnitude with locality, on every memory system, not just one cache geometry. Three habits follow. Spend your attention on the inner loop, where the references actually happen. Read objects in memory order, stride 1, so each block you pay for yields its neighbours. Once a block is in, use it as many times as you can before it is evicted.

Blocking is that third habit made structural. The array is cut into tiles that fit in the cache. The program finishes every use of a tile, then moves on. A straight triple pass over eight items, with a four-line cache, never reuses a line in time: every reference misses. The tiled pass misses eight times and hits sixteen.

Try it: play the straight scan, then the tiled scan. The cache holds four items. The highlighted use is tagged hit or miss as it runs.

What the book says

Focus on inner loops. Maximize spatial locality by reading data sequentially with stride 1. Maximize temporal locality by using a data object as much as possible once it has been read. Those habits help on any hierarchy, because they raise the fraction of references served from the fast levels.

Blocking (a web aside in this edition) organizes the data into chunks that fit in cache, exhausts the work on a chunk, then loads the next. On the Core i7, hardware prefetch already rewards plain stride-1 matrix multiply, so blocking is not what made kij fast there. The idea still matters on machines that do not prefetch, and it is the direct way to manufacture temporal locality.

Words to know

The chapter’s words, in plain language.

SRAM / DRAM
Bistable six-transistor cell, or charge on a capacitor that must be refreshed.
RAS / CAS
Row, then column, to read one DRAM supercell with fewer address pins.
seek / rotation / transfer
The three pieces of a disk access. The first two dominate.
DMA
The disk controller copies a sector into memory and interrupts the CPU.
page / block (flash)
A page is programmed. A block is the unit that must be erased first.
temporal locality
The same address is used again soon.
spatial locality
A nearby address is used next. Stride-1 is the friendly case.
hit / miss
The block is in this cache, or it must be fetched from the level below.
cold / conflict / capacity
First touch; the home slot is busy while the cache still has room; the working set does not fit.
set / line / block
A set holds E lines. A line holds a valid bit, a tag, and one block of B bytes.
C = S × E × B
Data capacity. Tag bits and valid bits are overhead, not part of C.
direct / set / full
E = 1, or several lines per set, or one set that can hold every block.
write-through / write-back
Update the next level on the store, or when a dirty line is evicted.
write-allocate
On a write miss, load the block and then update it.
i-cache / d-cache
Split L1 so an instruction and a data word can be read together.
miss rate / miss penalty
Misses per reference, and the extra cycles a miss costs.
memory mountain
Read throughput against working-set size and stride.
blocking
Finish every use of a tile that fits in cache, then load the next tile.
