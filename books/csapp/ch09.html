Virtual Memory

Every program thinks it owns a huge private building. Really it holds a map. A clerk on the chip turns map numbers into real rooms — and stops anyone who walks into the wrong one.

“Virtual memory is an elegant interaction of hardware exceptions, hardware address translation, main memory, disk files, and kernel software that provides each process with a large, uniform, and private address space.”

Big idea 1 · physical and virtual addressing

Street numbers, or a nickname the clerk translates

Main memory is a long row of lockers. The first locker is 0, the next is 1, and so on. That locker number is a physical address. On an old machine the CPU just shouts “locker 4!” down the bus.

On a modern chip the CPU shouts a virtual address instead — a nickname from the program’s private map. Dedicated hardware called the MMU looks the nickname up and only then sends a real locker number to memory.

Try it: Switch Physical, then press Load word. The CPU talks to locker 4 directly. Switch Virtual and load again: the CPU issues 4100, and the MMU rewrites it to 4 before the same word comes back.

What the book says

Main memory is M contiguous byte-size cells, each with a unique physical address (PA). Figure 9.1: a load of the 4-byte word at PA 4. Early PCs used physical addressing; digital signal processors, embedded microcontrollers, and Cray supercomputers still do.

Figure 9.2: the CPU generates a virtual address (VA). “The task of converting a virtual address to a physical one is known as address translation.” The memory management unit (MMU) on the CPU chip translates on the fly, using a lookup table in main memory that the operating system maintains.

Address translation, like exception handling, needs hardware and the kernel working together. The rest of the chapter is that cooperation, seen from both sides.

Big idea 2 · address spaces

Two kids, the same locker number, different rooms

Amina and Jorge each believe they own locker 1 and locker 2 in a gigantic hallway. That hallway is a virtual address space — an ordered set of numbers {0, 1, 2, …}. A 32-bit space has 232 of them; a 64-bit space has 264.

The school only has a modest row of real rooms (the physical address space). Each child gets a private map, so Amina’s “locker 1” and Jorge’s “locker 1” can live in different rooms. Sometimes the maps point at the same room on purpose — that is how they share one copy of the library.

Try it: Press Map both. Watch VP 1 and VP 2 for each process land on different physical pages, then notice the shared page that both maps may use.

What the book says

A linear address space is {0, 1, 2, …}. The CPU generates addresses from a virtual address space of N = 2n addresses. A physical address space of M = 2m bytes sits underneath. Each byte of main memory therefore has both a virtual address and a physical address.

Figure 9.9: the OS keeps a separate page table per process. Process i maps VP 1 → PP 2 and VP 2 → PP 7; process j maps VP 1 → PP 7 and VP 2 → PP 10. Multiple virtual pages can share one physical page.

A private space simplifies linking (on 64-bit Linux the code segment starts at 0x400000), loading (the loader maps .text and .data and never copies; pages arrive on demand), sharing (one libc, many processes), and allocation (k contiguous virtual pages may sit on k scattered physical pages).

Big idea 3 · VM as a cache

Four tables, a warehouse of books

Imagine the whole program lives in a warehouse on disk, cut into same-size books called virtual pages. The reading room (DRAM) has only a few tables — physical pages, or page frames. A book on a table is cached. A book still in the warehouse is allocated but uncached. Some shelf slots were never given out at all.

Ask for a word in a book that is already on a table: page hit. Ask for a book that is still in the warehouse: page fault. A clerk picks a victim table, maybe writes that book back, then wheels the missing book in. The instruction starts over and now hits. Waiting until the miss to fetch is demand paging.

Try it: Tap VP 2 for a hit (it already sits in PP 1). Then tap VP 3. That miss evicts VP 4 from PP 3 and pages VP 3 in. Reset to put the books back.

What the book says

Virtual memory is an array of N bytes on disk, cached in main memory. Transfer units are virtual pages and physical pages of P = 2p bytes. Figure 9.3 partitions pages into unallocated, cached, and uncached. SRAM cache means L1–L3; DRAM cache means this VM cache.

Misses are served from disk (about 100,000 times slower than DRAM), so pages are large — typically 4 KB to 2 MB — the DRAM cache is fully associative, replacement is sophisticated, and “DRAM caches always use write-back instead of write-through.”

Figure 9.4: a PTE holds a valid bit plus an address (PPN or disk). Figure 9.5: VP 2 cached in PP 1 is a hit. Figures 9.6–9.7: VP 3 faults; the handler victims VP 4 in PP 3, copies VP 3 in, then restarts. All modern systems use demand paging. Locality keeps a working set resident; if that set exceeds physical memory the program thrashes.

Big idea 4 · memory protection

Three stamps on every page

The same lookup that finds a room can also decide whether you may enter. Each page table entry grows a few extra bits: SUP (grown-ups / kernel only), READ, and WRITE. A user process may read its code, write its data, and must not touch the kernel’s pages or someone else’s.

Break a stamp and the CPU raises a general protection fault. The kernel sends SIGSEGV. A Linux shell prints “segmentation fault.”

Try it: Stay in user mode. Read VP 0 (allowed). Write VP 1 (allowed). Write VP 0 or touch VP 2 — those stamps refuse, and the page goes coral.

What the book says

A user process must not modify its read-only code, must not read or write kernel memory or another process’s private pages, and must not write shared pages unless every party agrees. Figure 9.10 adds SUP, READ, and WRITE bits to each PTE.

Kernel mode may access any page. User mode may access only pages with SUP = 0. Process i in user mode may read VP 0 and read or write VP 1, but “it is not allowed to access VP 2.”

A violating instruction triggers a general protection fault. The handler sends a SIGSEGV signal. Linux shells typically report this exception as a “segmentation fault.”

The MMU checks the stamps every time the CPU names a page.
Big idea 5 · address translation

Split the nickname, glue a new one

A virtual address snaps in two: the VPN (which book) and the VPO (which byte inside the book). The MMU uses the VPN as an index into the page table, reads a PTE, and — if the valid bit is on — glues the stored PPN onto the same offset. That offset is now the PPO. It is the same bits. Pages are the same size, so the byte-inside-the-book never changes.

Doing that lookup in DRAM every time would be slow. So the MMU keeps a tiny notebook of recent PTEs: the TLB. A hit never leaves the chip. A miss fetches the PTE, then writes the notebook.

Try it: Step the book’s load of 0x03d4. The TLB hits in set 3 and the cache returns byte 0x36. Switch to TLB miss to watch the extra walk through the page table.

What the book says

Figure 9.11–9.12: VA = VPN | VPO; PA = PPN | PPO; PPO is identical to VPO. The page table base register (PTBR) points at the current table. Figure 9.13(a): page hit is five hardware steps. Figure 9.13(b): a zero valid bit raises a fault; the kernel victims, pages in, updates the PTE, and restarts.

“A TLB is a small, virtually addressed cache where each line holds a block consisting of a single PTE.” TLBI is the t low bits of the VPN; TLBT is the rest. Figure 9.16: a hit stays inside the MMU; a miss fetches the PTE into the TLB.

Section 9.6.4 toy machine: n = 14, m = 12, P = 64, 4-way TLB with 16 entries. VA 0x03d4 → VPN 0x0F, VPO 0x14, TLBI 0x03, TLBT 0x03, PPN 0x0D, PA 0x354, cache byte 0x36.

Big idea 6 · multi-level page tables

A slim city book, then a street book

One giant table for a 32-bit space with 4 KB pages and 4-byte PTEs would be 4 MB — and it would have to sit in RAM even if the program used a handful of pages. That is a terrible tax. So we use a two-level book.

The first book has 1,024 lines. Each line covers a 4 MB chunk (1,024 pages). If that whole chunk is empty, the line is null and the second book does not exist. Only the first book must stay in memory. The second books can be paged like anything else.

Try it: Walk a code page in chunk 0, then a stack page in chunk 8. Chunks 2–7 stay null — no level-2 tables, no wasted RAM.

What the book says

A single-level table for a 32-bit address space, 4 KB pages, and 4-byte PTEs needs a 4 MB page table resident at all times. Figure 9.17 builds a two-level hierarchy instead. Each level-1 PTE maps a 4 MB chunk (1,024 pages). 1,024 such PTEs cover 4 GB. Each level-1 and level-2 table is itself 4 KB.

The example space: the first 2 K pages allocated for code and data, the next 6 K unallocated, then 1,023 unallocated, then one stack page. Level-1 PTEs 2–7 are null, so those level-2 tables do not exist. Only the level-1 table must stay in main memory.

Figure 9.18: a k-level walk splits the VA into k VPNs plus a VPO. The MMU reads k PTEs to find the PPN. The TLB caches PTEs at every level, so the extra walk is usually cheap.

A null level-1 PTE means that whole 4 MB chunk has no level-2 table at all.
Big idea 7 · Core i7 and Linux

Four nested drawers, then 4 KB of lockers

The book’s case study is an Intel Core i7 running Linux. The architecture could name a full 64-bit space, but the chips the book describes use a 48-bit virtual address (256 TB) and a 52-bit physical address (4 PB). Linux picks 4 KB pages.

Translation uses four page-table levels. The 36-bit VPN splits into four 9-bit indexes. Register CR3 holds the physical address of the first table and is swapped on every context switch. Linux remembers the user’s areas as a list of vm_area_structs — code, data, heap, libraries, stack — and treats a touch outside every area as a segmentation fault.

Try it: Press Walk. The VA is sliced 9+9+9+9+12. Each drawer hands you the next, until a PPN is glued to the 12-bit offset.

What the book says

Haswell allows full 64-bit spaces, but current Core i7 implementations support a 48-bit (256 TB) virtual address space and a 52-bit (4 PB) physical address space, plus a 32-bit (4 GB) compatibility mode. Figure 9.21: four cores, shared 8 MB 16-way L3; per core, 32 KB 8-way L1 i and d, 256 KB 8-way L2. TLBs are 4-way: L1 i-TLB 128, L1 d-TLB 64, L2 unified 512. Page size 4 KB or 4 MB; Linux uses 4 KB. Caches are physically addressed with 64-byte blocks.

“The Core i7 uses a four-level page table hierarchy.” CR3 holds the level-1 (page global directory) physical address and is part of process context. The 36-bit VPN is four 9-bit chunks; VPO is 12 bits; PTEs carry a 40-bit PPN plus P, R/W, U/S, XD, A (reference), and D (dirty) bits.

Figure 9.26: user code starts at 0x400000. Figure 9.27: task_struct → mm_struct (pgd, mmap) → vm_area_struct (vm_start, vm_end, vm_prot, vm_flags). Figure 9.28: a fault is illegal (no area), a protection error, or a normal page-in.

Big idea 8 · memory mapping

A photocopy, or a blank notebook of zeros

Linux fills a new stretch of virtual memory by tying it to something on disk. That tie is a memory mapping. Tie it to a regular file (say the .text of a.out) and the first touch copies that page of the file into RAM — demand paging again, no extra memcpy from the loader.

Tie it to an anonymous file (a kernel-made object of zeros) and the first touch just wipes a victim page to zeros. Nothing travels from disk. Those pages are demand-zero — heap and stack start this way. A private map can also be copy-on-write: share one copy until someone writes, then duplicate that page.

Try it: Switch File-backed and press Touch page. Bytes come from a.out. Switch Anonymous and touch: the page becomes zeros, no file read. Then press Write (CoW) to watch a shared private page split.

What the book says

Linux initializes a virtual memory area by associating it with a disk object. A regular file is split into page-size pieces; pages swap in on first touch, and extra area past the file is zero-padded. An anonymous file is all zeros; first touch overwrites a victim with zeros and marks the page resident — “demand-zero pages.” After that, pages swap against a kernel swap file.

Shared maps: writes are visible to every mapper and to the file. Private maps use copy-on-write (Figure 9.30): PTEs start read-only; a write fault copies the page, then the write retries. fork copies mm_struct, area structs, and page tables and flags everything copy-on-write. execve deletes user areas, maps private .text/.data (file-backed) plus demand-zero bss/heap/stack, maps shared libc.so, and sets the PC.

mmap(start, length, prot, flags, fd, offset) creates an area. PROT_EXEC / READ / WRITE / NONE; MAP_ANON, MAP_PRIVATE, MAP_SHARED. munmap deletes; later references segfault.

A file-backed page is born from disk. An anonymous page is born as zeros. A CoW write finally makes a private copy.
Big idea 9 · dynamic allocation

A hallway that splits and glues itself

Most programs do not call mmap by hand. They ask malloc for a piece of the heap — a demand-zero area that grows upward toward higher addresses as the kernel’s brk pointer climbs. Each piece is a block: either allocated (yours) or free (the hallway’s).

A simple allocator paints a header on every block: the size, and one bit that says taken or free. Walk the hallway by adding sizes — an implicit free list. First free stretch that fits wins (first fit). If the stretch is too long, split it. When you free, glue neighbors so the hallway does not turn into unusable crumbs.

Try it: Step the book’s tiny 16-word heap: malloc 4, malloc 5 (pads to 6), malloc 6, free the middle, malloc 2 (split). Then press Coalesce to glue the leftover crumbs, or Reset.

What the book says

The heap begins after .bss and grows toward higher addresses; brk marks the top. malloc / free are an explicit allocator. 32-bit malloc aligns to 8; 64-bit malloc aligns to 16. calloc zeros; realloc resizes; sbrk moves brk. Implicit allocators (garbage collectors) free unused blocks themselves.

Figure 9.34: a 16-word heap. malloc(4*sizeof(int)) carves 4 words; malloc of 5 words pads to 6 for double-word alignment; free leaves p2 dangling; a later malloc(2) reuses part of that hole. Figure 9.35–9.36: header encodes size | allocated bit (low 3 bits free because size is a multiple of 8). Search is linear in the number of blocks.

Placement: first fit, next fit (Knuth), best fit. Split the remainder (Figure 9.37). Immediate coalescing fights false fragmentation (Figure 9.38); boundary tags (header + footer, Figure 9.39) make all four neighbor cases constant time. The simple allocator in 9.9.12 uses a 16-byte minimum, prologue and epilogue blocks, and CHUNKSIZE of 1<<12.

Big idea 10 · C memory bugs

The wrong locker, a returned locker, a pad that overflows

C lets you name any address. Name a hole in the map, or write a read-only page, and you die at once with a segmentation or protection fault. Name a locker that happens to be writable — scanf("%d", val) instead of &val — and you may smash someone else’s data and crash hours later.

Give a heap locker back with free, then read it anyway: use-after-free. The next malloc may have handed those words to someone else. Or write past a stack pad with gets: the return address lives next door. Forgetting to free at all is a leak — quiet, until a server has no virtual memory left.

Try it: Run the scanf bug (a wild write). Switch to After free and reuse the old pointer. Switch to Overflow and type past an 8-byte pad until the return ticket dies.

What the book says

“Memory-related bugs are among the most frightening because they often manifest themselves at a distance, in both time and space, from the source of the bug.” Section 9.11 lists ten: dereferencing bad pointers (the classic scanf("%d", val) bug), reading uninitialized heap memory, stack buffer overflows (gets vs fgets), assuming pointers and objects have the same size, off-by-one errors, referencing a pointer instead of *p ((*size)-- not *size--), misunderstanding pointer arithmetic (p++ not p += sizeof(int)), referencing nonexistent stack variables, referencing data in free heap blocks, and memory leaks.

bss globals are zeroed; heap from malloc is not — use calloc. makeArray1 uses sizeof(int) instead of sizeof(int *); on a Core i7 a pointer is larger than an int, so the loop overwrites a footer and coalescing fails later. heapref frees x, then reads x[i] after y = malloc(m).

Leaks matter most in daemons and servers, which never terminate. The summary repeats the same list: bad pointers, uninitialized memory, stack overflows, size confusion, pointer-vs-object, pointer arithmetic, nonexistent variables, and leaks.

The seesaws from this chapter

Each row is a choice the hardware, the kernel, or the allocator makes. Virtual memory is the one mechanism behind all of them.

Physical addressing

CPU sends a locker number down the bus. Simple, used by Cray and many microcontrollers.

vs

Virtual addressing

CPU sends a nickname. The MMU translates, caches, and checks stamps.

SRAM cache

L1–L3, small blocks, misses from DRAM. Hardware replacement.

vs

DRAM cache

Pages of 4 KB–2 MB, fully associative, write-back, misses from disk.

One fat page table

32-bit, 4 KB, 4-byte PTE → 4 MB, always resident.

vs

Multi-level tables

Null chunks cost nothing. Only level 1 must stay in RAM.

Page-table walk

Correct, but tens to hundreds of cycles if the PTE is in DRAM.

vs

TLB hit

The PTE is already on the MMU. Translation never leaves the chip.

Shared map

One physical copy. Writes show up everywhere, and on disk.

vs

Private CoW

Share until a write. Then copy that page and let the write retry.

First fit

Fast. Leaves splinters at the front of the list.

vs

Best fit

Usually tighter. On an implicit list it scans every free block.

malloc / free

You allocate and you free. Fast, and easy to get wrong.

vs

Garbage collection

You allocate; the collector frees unreachable blocks.

Words to know

The chapter’s grown-up words, in plain language.

virtual address
The nickname the CPU issues. A translator turns it into a physical address.
physical address
The real locker number in DRAM, starting at 0.
MMU
On-chip hardware that translates addresses using the current page table.
page / page frame
A fixed-size block (virtual on disk, physical in DRAM). Typical Linux size: 4 KB.
PTE
One row of the page table: valid bit, PPN or disk address, and permission bits.
page fault
A DRAM-cache miss. The kernel pages the missing page in and restarts the instruction.
demand paging
Wait for the miss, then swap. All modern systems do this.
working set
The small set of pages a program is using right now. Too big, and it thrashes.
TLB
A tiny on-chip cache of PTEs, indexed by bits of the VPN.
VPN / VPO
Virtual page number and offset. PPO equals VPO because pages are the same size.
mmap
A system call that creates a virtual area and ties it to a file or to zeros.
demand-zero
An anonymous page, born as zeros on first touch. Heap and stack start this way.
copy-on-write
Share a read-only page until someone writes; then copy and retry.
implicit free list
Heap blocks laid end to end. Size fields are the only “links.”
SIGSEGV
The signal for a protection or segmentation fault. The shell prints “segmentation fault.”
