9.1 · physical and virtual addressing

A locker number, or a nickname a clerk rewrites

Main memory is a row of byte-size lockers. Locker 0, locker 1, locker 2. That number is a physical address. On an early PC, a microcontroller, or a Cray, the CPU puts that number on the memory bus itself. Figure 9.1 is a load of the 4-byte word at physical address 4.

A modern processor speaks a virtual address instead. Hardware on the chip, the MMU, turns it into a physical address before the bus ever sees it. That conversion is address translation. The lookup table lives in memory, and the operating system fills it in. Figure 9.2: the CPU issues 4100, the MMU writes 4, and the same word comes back.

Try it: Switch Physical, then press Load word. The CPU names locker 4. Switch Virtual and load again: the highlighted line is the virtual load, and the tag on the bus changes from 4100 to 4.

What the book says

Main memory is an array of M contiguous byte-size cells, each with a unique physical address starting at 0. Physical addressing sends that address over the memory bus. Early PCs worked this way; digital signal processors, embedded microcontrollers, and Cray supercomputers still do.

With virtual addressing the CPU generates a virtual address. The memory management unit translates it on the fly, using a table the kernel maintains. Translation, like exception handling, is hardware and the operating system working together.

9.2 · address spaces

An ordered set of nicknames

An address space is an ordered set of nonnegative integers {0, 1, 2, …}. When they sit in a row with no gaps, the space is linear. The CPU draws virtual addresses from a virtual address space of N = 2n addresses: an n-bit space. A 32-bit space and a 64-bit space are the two sizes modern systems usually offer.

Underneath sits a physical address space of M bytes, {0, 1, 2, …, M − 1}. The book treats M as 2m so the pictures stay simple. The point of two spaces: a byte can carry more than one address. One name from the virtual space, one name from the physical space.

Try it: Drag virtual bits n. The code recomputes N and the largest virtual address N − 1. Physical bits stay at m, so you can watch a virtual space grow past the real lockers.

What the book says

The size of an address space is the number of bits needed for its largest address. N = 2n virtual addresses, largest address N − 1. Physical memory has M bytes; the discussion assumes M = 2m.

Once a byte and its address are different things, each byte of main memory can have a virtual address and a physical address, chosen independently. That is the basic idea of virtual memory. Practice Problem 9.1 asks you to fill N and the largest address for a given n, using K = 210, M = 220, and so on up to E = 260.

9.3 · VM as a tool for caching

Eight books, three shelves

Conceptually the whole virtual memory is an array of N bytes stored on disk. The DRAM holds a cache of that array. Both sides are cut into fixed blocks of P = 2p bytes: virtual pages on disk, physical pages (page frames) in DRAM.

At any moment the virtual pages fall into three disjoint piles. Unallocated pages were never created, so they take no disk space. Cached pages sit in a physical page. Uncached pages are allocated and still on disk. Figure 9.3: eight virtual pages, and only some of them are in DRAM.

Try it: Press a virtual page. The code’s kind line follows your click: unallocated, cached, or uncached. The three counters under the picture are the partition.

What the book says

Figure 9.3 is a small virtual memory of eight pages. Virtual pages 0 and 3 are unallocated. Virtual pages 1, 4, and 6 are cached in physical memory. Pages 2, 5, and 7 are allocated and currently uncached.

Unallocated blocks have no data and occupy no disk. Cached pages are the DRAM-resident ones. Uncached pages are the rest of the allocated set.

9.3.1 · DRAM cache organization

A miss that costs a hundred thousand times

The book uses SRAM cache for the L1, L2, and L3 memories between the CPU and DRAM, and DRAM cache for this virtual-memory cache of pages in main memory. A DRAM is at least about 10× slower than an SRAM. A disk is about 100,000× slower than a DRAM, and the first byte of a sector costs about as much as the rest of the sector put together.

That penalty writes the rules. Pages are large, typically 4 KB to 2 MB. Any virtual page may sit in any physical page: the DRAM cache is fully associative. Replacement is careful, because evicting the wrong page is expensive. And DRAM caches always use write-back, never write-through, because a write that waited on the disk every time would be unbearable.

Try it: Press Miss on each side. The SRAM miss is served from DRAM and finishes quickly. The DRAM miss walks to disk; the code highlights write-back, full associativity, and the big page while the disk arm is still moving.

What the book says

Misses in the DRAM cache are served from disk, while SRAM misses are usually served from DRAM. The organization of the DRAM cache is driven by that cost.

Large pages, full associativity, sophisticated replacement (left as beyond the book’s scope), and write-back rather than write-through. The SRAM caches higher up the hierarchy make the opposite choices because their misses are cheap.

9.3.2 · page tables

One row per virtual page

The system has to answer three questions: is this virtual page in DRAM, which physical page holds it, and if not, where is it on disk? A page table in physical memory answers them. The MMU reads it on every translation. The kernel writes it, and the kernel moves pages between disk and DRAM.

The table is an array of page table entries. Page i lives at a fixed slot. The book’s PTE is a valid bit plus an address. Valid means the address is a physical page number in DRAM. Invalid plus a null address means unallocated. Invalid plus a disk address means allocated, waiting on disk. Figure 9.4: eight PTEs, four physical pages, and any physical page may hold any virtual page.

Try it: Press a PTE. The code reads valid and addr for that row. A green row is cached. A sun row names a disk block. A dim row is null — that page was never created.

What the book says

Figure 9.4 shows eight virtual pages and four physical pages. VP 1, VP 2, VP 4, and VP 7 are cached. VP 0 and VP 5 are unallocated (null). VP 3 and VP 6 are on disk. Because the DRAM cache is fully associative, any physical page can contain any virtual page.

Practice Problem 9.2: the number of PTEs is 2n / P. For n = 12 and P = 1 KB you need 4 entries; the book’s table continues through n = 36 and P = 1 GB.

9.3.3 · page hits

The book is already on the table

A page hit is a reference to a virtual page that is already cached in DRAM. The CPU wants a word in VP 2. The MMU uses the virtual address as an index, reads PTE 2, sees the valid bit, and builds the physical address from the physical page number stored there — PP 1 in Figure 9.5.

No disk, no kernel. The translation hardware finishes the load itself. The details of how the address is sliced live in §9.6; this section is the hit itself.

Try it: Press Step. Each press is one line of the hit: index PTE 2, test the valid bit, read PP 1, return the word. The highlighted line is the step you are on.

What the book says

Figure 9.5: the reference to a word in VP 2 is a hit. Address translation hardware locates PTE 2. The valid bit is set, so VP 2 is cached, and the PTE’s physical address points at the start of PP 1.

The MMU constructs the physical address of the requested word from that page address. The word returns to the CPU.

9.3.4 · page faults

A miss, a victim, then the instruction again

A DRAM-cache miss is a page fault. The CPU names a word in VP 3. The MMU reads PTE 3, finds the valid bit clear, and raises a page-fault exception. The kernel’s handler picks a victim — in the figure, VP 4 sitting in PP 3. If that victim was modified, the handler writes it back to disk, then updates PTE 4 so VP 4 is no longer cached.

Then it copies VP 3 from disk into PP 3, sets PTE 3 valid, and returns. The CPU restarts the faulting instruction. The second time through, the same reference is a hit. Waiting until the miss to fetch the page is demand paging. Modern systems do this.

Try it: Press Step through the fault. Watch VP 4 leave PP 3, VP 3 take its place, and the last step turn into a hit. The code panel is the handler, one line at a time.

What the book says

Figures 9.6 and 9.7: before the fault, VP 3 is on disk and VP 4 occupies PP 3. The handler victims VP 4, copies VP 3 in, and updates both PTEs. After the handler returns, the restarted instruction hits.

Demand paging loads a page only when it is touched. The transfer unit is a whole page, which is why the miss penalty in §9.3.1 pushed pages to be large.

9.3.5 · allocating pages

Create it on disk first

Allocating a page is not the same as paging it in. When the kernel creates a new virtual page — say the next piece of the heap — it reserves space on disk and points the PTE at that disk location with the valid bit still off. DRAM is left alone.

The page stays uncached until some instruction touches it. That touch is an ordinary page fault, and demand paging brings the page in. Allocation is the promise. The fault is the delivery.

Try it: Press Allocate VP 0. The PTE grows a disk address and stays invalid. Then press Touch and the fault handler finally gives it a physical page. The two code tabs are the two moments.

What the book says

The operating system allocates a virtual page by creating room on disk and updating the page table entry to point there. The page is not loaded into DRAM at allocation time.

The first reference faults, and the demand-paging machinery of §9.3.4 brings the page in. Until that reference, the PTE’s valid bit stays clear.

9.3.6 · locality to the rescue again

The working set has to fit

If every reference faulted, programs would run at disk speed. They don’t, for the same reason caches work: programs have locality. Over a short window they touch a small set of pages, the working set. As long as that set fits in DRAM, the fault rate stays tiny after the first touches.

When the working set is larger than physical memory, pages evict each other on every loop. The program spends its life in the fault handler. That collapse is thrashing.

Try it: This machine has 4 physical pages. Drag working set. At 4 and below, the loop hits after warmup. Above 4, every new touch evicts someone the loop still needs, and the fault lamp stays on.

What the book says

Locality makes demand paging practical. If the working set is resident, references hit in DRAM.

If the working set exceeds the physical pages available to the process, the program thrashes: the DRAM cache never holds the pages the loop is about to use.

9.4 · VM as a tool for memory management

One map per process, four jobs get easier

So far one page table mapped one space. Real kernels keep a separate page table, and so a separate virtual address space, for every process. Figure 9.9: process i maps VP 1 → PP 2 and VP 2 → PP 7; process j maps VP 1 → PP 7 and VP 2 → PP 10. Two virtual pages can share one physical page.

Separate spaces plus demand paging simplify four jobs. Linking: every 64-bit Linux process can start its code at 0x400000, because the linker never has to know the physical address. Loading: the loader maps .text and .data at invalid PTEs aimed at the file, and never copies a byte. Sharing: one physical copy of a library, many maps. Allocation: k contiguous virtual pages may sit in k scattered physical pages.

Try it: Press each job. The picture and the code tab change together: the linker’s fixed 0x400000, the loader’s map-not-copy, the shared physical page, and a contiguous virtual run on scattered frames.

What the book says

Even a machine whose virtual space was smaller than its physical memory, such as the DEC PDP-11/70, wanted virtual memory, because management and protection got simpler.

Figure 9.9 is the two-process picture. Linking uses a uniform layout (code at 0x400000 on 64-bit Linux, data after an alignment gap, stack at the top growing down). Loading allocates virtual pages and points PTEs at the object file. Sharing maps one physical page into several spaces. Allocation hands an application contiguous virtual pages without finding contiguous physical pages.

9.5 · VM as a tool for memory protection

Three stamps on every page

The same PTE that names a room can refuse the visit. The book adds three permission bits: SUP (kernel only), READ, and WRITE. A user process must not modify its read-only code, must not touch kernel memory or another process’s private pages, and must not write a shared page unless everyone agreed.

The MMU checks the bits on every access. Kernel mode may use any page. User mode may use only pages with SUP = 0, and only for the operations whose bits are set. A violation is a general protection fault. The handler sends SIGSEGV. A Linux shell usually prints “segmentation fault.”

Try it: Stay in user mode. Read VP 0 is allowed. Write VP 1 is allowed. Write VP 0 or anything on VP 2 faults, and the code takes the SIGSEGV branch. Switch to kernel and the same write on VP 2 succeeds.

What the book says

Figure 9.10 adds SUP, READ, and WRITE to each PTE. In the example, process i in user mode may read VP 0 and read or write VP 1. It is not allowed to access VP 2.

A violating instruction triggers a general protection fault. The kernel sends SIGSEGV, which shells report as a segmentation fault.

9.6 · address translation

Split the nickname, glue a new prefix

A virtual address breaks into a virtual page number (VPN) and a virtual page offset (VPO). The VPN selects the PTE. On a hit the MMU concatenates the stored physical page number (PPN) with the same offset bits, now called the physical page offset (PPO). PPO equals VPO because both pages are P bytes.

The page table base register (PTBR) points at the current process’s table, so PTE address = PTBR + VPN × sizeof(PTE). Figure 9.13(a) is five hardware steps for a hit. Figure 9.13(b): a clear valid bit raises a fault; the kernel updates the PTE and the instruction restarts. The MMU also sets a reference bit on use and a dirty bit on writes, when the PTE has them.

Try it: This toy uses 8-bit virtual addresses and 16-byte pages. Press Step on VA 0x2A. The code shifts out the VPN, and the readout shows PTE 2’s PPN glued back onto the offset. Switch to fault for the restart path.

What the book says

Figure 9.12: VA = VPN concatenated with VPO, PA = PPN concatenated with PPO, and PPO is identical to VPO. The MMU uses the VPN as an index into the page table identified by the PTBR.

A page hit is handled entirely by hardware. A page fault transfers to the kernel handler, which selects a victim, pages it out if dirty, pages the missing page in, updates the PTE, and returns to the faulting instruction.

9.6.1 · integrating caches and VM

Translate first, then ask the cache

SRAM caches and virtual memory have to agree on which address the cache sees. Most systems choose physical addressing for the cache. Translation happens, protection bits are checked, and only then does the cache look up the physical address. Several processes can keep blocks in the cache, and they can share a block that comes from the same physical page.

Figure 9.14 draws the order. The MMU may itself miss or hit when it fetches the PTE — PTEs are ordinary data words and can sit in the cache. Then the data request, now a physical address, hits or misses in the cache on its own.

Try it: Press Step. The request walks VA → PTE address → PTE → PA → cache. The two lamps are independent: the PTE can hit while the data misses, or the other way around. The code comments name each arrow.

What the book says

Whether an SRAM cache is virtually or physically addressed is a real design choice. Physical addressing makes sharing and protection straightforward, because rights are checked during translation.

Figure 9.14: address translation occurs before the cache lookup. Page table entries can be cached just like other data words, so a PTE fetch has its own hit/miss.

9.6.2 · speeding up translation with a TLB

A tiny notebook of recent PTEs

Every virtual address needs a PTE. In the worst case that is another memory fetch, tens to hundreds of cycles. If the PTE is in L1 it is only a handful. A translation lookaside buffer tries to make it zero trips off the MMU: a small, virtually addressed cache whose block is a single PTE, usually highly associative.

If the TLB has T = 2t sets, the TLB index (TLBI) is the t low bits of the VPN, and the TLB tag (TLBT) is the rest. A hit builds the physical address inside the MMU. A miss fetches the PTE from the cache/memory path, then writes it into the TLB. A further miss with valid = 0 is still a page fault.

Try it: Press TLB hit and the lookup never leaves the chip. Press TLB miss and the code fetches the PTE, fills the set, and only then builds the PA. The bit strip shows TLBT and TLBI cut out of the VPN.

What the book says

A TLB is a small, virtually addressed cache where each line holds one PTE. TLBI selects the set; TLBT is compared with the tags in that set.

Figure 9.16: a hit stays inside the MMU. A miss brings the PTE in from L1 or memory and installs it. The page-fault path is unchanged: a PTE with a clear valid bit still traps.

9.6.3 · multi-level page tables

A city book, then a street book

One flat table for a 32-bit space, 4 KB pages, and 4-byte PTEs is 4 MB, and it would have to stay resident even if the process used a handful of pages. A two-level table fixes the tax. Each level-1 PTE covers a 4 MB chunk (1,024 pages). If the chunk is empty, the level-1 entry is null and the level-2 table is never created.

Only the level-1 table must sit in memory. Level-2 tables can be paged like anything else. A k-level walk splits the VPN into k indexes plus a VPO; the MMU reads k PTEs to find the PPN. The TLB caches PTEs from every level, so the extra reads are usually avoided.

Try it: Press Code page (chunk 0) and Stack page (the high chunk). Chunks in the middle stay null — the code prints NULL and no level-2 table appears. That is the memory you did not spend.

What the book says

Figure 9.17: 1,024 level-1 PTEs cover 4 GB, and each level-1 or level-2 table is itself 4 KB. The example allocates the first 2 K pages for code and data, leaves a huge hole, and maps one stack page at the top. Level-1 PTEs for the hole are null.

9.6.4 · end-to-end address translation

VA 0x03d4, by hand

The book’s small machine: byte addresses, 1-byte accesses, n = 14 virtual bits, m = 12 physical bits, pages of P = 64 bytes. The TLB is 4-way set associative with 16 entries (4 sets). The L1 data cache is physically addressed, direct-mapped, 16 sets, 4-byte lines.

So the low 6 bits are VPO and PPO. The high 8 bits of the VA are the VPN. TLBI is the low 2 bits of the VPN. The cache splits a physical address into a 6-bit tag, a 4-bit set index, and a 2-bit offset. 9.7 · Core i7 / Linux memory system

What one real chip actually has

The case study is an Intel Core i7 running Linux. The chips the book describes implement a 48-bit virtual address (256 TB) and a 52-bit physical address (4 PB), plus a 32-bit compatibility mode. A full 64-bit virtual space is allowed by the architecture and left unused by these implementations.

Each core has its own L1 and L2; the cores share an L3. The book’s Haswell-class picture: 32 KB 8-way L1 instruction and data caches, 256 KB 8-way L2, and a shared 8 MB 16-way L3, with 64-byte blocks, physically addressed. TLBs are 4-way: an L1 i-TLB of 128 entries, an L1 d-TLB of 64, and a unified L2 TLB of 512. Pages may be 4 KB or 4 MB. Linux uses 4 KB.

Try it: Press a block — L1, L2, L3, or a TLB. The code record for that cache updates: size, associativity, and what it holds. The page-size line stays on 4 KB, which is the choice the rest of the case study assumes.

What the book says

Current Core i7 implementations support a 48-bit virtual address space and a 52-bit physical address space. Figure 9.21 shows four cores, private L1 and L2 caches, and a shared L3.

The TLBs cache PTEs. The data caches are physically addressed with 64-byte blocks. Linux on this system uses 4 KB pages, so the low 12 bits of an address are the page offset.

9.7.1 · Core i7 address translation

Four 9-bit drawers, then 12 offset bits

Each process has a private four-level page table. While a Linux process runs, the tables for its allocated pages stay resident (the hardware would allow them to be swapped). CR3 holds the physical address of the level-1 table, the page global directory, and CR3 is swapped on every context switch.

The 36-bit VPN is four 9-bit indexes. The VPO is 12 bits. A level-1, 2, or 3 PTE points at the next 4 KB table; a level-4 PTE points at a 4 KB data page. Permission bits include P, R/W, U/S, and XD (execute-disable). The MMU sets A (accessed) on use and D (dirty) on writes. The PPN field is 40 bits.

Try it: Press Walk. The code indexes one level per line, starting from CR3. Then press a permission chip — R/W, U/S, XD, A, D — and that field lights in the level-4 PTE picture and in the struct.

9.7.2 · Linux virtual memory system

A list of areas, and three kinds of fault

Linux keeps a process’s virtual memory as a list of areas. task_struct points at mm_struct, which holds pgd (the level-1 table, loaded into CR3) and mmap, the head of a list of vm_area_struct records. Each area stores vm_start, vm_end, vm_prot, and vm_flags (read, write, execute, shared, private).

User code on the book’s 64-bit Linux starts at 0x400000. Above it: data, the heap growing up, a gap, shared libraries, and the stack growing down from the top of the user space. A fault looks the area up. No area: the address is illegal. An area whose protection refuses the access: protection exception. A legal area whose page is not resident: the kernel pages it in.

Try it: Press an address. The code walks the area list. 0x400100 is code. 0x1000 falls in no area and dies. A write to code is a protection fault. A first touch of the heap is a normal page-in.

9.8 · memory mapping

Tie a stretch of the map to an object

Linux fills a new virtual memory area by associating it with an object on disk. That association is a memory mapping. Map it to a regular file, such as a slice of an executable, and the file is cut into page-size pieces that become the initial contents. Nothing is copied until the CPU first touches the page. If the area is longer than the file, the tail is zeros.

Map it to an anonymous file — a kernel object of pure zeros — and the first touch finds a victim page, overwrites it with zeros, and marks it resident. No bytes move from disk. Those are demand-zero pages. Heap and stack begin this way. After initialization, pages swap against a kernel swap area, which bounds how much virtual memory the running processes can have allocated.

9.8.1 · shared objects revisited

One libc in RAM, many maps

A shared object such as libc.so is mapped into every process that needs it. The code pages are a shared mapping: one physical copy, and a write would be visible to everyone (the dynamic linker does not ask processes to write the code).

The library’s data pages are a private mapping. Page tables start by sharing the physical page, marked read-only. The first write traps, the kernel copies that page, and the write retries on the private copy. That is copy-on-write. Processes share the clean page and split only the pages they dirty.

Try it: Press Map libc. Both processes point at one code page and one data page. Press Write data in process j. Only j’s data PTE swings to a new physical page. The code page stays shared, and the .text line in the panel stays on the shared mapping.

What the book says

Shared objects are mapped into the virtual address space. Instruction pages are shared. Writable data uses private copy-on-write so each process can keep its own globals.

9.8.2 · the fork function revisited

The child borrows pages until it writes

9.8.3 · the execve function revisited

Throw the map away and build a new one

9.9 · dynamic memory allocation

A hallway that grows toward the stack

The heap is the demand-zero area just after .bss. It grows toward higher addresses as the kernel’s brk pointer climbs. An allocator hands pieces of that hallway to the program. An explicit allocator, such as malloc, frees a block only when the program says so. 9.9.1 · malloc and free

Ask for words, hand them back

malloc(size) returns a pointer to a block of at least size bytes, aligned for any object: multiples of 8 in 32-bit mode, multiples of 16 in 64-bit mode. It does not initialize the bytes. Failure returns NULL and sets errno. calloc is malloc plus zero-fill. realloc resizes an existing block. The allocator grows the heap with sbrk or with mmap.

free(ptr) releases a block that came from malloc, calloc, or realloc. The pointer must be the start of that block. free returns nothing, so a bad pointer fails quietly, later. 9.9.2 · why dynamic memory allocation?

The size arrives with the input

9.9.3 · allocator requirements and goals

Immediate, aligned, and not allowed to slide

An explicit allocator has hard constraints. It must answer every request at once — it cannot reorder the program to get a tidier layout. It may use only the heap. Blocks must be aligned. Allocated blocks must not overlap. And it must not move an allocated block, because the program is holding a pointer into it.

Inside those rules it chases two goals: throughput (allocate and free return quickly) and utilization (as much of the heap as possible holds payload, not headers and holes). The two goals pull apart. A perfect pack is slow. A fast first-fit leaves crumbs.

Try it: Press Request to drop in another allocated block. Press Slide blocks — the machine refuses, and the code comment says why a live pointer forbids compaction. The utilization number is payload bytes over heap bytes.

What the book says

Constraints: immediate response, heap memory only, alignment, no overlap, and no relocation of allocated blocks.

Goals: maximize throughput and peak memory utilization. An allocator is judged by how close it gets to both at once.

9.9.4 · fragmentation

Waste inside a block, or crumbs between them

Internal fragmentation is space inside an allocated block that the payload does not use: padding for alignment, and the header the allocator needs. A request for 5 words that must be a multiple of 2 becomes 6. The extra word is internal.

External fragmentation is free space that is large enough in total and too small in any one hole. Two free blocks of 4 cannot satisfy a request for 6, even though 8 words are free. Coalescing and placement policy are how allocators fight it. External fragmentation is why utilization falls even when free bytes remain.

Try it: On Internal, allocate 5 and watch the pad. On External, the heap is free 4, allocated, free 4. Press malloc 6. Eight words are free and the request still fails. The code is the test each policy is doing.

What the book says

Internal fragmentation is padding and allocator overhead charged to an allocated block. It depends on the pattern of previous requests and on alignment.

External fragmentation is free memory split into holes too small for the next request. The total free space can exceed the request and still be unusable.

9.9.6 · implicit free lists

The size field is the only link

An implicit free list lays blocks end to end. Each block starts with a header: the block size, and an allocated bit. Because sizes are multiples of 8, the low 3 bits are free for flags; the allocated bit lives in the low bit. The next block starts at this address plus the size. There is no pointer. The size is the link.

Finding a free block means walking every block, allocated and free, until a free one fits. Search time grows with the total number of blocks, not the number of free ones. A special epilogue header marks the end.

Try it: Press Next block. The walker adds the header’s size and lands on the next header. The code is that addition. Allocated blocks are opaque payload; only the header is the allocator’s.

What the book says

The heap is a sequence of blocks. Given a header address p, the next header is p + size(p). A zero-size allocated epilogue can terminate the walk.

9.9.7 · placing allocated blocks

First hole, next hole, or tightest hole

First fit walks from the start and takes the first free block that fits. It is fast and tends to leave small splinters at the front. Next fit starts where the previous search stopped, so it spreads the splinters; Knuth studied it. Best fit examines every free block and takes the tightest fit. It wastes less and, on an implicit list, it always scans the whole heap.

Try it: The heap is free 8, allocated 4, free 6, allocated 4, free 10. Press a policy for a request of 5. First fit takes the 8. Next fit, with the rover past the first hole, takes the 6. Best fit takes the 6 as well — the tightest. The code is the comparison each policy makes.

What the book says

First fit searches from the beginning. Next fit searches from the last place a block was found. Best fit searches the entire free set for the smallest block that fits.

On an implicit list, best fit and a full first-fit scan have the same asymptotic cost. The difference is which block they return.

9.9.10 · coalescing free blocks

Glue the neighbors or drown in crumbs

There are four neighbor shapes: both sides allocated, only the previous free, only the next free, or both free. With only a header, finding the previous block’s size means walking from the start of the heap. The next subsection removes that walk.

9.9.13 · explicit free lists

Pointers that live only inside free blocks

9.9.14 · segregated free lists

A bin for each size

A segregated free list keeps several explicit lists, one per size class. A request looks in the smallest class that might fit, then in larger classes. Simple segregated storage never splits: a block freed from a class returns to that class, and a miss in every class asks the kernel for more blocks of that size. It is fast and can waste a whole block when the request was much smaller.

Segregated fits allow splitting and coalescing. The allocator searches the size class, takes a block, splits the remainder into the class it belongs in, and on free coalesces and puts the result in the class of its new size. A buddy allocator is this idea with power-of-two sizes, so the address of a buddy is a bit flip.

Try it: Press malloc 40. The 16-bin and 32-bin are too small. The 64-bin hits, the block splits, and the remainder drops into the 16-bin. The code is that search from the fitting class upward.

What the book says

Segregated storage approximates best fit without a full scan: the first block in the right size class is already a good fit. Simple segregated storage does not split or coalesce across classes.

Segregated fits do split and coalesce, then refile the resulting block by its new size. GNU malloc and many production allocators are variants of segregated fits.

9.10.2 · Mark&Sweep collectors

Mark what you can reach, sweep the rest

A Mark&Sweep collector, the kind McCarthy used for Lisp, has two phases. Mark starts at the roots and sets a mark bit on every reachable allocated block, following pointers stored in those blocks. Sweep walks the heap and frees every allocated block that is still unmarked, then clears the marks on the survivors.

The mark bit is a spare low bit in the header, the same kind of bit the allocator already uses for the allocated flag. The book’s pseudocode is mark, which returns when a word is not a pointer or the block is already marked, and sweep, which walks with nextBlock until the end of the heap.

What the book says

After sweep, the free list holds the garbage and the marked bits are clear for the next collection.

9.10.3 · conservative Mark&Sweep for C

An integer that looks like a pointer

C does not tag words as pointers or integers. A collector cannot know. A conservative collector treats any word that looks like a pointer into an allocated block as a pointer. If it is wrong, it keeps a block that was actually garbage. It never frees a block that is still live, because a real pointer still looks like a pointer.

The cost is leftover garbage. The guarantee is safety. That is why a C collector cannot compact the heap either: it might update a word that was an integer, not a pointer. The blocks stay where malloc put them.

Try it: The word in the root is the integer 100. Press Conservative: 100 looks like a pointer at block B, so B survives. Press Precise: the collector knows 100 is an int, B is garbage, and sweep frees it. The code is the looks_like_ptr test.

What the book says

A conservative collector identifies pointers by whether a bit pattern is a plausible address into an allocated block. Ambiguous words are treated as pointers.

The collector may fail to free some garbage. It will not free a live block. Because it cannot be sure which words are pointers, it also cannot relocate blocks.

malloc does not zero

The loader zeros .bss, so uninitialized globals start at 0. Heap memory from malloc does not. The book’s matvec does y[i] += A[i][j] * x[j] on a block malloc just returned. y[i] begins as whatever bits were in that page.

The sum is wrong and the program often still “works.” calloc, or an explicit zeroing loop, is the repair.

Try it: Press Dot. Each y[i] += adds the product onto garbage, and the total wanders. Switch the code to calloc and the same loop starts from zero.

9.11.4 · pointers and the objects they point to

sizeof(int) is not sizeof(int *)

The book’s makeArray1 allocates an array of n pointers with n * sizeof(int). On a machine where a pointer is larger than an int — 8 bytes and 4 bytes on the Core i7 the book uses — the array is half as long as the loop believes.

The loop writes past the block, into the next block’s header or footer. Much later, coalescing reads a corrupted size and the allocator falls over. The distance is the point.

Try it: Press Allocate. The block is n ints wide. Press Fill pointers and watch the writes cross the true end into the neighbor footer. The fixed tab uses sizeof(int *).

*size-- moves the pointer

Unary operators associate right to left, so *size-- is *(size--). The book’s heap-delete decrements the pointer size and dereferences the old value. The integer it meant to shrink does not change.

9.11.7 · misunderstanding pointer arithmetic

p += sizeof(int) skips ints

Pointer arithmetic scales by the pointee. If p is int *, p++ advances one int. p += sizeof(int) advances sizeof(int) ints — 4 ints on the book’s 32-bit int — and most of the array is never written.

People write the byte stride because they are thinking of the address as a char *. The type already carries the stride.

Try it: Press Step on the bug. The cursor jumps four ints. Switch to p++ and it visits every slot.

9.11.8 · referencing nonexistent variables

A local dies with its frame

Returning &val from a function hands the caller an address on a frame that ret just popped. The slot will be reused by the next call.

9.11.10 · introducing memory leaks

A block with no pointer left

A leak allocates a block and drops the only pointer to it — a local that returns, or a pointer overwritten by the next malloc. The block is still allocated, so a collector that only frees unreachable blocks would catch it, but malloc/free will not. The heap only grows.

Short programs get away with it. A server that loops forever eventually exhausts virtual memory, including swap. Free the block, or keep a pointer you can free later.

Try it: Press Request to leak one block per click. The free list never sees them. Press free on the fixed tab and the same loop returns the block.

9.12 · summary

One mechanism, three jobs

Virtual memory is a single machine with three jobs. As a cache, the valid bit and the disk address decide which pages of a larger address space occupy DRAM. As a manager, a private page table gives every process the same layout and lets scattered physical pages look contiguous. As a guard, the permission bits fault illegal accesses.

The second half of the chapter is what programs do with that machine: mmap, the heap allocators from implicit lists to segregated fits, a Mark&Sweep collector, and the C mistakes that poke the map in the wrong place.

Try it: Press Cache, Manage, or Protect. The same PTE lights a different field, and the struct in the code panel highlights that field. One entry, three reasons it exists.

What the book says

The summary restates the cache, memory-management, and protection roles, then the address-translation path from VPN and TLB through multi-level tables.

It closes on dynamic allocation and the catalog of memory bugs: bad pointers, uninitialized memory, stack overflows, size confusion, pointer-versus-object errors, pointer arithmetic, nonexistent variables, and leaks.

Words to know

The chapter’s names, in plain language.

virtual address
The number the CPU issues. The MMU turns it into a physical address.
physical address
The locker number in DRAM, starting at 0.
MMU
On-chip hardware that translates addresses with the current page table.
page / page frame
A fixed-size block. Virtual pages live in the address space; physical pages are DRAM frames. Linux uses 4 KB.
PTE
One page-table row: a valid bit, a physical page number or a disk address, and permission bits.
page fault
A DRAM-cache miss. The kernel brings the page in and restarts the instruction.
demand paging
Wait until a miss, then fetch. Allocation only reserves the page on disk.
working set
The pages a program is touching now. Larger than DRAM, and the program thrashes.
TLB
A small on-chip cache of page-table entries, indexed by bits of the VPN.
VPN / VPO
Virtual page number and offset. The offset equals the physical offset because pages match in size.
copy-on-write
Share a read-only page until a store, then copy that page and retry the store.
demand-zero
An anonymous page, born as zeros on first touch. Heap and stack start this way.
vm_area_struct
Linux’s record for one contiguous region: start, end, protection, and shared or private.
implicit free list
Heap blocks laid end to end. The size in the header is the only link.
boundary tag
A footer that repeats the header, so the previous block’s size is one word back.
external fragmentation
Free bytes split into holes too small for the next request.
Mark&Sweep
Mark every block reachable from roots, then free the unmarked allocated blocks.
SIGSEGV
The signal for a bad or forbidden virtual address. Shells print “segmentation fault.”
