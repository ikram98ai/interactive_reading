Optimizing Program Performance

The same sum can take ten cycles per number, or half a cycle. The chip is already fast. The job is to stop asking it to redo work, and to stop making it wait.

Big idea 1 · compilers

Two sticky notes, or one note with two names

Priya has two notes, xp and yp. Kenji’s recipe says: add the second note to the first, twice. That looks the same as adding double the second note, once. If the notes are different, both recipes finish at the same number — but the short one only touches memory three times, not six.

If both names point at the same note, they disagree. Adding a number to itself twice multiplies by four. Adding double once multiplies by three. The compiler cannot see Priya’s fingers, so it must assume the names might be twins. That is memory aliasing, and it is an optimization blocker.

Function calls block it too. func1 adds f() four times. func2 does 4*f(). If f ticks a counter, those are not the same answer.

Try it: Toggle alias so both pointers share one cell, then run twiddle1 and twiddle2. Switch to calls and compare func1 with func2.

What the book says

gcc with -Og applies a basic set of optimizations; -O1 and higher do more. The chapter mostly measures -O1, even though -O2 is the usual project default. Compilers may apply only safe optimizations: the result must match an unoptimized program for every case the C standard allows.

twiddle1 does *xp += *yp twice (six memory references). twiddle2 does *xp += 2 * *yp (three). “The compiler knows nothing about how twiddle1 will be called, and so it must assume that arguments xp and yp can be equal.” When they are equal, twiddle1 scales *xp by 4 and twiddle2 scales it by 3.

“If a compiler cannot determine whether or not two pointers may be aliased, it must assume that either case is possible, limiting the set of possible optimizations.” The other blocker is calls. With counter starting at 0, func1 returns 0+1+2+3 = 6 and func2 returns 0. gcc inlines only functions defined in the same file (-finline or -O1 and higher).

Safe vs tempting
If the two pointers might be the same cell, gcc will not rewrite twiddle1 as twiddle2.
Big idea 2 · CPE

The slope is the thing you can fix

Mei times a stamp machine. Lighting the lamp costs a fixed pile of ticks. After that, each extra ticket adds a steady number of ticks. For a long queue, the start-up pile barely matters. The slope does.

That slope is CPE — cycles per element. The book’s prefix-sum psum1 costs about 368 + 9.0n cycles. psum2 stamps two tickets per trip and costs 368 + 6.0n. Same intercept, kinder slope.

Try it: Slide n and watch both lines. Press Play to walk n upward. The gap is 3n cycles — never the 368.

What the book says

A 4 GHz clock is 4.0×109 cycles per second: period 0.25 nanoseconds, or 250 picoseconds. Cycles beat wall-clock units because they count work, not how fast the crystal ticks.

Figure 5.1: psum1 writes one prefix per iteration; psum2 uses 2-way loop unrolling. A least-squares fit of Figure 5.2 gives 368 + 9.0n and 368 + 6.0n. The 368 is timing code plus setup. “We focus our efforts on minimizing the CPE for our computations.”

By that measure psum2 (CPE 6.0) beats psum1 (CPE 9.0). Practice 5.2 later gives three combine-style fits: 60 + 35n, 136 + 4n, and 157 + 1.25n.

CPE is the slope. The 368-cycle intercept is the same on both lines.
Big idea 3 · combine1

A header, a row of lockers, a running answer

Omar’s class stores a vector as two pieces: a header (len and a pointer data) and a row of lockers. The combining function folds every locker into one answer. IDENT 0 and OP + make a sum. IDENT 1 and OP * make a product.

combine1 is the polite, abstract version. Every trip around the loop it asks vec_length again, then calls get_vec_element, which checks the index against the ends. Safe. Slow.

Try it: Pick sum or product, then Step through the four lockers. Watch dest update, and count the extra questions.

What the book says

Figure 5.3–5.4: vec_rec holds long len and data_t *data. data_t is compiled as int, long, float, or double. get_vec_element returns 0 on an out-of-range index. The book notes this style is similar to Java arrays: safer, and slower.

Figure 5.5 combine1 writes *dest = IDENT, then on each i from 0 to vec_length(v) it fetches val and does *dest = *dest OP val. Reference machine: Intel Core i7 Haswell. Integer 32-bit and 64-bit matched (except division); float matched double.

Unoptimized CPE: integer + 22.68, integer * 20.02, float + 19.98, float * 20.18. With -O1: 10.12, 10.12, 10.17, 11.14 — more than 2× with no rewrite. The book leaves the messy hundredths; the more likely CPE for integer sum is 23.00 rather than 22.68. Later measurements use -O1 and -O2.

        Big idea 4 · code motion
        
Do not recount the banner for every letter

        
Fatima lowercases a shouty banner. The slow recipe, lower1, measures the whole banner with strlen before every letter. strlen itself walks until it finds a zero. For n letters that is about n walks of length n — time like n².

        
lower2 measures once, stores len, and walks once. Same letters. Different universe. For 1,048,576 characters the book timed 17 minutes versus 2.0 milliseconds.

        
Try it: Step the slow recipe and watch the length-walker restart. Switch to hoist and the walker goes once. Slide n to see n² versus n.

        

          What the book says
          

            
combine2 moves vec_length out of the loop test into local length — code motion. Integer + CPE falls from 10.12 to 7.02; integer * from 10.12 to 9.03; float + 10.17 to 9.02; float * 11.14 to 11.03. Compilers stay cautious about moving calls: a side effect in vec_length would change the meaning.

            
Figure 5.7: lower1 calls strlen in the for test; lower2 hoists it. Figure 5.8(b): for length 1,048,576, lower1 takes 1,049.89 seconds and lower2 takes 0.0020 seconds, over 500,000 times faster. Each doubling of n quadruples lower1’s time.

            
“For a string of length 1,048,576, lower1 requires over 17 minutes of CPU time.” Even an inlining compiler cannot prove the string never gains or loses a zero in the middle. The programmer has to hoist.

        Big idea 5 · procedure calls
        
Stop asking the clerk for every jar

        
Yara still calls get_vec_element on every locker. That clerk checks whether i sits between 0 and len every time — useful for a stranger, silly once you have already proved the walk stays in range.

        
combine3 asks once for the shelf address (get_vec_start) and then reads data[i] itself. A modularity purist winces. The clock barely notices: integer + even gets a little worse, 7.02 to 7.17. The next bottleneck is still sitting there. This rewrite is a door, not the prize.

        
Try it: Step combine2 (clerk every time) then switch to combine3 (direct lockers). Count calls. Watch CPE refuse to fall.

        

          What the book says
          

            
Figure 5.9 adds get_vec_start, which returns v->data. combine3 hoists length and data, then does *dest = *dest OP data[i] with no call in the inner loop.

            
CPE after the change: integer + 7.17 (slightly worse than combine2’s 7.02), integer * 9.02, float + 9.02, float * 11.03. “Surprisingly, there is no apparent performance improvement.” Section 5.11.2 later shows the bounds checks were highly predictable, so they were not the limiter.

            
The transformation still matters: it enables the memory-reference rewrite that follows. The book treats it as one step in a chain, not a win by itself.

        Big idea 6 · memory references
        
Keep the running total in your head

        
Tomas writes the soup total back on the fridge after every spoon. The inner loop of combine3 does the same: read *dest, combine, write *dest. For double × that is vmovsd, vmulsd, vmovsd — two reads and a write per locker.

        
combine4 keeps a local acc and writes *dest once, after the loop. The compiler can park acc in %xmm0. Integer + drops to 1.27 CPE — about 5.7×. gcc will not do this to combine3 for you: dest might be one of the lockers.

        
Try it: Step combine3 and watch dest memory flicker. Switch to combine4 and only acc moves. Then open the alias case: vector [2, 3, 5] with dest at the last locker.

        

          What the book says
          

            
Figure 5.10: local acc = IDENT, then acc = acc OP data[i], then *dest = acc. combine3 CPE 7.17 / 9.02 / 9.02 / 11.03 becomes combine4 1.27 / 3.01 / 3.01 / 5.01 — factors from 2.2× to 5.7×.

            
Let v = [2, 3, 5] and dest alias the last element. combine3 writes 1, then 2, then 6, then 36. combine4 leaves the vector alone until the end and writes 30. “The two functions can have different behaviors due to memory aliasing.”

            
With -O2, gcc’s combine3 keeps the product in %xmm0 and still stores to dest each iteration (CPE 1.60 / 3.01 / 3.01 / 5.01). Practice 5.4 asks whether that still matches aliasing combine3.

        Big idea 7 · modern processors
        
A kitchen with eight stations, and a waiting line

        
Aisha’s kitchen can start more than one job per tick, and not always in menu order — superscalar and out of order. From the recipe it still looks like one instruction after another. Inside, a hundred operations can be in flight.

        
Two ceilings matter. The latency bound is how long a job that needs the previous answer must wait (float × takes 5 cycles). The throughput bound is how fast the stations can start independent jobs (two loads per cycle → CPE 0.50). combine4 sits on the latency ceiling, except integer + at 1.27 instead of 1.00.

        
Try it: Pick an operation and press Fire. Watch a token wait L cycles on one chain. Switch to stations to see which Haswell units can do the work.

        

          What the book says
          

            
Figure 5.11: instruction control unit (fetch, predict, decode) and execution unit (functional units, load/store, data cache). Haswell has eight units: 0 integer / float * / ÷ / branches; 1 integer / float + / integer * / float *; 2–3 load; 4 store; 5 integer; 6 integer / branches; 7 store address. A store needs two units.

            
Figure 5.12 latency / issue / capacity: integer + 1, 1, 4; integer * 3, 1, 1; integer ÷ 3–30; float + 3, 1, 1; float * 5, 1, 2; float ÷ 3–15. Issue 1 means fully pipelined. Latency bounds 1.00 / 3.00 / 3.00 / 5.00. Throughput bounds 0.50 / 1.00 / 1.00 / 0.50 (the 0.50 from two load units).

            
combine4 CPE 1.27 / 3.01 / 3.01 / 5.01 matches latency except integer +. 20 × 20 unrolling spills (16 integer registers, 16 YMM): some CPEs get worse. A mispredict on the reference machine cost about 19 cycles. combine4b’s predictable bounds checks barely move the latency-bound cases. minmax1 on random data: CPE about 13.5; minmax2 with conditional moves: about 4.0.

        Big idea 8 · loop unrolling
        
Two letters per trip, same waiting line

        
Soren used to walk to the mailbox once per letter. combine5 carries two: acc = (acc OP data[i]) OP data[i+1], then a short cleanup loop. Fewer trips. Less loop overhead.

        
Integer + finally hits its latency bound: 1.27 becomes 1.01. The other three stay put at 3.01 / 3.01 / 5.01. Why? Each iteration still does two combines in a chain. Half as many trips, still n multiplies in a line. gcc can unroll at -O3; the dependency does not care.

        
Try it: Step the 2 × 1 loop. Watch i jump by 2, and watch acc wait for the first combine before the second.

        

          What the book says
          

            
Figure 5.16: 2 × 1 unrolling. Limit is length - 1; i steps by 2; a tail loop finishes 0 or 1 leftover. For factor k the limit is n − k + 1.

            
CPE: combine4 1.27 / 3.01 / 3.01 / 5.01; combine5 1.01 / 3.01 / 3.01 / 5.01; 3 × 1 same as 2 × 1 on the last three. Figure 5.17: unrolling to k = 10 never beats the latency bound. The data-flow still has n sequential muls.

            
The inner loop becomes two vmulsds into the same %xmm0. Pointer-based versus array-based code did not change times on the reference machine. gcc may pick wildly different shapes from small source edits.

        Big idea 9 · ILP
        
Two running totals, or a sneakier pair of parentheses

        
Lucia and her twin each keep a product: even lockers in acc0, odd in acc1, then one combine at the end. That is combine6, 2 × 2 unrolling. The waiting line is n/2 long. Float × CPE falls from 5.01 to 2.51 — through the latency wall.

        
combine7 only moves parentheses: acc OP (data[i] OP data[i+1]). The first multiply does not need yesterday’s acc, so the critical path is again n/2. Integers are associative even on overflow. Floats are not; a wild mix of huge and tiny values could overflow one half. Most compilers will not reassociate floats for you.

        
Try it: Step 2 × 2 and watch both accumulators. Switch to reassociate and watch the pair multiply first, then acc.

        

          What the book says
          

            
combine6 CPE 0.81 / 1.51 / 1.51 / 2.51. combine7 (2 × 1a) 1.01 / 1.51 / 1.51 / 2.51. k × k needs k ≥ C · L to fill the pipes: float × wants k ≥ 10; float + wants k ≥ 3. 10 × 10 reaches 0.55 / 1.00 / 1.01 / 0.52 — near the throughput bounds. Integer + hits 0.54 at k = 7.

            
“We have broken through the barrier imposed by the latency bound.” Two’s-complement + and * stay associative; “floating-point multiplication and addition are not associative.” gcc may reassociate integers, not always helpfully.

            
Section 5.10: from combine1 at 10.12–11.14 down to 10 × 10 near 0.50–1.00 is a 10–20× scalar gain. With AVX vector code, single-precision * went from 11.14 to 0.06, over 180×. 20 × 20 spills and some CPEs worsen (0.83 / 1.03 / 1.02 / 0.68).

        Big idea 10 · limits
        
When memory is the queue, or the tallest bar

        
A treasure map where each box names the next one cannot go faster than a load. list_len walks ls = ls->next. The book measured CPE 4.00 — the L1 load latency. Stores are different: write_read is fine (CPE 1.3) until src and dest are the same cell (CPE 7.3). The load must wait for the store buffer.

        
On a big program you first find the tall bar. A gprof run on Shakespeare’s bigrams spent 3.5 minutes in insertion sort. qsort made sort vanish; list order, a weak hash, then lower1 each became the next jam. 3.5 minutes became 0.2 seconds. Amdahl: if one part is 97% of the time, fixing it is a huge win — and then a new 97% appears.

        
Try it: Step the linked list (one load waits for the last). Switch to the profiler and press Next version through the six rewrites.

        

          What the book says
          

            
Haswell: two load units (up to 72 pending reads each), one store unit (buffer of 42). Loads start one per unit per cycle, so a program that loads one value per result cannot beat CPE 0.50 without SIMD. list_len CPE 4.00. clear_array CPE 1.0 (one store unit). write_read Example A (different cells) CPE 1.3; Example B (same cell) CPE 7.3 — about 6 extra cycles for the write/read dependency. Matching addresses set the location to n − 1.

            
gprof: compile -Og -pg, run, then gprof prog. Shakespeare: 965,028 words, 23,706 unique; n = 2 gives 363,039 unique bigrams (“I am” 1,892 times, “to be” 1,020). Initial insertion sort: 3.5 minutes, sort_words 203.66 s (97.58%). qsort ≈ 5.4 s. Iter-first (insert at front) ≈ 7.5 s; iter-last ≈ 5.3 s. 1,021 buckets → 199,999 still 5.1 s until a shift/xor hash dropped it to 0.6 s; lower2 to about 0.2 s, around 1,000×.

            
Amdahl: sorting was 203.7 of 209.0 s, α = 0.974, predicted speedup 39.0 versus measured 38.5. Interval timing (δ of 1.0–10.0 ms) is rough under about 1 second. Library times hide inside callers unless you wrap them (the book’s Strlen wrapper: 12,511,031 calls, 0.30 s).

The seesaws from this chapter
Each row is a choice that moves CPE. The chip already has the stations. The source code decides whether they wait.

      

        
Safe gcc
Must assume aliasing and side effects. Leaves twiddle1 and dest-in-memory alone.
vs
You rewrite
Hoist, drop calls, keep acc local. Then the compiler can go further.

        
CPE slope
Work per element. This is what unrolling and ILP change.
vs
Intercept
368 cycles of setup in psum. Drowns only when n is tiny.

        
Abstract ADT
combine1: vec_length + get_vec_element every i. CPE ~10 after -O1.
vs
Direct + acc
combine4: one load per i, acc in a register. CPE 1.27–5.01.

        
Latency bound
One chain: L cycles per element. combine4 lives here.
vs
Throughput bound
Fill every pipe. 0.50–1.00. Needs k × k or reassociation.

        
k × 1 unroll
Fewer trips. Critical path still n combines. Helps integer +.
vs
k × k accs
k independent chains of n/k. Breaks the latency wall.

        
Integer + / *
Associative, even on overflow. Compiler may reassociate.
vs
Float + / *
Not associative. You own the risk; gcc usually will not.

        
Predictable branch
Loop tails, always-true bounds. Cheap. combine4b barely slower.
vs
Random branch
~19-cycle miss. Write functional code so gcc can emit cmov.

        
Compute-bound
Critical path or full pipes. Fix the C, watch assembly.
vs
Memory-bound
Load-to-load (CPE 4.00) or write/read (CPE 7.3). Or a bad algorithm.

Words to know
The chapter’s grown-up words, in plain language.

      

        
CPE
Cycles per element: the slope of time versus n, not the setup intercept.

        
memory aliasing
Two pointers that might name the same cell. The compiler must assume they can.

        
optimization blocker
Aliasing or a call with a possible side effect. gcc leaves the slow code alone.

        
code motion
Hoist a loop-invariant call or math to a place that runs less often.

        
combine1…7
The book’s running example: abstract fold, then hoist, direct data, acc, unroll, 2 × 2, reassociate.

        
latency bound
Minimum CPE when each combine must wait for the last. Equals L of the op.

        
throughput bound
Minimum CPE from how many results the units can start per cycle (and from loads).

        
issue time
Cycles before the same unit can start another independent op. 1 means fully pipelined.

        
superscalar / OoO
Several ops per cycle, not necessarily in program order, still looking sequential.

        
critical path
The longest dependency chain in the data-flow of a loop. A lower bound on time.

        
k × k unrolling
Stride-k loop plus k accumulators. Fill C · L pipes to reach throughput.

        
reassociation
acc OP (a OP b) instead of (acc OP a) OP b. Shortens the chain; changes float rounding.

        
register spilling
Too many live accs, so some sit on the stack. 20 × 20 lost its lead.

        
write/read dependency
A load of an address that a recent store still holds in its buffer. Extra wait.

        
gprof
Unix profiler: -pg, then a time table and a call graph. Points at the tall bar.
