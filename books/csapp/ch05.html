Optimizing Program Performance

The same sum can take about ten cycles per number, or half a cycle. The chip is already fast. The work is to stop asking it to redo things, and to stop making each answer wait for the last one.

“We focus our efforts on minimizing the CPE for our computations.” — Bryant & O’Hallaron

Rust setup: what the listings assume

The book’s combine functions use a small abstract vector (data_t, IDENT, OP). The Rust listings use the same idea, spelled with these definitions. Two Rust differences matter for speed: indexing a slice is bounds-checked, and a &mut parameter promises no aliasing, which lets rustc keep a running total in a register even where the C compiler must not. The listings use a raw dest so the aliasing question stays open, as in the book.

// The book's abstract vector, in Rust terms.
type DataT = i64;                        // C: data_t
const IDENT: DataT = 0;                  // 1 for the * version
fn OP(a: DataT, b: DataT) -> DataT { a.wrapping_add(b) }   // wrapping_mul for *

struct VecRec { data: Vec<DataT> }
fn vec_length(v: &VecRec) -> i64 { v.data.len() as i64 }
fn get_vec_start(v: &VecRec) -> &[DataT] { &v.data }
fn get_vec_element(v: &VecRec, i: i64, dest: &mut DataT) -> bool {
    if i < 0 || i >= vec_length(v) { return false; }
    *dest = v.data[i as usize]; true
}

// `data` is a slice, so every data[i] is bounds-checked (C's pointer indexing is
// not). `dest` stays a raw *mut DataT so it can alias the vector, as in the book.
// Fragments assume plain locals: v, dest, data, length, limit, i, acc, val, ...

5.1 · capabilities and limitations of optimizing compilers

The compiler only keeps transformations that stay true

gcc with -Og does a basic cleanup. -O1 and higher do more, and they may make the program larger and harder to debug. This chapter mostly measures -O1, so you can see what the wording of the C still decides.

A safe optimization has to match the unoptimized program for every case the C standard allows. Two names for memory, xp and yp, might be the same cell. That is memory aliasing, and it is an optimization blocker. A function call is the other blocker: f might change the world each time it runs.

Try it: Run twiddle1, then twiddle2. Turn on Same cell and run both again — the answers split into ×4 and ×3. Switch to calls and compare func1 with func2. The highlighted line is the statement running now.

What the book says

twiddle1 does *xp += *yp twice (six memory references). twiddle2 does *xp += 2 * *yp (three). “The compiler knows nothing about how twiddle1 will be called, and so it must assume that arguments xp and yp can be equal.” Equal pointers: twiddle1 scales the cell by 4, twiddle2 by 3. The same trap appears with *p and *q: after *q = 3000; *p = 1000, a later read of *q is 3000 or 1000.

With counter starting at 0, f as return counter++, func1 returns 0+1+2+3 = 6 and func2 returns 0. gcc inlines only functions defined in the same file (-finline, or -O1 and higher). Inlining can turn four counter++ updates into 4 * counter + 6. Practice 5.1: the adding swap zeros a cell when both pointers match.

5.2 · expressing program performance

The slope is the part you can still fix

A 4 GHz clock ticks 4.0×109 times a second. Each tick is 0.25 nanoseconds, or 250 picoseconds. Cycles are the useful unit: they count work, whatever the crystal’s speed.

A loop’s time is a fixed pile plus a steady cost per element. That per-element cost is CPE, cycles per element — the slope. psum1 writes one prefix per trip and fits about 368 + 9.0n. psum2 writes two per trip and fits 368 + 6.0n. The 368 is timing and setup. For a long vector, the slope is the program.

Try it: Press Step and watch one prefix land in p[i] while that line lights up. Then slide n. The gap between the lines is 3n cycles. The shared 368 barely moves the story once n is past a couple hundred.

What the book says

For a vector a, the prefix sum is p0 = a0 and pi = pi−1 + ai. Park the total in a register

5.7 · 5.7.1 overall operation

Many instructions in flight, one story at the end

At the machine-code level, instructions look one-at-a-time. On a modern chip, dozens can be in flight — sometimes 100 or more. The design is superscalar (several operations per cycle) and out of order (not stuck in program order). The result still matches the sequential story. That gap is instruction-level parallelism.

Figure 5.11 splits the chip into an instruction control unit and an execution unit. The ICU fetches ahead from an instruction cache, decodes x86 into primitive operations, and guesses branches so it can keep fetching. That guesswork is speculative execution. If the guess was wrong, the chip throws the guess away and refills. The EU runs the operations on functional units, then a retirement unit commits them in program order.

Two lower bounds show up everywhere after this. The latency bound is how long a chain of dependent operations must take. The throughput bound is how many independent operations the units can start.

Try it: Press Tick in In order: the multiply occupies the chip until it finishes. Switch to Out of order and tick again — the pointer add runs while the multiply is still in flight. Press Mispredict on the branch and watch the speculative load get discarded.

What the book says

The ICU reads an instruction cache, fetches well ahead, and uses branch prediction plus speculative execution. A wrong prediction resets state to the branch and starts the other path. Decode turns instructions into operations (micro-operations): an x86 memory operand often becomes a load plus the arithmetic. The EU’s functional units perform loads, stores, and arithmetic, then retirement updates the registers only for operations that were on the correct path.

5.7.2 · functional unit performance

Latency, issue time, capacity

Each arithmetic operation on the Haswell reference machine has three numbers. Latency is how many cycles the operation itself takes. Issue time is how soon another independent operation of that kind can start. Capacity is how many functional units can do it at once.

Integer and floating-point addition and multiplication all have issue time 1: they are fully pipelined. A floating-point adder is three stages (exponents, fractions, rounding), so its latency is 3, and a new independent add can enter every cycle. Division is different. Its issue time equals its latency, and both depend on the data. The divider finishes one division before it starts the next.

Try it: Pick an operation. Independent feeds the pipe every issue cycle and fills every unit. One chain waits out the latency before the next one may start. Division refuses to overlap with itself.

What the book says

Figure 5.12, Haswell. Integer: addition latency 1, issue 1, capacity 4; multiplication 3, 1, 1; division 3–30, 3–30, 1. Floating point: addition 3, 1, 1; multiplication 5, 1, 2; division 3–15, 3–15, 1. “Functional units with issue times of 1 cycle are said to be fully pipelined.” The divider is not.

5.7.3 · an abstract model of processor operation

The critical path is a lower bound

A data-flow graph draws each operation as a box and each value as an arrow. Boxes that do not depend on each other may run together. The longest chain of arrows is the critical path. If that chain’s latencies add up to T, the loop needs at least T cycles.

combine4’s inner loop, for double multiply, is four instructions. The decoder splits vmulsd (%rdx), %xmm0, %xmm0 into a load and a multiply. The multiply feeds the next acc. That chain is 5 cycles long, so CPE cannot beat 5. The pointer update is only an integer add, one cycle, and it runs beside the multiply. Measured CPE: 5.01.

Integer addition is the exception. Both chains have latency 1, which predicts CPE 1.00, and the machine measured 1.27. The critical path is a floor. Other limits — how many values can move between units in one cycle — can sit above it. The latency bounds are 1, 3, 3, 5. The throughput bounds, from the units and the two load ports, are 0.50, 1.00, 1.00, 0.50.

Try it: Switch float * and int +. The thick path is the one that sets the floor. The assembly under the picture highlights the instruction on that path.

What the book says

combine4 measured CPE 1.27, 3.01, 3.01, 5.01 against latency bounds 1.00, 3.00, 3.00, 5.00 and throughput bounds 0.50, 1.00, 1.00, 0.50. Registers in the loop fall into classes: read-only (%rax, the end pointer), updated in a chain (%rdx, %xmm0), and values that pass between operations with no register (the load feeding the mul, the condition codes feeding jne). For latency L > 1 the measured CPE is L. Integer addition’s 1.27 shows that a data-flow bound is only a lower bound.

5.8 · loop unrolling

Two elements per trip, one chain

Loop unrolling does more useful work per iteration, so the index math and the branch run less often. It also sets up later rewrites. By itself it does not shorten the chain of combines.

combine5 is 2 × 1 unrolling: i += 2, and acc = (acc OP data[i]) OP data[i+1]. The limit is length - 1, so i+1 stays inside the array. A second loop mops up a leftover element. k × 1 unrolling uses limit n - k + 1 and a tail of at most k − 1 elements.

Integer addition improves, 1.27 to 1.01, because the loop overhead was part of the jam. Integer multiply and both floating-point ops stay on their latency bounds: 3.01, 3.01, 5.01. There are still n combines in one line.

5.9 · 5.9.1 multiple accumulators

Two chains, so the pipes stay full

Addition and multiplication are fully pipelined, and some have more than one unit. combine5 still updates one acc, so the next combine waits L cycles. Splitting the work across several accumulators breaks that wait.

For an associative, commutative operation the product of the whole vector is the product of the even elements times the product of the odd ones. combine6 is 2 × 2 unrolling: acc0 takes even indices, acc1 takes odd, then one combine joins them. Each chain is only n/2 long. CPE becomes 0.81, 1.51, 1.51, 2.51 — under the latency bounds.

To fill every unit you need about k ≥ C × L independent accumulators. Floating-point multiply wants k ≥ 10 and then reaches CPE 0.51. Integer addition reaches 0.54 near k = 7, close to the 0.50 load limit. Integer multiply and floating-point add reach 1.01 once k ≥ 3.

Integer overflow still obeys associativity, so a compiler may do this for integers. Floating-point multiply and add do not. Even-index values near the top of the range and odd-index values near zero can overflow one partial product and underflow the other, while the straight product stays finite. gcc leaves the float code alone.

Try it: Step 2 × 2 and watch both accumulators update on the same click — both lines of the inner loop light up together. Press Wild floats to see a split product become non-finite while the straight product stays 1. The k buttons show how many accumulators the book needed to reach the throughput bound.

What the book says

Figure 5.21 is combine6. Figure 5.25: with k × k unrolling, integer + reaches CPE 0.54 at k = 7; integer * and float + reach 1.01 for k ≥ 3; float * reaches 0.51 for k ≥ 10. “For an operation with latency L and capacity C, this requires an unrolling factor k ≥ C · L.” Two’s-complement arithmetic stays associative even on overflow. 5.11 · 5.11.1 register spilling

Too many totals, and some live on the stack

The critical path and the throughput of the units are both floors on runtime. A third limit is the register file. If the loop needs more live values than there are registers, the compiler spills: it keeps some of them in memory, usually on the stack.

x86-64 has 16 integer registers and 16 YMM registers for floating-point values. 10 × 10 unrolling still keeps acc0 in %xmm0 and does one vmulsd. 20 × 20 loads the accumulator from 40(%rsp), multiplies, and stores it back. CPE for floating-point multiply goes from 0.52 back up to 0.68. Integer addition goes from 0.55 to 0.83. Nothing gets better, and some cases get worse.

Try it: Press 10 × 10 and read a one-instruction update. Press 20 × 20 and the same accumulator takes a load and a store around the multiply. The register boxes that no longer fit turn into stack slots.

What the book says

10 × 10 CPE 0.55, 1.00, 1.01, 0.52. 20 × 20 CPE 0.83, 1.03, 1.02, 0.68. Throughput bounds stay 0.50, 1.00, 1.00, 0.50. The 20 × 20 snippet is vmovsd 40(%rsp), %xmm0, then vmulsd (%rdx), %xmm0, %xmm0, then vmovsd %xmm0, 40(%rsp). “Once a compiler must resort to register spilling, any advantage of maintaining multiple accumulators will most likely be lost.”

5.11.2 · branch prediction and misprediction penalties

Guess the branch, or don’t branch

The chip fetches far ahead. At a conditional branch it guesses taken or not-taken and runs down that path without committing. A correct guess commits. A wrong guess throws the work away and refills the pipe. On this machine that penalty measured about 19 cycles.

Predictable branches are cheap. The loop-back branch is almost always taken, and misses once at the end. combine4b puts the bounds check back inside the loop; the check always succeeds, and only integer addition slows a little (1.27 to 2.02). The other three CPEs do not move.

Data-dependent branches are the expensive kind. minmax1 swaps a[i] and b[i] when they are out of order: CPE about 13.5 on random data, and 2.5–3.5 when the pattern is regular — a penalty near 20 cycles. minmax2 computes min and max, then writes both. gcc emits a conditional move. CPE stays about 4.0 for random and for regular data.

Try it: Step minmax1 on random pairs and watch a miss add 19 cycles. Switch the data to Sorted and the predictor learns. Then run minmax2: both values are computed, the branch is gone, and the cost stays flat.

What the book says

The book measures a 19-cycle misprediction penalty on the reference machine. combine4 versus combine4b: 1.27 / 3.01 / 3.01 / 5.01 against 2.02 / 3.01 / 3.01 / 5.01. minmax1 is the imperative swap; minmax2 is the functional min/max. Practice 5.9: the merge loop’s data comparison is unpredictable (CPE around 15.0 on random data) and can be rewritten so gcc has a chance to emit a conditional move. The loop-limit tests in that merge are predictable.

5.12 · 5.12.1 load performance

A load that names the next load

The combining loops touched only a few kilobytes, so they ran from cache. This section stays in that world; Chapter 6 opens the caches themselves. The reference machine has two load units, each holding up to 72 pending reads, and each can start one load per cycle. A loop that loads one value per result cannot beat CPE 0.50. Load k values per result and the floor becomes k/2.

Those combining loads did not sit on the critical path: the address was the loop index, known before the load finished. list_len is the opposite. ls = ls->next means the next address is the value just loaded. The book measured CPE 4.00, the L1 hit time. The movq (%rdi), %rdi is the whole chain.

Try it: Step the list. Each node waits until the previous load has delivered its next pointer, and the wait badge shows 4 cycles. Switch to an indexed array: the addresses are i, so the next load can start while the last one is still coming back.

5.12.2 · store performance

A store is quiet until a load reads it back

There is one store unit, with a buffer of up to 42 writes, and it can start a store every cycle. clear_array writes zeros and measures CPE 1.0 — the one store unit, fully used. Stores do not write registers, so a row of stores does not form a chain by itself.

A load of an address that a store has not finished is a write/read dependency. write_read stores val through dst, then sets val = (*src) + 1. When src and dst are different cells (example A, array starting at −10 and 17), CPE is 1.3 and a[0] stays −10. When they are the same cell (example B), each load sees the store that just happened, CPE rises to 7.3, and the cell becomes 0, then 1, then 2.

Try it: Step example A and watch a[1] settle at −9 while a[0] stays −10. Step example B and watch the single cell eat its own store. The code highlights the store, then the load, and the note says whether the addresses match.

5.13 · life in the real world: performance improvement techniques

Fix the shape first, then the inner loop

The chapter’s checklist has an order. Start with the algorithm and the data structure, and watch for anything that grows like n² when n gets large. Then clear the blockers so the compiler may move calls and reuse values. Then keep the inner loop free of needless calls and needless memory traffic. Only then unroll, split accumulators, reassociate, and write conditionals so gcc can emit a conditional move.

Each rewrite can introduce a bug: a new temporary, a wrong loop limit, a tail that forgets the last elements. Checking code runs the new function against the old one. Unrolled loops need many lengths, so the tail is tested for every remainder.

Try it: Press Apply next and walk the checklist in the book’s order. The picture’s clock only starts to care about CPE after the quadratic algorithm is gone. The code panel shows the shape you just switched to.

What the book says

Three layers: high-level design; basic coding (avoid blockers, move calls, accept a little less modularity, introduce temporaries); low-level optimizations (unroll, multiple accumulators, reassociation, functional style for conditional moves). “Be vigilant to avoid introducing errors as you rewrite programs in the interest of efficiency.” Checking code compares each new version with the original, with more cases as the loop gets more special cases.

5.14 · 5.14.1 program profiling

Three commands, then the tallest row

On a large program the slow part is not obvious. A profiler runs the real program on real data and reports where the time went. Unix gprof reports two things: CPU time per function, and how many times each function was called, by whom.

Compile with gcc -Og -pg so calls are not inlined away. Run the program; it writes gmon.out and runs about twice as slow. Then gprof prog prints the table. Library calls hide inside their callers unless you wrap them. The book’s Strlen wrapper shows 12,511,031 calls and 0.30 seconds.

The times come from a timer interrupt every δ, often 1 to 10 milliseconds, which charges the whole interval to whichever function was running. Over a long run that is fair. Under about a second it is a rough sketch. Call counts are exact, as long as nothing was inlined.

Try it: Press Next step through compile, run, and the report. Click a row. The code highlights that function, and the call-graph note for find_ele_rec shows why the lists were long.

What the book says

The sample flat profile: sort_words 97.58%, 203.66 seconds, 1 call; find_ele_rec 2.32%, 4.85 seconds, 965,027 calls; Strlen 0.14%, 0.30 seconds, 12,511,031 calls. The call graph shows 158,655,725 recursive calls of find_ele_rec against 965,027 top-level calls, a ratio of 164.4 to 1 — about 164 list elements scanned per lookup. It also called save_string and new_ele 363,039 times each.

5.14.2 · using a profiler to guide optimization

Fix the tall bar, then look again

The case study counts bigrams in Shakespeare: 965,028 words, 23,706 unique words, 363,039 unique pairs. “I am” appears 1,892 times, “to be” 1,020 times, and 266,018 pairs appear once. The first version spends 3.5 minutes in insertion sort.

Quicksort drops the run to about 5.4 seconds. Inserting new list nodes at the front makes things worse (about 7.5 seconds); keeping frequent keys near the front of each bucket helps (about 5.3). A weak hash then leaves one giant bucket. A better hash, and enough buckets, drops the run to about 0.6 seconds. Replacing lower1 with lower2 finishes near 0.2 seconds — about 1,000× from the start.

Amdahl’s law explains the first jump. Sorting was 203.7 of 209.0 seconds, so α = 0.974. If that part becomes free, the predicted speedup is 39.0; the measurement was 38.5. Then a new tall bar appears. Profile on representative data, and still avoid algorithms that blow up on the data you did not test — long strings would have made lower1 the first crisis.

Try it: Press Next version. The bar shrinks, the code panel shows the piece that changed, and the Amdahl card on the first fix shows the predicted 39 against the measured 38.5.

After quicksort, the list implementation dominates; iter-first is slower than iter-last; a shift-and-xor hash with many buckets removes the long scans; lower2 removes the remaining strlen traffic. “When one bottleneck is eliminated, a new one arises.”

5.15 · summary

You steer, the compiler finishes

A compiler can tidy the program you wrote. It will not replace an algorithm that does too much work, and it will not assume your pointers are independent or that your functions are pure. The fast combining code is still C. It is C shaped so the critical path is short and the functional units stay busy.

The path in this picture is the chapter in one walk: abstract code, hoist, direct access, a register accumulator, unrolling, several accumulators, then a vector form. Float multiply goes from CPE 11.14 to about 0.06. Along the way the limits change: latency, then throughput, then registers, branches, and memory.

Try it: Press Next rung. Each rung names the section that earned it, shows that version’s code, and moves the CPE for floating-point multiply.

What the book says

“No compiler can replace an inefficient algorithm or data structure.” The programmer’s job is to write code the compiler can turn into something close to the machine’s throughput, then to read the assembly and the measurements when a result is surprising. Single-precision multiplication in the chapter’s account falls from 11.14 to 0.06 with AVX, more than 180×. Practice problems in the chapter (prefix sums, polynomials, Horner’s method, merge, copying arrays) are the same ideas on new loops.

Words to know

The chapter’s words, in plain language.

CPE
Cycles per element: the slope of runtime versus n, after the fixed setup cost.
optimization blocker
Aliasing, or a call that might have a side effect. The compiler must leave the slow form in place.
code motion
Moving a loop-invariant computation to a place that runs less often.
latency bound
The CPE you get when each combine waits for the previous one. It equals the operation’s latency.
throughput bound
The CPE you get when every capable unit is kept busy. For one load per element, 0.50 on this machine.
issue time
Cycles before the same kind of independent operation can start again. 1 means fully pipelined.
critical path
The longest chain of data dependencies. A lower bound on the cycles a loop needs.
k × k unrolling
Stride-k loop plus k accumulators, enough to fill capacity × latency pipes.
reassociation
acc OP (a OP b) instead of (acc OP a) OP b. The pair leaves the accumulator chain.
register spilling
Live values that no longer fit in registers, so the compiler keeps them on the stack.
misprediction penalty
Cycles lost throwing away a speculative path. About 19 on the reference machine.
write/read dependency
A load of an address that still has a store waiting in the store buffer.
gprof
Compile with -Og -pg, run, then gprof. A time table and a call graph.
