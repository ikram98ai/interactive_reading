Optimizing Program Performance

The same sum can take about ten cycles per number, or half a cycle. The chip is already fast. The work is to stop asking it to redo things, and to stop making each answer wait for the last one.

“We focus our efforts on minimizing the CPE for our computations.” — Bryant & O’Hallaron

Rust setup: what the listings assume

The book’s combine functions use a small abstract vector (its data_t, IDENT and OP). The Rust listings use the same idea, spelled with the definitions below. Two Rust rules matter for speed. A & lends a value read-only, and a &mut lends it with permission to change it; while a &mut is alive, nothing else can reach that value. That is what lets rustc keep a running total in a register where the book’s C compiler must not. And indexing a slice (data[i]) is bounds-checked: an index out of range stops the program with a panic (“index out of bounds: the len is 4 but the index is 4”) instead of reading past the end.

How the listings were made. rustc --edition 2021 -C opt-level=1 -C target-cpu=haswell -C llvm-args=-unroll-runtime=false --emit=asm, rustc 1.100.0, x86-64 Linux. Level 1 stands in for the book’s -O1 (the two compilers’ levels are not the same set of passes). target-cpu=haswell asks for the book’s machine, so floating point uses the same AVX instructions (vmulsd). The last flag turns off one thing level 1 now does by itself: LLVM, rustc’s back end, copies a simple loop body 8 times. Without it each listing is twice as long and says the same. The accessor functions carry #[inline(never)], an attribute (a note to the compiler, written #[…]) asking it not to paste their bodies into the caller. That copies the book’s setup, where they sit in another file. Without it rustc inlines them and combine1 compiles to combine4’s loop. We removed only assembler bookkeeping lines (.cfi_*, alignment and section directives) and the panic paths after a function’s end.

// The book's abstract vector, in Rust.
type Data = i64; // a type alias: the book's data_t (the .s tabs use f64)
const IDENT: Data = 0; // const: a fixed value. 1 for the product version
// op combines two values. wrapping_add wraps around on overflow;
// a plain + would panic on overflow in a debug build.
fn op(a: Data, b: Data) -> Data { a.wrapping_add(b) } // wrapping_mul for *
// (f64 has no wrapping_ methods: for f64, op is plain a * b or a + b)

struct Vector { data: Vec<Data> } // struct: named fields. Vec: a growable array on the heap

// usize is Rust's type for lengths and indexes
#[inline(never)] // kept out of line, like the book's separate vec.c
fn vec_length(v: &Vector) -> usize { v.data.len() }
// &[Data] is a slice: a borrowed view of the array, a pointer plus a length
#[inline(never)]
fn get_vec_start(v: &Vector) -> &[Data] { &v.data }
// Option: Some(value) if i is in range, None if not (the bounds check)
#[inline(never)]
fn get_vec_element(v: &Vector, i: usize) -> Option<Data> {
    v.data.get(i).copied()
}

// The book's strings end in a zero byte. This walks to it, as C's strlen does.
fn strlen(s: &[u8]) -> usize {
    s.iter().position(|&b| b == 0).unwrap_or(s.len()) // first 0, or the end
}

5.1 · capabilities and limitations of optimizing compilers

The compiler only keeps transformations that stay true

The book compiles its C with gcc. -Og does a basic cleanup. -O1 and higher do more, and they may make the program larger and harder to debug. The chapter mostly measures -O1, so you can see what the wording of the source still decides. rustc has the same dial: -C opt-level=0 to 3 (plus s and z, which favour small code), where -O means level 3. Our listings use level 1, like the book.

A safe optimization has to match the unoptimized program in every case the language allows. In the book’s C, twiddle1 and twiddle2 take two pointers, xp and yp, and nothing stops a caller from passing the same cell twice. That is memory aliasing, and it is an optimization blocker: with one cell, twiddle1 multiplies it by 4 and twiddle2 by 3, so gcc may not turn one into the other. Rust closes this door. xp: &mut i64 is the only way to its cell while it lives, so passing the same cell as yp does not compile; the panel shows rustc’s real error. Because of that rule, rustc may give twiddle1 twiddle2’s shorter form, and it does: in the twiddle.s tab both functions are the same three instructions. Read *yp, double it, add it into *xp: three memory references, not six.

A function call is the other blocker: f might change the world each time it runs. Here f bumps a global counter, an AtomicI64 (a number that is safe to change from any thread). fetch_add hands back the old value and adds one; Relaxed says no extra ordering with other memory is needed, which is all a counter needs. Calling it four times is not the same as calling it once, in C or in Rust. rustc does inline f into func1, since both are in the same crate (one compiled unit of Rust). But the func1.s tab still has four lock xaddq instructions, one indivisible add to COUNTER per call. Unlike the book’s gcc with its plain counter++, rustc did not merge the four atomic adds into one.

Try it: Run twiddle1, then twiddle2. Turn on Same cell to see the book’s C case: run both again and the answers split into ×4 and ×3, while rustc’s refusal appears under the listing. Switch to calls and compare func1 with func2. The highlighted line is the statement running now; the .s tabs are what rustc compiled.

What the book says

twiddle1 adds the value at yp into the cell at xp twice (six memory references). twiddle2 adds twice that value once (three). “The compiler knows nothing about how twiddle1 will be called, and so it must assume that arguments xp and yp can be equal.” Equal pointers: twiddle1 scales the cell by 4, twiddle2 by 3. The same trap appears with two pointers p and q: store 3000 through q, then 1000 through p, and a later read through q gives 3000 or 1000, depending on whether they name one cell.

With counter starting at 0, and f returning counter and then adding one, func1 returns 0+1+2+3 = 6 and func2 returns 0. gcc inlines only functions defined in the same file (-finline, or -O1 and higher). Inlining can turn four counter++ updates into 4 * counter + 6. Practice 5.1: the adding swap zeros a cell when both pointers match.

5.2 · expressing program performance

The slope is the part you can still fix

A 4 GHz clock ticks 4.0×109 times a second. Each tick is 0.25 nanoseconds, or 250 picoseconds. Cycles are the useful unit: they count work, whatever the crystal’s speed.

A loop’s time is a fixed pile plus a steady cost per element. That per-element cost is CPE, cycles per element — the slope. psum1 writes one prefix per trip and fits about 368 + 9.0n. psum2 writes two per trip and fits 368 + 6.0n. The 368 is timing and setup. (Those lines are the book’s measurement of its C version; our Rust measurement is pending.) For a long vector, the slope is the program.

Try it: Press Step and watch one prefix land in p[i] while that line lights up. Then slide n. The gap between the lines is 3n cycles. The shared 368 barely moves the story once n is past a couple hundred.

What the book says

For a vector a, the prefix sum is p0 = a0 and pi = pi−1 + ai. Figure 5.1: psum1 computes one element per iteration; psum2 uses 2-way unrolling (mid_val, then p[i] and p[i+1]) and a cleanup when n is odd. A least-squares fit of Figure 5.2 gives the two lines. CPE is cycles per element, because unrolling changes how many iterations you need for the same n.

Practice 5.2 gives three later fits: 60 + 35n, 136 + 4n, and 157 + 1.25n, and asks which version wins for which n.

5.3 · program example

A header, a row of lockers, a running answer

The chapter’s running example is a vector: a header (its length and a pointer to the data) plus the array itself. In the Rust setup above it is a Vector holding a Vec. The element type, Data, is an integer or a floating-point type. IDENT 0 with op adding makes a sum; IDENT 1 with op multiplying makes a product.

combine1 is the abstract version. It takes dest: &mut Data, a borrowed place to write the answer, and *dest is that place. Every trip it calls vec_length, then get_vec_element, which returns an Option: Some(value) for an index in 0..len, None outside it. .unwrap() takes the value out (and would stop the program on None). Safe, in the same spirit as a Java array. The reference machine is an Intel Core i7 Haswell. In the book’s measurement, -O1 alone cuts the CPE by more than half, with no rewrite.

The combine1.s tab is rustc’s loop for the f64 product. Like the book’s, it makes two calls every trip: get_vec_element, then vec_length for the loop test. Between them it tests the Some/None answer, which is the unwrap. It writes *dest every trip but never reads it back. Nothing else can change *dest while the &mut lives, so rustc keeps its own copy.

Try it: Pick sum or product, then Step. Count the questions. The code under the picture highlights vec_length, then the bounds-checked fetch, then the update of *dest. Open combine1.s to find the two callq lines.

What the book says

Unoptimized CPE for combine1: integer + 22.68, integer * 20.02, float + 19.98, float * 20.18. With -O1: 10.12, 10.12, 10.17, 11.14. The book keeps the messy hundredths; integer sum is more likely 23.00 than 22.68. Integer 32-bit and 64-bit matched except for division; float matched double. Later tables use -O1 and -O2.

5.4 · eliminating loop inefficiencies

Ask for the length once

The loop test runs on every iteration. The vector’s length does not change. Code motion lifts vec_length into a local length. That is combine2. In the book’s measurement, integer addition falls from CPE 10.12 to 7.02. The compiler will not do this by itself if the call might have a side effect. rustc didn’t either: its combine2 still calls get_vec_element every trip, but vec_length only once.

The loud version of the same mistake is lower1. It calls strlen in the loop test, and strlen walks to the zero byte every time. (A Rust slice carries its length, so s.len() costs nothing; our strlen walks on purpose, as the book’s C one does.) For n characters that is on the order of n² inspections. lower2 measures once. At n = 1,048,576 the book timed 17 minutes against 2.0 milliseconds (its C; our Rust timing is pending).

Try it: Step lower1 and watch the length-walker restart before each letter. Switch to lower2. The n buttons scale the same idea up to the book’s million-character row. Then open combine2 and see the hoist in the combining loop.

What the book says

combine2 CPE: integer + 7.02, integer * 9.03, float + 9.02, float * 11.03. Figure 5.8: for length 1,048,576, lower1 takes 1,049.89 seconds and lower2 takes 0.0020 seconds, over 500,000 times faster. 5.5 · reducing procedure calls

The clerk was never the jam

get_vec_element checks the index on every locker. Once you already know the walk stays in range, that check is a ceremony. combine3 calls get_vec_start once, then reads data[i] itself. The inner loop has no call. The slice comes back in two registers, a pointer and a length.

Rust still checks data[i]. In the combine3.s tab, each trip starts with cmpq and jae: is i below the slice’s length? If not, the program panics. rustc can’t drop the check, because length came from vec_length, a separate function, and nothing tells it that this number equals the slice’s length. The check is always passed, so the processor predicts it right every time.

In the book’s measurement, integer addition moves from 7.02 to 7.17, a little worse. The bounds checks were highly predictable, so the processor was already guessing them right. This rewrite is a door. The next section walks through it.

Try it: Step combine2 and count clerk calls in the code notes. Switch to combine3: the two setup calls are marked “once”, the inner-call count stays at 0, and the book’s CPE stays near 7. Then open combine3.s and find the bounds check.

What the book says

Figure 5.9: get_vec_start returns v->data. combine3 CPE: integer + 7.17, integer * 9.02, float + 9.02, float * 11.03. “Surprisingly, there is no apparent performance improvement.” Section 5.11.2 shows why: the checks always succeed. 5.6 · eliminating unneeded memory references

Park the total in a register

combine3 keeps the total in *dest. In the book’s gcc -O1 loop, every element means: load dest, combine, store dest. combine4 keeps it in a local acc (let mut makes a variable you may change) and writes *dest once, after the loop. In the book’s measurement, integer addition falls from 7.17 to 1.27.

gcc must leave combine3 alone. In C, dest may point into the vector, and then updating it on the way changes later elements. With the vector [2, 3, 5], a product, and dest pointing at the last element, combine3 finishes at [2, 3, 36] and combine4 stores 30. With dest: &mut Data that call does not compile: the vector is already lent read-only, and rustc says so (error E0502). So rustc keeps the total in a register by itself. Look back at combine3.s in 5.5: nothing touches *dest inside the loop.

To get the C situation in Rust, use Cell: a value you may change through a shared & reference, with .get() to read it and .set() to write it. Now dest may honestly be one of the vector’s own cells, and the program really prints [2, 3, 36] and [2, 3, 30]. In memory.s, rustc writes dest back on every trip. It skips the read, because nothing else writes between its own write and the next read.

Try it: Press Memory and step: each element ends with a store to dest. Press Register and watch dest stay quiet until the end. Open alias 36 / 30 and step the real Cell program; its output is under the listing.

What the book says

Figure 5.10 holds the accumulated value in a temporary. combine4 CPE: integer + 1.27, integer * 3.01, float + 3.01, float * 5.01 — the latency bounds of those operations, except integer addition, which sits a little above 1.00. The aliasing example is why a compiler must leave combine3’s memory updates in place. Practice 5.4: at -O2 gcc keeps the product in a register but still stores it to dest on every trip.

5.7 · 5.7.1 overall operation

Many instructions in flight, one story at the end

At the machine-code level, instructions look one-at-a-time. On a modern chip, dozens can be in flight — sometimes 100 or more. The design is superscalar (several operations per cycle) and out of order (not stuck in program order). The result still matches the sequential story. That gap is instruction-level parallelism.

Figure 5.11 splits the chip into an instruction control unit and an execution unit. The ICU fetches ahead from an instruction cache, decodes x86 into primitive operations, and guesses branches so it can keep fetching. That guesswork is speculative execution. If the guess was wrong, the chip throws the guess away and refills. The EU runs the operations on functional units, then a retirement unit commits them in program order.

Two lower bounds show up everywhere after this. The latency bound is how long a chain of dependent operations must take. The throughput bound is how many independent operations the units can start.

Try it: Press Tick in In order: the multiply occupies the chip until it finishes. Switch to Out of order and tick again — the index update incq runs while the multiply is still in flight. The listing is rustc’s combine4 loop. Press Mispredict on the branch and watch the speculative load get discarded.

What the book says

The ICU reads an instruction cache, fetches well ahead, and uses branch prediction plus speculative execution. A wrong prediction resets state to the branch and starts the other path. Decode turns instructions into operations (micro-operations): an x86 memory operand often becomes a load plus the arithmetic. The EU’s functional units perform loads, stores, and arithmetic, then retirement updates the registers only for operations that were on the correct path.

5.7.2 · functional unit performance

Latency, issue time, capacity

Each arithmetic operation on the Haswell reference machine has three numbers. Latency is how many cycles the operation itself takes. Issue time is how soon another independent operation of that kind can start. Capacity is how many functional units can do it at once.

Integer and floating-point addition and multiplication all have issue time 1: they are fully pipelined. A floating-point adder is three stages (exponents, fractions, rounding), so its latency is 3, and a new independent add can enter every cycle. Division is different. Its issue time equals its latency, and both depend on the data. The divider finishes one division before it starts the next.

Try it: Pick an operation. Independent feeds the pipe every issue cycle and fills every unit. One chain waits out the latency before the next one may start. Division refuses to overlap with itself.

What the book says

Figure 5.12, Haswell. Integer: addition latency 1, issue 1, capacity 4; multiplication 3, 1, 1; division 3–30, 3–30, 1. Floating point: addition 3, 1, 1; multiplication 5, 1, 2; division 3–15, 3–15, 1. “Functional units with issue times of 1 cycle are said to be fully pipelined.” The divider is not.

5.7.3 · an abstract model of processor operation

The critical path is a lower bound

A data-flow graph draws each operation as a box and each value as an arrow. Boxes that do not depend on each other may run together. The longest chain of arrows is the critical path. If that chain’s latencies add up to T, the loop needs at least T cycles.

rustc’s combine4 loop for f64 multiply is four instructions, like the book’s. rustc counts with an index: %rcx is i, %rax holds the data’s address and %rdx its length. (The book’s gcc walked a pointer instead; the shape is the same.) The decoder splits vmulsd (%rax,%rcx,8), %xmm0, %xmm0 into a load of data[i] and a multiply. The multiply feeds the next acc. That chain is 5 cycles long, so CPE cannot beat 5. The index update is incq, one cycle, and it runs beside the multiply. %rax and %rdx are read-only. %rcx and %xmm0 are loop registers, carried from one trip to the next. The book measured CPE 5.01 for its C version; our Rust measurement is pending.

Integer addition is the exception. rustc’s loop is addq (%rax,%rsi,8), %rcx, then the same three instructions, with the total in %rcx and i in %rsi. Both chains have latency 1, which predicts CPE 1.00, and the book’s machine measured 1.27. The critical path is a floor. Other limits — how many values can move between units in one cycle — can sit above it. The latency bounds are 1, 3, 3, 5. The throughput bounds, from the units and the two load ports, are 0.50, 1.00, 1.00, 0.50.

Try it: Switch float * and int +. The thick path is the one that sets the floor. The assembly under the picture is rustc’s loop for that operation, with the instruction on that path highlighted.

What the book says

combine4 measured CPE 1.27, 3.01, 3.01, 5.01 against latency bounds 1.00, 3.00, 3.00, 5.00 and throughput bounds 0.50, 1.00, 1.00, 0.50. Registers in the loop fall into classes: read-only (%rax, the end pointer), updated in a chain (%rdx, %xmm0), and values that pass between operations with no register (the load feeding the mul, the condition codes feeding jne). For latency L > 1 the measured CPE is L. Integer addition’s 1.27 shows that a data-flow bound is only a lower bound.

5.8 · loop unrolling

Two elements per trip, one chain

Loop unrolling does more useful work per iteration, so the index math and the branch run less often. It also sets up later rewrites. By itself it does not shorten the chain of combines.

combine5 is 2 × 1 unrolling: i += 2, and acc = op(op(acc, data[i]), data[i + 1]). The book’s limit is length - 1, so i + 1 stays inside the array. In Rust a length is a usize, which can’t go negative: for an empty vector, length - 1 would overflow (a panic in a debug build). So our test is i + 1 < length, which means the same. It also lets rustc see that both reads are in range, so combine5.s has no bounds checks. A second loop mops up a leftover element. k × 1 unrolling uses limit n - k + 1 (in Rust, i + k <= n) and a tail of at most k − 1 elements.

In the book’s measurement, integer addition improves, 1.27 to 1.01, because the loop overhead was part of the jam. Integer multiply and both floating-point ops stay on their latency bounds: 3.01, 3.01, 5.01. There are still n combines in one line: in combine5.s the second vmulsd waits for the first.

rustc also unrolls by itself. At -C opt-level=1 and up, LLVM copies combine4’s loop body 8 times (our listings turn that off to stay readable). Its 8 × 1 loop is still one chain of eight vmulsd into %xmm0, so it cannot beat the latency bound either.

Try it: Press Step pair. The second combine waits until the first has updated acc. The combine line stays lit while its note shows data[i] first, then data[i + 1], and the chain length still grows by two.

What the book says

5.9 · 5.9.1 multiple accumulators

Two chains, so the pipes stay full

Addition and multiplication are fully pipelined, and some have more than one unit. combine5 still updates one acc, so the next combine waits L cycles. Splitting the work across several accumulators breaks that wait.

For an associative, commutative operation the product of the whole vector is the product of the even elements times the product of the odd ones. combine6 is 2 × 2 unrolling: acc0 takes even indices, acc1 takes odd, then one combine joins them. Each chain is only n/2 long. In combine6.s the two vmulsd lines write different registers, so neither waits for the other. The book measured CPE 0.81, 1.51, 1.51, 2.51 for its C version, under the latency bounds; our Rust measurement is pending.

To fill every unit you need about k ≥ C × L independent accumulators. Floating-point multiply wants k ≥ 10 and then reaches CPE 0.51. Integer addition reaches 0.54 near k = 7, close to the 0.50 load limit. Integer multiply and floating-point add reach 1.01 once k ≥ 3. (All of these are the book’s measurements.)

Integer arithmetic that wraps on overflow is still associative, so a compiler may do this for integers, and rustc does: at -C opt-level=3 with target-cpu=haswell, it turns combine4’s i64 sum into AVX2 vpaddq on four 256-bit registers, sixteen numbers per trip. Floating-point multiply and add are not associative. Rust’s f64 follows the IEEE 754 standard, so a result too big becomes infinity and one too small becomes 0. Even-index values near the top of the range and odd-index values near zero can overflow one partial product and underflow the other, while the straight product stays finite. So rustc, like gcc, leaves the float chain alone: at level 3 it unrolls combine4’s f64 product but keeps one chain of vmulsd.

Try it: Press Step on combine6 (2 × 2) and watch both accumulators update on the same click — both lines of the inner loop light up together. Press Wild floats to see a split product become NaN (“not a number”) while the straight product stays 1, exactly as the Rust program printed. The k buttons show how many accumulators the book needed to reach the throughput bound.

5.9.2 · reassociation transformation

Move the parentheses, shorten the chain

combine5 computes op(op(acc, data[i]), data[i + 1]). combine7 — called 2 × 1a — computes op(acc, op(data[i], data[i + 1])). Written with *, that is (acc * a) * b against acc * (a * b): the only edit is the parentheses. The pair combine does not need acc, so it sits off the critical path. The acc chain shrinks to n/2 combines. In combine7.s, rustc multiplies the pair into %xmm1 first, and only the last vmulsd touches acc in %xmm0. rustc keeps our parentheses: it may not move them for floating point by itself.

The book measured CPE for its C version: integer + 1.01, and 1.51, 1.51, 2.51 for the other three (our Rust measurement is pending). The multiply and floating-point cases match combine6. Integer addition stays at 1.01, the same as plain unrolling, because a latency-1 chain of length n/2 is already down at the other limits of the chip. Float results can round differently; the book treats that as the programmer’s choice.

5.11 · 5.11.1 register spilling

Too many totals, and some live on the stack

The critical path and the throughput of the units are both floors on runtime. A third limit is the register file. If the loop needs more live values than there are registers, the compiler spills: it keeps some of them in memory, usually on the stack.

x86-64 has 16 integer registers and 16 YMM registers for floating-point values (an %xmm register is the low half of a YMM one). In rustc’s 10 × 10 loop every accumulator is a register and gets one vmulsd. In its 20 × 20 loop, 15 fit, %xmm4 stays free as scratch, and five live on the stack. Each of those five is loaded from -40(%rsp) (and its neighbours), multiplied, and stored back. The negative offsets are the red zone: 128 bytes below the stack pointer that a function calling nobody may use without moving it. The book’s gcc did the same with 40(%rsp). In the book’s measurement, CPE for floating-point multiply goes from 0.52 back up to 0.68, and integer addition from 0.55 to 0.83. Nothing gets better, and some cases get worse.

Try it: Press 10 × 10 and read one-instruction updates. Press 20 × 20 and the sixteenth accumulator takes a load and a store around its multiply. Every register is busy, and one is left as scratch.

What the book says

10 × 10 CPE 0.55, 1.00, 1.01, 0.52. 20 × 20 CPE 0.83, 1.03, 1.02, 0.68. Throughput bounds stay 0.50, 1.00, 1.00, 0.50. The 20 × 20 snippet is vmovsd 40(%rsp), %xmm0, then vmulsd (%rdx), %xmm0, %xmm0, then vmovsd %xmm0, 40(%rsp). “Once a compiler must resort to register spilling, any advantage of maintaining multiple accumulators will most likely be lost.”

5.11.2 · branch prediction and misprediction penalties

Guess the branch, or don’t branch

The chip fetches far ahead. At a conditional branch it guesses taken or not-taken and runs down that path without committing. A correct guess commits. A wrong guess throws the work away and refills the pipe. On this machine that penalty measured about 19 cycles.

Predictable branches are cheap. The loop-back branch is almost always taken, and misses once at the end. The book’s combine4b puts the bounds check back inside the loop. In Rust you get that loop by taking length from vec_length instead of from the slice: rustc keeps the cmpq/jae check you saw in combine3.s. The check always succeeds. In the book’s measurement only integer addition slows a little (1.27 to 2.02), and the other three CPEs do not move.

Data-dependent branches are the expensive kind. minmax1 swaps a[i] and b[i] when they are out of order (std::mem::swap exchanges two values in place). In the book’s measurement that is CPE about 13.5 on random data, and 2.5–3.5 when the pattern is regular — a penalty near 20 cycles. minmax2 computes min and max (a[i].min(b[i]) gives the smaller of the two), then writes both. The book’s gcc emits a conditional move, and so does rustc: minmax2.s picks both values with cmovlq and cmovgq, while minmax1.s keeps a jle that depends on the data. In the book’s measurement, minmax2 stays near CPE 4.0 for random and for regular data.

One surprise: at -C opt-level=3 with target-cpu=haswell, rustc removes minmax1’s branch from its main loop by itself. It compares four pairs at once and stores with AVX2 masked moves (vpmaskmovq), which write only the lanes that need a swap; only the leftover pairs at the end still branch. For the default x86-64 target it keeps the branch. Our timings of all three builds are pending.

Try it: Step minmax1 on random pairs and watch a miss add 19 cycles. Switch the data to Sorted and the predictor learns. Then run minmax2: both values are computed, the branch is gone, and the cost stays flat.

What the book says

The book measures a 19-cycle misprediction penalty on the reference machine. combine4 versus combine4b: 1.27 / 3.01 / 3.01 / 5.01 against 2.02 / 3.01 / 3.01 / 5.01. minmax1 is the imperative swap; minmax2 is the functional min/max. 5.12 · 5.12.1 load performance

A load that names the next load

The combining loops touched only a few kilobytes, so they ran from cache. This section stays in that world; Chapter 6 opens the caches themselves. The reference machine has two load units, each holding up to 72 pending reads, and each can start one load per cycle. A loop that loads one value per result cannot beat CPE 0.50. Load k values per result and the floor becomes k/2.

Those combining loads did not sit on the critical path: the address was the loop index, known before the load finished. list_len is the opposite. Each node holds next: Option<Box<Node>>, a pointer to the next node or None at the end (a Box points to a value on the heap). The next address is the value just loaded. while let Some(node) = ls keeps going while there is a node, and as_deref() turns the Option<Box<Node>> into an Option<&Node>, a borrowed look at the next node. Rust guarantees that, for a sized type, an Option of a reference or a Box is one plain pointer, with None stored as the null pointer. So rustc’s loop in list_len.s is four instructions, like the book’s: count, load the next pointer, test it for null, jump. The movq (%rdi), %rdi is the whole chain. The book measured CPE 4.00 for its C version, the L1 hit time; our Rust measurement is pending.

Try it: Step the list. Each node waits until the previous load has delivered its next pointer, and the wait badge shows 4 cycles. Switch to an indexed array: the addresses are i, so the next load can start while the last one is still coming back.

5.12.2 · store performance

A store is quiet until a load reads it back

There is one store unit, with a buffer of up to 42 writes, and it can start a store every cycle. clear_array writes zeros, one movq $0 per element in clear_array.s, and the book measured CPE 1.0: the one store unit, fully used. Stores do not write registers, so a row of stores does not form a chain by itself.

A load of an address that a store has not finished is a write/read dependency. write_read stores val into dst, then reads src and adds one. The book’s C passes two pointers; the Rust listing passes two &Cell<i64>, a number you may change through a shared reference, so both may honestly name one cell. rustc’s loop in write_read.s is the book’s shape: store val, load src, add one, count down. Because a Cell may share its cell, rustc must do the load after the store, every trip. When src and dst are different cells (example A, array starting at −10 and 17), the book measured CPE 1.3 and a[0] stays −10. When they are the same cell (example B), each load sees the store that just happened, the book’s CPE rises to 7.3, and the cell becomes 0, then 1, then 2. Our Rust measurements are pending.

Try it: Step example A and watch a[1] settle at −9 while a[0] stays −10. Step example B and watch the single cell eat its own store. The code highlights the store, then the load, and the note says whether the addresses match.

5.13 · life in the real world: performance improvement techniques

Fix the shape first, then the inner loop

The chapter’s checklist has an order. Start with the algorithm and the data structure, and watch for anything that grows like n² when n gets large. Then clear the blockers so the compiler may move calls and reuse values. Then keep the inner loop free of needless calls and needless memory traffic. Only then unroll, split accumulators, reassociate, and write conditionals so the compiler can emit a conditional move.

Each rewrite can introduce a bug: a new temporary, a wrong loop limit, a tail that forgets the last elements. Checking code runs the new function against the old one. Unrolled loops need many lengths, so the tail is tested for every remainder.

Try it: Press Apply next and walk the checklist in the book’s order. The picture’s clock only starts to care about CPE after the quadratic algorithm is gone. The code panel shows the shape you just switched to.

What the book says

Three layers: high-level design; basic coding (avoid blockers, move calls, accept a little less modularity, introduce temporaries); low-level optimizations (unroll, multiple accumulators, reassociation, functional style for conditional moves). “Be vigilant to avoid introducing errors as you rewrite programs in the interest of efficiency.” Checking code compares each new version with the original, with more cases as the loop gets more special cases.

5.15 · summary

You steer, the compiler finishes

A compiler can tidy the program you wrote. It will not replace an algorithm that does too much work, and it will not assume that your functions are pure. The book’s C compiler also cannot assume your pointers are independent; Rust’s &mut rule hands it that fact. The fast combining code is still ordinary code, shaped so the critical path is short and the functional units stay busy.

The path in this picture is the chapter in one walk: abstract code, hoist, direct access, a register accumulator, unrolling, several accumulators, then a vector form. In the book’s measurements, float multiply goes from CPE 11.14 to about 0.06. Along the way the limits change: latency, then throughput, then registers, branches, and memory.

Words to know

The chapter’s words, in plain language.

CPE
Cycles per element: the slope of runtime versus n, after the fixed setup cost.
optimization blocker
Aliasing, or a call that might have a side effect. The compiler must leave the slow form in place.
code motion
Moving a loop-invariant computation to a place that runs less often.
latency bound
The CPE you get when each combine waits for the previous one. It equals the operation’s latency.
throughput bound
The CPE you get when every capable unit is kept busy. For one load per element, 0.50 on this machine.
issue time
Cycles before the same kind of independent operation can start again. 1 means fully pipelined.
critical path
The longest chain of data dependencies. A lower bound on the cycles a loop needs.
k × k unrolling
Stride-k loop plus k accumulators, enough to fill capacity × latency pipes.
reassociation
op(acc, op(a, b)) instead of op(op(acc, a), b). The pair leaves the accumulator chain.
register spilling
Live values that no longer fit in registers, so the compiler keeps them on the stack.
misprediction penalty
Cycles lost throwing away a speculative path. About 19 on the reference machine.
write/read dependency
A load of an address that still has a store waiting in the store buffer.
gprof
The book’s profiler: compile with -Og -pg, run, then gprof. A time table and a call graph.
perf
The usual Linux profiler for Rust programs. It samples where the time goes; it does not count calls.
bounds check
Rust’s test that data[i] is inside the slice, a compare and a branch. rustc drops it when it can prove the index is in range.
Cell
A Rust value you may change through a shared reference. Two names for one cell are allowed, so rustc must keep the memory traffic.
