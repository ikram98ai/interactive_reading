Transactions

A transaction is a promise: “these changes all happen together, or none of them happen at all.” It is how a database keeps its word when computers crash and everybody writes at once.

“We believe it is better to have application programmers deal with performance problems due to overuse of transactions as bottlenecks arise, rather than always coding around the lack of transactions.” — James Corbett et al., “Spanner: Google’s Globally-Distributed Database” (2012)

Big idea 1 · what a transaction is

The vending machine that never eats your coin

Moving $100 from Alice to Bob is really two changes: take money off one line, add it to the other. If the power dies in between, the money is gone from the world.

So the database lets you wrap both changes in one transaction. Either the whole thing commits, or it aborts and every write is thrown away — like a vending machine that gives your coin back when the snack gets stuck.

That is the whole trick: because an abort changes nothing, you can safely just try again.

Try it: crash the transfer with transactions on, then switch them off and crash it again. Watch the total.

What the book says

A transaction groups several reads and writes into one logical unit. It either commits, or it aborts (rolls back) and the database discards every write it made.

ACID atomicity is not about concurrency — that's the “I”. It describes what happens when a fault occurs partway through: process crash, network interruption, full disk, constraint violation. The book notes that “abortability” would have been a better word than atomicity.

Retrying an aborted transaction is simple and effective, but imperfect: a commit acknowledgment lost in the network causes a double-run unless you deduplicate; retrying under contention makes overload worse (use limited retries and exponential backoff); permanent errors like constraint violations should not be retried; and side effects outside the database, such as sending an email, still happen.

ORMs such as Rails ActiveRecord and Django don't retry aborted transactions — the error just bubbles up, which wastes the whole point of rollback.

Big idea 2 · the four letters

Four promises on the fridge door

People say a database is ACID: atomicity, consistency, isolation, durability. Four promises, coined in 1983 to give fault tolerance some precise words.

Three of them are the database's job. One of them — consistency — is mostly yours: only you know that credits must equal debits. And “ACID compliant” on a box tells you surprisingly little, because everyone implements isolation differently.

Try it: tap each letter and press Show me. Which promise is the odd one out?

What the book says
  • Atomicity: if a fault happens partway, the transaction aborts and its writes are discarded. The all-or-nothing guarantee.
  • Consistency: application-specific invariants stay true. The database can enforce some as constraints (foreign keys, uniqueness, check constraints, triggers, materialized views) — the rest is up to your code. So the C “often depends on how the application uses the database and is not a property of the database alone.”
  • Isolation: concurrent transactions don't step on each other's toes. Textbooks formalize this as serializability; in practice most databases use weaker levels.
  • Durability: once committed, data isn't forgotten — via nonvolatile storage, fsync, a write-ahead log, checksums, and/or replication to other nodes.

The term ACID was coined by Theo Härder and Andreas Reuter in 1983; the book warns it “has unfortunately become mostly a marketing term.” BASE (basically available, soft state, eventual consistency) is even vaguer — it mostly means “not ACID”.

Perfect durability does not exist: SSDs can violate their guarantees on power loss, fsync is hard to use correctly (PostgreSQL got it wrong for over 20 years), 30–80% of SSDs develop a bad block within four years, and correlated faults can take out every replica at once. Disk, replication and backups are risk-reduction techniques to use together.

Big idea 3 · single-object vs multi-object

The inbox and the little number on the icon

Counting unread emails every time is slow, so apps keep the count in a second place. Now a new email means two writes: store the email, bump the counter.

If someone looks between those two writes, they see an unread email and a counter that says zero. If the second write fails, the two stay out of sync forever. Swap “unread counter” for “account balance” and it stops being cute.

Try it: deliver an email with transactions off, then on. Then make the counter write fail.

What the book says

Writes to several objects need multi-object transactions: foreign-key references between rows, denormalized values that must stay in sync, and secondary indexes (which are separate objects — without isolation a record can appear in one index but not another).

Relational databases group operations by the client's TCP connection: everything between BEGIN TRANSACTION and COMMIT. Many nonrelational stores have no such grouping — a multi-put may succeed for some keys and fail for others.

Even single-object writes need atomicity and isolation: a 20 kB JSON document must not be stored half-sent, spliced with its old value, or read half-updated. Storage engines provide this with a log for crash recovery and a lock per object.

Some databases offer atomic increment and conditional write (compare-and-set) operations. Aerospike's strong-consistency mode and Cassandra/ScyllaDB “lightweight transactions” give linearizable reads and conditional writes on a single object, but no guarantees across objects.

Big idea 4 · the most common isolation level

No peeking at half-finished homework

Read committed makes two small promises. You only ever read finished work (no dirty reads), and you only ever overwrite finished work (no dirty writes).

Without the first, you can read a number that gets undone a second later. Without the second, two shoppers buying the same car can end up with the car going to one of them and the invoice to the other.

Try it: run the dirty read with protection off and on. Then try the dirty write — watch who gets the car and who gets the bill.

What the book says

Read committed is the default in Oracle Database, PostgreSQL, SQL Server and many others. A dirty read is reading another transaction's uncommitted write; a dirty write is overwriting one.

Dirty writes are prevented with row-level locks: a writer holds the lock until commit or abort. Dirty reads are usually prevented not by read locks (one long writer would block every reader and hurt response time) but by remembering both the old committed value and the new uncommitted one, and handing readers the old value until commit.

Read uncommitted is weaker still: it prevents dirty writes but not dirty reads.

Read committed does not prevent the lost-update race between two counter increments — there the second write happens after the first transaction committed, so it isn't a dirty write.

Big idea 5 · snapshot isolation and MVCC

Everybody gets their own photograph

Aaliyah has $500 in each of two accounts. While $100 is flying from one to the other, she refreshes her banking app — and sees $500 and $400. A hundred dollars has vanished into thin air. It's called read skew, and read committed allows it.

The fix: give each transaction a snapshot, a photograph of the whole database taken the moment it started. The database keeps several versions of every row, each stamped with the transaction that made it, and hands you the ones that were committed when your photo was taken. That's MVCC.

Because readers just pick older versions, readers never block writers, and writers never block readers.

Try it: step through with read committed, then with snapshot isolation. Watch which row versions light up as visible.

What the book says

Read skew (a nonrepeatable read) is acceptable under read committed. It is intolerable for backups (inconsistencies become permanent when restored) and for long analytical queries and integrity checks.

Multiversion concurrency control (MVCC): each transaction gets a unique, always-increasing txid. Each row has inserted_by and deleted_by fields; an update is internally a delete plus an insert. A garbage collection process removes versions nobody can see any more.

Visibility rules: ignore writes by transactions that were in progress when the snapshot was taken (even if they later commit), ignore writes by transactions with a later txid, ignore writes by aborted transactions — everything else is visible. Equivalently: a row is visible if the inserting transaction had committed when the reader started, and the deleting transaction (if any) had not.

CouchDB, Datomic and LMDB instead use immutable, copy-on-write B-trees: every write creates a new root, and each root is a consistent snapshot.

Naming is a mess: snapshot isolation is called “repeatable read” in PostgreSQL, “serializable” in Oracle; MySQL's “repeatable read” is weaker; Db2's means serializability. The SQL standard predates snapshot isolation, so “nobody really knows what repeatable read isolation means.”

Big idea 6 · lost updates

Two people counting the same cookie jar

Both of you read “42 cookies”, both add one, both write “43”. Two cookies went in; the jar says one. The second write clobbered the first. That's a lost update, and it happens any time code does read → change → write back.

There are four good cures, and the database can do most of the work: let it do the adding, take a lock first, only write if nothing changed, or let it catch you and make you retry.

Try it: run the unsafe version first, then each fix. The jar should reach 44 every time.

What the book says
  • Atomic write operations: UPDATE counters SET value = value + 1 WHERE key = 'foo'. Usually the best choice; MongoDB has atomic document updates, Redis has atomic data-structure operations. ORMs make it easy to accidentally write an unsafe read-modify-write cycle instead.
  • Explicit locking: SELECT … FOR UPDATE locks the returned rows. Easy to forget somewhere, and locking several objects risks deadlock (databases detect it and abort one transaction).
  • Automatic lost-update detection: PostgreSQL's repeatable read, Oracle's serializable and SQL Server's snapshot isolation abort the offending transaction. MySQL/InnoDB's repeatable read does not.
  • Conditional write (compare-and-set): UPDATE … WHERE id = 1234 AND content = 'old', or a version-number column — sometimes called optimistic locking.

With multi-leader or leaderless replication there is no single up-to-date copy, so locks and compare-and-set don't apply. Instead concurrent writes create siblings that get merged afterwards — the idea behind CRDTs. Last write wins is prone to lost updates.

Big idea 7 · write skew and phantoms

Both doctors call in sick

The hospital rule: at least one doctor on call. Aaliyah and Bryce are both on call, both feel ill, both press the button at the same moment. Each app checks “are there two or more on call?” — each sees 2 — and each takes themselves off. Now there are none.

No dirty write happened. No update was lost. They wrote to different rows. This is write skew: they read something, decided, and wrote — and the reason for the decision quietly stopped being true.

Meeting rooms are worse. Both transactions search for clashing bookings, find nothing, and insert. You can't lock rows that don't exist yet — that's a phantom.

Try it: both cases, all three protections. Notice that locking the rows fixes the doctors but not the room.

What the book says

Write skew generalizes lost updates: two transactions read the same objects, then update some of them. Snapshot isolation does not prevent it, and it is not caught by the lost-update detection in PostgreSQL's repeatable read, MySQL/InnoDB's repeatable read, Oracle's serializable or SQL Server's snapshot isolation.

Other examples: a meeting room booking system, a multiplayer game moving two figures to the same square, claiming a username (a uniqueness constraint fixes this one), and preventing double-spending.

The pattern is always: a SELECT checks a condition, the application decides, then a write changes the very set of rows that condition matched. When a write in one transaction changes another's search result, that's a phantom.

If the rows exist, SELECT … FOR UPDATE can lock them. If the query matches no rows there's nothing to lock. You can materialize conflicts — pre-create a table of room/time-slot rows purely to lock — but it's ugly and error-prone, “a last resort”. Automatically preventing write skew requires true serializable isolation.

Big idea 8 · serializability, way one

One cash register, no waiting room

The simplest way to stop transactions interfering is to never let two run at once. One thread, one transaction at a time. Whatever happens is serial by definition.

This only became sensible when RAM got cheap enough to hold the whole working set, and when people noticed most transactions are tiny. But a transaction that chats with the app between each statement wastes the single lane on network round trips — so you ship the whole transaction to the database ahead of time as a stored procedure.

Want more than one lane? Shard, and give each core its own shard. Transactions that touch two shards need lockstep coordination and get dramatically slower.

Try it: turn the arrival rate up in interactive mode until the queue explodes, then switch to stored procedures. Then add shards, then add cross-shard work.

What the book says

Serial execution is used by VoltDB/H-Store, Redis and Datomic. Two developments made it viable: cheap RAM for in-memory datasets, and the realization that OLTP transactions are short (long analytical reads run on a snapshot outside the serial loop).

Interactive multi-statement transactions aren't allowed; the application submits a stored procedure. Modern ones use general-purpose languages: VoltDB uses Java or Groovy, Datomic Java or Clojure, Redis Lua, MongoDB JavaScript. VoltDB also runs the same deterministic stored procedure on each replica — state machine replication.

Throughput is limited to one CPU core unless you shard. Cross-shard transactions must run in lockstep across shards; VoltDB reports about 1,000 cross-shard writes per second, orders of magnitude below single-shard throughput and not improved by adding machines.

Constraints: every transaction must be small and fast (one slow one stalls everything), the active dataset should fit in memory, and write throughput must fit on one core or shard cleanly.

Big idea 9 · serializability, way two

Everyone takes a key from the key rack

Two-phase locking is the old, strict way. Readers may share a key; a writer needs the key all to itself. Once you have taken a key you keep it until you commit — first you only collect keys (the growing phase), then you hand them all back at once (the shrinking phase).

It works: writers block readers, readers block writers, and every race in this chapter disappears. It also hurts: waiting, unstable latency, and deadlock when two transactions each hold the key the other needs. The database notices and kills one.

For phantoms you'd need a lock on a question (“any booking for room 123 at noon?”) — a predicate lock. Those are slow, so databases lock a range of an index instead: a bigger net, much cheaper.

Try it: run the three scripts. In the deadlock one, watch who gets aborted.

What the book says

2PL is not 2PC. 2PL gives serializable isolation; 2PC gives atomic commit across nodes.

Locks are shared or exclusive (multi-reader single-writer). A transaction may upgrade shared to exclusive, and must hold every lock until commit or abort — hence “two-phase”. 2PL is used by the serializable level in MySQL/InnoDB and SQL Server, and by repeatable read in Db2.

Performance is the reason it isn't the default: overhead plus much reduced concurrency. One big read takes a shared lock on the whole table and blocks all writers; latencies become unstable and very slow at high percentiles. Deadlocks are far more frequent than under read committed, and a deadlocked transaction's work is wasted.

A predicate lock covers all objects matching a search condition, including ones that don't exist yet. Because checking many predicate locks is slow, most databases use index-range locking (next-key locking), a safe approximation that locks a larger set. With no suitable index, the fallback is a shared lock on the whole table.

Big idea 10 · serializability, way three

Run first, check at the door

2PL is pessimistic: assume trouble, wait. Serializable snapshot isolation is optimistic: let everyone run on their own snapshot, nobody waits — but remember what each transaction read, like a tripwire.

At the door (commit time), the database asks: did anything I read change underneath me? If yes, this transaction acted on an outdated premise, so it is aborted and retried. Only genuinely serializable runs are let through.

It's the best of both worlds when there's spare capacity and not too much fighting over the same rows — and it scales, because the checking itself can be spread across machines.

Try it: run all three scripts. Notice the database waits until commit before deciding to abort.

What the book says

SSI was first described in 2008 and gives full serializability with only a small penalty over snapshot isolation. It's used by PostgreSQL's serializable level, SQL Server's In-Memory OLTP (Hekaton), HyPer, CockroachDB, FoundationDB and BadgerDB.

Two things to detect: stale MVCC reads (the transaction ignored an uncommitted write that has since committed) and writes that affect prior reads (tracked on index entries, like an index-range lock that doesn't block — a tripwire that only notifies).

Why wait until commit? A read-only transaction never needs aborting, the writer may yet abort, and avoiding unnecessary aborts preserves long-running consistent-snapshot reads.

Trade-offs: finer tracking means more precise aborts but more bookkeeping. Optimistic control performs badly under high contention; commutative atomic operations reduce contention. Read/write transactions should be short — long read-only ones are fine. Unlike 2PL, nothing blocks, so query latency is much more predictable.

Big idea 11 · distributed transactions

The wedding where everyone must say “I do”

When one transaction touches several machines, “just commit on each” goes wrong fast: some commit, some crash, some time out — and a commit can't be taken back, because someone has already read it.

So a coordinator asks everyone first. Phase one: “are you able to commit?” Saying yes is a promise you can never break. Phase two: once every answer is in, the coordinator writes its decision to its own disk — the commit point — and then tells everyone, retrying forever.

And if the coordinator faints between the two phases? Everyone who said yes is stuck in doubt, holding their locks, unable to decide alone. That's why 2PC is called a blocking protocol.

Try it: run all three scripts, especially the crash. Watch the locks stay locked.

What the book says

Two-phase commit solves the atomic commitment problem across nodes. A coordinator (transaction manager — Narayana, JOTM, BTM, MSDTC) hands out a global transaction ID, sends prepare to each participant, and commits only if all vote yes.

Two points of no return: a participant that votes yes has written everything to disk and checked all constraints, surrendering its right to abort; and the coordinator's decision, once written to its log, is irrevocable and retried forever.

If the coordinator crashes after votes, participants are in doubt and can only wait — they must keep holding locks even across restarts, blocking other transactions. Lost coordinator logs need manual resolution; heuristic decisions let a participant decide alone, which the book calls “a euphemism for probably breaking atomicity”. 3PC assumes bounded delays, so it doesn't help in practice.

XA (1991) standardizes 2PC across heterogeneous systems as a C API; it can't detect cross-system deadlocks and doesn't work with SSI. Database-internal distributed transactions (CockroachDB, TiDB, Spanner, FoundationDB, YugabyteDB, Kafka) avoid the lowest-common-denominator trap by replicating the coordinator with consensus and letting shards talk directly.

You often don't need distributed transactions at all: recording a processed message ID in the same database transaction makes processing idempotent, giving exactly-once semantics without atomic commit across systems.

Every guarantee costs something. Nobody gets everything.

No races at all, paid for in throughput or aborts

Words to know

Grown-up words, in plain language.

transaction
A bundle of reads and writes the database treats as one single move.
commit
“Done — make it real.” After this, the changes are official.
abort / rollback
“Never mind.” Every write from that transaction is thrown away.
atomicity
All of it happens, or none of it does. Really it means “abortable”.
consistency (ACID)
Your own rules about the data stay true. Mostly your job, not the database's.
invariant / constraint
A rule that must always hold, and the database's way of enforcing one.
isolation
Transactions don't step on each other's toes, even when they run at the same time.
durability
Once committed, not forgotten — written to disk and/or copied to other machines.
fsync
“Really write it to the disk now,” not just into memory.
write-ahead log
A notebook of what's about to change, so a crash can be cleaned up afterwards.
dirty read
Seeing someone's change before they've finished — it might get undone.
dirty write
Scribbling over someone's unfinished change.
read committed
Only read finished work, only overwrite finished work. The common default.
read skew
Seeing different parts of the database from different moments, so the sums look wrong.
snapshot isolation
Your transaction reads from a photograph of the database taken when it started.
MVCC
Keeping several versions of each row, each stamped with who wrote it.
txid
The ever-increasing number that names a transaction.
lost update
Two read-change-write cycles collide and one change disappears.
compare-and-set
“Only change it if it's still what I last saw.”
write skew
Two transactions each write something based on a fact that the other just made false.
phantom
A new row that changes the answer to someone else's search.
materializing conflicts
Inventing rows just so there is something to lock. A last resort.
serializable
The result is as if transactions had run one after another. The strongest level.
two-phase locking (2PL)
Collect every lock first, release them all at the end.
deadlock
Two transactions each holding what the other needs. Somebody has to be killed.
predicate / index-range lock
Locking a question instead of a row, or a chunk of an index as a cheap stand-in.
SSI
Let everyone run, remember what they read, and abort anyone whose reasons went stale.
two-phase commit (2PC)
Ask everyone “can you?”, then tell everyone “do it.”
in doubt
A participant that voted yes and lost contact: it must wait, still holding its locks.
idempotent
Safe to do twice. Doing it again changes nothing.
