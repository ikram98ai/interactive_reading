Storage and indexing for OLTP · the world’s simplest database

A database in two lines of shell

Amara keeps a notebook for her bike shop. Every time a price changes she writes a new line at the bottom — never crossing anything out. To find today’s price for a bike, she reads the whole notebook and trusts the last line that mentions it. Writing takes a second. Finding things takes longer every month.

That notebook is a real database. db_set appends key,value to the end of a file; db_get searches the file for every line starting with that key and keeps the last one. Old values are never overwritten, so the newest line wins. A file you only ever add to is called a log: an append-only sequence of records, not necessarily human-readable.

Appending is about the cheapest thing a disk can do, so writes are fast. But db_get reads every line to answer one question: double the records and a lookup takes twice as long. That is O(n), and it is why the rest of this chapter exists.

RememberA log makes writes trivially cheap — append one line — and reads hopelessly expensive: every lookup rereads the whole file. Indexes exist to fix the reads.

Try it: in Run the script, press Next command six times and follow the highlighted line of bash; watch db_get read every line of the file and keep the last match. Then switch to Grow the file, slide the number of records up, and press db_get 42 and db_set at each size.

What the book says

On the most fundamental level, a database stores the data you give it and gives it back when you ask later. Chapter 3 looked at that from your side (data models and query languages); this chapter looks from the database’s side. You will probably not implement a storage engine, but you do need to select one appropriate for your application and have a rough idea of what it does under the hood in order to configure it. Engines optimized for transactional workloads (OLTP) differ greatly from those optimized for analytics; for OLTP the chapter examines two families: log-structured engines that write out immutable data files, and engines such as B-trees that update data in place.

“Consider the world’s simplest database, implemented as two bash functions”: db_set appends key,value to a file named database; db_get greps for the key and uses tail -n 1, because updating a key several times leaves the old versions in the file and you need the last occurrence. The value can be almost anything, for example a JSON document.

Appending to a file is generally very efficient, and many databases internally use a log, an append-only data file. In this book, log means an append-only sequence of records on disk — it might be binary and intended only for internal use, unlike application logs. Real databases also have to handle concurrent writes, reclaim disk space so the log doesn’t grow forever, and handle partially written records when recovering from a crash.

db_get has terrible performance with many records: it scans the entire file from beginning to end, so a lookup is O(n) — double the records and a lookup takes twice as long.

Storage and indexing for OLTP · indexes

Every signpost has to be repainted

A city library shelves books in the order they arrive. To find one fast, the librarians keep card catalogues: one sorted by title, one by author. The catalogues don’t change a single book — throw them away and every book is still there — but with them, finding a title takes seconds instead of a walk past every shelf.

The catch: every new book now means a new card in every catalogue, and the drawers fill a room of their own. A database index is exactly that — an extra structure derived from the data, which speeds up some reads and slows down every write. That is why databases don’t index everything for you: you choose indexes from the queries your application actually runs.

RememberAn index is a sorted copy of part of your data, built for one kind of question. It speeds up only that question; every write pays to keep it current.

Try it: press Find country = NG with no indexes and watch every row being read. Tap the index on country box and find again. Press Insert a row with one, then two indexes on, and watch where each new entry lands. Finally set the Reads slider and press Run 100 queries: the bars compare all four choices of index on the same workload.

What the book says

To efficiently find the value for a key, we need an index. The general idea is to structure the data in a particular way (for example, sorted by a key) that makes it faster to locate what you want; to search the same data in several ways you may need several indexes on different parts of the data.

An index is an additional structure derived from the primary data. Many databases let you add and remove indexes; this doesn’t affect the contents of the database, only the performance of queries.

Maintaining additional structures incurs overhead, especially on writes: it is hard to beat simply appending to a file, and any kind of index usually slows down writes, because the index also needs to be updated every time data is written.

This is an important trade-off: well-chosen indexes speed up read queries, but every index consumes additional disk space and slows down writes, sometimes substantially. So databases don’t usually index everything by default; the application developer or administrator selects indexes manually, using knowledge of the typical query patterns.

Log-structured storage · an in-memory hash map

A sticky note that says where to look

Back to Amara’s notebook. Her friend Kenji tapes a sticky note inside the cover: “bike 42 → page 3, line 7.” Each time Amara writes a new line, she updates the note. Now finding a price is one glance at the note and one flip to the right line — however thick the notebook gets.

Keep writing to the same append-only log, but hold a hash map in memory from every key to the byte offset where its newest value starts. A write appends and updates the map; a read looks up the offset and seeks straight there. If that part of the file is still in the filesystem cache, the read needs no disk I/O at all.

Much faster — but it still has four problems, and each mode of the machine shows one: the log never frees overwritten entries; the map lives only in memory, so a restart has to rebuild it; every key must fit in memory; and you can’t ask for a range of keys.

RememberA hash map of offsets makes a log fast to read — only while every key fits in RAM, you never need a range, and restarts can afford a full rescan.

Try it: in Hash index, press db_set a few times and watch the map’s offsets move, then db_get 42 (cached), db_get 12 (one seek) and db_get 5 (absent). Then visit each problem: Disk fills (keep writing), Restart (restart, then grow the log and restart again), Too big (add keys, then move the map to disk and add more), Range (find 10000–19999).

What the book says

To keep storing data in the append-only file written by db_set and just speed up reads, keep a hash map in memory, mapping every key to the byte offset where the most recent value for that key can be found (Figure 4-1). Whenever you append a new key-value pair, also update the hash map; to look up a value, use the map to find the offset, seek there and read. If that part of the data file is already in the filesystem cache, a read doesn’t require any disk I/O at all.

Problems remain: you never free up disk space occupied by old log entries that have been overwritten, so you might run out of disk space; the hash map is not persisted, so on restart you must rebuild it — for example, by scanning the whole log file to find the latest byte offset for each key — which makes restarts slow with a lot of data.

The hash table must fit in memory. You could maintain one on disk, but it is difficult to make an on-disk hash map perform well: it requires a lot of random access I/O, it’s expensive to grow when it becomes full, and hash collisions require fiddly logic.

Range queries are not efficient: you can’t easily scan over all keys from 10000 to 19999 — you have to look up each key individually in the hash map.

Log-structured storage · the SSTable file format

A dictionary with thumb tabs

Nobody reads a dictionary from page one. The words are in order, and the tabs on the edge tell you where each letter begins, so you open at roughly the right page and read a few lines. You don’t need a tab for every word — one per section is plenty.

A Sorted String Table, or SSTable, is a file of key-value pairs sorted by key, with each key appearing once. The pairs are grouped into blocks of a few kilobytes, and the index keeps only the first key of each block — a sparse index. To find handiwork, which isn’t in the index, the order tells you it must sit between handbag and handsome: read that one block, and stop as soon as you pass where it would be.

In practice databases rarely use hash tables for indexes; sorted structures like this are much more common. Each block can also be compressed: less disk space and less I/O bandwidth, for a little CPU time.

RememberSorting lets the index forget most keys: the first key of each block is enough, because any key can only live in the one block whose range covers it.

Try it: press each get button and watch which tab is chosen and how far the scan goes: handiwork is there, handheld is not (the scan stops early), hamster sits in the first block, abacus is smaller than every tab, and zebra runs off the end of the last block. Then switch to Compressed blocks and watch a block get unpacked.

What the book says

In practice, hash tables are not used very often for database indexes; it is much more common to keep data sorted by key. One such structure is a Sorted String Table, or SSTable (Figure 4-2): it stores key-value pairs, but ensures they are sorted by key and each key appears only once in the file.

You no longer need to keep all the keys in memory: group the pairs into blocks of a few kilobytes and store the first key of each block in the index. An index that stores only some of the keys is called sparse. It is stored in a separate part of the SSTable — for example, as an immutable B-tree, a trie, or another structure that allows quick lookup of a particular key.

In Figure 4-2 the first key of one block is handbag and of the next handsome. Looking for handiwork, which isn’t in the sparse index, the sorting tells you it must appear between them: seek to the offset for handbag and scan from there until you find it (or not, if the key is not present). A block of a few kilobytes can be scanned very quickly.

Each block can also be compressed (the shaded area in the figure). Besides saving disk space, compression reduces I/O bandwidth use, at the cost of a bit more CPU time.

Constructing and merging SSTables · the memtable

Sort it in your head, then write it down

Sorted files are lovely to read and awful to write. If a new word arrives that belongs in the middle, everything after it has to move. Rewriting the whole file for each insert would be far too slow.

So Fatima, who runs a lost-property desk, keeps today’s arrivals on a small sorted card tray on her desk. Cards go in wherever they belong, in any order. When the tray is full she writes the whole tray out, already sorted, as a fresh page in the binder — and starts a new tray. To find something she checks the tray first, then the binder pages from newest to oldest.

That tray is the memtable: an in-memory ordered map such as a red–black tree, a skip list or a trie, which accepts keys in any order and reads them back sorted. Past a threshold (a few megabytes) it is written out as the newest SSTable segment, with its own index, while a fresh memtable keeps taking writes. Every so often a background merge combines old segments.

RememberSort in memory, write sorted files once: the memtable absorbs random-order writes, and reads check newest to oldest so the latest value always wins.

Try it: in Memtable, press Write four times and watch each key slot into sorted order. Press Write again: the new key lands in a fresh memtable while the full one streams to disk as a segment. Keep writing, then press each get: grape comes from memory, kiwi from the newest segment (not the older value), fig from the oldest, and lemon checks everything. In One sorted file, insert keys straight into a sorted file and count the records rewritten.

What the book says

The SSTable format is better for reading than an append-only log, but makes writes more difficult: you can’t simply append, because the file would no longer be sorted (unless keys arrive in ascending order), and rewriting the whole SSTable every time a key is inserted in the middle would make writes far too expensive.

The solution is a log-structured approach, a hybrid of an append-only log and a sorted file: (1) add each incoming write to an in-memory ordered map — a red–black tree, skip list or trie — called the memtable; you can insert keys in any order, look them up efficiently and read them back sorted. (2) When it gets bigger than a threshold, typically a few megabytes, write it to disk in sorted order as an SSTable file: the most recent segment, stored alongside older segments, each with a separate index of its contents. Meanwhile the database continues writing to a new memtable instance, and the old memtable’s memory is freed once the SSTable is complete.

(3) To read, first try the memtable and the most recent on-disk segment, then the next-older segment, until you find the key or reach the oldest; if it appears in no segment, it does not exist. (4) From time to time, run a merging and compaction process in the background to combine segment files and discard overwritten or deleted values.

Constructing and merging SSTables · merging segments

Three sorted piles, one sorted pile

Three teachers each hand Diego a stack of exam papers, already sorted by surname. To combine them he doesn’t shuffle and re-sort: he puts the three stacks side by side, looks at the top paper of each, moves the alphabetically first one onto his output pile, and repeats. If the same student appears in two stacks — a resit — he keeps only the most recent paper.

Merging SSTable segments works exactly like the merge step of mergesort. Read the inputs side by side, copy the lowest key to the output, and when a key appears in several inputs keep only the value from the most recent segment. The output is a new segment: still sorted, one value per key — and because only the head of each input is ever needed, it uses very little memory, however big the files are.

RememberMerging sorted segments is mergesort’s merge step: always copy the smallest head, and when several inputs share a key, the newest input wins.

Try it: press Step and follow the three blue heads and the highlighted pseudocode. Watch apple, fig and mango (in two inputs) and kiwi (in all three): only the newest value survives. Or press Play and watch “keys in memory” never go above three.

What the book says

Merging segments works similarly to the mergesort algorithm (Figure 4-3): start reading the input files side by side, look at the first key in each file, copy the lowest key (according to the sort order) to the output file, and repeat.

If the same key appears in more than one input file, keep only the more recent value. This produces a new merged segment file, also sorted by key, with one value per key.

It uses minimal memory, because we can iterate over the SSTables one key at a time.

Constructing and merging SSTables · the log and crash recovery

Memory forgets when the lights go out

Fatima’s card tray has a weakness: if someone knocks it off the desk, today’s cards are gone. So she adds a habit. Before a card goes on the tray, she jots the same item at the bottom of a plain paper list — no sorting, just one line after another. If the tray spills, she rebuilds it from the list. Once a tray has been copied into the binder, she tears off that part of the list.

LSM engines do the same. Every write is first appended to a separate log on disk, then put in the memtable. The log isn’t sorted — it only exists to restore the memtable after a crash, and the part covered by a finished SSTable is discarded. Segments are written once and never changed, so a crash halfway through writing one is easy too: delete the unfinished file and start afresh. A record cut off halfway (a crash mid-append, or a full disk) is caught by its checksum and thrown away.

RememberThe memtable is fast because it is in RAM; the log makes it safe. Append first, replay after a crash, and let checksums discard half-written records.

Try it: in No log, press Write twice and Flush, then Write twice more, Crash and Restart: the flushed SSTable survives, the memtable doesn’t. Do the same in With a log and nothing is lost; watch Flush discard the log. In Torn record, crash in the middle of a write and see the checksum reject it. In Crash mid-flush, crash while the SSTable is half-written.

What the book says

To ensure that the data in the memtable is not lost if the database crashes, the storage engine keeps a separate log on disk to which every write is immediately appended. This log is not sorted by key, but that doesn’t matter, because its only purpose is to restore the memtable after a crash. Every time the memtable gets written out to an SSTable, the corresponding part of the log can be discarded.

Immutable segment files simplify crash recovery: if a crash happens while writing out the memtable or while merging segments, the database can just delete the unfinished SSTable and start afresh.

The log that persists writes to the memtable could contain incomplete records if there was a crash halfway through writing a record, or if the disk was full. These issues are typically detected by including checksums in the log and discarding corrupted or incomplete log entries. Durability and crash recovery return in Chapter 8.

Constructing and merging SSTables · deleting with tombstones

You can’t erase ink, so you pin a “cancelled” card

The village notice board has one rule: nobody takes a note down. When Amara’s Tuesday yoga class is cancelled, she can’t remove last week’s poster, so she pins a new card on top: “Tuesday yoga — cancelled.” Anyone reading the board from the newest note downwards meets the card first and stops. Once a month the caretaker rewrites the whole board, and both the poster and the card disappear.

An LSM engine has the same problem: its segment files are never edited. To delete a key it appends a special deletion record, a tombstone, just like any other write. A read that meets the tombstone before any older value answers “not found”. When segments are merged, the tombstone tells the merge to throw away the older values for that key. The tombstone itself must survive every merge until it reaches the oldest segment, because until then some older segment might still hold a value it has to hide.

RememberA delete is just another write: a tombstone that hides older values until compaction carries it down to the oldest segment, where both disappear.

Try it: press Delete 42, then Read 42 and follow the probe down the segments. Press Flush memtable, then Merge two newest three times, watching the merge output fill up key by key and the count of copies of 42 on disk. Read 42 after each merge — it stays deleted, and the tombstone vanishes only in the last merge.

What the book says

If you want to delete a key and its associated value, you have to append a special deletion record called a tombstone to the data file.

When log segments are merged, the tombstone tells the merging process to discard any previous values for the deleted key. Once the tombstone is merged into the oldest segment, it can be dropped.

Reads look in the memtable first and then in segments from the most recent to the oldest, so the tombstone is met before any older value of the key.

Deletions therefore take space until compaction runs: a deleted record may still exist in older segments until its tombstone has propagated through all of them (the book comes back to this under disk space usage).

Constructing and merging SSTables · immutable segments

Build the new shelf in the back room

The museum is merging three small rooms of fossils into one big gallery. Nobody closes the museum for it. Curators copy the exhibits into the new gallery behind a curtain, while visitors keep walking through the three old rooms. When the gallery is complete, a guard turns one sign at the door, everybody goes to the new gallery from then on, and the old rooms are emptied.

That is how an LSM storage engine compacts. A segment file is written in one pass and is immutable afterwards. A background thread reads the input segments and writes the merged one, while reads keep using the inputs. When the merge is done, reads switch to the new segment in one step, and only then are the inputs deleted. If the machine crashes mid-merge, the half-written output is simply thrown away; the inputs were never touched. Files that are written whole and never edited are also exactly what object storage is good at.

RememberSegments are written once and never edited, so compaction builds a new file beside the old ones and swaps it in with one step — a crash leaves nothing half-changed.

Try it: press Merge: next step one step at a time, with a Send a read between steps: reads go to the old segments until the switch. Reset, step to the middle of the copying and press Crash. Then switch to Object storage and flush, flush, merge: count how many objects are ever modified.

What the book says

The algorithm (memtable, SSTables, merging and compaction) is essentially what is used in RocksDB, Cassandra, ScyllaDB and HBase, all of which were inspired by Google’s Bigtable paper, which introduced the terms SSTable and memtable. It was originally published in 1996 under the name Log-Structured Merge-tree, or LSM-tree, building on earlier work on log-structured filesystems; engines based on merging and compacting sorted files are often called LSM storage engines.

A segment file is written in one pass (by writing out the memtable or by merging existing segments), and thereafter it is immutable. Merging and compaction can be done in a background thread; while it goes on, reads are still served from the input segments. When merging is complete, read requests switch to the new merged segment, and the input segment files can be deleted.

Segment files don’t have to be on a local disk; they are also well suited to object storage. SlateDB and Delta Lake take this approach.

Immutable segments also simplify crash recovery: if a crash happens while writing out the memtable or merging, the database can just delete the unfinished SSTable and start afresh.

Log-structured storage · Bloom filters

A row of light switches that can say “definitely not”

Before Kenji walks to the far end of the warehouse, he checks a panel of 16 light switches by the door. When a box is shelved, a rule turns on three switches picked from its name. To check a name, he flips nothing — he just looks at its three switches. If any one of them is off, the box was never shelved, and he saves the walk. If all three are on, the box is probably there, though other boxes might have switched those lights on by coincidence.

That panel is a Bloom filter. LSM engines keep one per segment, because reading a key that is old — or that doesn’t exist — means checking segment after segment. Each key is hashed to a few bit positions, set to 1. A query hashes the same way: a single 0 means definitely absent, skip the file; all 1s means probably present. When it says “present” but the key isn’t there, that’s a false positive: a wasted block read, nothing worse.

RememberA Bloom filter only says “definitely not” or “maybe”: one 0 bit proves a key is absent for free; all 1s still costs a block read.

Try it: in The filter, query handheld, then add more keys and query again until you catch a false positive. In Tuning, slide the bits per key and compare the measured rate with the rule of thumb. In In an LSM read, look up a missing key with the filters on and off and compare the disk reads.

What the book says

With LSM storage it can be slow to read a key that was last updated long ago, or one that doesn’t exist, since several segment files must be checked. So LSM engines often include a Bloom filter in each segment: a fast but approximate way to check whether a key appears in that SSTable. It is stored with the sparse index and is generally small compared to the rest of the SSTable.

Figure 4-4 shows a filter with two keys and 16 bits. For every key, a hash function produces a set of numbers used as indexes into the bit array; those bits are set to 1. The key handbag hashes to (2, 9, 4). Querying handheld hashes to (6, 11, 2): bit 2 is 1, but the other two are 0. The checks are bitwise operations that all CPUs support.

If at least one bit is 0, the key definitely does not appear in the SSTable. If all are 1, it is likely there, but those bits may have been set by other keys — a false positive. The probability depends on the number of keys, the number of bits set per key and the total number of bits. Rule of thumb: 10 bits of filter per key gives about 1% false positives, and every 5 additional bits per key reduces it tenfold.

In an LSM engine false positives are no problem: if the filter says absent, skip that SSTable; if it says present, consult the sparse index and decode the block. A false positive costs a bit of unnecessary work, and the search continues with the next-oldest segment.

Log-structured storage · compaction strategies

Two ways to tidy the same pile

Two flatmates file the same stream of receipts. Lars waits until he has four folders of about the same thickness, then merges them into one fat folder; four fat folders become one enormous one. Mei keeps thin folders of fixed size, each covering a slice of the alphabet, arranged in shelves that get bigger further down; when a shelf overflows, she merges one folder into the overlapping folders on the shelf below.

Lars is doing size-tiered compaction: little rewriting, so it keeps up with very fast writes, but a lookup may have to check every folder, old copies linger, and merging huge folders needs lots of spare room. Mei is doing leveled compaction: each level beyond L0 is split into key ranges, so a lookup checks one folder per level, and work happens in small steps — at the price of rewriting data more often.

RememberSize-tiered rewrites little but leaves overlapping SSTables to check; leveled keeps each level’s key ranges apart, so a lookup reads one SSTable per level — paid for in rewrites.

Try it: press Write 4 batches and watch both sides compact the same writes. Press Look up a key and watch each side open SSTables one by one, newest first: leveled skips every SSTable whose key range can’t hold the key. Compare the numbers under each side, then switch to Few hot keys, reset, and write again.

What the book says

An important detail is how the engine chooses when to compact and which SSTables to include; many LSM systems let you configure the compaction strategy.

Size-tiered: newer and smaller SSTables are successively merged into older and larger ones. For example, four 256 MB SSTables might be compacted into one 898 MB SSTable (not 1,024 MB, because of deletions, overwrites, time-to-live expirations and so on). The older SSTables can get very large, and merging them needs a lot of temporary disk space. Its advantage: it can handle very high write throughput, since most data is rewritten only a few times in larger sequential merges.

Leveled: SSTable sizes stay fixed and are grouped into increasing “levels” (L0, L1, and so on). L0 holds the most recently written data; all levels beyond L0 contain key range–partitioned SSTables — for example L1 might have one SSTable for keys a–m and one for n–z. Each level has its own size limit and is larger than the one before; when a level exceeds its limit, SSTables from level i are merged into level i + 1 and deleted from level i. Compaction proceeds more incrementally and uses less disk space, and reads check fewer SSTables.

Rule of thumb: size-tiered performs better for mostly writes and few reads; leveled performs better for read-dominated workloads, and can also help if you write a small number of keys frequently and a large number rarely. Most LSM implementations offer several strategies.

Embedded storage engines

A database you call like a function

Most shops phone the wholesaler for every item. Ngozi’s corner shop keeps its own stockroom behind the counter instead: no call, no waiting on hold — she just turns around. The catch is that the stockroom is in her shop. A second branch across town can’t turn around into it.

An embedded database is the stockroom. It is a library that runs inside your application’s process, reads and writes files on the local disk, and is used through ordinary function calls — no server, no network. Phones are full of them. On a backend they fit when the data fits one machine and there aren’t many concurrent transactions, and one neat pattern is to give every small, separate tenant its own embedded database file.

RememberAn embedded database is a function call into a library that reads a local file: no network hop, but the data lives on one machine.

Try it: in Server or library, run the lookups both ways and compare the time, then press Add a second app server. In One file per tenant, send requests from different shops, add a tenant, and try a query across all tenants.

What the book says

Many databases run as a service that accepts queries over a network, but embedded databases don’t expose a network API. Signposts on numbered pages

A huge binder of recipes is split into numbered pages of equal size. Page 0 is a signpost: “below 100 → page 1, 100 to 200 → page 2, 200 to 300 → page 3 …”. Page 3 is a finer signpost for 200–300, pointing at more pages, and the bottom pages hold the recipes themselves. Finding recipe 251 takes three page turns, however thick the binder gets.

That is a B-tree, the most widely used structure for reading and writing records by key. Like an SSTable it keeps keys sorted, but instead of immutable segments it breaks the database into fixed-size pages and overwrites a page in place. Pages refer to each other by page number, a pointer on disk: page number × page size = byte offset in the file. Each page holds keys and child references; the keys between references are the boundaries of each child’s range. The number of children per page is the branching factor.

RememberA B-tree is fixed-size pages linked by page numbers: a lookup reads one page per level, and an update overwrites one page in place.

Try it: press Look up 251 and follow the code: on each page the key is compared with the boundaries (green ≤ 251, red > 251) to pick the child; three page reads, each at an offset you can see on the disk strip. What the book says

Introduced in 1970 and called “ubiquitous” less than 10 years later, B-trees remain the standard index implementation in almost all relational databases, and many nonrelational databases use them too. Like SSTables they keep key-value pairs sorted by key, allowing efficient lookups and range queries, but the design philosophy is very different.

Log-structured indexes break the database into variable-size segments, typically several megabytes or more, written once and then immutable. B-trees break it into fixed-size blocks or pages and may overwrite a page in place. A page is traditionally 4 KiB, but PostgreSQL now uses 8 KiB and MySQL 16 KiB by default. Each page has a page number, so one page can refer to another — like a pointer, but on disk. If all pages are in one file, page number × page size gives the byte offset.

One page is the root; every lookup starts there. A page contains keys and references to child pages; each child is responsible for a continuous range of keys, and the keys between the references mark the boundaries. To find 251 (Figure 4-5) you follow the reference between boundaries 200 and 300, then the page for 250–270, down to a leaf page, which holds each value inline or a reference to where it is stored. (This is sometimes called a B+ tree; the book doesn’t distinguish the variants.)

The number of child references in one page is the branching factor — six in Figure 4-5, typically several hundred in practice. To update a value, search for the leaf containing the key and overwrite that page on disk with the new version.

When a page is full, cut it in half

Kofi’s address book has one card per letter range, and the card for 333–345 is full. B-trees grow exactly like this. A new key goes into the leaf whose range covers it; if there’s no room, the page splits into two half-full pages, and the parent gains a boundary key and a reference. Splits can cascade to the root; a root split adds a new root. Because the tree only grows at the top, every leaf stays at the same depth: the tree is always balanced, with depth O(log n).

RememberB-trees grow only at the top: a full page splits in half and pushes a boundary up, so every leaf stays at the same depth.

What the book says

To add a new key, find the page whose range encompasses it and add it there. If there isn’t enough free space, the page is split into two half-full pages, and the parent page is updated to account for the new subdivision of key ranges.

In Figure 4-6 the page for 333–345 is full when key 334 arrives. It is split into a page for 333–337 (which includes 334) and a page for 337–345, and the parent gets references to both children with the boundary value 337 between them. If the parent doesn’t have enough space for the new reference, it may need to be split as well, and splits can continue all the way to the root. When the root is split, a new root is made above it. Deleting keys (which may require nodes to be merged) is more complex.

This algorithm ensures the tree remains balanced: a B-tree with n keys always has a depth of O(log n). Most databases fit into a B-tree that is three or four levels deep, so you don’t need to follow many page references. A four-level tree of 4 KiB pages with a branching factor of 500 can store up to 250 TB.

B-trees · making B-trees reliable

Write the plan down before you move the shelves

Mateo runs a library whose signposts point to shelves. One shelf is full, so he splits it: half the books go to an empty shelf, the old shelf keeps the rest, and the signpost gets a new arrow. Three separate jobs. Halfway through, the lights go out. The new shelf is full of books, but no signpost points to it, and the old shelf has lost half its books. Nobody will ever find them.

A B-tree changes data by overwriting a page in place, at the same spot on disk, so every reference to it stays valid. That works for one page. A page split overwrites three, and a crash between them leaves a corrupted tree: an orphan page no parent points to. Even one page isn’t safe: the disk can’t write all 4 KiB at once, so a crash can leave a torn page, half new and half old.

The fix is Mateo’s notebook: a write-ahead log (WAL). Every change is appended to it, and forced to disk with fsync, before any page is touched. Once the log is safe, pages can wait in memory and be written whenever it suits. After a crash, the database replays the log and the tree is whole again.

RememberA B-tree overwrites pages in place, so a change touching several pages is crash-safe only if it is appended to a write-ahead log and fsynced first.

Try it: in No WAL, press Insert 334. The power fails after the second page write. Press Restart & look up 340. Change the crash point with the second button and run it again. Then try the same in With WAL, and in Torn page.

What the book says

The basic underlying write operation of a B-tree is to overwrite a page on disk with new data. It is assumed that the overwrite does not change the location of the page; all references to that page remain intact. This is in stark contrast to log-structured indexes such as LSM-trees, which only append to files (and eventually delete obsolete files) but never modify files in place.

Overwriting several pages at once, as in a page split, is a dangerous operation: if the database crashes after only some of the pages have been written, you end up with a corrupted tree (e.g., an orphan page that is not a child of any parent). If the hardware can’t atomically write an entire page, you can also end up with a partially written page, known as a torn page.

To make the database resilient to crashes, B-tree implementations commonly include a write-ahead log (WAL): an append-only file to which every B-tree modification must be written before it can be applied to the pages of the tree itself. After a crash, this log is used to restore the B-tree to a consistent state. In filesystems, the equivalent mechanism is known as journaling.

To improve performance, B-tree implementations typically don’t immediately write every modified page to disk, but buffer the pages in memory for a while. The WAL ensures that data is not lost in a crash: as long as data has been written to the WAL and flushed to disk using the fsync system call, it is durable, because the database can recover it after a crash.

B-trees · using B-tree variants

Four tweaks to a fifty-year-old tree

B-trees have been around since 1970, so people have had plenty of time to improve them. The book picks four improvements, and each one fixes a different annoyance.

Copy-on-write never overwrites a page. It writes the changed page somewhere new, then new copies of its parents pointing at it, up to a new root, and switches over in one small step. Readers still holding the old root see the old tree, untouched. Abbreviated keys store only as much of a key as an interior page needs to tell two ranges apart, so more keys fit per page and the tree gets shallower. Sequential leaves keep leaf pages in key order on disk so a scan reads straight through. Sibling pointers let each leaf point to its neighbours, so a scan steps sideways instead of climbing back up.

RememberCopy-on-write replaces the WAL with new pages and a pointer switch; short separators widen the tree; ordered leaves and sibling pointers make range scans cheap.

Try it: one mode per tweak. In Copy-on-write, press Start a long read, then Update key 27. In Abbreviated keys, toggle the abbreviation and drag the key length. In Sequential leaves, scan, then Grow the tree and scan again. In Sibling pointers, scan 20–55 with the pointers off and on, and count the page reads.

What the book says

Since B-trees have been around for so long, many variants have been developed. Instead of overwriting pages and maintaining a WAL for crash recovery, some databases (like LMDB) use a copy-on-write scheme: a modified page is written to a different location, and a new version of the parent pages in the tree is created, pointing at the new location. This approach is also useful for concurrency control (see Snapshot Isolation and Repeatable Read, p. 293).

We can save space in pages by not storing the entire key but abbreviating it. Especially in pages on the interior of the tree, keys need to provide only enough information to act as boundaries between key ranges. Packing more keys into a page allows the tree to have a higher branching factor and thus fewer levels.

To speed up scans over the key range in sorted order, some B-tree implementations try to lay out the tree so that leaf pages appear in sequential order on disk, reducing the number of disk seeks. However, maintaining that order is difficult as the tree grows.

Additional pointers have been added to the tree. For example, each leaf page may have references to its sibling pages to the left and right, which allows scanning keys in order without jumping back to parent pages.

How many places must a read look?

Sofia keeps her recipes in one big indexed binder: three flips and she is on the right page, every time. Kenji keeps his in a stack of folders, newest on top. A recipe he wrote this morning is in the top folder; an old one means opening folder after folder. Sticky notes on each folder saying “definitely no soup recipes in here” save him a lot of opening.

A B-tree read touches one page per level, so it is fast and predictable. An LSM read may check the memtable and several SSTables at different stages of compaction; Bloom filters (the sticky notes) skip most of them. For a range the picture changes: the B-tree walks its sorted leaves, while the LSM must scan every segment in parallel and merge the results, and Bloom filters can’t help at all.

LSMs have one more read hazard: if writes arrive faster than the memtable can be flushed and compacted, the engine applies backpressure, pausing reads and writes until the flush finishes. That shows up as sudden latency spikes.

RememberA B-tree read costs one page per level. An LSM read may visit many SSTables: Bloom filters skip most for one key, never for a range.

Try it: in Point read, read a fresh key, an old key and a missing key, and switch Bloom filters off and on. In Range read, scan 20–40 in both engines. In Write burst, set Writes above Flush speed, press Run 30 seconds, and watch the code line that pauses everything.

What the book says

As a rule of thumb, LSM-trees are better suited for write-heavy applications, whereas B-trees are faster for reads. However, benchmarks are often sensitive to details of the workload; you need to test systems with your particular workload to make a valid comparison. And it’s not a strict either/or choice: storage engines sometimes blend both, for example by having multiple B-trees and merging them LSM-style.

In a B-tree, looking up a key involves reading one page at each level. Since the number of levels is usually quite small, reads are generally fast and have predictable performance. In an LSM storage engine, reads often have to check several SSTables at different stages of compaction, but Bloom filters help reduce the number of disk I/O operations required. Both approaches can perform well, depending on the engine and the workload.

Range queries are simple and fast on B-trees. On LSM storage, range queries can also use the SSTable sorting, but they need to scan all the segments in parallel and combine the results. Bloom filters don’t help for range queries (you would need to compute the hash of every possible key within the range, which is impractical), making range queries more expensive than point queries in the LSM approach.

High write throughput can cause latency spikes in a log-structured engine if the memtable fills up, for example because compaction cannot keep up with incoming writes. Many storage engines, including RocksDB, apply backpressure: they suspend all reads and writes until the memtable has been written out to disk. Regarding read throughput, modern SSDs (especially NVMe SSDs on the PCIe bus rather than SATA) can perform many independent reads in parallel; both LSM-trees and B-trees can provide high read throughput, but engines need to be carefully designed to take advantage of this parallelism.

Comparing B-trees and LSM-trees · sequential versus random writes

One long stroke beats eight short hops

Picture a record player whose needle can write. To change eight songs scattered across the record, Aisha lifts the needle, moves it, waits for the right groove to spin round, writes, and does it all again, eight times. To write eight new songs one after another, she drops the needle once and lets the record spin.

A B-tree that receives keys scattered all over the key space must overwrite pages that could be anywhere on disk: many small, scattered random writes. An LSM engine collects writes in its memtable and then writes one whole segment file in one go: fewer, larger sequential writes. On a spinning hard drive each random write costs a head movement plus a wait for the platter, several milliseconds each. SSDs have no moving parts, and the gap is smaller there, but it still exists.

RememberEvery random write pays for a seek and a spin before it writes; a sequential write pays once, then streams. That is the LSM’s write advantage.

Try it: press Write 8 keys with B-tree pages, then switch to LSM segment and press it again. Each finished write shows its cost as seek + wait + write; compare the two totals. Then switch the disk to SSD and repeat.

What the book says

With a B-tree, if the application writes keys that are scattered all over the key space, the resulting disk operations are also scattered randomly, since the pages to overwrite could be located anywhere on disk. A log-structured storage engine writes entire segment files at a time (writing out the memtable or compacting existing segments), which are much bigger than a page in a B-tree.

The pattern of many small, scattered writes is called random writes; the pattern of fewer large writes is called sequential writes. Disks generally have higher sequential write throughput than random write throughput, so a log-structured engine can generally handle higher write throughput on the same hardware than a B-tree. The difference is particularly big on spinning-disk hard drives; on the SSDs that most databases use today, it is smaller but still noticeable.

On HDDs, a random write has to mechanically move the disk head to a new position and wait for the right part of the platter to pass underneath it, which takes several milliseconds — an eternity in computing timescales. SSDs, including NVMe (flash memory attached to the PCI Express bus), have overtaken HDDs for many use cases and are not subject to such mechanical limitations.

Sidebar · sequential versus random writes on SSDs

Flash can write a page but only erase a block

A school whiteboard is split into big panels. You may write in any empty square, but the eraser is enormous: it wipes a whole panel at once. If a panel holds one class’s old notes and nothing else, you wipe it. If it mixes old notes with notes people still need, someone has to copy the needed ones somewhere else first.

Flash memory works like that. It reads and writes one page (typically 4 KiB) at a time but can only erase a whole block (typically 512 KiB). Before erasing a block, the SSD controller must move every still-valid page out of it. That is the SSD’s own garbage collection. A sequential workload fills each block with one file, so deleting the file frees whole blocks. Random writes leave blocks that mix live and dead pages, so GC has to copy more before every erase.

That copying uses write bandwidth the application can’t have, and every extra write wears the flash a little. Random writes wear an SSD out faster.

RememberFlash erases whole blocks, so live pages mixed with stale ones must be copied out first. Random writes cause that copying; sequential writes avoid it.

Try it: press Play the story with Sequential: three files are written, file B is deleted, then file D needs space. Then switch to Random and play it again. Watch which block is picked as the victim and why, then compare GC copies and Flash ÷ app.

What the book says

SSDs also have higher throughput for sequential writes than for random writes. The reason is that flash memory can be read or written one page (typically 4 KiB) at a time, but it can be erased only one block (typically 512 KiB) at a time. Some pages in a block may contain valid data, whereas others may contain data that is no longer needed.

Before erasing a block, the controller must move pages containing valid data into other blocks; this process is called garbage collection (GC).

A sequential write workload writes larger chunks of data at a time, so it is likely that a whole 512 KiB block belongs to a single file; when that file is later deleted, the whole block can be erased without any GC. With a random write workload, a block more likely contains a mixture of pages with valid and invalid data, so the garbage collector has to perform more work before a block can be erased.

The write bandwidth consumed by GC is then not available for the application. The additional writes performed because of GC also contribute to wear on the flash memory; therefore, random writes wear out the drive faster than sequential writes.

Comparing B-trees and LSM-trees · write amplification

You write 116 bytes; the disk writes far more

Grace sends one postcard. The post office logs it at the counter, sorts it into a bag, re-sorts it at the regional depot, and again at the local one. One postcard, four handlings. Every handling costs the post office time, whoever’s card it is.

In an LSM engine one value is written to the log, again when the memtable is flushed, and again in every compaction it passes through. A B-tree writes it at least twice, to the WAL and to its page, and sometimes writes the whole page even if only a few bytes changed. Divide all the bytes that reach the disk by the bytes a plain append-only log would have written, and you get the write amplification. If disk bandwidth is the bottleneck, writes per second fall as that ratio rises.

It also fools benchmarks. An empty LSM has nothing to compact yet, so every byte of bandwidth goes to new writes. Run the test longer and compaction starts taking its share.

RememberWrite amplification is disk bytes ÷ your bytes. It divides your write throughput, and an empty LSM-tree hides it from short benchmarks.

Try it: in LSM and B-tree, press Follow one write, then move the sliders and follow it again. Try Store values separately in LSM. In Over time, press Run the benchmark: an LSM-tree is simulated second by second. Watch compaction (coral) start, and the reported average fall.

What the book says

With any type of storage engine, one write request from the application turns into multiple I/O operations on the disk. With LSM-trees, a value is first written to the log for durability, then again when the memtable is written to disk, and again every time the key-value pair is part of a compaction. (If values are significantly larger than keys, this overhead can be reduced by storing values separately from keys and compacting only SSTables containing keys and references to values.)

A B-tree index must write every piece of data at least twice: once to the write-ahead log, and once to the tree page itself. In addition, writing out an entire page is sometimes necessary, even if only a few bytes changed, to ensure that the B-tree can be correctly recovered after a crash or power failure.

The total bytes written to disk divided by the bytes you would write with a simple append-only log and no index is the write amplification (sometimes defined in I/O operations rather than bytes). In write-heavy applications the bottleneck might be the rate at which the database can write to disk; the higher the write amplification, the fewer writes per second it can handle within the available bandwidth.

Which engine is better depends on key and value lengths and how often you overwrite existing keys versus insert new ones. For typical workloads LSM-trees tend to have lower write amplification, because they don’t write entire pages and can compress chunks of the SSTable. Lower write amplification also wears out an SSD less quickly. When measuring write throughput, run the experiment long enough: an empty LSM-tree has no compactions yet, but as the database grows, new writes share the disk bandwidth with compaction.

Holes, leftovers, ghosts and free snapshots

A B-tree file is like a car park. When half the cars leave, the empty spaces are scattered all over, and the car park doesn’t shrink. New cars can use the gaps, but you can’t sell off the middle of a building. Something has to move cars to the front and close the empty floors. PostgreSQL’s vacuum is that something.

LSM files have the opposite habit. Compaction rewrites them all the time, so there are no half-empty pages, and they compress well. But old values hang around until a compaction reaches them. A deleted record can survive in an old level until its tombstone has travelled down through every level, which matters when a law says data must really be gone. In return, immutable files make snapshots almost free: write out the memtable, remember the list of files, and don’t delete them.

RememberB-trees leave holes that need vacuuming; LSMs keep dead values until compaction reaches them, but immutable files make snapshots nearly free.

Try it: four modes. Fragmentation: delete keys, insert some, then vacuum. Old values: write updates, then compact leveled or size-tiered and watch the peak. Really deleted?: delete Ana’s record, then compact level by level. Snapshots: take one, then keep writing.

What the book says

B-trees can become fragmented over time: if a large number of keys are deleted, the file may contain many pages no longer used by the tree. Later additions can use those free pages, but they can’t easily be returned to the operating system because they are in the middle of the file, so they still take up space. Databases therefore need a background process that moves pages around to place them better, such as the vacuum process in PostgreSQL.

Fragmentation is less of a problem in LSM-trees, since compaction periodically rewrites the data files anyway, and SSTables don’t have pages with unused space. Blocks of key-value pairs also compress better in SSTables, often resulting in smaller files than with B-trees. Overwritten keys and values consume space until a compaction removes them, but this overhead is quite low with leveled compaction; size-tiered compaction uses more disk space, especially temporarily during compaction.

Multiple copies of data can be a problem when you need to be confident that something really has been deleted (perhaps to comply with data protection regulations). In most LSM engines a deleted record may still exist in the higher levels until the tombstone has propagated through all the compaction levels, which might take a long time. Specialist designs can propagate deletions faster.

On the other hand, immutable SSTable segments are useful for taking a snapshot (for a backup, or a copy for testing): write out the memtable and record which segment files existed at that time. As long as you don’t delete those files, you don’t need to copy them. In a B-tree whose pages are overwritten, taking such a snapshot efficiently is more difficult.

The card, or the book itself?

Ana looks up “Mei” in the school directory. In one school the directory page is Mei’s full record — address, city, everything. In another, the page only says “see the folder in cabinet 2, slot 1”, and Ana walks to the cabinet. In a third, the page says “cabinet 2, slot 1 — city: Lyon”, so if all she wanted was the city, she never walks anywhere.

Those are the three ways an index can hold its value. A clustered index stores the whole row inside the index. Otherwise the value is a reference: either the row’s primary key (then you look that up too) or a direct location in a heap file, where rows sit in no particular order. A covering index copies a few extra columns into the index, so some queries are answered without leaving it.

Heap files have their own wrinkle. If an update makes a row bigger than its slot, the row must move — and every index pointing at the old spot is now wrong.

RememberAn index entry holds the row itself (clustered), a pointer to it (primary key or heap location), or a few copied columns (covering): fewer read hops, more write work.

What the book says

The key in an index is what queries search by; other data may be stored in the index too. If the actual data (row, document, vertex) is stored directly within the index structure, it is a clustered index: in MySQL’s InnoDB storage engine the primary key of a table is always a clustered index, and in SQL Server you can specify one clustered index per table.

Alternatively the value can be a reference to the actual data: either the primary key of the row (InnoDB does this for secondary indexes) or a direct reference to a location on disk. In the latter case the place where rows are stored is a heap file, which stores data in no particular order; it may be append-only, or keep track of deleted rows to overwrite them later. Postgres uses the heap file approach.

A middle ground is a covering index or index with included columns, which stores some of a table’s columns within the index, in addition to the full row on the heap or in the clustered primary-key index. Some queries can then be answered using the index alone (the index is said to cover the query). This can make them faster, but the duplicated data uses more disk space and slows down writes.

When updating a value without changing the key, the heap file approach can allow the record to be overwritten in place, provided the new value is not larger than the old one. If it is larger, it probably needs to move to a new location in the heap with enough space; then all indexes need to be updated to point at the new heap location, or a forwarding pointer must be left behind in the old location.

Keep it all on the desk

Kofi keeps his whole stamp collection open on his desk, so finding any stamp takes a glance. Every structure so far is an answer to the awkwardness of disks. We put up with disks because they are durable and cheaper per gigabyte. As RAM gets cheaper and many datasets turn out to be small, in-memory databases keep everything in RAM. Some are only caches and may lose everything on a restart. Others stay durable with a log of changes, periodic snapshots, a replica on another machine, or special battery-powered RAM.

The surprise: they are not fast because they avoid reading the disk — with enough memory, a disk-based engine doesn’t read the disk either, because the operating system caches it. They are fast because they skip encoding their data structures into a form that can be written to disk.

What the book says

The data structures discussed so far have all been answers to the limitations of disks. We tolerate the awkwardness because disks are durable (contents survive power loss) and have a lower cost per gigabyte than RAM. As RAM gets cheaper that argument erodes, and many datasets are small enough to keep entirely in memory, potentially across several machines: in-memory databases.

Some in-memory key-value stores, such as Memcached, are intended for caching only, where losing data on a restart is acceptable. Others aim for durability, through special hardware (such as battery-powered RAM) or, more commonly, by writing a log of changes to disk, writing periodic snapshots to disk, or replicating the in-memory state to other machines. On restart they reload their state from disk or from a replica. They are still considered in-memory databases because the disk is merely an append-only log for durability, and reads are served entirely from memory. Files on disk also have operational advantages: they can be backed up, inspected and analysed by external utilities.

VoltDB, SingleStore and Oracle TimesTen are in-memory databases with a relational model; their vendors claim big performance improvements by removing the overheads of managing on-disk data structures. RAMCloud is an open source in-memory key-value store with durability, using a log-structured approach in memory as well as on disk. Redis and Couchbase provide weak durability by writing to disk asynchronously.

Counterintuitively, the performance advantage is not due to not reading from disk: even a disk-based engine may never read from disk with enough memory, because the operating system caches recently used disk blocks. Rather, in-memory databases are faster because they avoid the overheads of encoding in-memory data structures in a form that can be written to disk.

They can also offer data models that are hard to implement with disk-based indexes: Redis offers a database-like interface to data structures such as priority queues and sets, and because it keeps all data in memory its implementation is comparatively simple.

Read the columns, not the rows

Imagine every sale at a supermarket chain written on its own index card: date, product, store, promotion, customer, quantity, price, and ninety more boxes. Now Lars wants to know whether people buy more fruit or more candy on Mondays. He needs three boxes from each card, but with cards he must pick up every card and read past everything else. If instead each box had its own long strip of paper — all the dates on one strip, all the quantities on another — he would pull out three strips and leave the rest in the drawer.

That is column-oriented storage. Fact tables are often over a hundred columns wide, but a typical analytic query touches four or five. Every column keeps the rows in the same order, so the 23rd entry of each strip together is the 23rd row. Real engines cut the table into blocks of thousands or millions of rows, often by timestamp range, so a query loads only the blocks and columns it needs.

RememberStore each column separately, in the same row order: a query reads only the columns it names, and position k in every column is row k.

What the book says

Data warehouses by convention often use a relational schema with a big fact table containing foreign-key references into dimension tables. With trillions of rows and petabytes of data, storing and querying fact tables efficiently becomes challenging; dimension tables are usually much smaller (millions of rows). Fact tables are often over one hundred columns wide, but a typical warehouse query accesses only four or five of them (SELECT * is rarely needed for analytics). Example 4-1 reads many rows but only three columns of fact_sales: date_key, product_sk and quantity.

Most OLTP databases are row-oriented: all values from one row are stored next to one another; document databases are similar. Even with indexes on date_key or product_sk that say where the matching sales are, a row-oriented engine must still load those rows (each over 100 attributes) from disk into memory, parse them and filter them, which can take a long time. Column-oriented (columnar) storage instead stores all values from each column together, so a query reads and parses only the columns it uses.

The layout relies on every column storing the rows in the same order: to reassemble an entire row, take the 23rd entry from each column. In practice the table is broken into blocks of thousands or millions of rows, and within each block each column is stored separately; since many queries are restricted to a date range, each block commonly holds the rows of one timestamp range, and a query loads only the columns it needs in the blocks that overlap that range.

Column storage applies to nonrelational data too: Parquet is a columnar format supporting a document data model, based on Google’s Dremel, using a technique known as shredding or striping. Columnar storage is used in almost all analytical databases: Snowflake, DuckDB, Pinot and Druid; storage formats Parquet, ORC, Lance and Nimble; in-memory formats Apache Arrow and Pandas/NumPy; and time-series databases such as InfluxDB IOx and TimescaleDB.

Column-oriented storage · column compression

Ticks on a register

A teacher, Ms. Haddad, has a register with one line per pupil and a column of tick boxes for each club: chess, choir, football. Instead of writing “choir” next to every choir member, she just ticks a box. Most boxes are empty, so she could even write “first 9 empty, then 1 tick, then 8 empty” and save ink.

Columns repeat a lot, which makes them easy to compress. Bitmap encoding turns a column with n distinct values into n bitmaps, one bit per row: 1 if that row has the value. Mostly-zero bitmaps then shrink further with run-length encoding: store the lengths of the runs of 0s and 1s. And the bitmaps answer queries by themselves: IN (…) is a bitwise OR; a condition on two columns is a bitwise AND, because bit k is row k in every column.

RememberA column with few distinct values becomes one bitmap per value; runs of zeros shrink to counts, and AND/OR on bitmaps answer filters without decoding values.

Try it: in Encode, press Build the bitmaps and watch the bytes shrink. In IN (OR) and AND, press Run the query and follow the bits column by column, line by line in the code.

What the book says

Besides loading only the columns a query needs, we can further reduce disk throughput and network bandwidth by compressing data, and column-oriented storage lends itself very well to it: the sequences of values in each column have a fair amount of repetition. Different techniques suit different data; one particularly effective in data warehouses is bitmap encoding.

Often the number of distinct values in a column is small compared to the number of rows (a retailer may have billions of sales transactions but only 100,000 distinct products). A column with n distinct values becomes n separate bitmaps, one per distinct value, with one bit for each row: 1 if the row has that value, 0 if not. These bitmaps typically contain a lot of 0s (they are sparse), so they can additionally be run-length encoded by counting consecutive 0s or 1s and storing the counts. Techniques such as roaring bitmaps switch between the two representations, using whichever is the most compact.

Bitmaps suit warehouse queries. WHERE product_sk IN (31, 68, 69): load the three bitmaps and compute their bitwise OR. WHERE product_sk = 30 AND store_sk = 3: load both bitmaps and compute the bitwise AND — this works because the columns contain the rows in the same order, so the kth bit in one column’s bitmap is the same row as the kth bit in another’s. Bitmaps can also answer graph queries, such as finding all users followed by user X who also follow user Y.

Don’t confuse column-oriented databases with the wide-column (column-family) data model, where a row can have thousands of columns and rows need not share columns. Wide-column databases such as Google Bigtable, Apache Accumulo and HBase are row-oriented, since they store all values from a row together.

Sort whole rows, store by column

Back to the strips of paper. Yusuf decides to sort them so that all January sales come first, then February, then March. If he sorts just the date strip, it looks lovely — but now the 1st date no longer belongs with the 1st product. The rows are scrambled into sales that never happened. So he must move whole rows, every strip at once, even though each strip is still stored on its own.

A column store can keep rows in insertion order (easiest: appending means adding to the end of each column), or sort them by sort keys the administrator chooses. With date_key first, a query for last month reads one contiguous stretch instead of every row. A second key, like product_sk, groups the same product on the same day. And sorting compresses: the first sort key turns into a few long runs of the same value, which run-length encoding squashes to almost nothing. Later keys are more jumbled.

What the book says

In a column store the order of rows doesn’t necessarily matter. It’s easiest to store them in insertion order, since inserting a new row then just means appending to each column. But we can impose an order, as with SSTables, and use it as an indexing mechanism.

Sorting each column independently wouldn’t make sense, because we would no longer know which items in the columns belong to the same row: a row can be reconstructed only because the kth item in one column belongs to the same row as the kth item in another. The data needs to be sorted an entire row at a time, even though it is stored by column. The administrator chooses the sort columns using knowledge of common queries: if queries often target date ranges such as the last month, date_key could be the first sort key, so the query scans only the rows from the last month.

A second column determines the order of rows with the same value in the first: with date_key first, product_sk second groups all sales of the same product on the same day, which helps queries that group or filter by product within a date range.

Sorted order also helps compression. If the primary sort column has few distinct values, after sorting it has long sequences of the same value, and simple run-length encoding could compress it down to a few kilobytes — even with billions of rows. The effect is strongest on the first sort key; the second and third are more jumbled, and columns further down the sorting priority appear in essentially random order and probably won’t compress as well. Still, having the first few columns sorted is a win overall.

Don’t reshelve the whole library for one book

A school library keeps its books sorted by date of arrival, tightly packed, shelf after shelf. When one late book has to go in the middle, the librarian, Ayesha, has to shift every book after it along by one — on every shelf. Doing that for each new book would take all day. So she keeps a trolley: new books wait on it, in order, and once a week she reshelves the whole trolley in one sweep.

A sorted, compressed column file has the same problem. Inserting one row in the middle means rewriting every compressed column from that position onward. Warehouses mostly load data in bulk (often through ETL), so they do what Ayesha does: writes first go to a small row-oriented, sorted, in-memory store; when enough have piled up, they are merged with the column files and written out as new files in one pass. The old files are never modified — a perfect fit for object storage.

Queries look at both: the column files on disk and the recent rows in memory. The engine hides the seam, so an analyst sees a new insert, update or delete in the very next query.

RememberColumn files are rewritten, never patched: changes wait in a sorted in-memory store, get merged into new files in bulk, and queries read both.

What the book says

Reads in data warehouses tend to be aggregations over a large number of rows; column-oriented storage, compression and sorting all make those reads faster. Writes tend to be bulk imports of data, often via an ETL process.

With columnar storage, writing an individual row somewhere in the middle of a sorted table would be very inefficient, as you would have to rewrite all the compressed columns from the insertion position onward. A bulk write of many rows at once amortizes the cost of rewriting those columns, making it efficient.

A log-structured approach is often used to perform writes in batches. All writes first go to a row-oriented, sorted, in-memory store. When enough writes have accumulated, they are merged with the column-encoded files on disk and written to new files in bulk. As old files remain immutable and new files are written in one go, object storage is well suited for storing these files.

Queries need to examine both the column data on disk and the recent writes in memory, and combine the two. The query execution engine hides this distinction from the user: data that has been modified with inserts, updates or deletes is immediately reflected in subsequent queries. Snowflake, Vertica, Apache Pinot, Apache Druid and many other databases do this.

Query execution · compilation and vectorization

Read the recipe every time, or learn it by heart?

Tomás has to check 16 crates: is it bananas, and is it for store 3? A new helper reads the instruction card again for every crate — “first check the fruit, then check the store, then combine” — and spends more time reading the card than looking at crates. That is an interpreter: for each row, the engine walks a data structure that describes the query to find out which comparison to do next.

There are two ways to be quicker. Query compilation: write a tiny program just for this query (“if product is 31 and store is 3, keep it”), compile it to machine code — often with LLVM, like a JIT in the JVM — and run it over the rows. Vectorized processing: keep a set of ready-made operators and hand each one a whole batch of a column at once: “which of these 16 are bananas?” returns a bitmap; “which are store 3?” returns another; a bitwise AND gives the answer.

Both win the same way: they read memory sequentially, spend their time in tight loops with no function calls or surprise branches, use parallelism such as SIMD instructions, and can work on compressed data directly.

RememberAn interpreter pays overhead on every row; compiled code pays once per query; vectorized code pays once per batch. Both fast styles run tight loops over columns.

What the book says

A complex analytical SQL query is broken into a query plan of stages called operators, which may be distributed across machines for parallel execution. Query planners choose which operators to use, in which order, and where to run each one. Inside an operator, the engine may test column values — is it among a set of values (perhaps as part of a join), is it greater than 15 — and look at several columns of the same row, such as sales where the product is bananas and the store is a particular store.

When a query scans millions of rows, CPU time matters as well as disk reads. The simplest operator is like an interpreter: while iterating over each row, it checks a data structure representing the query to find out which comparisons or calculations to perform. This is too slow for many analytics purposes.

Query compilation: the engine generates code for the query that iterates over the rows, does the comparisons and copies matching values to an output buffer, then compiles it to machine code (often using an existing compiler such as LLVM) — similar to just-in-time (JIT) compilation in the Java Virtual Machine (JVM). Vectorized processing: the query is interpreted, not compiled, but each predefined operator processes many values from a column in a batch; an equality operator given the product_sk column and the ID for bananas returns a bitmap, another gives a bitmap for the store, and a bitwise AND operator combines them (Figure 4-9).

Both are used in practice, and both exploit modern CPUs: sequential memory access over random access to reduce cache misses; most work in tight inner loops (few instructions, no function calls) to keep the pipeline busy and avoid branch mispredictions; parallelism such as multiple threads and single-instruction, multiple-data (SIMD) instructions; and operating directly on compressed data without decoding it into a separate in-memory representation.

A virtual view is the first habit: just a saved query, expanded and run again on every read. What the book says

In a relational data model, materialized views are table-like objects whose contents are the results of a query. A materialized view is an actual copy of the query results, written to disk, whereas a virtual view is just a shortcut for writing queries: reading from it, the SQL engine expands it into the underlying query on the fly.

When the underlying data changes, a materialized view needs to be updated. Some databases do that automatically, and systems such as Materialize specialize in materialized view maintenance. That means more work on writes, but can improve read performance in workloads that repeatedly perform the same queries.

Materialized aggregates cache the results of aggregate functions such as COUNT, SUM, AVG, MIN or MAX. A data cube (also known as an OLAP cube) is a grid of aggregates grouped by different dimensions (Figure 4-10): with dates along one axis and products along the other, each cell holds, say, the SUM of net_price for that date–product combination, and summing along a row or column gives a summary reduced by one dimension. The advantage is that certain queries become very fast because they have effectively been precomputed — total sales per store yesterday is just a lookup along one dimension. The disadvantage is less flexibility: there is no way to calculate which proportion of sales comes from items that cost more than $100, because price isn’t one of the dimensions. Most warehouses therefore keep as much raw data as possible and use aggregates such as data cubes only as a performance boost for certain queries.

Find every café inside the screen

Mateus pans a restaurant map around central London. The app must find every restaurant inside the rectangle on his screen: latitude between two values and longitude between two others, at the same time. That is a two-dimensional range query.

A concatenated index on (latitude, longitude) can’t do it well: it can narrow the latitude, but that leaves a stripe across the whole map, every longitude from one edge to the other, to filter one by one. Two better ideas: squash the two numbers into one with a space-filling curve that visits nearby squares one after another, then use an ordinary B-tree on that number; or — more commonly — use a spatial index such as an R-tree, which groups nearby points into nested boxes so whole boxes can be skipped.

It isn’t only for maps: the same index finds products in a range of colours (red, green, blue) or weather readings from one year between 25°C and 30°C.

Multidimensional indexes allow you to query several columns at once, which is particularly important with geospatial data. A restaurant search website showing a map needs every restaurant within the visible rectangle — a two-dimensional range query like:

One option is to translate a two-dimensional location into a single number via a space-filling curve, then use a regular B-tree index. More commonly, specialized spatial indexes such as R-trees or Bkd-trees are used; they divide up the space so that nearby data points tend to be grouped in the same subtree. PostGIS implements geospatial indexes as R-trees using PostgreSQL’s Generalized Search Tree indexing facility. Regularly spaced grids of triangles, squares or hexagons are also possible.

Not just for maps: an ecommerce site could use a three-dimensional index on (red, green, blue) to search for products in a range of colors, and a weather database could index (date, temperature) to find all observations in a given year between 25°C and 30°C. A one-dimensional index would have to scan all records from that year and filter by temperature, or vice versa; a two-dimensional index narrows by both at once.

At the back of a cookbook, the index lists each word with the pages it appears on: apples — 4, 12, 31. To find recipes with apples and red, you don’t read the cookbook; you compare two short lists of page numbers. Search engines call this an inverted index: from each term to its postings list of document IDs. With numbered documents the list can be a bitmap, and “both words” becomes a bitwise AND.

Two tricks stretch the idea. Index every 3-letter piece of each word — its trigrams — and you can search for any substring of at least three characters, even a regular expression, at the cost of a much bigger index. And to forgive typos, look for terms within an edit distance of 1: one letter added, removed or replaced.

RememberAn inverted index maps each term to the documents that contain it; a multi-word search is a bitwise AND of their bitmaps.

What the book says

Full-text search lets you search a collection of text documents by keywords that might appear anywhere in the text. Information retrieval is a big specialist topic, often language-specific: several Asian languages are written without spaces between words, so splitting text into words needs a model; matching typos, different grammatical forms and synonyms goes beyond the book’s scope.

At its core, full-text search is another kind of multidimensional query: each term is a dimension, a document containing term x has a 1 in dimension x, and searching for “red apples” looks for a 1 in the red dimension and, simultaneously, a 1 in the apples dimension. Many search engines answer this with an inverted index: a key-value structure where the key is a term and the value is the list of IDs of all documents that contain it (the postings list). With sequential document IDs, the postings list can be a sparse bitmap; finding documents with both terms is a bitwise AND, efficient even if the bitmaps are run-length encoded.

Lucene, the indexing engine used by Elasticsearch and Solr, works like this; it stores the term → postings mapping in SSTable-like sorted files, merged in the background with the log-structured approach. PostgreSQL’s GIN index type also uses postings lists, for full-text search and indexing inside JSON documents.

Instead of words, you can index all substrings of length n, called n-grams; the trigrams of hello are hel, ell and llo. An inverted index of all trigrams supports searching for arbitrary substrings of at least three characters, even regular expressions — but such indexes are quite large. To cope with typos, Lucene can search for words within a certain edit distance (1 means one letter added, removed or replaced): it stores the set of terms as a finite state automaton over the characters, similar to a trie, and transforms it into a Levenshtein automaton.

Search by meaning, not by spelling

Ngozi wants to quit a music service and types how to close my account. The help page she needs is called canceling your subscription. Not one word matches, so a keyword index finds nothing. Semantic search tries to understand what she means instead.

An embedding model turns each document into a vector embedding: a list of numbers that is a point in a space with many dimensions, placed so that documents with similar meanings land near each other. At query time the same model turns the query into a vector, and the search looks for the nearest documents. “Near” needs a ruler: cosine similarity compares the angle between two vectors; Euclidean distance measures the straight line between the points.

Careful with the word: this “vector” is a list of floating-point numbers. The vectors of vectorized processing earlier were batches of values for fast code. Same word, different idea.

RememberAn embedding places a document by meaning; semantic search returns the nearest points, by angle (cosine) or by straight-line distance.

What the book says

Semantic search goes beyond synonyms and typos to try to understand document concepts and user intentions. It is becoming important in AI applications such as retrieval-augmented generation, which incorporates search results into the output of a large language model (LLM). A help page titled “canceling your subscription” should still be found by searches for “how to close my account” or “terminate contract”.

Semantic search indexes use embedding models — often LLMs — to translate a document into a vector embedding: a vector of floating-point values, a point in a multidimensional space. Embedding models generate embeddings that are near each other when the input documents are semantically similar. (This is different from vectorized processing, where a vector is a batch of bits processed with specially optimized code.)

A three-dimensional embedding for a Wikipedia page about agriculture might be [0.38, 0.83, 0.41]; a page about vegetables would be near, perhaps [0.36, 0.64, 0.67]; a page about star schemas might be [0.85, 0.10, -0.52], comparatively far away. Real embedding models use much larger vectors (often over 1,000 numbers); we don’t try to understand what the individual numbers mean. Search engines measure closeness with distance functions such as cosine similarity (the cosine of the angle between two vectors) or Euclidean distance (the straight-line distance between two points).

Early embedding models such as Word2Vec, BERT and GPT worked with text and are usually neural networks; there are now models for video, audio and images, and multimodal models that embed several modalities. At query time, the user’s query and related context (such as their location) go into the embedding model, and the search engine finds documents with similar embeddings using a vector index.

Finding the nearest point without measuring them all

Kaito drops a pin and wants the closest of 40 cafés. The honest way is to measure the distance to every single one: a flat index. Always right, but with millions of vectors of a thousand numbers each, painfully slow. R-trees don’t help either: they stop working well when there are many dimensions.

An IVF index groups the cafés into neighbourhoods around centroids. Kaito first finds the nearest centroid, then only measures the cafés in that neighbourhood — or in the nearest few, the number of probes. An HNSW index builds a stack of maps: the top one shows only a handful of cafés with long roads between them; each map below has more cafés and shorter roads. Walk downhill toward the pin on the top map, drop to the same café on the next map down, and keep walking.

Both are approximate: the closest café can sit just over a neighbourhood border, or behind a bend the walk never takes.

RememberA flat index measures every vector; IVF and HNSW measure far fewer by guessing where to look — fast, but sometimes the guess is wrong.

Try it: press Search in each mode and compare distances computed. In IVF, the pin starts near a border: search with 1 probe, then raise the probes until it finds the true nearest. In HNSW, press Pin where the walk gets stuck, then Search. Tap the plot to move the pin.

What the book says

Vector indexes store the embeddings of a collection of documents; queried with the query’s embedding, they return the documents whose vectors are closest. R-trees don’t work well for vectors with many dimensions, so specialized vector indexes are used.

Flat indexes store vectors as they are. A query must read every vector and measure its distance to the query vector: accurate, but slow.

Inverted file (IVF) indexes cluster the vector space into partitions (called centroids) to reduce the number of vectors that must be compared. They are faster than flat indexes but only approximate: the query and a document may fall into different partitions even though they are close. A query defines probes, the number of partitions to check; more probes are more accurate but slower.

Hierarchical Navigable Small World (HNSW) indexes maintain multiple layers of the vector space (Figure 4-11). Each layer is a graph whose nodes are vectors and whose edges connect nearby vectors. A query finds the nearest vector in the top layer, which has few nodes, moves to the same node in the layer below, follows that more densely connected layer’s edges toward vectors closer to the query, and continues to the last layer. Like IVF, HNSW is approximate.

Many vector databases implement IVF and HNSW; Facebook’s Faiss library has several variations of each, and PostgreSQL’s pgvector supports both.

Two kinds of work, two kinds of engine

The book’s summary, in two cards.

OLTP

Huge numbers of small requests, each reading or writing a few records and needing a fast answer. Records are found by primary key or a secondary index: ordered maps from key to record, which also answer range queries.

Analytics

Complex read queries that scan over huge numbers of records. Column-oriented layout plus compression cut what has to come off the disk; compiled or vectorized execution cuts the CPU time spent on it.

Two schools of OLTP storage

Every OLTP engine in the chapter belongs to one of them.

Log-structured

Append to files, delete obsolete files, never update a file once written. Tends to give high write throughput. SSTables, LSM-trees, RocksDB, Cassandra, HBase, ScyllaDB and Lucene.

Update-in-place

Treat the disk as fixed-size pages and overwrite them. B-trees are the main example, used by every major relational database. Tend to be better for reads: higher read throughput, lower response times.

Beyond one key

Multidimensional indexes such as R-trees search latitude and longitude together; full-text indexes find several words in the same text; vector indexes find documents that mean something similar.

Words to know

Grown-up words, in plain language.

storage engine
The part of a database that lays data out on disk and finds it again.
OLTP / analytics
Many small reads and writes by key, versus big scans that summarise many rows.
log
An append-only sequence of records on disk; not the text an app prints.
index
An extra structure, derived from the data, that makes some queries fast.
O(n)
Twice as much data means twice as long.
byte offset
How many bytes from the start of a file something begins.
hash index
An in-memory map from each key to where its latest value sits in the log.
range query
“Every key from 10000 to 19999” — needs keys in sorted order.
SSTable
Sorted String Table: a file of key-value pairs sorted by key, each key once.
sparse index
An index that keeps only some keys, such as the first key of each block.
memtable
The sorted in-memory map where new writes wait before going to disk.
segment
One SSTable file; written once, never changed afterwards.
compaction
Merging segments in the background, throwing away old and deleted values.
tombstone
A special record that means “this key was deleted.”
LSM-tree
Log-Structured Merge-tree: a cascade of SSTables merged in the background.
checksum
A short code stored with a record so a torn or corrupted one can be spotted.
Bloom filter
A small bit array that answers “definitely not here” or “probably here.”
false positive
The filter says “probably here” about a key that isn’t.
size-tiered / leveled
Two compaction strategies: merge similar-sized files, or keep fixed-size files in levels.
embedded database
A database that is a library inside your program, not a server you call.
B-tree
A balanced tree of fixed-size pages, sorted by key, updated in place.
page
A fixed-size block of the file (4, 8 or 16 KiB) that one node of the tree lives in.
branching factor
How many child pages one B-tree page points to; typically several hundred.
page split
A full page becomes two half-full ones, and the parent gets a new boundary.
torn page
A page only partly written when the power went out.
write-ahead log (WAL)
Every change is appended here first, so a crash can be repaired.
fsync
The system call that forces written data out of caches onto the disk.
copy-on-write
Write a changed page somewhere new and point fresh parents at it.
backpressure
Pausing reads and writes until a slow stage catches up.
sequential / random writes
Few big writes in a row, versus many small writes all over the disk.
garbage collection (SSD)
Moving still-valid pages out of a flash block so the block can be erased.
write amplification
Bytes actually written to disk, divided by bytes a plain log would write.
fragmentation
Unused pages stuck in the middle of a file, still taking up space.
secondary index
An index on a column other than the primary key; entries need not be unique.
postings list
The list of row or document IDs filed under one index entry.
clustered index
The whole row is stored inside the index itself.
heap file
Rows stored in no particular order; indexes point at their location.
covering index
An index holding enough columns to answer a query on its own.
in-memory database
Serves every read from RAM; the disk is only a log for durability.
HTAP
One product for transactions and analytics; inside, increasingly two engines.
query engine / table format / catalog
The separate parts of a modern warehouse: runs SQL, lists a table’s files, lists the tables.
column-oriented storage
Store each column’s values together, so a query reads only the columns it uses.
bitmap encoding
One bit per row per distinct value: 1 if the row has that value.
run-length encoding
Store “9 zeros, 2 ones, 5 zeros” instead of all sixteen bits.
sort key
The column(s) a column store sorts whole rows by.
vectorized processing
Running one built-in operator over a whole batch of column values at once.
query compilation
Turning a query into machine code, then running that code.
SIMD
One CPU instruction that works on several values at the same time.
materialized view
A query’s result, actually stored on disk and kept up to date.
data cube (OLAP cube)
A grid of precomputed aggregates, grouped by several dimensions.
concatenated index
One key made of several columns glued in order, like (last name, first name).
R-tree
A spatial index that groups nearby points into nested boxes.
inverted index
From each word to the list of documents that contain it.
n-gram
Every substring of length n: hello has trigrams hel, ell, llo.
edit distance
How many letters must be added, removed or replaced to turn one word into another.
vector embedding
A list of numbers that places a document in a space where similar meanings sit close.
cosine similarity
How close two vectors are, by the angle between them.
IVF / HNSW
Vector indexes that compare fewer vectors — by clusters, or by layered graphs.
