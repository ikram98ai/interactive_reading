Storage and Retrieval

A database only has two jobs: put your stuff away, and find it again fast. This chapter opens the filing cabinet and shows you the tricks inside.

Warm-up · the world's simplest database

The notebook you only ever add to

Here is a whole database in two lines of shell script: to store something, add a line to the end of a file. To read it, search the file for that key and take the last line that matches.

db_set () { echo "$1,$2" >> database } db_get () { grep "^$1," database | tail -n 1 }

Writing is wonderfully fast, because adding to the end of a file is the simplest thing a computer can do. Reading is terrible: to find one key you read every line, so twice the data means twice the wait. That's called O(n).

The fix is an index: a little extra map that says where things are. Keep a hash map in memory from each key to the byte offset of its newest line, and a lookup becomes one jump.

Try it: append a few lines, look up key 42 with the index switched off, then switch the index on and look it up again. Watch “rows read” change.

What the book says

Many databases internally use a log: an append-only sequence of records on disk (not the human-readable “application log”). Old values are never overwritten; the last occurrence of a key wins.

An index is an additional structure derived from the primary data. Adding or removing one never changes the contents, only performance. Well-chosen indexes speed up reads, but every index costs disk space and slows down writes, so databases make you choose them.

The append-only log plus in-memory hash index still has four problems: you never free the disk space occupied by old log entries; the map has to be rebuilt by scanning the whole log on restart; it must fit in memory (on-disk hash maps need lots of random I/O and fiddly collision logic); and range queries (“all keys from 10000 to 19999”) are not efficient.

Big idea 1 · sorted files

A dictionary with thumb tabs

Nobody reads a dictionary from page one. The words are in order, so you flip to roughly the right place and read a few lines. A Sorted Strings Table — an SSTable — is a file built the same way: sorted by key, each key appearing once.

Because it's sorted, the index doesn't need every key. Keep only the first key of each block: that's a sparse index. Looking for handiwork? The book's example puts it between handbag and handsome, so jump to that block and scan a few kilobytes.

Blocks can also be compressed, which saves disk space and I/O bandwidth for a little extra CPU time.

Try it: search for handheld, a word that isn't in the file. The sorted order still tells you exactly which block to check — and that it's definitely not there.

What the book says

An SSTable stores key-value pairs sorted by key, each key exactly once. Pairs are grouped into blocks of a few kilobytes; only the first key of each block goes into the index, which is therefore sparse. That index lives inside the SSTable, stored as an immutable B-tree, a trie, or similar.

In the book's example, one block starts at handbag and the next at handsome; the key handiwork must lie between them, so you seek to handbag's offset and scan forward. A block of a few kilobytes scans very quickly.

Each block can be compressed (the shaded area in Figure 4-2), saving space and I/O bandwidth at the cost of CPU time.

Big idea 2 · log-structured storage

The tidy-up crew at the toy library

Sorted files are great to read but awkward to write: you can't just add to the end without spoiling the order. So log-structured engines cheat. New writes go into a small sorted pile in memory called the memtable. When it gets full, the whole pile is written out to disk in sorted order as a brand-new SSTable segment, and it is never changed again.

To read, you look in the memtable, then in the newest segment, then the next-older one, until you find the key. Meanwhile a background tidy-up crew — compaction — merges old segments together, keeping only the newest value for each key, exactly like the merge step of mergesort.

Deleting doesn't erase anything either. It writes a special “it's gone” marker called a tombstone, and the merge finally drops the key for real. And because a crash could lose the memtable, every write is first appended to a separate log on disk.

Step through all 22 steps below. Watch the memtable fill and flush, watch a lookup walk from newest to oldest, and watch the merge pick the lower key each time.

What the book says
  • Writes go into an in-memory ordered structure (red-black tree, skip list, or trie) called the memtable.
  • When the memtable passes a threshold — typically a few megabytes — it is written out as the newest segment; a new memtable takes over immediately.
  • Reads check the memtable, then each segment from newest to oldest.
  • A background merging and compaction process combines segments and discards overwritten or deleted values.

A separate on-disk log makes the memtable crash-safe; it can be discarded once the memtable has been written out. Deletes append a tombstone, which is dropped once merged into the oldest segment.

This is the Log-Structured Merge-tree (LSM-tree), published in 1996 and used by RocksDB, Cassandra, ScyllaDB and HBase, all inspired by Google's Bigtable paper (which coined “SSTable” and “memtable”). Segment files are immutable, so crash recovery is easy: delete the unfinished file and start again. They also suit object storage — SlateDB and Delta Lake do exactly that.

Big idea 3 · a fast “definitely not here”

The bouncer with a very small notebook

Looking for a key that doesn't exist is the slowest thing an LSM engine does: it has to open every segment to be sure. A Bloom filter is a tiny bitmap that answers “is this key in this file?” almost instantly.

To add a key, you hash it into a few numbers and switch those bits to 1. To ask about a key, you hash it the same way and peek at those bits. If any of them is 0, the key is definitely not in the file: skip it. If all are 1, the key is probably there, so go and check properly.

Sometimes other keys have already set all the bits you check, and the filter says “probably” about a key that was never added. That's a false positive: you do a little wasted work, and nothing breaks.

Try it: add all three keys, then query handheld — the book's example, a definite miss. Then query handsome: it was never added, yet every one of its bits is already 1. That's a false positive.

What the book says

Each segment often carries a Bloom filter: hash every key in the SSTable into a set of numbers used as indexes into a bit array, and set those bits. The book's example uses 16 bits and the key handbag hashing to (2, 9, 4); the query handheld hashes to (6, 11, 2).

If at least one queried bit is 0, the key definitely isn't in that SSTable. If all are 1 it's likely present, but may be a false positive, in which case you consult the sparse index, decode the block, find nothing, and move on to the next-oldest segment. No harm done.

Rule of thumb: about 10 bits per key gives a 1% false-positive rate, and the rate drops tenfold for every 5 extra bits per key. Bloom filters don't help range queries, which is why range queries are relatively more expensive on LSM storage.

Big idea 4 · update in place

Signposts all the way down

The other great family of indexes is the B-tree, invented in 1970 and still the standard in almost every relational database. Instead of big immutable files, it chops the database into fixed-size pages (4 KiB traditionally; PostgreSQL uses 8 KiB, MySQL 16 KiB) and overwrites them in place.

One page is the root. It holds a few boundary keys and signposts to child pages: “keys 200–300 are over there.” You follow signposts until you reach a leaf page holding the actual keys. With a branching factor of several hundred, three or four levels cover almost any database.

Adding a key to a page that's already full means splitting it into two half-full pages and telling the parent about the new boundary. If the parent is full too, the split travels upward — and if a crash lands in the middle, the tree can end up broken. That's what the write-ahead log is for.

Try all three modes: look up 251, insert 334 into a full page, then crash the database halfway through the split and recover from the log.

What the book says

B-trees keep key-value pairs sorted by key, in fixed-size pages identified by a page number that works like a pointer on disk. Each child is responsible for a continuous range of keys; the keys between references are the boundaries. A leaf page holds values inline or references to them.

Inserting into a full page splits it into two half-full pages and updates the parent, possibly all the way to a new root. This keeps the tree balanced: depth O(log n). A four-level tree of 4 KiB pages with branching factor 500 holds up to 250 TB.

Overwriting several pages at once is dangerous: a crash can leave an orphan page, and hardware may leave a torn page. So B-trees keep a write-ahead log (WAL) — in filesystems the same idea is called journaling — where every modification is appended before it touches the tree. Data is durable once it is in the WAL and fsynced.

Variants: copy-on-write (LMDB) instead of a WAL, abbreviated keys for a higher branching factor, leaf pages laid out sequentially, and sibling pointers for scanning in order.

Big idea 5 · which one should you use?

Ink on the page, or a fresh sheet every time?

A B-tree rubs out and rewrites the same pages, wherever they happen to sit on the disk: lots of small scattered random writes. An LSM engine writes whole files at a time in one long stroke: fewer, bigger sequential writes. Disks — spinning ones especially, but SSDs too — are happier with the long strokes.

Watch the counter marked write amplification: how many bytes actually hit the disk for every byte your app writes. A B-tree writes each record to the log and rewrites a whole page, even if only a few bytes changed. An LSM engine writes the log, the flushed file, and then rewrites data again during compaction.

Rule of thumb: LSM-trees suit write-heavy work; B-trees are faster and more predictable for reads. But benchmarks depend enormously on your workload, so measure with your own data.

Try it: run the B-tree for a while, then switch to LSM. Compare the two bars — and notice the LSM bar jump when compaction runs.

What the book says

Reads: a B-tree reads one page per level, so it's fast and predictable; LSM reads may check several SSTables, helped by Bloom filters. Range queries are simple on B-trees; on LSM they must scan all segments in parallel and merge.

Writes: high write throughput can stall an LSM engine if the memtable fills faster than compaction drains it — RocksDB applies backpressure, suspending reads and writes. On SSDs, sequential writes still beat random ones because flash is written a page at a time but erased a block at a time, and random writes force more garbage collection (and wear the drive out faster).

Write amplification = bytes written to disk ÷ bytes you would have written to a plain log. LSM-trees usually amplify less because they never rewrite whole pages and can compress blocks. Measure for long enough that compaction has started, or you'll flatter the LSM engine.

Space: B-trees fragment and need processes like PostgreSQL's vacuum; LSM files are rewritten anyway and compress better, but deleted data can linger in old levels until the tombstone reaches the bottom — a real problem when you must prove data was erased. Immutable segments make cheap snapshots.

Keeping everything in memory: when a dataset fits in RAM, in-memory stores such as Memcached, Redis, VoltDB, SingleStore, RAMCloud and Oracle TimesTen skip disk structures entirely. Their speed comes not from avoiding disk reads (the OS caches those anyway) but from avoiding the work of encoding data into a disk-friendly form.

Big idea 6 · more than one way in

Sorted by name, but you want all the red ones

A primary key index finds one row by its ID. A secondary index lets you search by something else — colour, user ID, date — and the values there aren't unique, so each entry keeps a list of matching rows.

What the index stores at the end of that list matters. It can be a pointer into a heap file where rows live in no particular order; it can be the row itself (a clustered index); or it can carry a copy of a few columns so some questions are answered by the index alone: a covering index.

Every copy costs. More columns in the index means more disk space and slower writes. And in a heap file, making a value bigger can force the whole row to move.

Try it: ask “which toys are red?” in all three modes and count the reads. Then press Grow a value in heap mode and watch the row have to move house.

What the book says

A secondary index is built from a key-value index; because indexed values aren't unique, entries hold either a list of row identifiers (a postings list) or are made unique by appending a row ID. Both B-trees and log-structured storage can implement one.

In a clustered index the row is stored inside the index — MySQL's InnoDB always clusters on the primary key, and SQL Server allows one per table. Otherwise the value is a reference: the primary key (InnoDB's secondary indexes) or a location in a heap file, the approach Postgres uses.

A covering index (index with included columns) stores some columns in the index so a query can be answered without touching the heap — the index covers the query. Faster reads, more space, slower writes.

Updating a heap record in place works while the new value fits; a bigger value must move, so every index must be updated to the new location, or a forwarding pointer is left behind.

Big idea 7 · storage for analytics

Don't carry the whole shopping bag

Analysts ask questions like “did people buy more fruit or more candy on Saturdays in 2024?” That touches millions of rows — but only three of the hundred-plus columns in the sales table.

Ordinary row-oriented storage keeps everything from one row side by side, so the engine drags all hundred columns off the disk and throws most of them away. Column-oriented storage keeps each column in its own place, so a query loads only the columns it names.

Columns full of repeats also squash beautifully. Turn a column into one bitmap per distinct value — one bit per row, 1 if that row has that value — and a filter becomes a bitwise AND or OR. Long stretches of zeros get shortened again by run-length encoding.

Try it: run the same query in row mode and column mode and compare “cells read”. Then switch to bitmaps and combine two conditions.

What the book says

Fact tables are often over a hundred columns wide, yet a typical warehouse query reads four or five. Column-oriented storage stores the values of each column together; every column keeps rows in the same order, so the 23rd entry of each column reassembles the 23rd row. Engines break tables into blocks of thousands or millions of rows and store columns separately inside each block.

Used by Snowflake, DuckDB, Pinot, Druid, formats such as Parquet, ORC, Lance and Nimble, in-memory formats Arrow and Pandas/NumPy, and time-series stores like InfluxDB IOx and TimescaleDB.

Bitmap encoding turns a column with n distinct values into n bitmaps. Sparse bitmaps are run-length encoded; roaring bitmaps switch between representations. WHERE product_sk IN (31, 68, 69) becomes a bitwise OR; WHERE product_sk = 30 AND store_sk = 3 becomes a bitwise AND.

Choosing a sort order (say date first, product second) makes date-range queries fast and gives the first sort column long runs that compress to almost nothing. Writes arrive in a sorted in-memory store and are merged into new column files in bulk — log-structured again. Don't confuse column stores with wide-column (column-family) databases like Bigtable and HBase, which are row-oriented.

Queries get fast CPUs through query compilation (generate and JIT-compile code, often with LLVM) or vectorized processing (predefined operators chewing through batches of column values). Materialized views and data cubes precompute popular aggregates — fast, but less flexible than the raw data.

Big idea 8 · searching two things at once

Restaurants on a map, words in a book

A normal index sorts by one thing. Combine two into a concatenated index — like a phone book sorted by (lastname, firstname) — and you can search by last name, or last and first, but never by first name alone.

Now look for every restaurant inside the rectangle you can see on a map. A one-dimensional index gives you every restaurant in that band of latitude, right around the planet, and you filter the rest by hand. A multidimensional index such as an R-tree groups nearby places into boxes, so you open only the boxes your rectangle touches.

Full-text search is the same trick with a huge number of dimensions: one per word. An inverted index maps each word to the list of documents containing it — and if you write those lists as bitmaps, “red AND apples” is once again a bitwise AND.

Try both modes. In the map, compare how many restaurants each index has to examine. In the words mode, watch two bitmaps combine into an answer.

What the book says

A concatenated index appends one column to another; it can't answer a query on the second column alone. Two-dimensional range queries (latitude and longitude together) need a space-filling curve plus a B-tree, or specialized R-trees / Bkd-trees — PostGIS builds R-trees on PostgreSQL's Generalized Search Tree indexing facility. The same applies to (red, green, blue) colour search or (date, temperature) weather search.

Full-text search treats each term as a dimension. The inverted index maps a term to its postings list of document IDs, which can be stored as a sparse bitmap. Lucene (behind Elasticsearch and Solr) keeps term → postings in SSTable-like sorted files merged in the background; PostgreSQL's GIN index does something similar.

n-grams (the trigrams of “hello” are hel, ell, llo) allow substring and even regular-expression search, at the cost of a large index. Lucene handles typos with a Levenshtein automaton that finds words within a given edit distance.

Big idea 9 · searching by meaning

Neighbours in a space made of meaning

Someone types “how do I close my account?” but your help page is called “cancelling your subscription”. No word matches. Semantic search fixes that by turning each document into a list of numbers — a vector embedding — produced by an embedding model.

Think of each document as a dot in a huge space. Documents that mean similar things land near each other. To search, you embed the question too and look for the nearest dots, measuring with cosine similarity or Euclidean distance.

A flat index compares the question to every single dot: perfectly accurate, and slow. An HNSW index keeps layers of the space — a sparse top layer for big jumps, denser layers below — so you glide toward the answer in a handful of hops. It's approximate, and usually right.

Run both. Count the distance calculations in the flat index, then in HNSW. Do they find the same neighbours?

What the book says

Semantic search underpins retrieval-augmented generation, where search results are fed into a large language model. Embedding models (Word2Vec, BERT, GPT and newer multimodal models) map text, images, audio or video into a vector of floating-point numbers — often more than 1,000 of them — whose positions encode meaning.

Careful: the vector of vectorized query processing is a batch of values for fast CPU work; the vector of an embedding is a point in multidimensional space. Different meanings, same word.

Vector indexes: flat (exact, reads every vector), IVF (space clustered into partitions called centroids; a query picks how many probes to check — more probes, more accurate, slower), and HNSW (Hierarchical Navigable Small World: layered graphs, entering at a sparse top layer and descending into denser ones). IVF and HNSW are approximate. Facebook's Faiss and PostgreSQL's pgvector implement both.

The seesaws from this chapter

Every storage engine is a bargain: make one thing fast and something else gets slower.

No index

Fastest possible writes; reads scan everything

vs

Indexes

Fast reads, but extra disk space and slower writes

Log-structured (LSM)

Immutable files, sequential writes, high write throughput, lower write amplification

vs

Update in place (B-tree)

Fixed pages overwritten where they lie; fast, predictable reads and range scans

Sequential writes

Few big strokes; kinder to SSD garbage collection

vs

Random writes

Many small scattered page writes; more wear, less throughput

Heap file reference

One copy of the row; an extra hop to fetch it

vs

Clustered / covering index

Data inside the index: fewer hops, more duplication

Row-oriented (OLTP)

Whole records together for point reads and writes

vs

Column-oriented (analytics)

Read only the columns you asked for, compressed hard

Raw data

Any question you like, computed from scratch

vs

Materialized views & cubes

Precomputed answers: instant, but only the ones you planned

Exact search (flat index)

Always the true nearest neighbours, one comparison per document

vs

Approximate (IVF, HNSW)

A few hops instead of millions, occasionally imperfect

A map kept in memory from each key to the exact spot in the file where its value sits.

How many bytes into the file something starts — like a page number for a computer.

One SSTable file on disk. Once written, it never changes again.

Background tidying that merges segments and throws away old and deleted values.

When the filter says “probably here” about something that isn't. Harmless, just wasted work.

A tree of fixed-size pages full of signposts, overwritten in place. The classic index.
page
A fixed-size block of disk, typically 4 KiB, that a B-tree reads and writes as one lump.

How many child pages one page points at — usually several hundred.
page split
When a full page is cut into two half-full ones and the parent learns the new boundary.

Every change written to an append-only file first, so a crash can be undone.
write amplification
How many bytes really hit the disk for each byte your app writes.

One long stroke versus lots of little scattered pokes. Disks prefer the stroke.
secondary index
A second way to search — by colour, date, user — where many rows can share a value.

Where rows are kept in no particular order; indexes point at spots inside it.
clustered index
An index that keeps the whole row inside itself, so there's no extra hop.
covering index
An index carrying a few extra columns so some questions never touch the table.

Storing each column's values together so a query loads only the columns it needs.
bitmap encoding
One row of 0s and 1s per distinct value, so filters become fast bit operations.
run-length encoding
Writing “twelve zeros” instead of writing twelve zeros.
materialized view / data cube
Answers worked out in advance and saved, so popular questions are instant.
inverted index
Word → the list of documents that contain it. How search engines work.
vector embedding
A list of numbers standing for a document's meaning; similar meanings land nearby.
HNSW
A layered map of the meaning space that finds close-enough neighbours in a few hops.
