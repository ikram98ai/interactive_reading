Consistency and Consensus

Many computers keep copies of your data. This chapter is about making them behave like one honest computer — and about the vote they hold when one of them disappears.

Big idea 1 · linearizability

One final score, two phones, two answers

Aaliyah and Bryce sit in the same room watching a game. The moment it ends, Aaliyah refreshes and shouts the score. Bryce hits reload one second later — and his phone still says the game is going.

Bryce's request went to a copy of the database that hadn't caught up yet. Nothing crashed; nothing broke. The system simply let a later question get an older answer.

A system is linearizable when that can't happen: once anybody has seen the new value, nobody may see the old one again. It pretends there is only one copy of the data, and every operation touches it in one instant.

Try it: play the story with the lagging replica. Then switch to “reads go to the leader” and watch the confusion disappear — at the price of a longer trip for every read.

What the book says

Linearizability (also called atomic consistency, strong consistency, immediate consistency, or external consistency) makes a replicated system behave as if there were only one copy of the data and all operations on it were atomic.

It is a recency guarantee: as soon as one client's write completes, every client that reads must see the new value. A read may not return a value older than one another client already saw.

The violation is only noticeable here because of an extra communication channel: Aaliyah's voice. The same race appears in computers — a web server that stores a video in file storage and then puts a job on a message queue, or a push notification that arrives before the data does.

Linearizability is the strongest consistency model in common use; read-after-write consistency, monotonic reads, and consistent prefix reads are weaker guarantees it includes.

Big idea 2 · what makes it linearizable

When exactly did the number flip?

Draw every request as a bar: it starts when the client sends it and ends when the answer comes back. In between, nobody knows exactly when the database did the work.

Linearizability says: imagine there is one instant inside the write's bar where the value flips, once and for all. A read that takes effect before that instant returns the old value; a read after it returns the new one. Reads that overlap the write may go either way — but once one read has seen the new value, every later read must see it too.

Slide the flip point and watch the answers change. Then press “Break it” to see the one answer the system is not allowed to give.

What the book says

In distributed systems theory the object being read and written is a register — one key in a key-value store, one row, one document. Operations are read(x) ⇒ v, write(x, v) ⇒ r and cas(x, v_old, v_new) ⇒ r.

Every operation is marked with the point in time at which it appears to take effect. That marker must lie inside the operation's own bar, and joining the markers must produce a valid sequence for a register where each read returns the most recent write. The line joining the markers must always move forward in time, never backward.

Linearizability is not the same as serializability. Serializability is a transaction isolation level over many objects and permits stale reads; linearizability is a recency guarantee on a single object. A system with both is called strictly serializable (strong-1SR) — Spanner and FoundationDB offer it; CockroachDB offers serializability with some recency guarantees but not strict serializability.

Checking a recorded history for linearizability is possible but computationally expensive.

Big idea 3 · who needs it

Two people claim the same name at once

Picking a username is like grabbing a coat hook: only one person can have it. If two people press “Register” in the same second, exactly one must win and one must be told “sorry, taken”.

That decision needs a single up-to-date value that everybody agrees on. Same for the last seat on a plane, the last item in the warehouse, and a bank balance that must never go negative. Same, too, for deciding which server is the leader — that's a lock, called a lease.

Try it: let both people press Register at the same moment, first with one shared registry, then with two replicas that don't talk to each other.

What the book says

A hard uniqueness constraint requires linearizability. Claiming a username is very similar to an atomic compare-and-set: set the name to this user's ID, provided it isn't already taken.

Single-leader replication must ensure there is really only one leader, not several (split brain). One way to elect a leader is a lease that every node tries to acquire; the mechanism must be linearizable so two nodes can't hold it at once.

Coordination services like Apache ZooKeeper and etcd implement linearizable operations in a fault-tolerant way, and libraries like Apache Curator provide higher-level recipes on top. ZooKeeper provides linearizable writes, but its reads may be stale; etcd has provided linearizable reads by default since version 3.

Some constraints can be treated loosely — an overbooked flight can be fixed with compensation — and then linearizability isn't needed. Foreign-key and attribute constraints don't need it either.

Big idea 4 · implementing it

The majority vote that still gets it wrong

In a leaderless database you write to lots of copies and read from lots of copies, and you make sure the two groups overlap: w + r > n. It feels like that must give you the freshest answer.

It doesn't. The network delivers the write to one replica quickly and dawdles on the others. A reader who catches the fast replica returns the new value; a reader who starts later and catches two slow ones returns the old value. The overlap rule held, and the recency guarantee still broke.

Step through it once as a plain quorum, then turn on synchronous read repair and step through again.

What the book says

Reviewing the replication methods: single-leader replication is potentially linearizable (if you really know who the leader is, and replication is not asynchronous); consensus algorithms are likely linearizable; multi-leader replication is not; leaderless Dynamo-style replication probably isn't, even with quorums.

Dynamo-style quorums can be made linearizable at the cost of performance: a reader must perform read repair synchronously before returning, and a writer must read the latest state of a quorum before writing to ensure its write gets a greater timestamp. Riak skips synchronous read repair for performance; Cassandra waits for it but loses linearizability anyway because it uses time-of-day clocks for timestamps (as do ScyllaDB's last-write-wins rules).

Even then, only reads and writes can be made linearizable this way. A linearizable CAS operation cannot — it requires a consensus algorithm.

Big idea 5 · what it costs

Somebody cuts the cable between the cities

Two offices, one in the west and one in the east, share a database. A digger cuts the cable between them. Each office can still talk to itself, but not to the other. That's a network partition.

If there's one leader and it lives in the west, the east can't write anything and can't do an up-to-date read: it is stuck until the cable is fixed. If both offices are leaders, everybody keeps working — but they may write conflicting things that have to be untangled later.

You don't get to choose whether cables break. You only choose what to do when they do: stay correct, or stay open. And linearizability is slow even when nothing is broken, because every operation has to wait for the far side.

Try it: cut the cable in each mode and keep pressing the write buttons.

What the book says

This trade-off is popularly known as the CAP theorem, named by Eric Brewer in 2000: a linearizable system must become unavailable to disconnected replicas (CP), while a system that doesn't need linearizability can keep serving them (AP).

“Pick two out of three” is misleading — partitions are a fault, not a choice. A better phrasing is either consistent or available when partitioned. CAP is formally very narrow: one consistency model, one kind of fault (network partitions cause under 8% of incidents according to Google data), and an odd definition of availability. It is of mostly historical interest today, though it helped trigger the NoSQL movement. PACELC extends it: during a partition (P) choose availability (A) or consistency (C); else (E) choose low latency (L) or consistency (C).

Most systems that drop linearizability do it for performance, not fault tolerance. Even RAM on a multi-core CPU isn't linearizable, because each core has its own cache. Attiya and Welch proved that the response time of linearizable reads and writes is at least proportional to the uncertainty of network delays — no faster algorithm exists.

Big idea 6 · ID generators

Numbering the messages in a group chat

Every message needs an ID. On one computer that's easy: keep a counter, add one, hand it out. The numbers also tell you the order things happened — Aaliyah's question gets a smaller number than Bryce's answer, so the chat reads correctly.

But one counting computer is a single point of failure, a bottleneck, and a round trip to the other side of the planet. So people split it up — and the moment they do, the numbers stop telling the truth about order.

Post the messages and then switch schemes. The right-hand column sorts by ID. Red lines are messages that jumped out of order.

What the book says

A single-node autoincrementing ID generator is a fetch-and-add operation and is linearizable, but it isn't fault-tolerant, is slow from other regions, and can become a bottleneck.

The alternatives all weaken ordering: sharded ID assignment (reserve bits for a shard number — one node hands out even numbers, another odd), preallocated blocks of IDs, random UUIDs (version 4 is essentially a 128-bit random number, orderable only by luck), and wall-clock timestamps made unique — version 7 UUIDs, X's Snowflake, ULIDs, Hazelcast's Flake IDs, MongoDB ObjectIDs.

Clock-based IDs can be misordered whenever one machine's clock runs slightly fast or slow, or jumps because of an NTP adjustment, so they are unlikely to be linearizable. High-precision clock synchronization with atomic clocks or GPS reduces, but doesn't remove, the problem.

Big idea 7 · logical clocks

Lamport's counting game

A logical clock doesn't tell you what time it is. It just counts events — and it has one beautiful rule that keeps causes in front of their effects.

Every person keeps a counter. Rule 1: when you do something, add one to your counter and stamp it on. Rule 2: when you receive a message stamped with a bigger number than yours, jump your counter up to match. A stamp is the pair (counter, your name), so two people who reach the same number are still told apart by name.

Because an answer always comes after reading the question, the answer's number is always bigger. Causes stay in front of effects. But it is not linearizability: two people who never talk can both be at 1 while one of them really happened much later.

Step through the chat and watch the three counters. At the end, sort by stamp and see the question land before the answer.

What the book says

A Lamport clock (Leslie Lamport, 1978) gives timestamps that are compact and unique, totally ordered, and consistent with causality: if A happened before B, then A's timestamp is less than B's. Compare the counters first; break ties with the node ID.

A hybrid logical clock counts real seconds like a physical clock, but pulls itself forward like a Lamport clock when it sees a larger timestamp, and always increments, so it moves forward even if the underlying clock jumps backward. CockroachDB uses them.

These clocks order concurrent events arbitrarily, so you usually can't tell whether two timestamps were concurrent. A vector clock can — it keeps a counter per node — but its timestamps are much bigger, potentially one integer per node.

Lamport and hybrid logical clocks are good for generating transaction IDs for MVCC snapshot isolation, because the snapshot is then consistent with causality. But they are not linearizable: if you set your account to private on a laptop and then upload a photo from a phone, a lower timestamp on the photo can let a stranger see it.

Big idea 8 · consensus

Electing a captain when the old one vanishes

One node is the captain. When it stops answering, somebody else has to take over — but if two nodes both decide they're captain, they'll give contradictory orders. That's split brain.

The trick is a numbered round, called an epoch (a term in Raft, a ballot in Paxos, a view in Viewstamped Replication). A node that suspects the captain is gone starts a new, higher-numbered round and asks the others to vote. You only become captain by collecting votes from a majority, and if two captains ever meet, the higher epoch wins.

Majority is the whole reason this is safe — and the whole reason it has a limit. Five nodes tolerate two failures. Three nodes tolerate one. Lose the majority and the survivors must stop, because somewhere out there the other half might still be deciding.

Click nodes to crash them, then run an election. Crash three out of five and watch the cluster refuse to move.

What the book says

A consensus algorithm must satisfy uniform agreement (no two nodes decide differently), integrity (no changing your mind), validity (the decided value was proposed by some node) and termination (every node that doesn't crash eventually decides). Termination is a liveness property; it requires that fewer than half the nodes are unreachable. The safety properties hold even if a majority fails.

Best-known algorithms: Viewstamped Replication, Paxos, Raft, and Zab. All assume a non-Byzantine model: nodes may crash, restart and be disconnected, but they follow the protocol. Byzantine-fault-tolerant algorithms usually assume fewer than one-third of nodes are faulty.

There are two rounds of voting — one to elect a leader, one for each entry the leader wants to append — and the quorums must overlap. This looks superficially like 2PC but is different: any node can start an election and only a quorum must respond, whereas in 2PC only the coordinator requests votes and every participant must say yes.

The FLP result proves consensus is unsolvable by a deterministic algorithm in the asynchronous model, but that model forbids clocks and timeouts; with timeouts (or randomness) consensus becomes solvable in practice.

Costs: a strict majority is always required, adding nodes makes it slower rather than faster, and timeouts are hard to tune. Raft has edge cases where one consistently unreliable link makes leadership bounce forever; a pre-vote phase was added to fix this. EPaxos avoids a leader entirely.

Big idea 9 · shared logs

One notebook that everybody copies

Here's the surprise of the chapter: agreeing on a single value, grabbing a lock, keeping usernames unique, counting, and committing a distributed transaction are all the same problem. Solve one and you've solved them all.

In practice the most useful shape is an append-only notebook — a shared log. The leader decides the order of entries; every entry is copied to a majority before it counts as done; and every replica replays the same entries in the same order, so they all end up with exactly the same state.

That's what a consensus system really is: single-leader replication done right, with the election built in.

Add entries and watch them commit. Then crash one follower (still fine — two of three is a majority) and crash a second one to see everything stop.

What the book says

Single-value consensus, linearizable CAS, locks and leases, uniqueness constraints, shared logs (implemented with total order broadcast, also called atomic broadcast), atomic transaction commit, and linearizable fetch-and-add are all equivalent — except that fetch-and-add solves consensus only between two nodes, giving it a “consensus number” of 2, while CAS and shared logs have a consensus number of ∞.

Raft, Viewstamped Replication and Zab provide shared logs directly; Paxos gives single-value consensus, and Multi-Paxos adds the log. Replaying a log of deterministic writes on every replica is state machine replication, the principle behind event sourcing; a counter over log entries makes good fencing tokens (ZooKeeper's zxid, etcd's revision number).

A new leader must be at least as up to date as a majority before it may append (Raft) or must first bring its log up to date (Paxos). Weakening that — Kafka's unclean leader election, or asynchronous replication — trades safety for availability, and the theory no longer applies. Linearizable reads must also go through a quorum vote, as they do in etcd.

Coordination services — ZooKeeper, etcd, Consul, modeled on Google's Chubby — package this up with locks and leases, fencing tokens, failure detection via heartbeats and sessions (ZooKeeper's ephemeral nodes), and change notifications. Kubernetes relies on etcd; Spark and Flink in HA mode rely on ZooKeeper. They hold small, slow-changing data on a fixed set of three or five nodes, so thousands of application nodes can outsource their agreement to them. ZooKeeper's observers receive the log without voting, giving fast but possibly stale reads.

Words to know

Grown-up words, in plain language.

linearizability
Pretending all the copies are one copy: once someone sees the new value, nobody sees the old one again.
recency guarantee
A promise that what you read is the latest value, not an old one.
register
The theory word for one value you can read and write: a key, a row, a document.
stale read
An answer that was true a moment ago but isn't any more.
compare-and-set (CAS)
“Change it to this, but only if it's still that.” The move behind locks and unique names.
serializability
Transactions behave as if run one after another. It's about grouping, not about freshness.
strict serializability
Both at once: serializable transactions and no stale reads.
split brain
Two nodes both think they're the leader and give contradictory orders.
lease
A lock that expires by itself, so a crashed holder doesn't block everyone forever.
fencing token
An ever-increasing number handed out with a lock, so a sleepy old holder gets rejected.
network partition
The network splits into groups that can't reach each other.
CAP theorem
When the network splits, you must pick: stay consistent, or stay available.
quorum
Enough nodes to speak for the whole group — usually a majority.
read repair
Noticing a replica is behind while reading, and fixing it on the spot.
logical clock
A counter of events instead of a clock of seconds. It tells order, not time.
Lamport timestamp
A stamp of (counter, node name) that always puts a cause before its effect.
hybrid logical clock
Real seconds that also jump forward when they meet a bigger stamp.
vector clock
One counter per node, so you can also tell when two writes were truly at the same time.
causality
“This happened because of that.” Effects must never be ordered before their causes.
consensus
Getting a group of computers to agree on one value and never take it back.
epoch number
The round number of an election. A higher round beats a lower one.
total order broadcast
Delivering messages to everyone in exactly the same order — how a shared log is built.
state machine replication
Every replica replays the same log of changes, so they all end up identical.
coordination service
A small, careful cluster (ZooKeeper, etcd) that other systems use to agree on things.
