Consistency and consensus · two philosophies

Three copies of one document, and who has to cope with them

Amara and Kenji edit the title of the same shared document from two cities. The document lives on three replicas, R1, R2 and R3. Amara talks to R1, Kenji to R3. Replication makes the data survive a dead machine, but now there are three copies that can disagree for a while.

There are two ways to live with that. Eventual consistency lets the replication show: each replica answers right away, so Kenji may read an old title, and if both write at once the app gets two versions and has to merge them. Strong consistency hides the replicas: the system behaves as if there were one node, so the app never sees stale or conflicting data. The price is speed, and some faults that the eventual system shrugs off become outages.

Try it: in Eventual, press Amara writes, Kenji reads, then Both write at once. Switch to Strong and press them again: no stale read, no conflict, but slower. Then press Cut R3 off and try both modes once more.

What the book says

One of the best tools for fault tolerance is replication, but multiple copies on multiple replicas increase the risk of inconsistencies: reads might be served by a replica that is not up to date, and if several replicas accept writes, concurrent writes may conflict.

Eventual consistency makes the replication visible to the application, and you as the developer deal with the inconsistencies and conflicts. It is often used with multi-leader and leaderless replication. Strong consistency says applications should not have to worry about the internal details of replication: the system should behave as if it were a single node. That is simpler for the developer, but it has a performance cost, and some faults that an eventually consistent system can tolerate cause outages in strongly consistent systems.

Which is better depends on the application. If users can change data while offline, eventual consistency is inevitable. If the replicas are in datacenters with fast, reliable communication, strong consistency is often appropriate because its cost is acceptable.

The chapter covers three areas: a precise definition of strong consistency (linearizability), generating IDs and timestamps, and consensus algorithms, which achieve linearizability while remaining fault-tolerant. These topics are notorious for being hard to implement correctly: systems that behave fine without faults can fall apart under an unlucky combination of faults or message orderings.

Linearizability · the illusion of a single copy

One final score, two phones, two answers

Aaliyah and Bryce sit in the same room, following their team’s game on their phones. Just after the final whistle, Aaliyah refreshes, sees the result and shouts it out. Bryce refreshes too, and his phone says the game is still on.

Her request went to a replica that had the new score; his went to one that was lagging. If they had pressed reload at the same moment, nobody would be surprised by different answers. But Bryce knows he asked after Aaliyah got her answer, so he expects something at least as new. A system that promises this is linearizable: it acts as if there were one copy of the data and every operation on it were atomic. As soon as any read has returned the new value, no later read returns an older one. It is a recency guarantee.

Try it: press Final whistle with the lag slider high. Watch the timeline: Bryce’s read starts after Aaliyah’s ends, yet returns an older value. Turn the lag down, or switch to Read the leader, and play it again.

What the book says

To make a replicated database as simple as possible to use, make it behave as if it were a consistent single-node database. That is the idea behind linearizability, also known as atomic consistency, strong consistency, immediate consistency or external consistency. The basic idea is to make a system appear as if there is only one copy of the data, and all operations on it are atomic.

In a linearizable system, as soon as one client successfully completes a write, all clients reading from the database must be able to see the value just written. Maintaining the illusion of a single copy means the value read is the most recent, up-to-date value and doesn’t come from a stale cache or replica. In other words, linearizability is a recency guarantee.

Figure 10-1 shows a nonlinearizable sports website. Bryce’s request goes to a lagging replica, so his phone shows the game as still ongoing. Had they hit reload at the same time, different results would be less surprising; but Bryce initiated his query after hearing Aaliyah exclaim the final score, so he expects a result at least as recent as hers. His stale result is a violation of linearizability.

Linearizability · what makes a system linearizable?

A read that overlaps a write may see either value

Picture one value, x, that starts at 0. Client C asks the database to set it to 1. Meanwhile clients A and B keep asking for x. Each request is a bar: it starts when the request is sent and ends when the response arrives. Because the network delays messages by unknown amounts, a client knows only that the database did the work somewhere inside its bar.

That gives three cases. A read that ends before the write starts must return 0. A read that starts after the write ends must return 1. A read whose bar overlaps the write’s is concurrent with it: we can’t know whether the write had taken effect, so 0 and 1 are both allowed. In the theory, x is a register; in practice it could be one key, one row or one document.

Try it: pick client A or B, slide read starts at, and press Add read. Each new bar is labelled with the values it may legally return. Add a few, then press Database answers to see one possible set of responses.

What the book says

Figure 10-2 shows three clients concurrently reading and writing the same object x in a linearizable database. In distributed systems theory, x is called a register; in practice it could be one key in a key-value store, one row in a relational database, or one document in a document database.

Each bar is a request made by a client: its start is when the request was sent, and its end is when the response was received. Because of variable network delays, a client doesn’t know exactly when the database processed its request, only that it happened sometime between sending the request and receiving the response.

Read(x) ⇒ v means the client read register x and the database returned v. Write(x, v) ⇒ r means the client set x to v and got response r (OK or Error). With x initially 0 and client C writing 1: a read that completes before the write begins must return 0; a read that begins after the write has completed must return 1; any read that overlaps the write might return either 0 or 1, because these operations are concurrent with the write.

Linearizability · one moment when the value flips

Once anyone has seen 1, nobody may see 0 again

“Either value” for overlapping reads isn’t enough on its own. If every overlapping read could pick independently, A might see 1, then B might see 0, then A 1 again: the value would flicker while C’s write is still running. That isn’t how one copy of the data behaves.

So linearizability adds a rule: there is one point in time, somewhere inside the write’s bar, at which x atomically flips from 0 to 1. Every read takes effect at its own point inside its own bar, and sees 1 exactly if that point is after the flip. The consequence: once some read has returned 1, every read that starts after it returns 1 too, even if the write hasn’t finished yet.

Try it: in Each read picks, press Run the polls a few times and count the flip-backs. Switch to One atomic flip, move the flip point slider and run again: the arrow shows the first read that saw 1 forcing every later read to 1.

What the book says

If reads that are concurrent with a write can return either the old or the new value, readers could see a value flip back and forth between the old and the new value several times while a write is going on. That is not what we expect of a system that emulates a single copy of the data.

In a linearizable system, we imagine that there must be some point in time, between the start and end of the write operation, at which the value of x atomically flips from 0 to 1. If one client’s read returns the new value 1, all subsequent reads must also return the new value, even if the write operation has not yet completed.

In Figure 10-3, client A is the first to read the new value, 1. Just after A’s read returns, B begins a new read. Since B’s read occurs strictly after A’s, it must also return 1, even though the write by C is still ongoing. It’s the same situation as Aaliyah and Bryce.

Linearizability · linearization points and checking a history

Find one order that explains every answer

Four clients, A to D, read, write and compare-and-set the same x. CAS(x, old, new) sets x to new only if it currently equals old; otherwise it changes nothing and returns an error. Given the bars and every response, how can you tell whether the database was linearizable?

Try to put a marker inside every bar, the moment the operation “happened”, so that walking the markers from left to right replays a valid single-register story: every read returns the latest write, every CAS succeeds exactly when it should. The line joining the markers must only ever move forward in time. If no such placement exists, the history is not linearizable. Testing tools do exactly this search, which is why it is computationally expensive.

Try it: press Check history and watch the search in the code panel. It fails on B’s last read: A had already read 4 before that read began. Set B’s last read returns to 4 and check again: now a valid order exists and its markers are drawn. Then make D’s CAS succeed and see what that breaks.

What the book says

Figure 10-4 marks each operation with a vertical line, inside its bar, at the time when we think it executed. The markers are joined up in a sequential order, and the result must be a valid sequence of reads and writes for a register: every read must return the value set by the most recent write. Linearizability requires that the lines joining the markers always move forward in time, never backward.

CAS(x, vold, vnew) ⇒ r atomically sets x to vnew if it equals vold; otherwise it leaves the register unchanged and returns an error. In the figure, B’s first read returns 1 although D’s write of 0 and A’s write of 1 were sent after it: acceptable, because the three requests are concurrent. B’s read even returns 1 before A gets its OK. B’s and C’s CAS requests succeed, but D’s fails because x is no longer 0. The final read by B is not linearizable: it is concurrent with C’s CAS from 2 to 4, but A had already read 4 before B’s read started.

It is possible, though computationally expensive, to test whether a system’s behavior is linearizable by recording the timings of all requests and responses and checking whether they can be arranged into a valid sequential order. There are weaker consistency models than linearizability; read-after-write consistency, monotonic reads and consistent prefix reads are examples. Linearizability includes all of these guarantees and more: it is the strongest consistency model in common use.

Linearizability · versus serializability

Two words that both sound like “in some order”

Serializability is about transactions touching many objects: they must behave as if they ran one after another, in some order, and that order may differ from real time. So a read-only transaction may legally be placed before a write that already finished: a stale read. Linearizability is about single objects and recency: if one operation finishes before another starts, the second sees something at least as new. But it doesn’t group operations, so it can’t stop anomalies that span several objects, such as write skew.

You can have either one without the other. A database that gives both is strictly serializable.

Try it: in Stale snapshot, press Run and watch where the dot lands in the grid. Press Add recency and run again. In Write skew, press Run, then Add transactions and run again.

What the book says

Serializability is an isolation level of transactions, where every transaction may read and write multiple objects. It guarantees that transactions behave the same as if they had executed in some serial order, without interleaving. It is OK for that serial order to be different from the order in which the transactions were actually run.

Linearizability is a guarantee on reads and writes of a register (an individual object). It doesn’t group operations into transactions, so it does not prevent problems such as write skew that involve multiple objects. But it is a recency guarantee: if one operation finishes before another one starts, the later operation must observe a state at least as new. Serializability does not have that requirement; stale reads are allowed by serializability.

A database may provide both; the combination is known as strict serializability or strong one-copy serializability (strong-1SR). Single-node databases are typically linearizable. CockroachDB provides serializability and some recency guarantees on reads, but not strict serializability, because that would require expensive coordination between transactions; Spanner and FoundationDB offer strict serializability. The consistency model and the isolation level can be chosen largely independently of each other.

Relying on linearizability · locking and leader election

Three nodes wake up, and only one may be in charge

A single-leader database must have exactly one leader. A common way to choose it is a lease: a lock with an expiry time. Every node that starts tries to take the lease, and whoever succeeds leads, renewing it every few seconds. If the leader dies, the lease runs out and someone else takes it.

This only works if taking the lease is linearizable. If the lease store answers “free” from a replica that hasn’t yet heard about the first winner, a second node takes the lease too, and you have two leaders accepting writes: split brain. That is why lease stores such as ZooKeeper and etcd run on consensus.

Try it: press Start all three nodes in each mode. With Store reads a replica, two nodes can both become leader. With Linearizable store, exactly one wins; then press Crash the leader and watch the lease expire and pass on.

What the book says

A system using single-leader replication needs to ensure there is only one leader, not several (split brain). One way of electing a leader is to use a lease: every node that starts up tries to acquire the lease, and the one that succeeds becomes the leader. No matter how this mechanism is implemented, it must be linearizable: it shouldn’t be possible for two nodes to acquire the lease at the same time.

Coordination services like Apache ZooKeeper and etcd are often used to implement distributed leases and leader election. They use consensus algorithms to implement linearizable operations in a fault-tolerant way. Many subtle details are involved (such as fencing), and libraries like Apache Curator provide higher-level recipes on top of ZooKeeper, but a linearizable storage service is the basic foundation. Strictly speaking, ZooKeeper provides linearizable writes, but reads may be stale, since there is no guarantee they are served from the current leader; etcd since version 3 provides linearizable reads by default.

Distributed locking is also used at a much more granular level: Oracle Real Application Clusters (RAC) uses a lock per disk page, with multiple nodes sharing access to the same disk storage. Since these linearizable locks are on the critical path of transaction execution, RAC deployments usually have a dedicated cluster interconnect network.

Relying on linearizability · constraints and uniqueness guarantees

Two people claim the last of something at once

Priya in Mumbai and Tomás in Lisbon both press the button in the same second: both want the username maya, or the last seat on a flight, or to take money out of the same account. Each request lands on a nearby replica. If each replica just checks its own copy, both see “free” and both succeed.

Enforcing the rule while the data is written needs one up-to-date value that every node agrees on, which is the same as taking a lock on the name. It is a compare-and-set: set maya to my user ID, but only if it is still unset. Some businesses prefer to bend instead: overbook the flight, then move someone and compensate them.

Try it: pick Username, Last seat or Balance, then a strategy, and press Both submit at once. Compare Check own replica, Linearizable CAS and Allow, then apologize.

What the book says

Uniqueness constraints are common: a username or email address must uniquely identify one user, and a file storage service cannot have two files with the same path. To enforce such a constraint as the data is written, so that one of two concurrent attempts receives an error, you need linearizability. It is similar to acquiring a lock on the chosen username, and very similar to an atomic CAS that sets the username to the ID of the user who claimed it, provided it is not already taken.

Similar issues arise if a bank balance must never go negative, if you must not sell more items than you have in stock, or if two people must not book the same seat. These constraints require a single up-to-date value (the balance, the stock level, the seat occupancy) that all nodes agree on.

In real applications it is sometimes acceptable to treat such constraints loosely: if a flight is overbooked, you can move customers to a different flight and compensate them, and then linearizability may not be needed. A hard uniqueness constraint, as typically found in relational databases, requires linearizability; other kinds of constraints, such as foreign-key or attribute constraints, can be implemented without it.

Relying on linearizability · cross-channel timing dependencies

The message that arrived before the file

Bryce only noticed his stale score because a second channel existed: Aaliyah’s voice. Computers have second channels too. Leila uploads a new version of cat.mp4. The web server stores it in file storage, then puts a small “please transcode cat.mp4” message on a queue, because a message queue isn’t built for megabytes of video. A transcoder picks up the message and fetches the file.

If the queue is faster than the storage service’s own internal replication, the transcoder can be served by a storage replica that still has yesterday’s version, or no file at all. It shrinks the wrong video, and the original and the small copy stay different forever. Linearizable storage closes this race: once the write has completed, every read sees it, whichever channel told you to look.

Try it: press Upload with a high storage replication lag and a low queue delay. Then switch on Linearizable storage, or slow the queue down, and upload again. The Push notification mode shows the same race in a phone app.

What the book says

In Figure 10-1, the violation was noticed only because there was an additional communication channel: Aaliyah’s voice to Bryce’s ears. Similar situations arise in computer systems. A website lets users upload a video, and a background process transcodes it to a lower quality for slow connections (Figure 10-5). The instruction is sent from the web server to the transcoder via a message queue. Most message brokers are designed for small messages, so the video is first written to a file storage service, and once that write is complete, the instruction is placed on the queue.

If the file storage service is linearizable, this works fine. If not, there is a race condition: the message queue (steps 3 and 4) might be faster than the internal replication inside the storage service, so when the transcoder fetches the video (step 5) it might see an old version or nothing at all. If it processes an old version, the original and transcoded videos become permanently inconsistent.

The problem arises because there are two communication channels between the web server and the transcoder. A similar race occurs when a mobile app receives a push notification and then fetches data from a lagging replica. Linearizability is not the only way to avoid this, but it is the simplest to understand; if you control the additional channel, you can use approaches similar to reading your own writes, at the cost of additional complexity.

Linearizability · implementing linearizable systems

Which kinds of replication can keep the promise?

The simplest linearizable system is one copy of the data, but that copy dies with its machine. So which of the replication methods can pretend to be one copy? Each has a typical way of breaking the illusion.

Single-leader: potentially, if all reads and writes go to the leader, but a node that only thinks it is still leader can serve stale data. Consensus: likely, because it is single-leader replication built to prevent split brain, unless reads skip the leadership check. Multi-leader: not linearizable; two leaders accept conflicting writes. Leaderless: probably not; last-write-wins with clock timestamps can throw away the newer write.

Try it: pick each method and press Run the test. Then press its fault or fix button (for example No faults or Read without leader check) and run again to see what decides the verdict.

What the book says

Linearizability essentially means behaving as though there is only a single copy of the data with atomic operations. Really using one copy would not tolerate faults.

Single-leader replication (potentially linearizable). If you perform all reads and writes on the leader, they are likely to be linearizable, but this assumes you know for sure who the leader is. A node may think it is the leader when it is not; if the delusional leader continues to serve requests, it is likely to violate linearizability. With asynchronous replication, failover may lose committed writes. Sharding with a separate leader per shard does not affect linearizability, since it is only a single-object guarantee.

Consensus algorithms (likely linearizable). Some are essentially single-leader replication with automatic leader election and failover, carefully designed to prevent split brain: ZooKeeper uses Zab and etcd uses Raft. But if a system allows reads on a node without checking that it is still the leader, the reads may be stale if a new leader has just been elected.

Multi-leader replication (not linearizable). Writes are processed concurrently on several nodes and replicated asynchronously, producing conflicting writes. Leaderless replication (probably not linearizable). LWW conflict resolution based on time-of-day clocks (e.g., in Cassandra and ScyllaDB) is almost certainly nonlinearizable, because clock timestamps cannot be guaranteed to be consistent with actual event ordering, due to clock skew. Even with quorums, nonlinearizable behavior is possible.

Implementing linearizable systems · linearizability and quorums

Two majorities, two different answers

Yusuf runs a leaderless store with three replicas. Every write goes to all three (w = 3), every read asks two (r = 2). Since 3 + 2 > 3, every read quorum overlaps every write quorum, so the team assumes reads are always fresh. Then one write of x = 1 arrives at replica 1 quickly and at replicas 2 and 3 slowly.

While it is still in flight, Ingrid reads replicas 1 and 2, sees timestamps 1 and 0, and returns the newer value, 1. A moment after Ingrid is done, Rafael reads replicas 2 and 3. Neither has the write yet, so Rafael gets 0. The quorum condition held the whole time, and still a later read saw an older value than an earlier one. That is not linearizable.

The repair costs speed: a reader that sees a stale replica must write the newer value back before it answers (synchronous read repair), and a writer must first read a quorum’s latest timestamp so its own is larger. Even then you get linearizable reads and writes, but not a linearizable compare-and-set: that needs consensus.

Try it: in Plain quorum, press Run Figure 10-6 and watch Ingrid and Rafael disagree. Switch to Sync read repair and run it again: Ingrid’s read is slower, but Rafael now sees 1. Follow the lit lines in the code underneath.

What the book says

With leaderless (Dynamo-style) replication, people sometimes claim that quorum reads and writes (w + r > n) give strong consistency. Depending on the exact algorithm and how you define strong consistency, this is not quite true. LWW conflict resolution based on time-of-day clocks (e.g., in Cassandra and ScyllaDB) is almost certainly nonlinearizable, because of clock skew.

In Figure 10-6 the initial value of x is 0, and a writer updates x to 1 by sending the write to all three replicas (n = 3, w = 3). Concurrently, client A reads from a quorum of two nodes (r = 2) and sees 1 on one node and 0 on the other. Also concurrently, client B reads from a different quorum of two nodes and gets 0 from both. The quorum condition is met, but B’s request begins after A’s completes and returns the old value while A returns the new one.

Dynamo-style quorums can be made linearizable at the cost of performance: a reader must perform read repair synchronously before returning results, and before writing, a writer must read the latest state of a quorum of nodes to fetch the latest timestamp and ensure the new write has a greater one. Riak does not perform synchronous read repair because of the performance penalty. Cassandra does wait for read repair on quorum reads, but loses linearizability because it uses time-of-day clocks for timestamps.

Only linearizable reads and writes can be implemented this way; a linearizable CAS operation cannot, because it requires a consensus algorithm. It is safest to assume that a leaderless system with Dynamo-style replication does not provide linearizability, even with quorum reads and writes.

Linearizability · the cost of linearizability

Somebody cuts the cable between two regions

Zanele’s shop has a datacenter in Europe and one in Asia. Shoppers talk to the region nearest them. One afternoon a cable fault cuts the link between the two regions, while both regions keep working and every shopper can still reach their own region. That situation is a network partition.

With single-leader replication, the leader lives in one region. Every write and every linearizable read must reach it, so shoppers in the other region now get errors. They can still read their local follower, but that copy may be stale. With multi-leader replication, each region keeps accepting writes and simply queues them up for the other side, to exchange when the link heals. It stays available because it never promised linearizability.

Try it: in Single-leader, press Send requests and see every request served. Press Cut the link and send again: Asia’s writes and linearizable reads fail. Switch to Multi-leader, cut the link, send, then Repair the link to see the queued writes exchanged.

What the book says

Multi-leader replication is often a good choice for multi-region replication (Figure 10-7). Suppose the network between two regions is interrupted, but clients can still reach their local regions: this is a network partition.

With a multi-leader database, each region can continue operating normally: writes from one region are asynchronously replicated to the other, so they are simply queued up and exchanged when connectivity is restored.

With single-leader replication, the leader must be in one of the regions, and any writes and any linearizable reads must be sent to it. If the link is interrupted, clients connected to follower regions cannot make writes nor linearizable reads. They can still read from the follower, but those reads might be stale (nonlinearizable). If the application requires linearizable reads and writes, the interruption makes the application unavailable in the regions that cannot contact the leader, until the link is repaired. Clients that can reach the leader’s region continue to work normally.

The cost of linearizability · the CAP theorem

When the network splits, pick which promise to break

This isn’t only about regions, or about leaders. Any linearizable database has the same problem, on any unreliable network, even inside one building. If some replicas can’t talk to the others, a system that promised linearizability must make the cut-off replicas wait or return errors: it is CP, consistent under partitions. A system that doesn’t need linearizability can let every replica keep serving on its own: it is AP, available under partitions, and its answers may disagree.

That rule of thumb was named the CAP theorem in 2000 and helped start the NoSQL movement. But its formal version is narrow: one consistency model, one kind of fault. And most of the time there is no partition at all, yet many systems still trade consistency away, for latency. PACELC says it: under a Partition, choose Availability or Consistency; Else, choose Latency or Consistency.

Try it: in Partition (PAC), pick CP or AP, press Split the network, then Write on both sides. In No partition (ELC), choose where reads go and press Read 20 times: compare the latency and the number of stale answers.

What the book says

Any linearizable database has this problem, however it is implemented, and not just in multi-region deployments: it can occur on any unreliable network, even within one region. If your application requires linearizability and some replicas are disconnected, they must wait until the network is fixed or return an error (CP, consistent under network partitions). If it does not require linearizability, each replica can process requests independently (e.g., multi-leader) and remain available, but its behavior is not linearizable (AP, available under network partitions).

This insight is popularly known as the CAP theorem, named by Eric Brewer in 2000, although the trade-off had been known to designers of distributed databases since the 1970s. CAP was a rule of thumb meant to start a discussion; it encouraged engineers to explore distributed shared-nothing systems and helped trigger the NoSQL movement around the mid-2000s.

As formally defined, CAP is of very narrow scope: it considers only linearizability and only network partitions, which according to data from Google cause less than 8% of incidents. It says nothing about network delays, dead nodes or other trade-offs, so it has little practical value for designing systems.

The PACELC principle observes that designers may also weaken consistency when the network is fine, to reduce latency: during a partition (P), choose between availability (A) and consistency (C); else (E), choose between low latency (L) and consistency (C). It inherits several of CAP’s problems, and CAP has now been superseded by more precise results, so it is of mostly historical interest today.

You don’t get to pick partitions

Noor’s team is told CAP means “consistency, availability, partition tolerance: pick two”. They proudly pick C and A. Then a switch fails and the network splits, as networks do. Their system now has to break one of its two promises, and nobody planned which.

What the book says

CAP is sometimes presented as consistency, availability, partition tolerance: pick two out of three. Putting it this way is misleading. Network partitions are a kind of fault, so they aren’t something you choose: they will happen whether you like it or not. The only way to guarantee no network partitions is to have no network, that is, only one replica, but then you don’t have high availability either.

When the network is working correctly, a system can provide both consistency (linearizability) and availability. When a network fault occurs, you have to choose between them. A better phrasing is either consistent or available when partitioned. A more reliable network needs to make this choice less often, but at some point it is inevitable.

The CP/AP classification has other flaws: consistency is formalized as linearizability (nothing about weaker models), and the formal definition of availability does not match the usual meaning of the term. Many highly available (fault-tolerant) systems don’t meet CAP’s idiosyncratic definition of availability, and some designers choose, with good reason, to provide neither linearizability nor CAP’s form of availability, so their systems are neither CP nor AP. There is a lot of confusion around CAP, so it’s best not to dwell on it.

The cost of linearizability · linearizability and network delays

Even your CPU isn’t linearizable

Dmitri writes x = 1 on one CPU core, and a thread on another core reads x a moment later. It gets 0. Nothing failed. Each core has its own cache and store buffer: the write waits in core 1’s buffer and drains to memory later, while core 2 happily reads its own cached copy. Several copies, updated asynchronously: linearizability is gone, unless you pay for a memory barrier (fence).

Nobody does this to survive a “partition” between cores; a core cut off from the rest of the computer can’t work anyway. They do it for speed. Many distributed databases skip linearizability for the same reason, and the cost is real all the time, not just during faults: Attiya and Welch proved that a linearizable read or write takes time at least proportional to how uncertain the network’s delays are. No cleverer algorithm exists.

What the book says

Surprisingly few systems are linearizable in practice. Even RAM on a modern multi-core CPU is not: if a thread on one core writes to a memory address and a thread on another core reads it shortly afterward, it is not guaranteed to read the value written (unless a memory barrier or fence is used). Every core has its own memory cache and store buffer; reads are served from the cache, and changes are asynchronously written out to main memory. There are now several copies, asynchronously updated, so linearizability is lost.

It makes no sense to use the CAP theorem to justify this: within one computer we assume reliable communication, and a core disconnected from the rest of the computer can’t continue anyway. The reason for dropping linearizability is performance, not fault tolerance. The same is true of many distributed databases: linearizable systems tend to be higher latency, all the time, not only during a network fault.

Attiya and Welch prove that if you want linearizability, the response time of reads and writes is at least proportional to the uncertainty of delays in the network. With highly variable delays, as in most computer networks, linearizable reads and writes inevitably have high response times. A faster algorithm does not exist, but weaker consistency models can be much faster.

What the book says

Sharded ID assignment: several nodes assign IDs, e.g. one only even and one only odd numbers; in general you reserve some bits for a shard number. IDs stay compact, but you lose ordering: with IDs 16 and 17 you don’t know which was sent first, since different nodes assigned them and one might have been ahead.

Preallocated blocks of IDs: the single-node generator hands out blocks, e.g. node A claims 1 to 1,000 and node B claims 1,001 to 2,000, and requests a new block when running low. This doesn’t ensure correct ordering either.

Random UUIDs: universally unique identifiers (GUIDs) can be generated locally on any node without communication, but need more space (128 bits). Version 4 is essentially a random number so long that collisions are very unlikely; its order is also random, so comparing two IDs tells you nothing about which is newer.

Wall-clock timestamp made unique: if your nodes’ time-of-day clocks are kept approximately correct using NTP, put a timestamp from that clock in the most significant bits and fill the rest with a shard number and per-shard sequence number, or a long random value. This is used in version 7 UUIDs, X’s Snowflake, ULIDs, Hazelcast’s Flake ID generator and MongoDB ObjectIDs. Wall-clock timestamps give at best an approximate ordering: an earlier write with a slightly fast clock can get a later timestamp, and clock jumps can misorder even one node’s IDs, so such generators are unlikely to be linearizable. Atomic clocks or GPS receivers reduce the problem.

A clock that counts events, not seconds

A wristwatch is a physical clock: it measures seconds. A logical clock is an algorithm that counts events. Its timestamps don’t tell you what time it is, but compare any two and you know which came first.

A good logical clock makes three promises. Its timestamps are compact (a few bytes) and unique. Any two can be compared: they are totally ordered. And the order is consistent with causality: if A happened before B, for example because B’s node had heard about A, then A’s timestamp is smaller. The single-node counter keeps all three; every distributed scheme from the last scene breaks the third.

What the book says

Time-of-day clocks and monotonic clocks are both physical clocks: hardware devices that measure the passing of time. In distributed systems it is common to also use a logical clock: an algorithm that counts the events that have occurred. Its timestamp doesn’t tell you what time it is, but you can compare two timestamps to tell which one is earlier.

The general requirements for a logical clock: its timestamps are compact (a few bytes in size) and unique; you can compare any two and determine which is earlier (they are totally ordered); and the order of timestamps is consistent with causality, i.e., if operation A happened before operation B, then A’s timestamp is less than B’s.

A single-node ID generator meets these requirements, but the distributed ID generators just discussed do not meet the causal ordering requirement.

What the book says

A simple method for generating logical timestamps that is consistent with causality, usable as a distributed ID generator, is the Lamport clock, proposed in 1978 by Leslie Lamport, in one of the most-cited papers in distributed systems. Lamport clocks provide a total ordering, but not linearizability: they are not a way of ensuring a value is up-to-date, merely a way of assigning IDs such that if event A happened before event B, A’s ID is less than B’s.

Each node has a unique identifier (Aaliyah, Bryce or Caleb in Figure 10-9; in practice perhaps a random UUID) and keeps a count of the operations it has processed. A Lamport timestamp is a pair of (counter, node ID); two nodes may have the same counter, but including the node ID makes each timestamp unique.

Every time a node generates a timestamp, it increments its counter and uses the new value. Every time a node sees a timestamp from another node with a greater counter than its own, it increases its local counter to match.

To compare two Lamport timestamps, compare the counters first; if they are equal, compare the node IDs with lexicographic string comparison. In the example, (1, "Aaliyah") < (1, "Caleb") < (2, "Bryce").

Logical clocks · hybrid logical clocks

A wall clock that refuses to go backward

Lamport counters have two weak spots. They have nothing to do with real time, so you can’t ask for all the messages posted last Tuesday. And two nodes that never talk drift apart: one might be at 12 and the other at 40,000 for events at the same moment.

A hybrid logical clock fixes both. It counts like a real clock, in microseconds, so its timestamps read almost like times of day. Like a Lamport clock, when it sees a bigger timestamp from another node it jumps forward to match, and it bumps itself on every timestamp it generates, so it never runs backward even if NTP pulls the physical clock back. It may run slightly ahead of the real time, but its order is always consistent with causality. CockroachDB uses one.

What the book says

Lamport timestamps have limitations: since they have no direct relation to physical time, you can’t use them to find, say, all the messages posted on a particular date; and if two nodes never communicate, one node’s counter increments are never reflected in the other’s, so events generated around the same time can have wildly different counter values.

A hybrid logical clock combines the advantages of physical time-of-day clocks with the ordering guarantees of Lamport clocks. Like a physical clock, it counts seconds or microseconds. Like a Lamport clock, when a node sees a timestamp from another node greater than its local clock value, it moves its own value forward to match, so if one node’s clock runs fast, the others move forward too when they communicate.

Every time a timestamp is generated it is also incremented, so the clock moves forward monotonically even if the underlying physical clock jumps backward, e.g. because of NTP adjustments. It might be slightly ahead of the physical clock; details of the algorithm keep this discrepancy as small as possible. You can treat its timestamps almost like conventional time-of-day timestamps, with ordering consistent with the happens-before relation. It needs no special hardware, only roughly synchronized clocks. Hybrid logical clocks are used by CockroachDB, for example.

Linearizable ID generators · implementing one

A ticket machine that writes down a whole roll at a time

The deli counter’s ticket machine must never give two customers the same number, even if it’s unplugged. Writing every ticket number into the logbook would be slow, so Yusuf writes tickets up to 200 are spoken for once, then hands out 101, 102, 103… straight from memory. That is how a timestamp oracle (TiDB/TiKV’s name, inspired by Google’s Percolator) works: one node that atomically increments a counter, persists it, and replicates it to a follower with single-leader replication. What the book says

The simplest way to make ID assignment linearizable is to use a single node that does three things: atomically increment a counter and return its value, persist the counter value (so it doesn’t generate duplicate IDs after a crash and restart), and replicate it for fault tolerance using single-leader replication. TiDB/TiKV calls this a timestamp oracle, inspired by Google’s Percolator.

As an optimization, instead of a disk write and replication per request, the generator writes a record describing a batch of IDs; once that record is persisted and replicated, it hands out those IDs in sequence, and persists the next batch before running out. Some IDs are skipped if the node crashes and restarts or fails over to a follower, but no duplicate or out-of-order IDs are issued.

You can’t easily shard the generator, or distribute it across regions, so in a geographically distributed database all ID requests go to a node in one region. On the upside, its job is very simple, so a single node can handle a large request throughput.

Alternatively, Google’s Spanner relies on a physical clock that returns a range of timestamps indicating the uncertainty in the reading, and waits for the duration of that uncertainty interval to elapse before returning. If the interval is correct, a request that completes before another begins gets the smaller timestamp, without any communication, even across regions. The downside is the hardware and software support needed for tightly synchronized clocks and for computing the uncertainty interval.

Easy with one boss, hard without one

In a small office, one manager answers every question: who leads the project, what the next invoice number is, who gets the meeting room. Quick, consistent, and useless the day the manager is off sick. The best-known algorithms are Viewstamped Replication, Paxos, Raft and Zab. They all assume a non-Byzantine world: messages may be delayed or dropped, nodes may crash, restart or get cut off, but no node lies. What the book says

Several things are easy on a single node but hard with fault tolerance: a single leader making all reads and writes is linearizable, but how do you fail over without split brain, and make sure a node that believes it is leader hasn’t been voted out while paused? A linearizable ID generator on one node is just a counter with atomic fetch-and-add; what if it crashes? An atomic CAS decides who gets a lock or lease, or ensures a unique file or user name; on one node it may be one CPU instruction, but how do you make it fault-tolerant?

All of these are instances of the same fundamental problem: consensus, whose standard formulation is getting multiple nodes to agree on a single value. It is one of the most important problems in distributed computing, infamously difficult to get right, and many systems have gotten it wrong in the past.

The best-known algorithms are Viewstamped Replication, Paxos, Raft and Zab. They have similarities but are not the same. They work in a non-Byzantine system model: communication may be arbitrarily delayed or dropped, and nodes may crash, restart and become disconnected, but nodes otherwise follow the protocol and don’t behave maliciously.

Some consensus algorithms tolerate some Byzantine nodes, that don’t follow the protocol, for example by sending contradictory messages. A common assumption is that fewer than one-third of the nodes are Byzantine-faulty. Such algorithms are used in blockchains, for example, but are beyond the scope of the book.

Slow or dead? Without a clock you can never tell

Amara and Kenji must agree on 0 or 1 with Sione, but Sione has gone silent. Maybe his messages are just slow; maybe he has crashed. It doesn’t say agreement is never reached. Give the algorithm timeouts, so it can suspect a crash even if it is sometimes wrong, or random numbers, and consensus becomes solvable. Real systems do both.

What the book says

The FLP result, named after Fischer, Lynch and Paterson, proves that no algorithm is always able to reach consensus if there is a risk that a node may crash. Since in a distributed system we must assume nodes may crash, reliable consensus is impossible. Yet here we are, discussing algorithms for achieving it.

First, FLP doesn’t say that we can never reach consensus; it only says that we can’t guarantee that a consensus algorithm will always terminate. Moreover, it is proved assuming a deterministic algorithm in the asynchronous system model, which means the algorithm cannot use any clocks or timeouts.

If the algorithm can use timeouts to suspect that another node may have crashed (even if the suspicion is sometimes wrong), consensus becomes solvable. Even allowing the algorithm to use random numbers is sufficient. So although FLP is of great theoretical importance, distributed systems can usually achieve consensus in practice.

Solve one, get the rest for free

Leila has a fault-tolerant compare-and-set. Oskar has a fault-tolerant shared log. Mei has an atomic commit protocol for transactions across shards. They look like three different tools, but each of them can build the other two. Hand any one of them a single trick, and they can rebuild the rest.

This is the chapter’s big surprise: single-value consensus, compare-and-set, an append-only shared log (total order broadcast) and atomic commitment are equivalent. A solution to one converts into a solution to any other. Locks, leases and uniqueness constraints sit on top. Fetch-and-add looks like it belongs too, but it falls short: it only solves consensus between two nodes.

What the book says

Consensus can be expressed in several ways. Single-value consensus is very similar to an atomic CAS operation, and can implement locks, leases and uniqueness constraints. Constructing an append-only log also requires consensus, usually formalized as total order broadcast; with a log you can implement state machine replication, leader-based replication, event sourcing and other patterns. An atomic fetch-and-add (atomic increment) operation also turns out to be equivalent to consensus. Atomic commitment of a multidatabase or multishard transaction requires all participants to agree on whether to commit or abort.

In fact, these problems are all equivalent: an algorithm that solves one can be converted into a solution for any of the others. This is a profound and perhaps surprising insight, and why they can all be lumped together under consensus, even though they look quite different on the surface.

The later sections refine this for fetch-and-add: it solves consensus for two nodes only (a consensus number of 2), whereas CAS and shared logs work for any number of nodes.

Four promises, and the one that makes it hard

Five nodes start up at once and each proposes itself as the new leader. Whatever they decide must keep four promises. Uniform agreement: no two nodes decide differently. Integrity: once a node decides, it never changes its mind. Validity: the decided value was actually proposed by someone. Termination: every node that doesn’t crash eventually decides.

The first three are easy: let n1 be a dictator. But bury n1 under thirty feet of mud and nobody decides anything again. All the difficulty comes from termination, which is fault tolerance in disguise, and it has a limit: any consensus algorithm needs a majority of nodes working to terminate. The first three are safety properties; termination is liveness. A good algorithm keeps safety even when the majority is gone: it stops, but never decides inconsistently.

What the book says

One or more nodes may propose values, and the consensus algorithm decides on one of them, for example which node becomes leader, holds a lease, or buys a seat. It must satisfy: uniform agreement (no two nodes decide differently), integrity (after deciding a value, a node cannot change its mind), validity (if a node decides v, then v was proposed by a node) and termination (every node that does not crash eventually decides a value). To decide multiple values, run a separate instance per value, for example one per theater seat.

Validity rules out trivial solutions such as always deciding null. Without fault tolerance the first three are easy: hardcode one node as the dictator. But if it fails, the system can no longer decide anything, just like single-leader replication without failover. All the difficulty arises from the need for fault tolerance.

Termination formalizes fault tolerance: even if some nodes fail, the others must reach a decision, even if a crashed node never comes back (imagine it buried under 30 feet of mud). Termination is a liveness property; the other three are safety properties. Any consensus algorithm requires at least a majority of nodes functioning correctly to assure termination, and that majority can safely form a quorum.

Most consensus algorithms ensure the safety properties are always met, even if a majority of nodes fail or the network has severe problems: a large-scale outage can stop the system from processing requests, but cannot make it decide inconsistently.

What the book says

A CAS operation checks whether the current value of an object equals an expected value. If so, it atomically updates the object to a new value; if not, it leaves the object unchanged and returns an error.

With a fault-tolerant, linearizable CAS, consensus is easy: initially set the object to null, then have each node that wants to propose a value perform a CAS with expected value null and new value its proposal. The decided value is whatever the object is set to.

Likewise, with consensus you can implement CAS: whenever one or more nodes want to perform a CAS with the same expected value, use the consensus protocol to propose the new values, then set the object to whatever was decided. What the book says

A log stores a sequence of entries, and anyone reading it sees the same entries in the same order. A shared log is one where multiple nodes can request that entries be appended, for example single-leader replication. It supports requesting that a value be added and reading the entries, and must satisfy: eventual append (a node that requests a value and doesn’t crash eventually reads it in an entry), reliable delivery (if one node reads an entry, every node that doesn’t crash eventually reads it), append-only (entries read are immutable, new entries go only after them, rereads show the same sequence, even after a crash), agreement (if two nodes both read entry e, they read exactly the same sequence before e) and validity (a value read was previously requested by a node).

A shared log can be implemented with a total order broadcast protocol, also known as atomic broadcast or total order multicast.

With a shared log, consensus is easy: every proposer requests its value be added, and whichever value is read back in the first entry is decided. Conversely, with consensus you can build a shared log: run a separate consensus instance for every future slot; a node proposes its value for an undecided slot; when a slot is decided and all previous slots are decided, the value is appended, along with any consecutive decided slots; if a proposed value was not chosen, the node retries for a later slot. So consensus is equivalent to total order broadcast and shared logs.

Single-leader replication without failover does not meet the liveness requirements, since it stops delivering messages if the leader crashes. The challenge is performing failover safely and automatically.

Yusuf orders a lamp. Three shards must agree: orders records it, payments charges him, stock removes one lamp. If stock is out, nobody may commit. If every shard votes yes but one vote message gets lost, they may all commit or all abort, as long as they all do the same thing.

The two problems are still equivalent: each node broadcasts its vote, proposes “commit” only if it heard commit from everyone, and lets consensus pick among the proposals. What the book says

Atomic commitment ensures that the databases or shards in a distributed transaction all either commit or abort. Two-phase commit solves it, but relies on a coordinator that is a single point of failure. Unlike consensus, where it’s OK to decide any proposed value, atomic commitment must abort if any participant voted to abort.

  • Uniform agreement: no node commits while another aborts.
  • Integrity: once a node has committed it can’t change its mind to abort, and vice versa.
  • Validity: if a node commits, all nodes must have voted to commit; if any voted abort, all must abort.
  • Nontriviality: if all vote commit and no communication times out, all must commit.
  • Termination: every node that does not crash eventually commits or aborts.

From consensus: every node sends its vote to every other. Nodes that receive commit from themselves and everyone else propose commit; nodes that receive an abort, or time out, propose abort. If all voted commit but some messages timed out, some may propose commit and others abort; it doesn’t matter which wins, as long as everyone does the same.

From atomic commit: a proposer starts a transaction on a quorum of nodes, and each performs a single-node CAS to set a register to the proposed value if it isn’t already set. A node votes commit if its CAS succeeded, otherwise abort. A committed transaction decides its value; an aborted one is retried as a new transaction. So atomic commit and consensus are equivalent too.

What the book says

Single-value consensus, CAS, shared logs and atomic commitment are all equivalent, but which is most useful in practice? Two rounds of voting, and the leader who fell asleep

Single-leader replication already gives you a shared log, as long as the leader lives. When it dies, a traditional database waits for a human to promote a follower. That takes minutes and doesn’t meet consensus’s termination property. But electing a new leader automatically seems to need consensus itself, or two nodes could both think they lead. Chicken, meet egg.

The trick: don’t promise one leader at all times. Promise one leader per epoch (Raft says term, Paxos ballot, Viewstamped Replication view). A node that hears nothing from the leader for a while starts an election with a higher epoch number; a node votes yes only if it knows no higher epoch. Then, before appending each entry, the leader asks for a second vote, on the proposal itself. Both votes need a quorum, and any two majorities of five share a node, so if an old leader is still around, at least one of its voters has heard of the newer epoch and refuses.

Try it: press Client write twice. Then press Pause the leader and Election timeout: a new leader wins epoch 2 (rings mark its voters). Press Wake the old leader: it still thinks it leads epoch 1, tries to append, and is turned away. Tap nodes to crash them first and see when elections and writes stop.

What the book says

Single-value consensus is easy with a single dictator node, and a shared log is easy if one leader is the only node allowed to append. Traditionally, single-leader databases left failover to a human administrator, which means significant downtime and doesn’t satisfy termination. Consensus requires choosing a new leader automatically. (Not all consensus algorithms have a leader, but the commonly used ones do.)

All nodes need to agree on who the leader is, or two nodes could each believe themselves leader. It seems we need consensus to elect a leader, and a leader to solve consensus. Instead, consensus algorithms make a weaker guarantee: they define an epoch number (ballot number in Paxos, view number in Viewstamped Replication, term number in Raft) and guarantee that within each epoch, the leader is unique.

A node that hasn’t heard from the leader for some timeout may start a vote with a new epoch number greater than any previous one. If two leaders in two epochs conflict, the higher epoch prevails. Before appending the next entry, a leader collects votes from a quorum (typically, but not always, a majority); a node votes yes only if it is not aware of any leader with a higher epoch.

So there are two rounds of voting: one to choose a leader, one on each proposal. Their quorums must overlap: if a proposal vote succeeds, at least one voter also took part in the most recent successful election. If the proposal vote reveals no higher epoch, the leader can safely append. This looks superficially like 2PC, but in consensus any node can start an election and only a quorum must respond, whereas in 2PC only the coordinator requests votes and it needs a yes from every participant.

This structure is common to Raft, Multi-Paxos, Viewstamped Replication and Zab, and every new entry is synchronously replicated to a quorum before the write is confirmed to the client, so it won’t be lost if the leader fails.

The new captain must know the old captain’s orders

A ship’s captain falls ill. The officer who takes over must first read the log book, or she may give an order that cancels one already given. Algorithms differ in how they use that. Raft lets a node become leader only if its log is at least as up to date as a majority’s: voters with newer logs say no. What the book says

The devil is in the details. When the old leader fails and a new one is elected, the algorithm must ensure that the new leader honors any log entries the old leader had already appended. Raft allows a node to become the new leader only if its log is at least as up-to-date as those of a majority of its followers. Paxos allows any node to become the new leader, but requires it to bring its log up-to-date with other nodes before it can start appending new entries of its own.

Consistency versus availability in leader election. To strictly guarantee the shared-log properties, the new leader must be up-to-date with any confirmed entries before it processes any writes or linearizable reads. A leader with stale data might write new values to entries the old leader had already written, violating the append-only property.

You might weaken this to recover faster, or to recover at all: Kafka offers an option to enable unclean leader election, which allows any replica to become leader even if it is not up-to-date; and with asynchronous replication no follower is guaranteed to be up-to-date when the leader fails. That may improve performance and availability, but you are on thin ice: the theory of consensus no longer applies, and the problems of Chapter 9 can easily cause data loss or corruption.

Another subtlety is how algorithms handle entries the old leader had proposed but whose vote had not yet completed; the chapter’s references discuss the details.

Single-leader replication done right, at a price

Zanele runs a five-node consensus cluster. It has survived crashed machines, paused processes and a datacenter fire drill without losing one committed write, and without ever having two leaders. That is the prize: consensus is single-leader replication done right, with automatic failover that is actually safe.

The bill comes in three parts. A strict majority must be up: three nodes tolerate one failure, five tolerate two. Every operation talks to a quorum, so adding nodes doesn’t add throughput, it makes every decision slower, and a partitioned minority is simply blocked. Failure detection uses timeouts, which are hard to tune when delays vary: too long and recovery drags, too short and the cluster spends its time electing leaders. And one consistently bad link can make leadership bounce between two nodes forever, which Raft’s pre-vote phase was added to stop.

What the book says

Although they are complex and subtle, consensus algorithms are a huge breakthrough for distributed systems. Consensus is essentially single-leader replication done right, with automatic failover on leader failure, ensuring that no committed data is lost and split brain is not possible, even in the face of all the problems of Chapter 9. Any system that provides automatic failover but does not use a proven consensus algorithm is likely to be unsafe; using a proven algorithm is not a guarantee of correctness of the whole system, but it’s a good start.

The benefits come at a cost. Consensus systems always require a strict majority to operate: three nodes to tolerate one failure, or five nodes to tolerate two. Every operation requires communication with a quorum, so you can’t increase throughput by adding more nodes (in fact, every node you add makes the algorithm slower). If a network partition cuts off some nodes, only the majority portion of the network can make progress, and the other nodes are blocked.

Consensus systems generally rely on timeouts to detect failed nodes. With highly variable network delays, especially across geographic regions, tuning them is difficult: if they are too large, recovering from a failure takes a long time; if they are too small, lots of unnecessary leader elections can occur, and the system can spend more time choosing leaders than doing useful work.

Raft has been shown to have unpleasant edge cases: if the network works correctly except for one consistently unreliable link, leadership can continually bounce between two nodes, or the current leader is continually forced to resign, so the system effectively never makes progress. The original Raft algorithm was extended with a pre-vote phase to address this. Paxos also depends on leaders, which can cause similar issues; Egalitarian Paxos (EPaxos) and its derivatives use a leaderless protocol that is more robust against poorly performing nodes or network connections.

Somebody has to decide which worker serves which shard, someone else has to take over when that decider dies, and when a fourth machine arrives some shards should move to it. Every one of those is a small agreement, and getting any of them wrong means two workers serving one shard, or a shard nobody serves.

With a coordination service, it is a recipe. Each worker registers an ephemeral node, so its entry disappears if it dies. The workers run a leader election through the service, and the leader watches the list of workers and rewrites the assignment table with atomic operations. The voting happens on just three or five coordination nodes, no matter how many workers there are. The data is small and slow-changing: an entry like shard 7 → 10.1.1.23 may stay true for hours. Data that changes thousands of times a second belongs elsewhere.

Try it: press Add a worker and watch shards rebalance. Tap a worker to kill it: its session times out and its shards move. Press Kill the leader and see who takes over. Then press Store request counts here to see why fast-changing data is the wrong job for it.

What the book says

A coordination service is useful if you have several instances of a process or service and one of them needs to be chosen as leader or primary; if the leader fails, another node should take over. This is necessary for single-leader databases, and also appropriate for job schedulers and similar stateful systems.

Another use case: a sharded resource (database, message streams, file storage, distributed actor system, etc.) where you decide which shard to assign to which node. As new nodes join, some shards move to them to rebalance the load; as nodes are removed or fail, other nodes take over their work. This can be achieved by judicious use of atomic operations, ephemeral nodes and notifications, so the application recovers from faults without human intervention. It’s not easy, despite libraries such as Apache Curator, but it is much better than implementing consensus from scratch.

A dedicated coordination service can run on a fixed set of nodes (usually three or five), regardless of how many nodes rely on it. With thousands of shards, running consensus over thousands of nodes would be terribly inefficient; it’s much better to outsource the consensus to a small number of nodes.

The data is normally slow-changing: information like the fact that the node at IP address 10.1.1.23 is the leader for shard 7, with assignments changing on a timescale of minutes or hours. Coordination services are not intended for data that may change thousands of times per second; use a conventional database, or tools like Apache BookKeeper to replicate the fast-changing internal state of a service.

Finding the search service without asking a committee

Sione’s checkout service needs the search service, whose virtual machines come and go all day, so nobody knows their IP addresses in advance. Each search instance registers its address in a service registry when it starts. A coordination service makes a handy registry: its failure detection drops dead instances, and its notifications tell clients what changed.

But looking up an address doesn’t need linearizability, and if discovery stops, everything stops. So clients cache the answer, refresh it after a TTL, and only bypass the cache when a connection fails. ZooKeeper goes one step further with observers: replicas that receive the log but don’t vote. Their reads may be stale, but they stay available when the network is cut, and they add read capacity without slowing down the votes.

What the book says

ZooKeeper, etcd and Consul are also often used for service discovery: finding out which IP address to connect to in order to reach a particular service. In cloud environments, where virtual machines continually come and go, you often don’t know IP addresses ahead of time; services register their network endpoints in a service registry when they start up, where other services can find them.

Using a coordination service is convenient, since its failure detection and change notification features help clients keep track of instances as they come and go; and if you already use it for leases, locking or leader election, it already knows which node should receive requests.

However, using consensus for service discovery is often overkill. It generally doesn’t require linearizability, and it’s more important that it is highly available and fast, since without it everything would grind to a halt. It’s usually preferable to cache service discovery information: clients unable to connect can bypass the cache, retry with the latest value and update the cache; caches may also be refreshed periodically using a time-to-live (TTL). DNS-based service discovery uses multiple layers of caching to achieve good performance and availability.

To support this use case, ZooKeeper supports observers: replicas that receive the log and maintain a copy of the data, but do not participate in the voting. Reads from an observer are not linearizable as they might be stale, but they remain available even if the network is interrupted, and they increase the read throughput the system can support.

Beyond the book · Raft · leader election

Five referees, one whistle, and a timer that won’t sit still

Five referees run a long match in shifts. The one on duty blows a short whistle every few seconds to say “still here”. If the whistle goes quiet, any referee may stand up and ask the others for their vote. If all five have identical stopwatches, all five stand up at the same moment, each votes for themselves, and nobody gets a majority. Then it happens again. And again.

Raft fixes this with randomized election timeouts: each server waits a random time (the paper suggests something like 150–300 ms) before starting an election, so usually one server gets in first and wins before the others wake up. A candidate bumps its term, votes for itself and sends RequestVote(term, candidateId, lastLogIndex, lastLogTerm). A server grants one vote per term, remembered on disk as votedFor, and only to a candidate whose log is at least as up to date as its own: the last entry’s term decides, and the index breaks ties. So a longer log full of old terms loses to a shorter one that has seen a newer term.

Try it: press Crash the leader and watch the timer rings run down, the requests fly and a majority elect a new leader. Switch to Same timeouts and crash again: every election splits, forever. Then pick Mixed logs, crash the leader, and tap S3 to make its timer fire first: its log is the longest, but the servers that saw term 3 refuse it. Tap a crashed server to restart it with its saved term and vote.

Where this comes from

Raft servers are followers, candidates or leaders. Time is divided into terms, numbered with consecutive integers; each term begins with an election, and at most one leader can win in a given term. Every message carries the sender’s term. A server that sees a larger term updates its own and reverts to follower; a request with a stale term is rejected.

A follower that receives no heartbeat (an AppendEntries message with no entries) for an election timeout increments its term, becomes a candidate, votes for itself and sends RequestVote to every other server. It wins with votes from a majority, loses if it hears from a leader with a term at least as large, and times out and tries again in a new term if the vote is split. Each server votes for at most one candidate per term, first come, first served, and stores currentTerm and votedFor on stable storage before replying.

The election restriction: a voter denies its vote if its own log is more up to date than the candidate’s. Logs are compared by the term of their last entries; if those are equal, the longer log is more up to date. Because a committed entry is on a majority, and a winner needs votes from a majority, every possible winner holds every committed entry. This is the rule the book summarizes on p. 435.

Split votes are made rare by choosing each election timeout at random from a fixed interval, for example 150–300 ms, and the timer is restarted only when a server hears from a current leader or grants a vote. This machine simplifies: heartbeat replies and log replication are not drawn, the network delay is a fixed 20–40 ms, and one simulated millisecond takes several real ones.

Beyond the book · Raft · log replication and repair

“My page 9 says chapter 6.” “Then go back a page.”

Zanele dictates a book to a copyist over a crackly phone line. Before each new page, Zanele says which page came just before it and what chapter that page was in. If the copyist’s previous page doesn’t match, the copyist says so, and Zanele steps back one page and tries again, until they find the last page they agree on. From there, Zanele reads every page forward, and the copyist tears out any of their own pages that disagree.

That is Raft’s AppendEntries. Each call carries prevLogIndex and prevLogTerm, the entry just before the new ones. A follower that has no entry there with that term rejects it; the leader then decrements its nextIndex for that follower and retries. Once they match, the follower deletes any entry that conflicts with a new one (same index, different term) and everything after it, and appends the leader’s entries. Because of this check, two logs that agree on one entry’s index and term agree on every entry before it too: the Log Matching Property.

Try it: pick a follower, a to f (the six cases in the Raft paper’s Figure 7), and press Send AppendEntries one call at a time, following the lit lines in the code. Press Repair to the end to finish. In c and d the follower has extra entries: notice they survive a matching call, until you press Client write and a new entry conflicts with them.

Where this comes from

The leader appends each client command to its log, sends it to the followers with AppendEntries, and applies it once it is committed. Each entry stores a command and the term in which the leader received it; entries are identified by their index.

AppendEntries carries the leader’s term, prevLogIndex and prevLogTerm, the new entries, and leaderCommit. The receiver replies false if the term is stale or if its log has no entry at prevLogIndex whose term matches prevLogTerm. If an existing entry conflicts with a new one (same index, different terms), it deletes that entry and all that follow, then appends any new entries not already in its log. If leaderCommit is larger than its commitIndex, it sets commitIndex to the smaller of leaderCommit and the index of the last new entry.

The leader keeps a nextIndex for each follower, initialized to just after its own last entry when it takes office, and a matchIndex, the highest entry known to be replicated there. After a rejection it decrements nextIndex and retries; after a success it updates both. The leader never deletes or overwrites its own entries.

Figure 7 of the paper shows a leader at the start of term 8 and six followers (a–f) that could exist: some miss entries, some hold extra uncommitted entries, some both. The paper notes an optional optimization, where the follower reports the conflicting term and its first index so the leader can skip a whole term per round trip; this machine uses the basic one-step-back rule. It is the mechanism behind the book’s remark that the new leader must honour entries the old leader had already appended (p. 435).

Beyond the book · Raft · when is an entry committed?

On a majority isn’t the same as decided

Ingrid’s club votes by show of hands, but the minutes only become official once the current chair has passed a motion of their own. A motion left over from an old chair may have most hands up today, yet a rival chair from an even older session, holding a different motion, could still win a later election and replace it. Ingrid only announces “it’s decided” once a motion from this session has passed, and that carries every older motion before it.

Raft’s leader marks entry N committed when it is stored on a majority and log[N].term == currentTerm. Entries from earlier terms are never committed by counting copies; they become committed indirectly, when a later entry from the current term commits, thanks to the Log Matching Property. The paper’s Figure 8 shows why: an old-term entry on three of five servers can still be overwritten by a server elected with a newer last term. That is also why a new leader appends a no-op entry at the start of its term.

Try it: in Count copies (unsafe), press Play the story: S1 tells the client “committed” for an entry on a majority, and two steps later S5 overwrites it. Switch to Raft: crash early and play: the same overwrite happens, but no client was ever told OK. Then Raft: crash late: S1’s term-4 entry reaches a majority first, which commits both, and S5 can no longer win.

Where this comes from

The leader may set commitIndex to N if there is an N greater than commitIndex such that a majority of matchIndex values are at least N and the entry at N has the current term. Committing that entry also commits every entry before it. Each server applies entries up to commitIndex to its state machine, in log order.

Figure 8 in the paper: (a) S1 leads term 2 and replicates index 2 to S2 only. (b) S1 crashes; S5 wins term 3 with votes from S3, S4 and itself, and accepts a different entry at index 2. (c) S5 crashes; S1 restarts, wins term 4 and replicates its term-2 entry to S3, so it is on a majority, but not committed. (d) If S1 now crashes, S5 can win term 5 (with votes from S2, S3 and S4) and overwrite index 2 everywhere. (e) If instead S1 first replicates an entry from term 4 to a majority, that entry and everything before it are committed, and S5 can’t win any more.

A new leader doesn’t know which of its entries are committed. Raft has each leader commit a blank no-op entry at the start of its term; this is also what lets it serve read-only requests safely (see the reads scene that follows).

The chapter mentions this subtlety without detail: how algorithms deal with entries proposed by an old leader before it failed, for which the vote on appending had not completed (p. 436). This machine follows the paper’s scenario, with values added to the entries for concreteness.

Beyond the book · Raft · linearizable reads

The leader who doesn’t know it was replaced

Ingrid asks the node she thinks is the leader for the value of x. What she doesn’t know: a minute ago the network split, the other side elected a new leader in a higher term, and that leader has already committed x=2. The old leader is still sitting there with x=1, still believing it leads. If it simply answers from memory, Ingrid gets an old value after a newer write completed: not linearizable.

Raft offers four ways to read, and they differ in what they pay to be sure. A local read pays nothing and can be stale. A log read appends the read to the log like a write, so it only succeeds where a majority agrees, at the cost of a log write. ReadIndex skips the log: note the commitIndex, prove you are still leader with one heartbeat round to a majority, then wait until that much of the log is applied. A lease read skips even the heartbeat, trusting that no rival can be elected before a timer runs out, which is only true if clocks run at about the right speed.

Try it: pick a read method, then press Run the scenario: the network splits, the majority side elects n3 and commits x=2, and Ingrid reads from n1. Compare Local read with ReadIndex. In Lease read, run it once, then switch n1’s clock to half speed and run it again.

Where this comes from

Raft can serve a read-only query without writing to the log, but a leader must take two precautions. First, it must have the latest committed entries; at the start of its term it may not know which are committed, so each leader commits a blank no-op entry at the start of its term. Second, it must check that it has not been deposed before answering, by exchanging heartbeats with a majority of the cluster.

Ongaro’s thesis spells this out as ReadIndex: record the current commit index as the read index; confirm leadership with a round of heartbeats acknowledged by a majority; wait until the state machine has applied at least up to the read index; then answer. This costs one round of messages but no disk write, and followers can use the same mechanism by asking the leader for its read index.

The thesis also describes leases: after a majority acknowledges a heartbeat, the leader assumes no other leader can be elected for roughly an election timeout, adjusted for a bound on clock drift, and answers reads locally until then. This avoids messages entirely but relies on timing, so a clock that runs too slowly, or drift beyond the bound, can produce stale reads.

The chapter makes the same point in general terms: if you want linearizable reads in a consensus-based database, they too have to be confirmed by a quorum, as etcd does (p. 436). The timings in this machine are illustrative.

Photograph the ledger, then shred the old pages

Noor’s shop keeps a ledger of every change to its prices. After a year the ledger is thousands of pages long, but what anyone needs is the current price list. So she copies today’s prices onto one card, writes on it “this is everything up to page 7,” and throws pages 1 to 7 away. When a new clerk starts, she hands over the card plus the pages written since, not the whole year.

A Raft log grows forever unless it is compacted. Each server, on its own schedule, writes a snapshot of its state machine together with lastIncludedIndex and lastIncludedTerm, the position and term of the last entry the snapshot covers, and discards the log up to there. The catch comes when a follower is so far behind that the entries it needs next are already gone from the leader’s log. Then the leader sends InstallSnapshot instead of AppendEntries, and carries on with normal replication from the snapshot’s end.

Try it: press Client write a few times while n3 is down, then Take snapshot, and finally Restart n3: the leader no longer has entry 3, so it ships the snapshot. Switch to No compaction and restart n3 again: every entry is replayed, and the leader’s log keeps growing.

Where this comes from

In Raft each server snapshots independently, covering only committed entries in its log. A snapshot holds the state machine’s current state plus metadata: the last included index and the last included term, the index and term of the last entry the snapshot replaces. The term is kept so that the AppendEntries consistency check still works for the first entry after the snapshot. Once the snapshot is written, the server may delete every log entry up to the last included index, along with any earlier snapshot.

When the leader has already discarded the next entry it needs to send to a follower, which happens with a very slow follower or a new server joining the cluster, it sends an InstallSnapshot RPC carrying the term, the leader’s ID, the last included index and term, and the snapshot data (in chunks).

A follower that receives a snapshot covering information not in its log discards its entire log and resets its state machine from the snapshot. If the snapshot describes a prefix of its log (it has an entry with the same index and term as the last included one), it keeps the entries that follow and deletes only the covered ones.

The paper notes the trade-offs this machine glosses over: how often to snapshot (too often wastes disk bandwidth, too rarely wastes storage and slows replay after a restart) and writing a snapshot without stalling normal operation, for example with copy-on-write. Entry sizes here are toy numbers.

Growing from three voters to five without two majorities

Rafael’s cluster has three servers, A, B and C, and he wants five. The obvious way is to send every server the new list at once. But the message reaches some servers before others. For a moment, A and B still count votes out of three, so two of them are a majority, while C, D and E count out of five, so three of them are a majority. Those two groups share nobody. Cut the network between them and each side can elect its own leader and commit its own writes.

Raft prevents that in one of two ways. Joint consensus goes through a transitional configuration, Cold,new, in which every election and every commit needs a majority of the old servers and a majority of the new ones; only once that is committed does the leader switch to Cnew. Ongaro’s thesis adds a simpler rule: change one server at a time. Any majority of three and any majority of four must share a server, so two leaders can never both commit.

Try it: in each mode press Play the story (or Step): the leader starts the change, the network splits between A, B and C, D, E, and both sides try to commit a write. Watch Switch at once end with two committed values. In Joint consensus and One at a time the same split commits only one. The checker under the servers searches every pair of majorities for one with no server in common.

Where this comes from

Raft servers always use the latest configuration in their log, whether or not that entry is committed. Because it is impossible to switch every server atomically, any approach that moves directly from the old configuration to the new one is unsafe: for a time, a majority of the old configuration and a majority of the new one could elect two different leaders for the same term, or, as here, both commit.

The Raft paper uses joint consensus. The leader stores Cold,new as a log entry; while it is in force, log entries go to servers in both configurations, any server from either may be leader, and agreement for elections and for committing entries requires separate majorities from the old and the new configuration. Once Cold,new is committed, the leader appends Cnew; when that commits, servers not in it can be shut down. The paper also adds new servers as non-voting members until they have caught up, and has a leader that is not in Cnew step down once Cnew commits.

Ongaro’s thesis recommends a simpler scheme: add or remove a single server at a time, and wait until each change is committed before starting the next. Since a majority of the old and a majority of the new configuration then always overlap, no extra rules are needed. A later correction to that algorithm requires a new leader to commit an entry in its own term before it starts a change.

The chapter mentions why this matters: consensus algorithms assume a fixed set of voters, and have been extended with reconfiguration so you can add nodes, remove nodes, or migrate a cluster by adding the new nodes first (p. 436). Server names and the partition timing are illustrative.

Beyond the book · Paxos · single-decree Paxos

Two rounds, and the rule that keeps a chosen value chosen

Ingrid and Rafael both want the five-person committee to fix the club’s meeting day. Ingrid wants Tuesday, Rafael wants Friday. Letters get lost, either of them may give up halfway, and nobody is in charge. Paxos settles it with two rounds of letters. The people with an opinion are proposers. The committee members who vote are acceptors. Each acceptor keeps three numbers on paper: the highest ballot it has promised to respect, and the ballot and value it last accepted.

Phase 1: a proposer picks a ballot number nobody else uses (Ingrid odd numbers, Rafael even ones) and sends Prepare(n). An acceptor that hasn’t promised a higher ballot promises to ignore everything lower, and replies with whatever it has already accepted. Phase 2: with promises from a majority, the proposer sends Accept(n, v). Here is the rule that makes Paxos safe: if any promise reported an accepted value, v must be the one with the highest ballot. Only if none did may the proposer use its own. An acceptor accepts unless it has promised a higher ballot. Once a majority has accepted the same ballot, the value is chosen. Any later proposer’s majority overlaps that one, hears about the value, and has to propose it again.

Safety never depends on timing, but progress does. Two proposers can keep cutting each other off with ever-higher ballots, and nothing is ever chosen. That’s the FLP result showing up in practice. The fix is to let one distinguished proposer (a leader) do the proposing, and to make the others back off for a random while.

Try it: in Clean run, press Step four times and follow the highlighted lines. Tap two acceptors to crash them and try again: three promises are still a majority, but with three crashed, Ingrid is stuck. In Late proposer, press Play with the adopt rule on, then switch it off and play again: two different days get chosen. In Dueling proposers, play with backoff off (no progress), then on.

Where this comes from

Paxos (Lamport, Paxos Made Simple) separates three roles: proposers, acceptors and learners. Proposals are numbered, and the numbers must be totally ordered and unique per proposer, for example a round number paired with the proposer’s ID. Phase 1a sends prepare(n). In phase 1b an acceptor promises never again to accept a proposal numbered below n, and returns the highest-numbered proposal it has accepted, if any. Phase 2a sends accept(n, v) to acceptors once a majority has promised. Phase 2b: an acceptor accepts unless it has already promised a higher number. A value is chosen when a majority of acceptors has accepted it.

The safety argument rests on one invariant: if a proposal with value v is chosen, every higher-numbered proposal issued by any proposer has value v. The proposer enforces it by adopting the value of the highest-numbered accepted proposal reported in phase 1. Because any two majorities intersect, at least one acceptor in the new majority has seen the chosen value. Acceptors must record their promise and acceptance in stable storage before replying, so a restarted acceptor keeps its word.

Progress isn’t guaranteed. Two proposers can each complete phase 1 with ever-higher numbers so that neither ever completes phase 2. The paper’s remedy is to select a distinguished proposer, the only one that tries to issue proposals; electing one reliably needs randomness or timeouts. In this machine, that happens through random backoff.

The chapter says Paxos provides single-value consensus (p. 433), and that it lets any node become the new leader but requires that leader to bring its log up to date first (p. 435–436). Phase 1, which collects already-accepted values, is that catching up. Simplifications here: learners are folded into the proposers, and ballots are small integers.

Prepare once, then one round trip per entry

Leila’s ledger service needs a log, not a single value. The obvious approach: treat every log slot as its own Paxos instance. It works, but each entry then pays for both phases, which is two round trips to a majority. Most of that is wasted, because the same node keeps proposing entry after entry.

Multi-Paxos keeps a stable leader. When it takes over, it runs phase 1 once, for every slot from s onward: one Prepare(b) covers them all. The acceptors reply with anything they have already accepted in those slots. After that, each client command needs only phase 2, Accept(b, slot, cmd), which is one round trip. The hard part is a leader change. The new leader’s phase 1 may turn up a value the old leader got onto a majority without announcing it, which it must propose again. It may also find a hole, a slot nobody accepted anything in, which it fills with a no-op so the slots after it can be applied in order.

Try it: in Basic Paxos per slot, press Client command three times and watch the stats: two round trips each. Switch to Multi-Paxos: the first command pays for phase 1, and every later one is a single round trip. Then press Leader crashes mid-flight: n1 dies with one entry on a majority and another on only itself. Watch n2 recover the first and turn the second into a no-op.

Where this comes from

In Paxos Made Simple, Lamport builds a replicated state machine by running a separate Paxos instance for each command slot. A single leader acts as distinguished proposer for every instance. A newly chosen leader runs phase 1 for infinitely many instances at once, with one short message, and acceptors reply with the accepted proposals they hold. From then on, only phase 2 is needed per command, as long as the leader stays the leader.

When the new leader learns of a value accepted in some instance, it must propose that value again. When an earlier instance has no value but a later one does, there is a gap. The leader fills it with a special command that leaves the state unchanged, so the following commands can be executed in order.

The chapter notes that in practice most systems using Paxos actually use this extension, Multi-Paxos, which provides a shared log (p. 433). Like Raft, Viewstamped Replication and Zab, it elects a leader by a quorum and then needs another quorum vote for each entry (p. 435). Where Raft only lets an up-to-date node win the election, a Paxos leader catches up during phase 1 (p. 435–436).

Simplifications here: message counts assume five acceptors with the leader among them, and recovery runs as one scripted story rather than with timers.

Beyond the book · Paxos · flexible quorums

Only the election and the replication quorums must meet

Every Paxos vote so far used a majority. But look at what the overlap is actually for. A new leader’s phase 1 must meet every phase-2 quorum that might already have chosen a value, so that it hears about that value. Two phase-2 quorums never need to meet: within one ballot there is only one leader, and it doesn’t contradict itself.

So the real requirement is |Q1| + |Q2| > n, where Q1 is the phase-1 (election) quorum and Q2 the phase-2 (replication) quorum. That opens a trade-off. Make Q2 small and every write waits for fewer, nearer acknowledgements. In return Q1 must be large, which makes elections, the rare event, slower, and survivable only if few nodes are down.

Try it: keep n = 5 with majorities (3 and 3) and press Worst case: the quorums still share a node. Now set n = 6 and |Q2| = 2. With |Q1| = 4, the worst case leaves them disjoint, and the new leader never hears about x=7. Raise |Q1| to 5 and try again. Press Random quorums a few times to watch the overlap move around.

Where this comes from

Howard, Malkhi and Spiegelman’s Flexible Paxos observes that Paxos needs majorities in both phases only for simplicity. For safety it suffices that every phase-1 quorum intersects every phase-2 quorum. Phase-2 quorums need not intersect each other, because in each ballot only one proposer issues phase-2 messages.

This lets a deployment use small replication quorums, so each command waits for fewer acknowledgements, as long as leader election uses correspondingly larger quorums. Since leader changes are rare compared with commands, that is often a good trade. The cost is availability during elections: if more than n − |Q1| nodes are down, no new leader can be elected.

The chapter cites this paper where it says a leader collects votes from a quorum of nodes, typically, but not always, a majority, and that the election and proposal quorums must overlap (p. 435).

Simplifications here: a single previously chosen value stands for the whole log, and the round-trip times are toy numbers.

Three phases and 3f + 1 replicas, because some of them lie

Every algorithm so far assumed nodes crash but never lie. Mei’s payment ledger runs at four companies that don’t fully trust each other. Any one of them could run buggy or malicious software that tells different replicas different things. To tolerate f such Byzantine replicas, PBFT uses n = 3f + 1 of them, with one acting as primary for the current view.

A client sends its request to the primary, which assigns a sequence number and multicasts a pre-prepare. Each backup that accepts it multicasts a prepare. A replica is prepared once it holds the pre-prepare and 2f matching prepares from different backups. Since honest replicas never prepare two requests for the same slot, a lying primary can’t get two different requests prepared. Prepared replicas then multicast a commit. With 2f + 1 matching commits, a replica executes the request and replies. The client trusts a result once f + 1 replicas agree on it, because at least one of those is honest. If the primary stalls or equivocates, the backups’ timers expire and they move to the next view, with a new primary.

Try it: in All honest, press Step through request, pre-prepare, prepare, commit and reply. In Lying backups, f backups send forged prepares, commits and replies, and are simply outvoted. In Lying primary, the primary sends different requests to different backups: nothing gets prepared, timers expire, and view 1 finishes the job. Drag f to 2 for seven replicas. Why 3f + 1 shows the counting argument.

Where this comes from

Castro and Liskov’s Practical Byzantine Fault Tolerance (PBFT) is a state machine replication algorithm that tolerates up to f faulty replicas out of 3f + 1. That is the minimum: the system must make progress after hearing from n − f replicas, since f may never answer, and among those n − f, the f that do answer may be lying. Quorums of 2f + 1 among 3f + 1 replicas intersect in at least f + 1 replicas, so the intersection always contains an honest one.

Normal operation has three phases. The primary of view v assigns sequence number n to a request and multicasts PRE-PREPARE. Each backup that accepts it multicasts PREPARE. A replica is prepared when it has logged the request, the pre-prepare, and 2f matching prepares from different backups. Pre-prepare and prepare together totally order requests within a view. Prepared replicas multicast COMMIT, and a replica executes once it has 2f + 1 matching commits, including its own; the commit phase makes the order hold across view changes. The client waits for f + 1 replies with the same result.

If a backup’s timer expires while it waits for a request to execute, it multicasts VIEW-CHANGE for view v + 1, carrying proof of what it has prepared. The primary of view v + 1, replica (v + 1) mod n, multicasts NEW-VIEW once it holds 2f + 1 of them, and re-proposes prepared requests. Messages are authenticated, so a faulty replica can’t forge another replica’s messages or a client’s request.

The chapter says Byzantine fault-tolerant algorithms commonly assume fewer than one-third of nodes are faulty, are used in blockchains, and are beyond the book’s scope (p. 426). Simplifications here: one request, no checkpoints, and a view change without the prepared certificates.

Problems that are secretly the same problem

From the book’s summary: solve one fault-tolerantly and you can build all the others.

Linearizable CAS

The register decides, atomically, whether to take the new value, based on whether its current value equals the expected one.

Locks and leases

Several clients grab for the same lock at once; the lock decides which one got it.

Uniqueness constraints

Several transactions try to create records with the same key; the constraint decides which one succeeds and which one fails.

Shared logs

Several nodes want to append at once; the log decides the order. Built with total order broadcast.

Atomic commit

Every database in a distributed transaction must decide the same way: commit, or abort.

Linearizable fetch-and-add

Decides the order in which nodes bump a counter, which makes an ID generator. It only solves consensus between two nodes.

The seesaws from this chapter

Strong consistency is bought, not found. Here is the price list.

Strong consistency

Behaves like a single node, so the app developer stops worrying about replicas

vs

Eventual consistency

Faster, and survives faults that stop a strongly consistent system, but the app must handle stale reads and conflicts

Linearizable reads and writes

Never stale, and no races between channels, but every operation pays for the network’s uncertainty

vs

Weaker consistency

Much lower latency, all the time, not only during faults

CP during a partition

Disconnected replicas wait or return errors

vs

AP during a partition

Every replica keeps serving, and its answers may not be linearizable

A single-node ID generator

IDs in true order, compact, but a single point of failure, a bottleneck, and far away for other regions

vs

Sharded, block, UUID or clock IDs

Made anywhere without coordination, but their order is a guess

Lamport and hybrid logical clocks

A few bytes, totally ordered, and consistent with causality

vs

Vector clocks

Can also tell when two writes were concurrent, at one counter per node

Consensus

Automatic failover with no split brain and no lost committed writes

vs

Manual failover

Simpler, but the system stops until a human reacts

More voting nodes

Survive more failures: five nodes tolerate two

vs

Fewer voting nodes

Every node added makes each decision slower, not faster

Short failure timeouts

Fast recovery after a real crash

vs

Long failure timeouts

Fewer needless elections when the network is slow

The book’s conclusion: consensus algorithms such as Raft and Paxos are single-leader replication with built-in, automatic leader election and failover. Every write, and every linearizable read, is confirmed by a quorum, which is expensive, especially across regions, but unavoidable if you want strong consistency and fault tolerance together. If you need something that reduces to consensus, use a coordination service rather than inventing your own. And when you don’t need strong consistency, leaderless or multi-leader replication with logical clocks may serve you better.

Words to know

Grown-up words, in plain language.

eventual consistency
Replicas may disagree for a while; the application sees that and copes with stale reads and conflicts.
strong consistency
The system hides its replicas and behaves as if it were one node.
linearizability
Acting as if there is one copy and every operation on it is atomic: once anyone has seen a new value, nobody sees an older one.
recency guarantee
If one operation finishes before another starts, the later one sees a state at least as new.
register
The theory word for one readable, writable object: a key, a row, a document.
concurrent operations
Operations whose request-to-response intervals overlap, so either could take effect first.
compare-and-set (CAS)
“Set it to this, but only if it is still that”, done atomically, or fail with an error.
serializability
Transactions behave as if run one at a time in some order, which need not be the real-time order.
strict serializability
Serializable and linearizable at once; also called strong one-copy serializability.
split brain
Two nodes both believe they are the leader and accept conflicting writes.
lease
A lock with an expiry time, so a holder that dies doesn’t block everyone forever.
network partition
The network splits into groups that can’t reach each other, while each group still works.
CAP theorem
With a partition, a linearizable system must give up availability on the cut-off side. Narrow, and mostly of historical interest.
PACELC
Under a Partition, choose Availability or Consistency; Else, choose Latency or Consistency.
read repair
A reader noticing a stale replica and writing the newer value back to it.
fetch-and-add
Atomically add to a counter and return its old value: the heart of an ID generator.
UUID
A 128-bit ID any node can make alone; version 4 is random, version 7 starts with a timestamp.
logical clock
An algorithm that counts events instead of seconds; it tells order, not time.
causality
“A happened before B” because B could have known about A. A cause must get the smaller timestamp.
Lamport timestamp
A pair (counter, node ID); counters jump to the largest one seen, so causes sort before effects.
hybrid logical clock
A clock that counts real microseconds but also jumps forward to match larger timestamps it sees, and never runs backward.
vector clock
One counter per node, carried with each write, so concurrent writes can be detected.
timestamp oracle
A single, replicated node that hands out increasing IDs, often in persisted batches.
consensus
Getting several nodes to agree on one value, and never change their minds, even when some fail.
Byzantine fault
A node that doesn’t follow the protocol, for example by sending contradictory messages.
FLP result
A proof that no deterministic algorithm without clocks or timeouts can guarantee consensus terminates if a node may crash.
safety vs liveness
Safety: nothing bad ever happens (agreement). Liveness: something good eventually happens (termination).
total order broadcast
Delivering messages to every node in the same order; how a shared log is built. Also atomic broadcast.
consensus number
How many proposers an operation can solve consensus for: 2 for fetch-and-add, infinity for CAS and shared logs.
atomic commitment
All participants of a distributed transaction commit, or all abort.
state machine replication
Replicas apply the same log, in the same order, with deterministic logic, and so end up identical.
epoch number
The election round: ballot (Paxos), view (Viewstamped Replication), term (Raft). Higher wins.
quorum
Enough voters, typically a majority, that any two quorums share at least one node.
unclean leader election
Letting a replica that isn’t up to date become leader, trading consistency for availability.
pre-vote
A Raft extension: check you could win before starting an election, so one flaky link can’t keep deposing leaders.
coordination service
A small consensus cluster (ZooKeeper, etcd, Consul) offering locks, leases, fencing, failure detection and notifications.
fencing token
An ever-increasing number handed out with a lease, so a stale holder’s writes can be rejected.
ephemeral node
A ZooKeeper entry that disappears when its client’s session times out.
observer
A ZooKeeper replica that receives the log but doesn’t vote: stale reads, but always available.
term (Raft)
Raft’s epoch number. Every message carries one; a node that sees a higher term steps down to follower.
RequestVote
Raft’s election message. A node grants one vote per term, and only to a candidate whose log is at least as up to date as its own.
AppendEntries
Raft’s replication message and heartbeat. It carries the previous entry’s index and term, so a follower can spot a gap or conflict.
nextIndex / matchIndex
Per follower, the leader’s guess of where to send next, and the highest entry known to match.
commit index
The highest log entry known to be safely stored on a majority; only entries up to it are applied.
ReadIndex
A linearizable read without a log write: note the commit index, confirm leadership with a heartbeat round, wait until applied.
snapshot
A saved copy of the state machine that lets a node throw away the log prefix it covers.
joint consensus
A transitional configuration where decisions need majorities of both the old and the new member sets.
prepare / promise
Paxos phase 1: a proposer asks acceptors to ignore lower ballots and report any value they already accepted.
accept / accepted
Paxos phase 2: acceptors store the proposed value unless they promised a higher ballot. A majority of accepts chooses it.
flexible quorums
Paxos only needs every phase-1 quorum to overlap every phase-2 quorum, not majorities everywhere.
PBFT
Practical Byzantine Fault Tolerance: 3f+1 replicas, quorums of 2f+1, three phases, tolerating f liars.
