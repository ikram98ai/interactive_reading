Data Models and Query Languages

The same facts can be written down in very different shapes: neat tables, one nested document, or a web of arrows. The shape you pick decides which questions are easy to ask.

Warm-up · query languages

Tell the kitchen what you want, not how to cook it

Imagine a marine biologist with a notebook of ocean sightings. The question: how many sharks did I see each month?

One way is to write out every step yourself: “start at row one, look at it, add it up if it's a shark, go to row two…” That's an algorithm, and it's what ordinary programming languages make you do.

A declarative query language like SQL lets you describe the pattern you want instead. The database's query optimizer then picks the clever way: use an index, skip rows, split the work across CPU cores.

Try it: run the hand-written loop, then the declarative query. Now slide the number of cores up and run both again. Only one of them gets faster.

What the book says

Most applications are built by layering data models: real-world objects → a general-purpose data model (JSON documents, relational tables, graph vertices and edges) → bytes on disk → electrical signals. Each layer hides the complexity below it.

SQL, Cypher, SPARQL and Datalog are declarative: you say what conditions the results must meet and how to transform them (sorted, grouped, aggregated), not how to achieve it. Languages like Python and Java make you write the algorithm.

Because implementation details are hidden, the database can add performance improvements without any change to your queries, and can run a query in parallel across multiple cores and machines.

The chapter's real example: SELECT date_trunc('month', observation_timestamp) AS observation_month, sum(num_animals) FROM observations WHERE family = 'Sharks' GROUP BY observation_month; — expressible in MongoDB's aggregation pipeline too, with $match and $group.

Big idea 1 · relational vs document

Four folders, or one big scrapbook?

A résumé has a name, some jobs, some schools, some ways to contact you. In a relational database you split that across four tables: one row per job, one row per school, all pointing back to the user with a foreign key.

In a document database you keep the whole thing as one piece of JSON, with the jobs and schools nested inside. It looks a lot more like the object in your program — that's why some developers say it reduces the impedance mismatch.

The scrapbook wins when you want the whole profile at once: one read instead of four. It loses when you change one tiny thing, because the whole document usually has to be written out again.

Try it: read the whole profile in both shapes, then change just the headline in both. Watch the two counters swap places.

What the book says

Splitting a document-like structure into several tables is called shredding; it can lead to cumbersome schemas and complicated application code. One-to-many relationships form a tree, which JSON makes explicit.

The JSON representation has better locality: fetching a profile from the relational schema needs multiple queries or a messy multiway join. But the database usually loads the entire document, and rewrites the entire document on update — so keep documents small and avoid frequent small updates.

Locality isn't unique to documents: Google's Spanner can interleave a table's rows inside a parent table, Oracle has multi-table index cluster tables, and Bigtable-style wide-column stores use column families.

ORMs (ActiveRecord, Hibernate) reduce translation boilerplate but can't hide the two models, and make it easy to write the N+1 query problem: one query for N comments, then N more to look up each author.

One-to-many is often “one-to-few”. For a genuinely large number of related items — thousands of comments on a celebrity's post — embedding them all in one document is too unwieldy, and separate tables are better.

Big idea 2 · normalization

Write the city's name once, or on every card?

Five people all live in the same town. You can write the town's name on every profile — or write a meaningless ID on every profile and keep the name in one little table of its own.

Keeping it in one place is called normalizing. IDs never need to change, because they mean nothing to humans. Names do change — and if the name is copied five times, all five copies must be found and updated.

The price of normalizing is that every read needs an extra lookup, called a join, to turn the ID back into something a person can read.

Try it: copy the name everywhere, rename the town, then hit Crash! halfway through. Some cards say the old name and some say the new one. Now do the same with IDs.

What the book says

In the book's example a profile stores region_id: "us:91" instead of the text “Washington, DC”. Advantages of the standardized list: consistent spelling, no ambiguity, easy updating, localization into other languages, and better search (the list can encode that Washington is on the US East Coast).

Normalized data is usually faster to write (one copy) but slower to query (needs joins). Denormalized data is faster to read but more expensive to write, and risks inconsistency if a process crashes halfway. Denormalization is a form of derived data.

Some document databases have no joins at all, so you do them in application code; MongoDB offers $lookup in an aggregation pipeline.

X (formerly Twitter) stores only post IDs and sender IDs in each precomputed timeline, then looks up the content, like count and profile picture when the timeline is read — a join in application code called hydrating the IDs. It's done that way because likes and profile pictures change fast.

Normalization is better for OLTP; analytics often fares better denormalized. Neither is good or bad — they're trade-offs between read cost, write cost and effort.

Big idea 3 · many-to-many

The lost-property book that works both ways

One person works at many companies over their life; one company has many employees. That's a many-to-many relationship, and it doesn't fit inside one self-contained document.

The usual answer is a little book in the middle — an associative table (or join table) — where each line says “person 1 worked at company 2”.

People want to read that book in both directions: “where did Lucy work?” and “who worked at NASA?”. Without a secondary index you have to read every line. With an index on each column, you jump straight to the lines you need.

Try it: ask in both directions with the indexes off, then switch them on and watch how many lines get read.

What the book says

Positions and education are one-to-many; region_id is many-to-one; organizations and schools as entities make it many-to-many, usually stored as an associative table where each row links one user ID to one organization ID.

A denormalized option is to store the references on both sides (the résumé lists the org, the org lists the résumé), but then the relationship lives in two places and they can disagree.

A normalized representation stores the relationship once and relies on secondary indexes on both the user_id and org_id columns so it can be queried efficiently in both directions. Many document databases can index fields inside arrays, such as org_id inside positions.

The document model also can't refer directly to a nested item — you have to say “the second item in the list of positions for user 251”. It is, however, great for user-orderable lists like a to-do list, because order is just the array order.

Big idea 4 · schemas for analytics

A star in the middle of the warehouse

A supermarket's data warehouse keeps one gigantic fact table: one row every single time someone buys one product. Petabytes of rows.

Each row is mostly IDs: which product, which store, which day, which customer. Those point outwards to smaller dimension tables holding the who, what, where, when, how and why. Drawn on a whiteboard, the rays look like a star.

Break the dimensions into smaller dimensions (brand, category) and you get a snowflake: tidier, but more hops. Squash everything into the fact table instead and you get one big table: no joins at all, but a lot more disk.

Try it: run the same question in all three shapes and compare the joins, the width of the fact table, and the storage bar.

What the book says

Data warehouses are usually relational. Common conventions: star schema, snowflake schema, dimensional modeling, and one big table (OBT). ETL processes translate operational data into the chosen schema.

Each row of fact_sales is an event — a customer's purchase of a product (or a page view, for website traffic). Some columns are attributes like price and cost; others are foreign keys into dimension tables such as dim_product (SKU, description, brand, category, fat content, package size).

Even dates get a dimension table, so queries can tell holidays from ordinary days. Fact tables often have over a hundred columns; dimension tables are wide too (dim_store may record the square footage, the in-store bakery, when it was last remodeled).

A star or snowflake is mostly many-to-one relationships. Snowflake schemas are more normalized, but star schemas are often preferred because they're simpler for analysts. OBT precomputes the joins: more storage, sometimes faster queries — and denormalization is unproblematic here, because the data is a historical log that doesn't change.

Big idea 5 · schema flexibility

Tidy the whole cupboard now, or as you go?

Today every record stores one name field. Tomorrow you want first_name and last_name instead. There are two ways to get there.

Schema-on-write (the relational way): change the table's shape up front. Adding an empty column is fast, but filling it in rewrites every single row — slow and risky on a big table.

Schema-on-read (the document way): change nothing. Start writing new records in the new shape, and add a few lines of code that patch up old records when they're read. Nothing is rewritten — but that patch-up code has to live in your app forever.

Try it: ship the change both ways. Then read an old record and watch where the split actually happens.

What the book says

Document databases are often called schemaless, but that's misleading: the code that reads the data assumes a structure. A better term is schema-on-read (structure is implicit, interpreted when read) versus schema-on-write (explicit, enforced by the database on write). It's like dynamic versus static type checking.

The book's own example: if (user && user.name && !user.first_name) { user.first_name = user.name.split(" ")[0]; } versus ALTER TABLE users ADD COLUMN first_name text DEFAULT NULL; followed by an UPDATE that rewrites every row.

Adding a column with a default is fast even on large tables; the UPDATE is slow, and changing a column's datatype often copies the whole table. Tools exist for online migrations, but large migrations remain operationally challenging.

Schema-on-read shines when data is heterogeneous: many types of object, or a structure decided by external systems you don't control. When all records really do have the same structure, a schema documents and enforces it.

Big idea 6 · graph data models

Follow the arrows until you get there

When almost everything is connected to everything, a graph fits best. Vertices are things (people, places, web pages); edges are arrows between them, each with a label like BORN_IN or WITHIN.

Here's a question that graphs are brilliant at: which people were born in the United States but now live in Europe? The tricky part is that “inside the US” could be a state, a county or a city — you don't know how many arrows you'll have to follow.

Five languages, one question

In Cypher, :WITHIN*0.. means “follow a WITHIN edge zero or more times”, like * in a search pattern. Four lines.

The same graph fits fine in SQL tables — one table of vertices, one of edges — but the query needs a recursive common table expression, and it balloons to 31 lines. Same answer, much more typing.

Triple stores say everything in three-word sentences: (subject, predicate, object), like (lucy, marriedTo, alain). SPARQL queries those. Datalog builds the answer up rule by rule, and a rule may call itself — which is exactly what makes the traversal work.

What the book says

In the property graph model (Neo4j, Memgraph, KùzuDB) each vertex has an ID, a label, incoming and outgoing edges and a set of properties; each edge has an ID, a tail vertex, a head vertex, a label and properties. It maps onto two relational tables — vertices and edges — with indexes on both tail_vertex and head_vertex so you can traverse forwards and backwards.

Any vertex can connect to any other: there's no schema restricting what may be associated, which makes graphs good for evolvability. A limitation: an edge joins only two vertices, while a join table row can express three-way relationships.

In a triple store everything is a (subject, predicate, object) statement; the object is either a primitive value (a property) or another vertex (an edge). Turtle/N3 and RDF/XML are encodings; SPARQL is the query language; the Semantic Web lives on in JSON-LD, Wikidata, Schema.org and Open Graph.

Datalog (Datomic, LogicBlox, CozoDB, LinkedIn's LIquid) defines derived virtual tables with rules like within_recursive(...) :- ...; rules can invoke themselves, enabling graph traversal.

Facebook keeps one graph of people, locations, events, check-ins and comments; search engines keep knowledge graphs. The GQL ISO standard, based on Cypher, was published in 2024.

Big idea 7 · GraphQL

Order exactly what's on your plate

A chat app on your phone doesn't want “everything about every message”. It wants precisely the fields it will draw on screen — and nothing else, because every extra byte travels over a phone network.

GraphQL lets the app write down the shape it wants, and the answer comes back as JSON in exactly that shape. Change the screen, change the query — no server change needed.

It is deliberately limited, because the queries come from strangers' devices. No recursion, no arbitrary search conditions: otherwise a phone could accidentally knock the server over.

Try it: switch fields on and off and watch the reply grow and shrink. Then try the recursive one.

What the book says

GraphQL is intended for OLTP queries: it lets client software request a JSON document with a particular structure containing the fields needed to render its UI. The response “contains exactly those attributes that were requested, no more and no less”.

It does not allow recursive queries (unlike Cypher, SPARQL, SQL or Datalog) or arbitrary search conditions, because queries come from untrusted sources and expensive queries could cause a denial of service.

It accepts duplication on purpose: a sender's name and image URL are repeated in every message, and the content of a replied-to message is duplicated under replyTo, because that's simpler for the client than making another request.

The server can store the data normalized and do the joins itself — but only joins declared in the GraphQL schema can be requested. GraphQL can sit on top of a relational, document or graph database. Costs: tooling to convert queries into REST/gRPC calls, plus authorization, rate limiting and performance concerns.

Big idea 8 · event sourcing and CQRS

The logbook that can rebuild the whole office

A conference is complicated: people book seats, companies buy ten at a time, someone cancels, the organizer moves to a bigger room. Just answering “how many seats are left?” gets messy.

So don't store the answer — store what happened. Every change is written as an event in an append-only log, named in the past tense, and never changed afterwards. That's event sourcing.

Then build materialized views (also called read models) from that log: a seats counter, a bookings board, a badge printer. If a view has a bug, you delete it, fix the code and replay the log. That split between writing events and reading views is CQRS.

Try it: book and cancel with the buggy view code — the seat count drifts. Then switch to the fixed code and press Rebuild.

What the book says

A request from a user is a command; it is validated first (were there enough seats?), and only once it is valid does it become a fact appended to the log. A view that consumes the log is not allowed to reject an event.

Events should be named in the past tense, because an event records that something happened. A later change or cancellation is a separate event.

Advantages: intent is clearer than row edits; views are reproducible (delete and recompute with fixed code); many views optimized for different queries; new views from the existing log; mistakes reversed with a later event; the log doubles as an audit log; logs absorb write bursts.

Downsides: event processing must be deterministic (put the exchange rate in the event); immutability clashes with deletion requests under GDPR (hence crypto-shredding); and reprocessing must not repeat side effects like confirmation emails.

Like a star-schema fact table, a log is a collection of past events — but fact table rows all share columns and are unordered, while events have many types and their order matters. Implementations: EventStoreDB, MartenDB, Axon, or Apache Kafka plus stream processors.

Big idea 9 · DataFrames, matrices, arrays

Turning a list into a grid of numbers

A data scientist's table of movie ratings is a list: “user 1 gave movie 3 four stars”. Machine-learning algorithms don't want a list — they want a matrix: one row per user, one column per movie.

A DataFrame (pandas, R, Spark) does that reshaping. Most of the grid stays empty, because most people haven't seen most movies. That's called a sparse matrix, and it's completely fine.

Words aren't numbers, so a category like a movie's genre gets one-hot encoded: one column per genre, with a 1 in the right one and 0 everywhere else.

Try it: pivot the ratings into the grid, then one-hot encode the genre and watch three new columns appear.

What the book says

DataFrames (R, pandas, Apache Spark, ArcticDB, Dask) look like a relational table and support relational-like bulk operators — filter, group, aggregate, and merge (what a database calls a join). But instead of a declarative query language they're driven by a series of commands, matching how data scientists incrementally “wrangle” data, usually on a private copy.

A common use is transforming relational-like data into a matrix, like a pivot table: users as rows, movies as columns. The matrix is sparse, may have thousands of columns, and wouldn't fit well in a relational database — but NumPy and DataFrame libraries handle it easily.

A matrix contains only numbers, so dates are scaled to floats and small fixed sets of values get one-hot encoding (which also generalizes to movies in several genres). Then linear algebra — the basis of many ML algorithms, such as recommending movies — becomes possible.

Related: array databases such as TileDB for geospatial rasters, medical imaging and telescope data; DataFrames for financial time series; and DataFrame APIs added to Spark and Flink.

Words to know

Grown-up words, in plain language.

data model
The shape you choose for your data: tables, documents, or a graph.
relational model
Data as tables (relations) of rows (tuples). Proposed by Edgar Codd in 1970.
document model
Data as self-contained JSON documents with things nested inside.
declarative query
You describe the answer you want; the database works out how to get it.
query optimizer
The part of the database that picks indexes, join order and parallelism for you.
impedance mismatch
The awkward gap between objects in code and rows in tables.
ORM
A library that translates between objects and tables for you.
N+1 query problem
Fetching N things, then doing one extra query for each of them instead of one join.
one-to-many
One profile has many jobs. It makes a tree.
many-to-many
Many people worked at many companies. It makes a web.
join
Looking up an ID to fetch the record it points at.
join table
A little middle table whose rows just link two IDs together.
normalization
Storing each human-readable fact in exactly one place and pointing at it with IDs.
denormalization
Keeping copies of a fact in many records so reads don't need joins.
hydrating IDs
Turning stored IDs back into names and pictures when a page is shown.
locality
Keeping things that are read together stored together.
shredding
Chopping one document-shaped thing into several tables.
schema-on-write
The database checks the shape when data goes in.
schema-on-read
Nothing is checked on the way in; the reading code figures it out.
star schema
A big fact table in the middle with dimension tables around it.
fact table
One row per event that happened — a sale, a click, a page view.
dimension table
The who, what, where and when that a fact row points at.
vertex & edge
A dot and an arrow: the two pieces every graph is made of.
property graph
A graph where dots and arrows both carry labels and key-value properties.
triple store
A database of three-word sentences: subject, predicate, object.
event sourcing
Storing what happened as an append-only log instead of overwriting the answer.
materialized view
A ready-made answer built from the log, which can always be rebuilt.
CQRS
Writing in one shape (events) and reading from another (views).
DataFrame
A table you reshape step by step, on the way to a grid of numbers.
one-hot encoding
Turning a category into columns of 0s with a single 1.
