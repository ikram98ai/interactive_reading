Data models · one model on top of another

Every layer hides the one below

Zeynep writes a recipe app. In her code a recipe is an object with a title and a list of steps. She never thinks about the electricity in the disk, and she doesn’t have to: someone built a database that stores her object, and someone else built the disk that stores the database’s bytes.

Software is a stack of data models. You model the real world as objects and data structures. To store them you express them in a general-purpose data model: JSON documents, tables of rows, or vertices and edges in a graph — the subject of this chapter. The database’s engineers chose how to turn that into bytes (Chapter 4), and hardware engineers turn bytes into currents, light pulses or magnetic fields. Each layer offers a clean model and hides the mess underneath, so different groups of people can work together.

Try it: pick a data model and press Save the object. Watch the same résumé become JSON, rows or a graph, then bytes, then signals. Press Swap the hardware and notice that no layer above it changes.

What the book says

Data models are perhaps the most important part of developing software, because of their profound effect not only on how the software is written, but also on how we think about the problem we are solving.

Most applications are built by layering one data model on top of another; for each layer, the key question is how it is represented in terms of the next-lower layer: (1) the application developer models the real world (people, organizations, goods, actions, money flows, sensors) as objects or data structures and APIs; (2) to store them, they are expressed in a general-purpose data model such as JSON or XML documents, relational tables, or vertices and edges in a graph; (3) the database engineers decided how to represent that as bytes in memory, on disk or on a network, so it can be queried, searched and processed (Chapter 4); (4) hardware engineers represent bytes as electrical currents, pulses of light, magnetic fields and more.

A complex application may have more intermediary levels, such as APIs built upon APIs, but each layer hides the complexity of the layers below by providing a clean data model. These abstractions let different groups of people — for example, the engineers at the database vendor and the application developers using their database — work together effectively.

Some types of data and some queries are easy to express in one model and awkward in another. The chapter compares the relational model, the document model, graph-based data models, event sourcing and DataFrames, plus their query languages.

Terminology · declarative query languages

Say what you want, not how to find it

You can tell a taxi driver “the train station, please,” or you can read out every turn yourself. Give the address, and the driver can use a new bridge that opened last week. Give turn-by-turn directions, and you’ll take the old road forever, because that’s what you wrote down.

A declarative query language (SQL, Cypher, SPARQL, Datalog) is the address. You describe the pattern of data you want — conditions, sorting, grouping — and the database’s query optimizer decides which indexes and join algorithms to use, in which order, and whether to split the work across CPU cores. In Python or Java you’d write the algorithm yourself, and every speed-up would be your job.

Try it: run the Hand-written loop, then the Declarative SQL. Now turn on Add an index, or slide the cores up, and run both again. Watch the plan line in the code: only the SQL gets faster, and its text never changes.

What the book says

Many of the query languages in the chapter (SQL, Cypher, SPARQL, Datalog) are declarative: you specify the pattern of the data you want — what conditions the results must meet and how you want the data transformed (sorted, grouped, aggregated) — but not how to achieve that goal. The query optimizer decides which indexes and join algorithms to use and in which order to execute the parts of the query.

With most programming languages, such as Python and Java, you write an algorithm telling the computer which operations to perform in which order.

A declarative language is typically more concise and easier to write. More importantly, it hides the implementation details of the query engine, which makes it possible for the database to introduce performance improvements without requiring any changes to queries. For example, a database might execute a declarative query in parallel across multiple CPU cores and machines; in a handcoded algorithm, implementing such parallel execution yourself would be a lot of work.

Relational versus document models · fifty years of challengers

The table that outlasted every challenger

In 1970 Edgar Codd proposed storing data as relations — tables of rows, called tuples, in no particular order. Plenty of people doubted it could ever run fast. By the mid-1980s, relational databases and SQL were what most people reached for whenever their data had some regular structure.

Then came the challengers, each with its moment of hype: the network and hierarchical models, object databases, XML databases, and in the 2010s NoSQL (with NewSQL promising NoSQL’s scale with SQL’s guarantees). None replaced SQL. Instead, SQL quietly learned their tricks: XML, JSON, graph queries. NoSQL’s lasting gift is the document model: data as JSON, popularized by MongoDB and Couchbase.

Try it: press Play history, or drag the year slider. Watch each challenger rise and fade, and its best idea fly into the SQL box. Tap any lane to read what it was.

What the book says

The best-known data model today is probably SQL’s, based on the relational model proposed by Edgar Codd in 1970: data is organized into relations (tables in SQL), each an unordered collection of tuples (rows). It was originally a theoretical proposal, and many doubted it could be implemented efficiently; by the mid-1980s, relational database management systems (RDBMSs) and SQL had become the tools of choice for most people with regularly structured data. Business analytics is still dominated by relational data decades later.

In the 1970s and early 1980s the network model and the hierarchical model were the main alternatives. Object databases (not to be confused with object storage) came and went in the late 1980s and early 1990s. XML databases appeared in the early 2000s but saw only niche adoption. Each generated a lot of hype, but none lasted; instead SQL has grown to incorporate other types of data, adding support for XML, JSON and graph data.

In the 2010s, NoSQL was the latest buzzword: not one technology but a loose set of ideas around new data models, schema flexibility, scalability and open source licensing. NewSQL databases aimed to provide NoSQL’s scalability with the data model and transactional guarantees of relational databases. As the principles became widely adopted, use of both terms has faded.

One lasting effect of NoSQL is the popularity of the document model, usually JSON, popularized by MongoDB and Couchbase; most relational databases have now added JSON support. JSON documents are thought to be more flexible than relational tables, which are often seen as having a rigid schema.

Relational versus document models · the object-relational mismatch

When the plug doesn’t fit the socket

Electrical engineers know that when you connect one circuit’s output to another’s input, power flows best when their impedances match. When they don’t, part of the signal bounces back. Programmers borrowed the word.

Your code thinks in objects: a user holding a list of positions, a list of schools and some contact details. A relational database thinks in tables, rows and columns. Every save has to take the object apart into rows; every load has to glue rows back into an object. That awkward translation layer is the impedance mismatch.

Try it: in Circuits, slide the input impedance away from 50 Ω and press Send a pulse: part of it reflects. In Objects ↔ tables, press Save and Load and count the statements, then switch on Store as one document.

What the book says

Much application development is done in object-oriented languages, which leads to a common criticism of the SQL data model: if data is stored in relational tables, an awkward translation layer is required between the objects in the application code and the database model of tables, rows and columns. The disconnect is sometimes called an impedance mismatch.

The term is borrowed from electronics. Every electric circuit has a certain impedance (resistance to alternating current) on its inputs and outputs. When you connect one circuit’s output to another one’s input, the power transfer across the connection is maximized if the output and input impedances of the two circuits match. An impedance mismatch can lead to signal reflections and other troubles.

Some developers feel that the JSON model reduces the impedance mismatch between the application code and the storage layer, because a document maps more closely to an object structure in application code.

The object-relational mismatch · object-relational mapping

The helpful translator who asks one question at a time

Amara’s page shows a blog post’s comments, each with its author’s name. Her ORM (object-relational mapping library) makes the code lovely: loop over the comments, print comment.author.name. But behind the scenes the ORM fetched the comments in one query and then, every time she touched .author, quietly ran another query. Twelve comments, thirteen queries.

That is the N+1 query problem. In hand-written SQL you would join comments to users and get everything in one trip. With the ORM you have to know to ask for the authors up front (often called eager loading). ORMs cut boilerplate, can cache results and manage schema migrations — but they can’t fully hide the tables underneath, so you end up thinking about both models anyway.

Try it: set the number of comments and press Load the page with ORM, lazy. Count the round trips and read the SQL log. Then try Hand-written JOIN and ORM, fetch authors too.

What the book says

ORM frameworks like ActiveRecord and Hibernate reduce the boilerplate needed for the translation layer, but they are often criticized: they are complex and can’t completely hide the differences between the two models; they are generally used only for OLTP app development, while data engineers making data available for analytics work with the underlying relational representation, so the relational schema still matters; many ORMs work only with relational OLTP databases, so organizations with search engines, graph databases and NoSQL systems may find support lacking; automatically generated schemas can be awkward for people reading the tables directly and inefficient, and customizing them can negate the benefit of the ORM.

ORMs make it easy to accidentally write inefficient queries, such as the N+1 query problem: one query returns N comments, each containing its author’s ID; handwritten SQL would join with the users table, but an ORM may make a separate query on the users table for each of the N comments, N+1 queries in total, which is slower than performing the join in the database. To avoid it, you may need to tell the ORM to fetch the author information at the same time as the comments.

Advantages: for data well suited to a relational model, some translation between the persistent relational and in-memory object representation is inevitable, and ORMs reduce the boilerplate (complicated queries may still be handled outside the ORM); some ORMs cache query results, reducing database load; and ORMs can help with schema migrations and other administrative activities.

Relational versus document models · the document model for one-to-many

A résumé is a tree

A profile has one first name and one last name, but many jobs, many schools and several ways to contact you. Those are one-to-many relationships, and together they form a tree: the person at the root, lists hanging off it.

The relational way puts each list in its own table — positions, education, contact_info — each row carrying a foreign key back to user_id 251. To show the page you either run four queries or one messy multiway join that multiplies the rows. The document way stores the whole tree as one JSON document: one read, and everything is already in place. That is better locality. The catch: when a list can grow to thousands of items — comments on a celebrity’s post — embedding it all in one document becomes unwieldy.

Try it: press Load profile in each of the three modes and compare queries and rows. In the multiway join, look how often “Harvard” is repeated. Then drag the comments slider and watch the document swell.

What the book says

Figure 3-1 expresses a résumé (a LinkedIn profile) relationally: the profile is identified by user_id; fields like first_name and last_name appear once per user, so they are columns on the users table; positions, education and contact information are one-to-many, so they go in separate tables with a foreign-key reference to users. Example 3-1 stores the same data as one JSON document, which is perhaps more natural and maps more closely to an object structure in application code.

The JSON representation has better locality: to fetch a profile in the relational example you must either perform multiple queries (query each table by user_id) or a messy multiway join between users and its subordinate tables. In the JSON representation all the relevant information is in one place, making the query both faster and simpler.

The one-to-many relationships from the profile to the positions, educational history and contact information imply a tree structure, which JSON makes explicit (Figure 3-2).

A one-to-many relationship is sometimes called one-to-few, since a résumé typically has a small number of positions. With a genuinely large number of related items — say, many thousands of comments on a celebrity’s social media post — embedding them all in the same document may be too unwieldy, so the relational approach is preferable.

Relational versus document models · normalization, denormalization and joins

Write the place once, point at it everywhere

In the JSON résumé, the region isn’t written as “Washington, DC, United States”. It is "region_id": "us:91". Why store a code nobody can read?

Because the code points into one standard list of regions. Everyone spells it the same way; “Washington” can’t be mistaken for the state; a rename touches one row; the list can be translated for each viewer; and the list can know facts the text doesn’t, such as “on the US East Coast”. Storing the ID is normalized: the human-meaningful text lives in one place. Copying the text into every profile is denormalized. The price of normalizing: every time you show a profile, you look the ID up — a join.

Try it: in each mode press Read profile 251, then Rename region. Try Rename, crash halfway in the text mode. Then press Show in Spanish and Search: East Coast in both modes.

What the book says

Advantages of standardized lists of geographic regions chosen from a drop-down list or autocompleter: consistent style and spelling across profiles; avoiding ambiguity if several places have the same name; ease of updating (the name is stored in one place, e.g. a city renamed due to political events); localization support (the list can be translated into the viewer’s language); and better search (a search for the US East Coast can match the profile because the list can encode that Washington is on the East Coast).

Using an ID is more normalized: the human-meaningful information is stored in only one place, and everything that refers to it uses an ID, which has meaning only within the database and so never needs to change. Storing the text directly duplicates human-meaningful information in every record; that is denormalized. Duplicated information that changes must be updated in every copy: more code, more writes, more disk space, and a risk of inconsistency when some copies are updated but others aren’t.

The downside of normalization: every time you display a record containing an ID, you need an additional lookup to resolve it, which in the relational model is a join. Document databases can store both forms but are often associated with denormalization, partly because JSON makes extra fields easy and partly because many have weak join support; some have no joins at all, so the application fetches a document and then runs a second query to resolve the ID. MongoDB can join with the $lookup operator in an aggregation pipeline.

Normalization, denormalization and joins · trade-offs of normalization

Cheap writes or cheap reads — pick per field

The résumés now show each employer’s logo. Store the logo’s URL inside every résumé, and each page renders with no lookup at all — until the company changes its logo, and someone has to hunt down every copy. Store the company once as its own entity, and the logo change is one write, but every page view now needs a join.

The rule of thumb: normalized data is faster to write and slower to query; denormalized data is faster to read and more expensive to write. Think of denormalized copies as derived data: you need a process to keep them updated, and if that process crashes halfway, the copies disagree — unless the database gives you atomic transactions across those records.

Try it: press Change the logo in both modes and count writes. Turn on Crash halfway and change it again; then add Atomic transaction. Finally drag page views per logo change and watch which design costs less.

What the book says

In the résumé example, organization and school_name are just strings, which is denormalized: many people may have worked at the same company, but no ID links them. To include a logo, a denormalized representation would put the logo URL on every individual profile, which keeps the document self-contained but means finding and updating every occurrence if the logo changes. A normalized one creates an entity for the organization or school with its name, logo URL and other attributes, stored once; every résumé references its ID.

As a general principle, normalized data is usually faster to write (only one copy) but slower to query (requires joins); denormalized data is usually faster to read (fewer joins) but more expensive to write (more copies to update, more disk space). Denormalization can be seen as a form of derived data, since you need a process for updating the redundant copies.

You must also consider consistency if a process crashes halfway through its updates. Databases that offer atomic transactions make it easier to remain consistent, but not all databases offer atomicity across multiple documents; stream processing (Chapter 12) is another way.

Normalization tends to be better for OLTP systems, where both reads and updates need to be fast; analytical systems often fare better with denormalized data, since they update in bulk and read-only query performance dominates. At small to moderate scale a normalized model is often best; in very large-scale systems the cost of joins can become problematic.

Relational versus document models · denormalization in the social networking case study

A timeline of numbers, filled in when you look

Mei follows Ravi and Amara. Her home timeline is ready before she opens the app: every time one of them posts, a little worker drops the new post into Mei’s list. That precomputed list is denormalized data — a cached copy of the result of joining posts with follows.

But what goes in the list? If it holds the whole post — text, sender’s name, profile photo, like count — the list goes stale the moment someone taps like, and every follower stores another full copy. So X keeps only two numbers per entry: the post ID and the sender ID. When Mei opens the app, the service looks those IDs up in the posts and users tables, in parallel. Turning IDs into readable records like this is called hydrating them: a join done in application code.

Try it: in IDs only, press Read timeline and follow the two parallel lookups in the code. Press Someone likes it and Ravi changes photo, then read again: always fresh. Switch to Copy everything, read, like, change the photo, and read once more — count the stale fields.

What the book says

In the home-timelines case study the join between posts and follows was too expensive, so the materialized timeline is a cache of the result of that join, and the fan-out process that inserts a new post into followers’ timelines keeps the denormalized representation consistent.

X (formerly Twitter) does not store the actual text of each post in its materialized timelines. Each entry stores only the post ID, the ID of the user who posted it, and a little extra information to identify reposts and replies — a precomputed result of approximately SELECT posts.id, posts.sender_id FROM posts JOIN follows … ORDER BY posts.timestamp DESC LIMIT 1000.

So reading a timeline still needs two joins: look up each post ID for the content and statistics such as likes and replies, and look up the sender’s profile by ID. This is called hydrating the IDs, essentially a join performed in application code. Only IDs are stored because the data they refer to changes fast — like counts many times per second on a popular post, usernames and profile photos now and then — and denormalizing it would also increase storage cost significantly.

Joins at read time are therefore not an impediment to high-performance, scalable services: hydration parallelizes well, and its cost doesn’t depend on how many accounts you follow or how many followers you have. The most scalable approach may denormalize some things and leave others normalized; consider how often the information changes and the cost of reads and writes, which may be dominated by outliers. Normalization and denormalization are not inherently good or bad — they are trade-offs.

Relational versus document models · many-to-one and many-to-many relationships

A ledger that answers both ways

A résumé has many positions, but each position belongs to one résumé: one-to-many. Many people live in one region: many-to-one. Once organizations are their own records, one person has worked at several organizations and one organization has had many people: many-to-many. That doesn’t fit inside one self-contained document.

Relational databases put a small ledger in the middle, an associative table (or join table): each row of positions links one user_id to one org_id. People ask it in both directions — “where did 251 work?” and “who worked at 514?” — so you add a secondary index on each column. The alternative, storing the IDs on both sides, writes the same fact twice, and two copies can disagree.

Try it: in Join table, ask both questions with indexes off and watch every row get read; press Indexes: off to turn them on and ask again. In IDs on both sides, press 302 joins 513 with Crash between writes on, then ask from each side. In Documents, see the same reverse question answered by an index on positions.org_id.

What the book says

The positions and education tables are one-to-many (or one-to-few). The region_id field is many-to-one: many people live in the same region, but each lives in one region at a time. Introducing entities for organizations and schools, referenced by ID, gives many-to-many relationships, usually represented in a relational model as an associative table or join table (Figure 3-3): each position associates one user ID with one organization ID.

Many-to-one and many-to-many relationships do not easily fit within one self-contained JSON document; they lend themselves to a normalized representation. In a document model (Example 3-2) each résumé can be one document, while the links to organizations and schools are references to other documents, such as "org_id": 513 inside each position.

Many-to-many relationships often need to be queried in both directions. Storing ID references on both sides (the résumé lists its organizations, the organization lists its résumés) is denormalized: the relationship is stored in two places, which could become inconsistent with each other.

A normalized representation stores the relationship in one place and relies on secondary indexes to query it efficiently in both directions — in Figure 3-3, indexes on both the user_id and org_id columns of positions. In Example 3-2 the database must index the org_id field of objects inside the positions array; many document databases and relational databases with JSON support can index values inside a document.

Relational versus document models · stars and snowflakes: schemas for analytics

A star in the middle of the warehouse

Every time a shopper at a grocery chain buys one product, the warehouse writes one row into a giant fact table, fact_sales. A few columns are plain numbers (quantity, price). The rest are foreign keys: which product, which store, which day, which customer, which promotion. They point out to dimension tables holding the who, what, where, when, how and why. Drawn on a whiteboard, the lines look like the rays of a star.

Split a dimension further — categories into their own table — and the star becomes a snowflake: more normalized, one more join. Go the other way, copy every dimension column into the fact rows, and you have one big table: no joins at all, a lot more storage. In analytics this copying is harmless, because the rows are history that never changes.

Try it: press Run query in each shape and follow each sale along its rays; the code shows the join it is on. Compare the joins per row and the storage. Then press Find one basket: a shopper bought two things at once, and it is just two rows that share a customer, store and date.

What the book says

Data warehouses are usually relational, with conventions such as the star schema, the snowflake schema, dimensional modeling and one big table (OBT), optimized for business analysts; ETL processes translate data from operational systems into the chosen schema. At the centre of a star schema is a fact table (fact_sales in Figure 3-5); each row is an event at a particular time — here a customer’s purchase of a product, for website traffic a page view or click. Fact tables can become extremely large: a big enterprise may have many petabytes of transaction history.

Some fact columns are attributes, such as the price and the cost from the supplier; others are foreign keys into dimension tables, which represent the who, what, where, when, how and why of the event. Each dim_product row is one product type (SKU, description, brand, category, fat content, package size). Even date and time are often dimensions, so queries can tell sales on holidays from other days. Fact tables frequently have over a hundred columns, and dimensions are wide too (dim_store may record services offered, an in-store bakery, square footage, opening and remodeling dates).

A snowflake schema breaks dimensions into subdimensions, such as separate brand and category tables referenced from dim_product. It is more normalized, but star schemas are often preferred because they are simpler for analysts. A star or snowflake is mostly many-to-one relationships; other relationship types are often denormalized — a customer buying several products at once is not represented explicitly, just as several fact rows with the same customer ID, store ID and timestamp.

One big table leaves out the dimension tables entirely, folding their information into denormalized fact columns — precomputing the join. It needs more storage but sometimes enables faster queries. In analytics such denormalization is unproblematic, since the data is a log of history that is not going to change (except occasionally correcting an error).

Relational versus document models · when to use which model

Drag a card, count the writes

Ines drags “Pay rent” from the bottom of her to-do list up to second place. In a document, the list is just a JSON array: its order is the order. A relational table has no standard way to remember order, so people use tricks: an integer position column (and renumber everything below the drop point), a linked list of IDs, or fractional indexing — give the moved card a number between its new neighbours, like 1.5.

Documents have the opposite weak spot. You can’t point straight at something nested inside one; you have to say “the second item in the positions list of user 251”. Insert a new item at the front and that address now means something else. A row with its own ID can be referred to forever.

Try it: pick a strategy and press Move last to 2nd a few times, watching which rows light up as written. Then try Point at a nested item: press Add a position at the front and see which bookmark still points at the right job.

What the book says

The main arguments for the document model are schema flexibility, better performance due to locality, and that for some applications it is closer to the application’s object model. The relational model counters with better support for joins and for many-to-one and many-to-many relationships.

If the data has a document-like structure — a tree of one-to-many relationships where typically the entire tree is loaded at once — a document model is probably a good idea. The relational technique of shredding (splitting it into tables such as positions, education and contact_info) can lead to cumbersome schemas and unnecessarily complicated application code.

A limitation of documents: you cannot refer directly to a nested item; you need to say something like “the second item in the list of positions for user 251.” If you need to reference nested items, a relational approach works better, since you can refer to any item directly by its ID.

For user-reorderable lists, such as a to-do list or issue tracker with drag and drop, documents work well: the items or their IDs are stored in a JSON array that determines their order. Relational databases have no standard way to represent reorderable lists; tricks include sorting by an integer column (requiring renumbering when you insert into the middle), maintaining a linked list of IDs, or fractional indexing.

Relational versus document models · schema flexibility in the document model

Tidy the whole cupboard now, or each cup as you use it?

Every user record stores one name: “Ana Souza”. Now the app wants first_name too. A relational database is schema-on-write: the table has an explicit shape the database enforces, so you change the shape — and to fill in the new column, an UPDATE rewrites every single row. On a huge table that is slow and operationally scary.

A document database is usually called schemaless, but the code that reads it still expects certain fields. It is really schema-on-read: new records get the new field, and a few lines in the app patch old records whenever they are read. Nothing is rewritten — but every reader must cope with old shapes forever. It is the same argument as static versus dynamic type checking, and neither side wins outright. Schema-on-read shines when records genuinely differ, such as data whose shape another company controls.

Try it: in each mode press Ship the change and watch the counters; then press Read a user and follow the code. Hybrid is the cheap middle way: add an empty column, fill it on read. In Data from outside, press Receive a record several times with both kinds of store.

What the book says

Most document databases, and the JSON support in relational databases, do not enforce any schema on the data in documents; clients have no guarantees about which fields a document contains. Calling them schemaless is misleading, because the reading code usually assumes some structure — an implicit schema. A more accurate term is schema-on-read, in contrast with schema-on-write, where the schema is explicit and the database ensures all written data conforms. The first is like dynamic (runtime) type checking, the second like static (compile-time) type checking; there’s no clear winner.

The difference shows when the format changes, for example splitting a full name into first and last names. In a document database you write new documents with the new fields and handle old ones when reading: if (user && user.name && !user.first_name) { user.first_name = user.name.split(" ")[0]; }. The downside is that every part of the application that reads must deal with old formats.

In a schema-on-write database you would run ALTER TABLE users ADD COLUMN first_name text DEFAULT NULL; and then UPDATE users SET first_name = split_part(name, ' ', 1); in PostgreSQL (substring_index(name, ' ', 1) in MySQL). Adding a column with a default is fast even on large tables; the UPDATE is likely slow because every row is rewritten, and changing a column’s datatype typically copies the whole table. Tools exist to run such changes in the background without downtime, but large migrations remain operationally challenging. You can avoid them by adding the column with a NULL default and filling it in at read time, as with documents.

Schema-on-read is advantageous when the data is heterogeneous: many types of objects that can’t each have their own table, or structure determined by external systems you don’t control. When all records are expected to have the same structure, schemas usefully document and enforce it.

Relational versus document models · data locality for reads and writes

One drawer, or four filing cabinets?

Kwame keeps each customer’s papers in one drawer: grab the drawer, you have everything. His colleague files by type — all addresses in one cabinet, all orders in another — so one customer means four trips across the room. That is locality: a document is stored as one continuous string (JSON, XML or a binary form like BSON), so reading all of it costs one trip to the disk.

The drawer has a catch. To read just one sheet, Kwame still pulls the whole drawer, and to change one sheet the database usually rewrites the whole document. So keep documents small and avoid many tiny updates. And locality isn’t only for documents: a relational database can be told to store a parent’s child rows right next to it.

What the book says

A document is usually stored as a single continuous string, encoded as JSON, XML or a binary variant (such as MongoDB’s BSON). If the application often needs the entire document, for example to render it on a web page, this storage locality is a performance advantage. If data is split across multiple tables, as in Figure 3-1, multiple index lookups are required to retrieve it all, which may require more disk seeks and take more time.

The locality advantage applies only if you need large parts of the document at the same time. The database typically needs to load the entire document, which is wasteful if you need only a small part of a large document, and on updates the entire document usually needs to be rewritten. It is generally recommended to keep documents fairly small and avoid frequent small updates.

Storing related data together is not limited to documents. Google’s Spanner offers the same locality in a relational model by letting the schema declare that a table’s rows should be interleaved (nested) within a parent table; Oracle allows the same with multi-table index cluster tables; and the wide-column model popularized by Bigtable, used in HBase and Accumulo, has column families with a similar purpose.

What the book says

Most relational databases are queried with SQL, but document databases are more varied: some allow only key-value access by primary key, others offer secondary indexes to query values inside documents, and some provide rich query languages. XML databases are often queried using XQuery and XPath, which allow complex queries including joins across documents. JSON Pointer and JSONPath provide an equivalent to XPath for JSON. MongoDB’s aggregation pipeline is a query language for collections of JSON documents.

The book’s example is an aggregation, especially needed for analytics: a marine biologist reports how many sharks were sighted per month. The aggregation pipeline is similar in expressiveness to a subset of SQL, but uses a JSON-based syntax rather than SQL’s English sentence–style syntax. The difference is perhaps a matter of taste.

Relational versus document models · convergence of document and relational databases

Two rivals that learned each other’s tricks

Document and relational databases started as very different ideas, and they have been borrowing from each other ever since. Relational databases added JSON column types, operators to query inside JSON, and indexes on values inside documents. Document databases such as MongoDB, Couchbase and RethinkDB added joins, secondary indexes and declarative query languages.

That is good news: most real data has a bit of both. A user table can keep tidy columns for the things everyone has, and one JSON column for the odds and ends that differ per user. The idea is older than it looks: Edgar Codd’s 1970 paper already allowed a value in a row to be a whole nested table, which he called a nonsimple domain.

What the book says

Document and relational databases started out as very different approaches but have grown more similar over time. Relational databases added support for JSON types and query operators, and the ability to index properties inside documents. Some document databases (such as MongoDB, Couchbase and RethinkDB) added support for joins, secondary indexes and declarative query languages.

This convergence is good news for application developers, because the two models work best when you can combine both in the same database. Many document databases need relational-style references to other documents, and many relational databases have sections where schema flexibility is beneficial. Relational–document hybrids are a powerful combination.

Codd’s original description of the relational model allowed something similar to JSON within a relational schema. He called it nonsimple domains: a value in a row doesn’t have to be a primitive datatype like a number or a string; it can also be a nested relation (table), so you can have an arbitrarily nested tree structure as a value — comparable to the JSON and XML support added to SQL over 30 years later.

Graph-like data models · vertices and edges

Dots and arrows

Draw your friends as dots and put a line between any two who know each other. Draw web pages as dots and an arrow for every link. Draw road junctions as dots and the roads between them as lines with a travel time. Three different worlds, one picture: a graph, made of vertices (the dots, also called nodes or entities) and edges (the lines, also called relationships or arcs).

How do you store one? An adjacency list keeps, for each vertex, the IDs of its neighbours one edge away. An adjacency matrix is a grid with a row and a column per vertex: 1 where there is an edge, 0 where there isn’t. To walk the graph you only need a vertex’s neighbours, so lists win; a matrix is all numbers, so it suits machine learning. And a graph need not hold one kind of thing: Facebook keeps people, places, events, check-ins and comments in one graph, with a label on every edge.

Try it: pick a world and press Run: find Aiko’s friends of friends, rank the web pages, or find the quickest road from J1 to J6. Watch the entries read counter, then switch to Adjacency matrix and run it again. In Many kinds, compare what the list keeps and what the matrix forgets.

What the book says

If an application has mostly one-to-many relationships (tree-structured data), the document model fits. But as many-to-many relationships become common and the connections more complex, it becomes more natural to model the data as a graph: vertices (nodes, entities) and edges (relationships, arcs).

Typical examples are social graphs (people who know each other), the web graph (pages and HTML links) and road or rail networks (junctions and the roads or railway lines between them). Well-known algorithms run on them: map navigation apps search for the shortest path between two points, and PageRank on the web graph determines the popularity of a page and thus its ranking in search results.

In the adjacency list model each vertex stores the IDs of its neighbour vertices one edge away; an adjacency matrix is a two-dimensional array with 1 where there is an edge and 0 where there isn’t. An adjacency list is good for graph traversals, and matrices are good for machine learning.

Graphs are not limited to homogeneous data. Facebook maintains a single graph whose vertices are people, locations, events, check-ins and comments, and whose edges say who is friends with whom, which check-in happened where, who commented on which post and who attended which event. Search engines keep knowledge graphs of organizations, people and places; Wikidata publishes graph data in a structured form.

The chapter covers the property graph model (Neo4j, Memgraph, KùzuDB) and the triple store model (Datomic, AllegroGraph, Blazegraph), which are fairly similar in what they can express (Amazon Neptune supports both), and four graph query languages: Cypher, SPARQL, Datalog and GraphQL, plus SQL. Gremlin is another.

Graph-like data models · property graphs

Two tables can hold any graph

Lucy was born in Idaho and lives in London with Alain, who grew up in Saint-Lô in Normandy. Write every person and every place on a card (a vertex) and every “born in”, “lives in” and “within” as an arrow (an edge). In a property graph each vertex has an ID, a label such as Location and a bag of key-value properties; each edge has an ID, a label, properties, the vertex it starts at (the tail) and the vertex it points to (the head).

That fits in two plain tables: vertices and edges. The trick is the two indexes on edges: one on tail_vertex finds every arrow leaving a vertex, one on head_vertex every arrow arriving, so you can walk the graph forwards and backwards. Nothing says which kinds of things may be linked, so new kinds of facts slot straight in. The one thing an edge can’t do is join three vertices.

What the book says

In the property graph (labeled property graph) model, each vertex has a unique identifier, a label describing the type of object, a set of outgoing edges, a set of incoming edges and a collection of properties (key-value pairs). Each edge has a unique identifier, the vertex at which it starts (the tail vertex), the vertex at which it ends (the head vertex), a label for the kind of relationship and a collection of properties.

A graph store can be thought of as two relational tables, one for vertices and one for edges (Example 3-3, using PostgreSQL’s jsonb for properties), with indexes on tail_vertex and head_vertex so that incoming and outgoing edges can be found efficiently and the graph traversed forward and backward. Any vertex can be connected to any other; no schema restricts which kinds of things can be associated. Different labels let one graph hold several kinds of information while keeping a clean data model.

The edges table is like the many-to-many join table, generalized to store many types of relationship in one table. Figure 3-6 shows things awkward in a traditional relational schema: different regional structures in different countries (France has départements and régions, the US counties and states), a country within a country, and varying granularity (Lucy’s residence is a city, her birthplace only a state).

Graphs are good for evolvability: you could add a vertex for each allergen, edges from people to allergens, and links from allergens to the foods that contain them, then query what each person can safely eat.

A limitation: an edge associates only two vertices, whereas a relational join table can represent three-way or higher-degree relationships with several foreign keys on one row. In a graph you create an extra vertex for each such row, with edges to and from it, or use a hypergraph.

Graph-like data models · the cypher query language

Draw the pattern with arrows

Cypher lets you type a graph almost the way you would sketch it on a napkin: (idaho) -[:WITHIN]-> (usa) is a vertex, an arrow labelled WITHIN, and another vertex. Names like idaho are just nicknames for this one query, so you can point at the same vertex twice; they are never stored.

The same arrows also ask. “Who was born somewhere in the United States and now lives somewhere in Europe?” becomes a pattern with -[:WITHIN*0..]->: follow WITHIN zero or more times, like * in a regular expression, because a birthplace might be a state, a city or the country itself. Since you only describe the pattern, the database chooses where to start: from every person, or from the two places at the far end.

Besides Neo4j it is supported by Memgraph, KùzuDB, Amazon Neptune, Apache AGE (with storage in PostgreSQL) and others. It is named after a character in the movie The Matrix, not after ciphers in cryptography.

Joins until nothing new turns up

Store the graph in the two tables from before and SQL can answer the same question, but every arrow you follow is one more join with the edges table. A normal SQL query has a fixed number of joins. Here you don’t know how many you need: London is three hops from Europe, Saint-Lô four.

What the book says

Graph data can be represented in a relational database and queried with SQL, but with some difficulty. Every edge you traverse in a graph query is effectively a join with the edges table. In a relational database you usually know in advance which joins you need; in a graph query you may need to traverse a variable number of edges before you find the vertex you’re looking for — the number of joins is not fixed in advance.

A LIVES_IN edge may point to a street, a city, a district, a region or a state, which may be within a region, a state, a country and so on. Cypher’s :WITHIN*0.. expresses this concisely. Graph-like data models · triple stores

Every fact is a three-word sentence

“Jim likes bananas.” Subject, verb, object. A triple store keeps everything that way: (subject, predicate, object). If the object is a plain value, like the string “Idaho”, the triple is a property of the subject. If the object is another vertex, like _:usa, the triple is an edge. That is the whole model, and it says what a property graph says, with different words.

One popular way to write triples is Turtle. Names such as _:idaho exist only so that several lines can talk about the same vertex. Writing the subject on every line gets repetitive, so Turtle lets you use semicolons to say several things about one subject.

What the book says

The triple store model is mostly equivalent to the property graph model, using different words to describe the same ideas. All information is stored as very simple three-part statements: (subject, predicate, object). In the triple (Jim, likes, bananas), Jim is the subject, likes the predicate (verb) and bananas the object.

The subject is equivalent to a vertex. The object is either a value of a primitive datatype — then predicate and object are the key and value of a property on the subject, so (lucy, birthYear, 1989) is like a vertex lucy with properties {"birthYear": 1989} — or another vertex, in which case the predicate is an edge, the subject the tail and the object the head, as in (lucy, marriedTo, alain).

Whose “within” is it?

Turtle is one way of writing the Resource Description Framework (RDF), the triple model designed for the Semantic Web. Because RDF expects data from strangers to be mixed together, its words are usually URIs: not within but <urn:example:within>. The URI doesn’t have to lead anywhere; it is just a namespace, declared once at the top of the file and then forgotten. The same triples can be written as Turtle or, much more verbosely, as RDF/XML, and tools such as Apache Jena convert between them.

What the book says

The Turtle language is a way of encoding data in the Resource Description Framework (RDF), a data model designed for the Semantic Web. RDF data can also be encoded in other ways, including (more verbosely) XML, as in Example 3-9. Tools like Apache Jena can automatically convert between different RDF encodings.

RDF has a few quirks because it is designed for internet-wide data exchange. The subject, predicate and object of a triple are often URIs: a predicate might be <http://my-company.com/namespace#within> rather than just WITHIN. The reasoning is that you should be able to combine your data with someone else’s, and if they attach a different meaning to within or lives_in, you won’t get a conflict, because their predicates are actually <http://other.org/foo#within> and <http://other.org/foo#lives_in>.

The URL doesn’t necessarily need to resolve to anything; from RDF’s point of view it is simply a namespace. The book’s examples use nonresolvable URIs such as urn:example:within, specified once with a prefix at the top of the file.

Graph-like data models · the sparql query language

Fill in the blanks with question marks

SPARQL (say “sparkle”) asks triple stores questions by writing triples with blanks in them. A word starting with ? is a blank to fill: ?person :name ?personName matches every triple whose predicate is :name, and each match fills in both blanks. Every further line must hold for the same filled-in values, so the list of candidates shrinks line by line.

The path :bornIn / :within* / :name "United States" says: follow bornIn once, then within zero or more times, then check the name. If that looks like Cypher, it is the other way round: SPARQL is older, and Cypher borrowed its pattern matching.

What the book says

SPARQL is a query language for triple stores using the RDF data model. The name is a recursive acronym for SPARQL Protocol and RDF Query Language, pronounced “sparkle.” It predates Cypher, and since Cypher’s pattern matching is borrowed from SPARQL, they look quite similar.

Example 3-10 finds people who moved from the US to Europe, as concisely as Cypher. Variables start with a question mark: (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location) in Cypher is equivalent to ?person :bornIn / :within* ?location. in SPARQL.

Because RDF doesn’t distinguish between properties and edges but uses predicates for both, the same syntax matches properties: (usa {name:'United States'}) in Cypher is ?usa :name "United States". in SPARQL, binding usa to any vertex with that name.

SPARQL is supported by Amazon Neptune, AllegroGraph, Blazegraph, OpenLink Virtuoso, Apache Jena and various other triple stores.

Graph-like data models · datalog: recursive relational queries

Small rules that keep adding facts

Amara keeps a family atlas. On one card she writes plain facts: “Idaho is in the United States”, “the United States is in North America”. On another card she writes two rules: a place is in its own name, and if A is in B and B is in somewhere, then A is in that somewhere too. She never writes down “Idaho is in North America” — she can always work it out, one rule at a time.

Datalog works exactly like that. The database holds facts, which are just rows in tables: within(3, 2) means the within table has a row (3, 2). A rule derives a new virtual table, like a SQL view: if every pattern on the right of :- matches, the left side counts as a new row. Rule 2 uses its own table on the right, so it can keep climbing the hierarchy — that recursion is what makes graph traversal possible.

The query is built up rule by rule, the way you would split a program into small functions that call each other.

Try it: in Example 3-11, press Step and watch each rule fire, with the facts it matched lit up on the left. Keep stepping until nothing new appears. Then switch to With London and Europe (extra toy facts) and press Run to the end: rule 3 fills a grid of Lucy’s birthplaces and homes, and rule 4 picks one cell.

What the book says

Datalog arose from academic research in the 1980s and is much older than SPARQL or Cypher. It is less well known among software engineers and not widely supported in mainstream databases, but it is very expressive and especially powerful for complex queries. Datomic, LogicBlox, CozoDB and LinkedIn’s LIquid use it. It is based on a relational data model, not a graph, but recursive queries on graphs are a particular strength.

The contents of a Datalog database are facts, and each fact corresponds to a row in a relational table: location(2, "United States", "country"). In Example 3-11 the edges of the graph (within, born_in, lives_in) are two-column join tables, so Lucy (ID 100) born in Idaho (ID 3) is born_in(100, 3).

Rules define derived tables that are like (virtual) SQL views: not stored in the database, but queryable like a table. The name and columns come from the part before :-; the contents come from matching the patterns after it. A rule applies if the system can find a match for all patterns on the right-hand side; then it is as though the left-hand side was added to the database, with variables replaced by the values they matched.

Rule 3 finds people born in some location BornIn and living in some location LivingIn; rule 4 invokes rule 3 with BornIn = 'United States' and LivingIn = 'Europe'. Datalog is a subset of Prolog, and its rules can invoke themselves, like recursive functions.

Graph-like data models · graphql

Order exactly what goes on the screen

Tomás builds a chat app like Slack or Discord. The phone screen shows each channel’s name, its latest messages, each sender’s name and picture, and — for a reply — a small grey line quoting the message it answers. The phone wants exactly those fields and not one byte more.

With GraphQL the app writes down the shape it wants, and the server answers with a JSON document in exactly that shape. If the designer adds the replied-to sender’s picture next week, Tomás adds one field to the query; the server doesn’t change. The answer even repeats Aaliyah’s name in every message and copies the replied-to text, because that makes the screen trivial to draw.

The catch: these queries come from strangers’ phones. So GraphQL is deliberately limited — no recursion, no arbitrary search conditions, and only the joins the server declared in its schema. Otherwise one phone could keep a server busy forever.

What the book says

GraphQL is, by design, much more restrictive than the other languages in the chapter. It is intended for OLTP queries: client software on a user’s device, such as a mobile app or a JavaScript web frontend, requests a JSON document with a particular structure, containing the fields necessary for rendering its UI. Developers can rapidly change queries in client code without changing server-side APIs.

That flexibility has a cost: organizations often need tooling to convert the queries into requests to internal services (commonly REST or gRPC), plus authorization, rate limiting and performance concerns. Because queries come from untrusted sources, GraphQL does not allow recursive queries (unlike Cypher, SPARQL, SQL or Datalog), nor arbitrary search conditions such as finding people born in the US and now living in Europe, unless the service owners choose to offer such a search.

Returning only the ID of the replied-to message would force another request if it wasn’t among the 50 most recent.

The server can store the data normalized (a message with its sender’s user ID and the ID of the message it replies to) and resolve those IDs when it receives the query — but only joins explicitly declared in the GraphQL schema can be requested. Despite the name, GraphQL can be implemented on top of any type of database: relational, document or graph.

Event sourcing and CQRS · commands, events and views

Write down what happened, derive everything else

Running a conference is messy. People register and pay by card, companies buy seats in bulk and assign them later, some seats are held for speakers, bookings get canceled, the organizer moves to a bigger room. Even “how many seats are left?” becomes a hard query if you keep only the current state.

So don’t overwrite state; keep a diary. Every request is a command (“book me 3 seats”). It is validated first — are there enough seats? Only if it is valid does it become a fact, appended to an append-only event log as an event named in the past tense: seats_reserved. Events are never edited. That idea is event sourcing.

Nobody queries the log directly. Each time an event is appended, several materialized views (projections, read models) update themselves: a booking confirmation, the organizer’s dashboard, the badge printer’s files. Writing in one shape and reading from others derived from it is CQRS. A view is not allowed to reject an event: the decision was made when the command was validated.

Try it: press Book seats before registrations open, then Open registrations and book again a few times until a booking no longer fits. Press Cancel 4001. Then switch to Update in place and cancel the same booking: count the row changes, and ask yourself why they happened.

What the book says

In the models so far, data is queried in the same form as it is written. In complex applications it can be hard to find one representation that satisfies every way the data is queried, so it helps to write data in one form and derive read-optimized representations from it. Perhaps the simplest, fastest and most expressive way of writing is an event log: each write is a self-contained string (perhaps JSON) with a timestamp, appended to a sequence. Events are immutable; you only ever append more, which may supersede earlier ones.

In Figure 3-8 every change to the conference (opening registrations, making and canceling registrations) is first stored as an event; whenever one is appended, several materialized views (also known as projections or read models) are updated: booking status, charts for the organizer’s dashboard, files for the printer that produces badges. Using events as the source of truth is event sourcing; maintaining separate read-optimized representations derived from the write-optimized one is command query responsibility segregation (CQRS). The terms come from the DDD community; similar ideas exist in state machine replication.

A request from a user is a command; it is validated first, and once it is valid it becomes a fact and the event is added to the log. So the log contains only valid events, and a consumer building a materialized view is not allowed to reject an event. Name events in the past tense, because an event records that something happened; a later change or cancellation is a separate event.

Events also explain themselves: “the booking was canceled” is easier to understand than “the active column on row 4001 of the bookings table was set to false, three rows associated with that booking were deleted from the seat_assignments table, and a row representing the refund was inserted into the payments table.” Those row changes may still happen when a view processes the event, but the reason is clear.

Event sourcing and CQRS · rebuilding from the log

Throw the view away, keep the diary

Yusuf’s dashboard says 12 seats are booked. The venue says 9 people turned up with badges. A bug: the dashboard code forgot that bookings can be canceled. In an ordinary database he would now write a careful repair script. Here he deletes the view, fixes the code, and replays the very same events in the very same order. The right number falls out.

The same trick gives you new views for free: want seats per customer? Run new code over the old log. A mistaken event can’t be erased, but a later event can reverse it, and every view follows along — while the log keeps an honest audit trail of both. And because appending is sequential, a log can absorb a burst of writes while the views catch up at their own pace.

There is one rule you must not break: order. Unlike rows in a star schema’s fact table, events come in many types, and a cancellation only makes sense after the booking it cancels.

What the book says

A key principle of event sourcing is that the materialized views are derived from the event log in a reproducible way: you should always be able to delete the views and recompute them by processing the same events in the same order, using the same code. If the view maintenance code had a bug, delete the view and recompute it with the new code; the bug is also easier to find because you can rerun the code as often as you like.

You can have multiple materialized views optimized for particular queries, stored in the same database as the events or a different one, using any data model, denormalized for fast reads — or even kept only in memory and recomputed when the service restarts. Presenting existing information in a new way just means building a new view from the existing log. You can add new event types or new properties (older events stay unmodified) and chain new behaviors off existing events, such as offering a canceled seat to the next person on the waiting list.

If an event was written in error, a subsequent deletion event reverses it, and downstream views incorporate the deletion automatically; a committed transaction in an update-in-place database is often hard to reverse. Event sourcing can therefore reduce the number of irreversible actions. The log doubles as an audit log, valuable in regulated industries, and logs typically handle higher write throughput than databases thanks to sequential access, absorbing bursts while views catch up.

Like a star schema’s fact table, an event log is a collection of events that happened in the past. But fact table rows all have the same columns and form an unordered collection, while event sourcing has many event types with different properties, and order is important: processing a booking and its cancellation in the wrong order would not make sense.

Event sourcing and CQRS · the downsides

Three traps in the diary

Replaying the log only works if replaying is boring: the same events through the same code must give the same answer, today or next year, and must not do anything to the outside world. Three things break that.

Outside information. If a view converts a price using today’s exchange rate, rebuilding it next week gives a different total. Put the rate in the event, or look up the historical rate for the event’s own timestamp. Personal data. Events are immutable, but people may ask for their data to be deleted. If the log mixes many users, you can’t just drop one person’s events; you can encrypt their details with a per-person key and delete the key (crypto-shredding). Side effects. A view that sends a confirmation email will send it again on every rebuild.

Beneath it all sits one hard requirement: every view must process the events in exactly the same order as they appear in the log.

Try it: in Exchange rate, rebuild on Monday and on Friday with each strategy and compare the totals. In Personal data, press Aaliyah asks to be forgotten with each strategy. In Side effects, press Rebuild the view a few times and watch the inbox, then separate the emails and rebuild again.

What the book says

Be careful if external information is involved. If an event contains a price in one currency that a view converts into another, fetching the fluctuating exchange rate from an external source while processing would give a different result when the view is recomputed on another date. To make event processing deterministic, either include the exchange rate in the event itself or query the historical rate at the event’s timestamp, ensuring the query always returns the same result for the same timestamp.

Immutable events create problems if they contain personal data, since users may exercise their right (e.g., under the GDPR) to request deletion. A per-user log can simply be deleted, but that doesn’t work if the log contains events relating to multiple users. You can store the personal data outside the event, or encrypt it with a key you can later delete (crypto-shredding), but that also makes it harder to recompute derived state.

Reprocessing events requires care if there are externally visible side effects — you probably don’t want to resend confirmation emails every time you rebuild a materialized view.

Event sourcing can be implemented on any database, but EventStoreDB, MartenDB (based on PostgreSQL) and Axon Framework are designed for it; message brokers such as Apache Kafka can store the log, with stream processors keeping views up to date (Chapter 12). The only important requirement is that the event storage system guarantees all materialized views process the events in exactly the same order as they appear in the log — not always easy in a distributed system (Chapter 10).

DataFrames, matrices, and arrays · dataframes

Wrangle the table one command at a time

Mei is a data scientist. She doesn’t write one perfect query and send it to the company database. She copies the data onto her laptop and pokes at it: drop the bad rows, look; join in the movie titles, look; add a column, look; group and average, look. Each step is a small command, and she checks the result before deciding the next one.

That is a DataFrame (pandas in Python, R, Apache Spark, Dask, ArcticDB). It looks like a relational table and offers the same bulk operations — filter rows, apply a function to every row, group and aggregate, join (which DataFrames call merge) — but you drive it with a series of commands instead of one declarative query. That matches how people incrementally “wrangle” data into a form that answers their questions.

What the book says

Some data models are mostly met in analytical or scientific contexts and rarely in OLTP systems: DataFrames and multidimensional arrays of numbers such as matrices. The DataFrame model is supported by R, the Pandas library for Python, Apache Spark, ArcticDB, Dask and other systems. DataFrames are popular with data scientists preparing data for training ML models, and widely used for data exploration, statistical analysis and visualization.

At first glance a DataFrame is like a relational table or a spreadsheet, with relational-like operators for bulk operations: applying a function to all rows, filtering rows by a condition, grouping rows by some columns and aggregating others, and joining one DataFrame with another on a key (what a relational database calls join is typically called merge).

Instead of a declarative query language such as SQL, a DataFrame is generally manipulated through a series of commands that modify its structure and content. This matches the typical workflow of data scientists, who incrementally “wrangle” the data into a form that answers their questions. The manipulations usually happen on the data scientist’s private copy of the dataset, often on their local machine, though the result may be shared.

DataFrame APIs also offer many operations far beyond what relational databases offer, and the model is often used very differently from typical relational data modeling — for example, to turn relational-like data into a matrix.

DataFrames, matrices, and arrays · matrices

From a list of ratings to a grid of numbers

A table of ratings is a list: “user 101 gave movie 13 two stars.” Most machine-learning algorithms want something else — a matrix, one row per user and one column per movie, like a spreadsheet’s pivot table. Most cells stay empty, because most people haven’t rated most movies. That is a sparse matrix, and it is fine.

A matrix holds only numbers, so everything else must be turned into numbers. A date can be scaled to a decimal in a sensible range. A small, fixed set of labels such as a genre becomes one-hot columns: one column per genre, a 1 in the matching one, 0 in the rest — and a movie in two genres simply gets two 1s.

Once everything is numbers, linear algebra takes over. Multiply rows together and you can tell which users rate alike — the start of a recommender.

Try it: in Pivot, press Pivot and watch each rating fly into its cell. In Encode, press One-hot encode to turn genres and dates into numbers, then Make 14 a comedy-drama. In Recommend, pick a user and press Find similar users.

What the book says

A common use of DataFrames is transforming relational-like data into a matrix or multidimensional array, the form many ML algorithms expect. In Figure 3-9 a table of users’ ratings of movies (1 to 5) becomes a matrix with a column per movie and a row per user, similar to a pivot table. The matrix is sparse; it may have many thousands of columns and would not fit well in a relational database, but DataFrames and libraries offering sparse arrays (such as NumPy) handle it easily.

A matrix can contain only numbers. Dates (omitted from the example matrix) could be scaled to floating-point numbers within a suitable range. For columns with a small fixed set of values, such as a movie’s genre, one-hot encoding creates a column per possible value (“comedy,” “drama,” “horror,” etc.) with a 1 in the matching column and 0 in the others; it generalizes easily to movies in several genres.

A matrix of numbers is amenable to linear algebra, the basis of many ML algorithms; the data in Figure 3-9 could be part of a movie recommendation system. DataFrames let data evolve gradually from relational form into a matrix, under the data scientist’s control.

Array databases such as TileDB specialize in large multidimensional arrays of numbers, mostly for scientific datasets: geospatial measurements (raster data on a regularly spaced grid), medical imaging, astronomical observations. DataFrames also represent financial time series, and have been added to batch frameworks such as Spark and Flink (Chapter 11).

Which shape for which data?

The book’s summary, as four cards.

Relational

Over half a century old and still central, especially in warehouses and analytics, where star and snowflake schemas and SQL are everywhere. Best at joins, many-to-one and many-to-many.

Document

For data that comes as self-contained JSON documents, where links from one document to another are rare. A tree you load all at once.

Graph

The opposite direction: anything may relate to everything, and queries may hop many times to find what they want — recursive queries in Cypher, SPARQL or Datalog.

DataFrames

Relational-like tables with huge numbers of columns: the bridge from databases to the matrices behind machine learning, statistics and science.

Event sourcing

An append-only log of immutable events, good for writing; read-optimized materialized views derived from it through CQRS.

Schema: explicit or implicit

Non-relational models usually don’t enforce a schema, but your code still assumes one. The only question is whether it is checked on write or assumed on read.

data model
The shape you choose for your data: tables, documents, a graph, an event log…
declarative query
You describe the result you want; the database decides how to get it.
query optimizer
The part of the database that picks indexes, join algorithms and order of work.
relational model
Data as relations (tables) of tuples (rows). Proposed by Edgar Codd in 1970.
document model
Data as self-contained documents, usually JSON, with things nested inside.
NoSQL / NewSQL
Loose movements around new data models and scale; NewSQL kept the relational model and transactions.
impedance mismatch
The awkward translation between objects in code and rows in tables.
ORM
A library that translates between objects and tables for you.
N+1 query problem
One query for N items, then one more query per item, instead of one join.
one-to-many
One profile has many positions. Together they form a tree.
many-to-one
Many people live in one region.
many-to-many
One person worked at many organizations; one organization had many people.
foreign key
A column holding the ID of a row in another table.
join
Combining rows from two tables by matching IDs.
associative (join) table
A table whose rows each link one ID to another ID.
normalization
Store each human-meaningful fact once; everything else refers to it by ID.
denormalization
Copy the fact into every record that uses it, so reads need no lookup.
hydrating
Turning stored IDs into the full records they point at, in application code.
secondary index
An extra lookup structure so you can find rows by a column other than the key.
star schema
A fact table in the middle, dimension tables around it like the rays of a star.
fact / dimension table
Facts are events (one sale); dimensions are the who, what, where, when, how and why.
snowflake schema
A star whose dimensions are split further into subdimensions.

Fold the dimensions into the fact table: no joins, more storage.
shredding
Splitting a document-shaped thing into several tables.
fractional indexing
Ordering items by numbers you can always squeeze another number between.
schema-on-write
The database checks every record against an explicit schema when it is written.

Nothing is checked on write; the reading code interprets the structure.
locality
Storing together what is read together.

MongoDB’s query language: a list of stages such as $match, $group and $lookup.

The dots and arrows of a graph. Also called nodes and relationships.

A graph stored as each vertex’s neighbour IDs, or as a grid of 0s and 1s.

Vertices and edges that each have a label and key-value properties.

Where an edge starts, and where it points.

A query language for property graphs, built on arrow patterns like (a)-[:WITHIN]->(b).

SQL’s WITH RECURSIVE: a query that keeps adding rows until nothing new appears.
triple
One fact as (subject, predicate, object).
RDF / Turtle
The Semantic Web’s triple data model, and a compact way of writing it.

The query language for RDF triple stores. Pronounced “sparkle.”
Datalog
Facts plus rules that derive new virtual tables; rules may call themselves.
GraphQL
A deliberately limited query language that returns JSON shaped exactly like the request.

Storing every change as an immutable event in an append-only log.

A request that may be rejected, versus a validated fact that already happened.

A read-optimized result derived from the log. Also a projection or read model.

Writing in one representation and reading from others derived from it.
crypto-shredding
Encrypt personal data and delete the key, so the data becomes unreadable.
DataFrame
A table you transform with a series of commands, as in pandas or R.

A grid of numbers where most cells are empty.

One column per category value: a 1 in the matching column, 0 in the rest.
