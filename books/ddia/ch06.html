Replication · why keep copies

Three reasons to keep copies

A library with one copy of a popular book has three problems. Readers on the far side of town walk a long way to reach it. If the book is lost, it’s gone. And only so many people can read it at once. Buy more copies and put them in branch libraries, and all three problems shrink.

Replication does the same with data: the same data sits on several machines, called replicas, connected by a network. The copies bring data closer to users (lower latency). They keep things running when parts fail (availability and durability). And they spread out reads (more throughput). This chapter assumes every machine can hold the whole dataset; splitting data that is too big for one machine is sharding, in the next chapter.

If the data never changed, you would copy it once and be done. All the difficulty is in the changes: every write has to reach every copy. Databases do it in one of three ways: single-leader, multi-leader or leaderless.

Try it: in Closer to users, press Read from every city, then Add nearby copies and read again. In Survive failures, crash machines with one copy and with three. In More reads, slide the number of replicas up until no read has to wait.

What the book says

Replication means keeping a copy of the same data on multiple machines that are connected via a network. Reasons to do it: to keep data geographically close to your users (reducing access latency); to allow the system to continue working even if some of its parts have failed (increasing availability and durability); and to scale out the number of machines that can serve read queries (increasing read throughput).

The chapter assumes the dataset is small enough that each machine can hold a copy of the entire dataset; Chapter 7 relaxes that with sharding (partitioning).

If the data never changed, replication would be easy: copy it to every node once. All the difficulty lies in handling changes to replicated data. Almost all distributed databases use one of three families of algorithms: single-leader, multi-leader and leaderless replication. Trade-offs such as synchronous vs asynchronous replication, and how to handle failed replicas, are often configuration options.

The principles haven’t changed much since they were studied in the 1970s, because the fundamental constraints of networks have remained the same — yet concepts such as eventual consistency still cause confusion.

Replication · backups and replication

A copy is not a backup

Zainab keeps the club’s member list on three laptops that copy each other’s changes instantly. One evening she runs a cleanup script and deletes every member by mistake. Within a second, all three laptops are empty: they copied the mistake perfectly.

Replicas exist to reflect every write quickly, including the bad ones. A backup has a different job: it keeps old snapshots so you can go back in time. The two work together. A snapshot can seed a new replica, and if you also archive the replication log, you can replay the changes made since the last snapshot and stop just before the mistake.

Try it: press Write a row a couple of times, then Oops: DELETE FROM orders and watch it reach every replica. Press Restore. Then switch to Snapshots + archived log and do it again — count the rows you get back.

What the book says

You still need backups if you have replication, because they have different purposes: replicas quickly reflect writes from one node on other nodes, but backups store old snapshots of the data so that you can go back in time. If you accidentally delete some data, replication doesn’t help, since the deletion will also have been propagated to the replicas.

Replication and backups are often complementary. Backups are sometimes part of setting up replication (see Setting Up New Followers); conversely, archiving replication logs can be part of a backup process.

Some databases internally maintain immutable snapshots of past states, a kind of internal backup — but that keeps old versions on the same storage medium as the current state. With a large amount of data, it can be cheaper to keep backups of old data in an object store optimized for infrequently accessed data, and to keep only the current state in primary storage.

Single-leader replication · leaders and followers

One notebook everyone copies

In Mr. Okafor’s class one student, the leader, holds the official notebook. Anyone with news tells the leader, who writes it down first and then reads each new line out to the others, the followers. They copy every line, in exactly the order it was read. If you only want to look something up, you can ask anyone. If you want to add something, only the leader will take it.

In a database, every copy is a replica. Each write goes to the leader, which applies it to its own storage and appends it to its replication log: numbered entries (a log sequence number, LSN) that it streams to every follower. A follower applies the entries strictly in LSN order, so it passes through exactly the states the leader did, just a little later. To clients, followers are read-only.

A sharded database (next chapter) does the same thing once per shard: every shard has exactly one leader, but different shards can have their leaders on different machines.

Try it: press Write a few times and follow the numbered log entries to both followers, line by line in the code. Press Read from a follower, then Write to a follower. Switch to Sharded to see two leaders on two different nodes.

What the book says

Each node that stores a copy of the database is a replica. Every write must be processed by every replica. The most common solution is leader-based (also primary-backup or active/passive) replication: one replica is designated the leader (also primary or source), and clients must send writes to it; it first writes the new data to its local storage.

The others are followers (read replicas, secondaries, hot standbys). Whenever the leader writes, it also sends the change to all followers as part of a replication log or change stream; each follower applies all writes in the same order as they were processed on the leader. Clients can read from the leader or any follower, but writes are accepted only by the leader. If the database is sharded, each shard has one leader, and different shards may have their leaders on different nodes.

It is built into PostgreSQL, MySQL, Oracle Data Guard and SQL Server’s Always On availability groups; used by MongoDB and DynamoDB, by message brokers such as Kafka, replicated block devices such as DRBD, and some network filesystems. Consensus algorithms such as Raft (used in CockroachDB, TiDB, etcd and RabbitMQ quorum queues) are also single-leader and elect a new leader automatically.

Older documents call this master–slave replication; the term means the same but should be avoided, as it is widely considered offensive.

Single-leader replication · synchronous versus asynchronous

Do you wait for your friend to finish copying?

Lucía tells the class leader some news. Should the leader say “got it, it’s official” right away, or first wait until a follower has copied it into their notebook too? Waiting is slower — and if that follower has fallen asleep, Lucía waits forever. Not waiting is fast, but if the leader’s notebook falls into a puddle a moment later, the news is gone, even though Lucía was told it was saved.

With synchronous replication the leader waits for a follower’s acknowledgement before reporting success, so that follower is guaranteed to be up to date. With asynchronous replication it sends the change and doesn’t wait. Making every follower synchronous would let any single outage halt all writes, so real systems use semi-synchronous (one synchronous follower, the rest asynchronous) or wait for a majority (3 of 5), which is a quorum.

Try it: in each mode press Write and read the timeline left to right. Then press Stall follower 1 and write again. In All async, press Crash leader after OK before writing and watch a confirmed write disappear.

What the book says

In Figure 6-2 replication to follower 1 is synchronous: the leader waits until follower 1 confirms it received the write before reporting success to the user and before making the write visible to other clients. Replication to follower 2 is asynchronous (nonblocking): the leader sends the message but doesn’t wait.

Most systems apply changes to followers in less than a second, but there is no guarantee: followers might fall behind by several minutes or more if recovering from a failure, if the system operates near maximum capacity, or if there are network problems.

A synchronous follower is guaranteed to have an up-to-date copy; but if it doesn’t respond, the leader must block all writes. So it is impracticable for all followers to be synchronous. In practice one follower is synchronous and the others asynchronous; if the synchronous one becomes unavailable or slow, an asynchronous follower is made synchronous. That guarantees an up-to-date copy on at least two nodes, and is sometimes called semisynchronous. Some systems update a majority (e.g., three out of five, including the leader) synchronously — an example of a quorum.

Fully asynchronous replication means a write is not guaranteed to be durable even if it was confirmed to the client: if the leader fails unrecoverably, unreplicated writes are lost. In exchange, the leader can keep processing writes even if all followers have fallen behind. It is nevertheless widely used, especially with many followers or geographically distributed ones.

Single-leader replication · setting up new followers

The new kid copies the notebook

Kenji joins the class halfway through term and needs a copy of the official notebook. If he copies it page by page while the leader keeps writing, his early pages come from Monday and his later pages from Wednesday — a line on page 9 may mention a name that page 2 never got. Stopping the whole class while he copies would work, but nobody could add anything for an hour.

Databases do it without downtime. Take a consistent snapshot of the leader (no global lock), and remember the exact position in the replication log it corresponds to. Copy the snapshot to the new node. Then the follower asks the leader for every change since that position, works through the backlog, and is caught up, after which it follows the live stream like any other follower. If snapshots and the log are already archived in object storage, the first two steps are just a download.

Try it: in Copy the files, press Copy files and read the verdict; then turn on Lock writes and copy again. In the other two modes press Next step four times and follow the lit line in the code.

What the book says

New followers are needed to increase the number of replicas or replace failed nodes. Simply copying data files is typically not sufficient: clients keep writing, so a standard file copy would see different parts of the database at different points in time, and the result might not make sense. Locking the database would make the copy consistent but goes against the goal of high availability.

Conceptually: (1) take a consistent snapshot of the leader’s database at some point in time, if possible without locking the entire database — most databases have this, since backups need it; in some cases third-party tools are needed, such as Percona XtraBackup for MySQL. (2) Copy the snapshot to the new follower. (3) The follower requests all data changes since the snapshot, which requires the snapshot to be associated with an exact position in the leader’s replication log: PostgreSQL calls it the log sequence number; MySQL has binlog coordinates and global transaction identifiers (GTIDs). (4) When it has processed the backlog, it has caught up and continues to process changes as they happen.

The practical steps vary significantly: in some systems the process is fully automated, in others it is a somewhat arcane multistep workflow performed manually by an administrator.

Archiving the replication log to an object store along with periodic snapshots is a good way to implement backups and disaster recovery, and steps 1 and 2 can then be done by downloading those files. WAL-G does this for PostgreSQL, MySQL and SQL Server; Litestream does the equivalent for SQLite.

Setting up new followers · databases backed by object storage

The database that lives in a bucket

Picture a town library that keeps only today’s newspapers on its own shelves and sends everything else to a huge, cheap, fireproof warehouse across town. Fetching from the warehouse is slow, and every delivery van costs a fee, so the librarian waits until a whole crate is full before sending one.

Cloud object stores such as Amazon S3 are that warehouse: inexpensive, replicated across zones or regions, and very durable. Many databases now keep their live data there. But every API call costs money and takes far longer than a local disk, so writes get batched, which adds even more latency. Objects are usually immutable, so changing a few bytes in the middle of a big one means rewriting it.

The store’s conditional write — essentially a compare-and-set — is a gift: “replace this object only if it is still at version 4” lets two nodes race for leadership with exactly one winner. Taken to the extreme, a zero-disk architecture keeps nothing durable on the node at all: disks and memory are only a cache.

Try it: in Batching, press Stream 40 writes with 1 write per PUT, then drag the slider to 20 and stream again — watch the toy bill and the toy latency trade places. In Conditional write, press Race for leadership, then Old leader wakes up. In Architectures, write a row and press Replace the node for each layout.

What the book says

Object storage can be used for more than archiving. Many databases are beginning to use object stores such as Amazon S3, Google Cloud Storage and Azure Blob Storage to serve data for live queries. Benefits: it is inexpensive, so data that’s queried less often can sit on cheaper, higher-latency storage while the working set is served from memory, SSDs and NVMe; object stores provide multi-zone, dual-region or multi-region replication with very high durability (and let databases bypass inter-zone network fees); their conditional write feature — essentially a compare-and-set (CAS) operation — can implement transactions and leadership election; and keeping many databases’ data in one object store, in open formats such as Parquet and Iceberg, simplifies data integration.

The trade-offs: much higher read and write latencies than local disks or virtual block devices such as Amazon EBS; a per-API-call fee that forces batching, which increases latency further; objects are often immutable, making random writes in a large object extremely resource-intensive; and many stores lack standard filesystem interfaces. FUSE lets operators mount buckets as filesystems, but many FUSE interfaces lack POSIX features such as nonsequential writes or symlinks.

Some systems use a tiered storage architecture: less frequently accessed data on object storage, new or hot data on SSDs, NVMe or in memory. Others make object storage the primary tier but keep the WAL on a separate low-latency system (such as Amazon EBS or Neon’s Safekeepers). A zero-disk architecture (ZDA) persists all data to object storage and uses disks and memory strictly for caching, so nodes have no persistent state — which dramatically simplifies operations.

WarpStream, Confluent Freight, Buf’s Bufstream and Redpanda Serverless are Kafka-compatible systems built with a zero-disk architecture; so is nearly every modern cloud data warehouse, Turbopuffer (a vector search engine) and SlateDB (a cloud native LSM storage engine).

Handling node outages · follower failure: catch-up recovery

The student who missed a week of class

Any machine can go down: a crash, a power cut, or simply a planned reboot to install a kernel security patch. The goal is that the system as a whole keeps running, and that rebooting one node at a time needs no downtime at all.

A follower is like a student who writes in their notebook the number of the last lesson they copied. After being off sick, they don’t start over — they ask the teacher for “everything after lesson 57.” A follower does the same: on its own disk it keeps a log of the changes it has applied, so after a restart it knows its last log position, asks the leader for every change after it, applies the backlog, and is caught up.

Simple, but not free. A big backlog means heavy load on both the follower and the leader that streams it. And the leader may only delete old log entries once every follower has confirmed them — so a follower that stays away for days forces a nasty choice: keep the log and risk filling the leader’s disk, or delete it and rebuild that follower from a backup.

Try it: press Write ×3, then Crash follower and write some more. Press Restart follower and follow the lit line as it catches up. Try Reboot for a patch too. Then open Long outage, slide the outage longer and flip between Keep the log and Delete old log.

What the book says

Any node can go down, unexpectedly because of a fault, or because of planned maintenance (e.g. rebooting a machine to install a kernel security patch). Being able to reboot individual nodes without downtime is a big advantage for operations and maintenance. The goal is to keep the system as a whole running despite individual node failures, and to keep the impact of a node outage as small as possible.

On its local disk, each follower keeps a log of the data changes it has received from the leader. If a follower crashes and restarts, or the network between it and the leader is temporarily interrupted, it knows from its log the last transaction processed before the fault. It connects to the leader and requests all the changes that occurred while it was disconnected; once applied, it has caught up and continues receiving the stream of changes as before.

Recovery can be challenging for performance: with high write throughput, or a follower offline for a long time, there may be a lot of writes to catch up on, putting high load on both the recovering follower and the leader sending the backlog.

The leader can delete its log of writes after all followers have confirmed processing it. If a follower is unavailable for a long time, the leader must choose: retain the log until the follower recovers (at the risk of running out of disk space), or delete the log the follower hasn’t acknowledged (so the follower can’t recover from the log and must be restored from a backup).

Handling node outages · leader failure: failover

When the captain falls over

If a follower dies, the team barely notices. If the captain dies, someone must take over: a follower is promoted to leader, clients must send their writes to it, and the other followers must start copying from it. That’s failover. A human can do it by hand, or the system can do it automatically in three steps.

1 · Detect. Nothing tells you “the leader crashed” — it could be a crash, a power cut or a broken network. So nodes keep pinging each other, and one that stays silent longer than a timeout (say 30 seconds) is presumed dead. 2 · Choose. The best candidate is the follower with the most up-to-date copy, the highest log position; getting all nodes to agree on it is a consensus problem. 3 · Reconfigure. Clients send writes to the new leader, and if the old leader comes back it must accept that it is now a follower.

The timeout is a real trade-off. Too long, and a real crash means a long outage. Too short, and a leader that is merely slow — a load spike, a network glitch — gets replaced for nothing, adding a failover to a system that is already struggling.

Try it: press Leader crashes and follow the three steps, then Old leader returns. Now press Load spike with the timeout at 30 s, slide it down to 10 s and press it again. Finally try Planned handoff.

What the book says

Handling a failure of the leader is trickier: one of the followers is promoted to be the new leader, clients are reconfigured to send their writes to it, and the other followers start consuming data changes from it. This is failover. It can happen manually (an administrator is notified and takes the necessary steps) or automatically.

An automatic failover usually consists of: (1) Determining that the leader has failed — there is no foolproof way of detecting what went wrong, so most systems use a timeout: nodes frequently bounce messages back and forth, and a node that doesn’t respond for some period, say 30 seconds, is assumed dead. A leader taken down for planned maintenance can instead trigger a safe handoff. (2) Choosing a new leader, by an election among the remaining replicas or by a previously established controller node; the best candidate is usually the replica with the most up-to-date changes, to minimize data loss. Getting all nodes to agree is a consensus problem (Chapter 10). (3) Reconfiguring the system so clients send writes to the new leader; if the old leader comes back it might still believe it is the leader, and the system must make sure it becomes a follower.

Choosing the timeout is tricky: longer means a longer time to recovery when the leader fails; too short causes unnecessary failovers, e.g. when a temporary load spike pushes response time above the timeout or a network glitch delays packets. If the system is already struggling with high load or network problems, an unnecessary failover is likely to make things worse. For these reasons some operations teams prefer to perform failovers manually, even if the software supports automatic failover.

Handling node outages · failover is fraught with things that can go wrong

Four ways a new captain makes things worse

With asynchronous replication, the dead leader may have confirmed writes that never reached anyone. Promote a follower and those writes simply aren’t there. When the old leader rejoins, its extra writes clash with the new leader’s, and the usual fix is to throw them away: writes the clients were told were committed turn out not to be durable.

It gets worse when another system has already seen the lost data. In one GitHub incident, a lagging MySQL follower was promoted; its autoincrement counter was behind, so it handed out primary keys the old leader had already used — and those keys were also used in Redis. Some private data was shown to the wrong users.

Sometimes two nodes both believe they lead: split brain. If both accept writes, data gets lost or corrupted. A safety catch that shuts one down is called fencing, but a careless one can shut down both, and it may come too late. The single most important rule: promote the most up-to-date follower.

Try it: in each of the first three modes press Step until the story ends (or Play). In Split brain, switch the fencing between careful and careless. In Pick a fresh one, tap a follower to promote it, then switch to Semi-synchronous.

What the book says

If asynchronous replication is used, the new leader may not have received all the writes from the old leader before it failed. If the former leader rejoins after a new leader has been chosen, the new leader may have received conflicting writes in the meantime. The most common solution is to discard the old leader’s unreplicated writes — so writes you believed to be committed weren’t durable after all.

Discarding writes is especially dangerous if other storage systems outside the database are coordinated with its contents. In one incident at GitHub, an out-of-date MySQL follower was promoted to leader. The new leader’s autoincrement counter lagged behind the old leader’s, so it reused primary keys previously assigned by the old leader. These keys were also used in a Redis store, so the reuse caused inconsistency between MySQL and Redis, and some private data was disclosed to the wrong users.

In certain fault scenarios two nodes could both believe they are the leader: split brain. If both accept writes with no process for resolving conflicts, data is likely to be lost or corrupted. As a safety catch some systems shut down one node if two leaders are detected; if not carefully designed, both nodes can end up shut down. And by the time split brain is detected, data may already be corrupted. Guarding against split brain by limiting or shutting down old leaders is called fencing (discussed further on p. 373). These problems have no easy solutions, which is why some teams prefer manual failover.

The most important thing with failover is to pick an up-to-date follower. With synchronous or semisynchronous replication, that is the follower the old leader waited for; with asynchronous replication, pick the follower with the highest log sequence number. Losing a fraction of a second’s worth of writes may be tolerable; picking a follower that is behind by several days could be catastrophic.

Failover gone wrong
Implementation of replication logs · statement-based replication

Sending the recipe instead of the cake

How does the leader actually describe a change to its followers? The simplest idea: send the statement itself. Every INSERT, UPDATE and DELETE the leader executes goes into a statement log, and each follower parses and runs the same SQL as if a client had sent it. Compact — like mailing a recipe instead of a cake.

But a recipe that says “add a random spice” or “bake until it’s now” comes out differently in every kitchen. NOW() and RAND() give each replica a different value. Statements that use an autoincrement column, or depend on existing data like UPDATE … WHERE, must run in exactly the same order everywhere — awkward when many transactions run at once. And triggers, stored procedures and user-defined functions can cause different side effects on each replica.

There are workarounds: the leader can replace every nondeterministic call with the fixed value it got when it logs the statement. Executing deterministic statements in a fixed order is the idea behind state machine replication.

Try it: pick a case and press Run on both. Watch the follower’s rows turn coral where they differ. Then switch the fix on (the second button of the small toggle) and run it again. Follow the lit statement in the log underneath.

What the book says

In the simplest case, the leader logs every write request (statement) that it executes and sends that statement log to its followers. For a relational database, every INSERT, UPDATE or DELETE statement is forwarded, and each follower parses and executes it as if it had been received from a client.

It can break down: a statement that calls a nondeterministic function, such as NOW to get the current date and time or RAND to get a random number, is likely to generate a different value on each replica. Statements using an autoincrementing column, or depending on existing data (UPDATE … WHERE <some condition>), must be executed in exactly the same order on each replica, which is limiting with multiple concurrently executing transactions. Statements with side effects (triggers, stored procedures, user-defined functions) may cause different side effects on each replica unless the side effects are absolutely deterministic.

Workarounds exist — the leader can replace any nondeterministic function call with a fixed return value when the statement is logged. Executing deterministic statements in a fixed order resembles event sourcing, and is also known as state machine replication.

Statement-based replication was used in MySQL before version 5.1. It is still sometimes used, as it is quite compact, but by default MySQL now switches to row-based replication if there is any nondeterminism in a statement. VoltDB uses statement-based replication and makes it safe by requiring transactions to be deterministic. Because determinism is hard to guarantee in practice, many databases prefer other methods.

Implementation of replication logs · write-ahead log shipping

Copying the notebook ink blot by ink blot

A B-tree storage engine already keeps a write-ahead log (WAL): before it touches the tree, it writes down every modification, so it can repair itself after a crash. That log holds everything needed to rebuild the indexes and the heap. So why not reuse it? Besides writing it to disk, the leader sends the very same log over the network, and the follower replays it into exactly the same files, byte for byte.

The catch: the WAL speaks the storage engine’s private language — which bytes changed in which disk block. It doesn’t say “Zoe renamed herself”; it says “block 2, offset 0x1a0: 5a 6f.” That ties replication tightly to the storage format. If a new database version lays out its pages differently, a follower on the new version can’t read the old leader’s WAL.

That matters operationally. The dream upgrade: upgrade the followers first, fail over to an upgraded one, then upgrade the old leader — zero downtime. With WAL shipping, the versions usually can’t be mixed, so upgrades need downtime.

Try it: press Run a write a few times and watch the WAL records turn into identical bytes on the follower. Then switch to Rolling upgrade, press Upgrade the follower and run another write. Finally, try Upgrade with downtime.

What the book says

A write-ahead log is needed to make B-tree storage engines robust: every modification is first written to the WAL so the tree can be restored to a consistent state after a crash. Since the WAL contains all the information necessary to restore the indexes and heap, the exact same log can build a replica on another node: besides writing the log to disk, the leader sends it across the network to its followers, which build a copy of the exact same files.

This method is used in PostgreSQL and Oracle, among others. The main disadvantage is that the log describes the data at a very low level — which bytes were changed in which disk blocks — making replication tightly coupled to the storage engine. If the database changes its storage format from one version to another, it is typically not possible to run different versions on the leader and the followers.

That has a big operational impact. If the protocol allows a follower to run newer software than the leader, you can do a zero-downtime upgrade by first upgrading the followers and then performing a failover to make an upgraded node the new leader. If it does not allow the mismatch, as is often the case with WAL shipping, upgrades require downtime.

Shipping disk-block changes
Implementation of replication logs · logical (row-based) log replication

Write down what changed, not where the ink went

Imagine telling a friend how to update their copy of the class list. You could say “rub out the third line on page 7 and write these letters there” — but only if their notebook has exactly your page layout. Or you could say “Ravi moved to Lagos.” That works in any notebook.

A logical log is the second kind. It records each change at the level of a row: an insert carries all the new column values, an update names the row and its new values, a delete names the row by its primary key (or, if the table has none, by all its old values). A transaction that touches three rows becomes three records followed by a commit record. The storage engine’s own byte-level log stays private.

Because the log no longer depends on the disk layout, leader and followers may run different versions of the database — so you can upgrade with no downtime. And because it is easy to read, other systems can follow it too: change data capture.

Try it: in Row log, press Run transaction and watch each row change fly to the follower; notice the follower’s rows stay yellow until the COMMIT arrives. Flip Primary key to no and run again. Then step through a Rolling upgrade, and in Change data capture switch the feed to raw WAL bytes.

What the book says

An alternative to shipping the storage engine’s log is to use different log formats for replication and for the storage engine, decoupling the replication log from the storage engine internals. This kind of replication log is called a logical log, to distinguish it from the storage engine’s (physical) data representation.

A logical log for a relational database is usually a sequence of records describing writes at the granularity of a row: for an inserted row, the new values of all columns; for a deleted row, enough information to uniquely identify it — typically the primary key, but if the table has no primary key, the old values of all columns; for an updated row, enough to identify it plus the new values of all columns (or at least the changed ones). A transaction that modifies several rows generates several records, followed by a record indicating that the transaction was committed.

MySQL, when configured for row-based replication, keeps a separate logical replication log, the binlog, in addition to the WAL. PostgreSQL implements logical replication by decoding the physical WAL into row insertion/update/delete events.

Since a logical log is decoupled from storage engine internals, it can more easily be kept backward compatible, allowing leader and followers to run different versions of the database software — which enables upgrading with minimal downtime. It is also easier for external applications to parse, for example to send the contents of a database to a data warehouse or to a specialized system for custom indexes and caches. This is called change data capture, and it returns in Chapter 12.

Problems with replication lag · read scaling and eventual consistency

Many copies, each a little behind

A popular website is mostly reading: thousands of people look at a post for every one who writes a comment. With one leader, writes must go to the leader — but reads can go anywhere. So add followers and spread the reads across them. Need more read capacity? Add more followers. This is the read-scaling architecture.

It only really works if replication is asynchronous. If the leader had to wait for every follower, then any one follower being down would stop all writes — and the more followers you have, the more likely one of them is down right now.

The price: a follower can be behind. Ask the leader and a follower the same question at the same moment and you may get two different answers. Stop writing and wait, and the followers catch up — that’s eventual consistency. The delay is the replication lag: usually a fraction of a second, but nothing stops it from growing to seconds or minutes when a system is overloaded or the network is struggling.

What the book says

Besides tolerating node failures, replication is wanted for scalability (more requests than one machine can handle) and latency (replicas geographically closer to users). Leader-based replication sends all writes through one node, but read-only queries can go to any replica. For workloads of mostly reads with a small percentage of writes — often the case for online services — you can create many followers and distribute reads across them, removing load from the leader and serving reads from nearby replicas.

In this read-scaling architecture you increase read capacity simply by adding followers, but realistically only with asynchronous replication: synchronously replicating to all followers would let a single node failure or network outage make the entire system unavailable for writing, and the more nodes you have, the likelier one is down.

An application reading from an asynchronous follower may see outdated information. Run the same query on the leader and a follower at the same time and you may get different results. This is temporary — stop writing and wait, and the followers eventually catch up — so the effect is called eventual consistency. The term was coined by Douglas Terry et al. and popularized by Werner Vogels, and became the battle cry of many NoSQL projects; but followers in an asynchronously replicated relational database have the same characteristics.

“Eventually” is deliberately vague: there is no limit to how far a replica can fall behind. The replication lag may be a fraction of a second in normal operation, but near capacity or with a network problem it can easily grow to several seconds or even minutes — and then the inconsistencies become a real problem for applications.

What the book says

Many applications let the user submit data and then view what they submitted. New data must go to the leader, but the view can be read from a follower. With asynchronous replication, if the user views the data shortly after writing, the new data may not have reached the replica yet, and it looks as though their data was lost (Figure 6-3).

Read-after-write consistency, also known as read-your-writes consistency, guarantees that if the user reloads the page, they will always see any updates they submitted themselves. It makes no promises about other users.

Techniques: read anything the user may have modified from the leader or a synchronously updated follower — e.g. always read the user’s own profile from the leader and other users’ profiles from a follower. If most things are editable by the user, that negates read scaling, so use other criteria: for one minute after the last update, make all reads from the leader, or prevent queries on any follower more than one minute behind. Or the client remembers the timestamp of its most recent write, and the replica serving the user’s reads must reflect updates at least until that timestamp; if not, another replica handles the read or the query waits. The timestamp can be logical (such as the log sequence number) or the actual system clock, in which case clock synchronization becomes critical.

If replicas are distributed across regions, any request that needs to be served by the leader must be routed to the region that contains the leader.

Replication lag · regions and availability zones

One building, one city, or two cities?

Where you put your copies decides what disaster they survive. A cloud region is one geographic place — say, around one city. Inside it are several availability zones (or just zones): separate datacenters in separate buildings, each with its own power and cooling.

Zones in the same region are joined by very fast network links — so fast that most distributed systems can spread their nodes across zones as if they were in one. That buys survival when a whole zone goes dark. But if the entire region goes down, every zone in it goes too. To survive that, you must spread across regions, and pay with higher latency, lower throughput and a bigger cloud networking bill.

What the book says

A zone is a separate datacenter in a separate physical facility with its own power, cooling, and so on.

Zones in the same region are connected by very high-speed network connections, with latency low enough that most distributed systems can run with nodes spread across multiple zones as though they were in a single zone.

Problems with replication lag · monotonic reads

The comment that came and went

User 1234 posts a comment. User 2345 refreshes the page, and the request lands on a follower that already has it: one comment. They refresh again; this time a random load balancer sends them to a follower that is further behind. The comment is gone. Time seems to have run backwards.

Seeing old data isn’t the problem — user 2345 wouldn’t have known about the comment at all. Seeing new data and then older data is what confuses people. Monotonic reads rules that out: in a sequence of reads, you never read older data after newer data. It is weaker than strong consistency, but stronger than eventual consistency.

The simple fix: always send a user to the same replica, chosen from a hash of their user ID rather than at random. Different users can use different replicas. If that replica fails, the user has to be rerouted — and may step back in time once.

What the book says

A second anomaly of reading from asynchronous followers is that a user can see things moving backward in time. In Figure 6-4, user 2345 makes the same query twice, first to a follower with little lag, then to one with greater lag — quite likely if the user refreshes a web page and each request is routed to a random server. The first query returns a comment recently added by user 1234; the second returns nothing, because the lagging follower hasn’t picked up that write yet.

Monotonic reads guarantee this anomaly does not happen. It’s a lesser guarantee than strong consistency, but stronger than eventual consistency. When you read data you may see an old value; monotonic reads only mean that if one user makes several reads in sequence, they will not read older data after having previously read newer data.

One way of achieving it is to make sure each user always reads from the same replica (different users can read from different replicas) — for example, choosing the replica from a hash of the user ID rather than randomly. If that replica fails, the user’s queries need to be rerouted to another replica.

Problems with replication lag · consistent prefix reads

Answers before questions

Mr. Poons asks Mrs. Cake a question, and she answers. Mrs. Cake heard the question first, so her answer depends on it — there is a causal dependency between the two lines.

Now a third person listens in by reading from followers. In a sharded database, the question and the answer can be stored in different shards, and each shard replicates on its own with its own lag. If Mr. Poons’s shard is slow, the listener hears the answer first. It sounds as if Mrs. Cake can see the future.

The guarantee that stops this is called consistent prefix reads: if writes happen in some order, everyone who reads them sees them in that order. A single replication log gives you that for free, because each follower applies the log in order. Independent shards have no global order. The simple fix is to put causally related writes in the same shard.

What the book says

The third replication-lag anomaly is a violation of causality. Mr. Poons: “How far into the future can you see, Mrs. Cake?” Mrs. Cake: “About 10 seconds usually, Mr. Poons.” If a listener reads Mrs. Cake’s words through a follower with little lag and Mr. Poons’s through one with a longer lag, the answer arrives before the question. “Such psychic powers are impressive but very confusing.”

Consistent prefix reads: “if a sequence of writes happens in a certain order, anyone reading those writes will see them appear in the same order.”

This is a particular problem in sharded (partitioned) databases. If the database always applies writes in the same order, reads always see a consistent prefix. But in many distributed databases different shards operate independently, so there is no global ordering of writes: a reader may see some parts of the database in an older state and some in a newer state.

One solution is to make sure causally related writes go to the same shard — though in some applications that cannot be done efficiently. Some algorithms explicitly keep track of causal dependencies (see “The happens-before relation and concurrency”).

Problems with replication lag · solutions for replication lag

What if the lag were an hour?

Most of the time followers are a fraction of a second behind, and every screen of your app looks fine. The useful question is the uncomfortable one: what does each screen do if the lag grows to a minute, or an hour? If the answer is “no problem,” great. If not, you need a stronger guarantee — and quietly pretending replication is synchronous when it isn’t will catch up with you later.

One way out is app-level tricks: read your own profile from the leader, pin each user to one replica, track causality yourself. They work, but every new feature needs its own rule, and the code is complex and easy to get wrong.

The other way is a database that promises strong consistency — linearizability plus ACID transactions — so you can treat it as if it were one node. These NewSQL systems now scale too. Weaker replication still has fans, because it keeps answering through network interruptions and has lower overhead.

What the book says

With an eventually consistent system, think about how the application behaves if the replication lag increases to several minutes or even hours. If the answer is “no problem,” that’s great; if the result is a bad experience for users, design the system to provide a stronger guarantee, such as read-after-write. “Pretending that replication is synchronous when in fact it is asynchronous is a recipe for problems down the line.”

An application can provide a stronger guarantee than the underlying database — for example by performing certain kinds of reads on the leader or a synchronously updated follower — but dealing with these issues in application code is complex and easy to get wrong.

The simplest programming model is a database that provides a strong consistency guarantee for replicas, such as linearizability (Chapter 10), and supports ACID transactions (Chapter 8): you can mostly ignore replication and treat the database as if it had just a single node. In the early 2010s the NoSQL movement argued that these features limited scalability; since then a number of databases have offered strong consistency and transactions together with fault tolerance, high availability and scalability — the trend known as NewSQL, which is less about SQL than about new approaches to scalable transaction management.

Some applications still choose replication with weaker consistency guarantees: they can offer stronger resilience in the face of network interruptions and have lower overheads compared to transactional systems.

Multi-leader replication · more than one leader

Two leaders, one cable

Single-leader replication has one big weakness: every write must reach the leader. If the network between you and the leader breaks, you can’t write at all.

The natural fix is to let more than one node accept writes. Each leader applies a write, then forwards the change to the other leaders — so each leader is also a follower of the others. That’s multi-leader replication, also called active/active or bidirectional replication.

Just like before, the copying between leaders can be synchronous or asynchronous. Synchronous turns out to be a disguise: if A must wait for B, cutting the cable stops writes at A, which is just single-leader with B in charge. The interesting kind is asynchronous: each leader keeps accepting writes while the cable is down, and they swap changes once it’s back.

Try it: press Write at A and Write at B a few times, then Cut the link and keep writing. Compare Synchronous with Asynchronous, and finally press Restore the link. Follow the lit lines in the code.

What the book says

Single-leader replication has one major downside: all writes must go through the one leader. If you can’t connect to the leader for any reason — for example a network interruption between you and the leader — you can’t write to the database.

A natural extension is to allow more than one node to accept writes. Replication happens the same way: each node that processes a write must forward that data change to all the other nodes. This is a multi-leader configuration, also known as active/active or bidirectional replication; each leader simultaneously acts as a follower to the other leaders.

There is again a choice between synchronous and asynchronous. With two leaders A and B, if writes are synchronously replicated from A to B and the network between them is interrupted, you can’t write to A until the connection is restored. Synchronous multi-leader replication is therefore very similar to single-leader replication where B is the leader and A simply forwards write requests to B — so the book treats it as equivalent and focuses on asynchronous multi-leader replication, in which any leader can process writes even when its connection to the other leaders is interrupted.

Multi-leader replication · geographically distributed operation

A leader in every region

Inside one region, multi-leader replication is rarely worth the trouble. It earns its keep when your replicas live in several regions — to survive losing a whole region, or to be close to users. That’s a geo-distributed (geo-replicated) setup.

With a single leader, every write from Tokyo crosses the internet to the leader’s region and back. With a leader in each region, Tokyo’s write is handled in Tokyo, and the leaders copy their changes to each other asynchronously in the background. Within each region it’s ordinary leader–follower replication, often with followers in another zone.

Compare the two on four things: performance, regional outages and network problems — where multi-leader shines — and consistency, where it can’t promise that a username is unique or a balance never goes negative. Two leaders can each accept a write that is fine on its own and broken together.

What the book says

It rarely makes sense to use multi-leader within a single region. With replicas in several regions (a geographically distributed, geo-distributed or geo-replicated setup), single-leader means all writes go through the leader’s region; multi-leader allows a leader in each region, with regular leader–follower replication inside each region and each region’s leader replicating its changes to the leaders in other regions.

  • Performance: with a single leader every write must go over the internet to the leader’s region; with multi-leader every write is processed locally and replicated asynchronously, hiding the inter-region delay from users.
  • Tolerance of regional outages: single-leader can fail over to a follower in another region; with multi-leader each region continues independently and replication catches up when the offline region returns.
  • Tolerance of network problems: traffic between regions is less reliable than within one; single-leader is very sensitive to the inter-region link, while asynchronous multi-leader keeps processing writes in each region during an interruption.
  • Consistency: single-leader can provide strong guarantees such as serializable transactions. Multi-leader can’t guarantee that a bank account won’t go negative or that a username is unique — a fundamental limitation of distributed systems.

Geographically distributed operation · multi-leader replication topologies

Who passes the news to whom?

With two leaders there’s only one sensible wiring: each sends its writes to the other. With five, you have to decide the replication topology — the paths a write travels to reach every leader.

In all-to-all, every leader sends its writes straight to every other leader. In a circular topology, each leader passes writes (its own and those it received) to the next one around the ring. In a star, one root node forwards writes to everyone else; a star can grow into a tree.

In a ring or a star, a write has to be forwarded through other nodes. So how does it ever stop? Each node has a unique ID, and every write carries the IDs of the nodes it has passed through. A node that sees its own ID on a change ignores it — it has already processed it.

Try it: press Write at L1 in each topology (or tap any leader to write there), and watch the tags on the messages grow. Then switch to Circular, press Loop guard: on to turn it off, and write again.

What the book says

A replication topology describes the communication paths along which writes are propagated from one node to another. With two leaders only one topology is plausible; with more, various topologies are possible (Figure 6-7).

The most general is all-to-all: every leader sends its writes to every other leader. In the circular topology each node receives writes from one node and forwards those writes (plus any writes of its own) to one other node. In the popular star topology one designated root node forwards writes to all the other nodes; a star can be generalized to a tree. (A star-shaped network topology is unrelated to a star schema, which describes the structure of a data model.)

In circular and star topologies a write may need to pass through several nodes before it reaches all replicas, so nodes must forward data changes they receive. To prevent infinite replication loops, each node is given a unique identifier, and in the replication log each write is tagged with the identifiers of all the nodes it has passed through. A node that receives a data change tagged with its own identifier ignores it, because it knows it has already been processed.

Geographically distributed operation · problems with different topologies

Messages that overtake each other

Rings and stars have a weak spot: one broken node can stop the news from reaching the nodes behind it. You could rewire around it, but in most deployments someone has to do that by hand. A densely connected topology like all-to-all has no such single point of failure — messages take other paths.

All-to-all has its own trap. Some links are faster than others, so one replication message can overtake another. Ana inserts a row on leader 1; Ben, on leader 3, sees it and updates it. Leader 2’s link from leader 1 is congested, so it receives the update first — an update to a row that doesn’t exist yet.

This is a causality problem: the update depends on the insert. Stamping each write with a clock time doesn’t fix it, because the leaders’ clocks can’t be trusted to agree. What works is tracking dependencies explicitly — with version vectors, met again later in this chapter.

What the book says

With circular and star topologies, if just one node fails it can interrupt the flow of replication messages between other nodes, leaving them unable to communicate until the node is fixed. The topology could be reconfigured to work around the failed node, but in most deployments that would have to be done manually. A more densely connected topology such as all-to-all is more fault tolerant, because messages can travel along different paths, avoiding a single point of failure.

All-to-all has issues too: some network links may be faster than others (e.g., because of network congestion), so some replication messages may “overtake” others. In Figure 6-8, client A inserts a row on leader 1 and client B updates that row on leader 3, but leader 2 may first receive the update — from its point of view an update to a row that does not exist — and only later the insert.

This is a problem of causality, similar to consistent prefix reads: the update depends on the prior insert, so all nodes must process the insert first. Simply attaching a timestamp to every write is not sufficient, because clocks cannot be trusted to be sufficiently in sync to order these events correctly (Chapter 9). Version vectors can be used instead (see “Detecting Concurrent Writes”).

Many multi-leader replication systems don’t use good techniques for ordering updates. If you use multi-leader replication, be aware of these issues, read the documentation carefully, and test your database thoroughly to make sure it really provides the guarantees you believe it to have.

Sync engines · pros and cons of sync engines

Fast, offline, simple — if it fits

Most web apps today keep almost nothing on your device. Every time you open a page or press a button, they ask a server and wait. A sync-engine app is built the other way round: the data lives on the device, the screen reads and writes that local copy, and talking to the server happens in a background process.

That buys three things. Speed: a local write can be drawn in the very next frame — within 16 ms on a 60 Hz screen — instead of after a network round trip. Offline for free: being offline is just a very large network delay, so there’s no separate offline mode to build. Simpler code: every service call can fail and needs an error screen, but local reads and writes almost never fail; combine that with reactive UI and other people’s edits simply appear.

The catch is size. It works best when everything the user might need is downloaded in advance. Your own files: fine. A shop’s entire product catalog: it won’t fit, and it shouldn’t.

What the book says

The dominant way of building web apps today keeps very little persistent state on the client and makes requests to a server whenever data needs to be displayed or updated. With a sync engine you have persistent state on the client, and communication with the server is moved into a background process.

  • Local data means the UI can respond much faster; some apps aim to respond in the next frame — rendering within 16 ms on a 60 Hz display.
  • Users can keep working offline, valuable on mobile devices with intermittent connectivity; the app needs no separate offline mode, since being offline is the same as a very large network delay.
  • The programming model is simpler: every service call requires error handling, whereas local reads and writes almost never fail, leading to a more declarative style. Combined with a reactive programming model, it is a good way to show other users’ edits in real time.

Sync engines work best when all the data the user may need is downloaded in advance and stored persistently on the client, so they are not suitable if the user has access to a very large amount of data: downloading all the files a user created is probably fine, but downloading the entire catalog of an ecommerce website probably doesn’t make sense.

Lotus Notes pioneered the idea in the 1980s, without using the term. Today some sync engines use a proprietary backend service (Google Firestore, Realm, Ditto); others have an open source backend, suitable for local-first software (PouchDB/CouchDB, Automerge, Yjs). Multiplayer games have a similar need; their equivalent is called netcode, whose techniques are specific to games.

The biggest problem with multi-leader replication — both in a geo-distributed server-side database and in a local-first sync engine on end-user devices — is that concurrent writes on different leaders can lead to conflicts that need to be resolved.

The two writes are concurrent because neither was aware of the other at the time it was made. “It doesn’t matter whether the writes literally happened at the same time; indeed, if the writes were made while offline, they might have happened some time apart.” What matters is whether one write occurred in a state where the other had already taken effect.

Dealing with conflicting writes · conflict avoidance

Stop conflicts before they start

The easiest conflict to resolve is one that never happens. If every write to one record goes through the same leader, that leader puts them in order, and there is nothing to argue about — even though the database as a whole has many leaders.

Lena only ever edits her own profile. So give her a home region: all her reads and writes go to the Europe leader, while Kenji’s go to the Asia leader. From Lena’s point of view, the database is simply single-leader. The trick breaks the moment her home has to change — her region goes down, or she moves to Seoul. While the switch is in progress, one write can take the old route and another the new one, and the conflict is back. Offline devices can’t use this trick at all.

Another kind of avoidance: two leaders handing out IDs from their own counters will both hand out 1, 2, 3. Let one hand out only odd numbers and the other only even ones, and they can never clash.

What the book says

One strategy is to prevent conflicts from occurring at all. If the application can ensure that all writes for a particular record go through the same leader, conflicts cannot occur, even if the database as a whole is multi-leader. This is not possible for a sync engine client being updated offline, but it is sometimes possible in geo-replicated server systems.

For example, where a user can edit only their own data, requests from a particular user can always be routed to the same region, using the leader in that region for reading and writing. Different users may have different “home” regions (perhaps picked by geographic proximity), but from any one user’s point of view the configuration is essentially single-leader.

Sometimes you need to change the designated leader for a record — because one region is unavailable and traffic must be rerouted, or because a user has moved and is closer to a different region. A user may then write while the change of designated leader is in progress, causing a conflict that has to be resolved some other way. Conflict avoidance breaks down if you allow the leader to be changed.

Another example: to generate unique IDs from an autoincrementing counter with two leaders, set one up to generate only odd numbers and the other only even numbers, so they never assign the same ID concurrently. Other ID schemes come later, in “ID Generators and Logical Clocks.”

Dealing with conflicting writes · last write wins

Last write wins — and the other one vanishes

Aiko and Bruno change the same wiki title at the same moment, through two different leaders. Each of them gets a cheerful “saved”. Later the leaders swap changes and must settle on one title. The simplest rule: stamp every write with a time and keep the one with the greatest stamp. That rule is last write wins (LWW).

The name flatters it. When two writes are concurrent, neither is really “last”, so the timestamp order is basically a coin toss. What LWW actually does is pick one write at random and silently discard the others — even though their leaders already told the user “OK”. The replicas do end up identical. The price is lost data.

It gets worse with real clocks. If one node’s clock runs fast, a write made later — by someone who had already seen the old value — can lose because its stamp is smaller. A logical clock fixes that ordering. And if every write inserts a new record under a unique key and nothing is ever updated, no two writes collide, so LWW costs nothing.

What the book says

If conflicts can’t be avoided, the simplest way of resolving them is to attach a timestamp to each write and always use the value with the most recent (greatest) timestamp. In Figure 6-9, if user 1’s write has the greater timestamp, both leaders decide the new title is B and discard the write that sets it to C. If the timestamps happen to be equal, the winner can be chosen by comparing the values — for strings, taking the one earlier in the alphabet.

This is called last write wins (LWW), but the term is misleading: when two writes are concurrent, which one is most recent is undefined, so their timestamp order is essentially random. The real meaning of LWW is that one of the concurrent writes is randomly chosen as the winner and the others are silently discarded, even though they were successfully processed by their respective leaders. All replicas eventually end up consistent, at the cost of data loss.

If you can avoid conflicts — for example by only inserting records with a unique key and never updating them — LWW is no problem. If you update existing records, or different leaders may insert records with the same key, you have to decide whether lost updates are a problem for your application; if they are, you need one of the other resolution approaches.

If a real-time clock (such as a Unix timestamp) is used, the system becomes very sensitive to clock synchronization: if one node’s clock is ahead and you overwrite a value it wrote, your write may be ignored because it has a lower timestamp, even though it clearly occurred later. A logical clock solves this (“ID Generators and Logical Clocks”, p. 417).

Dealing with conflicting writes · manual conflict resolution

Keep both, and sort it out later

You know merge conflicts from Git: two branches change the same line, and Git stops until a person decides. A database can’t pause all replication while it waits for someone. So instead of throwing a write away, it keeps every concurrently written value — the siblings — and hands you the whole set the next time you read that record.

Then it’s your move. Merge them in code (glue B and C into “B/C”), or show them to the user and ask. Either way you write a new value back, and that replaces the siblings. CouchDB works like this.

Nothing is lost, but there are catches. The API changes: a title used to be a string, and now it’s a set of strings that usually has one element. Asking users is work for the developer and confusing for the user. Merging automatically can surprise you — Amazon’s cart merged siblings by set union, so items people had removed came back. And two nodes resolving the same conflict at once can create a brand-new conflict.

Try it: in Siblings, press Edit concurrently, then Read, then Merge in code or Ask the user. In Shopping cart and Merging the merges, press Run and watch what the union brings back.

What the book says

If randomly discarding writes is not desirable, the next option is to resolve the conflict manually, much like a merge conflict in Git. In a database it would be impractical for a conflict to stop the entire replication process until a human has resolved it. Instead, databases typically store all the concurrently written values for a record — both B and C in Figure 6-9. These values are sometimes called siblings. The next query returns all of them; you resolve them in application code (e.g., concatenating B and C into B/C) or by asking the user, then write back a new value. Some systems, such as CouchDB, use this approach.

The API of the database changes: a wiki title that was a string becomes a set of strings that usually contains one element but may contain several, which can be awkward in application code. Asking the user to merge is a lot of work for the app developer, who must build the UI, and for the user, who may be confused about what is being asked and why. In many cases it’s better to merge automatically.

Automatic merging can behave surprisingly if not done carefully. Amazon’s shopping cart used to merge concurrent updates by keeping every item that appeared in any sibling — the set union. An item removed in one sibling but still present in another would unexpectedly reappear: in Figure 6-10, device 1 removes Book and device 2 removes DVD, and after merging both items are back.

If multiple nodes observe the conflict and resolve it concurrently, the resolution can itself introduce a new conflict, and the resolutions may even be inconsistent: one node merges B and C into B/C, another into C/B, and merging those may give B/C/C/B.

Dealing with conflicting writes · automatic conflict resolution

Merge by the rules, in any order

For many apps the best answer is an algorithm that merges concurrent writes by itself. It has two jobs. First, keep the intended effect of every update, so nothing is silently dropped. Second, make every replica land in the same state, whatever order the changes arrive in. Eventual consistency plus that promise of convergence is called strong eventual consistency: replicas that have processed the same set of writes are identical.

The trick is to merge each kind of data by its own rule. Text keeps every insertion and every deletion. A collection remembers what was deleted, so a removed item stays removed. A counter adds up each replica’s increments and decrements instead of copying totals around. A map merges key by key, and only a key written on both sides needs a decision.

Some rules can’t survive concurrency. If a list may hold at most five items and two people add items at once, the merged list has seven, and the only way out is to drop some.

What the book says

For many applications, the best way of handling conflicts is an algorithm that automatically merges concurrent writes into a consistent state. Automatic conflict resolution ensures that all replicas converge: all replicas that have processed the same set of writes have the same state, regardless of the order in which the writes arrived. Combining eventual consistency with a convergence guarantee is known as strong eventual consistency.

LWW is a simple example of a conflict resolution algorithm. More sophisticated merge algorithms for different types of data aim to preserve the intended effect of all updates and hence avoid data loss. For text, detect which characters were inserted or deleted; the merged result preserves all insertions and deletions made in any sibling, and concurrent insertions at the same position can be ordered deterministically. For a collection (ordered like a to-do list or unordered like a shopping cart), track insertions and deletions: because the algorithm tracks that Book and DVD were deleted, the cart of Figure 6-10 merges to Cart = {Soap}.

For a counter that can be incremented or decremented, such as the number of likes on a post, the algorithm can tell how many increments and decrements happened on each sibling and add them together correctly, without double-counting or dropping updates. For a key-value mapping, updates to the same key are merged by applying one of the other algorithms to its values; updates to different keys are handled independently.

There are limits: if a list must contain no more than five items and concurrent additions push it over, the only option is to drop some items. Nevertheless, automatic conflict resolution is sufficient for many useful apps, and if you are building a collaborative offline-first or local-first app, conflict resolution is inevitable and automating it is often the best approach.

Dealing with conflicting writes · CRDTs and operational transformation

ice, nice, ice! — nice!

Two replicas hold the word “ice”. At the same moment, one puts an n in front (“nice”) and the other adds ! at the end (“ice!”). Both should end up with “nice!”. Two families of algorithms get there in different ways.

Operational transformation (OT) describes an edit by its position: “insert n at index 0”, “insert ! at index 3”. Applied blindly on the other replica, the second edit lands in the wrong place — “nic!e” — because the n has shifted everything one step right. So each incoming operation is transformed against the concurrent operations already applied there: index 3 becomes 4.

A CRDT (conflict-free replicated datatype) never uses positions. Every character gets a unique, immutable ID, and an insert says “put ! right after the character with ID 3A”. However much the text moves around, 3A is still the e, so the replicas converge with no transformation at all. When two inserts target the same spot, their IDs decide the order, the same way on every replica.

Try it: choose OT or CRDT and press Step to walk through the merge, or Play to run it all. In OT, watch the blind attempt go wrong before the transform fixes it. The code underneath lights up in step.

What the book says

Two families of algorithms are commonly used to implement automatic conflict resolution: conflict-free replicated datatypes (CRDTs) and operational transformation (OT). They have different design philosophies and performance characteristics, but both can perform automatic merges for all the data types above. In Figure 6-11, two replicas start with the text ice; one prepends n to make nice while the other concurrently appends an exclamation mark to make ice!; both reach nice!.

OT records the index at which characters are inserted or deleted: n at index 0 and ! at index 3. The replicas exchange operations. The insertion of n at index 0 can be applied as is, but inserting ! at index 3 into nice would give nic!e, which is incorrect, so the index of each operation is transformed to account for concurrent operations already applied — here, ! moves to index 4.

Most CRDTs give each character a unique, immutable ID and use those IDs instead of indexes: i is 1A, c is 2A, and so on. Inserting the exclamation mark generates an operation containing the new character’s ID (4B) and the ID of the existing character after which to insert it (3A); nil as the preceding ID means the beginning of the string. Concurrent insertions at the same position are ordered by the IDs of the characters, so replicas converge without performing any transformation.

Lists and arrays work the same way with list elements instead of characters, and key-value maps can be added easily. OT is most often used for real-time collaborative text editing, as in Google Docs; CRDTs appear in distributed databases such as Redis Enterprise, Riak and Azure Cosmos DB. Sync engines for JSON data can use CRDTs (Automerge, Yjs) or OT (ShareDB), and it is possible to combine the advantages of both in one algorithm.

Leaderless replication · writing when a node is down

No boss: just tell everyone

Picture a class with no class captain. When Ana has news, she doesn’t hand it to one person to pass on — she shouts it to all three note-takers at once. One of them is out of the room. Two write it down, and two is enough: Ana moves on.

That is leaderless replication. There is no leader deciding the order of writes, and so there is no failover either: the client (or a coordinator working for it) sends every write to all replicas in parallel and counts the OKs. A replica that was rebooting simply missed the write.

The catch comes later. The replica comes back holding an old value. So reads are also sent to several replicas, and every value carries a version number. The reader takes the answer with the greatest version, even if only one replica gave it.

Try it: replica 3 starts out rebooting. Press Write and count the OKs. Tap replica 3 to bring it back, then press Read: three answers come back, and one of them is stale. Switch to Coordinator sends to see the same thing with a middleman.

What the book says

Single-leader and multi-leader replication rely on a leader that determines the order in which writes are processed. Some systems abandon the leader and let any replica accept writes directly from clients. Some of the earliest replicated data systems were leaderless; the idea became fashionable again after Amazon used it for its in-house Dynamo system in 2007. Riak, Cassandra and ScyllaDB are open source datastores inspired by Dynamo, so this style is also called Dynamo-style.

The original Dynamo was described in a paper but never released outside Amazon. The similarly named DynamoDB has a completely different architecture: single-leader replication based on the Multi-Paxos consensus algorithm.

In some implementations the client sends its writes to several replicas directly; in others a coordinator node does it on the client’s behalf — but unlike a leader, the coordinator does not enforce a particular ordering of writes.

With three replicas and one unavailable, there is no failover: the client sends the write to all three in parallel, and once two have acknowledged it the write counts as successful. Reads are also sent to several nodes in parallel; every value is tagged with a version number or timestamp, and the client uses the one with the greatest timestamp, even if only one replica returned it.

Leaderless replication · catching up on missed writes

Three ways to catch up

Replica 3 was out of the room while two things changed: Ana’s avatar (looked at all day long) and an old 2019 invoice (nobody has opened it in years). When R3 comes back, both of its copies are stale. In a leaderless system there is no leader’s log to replay — so who brings it up to date?

Read repair: whoever reads a key from several replicas and spots an old version writes the newer one back. Great for the avatar, useless for the invoice nobody reads. Hinted handoff: while R3 is down, another replica keeps hints — “these writes are for R3” — and hands them over when it returns. Anti-entropy: a background process keeps comparing replicas and copies whatever is missing, in no particular order, sometimes long after the fact.

What the book says

The replication system should ensure that eventually all the data is copied to every replica. After an unavailable node comes back online, several mechanisms are used in Dynamo-style datastores to help it catch up on the writes it missed.

Read repair: when a client reads from several nodes in parallel, it can detect stale responses — in Figure 6-12, user 2345 gets version 6 from replica 3 and version 7 from replicas 1 and 2 — and write the newer value back to the stale replica. This works well for values that are read often.

Hinted handoff: if one replica is unavailable, another may store writes on its behalf in the form of hints. When the intended replica comes back, the replica storing the hints sends them over and then deletes them. This helps even for values that are never read and therefore never handled by read repair.

Anti-entropy: a background process periodically looks for differences in the data between replicas and copies any missing data. Unlike the replication log in leader-based replication, it does not copy writes in any particular order, and there may be a significant delay before data is copied.

Leaderless replication · using quorums for reading and writing

Voting instead of a boss

Five note-takers. Every new fact has to be written down by at least three of them before it counts. Later, when you want the fact back, you ask at least three of them. Three plus three is six, and there are only five note-takers — so at least one person you ask must be someone who wrote it down. That one overlap is the whole trick.

With n replicas, a write must be confirmed by w of them and a read must hear from r of them. If w + r > n, every read set and every write set share at least one replica, so a read can find the latest value. These are quorum reads and writes: w and r are the minimum votes needed. Requests still go to all n replicas; w and r only say how many replies to wait for.

The leftovers buy fault tolerance: writes survive n − w unavailable replicas, reads survive n − r. Below that, you get an error — and the client doesn’t care why a replica didn’t answer, only that it didn’t.

Try it: press Write, then Read, and look for the replica marked both W and R. Drag w and r down until w + r ≤ n and read a few times. Tap replicas to crash them until a write fails. Try the preset w = n, r = 1 and crash just one.

What the book says

If every successful write is guaranteed to be on at least two of three replicas, at most one replica can be stale, so reading from at least two guarantees that one of them is up to date. More generally, with n replicas, every write must be confirmed by w nodes and every read must query at least r nodes; as long as w + r > n, we expect an up-to-date value when reading. These are quorum reads and writes; r and w are the minimum number of votes required.

In Dynamo-style databases n, w and r are typically configurable. A common choice is an odd n (commonly 3 or 5) with w = r = (n + 1) / 2, rounded up. A workload with few writes and many reads may set w = n and r = 1: reads get faster, but just one failed node makes all database writes fail.

There may be more than n nodes in the cluster, but any given value is stored on only n nodes, which allows the dataset to be sharded (Chapter 7).

If w < n, writes still work with a node unavailable; if r < n, reads do. n = 3, w = 2, r = 2 tolerates one unavailable node; n = 5, w = 3, r = 3 tolerates two. Reads and writes are normally sent to all n replicas in parallel; w and r determine how many we wait for. If fewer than w or r nodes are available, writes or reads return an error. A node may be unavailable because it crashed, hit an error such as a full disk, or is cut off by the network — we only care whether it returned a successful response.

Leaderless replication · the limitations of quorum consistency

When the vote still goes wrong

The overlap argument is neat: if w + r > n, the replicas you read from must include one that took the latest write. So why do Dynamo-style databases still call themselves eventually consistent? Because real life sneaks around the argument.

You might choose w + r ≤ n on purpose, trading staleness for lower latency and higher availability. A replica holding the new value might die and be restored from a stale copy. A write might land on too few replicas, be reported as failed, and still not be rolled back. Real-time clocks might silently drop a later write. And a read running concurrently with a write might see the new value, then the old one.

So treat w and r as dials for the probability of reading stale data — not as an absolute guarantee.

Try it: in Small quorums, set w and r, then press Run 100 trials and compare the stale count with the formula. Then press Step through each of the other four stories and watch a quorum read return the wrong answer.

What the book says

With w + r > n you can generally expect every read to return the most recent value, because the set of nodes written to and the set read from must overlap. Often r and w are a majority (more than n / 2), which tolerates up to n / 2 (rounded down) failures — but quorums are not necessarily majorities; only the overlap matters.

With w + r ≤ n, reads and writes still go to n nodes but fewer successful responses are needed. You are more likely to read stale values, but get lower latency and higher availability: only when the reachable replicas fall below w or r does the database become unavailable for writing or reading.

Even with w + r > n there are edge cases: a node carrying a new value fails and is restored from a replica carrying an old value, so fewer than w replicas hold the new value; during rebalancing, nodes may disagree about which nodes hold the n replicas, so quorums no longer overlap; a read concurrent with a write may or may not see it, and one read may see the new value while a later one sees the old; a write that succeeded on fewer than w replicas (say, because disks were full) is reported as failed but not rolled back, so later reads may or may not return it; with timestamps from a real-time clock (as Cassandra and ScyllaDB use) writes can be silently dropped if another node with a faster clock wrote the same key; and two concurrent writes may be processed in different orders on different replicas, causing a conflict.

Dynamo-style databases are generally optimized for use cases that can tolerate eventual consistency. The parameters w and r let you adjust the probability of stale values being read, but it’s wise not to take them as absolute guarantees.

Leaderless replication · monitoring staleness

How far behind are we?

Even if your app can live with stale reads, you want to know how stale they are. A follower that drifts minutes behind usually means something is wrong — an overloaded node, a sick network — and someone should get paged.

With a leader this is easy. Every node applies writes in the same order, so each one has a position in the replication log. Subtract a follower’s position from the leader’s and you have its replication lag, a number you can graph and alert on.

Leaderless systems have no fixed order of writes. Replica 1 might have writes 41, 43, 42; replica 2 has 42, 41. There is nothing to subtract. The number of hints a replica is holding for an absent neighbour is one signal, but it’s hard to read. Yet “eventually” is too vague to operate a system on — it needs a number.

What the book says

From an operational perspective it’s important to monitor whether your databases are returning up-to-date results. Even if your application can tolerate stale reads, you need to be aware of the health of your replication: if it falls behind significantly, it should alert you so that you can investigate the cause, such as a network problem or an overloaded node.

For leader-based replication the database typically exposes metrics for replication lag, which you can feed into a monitoring system. This is possible because writes are applied to the leader and followers in the same order, and each node has a position in the replication log (the number of writes it has applied locally). Subtracting a follower’s position from the leader’s gives the amount of replication lag.

In leaderless replication there is no fixed order in which writes are applied, which makes monitoring more difficult. The number of hints a replica stores for handoff can be one measure of system health, but it’s difficult to interpret usefully. Eventual consistency is a deliberately vague guarantee, but for operability it’s important to be able to quantify “eventual.”

Leaderless replication · single-leader versus leaderless performance

Don’t wait for the slow one

Picture a quiz where one student, the leader, must answer every question. If that student is ill but still at school, answering slowly, the whole class waits. The teacher has an awkward decision: is it bad enough to swap in someone else? That swap is a failover, and it is disruptive in itself.

A leaderless database asks three students at once and takes the first two answers. It already sends every request to several replicas in parallel, so one sluggish replica barely matters: the client uses the fastest replies. That trick is request hedging, and it cuts tail latency. A node that isn’t dead, just limping, is a gray failure. Here it needs no special handling, because the normal case and the failure case are the same code path.

It isn’t free. Bigger quorums mean more replies to wait for, so more chances to hit a slow one. And if a network cut hides a key’s usual replicas, a sloppy quorum lets other nodes accept the write. The write succeeds, but nothing promises that the next read will see it.

What the book says

A single-leader system can provide strong consistency guarantees that are difficult or impossible in a leaderless one. But reading from the leader has performance problems: read throughput is limited by the leader’s capacity; if the leader fails you must wait for detection and failover, and users notice the increased response times; and the system is very sensitive to the leader being slow because of overload or resource contention.

A leaderless architecture is more resilient: there is no failover, and requests go to several replicas in parallel anyway, so one slow or unavailable replica has very little impact on response times. Using the fastest responses is called request hedging, and it can significantly reduce tail latency. The resilience comes from not distinguishing the normal case from the failure case. That is especially helpful for gray failures, where a node is running in a degraded, unusually slow state, or a node is simply overloaded (for example by hinted handoff after being offline).

Leaderless systems have performance problems too. A replica must detect that another is unavailable so it can store hints, and the handoff adds load when the system is already under strain. The more replicas you have, the bigger the quorums and the more responses you wait for. A bigger r or w raises the chance of hitting a slow replica: “quorums are seldom more than four out of seven nodes or five out of nine nodes.”

A large network interruption can make a quorum impossible. Some databases let any reachable replica accept writes even if it is not one of the usual replicas for that key: Riak and Dynamo call this a sloppy quorum; Cassandra and ScyllaDB call it consistency level ANY. There is no guarantee subsequent reads see the value, but it may be better than failing the write.

Multi-leader replication can be even more resilient to network interruptions, since a client only talks to one nearby leader, but reads can be arbitrarily out of date. Quorum reads and writes are a compromise: good fault tolerance and a high likelihood of reading up-to-date data.

One trip across the ocean, not three

Imagine a company with offices in three countries, each keeping three copies of the client files. When Lisbon updates a file, it doesn’t courier three envelopes to Singapore. It sends one, and the Singapore office photocopies it for its own two cabinets.

Cassandra and ScyllaDB work the same way. The client sends its write to a coordinator node in its own region. The coordinator forwards it to every replica in that region, and to just one replica in each other region, which passes it on locally. Expensive cross-region requests are made once per region, not once per replica.

Then you pick a consistency level: how many replies, and from where, before a request counts as done. A quorum across all regions is safest but waits on the ocean. A local quorum answers in a couple of milliseconds, so a friend reading in another region straight away may still see the old value.

Try it: press Write, then read in region 3 under each consistency level and compare the waits with the read result. Toggle Naive forwarding and count the cross-region messages. Then try Riak (async).

What the book says

Leaderless replication is suitable for multi-region operation, since it is designed to tolerate conflicting concurrent writes, network interruptions and latency spikes.

In Cassandra and ScyllaDB, a client that wants a multi-region write first chooses a node in its local region, the coordinator node, and sends its write there. The coordinator forwards the write to all replicas in its own region and to one replica in every other region, which then forwards it to the other replicas in that region. This optimization avoids making the cross-region request multiple times.

You can choose from a variety of consistency levels that determine how many responses are required: a quorum across the replicas in all the regions, a separate quorum in each of the regions, or a quorum only in the client’s local region. A local quorum avoids waiting for slow requests to other regions, but it is also more likely to return stale results.

Riak keeps all communication between clients and database nodes local to one region, so n describes the number of replicas within one region. Cross-region replication between database clusters happens asynchronously in the background, in a style similar to multi-leader replication.

Three nodes, three different stories

Amara and Bruno both change the same setting X at the same moment. Each of them sends the change to all three nodes, and the network delivers the six messages in whatever order it likes. Node 1 gets Amara’s and never sees Bruno’s, which was lost in a brief outage. Node 2 gets Amara’s then Bruno’s. Node 3 gets Bruno’s then Amara’s.

If every node simply overwrites on arrival, they end up holding different values. Nothing will ever fix that, because no node can tell which value should win. The replicas must converge. Last write wins makes them converge by comparing timestamps, but it quietly throws one write away. And a timestamp can’t tell you whether the two writes were concurrent or one after the other.

Try it: press Play with Overwrite on arrival and read the final get X on each node. Then switch to Last write wins and play again. Count how many writes survive.

What the book says

As with multi-leader replication, leaderless databases allow concurrent writes to the same key, resulting in conflicts that need to be resolved. They might be detected as the writes happen, or later, during read repair, hinted handoff or anti-entropy.

The problem is that events may arrive in a different order at different nodes, because of variable network delays and partial failures. In Figure 6-14, clients A and B simultaneously write to key X in a three-node datastore: node 1 receives the write from A but never the write from B, because of a transient outage; node 2 receives A then B; node 3 receives B then A.

If each node simply overwrote the value whenever it received a write, the nodes would become permanently inconsistent: node 2 thinks the final value of X is B, the others think it is A. To become eventually consistent, the replicas should converge toward the same value, using any of the conflict resolution mechanisms: LWW (used by Cassandra and ScyllaDB), manual resolution, or CRDTs (used by Riak).

LWW is easy to implement: each write is tagged with a timestamp, and a value with a higher timestamp always overwrites a lower one. However, a timestamp doesn’t tell you whether two values are actually conflicting (written concurrently) or written one after another. To resolve conflicts explicitly, the system needs to take more care to detect concurrent writes.

Detecting concurrent writes · the happens-before relation and concurrency

Who knew what, and when

Kwame posts “Want to get lunch?”. An hour later Leila replies “Yes!” — she read his message first, so her reply builds on his. We say his post happened before her reply. Now suppose both write a reply to the same old post without either seeing the other’s. Neither knew about the other, so they are concurrent — even if one was typed an hour after the other.

For any two operations A and B there are exactly three possibilities. A happened before B: B may safely overwrite A. B happened before A: the other way round. Or they are concurrent: that is a conflict to resolve. The clock on the wall doesn’t decide which. What decides it is what each operation could have known. A slow or broken network can make two operations far apart in time still concurrent.

Try it: pick a preset and press Play to watch the messages. Then turn B reads first off or on, slide B starts later by, and switch on A’s link down. Watch the verdict at the bottom change — and notice that the gap in time never decides it.

What the book says

In Figure 6-8, the two writes are not concurrent: A’s insert happens before B’s increment, because the value incremented by B is the value inserted by A. B’s operation builds upon A’s, so B is causally dependent on A. In Figure 6-14, the writes are concurrent: when each client starts its operation, it does not know that another client is also performing an operation on the same key.

“An operation A happens before another operation B if B knows about A, or depends on A, or builds upon A in some way.” Two operations are concurrent if neither happens before the other. So there are three possibilities: A happened before B, B happened before A, or A and B are concurrent. If one happened before the other, the later one should overwrite the earlier; if they are concurrent, there is a conflict to resolve.

Concurrency, time, and relativity: it is not important whether the operations literally overlap in time. Because of problems with clocks it is hard to tell whether two things happened at exactly the same time, so two operations are called concurrent if they are both unaware of each other, regardless of the physical time at which they occurred.

People connect this with the special theory of relativity: information cannot travel faster than the speed of light, so two distant events cannot affect each other if the time between them is shorter than light needs to cross the distance. In computer systems, two operations can be concurrent even though light would in principle have allowed one to affect the other: if the network was slow or interrupted, they can occur some time apart and still be concurrent.

The shopping cart that remembers who knew what

Two flatmates, Ines and Tomás, fill the same online shopping cart from their own phones. Neither waits for the other. The server can’t look inside a cart to guess who saw what, but it can count. It gives the key a version number that goes up on every write.

The rules are short. A client must read before it writes. A read returns every value not yet overwritten — the siblings — plus the current version. A write sends back the version from the client’s last read, with all those siblings merged into the new value. The server then drops every sibling at or below that version, because the client has seen them and folded them in. It keeps every sibling above that version, because those were written concurrently.

The server never interprets the values: version numbers alone tell an overwrite from a concurrent write. A write that carries no version at all is concurrent with everything, so it overwrites nothing.

Try it: press Next write five times to replay the book’s Figure 6-15 and watch the lit line in the code. Each time, see which siblings turn red (dropped) and which stay green (kept). Then press Write without a version.

What the book says

Start with a single replica. The server maintains a version number for every key, increments it every time that key is written, and stores the new version number along with the value. When a client reads a key, the server returns all siblings (all values that have not been overwritten) as well as the latest version number. A client must read a key before writing.

When a client writes a key, it must include the version number from the prior read, and it must merge together all values it received in that read (e.g., using a CRDT with input from the user). The response to a write also returns all siblings, which lets a client chain several writes. When the server receives a write with a particular version number, it can overwrite all values with that version number or below, but it must keep all values with a higher version number, because those are concurrent with the incoming write.

The server can determine whether two operations are concurrent by looking only at version numbers; the value could be any data structure. A write without a version number is concurrent with all other writes, so it overwrites nothing and is simply returned as one of the values on subsequent reads.

In Figure 6-15, client 1 adds milk (version 1); client 2 adds eggs, not knowing about the milk (version 2, siblings [milk] and [eggs]); client 1 writes [milk, flour] with version 1, which overwrites [milk] but keeps [eggs] (version 3); client 2 writes [eggs, milk, ham] with version 2, which overwrites [eggs] but keeps [milk, flour] (version 4); client 1 writes [milk, flour, eggs, bacon] with version 3, keeping [eggs, milk, ham] (version 5). The clients are never fully up to date, since another operation is always going on concurrently, but old versions do get overwritten eventually, and no writes are lost. (If the cart seems too inane, the book suggests two air traffic controllers adding aircraft to the sector they are tracking.)

Detecting concurrent writes · version vectors

One counter per replica

A single version number worked because one server handed out every number. With three replicas all accepting writes, there is no one to count for everyone. So each replica keeps its own counter for the key and remembers the highest count it has seen from each of the others. Together those counters form a version vector, such as {A:2, B:1, C:0}.

When you read, you get the vector along with the values (Riak calls it the causal context). When you write — to any replica — you send it back. The replica compares vectors. If yours is at least as big as an old value’s in every slot, you had seen that value: overwrite it. If yours is bigger in one slot but smaller in another, neither saw the other. That makes them concurrent, so both are kept as siblings.

Try it: keep read from A, write to B and press Write: the old value is overwritten. Now choose read from: nobody, write to C and press Write: the result is a concurrent sibling. Press Sync replicas, then tap any two values to compare their vectors.

What the book says

Figure 6-15 used a single version number, which is not sufficient when several replicas accept writes concurrently. Instead we need a version number per replica as well as per key. Each replica increments its own version number when processing a write, and also keeps track of the version numbers it has seen from each of the other replicas. This indicates which values to overwrite and which to keep as siblings.

The collection of version numbers from all the replicas is called a version vector. The most interesting variant is probably the dotted version vector, used in Riak 2.0; it works much like the cart example.

Version vectors are sent from the database replicas to clients when values are read, and must be sent back when a value is subsequently written. Riak encodes the vector as a string it calls the causal context. The version vector lets the database distinguish between overwrites and concurrent writes. It also makes it safe to read from one replica and write back to another: siblings may be created, but no data is lost as long as siblings are merged correctly.

A version vector is sometimes called a vector clock, even though they are not quite the same; the difference is subtle. In brief, when comparing the state of replicas, version vectors are the right data structure to use.

Why keep copies at all?

The book’s summary lists five reasons.

High availability

Keep running even when one machine, several machines, a zone or a whole region goes down.

Durability

Don’t lose data, even if a whole machine or region fails for good.

Disconnected operation

Keep working through a network interruption, like a calendar on a phone with no signal.

Latency

Put the data close to the people who use it, so they get answers faster.

Scalability

Serve more reads than one machine could, by reading from the copies.

Three ways to copy

Almost every distributed database uses one of them.

Single-leader

All writes go to one leader, which streams changes to its followers. Easy to understand, strong consistency possible — but reads from followers may be stale, and losing the leader means a failover.

Multi-leader

Several leaders each accept writes and send their changes to one another. Survives outages and slow networks, at the price of conflicts to resolve.

Leaderless

Clients write to several replicas and read from several in parallel, using quorums to find and fix stale copies. No failover at all.

Promises that tame replication lag

Three guarantees, from the summary.

Read-after-write

You always see what you submitted yourself.

Monotonic reads

Once you’ve seen newer data, you never see older data again.

Consistent prefix reads

You see things in an order that makes sense: the question before its answer.

The book’s verdict: keeping a copy of the same data on several machines sounds simple, yet it turns out to be remarkably tricky. You have to think about concurrency, everything that can go wrong, and what happens next. Single-leader is popular because it is easy to understand; multi-leader and leaderless cope better with faults, network trouble and latency spikes, at the cost of conflict resolution and weaker guarantees.
