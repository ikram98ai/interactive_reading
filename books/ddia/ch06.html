Replication

Keeping the same data on several computers, so a broken machine never means lost homework — and so the copy nearest you can answer first. Easy, until the copies disagree.

“The major difference between a thing that might go wrong and a thing that cannot possibly go wrong is that when a thing that cannot possibly go wrong goes wrong, it usually turns out to be impossible to get at or repair.” — Douglas Adams, Mostly Harmless (1992)

Big idea 1 · single-leader replication

One notebook everybody copies

Say three friends each keep a notebook with the same facts in it. If they all scribble whenever they like, the notebooks drift apart. So they agree on a rule: only one notebook is allowed to be written in. That one is the leader.

Every change the leader makes gets read out loud, in order, to the other notebooks — the followers. Followers copy the changes in exactly the same order, so they end up saying the same thing.

You may read from any notebook. But if you try to write in a follower, it says: sorry, take that to the leader.

Try it: send a few writes, read from a follower, then try writing straight into a follower and see what happens.

What the book says

Each node that stores a copy of the database is a replica. In leader-based (also primary–backup or active/passive) replication, one replica is the leader (primary, source) and the rest are followers (read replicas, secondaries, hot standbys).

Clients send all writes to the leader. The leader writes locally, then sends every change to its followers as a replication log or change stream. Followers apply the writes in the same order. Reads may go to any replica.

Used by PostgreSQL, MySQL, Oracle Data Guard, SQL Server Always On, MongoDB, DynamoDB, Kafka, DRBD, and by consensus algorithms like Raft (CockroachDB, TiDB, etcd, RabbitMQ quorum queues), which elect a new leader automatically.

The replication log itself comes in flavours: statement-based (replay the SQL — breaks on NOW(), RAND() and autoincrements), write-ahead log shipping (byte-level, ties the versions together), and logical (row-based) logs such as MySQL's binlog, which stay readable across versions and power change data capture.

Big idea 2 · synchronous vs asynchronous

Do you wait for your friend to finish copying?

When you tell the leader something new, when should it say “saved!”? It could wait until a follower has written it down too — that's synchronous. Then you know two notebooks have it, so nothing is lost if the leader falls in a puddle.

Or it can say “saved!” straight away and post the change to the followers later — asynchronous. Much faster… but if the leader dies in the next second, that write was never really safe.

Waiting on all followers is a trap: one sleepy follower freezes the whole database. So real systems usually keep one synchronous follower and the rest asynchronous.

Break it: pause follower 1 in each mode. Then send a write and crash the leader before the copy arrives.

What the book says

Synchronous: the leader waits for the follower's confirmation before reporting success. The follower is guaranteed to have an up-to-date copy — but if it doesn't respond, the leader must block all writes until it returns.

So it is impracticable for all followers to be synchronous. In practice one follower is synchronous and the others asynchronous; if the synchronous one stalls, an asynchronous one is promoted to take its place. This is called semisynchronous.

Some systems replicate synchronously to a majority of replicas (3 of 5) — a quorum. Fully asynchronous replication means a confirmed write may not be durable at all, yet it is widely used, especially with many or geographically distributed followers.

Normally followers are less than a second behind, but there is no guarantee: recovery, near-capacity operation or network trouble can push them minutes behind.

Big idea 3 · setting up and catching up

The new kid copies the notebook

A new follower joins. You can't just photocopy the leader's pages while it is still being written in — you'd get the first half from one moment and the second half from another, and the result would make no sense.

Instead: take a snapshot (a clean picture of the whole notebook at one exact moment), note which line of the log that picture matches, copy it over, and then ask the leader for everything written since that line.

Once the new follower has chewed through the backlog, it has caught up and just follows along live. A follower that crashed and came back does exactly the same thing from its own last line.

Step through it and watch the log position do the work: the snapshot alone is never enough.

What the book says

Setting up a follower without downtime: (1) take a consistent snapshot of the leader, ideally without locking; (2) copy it to the new node; (3) the follower requests all changes since the snapshot, which requires the snapshot to be tied to an exact position in the replication log — PostgreSQL's log sequence number, MySQL's binlog coordinates or GTIDs; (4) when the backlog is processed, it has caught up.

Tools: Percona XtraBackup for MySQL snapshots; WAL-G and Litestream archive the log to object storage so steps 1–2 become a download.

Follower failure is the easy case: each follower keeps a log of what it has applied, so after a crash it asks the leader for everything since its last transaction. The leader can only delete log entries once all followers have them — otherwise it must choose between filling its disk and forcing a restore from backup.

Replication is not a backup: a deletion replicates too. Backups store old snapshots so you can go back in time.

Big idea 4 · failover and split brain

When the captain falls over

If the leader dies, somebody has to take charge. The others notice no heartbeat, wait a bit, then vote: whoever has copied the most gets promoted. Clients are pointed at the new leader. That is failover.

It is full of traps. Any writes the old leader accepted but never sent on are simply thrown away — writes you were told were saved. Wait too long and the site is down; wait too little and a brief traffic spike triggers a pointless failover that makes everything worse.

And worst of all: the old leader wakes up still believing it's in charge. Two leaders taking writes is called split brain. Fencing is the safety catch that forces the old one to step down.

Break it: crash the leader, then bring it back with fencing off. Then try a load spike with a short timeout.

What the book says

Automatic failover: (1) detect the failure — usually just a timeout, say 30 seconds without a response; (2) choose a new leader by election or by a controller node, ideally the replica with the most up-to-date changes (a consensus problem); (3) reconfigure clients, and make sure the old leader becomes a follower.

With asynchronous replication the new leader may be missing writes; the usual fix is to discard them, so writes believed committed weren't durable. At GitHub, an out-of-date MySQL follower was promoted and reused autoincrement primary keys that were already referenced in Redis — private data was shown to the wrong users.

Split brain: two nodes both believe they are leader. If both accept writes with no conflict resolution, data is lost or corrupted. Shutting one down (fencing) is the safety catch — carelessly designed, it can shut down both.

Timeouts are a genuine trade-off, and for these reasons many teams prefer to do failover manually.

Big idea 5 · replication lag, part one

“I posted it… where did it go?”

Writes go to the leader, but reads can go to any follower — that's how a site serves millions of readers. The catch: a follower may be a moment (or a minute) behind. Everything catches up in the end, which is why this is called eventual consistency.

It feels fine until you post a comment, reload the page, land on a follower that hasn't heard yet, and your own comment is missing. Very upsetting!

The fix: for things you may have changed, read from the leader. That guarantee is called read-after-write (or read-your-writes) consistency. It says nothing about other people's updates — only that your own input isn't swallowed.

Try it: drag the lag up, post, and reload a few times. Then switch on read-your-writes.

What the book says

The delay between a write on the leader and it showing up on a follower is the replication lag — usually a fraction of a second, but there is no upper limit.

Read-after-write consistency techniques: read anything the user might have modified from the leader (e.g. always read your own profile from the leader); for one minute after a user's last write, send all their reads to the leader; monitor lag and avoid followers more than a minute behind; or have the client remember the timestamp (a logical one, such as a log sequence number) of its last write and require the replica to be at least that fresh, waiting or rerouting if it isn't.

Across devices you may want cross-device read-after-write consistency: the metadata must then be centralized, and requests from all of a user's devices may need routing to the same region.

Big idea 6 · replication lag, part two

Time running backwards, and answers before questions

Two more strange things happen when copies are out of step. First: you refresh a page and each refresh lands on a different follower. One is fresh, one is behind — so a comment appears, then disappears. You just watched time run backwards.

Monotonic reads promises that won't happen: you may see old data, but never older data than you already saw. The simple trick is to send each user to the same replica every time, picked from a hash of their user ID.

Second: a question and its answer are stored in different shards (different piles of data), and one shard is slower to copy than the other. An onlooker hears the answer arrive first — as if Mrs. Cake could see into the future.

Consistent prefix reads promises that writes are seen in the order they happened. One fix is to keep causally related writes in the same shard, so a single order exists for both.

Play it twice: once with the two lines on different shards, once with both on the same shard.

What the book says

Monotonic reads is stronger than eventual consistency and weaker than strong consistency: if one user makes several reads in sequence, they will not see time go backward. Achieved by routing each user to the same replica (e.g. by a hash of the user ID) — with rerouting needed if that replica fails.

Consistent prefix reads: if a sequence of writes happens in a certain order, anyone reading them sees them in that order. It is violated mainly in sharded databases, where shards operate independently and there is no global ordering of writes. Solutions: keep causally related writes in one shard, or explicitly track causal dependencies.

If replication lag of minutes or hours would ruin the user experience, design for a stronger guarantee. Doing it in application code is complex and easy to get wrong; the simplest model is a database with linearizability and ACID transactions — the trend known as NewSQL.

Big idea 7 · multi-leader replication

A leader in every town

If the only leader lives in Europe, a writer in America has to shout across an ocean and wait for the echo. And if the undersea cable hiccups, they can't write at all.

Multi-leader replication gives each region its own leader. You write to the one next door — quick — and the leaders gossip their changes to each other in the background. If the link between regions breaks, both regions keep working and catch up later.

The same shape appears on your phone: a calendar app that works on a plane is a leader in your pocket, syncing with the others when it can. That's a sync engine, and it's what makes Google Docs or Figma feel instant.

Try it: write from the US in each mode, then cut the link between regions and write again.

What the book says

In a multi-leader (active/active, bidirectional) configuration several nodes accept writes and each leader acts as a follower to the others. Synchronous multi-leader is basically single-leader, so the interesting case is asynchronous.

Across regions it wins on performance (writes served locally), tolerance of regional outages and tolerance of network problems. It loses on consistency: you can't guarantee a unique username or a non-negative balance, because two leaders can each accept a write that is fine alone but broken together.

Topologies: circular, star, and all-to-all. Circular and star break when one node fails; all-to-all is more fault tolerant but messages can overtake each other, so an update may arrive before the insert it depends on — a causality problem that needs version vectors, not wall-clock timestamps.

Supported by MySQL, Oracle, SQL Server, YugabyteDB, and add-ons like Redis Enterprise, EDB Postgres Distributed and pglogical. It's often a retrofitted feature with sharp edges (autoincrementing keys, triggers, constraints). Sync engines (Google Firestore, Realm, Ditto, PouchDB/CouchDB, Automerge, Yjs) apply the same model to offline-first and local-first apps.

Big idea 8 · dealing with conflicting writes

Two people edit the same page

Two leaders, two edits to the same word, neither knowing about the other. When the two changes finally meet, the database has a conflict. Note that “concurrent” has nothing to do with clocks: two writes are concurrent if neither one knew about the other — even if they were days apart.

You can keep the one with the biggest timestamp (last write wins) and quietly bin the other. You can keep both as siblings and ask a human. Or you can merge them properly, which is what CRDTs and operational transformation do in collaborative apps.

“ice” becomes “nice” and “ice!” at once
Both devices start from the same word.

The shopping cart that refills itself

Merging badly is its own kind of bug. Amazon's old cart merged siblings by keeping every item that appeared in any copy. So if you deleted a book on your laptop and a DVD on your phone, the merge politely put both back in.

A proper merge algorithm records the deletions too, so removed things stay removed. That's the difference between a set union and a real conflict-free replicated datatype.

Compare: run the same two deletions with union merging, then with deletion tracking.

What the book says

Conflict avoidance (route all writes for a record to the same leader) is the simplest strategy, but breaks down when the designated leader has to change, and is impossible for an offline sync engine.

LWW converges but loses data: with concurrent writes, which is “latest” is undefined, so the winner is essentially random — and real-time clocks make it sensitive to clock skew. Siblings (CouchDB) return all concurrent values and let the app or the user merge, which changes the API and can create fresh conflicts.

Automatic conflict resolution gives strong eventual consistency: all replicas that processed the same writes have the same state. Text merges keep every insertion and deletion; collections track deletes so removed items stay removed (Cart = {Soap}); counters add up increments and decrements without double counting.

Two algorithm families: CRDTs (unique immutable IDs per character, used in Redis Enterprise, Riak, Azure Cosmos DB, Automerge, Yjs) and operational transformation (transform the index of each operation, used in Google Docs, ShareDB).

Big idea 9 · leaderless replication

Voting instead of a boss

Throw away the leader entirely. The client sends every write to all the copies and counts the “done!” replies. If enough reply — w of them — the write counts. Reads work the same way: ask everyone, wait for r replies, and believe the one with the newest version number.

The magic rule is w + r > n. If the group you wrote to and the group you read from must overlap in at least one machine, then at least one of your answers is up to date. Nobody has to be in charge; nobody has to fail over.

Stale copies get fixed by read repair (the client writes the fresh value back to whoever was behind), by hinted handoff, and by a slow background anti-entropy sweep.

Break it: click a node to knock it out, write, bring it back, then read. Watch read repair patch it up. Then set w + r ≤ n and see the pill turn yellow.

What the book says

Dynamo-style datastores (Riak, Cassandra, ScyllaDB — not DynamoDB, which is single-leader) let any replica accept writes. With n replicas, w write confirmations and r read responses, w + r > n means at least one node you read from has the latest write. Common: n odd, w = r = (n+1)/2. Reads and writes always go to all n; w and r only say how many you wait for.

Catching up: read repair (the client writes back the newer value it saw), hinted handoff (a stand-in stores writes for an absent replica and delivers them later), and anti-entropy (a background process copying differences in no particular order).

Quorums are not absolute guarantees. Edge cases: restoring a node from an old replica, rebalancing, a read concurrent with a write, a write that succeeded on fewer than w replicas and is never rolled back, clock-based LWW dropping writes, and genuinely concurrent writes.

A sloppy quorum (Riak and Dynamo; “consistency level ANY” in Cassandra/ScyllaDB) lets any reachable node accept the write during a big network interruption — no guarantee that later reads see it, but better than failing. Leaderless systems shine at gray failures and let clients use the fastest responses (request hedging).

Big idea 10 · detecting concurrent writes

Who knew what, and when

How can a database tell “this write replaces that one” from “these two writes never heard of each other”? Not with clocks — with version numbers. Read first, and the server hands you a version. Write it back with that version, and the server knows exactly which state your write was based on.

Anything at or below your version is safely overwritten. Anything above it must have happened without you knowing, so it is kept as a sibling. Nothing is lost, and nobody needs to agree on the time.

With many replicas each taking writes, one number isn't enough: you need one per replica. That bundle is a version vector.

Step through the five writes and watch the sibling list. Two shoppers, one cart, no lost groceries.

What the book says

Operation A happens before B if B knows about, depends on, or builds upon A. Two operations are concurrent if neither happens before the other — regardless of physical time.

The algorithm: the server keeps a version number per key and bumps it on every write; a read returns all siblings plus the latest version; a client must read before writing and must merge what it read; a write carries the version from that prior read, and the server overwrites everything at that version or below while keeping anything higher as a sibling. A write with no version number is concurrent with everything.

With multiple replicas you need a version number per replica per key: the collection is a version vector (Riak calls its encoding the causal context; the dotted version vector is used in Riak 2.0). It makes it safe to read from one replica and write back to another. A version vector is not quite the same as a vector clock — for comparing replica states, version vectors are the right structure.

Why keep copies at all?

Five reasons, straight from the chapter.

High availability

Keep running when a machine, a zone, or a whole region goes down.

Durability

Don't lose data even if a machine fails permanently.

Disconnected operation

Keep working through a network interruption — or a plane flight.

Latency

Put the data near the people using it, so it answers faster.

Scalability

Serve more reads than one machine ever could, by reading from replicas.

The seesaws from this chapter

Every choice buys something and costs something.

Synchronous

The copy is guaranteed safe, but one slow follower blocks every write

vs

Asynchronous

Fast and keeps going, but a confirmed write may not be durable

Single leader

vs

Multi-leader

Write locally and survive cut links, at the price of conflicts

Leader-based

vs

Leaderless quorums

No failover at all, but staleness is hard to monitor

Last write wins

Dead simple, converges — silently throws away real writes

vs

Merge (siblings or CRDT)

Keeps everyone's work, but needs an algorithm or a human

Short failover timeout

Back up fast — and failing over when the leader was only busy

vs

Long failover timeout

No false alarms, but a longer outage when it really did die

Strict quorum

w + r > n, high chance of fresh data, fails when too many nodes are unreachable

vs

Sloppy quorum

Any reachable node takes the write; later reads may not see it

Stop writing, wait a bit, and all copies will agree. “Eventually” is deliberately vague.

Concurrent values kept side by side until someone merges them.
