Encoding and Evolution

Inside a program, data is a web of little boxes joined by invisible strings. To send it anywhere you have to flatten it into a line of bytes — and the program that unpacks it may be a different, older, or newer version of your app.

“Everything changes and nothing stands still.” — Heraclitus of Ephesus, as quoted by Plato in Cratylus (360 BCE), quoted at the start of the chapter

Big idea 1 · old and new at the same time

Painting the town while everyone is still walking through it

Apps change. New features arrive, so the data they save changes too. But you can't change every computer at the same instant. Server code is usually updated a few machines at a time — a rolling upgrade — and phone apps only update when the user feels like it.

So for a while, old code and new code are both running, reading each other's data. That needs two kinds of politeness: backward compatibility (new code can read old data) and forward compatibility (old code can read new data). The second one is harder, because yesterday's code has to be happy about things it has never heard of.

Try it: upgrade the nodes one at a time and watch the traffic keep flowing. Then, in the second stage, let old code read a record that has a field it doesn't know — and see what happens when it saves it back.

Rolling upgrade · five nodes
All five nodes run v1. Requests are flowing. Upgrade one node and nobody notices.

The field that fell out of the note

New code saves a record with a brand-new field, nickname. Then old code reads that record, changes something small, and writes it back. If the old code unpacked the record into an object that has no place to keep nickname, the field quietly disappears.

The fix is for the decoder to keep unknown fields in a pocket and put them back when it writes. Good encoders do this for you.

What the book says

A rolling upgrade (also called a staged rollout) deploys a new version to a few nodes at a time, with no downtime, which encourages frequent releases and better evolvability.

Backward compatibility: newer code can read data written by older code. Forward compatibility: older code can read data written by newer code.

For APIs: for an older client to call a newer service you need backward compatibility on the request and forward compatibility on the response.

Big idea 2 · encoding and decoding

You can't mail a Lego castle with the strings still attached

In memory, data is objects, lists and hash tables held together by pointers — tiny "it's over there" notes. A pointer is a house number inside your program only. Another program has completely different houses.

So before data goes into a file or across a network, you flatten it into a self-contained line of bytes. That's encoding (also called serialization). Rebuilding the objects on the other side is decoding (parsing).

Try it: step through a normal encoding, then switch to your language's own built-in format and try to open the parcel from a program written in a different language.

What the book says

Programs keep data in two representations: in memory (objects, structs, lists, arrays, hash tables, trees, usually with pointers), and as a self-contained sequence of bytes for files and networks. Encoding = in-memory → bytes; decoding = bytes → in-memory.

Careful: "serialization" also means something completely different in transactions, so the book says encoding.

Some formats skip the step: Cap'n Proto and FlatBuffers are zero-copy formats usable both at runtime and on disk.

Language-built-ins — Java's java.io.Serializable, Python's pickle, Ruby's Marshal, Kryo — are convenient but: tied to one language; decoding instantiates arbitrary classes, a classic security hole that can allow remote code execution; versioning is an afterthought; and they are often slow and bloated. Use them only for very transient purposes.

Big idea 3 · JSON, XML and CSV

Writing it out in words on a postcard

The friendliest way to send data is to write it as text: JSON, XML or CSV. Anyone can read it, every language can parse it, and two companies can agree on it — which, honestly, is the hardest part of all.

But text is vague. Is 1337 a number or the word "1337"? How big can a number be before it gets rounded? Where do you put a photo, which isn't text at all? And what if someone's name contains a comma?

Try it: pick a format, then push each of the four values through it and see which ones come out changed.

What the book says

XML is criticized as too verbose and complicated. In XML and CSV you can't tell a number from a string of digits without an external schema. JSON distinguishes strings and numbers but not integers from floats, and doesn't specify precision.

Integers greater than 253 can't be represented exactly in an IEEE 754 double, so they break in JavaScript. X (Twitter) returns post IDs twice — once as a JSON number and once as a decimal string — to work around it.

JSON and XML have no binary string type, so people Base64-encode bytes as text: hacky, and about a third bigger.

CSV has no schema and is vague (commas and newlines inside values); its escaping rules are specified in RFC 4180 but not all parsers implement them correctly. Despite the flaws, these formats are good enough as interchange formats.

Big idea 4 · JSON Schema

The doorkeeper with a clipboard

A schema is a written description of what a record is allowed to look like. JSON Schema is the popular one for JSON, and it can also check values: a port must be a whole number between 1 and 65,535.

The interesting switch is the content model. An open model (the default) lets any extra field in. A closed model (additionalProperties: false) turns away anything not on the clipboard.

Try it: send each field to the door with the model set to open, then flip to closed and send them again. Which switch would break an app that is being upgraded right now?

What the book says

JSON Schema is used in OpenAPI service definitions, in schema registries (Confluent's Schema Registry, Red Hat's Apicurio) and in databases (PostgreSQL's pg_jsonschema, MongoDB's $jsonSchema).

It has primitive types (string, number, integer, object, array, boolean, null) plus a separate validation specification for constraints such as a minimum and maximum.

Open content models (additionalProperties: true, the default) allow undeclared fields; closed ones allow only declared fields. So JSON Schemas usually define what isn't permitted rather than what is.

JSON has no map type with integer keys — object keys are always strings — so you express it with patternProperties and additionalProperties: false. With conditional if/else logic, named types and remote schema references, it is very powerful but unwieldy: resolving remote schemas and evolving schemas compatibly is hard.

Big idea 5 · binary encodings

The same parcel, four sizes of wrapping

Here is one small record: a name, a favourite number, and two interests. Written as JSON text it takes 81 bytes. MessagePack, a binary version of JSON, gets it down to 66 — not much, because with no schema it still has to spell out every field name.

Formats that have a schema can drop the names entirely: Protocol Buffers uses 33 bytes and Avro just 32. Look at the yellow part of each bar: the values are almost identical every time. What shrinks is the packaging.

Try it: click any coloured band to find out what those bytes are doing, then drag the slider to send a million records and watch the difference turn into megabytes.

What the book says

The record is {"userName": "Martin", "favoriteNumber": 1337, "interests": ["daydreaming", "hacking"]}: 81 bytes as JSON with whitespace removed.

Binary JSON variants (MessagePack, CBOR, BSON, BJSON, UBJSON, BISON, Hessian, Smile) and binary XML (WBXML, Fast Infoset) exist in niches; none are as widely adopted as the textual versions. Because they prescribe no schema, they must include every field name. MessagePack takes 66 bytes: 0x83 = object with 3 fields, 0xa8 = an 8-byte string, then userName in ASCII, then 0xa6 and Martin.

Protocol Buffers needs 33 bytes, Avro 32 — the most compact of all.

Schema-based binary encodings can be much more compact; the schema is documentation that can't go stale, a schema database lets you check compatibility before deploying, and code generation gives compile-time type checking in statically typed languages.

Big idea 6 · field tags

Numbered coat hooks

In a Protocol Buffers schema every field gets a number: user_name = 1, favorite_number = 2, interests = 3. The encoded record never spells out the names — it just says "hook 1", "hook 2". You may rename a field freely, but you may never renumber one.

Each field also carries a tiny type annotation. That's the trick that makes forward compatibility work: old code that meets an unknown hook number can read the type, skip exactly the right number of bytes, and keep the mystery bytes safe.

Step through old code reading a record written by new code. Then pick the two rules-breaking scenarios and watch what goes wrong.

What the book says

Protocol Buffers (protobuf) is a binary encoding from Google, similar to Apache Thrift (from Facebook). It requires a schema written in an IDL, and a code generator produces classes in many languages.

An encoded record is just the concatenation of its encoded fields; each is identified by its field tag and annotated with a datatype. Unset fields are simply omitted. Field type and tag are packed into a single byte, and integers use variable-length encoding: 1337 takes two bytes; –64 to 63 fit in one.

Adding a field: give it a new tag number. Old code sees an unknown tag and can skip it using the datatype annotation, preserving the unknown field — forward compatibility. Reading old data with a new schema fills missing fields with a default value (empty string, 0) — backward compatibility.

You can never reuse an old tag number; tags used in the past can be reserved. Changing a datatype is sometimes possible, but a 64-bit value read by old 32-bit code will be truncated. There is no list type: repeated means the same tag simply appears several times.

Big idea 7 · writer's and reader's schema

Two secret decoder rings

Avro goes further: its bytes contain no names and no numbers. Just values, glued end to end. On its own the parcel is meaningless — you have to know the order the writer used.

So Avro reads with two schemas: the writer's schema (exactly the one used to encode) and the reader's schema (what your code expects today). Avro lines the two up by field name: fields only the writer has are ignored, fields only the reader has are filled from the reader's declared default.

Try each scenario. Shuffle the field order — still fine. Add a field with a default — fine. Add one without a default — that's where compatibility breaks.

What the book says

Avro started in 2009 as a Hadoop subproject. It has two schema languages: Avro IDL for humans and a JSON-based one for machines. Our record encodes to 32 bytes: nothing in the data identifies fields or types, so it can be decoded only with the writer's schema.

Resolution matches fields by name. Different field order is no problem. A field in the writer's schema but not the reader's is ignored; a field the reader expects but the writer lacks is filled with the default declared in the reader's schema.

You may add or remove only a field that has a default value. Adding one with no default breaks backward compatibility; removing one with no default breaks forward compatibility. null is not a default for everything: you need a union type, and null must be the first branch.

Where does the writer's schema come from? A large file stores it once at the start (Avro object container files); a database stores a version number per record and keeps a list of schema versions (Confluent's schema registry for Kafka, LinkedIn's Espresso); a network connection negotiates it at setup (Avro RPC).

Avro suits dynamically generated schemas — dump a relational table and each column becomes a field by name, with no tag numbers to assign by hand. Renaming a field via aliases in the reader's schema is backward but not forward compatible.

Big idea 8 · dataflow through databases

A note to your future self

Writing to a database is sending a message to whoever reads it later — often a future version of you. You replace all your app code in an afternoon, but the rows written five years ago are still sitting there in their original encoding. People say: data outlives code.

Rewriting every row is expensive, so databases cheat kindly. Adding a column with a null default doesn't touch the old rows: when one is read, the missing column is filled in with null. LSM-tree storage engines rewrite rows into the newest format later, during compaction.

Try it: deploy the new version, read an ancient row, then run a compaction and watch the old shapes quietly become the new shape.

What the book says

Several processes usually access a database at once, and during a rolling upgrade some run new code and some old. So a value may be written by newer code and read by older code: forward compatibility is often required for databases too.

Migrating data into a new schema is possible but expensive on a large dataset, so most databases defer it, asynchronously and best-effort. LSM-tree engines rewrite data in the latest format during compaction; relational databases add a column with a null default without rewriting existing rows.

Schema evolution lets the whole database appear to use one schema even though the storage holds many historical versions. Harder changes — single-valued to multivalued, moving data to another table — still need rewriting at the application level, and staying compatible across such migrations is a research problem.

A snapshot for backup or for a data warehouse is written in one go and is immutable, so it is usually encoded with the latest schema — a good fit for Avro object container files, or a column-oriented format such as Parquet.

Big idea 9 · REST and RPC

Shouting across the playground

A service is a program that takes requests over the network. When it speaks HTTP we call it a web service, and the most popular style is REST: plain data formats, URLs that name things, and the features HTTP already has.

An old idea called RPC tries to make a network call look exactly like calling a function next door. It never quite works. Calling the kid beside you always works. Shouting across the playground can be lost, can be slow, and worst of all: if no answer comes back, you can't tell whether they heard you.

Try it: lose the response, then hit Retry. The cupcake gets paid for twice — unless the request carries a unique ID so the server can spot the duplicate (the book calls this idempotence).

What the book says

Services expose an application-specific API rather than arbitrary queries, which gives encapsulation. Microservices aim to make services independently deployable and evolvable, each owned by one team, so old and new versions of clients and servers run at once.

Service developers publish an IDL: OpenAPI (Swagger) for JSON web services, Protocol Buffers for gRPC. Frameworks like Spring Boot, FastAPI and gRPC handle routing, metrics, caching and authentication; tools generate clients, docs and compatibility checks.

RPC's promise of location transparency is fundamentally flawed. A network request is unpredictable; it can time out, and then you simply don't know what happened; retrying may perform the action twice unless you build in idempotence; latency is wildly variable; parameters must be encoded; and languages disagree about datatypes.

For services you can assume servers are updated first, so you need backward compatibility on requests and forward compatibility on responses. Because clients outside your organization may never upgrade, compatibility must be kept for a long time, often by running several API versions side by side (version in the URL, in an Accept header, or per API key).

Clients find servers through service discovery and load balancing: hardware load balancers, software ones (NGINX, HAProxy), DNS (which caches, so entries go stale), registries such as etcd and ZooKeeper with heartbeats, or a service mesh (Istio, Linkerd) using sidecars that handle encryption and observability.

Big idea 10 · workflows and event-driven systems

The recipe that remembers, and the mailbox that waits

Paying for something touches several services: check for fraud, debit the card, deposit the money. That chain is a workflow and each link is a task. You can't wrap them in one database transaction, so what happens if the machine dies halfway?

Durable execution frameworks (Temporal, Restate) write every call and its result to a durable log. When the task is re-run, finished calls aren't really made again — the framework replays the answers from the log. That gives exactly-once behaviour, as long as your code is deterministic.

The other way to move data is to not wait at all: drop a message in a message broker and walk away. The broker holds it, redelivers it if a consumer crashes, and can hand the same message to many subscribers.

Crash it and see

Run the payment, press Crash now in the middle, then restart. Without a log, the card gets charged a second time. With the log, the first two steps are replayed from memory of what happened and only the unfinished step really runs.

What the book says

Workflows are graphs of tasks, defined in code, a DSL, or markup such as BPEL; drawn with notations like BPMN. Temporal calls tasks activities; others say durable functions.

A workflow engine has an orchestrator (scheduling) and an executor (running). Airflow, Dagster and Prefect orchestrate ETL; Camunda and Orkes give a graphical notation; Temporal and Restate provide durable execution.

If a task fails the framework re-executes it but skips RPC calls and state changes that already succeeded, returning the previous results, because everything is logged to durable storage like a write-ahead log.

Catches: external services must still provide an idempotent API with unique IDs; the framework expects the same RPCs in the same order, so reordering calls is risky — deploy a new version instead of editing an existing workflow; and nondeterministic code (random numbers, clocks) breaks replay, which is why frameworks ship deterministic replacements and checkers like Temporal's Workflow Check.

Leave it in the mailbox

With a broker the sender doesn't wait for anyone. If a consumer is switched off, messages pile up safely and are delivered when it comes back. A queue gives each message to one consumer; a topic gives a copy to every subscriber.

Try it: crash consumer B, publish a few messages, then bring B back.

What the book says

In event-driven architectures a request is an event or message, sent via a message broker (event broker, message queue, message-oriented middleware) that stores it temporarily. Senders don't wait: communication is asynchronous.

A broker buffers when the recipient is unavailable, redelivers to crashed processes, removes the need for service discovery, lets one message reach several recipients, and decouples sender from recipient.

Two patterns: a named queue (one of the consumers receives each message) and a named topic (all subscribers receive it). Open source brokers include RabbitMQ, ActiveMQ, HornetQ, NATS, Redpanda and Apache Kafka; cloud ones include Amazon Kinesis, Azure Service Bus and Google Cloud Pub/Sub.

Brokers don't enforce a data model — a message is bytes plus metadata — so teams use Protocol Buffers, Avro or JSON with a schema registry, and AsyncAPI to specify messages. Many brokers delete messages after consumption; some can keep them forever, which is what event sourcing needs. A consumer that republishes messages must be careful to preserve unknown fields.

In distributed actor frameworks (Akka, Orleans, Erlang/OTP) each actor has private state and communicates only by asynchronous messages that may be lost — so location transparency works better than in RPC. Rolling upgrades still need forward and backward compatible message encodings.

The seesaws from this chapter

Every encoding choice buys something and costs something else.

Text formats (JSON, XML, CSV)

Anyone can read them; every language parses them; easy to agree on between companies

vs

Binary schema formats (Protobuf, Avro)

Half the size and precise types, but you must decode before a human can read it

Your language's own format

One line of code to save an object

vs

A standard format

Other languages can read it, it's safer to decode, and versioning was actually thought about

Field tags (Protocol Buffers)

Numbers never change meaning; renaming is free; but tags are assigned by hand

vs

Field names (Avro)

Great for schemas generated automatically from a database; needs the writer's schema on hand

Open content model

Unknown fields pass through, so old and new code can share data

vs

Closed content model

Catches typos and junk, but rejects anything a newer version invents

RPC / REST request

You get an answer right away — if the network cooperates

vs

Message broker

Send and forget; it buffers, redelivers and fans out, but nobody replies

Rewrite all the data on upgrade

One single schema everywhere, expensive on a big dataset

vs

Let schemas evolve

Old rows stay as they are and are translated when read or compacted

Words to know

Grown-up words, in plain language.

encoding
Flattening in-memory objects into a line of bytes. Also called serialization or marshaling.
decoding
Turning those bytes back into objects. Also called parsing or deserialization.
backward compatibility
New code can read data written by old code.
forward compatibility
Old code can read data written by new code — the trickier one.
rolling upgrade
Updating a few machines at a time so the service never goes down.
evolvability
How easy it is to change a system later.
schema
A written description of what a record looks like: its fields and their types.
schema evolution
Changing that description over time without breaking old data or old code.
schema migration
Actually rewriting stored data into a new shape. Expensive when there's a lot of it.
JSON Schema
A way to describe and check JSON, including rules like "between 1 and 65,535".
open / closed content model
Whether extra fields nobody declared are allowed in (open) or turned away (closed).
Base64
Writing raw bytes as ordinary text so they fit in JSON or XML. Makes them about a third bigger.
MessagePack
A binary version of JSON. Smaller, but still ships every field name.
Protocol Buffers
A compact binary format from Google where each field has a number.
field tag
That number. A short nickname for a field, so names never travel.
variable-length integer
Small numbers use fewer bytes; big ones use more.
Avro
A binary format with no names and no tags in the data — just values in schema order.
writer's schema
The exact schema used when the bytes were written.
reader's schema
What your code expects today. Avro translates between the two by field name.
schema registry
A list of every schema version, so a reader can look up the one it needs.
data outlives code
You can replace all your code in minutes; five-year-old rows stay exactly as they were.
IDL
Interface definition language: the file that describes an API, like OpenAPI or a .proto file.
RPC
Remote procedure call: pretending a network request is an ordinary function call.
idempotence
Doing something twice has the same effect as doing it once — so retries are safe.
service discovery
How a client finds out which machine is running the service right now.
durable execution
Logging every step of a workflow so a crashed run can carry on instead of starting over.
message broker
A mailbox in the middle that stores messages and delivers them later.
