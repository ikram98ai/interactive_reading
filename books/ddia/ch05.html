Encoding and evolution · old and new code at the same time

Repainting the bus fleet while it’s still running

Amara’s city has four buses and a new timetable format. She can’t park the whole fleet for a day, so she upgrades one bus a night. For a week, old buses and new buses share the same road, and every bus reads timetables that any other bus may have written.

Servers work the same way. A rolling upgrade deploys the new version to a few nodes at a time, so there is no downtime. Phone and desktop apps are worse: you’re at the mercy of users, who may not install the update for months. So old and new code, and old and new data, live side by side, and every read needs one of two promises. Backward compatibility: newer code can read what older code wrote. Forward compatibility: older code can read what newer code wrote. Backward is usually easy, because you know the old format. Forward is harder, because old code has to ignore things it has never heard of.

Try it: in Rolling upgrade, press Upgrade next node once, then press Write, then read a few times and watch which promise each read needs. In API calls, pick who is old, the client or the service, and press Call: the request and the response need different promises.

What the book says

Applications inevitably change over time, and a change to features usually means a change to the data they store. Relational databases assume that exactly one schema is in force at any one time (changed by migrations, i.e. ALTER statements); schema-on-read databases may hold a mixture of older and newer formats written at different times.

In a large application, code changes can’t happen instantaneously. Server-side applications use a rolling upgrade (also known as a staged rollout): deploy to a few nodes at a time, check that it runs smoothly, and work through all the nodes, with no downtime. With client-side applications you’re at the mercy of the user, who may not install the update for some time. So old and new versions of the code, and old and new data formats, may coexist.

Backward compatibility ensures that newer code can read data written by older code; forward compatibility ensures that older code can read data written by newer code. For an older client to call a newer service, you need backward compatibility on the request and forward compatibility on the response; for a newer client calling an older service, the reverse.

Backward compatibility is normally not hard, since the author of the new code knows the old format. Forward compatibility is trickier, because older code must ignore additions made by a newer version.

Encoding and evolution · keeping unknown fields intact

The old app that quietly deletes your new field

Kenji’s team adds a language field to user profiles. A new server saves Kenji’s profile with lang: "ja". A minute later an old server, which has never heard of lang, changes his photo and saves the profile back. Kenji’s language setting is gone, and nobody touched it.

The old code decoded the record into a model object that only had slots for the fields it knew. The unknown field fell out during decoding, so it wasn’t there to write back. The fix is for decoders to keep unknown fields on the side and re-encode them untouched, even though the old code can’t interpret them.

Try it: press Run the story and follow the record through decode, update and encode in the code. Then switch to Keep unknown fields and run it again: the old code still can’t read lang, but it no longer destroys it.

What the book says

Another challenge with forward compatibility (Figure 5-1): you add a field to a record schema, and newer code creates a record containing that field and stores it in a database. Then an older version of the code, which doesn’t know about the new field, reads the record, updates it and writes it back.

The desirable behavior is usually for the old code to keep the new field intact, even though it couldn’t interpret it. But if the record is decoded into a model object that does not explicitly preserve unknown fields, data can be lost.

The chapter then looks at JSON, XML, Protocol Buffers and Avro, how they handle schema changes, and how they are used in databases, web services, REST APIs, RPCs, workflow engines and event-driven systems such as actors and message queues.

Formats for encoding data · two representations

You can’t mail a pointer

Priya’s shopping list lives in her program’s memory as objects that point at each other: a user object holds the address of a list, and the list holds the addresses of two strings. If she sends those raw bytes to Tomás’s computer, the addresses point into his memory, where they mean nothing, or something else entirely.

So every program keeps data in two forms. In memory: objects, structs, lists, hash tables, trees, tuned for the CPU and full of pointers. On disk or on the wire: one self-contained sequence of bytes. Turning the first into the second is encoding (also serialization or marshaling); the reverse is decoding (parsing, deserialization, unmarshaling). This book says encoding, because serialization means something else in transactions (Chapter 8).

Try it: press Encode → send → decode and watch the pointers become nested text and then new pointers in a different process. Switch to Copy raw memory and send again: the addresses arrive, the objects don’t.

What the book says

Programs usually work with data in (at least) two representations. In memory, data is kept in objects, structs, lists, arrays, hash tables and trees, optimized for efficient access by the CPU, typically using pointers. To write data to a file or send it over the network, you encode it as a self-contained sequence of bytes (e.g., a JSON document). Since a pointer wouldn’t make sense to any other process, this looks quite different from in-memory structures.

The translation from in-memory representation to bytes is encoding (also serialization or marshaling), and the reverse is decoding (parsing, deserialization or unmarshaling). Because serialization also has a completely different meaning in the context of transactions, the book sticks with encoding.

Sometimes no conversion is needed: a database may operate directly on compressed data loaded from disk, and zero-copy formats such as Cap’n Proto and FlatBuffers are designed to be used at runtime and on disk or the network without an explicit conversion step. Most systems, though, do need to convert.

Formats for encoding data · language-specific formats

The one-line save that costs you later

Leila’s Python service saves orders with one line: pickle.dumps(order). It works beautifully until Oskar’s Java team needs to read those orders, the order class gets a new field, and a security review asks what happens when the decoder is handed bytes from a stranger.

Built-in formats such as Java’s java.io.Serializable, Python’s pickle and Ruby’s Marshal are convenient, but they have four deep problems: they tie the data to one language; decoding can build any class the bytes name, a classic route for attackers; versioning is an afterthought; and efficiency often is too. Use them only for very short-lived data.

Try it: pick each problem and press its button. Language sends the bytes to a Java reader. Classes feeds the decoder bytes from outside, first trusting whatever they name, then with an allow-list. Versions reads an old order with new code. Size compares the same order in two encodings.

What the book says

Many programming languages have built-in support for encoding in-memory objects: Java has java.io.Serializable, Python has pickle, Ruby has Marshal; third-party libraries such as Kryo exist for Java. They are convenient, because objects can be saved and restored with minimal code, but they have a number of deep problems:

  • The encoding is often tied to one programming language, so reading it in another is difficult. You commit to your current language for a long time and preclude integrating with other organizations.
  • To restore the same object types, the decoder must be able to instantiate arbitrary classes. This is frequently a source of security problems: if an attacker can get your application to decode an arbitrary byte sequence, they can instantiate arbitrary classes, which often lets them do terrible things such as remotely executing arbitrary code.
  • Versioning data is often an afterthought; forward and backward compatibility are neglected.
  • Efficiency (CPU time and encoded size) is often an afterthought too; Java’s built-in serialization is notorious for bad performance and bloated encoding.

So it’s generally a bad idea to use your language’s built-in encoding for anything other than very transient purposes.

JSON, XML and binary variants · the trouble with numbers

The post ID that changed on the way

Mei’s app fetches a post by its ID, a big 64-bit number. The server sends it correctly. Her browser parses the JSON and gets a slightly different number, then asks the server for a post that doesn’t exist.

JSON tells strings from numbers, but not integers from floating-point, and sets no precision. JavaScript reads every JSON number into an IEEE 754 double, which holds integers exactly only up to 253. Above that, neighbouring integers collapse into one. XML and CSV are vaguer still: 007 could be a number or a string of digits. X’s API sends each post ID twice, once as a number and once as a decimal string, for exactly this reason.

Try it: press Send as JSON number for each ID, from small to huge. This machine runs your browser’s own JSON.parse, so the damage you see is real. Then press Send as string too. In XML / CSV, decide whether 007 is a number.

What the book says

JSON and XML are the obvious language-independent contenders: widely known and supported. CSV is another, but supports only tabular data without nesting. All three are textual and somewhat human-readable. XML is often criticized as too verbose and unnecessarily complicated.

There is a lot of ambiguity around numbers. In XML and CSV you can’t distinguish a number from a string of digits (except via an external schema). JSON distinguishes strings and numbers, but not integers and floating-point numbers, and it doesn’t specify a precision.

Integers greater than 253 cannot be exactly represented in an IEEE 754 double-precision floating-point number, so such numbers become inaccurate when parsed in a language that uses floating-point numbers, such as JavaScript. X uses a 64-bit number to identify each post; its API returns post IDs twice, once as a JSON number and once as a decimal string, to work around the incorrect parsing by JavaScript applications.

JSON, XML and binary variants · binary strings, schemas and CSV

Bytes in a text costume, and the comma that broke a row

Tomás wants to put a user’s thumbnail inside a JSON message. JSON has text strings, but no way to say “these are raw bytes.” So the bytes are dressed up as text with Base64: every 3 bytes become 4 letters. It works, but it’s hacky, and the message grows by about a third. Only a schema, or code written by hand, tells the reader to undo it.

CSV has no schema at all. Each application decides what each column means, and handles a new row or column by hand. It is also vague: what if a value contains a comma or a newline? The escaping rules are written down (wrap the value in double quotes, and double any quote inside), but not every parser follows them.

Try it: in Base64, press Grow the image and watch both sizes; the encoding is your browser’s real btoa. In CSV, press Parse with the naive splitter, then switch the parser to quote-aware and parse again.

What the book says

JSON and XML have good support for Unicode character strings, but they don’t support binary strings (sequences of bytes without a character encoding). People get around this by encoding binary data as text using Base64, with the schema indicating that the value should be interpreted as Base64. This works, but it’s somewhat hacky and increases the data size by about a third.

XML Schema and JSON Schema are powerful and thus quite complicated to learn and implement. Since the correct interpretation of data (such as numbers and binary strings) depends on the schema, applications that don’t use one may need to hardcode the encoding and decoding logic instead.

CSV has no schema, so it’s up to the application to define the meaning of each row and column; a new row or column must be handled manually. It is also vague (what if a value contains a comma or a newline?). Its escaping rules have been formally specified, but not all parsers implement them correctly.

Despite these flaws, JSON, XML and CSV are good enough for many purposes and will likely remain popular as data interchange formats between organizations. As long as people agree on the format, it often doesn’t matter how pretty or efficient it is; the difficulty of getting different organizations to agree on anything outweighs most other concerns.

JSON, XML and binary variants · JSON Schema

The doorkeeper who only knows what isn’t allowed

Freya runs the door at a club. Her list says “guests named on the list must show a valid ticket.” Someone not on the list at all? With an open list, she waves them in. With a closed list, only named guests get in. That one setting decides whether a newer app can add fields that older readers never declared.

JSON Schema describes JSON with types (string, number, integer, object, array, boolean, null) plus validation rules: a port must be between 1 and 65,535. Its default is an open content model (additionalProperties: true): undeclared fields pass. So a schema usually says what isn’t permitted. JSON objects only have string keys, so a map from integer IDs to names needs patternProperties with a ^[0-9]+$ key pattern and additionalProperties: false.

Try it: press Validate on each document under the Port rule schema, then flip it between open and closed. Switch to Integer-keyed map (the book’s Example 5-1) and validate the documents there. The highlighted line in the schema is the rule that decided.

What the book says

JSON Schema has become widely adopted to model data exchanged between systems or written to storage: in web services as part of the OpenAPI specification, in schema registries such as Confluent’s Schema Registry and Red Hat’s Apicurio Registry, and in databases (PostgreSQL’s pg_jsonschema validator extension and MongoDB’s $jsonSchema validator syntax).

Schemas include primitive types such as string, number, integer, object, array, boolean and null, and a separate validation specification lets developers overlay constraints on fields; for example, a port field might have a minimum value of 1 and a maximum of 65,535.

An open content model permits any field not defined in the schema to exist with any datatype; a closed content model allows only explicitly defined fields. The open model is enabled when additionalProperties is true, which is the default. Thus JSON Schemas are usually a definition of what isn’t permitted rather than what is.

Example 5-1 defines a map from integers to strings: since JSON object keys are always strings, it uses patternProperties to allow only digit keys with string values, and additionalProperties false. JSON Schema also supports conditional if/else logic, named types and references to remote schemas. This makes it a very powerful schema language, but definitions get unwieldy, and evolving schemas in a forward- or backward-compatible way can be challenging. Similar concerns apply to XML Schema.

JSON, XML and binary variants · binary encodings

Binary JSON still spells out every field name

Nadia shrinks her JSON messages with MessagePack, a binary encoding of JSON. Instead of quotes, colons and braces, each value starts with a small type byte: 0x83 means “an object with 3 fields,” 0xa8 means “a string of 8 bytes.” Because each string’s length comes first, the reader needs no closing quote and no escaping.

But MessagePack has no schema, so the reader can’t know the field names in advance. The names userName, favoriteNumber and interests travel inside every record. The book’s record shrinks from 81 bytes of JSON to 66: not much, for giving up human-readability.

Try it: press Next byte to decode the record one piece at a time, or click any byte. Lilac bytes are field names, yellow are values, blue are type and length markers. Then change the name with Change userName and watch the encoder rebuild the bytes.

What the book says

JSON is less verbose than XML, but both use a lot of space compared to binary formats. This led to a profusion of binary encodings for JSON (MessagePack, CBOR, BSON, BJSON, UBJSON, BISON, Hessian and Smile) and for XML (WBXML and Fast Infoset). They have been adopted in niches, but none is as widely adopted as textual JSON and XML.

Some extend the set of datatypes (distinguishing integers and floats, or adding binary strings), but otherwise keep the JSON/XML data model. Since they don’t prescribe a schema, they must include all the object field names within the encoded data.

For Example 5-2 in MessagePack (Figure 5-2): the first byte, 0x83, indicates an object (top four bits 0x80) with three fields (bottom four bits 0x03); an object with more than 15 fields gets a different type indicator, with the count in two or four bytes. The second byte, 0xa8, indicates a string (top bits 0xa0) eight bytes long. The next eight bytes are the field name userName in ASCII; no end marker or escaping is needed. The next seven bytes encode the six-letter value Martin with the prefix 0xa6, and so on.

The binary encoding is 66 bytes long, only a little less than the 81 bytes of textual JSON with whitespace removed. It’s not clear whether such a small space reduction (and perhaps faster parsing) is worth the loss of human-readability.

Formats for encoding data · Protocol Buffers

Numbered coat hooks instead of name tags

At Kwame’s school every coat hook has a number. A letter home doesn’t say “the blue coat belongs on the hook marked favouriteNumber”; it says “hook 2.” Everyone has the same chart that maps numbers to names, so the names never need to travel.

Protocol Buffers (from Google, much like Apache Thrift) requires a schema, written in its IDL. Each field gets a field tag number, and a code generator turns the schema into classes for many languages. On the wire, one byte holds both the tag and a wire type: (tag << 3) | type. Integers are varints: 7 bits per byte, the top bit saying “more bytes follow,” least significant group first. A repeated field is just the same tag appearing again. The book’s record becomes 33 bytes.

Try it: press Next field to decode the 33 bytes; the matching schema line lights up. Then open Varint lab and drag the number: watch it split into 7-bit groups, and see how many bytes small and large numbers need.

What the book says

Protocol Buffers (protobuf) is a binary encoding library developed at Google, similar to Apache Thrift, originally developed by Facebook; most of what applies to Protocol Buffers applies to Thrift. It requires a schema, written in its interface definition language (IDL), and comes with a code generation tool that produces classes implementing the schema in various programming languages. Its schema language defines fields and types, but doesn’t support other restrictions on values.

Encoding Example 5-2 takes 33 bytes (Figure 5-3). Each field has a type annotation and, where required, a length. There are no field names; instead the data contains field tags, the numbers 1, 2 and 3 from the schema, a compact alias for each field. It packs the field type and tag number into a single byte.

It uses variable-length integers: 1337 is encoded in two bytes, with the top bit of each byte indicating whether more bytes follow; the least significant seven bits come first. So numbers from –64 to 63 are encoded in one byte, –8,192 to 8,191 in two bytes, and so on.

There is no explicit list or array type. The repeated modifier on interests means the field contains a list, represented simply as repeated occurrences of the same field tag in the record.

Protocol Buffers · field tags and schema evolution

Never repaint the number on a hook

Back at Kwame’s school, the hooks get new name labels all the time, and nobody minds: letters only mention numbers. New hooks can be added with new numbers. But if hook 2 suddenly means “lunchbox” instead of “coat,” every old letter is now wrong.

Changing a schema over time is schema evolution. In Protocol Buffers a record is just its fields, each labelled with a tag and a type. Rename a field freely; names never travel. Add a field with a new tag: old code skips it, using the type to know how many bytes to skip, and can keep it (forward compatible); new code reading old data fills in a default such as "" or 0 (backward compatible). Remove a field, and never reuse its tag; reserve it. Widening int32 to int64 is safe one way only: old code truncates big values.

Try it: choose a change, then press New writes, old reads and Old writes, new reads. Try Reuse tag 2 and int32 → int64 to see the two ways it goes wrong. The schema tabs show v1 and v2 side by side.

What the book says

Schemas inevitably need to change over time; this is schema evolution. An encoded record is just the concatenation of its encoded fields, each identified by its tag number and annotated with a datatype. A field whose value is not set is simply omitted. Field tags are critical: you can change a field’s name, since the data never refers to names, but you cannot change a field’s tag, since that would make all existing encoded data invalid.

You can add new fields with new tag numbers. Old code reading data written by new code can ignore a tag it doesn’t recognize; the datatype annotation tells the parser how many bytes to skip, while preserving the unknown fields to avoid the problem in Figure 5-1. This keeps forward compatibility. As long as each tag is unique, new code can always read old data, filling missing fields with a default (the empty string, or 0 for a number): backward compatibility.

Removing a field is like adding one, with the concerns reversed. You can never use the same tag number again, because data with the old tag may still exist; past tags can be reserved in the schema so they are not forgotten.

Changing a datatype is possible with some types, with a risk of truncation: change a 32-bit integer into a 64-bit integer, and new code can read old data (filling missing bits with 0s), but old code reading new data still uses a 32-bit variable, so a value that won’t fit will be truncated.

Formats for encoding data · Avro

No names, no numbers, just values in a row

Hana and Diego swap notes in a code where nothing is labelled: “six letters, then a number, then two words.” It’s the shortest note possible, but only someone holding the exact same field list can read it. Swap two lines of the list, and the note turns into nonsense.

Apache Avro began in 2009 as part of Hadoop. It has two schema languages, Avro IDL for people and a JSON form for machines, and its schema has no tag numbers. The encoding is just values one after another: a string is a length then UTF-8 bytes, an integer is a varint, and nothing says which is which. The book’s record is 32 bytes, the smallest yet. To decode, you walk the schema’s fields in order, so the reader must know the exact schema the writer used.

Try it: press Next field to decode the 32 bytes with the correct schema. Then pick Reader swaps two fields and decode again: the same bytes, read with the wrong schema, come out as garbage or an error. This is a real decoder, not a drawing.

What the book says

Apache Avro is another binary encoding format, started in 2009 as a subproject of Hadoop because Protocol Buffers was not a good fit for Hadoop’s use cases. It also uses a schema, with two schema languages: Avro IDL, intended for human editing, and one based on JSON that is more easily machine-readable. Like Protocol Buffers, they specify only fields and their types, without complex validation rules.

The schema has no tag numbers. Encoding Example 5-2 gives just 32 bytes, the most compact of all the encodings seen (Figure 5-4). Nothing identifies fields or their datatypes; the encoding simply consists of values concatenated together. A string is a length prefix followed by UTF-8 bytes, but nothing says it is a string; an integer uses a variable-length encoding.

To parse the data, you go through the fields in the order they appear in the schema and use the schema to determine each field’s datatype. So the data can be decoded correctly only if the reader uses the exact same schema as the writer; any mismatch would mean incorrectly decoded data.

Avro · the writer’s schema and the reader’s schema

Two lists, matched up by name

A hotel receptionist gets a guest form from last year (the writer’s version) and must type it into this year’s booking system (the reader’s version). She lines up the boxes by their labels, not their position: “Name” goes to “Name” even if it moved. A box the new system doesn’t have, she skips. A box the old form never had, she fills with the default.

Avro decodes with two schemas. The writer’s schema is exactly the one used to encode, needed to walk the bytes. The reader’s schema is what today’s code expects. Avro resolves one into the other by field name: order doesn’t matter, writer-only fields are ignored, reader-only fields get the reader’s default. That’s how Avro reaches compatibility without tags.

Try it: press Resolve and watch each writer field find its partner. Then edit the reader’s schema: Shuffle order, Drop interests, Add photoUrl (default null). Resolve after each change; the pseudocode shows which rule fired.

What the book says

When an application encodes data, it uses whatever version of the schema it knows about, for example one compiled into the application. This is the writer’s schema.

To decode, an application uses two schemas: the writer’s schema, identical to the one used for encoding, and the reader’s schema, which may be different (Figure 5-5). The reader’s schema defines the fields the application code expects, and their types. In Protocol Buffers, encoding and decoding can use different versions of a schema; in Avro, the writer’s schema must be identical to the one used for encoding, but the reader’s schema can be older or newer.

If the two are the same, decoding is easy. If they differ, Avro resolves the differences by comparing them and translating the data from the writer’s schema into the reader’s schema, as defined by the Avro specification (Figure 5-6). Fields in a different order are fine, because resolution matches fields by name. A field in the writer’s schema but not the reader’s is ignored. A field the reader expects but the writer’s schema lacks is filled in with a default value declared in the reader’s schema.

Avro · schema evolution rules

Only fields with a default may come and go

Jonas edits the team’s Avro schema and asks the same two questions every time. Can new readers still read old data (backward)? Can old readers read new data (forward)? In Avro, “forward” means the writer is newer than the reader; “backward” means the writer is older.

The rule of thumb: add or remove only fields that have a default. Add a field without one, and new readers have nothing to fill in for old records. Remove one without a default, and old readers have nothing to fill in for new records. null isn’t automatically allowed: a nullable field is a union like union { null, long }, and null can be the default only if it is the first branch. Renames use aliases in the reader’s schema, and so do adding a union branch: both are backward but not forward compatible.

Try it: pick a change and press Check both directions. The machine really runs two readers: a new reader on an old record, and an old reader on a new record. The schema below shows the change as a diff.

What the book says

With Avro, forward compatibility means the writer can use a newer version of the schema than the reader; backward compatibility means the writer can use an older version than the reader.

To maintain compatibility, you may add or remove only a field that has a default value (like favoriteNumber). Add a field with a default, and a reader with the new schema reading an old record fills in the default. Add a field with no default, and new readers can’t read old data: backward compatibility breaks. Remove a field with no default, and old readers can’t read new data: forward compatibility breaks.

In some languages null is an acceptable default for any variable, but not in Avro: to allow a field to be null you use a union type, e.g. union { null, long, string } field. You can use null as a default only if it is the first branch of the union. This is more verbose than everything being nullable by default, but it helps prevent bugs by being explicit about what can and cannot be null.

Changing a datatype is possible if Avro can convert the type. Changing a field name is possible but a little tricky: the reader’s schema can contain aliases for field names, so a rename is backward compatible but not forward compatible. Similarly, adding a branch to a union type is backward compatible but not forward compatible.

Avro · but what is the writer’s schema?

Where the decoder finds the key

Avro can’t decode without the writer’s schema, but sending the whole schema with every record would be silly: the schema is bigger than the data. So where does the reader find it? It depends on how the data travels.

A big file of millions of records all written with one schema puts it once in the file header (Avro’s object container files). A database whose records were written at different times stores a small version number in front of each record and a table of schemas; Confluent’s schema registry for Kafka and LinkedIn’s Espresso work like this. Two processes on a network connection agree on the schema version when the connection opens, as the Avro RPC protocol does.

Try it: in each mode press Read a record and watch where the writer’s schema comes from. In Database, read several times: records from different years point at different schema versions, and the bytes it costs per record stay tiny.

What the book says

How does the reader know the writer’s schema for a particular piece of data? Including the entire schema with every record is not an option, because the schema would likely be much bigger than the encoded data, negating the space savings. The answer depends on the context.

  • Large file with lots of records: millions of records all encoded with the same schema. The writer can include the schema once at the beginning of the file; Avro specifies a file format, object container files, to do this.
  • Database with individually written records: records may be written at different times using different schemas. Include a version number at the beginning of every record and keep a list of schema versions in the database; a reader extracts the version and fetches that writer’s schema. Confluent’s schema registry for Apache Kafka and LinkedIn’s Espresso work this way.
  • Sending records over a network connection: two processes on a bidirectional connection can negotiate the schema version on connection setup and use it for the connection’s lifetime. The Avro RPC protocol works like this.

A database of schema versions is useful in any case: it acts as documentation and gives you a chance to check schema compatibility. A simple incrementing integer or a hash of the schema can serve as the version number.

Avro · dynamically generated schemas

The nightly export that writes its own schema

Every night, Chidi’s job dumps a database table to a file. Analysts change the table often: a column added here, one dropped there. Chidi doesn’t want to touch the export code each time.

With Avro, the job simply generates the schema from the table on every run: one record per table, one field per column, the column name as the field name. Old readers still match up the fields by name. With Protocol Buffers, every column needs a hand-picked tag number. An automatic tagger must remember every tag ever used, or it will hand a dropped column’s number to a new one, and old files will be read as the wrong column. Dynamic schemas were a design goal of Avro, never of Protocol Buffers.

Try it: press Run export. Then Add column or Drop column and export again. Compare the two generators below the table: in Protobuf (naive tags), drop then add a column and read an old file with the new mapping.

What the book says

One advantage of Avro compared to Protocol Buffers is that the schema contains no tag numbers, which makes Avro friendlier to dynamically generated schemas.

Say you want to dump a relational database to a file in a binary format, avoiding the problems of textual formats. With Avro you can fairly easily generate an Avro schema (in its JSON representation) from the relational schema and dump the contents to an Avro object container file. You generate a record schema for each table; each column becomes a field, and the column name maps to the field name.

If the database schema changes (e.g., one column added and one removed), you just generate a new Avro schema and export with it; the export doesn’t need to pay attention to the change. Readers see that the fields changed, but since fields are identified by name, the updated writer’s schema can still be matched with the old reader’s schema.

With Protocol Buffers, the field tags would likely have to be assigned by hand, and an administrator would have to update the mapping from column names to tags every time the schema changed. It might be possible to automate, but the generator would have to be very careful not to assign previously used tags. Dynamically generated schemas simply weren’t a design goal of Protocol Buffers, whereas they were for Avro.

Formats for encoding data · the merits of schemas

A schema is documentation that can’t go stale

Elif’s team keeps every version of every schema in a registry. Before anyone deploys, a check runs: “Can the new schema still read data written with each old one, and the other way round?” Twice this month it stopped a deploy that would have broken a reader nobody remembered.

Schema-based binary formats earn their keep four ways. They are compact, because names stay out of the data. The schema is documentation that must be accurate, because decoding needs it. A schema database lets you check compatibility before deploying. And generated code gives statically typed languages compile-time type checks. The idea isn’t new: ASN.1, standardized in 1984, used tag numbers too, and its DER encoding still carries SSL certificates (X.509). It is also very complex.

Try it: in Size, press Encode all four and compare the bars, made by this page’s real encoders. In Registry gate, propose each change and press Deploy: the registry checks it against every stored version first.

What the book says

Protocol Buffers and Avro use schema languages much simpler than XML Schema or JSON Schema, which support more detailed validation rules (e.g., a string matching a regular expression, an integer between 0 and 100). Being simpler to implement and use, they are supported by a fairly wide range of programming languages.

The ideas are not new: they have a lot in common with ASN.1, a schema definition language first standardized in 1984, used to define network protocols; its binary encoding (DER) is still used to encode SSL certificates (X.509). ASN.1 supports schema evolution using tag numbers, like Protocol Buffers, but it’s very complex and badly documented, so probably not a good choice for new applications. Many data systems also use a proprietary binary encoding, such as a relational database’s network protocol, decoded by a vendor driver (e.g., using the ODBC or JDBC APIs).

Schema-based binary encodings have nice properties: they can be much more compact than binary JSON variants, since they omit field names; the schema is valuable documentation, guaranteed up to date because decoding requires it; a database of schemas lets you check forward and backward compatibility before anything is deployed; and for statically typed languages, generating code from the schema enables type checking at compile time.

Schema evolution allows the same kind of flexibility as schemaless JSON databases, with better guarantees and tooling. Still, it’s advisable to keep the number of concurrent schema formats to a minimum.

A letter to your future self

Encoding matters wherever data leaves one process for another. So the rest of the chapter asks one question about each way data flows: who encodes, and who decodes? In a database, the writer encodes and the reader decodes.

If only one program ever uses the database, storing a row is like writing a letter to your future self: the reader is just a later version of you, so you need backward compatibility. But usually many processes share a database, and during a rolling upgrade some run new code and some old. Then a row written by new code can be read by old code, so you need forward compatibility as well.

Try it: in Future self, press Write today, then Upgrade, then read. In Shared database, press Upgrade one instance, then press Random write and read several times. Each read shows which promise it relied on.

What the book says

Whenever you send data to another process with which you don’t share memory, you encode it as bytes. Compatibility is a relationship between one process that encodes the data and another that decodes it. Data can flow between processes via databases, service calls, workflow engines and asynchronous messages.

In a database, the process that writes encodes the data, and the process that reads decodes it. If just one process accesses the database, the reader is simply a later version of the same process; you can think of storing something as sending a message to your future self. Backward compatibility is clearly necessary, or your future self won’t be able to decode what you wrote.

In general several processes access a database at the same time: different applications or services, or multiple instances of the same service. Some may run newer code and some older, for example during a rolling upgrade. So a value may be written by newer code and subsequently read by older code that is still running, and forward compatibility is also often required for databases.

Dataflow through databases · different values written at different times

Data outlives code

Sofia can replace every server in her company in ten minutes. She can’t replace the database rows written five years ago: they’re still sitting there, in the encoding of five years ago, unless someone rewrote them. Code gets swapped out; data outlives code.

Rewriting (migrating) every row to a new schema is expensive on a big dataset, so most databases defer it. Adding a column with a NULL default doesn’t touch old rows: when an old row is read, the database fills in the null. LSM-tree engines rewrite rows in the latest format when they compact. The database looks as if it had one schema, while its storage holds many generations. Bigger changes, such as making a single-valued field multi-valued, still need a real rewrite.

Try it: press ALTER TABLE ADD COLUMN, then Read every row: no old row was rewritten, yet every row has the new column. Press Compact and watch the encodings on disk converge. Then try Make phone multi-valued.

What the book says

A database generally allows any value to be updated at any time, so within one database there may be values written five milliseconds ago and others written five years ago. A new version of a server-side application may replace the old one within a few minutes; the five-year-old data will still be there, in the original encoding, unless explicitly rewritten. This is sometimes summed up as data outlives code.

Rewriting (migrating) data into a new schema is possible but expensive on a large dataset, so most databases defer it, performing it asynchronously and on a best-effort basis. LSM-tree storage engines rewrite data using the latest format during compaction. Most relational databases allow simple schema changes, such as adding a column with a null default, without rewriting existing data; when an old row is read, the database fills in nulls for missing columns. Schema evolution thus lets the entire database appear as if it was encoded with a single schema, even though storage contains records encoded with various historical versions.

More complex changes, such as changing a single-valued attribute to be multivalued or moving data into a separate table, still require data to be rewritten, often at the application level. Maintaining forward and backward compatibility across such migrations remains a research problem.

A shop counter, not the stockroom keys

You can give a friend the keys to your stockroom: they can take anything, in any order. Or you can run a counter: they ask for “one loaf,” and you decide what to hand over. A database is the stockroom; a service is the counter.

Over a network, the common arrangement is clients and servers: servers expose an API, the service, and clients call it. A database accepts arbitrary queries; a service only accepts the inputs and outputs its business logic allows. That encapsulation is what lets each team own its service and deploy it independently, often. What the book says

The most common arrangement for processes communicating over a network has two roles: clients and servers. Servers expose an API over the network, and clients connect to make requests to it. The API exposed by the server is known as a service. The web works this way: browsers make GET requests to download HTML, CSS, JavaScript and images, and POST requests to submit data, using standardized protocols and formats (HTTP, URLs, SSL/TLS, HTML).

Native apps and client-side JavaScript also make HTTP requests; the response is then typically data for the client code to process (most often JSON). HTTP may be the transport, but the API on top is application-specific, and client and server must agree on its details.

Services resemble databases in letting clients submit and query data, but while databases allow arbitrary queries, services expose an application-specific API that allows only inputs and outputs predetermined by the business logic. This gives a degree of encapsulation: services can impose fine-grained restrictions on what clients can do.

A key goal of service-oriented/microservices architecture is to make the application easier to change by making services independently deployable and evolvable. Each service should be owned by one team, able to release frequently without coordinating with other teams. So old and new versions of servers and clients run at the same time, and their data encoding must be compatible across versions of the service API.

What the book says

When HTTP is the underlying protocol, the service is called a web service, commonly used in service-oriented or microservices architectures. It’s a slight misnomer, since web services are used in several contexts: a client app on a user’s device making requests over the public internet; one service calling another in the same organization, often in the same private network; and one service calling another organization’s service, as in public APIs such as credit card processing systems or OAuth.

Dataflow through services · the problems with remote procedure calls

A phone call is not a thought

Asking yourself “what’s 2 + 2?” always gets an answer, instantly. Phoning a friend to ask can go many ways: the line drops before they hear you, or after they answer but before you hear it, or they put you on hold for a minute. And if you hang up and call again, they may do the thing twice.

Remote procedure calls (RPC, from the 1970s) make a network request look like a local function call; that illusion is location transparency, and the book calls it fundamentally flawed. A network call can be lost; it can time out, leaving you not knowing whether it ran; a retry can run it twice unless the protocol has idempotence (deduplication); its latency swings from under a millisecond to seconds; every argument must be encoded into bytes instead of passed by pointer; and the two ends may be different languages with different types. REST’s appeal is that it doesn’t pretend.

Try it: set the network to Lose the response and press chargeCard(€20). The client times out and retries. Count the charges. Then turn on Idempotency key and do it again. Try Slow for the latency spread, and compare with a local call.

What the book says

Web services are the latest of a long line of technologies for API requests over a network: Enterprise JavaBeans (EJB) and Java’s Remote Method Invocation (RMI) are limited to Java; DCOM to Microsoft platforms; CORBA is excessively complex and lacks backward or forward compatibility; SOAP and the WS-* framework are plagued by complexity and compatibility problems.

All are based on remote procedure calls (RPC), from the 1970s. RPC tries to make a remote request look like a local function call (location transparency). This is fundamentally flawed, because a network request is very different:

  • A local call is predictable; a network request may be lost, or the remote machine may be slow or unavailable, so applications must anticipate this, e.g. by retrying.
  • A local call returns, throws, or never returns. A network request may also return without a result, because of a timeout; then you have no way of knowing whether the request got through.
  • If you retry, the previous request may have got through and only the response was lost; retrying then performs the action multiple times, unless you build deduplication (idempotence) into the protocol.
  • A network request is much slower than a function call, and its latency is wildly variable: under a millisecond at good times, many seconds when congested or overloaded.
  • Parameters must be encoded into bytes instead of passed as pointers, which gets problematic with large data and mutable objects; and client and service may use different languages, so the framework must translate types (recall JavaScript and numbers above 253).

So there’s no point making a remote service look too much like a local object. Part of REST’s appeal is that it treats state transfer over a network as distinct from a function call.

Dataflow through services · load balancers, service discovery and service meshes

Finding a server that’s still there

Luca’s app talks to an inventory service that runs on three machines, and the machines come and go: one crashes, another moves, a fourth joins at lunchtime. If the app has one IP address written into its config, a single crash leaves it calling an empty room. Finding the service is service discovery; spreading requests over instances is load balancing.

There are five common answers. Hardware load balancers in the datacenter and software ones (NGINX, HAProxy) give clients one address and route around failed servers. DNS maps one name to many IPs, but caches entries, so clients may see stale addresses. A service discovery registry (etcd, ZooKeeper) knows which instances are alive because each one registers and sends heartbeats; clients fetch the list and connect directly. A service mesh (Istio, Linkerd) puts a sidecar load balancer next to every client and server, which handles TLS and sees all the traffic.

Try it: in each mode press Send 6 requests, then Crash a server and send again. Watch DNS keep sending to a dead address until its cache expires, while the registry drops the server as soon as its heartbeats stop.

What the book says

A client must know the address of the service it connects to: service discovery. The simplest approach, configuring the IP address and port, works, but if the server goes offline, moves or becomes overloaded, the client must be reconfigured by hand. For availability and scalability, multiple instances usually run on numerous machines; spreading requests across them is load balancing.

  • Hardware load balancers: specialized equipment in datacenters; clients connect to a single host and port, and connections are routed to a server; they detect failures and shift traffic.
  • Software load balancers (NGINX, HAProxy): the same behavior as applications on a standard machine.
  • DNS: multiple IP addresses for one domain name; the client’s network layer picks one. DNS propagates changes slowly and caches entries, so with servers started, stopped or moved frequently, clients might see stale IP addresses.
  • Service discovery systems: a centralized registry such as etcd or Apache ZooKeeper. A new instance registers its host, port and metadata (shard ownership, datacenter location), then sends periodic heartbeats. Clients query the registry for endpoints and connect directly. This suits much more dynamic environments, and the metadata enables smarter load balancing.
  • Service meshes: combine software load balancers and service discovery, deployed as an in-process library or a sidecar container on both client and server. Clients connect to their local load balancer, which connects to the server’s. Encryption can be handled entirely at the load-balancer level, shielding apps from SSL certificates and TLS, and meshes give rich observability.

Very dynamic environments with an orchestrator such as Kubernetes often run a service mesh such as Istio or Linkerd; databases or messaging systems may need purpose-built load balancers; simpler deployments are best served with software load balancers.

Servers first, clients whenever

Thandiwe’s weather API has thousands of clients she doesn’t control: other companies’ apps, scripts nobody remembers. She can upgrade her servers tonight, but those clients will upgrade next month, or never. So she always upgrades servers first. A new server must accept old requests (backward), and old clients must cope with new responses (forward).

An RPC scheme inherits its compatibility from its encoding: gRPC follows the Protocol Buffers rules, Avro RPC the Avro rules. RESTful JSON APIs usually treat adding optional request parameters and adding response fields as compatible. When a change must break compatibility, the provider runs several API versions side by side, sometimes indefinitely. Nobody agrees how a client should choose: a version in the URL, in the HTTP Accept header, or one stored on the server per API key.

Try it: choose an API change and press Old client calls new server. Additive changes pass; renaming or removing a field breaks the old client. For a breaking change, press Keep v1 alongside and pick how clients choose their version.

What the book says

For evolvability, RPC clients and servers must be changeable and deployable independently. Compared with dataflow through databases, a simplifying assumption is reasonable: all the servers will be updated first, and all the clients second. Thus you need backward compatibility only on requests, and forward compatibility on responses.

The compatibility of an RPC scheme is inherited from its encoding: gRPC (Protocol Buffers) and Avro RPC can be evolved according to their format’s rules. RESTful APIs most commonly use JSON for responses and JSON or URI-encoded/form-encoded parameters for requests; adding optional request parameters and adding new fields to response objects are usually considered compatible changes.

RPC is often used across organizational boundaries, so the provider can’t force clients to upgrade, and compatibility must be maintained for a long time, perhaps indefinitely. If a breaking change is required, the provider frequently ends up maintaining multiple versions of the API side by side.

There is no agreement on how API versioning should work. For RESTful APIs, common approaches put a version number in the URL or in the HTTP Accept header. For services that identify clients by API key, another option is to store a client’s requested API version on the server and let it be updated through a separate administrative interface.

Modes of dataflow · durable execution and workflows

The recipe card that remembers every step

Noor’s payment app does three things for each payment: ask the fraud service, debit the card, and deposit the money at the bank. Halfway through one payment the machine running it crashes. The card was charged; the bank deposit never happened. Run it again from the top, and the card is charged twice.

Such a sequence of steps is a workflow; each step is a task (Temporal says activity; others say durable function). A workflow engine runs it: an orchestrator schedules tasks and an executor runs them, triggered on a schedule, by a service or by a person. A durable execution engine (Temporal, Restate) also writes every RPC and its result to a durable log. When a task is re-run after a crash, calls that already succeeded are not repeated: the engine returns the logged result instead. That gives workflows exactly-once semantics, which you can’t get by wrapping two different services in one database transaction.

Try it: turn on Crash after debit and press Run payment, first with Plain retry and then with Durable execution. Watch the event history fill, and see the re-run replay the card debit from the log instead of charging again.

What the book says

Service-based architectures have multiple services responsible for different parts of an application. A payment processor might invoke a fraud detection service, call the credit card service to debit the card, and call the banking service to deposit the funds (Figure 5-7). This sequence is a workflow, and each step is a task; workflows are typically defined as a graph of tasks, in a general-purpose language, a DSL, or a markup language such as BPEL. Temporal calls tasks activities; others call them durable functions.

Workflows are executed by a workflow engine, which decides when and where each task runs, what to do if a task fails, how many tasks may run in parallel, and more. Engines are typically composed of an orchestrator, which schedules tasks, and an executor, which executes them. Execution begins when a workflow is triggered: by the orchestrator on a time-based schedule, or by external sources such as a web service or even a human.

Some engines (Airflow, Dagster, Prefect) orchestrate ETL tasks; others (Camunda, Orkes) offer graphical notations such as BPMN; others, such as Temporal and Restate, provide durable execution. We want each payment processed exactly once; a failure could leave a card charged with no deposit, and we can’t wrap the two tasks in a database transaction, especially with third-party payment gateways.

Durable execution frameworks provide exactly-once semantics for workflows. If a task fails, the framework re-executes it, but skips any RPC calls or state changes it made successfully before failing: it pretends to make the call and returns the results from the previous call. This works because they log all RPCs and state changes to durable storage like a write-ahead log. Example 5-5 shows a Temporal workflow definition.

Durable execution and workflows · the price of replay

Replay only works if the story repeats

Replaying from a log is like re-reading a diary to remember where you were: “first I checked fraud, then I charged the card.” If you rewrite the recipe so that you charge the card first, the diary no longer matches the recipe, and the engine can’t tell which logged result belongs to which call.

Durable execution has three catches. External services must still offer an idempotent API, called with unique IDs. Because results are matched to calls by their order, changing a workflow’s code (even just reordering calls) can break the replay of runs already in progress; it’s safer to deploy the new code as a new version, so old runs replay with the old code. And the code must be deterministic: a random number or a clock reading differs on replay, so frameworks provide their own deterministic versions, and tools like Temporal’s Workflow Check look for mistakes.

Try it: start a run with Start payment, then pick an edit (Swap two calls, or Use random()) and press Deploy and replay. Then pick the fix (Deploy as v2, or Use workflow.random()) and replay again.

What the book says

Frameworks like Temporal are not without challenges. External services, such as the third-party payment gateway, must still provide an idempotent API, and developers must remember to use unique IDs for these APIs to prevent duplicate execution.

Because durable execution frameworks log each RPC call in order, they expect subsequent executions to make the same RPC calls in the same order. This makes code changes brittle; you might introduce undefined behavior simply by reordering function calls. Instead of modifying the code of an existing workflow, it is safer to deploy a new version separately, so re-executions of existing invocations use the old version and only new invocations use the new code.

Similarly, because they expect to replay all code deterministically (the same inputs produce the same outputs), nondeterministic code such as random number generators or system clocks is problematic. Frameworks often provide their own deterministic implementations of such library functions, but you have to remember to use them. Some provide static analysis tools, like Temporal’s Workflow Check, to detect nondeterministic behavior. Making code deterministic is a powerful idea but tricky to do robustly; Chapter 9 returns to it.

Modes of dataflow · event-driven architectures

Leave it in the mailbox

Calling someone needs them to pick up right now. Leaving a note in their mailbox doesn’t: you drop it and walk away, and they read it when they’re back. If they’re ill for a week, the notes simply wait.

In an event-driven architecture, a request is an event or message, and it goes through a message broker (event broker, message queue, message-oriented middleware) that stores it for a while. The sender doesn’t wait. Compared with direct RPC, a broker buffers when the recipient is down or overloaded, redelivers to a consumer that crashed, removes the need for service discovery, fans out one message to several recipients, and decouples sender from recipient. The flow is asynchronous; if you need an answer, the recipient can reply on a separate channel.

Try it: switch off the shipping service and press Place order a few times, first in Direct RPC, then in Via a broker. Turn shipping back on and watch the broker deliver the backlog. Then press Crash mid-message to see redelivery.

What the book says

In event-driven architectures, a request is called an event or message. Unlike with RPC, the sender usually doesn’t wait for the recipient to process it, and events are typically not sent via a direct connection but via an intermediary called a message broker (also called an event broker, message queue or message-oriented middleware), which stores the message temporarily.

Advantages compared to direct RPC:

  • It can act as a buffer if the recipient is unavailable or overloaded, improving reliability.
  • It can automatically redeliver messages to a process that has crashed, preventing loss.
  • It avoids the need for service discovery, since senders don’t connect directly to the recipient’s IP address.
  • It allows the same message to be sent to several recipients.
  • It logically decouples sender from recipient: the sender publishes and doesn’t care who consumes.

Communication via a broker is asynchronous: the sender doesn’t wait for delivery, it sends and forgets. A synchronous RPC-like model is possible by having the sender wait for a response on a separate channel.

Event-driven architectures · message brokers

A queue hands each job to one; a topic tells everyone

At a bakery, order tickets on the kitchen rail go to whichever baker is free: each ticket is baked once. The shop’s newsletter is different: every subscriber gets every issue. Message brokers offer both.

With a queue, one consumer receives each message, so adding consumers spreads the work. With a topic, the broker delivers each message to all subscribers. A message is just bytes plus metadata, so any encoding works; teams often use Protocol Buffers, Avro or JSON with a schema registry beside the broker, or describe messages with AsyncAPI. Brokers differ in durability: many write to disk, and many delete a message once it’s consumed, while some can keep messages forever, which event sourcing needs. And a consumer that republishes messages must keep unknown fields, or it repeats Figure 5-1.

What the book says

The broker landscape was once dominated by commercial enterprise software from TIBCO, IBM WebSphere and webMethods, before open source implementations such as RabbitMQ, ActiveMQ, HornetQ, NATS, Redpanda and Apache Kafka became popular; more recently, cloud services such as Amazon Kinesis, Azure Service Bus and Google Cloud Pub/Sub. Chapter 12 compares them.

Delivery semantics vary, but two distribution patterns are most common: one process adds a message to a named queue, and one of the queue’s consumers receives it; or one process publishes a message to a named topic, and the broker delivers it to all subscribers of that topic.

Brokers typically don’t enforce a data model; a message is a sequence of bytes with some metadata. A common approach is Protocol Buffers, Avro or JSON with a schema registry alongside the broker to store valid schema versions and check compatibility. AsyncAPI, a messaging-based equivalent of OpenAPI, can also specify message schemas.

Brokers differ in durability. Many write messages to disk so they survive a crash or restart. Unlike databases, many delete messages automatically after they have been consumed; some can be configured to store messages indefinitely, which event sourcing requires. If a consumer republishes messages to another topic, it may need to preserve unknown fields, to prevent the issue of Figure 5-1.

Event-driven architectures · distributed actor frameworks

Workers with mailboxes, one letter at a time

Picture an office where nobody shares a desk. Each clerk has a private drawer and an inbox, handles one letter at a time, and talks to the others only by sending letters. No two clerks ever grab the same drawer, so there are no fights over it. And it makes no difference whether a letter goes to the next desk or to the branch across town.

That’s the actor model: logic lives in actors, each with private state and a mailbox, talking by asynchronous messages, processing one message at a time, so no locks or race conditions. Delivery isn’t guaranteed; messages can be lost. Distributed actor frameworks (Akka, Orleans, Erlang/OTP) use the same messaging across nodes, encoding messages to bytes when they leave a node. Location transparency works better here than in RPC, because actors already assume messages can be lost. But in a rolling upgrade, new and old nodes exchange messages, so you need forward and backward compatibility again.

Try it: press Send 5 messages and watch each actor work through its mailbox one message at a time. Press Move cart actor to node 2: the same messages now cross the network and get encoded. Then press Upgrade node 2 to v2 and send again, first with No compatibility and then with Compatible encoding.

What the book says

The actor model is a programming model for concurrency in a single process. Instead of dealing directly with threads (and race conditions, locking and deadlock), logic is encapsulated in actors. Each actor typically represents one client or entity, may have local state not shared with any other actor, and communicates by sending and receiving asynchronous messages. Message delivery is not guaranteed; in certain error scenarios messages will be lost. Since each actor processes only one message at a time, it doesn’t need to worry about threads, and the framework can schedule each actor independently.

In distributed actor frameworks such as Akka, Orleans and Erlang/OTP, this model scales an application across multiple nodes. The same message-passing mechanism is used whether sender and recipient are on the same node or different ones; across nodes, the message is transparently encoded into bytes, sent over the network and decoded.

Location transparency works better in the actor model than in RPC, because the actor model already assumes messages may be lost, even within one process. Network latency is higher, but there is less fundamental mismatch between local and remote communication.

A distributed actor framework essentially integrates a message broker and the actor model into one framework. But for rolling upgrades you still have to worry about forward and backward compatibility, since messages may be sent from a node on the new version to one on the old, and vice versa; one of the encodings discussed in the chapter can achieve this.

Three families of encodings

From the book’s summary.

Language-specific

Tied to one programming language, and often no forward or backward compatibility. Fine only for very short-lived data.

Textual: JSON, XML, CSV

Everywhere, and their compatibility depends on how you use them. Optional schema languages help or hinder. Vague about types: watch numbers and binary strings.

Binary, schema-driven: Protobuf, Avro

Compact and efficient, with clearly defined forward and backward compatibility. Schemas document and generate code. Downside: you must decode before a human can read it.

Who encodes, who decodes

The modes of dataflow.

Databases

The writing process encodes; the reading process, possibly an older or newer version, decodes, maybe years later.

RPC and REST APIs

The client encodes a request, the server decodes it and encodes a response, and the client decodes the response.

Workflows

An engine calls a chain of services, logging each call so a crashed run can replay instead of repeating.

Event-driven (brokers and actors)

Nodes send each other messages, encoded by the sender and decoded by the recipient, without waiting for each other.

The seesaws from this chapter

Each choice buys something and costs something else.

Your language’s own format

One line of code to save an object

vs

Readable, universal, easy for organizations to agree on

An answer right away, if the other side is up

Message broker

Buffers, redelivers and fans out; the sender doesn’t wait for an answer

The book’s conclusion: rolling upgrades let you release often, without downtime and with less risk, and that is what makes a system evolvable. During one, different nodes run different code, so every piece of data that flows around must be encoded with backward compatibility (new code reads old data) and forward compatibility (old code reads new data). With a bit of care, both are quite achievable.

Words to know

Grown-up words, in plain language.

rolling upgrade
Deploying a new version to a few nodes at a time, so the service never stops. Also called a staged rollout.
backward compatibility
Newer code can read data written by older code.
forward compatibility
Older code can read data written by newer code, ideally without destroying the parts it doesn’t understand.
evolvability
How easily a system can be changed.
encoding
Turning in-memory objects into a self-contained sequence of bytes. Also serialization or marshaling.
decoding
Turning those bytes back into objects. Also parsing, deserialization or unmarshaling.
zero-copy format
A format that is used the same way in memory and on disk, so there’s no conversion step (Cap’n Proto, FlatBuffers).
IEEE 754 double
The 64-bit floating-point number JavaScript uses for every number; it holds integers exactly only up to 253.
Base64
Writing raw bytes as text, 4 characters for every 3 bytes, so they fit into JSON or XML.
JSON Schema
A language for describing and validating JSON, including rules like “between 1 and 65,535.”
open / closed content model
Whether fields the schema never declared are allowed (open, the JSON Schema default) or rejected (closed).
MessagePack
A binary encoding of JSON. Smaller, but every field name still travels in every record.
IDL
Interface definition language: the file that describes a schema or an API, such as a .proto file or an OpenAPI document.
field tag
The number that stands for a field in Protocol Buffers. Never change it, never reuse it.
varint
A variable-length integer: 7 bits per byte, with the top bit saying whether more bytes follow.
schema evolution
Changing a schema over time while old and new data and code keep working together.
writer’s schema
The exact schema used to encode some Avro data. The decoder needs it to walk the bytes.
reader’s schema
The schema today’s code expects. Avro translates the writer’s fields into it by name.
union type
An Avro field that can hold one of several types, such as union { null, long }. The only way to allow null.
object container file
Avro’s file format: the schema once in the header, then many records.
schema registry
A store of every schema version, used to find a writer’s schema and to check compatibility before deploying.
data outlives code
Code can be replaced in minutes; old rows stay in their old encoding until something rewrites them.
migration
Rewriting existing data into a new schema. Expensive on big datasets, so databases often defer it.
service
The API a server exposes over the network. Unlike a database, it only allows the operations its business logic permits.
REST
A design style for web services built on HTTP: URLs name resources, and HTTP handles caching, authentication and content types.
OpenAPI
The most popular IDL for JSON web services, also known as Swagger.
RPC
Remote procedure call: making a network request look like a local function call.
location transparency
Hiding whether something is local or remote. Misleading for RPC; a better fit for actors.
idempotence
Doing something twice has the same effect as doing it once, so a retry is safe.
service discovery
How a client finds the address of a service instance that is up right now.
service mesh
A load balancer next to every client and server (often a sidecar) that also handles TLS and observability.
workflow / task
A sequence of service calls (tasks, or activities in Temporal) run by a workflow engine.
durable execution
Logging every call and result of a workflow so a re-run skips what already succeeded: exactly-once semantics.
message broker
A middleman that stores messages and delivers them later: a queue (to one consumer) or a topic (to all subscribers).
actor
A unit of logic with private state and a mailbox that handles one message at a time.
