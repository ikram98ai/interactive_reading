Sharding

When there is too much data, or too many writes, for one computer, you cut the data into pieces called shards and give each piece to a different machine. The hard parts are choosing which piece each record goes in, and finding it again.

Sharding · shards and their copies

Cut the pile, then copy every piece

Amara runs a lending library with far too many books for one building. She splits the catalogue into four sections, A to D, and gives each section to one branch. Every book now lives in exactly one section. But if a branch floods, that section is gone, so each section is also photocopied to two other branches.

Databases do both. Sharding (also called partitioning) splits the data so each record belongs to one shard, and each shard is like a small database of its own. Replication (Chapter 6) then keeps copies of each shard on several nodes. With a leader per shard, a node can be the leader for some shards and a follower for others, but each shard still has only one leader.

Try it: press Write a record a few times and watch each write go to its shard’s leader, then copy to its followers. Then click a node to crash it: every shard it led gets a new leader on another node, and no shard is lost.

What the book says

A distributed database typically distributes data across nodes in two ways: it stores a copy of the same data on multiple nodes (replication, Chapter 6), and, if there is so much data or such a high write throughput that a single node cannot handle it, it splits the data into smaller shards or partitions and stores different shards on different nodes.

Normally each piece of data (each record, row or document) belongs to exactly one shard. In effect, each shard is a small database of its own, although some systems support operations that touch multiple shards at the same time.

Sharding is usually combined with replication, so that copies of each shard are stored on multiple nodes: each record belongs to exactly one shard, but may still be stored on several nodes for fault tolerance. With single-leader replication (Figure 7-1), each shard’s leader is assigned to one node and its followers to other nodes; a node may be the leader for some shards and a follower for others, but each shard still has only one leader.

Sharding and partitioning · one idea, many names

Same piece, different name tag

Kenji asks five engineers what they call a piece of a split-up database and gets five answers. They all mean the same thing: one slice of the data that one node is responsible for.

Kafka calls it a partition, CockroachDB a range, HBase a region, Bigtable a tablet. Watch out for two traps. In PostgreSQL, partitioning means splitting a big table into several files on the same machine, which is not sharding. And sharding has nothing to do with a network partition, a fault where the network between nodes breaks (Chapter 9).

Try it: in Many names, tap the systems to relabel the same four shards. In Postgres partitions, press Drop March for each kind of table: deleting a whole partition is one quick step, deleting rows is many. In Not a netsplit, cut the cable.

What the book says

What the chapter calls a shard has many names: a partition in Kafka, a range in CockroachDB, a region in HBase and TiDB, a vBucket in Couchbase, a vnode in Riak, a token-range in Cassandra, and a tablet in Bigtable, YugabyteDB and ScyllaDB.

Some databases treat partitions and shards as distinct concepts. In PostgreSQL, partitioning splits a large table into several files stored on the same machine (which, among other advantages, makes it very fast to delete an entire partition), whereas sharding splits a dataset across multiple machines. In many other systems, partitioning is just another word for sharding.

One theory says the term shard came from the online role-playing game Ultima Online, in which a magic crystal was shattered into pieces, each refracting a copy of the game world; shard came to mean one of a set of parallel game servers. Another says it was an acronym for System for Highly Available Replicated Data, a 1980s database whose details are lost to history.

Partitioning has nothing to do with network partitions (netsplits), a type of fault in the network between nodes, discussed in Chapter 9. Because sharding and replication are mostly independent choices, the chapter ignores replication from here on.

Pros and cons of sharding · scaling out

When one oven can’t bake enough bread

Diego’s bakery has one oven. When orders double, he can buy a bigger oven (there is always a biggest one), or he can rent more small kitchens and send each order to one of them. The second way keeps growing.

The main reason to shard is scalability: when the volume of data or the write throughput is too much for one node, you spread both across many nodes. That is horizontal scaling, or scale-out. If only reads are too many, you may not need sharding at all: read replicas (Chapter 6) can carry them. And a single machine can do a lot nowadays, so sharding is a heavyweight tool for large scale.

Try it: drag Writes per second and Data size past what one node can hold and watch it overflow. Then raise Shards until every node is under its line. Switch to Read-heavy: extra followers fix it with only one shard.

What the book says

The primary reason for sharding a database is scalability: it is a solution if the volume of data or the write throughput has become too great for a single node, as it lets you spread that data and those writes across multiple nodes. If read throughput is the problem, you don’t necessarily need sharding; you can use read scaling (Chapter 6).

Sharding is one of the main tools for horizontal scaling (a scale-out architecture): growing capacity not by moving to a bigger machine, but by adding more (smaller) machines. If each shard handles a roughly equal share, the shards can be assigned to different machines that process their data and queries in parallel.

Replication is useful at both small and large scale, because it enables fault tolerance and offline operation. Sharding is a heavyweight solution mostly relevant at large scale: if a single machine can handle your data volume and write throughput (and a single machine can do a lot nowadays!), it’s often better to avoid sharding and stick with a single-shard database.

Pros and cons of sharding · the price of complexity

Fast if you know the drawer, slow if you don’t

Priya files customer letters in four cabinets by customer ID. Asked for customer 2051’s letters, she walks straight to the right cabinet. Asked for “every letter mentioning a refund,” she has to open all four. And when one change must land in two cabinets at once, she needs both cabinets to agree, or neither.

Sharding adds complexity. You choose a partition key, and all records with the same key go to the same shard. Access by that key is fast; anything else means an inefficient search across all shards. The scheme is hard to change later. And a write that updates related records on several shards needs a distributed transaction (Chapter 8), usually much slower than a single-node one.

Try it: press each button. Find by ID touches one shard. Find by city must ask every shard. Transfer between users picks two users on different shards and shows the extra round trips to make both writes happen together.

What the book says

Sharding adds complexity. You typically have to decide which records go in which shard by choosing a partition key; all records with the same partition key are placed in the same shard. Accessing a record is fast if you know which shard it’s in, but if you don’t, you have to do an inefficient search across all shards. The sharding scheme is also difficult to change.

Sharding often works well for key-value data, where you can easily shard by key, but it’s harder with relational data, where you may want to search by a secondary index or join records that might be in different shards.

A write may need to update related records in several shards. While transactions on a single node are quite common, ensuring consistency across multiple shards requires a distributed transaction. Those are available in some databases, but they are usually much slower than single-node transactions and may become a bottleneck for the system as a whole (Chapter 8).

Pros and cons of sharding · sharding inside one machine

Four cooks, four counters, one kitchen

Sofia’s kitchen has four burners but one cook who does everything in order. Three burners sit cold. Hire one cook per burner, give each cook their own set of orders and their own fridge next to them, and all four burners work at once.

Some systems shard inside a single machine: they run one single-threaded process per CPU core, each owning a slice of the keys. That uses all the cores, and on a NUMA machine, where some memory banks are closer to one CPU than to others, each process can keep its data in the nearby bank. Redis, VoltDB and FoundationDB work this way.

Try it: press Run 40 requests with One process, then switch to One per core and run again. Then set memory to far and run again: each process’s data now lives in the other bank.

What the book says

Some systems use sharding even on a single machine, typically running one single-threaded process per CPU core to make use of the parallelism in the CPU, or to take advantage of a nonuniform memory access (NUMA) architecture in which some banks of memory are closer to one CPU than to others.

For example, Redis, VoltDB and FoundationDB use one process per core and rely on sharding to spread load across CPU cores in the same machine.

Sharding for multitenancy · isolation

One flat per family, not one big dormitory

An email marketing service has thousands of business customers: a bakery, a clinic, a bike shop. Each business is a tenant with its own sign-ups and delivery data, and many staff logins. They share the software but must never share each other’s data.

You can give each tenant its own shard (or group small tenants into one). Two things improve at once. Resource isolation: one tenant’s expensive job is less likely to slow the others if they run on different shards. Permission isolation: if your access-control code has a bug, it is far less likely to leak one tenant’s data to another when their datasets are stored physically apart.

Try it: in Resource, press Bakery runs a huge report with Shared storage, then with Shard per tenant. In Permission, press Buggy query (it forgot the tenant filter) both ways and count whose rows leak.

What the book says

Software as a service (SaaS) products and cloud services are often multitenant, where each tenant is a customer. Multiple users may have logins on the same tenant, but each tenant has a self-contained dataset separate from other tenants’. In an email marketing service, each business that signs up is typically a separate tenant.

Sometimes sharding is used to implement multitenant systems: either each tenant is given a separate shard, or multiple small tenants are grouped together into a larger shard. These shards might be physically separate databases or separately manageable portions of a larger logical database.

Resource isolation: if one tenant performs a computationally expensive operation, other tenants’ performance is less likely to be affected if they are on different shards. Permission isolation: if there is a bug in your access control logic, it’s less likely you will accidentally give one tenant access to another tenant’s data if their datasets are stored physically separately.

Sharding for multitenancy · per-tenant operations

Fix one customer without touching the rest

On Monday the clinic deletes its own mailing list by mistake. On Tuesday a customer asks for all their data to be erased. On Wednesday a German tenant must keep its data in Europe. On Thursday you ship a schema change and want to try it on one tenant first.

With a shard per tenant, each of these becomes a small, local job: restore one tenant from its own backup, export or delete one person’s shard to comply with laws like the GDPR and CCPA, place a tenant’s shard in a particular region for data residency, and roll a schema migration out one tenant at a time so a bug shows up before it hits everyone.

Try it: pick a job and press its button. Restore rolls back the clinic only. Erase deletes one shard. Residence moves a shard to the EU region. Rollout migrates tenants one at a time; the second one fails, and the rest are never touched.

What the book says

Per-tenant backup and restore: backing up each tenant’s shard separately makes it possible to restore a tenant’s state from a backup without affecting other tenants, useful if the tenant accidentally deletes or overwrites important data.

Regulatory compliance: data privacy regulations such as the GDPR and CCPA give individuals the right to access and request deletion of personal information. If each person’s data is stored in a separate shard, this translates into simple data export and deletion operations on their shard.

Data residence: if a tenant’s data must be stored in a particular jurisdiction, a region-aware database can assign that tenant’s shard to a particular region. Gradual schema rollout: schema migrations can be rolled out one tenant at a time, reducing risk because you can detect problems before they affect all tenants, but it can be difficult to do transactionally.

Sharding for multitenancy · cell-based architecture

Watertight compartments for a whole app

A ship is built from watertight compartments, so a hole floods one room, not the whole hull. Ravi’s team does the same with their app: tenants are grouped into cells, and each cell has its own copy of the services and its own storage.

That is a cell-based architecture: sharding applied not just to the data but to the services running your application code. Cells run largely independently, so you get fault isolation: a bad deploy, a crash or an overload in one cell stays in that cell, and tenants in other cells don’t notice.

Try it: press Break something in Shared services: one bad app server takes everyone down. Switch to Cells and break the same thing. Count the tenants affected each time.

What the book says

You can apply sharding not only at the data storage level, but also for the services running your application code. In a cell-based architecture, the services and storage for a particular set of tenants are grouped into a self-contained cell, and different cells are set up so that they can run largely independently from each other.

This approach provides fault isolation: a fault in one cell remains limited to that cell, and tenants in other cells are not affected.

Sharding for multitenancy · the challenges

When a tenant outgrows its flat

The one-flat-per-family plan has three cracks. A family grows into a crowd that won’t fit any flat. Thousands of tiny families each get a flat they barely use. And the day you want a party for the whole building, everyone is behind a different door.

In database terms: a tenant too big for one node needs sharding inside the tenant, which brings you back to sharding for scale. Many small tenants make one shard each too costly, so you group them, and then you must move a tenant out of its group when it grows. And features across tenants become cross-shard joins.

Try it: in Too big, press Grow until the tenant overflows its node. In Too small, compare one shard per tenant with grouped shards, then press Move the grower. In Across tenants, run a report over everyone.

What the book says

Sharding for multitenancy assumes that each tenant is small enough to fit on a single node. If a single tenant is too big for one machine, you need to additionally perform sharding within that tenant, which brings us back to sharding for scalability.

If you have many small tenants, creating a separate shard for each may incur too much overhead. You could group several small tenants into a bigger shard, but then you have the problem of how to move tenants from one shard to another as they grow.

If you ever need features that connect data across multiple tenants, these become harder to implement if you need to join data across multiple shards.

Sharding of key-value data · skew and hot spots

Ten cashiers, one long queue

A supermarket opens ten tills. In theory it now serves ten times as many shoppers. But if everyone lines up at till 3, nine cashiers are idle and the shop is exactly as slow as it was with one till.

The goal of sharding is to spread data and query load evenly. When it isn’t even, it is skewed. A shard with far more load than the others is a hot shard or hot spot; one key with very high load, like a celebrity’s account, is a hot key. You need an algorithm that maps each record’s partition key to a shard, and lets you rebalance to relieve hot spots.

Try it: pick Even, Skewed or Hot key and press Send 200 requests. The cluster can only go as fast as its busiest node, so watch Speed-up vs 1 node.

What the book says

The goal with sharding is to spread the data and the query load evenly across nodes. If every node takes a fair share, then in theory 10 nodes should handle 10 times as much data and 10 times the read and write throughput of a single node (ignoring replication). If you add or remove a node, you want to rebalance so the load is evenly distributed across the new number of nodes.

If the sharding is unfair, so that some shards have more data or queries than others, it is skewed. Skew makes sharding much less effective: in an extreme case all the load lands on one shard, 9 out of 10 nodes are idle, and your bottleneck is the single busy node. A shard with disproportionately high load is a hot shard or hot spot; one key with particularly high load (e.g., a celebrity in a social network) is a hot key.

Sharding needs an algorithm that takes the partition key of a record and tells us which shard holds it. In a key-value store the partition key is usually the key or its first part; in a relational model it might be a column of a table (not necessarily its primary key). The algorithm needs to be amenable to rebalancing to relieve hot spots.

Sharding by key range · encyclopedia volumes

Volumes that fit the words, not the alphabet

A paper encyclopedia is sharded by key range: volume 1 holds A–B, volume 12 holds T–Z. To find “Lima,” you don’t open every book; you pick the one whose spine covers L. Each volume owns a contiguous range of keys, from a minimum to a maximum.

The ranges aren’t evenly spaced, because words aren’t evenly spread over the alphabet: lots start with S, very few with X. Two letters per volume would make some volumes fat and some thin. So the boundaries adapt to the data, set by an administrator (Vitess) or automatically (Bigtable, HBase, CockroachDB, MongoDB’s range option and others).

Try it: switch between Two letters each and Fit the data and compare the volume sizes. Then press Look up: the lookup walks the boundaries in the code to find the one volume to open.

What the book says

One way of sharding is to assign a contiguous range of partition keys (from a minimum to a maximum) to each shard, like the volumes of a paper encyclopedia (Figure 7-2). If you want to look up a title, you can easily determine which shard contains it by finding the volume whose key range contains the title.

The ranges are not necessarily evenly spaced, because your data may not be evenly distributed: in Figure 7-2 volume 1 contains words starting with A and B, but volume 12 contains T, U, V, W, X, Y and Z. To distribute data evenly, the shard boundaries need to adapt to the data.

Boundaries might be chosen manually by an administrator or automatically by the database. Manual key-range sharding is used by Vitess (a sharding layer for MySQL); the automatic variant is used by Bigtable and its open source equivalent HBase, the range-based sharding option in MongoDB, CockroachDB, RethinkDB and FoundationDB. YugabyteDB offers both manual and automatic tablet splitting.

Sharding by key range · range scans and the timestamp trap

Every new reading goes to the same drawer

Inside each shard, keys are kept in sorted order (in a B-tree or SSTables, Chapter 4). So range scans are easy: “all readings from March” is one contiguous slice. Hana’s weather network keys each reading by its timestamp, and monthly reports are a joy.

Writes are not. Shards are ranges of time, so every reading taken now lands in the shard for this month. That one shard is hot, and the others sit idle. The fix: put the sensor ID first in the key, then the timestamp. Writes from many sensors spread out, but a query across many sensors now needs one range query per sensor.

Try it: with Key = time, press Sensors report and watch one shard take every write. Switch to Key = sensor, time and report again. Then press Query: all sensors in May under each key and count the range queries.

What the book says

Within each shard, keys are stored in sorted order (e.g., in a B-tree or SSTables). Range scans are easy, and you can treat the key as a concatenated index to fetch several related records in one query. For an application storing data from a network of sensors keyed by the timestamp of the measurement, range scans let you easily fetch, say, all the readings from a particular month.

A downside of key-range sharding is that you can easily get a hot shard if there are a lot of writes to nearby keys. If the key is a timestamp, shards correspond to ranges of time (for example, one shard per month), and if you write sensor data as the measurements happen, all the writes go to the same shard (this month’s), which is overloaded while others sit idle.

To avoid this, use something other than the timestamp as the first element of the key: for example, prefix each timestamp with the sensor ID, so the ordering is first by sensor ID and then by timestamp. With many sensors active at once, the write load spreads more evenly. The downside: fetching multiple sensors’ values within a time range now needs a separate range query for each sensor.

Rebalancing key-range sharded data · split and merge

A volume that gets too thick splits in two

When the database is new and empty, there are no ranges to split. HBase and MongoDB let you pre-split: create shards up front, if you can guess the key distribution. Otherwise the system grows by splitting a shard that gets too big into two halves, each a contiguous sub-range, which can then move to other nodes. If lots of data is deleted, small neighbours can be merged.

A split is triggered by size (HBase’s default is 10 GB) or, in some systems, by write throughput staying above a threshold, so a hot shard may split even if it is small. But splitting is expensive: all its data is rewritten into new files, like compaction. And the shard that needs splitting is usually the busy one.

Try it: press Insert 6 keys a few times and watch the split rule fire in the code. Press Delete 6 keys to make neighbours merge. Turn on Pre-split and reset: four empty shards are ready before the first write.

What the book says

When you first set up your database, there are no key ranges to split into shards. Some databases, such as HBase and MongoDB, let you configure an initial set of shards on an empty database, called pre-splitting. This requires some idea of what the key distribution will look like, so you can choose appropriate boundaries.

As data volume and write throughput increase, a key-range system grows by splitting an existing shard into two or more smaller shards, each holding a contiguous subrange of the original shard’s range; the smaller shards can then be distributed across nodes. If large amounts of data are deleted, you may need to merge several adjacent small shards into one. This is similar to what happens at the top level of a B-tree.

With automatic boundaries, a split is typically triggered by the shard reaching a configured size (on HBase, the default is 10 GB) or, in some systems, the write throughput being persistently above a threshold, so a hot shard may be split even if it is not storing a lot of data. The number of shards adapts to the data volume: little data needs few shards, and with a huge amount each shard’s size is limited to a configurable maximum.

Splitting a shard is expensive, since all its data is rewritten into new files, similarly to a compaction in a log-structured storage engine. A shard that needs splitting is often also one under high load, and the cost of splitting can make that worse, risking overload.

Key-range shards that split and merge
Sharding by hash of key · a good hash function

Turn neighbours into strangers

Key ranges keep neighbours together, which is great for timestamps and terrible for hot spots. If you don’t care whether keys are near each other, such as tenant IDs, you can first hash the key. A good hash function takes skewed input and makes it uniformly distributed: user1 and user2 land far apart, and the same input always gives the same output.

It needn’t be cryptographically strong: MongoDB uses MD5; Cassandra and ScyllaDB use Murmur3. But beware your language’s built-in hash. Java’s Object.hashCode() and Ruby’s Object#hash can give the same key a different hash in different processes, so two servers would disagree on where a key lives.

Try it: press Hash next key and watch similar keys scatter over the 32-bit range. These are real Murmur3 values. Then switch to Per-process hash and press Write on A, read on B: process B looks in the wrong shard.

What the book says

Key-range sharding is useful if you want records with nearby (but different) partition keys grouped into the same shard, as with timestamps. If you don’t care whether partition keys are near each other (e.g., tenant IDs in a multitenant application), a common approach is to first hash the partition key before mapping it to a shard.

A good hash function takes skewed data and makes it uniformly distributed. A 32-bit hash function given a string returns a seemingly random number from 0 to 232 − 1; even if input strings are very similar, their hashes are evenly distributed across that range, but the same input always produces the same output.

For sharding, the hash function need not be cryptographically strong: MongoDB uses MD5, whereas Cassandra and ScyllaDB use Murmur3. Many languages have simple hash functions built in for hash tables, but they may not be suitable: in Java’s Object.hashCode() and Ruby’s Object#hash, the same key may have a different hash value in different processes, making them unsuitable for sharding.

Sharding by hash of key · hash modulo number of nodes

Add one node, move almost everything

The first idea anyone has: node = hash(key) % N. With 10 nodes, that’s just the last digit of the hash. Easy to compute, and it spreads keys evenly.

Then you add an eleventh node and N changes. Almost every key now gives a different remainder, so almost every record has to move to a different node, even though only one node was added. With 3 nodes going to 4 (Figure 7-3), the key with hash 3 moves from node 0 to node 3, hash 6 to node 2, hash 9 to node 1, and so on. We need a scheme that moves as little data as possible.

Try it: press Add a node and watch the keys that change colour: those are the ones that must travel. Press it again, or Remove a node, and compare Moved with the share a new node actually needed.

What the book says

Once you have hashed the key, your first thought may be to take the hash modulo the number of nodes (the % operator). For example, hash(key) % 10 returns a number from 0 to 9 (the last digit, if the hash is written in decimal); with 10 nodes numbered 0 to 9, that seems like an easy way of assigning each key to a node.

The problem with the mod N approach is that if the number of nodes N changes, most of the keys have to be moved from one node to another. Figure 7-3 shows three nodes and a fourth added: before, node 0 stored the keys whose hashes are 0, 3, 6, 9 and so on; after, the key with hash 3 has moved to node 3, hash 6 to node 2, hash 9 to node 1, and so on.

The mod N function is easy to compute, but it leads to very inefficient rebalancing because of a lot of unnecessary movement of records from one node to another. We need an approach that moves as little data as possible.

Sharding by hash of key · fixed number of shards

Lots of small boxes, moved whole

Instead of one bin per node, make many more shards than nodes from day one: say 1,000 shards on 10 nodes, 100 each. A key always goes to shard hash(key) % 1000, and a separate table says which node holds which shard.

When a node joins, it simply takes a few whole shards from each existing node. Keys never change shard; only the shard-to-node table changes. Moving takes time over the network, so reads and writes keep using the old assignment until the transfer is done. A shard count with many factors (12, 60, 1,000…) splits evenly over many cluster sizes, and a more powerful node can take more shards.

Try it: press Add a node and watch whole shards travel while requests still go to the old owner. Add more, until you hit the limit: you can’t have more nodes than shards. Toggle Node 0 is twice as big and rebalance.

What the book says

One simple but widely used solution is to create many more shards than there are nodes and assign several shards to each node. A database on a cluster of 10 nodes may be split into 1,000 shards from the outset, 100 per node. A key is stored in shard number hash(key) % 1,000, and the system separately keeps track of which shard is stored on which node.

When a node is added, the system reassigns some shards from existing nodes to the new node until they are fairly distributed again (Figure 7-4); when one is removed, the reverse. Only entire shards are moved, which is cheaper than splitting shards. The number of shards and the assignment of keys to shards don’t change; only the assignment of shards to nodes. The transfer takes some time, so the old assignment is used for reads and writes while it is in progress.

It’s common to choose a number of shards divisible by many factors, so the dataset can be evenly split across various numbers of nodes. You can account for mismatched hardware by assigning more shards to more powerful nodes. This approach is used in Citus (a sharding layer for PostgreSQL), Riak, Elasticsearch and Couchbase, among others; the limitation is that you can’t have more nodes than you have shards.

Fixed number of shards · picking the number

Goldilocks shards in a growing dataset

With a fixed number of shards, each shard always holds the same fraction of the data. So when the dataset grows a hundredfold, every shard grows a hundredfold too.

Shards that are too big make rebalancing and recovery from a node failure slow and expensive. Shards that are too small add overhead. The best is “just right,” which is hard when the shard count is fixed and the data isn’t. If you guessed wrong, you need resharding: split every shard and write it to new files, using lots of extra disk, and some systems can’t do that while writes continue.

Try it: pick a shard count, then drag Dataset size from small to huge and watch each shard’s size cross the zones. When it goes red, press Reshard ×4 and see what it costs.

What the book says

Fixed shards work well as long as you have a good estimate of how many you will need when you first create the database; then you can add or remove nodes easily. If the original number turns out wrong (e.g., you need more nodes than you have shards), an expensive resharding operation is required: it splits each shard and writes it out to new files, using a lot of additional disk space. Some systems don’t allow resharding while concurrently writing, making it difficult to change the number of shards without downtime.

Choosing the right number is difficult if the total dataset size is highly variable (e.g., it starts small but may grow much larger). Each shard contains a fixed fraction of the total data, so its size grows proportionally to the total. If shards are very large, rebalancing and recovery from node failures become expensive; if they are too small, they incur too much overhead. The best performance is achieved when shards are “just right,” neither too big nor too small.

Sharding by hash of key · sharding by hash range

Ranges, but of hashes

Can we have shards that split as data grows, like key ranges, without the hot spots? Yes: give each shard a range of hash values instead of a range of keys. With a 16-bit hash (0 to 65,535), shard 0 takes 0–16,383, shard 1 takes 16,384–32,767, and so on. Even consecutive timestamps hash all over the line.

A shard that grows too big or too busy still splits, so the number of shards adapts to the data. The price: a range query over the partition key is no longer efficient, because the keys in the range are scattered across all shards. But with a compound key, where only the first column is hashed, you can still range-scan the later columns inside one shard.

Try it: press Write 8 readings (consecutive seconds) and watch them spread. Press Split the fullest. Then try both queries: a time range over the hashed key, and a range of times for one sensor with key (sensor, time).

What the book says

If the required number of shards can’t be predicted, it’s better to use a scheme where the number adapts to the workload. Key-range sharding has this property but risks hot spots with many writes to nearby keys. One solution is to combine key-range sharding with a hash function, so that each shard contains a range of hash values rather than a range of keys.

Figure 7-5 uses a 16-bit hash function returning a number from 0 to 65,535 = 216 − 1 (in reality, usually 32 bits or more). Even very similar input keys, such as consecutive timestamps, have hashes uniformly distributed across that range. Values from 0 to 16,383 go to shard 0, from 16,384 to 32,767 to shard 1, and so on. As with key ranges, a shard can be split when it becomes too big or too heavily loaded; still expensive, but done as needed.

The downside compared with key ranges is that range queries over the partition key are not efficient, as keys in the range are scattered across all the shards. However, if keys consist of two or more columns and the partition key is only the first, you can still perform efficient range queries over the second and later columns: as long as all records in the range query have the same partition key, they are in the same shard. YugabyteDB and DynamoDB use hash-range sharding, and it is an option in MongoDB.

Many random slices even out

What the book says

Cassandra and ScyllaDB use a variant of hash-range sharding (Figure 7-6): the space of hash values (in the figure, 0–1024) is split into a number of ranges proportional to the number of nodes, with random boundaries, and several ranges are assigned to each node. Sharding by hash of key · consistent hashing

Move only the keys the new node needs

A consistent hashing algorithm maps keys to shards with two promises: each shard gets roughly the same number of keys, and when the number of shards changes, as few keys as possible move. (“Consistent” here has nothing to do with replica consistency or ACID; it means a key tends to stay put.)

Cassandra’s scheme is close to the original definition. Others include rendezvous hashing (highest random weight) and jump consistent hashing. With these, a new node doesn’t take slices of a few ranges: it takes individual keys scattered across all the other nodes.

Try it: pick mod N, Rendezvous or Jump and press Add a node. Count the moved keys (red outline): mod N moves most of them; the other two move about one in N, and only to the new node. Follow the highlighted line in the code for one key.

What the book says

A consistent hashing algorithm is a hash function that maps keys to a specified number of shards so that the number of keys mapped to each shard is roughly equal, and when the number of shards changes, as few keys as possible are moved from one shard to another.

Consistent here has nothing to do with replica consistency (Chapter 6) or ACID consistency (Chapter 8); it describes the tendency of a key to stay in the same shard if possible.

The algorithm used by Cassandra and ScyllaDB is similar to the original definition of consistent hashing, but several others have been proposed, such as highest random weight, also known as rendezvous hashing, and jump consistent hashing. With these, rather than a small number of existing shards being split into subranges for a new node, the new node is assigned individual keys previously scattered across all the other nodes. Which is preferable depends on the application.

Skewed workloads and relieving hot spots · the celebrity key

Split one hot key into a hundred cool ones

Hashing spreads keys evenly, not load. When a celebrity with millions of followers posts, a storm of reads and writes hits one key (the celebrity’s user ID or the post’s ID), so one shard melts no matter how good your hash is.

With shards defined by ranges, you can put a hot key in a shard by itself, even on a dedicated machine. Or fix it in the app: add two random digits to the hot key, so writes spread over 100 keys on different shards. The catch: every read must fetch all 100 and combine them. Writes get cheaper; reads get dearer.

Try it: press Fans comment with One key and watch one shard redline. Switch to Key + 2 random digits and repeat. Then press Read the comments in both modes and compare how many keys one read touches.

What the book says

Consistent hashing ensures keys are uniformly distributed across nodes, but that doesn’t mean the actual load is. If the workload is highly skewed (much more data under some partition keys, or much higher request rates to some keys), some servers can still be overloaded while others sit almost idle. On a social media site, a post by a celebrity user with millions of followers may cause a storm of activity: a large volume of reads and writes to the same key (perhaps the celebrity’s user ID, or the ID of the action people are commenting on).

A system that defines shards based on ranges of keys (or ranges of hashes) makes it possible to put an individual hot key in a shard by itself, perhaps even assigning it a dedicated machine.

It’s also possible to compensate at the application level: if one key is known to be very hot, add a random number to the beginning or end of the key. Adding just two random digits splits the writes to the key evenly across 100 keys, which can be distributed to different shards. However, any reads now have to read the data from all 100 keys and combine it. The volume of reads to each shard of the hot key is not reduced; only the write load is split.

Skewed workloads and relieving hot spots · heat changes

Yesterday’s viral post is today’s quiet one

Splitting a key costs every reader, so you only want it for the few keys that really are hot. That means bookkeeping: a list of which keys are split, and a process for turning an ordinary key into a specially managed hot key, and back.

Heat also moves. A post that goes viral is hot for a couple of days, then calms down. Some keys are hot for writes (split them), others are hot for reads (splitting wouldn’t help), and they need different strategies. Large cloud services automate this: Amazon calls it heat management or adaptive capacity.

Try it: press Next day to step through a week. With Split forever, the post stays split after it cools and reads keep paying. With Track heat, watch the bookkeeping table add and remove the key.

What the book says

Splitting a hot key requires additional bookkeeping: it makes sense to append the random number only for the small number of hot keys; for the vast majority of keys with low write throughput it would be unnecessary overhead. So you also need some way of keeping track of which keys are being split, and a process for converting a regular key into a specially managed hot key.

The problem is compounded by changes in load over time: a particular social media post that has gone viral may experience high load for a couple of days, but thereafter it’s likely to calm down. In addition, some keys may be hot for writes while others are hot for reads, necessitating different strategies.

Some systems (especially cloud services designed for large scale) automate dealing with hot shards. Amazon, for instance, calls it heat management or adaptive capacity. The details of how these systems work are beyond the scope of the book.

Operations · automatic versus manual rebalancing

The helpful robot that starts a stampede

Automatic rebalancing is convenient: less operational work, and cloud databases like DynamoDB can add and remove shards within minutes as load changes. But rebalancing is expensive: it reroutes requests and moves lots of data, and the system must keep taking writes the whole time.

Now combine it with automatic failure detection. One node is overloaded and slow. The others decide it’s dead and move its load onto themselves, which makes them slow, so they get declared dead too: a cascading failure. A human in the loop is slower but prevents surprises, and can rebalance ahead of a known surge like Cyber Monday or World Cup ticket sales.

Try it: with Fully automatic, press Traffic spike on node 2 and watch the cascade. Reset, pick Human approves and spike again. Then try Rebalance ahead, which adds capacity before the surge.

What the book says

Some systems decide automatically when to split shards and move them between nodes; others leave sharding to an administrator. There is a middle ground: Couchbase and Riak generate a suggested shard assignment automatically but require an administrator to commit it before it takes effect. Fully automated rebalancing is convenient and can even autoscale; cloud databases such as DynamoDB are promoted as able to add and remove shards to adapt to big increases or decreases in load within a matter of minutes.

However, automatic shard management can be unpredictable. Rebalancing is expensive: it requires rerouting requests and moving a large amount of data. Done carelessly, it can overload the network or the nodes and harm other requests. The system must continue processing writes during rebalancing; near its maximum write throughput, the shard-splitting process might not even keep up with incoming writes.

Such automation can be dangerous combined with automatic failure detection. If one node is overloaded and temporarily slow, the other nodes may conclude it is dead and automatically rebalance to move load away from it. This puts additional load on other nodes and the network, making things worse, and risks a cascading failure where other nodes become overloaded and are also falsely suspected of being down.

So it can be good to have a human in the loop. It’s slower, but it can help prevent operational surprises. Manual rebalancing is also useful preemptively, if a surge in traffic is expected because of a known event such as Cyber Monday holiday sales or ticket sales for the World Cup.

Request routing · three ways to find the node

Which door do I knock on?

You want key user:7. Which IP address and port do you connect to? This is request routing. It is like service discovery (Chapter 5), with one big difference: a stateless app server can serve any request, but a database request can only be served by a node that holds the right shard.

There are three approaches. 1. Ask any node (via a round-robin load balancer); if it doesn’t own the shard, it forwards the request and passes the reply back. 2. A routing tier that only routes: a shard-aware load balancer. 3. A shard-aware client that connects straight to the right node.

Try it: pick an approach and press Get a key several times. Count the network hops each request takes. In approach 1, sometimes you get lucky and land on the owner.

What the book says

If you want to read or write a particular key, how do you know which node (which IP address and port number) to connect to? This problem is request routing, and it’s very similar to service discovery. The biggest difference is that application services are usually stateless, so a load balancer can send a request to any instance; with sharded databases, a request for a key can be handled only by a node that is a replica for the shard containing that key.

So request routing has to be aware of the assignment from keys to shards and from shards to nodes. At a high level there are a few approaches (Figure 7-7): (1) allow clients to contact any node, e.g. via a round-robin load balancer; if that node owns the shard it handles the request directly, otherwise it forwards it to the appropriate node, receives the reply and passes it along; (2) send all requests to a routing tier first, which determines the node and forwards accordingly; it handles no requests itself, acting only as a shard-aware load balancer; (3) require clients to be aware of the sharding and the assignment of shards to nodes, so they connect directly to the appropriate node.

Each approach has some key problems. Who decides which shard should live on which node? News that spreads by word of mouth

Riak skips the notice board. Its nodes gossip: each one tells a few others what it knows about the cluster, and they pass it on. Eventually everyone hears, but in the meantime different nodes hold different maps for the same shard. That is much weaker than consensus; split brain is possible. Leaderless databases can live with it, since they make weak consistency guarantees anyway.

Clients still need IP addresses to reach the routing tier or a random node. Those change far less often than shard assignments, so plain DNS is usually enough. And analytical databases rarely route to one shard at all: their queries run on many shards in parallel (Chapter 11).

What the book says

Riak takes a different approach: it uses a gossip protocol among the nodes to disseminate any changes in cluster state. Leaderless databases can tolerate this because they generally make weak consistency guarantees anyway.

When using a routing tier or sending requests to a random node, clients still need to find the IP addresses to connect to. These are not as fast-changing as the assignment of shards to nodes, so it is often sufficient to use DNS for this purpose.

This discussion focused on finding the shard for an individual key, most relevant for sharded OLTP databases. Analytical databases often use sharding as well, but a query commonly needs to aggregate and join data from many shards in parallel rather than executing in a single shard (Chapter 11).

Sharding and secondary indexes · the problem

Find all the red cars

So far you always knew the partition key of the record you wanted. Kwame runs a used-car website sharded by listing ID. “Show me car 742” is easy: the ID says which shard.

But buyers search for “red cars” or “every Volvo.” That’s a secondary index: it doesn’t identify one record, it finds every record with a value. Relational and document databases have them, and they are the reason full-text search engines such as Solr and Elasticsearch exist. They don’t map neatly to shards. There are two answers: local and global indexes, next.

Try it: press Find car 742: one shard. Press Find red cars with no index: every shard must scan every car. Count rows read.

What the book says

The sharding schemes so far rely on the client knowing the partition key for any record it wants to access. This is easiest in a key-value model, where the partition key is the first part of the primary key (or the entire primary key), so it determines the shard and routes reads and writes to the responsible node.

It gets more complicated with secondary indexes. A secondary index usually doesn’t identify a record uniquely but is a way of searching for occurrences of a particular value: find all actions by user 123, find all articles containing the word hogwash, find all cars whose color is red.

Key-value stores often don’t have secondary indexes, but they are a standard feature of relational databases, common in document databases, and the raison d’être of full-text search engines such as Solr and Elasticsearch. They don’t map neatly to shards. There are two main approaches: local and global.

Sharding and secondary indexes · local secondary indexes

Each shard keeps its own little catalogue

In a local index, each shard indexes only its own records. Add a red car to shard 0, and shard 0 appends its ID to its own color:red list (a postings list). A write touches one shard, which is why it’s also called a document-partitioned index.

Reads pay instead. Red cars can be on any shard, so “all red cars” must go to every shard and merge the answers: scatter/gather. If you only need some results, any one shard will do; and if you know the partition key, ask just that shard. MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud and VoltDB use local indexes.

Try it: press List a red Ford and watch only one shard’s index change. Then compare three reads: All red cars (scatter/gather), Any 2 red cars (one shard), and Red cars, IDs 500–999 (you know the shard).

What the book says

In a local index, each shard independently maintains its own secondary indexes, covering only the records in that shard. Whenever you add, remove or update a record, you deal only with the shard containing that record. In information retrieval it is also known as a document-partitioned index.

In Figure 7-9, a used-car website uses the listing ID as partition key (IDs 0 to 499 in shard 0, 500 to 999 in shard 1, etc.) with secondary indexes on color and make. Whenever a red car is added, the shard automatically adds its ID to the list of IDs for the index entry color:red, which is also called a postings list.

When reading, if you already know the partition key you can search the appropriate shard; if you want only some results, you can send the request to any shard. But if you want all the results and don’t know their partition key, you must send the query to all shards and combine the results, because matches might be anywhere: red cars appear in both shard 0 and shard 1.

Local secondary indexes are widely used: MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud and VoltDB all use them.

Race conditions and intermittent write failures (where some changes were saved but others weren’t) can very easily cause the data to go out of sync; see the need for multi-object transactions in Chapter 8.

Local secondary indexes · tail latency and throughput

Wait for the slowest of everyone

A scatter/gather query is only as fast as its slowest shard. Say each shard is usually quick but slow one time in fifty. Ask one shard and you’re rarely slow. Ask twenty in parallel and odds are that one of them is slow, so most of your queries are. That is tail latency amplification (Chapter 2).

It also caps throughput. More shards let you store more data, but if every shard must process every query, adding shards doesn’t let you answer more queries per second.

Try it: slide Shards and press Run 100 queries. Watch the share of slow queries climb. Then compare Queries/sec the cluster can serve for scatter/gather and for single-shard lookups.

What the book says

Querying a sharded database this way can make read queries on secondary indexes quite expensive. Even if you query the shards in parallel, it is prone to tail latency amplification (see Use of Response Time Metrics, Chapter 2).

It also limits the scalability of your application: adding more shards lets you store more data, but it doesn’t increase your query throughput if every shard has to process every query anyway.

Sharding and secondary indexes · global secondary indexes

One catalogue, cut by the letter of the term

A global index covers data in all shards: color:red lists every red car anywhere. It can’t live on one node (that node would be the bottleneck), so it is sharded too, but by the indexed value: colours a–r on index shard 0, s–z on shard 1; makes split between f and h. It’s called term-partitioned.

Now “red cars” reads one index shard to get the postings list. Fetching the cars themselves still means visiting the shards that hold those IDs. And “red and Ford” needs two postings lists from two index shards, sent over the network and intersected: fine when the lists are short, slow when they are long.

Try it: press color = red: one index shard answers. Press Fetch the records to visit the data shards. Then press red AND Ford, and drag Cars in the database up to see the lists that must cross the network grow.

What the book says

Rather than each shard having its own local index, we can construct a global index covering data in all shards. It can’t just be stored on one node, which would become a bottleneck and defeat the purpose of sharding; a global index must also be sharded, but can be sharded differently from the primary-key index.

In Figure 7-10, the IDs of red cars from all shards appear under color:red, but the index is sharded so that colors starting with a to r are in shard 0 and s to z in shard 1; the make index is partitioned similarly, with the boundary between f and h. This is also called term-partitioned: a term is generalized to mean any value you can search for. A shard can hold a contiguous range of terms, or terms can be assigned by hash.

A query with a single condition (such as color = red) needs to read only a single shard to fetch the postings list. But to fetch records and not just IDs, you still have to read from all the shards responsible for those IDs. With multiple conditions (a color and a make, or multiple words in the same text), the terms will likely be on different shards; to compute the logical AND, the system must find all IDs that occur in both postings lists, which can be slow to send over the network if the lists are long.

Global secondary indexes · writes and staleness

Writes are where global indexes hurt. Listing one red Ford touches the data shard for its ID, the index shard for color:red, and the index shard for make:Ford, possibly three different nodes. Keeping them in step is hard.

One option is a distributed transaction (Chapter 8) that updates all three atomically. DynamoDB instead updates its global indexes asynchronously, so an index read may be stale for a moment, like replication lag. Global indexes pay off when reads far outnumber writes and postings lists are not too long. CockroachDB, TiDB and YugabyteDB use them; DynamoDB supports both local and global.

What the book says

Writes are more complicated with global indexes than with local ones, because writing a single record might affect multiple shards of the index (every term in the document might be on a different shard). This makes it harder to keep the secondary index in sync with the underlying data. One option is a distributed transaction to atomically update the shards storing the primary record and its secondary indexes (Chapter 8).

Global secondary indexes are used by CockroachDB, TiDB and YugabyteDB; DynamoDB supports both local and global secondary indexes. In DynamoDB, writes are asynchronously reflected in global indexes, so reads from a global index may be stale (similar to replication lag, Chapter 6).

Nevertheless, global indexes are useful if read throughput is higher than write throughput, and if the postings lists are not too long.

One write, three shards

Two ways to cut, two ways to index

From the book’s summary.

Key-range sharding

Keys are sorted, and each shard owns every key from a minimum up to a maximum. Range queries are efficient, but keys that are close together in the sort order can make a hot spot. Shards are rebalanced by splitting a range in two when it gets too big.

Hash sharding

Hash each key, and let each shard own a range of hash values (or use another consistent hashing algorithm). Load spreads more evenly, but the key order is destroyed, so range queries are inefficient. Often: a fixed number of shards, several per node, moved whole when nodes join or leave.

Compound keys

Use the first part of the key as the partition key, and sort records inside the shard by the rest. You keep efficient range queries among records that share a partition key.

Routing

A request must reach a node that holds its shard: through any node, a routing tier, or a shard-aware client. A coordination service such as ZooKeeper or etcd usually keeps the authoritative map.

Local secondary indexes

Stored in the same shard as the records. A write updates one shard; a lookup by the indexed value has to read every shard.

Global secondary indexes

Sharded by the indexed value. A lookup reads one index shard (fetching the records still visits several); a write may have to update several index shards.

The seesaws from this chapter

Each choice buys something and costs something else.

One node

Simple: no partition key, no cross-shard transactions

vs

Sharded

Cheap rebalancing: move whole shards, keys never change shard

Trivial to compute

The book’s closing thought: by design, every shard operates mostly independently, and that is what lets a sharded database scale to many machines. Operations that write to several shards are the problem: what if the write to one shard succeeds and another fails? That question belongs to the next chapters.

Words to know

Grown-up words, in plain language.

shard / partition
One piece of a dataset. Each record belongs to exactly one shard, and each shard is like a small database.
sharding
Splitting data across nodes so that each node stores and serves only some of it.
partition key
The part of a record that decides its shard. Every record with the same partition key is in the same shard.
horizontal scaling
Growing by adding more machines instead of buying a bigger one. Also called scale-out.
multitenancy
One service holding many customers (tenants), each with a self-contained dataset.
cell-based architecture
Grouping the services and storage for a set of tenants into a self-contained cell, so faults stay inside it.
NUMA
Nonuniform memory access: some memory banks are closer to one CPU than to others.
skew
Unfair sharding: some shards get more data or queries than others.
hot shard / hot spot
A shard with disproportionately high load.
hot key
One key with very high load, like a celebrity’s account.
key-range sharding
Each shard owns a contiguous range of sorted keys, like encyclopedia volumes.
range scan
Reading every key between two values in sorted order, such as all readings from one month.
pre-splitting
Creating shard boundaries on an empty database, before any data arrives.
shard split / merge
Cutting a too-big shard into two contiguous halves, or joining small neighbours back into one.
hash sharding
Hashing the partition key first, so similar keys land on different shards.
mod N
Picking a node with hash % N. Easy, but changing N moves most keys.
rebalancing
Moving shards between nodes so the load is even again after nodes join or leave.
resharding
Changing the number of shards: splitting every shard and rewriting it, which is expensive.
hash-range sharding
Each shard owns a range of hash values; shards can split as they grow.
cluster columns
In a data warehouse, the columns that decide how rows are sorted inside a partition.
consistent hashing
A mapping that keeps shards about equal and moves as few keys as possible when the number of shards changes.
rendezvous hashing
Every node scores the key; the highest score owns it. Also called highest random weight.
jump consistent hashing
A short loop that maps a key to one of N buckets, moving only about 1/N of keys when N grows.
heat management
Amazon’s name for automatically handling hot shards; also called adaptive capacity.
cascading failure
Moving load off a node wrongly thought dead overloads others, which are then thought dead too.
request routing
Finding which node (IP address and port) holds the shard for a key.
routing tier
A shard-aware load balancer that forwards each request to the right node and serves none itself.
split brain
Two parts of a system each believe they are in charge and make contradictory decisions.
coordination service
A small fault-tolerant service, such as ZooKeeper or etcd, that holds the authoritative shard map using consensus.
gossip protocol
Nodes pass cluster news to each other a few at a time, until everyone has heard.
secondary index
An index for searching by a value (color = red) rather than by the record’s key.
postings list
The list of record IDs filed under one index entry, such as every ID under color:red.
local index
Each shard indexes only its own records. Also called document-partitioned.
global index
One index over all shards, itself sharded by the indexed value. Also called term-partitioned.
scatter/gather
Sending a query to every shard and combining their answers.
tail latency amplification
When a request waits for many backends, the slowest one decides its speed, so slow responses become common.
