Sharding

When one pile of data gets too big for one computer, you cut it into pieces called shards and give each piece its own machine. The trick is deciding which piece each thing belongs to.

Big idea 1 · copies vs pieces

Two ways to use more than one computer

There are only two things you can do with a second computer. You can put the same data on it — that's replication, from the last chapter. Or you can put different data on it — that's sharding.

Each record lives in exactly one shard, so every shard is like a small database of its own. Real systems do both at once: the data is cut into shards, and every shard is copied to a few machines so nothing is lost.

Try it: turn the writes up until one node goes red, then split the data into three shards. Then switch on the copies and see how each node is the leader for one shard and a follower for others.

What the book says

A distributed database spreads data two ways: replication (a copy of the same data on several nodes) and sharding (splitting data into shards, also called partitions, and putting different shards on different nodes).

Normally each record, row or document belongs to exactly one shard, and each shard is effectively a small database of its own. Sharding is usually combined with replication, so one node can be leader for some shards and follower for others — but each shard still has only one leader.

The reason to shard is scalability: too much data or too high a write throughput for one machine. (If only reads are the problem, read scaling with replicas is enough.) Sharding is a heavyweight solution, mostly relevant at large scale — a single machine can do a lot nowadays. It adds complexity: you must choose a partition key, cross-shard writes need distributed transactions, and the scheme is hard to change later.

A shard is called a partition in Kafka, a range in CockroachDB, a region in HBase and TiDB, a vBucket in Couchbase, a vnode in Riak, a token-range in Cassandra, and a tablet in Bigtable, YugabyteDB and ScyllaDB. In PostgreSQL, partitioning means splitting a table into files on one machine, while sharding spreads it over machines. (Nothing to do with network partitions.) Redis, VoltDB and FoundationDB even shard inside one machine, one process per CPU core.

Big idea 2 · a shelf per customer

Three schools, one cupboard

Lots of apps serve many separate customers, called tenants. One newsletter company's sign-ups have nothing to do with another's. So you can give each tenant its own shard, like giving each school its own cupboard.

Then a noisy neighbour can't slow everyone down, and “please delete everything about us” becomes “throw away that one cupboard” instead of hunting through a shared pile.

Try it: let Bolt run a giant report in each mode, then delete Cosy's data. Notice who else feels it.

What the book says

SaaS and cloud products are often multitenant: each tenant (customer) has a self-contained dataset. Sharding by tenant gives resource isolation (one tenant's expensive query doesn't hurt others), permission isolation (an access-control bug is less likely to leak another tenant's data), per-tenant backup and restore, regulatory compliance (GDPR and CCPA export/deletion becomes an operation on one shard), data residence (a region-aware database can pin a tenant's shard to a jurisdiction), and gradual schema rollout, one tenant at a time.

In a cell-based architecture the same idea is applied to the services too: services and storage for a set of tenants form a self-contained cell, so a fault stays inside one cell.

The challenges: a tenant may grow too big for one node (then you must shard within that tenant), many tiny tenants make per-tenant shards expensive so they get grouped — and then must be moved as they grow — and features that join data across tenants become hard.

Big idea 3 · sharding by key range

Like the volumes of an encyclopedia

A paper encyclopedia is sharded: volume 1 holds A–B, volume 12 holds T–Z. To find “kangaroo” you don't search every book, you just grab the right volume. Databases can do the same with the partition key.

The volumes aren't equal widths, because words aren't spread evenly — the boundaries adapt to the data. And because keys are kept in sorted order inside a shard, asking for “everything from Ca to Cl” is easy.

There's a catch. If your key is a timestamp, every single write happens “now”, so they all pile into the newest volume while the others nap. That shard becomes a hot spot.

Try it: send writes in each mode. Watch the load bars. Then run the range query and count how many shards it has to read.

What the book says

Key-range sharding assigns a contiguous range of partition keys to each shard, like the volumes of a print encyclopedia. Ranges need not be evenly spaced; boundaries must adapt to the data. Boundaries can be chosen manually (Vitess, a sharding layer for MySQL) or automatically (Bigtable, HBase, MongoDB's range option, CockroachDB, RethinkDB, FoundationDB; YugabyteDB offers both).

Within a shard keys are stored sorted (B-tree or SSTables), so range scans are easy and the key can act as a concatenated index to fetch related records in one query — for example all sensor readings in a month.

The downside: lots of writes to nearby keys create a hot shard. With a timestamp key, all of today's writes land on this month's shard. The fix is to put something else first — e.g. sensor ID, then timestamp — which spreads the writes but then needs a separate range query per sensor.

Big idea 4 · rebalancing by splitting

When a volume gets too fat, cut it in half

A key-range database grows by splitting. When one shard gets too big — HBase splits at 10 GB by default — the database picks a point in the middle of its key range and makes two shards out of one. One of them can then move to a new machine.

Splitting is not free: every record has to be rewritten into new files, a bit like a compaction. And the shard that needs splitting is usually the busy one, so the split makes it busier for a while.

If lots of data is deleted, neighbouring small shards can merge back together. And on a brand-new empty database you can pre-split, if you can guess how the keys will be spread.

Step through it and watch shard C become two, move house, and later merge with its neighbour.

What the book says

On an empty database, HBase and MongoDB let you configure an initial set of shards — pre-splitting — which requires knowing roughly how keys will be distributed. Later, the system grows by splitting a shard into two or more smaller shards, each holding a contiguous subrange; if lots of data is deleted, small adjacent shards may be merged. This is similar to what happens at the top level of a B-tree.

A split is triggered by a shard reaching a configured size (HBase: 10 GB by default) or, in some systems, by sustained write throughput — so a hot shard can be split even when it is small. The number of shards therefore adapts to the data volume. Splitting is expensive: all the data must be rewritten into new files, like a compaction, and that cost lands on a shard that is already under high load.

Automatic or manual? Some systems rebalance by themselves; Couchbase and Riak generate a suggested assignment that an administrator must commit; DynamoDB adds and removes shards automatically within minutes. But automatic rebalancing is expensive and unpredictable, and combined with automatic failure detection it can cause a cascading failure: a slow node is declared dead, its load moves elsewhere, and now those nodes are overloaded too. A human in the loop is slower but safer, and lets you rebalance ahead of a known surge like Cyber Monday or a World Cup ticket sale.

Big idea 5 · sharding by hash of key

The number machine (and a trap)

If you don't care about keeping neighbouring keys together, you can feed the key into a hash function first. It's a machine that turns any word into a scrambled number — the same word always gives the same number, but similar words give wildly different ones. Skewed data comes out spread flat.

Now, how do you turn that number into a shard? The obvious idea is hash % N, where N is the number of nodes. It works… until you add a node. Then nearly everything has to move house at once.

Try it: go from 3 nodes to 4 and count how many of the 12 keys move. Only 3 stay put.

What the book says

A good hash function takes skewed data and makes it uniformly distributed: a 32-bit hash maps any string to a seemingly random number from 0 to 2³² − 1, and similar inputs land far apart. It need not be cryptographically strong — MongoDB uses MD5, Cassandra and ScyllaDB use Murmur3. Built-in language hashes can be unsafe here: Java's Object.hashCode() and Ruby's Object#hash may give a different value in different processes.

The mod N approach (hash(key) % 10 for 10 nodes) is easy to compute but leads to very inefficient rebalancing: if N changes, most keys must move from one node to another. We need an approach that moves as little data as possible.

Big idea 6 · a fixed number of shards

Make far more bins than you have shelves

Here's the fix that most systems use. Don't map keys to nodes — map them to a big, fixed number of shards, and then keep a separate note of which node is holding which shard.

A 10-node cluster might be split into 1,000 shards, 100 per node. When a machine joins, you just hand it whole bins from the others. No key ever changes bin; only bins change shelf.

Slide the number of nodes. Count the bins that move. Compare it with the 75% you saw with hash % N.

What the book says

Create many more shards than nodes and assign several shards to each node: 10 nodes, 1,000 shards, 100 each. A key goes to shard hash(key) % 1,000, and the system separately tracks which shard sits on which node. When a node joins, whole shards are reassigned to it; when one leaves, the reverse. Only entire shards move, which is cheaper than splitting, and the assignment of keys to shards never changes. The transfer takes time, so the old assignment keeps serving reads and writes while data moves.

Pick a shard count divisible by many factors, and give more shards to more powerful nodes. Used by Citus (a sharding layer for PostgreSQL), Riak, Elasticsearch and Couchbase. The limits: you can't have more nodes than shards, and if the original number turns out wrong, resharding is expensive — splitting every shard into new files, using lots of extra disk, sometimes without concurrent writes. Shards that are too big make rebalancing and recovery slow; too small and the overhead dominates.

Big idea 7 · sharding by hash range

One long ruler of hash numbers

You can combine both ideas: hash the key so the load spreads flat, then give each shard a range of hash numbers instead of a range of keys. Now shards can still be split when they grow, so the number of shards adapts by itself.

Cassandra and ScyllaDB cut the ruler into many pieces with random boundaries and hand several pieces to each node. Some pieces are bigger than others, but with many pieces per node the lumps even out.

Try it: look up a key, then add a node. It takes a slice from a few neighbours instead of reshuffling everybody — that's what consistent hashing means.

What the book says

In hash-range sharding each shard owns a contiguous range of hash values — with a 16-bit hash (0 to 65,535) shard 0 might take 0–16,383, shard 1 16,384–32,767, and so on. Shards can still be split when they get too big, so the number of shards adapts to the data instead of being fixed. The cost: range queries over the partition key are no longer efficient, because neighbouring keys are scattered. If the key has several columns and only the first is the partition key, range queries over the later columns are still efficient.

YugabyteDB and DynamoDB use hash-range sharding, and it's an option in MongoDB. Cassandra and ScyllaDB split the hash space into ranges with random boundaries, proportional in number to the nodes — 16 ranges per node in Cassandra by default, 256 in ScyllaDB — and adjust boundaries when nodes come and go.

A consistent hashing algorithm has two properties: roughly equal numbers of keys per shard, and as few keys as possible move when the number of shards changes. ("Consistent" here has nothing to do with replica or ACID consistency.) Other variants include rendezvous hashing (highest random weight) and jump consistent hashing, where a new node is given individual keys scattered across all other nodes rather than whole subranges.

Big idea 8 · skew and hot spots

Everyone is shouting at one door

Even a perfect hash can't save you if the traffic is lopsided. When a celebrity posts, millions of people read and write the same key. Hashing puts that key in one shard, and that shard catches fire while the others are bored. That's a hot key.

Two tricks help. Give the hot key a shard of its own — maybe a whole machine — so it can't hurt its neighbours. Or stick two random digits on the end of the key, splitting the writes across 100 keys.

The second trick has a price: every read must now visit all 100 keys and glue the answers together. And you need to remember which keys you did this to.

Try each mode and watch both numbers: the hottest shard's load, and the work a single read has to do.

What the book says

Unfair sharding is called skew; a shard with disproportionately high load is a hot shard or hot spot, and a single very busy key is a hot key — for example a celebrity user on a social network, where the partition key might be their user ID. Consistent hashing spreads keys evenly but not necessarily load.

Range-based schemes can put a single hot key in a shard by itself, perhaps with a dedicated machine. At the application level you can add a random number to the start or end of a hot key: two digits spread the writes over 100 keys. But reads then have to read all 100 and combine them — only the write load is split — and you need bookkeeping to track which keys are treated this way. Load also changes over time: a viral post is hot for days, and some keys are hot for reads while others are hot for writes. Cloud systems automate parts of this; Amazon calls it heat management or adaptive capacity.

Big idea 9 · request routing

“Which door do I knock on?”

Splitting the data is only half the job. When you ask for one key, something has to know which machine is holding it right now. There are three ways: ask any node and let it forward you, ask a routing tier in front, or let the client keep the map itself.

And somebody has to keep that map true while shards move about. Many systems park the map in a coordination service like ZooKeeper or etcd, which every node registers with and every router subscribes to.

Try it: move a shard without telling ZooKeeper, send a request, and watch it knock on the wrong door. Then let ZooKeeper announce the change.

What the book says

Request routing is like service discovery, except that a request for a key can be handled only by a node that holds the right shard. Three approaches: (1) clients contact any node, which forwards if the shard isn't its own; (2) a routing tier acts as a shard-aware load balancer; (3) sharding-aware clients connect directly.

Hard parts: who decides the assignment, how to keep that decision fault-tolerant without split brain, how routers learn about changes, and what to do with requests still in flight to the old node during a cutover.

Many systems use ZooKeeper or etcd with a consensus algorithm to hold the authoritative shard-to-node map and notify subscribers: HBase and SolrCloud use ZooKeeper, Kubernetes uses etcd, MongoDB uses its own config servers plus mongos routers, while Kafka, YugabyteDB, TiDB and ScyllaDB use built-in Raft. Riak instead gossips cluster state between nodes, which is weaker — split brain is possible — but leaderless databases tolerate that. DNS is usually enough for finding the IP addresses themselves.

Big idea 10 · sharding secondary indexes

The used-car lot: finding every red car

Cars are filed by their ID, so “show me car 137” is easy. But “show me every red car” doesn't match the filing system at all. For that you need a secondary index — and the index has to be sharded too.

A local index lives beside the data: each shard indexes only its own cars. Writing is cheap, but searching means asking every shard and merging the answers — a scatter/gather.

A global index is sharded by the search term instead: everything red is in one place. Now one read finds the whole list — but a single new car may have to update index shards all over the cluster.

Try it: search for red cars and add a red Honda in both modes. Watch the “shards touched” counters swap places.

What the book says

With a local secondary index (also called document-partitioned), each shard keeps indexes covering only its own records, so a write touches one shard. A read that doesn't know the partition key must query all shards and combine results — scatter/gather — which is prone to tail latency amplification and doesn't get faster as you add shards. Still widely used: MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud and VoltDB.

A global secondary index (term-partitioned) covers all shards and is itself sharded by the indexed value: colors a–r in one shard, s–z in another. A single-condition query reads one shard's postings list; but fetching the actual records still means reading the shards that hold those IDs, an AND of two long postings lists may have to travel the network, and a write may have to update several index shards — possibly with a distributed transaction.

Global indexes are used by CockroachDB, TiDB and YugabyteDB; DynamoDB supports both kinds, and updates its global indexes asynchronously, so reads from them may be stale.
