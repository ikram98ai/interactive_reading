Faults and partial failures · one machine vs many

The calculator that never fibs, and the office that sometimes does

Ask Amara’s pocket calculator for 3 + 5 + 8 a thousand times and you get 16 a thousand times. If its battery dies, you get nothing at all, never a 17. Computers are built that way on purpose: when something inside breaks, a single machine would rather crash completely than hand you a wrong answer. It hides the fuzzy physics underneath and pretends to be a perfect, deterministic machine.

Now ask an office to do it: Jonas debits the account, Mei credits the other one, Ravi writes it in the ledger, and they pass notes to each other. Most days it works. Some days Mei’s note never arrives. Some days Ravi did the work but his reply got lost, so you don’t even know whether it happened. That is a partial failure: some parts broken, the rest fine, and which parts changes every time. Distributed systems live here. The upside: if the system tolerates partial failure, you can reboot one node at a time for an upgrade and the service never stops.

Try it: in One computer, press Run ×5, then Hardware fault and run again: it crashes, it never lies. In Five nodes, press Run ×5 a few times and read the results: success, partial failure, and the worst one, unknown. Then press Rolling upgrade: every node reboots and the service keeps answering.

What the book says

Making a system reliable means it keeps working as a whole even when there is a fault. It is tempting to focus on the happy path and neglect faults, but in a large enough system one-in-a-million events happen every day, and experienced operators will tell you that anything that can go wrong will go wrong. The chapter turns pessimism “up to the maximum.”

On a single computer, when the hardware works, the same operation always produces the same result: it is deterministic. A hardware problem usually causes a total system failure (kernel panic, “blue screen of death,” failure to start up). This is deliberate: we prefer a computer to crash completely rather than return a wrong result, so computers present an idealized system model that operates with mathematical perfection. (In reality data does get silently corrupted and CPUs do sometimes return wrong results, but rarely enough to ignore.)

In distributed systems, faults occur much more frequently. Coda Hale’s anecdote lists long-lived network partitions in a single datacenter, PDU failures, switch failures, accidental power cycles of whole racks, whole-DC backbone and power failures, and a driver crashing a pickup truck into a datacenter’s HVAC system. Some parts can be broken in an unpredictable way while others work fine: a partial failure. Partial failures are nondeterministic, and you may not even know whether something succeeded.

If a system can tolerate partial failures, it can perform a rolling upgrade, rebooting one node at a time while the system as a whole keeps working: we can build a reliable system from unreliable components. “In distributed systems, suspicion, pessimism, and paranoia pay off.”

Unreliable networks · six ways to get no reply

You posted a letter and heard nothing back

Lucía mails a form to the tax office and waits. Weeks pass. Was the letter lost? Is it sitting in a sorting room? Did the office burn down, or is the clerk on holiday and will answer next month? Did they reply, and the reply got lost, or is the reply still on its way? From Lucía’s kitchen, all six look identical: no reply yet.

Our machines are in Lucía’s position. Each one has its own memory and disk and can’t look inside another (shared-nothing); the network is the only way to talk. And the internet and datacenter Ethernet are asynchronous packet networks: they promise nothing about when a packet arrives, or whether it arrives at all. The usual answer is a timeout, but when it fires you still don’t know what happened, and a request that was only stuck in a queue may still be delivered after you gave up.

Try it: leave the fate on Random and press Send request. The fog hides the network, exactly as it hides it from the client. When the timeout fires, tap the explanation you think is right. Then pick a specific fate, like Req queued, and watch it happen in the open, including what arrives after the timeout.

What the book says

The distributed systems in this book are mostly shared-nothing: machines connected by a network, each with its own memory and disk, using replication across machines for redundancy. The network is the only way they can communicate; even shared storage such as object storage is reached over the network.

The internet and most internal networks in datacenters (often Ethernet) are asynchronous packet networks: one node can send a message to another, but the network gives no guarantees as to when it will arrive or whether it will arrive at all. If you send a request and expect a response, your request may have been lost, or be waiting in a queue; the remote node may have failed, or temporarily stopped responding (say, during a long GC pause); it may have processed the request but the response was lost, or the response may be delayed (Figure 9-1).

These issues are indistinguishable: the only information you have is that you haven’t received a response yet. “If you send a request to another node and don’t receive a response, it is impossible to tell why.”

The usual way of handling this is a timeout: after some time you give up waiting. But when a timeout occurs, you still don’t know whether the remote node got your request, and if the request is still queued somewhere, it may still be delivered to the recipient.

Unreliable networks · the limitations of TCP

The courier who promises delivery, but only to the front desk

Omar sends a long contract by courier, cut into numbered envelopes. The courier service is diligent: it re-sends any envelope that isn’t signed for, and puts the pages back in order at the other end. But a signature from the front desk only proves the envelopes reached the building. If the lawyer upstairs has a heart attack before reading them, the contract was never handled, and the courier can’t tell Omar that.

That courier is TCP. It splits your byte stream into packets, retransmits lost ones, reorders, checksums, and runs congestion control so it doesn’t swamp the network. Your write() only puts bytes in the OS send buffer; the receiving kernel sends the acknowledgment. So TCP can’t plug a cable back in, an ACK isn’t proof the application processed anything, and its duplicate detection lives inside one connection: reconnect and resend, and the server may do the work twice. Messages ride on the stream with a length header in front, which is how HTTP and many RPC protocols frame requests.

Try it: pick a mode and press Send 2 messages. Packet lost: TCP quietly retransmits; the app only notices delay. Cable cut: retries go nowhere until TCP gives up. ACKed, app crashed: every packet is acknowledged, yet nothing was processed. Reconnect & resend: the add runs twice.

What the book says

Packets have a maximum size (generally a few kilobytes), so applications use TCP, the Transmission Control Protocol, to break large data streams into packets and reassemble them. Most of this also applies to QUIC, the Stream Control Transmission Protocol (SCTP) used in WebRTC, the BitTorrent uTP protocol, and other transport protocols.

TCP detects and retransmits dropped packets, puts reordered packets back in order, and detects corruption with a simple checksum. It also works out how fast it can send without overloading the network or the receiver: congestion control, flow control, or backpressure. Writing to a socket places data in a buffer managed by the OS; the receiving OS puts packet data in a receive buffer and sends an acknowledgment, and only then notifies the application.

TCP decides a packet was lost if no acknowledgment arrives within a timeout, but can’t tell whether the outbound packet or the acknowledgment was lost. It can resend, but can’t guarantee the new packet gets through (“TCP can’t plug it back in for you”). Eventually, after a configurable timeout, it gives up and signals an error. Its deduplication and retransmission apply to only a single connection, so if the application reconnects and retransmits, data could be duplicated.

If a connection closes with an error, you have no way of knowing how much data the remote node actually processed. An acknowledgment means only that the remote kernel received it; the application may have crashed first. “If you want to be sure that a request was successful, you need a positive response from the application itself.” Over one connection you can send many messages, each usually preceded by a header giving its length in bytes, as HTTP and many RPC protocols do.

Unreliable networks · network faults in practice

Cows, beavers, sharks, and a typo in a switch config

Hiro runs a small datacenter: two racks of three machines, each rack under a top-of-rack switch, both racks joined by a pair of aggregation switches for redundancy. Decades of networking, and it still breaks all the time: a cable works loose, a whole rack goes dark, an engineer pushes a bad config to both redundant switches at once, a fiber link gets stepped on by a cow.

The faults aren’t even tidy. A can talk to B and B to C while A and C can’t reach each other. A network card drops everything coming in but happily sends everything going out, so the machine looks chatty and is deaf. And a delay can stretch past a minute while switches reconfigure. When a chunk of the network is cut off from the rest, people call it a network partition or netsplit. The lesson: any communication over a network may fail, and your software has to know what it does when it does.

Try it: choose a fault and press Ping all pairs. The grid shows whether the machine in each row can reach the machine in each column. Compare Partial (one pair broken, both still reach a third machine) and One-way NIC (a row of green, a column of red).

What the book says

Network problems are surprisingly common, even in datacenters run by one company. One study in a medium-sized datacenter found about 12 network faults per month, half disconnecting a single machine and half an entire rack. Another found that adding redundant networking gear doesn’t reduce faults as much as you might expect, since it doesn’t guard against human error such as misconfigured switches, a major cause of outages.

Wide-area fiber interruptions have been blamed on cows, beavers and sharks, and humans cause them too, by misconfiguration, scavenging or sabotage. Across cloud regions, round-trip times of up to several minutes have been seen at high percentiles; within one datacenter, packet delay of more than a minute can occur during a network topology reconfiguration. So we have to assume messages might be delayed arbitrarily.

Communication can be partially interrupted: A and B can communicate, and B and C, but not A and C. A network interface may drop all inbound packets while sending outbound ones successfully, so a link working in one direction doesn’t mean it works in the other. Even a brief interruption can have repercussions lasting much longer.

Network partitions (netsplits) are one part of the network cut off from the rest; this is not fundamentally different from other interruptions, and unrelated to partitioning (sharding) of storage. If error handling isn’t defined and tested, arbitrarily bad things can happen: a cluster deadlocked even after the network recovers, or deleted data. Handling faults doesn’t have to mean tolerating them (showing users an error can be fine), but you must know how your software reacts and make sure it recovers; deliberately triggering network problems is one way to find out.

Unreliable networks · fault detection

Is anybody home?

Fatima knocks on her neighbour’s door to return a drill. Sometimes she gets a clear answer: a note on the door saying “moved out,” or the house is dark with the power meter stopped. Usually she just gets silence. Silence could mean nobody’s home, or they’re in the shower. So she knocks again, waits a bit longer, and eventually decides they’re out, without ever being sure.

A load balancer needs to stop sending requests to a dead node, and a database needs to promote a follower when the leader dies. Sometimes the system gets explicit feedback: the remote OS refuses the connection with an RST because nothing listens on the port; a script on the host announces that the process died (HBase does this); the switch’s management interface reports the link is down; a router replies ICMP Destination Unreachable. But you can’t count on any of it. In general you get no response at all, so you retry, wait for a timeout, and declare the node dead, while knowing it might be alive.

Try it: pick each case and press Check node 2. Watch where the answer comes from and how long it takes; the bars at the bottom keep score. Then turn off Switch access and try Powered off again: you’re reaching the node over the internet now.

What the book says

Many systems need to detect faulty nodes automatically: a load balancer needs to take a dead node out of rotation, and with single-leader replication a follower must be promoted if the leader fails. The uncertainty about the network makes it difficult to tell whether a node is working.

In specific circumstances you get explicit feedback. If you can reach the machine but no process is listening on the destination port (e.g. the process crashed), the OS will close or refuse TCP connections by replying with an RST or FIN packet. If a node process crashed or was killed but the OS still runs, a script can notify other nodes so another can take over without waiting for a timeout; HBase does this.

With access to the management interface of the datacenter’s network switches, you can query them to detect link failures at a hardware level (e.g. the remote machine is powered down). That’s ruled out over the internet, in a shared datacenter without access to the switches, or if a network problem stops you reaching the interface. A router that is sure an IP address is unreachable may reply with an ICMP Destination Unreachable packet, but it has no magic failure detection either.

Rapid feedback is useful but you can’t count on it; in general you have to assume you will get no response at all. You can retry a few times, wait for a timeout, and eventually declare the node dead. Since it could actually be alive, you balance false positives against false negatives: too short a timeout suspects alive nodes; too long means waiting on dead ones.

Unreliable networks · timeouts and unbounded delays

How long do you wait for a friend who’s late?

Kwame waits at the café for Sofia. Leave after two minutes and he’ll often leave while she’s still on the bus, and when she arrives, she buys the tickets he already bought. Wait an hour and he wastes an afternoon whenever she truly isn’t coming. There is no right number, because the bus has no timetable.

A failure detector has the same dilemma. A short timeout notices crashes fast but declares merely slow nodes dead; if the slow node was halfway through sending an email, a replacement sends it again. Worse, a dead node’s work moves to the others, and if they were slow because of overload, the extra work slows them too, and they get declared dead in turn: a cascading failure. If the network promised that every packet arrives within d and every request is handled within r, then 2d + r would be a perfect timeout. Real networks have unbounded delays.

Try it: in Detector, press Run 40 pings with the timeout at 300 ms, then drag the slider and run again; press Kill node B to see how long detection takes. In Takeover, try a timeout below and above 900 ms. In Cascade, press Run with a short timeout. In Bounded network, set the slider to 2d + r.

What the book says

If a timeout is the only sure way of detecting a fault, how long should it be? There is no simple answer. A long timeout means a long wait until a node is declared dead, during which users wait or see errors. A short timeout detects faults faster but risks declaring a node dead when it only suffered a temporary slowdown, such as a load spike.

Prematurely declaring a node dead is problematic: if it is actually alive and in the middle of an action (e.g. sending an email) and another node takes over, the action may be performed twice. Its responsibilities also move to other nodes, adding load. If the node was only slow because of overload, this can cause a cascading failure; in the extreme, all nodes declare each other dead and everything stops working.

In a fictitious network where every packet is delivered within time d or lost, and a non-failed node always handles a request within time r, every successful request receives a response within 2d + r, which would make a reasonable timeout. But asynchronous networks have unbounded delays, and most servers can’t guarantee a maximum handling time. For failure detection it isn’t enough to be fast most of the time: with a low timeout, a transient spike in round-trip times throws the system off balance.

Timeouts and unbounded delays · network congestion and queueing

Three on-ramps, one lane

Three motorway on-ramps merge into one lane toward the city. At 3 a.m. you sail through. At rush hour every car waits its turn at the merge, and if the queue backs up past the slip road, cars get turned away and have to try again later. The road isn’t broken. It’s just full.

Packets queue the same way, in many places. Ports 1, 2 and 4 of a switch all send to port 3, so the switch feeds them onto that link one at a time; that wait is network congestion, and if the switch queue fills, the packet is dropped and must be resent. At the destination, if every core is busy, the OS queues the request. A virtual machine can be paused for tens of milliseconds while another VM uses the core, and its incoming data piles up in the VM monitor. Even the sender queues, because TCP limits its own rate. When TCP retransmits a dropped packet, the application never sees the loss, only the delay.

Try it: press Send a burst with only machine 1 sending, then tap machines 2 and 4 to switch them on and send again: the queue at port 3 fills and starts dropping. Then add CPU busy, VM paused or TCP rate limit and watch where the waiting moves.

What the book says

As with traffic on roads, the variability of packet delays on computer networks is most often due to queueing. If several nodes simultaneously send packets to the same destination, the network switch must queue them up and feed them into the destination link one by one (Figure 9-2: ports 1, 2 and 4 all sending to port 3). On a busy link a packet may wait for a slot (network congestion); if the switch queue fills up, the packet is dropped and must be resent, even though the network is functioning fine.

When a packet reaches the destination machine and all CPU cores or application threads are busy, the OS queues the request until the application is ready, which may take an arbitrary length of time. In virtualized environments, a running OS is often paused for tens of milliseconds while another VM uses a CPU core; the incoming data is queued (buffered) by the VM monitor. And to avoid overloading the network, TCP limits the rate at which it sends, adding queueing at the sender before the data even enters the network.

When TCP detects and automatically retransmits a lost packet, the application does not see the loss directly, but does see the resulting delay: waiting for the timeout, then for the retransmitted packet to be acknowledged.

Timeouts and unbounded delays · TCP versus UDP

A phone call can’t wait for a lost word

Mei is telling Tomás on a VoIP call that the meeting moves to Thursday at ten. One packet of her voice, the one carrying “Thurs,” is lost. Waiting for it to be resent is pointless: by the time it arrives, the moment it should have played is long gone, and everything behind it has been held up too.

That’s why latency-sensitive apps like videoconferencing and VoIP use UDP. TCP retransmits and delivers bytes in order, so one lost packet blocks all the later ones until it’s resent: the sound freezes, then rushes. UDP doesn’t retransmit or do flow control, which removes some reasons for variable delay (switch queues and scheduling still apply). The app plays a moment of silence in the missing slot and carries on. The retry happens at the human layer instead.

Try it: press Play the call over TCP and watch the receive buffer hold every frame behind the lost one. Then switch to UDP and play it again: a short gap, no stall, and Tomás asks Mei to repeat herself.

What the book says

Some latency-sensitive applications, such as videoconferencing and Voice over IP (VoIP), use UDP rather than TCP. This is a trade-off between reliability and variability of delays: as UDP does not perform flow control and does not retransmit lost packets, it avoids some of the reasons for variable network delays (although it is still susceptible to switch queues and scheduling delays).

UDP is a good choice when delayed data is worthless. In a VoIP call there probably isn’t enough time to retransmit a lost packet before its data is due to be played over the speaker, so there’s no point retransmitting: the application fills the missing packet’s time slot with silence (a brief interruption in the sound) and moves on in the stream.

“The retry happens at the human layer instead.” (“Could you repeat that please? The sound just cut out for a moment.”)

Timeouts and unbounded delays · variability of network delays

The shared kitchen at dinner time

Nadia shares a flat kitchen with four others. At four in the afternoon the stove is free and pasta takes ten minutes. At seven everyone cooks at once and it might take forty, and on the night her neighbour bakes for a party, nobody can guess. She can’t control the neighbour; she can only learn how long dinner usually takes.

Queueing delay grows gently while a link is lightly used and explodes as it nears full capacity. In public clouds and multitenant datacenters the links, switches, network cards and even CPUs are shared, and a noisy neighbor you can’t see can saturate them. So timeouts can only be chosen experimentally: measure round-trip times for a long time, on many machines. Better still, let the system keep measuring response times and their spread, the jitter, and adjust its timeout automatically, as the Phi Accrual failure detector (used in Akka and Cassandra) and TCP’s retransmission timeouts do.

Try it: press Measure 60 round trips at 50% utilization, then push the slider toward 95% and measure again: the histogram stretches to the right and the fixed 200 ms timeout starts firing on live nodes. Turn on the noisy neighbor. Then switch the code tab to adaptive and compare false alarms and how slowly it would catch a real death.

What the book says

All these factors contribute to the variability of network delays. Queueing delays have an especially wide range when a system is close to its maximum capacity: a system with plenty of spare capacity can easily drain queues, whereas in a highly utilized system long queues build up very quickly.

In public clouds and multitenant datacenters, network links and switches, and even each machine’s network interface and CPUs (when running on VMs), are shared among many customers. Processing large amounts of data can saturate network links. With no control over or insight into other customers’ usage, delays can be highly variable if a noisy neighbor is using a lot of resources.

In such environments you can choose timeouts only experimentally: measure the distribution of round-trip times over an extended period and many machines, then trade off failure detection delay against the risk of premature timeouts. Even better, systems can continually measure response times and their variability (jitter) and adjust timeouts automatically. The Phi Accrual failure detector, used for example in Akka and Cassandra, is one way of doing this; TCP retransmission timeouts work similarly.

Unreliable networks · synchronous versus asynchronous networks

The phone call that never waits in line

When Amara phones her grandmother in Accra over an old landline, her voice never stutters. The moment the call connects, the telephone network books a tiny seat for it on every link along the route, in every frame, for as long as the call lasts. Nobody else can sit there, even when Amara says nothing.

That booked seat is a circuit. An ISDN line sends 4,000 frames a second, and the call owns 16 bits of each frame in each direction, so it can send exactly 16 bits every 250 µs. Because the space in the next hop is already reserved, a sample never queues behind anyone else’s data, and the end-to-end latency has a fixed maximum: a bounded delay. A network like this is synchronous. Ethernet and IP aren’t: there, packets take turns, and turns mean queues.

Try it: in Circuit, press Talk: send 12 samples and watch the latency bars: every one is the same height. Switch to Packets and talk again: other senders’ bursts land in the switch queues and your samples wait behind them.

What the book says

Distributed systems would be a lot simpler if the network delivered packets with a fixed maximum delay and never dropped them. To see why we can’t simply build that in hardware, the book compares datacenter networks with the traditional fixed-line telephone network (non-cellular, non-VoIP), which is extremely reliable: delayed audio frames and dropped calls are very rare. A call needs a constantly low end-to-end latency and enough bandwidth for the audio samples.

A telephone call establishes a circuit: a fixed, guaranteed amount of bandwidth is allocated for the call along the entire route between the two callers, and it stays in place until the call ends. For example, an ISDN network runs at a fixed rate of 4,000 frames per second; a call is allocated 16 bits of space within each frame (in each direction), so each side is guaranteed to be able to send exactly 16 bits of audio data every 250 microseconds.

This kind of network is synchronous: even as data passes through several routers, it does not suffer from queueing, because the 16 bits of space for the call have already been reserved in the next hop. With no queueing, the maximum end-to-end latency is fixed: a bounded delay.

Unreliable networks · can we not simply make network delays predictable?

Booking a lane for a file you can’t measure

Tomás wants to copy a 400 Mb backup across a 100 Mb/s link. On a circuit network he must first say how much bandwidth to book, and keep it booked until he’s done. Book too little and the copy crawls while most of the wire sits empty. Book too much and the network refuses to set the circuit up at all, because it can’t guarantee what it can’t spare.

A TCP connection doesn’t book anything. It sends as fast as the free capacity allows, right now, speeding up when the link is quiet and backing off when others burst, and it uses no bandwidth at all while idle. Web pages, emails and file copies are bursty: they have no particular bit rate, they just want to finish quickly. That is why Ethernet and IP are packet-switched, and why they queue.

Try it: in Circuit, drag Booked bandwidth and press Copy 400 Mb. Try 20 Mb/s, then 90 Mb/s. Then switch to TCP and copy the same file over the same busy link.

What the book says

A circuit in a telephone network is very different from a TCP connection. A circuit has a fixed amount of reserved bandwidth that nobody else can use while it is established, whereas the packets of a TCP connection opportunistically use whatever network bandwidth is available. You can give TCP a variable-sized block of data (an email or a web page) and it will try to transfer it in the shortest time possible. While a TCP connection is idle, it doesn’t use any bandwidth (except perhaps an occasional keepalive packet).

If datacenter networks and the internet were circuit-switched, a guaranteed maximum round-trip time could be established when a circuit was set up. They are not: Ethernet and IP are packet-switched protocols, which suffer from queueing and thus unbounded delays, and have no concept of a circuit.

They use packet switching because they are optimized for bursty traffic. A circuit is good for an audio or video call, which transfers a fairly constant number of bits per second. Requesting a web page, sending an email or transferring a file has no particular bandwidth requirement; we just want it to complete as quickly as possible.

To transfer a file over a circuit, you would have to guess a bandwidth allocation. Guess too low and the transfer is unnecessarily slow, leaving capacity unused. Guess too high and the circuit cannot be set up, because the network cannot allow a circuit whose bandwidth allocation it cannot guarantee. TCP, by contrast, dynamically adapts the rate of data transfer to the available network capacity.

Unreliable networks · latency and resource utilization

Twenty reserved tables, or one busy counter

Picture a café with twenty tables, each booked for one regular all day. A regular always finds a seat, instantly. But most regulars drop in for ten minutes, so most tables sit empty, and the twenty-first customer is turned away at the door. The café next door has no bookings: anyone sits anywhere. It serves three times the people with the same tables, but at lunch you may wait.

A wire that can carry 10,000 calls is the same kind of resource. Divide it statically and every call keeps its slot even when the other 9,999 are idle: delays are fixed, utilization is poor. Share it dynamically and senders jostle for the wire packet by packet: utilization is high, so each byte is cheaper, but there are queues. CPU cores shared among threads, and one physical machine shared among many customers’ VMs, make the same trade. Variable delay isn’t a law of nature; it’s the price of cheap.

Try it: keep Static slots and drag Active users past 20: people get refused while the wire is mostly idle. Switch to Dynamic sharing and push it to 100: everyone is served and the wire fills up, but the delay dots spread out. Pick CPU core or VMs to see the same picture in another costume.

What the book says

More generally, variable delays are a consequence of dynamic resource partitioning. A wire between two telephone switches that can carry up to 10,000 simultaneous calls is a resource shared by up to 10,000 users, divided in a static way: even if you are the only call on the wire and the other 9,999 slots are unused, your circuit gets the same fixed bandwidth as when the wire is fully utilized.

The internet shares bandwidth dynamically. Senders push and jostle to get their packets over the wire as quickly as possible, and the switches decide which packet to send from one moment to the next. The downside is queueing; the advantage is that it maximizes utilization of the wire. The wire has a fixed cost, so if you utilize it better, each byte you send over it is cheaper.

CPUs are similar. Sharing each core dynamically among several threads means a thread sometimes waits in the operating system’s run queue, so it can be paused for varying lengths of time, but this utilizes the hardware better than allocating a static number of CPU cycles to each thread. Better utilization is also why cloud platforms run several VMs from different customers on the same physical machine.

Latency guarantees are achievable if resources are statically partitioned (dedicated hardware, exclusive bandwidth allocations), at the cost of reduced utilization, i.e. more expense. Multitenancy with dynamic partitioning is cheaper but has variable delays. “Variable delays in networks are not a law of nature but simply the result of a cost/benefit trade-off.”

What the book says

There have been attempts to build hybrid networks supporting both circuit and packet switching. Applications depend on clocks to answer questions like: has this request timed out yet? What’s the 99th percentile response time of this service? In a distributed system, time is tricky because communication is not instantaneous. The time when a message is received is always later than the time when it is sent, but because of variable delays in the network, we don’t know how much later. This sometimes makes it difficult to determine the order in which things happened when multiple machines are involved.

Each machine has its own clock, a hardware device, usually a quartz crystal oscillator. They are not perfectly accurate, so each machine has its own notion of time. Clocks can be synchronized to some degree; the most common mechanism is the Network Time Protocol (NTP), which adjusts the computer clock according to the time reported by a group of servers, which in turn get their time from a more accurate source such as a GPS receiver.

What the book says

Modern computers have at least two kinds of clocks, a time-of-day clock and a monotonic clock, which serve different purposes. A time-of-day clock returns the current date and time according to a calendar (also known as wall-clock time). For example, clock_gettime(CLOCK_REALTIME) on Linux and System.currentTimeMillis in Java return the number of seconds (or milliseconds) since the epoch, midnight UTC on January 1, 1970, according to the Gregorian calendar, not counting leap seconds. (Although the Linux clock is called real-time, it has nothing to do with real-time operating systems.)

Time-of-day clocks are usually synchronized with NTP, so a timestamp from one machine (ideally) means the same as a timestamp on another. But if the local clock is too far ahead of the NTP server, it may be forcibly reset and appear to jump back to a previous point in time. These jumps, and similar jumps caused by leap seconds, make time-of-day clocks unsuitable for measuring elapsed time.

Time-of-day clocks can also jump at the start and end of Daylight Saving Time (DST), which can be avoided by always using UTC, which has no DST. Historically they also had coarse resolution (e.g., moving forward in steps of 10 ms on older Windows systems); on recent systems this is less of a problem.

What the book says

A monotonic clock is suitable for measuring a duration (time interval), such as a timeout or a service’s response time. clock_gettime(CLOCK_MONOTONIC) or clock_gettime(CLOCK_BOOTTIME) on Linux and System.nanoTime in Java use one. The name comes from the guarantee that it always moves forward, whereas a time-of-day clock may jump back.

You can check it at one point in time, do something, and check it again; the difference tells you how much time elapsed, more like a stopwatch than a wall clock. But the absolute value is meaningless: it might be the number of nanoseconds since the computer was booted, or something similarly arbitrary. It makes no sense to compare monotonic clock values from two computers. On a server with multiple CPU sockets there may be a separate timer per CPU; operating systems try to present a monotonic view, but it is wise to take that guarantee with a pinch of salt.

NTP may adjust the frequency at which the monotonic clock moves forward (slewing) if the local quartz is faster or slower than the NTP server. By default NTP allows the rate to be sped up or slowed down by up to 0.05%, but it cannot make the monotonic clock jump forward or backward. Resolution is usually quite good: microseconds or less on most systems.

In a distributed system, using a monotonic clock for elapsed time (e.g., timeouts) is usually fine, because it doesn’t assume any synchronization between different nodes’ clocks and is not sensitive to slight inaccuracies of measurement.

Seven ways a clock goes wrong quietly

Every quartz crystal ticks at a slightly wrong speed, and the speed changes with temperature. Google assumes its servers’ clocks drift by up to 200 parts per million. That sounds tiny: it’s 6 ms if the clock is corrected every 30 seconds. Correct it once a day and it can be 17 seconds off. Drift alone sets a floor on how accurate a clock can be, even when everything works.

And things don’t always work. A clock too far from the NTP server gets forcibly reset. A firewall can quietly cut a node off from NTP. Over a congested network NTP is only as good as the delay. Some NTP servers are simply wrong by hours. Leap seconds make a minute 61 seconds long. A paused VM sees its clock leap forward. And a phone’s clock is whatever its owner set it to.

What the book says

Google assumes a drift of up to 200 ppm for its servers, equivalent to 6 ms for a clock resynchronized every 30 seconds, or 17 seconds for one resynchronized once a day. This drift limits the best possible accuracy, even if everything is working correctly.

A clock that differs too much from an NTP server may refuse to synchronize or be forcibly reset, so applications may see time go backward or suddenly jump forward. A node accidentally firewalled off from NTP may go unnoticed for some time while drift piles up. NTP can only be as good as the network delay: one experiment achieved a minimum error of 35 ms over the internet, with occasional spikes of around a second, and large delays can make the client give up. Some NTP servers are wrong or misconfigured, reporting time that is off by hours; clients mitigate this by querying several servers and ignoring outliers.

Leap seconds make a minute 59 or 61 seconds long and have crashed many large systems. The best handling may be to have NTP servers “lie” by smearing the adjustment over a day; leap seconds will no longer be used from 2035 on. In VMs, a VM paused while another runs sees its clock suddenly jump forward, and the NTP client inside may misreport its accuracy. On devices you don’t control, some users deliberately set the clock wrong, for example to cheat in games.

Very good accuracy is possible with enough investment. MiFID II requires high-frequency trading funds to synchronize clocks to within 100 microseconds of UTC. This takes GPS receivers and/or atomic clocks, the Precision Time Protocol (PTP), and careful deployment and monitoring; GPS signals can easily be jammed. Some cloud providers now offer high-accuracy clock synchronization for VMs, but it still requires a lot of care.

What the book says

Clocks seem simple, but they have a surprising number of pitfalls: a day may not have exactly 86,400 seconds, time-of-day clocks may move backward, and one node’s clock may be quite different from another’s. The increment that lost to the number it added to

Amaka sets a shared counter to 1 on a server in Lagos. A moment later, after that write has reached a server in Lima, Mateo adds 1 to it there, so it should be 2. Both writes travel on to a third server, which has to decide which one is newer. It looks at the timestamps, and Mateo’s says 42.003 while Amaka’s says 42.004. The Lima server’s clock was just two milliseconds behind. The third server keeps 1, and Mateo’s increment is gone. No error, no warning.

This is last write wins (LWW): keep the value with the greatest timestamp and discard the rest. It trusts each node’s time-of-day clock to say which write happened later, and a few milliseconds of skew is enough to fool it. The increment was causally later, since it was built on top of the first write, yet it got the earlier timestamp. A logical clock fixes this: a counter that every node pushes past any value it has seen, so whatever builds on a write is always stamped higher.

Ordering events across multiple nodes is a tempting but dangerous use of clocks. In Figure 9-3 (multi-leader replication), client A writes x = 1 on node 1; it is replicated to node 3; client B increments x on node 3 (x = 2); both writes are replicated to node 2. Each write is tagged with the time-of-day clock of the node where it originated, and the skew between node 1 and node 3 is under 3 ms. Yet x = 1 has timestamp 42.004 seconds and x = 2 has 42.003 seconds, so with last write wins node 2 concludes x = 1 is more recent and drops the increment.

You could make every overwrite carry a timestamp higher than the value it replaces, but that costs an extra read. Cassandra and ScyllaDB instead use the client clock’s timestamp with an LWW policy. The problems: writes can mysteriously disappear, because a node with a lagging clock can’t overwrite values from a node with a faster clock until the skew has elapsed; LWW can’t tell sequential writes from truly concurrent ones (version vectors are needed for that); and two writes can get the same timestamp, especially with millisecond resolution, needing a tiebreaker (such as a large random number) that can also violate causality.

Even with tightly NTP-synchronized clocks you could send a packet at 100 ms by the sender’s clock and have it arrive at 99 ms by the recipient’s, so it appears to arrive before it was sent. Correct ordering would need clock error well below the network delay, which isn’t possible, since NTP’s own accuracy is limited by the network round-trip time.

Logical clocks, based on incrementing counters rather than an oscillating quartz crystal, are a safer alternative: they capture only the relative ordering of events. Time-of-day and monotonic clocks, which measure actual elapsed time, are called physical clocks.

You may be able to read a time-of-day clock with microsecond or even nanosecond resolution, but that doesn’t mean it is accurate to that precision. Most systems don’t expose this: clock_gettime doesn’t tell you whether the error is five milliseconds or five years. What the book says

Multiversion concurrency control (MVCC) lets read-only transactions see a consistent snapshot without locking. It generally requires a monotonically increasing transaction ID: a write with a greater ID than the snapshot is invisible to it. On a single node a counter suffices, but a global, monotonically increasing ID across all shards and datacenters is difficult, because it requires coordination. The ID must reflect causality: if B reads or overwrites a value written by A, B needs a higher ID. With lots of small, rapid transactions, creating such IDs becomes an untenable bottleneck.

Timestamps from synchronized time-of-day clocks would have the right properties if synchronization were good enough; the problem is uncertainty. Spanner implements snapshot isolation across datacenters this way, using TrueTime’s confidence interval: if A = [Aearliest, Alatest] and B = [Bearliest, Blatest] do not overlap, B definitely happened after A. Only overlapping intervals leave the order unsure.

To ensure transaction timestamps reflect causality, Spanner deliberately waits for the length of the confidence interval before committing a read/write transaction, so any transaction that may read the data is at a sufficiently later time. To keep the wait short, Google deploys a GPS receiver or atomic clock in each datacenter, synchronizing clocks to within about 7 ms.

The atomic clocks and GPS receivers aren’t strictly necessary: the important thing is having a confidence interval, and accurate sources only keep it small. YugabyteDB can leverage ClockBound when running on AWS, and several other systems now rely on clock synchronization to various degrees.

Eight ways to freeze a thread mid-sentence

Is a 15-second pause realistic? Unfortunately, yes. A thread can stop between any two instructions: the garbage collector stops the world, the hypervisor runs someone else’s VM, a class file is lazily loaded from a slow disk, a page of memory has to come back from swap, someone presses Ctrl-Z. When it continues, it picks up from the very next instruction, and nothing in its own code tells it that the world moved on.

On a single machine we tame this kind of timing chaos with mutexes, semaphores, atomic counters and blocking queues. None of them carry over to a distributed system, because there is no shared memory, only messages over an unreliable network. A node has to assume it can be paused for a long time at any point, even in the middle of a function, and that meanwhile the others may decide it is dead.

What the book says

Reasons a thread might be paused for a long time:

  • Contention among threads for a shared resource such as a lock or queue; often worse with more CPU cores, and hard to diagnose.
  • Garbage collection that needs to stop all running threads. Such “stop-the-world” garbage collection pauses once sometimes lasted several minutes; modern GC algorithms make this less of a problem.
  • VM suspend and resume, at any point and for any length of time, sometimes used for live migration, where the pause depends on how fast processes write to memory. Laptops and phones are suspended when the lid closes.
  • Context switches by the OS or hypervisor; CPU time spent in other VMs is steal time. Under heavy load, with a long run queue, the paused thread may wait a while.
  • Synchronous disk access, sometimes hidden (the Java classloader lazily loads class files); on a network block device such as Amazon EBS, network delays add to it.
  • Swapping: a memory access may page-fault and wait for disk; under memory pressure the OS may end up thrashing, so paging is often disabled on servers.
  • SIGSTOP (e.g. Ctrl-Z) stops a Unix process until SIGCONT, and may be sent accidentally by an operations engineer.

All of these can preempt the thread at any point and resume it later without it noticing. Mutexes, semaphores, atomic counters, lock-free data structures and blocking queues don’t directly translate to distributed systems, which have no shared memory.

A variant: collect only short-lived objects (fast), and restart each process periodically, one at a time, before long-lived objects pile up enough to need a full collection.

What the book says

Garbage collection used to be one of the biggest reasons for process pauses, but GC algorithms have improved a lot: a properly tuned collector now usually pauses for no more than a few milliseconds. Java offers concurrent mark sweep (CMS), garbage-first (G1), the Z garbage collector (ZGC), Epsilon and Shenandoah, each optimized for different memory profiles. Go offers a simpler concurrent mark and sweep collector that attempts to optimize itself.

To avoid GC pauses entirely, use a language without a garbage collector: Swift uses automatic reference counting, while Rust and Mojo track object lifetimes via the type system. In a garbage-collected language you can mitigate pauses by reusing objects from pools, or allocating data off-heap.

A more extreme approach treats GC pauses like brief planned outages: if the runtime can warn that a node soon needs a GC pause, the application stops sending new requests to it, waits for outstanding requests to finish, and performs the GC while no requests are in progress. This hides GC pauses from clients and reduces the high percentiles of response time.

A variant uses the garbage collector only for short-lived objects and restarts processes periodically, before they accumulate enough long-lived objects to need a full GC; one node at a time, with traffic shifted away first, as in a rolling upgrade. These measures can’t fully prevent GC pauses, but they usefully reduce their impact.

It is also safe, because there can be only one majority at a time, never two with conflicting decisions.

A client that lost its lease but doesn’t know it yet is a zombie. We can’t prevent zombies, so we make them harmless: fencing. What the book says

A zombie is a former leaseholder that has not yet found out that it lost the lease and is still acting as if it were the current leaseholder. Since we cannot rule out zombies entirely, we have to ensure they can’t do any damage in the form of split brain. This is called fencing off the zombie.

Some systems shut zombies down: disconnecting them from the network, shutting down the VM via the cloud provider’s management interface, or even physically powering down the machine, sometimes known as shoot the other node in the head (STONITH). It is not particularly effective: it does not protect against the large network delays of Figure 9-5; all the nodes could shut one another down; and by the time a zombie has been detected and shut down, data may already have been corrupted.

In the more robust solution (Figure 9-6), every time the lock service grants a lock or lease it also returns a fencing token, a number that increases every time a lock is granted, and every write to the storage service must include the client’s current token. Client 1 acquires the lease with token 33 and pauses; client 2 acquires it with token 34 and writes; when client 1 comes back with 33, the storage service remembers that it has already processed a write with the higher token 34 and rejects it. A client that has just acquired the lease must immediately make a write, and once that write has completed, any zombies are fenced off. This resembles optimistic concurrency control, except that fencing is permanent, while concurrency control failures can be retried.

Other names: sequencers in Chubby (Google’s lock service), epoch numbers in Kafka, the ballot number (Paxos) or term number (Raft). With ZooKeeper you can use the transaction ID zxid or the node version cversion; with etcd, the revision number along with the lease ID; the FencedLock API in Hazelcast explicitly generates a fencing token.

Storage needs a way to check whether a write is based on an outdated token. Alternatively, it is sufficient to support a write that succeeds only if the object has not been written by another client since the current client last read it, like an atomic CAS: Amazon S3 calls it conditional writes, Azure Blob Storage conditional headers, and Google Cloud Storage request preconditions.

Fencing tokens can detect and block a node that is inadvertently acting in error (e.g., because it hasn’t yet found out that its lease has expired). However, if the node deliberately wanted to subvert the system’s guarantees, it could easily do so by sending messages with a fake fencing token.

The book assumes that nodes are unreliable but honest: they may be slow or never respond, and their state may be outdated (because of a GC pause or network delays), but if a node does respond, it is playing by the rules of the protocol to the best of its knowledge. The Byzantine Generals Problem generalizes the two generals problem, which imagines two army generals needing to agree on a battle plan; camped at different sites, they communicate only by messenger, and the messengers sometimes get delayed or lost (like packets in a network). In the Byzantine version, n generals need to agree, hampered by traitors in their midst. Most generals are loyal and send truthful messages, but the traitors may try to deceive and confuse the others by sending fake or untrue messages. It is not known in advance who the traitors are.

Byzantium was an ancient Greek city that later became Constantinople, in what is now Istanbul. There is no historic evidence that its generals were more prone to intrigue than others; the name comes from Byzantine in the sense of excessively complicated, bureaucratic, devious. Lamport wanted a nationality that would not offend any readers, and was advised that calling it The Albanian Generals Problem was not such a good idea.

Who actually needs to defend against liars?

Byzantine fault tolerance is like hiring four independent accountants and only trusting a figure three of them agree on. Wonderful when the books might be cooked, wildly expensive when you employ the only accountant and trust them.

What the book says

A system is Byzantine fault-tolerant if it continues to operate correctly even if some of the nodes are malfunctioning and not obeying the protocol, or if malicious attackers are interfering with the network. In aerospace environments, memory or CPU register data could become corrupted by radiation, so flight control systems must tolerate Byzantine faults. In a system with multiple participating parties, some may attempt to cheat or defraud others; the consensus mechanisms underlying cryptocurrencies like Bitcoin and other blockchain-based systems can be considered a way of getting mutually untrusting parties to agree on whether a transaction happened, without relying on a central authority.

In the kinds of systems this book discusses, we can usually safely assume there are no Byzantine faults: in a datacenter all the nodes are controlled by your organization, and radiation levels are low enough that memory corruption is not a major problem (although datacenters in orbit are being considered). Multitenant systems have mutually untrusting tenants, but they are isolated via firewalls, virtualization and access control policies, not Byzantine fault tolerance. Byzantine fault-tolerant protocols are quite expensive, and fault-tolerant embedded systems rely on support from the hardware level; in most server-side data systems the cost makes them impracticable.

Web applications must expect arbitrary and malicious behavior from clients under end-user control, such as web browsers; that is why input validation, sanitization and output escaping matter (to prevent SQL injection and cross-site scripting). But they make the server the authority on what client behavior is allowed rather than using Byzantine fault-tolerant protocols. In peer-to-peer networks, with no central authority, Byzantine fault tolerance is more relevant.

A software bug could be regarded as a Byzantine fault, but if you deploy the same software to all nodes, a Byzantine fault-tolerant algorithm cannot save you. Most require a supermajority of more than two-thirds of the nodes to be functioning correctly (with four nodes, at most one may malfunction), so you would need four independent implementations and hope a bug appears in only one. Likewise, if an attacker can compromise one node, they can probably compromise all of them; authentication, access control, encryption, firewalls and so on remain the main protection against attackers.

Grace runs a ferry. What the book says

Algorithms must be written so that they do not depend too heavily on the details of the hardware and software configuration on which they run. With regard to timing, three system models are in common use.

Synchronous model: assumes bounded network delay, bounded process pauses and bounded clock error. This does not imply exactly synchronized clocks or zero network delay; it means you know that delay, pauses and drift will never exceed a fixed upper bound. It is not a realistic model of most practical systems, because unbounded delays and pauses do occur.

Partially synchronous model: the system behaves like a synchronous system most of the time, but it sometimes exceeds the bounds for network delay, process pauses and clock drift. This is a realistic model of many systems: most of the time networks and processes are quite well behaved, but any timing assumptions may be shattered occasionally, and then delay, pauses and clock error may become arbitrarily large.

Asynchronous model: an algorithm is not allowed to make any timing assumptions; in fact, it does not even have a clock, so it cannot use timeouts. Some algorithms can be designed for the asynchronous model, but it is very restrictive.

Crash-stop faults: in the crash-stop (or fail-stop) model, an algorithm may assume a node can fail in only one way, by crashing. It may suddenly stop responding at any moment, and thereafter it is gone forever; it never comes back.

Byzantine (arbitrary) faults: nodes may do absolutely anything, including trying to trick and deceive other nodes.

System model and reality · distinguishing between safety and liveness

Broken at 10:06, or just not yet?

Tariq’s bakery promises two things. One: no two customers ever get the same ticket number. Two: everyone who takes a ticket is eventually served. If two people hold ticket 34, Tariq can say exactly when it went wrong, the moment the second 34 was printed, and nothing he does afterwards un-prints it. But if a customer has waited ten minutes during a power cut, the second promise isn’t broken. It just hasn’t come true yet.

These are the two kinds of property. A safety property, once violated, was violated at a point in time you can name, and the damage is permanent. A liveness property can be unmet right now and still come true later; its definition usually contains the word “eventually.” Distributed algorithms are expected to keep safety always, even if every node crashes or the whole network fails. Liveness gets caveats: a request is answered only if a majority of nodes are up and the network eventually recovers. The partially synchronous model promises exactly that: outages are finite.

Outage never heals and All nodes crash show what an algorithm still owes you when everything fails: no wrong answers, even if it can give no answers at all.

What the book says

In the fencing token example, uniqueness and monotonic sequence are safety properties, but availability is a liveness property. A giveaway is that liveness properties often include the word “eventually” in their definition. And eventual consistency is a liveness property.

Safety is often informally defined as nothing bad happens, and liveness as something good eventually happens, but good and bad are value judgments that don’t apply well to algorithms. More precisely: if a safety property is violated, we can point to the particular point in time that it was broken (for example, the operation in which a duplicate fencing token was returned), and “the violation cannot be undone—the damage is already done.” A liveness property may not hold at a certain point in time, but there is always hope that it may be satisfied in the future.

For distributed algorithms, it is common to require that safety properties always hold, in all possible situations of a system model. Even if all nodes crash, or the entire network fails, the algorithm must ensure that it does not return a wrong result. With liveness properties we are allowed to make caveats: for example, a request needs to receive a response only if a majority of nodes have not crashed, and only if the network eventually recovers from an outage.

The definition of the partially synchronous model requires that eventually the system returns to a synchronous state: any period of network interruption lasts only for a finite duration and is then repaired.

What the book says

Safety and liveness properties and system models are very useful for reasoning about correctness, but when implementing an algorithm, the messy facts of reality come back to bite you, and the system model turns out to be a simplified abstraction of reality.

Algorithms in the crash-recovery model generally assume that data in stable storage survives crashes. But what if the data on disk is corrupted or wiped out by hardware error or misconfiguration? What if a server has a firmware bug and fails to recognize its hard drives on reboot, even though the drives are correctly attached?

Quorum algorithms rely on a node remembering the data that it claims to have stored. If a node may suffer from amnesia and forget previously stored data, that breaks the quorum condition and thus breaks the correctness of the algorithm. A new system model, in which stable storage mostly survives crashes but may sometimes be lost, becomes harder to reason about.

A real implementation may still have to include code to handle the case of something happening that was assumed to be impossible, even if that handling boils down to printf("Sucks to be you") and exit(666), letting a human operator clean up the mess. This is one difference between computer science and software engineering. Abstract system models are not worthless, quite the opposite: they distill the complexity of real systems down to a manageable set of faults that we can reason about.

Billions of ways to run three nodes

Kwame wants to know whether his three-node protocol is right. With one message per node there are 6 orders things can happen in. Handwritten tests cover the cases someone thought of, mostly happy paths. Randomized testing (property-based testing, fuzzing, deterministic simulation testing) throws thousands of random executions at the system and finds what nobody imagined, but a needle gets harder to hit as the haystack grows. Formal verification describes the algorithm mathematically and proves its properties hold in every execution the system model allows: it can’t miss a case, but it proves the model, not your code. What the book says

How do we know that an algorithm satisfies the required properties? Because of concurrency, partial failures and network delays, there are a huge number of potential states. We need to guarantee that the properties hold in every possible state and ensure that we haven’t forgotten about any edge cases.

One approach is to formally verify an algorithm by describing it mathematically and using proof techniques to show that it satisfies the required properties in all situations that the system model allows. Proving an algorithm correct does not mean its implementation on a real system will necessarily always behave correctly, but it is a very good first step: theoretical analysis can uncover problems that might remain hidden for a long time in a real system and only bite when your assumptions (e.g., about timing) are defeated by unusual circumstances.

It is prudent to combine theoretical analysis with empirical testing. Techniques such as property-based testing, fuzzing and deterministic simulation testing use randomization to test a system in a wide range of situations. Organizations such as Amazon Web Services, FoundationDB and TigerBeetle have successfully used a combination of these techniques on many of their products.

A machine that tries every move

Sofia writes the lease protocol from the lock scenes as a tiny specification: a handful of variables and the moves that change them, such as a client acquires the lease, the lease expires without telling anyone, a client writes. No networking code, no retries, no logging. Then a model checker starts from the initial state and tries every move from every state it reaches, breadth first, checking the invariant no write lands after a newer leaseholder has written in each one.

When the invariant breaks, the checker hands back the shortest sequence of moves that breaks it: a counterexample. The catch is size. Real state spaces are infinite, so you bound the search, for example to a maximum number of steps. A bug that needs more steps than the bound is never found. And because the checker runs the spec rather than your code, the two can quietly drift apart.

Try it: press Check model with the bound at 6: the checker finds a 5-step counterexample and replays it against the spec. Drag Depth bound down to 4 and check again: “no violation found,” which is not the same as no bug. Then switch to With fencing tokens: the invariant holds at every depth.

What the book says

Model checkers are tools that help verify that an algorithm or system behaves as expected. An algorithm specification is written in a purpose-built language such as TLA+, Gallina, or FizzBee, which makes it easier to focus on an algorithm’s behavior without worrying about implementation details. Model checkers then verify that invariants hold across all of an algorithm’s states by systematically trying all the things that could happen.

Model checking can’t actually prove that invariants hold for every possible state, since most real-world algorithms have an infinite state space; that would require a formal proof, which is typically more difficult. Instead, model checkers encourage you to reduce the model to an approximation that can be fully verified, or to limit the execution to an upper bound (e.g., a maximum number of messages). Bugs that occur only with longer executions would then not be found.

Still, model checkers strike a nice balance between ease of use and the ability to find nonobvious bugs. CockroachDB, TiDB, Kafka and many other distributed systems use model specifications to find and fix bugs. Using TLA+, researchers demonstrated the potential for data loss in viewstamped replication (VR) caused by ambiguity in the prose description of the algorithm.

By design, model checkers don’t run your actual code but a simplified model of the protocol’s core ideas. That makes the state space tractable, but risks the specification and the implementation going out of sync. Checking that they behave equivalently is possible, but requires instrumentation in the real implementation.

What the book says

Many bugs are triggered when machine and network failures occur. Fault injection is an effective (and sometimes scary) technique that verifies whether a system’s implementation works as expected when things go wrong: inject faults into a running system’s environment and see how it behaves. Faults can be network failures, machine crashes, disk corruption, paused processes, anything you can imagine going wrong with a computer.

Fault injection tests are typically run in an environment that closely resembles production; some inject faults directly into production. Netflix popularized this approach with its Chaos Monkey tool. Production fault injection is often referred to as chaos engineering.

The system under test is deployed along with fault injection coordinators and scripts. Coordinators decide what faults to execute and when; local or remote scripts inject failures into individual nodes or processes. A Linux process can be paused or killed using Linux’s kill command, a disk can be unmounted with umount, and network connections can be disrupted through firewall settings. You inspect system behavior during and after faults are injected.

The myriad of tools required makes fault injection tests cumbersome to write, so it’s common to adopt a framework like Jepsen, which comes with integrations for various operating systems and many prebuilt fault injectors. Jepsen has been remarkably effective at finding critical bugs in many widely used systems.

Seed 37 fails. Every single time.

Rahul’s overnight chaos test failed once in a thousand runs, and the logs aren’t enough to say why. He reruns it all day; it never fails again. The failure depended on a particular order of thread wake-ups and packet delays that he can’t recreate.

Deterministic simulation testing (DST) runs your real code, but replaces the network, disk I/O, clocks and thread scheduling with mocks the simulator controls. Every “random” choice (how long a packet takes, which message arrives first, whether a node crashes) comes from one pseudo-random generator started from a seed. Run thousands of seeds; when one fails, run that seed again and you get the identical execution, step by step. And because the clock is fake, a 30-second timeout costs no real time at all.

Try it: press Run 100 seeds: a few seeds break the invariant (an increment applied twice). Press Replay seed as often as you like: the same events at the same simulated times. Now turn Real threads & clock on and replay: the failure usually vanishes. The head switch shows the three places determinism can be injected.

What the book says

Deterministic simulation testing (DST) uses a state space exploration process similar to a model checker, but it tests your actual code, not a model. A simulation automatically runs through a large number of randomized executions. Network communication, I/O and clock timing are replaced with mocks that let the simulator control the exact order in which things happen, including timings and failure scenarios. If a test fails, it can be rerun, since the simulator knows the exact order of operations that triggered the failure, unlike fault injection.

DST requires the simulator to control all sources of nondeterminism, such as network delays or thread scheduling. Three strategies are common. Application-level: FoundationDB is built on an asynchronous communication library called Flow, which provides a point to inject a deterministic network simulation; TigerBeetle models its state as a state machine with all mutations in a single event loop, combined with mock deterministic primitives such as clocks. Runtime-level: a single-threaded runtime forces asynchronous code to run sequentially; FrostDB patches Go’s runtime to execute goroutines sequentially, and Rust’s MadSim provides deterministic implementations of Tokio’s asynchronous runtime API, Amazon’s S3 library, Kafka’s Rust library and others. Machine-level: tools such as Antithesis build a custom hypervisor that replaces normally nondeterministic operations with deterministic ones, from clocks to network and storage.

DST offers more than replayability: Antithesis branches a test execution into multiple subexecutions when it discovers less common behavior, and because deterministic tests use mocked clocks and network calls, they can run faster than wall clock time. TigerBeetle’s time abstraction simulates network latency and timeouts without actually taking the full length of time.

Same steps, same order, same result

Yuki, Olu and Zainab each bake from the same recipe card in three different kitchens. As long as every step is exact, “add 50 g of sugar,” the three cakes are identical. Then a step says “add sugar to taste,” and the cakes come out different, with nobody having made a mistake.

Nondeterminism is behind every problem in this chapter, so removing it is powerful. State machine replication sends the same log of transactions, in the same order, to every replica, and each replica executes it independently. If apply() is deterministic, every replica ends in the same state. It’s the idea behind statement-based replication and serial execution with stored procedures, and behind replaying an event-sourcing log or a durable workflow. But nondeterminism hides in plain sight: reading the clock, a random number, a hash table whose iteration order varies, even whether you run out of memory.

What the book says

Nondeterminism is at the core of all the distributed systems challenges in this chapter: concurrency, network delay, process pauses, clock jumps and crashes all happen in unpredictable ways that vary from one run of a system to the next. Conversely, if you can make a system deterministic, that can hugely simplify things. Making things deterministic is a simple but powerful idea that arises again and again in distributed system design.

Besides deterministic simulation testing: a key advantage of event sourcing is that you can deterministically replay a log of events to reconstruct derived materialized views. Workflow engines rely on workflow definitions being deterministic to provide durable execution semantics. State machine replication replicates data by independently executing the same sequence of deterministic transactions on each replica; statement-based replication and serial transaction execution using stored procedures are two variants of that idea.

However, making code fully deterministic requires care. Even once you have removed all concurrency and replaced I/O, network communication, clocks and random number generators with deterministic simulations, elements of nondeterminism may remain. In some programming languages, the order in which you iterate over the elements of a hash table may be nondeterministic, and whether you run into a resource limit (memory allocation failure, stack overflow) is also nondeterministic.

Three things that go wrong

From the book’s summary.

The network

Any packet may be lost or arbitrarily delayed, and so may its reply. If you don’t hear back, you have no idea whether the message got through.

The clock

A node’s clock can be far out of sync with the others, can jump forward or back, and rarely tells you how wrong it might be.

The process

A process can pause for a long time at any point, be declared dead by the others, and come back to life without realizing it was ever gone.

So: ask a quorum

There is no shared memory and no common knowledge. Detection rests on timeouts, and big decisions need votes from several nodes, never one node’s judgment.

The book’s conclusion: partial failure is the defining characteristic of distributed systems. If a problem fits on one machine, keeping it there is generally worth it. But fault tolerance and low latency for users far apart can’t be had from a single node, and a distributed system can in principle keep running forever, because every fault and every bit of maintenance is handled one node at a time. Unreliable networks, clocks and processes aren’t laws of nature: bounded delays and hard real-time are possible, just expensive, so most systems choose cheap and unreliable.

Words to know

Grown-up words, in plain language.

partial failure
Some parts of the system are broken while others work fine, and which ones changes from moment to moment.
nondeterministic
The same action can succeed one time and fail the next, for reasons you can’t see.
shared-nothing
Machines with their own memory and disk that can only talk over the network.
asynchronous packet network
A network that promises nothing about when, or whether, a packet arrives. Ethernet and the internet are like this.
timeout
Giving up waiting after some time and assuming the reply isn’t coming. You still don’t know what happened.
congestion control
TCP working out how fast it may send without overloading the network or the receiver. Also flow control or backpressure.
network partition
Part of the network cut off from the rest. Also netsplit. Nothing to do with partitioning (sharding) data.
unbounded delay
No upper limit on how long a packet or a request may take.
cascading failure
Declaring a slow node dead moves its load onto others, which slow down and get declared dead too.
network congestion
A packet waiting in a switch queue for its turn on a busy link.
noisy neighbor
Another customer on shared hardware whose heavy use makes your delays jump around.
jitter
How much response times vary.
Phi Accrual failure detector
A failure detector that keeps measuring response times and adjusts its suspicion to what it sees. Used in Akka and Cassandra.
circuit switching
Reserving a fixed slice of bandwidth along the whole route for one call, as the telephone network does.
packet switching
Every packet competes for whatever bandwidth is free right now, as Ethernet and IP do.
bounded delay
A known maximum end-to-end latency, which a synchronous network can promise.
quality of service (QoS)
Prioritizing and scheduling packets and rate-limiting senders, to emulate circuits on a packet network.
time-of-day clock
Wall-clock time since the epoch. Synchronized by NTP, and able to jump backward.
monotonic clock
A stopwatch that only moves forward. Good for durations; its absolute value means nothing.
NTP
Network Time Protocol: setting a computer’s clock from the time reported by a group of servers.
clock drift
A quartz clock running faster or slower than it should. Google assumes up to 200 ppm.
slewing
NTP nudging the clock’s rate (by up to 0.05%) instead of making it jump.
leap second smearing
Spreading a leap second’s adjustment over a whole day so no minute has 61 seconds.
last write wins (LWW)
Keep the write with the greatest timestamp and throw the rest away.
logical clock
A counter that orders events (which came first) without measuring time.
physical clock
A clock that measures real elapsed time: time-of-day and monotonic clocks.
confidence interval
A clock reading as a range, [earliest, latest], instead of a single point. TrueTime and ClockBound report it.
commit wait
Spanner waiting out the clock uncertainty before committing, so later transactions get later timestamps.
lease
A lock with a timeout. Only one node holds it, and it must be renewed before it expires.
process pause
A thread stopped at an arbitrary line (by GC, a VM, the OS, the disk) and resumed later without noticing.
stop-the-world GC
A garbage collection that halts every running thread until it finishes.
steal time
CPU time a virtual machine loses while the hypervisor runs other VMs.
thrashing
An OS so short of memory that it spends most of its time swapping pages in and out.
hard real-time
Software that must respond by a deadline in all circumstances, like an airbag controller.
quorum
A vote among nodes. Usually an absolute majority, so there can never be two at once.
split brain
Two nodes both believing they are the one leader, or the one lock holder.
zombie
A former leaseholder that hasn’t found out it lost the lease and keeps acting.
fencing token
A number that grows every time a lease is granted; storage rejects writes with an older one.
Byzantine fault
A node that sends arbitrary, faulty or deliberately misleading messages.
system model
The written-down assumptions about timing and faults that an algorithm is designed and proved for.
partially synchronous
Behaves within known bounds most of the time, and occasionally exceeds them by any amount.
crash-recovery
Nodes crash and may come back; disk survives, memory does not.
limping node
A node that still answers health checks but is too slow to do real work. Also gray failure or fail-slow.
safety property
Something that, once violated, was violated at a point in time you can name, and can’t be undone.
liveness property
Something that may not hold yet but may still come true. It often contains the word “eventually.”
model checker
A tool that tries every state of a specification (TLA+, Gallina, FizzBee) to check its invariants.
fault injection
Deliberately crashing, pausing and cutting off parts of a running system to see how it copes.
chaos engineering
Fault injection in production, made popular by Netflix’s Chaos Monkey.
deterministic simulation testing
Running the real code with a mocked network, disk and clock, so a seed reproduces every run exactly.
