Every app is a little town where data gets made, stored and looked at. Building that town means choosing between good options that each cost something.

Opening · data-intensive applications

An app is a box of building blocks

Every time you use an app, you read data that is already stored and you make new data. A shoe shop app reads prices and writes your order. When the hardest part of building an app is the data itself — how much there is, how it changes, keeping it right when things fail — we call the app data-intensive.

Nobody builds that from nothing. Apps are glued together from standard building blocks: a database to find things again later, a cache to remember an expensive answer, a search index to find things by keyword, stream processing to react the moment something happens, and batch processing to crunch a big pile of data now and then.

Try it: press Send next job and watch which block catches it. Then tap a block to unplug it and send the same job again. With no block to help, the plain app code has to do the work — slowly, or not at all.

What the book says

An application is data-intensive if data management is one of the primary challenges in developing it. In compute-intensive systems the challenge is parallelizing a very large computation; in data-intensive ones it is storing and processing large data volumes, managing changes to data, ensuring consistency in the face of failures and concurrency, and keeping services highly available.

Such applications are built from standard building blocks: databases (store data so it can be found again later), caches (remember the result of an expensive operation), search indexes (search by keyword or filter), stream processing (handle events and changes as soon as they occur) and batch processing (periodically crunch a large amount of accumulated data). Application code glues them together.

The hard part is choosing among many systems with different characteristics, and combining tools when one alone can't do the job. The book's stance: “no one approach is fundamentally better than others; everything has pros and cons.”

Different teams may want very different things from the same dataset, and those goals are often not spelled out, which leads to disagreement about the right approach.

Terminology · frontends and backends

The waiter who forgets everything

The app on your phone is the frontend. It sends requests over the internet to the backend: code running on a server, a bit like a waiter carrying orders to the kitchen.

Here’s the funny part: that waiter is stateless. As soon as it finishes a request, it forgets all about it. Anything that has to be remembered must be kept somewhere else — on your phone, or in the backend’s database.

Your phone only ever looks after your data. The backend looks after everyone’s. That’s why the hard data problems live in the backend.

Try it: order something, then ask “What did I order?” from the phone and from the laptop. Then switch Keep it in to Phone or Nowhere and try again. Follow the lit line in the code underneath.

What the book says

For web applications, client-side code running in the browser is the frontend; server-side code that handles user requests is the backend. Mobile apps are similar to frontends. A frontend handles only one user's data, whereas the backend manages data on behalf of all the users — so the greatest data infrastructure challenges commonly lie in the backend.

A backend service is often reached via HTTP (or sometimes WebSocket). It consists of application code that reads and writes one or more databases and sometimes caches or message queues: together, data infrastructure.

The application code is often stateless: when it finishes one HTTP request, it forgets everything about it. Anything that must persist from one request to the next is stored either on the client or in the server-side data infrastructure.

Operational vs analytical · who works with data

Same data, very different jobs

In a supermarket company, backend engineers build the services that read and change data as customers shop. Business analysts write reports that help managers decide what to do next. Data scientists dig for new insights and build features such as “people who bought X also bought Y.”

Analysts and data scientists both look at data that others created, and they don’t change it. So the data splits into two worlds: operational systems, where data is created and changed, and analytical systems, which hold a read-only copy. Data engineers build the bridge between them, and analytics engineers reshape the copy so it’s easier to use.

Try it: pick a person and press Do their job. Then pick the analyst and press Edit a sale — what happens when someone tries to change the read-only copy?

What the book says

Backend engineers build services that handle requests for reading and updating data, for external users or other parts of the organization. Business analysts generate reports about the organization's activities to help management decide (business intelligence, BI). Data scientists look for novel insights or create user-facing features enabled by data analysis and ML/AI: recommendations, risk scoring or spam filtering, ranking of search results.

Both analysts and data scientists perform analytics: they look at data that users and backend services generated, and they generally do not modify it (except perhaps to fix mistakes), although they might create derived datasets.

Operational systems are the backend services and data infrastructure where data is created; the application code both reads and modifies it. Analytical systems contain a read-only copy of that data, optimized for analytics.

Data engineers integrate the operational and analytical systems and take responsibility for the data infrastructure more widely. Analytics engineers model and transform data to make it more useful for analysts and data scientists.

Operational vs analytical · transaction processing and analytics

The cashier and the detective

A cashier deals with one customer at a time: find this product by its barcode, take one off the stock count, next! Each job finds a few records by their key — a point query. Tiny, fast, and there are lots of them. That’s OLTP: online transaction processing.

A detective — a business analyst — asks big questions: “What was each store’s revenue in January?” Answering means reading a huge number of records and adding them up into a count, sum or average. That’s analytics, or OLAP.

The cashier’s questions are fixed, built into the till. Shoppers aren’t allowed to type their own queries — they might peek at data that isn’t theirs, or write one so slow it jams the shop. The detective, on the other hand, may ask anything.

Try it: run each query and count how many rows it has to touch. Then, in the second machine, sort each card from the book’s Table 1-1 into the right column.

What the book says

A transaction once meant a commercial one: a sale, an order, a salary payment. The word stuck for a group of reads and writes that form a logical unit; this chapter uses it loosely for low-latency reads and writes.

An operational system typically looks up a small number of records by a key, a point query, and inserts, updates or deletes records based on user input. Because these applications are interactive, the pattern is called online transaction processing (OLTP). An analytical query scans a huge number of records and calculates aggregate statistics such as count, sum or average: online analytical processing (OLAP).

Table 1-1 contrasts them: point queries vs aggregates over many records; create, update and delete individual records vs bulk import (ETL) or event stream; fixed queries predefined by the application vs ad-hoc exploration; lots of small queries vs few complex ones; latest state vs history of events; gigabytes to terabytes vs terabytes to petabytes.

OLTP users generally can't run custom SQL: they could read or modify data they have no permission to access, or write expensive queries that hurt other users. Analysts can write arbitrary SQL or use tools such as Tableau, Looker or Microsoft Power BI. Product analytics or real-time analytics systems (Pinot, Druid, ClickHouse) embed analytical workloads in user-facing products and are optimized for low-latency queries.

Operational vs analytical · data warehousing

Give the detective a copy

A big company runs dozens of operational systems: the checkout tills, the website, the stock room, the delivery vans. Each has its own team and its own way of storing things.

Letting the detective query those systems directly goes wrong in four ways. The data is scattered across silos, so one question can’t combine them. Their layout suits cashiers, not detectives. A giant scan slows the till for everyone. And some sit behind a locked door for security.

So companies keep a separate copy for analysis: a data warehouse. Getting data in is ETL — Extract it, Transform it into one tidy shape, Load it. Do the last two the other way round and it’s ELT.

Try it: in the first machine, choose Both, one DB and watch the queue at the till grow, then Add warehouse. In the second, press Step to walk three messy sources through ETL and see their rows come out tidy.

What the book says

In the late 1980s and early 1990s companies began running analytics on a separate database, the data warehouse, instead of their OLTP systems. A large enterprise may have dozens or hundreds of OLTP systems, each complex and maintained by its own team.

Querying them directly is undesirable: data is spread across systems (data silos); OLTP schemas and layouts suit analytics less well; analytical queries can be expensive and would impact performance for other users; and OLTP systems may sit in a separate network for security or compliance reasons.

Data is extracted (a periodic dump or a continuous stream of updates), transformed into an analysis-friendly schema, cleaned up and loaded: extract–transform–load (ETL). Transforming inside the warehouse after loading gives ELT. Sources can be external SaaS products (CRM, email marketing, credit card processing) reachable only through the vendor's API, often via connectors such as Fivetran, Singer or Airbyte.

HTAP systems aim to do OLTP and analytics in one system, but many are an OLTP system coupled with a separate analytical one behind a common interface. HTAP doesn't replace warehouses: each operational system tends to have its own database, while an enterprise usually has a single warehouse. The greater the scale, the more specialized systems tend to become.

Operational vs analytical · from data warehouse to data lake

Tidy shelves, or a big raw lake?

A warehouse is a set of neat tables you query with SQL. Perfect for the analyst’s reports. But data scientists want other things: to turn rows into lists of numbers that train a machine-learning model, to read thousands of product reviews and tell happy from angry, to look at photos. That’s hard to do in SQL.

So companies also keep a data lake: one big store of files, in any format, with no fixed shape. Reviews, photos, sensor readings, table dumps — all of it goes in raw, and it’s cheap. Each person later cooks the raw data the way they need it. People call this the sushi principle: raw data is better.

Try it: with Warehouse chosen, press Send next item until every kind of data has tried to get in — some won’t fit. Switch to Data lake and send them again. Then press Two cooks to see the analyst and the data scientist make different dishes from the same raw files.

What the book says

A warehouse often uses a relational model queried through SQL. That suits business analysts but less so data scientists: feature engineering (turning rows into vectors or matrices of numerical values, called features, for an ML model) commonly needs custom code that is hard to express in SQL; so does NLP on text such as product reviews, or computer vision on photos.

Many data scientists prefer Python libraries such as Pandas and scikit-learn, statistical languages such as R, and distributed frameworks such as Spark.

A data lake is a centralized repository holding a copy of any data that might be useful for analysis. Unlike a warehouse it simply contains files, without imposing a file format, data model or schema: Avro or Parquet records, text, images, videos, sensor readings, feature vectors, genome sequences. It is often cheaper too, because it can use object stores.

ETL has been generalized to data pipelines, and the lake may be an intermediate stop on the way to the warehouse. Keeping data raw lets each consumer transform it to suit its needs — the sushi principle: “raw data is better”.

Operational vs analytical · beyond the data lake

Catch the thief before tomorrow’s report

If your analysis reads files, you rerun it now and then — say, every night. That’s fine for a sales report. It’s too slow for a stolen credit card: by tomorrow morning the thief has gone on a spree.

More and more, analytics also reads streams of events: each purchase flows in the moment it happens, so the system can spot something fishy and block it within seconds.

And sometimes the answer travels back the other way. A model trained on the analytics side — “people who bought X also bought Y” — is sent back into the live shop to make suggestions. That’s reverse ETL.

Try it: with Nightly files chosen, press Thief strikes and count the money lost. Try again with Event stream. Then switch to Reverse ETL and press Train & ship model.

What the book says

As analytics practices have matured, organizations pay more attention to the management and operations of analytical systems and data pipelines (as in the DataOps Manifesto), driven partly by governance, privacy and compliance with regulations such as the GDPR and the CCPA.

Data for analytics is increasingly available as streams of events, not only files and relational tables. File-based analysis can be rerun periodically (e.g., daily); stream processing lets analytical systems respond in seconds — valuable, for example, to identify and block potentially fraudulent or abusive activity.

Sometimes the outputs of analytical systems are made available to operational systems: reverse ETL. An ML model trained in an analytical system may be deployed to production to generate recommendations for end users, using tools such as TFX, Kubeflow or MLflow.

Operational vs analytical · systems of record and derived data

The scorebook and its copies

Picture a class game. The teacher’s scorebook is the one true record: the system of record. A new point is written there first, and whenever it disagrees with anything else, the scorebook wins.

The leaderboard on the wall, the total on the whiteboard and the sticky note with Ben’s score are derived data: copies made from the scorebook so people can read things faster. The sticky note is a cache — if it’s there, read it; if not, go and look in the scorebook.

A notebook isn’t a scorebook by nature. It’s a scorebook because of how the class uses it. Databases are the same.

Try it: press Read Ben’s score twice and watch the code. Give Ben a point. Spill juice on the leaderboard, then Rebuild copies. Finally, spill juice on the scorebook. Can you rebuild that?

What the book says

A system of record, also known as a source of truth, holds the authoritative version of data. New data is written there first, each fact represented exactly once (typically normalized). If another system disagrees with it, the value in the system of record is by definition the correct one.

Derived data is the result of transforming or processing data from another system; if you lose it, you can re-create it from the original source. A cache is the classic example: serve from the cache if present, otherwise fall back to the underlying database. Denormalized values, indexes, materialized views, transformed representations and trained models also count.

Derived data is technically redundant, but often essential for good read performance, and several datasets can be derived from one source. Analytical systems are usually derived; operational services mix both.

Whether a database is one or the other depends not on the tool but on how you use it. When the original changes, derived data needs a process to update it, and many databases don't make integrating several systems easy (Chapter 11 covers data pipelines).

Cloud vs self-hosting · build or buy?

Cook from scratch, or order takeout?

With anything a company needs, the first question is: do it ourselves, or pay someone else? A handy rule: do the things that make you special yourself, and buy the ordinary ones. A bakery bakes its own bread — but it doesn’t build its own ovens.

For software there are two separate choices: who writes it, and who runs it. You can write and run your own; download ready-made software such as a database and run it on your own computers (self-hosting); rent computers in the cloud and run it there; or just use a cloud service someone else writes and runs.

Try it: tap each column of the chart to see who does which job. Then switch to Rule of thumb and decide build or buy for a bakery-delivery startup.

What the book says

Build or buy is a question of business priorities. A common rule of thumb: things that are a core competency or competitive advantage are done in-house, and non-core, routine or commonplace things are left to a vendor. Most companies don't fabricate their own CPUs; buying them is cheaper.

For software, the two decisions are who builds it and who deploys it (Figure 1-2). At one extreme is bespoke software written and run in-house; at the other, widely used cloud services or SaaS products implemented and operated by a vendor, used through a web interface or API.

In between is off-the-shelf software (open source or commercial) that you self-host — for example, MySQL on a server you control — either on premises (even when the server is in a rented datacenter rack) or on a cloud VM (infrastructure as a service, IaaS). Deployment tooling such as Kubernetes is beyond the book's scope.

Cloud vs self-hosting · pros and cons of cloud services

Cheaper? Easier? It depends

If you own your machines, you must buy enough for your busiest moment, and they sit idle the rest of the time. In the cloud you rent more when you’re busy and hand them back afterwards — but each hour costs more. Steady traffic and a team that knows the system? Owning is often cheaper. Spiky traffic, or nobody who knows how to run it? The cloud wins.

The biggest catch with a cloud service is that you’re not in control. When it breaks, all you can do is wait. When it lacks something, all you can do is ask nicely.

Try it: slide the traffic spikiness and flip the team switch. Then, in the second machine, throw each kind of trouble at the two shops and compare what each owner can do about it.

What the book says

Whether the cloud is cheaper and easier depends on your skills and workload. If you already know how to operate the system and your load is predictable, buying your own machines is often cheaper. If you don't, a cloud service is often easier and quicker than hiring and training staff.

A specialist provider may give better service through experience with many customers; running it yourself lets you tune it to your workload. The cloud is particularly valuable when load varies a lot — for example interactive analytical queries on a large dataset — because unused resources go back to the provider instead of sitting idle.

The biggest downside is that you have no control: you can only ask for missing features; you wait out outages; you lack the internals to debug; a shutdown, price rise or product change forces a migration, and without standard APIs there is vendor lock-in; sanctions may lock you out; and you must trust the provider to keep the data secure.

Many organizations take a hybrid approach. In-house systems remain necessary for older systems and specialist needs: high-frequency trading requires full control of the hardware.

Cloud native · layering of cloud services

Services built on services built on services

Old-style database software needs just an ordinary computer: processors, memory, a disk and a network. In the cloud you can rent exactly that, a virtual machine — but then looking after the software is still your job.

Cloud native systems are built differently: they stack services on top of other services. At the bottom, object storage keeps big files by spreading them over many machines, so no single disk fills up and a broken disk loses nothing. On top of that, a cloud data warehouse stores its tables in object storage. On top of that, other services use the warehouse.

Try it: in Object storage, press Upload a file a few times, then Break a disk — on both sides. Then switch to Pick a layer and choose where to build for each need.

What the book says

Cloud native describes an architecture designed to take advantage of cloud services. Systems designed this way from the ground up have shown better performance on the same hardware, faster recovery from failures, quick scaling of computing resources, and support for larger datasets.

Table 1-2: self-hosted OLTP — MySQL, PostgreSQL, MongoDB; cloud native OLTP — AWS Aurora, Azure SQL DB Hyperscale, Google Cloud Spanner. Self-hosted OLAP — Teradata, ClickHouse, Spark; cloud native OLAP — Snowflake, Google BigQuery, Azure Synapse Analytics.

Self-hosted software mostly uses generic resources: CPUs, RAM, a filesystem and an IP network. On IaaS it runs on VMs (instances) much like on physical computers, and you administer it yourself. Cloud native services build higher-level services on lower-level ones: object storage (Amazon S3, Azure Blob Storage, Cloudflare R2) has a more limited API than a filesystem but hides the machines, distributes data across many of them and loses no data when some fail; Snowflake relies on S3, and other services build upon Snowflake.

Higher-level abstractions tend to be oriented toward particular use cases. If your needs match one, it saves a lot of hassle; if no high-level system fits, building from lower-level components is the only option.

Cloud native · separation of storage and compute

Keep the toys in the toy box, not in your pockets

In an old-style setup, one computer does the thinking (compute) and keeps the data on its own disks (storage). Spare disks in the same box (RAID) protect against one disk dying — but not against the whole computer going away.

In the cloud, computers come and go: one breaks, or gets swapped for a bigger one. So cloud native systems treat a computer’s own disk as a scratch pad, and keep the real data in a separate storage service. A virtual disk is one halfway step: it pretends to be a disk, but every read crosses the network.

Many customers often share the same machines, too. That’s multitenancy: cheaper and easier to run, as long as one noisy customer can’t slow down everyone else.

Try it: pick where the data lives, then press Disk dies, Machine dies, Swap for bigger and Network hiccup. Then try Multitenant and turn isolation off.

What the book says

Traditionally, disk storage is regarded as durable, and RAID keeps copies on several disks attached to the same machine. Cloud native systems treat a VM's local disk more like an ephemeral cache: it becomes inaccessible if the instance fails, or if it is replaced with a bigger or smaller one on a different physical machine.

Virtual disks (Amazon EBS, Azure managed disks, persistent disks in Google Cloud) can be detached and attached to another instance. They emulate a block device (blocks typically 4 KiB) using a separate set of machines. Traditional disk-based software can run on them, but the emulation adds overhead, and every I/O is a network call, so the application becomes sensitive to network glitches.

Cloud native services instead build on storage services optimized for particular workloads: object stores such as S3 for fairly large files (hundreds of kilobytes to several gigabytes), with smaller values managed in a separate service. Storage and compute become disaggregated: to analyze data in S3, you run code elsewhere and move the data over the network.

Cloud native systems are often multitenant: several customers on shared hardware. That allows better utilization, easier scalability and management, but needs careful engineering so one customer's activity doesn't affect others' performance or security.

Cloud vs self-hosting · operations in the cloud era

The disk that keeps filling up

Someone has to keep the systems running smoothly: that’s operations. With your own machines, much of it is machine chores: watch the disks fill, order new ones before they run out, set up machines, install updates.

Cloud storage has no fixed-size disk to fill — you just pay for what you use. But the job doesn’t vanish, it changes. Now you watch the bill: find machines nobody uses any more, and know your quotas, the limits the cloud puts on you, before you hit them. Planning disk space turns into planning money.

Try it: in Own machines, press Start the week and keep the disk from filling — new disks take a day to arrive. Then switch to Cloud: shut down forgotten machines to save money, and see what happens when you launch one job too many.

What the book says

Server-side data infrastructure was traditionally run by database administrators (DBAs) or system administrators. The DevOps philosophy merges development and operations into shared teams; site reliability engineers (SREs) are Google's implementation of the idea.

For self-hosted systems, operations involve a lot of work on individual machines: capacity planning (monitoring disk space and adding disks before you run out), provisioning machines, moving services, installing OS patches. Cloud services hide the machines behind an API; cloud storage replaces fixed-size disks with metered billing.

DevOps/SRE emphasizes automation over one-off manual jobs, ephemeral VMs over long-running servers, frequent updates, learning from incidents, and preserving the organization's knowledge as people come and go.

Cloud customers still need operations: choosing services, integrating them, migrating between them. “Capacity planning becomes financial planning, and performance optimization becomes cost optimization.” Quotas must be known and planned for. Security, monitoring load and tracking down problems can't be fully outsourced: “the need for operations is as great as ever.”

A system that involves several machines communicating via a network is a distributed system; each participating process is a node.

Distributed vs single-node · problems with distributed systems

Every message can get lost

When you ask another computer to do something, the network might lose your message — or lose the answer. Either way you just wait, and then give up: a timeout. The nasty part: you can’t tell which one happened. Did the payment go through? Should you try again?

Calling another computer is also far slower than calling a function inside your own program. So with lots of data, it can be quicker to send the work to the data than the data to the work. And more computers isn’t always faster: sometimes one simple program on one computer beats a cluster with over a hundred processors.

When it’s slow, where is the problem? Tools for observability — like tracing, which records who called whom and how long it took — help you find out. That’s why the book’s advice is: don’t go distributed if one machine will do.

Try it: send a charge; when it times out, press Retry and check what the server did. Then find the slow service in the trace. Finally, slide the number of computers.

What the book says

Every request over the network may fail: the network may be interrupted, or the service overloaded or crashed, so any request may time out without a response. In that case “we don't know whether the service received the request, and simply retrying it might not be safe” (Chapter 9).

A call to another service is vastly slower than calling a function in the same process. With large volumes of data, it can be faster to bring the computation to the machine that already has the data. More nodes are not always faster: a simple single-threaded program on one computer can significantly beat a cluster with over 100 CPU cores.

Troubleshooting relies on observability: collecting data about execution so both high-level metrics and individual events can be analyzed. Tracing tools such as OpenTelemetry, Zipkin and Jaeger track which client called which server for which operation and how long each call took.

When each service has its own database, keeping data consistent across services becomes the application's problem; distributed transactions are rarely used with microservices. A single machine is often much simpler and cheaper, and with single-node databases such as DuckDB, SQLite and KùzuDB many workloads can now run on one node.

Distributed vs single-node · microservices and serverless

One giant robot, or a team of small robots?

You can build a whole app as one big program. Or you can split it into microservices: small programs that each do one job, each looked after by one team, each with its own database, all talking to each other through APIs.

Then teams can ship without waiting for each other — handy in a big company. The price: many more things to deploy and watch, testing needs the other services running, and changing an API can break whoever calls it. In a small company, it’s usually not worth it.

Serverless goes one step further: you hand the cloud a function, and it runs it only when a request arrives. You pay only while your code runs — but the first request after a quiet spell can be slow to start.

Try it: step through the four modes of the first machine — especially Shared DB (press Make the change, then Heavy search query) and Change an API (try it again with Check with API description). In the second, slide the traffic and press New day.

What the book says

The most common way to distribute a system is to divide it into clients and servers, usually talking HTTP; a process can be both. This was called service-oriented architecture (SOA), refined into microservices: each service has one well-defined purpose, exposes an API, and has one team responsible for it.

Advantages: services update independently, get the hardware they need, and can change their implementation behind the API. Each service usually has its own databases; sharing one would make the whole database structure part of the API, and one service's queries could hurt the others' performance.

Costs: testing a service needs the services it depends on; each needs deployment, resource adjustment, logs, monitoring and alerting (Kubernetes provides a foundation); and adding or removing API fields can break clients, often discovered late (OpenAPI and gRPC help). Microservices are “primarily a technical solution to a people problem” — valuable in a large company, likely unnecessary overhead in a small one.

Serverless, or function as a service (FaaS): the provider allocates and frees hardware automatically based on incoming requests, bringing metered billing to code execution. Providers impose time limits and limited runtimes, and functions may start slowly when first invoked. Each execution still runs on a server; BigQuery and various Kafka offerings use the word to mean autoscaling and billing by usage.

Distributed vs single-node · cloud computing vs supercomputing

The weather machine that stops for every broken part

A supercomputer crunches one giant science problem — tomorrow’s weather, say — on thousands of nodes. Every so often it saves its progress (a checkpoint). If one node breaks, it stops everything, fixes the node and starts again from the last save.

A cloud shop can’t do that: customers are shopping right now. So when a node breaks, the others carry on serving. Supercomputer nodes also trust each other and sit close together in one room with special wiring; cloud machines are shared by strangers, so they need locks, and they’re spread around the world.

Try it: press Run, then Break a node on both sides. Slide how often the supercomputer saves and see how much work it loses. Then look at the Network shape and Trust modes.

What the book says

High-performance computing (HPC), also known as supercomputing, is another way to build large-scale systems, with different priorities from cloud computing:

  • Supercomputers run computationally intensive scientific tasks — weather forecasting, climate modeling, molecular dynamics, complex optimization, partial differential equations. Clouds run online services and business data systems that serve users with high availability.
  • A supercomputer runs large batch jobs that checkpoint their state to disk from time to time. If a node fails, a common solution is to stop the entire cluster workload, repair the node and restart from the last checkpoint. Cloud services usually can't stop the whole cluster.
  • Supercomputer nodes communicate through shared memory and RDMA, with high bandwidth and low latency but assuming a high level of trust. Clouds shared by mutually untrusting organizations need resource isolation (e.g., VMs), encryption and authentication.
  • Cloud networks use IP and Ethernet in Clos topologies for high bisection bandwidth; supercomputers often use multidimensional meshes and toruses suited to known communication patterns. Clouds span geographic regions; supercomputers assume nodes are close together.

Data systems, law, and society

“Please forget me”

Data is often about people, and computer systems decide real things about them: who gets a loan, who gets a job interview, who gets suspected of a crime. Everyone who builds such systems shares the responsibility.

In Europe, a law called the GDPR gives people the right to be forgotten: delete my data when I ask. That sounds easy until you notice copies hiding everywhere — caches, warehouses, logs that are never supposed to change, even models that have learned from it.

Every piece of data you keep can leak, be demanded by a government, or put someone in danger. Sometimes the wisest choice is not to collect it at all: data minimization.

Try it: ask to delete Mia’s data after Collect everything, then after Collect only what’s needed. In the second machine, decide what to keep, then press Let a year pass.

What the book says

Since 2018 the GDPR has given residents of many European countries more control over their personal data; similar laws exist elsewhere, such as the CCPA, and the EU AI Act restricts how personal data may be used. Automated systems make decisions with profound consequences — loans, insurance, job interviews, suspicion of crime — and everyone who works on them shares responsibility for their ethical impact.

The GDPR grants the right to have data erased on request (the right to be forgotten). But many systems rely on immutable constructs such as append-only logs, and data may already be in derived datasets such as ML training data. The regulation deliberately does not mandate particular technologies, so there are no clear guidelines on what counts as compliant.

The cost of storage goes beyond the bill: liability and reputational damage if data leaks, legal costs and fines, governments compelling companies to hand data over, and real safety risks for users when data could reveal criminalized behavior — even a log of IP addresses indicates approximate location.

Data minimization (the German term is Datensparsamkeit) runs counter to the big-data habit of storing everything speculatively, but fits the GDPR: personal data only for a specified, explicit purpose, not used for any other, and not kept longer than necessary. Payment processors must meet PCI standards and many buyers require SOC Type 2 from vendors, both checked by independent auditors.

The seesaws from this chapter

Neither side is “right.” Each one wins in a different situation.

Operational (OLTP)

Many tiny reads and writes for users, right now

vs

Analytical (OLAP)

Few huge scans that summarize history

Data warehouse

Cleaned, organized tables, ready for SQL

vs

Data lake

Raw files of any shape, flexible and cheap

System of record

Each fact once; the one that wins any argument

vs

Derived data

Redundant copies that make reads fast and can be rebuilt

Self-hosting

Control and tuning; cheap for steady load if you have the skills

vs

Cloud services

Scales up and down, less work — but less control and lock-in

Storage + compute together

One machine, local disks, simple

vs

Disaggregated

Machines come and go; data waits safely in storage, over the network

Single node

Simple, fast, easy to debug

vs

Distributed

Survives failures and grows big, but messages get lost

One app

Few moving parts, best for small teams

vs

Microservices

Teams work independently, with much more to operate

Store everything

Might be useful someday

vs

Data minimization

Less risk, easier to follow privacy laws

The book’s summary: in some situations you can’t avoid going distributed, but it’s wise not to rush into it if one machine will do — and a system’s design is shaped not only by what the business wants, but by the rights of the people whose data it holds.

Words to know

Grown-up words, in plain language.

data-intensive
An app whose hardest problem is the data itself: how much there is, how it changes, and keeping it right.
frontend / backend
The app you touch, and the server code it talks to.
stateless
Forgets everything after each request, so anything to remember goes in a database or on the client.
operational system
Where data is created and changed as users do things.
analytical system
A read-only copy of the data, arranged for big questions.
point query
Fetch one record (or a few) by its key.
OLTP
Lots of small, fast lookups and changes, like a cashier.
OLAP / analytics
Big questions that scan lots of records and add them up, like a detective.
data warehouse
A separate copy of company data, cleaned and organized for analysis with SQL.
ETL / ELT
Extract, transform, load: copy data out, tidy it, put it in the warehouse. ELT tidies after loading.
data silo
Data locked inside one system, hard to combine with the rest.
data lake
One big store of raw files of any kind.
reverse ETL
Sending results from the analytics side back into the live app.
system of record
The one official version of the truth.
derived data
Copies built from the truth (caches, indexes, models) that can be rebuilt.
self-hosting
Running ready-made software on machines you control.
IaaS
Renting virtual machines from a cloud and running your own software on them.
vendor lock-in
When switching to another provider is so hard you’re stuck.
cloud native
Built from the start on top of other cloud services.
object storage
A cloud service that keeps big files spread over many machines (like Amazon S3).
disaggregation
Keeping storage and computing on separate machines.
multitenant
Many customers sharing the same machines, kept safely apart.
DevOps / SRE
Teams that both build software and keep it running, with lots of automation.
node
One computer (process) in a distributed system.
timeout
Giving up on waiting for an answer — without knowing what happened.
observability
Recording what a system does so you can find out why it’s slow or broken.
microservices
An app split into small services, each doing one job for one team.
serverless
Code the cloud runs only when needed. You pay per run.
checkpoint
A saved snapshot of a long job, to restart from after a failure.
data minimization
Collect only what you truly need, and delete it when you’re done.
