Trade-Offs in Data Systems Architecture

Every app is a little town where data gets made, stored, and looked at. Building that town means picking between good options that each cost something.

Warm-up · where data lives

The waiter who forgets everything

The app on your phone is the frontend. It sends requests over the internet to the backend: code running on a server, a bit like a waiter taking orders to the kitchen.

Here's the funny part: that waiter is stateless. As soon as it finishes a request, it forgets all about it. Anything that has to be remembered must be written into a database.

Try it: order something, then ask “What did I order?” Next, switch saving Off and try again.

What the book says

Client-side code is the frontend. Server-side code that handles requests is the backend, usually reached over HTTP.

Application code is often stateless: information that must last from one request to the next lives on the client or in the server's data infrastructure (databases, caches, message queues).

A frontend handles one user's data. The backend handles data for all users, which is where most of the hard problems are.

Big idea 1 · operational vs analytical

The cashier and the detective

A cashier works on one customer at a time: find this item, change that one number, next! Those are tiny, quick jobs, and there are lots of them. That's OLTP.

A detective (a business analyst) asks big questions like “How many bananas did we sell in January?” Answering means reading every record and adding them up. That's analytics, or OLAP.

Watch what happens when both work in the same database at the same time. The waiting line grows. So companies give the detective a separate copy: a data warehouse.

What the book says
  • Operational systems (OLTP): point queries that fetch records by key; create, update, and delete individual records; fixed queries built into the app; data shows the latest state; gigabytes to terabytes.
  • Analytical systems (OLAP): aggregate over huge numbers of records; bulk import (ETL) or event streams; ad-hoc queries by analysts; data is a history of events; terabytes to petabytes.

Analysts avoid querying OLTP systems directly: data is spread across silos, OLTP schemas don't suit analytics, big queries hurt performance for other users, and the systems may sit behind security boundaries.

HTAP systems try to do both in one system. Product analytics (Pinot, Druid, ClickHouse) put analytics inside user-facing features.

Big idea 2 · moving data for analysis

Tidy warehouse or big messy lake?

A company has lots of little systems: checkout, website, inventory. Each one stores data in its own shape. To study everything together, you copy it all to one place.

ETL means Extract (copy it out), Transform (clean it into neat blocks), and Load (put it on the warehouse shelves). ELT loads first and cleans later.

A data lake skips the tidying. Every file goes in raw, in any shape, because data scientists like to clean it their own way. People call that the “sushi principle”: raw data is better.

What the book says

A data warehouse is a separate database holding a read-only copy of data from many OLTP systems. Analysts can query it as much as they like without slowing operations. It usually uses a relational model and SQL.

A data lake is a central store of files with no fixed format or schema: Avro or Parquet records, text, images, sensor readings, feature vectors. It's often cheaper because it can sit on object storage.

ETL has grown into general data pipelines. When analytics results flow back into operational systems (for example, an ML recommendation model), that's called reverse ETL.

Big idea 3 · where the truth lives

The scorebook and its copies

Picture a class game. The teacher's scorebook is the one true record: the system of record. Whenever it and anything else disagree, the scorebook wins.

The leaderboard on the wall, the total on the whiteboard, and the sticky note with Ben's score are derived data. They're copies made from the scorebook so people can read things faster.

Try it: spill juice on the leaderboard, then rebuild it. Next, spill juice on the scorebook. Can you rebuild that?

What the book says

System of record (also called the source of truth): holds the authoritative version. New data is written here first, each fact once, usually normalized.

Derived data systems: caches, indexes, materialized views, denormalized values, trained models. It's technically redundant, but it's often essential for fast reads. If you lose it, you can re-create it from the source.

A database isn't one kind or the other by nature. It depends on how you use it. Being clear about what is derived from what makes a messy architecture easier to follow.

Big idea 4 · build or buy?

Cook at home, or order takeout?

You can run your own database on your own computers, like cooking at home: total control, but you do all the dishes. Or you can pay a cloud service to run it for you, like takeout: easy, but you eat whatever's on the menu.

Who does the work?

Which is cheaper? It depends on your traffic

If you own the machines, you have to buy enough for your busiest moment, and they sit idle the rest of the day. In the cloud you can rent more when you're busy and give them back later. But each machine-hour costs more.

Slide the spikiness. Steady traffic favors your own machines. Spiky traffic favors the cloud. If you'd have to hire experts first, owning your machines gets much more expensive.

What the book says

Self-hosting is often cheaper if you already know how to run the system and your load is predictable. The cloud shines when load varies a lot, as it does for analytical queries.

The downsides of the cloud come from lack of control: you can't add missing features, you wait out outages, you can't see internals when debugging, you risk vendor lock-in and price changes, sanctions can cut you off, and you have to trust the provider with your data.

Operations doesn't go away. It shifts: capacity planning becomes financial planning, and performance tuning becomes cost tuning.

Big idea 5 · cloud native

Keep the toys in the toy box, not in your pockets

In an old-style setup, one computer does the thinking (compute) and keeps the data on its own disk (storage). If that computer breaks, the data is stuck inside it.

Cloud-native systems split the two. The data sits in a shared, super-safe “toy box” called object storage. Computers that come and go borrow data from it.

Try it: crash a machine on each side, then add more compute for a busy day.

What the book says

Traditionally, disks were treated as durable, with RAID keeping copies within one machine. In the cloud, a VM's local disk is an ephemeral cache: it disappears if the instance fails or gets replaced.

Virtual block devices (like EBS) imitate disks over the network, but that adds overhead and every I/O becomes a network call. Cloud-native databases use dedicated services instead: object stores such as S3 for big blocks, and separate services for small values.

This is disaggregation, or the separation of storage and compute. Cloud systems are also often multitenant: many customers share hardware, which takes care to isolate.

Big idea 6 · distributed vs single-node

One kitchen, or many kitchens that have to phone each other?

A distributed system is a group of computers (called nodes) working together over a network. There are good reasons to use one:

users on many deviceskeep working if one breakstoo much data for one machinebe close to users worldwidegrow & shrink with demandspecial hardware (GPUs)laws on where data livesrun where power is green

But every computer you add has to talk to the others, and messages can go missing. Sometimes one simple computer beats a whole crowd of them.

What the book says

Calls over the network are far slower than function calls, and any request might time out. When that happens, you don't know whether it was processed, so retrying may not be safe (Chapter 9).

A simple single-threaded program can outperform a cluster with more than 100 CPU cores. Tools like DuckDB and SQLite let many workloads run on one node.

Debugging a distributed system needs observability: tracing tools such as OpenTelemetry, Zipkin, and Jaeger. Keeping data consistent across services becomes the application's problem.

Supercomputers (HPC) are different: when a node fails they often stop the whole job and restart from a checkpoint, while cloud services have to keep serving users.

Big idea 7 · splitting up the app

One giant robot, or a team of small robots?

You can build the whole app as one big program. Or you can build microservices: small programs that each do one job, each owned by one team, each with its own database, and all talking through APIs.

Microservices let teams work without waiting for one another. But now there are many more things to deploy, monitor, and keep working together.

Serverless goes further: you hand the cloud a function, and it runs only when a request arrives. You pay only while it runs, though a “cold” function can be slow to wake up.

What the book says

Microservices are “primarily a technical solution to a people problem”: they let teams make progress independently. That helps in a big company but is often unnecessary overhead in a small one.

Services shouldn't share a database. Otherwise the whole database schema becomes part of the API and gets hard to change. Changing an API can break its clients, and standards like OpenAPI and gRPC help with that.

Serverless / FaaS brings metered billing to running code, with limits on execution time and possible slow cold starts. It still runs on servers, just not ones you manage.

Big idea 8 · data, law & society

“Please forget me”

Data is often about people. In Europe, a law called the GDPR gives people the right to be forgotten: a company must delete their data when they ask.

That sounds easy until you notice copies hiding everywhere: caches, search indexes, warehouses, append-only logs that are never supposed to change, even AI models that learned from the data.

Try both: ask to delete Mia's data after collecting everything, then again after collecting only what's needed. The second way, called data minimization, leaves fewer places to clean and less to leak.

What the book says

Regulations like the GDPR, the CCPA, and the EU AI Act shape how personal data can be used. Many systems rely on immutable, append-only logs, which makes deleting data from the middle of one hard. So does removing data from derived datasets and ML training data.

The cost of storing data isn't just the storage bill. It also includes the risk of leaks, fines, government demands, and real danger to users when data could reveal criminalized behavior.

Data minimization (German: Datensparsamkeit) means collecting only for a specific purpose and not keeping data longer than needed. That runs against the “store everything” big-data habit.

Words to know

Grown-up words, in plain language.

data-intensive
An app whose hardest problem is the data itself: how much there is, how it changes, and keeping it safe.
frontend / backend
The app you touch, and the server code it talks to.
stateless
Forgets everything after each request, so memory has to go in a database.
OLTP
Lots of small, fast lookups and changes, like a cashier.
OLAP / analytics
Big questions that scan lots of data, like a detective.
point query
Fetch one record by its key (its ID).
data warehouse
A separate, read-only copy of company data, organized for analysis.
ETL / ELT
Extract, transform, load: copy data out, clean it, and put it in the warehouse. ELT does the last two in the other order.
data lake
A big pile of raw files of any kind.
system of record
The one official version of the truth.
derived data
Copies built from the truth (caches, indexes) that can be rebuilt.
cache
A quick-to-reach copy of something that's slow to get.
cloud native
Built from the start to use cloud services like object storage.
object storage
A huge, safe “toy box” for files (like Amazon S3).
multitenant
Many customers sharing the same machines, kept apart safely.
vendor lock-in
When switching to another provider is so hard you're stuck.
node
One computer (process) in a distributed system.
microservices
An app split into small services, each doing one job.
serverless
Code the cloud runs only when needed. You pay per run.
data minimization
Collect only what you truly need, and delete it when you're done.
