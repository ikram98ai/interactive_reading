Batch Processing

Some questions are too big to answer while somebody waits. So you gather a mountain of data, run one big job over all of it, and come back later for a small, tidy answer.

Big idea 1 · what a batch job is

If the answer comes out wrong, run it again

Most of this book has been about online systems: you ask, and an answer comes back as fast as possible. But some work is too big for that. Adding up a whole week of house points for the whole school is not something you do while a kid stands waiting at your desk.

A batch job takes a pile of input, reads it without ever changing it, and builds its output from scratch. It may run for minutes, hours or even days, often on a schedule — say, every night. Nobody measures how quickly one answer comes back. They measure throughput: how much data gets crunched per hour.

Here is the lovely part. One day somebody “improves” teacher Imani's adding-up code, and every total comes out ten times too big. No panic: the points log was never touched. Put the old code back, run the job again, and the totals are right. A program that scribbles straight into the live totals can't do that — the wrong numbers are already mixed in.

Try it: run the job. Deploy the buggy code and run again. Roll the code back and run once more. Then switch to “Change totals in place” and do exactly the same three things.

What the book says

Online systems are measured by response time and need high availability. Batch processing jobs (sometimes called offline systems) take read-only input and produce output that is generated from scratch on every run, so the output is derived from the input. The main performance measure is throughput. Jobs may run for minutes, hours or days, and are often scheduled periodically.

Treating inputs as immutable and avoiding side effects gives human fault tolerance: roll back buggy code and rerun, or simply switch back to the old output directory. Most object stores and open table formats support this as time travel. Most databases with read/write transactions don't have this property — rolling back the code does nothing to fix bad data already written. This minimizing of irreversibility speeds up feature development. The same input files can also feed other jobs, such as monitoring jobs that compare a run's output with the previous run.

The downsides: with most frameworks the output can be used by other jobs only after the whole job finishes, and any change to the input — even a single byte — means reprocessing the entire input. The alternative, stream processing, is the subject of Chapter 12.

Modern batch processing was shaped by MapReduce, published by Google in 2004 and implemented in Hadoop, CouchDB and MongoDB. It is now largely obsolete and no longer used at Google; batch work today is more often done with Spark, Flink or data warehouse query engines. Workflow schedulers such as Oozie and Azkaban have given way to Airflow, Dagster and Prefect; storage is shifting from distributed filesystems (HDFS, GlusterFS, CephFS) to object stores such as S3; and cloud warehouses like BigQuery and Snowflake blur the line between warehouse and batch processor.

Big idea 2 · batch processing with Unix tools

Six little tools holding hands

Mateo runs a website about animals. Every time somebody opens a page, the web server adds one line to a log file: who asked, when, for which page, and how it went. After a while that is a very long file. Mateo wants to know: which five pages are the most popular?

He doesn't write a program. He chains six tiny tools together with the pipe sign |, so whatever one tool prints becomes the next tool's input:

cat /var/log/nginx/access.log |
  awk '{print $7}' |
  sort             |
  uniq -c          |
  sort -r -n       |
  head -n 5

Read the file, keep only the 7th word of each line (the page), sort, count the repeats, sort by the count, keep the top five. The clever bit is the first sort: uniq -c only notices repeats that are next to each other, and sorting is what puts them side by side.

Try it: step through the chain and watch ten log lines shrink into a report. Then press “Skip the first sort” and play again to see uniq get fooled. Switch to “Top visitors” to change one word of awk and get a different report.

What the book says

The example uses the NGINX default access log format: $remote_addr - $remote_user [$time_local] "$request" $status $body_bytes_sent "$http_referer" "$http_user_agent". Splitting a line on whitespace, the seventh field happens to be the requested URL.

sort makes a URL requested n times appear n times in a row; uniq -c collapses adjacent equal lines and prefixes a counter; sort -r -n orders by that number, largest first; head -n 5 keeps five lines. The chain processes gigabytes of logs in a matter of seconds and is easy to change: $7 !~ /\.css$/ {print $7} leaves out CSS files, {print $1} counts client IP addresses instead.

Many analyses take a few minutes with a mix of awk, sed, grep, sort, uniq and xargs, and they perform surprisingly well. The book also shows the same analysis as a short Python program with a hash table of counters; which you prefer is partly taste, but the execution flow is very different — that's the next scene.

Log parsing may look contrived, but it is a critical part of operations at many technology companies, from ad pipelines to payment processing, and it was a driving force behind MapReduce and the “big data” movement.

Big idea 3 · sorting versus in-memory aggregation

A tally sheet, or sorted piles on the floor?

There are two ways to count votes. The tally sheet: keep one line per name on your desk and add a stroke for every ballot. A million ballots is no problem — you only need as many lines as there are different names. A program with a hash table works like this, and the desk space it needs is called its working set.

But what if there are more names than lines on your desk? Then do it the other way: grab a handful of ballots, sort that handful, and lay it on the floor as a neat pile. Repeat. At the end, merge the piles by always taking the smallest top card. Equal names come out in a row, so one finger is enough to count them. The desk never holds more than a handful.

That's what Unix sort does. When the data won't fit in memory it spills sorted chunks to disk and merges them — reading and writing in long straight runs, which disks are good at.

Try it: run the tally with 3 different pages. Drag “Different pages” up to 8 and run again: the desk overflows. Now switch to “Sort, spill, merge” and run the very same input.

What the book says

The Python version keeps an in-memory hash table from URL to count; the Unix pipeline has no such table and relies on sorting a list in which repeated URLs simply appear repeatedly. Which is better depends on how many distinct URLs there are.

The working set — the memory a job needs random access to — depends only on the number of distinct URLs: a million log entries for one URL still need just one entry and one counter. For most small to mid-sized sites all distinct URLs fit in (say) 1 GB, and a hash table works fine, even on a laptop.

If the working set is larger than memory, sorting wins because it uses disks efficiently, on the same principle as log-structured storage: chunks are sorted in memory and written out as segment files, then several sorted segments are merged into a larger sorted file. Mergesort has sequential access patterns that perform well on disks.

GNU Coreutils sort automatically spills to disk for larger-than-memory datasets and parallelizes across CPU cores, so the simple chain scales to large datasets without running out of memory; the bottleneck is likely the rate at which the input can be read from disk. The real limitation of Unix tools is that they run on a single machine.

Big idea 4 · distributed filesystems and object stores

One giant file, living on many machines

A batch job's input is often far too big for one disk. A distributed filesystem chops every file into big blocks and spreads them over lots of ordinary machines. One service keeps the index card: which blocks make up which file, and where each block lives.

Ordinary machines break. So every block is copied onto several of them, and when one machine dies, each block it held still has a twin somewhere else. There's a bonus: the scheduler can send a task to any machine that already holds the block it needs, so the data doesn't have to travel at all.

An object store such as S3 is the newer way. You put a whole object under a key and get it back; you can't edit it in place. Storage and computers are kept apart. Every read crosses the network — but you can add or remove computers without touching the data.

Try it: click a machine to crash it. With 2 copies the file survives; press “Re-copy” to get back to full strength. Set copies to 1 and crash a machine again. Then switch to “Object store”, crash computers all you like, and run tasks.

What the book says

Batch frameworks are like distributed operating systems: they have a filesystem, a scheduler, and programs passing data to one another. A DFS mirrors a local filesystem's layers (block devices, page cache, filesystem, VFS). DFS blocks are much larger than local ones — HDFS defaults to 128 MB, JuiceFS and many object stores use 4 MB, ext4 uses 4,096 bytes — so there is less metadata and less seek overhead. A 900 MB file with 128 MB blocks has seven full blocks and one 4 MB block.

Each machine runs a daemon serving blocks (HDFS DataNodes, GlusterFS glusterfsd); a metadata service tracks where things are (Hadoop's NameNode; DeepSeek's 3FS keeps metadata in a key-value store such as FoundationDB). A DFS is shared-nothing on commodity hardware, unlike NAS and SAN appliances. Blocks are replicated, or protected by erasure coding such as Reed–Solomon codes — like RAID, but over an ordinary datacenter network. Replicas also let a scheduler run a task on any node holding its input.

Object stores (Amazon S3, Google Cloud Storage, Azure Blob Storage, OpenStack Swift) address objects by bucket and key, read with get and written with put. Objects are immutable once written (Azure Blob Storage and S3 Express One Zone support appends). There are no real directories — slashes are part of the key, a prefix listing behaves like a recursive ls -R, and empty directories can't exist. There are no hard links, symbolic links or locks, and renames are nonatomic: copy, then delete. S3's API is also spoken by MinIO, Cloudflare R2, Tigris, Backblaze B2 and others.

DFSs such as HDFS let a task run on the machine that stores its file, saving bandwidth. Object stores usually keep storage and computation separate: more bandwidth, but modern datacenter networks are fast, and CPU and memory can be scaled independently of storage.

Big idea 5 · distributed job orchestration

Who gets which machine?

On your laptop, the operating system decides which program gets the processor. In a cluster that is the work of an orchestrator. You hand it a job — “eight tasks, one core each, here's the code” — and its scheduler finds machines with room. A small helper on every machine starts the tasks and keeps sending a heartbeat: “still alive”.

Two things regularly spoil a task's day. A machine can crash. Or the scheduler can kill the task on purpose — preempt it — to make room for something more urgent. Cheap cloud machines work just like that: they're yours until somebody who pays more shows up.

Neither is a disaster, because a batch task has no side effects. Throw away its half-written output and run it again somewhere else. And only that one task — not the whole job.

Try it: submit the nightly report, then click a machine to crash it and watch its tasks get retried. Submit the urgent job while the cluster is full to see preemption. Then switch to “Restart the whole job”, crash a machine again, and compare the work thrown away.

What the book says

A job request names the number of tasks; the memory, CPU and disk each needs; a job identifier; credentials; input and output parameters; required hardware such as GPUs; and where the executable code lives. Orchestrators such as Kubernetes and Hadoop YARN run it with three parts: task executors on every node (YARN's NodeManager, Kubernetes's kubelet) that run tasks, send heartbeats and isolate tasks with Linux cgroups; a resource manager holding a global view of the cluster (state kept in ZooKeeper for YARN, etcd for Kubernetes); and a usually centralized scheduler. Application-specific subschedulers are called ApplicationMasters in YARN and operators in Kubernetes.

Scheduling balances fairness and efficiency. The book's puzzle: 160 cores, two jobs wanting 100 each. Run 80 tasks of each? Run one job completely and start the other only when 100 cores are free (gang scheduling) — leaving nodes idle, and risking deadlock? Just wait, and risk starvation? Or preempt running tasks, wasting their work? The general problem is NP-hard, so real schedulers use heuristics: FIFO, dominant resource fairness (DRF), priority queues, capacity or quota-based scheduling, and bin-packing.

Jobs usually form a workflow, a directed acyclic graph (DAG) in which one job's output is another's input. Per-job schedulers such as YARN's ResourceManager or Spark's built-in one don't manage that; workflow schedulers — Airflow, Dagster, Prefect — do, waiting until all of a job's inputs have completed successfully. Workflows of 50 to 100 jobs are common.

Low-priority tasks on spare capacity — spot instances on Amazon EC2, spot virtual machines on Azure, preemptible instances on Google Cloud — are cheap, and preemptions happen more often than hardware faults. Because tasks regenerate output from scratch, the system deletes the partial output and reschedules just that task; MapReduce and its successors keep parallel tasks independent so they can retry at the granularity of one task.

Big idea 6 · MapReduce and the shuffle

Map, shuffle, reduce

Now do the log-counting trick on a file so big that it lives in pieces on three machines. MapReduce is the Unix chain, spread out. Each piece of input gets its own mapper. It looks at one record at a time and writes down a key and a value — here, the page and the number 1. Mappers don't talk to each other and remember nothing between records.

Then comes the shuffle. All the /cats pairs must meet in one place, whichever mapper made them. Which place? Take a hash of the key, divide by the number of reducers, and the remainder decides. On the way the pairs are sorted, so equal keys arrive side by side. Despite its name, nothing about a shuffle is random.

Each reducer walks down its sorted list and adds up the run for each key — exactly what uniq -c did. You write only the mapper and the reducer. The sorting in between is done for you.

Try it: step through with 3 reducers, then pick 1 or 2 and watch where the pairs go. The number of mappers comes from the input; the number of reducers is your choice.

What the book says

One MapReduce job is four steps: (1) read input files and break them into records — files sit in HDFS or an object store, in formats such as Apache Parquet (columnar) or Apache Avro (row-based); (2) call the mapper to extract a key and value from each record, like awk '{print $7}'; (3) sort all key-value pairs by key — implicit, you never write it; (4) call the reducer over the sorted pairs, like uniq -c. A second sort, as in the log example, needs a second MapReduce job reading the first one's output.

The mapper is called once per record, may emit any number of pairs, and keeps no state between records. The reducer is called once per key with an iterator over that key's values. The idea comes from functional programming (Lisp's map and reduce/fold): with no mutable state, the framework may run calls in parallel and simply call them again elsewhere if a task fails.

A shuffle is a distributed sort whose input and output are both sharded. One map task runs per input shard; the number of reduce tasks is set by the job's author. Each mapper writes one sorted file per reducer on its local disk, choosing the file by a hash of the key; reducers copy their files from every mapper and merge them mergesort-style, so equal keys become consecutive. Each reducer writes one output file, and those files are the shards of the output dataset.

Raw MapReduce is laborious (joins must be written from scratch) and slow — its file-based I/O prevents pipelining. Shuffles live on in Spark, Flink, Daft, Dataflow and BigQuery, which keeps shuffle data in memory and uses external sorting services.

Big idea 7 · dataflow engines

Stop filing every half-finished answer

A real pipeline needs several rounds: tidy the log, count the views, rank the pages. With MapReduce every round is a separate job. Job one must write all its output into the distributed filesystem — several copies of every file — before job two may read a single line. It's a kitchen where each cook has to lock the half-made dish in a safe before the next cook may fetch it.

Dataflow engines such as Spark and Flink treat the whole workflow as one job. They know the entire recipe, so they hand results straight from one step to the next, start a step as soon as its input is ready, glue simple steps together, and sort only where sorting is needed. Only the final answer goes to the filesystem.

The catch: if a machine dies, half-finished results held in memory die with it. The engine remembers how they were made and computes them again. MapReduce just rereads its safely filed copy.

Try it: run the workflow both ways and compare the writes and the time. Then switch on “Crash a worker” and run both again.

What the book says

Spark and Flink, building on research systems such as Dryad and Nephele, handle an entire workflow as one job. Besides a low-level per-record API they offer operators such as join and group by, which need not alternate strictly between map and reduce.

Their advantages over MapReduce: expensive work such as sorting happens only where required; operators that don't change the sharding (map, filter) are combined into a single task; the scheduler sees all data dependencies and can make locality optimizations; intermediate state usually stays in memory or on local disk instead of being replicated to a DFS or object store; operators start as soon as their input is ready; and existing processes are reused, where MapReduce launches a new JVM for every task.

For faults, MapReduce always writes intermediate data back to the DFS and waits for it, which works even when preemption is common but means a lot of writes. Spark keeps intermediate data in memory (spilling to local disk), tracks how it was computed, and recomputes it if lost; Flink periodically checkpoints a snapshot of tasks.

Writing to a DFS between jobs does have a use: it decouples jobs so they can run at different times or be read by several teams. A Unix pipe, by contrast, has only a small in-memory buffer, and a full buffer makes the producer wait — a form of backpressure.

Big idea 8 · joins and grouping

Matching two giant lists without asking around

A website has two lists. One is a log of who looked at what: “u2 viewed /cats”. The other is the user database: “u2 was born in 2001”. A question like “are the cat pages more popular with younger or older people?” needs the two lists matched up, user by user. That's a join.

The slow way: for every single view, phone the user database and ask. With billions of views, that's billions of little phone calls.

The batch way uses the shuffle. Give both lists the same key — the user ID — and let the shuffle sort them into one list. Now each user's profile sits directly above that user's views. The reducer remembers one birth year, stamps it on the views below, forgets it, and moves on. No phone calls, and only one user in memory at a time.

Try it: play “Ask the database every time” and count the requests. Then play the sort-merge join.

What the book says

The book's example joins a log of activity events (clickstream data) with a database of user profiles — in star-schema terms, the fact table and one of its dimensions — assuming both are so large that they must be sharded.

One mapper goes over the events and emits the viewed URL keyed by user ID; another goes over the user database and emits the date of birth keyed by user ID. The shuffle brings all pairs with the same key to the same reducer. With a secondary sort, the reducer always sees the user record first, followed by that user's events in timestamp order.

The reducer stores the date of birth in a local variable and then iterates over the events, outputting each URL with the viewer's date of birth. It keeps only one user record in memory at a time and never makes a request over the network. This is a sort-merge join: mapper output is sorted by key, and reducers merge the sorted lists from both sides.

A following job can shuffle by URL and count views per age group — that is how group by and aggregation are built. Shuffling is the foundation for both joins and aggregations in most batch systems.

Big idea 9 · query languages and DataFrames

Say what you want, not how to get it

Writing mappers and reducers by hand is hard work. Today most batch jobs are written in SQL, or with a DataFrame — a table you change by calling functions such as filter and join. You describe what you want. A query optimizer decides how: which kind of join to use, and in which order to do things.

Order matters a lot. Priya asks: “Which pages did the chess-club kids look at?” That needs three tables. Join the big views table to every user first and you drag a big pile of rows through the pipeline, only to throw most of them away. Start with the tiny chess-club list and the pile stays small. Same answer, much less carrying.

An optimizer looks at the size of each input and picks the cheapest plan. Some tools run each step the moment you type it; others collect all your steps into a plan first — precisely so they can rearrange them.

Try it: run the query as written, then let the optimizer plan it. Now drag “Rows in views” down to 2 and watch the optimizer change its mind.

What the book says

With clusters of over 10,000 machines storing many petabytes, operating batch systems at scale is considered more or less solved, and attention has turned to the programming model. MapReduce, dataflow engines and cloud warehouses have all embraced SQL as the lingua franca; it needs less code and allows interactive, exploratory use by analysts, product managers, and finance teams.

Query engines such as Hive, Trino, Spark and Flink translate a query into a syntax tree and physical operators, and have cost-based optimizers that analyze the properties of join inputs, choose the most suitable join algorithm, and may even change the order of joins to minimize intermediate state. Niche languages remain: Apache Pig and the newer Morel, JSON languages like jq, JMESPath and JSONPath, and graph languages such as TinkerPop's Gremlin.

Batch systems and cloud warehouses are converging: batch frameworks speak SQL over columnar formats like Parquet, while warehouses adopted scheduling, fault-tolerance and shuffling techniques — and other models too (BigQuery's DataFrames library, Snowflake's Snowpark with Pandas). But iterative graph algorithms such as PageRank, complex ML, and multimodal AI data are hard to express in SQL; row-by-row computation suits columnar storage poorly; and warehouses tend to cost more for large jobs than Spark or Flink.

DataFrames come from R and Pandas. Spark, Flink and Daft offer distributed versions, which are generally not indexed and ordered the way local ones are — a source of performance surprises. Pandas executes each call immediately; Spark first turns the calls into a query plan and optimizes it. Daft computes small things on the client and large ones on a server; Apache Arrow gives both a shared columnar data model.

        Big idea 10 · batch use cases
        
Getting the answers back to the people

        
Where do you meet batch jobs? Wherever there's a lot of data and nobody needs the answer this second. ETL: copying data out of live databases, tidying it, and loading it into a warehouse. Analytics: reports and questions over everything. Machine learning: preparing data, training models, scoring in bulk. Even the US banking network runs almost entirely on batch jobs.

        
Often the result has to go back into a live app — tonight's “recommended for you” list, say. The tempting way is to let every task write straight into the live database, record by record. That's a bad idea three times over: one network request per record is slow; many tasks hammering at once make the database crawl for real users; and if a task dies half-way and is retried, people see half-done or doubled results.

        
The better way keeps the batch job's all-or-nothing promise. Build complete files off to the side, and only when the whole job has succeeded, bulk-load them and switch versions in one move.

        
Try it: run tonight's job both ways and watch Noor's waiting time. Then switch on “A task crashes half-way” and run both again.

        

          What the book says
          

            
Batch fits wherever there is a lot of data and freshness isn't important: accounting and inventory reconciliation, demand forecasting, training recommendation models, and the US banking network, which runs almost entirely on batch jobs. ETL is often “embarrassingly parallel”; workflow schedulers retry failed jobs, mark repeat offenders as failed, and ship with connectors (Airflow has operators for MySQL, PostgreSQL, Snowflake, Spark, Flink and more). Data mesh, data contract and data fabric practices help teams publish data safely, and pipelines increasingly run on the same engines as analytical queries (SparkSQL, Trino, DuckDB).

            
Analytics: SQL on a query engine over a DFS or object store, with table formats like Apache Iceberg and catalogs like Unity, is a data lakehouse. Queries are either scheduled pre-aggregations (OLAP cubes, data marts, pushed to Apache Druid or Pinot) or ad hoc. Machine learning: feature engineering, model training, batch inference (Spark MLlib, FlinkML); graph processing in the bulk synchronous parallel (Pregel) model (Giraph, GraphX, Gelly); LLM data preparation on Kubeflow, Flyte and Ray; and notebooks such as Jupyter and Hex.

            
Serving derived data: writing to the production database from inside tasks is slow (a request per record), can overwhelm the database, and breaks the clean all-or-nothing guarantee — partial results become visible and retried tasks may duplicate output.

            
Better: push the output to a stream such as a Kafka topic, which Elasticsearch, Pinot, Druid, Venice and ClickHouse can ingest. Streams take sequential writes well, buffer so consumers can throttle, feed several systems, and can sit in a DMZ; but the job must still signal completion, and consumers must keep the data invisible until then. Or build a brand-new database inside the job and bulk-load its files (TiDB Lightning, Pinot's Hadoop import jobs, RocksDB's SST file import), which makes atomic version switches easy but incremental updates hard; Venice supports a hybrid.

Words to know
Grown-up words, in plain language.

      

        
batch job
A program that reads a big pile of input, never changes it, and builds its output from scratch.

        
online system
A system that answers each request straight away, while somebody waits.

        
throughput
How much data a job gets through per unit of time. The score that matters for batch jobs.

        
derived data
Data worked out from other data. Lose it and you can always make it again.

        
human fault tolerance
Being able to recover from your own buggy code: roll it back, run again, and the output is right.

        
pipe
The | sign: one program's output becomes the next program's input.

        
working set
The memory a job needs to reach into at random. For counting, it's one entry per different key.

        
spill to disk
Writing sorted chunks out to disk when the data won't fit in memory, and merging them later.

        
distributed filesystem
A filesystem that chops files into blocks and spreads the blocks over many machines.

        
block
One big slice of a file — 128 MB by default in HDFS.

        
replication
Keeping each block on several machines so one broken machine loses nothing.

        
object store
Storage where you put and get whole objects by key, like S3. Objects can't be edited in place.

        
orchestrator
The cluster's operating system: it decides where tasks run and watches over them.

        
scheduler
The part of the orchestrator that matches waiting tasks to machines with free CPU and memory.

        
preemption
The scheduler killing a running task on purpose to make room for a more important one.

        
spot instance
A cheap cloud machine that can be taken away at any moment.

        
workflow (DAG)
A chain of jobs where one job's output is another's input, and nothing loops back.

        
mapper
A function called once per record that pulls out a key and a value.

        
reducer
A function called once per key with all of that key's values, to combine them.

        
shuffle
A sort spread over many machines, so that equal keys end up together. Not random at all.

        
dataflow engine
A system like Spark or Flink that runs a whole multi-step workflow as one job.

        
sort-merge join
Matching two datasets by sorting both on the same key and zipping them together.

        
query optimizer
The planner that turns “what I want” into the cheapest “how to do it”.

        
DataFrame
A table you transform by calling functions such as filter and join, instead of writing one SQL query.

        
ETL
Extract–transform–load: copy data out of one system, reshape it, and load it into another.

        
bulk load
Importing whole finished files into a database in one go, instead of record by record.
