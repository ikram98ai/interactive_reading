Batch processing · online versus offline systems

If the answer comes out wrong, fix the job and run it again

Ana runs a bakery’s website. When a customer taps Order, the site must answer in a few milliseconds: that is an online system, judged by its response time. Every night a different kind of program wakes up, reads all of the day’s orders and writes a fresh revenue report. Nobody is waiting on it; what matters is how much data it gets through per hour, its throughput. That is a batch job, an offline system.

On Tuesday, Wei ships a bug that turns €12.50 into €1,250.00. In the read/write database, the bad code overwrote rows in place, so rolling the code back fixes tomorrow but not yesterday. The batch job never changes its input: it reads read-only files and builds its output from scratch every run. Roll back and run it again, or simply point readers at last night’s output directory (time travel). Being able to recover from your own buggy code is called human fault tolerance.

Try it: in Read/write database, press Deploy buggy v2, then Save an order three times, then Roll back to v1: the bad rows stay. Switch to Batch job, deploy v2 and press Run the job. Now either press Use previous output, or roll back and run the job again.

What the book says

Online systems (browsers fetching pages, services calling APIs, databases, caches, search indexes) answer a request as quickly as possible; response time is usually their primary measure, and they often need fault tolerance for high availability. Batch processing jobs run in offline systems: bigger computations such as training an AI model, transforming lots of data, or analytics over a very large dataset. A job takes read-only input and produces output generated from scratch every time it runs, so the output is derived data. It may run for minutes, hours or days, often on a schedule, and its primary measure is usually throughput.

Treating inputs as immutable and avoiding side effects brings benefits. If buggy code corrupts the output, roll back the code and rerun the job, or keep the old output in a different directory and switch back to it; most object stores and open table formats support this as time travel. Rolling back buggy code that wrote bad data into a read/write database does nothing to fix that data. Recovering from buggy code has been called human fault tolerance, and minimizing irreversibility helps Agile development. The same files can feed many jobs, including monitoring jobs that compare a run’s output with the previous run. Batch frameworks also use computing resources efficiently.

The costs: with most frameworks, other jobs can use the output only after the whole job finishes, and any change to the input, even a single byte, means reprocessing the entire input. Some systems handle faults by restarting the whole job, others complete despite crashed nodes. The boundary with online systems is fuzzy (a long-running database query looks like a batch process), and batch processing is a building block for data integration, such as ETL. Stream processing (Chapter 12) instead keeps watching its input.

MapReduce, published by Google in 2004 and implemented in Hadoop, CouchDB and MongoDB, shaped modern batch processing; it is fairly low-level and is now largely obsolete and no longer used at Google. Today’s work runs on Spark, Flink or data warehouse query engines, with dataflow APIs, query languages and DataFrame APIs; workflow schedulers such as Oozie and Azkaban gave way to Airflow, Dagster and Prefect; storage is shifting from distributed filesystems (HDFS, GlusterFS, CephFS) to object storage such as S3; and BigQuery and Snowflake blur the line between warehouses and batch processing.

Batch processing with Unix tools · one line of a web log

Reading one line of a web server’s diary

Every time Martin’s web server sends a file, it appends one line to access.log, like a shop’s till roll. One line says who asked (an IP address), when, what they asked for, how it went (the status code), how big the answer was, which page sent them, and which browser they used.

The log format names each piece, but Unix tools such as awk don’t know the format. awk simply splits the line wherever there is whitespace and numbers the pieces $1, $2, … So the timestamp, which contains a space, becomes $4 and $5; the request "GET /css/typography.css HTTP/1.1" becomes $6 $7 $8; and the URL is $7. Every analysis in the next scenes leans on that one fact.

Try it: tap any piece of the log line, or press Next field, and watch the matching variable light up in the format underneath, with the awk field numbers it turns into.

What the book says

A web server appends a line to a log file every time it serves a request. With the NGINX default access log format, one line looks like 216.58.210.78 - - [27/Jun/2025:17:55:11 +0000] "GET /css/typography.css HTTP/1.1" 200 3377 "https://martin.kleppmann.com/" "Mozilla/5.0 (Macintosh; …) … Chrome/137.0.0.0 Safari/537.36" (really one line).

The format is $remote_addr - $remote_user [$time_local] "$request" $status $body_bytes_sent "$http_referer" "$http_user_agent". So on June 27, 2025, at 17:55:11 UTC, the server received a request for /css/typography.css from client 216.58.210.78. The user was not authenticated, so $remote_user is a hyphen. The status was 200 (success), the response was 3,377 bytes, the browser was Chrome 137, and it loaded the file because the page at https://martin.kleppmann.com/ referenced it.

Log parsing may seem contrived, but it is a critical part of operations at many technology companies, used for everything from ad pipelines to payment processing, and it drove the rapid adoption of MapReduce and the “big data” movement.

Simple log analysis · six tools in one pipe

Six little tools holding hands

Martin wants his five most popular pages. No database, no cluster: six standard Unix tools, each doing one small job and handing its output to the next through a pipe (|). cat reads the log, awk keeps only field 7 (the URL), sort puts the URLs in alphabetical order, uniq -c counts each run of identical lines, the second sort puts the biggest counts first, and head keeps five.

The clever bit is the first sort. uniq only ever compares a line with the one just before it, so it can only count a URL correctly once all its copies sit next to each other. Sorting guarantees that. Changing the question is a one-word edit: skip CSS files, or count client IPs instead of pages.

Try it: press Run next command six times and watch what each tool does to the stream of lines. Then pick Skip CSS or Top clients and run it again: only the awk program changes. Notice how sort puts 81.2.69.160 last: it sorts text, not numbers.

What the book says

To find the five most popular pages: cat /var/log/nginx/access.log | awk '{print $7}' | sort | uniq -c | sort -r -n | head -n 5. cat reads the log (strictly unnecessary, since awk could take the file as an argument, but it makes the linear pipeline more apparent). awk splits each line into fields by whitespace and outputs only the seventh, the requested URL.

sort orders the URLs alphabetically so that a URL requested n times appears n times in a row. uniq filters out repeated lines by checking whether two adjacent lines are the same, and -c makes it output a counter for every distinct URL. The second sort sorts by the number (-n) at the start of each line, in reverse (-r) order, largest first. head -n 5 outputs the first five lines and discards the rest.

The chain is incredibly powerful: it will process gigabytes of log files in a matter of seconds, and it is easy to modify. To omit CSS files, change the awk argument to $7 !~ /\.css$/ {print $7}; to count top client IP addresses, change it to {print $1}. Many analyses can be done in minutes with awk, sed, grep, sort, uniq and xargs, and they perform surprisingly well.

Chain of commands versus custom program · the hash table

The same answer, written as a Python program

Joon would rather write Python than remember uniq’s flags. His program keeps a tally: a hash table that maps each URL to a counter, starting at 0. For every line it takes the seventh field (index 6, because Python counts from zero), adds one to that URL’s counter, and at the end sorts the table by count and prints the top five.

The output is identical, and which version you prefer is partly taste. But the two run very differently. Joon’s program holds one entry per distinct URL, no matter how many times it appears. The pipeline holds every URL line, repeats and all, and relies on sort to put the repeats side by side. On a small file you can’t tell. On a huge one, that difference decides everything.

Try it: press Next line a few times and watch the program’s current line and the table grow, then Run to the end. Switch to Pipeline and step through the same log: compare Entries in memory when all 12 lines are in.

What the book says

Instead of the chain of Unix commands you could write a simple program, for example in Python. It initializes counts as a hash table that keeps a counter for each URL, starting at 0; gets the requested URL, the seventh whitespace-separated field (array index 6, because Python’s arrays are zero-indexed); increments the counter for that URL; sorts the hash table contents by counter value, descending, and takes the top five; and prints them.

The program is not as concise as the chain of Unix commands, but it’s fairly readable, and which of the two you prefer is in part a matter of taste. Besides the superficial syntactic differences, though, there is a big difference in the execution flow, which becomes apparent if you run the analysis on a large file.

Sorting versus in-memory aggregation · the working set

A tally sheet, or sorted piles on the floor?

Mina counts a town’s votes on a tally sheet with room for six names. With three candidates, a million ballots are no problem: the sheet only needs one line per candidate. But in a write-in election with thousands of names, the sheet fills up and she is stuck. So she changes method: sort a deskful of ballots, put that sorted pile on the floor, repeat; then merge the piles by always taking the smallest name off the top, and count each run of identical names as it goes by.

The memory a hash table needs, its working set, depends on the number of distinct keys, not the number of records. If that fits in memory, the hash table is great, even on a laptop. If it doesn’t, sorting wins: sort chunks in memory, write them out as sorted segment files, then merge them. Every step reads and writes files from start to end, a sequential pattern that disks handle well. GNU sort does exactly this by itself, which is why the pipeline scales.

Try it: keep Hash table, pick 10 distinct URLs and press Run: the seventh new URL has no slot. Switch to Sort, spill, merge and run the same input: memory never holds more than 6 records, and the counts come out right.

What the book says

The Python script keeps an in-memory hash table of URLs; the Unix pipeline has no hash table, but sorts a list in which repeated URLs are simply repeated. Which is better depends on how many URLs you have. For most small to mid-sized websites, all distinct URLs and a counter for each fit in (say) 1 GB of memory. The job’s working set (the amount of memory to which it needs random access) depends only on the number of distinct URLs: a million log entries for one URL still take one URL plus a counter. If the working set is small enough, an in-memory hash table works fine, even on a laptop.

If the working set is larger than the available memory, sorting can make efficient use of disks, as in log-structured storage: chunks are sorted in memory and written to disk as segment files, then multiple sorted segments are merged into a larger sorted file. Mergesort has sequential access patterns that perform well on disks.

The sort utility in GNU Coreutils automatically handles larger-than-memory datasets by spilling to disk and parallelizes sorting across multiple CPU cores, so the simple chain of Unix commands easily scales to large datasets; the bottleneck is likely the rate at which the input file can be read from disk. The limitation is that Unix tools run on a single machine. Datasets too large for one machine’s memory or local disk are where distributed batch processing frameworks come in.

Batch processing in distributed systems · a distributed operating system

The same three parts, spread over a whole building

Inés runs a corner bakery: one pantry, one oven, and one baker who decides which tray goes in next. Her friend runs a chain of forty bakeries. It has exactly the same parts, only bigger: a central warehouse instead of a pantry, a head office that decides which bakery bakes what, and vans instead of a hand passing trays along the counter.

The laptop that ran our log pipeline had three parts working together: storage reached through the operating system’s filesystem interface, a scheduler that decides when each process gets the CPU, and programs whose stdout is joined to the next one’s stdin by pipes. A distributed batch framework has the same three, so you can think of it as a distributed operating system: a distributed filesystem or object store, a job orchestrator, and tasks that pass data through the filesystem or over the network.

What the book says

The machine that runs the Unix tools example has components that work together to process the log data: storage devices accessed through the operating system’s filesystem interface; a scheduler that determines when processes get to run and how to allocate CPU resources to them; and a series of Unix programs whose standard input and standard output (stdin and stdout) are connected together by pipes.

These same components exist in distributed data processing frameworks. You can think of these frameworks as distributed operating systems: they have filesystems, job schedulers, and programs that send data to one another through the filesystem or other communication channels.

The reason to go distributed at all: Unix tools run on a single machine, and datasets that are too large to fit in memory or on the local disk present a problem. That is where distributed batch processing frameworks come in.

Distributed filesystems · blocks, metadata and a protocol

One file, cut into fat blocks and scattered

A small library keeps each book on one shelf, and the catalogue card says “shelf 12.” A 900-page atlas that fits on no shelf is split into volumes kept in different rooms. Now the catalogue needs one line per volume, so the librarian wants a few fat volumes, not thousands of thin ones.

Your operating system’s filesystem is a stack of layers: a block device driver that reads raw blocks from the disk, a page cache that keeps recent blocks in memory, a filesystem such as ext4 or XFS that cuts files into blocks and tracks inodes and directories, and the VFS that gives every application one API. A distributed filesystem copies the design: blocks live as files on many data nodes, each data node’s own page cache keeps hot blocks in memory, a metadata service (HDFS’s NameNode) remembers where every block is, and a protocol such as the S3 API plays the VFS.

The blocks are much bigger: ext4 uses 4,096 bytes, JuiceFS and many object stores 4 MB, HDFS 128 MB by default. Fewer blocks mean less metadata, and less seeking per byte read. A DFS also doesn’t pad: a 900 MB file becomes seven 128 MB blocks and one 4 MB block.

Try it: in Layers, press Send a read down, then click any layer to see its twin. In Blocks, press Split the file for 900 MB with 128 MB blocks, then pick 1 PB with 4 KB blocks and look at the metadata count. In Read a file, press Read the file twice: the second time the data nodes answer from their page cache.

What the book says

The OS filesystem has several layers. At the lowest level, block device drivers speak directly to the disk and let the layers above read and write raw blocks. Above them sits a page cache that keeps recently accessed blocks in memory. A filesystem layer (on Linux, for example, ext4 and XFS) breaks large files into blocks and tracks metadata such as inodes, directories and files. Finally, the virtual filesystem (VFS) exposes different filesystems to applications through one common API.

Distributed filesystems work in much the same way. Files are broken into blocks distributed across many machines, and DFS blocks are typically much larger than local ones: HDFS defaults to 128 MB, while JuiceFS and many object stores use 4 MB blocks, against ext4’s 4,096 bytes. Larger blocks mean less metadata to keep track of, which makes a big difference on petabyte-sized datasets, and they lower the overhead of seeking to a block relative to reading it. Because a DFS is usually built on top of OS filesystems, it doesn’t have to write whole blocks: a 900 MB file stored with 128 MB blocks has seven blocks that use 128 MB and one block that uses 4 MB.

Blocks are read with network requests to a daemon on the machine that stores them, which reads and writes blocks as files on its local filesystem (HDFS calls these daemons DataNodes, GlusterFS glusterfsd processes; the book says data nodes). Those reads go through each data node’s in-memory page cache; some systems add more tiers, such as the client-side and local disk caching in JuiceFS.

Metadata such as file block locations and permissions is kept by a service: Hadoop’s NameNode, or the metadata service of DeepSeek’s 3FS, which persists to a key-value store such as FoundationDB. The VFS’s analogue is the DFS’s protocol, a pluggable interface: Amazon S3’s API is implemented by MinIO, Cloudflare’s R2, Tigris, Backblaze’s B2 and many others. Some DFSs are POSIX-compliant and plug into the VFS through FUSE or NFS; Amazon EFS and Archil provide NFS-compatible implementations that are far more scalable.

Distributed filesystems and network storage · surviving dead disks

Cheap machines die, so every block lives in several places

Tomasz keeps the family photos on three cheap drives instead of one expensive one: if a drive dies, two copies are left. Aiko is thriftier. She cuts the album into four parts and computes two extra parity parts from them, so any four of her six drives can rebuild the whole album, with half the drives Tomasz needs per photo.

A distributed filesystem is shared-nothing: ordinary computers on an ordinary datacenter network, not the shared-disk approach of NAS and SAN, where every server talks to one central storage appliance over special hardware such as Fibre Channel. Ordinary commodity machines are cheap but fail more often, so each block is replicated on several machines, or protected by an erasure code such as Reed–Solomon that recovers lost data with less storage overhead. Replicas have a second benefit: the scheduler can run a task on any node that holds a copy of its input.

Try it: in 3 replicas, click two data nodes to crash them and press Read the file: every block still has a copy. Crash a third and look again. In Erasure code, crash any two: the missing parts are rebuilt from four survivors, at 1.5× storage instead of 3×. Press Place a task on B to see where the scheduler can run it. (The 4 data + 2 parity layout is our example; the book names no particular scheme.)

What the book says

Distributed filesystems are based on the shared-nothing principle, in contrast to the shared-disk approach of network attached storage (NAS) and storage area network (SAN) architectures. Shared-disk storage is implemented by a centralized storage appliance, often using custom hardware and special network infrastructure such as Fibre Channel. The shared-nothing approach requires no special hardware, only computers connected by a conventional datacenter network.

Many distributed filesystems are built on commodity hardware, which is less expensive but has higher failure rates than enterprise-grade hardware. To tolerate machine and disk failures, file blocks are replicated on multiple machines. This also lets schedulers distribute workloads more evenly, since they can execute a task on any node that contains a replica of the task’s input data.

Replication may mean simply keeping several copies of the same data on multiple machines (Chapter 6), or using an erasure coding scheme such as Reed–Solomon codes, which allows lost data to be recovered with lower storage overhead than full replication. The techniques are similar to RAID, which provides redundancy across several disks attached to the same machine; the difference is that in a distributed filesystem, file access and replication are done over a conventional datacenter network without special hardware.

Object stores · keys, not directories

The folders are an illusion

Rosa’s photos sit in a bucket at s3://my-photo-bucket/2025/04/01/birthday.png. It looks like four nested folders. It isn’t: the bucket is a giant flat dictionary, and 2025/04/01/birthday.png, slashes and all, is a single key. Everything odd about object stores follows from that.

You get and put whole objects; there is no fopen or fseek, and an object is immutable, so changing one byte means putting the whole object again. “Listing a folder” is a prefix match that returns every key below it, like ls -R. A folder with nothing in it can’t exist. And there is no atomic rename: renaming a “directory” means copying every object to a new key and deleting the old one, one at a time.

Try it: in List & delete, press List 2025/04/, then Delete 01’s photos and list again: the filesystem keeps an empty 01/, the bucket forgets it. Turn on the zero-byte marker and repeat. In Rename, rename 2025/04, then turn on Crash midway and rename again. In Update, fix a one-byte typo and compare the bytes written.

What the book says

Object storage services such as Amazon S3, Google Cloud Storage, Azure Blob Storage and OpenStack Swift have become a popular alternative to distributed filesystems for batch jobs, and the line between the two is somewhat blurry: FUSE drivers let users treat object stores such as S3 as a filesystem, and JuiceFS and Ceph offer both object storage and filesystem APIs. But their APIs, performance and consistency guarantees are very different, so check that such systems behave as expected.

Each object has a URL such as s3://my-photo-bucket/2025/04/01/birthday.png. The host portion (my-photo-bucket) is the bucket, whose name is globally unique; the rest is the object’s key, unique within its bucket. Objects are read with a get call and written with a put call, and unlike files they are immutable once written: to update an object it must be fully rewritten with put, much like a key-value store. Azure Blob Storage and S3 Express One Zone support appends, but most other stores do not. There are no file handle APIs with functions like fopen and fseek.

Object stores have no concept of directories; the path structure is a convention and the slashes are part of the key. A prefix list operation behaves like a recursive ls -R, including objects in subpaths. Empty directories are not possible: remove every object under s3://my-photo-bucket/2025/04/01 and 01 no longer appears when listing s3://my-photo-bucket/2025/04. It’s common practice to create a zero-byte object to represent an empty directory.

Hard links, symbolic links, file locking and atomic renames, which DFS implementations often support, are missing. Renames are nonatomic: the object is copied to the new key and the old object deleted. To rename a directory you have to rename every object within it individually, since the directory name is part of the key.

Object stores · move the code, or move the data

Send the recipe to the pantry, or the pantry to the kitchen?

Kofi’s job is a 2 MB program that must read eight 128 MB blocks. HDFS can run each task on the machine that already stores its block, so only the small program crosses the network. An object store keeps storage machines and compute machines apart: every block travels over the network to wherever the task runs, but tonight Kofi can rent eight compute machines without buying a single extra disk.

Modern datacenter networks are fast, so moving the data is often acceptable, and decoupling lets CPU and memory grow independently of storage. It also matters what you store: key-value stores are built for small values (kilobytes) and frequent low-latency reads and writes, while distributed filesystems and object stores are built for large objects (megabytes to gigabytes) read less often, in bigger pieces, though S3 Express One Zone now offers single-millisecond latency.

What the book says

The key-value stores of Chapter 4 are optimized for small values (typically kilobytes) and frequent, low-latency reads and writes. Distributed filesystems and object stores are generally optimized for large objects (megabytes to gigabytes) and less frequent, larger reads. Recently object stores have begun to support frequent and smaller reads and writes: S3 Express One Zone now offers single-millisecond latency and a pricing model more like key-value stores.

Another difference: DFSs such as HDFS allow computing tasks to run on the machine that stores a copy of a particular file, so the task can read that file without sending it over the network. That saves bandwidth if the task’s executable code is smaller than the file it needs to read.

Object stores usually keep storage and computation separate. That might use more bandwidth, but modern datacenter networks are very fast, so this is often acceptable. The architecture also allows machine resources such as CPU and memory to be scaled independently of storage, since the two are decoupled.

Distributed job orchestration · scheduler, resource manager, executors

The taxi dispatcher for a thousand computers

Ines runs dispatch at a taxi company. A call comes in: six cars, each must take a wheelchair. She looks at the board of which cars are free and which are accessible, radios drivers their pickups, and every driver checks in by radio every minute. When Tunde’s radio goes quiet for too long, she wipes his car off the board and gives his fares to somebody else.

On one machine, the kernel does this for awk, sort and uniq: start processes, give them memory and CPU time, fence them in. On a cluster, a job orchestrator such as Kubernetes or Hadoop YARN does it, with three parts. The scheduler (Ines) reads a job request and decides which task runs on which node. The resource manager (the board) holds the global view: every node’s CPUs, GPUs, memory and health, kept in etcd or ZooKeeper. A task executor on every node (YARN’s NodeManager, Kubernetes’s kubelet: the drivers) fetches the job’s code, starts the task, watches it, fences it in with Linux cgroups, and sends heartbeats.

Try it: press Submit job and follow the request through the scheduler’s placement loop: only the two GPU nodes qualify. Then click node-2 to cut its heartbeats and press Heartbeat round twice: the resource manager declares it dead and the scheduler re-places its tasks, some of which won’t fit. Change the request (more tasks, more cores, any node) and submit again.

What the book says

When you run a Unix batch job, something must start the processes, pass data from one to the next, allocate memory, schedule instructions fairly on the CPU and enforce memory and I/O boundaries. On a single machine that is the kernel’s job; in a distributed environment it is the role of a job orchestrator.

A batch framework asks the orchestrator’s scheduler to run a job. The request carries metadata such as the number of tasks, the memory, CPU and disk each task needs, a job identifier, access credentials, job parameters such as input and output data, required hardware such as GPUs or disk types, and the location of the job’s executable code.

Orchestrators such as Kubernetes and Hadoop YARN combine this with cluster metadata using three components. Task executors (YARN’s NodeManager, Kubernetes’s kubelet) run on each node: they retrieve the code, start and monitor tasks, send heartbeats to signal liveness, and track task status and resource allocation; YARN and Kubernetes use Linux cgroups for security and performance isolation. The resource manager stores metadata about each node (hardware, task statuses, network location, node status) and so gives a global view of the cluster; being centralized, it can become a scalability and availability bottleneck. YARN stores cluster state in ZooKeeper and Kubernetes in etcd. The scheduler receives requests to start, stop or check on jobs, for example 10 tasks with a specific Docker image on nodes with a specific type of GPU, and uses the request and the resource manager’s state to decide which tasks run on which nodes.

Some decisions need application-specific schedulers that work alongside the central one, for example to autoscale read replicas when a query threshold is reached. YARN calls them ApplicationMasters; Kubernetes calls them operators.

Distributed job orchestration · resource allocation

160 cores, two jobs that each want 100

Mei and Rafael book the same sports hall for Saturday. Mei’s tournament needs 100 seats, Rafael’s needs 100 too, and the hall has 160. Give each 80 and let latecomers sit as others leave? Seat Mei’s whole crowd first and make Rafael’s wait outside until 100 seats are empty at once? And if Rafael phones an hour later, should Mei have been told to leave some seats free, just in case?

A cluster scheduler faces exactly this, over and over. Sharing keeps every core busy but finishes both jobs later. Gang scheduling starts all 100 tasks together, but if it reserves cores while it waits, they sit idle, and two jobs that both reserve can each end up holding 80 and wait for each other forever: a deadlock. If it just waits for 100 free cores, smaller jobs grab them first and the big job starves. Preemption kills running tasks to make room, and their work is thrown away. Finding the best plan is NP-hard, so real schedulers use heuristics.

What the book says

Schedulers must figure out how to allocate the cluster’s limited resources among jobs with competing needs, balancing fairness and efficiency. The book’s example: a cluster of five nodes with 160 CPU cores receives two job requests, each wanting 100 cores.

  • Run 80 tasks of each job, starting the remaining 20 of each as earlier tasks complete.
  • Run all of one job’s tasks, then start the second job only when 100 cores are available (gang scheduling).
  • If the second request arrives much later, the scheduler has incomplete information: give all 100 cores to the first job, or hold some back for a job that may never come?

If a gang scheduler reserves cores until all 100 are available, nodes sit idle, utilization drops, and a deadlock might occur if other jobs also reserve cores. If it simply waits for 100 free cores, other jobs might grab them in the meantime, which leads to starvation. It could instead preempt some of the first job’s tasks, but the killed tasks must be restarted later, which also lowers efficiency.

With hundreds or millions of requests, the optimal allocation is NP-hard, so schedulers use heuristics that are not optimal but reasonable: first-in first-out (FIFO), dominant resource fairness (DRF), priority queues, capacity or quota-based scheduling, and various bin-packing algorithms.

Distributed job orchestration · scheduling workflows

A recipe where every step waits for its ingredients

Sanjay’s bakery makes a wedding cake. The sponge and the icing are made by different people at different times, and the assembly can only start when both are on the shelf. If the icing burns, assembly just waits; nobody rebakes the sponge. Meanwhile the café team takes slices of the same sponge for their own trifle.

Batch jobs chain the same way. The output of one job is the input of others, and a job may need several inputs: a workflow, or directed acyclic graph (DAG) of jobs. Usually each job writes its output to a distributed filesystem or object store and the next one reads it from there, so jobs are decoupled in time and a second team can read the same files. A workflow scheduler such as Airflow, Dagster or Prefect runs a job only after every job that produces its inputs has succeeded. The alternative is the Unix pipe: a small in-memory buffer between running processes, where a slow reader makes the writer wait. That is backpressure.

What the book says

Often the output of one job becomes the input to one or more other jobs, and each job may have several inputs produced by other jobs: a workflow or directed acyclic graph (DAG) of jobs. (This is a different meaning of “workflow” from the durable execution engines of Chapter 5, which typically perform RPCs and process less data per request.)

Reasons for a workflow: one job’s output may feed several jobs maintained by different teams, so it should be written where they can all read it; data may move between tools (a Spark job outputs to HDFS, then a Python script triggers a Trino SQL query that processes the HDFS files and outputs to S3); and a pipeline may need several stages, for example when one stage shards by one key and the next by another.

A Unix pipe uses only a small in-memory buffer; if it fills up, the producer must wait for the consumer, a form of backpressure. Spark, Flink and other engines can pass one task’s output directly to another in a similar way. But more typically one job writes its output to a distributed filesystem or object store and the next reads it, which decouples the jobs so they can run at different times. A job with several inputs usually waits until all the jobs producing them have completed successfully.

Schedulers such as YARN’s ResourceManager or Spark’s built-in scheduler work per job, not per workflow. Workflow schedulers such as Airflow, Dagster and Prefect handle the dependencies; workflows of 50 to 100 jobs are common, and many teams may read one another’s output across many systems.

Distributed job orchestration · handling faults

When the landlord wants the room back

Yuki rents empty classrooms in the evening at a tenth of the price, on one condition: if a paying course turns up, she has to leave right away. She is grading 240 exams in batches of 30. Long batch jobs with many tasks will meet failures: broken hardware, network trouble, and above all preemption. Cheap low-priority machines (spot instances on EC2, spot VMs on Azure, preemptible instances on Google Cloud) run batch work on spare capacity and get killed when a higher-priority task arrives, which happens more often than hardware faults. Because a batch task’s output is rebuilt from scratch, the fix is easy: delete the partial output and rerun that one task elsewhere. The hard part is intermediate data that the next step needs. What the book says

Long-running jobs with many parallel tasks are likely to see at least one task failure, from hardware faults (especially on commodity hardware) or network interruptions. A task may also be preempted (killed) by the scheduler, which is useful with several priority levels: cheaper low-priority tasks run on spare capacity but can be preempted at any moment by a higher-priority task. Such virtual machines are called spot instances on Amazon EC2, spot virtual machines on Azure and preemptible instances on Google Cloud.

Batch jobs are rarely time-sensitive, so they suit low-priority tasks and spot instances: they use resources that would otherwise be idle and raise cluster utilization. But they are then more likely to be killed, since preemptions occur more frequently than hardware faults.

Because batch jobs regenerate their output from scratch, the system can delete the partial output of a failed task and run it again on another machine. Rerunning the whole job for one failed task would be wasteful, so MapReduce and its successors keep parallel tasks independent and retry at the granularity of an individual task.

When one task’s output is another’s input, MapReduce always writes the intermediate data back to the distributed filesystem and waits for the writing task to complete before others read it; this works even where preemption is common, but means many DFS writes. Spark keeps intermediate data in memory (spilling to local disk), writes only the final result to the DFS, and tracks how the intermediate data was computed so it can recompute it if lost. Flink periodically checkpoints a snapshot of its tasks.

The Unix pipeline, split into two callbacks

Remember the six-tool pipeline? Ines notices that only two of the tools hold her own logic: awk '{print $7}' decides what to pull out of each line, and uniq -c decides what to do with each run of identical lines. Reading the file and sorting are the same every time. MapReduce keeps exactly that split.

You write a mapper, called once per input record, which emits any number of key-value pairs and remembers nothing between records. The framework sorts every pair by key, without being asked. Then it calls your reducer once per key, with an iterator over that key’s values. What the book says

The two most common batch processing models are MapReduce and dataflow engines. Dataflow engines have largely replaced MapReduce in practice, but MapReduce influenced many modern frameworks. Both have evolved to support several programming models: low-level programmatic APIs, relational query languages and DataFrame APIs.

MapReduce follows the same pattern as the log analysis: (1) read a set of input files (in HDFS or an object store like S3, in formats such as Parquet or Avro) and break it into records; (2) call the mapper to extract a key and value from each record, like awk '{print $7}'; (3) sort all the key-value pairs by key, like the first sort; (4) call the reducer to iterate over the sorted pairs, like uniq -c. Steps 2 and 4 are your code; step 1 is the input format parser; step 3 is implicit.

The mapper is called once for every input record and may generate any number of key-value pairs, including none. It keeps no state from one record to the next, and many mappers run in parallel on different parts of the input. The framework collects all the values for the same key and calls the reducer with an iterator over them; reducers for different keys can also run in parallel.

A second sorting stage, such as ranking URLs by number of requests, is a second MapReduce job that uses the first job’s output as its input. The mapper’s role is to put the data into a form suitable for sorting; the reducer’s role is to process the data that has been sorted.

A mapper that scribbles on the wall can’t be retried

What the book says

Though MapReduce is used for batch processing, the programming model comes from functional programming. Lisp introduced map and reduce (or fold) as higher-order functions on lists, and they have made their way into mainstream languages such as Python, Rust and Java. Many common data processing operations, including those offered by SQL, can be implemented on top of MapReduce.

Avoiding mutable state helps enable parallel execution. Every call to the mapper and reducer depends only on the data the framework explicitly passes to it, so the framework is free to run independent calls in parallel on different nodes. And if a task fails, it is free to call the mapper and reducer again with the same input on another node.

Implementing a complex job with the raw MapReduce APIs is quite laborious: any join algorithm would have to be implemented from scratch. MapReduce is also quite slow compared to more modern batch processors; one reason is that its file-based I/O prevents job pipelining, i.e. processing output data in a downstream job before the upstream job is complete.

Dataflow engines · the whole workflow as one job

Stop filing every half-finished answer in triplicate

Imagine a kitchen where every cook must finish the whole batch, label it, and put three copies in the walk-in freezer before the next cook may start, and where every cook is hired fresh each morning for one task. That’s a chain of MapReduce jobs: each step sorts whether it needs to or not, writes its output to the replicated distributed filesystem, and the next job waits for all of it.

Dataflow engines such as Spark and Flink see the whole workflow as one job, built from operators like map, filter, join and group by that don’t have to alternate map, reduce, map, reduce. Knowing the whole graph lets them skip work: sort only where needed, fuse a map and a filter into one task, place a consumer next to its producer, keep intermediate data in memory or on local disk, start an operator as soon as input arrives, and reuse processes.

Try it: press Run with MapReduce chain and watch the timeline. Switch to Dataflow engine and run it again. Then click the six optimizations on the left one at a time to see what each one saves on the clock, in DFS writes, sorts and process launches.

What the book says

To fix some of MapReduce’s problems, new execution engines were developed, most famously Spark and Flink, based on research systems like Dryad and Nephele. They handle an entire workflow as one job rather than breaking it into independent subjobs. Because they explicitly model the flow of data through several processing stages, they are known as dataflow engines.

Like MapReduce they offer a low-level API that calls a user-defined function one record at a time, but also higher-level operators such as join and group by. They parallelize work by sharding inputs and copy the output of one task over the network to become another’s input. Operators need not take the strict roles of alternating map and reduce. The relational-style building blocks (joining on a field, grouping by key, filtering, aggregating) are implemented internally with shuffles.

Advantages over MapReduce: expensive work such as sorting happens only where required; several operators in a row that don’t change the sharding (such as map or filter) can be combined into a single task; because all joins and data dependencies are declared, the scheduler can make locality optimizations, such as exchanging data through a shared memory buffer instead of the network; intermediate state can be kept in memory or on local disk rather than in a distributed filesystem or object store, where it must be replicated and written to disk on each replica; operators can start as soon as their input is ready; and existing processes can be reused, instead of launching a new JVM for each task.

Dataflow engines can implement the same computations as MapReduce workflows, and they usually execute significantly faster because of these optimizations.

Shuffling data · a distributed sort

The shuffle: every key finds its one reducer

A post office sorts letters at three branches. Each branch drops every letter into one of three outgoing sacks, chosen by a rule on the postcode, and keeps each sack in postcode order. When a branch is done, each delivery depot collects its sack from every branch and merges them. All letters for one street end up next to each other at one depot, no matter which branch took them in.

That is the shuffle, and despite the name nothing is random: it is a distributed sort whose input and output are both sharded. There is one map task per input shard. Each mapper writes one local file per reducer, choosing the file by hash(key) mod R, and keeps each file sorted. Each reducer copies its file from every mapper, merges them like mergesort, and calls the reducer function once per key. The R output files go back to the distributed filesystem.

Try it: press Step and follow one phase at a time: map, sort, copy, merge, reduce. The line under the machine shows the hash sum for each key. Then pick 2 or 4 reducers and press Play: the same key always lands on one reducer, but which one changes with R. With 4 reducers, count the local files: 3 mappers × 4 reducers = 12.

What the book says

Batch processors must sort datasets petabytes in size, too large for one machine, so they need a distributed sorting algorithm where both the input and the output are sharded: a shuffle. Unlike shuffling a deck of cards, it produces a sorted order with no randomness. It is used for joins and aggregations; MapReduce, Spark, Flink, Daft, Dataflow and BigQuery all implement scalable shuffles. The book uses Hadoop MapReduce’s shuffle as the illustration (Figure 11-1).

The framework starts a separate map task for each input shard (m1, m2, m3), reading one record at a time. The number of map tasks is set by the number of input shards; the number of reduce tasks is configured by the job’s author. To make sure the same key from two mappers reaches the same reducer, each mapper creates a separate output file on its local disk for every reducer (file m1, r2 holds mapper 1’s data for reducer 2), and a hash of the key typically decides which file a pair goes to.

While writing, the mapper sorts the pairs within each file, using log-structured techniques: batches are collected in a sorted in-memory structure, written out as sorted segment files, and progressively merged. After each mapper finishes, reducers connect to it and copy their file to local disk. Once a reducer has its share from all mappers, it merges the files, preserving sort order, mergesort-style; pairs with the same key are now consecutive. The reducer function is called once per key with an iterator over that key’s values, and its output is written sequentially to one file per reduce task (r1, r2, r3), back to the distributed filesystem or object store.

Modern dataflow engines and cloud data warehouses are more sophisticated: BigQuery, for example, keeps shuffle data in memory and writes it to external sorting services, which speed up shuffling and replicate the shuffled data for resilience.

Execution engines for distributed batch processing have matured: the infrastructure can store and process many petabytes on clusters of over 10,000 machines. Extract–Transform–Load · a pipeline you can debug

When the pipeline breaks at night, it leaves you the evidence

Every night Kwame’s pipeline extracts the day’s orders from the production database into three files, transforms them (keep only paid orders, keep only three fields) and loads the result into the warehouse. Each file is transformed by its own task at the same time. No task needs anything from another, which is what people call embarrassingly parallel.

Things go wrong, and the scheduler knows two kinds. A transient failure, like a network blip, usually goes away if you just try again, so the scheduler retries. A failure that comes back on every attempt is real, so after the last retry the job is marked failed and a human looks. Because the input files are still sitting there untouched, that human can open the exact file that broke the task, see what changed, fix the logic, and rerun.

ETL and ELT pipelines extract data from a production database, transform it, and load the results into a downstream system; batch jobs are often used for this, especially when the downstream system is a data warehouse. When a failure occurs, schedulers often retry jobs to mitigate transient issues; a job that fails repeatedly is marked as failed, so developers can easily see which job stopped working. Schedulers like Airflow come with built-in source, sink and query operators for MySQL, PostgreSQL, Snowflake, Spark, Flink and dozens of other systems.

Batch jobs are easy to troubleshoot: failed files can be inspected, and jobs fixed and rerun. If an input file does not contain a field that a transformation intends to use, data engineers can spot it and update the transformation logic or the job that produced the input.

Pipelines used to be managed by a single data engineering team; now data mesh, data contract and data fabric practices give teams standards and tools to safely publish data for anybody in the organization. Many ETL jobs run on the same systems as the analytical queries that read their output, such as SparkSQL, Trino or DuckDB.

What the book says

Analytical queries (OLAP) often scan over a large number of records, performing groupings and aggregations. Such workloads can run in a batch processing system alongside other batch workloads: analysts write SQL queries that execute atop a query engine, which reads from and writes to a distributed filesystem or object store. Table metadata such as table-to-file mappings, names and types is managed with table formats such as Apache Iceberg and catalogs such as Unity. This architecture is known as a data lakehouse.

Improvements in SQL query interfaces mean many organizations now use batch frameworks such as Spark for analytics, in two styles. Pre-aggregation queries: data is rolled up into OLAP cubes or data marts to speed up queries, then queried in the warehouse or pushed to purpose-built real-time OLAP systems such as Apache Druid or Apache Pinot. Pre-aggregation normally takes place at a scheduled interval, managed by workflow schedulers.

Ad hoc queries: users run these to answer specific business questions, investigate user behavior, debug operational issues and much more. Response times are important here, because analysts run queries iteratively as they get responses and learn more about the data. Batch frameworks with fast query execution help reduce their waiting times.

SQL support lets batch frameworks integrate with spreadsheets and visualization tools such as Tableau, Power BI, Looker and Apache Superset. Tableau offers SparkSQL and Presto connectors, while Apache Superset supports Trino, Hive, Spark SQL, Presto and many other systems that ultimately execute batch jobs to query data.

Machine learning (ML) makes frequent use of batch processing. Data scientists, ML engineers and AI engineers use batch frameworks to investigate data patterns, transform data and train ML models. Common uses:

Machine learning · graphs and the bulk synchronous parallel model

Everyone passes a note, then everyone waits

Picture six people in two rooms. In each round, everybody writes a note to each person they follow and drops it in the post. Then a bell rings, and nobody reads a note until every note of the round has been delivered, even the ones that had to cross to the other room. Then everybody reads, updates their own number, and the next round starts.

That is the bulk synchronous parallel (BSP) model, also called Pregel. A graph is split across workers. In each superstep, every vertex runs the same small function: it reads the messages sent to it in the previous superstep, updates its value, and sends messages along its edges. A barrier separates supersteps. Graph algorithms work this way, one edge at a time, until a metric converges (PageRank) or there are no more edges to follow (distances from a starting vertex).

Try it: in PageRank, press Run one superstep a few times and watch the ranks settle; Run to the end stops once no rank moves by more than 0.002. Messages that cross between workers are drawn in blue: those travel over the network. Then try Hop distance: it stops when nothing new is learned.

What the book says

ML applications such as recommendation engines and ranking systems also make heavy use of graph processing. Many graph algorithms are expressed by traversing one edge at a time, joining one vertex with an adjacent vertex in order to propagate some information, and repeating until a certain condition is met, for example until there are no more edges to follow, or until a metric converges.

The bulk synchronous parallel (BSP) model of computation has become popular for batch processing graphs. It is implemented by Apache Giraph, Spark’s GraphX API and Flink’s Gelly API, among others. It is also known as the Pregel model, as Google’s Pregel paper popularized this approach for processing graphs.

Earlier, the book lists iterative graph algorithms such as PageRank among the batch jobs that are not easily expressed in SQL.

Serving derived data · getting batch output to users

Don’t pour a truckload through the shop’s front door

Every night Sofia’s batch job computes fresh video recommendations for every user. The easy way to deliver them is to open a database connection inside each task and insert the rows one at a time. It works, and it is a bad idea. Hundreds of parallel tasks hammer the same database that is serving real users, so their pages slow down. And if a task crashes halfway, its first rows are already live, and the retry writes them again.

The better way is to push the output to a stream, such as a Kafka topic. Appending to a log is a fast sequential write; the database reads from it at its own pace; several systems can consume the same output; and the stream can sit in a separate network zone between the batch cluster and production. One thing streaming doesn’t fix on its own: the database must keep the new rows invisible until the job announces it is done, like a transaction that hasn’t committed yet.

Try it: in Write straight into the DB, press Run the job and watch the users’ latency and the half-finished rows they can see. Turn on t2 crashes halfway and run it again: duplicates. Then switch to Through a stream with the crash still on, and run it.

What the book says

Batch jobs often build precomputed or derived datasets such as product recommendations, user-facing reports and features for ML models, typically served from a production database, key-value store or search engine. The precomputed data needs to make its way from the batch processor’s distributed filesystem or object store back into the database serving live traffic.

Using the database’s client library inside the batch job and writing one record at a time will work, but it is a bad idea: a network request for every record is orders of magnitude slower than a batch task’s normal throughput; many tasks writing concurrently at batch rates can overwhelm the database, and its performance for queries is likely to suffer; and writing to an external system produces externally visible side effects, so results from partially completed jobs become visible, and a task that fails and is restarted may duplicate output. That breaks the clean all-or-nothing guarantee batch jobs normally give.

A better solution is to push precomputed datasets to streams such as Kafka topics; Elasticsearch, Apache Pinot, Apache Druid, Venice and ClickHouse can all ingest from Kafka. Streaming systems are optimized for sequential writes; act as a buffer, so downstream systems can throttle their read rate; let one job’s output be consumed by multiple downstream systems; and can serve as a security boundary in a demilitarized zone (DMZ) network between the batch and production networks.

Streaming doesn’t inherently solve the all-or-nothing guarantee. On completion the batch job must notify downstream systems that the data can now be served, and consumers must keep the data they receive invisible to queries, like an uncommitted transaction with read-committed isolation, until they are notified.

Serving derived data · building a database in batch

Print the new catalogue, then swap it on the counter

Every night, Kwame’s shop prints a fresh catalogue of what to recommend to each regular customer. He doesn’t cross out lines in the old one while customers are reading it. He prints the whole new catalogue in the back room, sorted by customer, and at opening time swaps it onto the counter in one move. If the new one has a mistake, he swaps the old one back. The catch: if one customer’s entry changes at lunchtime, the only way to fix it is to reprint the whole thing.

Batch jobs can do the same with a database. Instead of sending millions of writes to the live server, the job builds the database files itself (for RocksDB, sorted SST files) and the database bulk-imports them. It’s very fast, and switching between dataset versions is a single atomic step. Incremental updates are the weak spot, so systems like Venice offer hybrid stores: full dataset swaps from batch, plus row updates on top.

Try it: press Run nightly build and watch queries keep reading v1 until the switch, then only v2. Press Switch back to roll back in one step. Press One row changes: in Rebuild & swap it costs a full rebuild; in Hybrid store it’s one row update on top of the bulk-loaded version.

What the book says

A pattern that is more common when bootstrapping databases is to build a brand-new database inside the batch job and bulk-load its files directly into the database from a distributed filesystem, object store or local filesystem.

Many data systems offer bulk import tools, such as TiDB’s Lightning and Apache Pinot’s Hadoop import jobs. RocksDB offers an API to bulk-import Sorted String Table (SST) files from batch jobs.

Building databases in batch and bulk-importing them is very fast and makes it easier for systems to atomically switch between dataset versions. On the other hand, it can be challenging to incrementally update datasets from batch jobs that build brand-new databases. A hybrid approach is common when both bootstrapping and incremental loads are needed: Venice, for example, supports hybrid stores that allow batch row-based updates and full dataset swaps.

The whole chapter in three layers

From the book’s summary.

The idea

A batch job reads immutable, bounded input and writes output from scratch. Because nothing is changed in place, a wrong answer is fixed by fixing the code and running the job again.

Storage layer

Distributed filesystems and object stores cut huge files into big blocks, replicate or erasure-code them, cache hot blocks, keep metadata in a separate service, and speak a pluggable protocol such as the S3 API.

Orchestration layer

Job orchestrators decide where and when tasks run, share a cluster’s cores fairly enough, and retry failed or preempted tasks. Workflow schedulers run whole graphs of jobs in dependency order.

Computation layer

MapReduce gave us map, sort and reduce. Dataflow engines such as Spark and Flink run a whole workflow as one job, faster. The shuffle underneath both is what makes grouping, joining and aggregating possible.

Easier to use

Once running petabyte jobs was routine, attention turned to the humans: SQL and DataFrame APIs, whose plans an optimizer turns into efficient jobs.

What it’s for

ETL pipelines, analytics (pre-aggregated and ad hoc), machine learning and LLM data preparation, and building derived data that is then served to users through streams or bulk loads.

The seesaws from this chapter

Each choice buys something and costs something else.

Online system

Answers each request quickly; measured by response time

vs

Batch job

Crunches everything at once; measured by throughput, and answers arrive minutes to days later

In-memory hash table

Simple and fast while every distinct key fits in memory

vs

Sort, spill and merge

Uses the disk sequentially, so it keeps going when the working set doesn’t fit

Full replication

Several whole copies of every block; easy to read and recover

vs

Erasure coding

Recovers lost blocks with much less storage overhead, at the cost of computing them back

Run the task where the data is

Send small code, not big files, over the network

vs

Separate storage and compute

More network traffic, but CPU and storage scale independently

Gang scheduling

A job gets all its cores at once

vs

Sharing and preemption

Higher utilization, but jobs wait longer or redo killed work

Intermediate data in the DFS

Survives any crash or preemption (MapReduce)

vs

Intermediate data in memory

Far less I/O; lost pieces are recomputed from lineage (Spark) or a checkpoint (Flink)

Downstream starts at once, with backpressure

vs

Files between jobs

Jobs run at different times, and other teams can read the output

Cloud data warehouse

Convenient SQL on managed infrastructure

Words to know

Grown-up words, in plain language.

online system
A system that answers each request as soon as possible, such as a web server or database. Judged by response time.
batch job
A job that reads a fixed, read-only input and produces output from scratch, often taking minutes to days. Judged by throughput.
derived data
Data computed from other data, so it can be thrown away and computed again.
human fault tolerance
Being able to recover from buggy code: roll the code back and rerun the job.
time travel
Keeping older versions of a dataset so you can switch back to one.
working set
The data a job needs random access to in memory, such as one counter per distinct URL.
spilling to disk
Writing sorted chunks out as segment files when memory is full, then merging them.
distributed filesystem (DFS)
A filesystem whose files are cut into blocks spread over many machines, such as HDFS.
data node
A daemon on each machine that serves the DFS blocks stored on its local disk.
metadata service
The service that knows which blocks make up each file and where they live, such as HDFS’s NameNode.
shared-nothing
Ordinary machines on an ordinary network, each with its own disks, instead of one central storage appliance.
erasure coding
Storing extra computed blocks (for example Reed–Solomon codes) so lost blocks can be rebuilt, with less overhead than full copies.
object store
Storage such as S3 that holds immutable objects under keys in a bucket, read with get and written with put.
prefix listing
Listing every key that starts with a string. It looks like a directory listing, but object stores have no directories.
data locality
Running a task on a machine that already stores its input, so only the code crosses the network.
job orchestrator
The cluster’s kernel: it runs tasks on machines and tracks their resources, as YARN and Kubernetes do.
task executor
The daemon on each node that starts tasks, watches them and sends heartbeats (NodeManager, kubelet).
resource manager
The orchestrator’s global view of every node’s hardware, status and running tasks.
gang scheduling
Starting all of a job’s tasks at the same time, or none of them.
starvation
A job that waits forever because others keep taking the resources it needs.
preemption
The scheduler killing a running task to make room for a more important one.
spot instance
A cheap, low-priority virtual machine that can be taken away at any moment.
workflow (DAG)
A graph of jobs where one job’s output is another’s input, run by Airflow, Dagster or Prefect.
backpressure
A full buffer making the producer wait until the consumer catches up.
MapReduce
A batch model with two callbacks: a mapper that emits key-value pairs, and a reducer that sees all values for one key.
dataflow engine
An engine such as Spark or Flink that runs a whole workflow of operators as one job.
shuffle
A distributed sort: every mapper’s output is partitioned by key, sorted and sent to the reducer responsible for that key. Not random at all.
sort-merge join
Joining two datasets by sorting both by the join key so matching records arrive at the same reducer together.
secondary sort
Ordering the values for one key too, for example the user record first and then events by time.
cost-based optimizer
The part of a query engine that picks join algorithms and join order from statistics about the data.
DataFrame
A table-like object you transform by calling functions such as filter, join and group by.
ETL
Extract–transform–load: copying data out of production systems, reshaping it, and loading it into a warehouse.
data lakehouse
SQL engines over files in an object store, with table formats (Iceberg) and catalogs (Unity) describing the tables.
OLAP cube
Data rolled up ahead of time along chosen dimensions so known questions are answered instantly.
batch inference
Using a trained model to make predictions for a whole dataset at once.
BSP / Pregel model
Graph processing in supersteps: every vertex sends messages along its edges, everyone waits at a barrier, then repeat.
embedding
A numeric representation of a word or token that a model can compute with.
bulk load
Building a database’s files inside the batch job and importing them in one go, such as RocksDB SST files.
DMZ
A network zone between the batch environment and production, where a stream such as Kafka can sit as a security boundary.
