Stream processing · bounded and unbounded data

The shop that never closes its books

Leilani runs an online shop. Every night at midnight a batch job counts the day’s orders and updates the sales page. A customer who orders at 01:20 waits almost a whole day to see it in the report. Run the job every hour and the wait shrinks to minutes; run it every second and it nearly disappears.

A batch job can only start when its input is bounded: a known, finished pile. But orders keep coming yesterday, today and tomorrow. That data is unbounded, so batch jobs cut it into artificial chunks. Stream processing drops the chunks and handles each event as it happens. Some operations can’t do that: a sort can’t emit its first record until it has seen the last one, because the last one might be the smallest.

Try it: in Batch vs stream, pick Daily batch and press Run the day, then try Hourly, Every second and Stream and compare the delays. In Why sort waits, press Next record a few times, then Emit smallest now to see why it’s a mistake.

What the book says

Chapter 11’s batch processing reads a set of files and produces new files: derived data that can be re-created by running the job again. It assumes the input is bounded, of a known and finite size, so the job knows when it has finished reading. The sort at the heart of MapReduce must read its entire input before producing output, because the very last input record could be the one with the lowest key.

In reality a lot of data is unbounded because it arrives gradually over time; unless you go out of business, the dataset is never “complete” in any meaningful way. So batch processors artificially divide it into chunks of fixed duration, such as a day’s or an hour’s worth of data.

With daily batches, changes in the input show up in the output a day later, which is too slow for many impatient users. You can process a second’s worth of data at the end of every second, or abandon fixed time slices and process every event as it happens. That is the idea behind stream processing.

A stream is data that is incrementally made available over time: Unix stdin and stdout, lazy lists, Java’s FileInputStream, TCP connections, audio and video over the internet. The chapter treats event streams as a data management mechanism, the unbounded counterpart to batch data.

Transmitting event streams · events, producers and topics

Are we there yet? Are we there yet?

Every time someone opens a page, Tomás’s web server writes a line: 10:02:07 GET /cart. That line is an event: a small record of one thing that happened, stamped with the time, never changed afterwards. The web server is the producer; the dashboard that reads the lines is a consumer. Lines about the same kind of thing go into a topic, the streaming version of a file name.

The simplest way to connect them is a database: the producer writes, and the consumer keeps asking “anything new?”. Ask rarely and news arrives late. Ask often and most answers are “no”, which wastes work. It is better if the consumer is simply notified when something new arrives.

Try it: in Polling, set the interval and press Run one minute. Watch the coral ticks: requests that found nothing. Drag the interval down and run again. Then switch to Notification and run the same minute.

What the book says

In stream processing a record is usually called an event: a small, self-contained, immutable object containing the details of something that happened at a point in time, usually with a timestamp from a time-of-day clock. It might be a user action such as viewing a page or making a purchase, or come from a machine, such as a temperature sensor or a CPU utilization metric. Each line of a web server log is an event.

An event may be encoded as a text string, JSON or a binary form, so it can be stored (appended to a file, inserted into a table, written to a document database) or sent over the network. It is generated once by a producer (publisher, sender) and potentially processed by multiple consumers (subscribers, recipients). Related events are grouped into a topic or stream, as a filename groups related records.

A file or database is in principle enough to connect them: each consumer periodically polls for events that appeared since it last ran, which is what a daily batch process does. But for continual processing with low delays, polling becomes expensive if the datastore isn’t designed for it: the more often you poll, the lower the percentage of requests that return new events, and the higher the overheads. It is better for consumers to be notified.

Databases have traditionally not supported notification well. Relational triggers can react to a change, but they are very limited and somewhat of an afterthought, so specialized tools were developed to deliver event notifications.

Messaging systems · producers faster than consumers

The baker is faster than the packer

Ingrid bakes six buns a second and puts them on a belt. Kofi packs three a second. The belt fills up. There are only three things to do: let extra buns fall on the floor (drop), pile them up somewhere (buffer), or tell Ingrid to stop until there is room (backpressure).

A messaging system faces the same choice whenever producers send faster than consumers process. Buffering raises its own questions. Keep the pile in memory and the system may crash when it runs out. Spill it to disk and each message gets slower. And then the disk can fill up, too.

Try it: leave the producer faster than the consumer, pick a rule and press Run 20 seconds. Try all four rules. Then slow the producer below the consumer and see every rule behave the same.

What the book says

A common way to notify consumers is a messaging system: a producer sends a message containing the event, which is pushed to consumers. A Unix pipe or TCP connection connects exactly one sender with one recipient; a messaging system lets multiple producer nodes send to the same topic and multiple consumer nodes receive from it. Within this publish/subscribe model there is no one right answer, and two questions tell systems apart.

First: what happens if producers send messages faster than consumers can process them? Broadly there are three options: drop messages, buffer them in a queue, or apply backpressure (also known as flow control), which blocks the producer from sending more. Unix pipes and TCP use backpressure: they have a small fixed-size buffer, and if it fills up, the sender is blocked until the recipient takes data out.

If messages are buffered, it matters what happens as the queue grows. Does the system crash if the queue no longer fits in memory, or does it write messages to disk? In the latter case, how does disk access affect performance, and what happens when the disk fills up?

Messaging systems · when nodes crash

A lost temperature is a shrug; a lost order is a bug

Amara’s broker carries two kinds of messages: a greenhouse sensor reporting the temperature every second, and the shop’s new orders. One night the broker crashes while it is holding a few of each.

If the broker kept them only in memory, they are gone. The thermostat display shrugs: a fresh reading arrives a second later. The order counter is now wrong for good, and nothing on the screen says so. Writing to disk, or also to a replica on another machine, keeps messages safe, but every message costs more time.

Try it: with Memory only, press Send 6 messages, then Crash broker, then Deliver. Compare the two consumers. Switch to Disk and repeat, then try Lose the machine with and without a replica.

What the book says

The second question: what happens if nodes crash or temporarily go offline, are any messages lost? As with databases, durability may require a combination of writing to disk and/or replication, which has a cost. If you can afford to sometimes lose messages, you can probably get higher throughput and lower latency on the same hardware.

Whether loss is acceptable depends on the application. With sensor readings and metrics transmitted periodically, an occasional missing data point is perhaps not important, since an updated value will be sent a short time later. But if a large number of messages are dropped, it may not be immediately apparent that the metrics are incorrect. If you are counting events, reliable delivery matters more, since every lost message means incorrect counters.

Batch processing provides a strong reliability guarantee: failed tasks are automatically retried and partial output from failed tasks is discarded, so the output is the same as if no failures had occurred. The chapter later examines how to provide similar guarantees for streams.

Messaging systems · direct messaging from producers to consumers

Shouting across the room, with nobody taking notes

Some systems skip the middleman and send straight from producer to consumer. A stock exchange shouts prices to every trader at once over UDP multicast; if a packet goes missing, a trader notices the gap in the numbers and asks the exchange to repeat it, which only works if the exchange remembers what it sent. Metrics agents like StatsD send counters over UDP and never find out what was lost. A webhook is a URL one service gives another: “call me here when something happens.”

These work well when everybody is online. But if the consumer is away, it misses what was sent. And if the producer crashes while holding messages it meant to retry, those are gone too.

Try it: in UDP feed, press Send 8 prices with retransmit off, then on. In StatsD, raise the loss and press Count 20 orders. In Webhook, take the shop offline, send a few events, then press Crash sender before the shop comes back.

What the book says

A number of messaging systems use direct network communication between producers and consumers, without intermediary nodes. UDP multicast is widely used in the financial industry for streams such as stock market feeds, where low latency is important; UDP itself is unreliable, but application-level protocols can recover lost packets, as long as the producer remembers the packets it has sent so it can retransmit them on demand.

Brokerless messaging libraries such as ZeroMQ and nanomsg take a similar approach, implementing publish/subscribe over TCP or IP multicast. Some metrics agents, such as StatsD, use unreliable UDP messaging; counter metrics are correct only if all messages are received, so UDP makes them at best approximate. If the consumer exposes a service, producers can make a direct HTTP or RPC request; that is the idea behind webhooks, a callback URL of one service registered with another, which calls it whenever an event occurs.

These systems work well where they are designed for, but the application code must be aware of possible message loss, and the faults they tolerate are limited. Even protocols that retransmit lost packets generally assume producers and consumers are constantly online. An offline consumer may miss messages; producer retries break down if the producer crashes and loses the buffer of messages it was supposed to retry.

Messaging systems · message brokers

A post office that holds your mail while you’re away

Instead of handing parcels to each other, Wei and Sofia both use the post office. Wei drops a parcel off, gets a receipt, and walks away; he doesn’t wait for Sofia to open it. If Sofia is on holiday, the post office keeps her parcels until she’s back.

A message broker is that post office: a server, a bit like a database built for messages, that producers and consumers connect to. Clients can come and go, and keeping messages safe becomes the broker’s job. Because the producer only waits for the broker’s receipt, the consumer is asynchronous: delivery happens later, usually within a fraction of a second, sometimes much later if a queue has built up.

Try it: press Send 3 and watch the producer get its receipt before delivery. Press Consumer offline, send more, then bring it back. Fill the queue again and press Crash broker, first with Memory, then with Disk.

What the book says

A widely used alternative is to send messages via a message broker (also known as a message queue), which is essentially a kind of database optimized for handling message streams. It runs as a server, with producers and consumers connecting to it as clients. Producers write messages to the broker, and the broker delivers them to consumers.

By centralizing the data in the broker, these systems can more easily tolerate clients that connect, disconnect and crash, and the question of durability is moved to the broker. Some brokers only keep messages in memory, while others (depending on configuration) write them to disk so they are not lost in a broker crash. Faced with slow consumers, they generally allow unbounded queueing rather than dropping messages or backpressure, though this may depend on configuration.

A consequence of queueing is that consumers are generally asynchronous: a producer normally waits only for the broker to confirm it has buffered the message, not for the message to be processed. Delivery happens at an undetermined future point, often within a fraction of a second, but sometimes significantly later if there is a queue backlog.

Message brokers · compared to databases

A filing cabinet and a letterbox

A database is a filing cabinet: you put papers in, they stay until someone throws them out, and you can search the drawers any way you like. A traditional message broker is a letterbox: letters pass through, and once collected they’re gone. Both store data, but they behave very differently.

Four differences matter. Brokers delete a message once it’s delivered. They expect their queues to be short, and slow down when they aren’t. You pick data from a broker by subscribing to topics that match a pattern, not with rich queries. And a database answers once and forgets you, while a broker tells you every time something new arrives.

Try it: step through the four tabs. In Deletion, press Read everything twice. In Queue length, drag the slider past the memory line. In Selecting, run the query and the subscription. In Freshness, read first, then press Someone updates the stock.

What the book says

Some message brokers can even participate in two-phase commit protocols using XA or JTA, which makes them quite similar to databases, but there are important practical differences. Databases usually keep data until it is explicitly deleted, whereas some brokers automatically delete a message when it has been successfully delivered, so they are not suitable for long-term storage. Since they quickly delete messages, most brokers assume their working set is fairly small: if they must buffer a lot of messages (perhaps spilling to disk), each message takes longer to process and overall throughput may degrade.

Databases often support secondary indexes and a query language, while brokers often support subscribing to a subset of topics matching a pattern. Both let a client select the data it wants, but databases typically offer much more advanced querying.

A database query result is typically based on a point-in-time snapshot; if another client later changes the data, the first client doesn’t find out unless it queries again or polls. Brokers don’t support arbitrary queries or updates to sent messages, but they do notify clients when new messages become available.

This is the traditional view of message brokers, encapsulated in standards like JMS and AMQP and implemented in RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO Enterprise Message Service, IBM MQ, Azure Service Bus and Google Cloud Pub/Sub. It is possible to use databases as queues, but tuning them for good performance is not straightforward.

Message brokers · multiple consumers

Share the tickets, or print one for everybody?

Lucía runs a pizza kitchen. Order tickets arrive on one rail, and three cooks stand by it. Each ticket should be cooked once, so whoever is free takes the next one. Add a fourth cook and the rail empties faster. That is load balancing: every message goes to one of the consumers, and they share the work.

But the accountant also needs every ticket, and so does the delivery planner. They don’t share; each wants its own copy of all of them. That is fan-out: every message goes to every consumer, like several radios tuned to the same station. Kafka’s consumer groups mix both: inside a group the tickets are shared, and every group gets the whole stream.

Try it: in Load balancing, press Publish 6 messages and count each cook’s tickets, then Add consumer and publish again. Switch to Fan-out and see the deliveries triple. In Consumer groups, the kitchen shares and accounting gets everything.

What the book says

When multiple consumers read messages in the same topic, two main patterns are used (Figure 12-1). With load balancing, each message is delivered to one of the consumers, so they share the work of processing the topic; the broker may assign messages to consumers arbitrarily. It is useful when messages are expensive to process and you want to add consumers to parallelize. In AMQP you get it by having several clients consume from the same queue; in JMS it is called a shared subscription.

With fan-out, each message is delivered to all of the consumers, so several independent consumers can each “tune in” to the same broadcast without affecting one another: the streaming equivalent of several batch jobs reading the same input file. JMS provides it with topic subscriptions, AMQP with exchange bindings.

The two patterns can be combined, for example with Kafka’s consumer groups. When a consumer group subscribes to a topic, each message is sent to one consumer in the group. If two separate groups subscribe to the same topic, each message is sent to one consumer in each group.

Message brokers · acknowledgments and redelivery

The courier who fainted holding parcel 3

Tomasz and Ngozi take parcels from the same depot. The depot only crosses a parcel off its list when the courier phones back “delivered”. That phone call is an acknowledgment. If Ngozi faints holding parcel 3 and never calls, the depot assumes it wasn’t delivered and gives it to Tomasz, so nothing is lost.

There is a catch. Tomasz was already carrying parcel 4, so he delivers 4 before 3: sharing work plus redelivery reorders messages. And if Ngozi did deliver parcel 3 but her phone call was lost, Tomasz delivers it a second time. Giving each courier their own separate list avoids the reordering, at the cost of waiting for the fainted courier.

Try it: press Run the story to replay Figure 12-2 and read consumer 1’s order. Then step through it yourself with Step, clicking a consumer to crash it while it holds a message. Try Lost ack for a duplicate, and Queue per consumer for order without reordering.

What the book says

Consumers may crash at any time, so a broker could deliver a message to a consumer that never processes it, or only partially processes it. To make sure the message is not lost, brokers use acknowledgments: a client must explicitly tell the broker when it has finished processing a message so that the broker can remove it from the queue.

If the connection to a client closes or times out without an acknowledgment, the broker assumes the message was not processed and delivers it again to another consumer. The message may in fact have been fully processed and only the acknowledgment lost in the network; handling that case requires an atomic commit protocol, unless the operation was idempotent or exactly-once semantics are not required.

Combined with load balancing, redelivery reorders messages (Figure 12-2): consumer 2 crashes while processing m3, at the same time as consumer 1 is processing m4; m3 is redelivered to consumer 1, which processes m4, m3, m5. Even if the broker otherwise tries to preserve order, as both JMS and AMQP require, load balancing with redelivery inevitably reorders messages. To avoid it you can use a separate queue per consumer.

Reordering is not a problem if messages are completely independent of each other, but it can be important if there are causal dependencies between them.

Acknowledgments and redelivery · dead letter queues

The letter that knocks out every postman

One payment message was written by a buggy producer: it says {"user": 7} and forgot the amount. The consumer that picks it up crashes. No acknowledgment, so the broker hands it to the next consumer, which crashes too. Round and round, for ever.

If the broker insists on strict order, nothing behind the bad message ever moves. If it lets others overtake, the queue keeps flowing, but the poison message burns a consumer every few seconds. The fix is a dead letter queue: after a few failed tries, move the message aside, unblock everyone, and ring an alarm, because any message in that queue is an error a person must look at.

Try it: pick Strict order and press Run the queue: the line jams. Try Reordering: the rest gets through but the crashes never stop. Then DLQ after 3 tries, and once the alarm rings, choose what the operator does: Drop it, Fix & resend or Patch the consumer.

What the book says

Redelivery can also result in wasted resources, resource starvation or permanent blockages in a stream. A common scenario is a producer that improperly serializes a message, for example by leaving out a required key in a JSON-encoded object. If that message causes a consumer to crash and restart, it won’t acknowledge the message, so the broker resends it, which causes another consumer to fail, indefinitely.

If the broker guarantees strong ordering, no further progress can be made. Brokers that allow message reordering can continue to make progress, but they waste resources on messages that will never be acknowledged.

Dead letter queues (DLQs) handle this: rather than keeping the message in the current queue and retrying forever, it is moved to a different queue to unblock consumers. Monitoring is usually set up on DLQs, since any message in the queue is an error. An operator can then permanently drop it, manually modify and reproduce it, or fix the consumer code to handle it.

DLQs are common in most queuing systems, and log-based messaging systems such as Apache Pulsar and stream processing systems such as Kafka Streams now support them as well.

Log-based message brokers · reading that destroys

A notice board that eats its notes

At Rahul’s school, notes are pinned to a board and the board throws each note away the moment someone reads it and says “got it”. Convenient for keeping the board tidy. But a new pupil who arrives in March can never read September’s notes, and if Rahul misread a note, he can’t read it again: it’s gone.

Traditional AMQP/JMS-style brokers work like that board: a phone call or a network packet leaves no trace, and they inherited that transient mindset. Databases and files work the other way: what you write stays until someone deletes it, so a batch job can be run again and again on the same input. Combine the two, durable storage plus instant notifications, and you get a log-based message broker.

Try it: press Publish 4 orders, then Add a late consumer and Rerun A with fixed code. Switch to Log-based broker and do the same three things.

What the book says

Sending a packet over a network or making a request to a network service is normally a transient operation that leaves no permanent trace. AMQP/JMS-style message brokers inherited this transient messaging mindset: even though they may write messages to disk, they quickly delete them again after they have been delivered. Databases and filesystems take the opposite approach: everything written is normally expected to be permanently recorded, until someone explicitly chooses to delete it.

This difference matters for derived data. A key feature of batch processes is that you can run them repeatedly, experimenting with the processing steps, without risk of damaging the read-only input. With AMQP/JMS-style messaging, receiving a message is destructive if the acknowledgment causes it to be deleted from the broker, so you cannot run the same consumer again and expect to get the same result.

A new consumer typically starts receiving only messages sent after it was registered; prior messages are already gone. With files and databases, a new client can read data written arbitrarily far in the past. Why not a hybrid, combining the durable storage approach of databases with the low-latency notification facilities of messaging? That is the idea behind log-based message brokers.

Log-based message brokers · using logs for message storage

Three notebooks, numbered pages, no eraser

Mei keeps the club’s news in notebooks. New news goes on the next line, never in between, and lines are never erased. Each line has a number, its offset. A reader just reads line after line, and at the last line waits for more, like tail -f on a file.

One notebook can only be written so fast, so Mei splits the topic into three notebooks kept on three different shelves. Each is a partition with its own offsets 0, 1, 2… Inside one partition the order is perfect. Across partitions there is no order at all: a reader that merges them can see message #5 before message #2.

Try it: press Send 6 messages (numbered #1 to #6 in the order they were sent) and watch the consumer merge the three partitions. Every partition stays in order, the merged list doesn’t. Send more and count the out of send order stat.

What the book says

A log is simply an append-only sequence of records on disk, the same structure as log-structured storage engines and write-ahead logs, replication logs, and consensus. A producer sends a message by appending it to the end of the log, and a consumer receives messages by reading the log sequentially. If it reaches the end, it waits for a notification that a new message has been appended, much as tail -f watches a file.

To scale beyond a single disk, the log can be sharded: shards hosted on different machines, each a separate log read and written independently, with a topic defined as a group of shards carrying messages of the same type (Figure 12-3). Within each shard, which Kafka calls a partition, the broker assigns a monotonically increasing sequence number, or offset, to every message. Messages within a partition are totally ordered; there is no ordering guarantee across different partitions.

Apache Kafka and Amazon Kinesis Streams are log-based brokers that work like this; Google Cloud Pub/Sub is architecturally similar but exposes a JMS-style API. Even though they write all messages to disk, they achieve throughput of millions of messages per second by sharding across machines, and fault tolerance by replicating messages.

Log-based message brokers · logs compared to traditional messaging

Whole notebooks, not single pages

A log broker doesn’t deal out single messages. It hands each consumer in a group whole partitions, and the consumer reads them line by line on one thread. Fan-out is free, since reading deletes nothing. But Olu can hire five readers for three notebooks and two of them will sit idle: the number of partitions caps the parallelism.

And one hard message stalls its whole notebook. If line 3 takes ages, lines 4, 5 and 6 wait behind it: head-of-line blocking. A traditional queue would let another consumer grab line 4. The log’s reward is order: route every event of one user to the same partition with a partition key, and that user’s events are always processed in the order they happened.

Try it: in Consumers vs shards, drag the consumers slider to 5 and press Process a round. In Head-of-line, press Process 6 messages and compare the two lanes. In Partition key, press Send 9 events with a random partition, then with key = user.

What the book says

The log-based approach trivially supports fan-out, because several consumers can read the log independently: reading does not delete. To balance load across a consumer group, the broker assigns entire shards to nodes in the group, and each client typically reads the messages of its shards sequentially, in a single thread. This coarse-grained approach has downsides.

The number of nodes sharing the work can be at most the number of shards. (Two consumers could both read everything, one handling even-numbered offsets and the other odd ones, or you could use a thread pool, but that complicates consumer offset management; in general, single-threaded processing of a shard is preferable, and parallelism comes from more shards.) And if a single message is slow to process, it holds up the subsequent messages in that shard, a form of head-of-line blocking.

So when messages may be expensive to process, you want to parallelize message by message, and ordering is not so important, the JMS/AMQP style is preferable. With high message throughput, fast messages and important ordering, the log-based approach works very well. The distinction is blurring: Kafka now supports JMS/AMQP-style consumer groups that let multiple consumers receive messages from the same partition.

Since order is preserved only within a shard, messages that need consistent ordering must be routed to the same shard, for example by choosing the shard from the user ID, which makes the user ID the partition key.

Log-based message brokers · consumer offsets

A bookmark you only write down now and then

Priya reads a long logbook. She doesn’t tick every line; she just knows that everything above her finger is done. Every few lines she writes her place on a sticky note at the front desk. That note is her committed offset, and it is much cheaper than ticking off every single line.

Then Priya falls ill. Farid takes over her logbook and opens it at the sticky note, not where her finger was. The lines between the note and her finger get read twice. Commit more often and fewer lines repeat, at the cost of more bookkeeping. It is exactly how a database follower uses the leader’s log sequence number to catch up after a disconnect.

Try it: set commit every to 4 and press Run the story: Priya processes, crashes, and Farid takes over at the committed offset. Count the duplicates, set the slider to 1 and run it again. Or use Process next and Crash Priya yourself.

What the book says

Consuming a shard sequentially makes it easy to tell which messages have been processed: all messages with an offset less than a consumer’s current offset have been, and all with a greater offset have not yet been seen. So the broker does not need to track acknowledgments for every single message, only to periodically record the consumer offsets. The reduced bookkeeping overhead and the opportunities for batching and pipelining help increase the throughput of log-based systems.

If a consumer fails, however, it will resume from the last recorded offset rather than the more recent last offset it saw, so it can see some messages twice. If a consumer node fails, another node in the consumer group is assigned the failed consumer’s shards and starts consuming at the last recorded offset; messages processed but not yet recorded are processed a second time.

The offset is very similar to the log sequence number found in single-leader database replication, which lets a follower reconnect to a leader after a disconnection and resume replication without skipping any writes. Exactly the same principle applies: the message broker behaves like a leader database, and the consumer like a follower.

A notebook with a fixed number of pages

Aiko’s café keeps its order log in a binder that holds four sections. When a fifth section starts, the oldest one is taken out. Usually nobody minds, because every reader finished those pages long ago. But a reader who dozed off on page 3 wakes up to find page 3 gone.

A log-based broker works the same way. It splits each log into segments, and from time to time it deletes the oldest one or moves it to cheaper archive storage. So the log is really a bounded buffer that throws old messages away when it is full: a ring buffer. Because it lives on disk, though, it is huge. At full speed, a 20 TB drive takes about 22 hours to fill.

Try it: press Produce a segment four times. The fast reader keeps up; the slow reader reads one message per segment. When segment 0 is deleted, look at what the slow reader missed. Then set old segments to tier to object storage and do it again. Finally open Back of the envelope and move the sliders.

What the book says

If you only ever append to the log, you will eventually run out of disk space. To reclaim it, the log is divided into segments, and from time to time old segments are deleted or moved to archive storage. (Log compaction, a more sophisticated way of freeing space, comes later in the chapter.)

So a slow consumer that falls so far behind that its offset points to a deleted segment will miss some messages. Effectively, the log implements a bounded-size buffer that discards old messages when it gets full, also known as a circular buffer or ring buffer. Since that buffer is on disk, it can be quite large.

A back-of-the-envelope calculation: a typical large hard drive has a capacity of 20 TB and a sequential write throughput of 250 MB/s. Writing at the fastest possible rate, it takes about 22 hours until the drive is full. So a disk-based log can always buffer at least 22 hours’ worth of messages, even with many disks on many machines, because more disks increase both the space and the total write bandwidth. In practice deployments rarely use the full write bandwidth, so the log can typically keep several days’ or even weeks’ worth of messages.

Many log-based brokers now store messages in object storage. Apache Kafka and Redpanda serve older messages from object storage as part of their tiered storage; WarpStream, Confluent Freight and Bufstream store all their data in the object store. Besides cost efficiency, the messages are stored as Iceberg tables, so batch and data warehouse jobs can run directly on them without copying them into another system.

What the book says

Of the three choices for a consumer that can’t keep up with the producer (dropping messages, buffering, or applying backpressure), the log-based approach is a form of buffering with a large but fixed-size buffer, limited by the available disk space.

If a consumer falls so far behind that the messages it requires are older than those retained on disk, it will not be able to read them, so the broker effectively drops old messages that go back further than the buffer can hold. You can monitor how far a consumer is behind the head of the log and raise an alert if it falls behind significantly. As the buffer is large, there is enough time for a human operator to fix the slow consumer and let it catch up before it starts missing messages.

Even if a consumer does start missing messages, only that consumer is affected; it does not disrupt the service for other consumers. This is a big operational advantage: you can experimentally consume a production log for development, testing or debugging without worrying much about disrupting production services. When a consumer is shut down or crashes, it stops consuming resources; the only thing that remains is its consumer offset.

This contrasts with traditional message brokers, where you need to be careful to delete any queues whose consumers have been shut down, to avoid them accumulating messages and taking away memory from active consumers.

What the book says

With AMQP- and JMS-style message brokers, processing and acknowledging messages is a destructive operation, since it causes the messages to be deleted on the broker. This makes log-based messaging more like batch processing, where derived data is clearly separated from input data through a repeatable transformation process. It allows more experimentation and easier recovery from errors and bugs, making it a good tool for integrating dataflows within an organization.

Databases and streams · the replication log is a stream

Two copies agree if they hear the same story

Log-based brokers borrowed an idea from databases. Now turn it round: every write to a database is an event, such as deposit 50. A leader’s replication log is exactly such a stream of write events, and its followers stay in step by applying it to their own copy.

That is the state machine replication principle. If every replica processes the same events in the same order, and processing an event is deterministic, they all end up in the same state. Break either condition and the copies drift apart, without any error.

Try it: press Replicate. Then set replica B’s order to swapped and replicate again; then set event 4 to now() on each replica. Put both back and the copies agree again.

What the book says

Log-based message brokers took ideas from databases and applied them to messaging. We can also do the opposite. One approach is to use an event stream as the system of record, as in event sourcing: instead of a data model that is mutated by updates and deletes, every state change is an immutable event written to an append-only log, and read-optimized materialized views are derived from it. Log-based brokers configured never to delete old events suit this well.

You don’t have to go as far as event sourcing: even with mutable data models, every write to a database is an event that can be captured, stored and processed.

A replication log is a stream of database write events, produced by the leader as it processes transactions. The followers apply that stream to their own copy of the database and so end up with an accurate copy of the same data.

The state machine replication principle says: if every event represents a write to the database, and every replica processes the same events in the same order, then the replicas will all end up in the same final state (processing an event is assumed to be deterministic). “It’s just another case of event streams!”

What the book says

No single system can satisfy all data storage, querying and processing needs, so most nontrivial applications combine an OLTP database, a cache, a full-text index and a data warehouse, each with its own copy of the data in its own representation. If an item is updated in the database, it also needs to be updated in the others. Data warehouses are usually synchronized by ETL processes, often a full copy of the database, transformed and bulk-loaded: a batch process.

If periodic full dumps are too slow, an alternative is dual writes: the application code explicitly writes to each system when data changes, for example first the database, then the search index, then invalidating cache entries (or all of them concurrently).

Dual writes have serious problems. In Figure 12-4 two clients concurrently update X, one to A and one to B. The database sees A then B, so its final value is B; the search index sees B then A, so its final value is A. The two systems are now permanently inconsistent with each other, even though no error occurred. Unless you have an additional concurrency detection mechanism, such as version vectors, you will not even notice.

Another problem is that one write may fail while the other succeeds. Ensuring both succeed or both fail is the atomic commit problem, which is expensive to solve (two-phase commit). With a single leader, the leader determines the order of writes; here the database and the index may each have a leader, but neither follows the other, so conflicts occur as in multi-leader replication. It would be better if the search index were a follower of the database.

What the book says

Most databases’ replication logs have long been considered an internal implementation detail, not a public API: clients are supposed to use the data model and query language, not parse the replication logs. For decades many databases had no documented way of getting the log of changes, which made it difficult to replicate them to a search index, cache or data warehouse.

Change data capture (CDC) is the process of observing all data changes written to a database and extracting them in a form in which they can be replicated to other systems. It is especially interesting if changes are made available as a stream, immediately as they are written.

If the log of changes is applied in the same order, you can expect the data in the search index to match the data in the database. The search index and any other derived data systems are just consumers of the change stream.

What the book says

The log consumers are derived data systems: the data in the search index and the data warehouse is just another view onto the data in the system of record. CDC ensures that all changes made to the system of record are also reflected in them. Essentially, CDC makes one database the leader (the one from which changes are captured) and turns the others into followers. A log-based message broker is well suited to transporting the change events, since it preserves the ordering of messages (avoiding the reordering issue of Figure 12-2).

Logical replication logs can be used to implement CDC, although it comes with challenges, such as handling schema changes and properly modeling updates. The Kafka Connect framework offers CDC connectors as well. Maxwell does something similar for MySQL by parsing the binlog, GoldenGate for Oracle, and pgcapture for PostgreSQL.

Like message brokers, CDC is usually asynchronous: the system-of-record database does not wait for a change to be applied to consumers before committing it. Adding a slow consumer then does not affect the system of record too much, but all the issues of replication lag apply.

Change data capture · log compaction

Keep only the newest line for each cat

Mateo’s video site logs a play count every time a cat video is watched: mew: 1, then mew: 2, then mew: 3. Each new line makes the older ones for the same key pointless, yet the log keeps all of them and grows forever.

Log compaction runs in the background. It looks for records with the same key, throws away the duplicates and keeps only the most recent one, then merges the shrunken segments. To delete a key you append a tombstone, a record whose value is null, and compaction removes the key altogether. The log’s size now depends on how many keys exist, not on how many writes ever happened, so a brand-new consumer can read it from offset 0 and get a full copy of the data.

Try it: press Play videos a few times: the log grows, but there are still only four keys. Press Compact and follow the pseudocode. Then press Delete yawn, Compact again, and New consumer from offset 0.

What the book says

If you can keep only a limited amount of log history, you need to go through the snapshot process every time you add a new derived data system. Log compaction is a good alternative. The principle is the same as in log-structured storage engines: periodically look for log records with the same key, throw away any duplicates, and keep only the most recent update for each key. Segments become much smaller, so they may also be merged as part of compaction, which runs in the background (Figure 12-6 is a log of cat video IDs, mew, purr, scratch and yawn, with their play counts).

An update with a special null value, a tombstone, indicates that a key was deleted and causes it to be removed during compaction. As long as a key is not overwritten or deleted, it stays in the log forever. The disk space needed for a compacted log depends only on the current contents of the database, not on the number of writes that have ever occurred.

The same idea works for log-based message brokers and CDC: if every change has a primary key and every update for a key replaces the previous value, it is enough to keep the most recent write for each key. To rebuild a derived data system such as a search index, start a new consumer from offset 0 of the log-compacted topic. The log is guaranteed to contain the most recent value for every key (and maybe some older values), so you get a full copy of the database contents without taking another snapshot of the CDC source.

Apache Kafka supports log compaction, which lets the message broker be used for durable storage, not just transient messaging.

Three notebooks and no single story

With PostgreSQL or MySQL there is one leader, and its replication log is the story of every write, in commit order. Subscribing to changes means reading that one log, and databases now offer it on purpose, as a public change stream interface instead of something you reverse-engineer.

Cassandra has no leader. Each write is stored by a quorum of nodes, say two out of three, so every node’s log holds a different subset of the writes. Read one node and you miss writes. Glue all three logs together and you get every write twice, out of order. Cassandra hands you the raw per-node logs, and the consumer has to merge them like a quorum reader: collect, drop copies of the same write, put them in order.

What the book says

Most popular databases now expose change streams as a first-class interface, rather than the retrofitted and reverse-engineered CDC efforts of the past. Relational databases such as MySQL and PostgreSQL typically send changes through the same replication log they use for their own replicas. Most cloud vendors offer CDC for their products as well; for example, Datastream offers streaming data access for Google Cloud’s relational databases and data warehouses.

Even eventually consistent, quorum-based databases such as Cassandra now support CDC. Clients must persist writes to a majority of nodes before they’re considered visible, so CDC for quorum writes is challenging: there’s no single source of truth to subscribe to, and whether data is visible depends on each reader’s consistency preferences.

Cassandra sidesteps this by exposing raw log segments for each node rather than a single stream of mutations. Systems that consume the data must read each node’s raw log segments and decide how best to merge them into a single stream, much as a quorum reader does.

What the book says

Like CDC, event sourcing stores all changes to the application state as a log of change events; the biggest difference is the level of abstraction. In CDC the application uses the database in a mutable way, updating and deleting records at will. The log of changes is extracted from the database at a low level (for example by parsing the replication log), which ensures that the order of writes extracted matches the order in which they were actually written.

In event sourcing, the application logic is explicitly built on immutable events written to an event log. The event store is append-only, and updates or deletes of events are discouraged or prohibited. Events reflect things that happened at the application level rather than low-level state changes.

Adopting event sourcing is a big change for an application that is not already doing it. CDC can be added to an existing database with minimal changes; the application writing to the database might not even know that CDC is occurring.

Log compaction differs too. A CDC event for an update typically contains the entire new version of the record, so the most recent event for a primary key determines its value and earlier events for that key can be discarded. With event sourcing, an event expresses the intent of a user action, so later events typically do not override prior ones, and you need the full history to reconstruct the final state. Event-sourced applications store snapshots of the derived state, but only as a performance optimization for reads and crash recovery.

What the book says

CDC appears easier to adopt than event sourcing, but it has its own challenges. In a microservices architecture, a database is typically accessed by only one service; other services go through that service’s public API. This makes the database an internal implementation detail, so developers can change its schema without affecting the public API.

CDC systems, however, typically use the upstream database’s schema when replicating its data, which turns these schemas into public APIs that must be managed much like the service’s public API. Removing a column breaks downstream consumers that depend on that field. Such problems used to affect mainly data warehouse ETL, but CDC streams may be consumed by other production services, so a breakage can cause a customer-facing outage. Data contracts are often used to prevent these breakages.

The outbox pattern decouples internal from external schemas. Outboxes are tables with their own schemas, exposed to the CDC system instead of the internal domain model, so developers can modify internal schemas while leaving outbox tables untouched. This might look like a dual write, and it is, but keeping both writes in the same system, the database, lets them appear in a single transaction.

The trade-offs: developers must still maintain the transformation between their internal and outbox schemas, which can be challenging, and an outbox increases the amount of data the database has to write to its underlying storage, which might trigger performance problems.

What the book says

Batch processing benefits from the immutability of its input files, and the same principle makes event sourcing and CDC powerful. We normally think of databases as storing the current state of the application, a representation optimized for reads; because state changes, databases support updating and deleting data as well as inserting it.

Whenever state changes, it is the result of the events that mutated it over time: the currently available seats are the result of the reservations processed, the account balance of the credits and debits, the response time graph of the individual requests. Mutable state and an append-only log of immutable events do not contradict each other; they are two sides of the same coin. Mathematically, the application state is what you get when you integrate an event stream over time, and a change stream is what you get when you differentiate the state by time (Figure 12-7). The analogy has limitations (the second derivative of state does not seem to be meaningful), but it’s a useful starting point.

Storing the changelog durably makes the state reproducible. As Jim Gray and Andreas Reuter put it in 1992: “There is no fundamental need to keep a database at all; the log contains all the information there is. The only reason for storing the database (i.e., the current end-of-the-log) is performance of retrieval operations.” Log compaction is one way of bridging the distinction between log and database state.

Accountants never use an eraser

Olu’s shop charged a customer twice for the same pair of shoes. An accountant doesn’t rub out the second charge. They add a new line, a refund of the same amount. The mistake stays in the ledger next to its fix, so anyone can see exactly what happened.

The same habit saves software. If buggy code overwrites rows in place, the old values are simply gone. If it can only append events, you can find the bad ones and rebuild. And a log remembers what the current state forgets: a shopper who put a mug in the cart and took it out again leaves no trace in the cart, but the log knows they almost bought it.

What the book says

Immutability in databases is an old idea: accountants have used it for centuries in financial bookkeeping. When a transaction occurs, it is recorded in an append-only ledger, essentially a log of events describing money, goods or services that have changed hands. The accounts, such as profit and loss or the balance sheet, are derived from the ledger by adding the transactions up.

If a mistake is made, accountants don’t erase or change the incorrect transaction. They add another transaction that compensates for the mistake, for example refunding an incorrect charge. The incorrect transaction remains in the ledger forever, because it might be important for auditing; if incorrect figures have already been published, the next accounting period’s figures include a correction.

Auditability helps many systems that are not strictly regulated. If you accidentally deploy buggy code that writes bad data to a database, recovery is much harder if the code can destructively overwrite data; with an append-only log of immutable events, diagnosing what happened and recovering is much easier. Customer service can use an audit log to diagnose customer requests and complaints.

Immutable events also capture more information than the current state. A customer may add an item to their cart and then remove it again; the second event cancels the first for order fulfillment, but analytics may want to know the customer was considering that item. The event log records this; a database that deletes items when they are removed from the cart loses it.

By separating mutable state from the immutable event log, you can derive several read-oriented representations from the same log of events. This works just like having multiple consumers of a stream (Figure 12-5): the analytical database Druid ingests directly from Kafka this way, and Kafka Connect sinks can export data from Kafka to various databases and indexes.

An explicit translation step from an event log to a database makes it easier to evolve your application over time. To present existing data in a new way, use the event log to build a separate read-optimized view for the new feature and run it alongside the existing systems without modifying them. Running old and new systems side by side is often easier than a complicated schema migration; once readers have switched, you can shut the old system down and reclaim its resources.

This is the idea of CQRS: write data in one write-optimized form, then translate it into different read-optimized representations. It doesn’t require event sourcing; you can build multiple materialized views from a stream of CDC events too.

Traditional database and schema design is based on “the fallacy that data must be written in the same form as it will be queried.” Debates about normalization and denormalization become largely irrelevant if you can translate data from a write-optimized event log to read-optimized application state; denormalizing the views is entirely reasonable, because the translation process keeps them consistent with the log. Social network home timelines are an example: highly denormalized, since your posts are duplicated in all your followers’ timelines, but the fan-out service keeps that duplicated state in sync.

What the book says

The biggest downside of CQRS is that consumers of the event log are usually asynchronous, so a user could write to the log, then read from a derived view and find that their write has not yet been reflected (see “Reading your own writes”). Updating the read view synchronously with the append would require a distributed transaction across the log and the view, or some way of waiting until an event has been reflected in the view. Both are usually impractical, so views are normally updated asynchronously.

On the other hand, deriving the current state from an event log simplifies some aspects of concurrency control. Much of the need for multi-object transactions stems from a single user action requiring data to be changed in several places. With event sourcing, you can design an event to be a self-contained description of a user action, which then requires only a single write in one place, appending the event to the log, which is easy to make atomic.

If the event log and the application state are sharded in the same way (processing an event for a customer in shard 3 only updates shard 3 of the state), a straightforward single-threaded log consumer needs no concurrency control for writes: it processes one event at a time. The log removes the nondeterminism of concurrency by defining a serial order of events in a shard. Events that touch several state shards need more work, discussed in Chapter 13.

Many systems that don’t use an event-sourced model still rely on immutability for concurrency control: databases use immutable data structures or multiversion data for point-in-time snapshots, and version control systems such as Git, Mercurial and Fossil rely on immutable data to preserve the history of files.

State, streams and immutability · limitations of immutability

The diary that can’t forget

Keeping every event forever is easy when data mostly grows: a shop’s orders. It is painful when a few things change all the time: five delivery vans reporting their position every second. The history becomes enormous while the current state stays tiny, and compaction and garbage collection have to keep up.

Then Lena asks to be forgotten, as privacy law allows. Appending “Lena was deleted” leaves her email in every old event, and copies hide on SSDs and in backups. One trick is crypto-shredding: store her data encrypted and, to delete it, throw away the key. But which data shares a key has to be decided before anything is written.

Try it: in Churn, press Run 40 writes for each workload and compare history with state. In Delete Lena, try Append a delete event, then Excise from the log, and count the copies left. In Crypto-shred, pick a key granularity and press Shred Lena’s key.

What the book says

How feasible it is to keep an immutable history of all changes forever depends on the amount of churn in the dataset. Workloads that mostly add data and rarely update or delete are easy to make immutable. Workloads with a high rate of updates and deletes on a comparatively small dataset may see the immutable history grow prohibitively large, fragmentation may become an issue, and the performance of compaction and garbage collection becomes crucial for operational robustness.

You may also need data deleted for administrative or legal reasons: privacy regulations such as the GDPR require that a user’s personal information be deleted and erroneous information be removed on demand, or an accidental leak may need to be contained. Appending another event that says the prior data should be considered deleted is not sufficient; you want to rewrite history as if the data was never written. Datomic calls this excision, and the Fossil version control system has a similar concept called shunning.

Truly deleting data is surprisingly hard, since copies can live in many places: storage engines, filesystems and SSDs often write to a new location rather than overwriting in place, and backups are often deliberately immutable.

Crypto-shredding stores data you may want to delete encrypted, and deletes it by forgetting the key. This moves the problem around: the key storage is mutable, and you must decide up front which data shares a key, because you can later shred all or none of the data encrypted with one key. A key per data item would make key storage as big as the data. Puncturable encryption can selectively revoke a key’s decryption abilities, but is not yet widely used. Overall, deletion is more a matter of “making it harder to retrieve the data” than actually making it impossible.

The conveyor belt with no last parcel

What the book says

Streams come from user activity events, sensors and writes to databases, and are transported through direct messaging, message brokers and event logs. Once you have a stream, you can broadly do three things with it: (1) write the data to a database, cache, search index or similar storage system, where other clients can query it, which is a good way of keeping a database in sync, especially if the stream consumer is its only writer; (2) push events to users, by email alerts, push notifications or a real-time dashboard, so a human is the ultimate consumer; (3) process one or more input streams to produce one or more output streams, possibly through a pipeline of several stages before ending up at option 1 or 2.

A piece of code that processes streams like this is an operator or a job. It is closely related to Unix processes and MapReduce jobs, and the dataflow is similar: it consumes input streams in a read-only fashion and writes its output to a different location in an append-only fashion. Sharding and parallelization, and basic mapping operations such as transforming and filtering, work as in batch processing.

The crucial difference from batch jobs is that a stream never ends. Sorting does not make sense with an unbounded dataset, so sort-merge joins cannot be used. Fault-tolerance mechanisms must change too: a batch task that has run for a few minutes can be restarted from the beginning, but restarting a stream job that has run for several years may not be a viable option.

A question that waits for the answer to walk past

A thief who steals a card number often tests it first with two tiny payments, then makes one big purchase. For each card the engine remembers how far into the pattern it has got, a little state machine, and when the last step matches it emits a new, complex event: possible fraud on card 4417. A database does the opposite: it keeps the data and forgets each query as soon as it has answered it.

Try it: press Next event a few times and follow each card’s token along the states and the lit line of the query. Press Play the rest. Then make your own attack on card 4417 with €1 test charge and €700 purchase.

What the book says

Stream processing has long been used for monitoring, where an organization wants to be alerted if certain things happen: fraud detection systems that block a credit card whose usage pattern has unexpectedly changed, trading systems that execute trades according to rules on price changes, manufacturing systems that spot a malfunctioning machine, and military and intelligence systems that raise the alarm at signs of an attack. These need sophisticated pattern matching and correlations.

Complex event processing (CEP), developed in the 1990s, is geared toward searching for certain event patterns. Similarly to the way a regular expression lets you search for patterns of characters in a string, CEP lets you specify rules to search for patterns of events in a stream. Patterns are described in a high-level declarative query language like SQL, or a GUI; the engine consumes the input streams and internally maintains a state machine that performs the matching. When a match is found, it emits a complex event with the details of the pattern detected.

The relationship between queries and data is reversed. A database stores data persistently and treats queries as transient; CEP engines store queries long-term, and as each event arrives they check whether it completes a match for any standing query. Implementations include Esper, Apama and TIBCO StreamBase; distributed stream processors like Flink and Spark Streaming also support SQL for declarative queries on streams.

What the book says

The boundary between CEP and stream analytics is blurry, but stream analytics is less focused on detecting specific event sequences and more oriented toward aggregations and statistical metrics over large volumes of events: measuring the rate of a type of event per time interval, calculating the rolling average of a value over a time period, and comparing current statistics to previous time intervals, to detect trends or alert on metrics unusually high or low compared to the same time last week.

Such statistics are usually computed over fixed time intervals, for example the average number of queries per second over the last five minutes and their 99th percentile response time. Many open source frameworks are designed with analytics in mind: Apache Storm, Spark Streaming, Flink, Samza, Apache Beam and Kafka Streams. Hosted services include Google Cloud Dataflow and Azure Stream Analytics.

What the book says

Databases are designed to keep full copies of a dataset, and many support materialized views (analytical queries can be materialized into OLAP cubes). What the book says

Message-passing systems are an alternative to RPC for services to communicate, used for example in the actor model. Although they are based on messages and events too, we normally don’t think of them as stream processors, for a few reasons.

  • Actor frameworks are primarily a mechanism for managing concurrency and distributed execution of communicating modules, whereas stream processing is primarily a data management technique.
  • Communication between actors is often ephemeral and one-to-one, whereas event logs are durable and multi-subscriber.
  • Actors can communicate in arbitrary ways, including cyclic request/response patterns, but stream processors are usually set up in acyclic pipelines where every stream is the output of one particular job, derived from a well-defined set of input streams.

There is some crossover: Apache Storm has a feature called distributed RPC, which farms user queries out to nodes that also process event streams; the queries are interleaved with events from the input streams, and results can be aggregated and sent back to the user.

You can also process streams with actor frameworks. However, many of them do not guarantee message delivery in the case of crashes, so the processing is not fault-tolerant unless you implement additional retry logic.

Stream processors often need to deal with time, especially for analytics that use time windows such as “the average over the last five minutes.” The meaning of the last five minutes might seem clear, but the notion is surprisingly tricky.

When windows are defined by event time, you can never be sure whether you have received all the events for a window or some are still to come. Say you count requests in 1-minute windows: you have counted events in the 37th minute, and now most events fall in the 38th and 39th minutes. When do you declare the window for minute 37 finished and output its counter?

You can time out and declare a window ready after you have not seen any new events for it in a while.   • Ignore the stragglers, as they are probably a small percentage in normal circumstances. Track the number of dropped events as a metric, and alert if you start dropping a significant amount of data.
  • Publish a correction, an updated value for the window with stragglers included. You may also need to retract the previous output.

But if several producers on different machines generate events, each with its own minimum timestamp threshold, consumers must keep track of each producer individually, and adding and removing producers is trickier.

Received minus sent tells you how wrong the phone is, and you correct the first time by that much.

What the book says

Assigning timestamps is even more difficult when events can be buffered at several points in the system. A mobile app reporting usage metrics may be used while the device is offline; it buffers events locally and sends them when an internet connection is next available, which may be hours or even days later. To any consumer of the stream, the events appear as extremely delayed stragglers.

The timestamp should really be the time the user interaction occurred, according to the device’s local clock. But the clock on a user-controlled device often cannot be trusted, as it may be accidentally or deliberately set to the wrong time. The time the server received the event is more likely to be accurate, since the server is under your control, but it is less meaningful in describing the user interaction.

One approach is to log three timestamps: the time the event occurred, according to the device clock; the time it was sent to the server, according to the device clock; and the time it was received by the server, according to the server clock. Subtracting the second from the third estimates the offset between the device and server clocks (assuming network delay is negligible compared to the required accuracy). Applying that offset to the event timestamp estimates when the event truly occurred (assuming the device clock offset did not change between the event and the send).

This problem is not unique to stream processing; batch processing suffers from exactly the same issues. It is just more noticeable in a streaming context, where we are more aware of the passage of time.

Once you know how the timestamp of an event should be determined, the next step is to decide how windows over time periods should be defined. The window can then be used for aggregations, for example to count events or to calculate the average of values within the window. Several types of windows are in common use.

A tumbling window has a fixed length, and every event belongs to exactly one window. With a one-minute tumbling window, all the events with timestamps from 10:03:00 to 10:03:59 are grouped into one window, events from 10:04:00 to 10:04:59 into the next window, and so on.

You could implement a one-minute tumbling window by taking each event timestamp and rounding it down to the nearest minute to determine the window that it belongs to.

Window operations usually maintain temporary state. In some cases the state is of a fixed size, however large the window or however many events occur: a counting operation has only one counter regardless of the window size or event count.

Were these two visits less than five minutes apart?

What the book says

A sliding window contains all the events that occur within a certain interval of each other. For example, a five-minute sliding window would cover events at 10:03:39 and 10:08:12, because they are less than five minutes apart. Tumbling and hopping five-minute windows would not have put these two events in the same window, as they use fixed boundaries.

A sliding window can be implemented by keeping a buffer of events sorted by time and removing old events when they expire from the window.

Window operations usually maintain temporary state. A counting operation has a single counter regardless of window size or event count. Sliding windows, and the stream joins discussed next, instead require that events be buffered until the window finishes. So large window sizes or high-throughput streams can make stream processors keep a lot of temporary state, and the machines running the tasks need enough capacity for it, in memory or on disk.

Batch jobs join two datasets by a key. Streams need joins too, but a new event can turn up at any moment. Leila runs the search box of an outdoor shop. What the book says

Batch jobs join datasets by key, and since stream processing generalizes data pipelines to incremental processing of unbounded datasets, there is exactly the same need for joins on streams. New events can appear on a stream at any time, which makes stream joins harder. The book distinguishes three types: stream–stream joins, stream–table joins, and table–table joins.

Example: to detect recent trends in searched-for URLs, you log an event for every search (the query and the results returned) and another for every click on a result. To calculate the click-through rate for each URL, you bring together the search and click events, connected by having the same session ID. Similar analyses are needed in advertising systems. The click may never come if the user abandons their search; if it comes, it may be seconds later, or days or weeks later; and because of variable network delays it may even arrive before the search event. You choose a window for the join, for example joining a click with a search if they occur at most one hour apart.

Embedding the details of the search in the click event is not equivalent to joining the events: it tells you only about the cases where the user clicked, not about searches where the user clicked nothing. To measure search quality you need accurate click-through rates, so you need both the search events and the click events.

To implement it, the stream processor maintains state, for example all the events of the last hour, indexed by session ID. Each search or click event is added to its index, and the processor checks the other index for an event with the same session ID. If there is a match, it emits an event saying which search result was clicked. If the search event expires without a matching click, it emits an event saying which search results were not clicked.

What the book says

Chapter 11 (Figure 11-2) joined user activity events with a database of user profiles in a batch job. Done continuously, the input is a stream of activity events containing a user ID, and the output is a stream of activity events in which the user ID has been augmented with profile information. This is sometimes known as enriching the activity events with information from the database.

The join takes one activity event at a time, looks up the event’s user ID in the database, and adds the profile information. The lookup could query a remote database, but such remote queries are likely to be slow and risk overloading the database. Another approach is to load a copy of the database into the stream processor so that it can be queried locally without a network round trip. This is called a hash join, since the local copy might be an in-memory hash table if it is small enough, or an index on the local disk.

CDC solves this: the stream processor subscribes to a changelog of the user profile database as well as to the activity events, and updates its local copy when a profile is created or modified. The result is a join between two streams.

A stream–table join is very similar to a stream–stream join. The biggest difference is that for the table changelog stream, the join uses a window that reaches back to the “beginning of time” (a conceptually infinite window), with newer versions of records overwriting older ones. For the stream input, the join might not maintain a window at all.

What the book says

In the case study of social network home timelines, it is too expensive, when a user views their home timeline, to iterate over all the people they follow, find their recent posts and merge them. Instead we want a timeline cache, a kind of per-user “inbox” to which posts are written as they are sent, so that reading the timeline is a single lookup. Maintaining it requires: when user u sends a new post, it is added to the timeline of every user who is following u; when a user deletes a post, or deletes their entire account, it is removed from all users’ timelines; when user u1 starts following user u2, recent posts by u2 are added to u1’s timeline; when u1 unfollows u2, posts by u2 are removed from u1’s timeline.

The stream processor needs streams of events for posts (sending and deleting) and for follow relationships (following and unfollowing), and it maintains a database containing the set of followers for each user, so that it knows which timelines to update when a new post arrives.

The join of the streams corresponds directly to the join of the tables in this query. The timelines are effectively a cache of the result of the query, updated every time the underlying tables change.

Any change of posts is joined with the current followers, and any change of follows is joined with the current posts.

Stream joins · time dependence of joins

Which tax rate did that sale pay?

Lucía runs a shop. On Tuesday at 10:10 the tax rate goes up from 20% to 25%. A sale at 10:06 should pay 20%; a sale at 10:12 should pay 25%. Simple, as long as everything arrives in order.

But the sales and the tax-rate changes travel on two different streams. Each stream keeps its own order, yet nothing decides how they interleave at the join. If the rate change happens to arrive early, the 10:06 sale is taxed at 25%. Run the same job again on the same input and you may get a different total: the join is nondeterministic. Data warehouses call this a slowly changing dimension, and fix it by giving every version of the rate its own ID, which the sale carries with it.

Try it: in Current rate, press Run the join several times and watch the arrival order and the total change. Then switch to Versioned rate IDs or Rate in each sale and run again: the total stops moving.

What the book says

The stream–stream, stream–table and table–table joins have a lot in common: they all require the stream processor to maintain a state (search and click events, user profiles, or follower list) derived from one join input and to query that state when processing records from the other input.

The order of the events that maintain the state is important: it matters whether you first follow and then unfollow a user, or the other way round. In a sharded event log like Kafka, ordering within a single partition is preserved, but there is typically no ordering guarantee across different streams or shards. So if a user updates their profile, which activity events are joined with the old profile and which with the new one?

If you sell things, you need to apply the right tax rate to invoices, which depends on the country or state, the type of product and the date of sale. When joining sales to a table of tax rates, you probably want the rate at the time of the sale, which may differ from the current rate if you are reprocessing historical data. If the ordering of events across streams is undetermined, the join becomes nondeterministic: rerunning the same job on the same input does not necessarily give the same result.

In data warehouses this is known as a slowly changing dimension (SCD), often addressed with a unique identifier for each version of the joined record: every time the tax rate changes it gets a new identifier, and the invoice includes the identifier for the rate at the time of sale. That makes the join deterministic, but log compaction is then not possible, since all versions must be retained. Alternatively, you can denormalize and include the applicable tax rate directly in every sale event.

Count every visitor once, even if the counter faints

A batch job has an easy answer: if a task fails, rerun it and throw away its half-written output, which nobody could see yet. The result looks as if every record was processed exactly once. A stream job can’t wait until it has finished before showing output, because a stream never finishes. It needs a finer way to discard partial output.

What the book says

Batch processing frameworks tolerate faults fairly easily: if a task fails, it is started again on another machine and the output of the failed task is discarded. This transparent retry is possible because input files are immutable, each task writes its output to a separate file, and output is made visible only when a task completes successfully.

So the output of a batch job is the same as if nothing had gone wrong. It appears as though every input record was processed exactly once: none are skipped and none processed twice. Records may in fact be processed multiple times, but the visible effect is as if they had been processed only once. This principle is known as exactly-once semantics, although effectively-once would be a more descriptive term.

The same issue arises in stream processing, but it is less straightforward to handle. Waiting until a task is finished before making its output visible is not an option, because a stream is infinite, so you can never finish processing it.

Fault tolerance · microbatching

Slice the river into buckets

A river never stops, but you can fill a bucket every second and treat each bucket as a tiny, finished batch job. If something goes wrong while you process one bucket, you pour its results away and process that bucket again. Nobody downstream ever saw the bad results.

That is microbatching. The bucket size is a compromise. Tiny buckets mean fresh results but a lot of time spent scheduling and coordinating each one. Big buckets waste less effort but make you wait longer for any answer. Spark Streaming settles on about one second. Each bucket is also, quietly, a tumbling window cut by the clock of the machine processing it, not by the events’ own timestamps.

Try it: drag Batch size and press Run 8 seconds; watch the overhead and the wait for results trade places. Then set Failures to Crash at 3 s and run again: one batch is thrown away and rerun.

What the book says

One solution is to break the stream into small blocks and treat each block like a miniature batch process. This approach is called microbatching, and it is used in Spark Streaming. The batch size is typically around one second, the result of a performance compromise: smaller batches incur greater scheduling and coordination overhead, while larger batches mean a longer delay before results of the stream processor become visible.

Microbatching also implicitly provides a tumbling window equal to the batch size (windowed by processing time, not event timestamps); any jobs that require larger windows need to explicitly carry over state from one microbatch to the next.

Within the confines of the stream processing framework, microbatching provides the same exactly-once semantics as batch processing.

Fault tolerance · checkpointing

Bookmarks that ride along the stream

Every few orders, a little marker called a barrier is slipped into the stream. When the operator meets one, it writes a copy of its state, a checkpoint, to durable storage. If it crashes, it reloads the latest checkpoint, throws away any output it produced since then, and carries on from the barrier. Inside the framework, that is as good as a batch rerun. Apache Flink works this way.

There is a catch. Some output leaves the framework: a row in somebody else’s database, a message to another broker, an email to a customer. You can’t un-send an email. When the operator replays the orders since the checkpoint, Ana gets her receipt twice.

Try it: press Run 9 orders and follow the barriers b1 and b2 into the operator and the code. The operator crashes after o7. Watch which output is discarded and which email goes out twice. Set Crash to No crash to compare.

What the book says

A variant approach to microbatching, used in Apache Flink, is to periodically generate rolling checkpoints of state and write them to durable storage. If a stream operator crashes, it can restart from its most recent checkpoint and discard any output generated between the last checkpoint and the crash.

The checkpoints are triggered by barriers in the message stream, similar to the boundaries between microbatches, but without forcing a particular window size.

Within the confines of the stream processing framework, the microbatching and checkpointing approaches provide the same exactly-once semantics as batch processing. However, as soon as output leaves the stream processor (when it writes to a database, publishes messages to an external message broker, or triggers the sending of emails), the framework is no longer able to discard the output of a failed microbatch. Restarting a failed task then causes the external side effect to happen twice, and microbatching or checkpointing alone is not sufficient to prevent this.

Fault tolerance · atomic commit revisited

Four things must happen, or none of them

When Priya’s stream task handles one message, it does four things: it updates its state, sends an output message, writes to a database, and moves its offset forward to say “done.” If it crashes between any two of them, the message is processed again after restart, and whatever already happened happens twice.

The cure is the one from distributed transactions: make all four atomic. Either they all take effect or none of them do. Cross-technology transactions are hard, but a stream framework that keeps the state and the messaging inside itself can do this cheaply, especially if one transaction covers several messages at once.

Try it: in Separate writes, set Crash to after output and press Process m42; count how many times each effect happened. Switch to One transaction and repeat. Then drag Messages per transaction to see the commit cost shrink per message.

What the book says

To give the appearance of exactly-once processing in the presence of faults, all outputs and side effects of processing an event must persist if and only if the processing is successful. That includes messages sent to downstream operators or external messaging systems (including email or push notifications), database writes, changes to operator state, and acknowledgments of input messages (including moving the consumer offset forward in a log-based message broker).

These actions must all happen atomically: either they all occur, or none of them do. This is the same idea as exactly-once message processing with distributed transactions and two-phase commit.

Traditional implementations of distributed transactions such as XA have problems, but in more restricted environments it is possible to implement such an atomic commit facility efficiently. This approach is used in Google Cloud Dataflow, VoltDB and Apache Kafka. Unlike XA, these implementations do not attempt to provide transactions across heterogeneous technologies, but keep the transactions internal by managing both state changes and messaging within the stream processing framework. The overhead of the transaction protocol can be amortized by processing several input messages within a single transaction.

Fault tolerance · idempotence

Write it twice, count it once

Pressing a lift button twice doesn’t call two lifts: the second press has no extra effect. That is idempotence. Deleting a key is idempotent. Adding one to a counter is not: do it twice and it counts twice.

You can often make a write idempotent with a little extra data. Store, next to the counter, the offset of the message that last changed it. When a restarted job replays message 12, the database already says “last offset 13”, so the job skips it. This only works if the replay brings the same messages in the same order, the processing is deterministic, and nobody else writes to the same value. A node that was thought dead but is only paused can break that last rule, which is what fencing is for.

Try it: in Plain increment, press Run with a crash and compare the counter with 6. Switch to With offset and run again. In Zombie node, press Run the takeover with No fencing, then with Fencing token.

What the book says

The goal is to discard the partial output of any failed tasks so that they can be safely retried. Distributed transactions are one way of achieving that; another is to rely on idempotence.

An idempotent operation is one that you can perform multiple times with the same effect as if you performed it only once. Deleting a key in a key-value store is idempotent; incrementing a counter is not. Even if an operation is not naturally idempotent, it can often be made idempotent with a bit of extra metadata. When consuming messages from Kafka, every message has a persistent, monotonically increasing offset. When writing a value to an external database, you can include the offset of the message that triggered the last write with the value, and so tell whether an update has already been applied. The state handling in Storm’s Trident is based on a similar idea.

Relying on idempotence implies several assumptions: restarting a failed task must replay the same messages in the same order (a log-based message broker does this), the processing must be deterministic, and no other node may concurrently update the same value. When failing over from one processing node to another, fencing may be required to prevent interference from a node that is thought to be dead but is actually alive. Despite those caveats, idempotent operations can be an effective way of achieving exactly-once semantics with only a small overhead.

Fault tolerance · rebuilding state after a failure

Where does the memory come back from?

A stream task that counts orders per customer keeps a little table in memory. When the task crashes, the table is gone, and its replacement must get it back before it can carry on. Where from?

Keep the table in a remote database and nothing is lost, but every single message now waits for a network round trip. Keep it local and copy it somewhere now and then: a snapshot on a distributed filesystem, or every change sent to a compacted changelog topic. Run the same messages on a second node so a twin is always ready. Or, if the state only covers a short window, simply replay the input. Which is best depends on your hardware: sometimes the network is faster than the disk.

Try it: pick a strategy and press Run, crash, recover. Watch where the four counts come back from, then compare the latency per message and the recovery work in the stats with another strategy.

What the book says

Any stream process that requires state (windowed aggregations such as counters, averages and histograms, and any tables and indexes used for joins) must ensure that this state can be recovered after a failure.

One option is to keep the state in a remote datastore and replicate it, although having to query a remote database for each individual message can be slow. An alternative is to keep state local to the stream processor and replicate it periodically; a new task can then read the replicated state and resume without data loss. Flink periodically captures snapshots of operator state and writes them to durable storage such as a distributed filesystem; Kafka Streams replicates state changes by sending them to a dedicated Kafka topic with log compaction, similar to CDC; VoltDB replicates state by redundantly processing each input message on several nodes.

Sometimes replicating the state is not even necessary, because it can be rebuilt from the input streams: if the state is an aggregation over a fairly short window, it may be fast enough to replay the input events for that window; if it is a local replica of a database maintained by CDC, it can be rebuilt from the log-compacted change stream.

All this depends on the performance characteristics of the infrastructure. In some systems, network delay may be lower than disk access latency, and network bandwidth may be comparable to disk bandwidth. No solution is universally ideal, and the merits of local versus remote state may shift as storage and networking technologies evolve.

Two kinds of message broker

From the book’s summary.

AMQP/JMS-style broker

Hands individual messages to consumers, which acknowledge each one when it is processed; acknowledged messages are deleted. A good fit for a task queue, an asynchronous form of RPC, where the exact order doesn’t matter and nobody needs to reread old messages.

Log-based broker

Gives every message in a shard to the same consumer node, always in the same order. Parallelism comes from sharding; consumers checkpoint the offset of the last message they processed. Messages stay on disk, so you can jump back and reread them.

event
A small, self-contained, immutable record of something that happened at a point in time.
producer / consumer
Who writes an event (also publisher or sender) and who processes it (subscriber or recipient).
topic
A named group of related events, the streaming version of a file name.
backpressure
Blocking a producer until the consumer catches up. Also called flow control.
message broker
A server that stores messages between producers and consumers; also called a message queue.
load balancing
Each message goes to one of the consumers, so they share the work.
fan-out
Each message goes to every consumer, so independent readers all see the same stream.
consumer group
Kafka’s mix of both: load balancing inside a group, fan-out across groups.
acknowledgment
A consumer telling the broker it finished a message, so the broker may remove it.
dead letter queue
A separate queue for messages that keep failing, so they stop blocking everyone else.
log-based broker
A broker that appends messages to a log on disk and lets consumers read it like a file.
partition (shard)
One independent log of a topic; messages are totally ordered within it, not across.
offset
A message’s sequence number within its partition, and a consumer’s bookmark.
head-of-line blocking
One slow message holding up every message behind it.
segment
A chunk of the log on disk; old segments are deleted or archived to free space.
consumer lag
How far a consumer is behind the head of the log.
state machine replication
Same deterministic events, same order, on every replica: same final state.
dual writes
Application code writing the same change to several systems itself.
change data capture (CDC)
Observing every change written to a database and streaming it to other systems.
derived data system
A copy of data (index, cache, warehouse) that can be rebuilt from the system of record.
log compaction
Keeping only the newest record for each key, so the log holds the current state.
tombstone
A record with a null value that marks a key as deleted.
event sourcing
Building an application on an append-only log of immutable, application-level events.
outbox pattern
A table with its own public schema, written in the same transaction, that CDC exposes instead of internal tables.
changelog
The log of all changes; state is what you get by applying it.
CQRS
Writing in one form (the log) and reading from views derived in other forms.
crypto-shredding
Deleting immutable data by throwing away the key it was encrypted with.
operator (job)
A piece of code that consumes input streams and produces output streams.
complex event processing
Stored queries that search a stream for patterns of events, like a regular expression for events.
stream analytics
Aggregations and statistics over windows of events: rates, averages, percentiles.
incremental view maintenance
Updating a materialized view by processing only what changed.
event time / processing time
When an event happened, versus when a machine got round to processing it.
straggler
An event that arrives after its window was declared complete.
window
The time interval an aggregation covers: tumbling, hopping, sliding or session.
stream enrichment
A stream–table join that adds database details to each event.
slowly changing dimension
A joined record that changes over time, often given a new ID per version.
exactly-once semantics
Output as if each record was processed once, even if some were retried. Better named effectively-once.
microbatching
Cutting the stream into small blocks, about a second each, and processing each like a tiny batch job.
checkpoint
A snapshot of operator state written to durable storage, triggered by barriers in the stream.
idempotent
Doing it twice has the same effect as doing it once.
