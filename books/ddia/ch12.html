Stream Processing

The last chapter counted a mountain of data once a night. But data never stops arriving — so this chapter handles every event the moment it happens, forever.

Big idea 1 · messaging systems

The baker is faster than the packer

An event is a small note that says “this happened, at this time”: a page was viewed, a ticket was sold, a thermometer read 21°. Whoever writes the note is the producer. Whoever reads it is a consumer. Notes about the same kind of thing travel together in a topic.

Picture a bakery. Ingrid bakes buns and puts them on a belt; Kofi packs them into boxes. As long as Kofi is at least as fast as Ingrid, all is well. But what if Ingrid is faster?

There are only three things you can do. Let the extra buns fall on the floor (drop them). Pile them up on the belt (buffer them in a queue). Or make Ingrid stop baking until there is room (backpressure).

Try it: start the belt, then drag the producer's speed above the consumer's. Try all three rules and watch what each one gives up: buns, belt space, or the baker's time.

What the book says

An event is a small, self-contained, immutable record of something that happened, usually with a time-of-day timestamp. It is generated once by a producer (publisher, sender) and potentially processed by several consumers (subscribers, recipients); related events are grouped into a topic or stream. Polling a datastore for new events gets expensive as you poll more often, so it is better for consumers to be notified; database triggers can do this only in a very limited way.

Two questions tell messaging systems apart. First: what if producers send faster than consumers can process? The options are to drop messages, buffer them in a queue, or apply backpressure (flow control) — Unix pipes and TCP use backpressure with a small fixed-size buffer. If you buffer: does the system crash when the queue no longer fits in memory, or spill to disk, and what does that do to performance?

Second: what if nodes crash or go offline — are messages lost? Durability needs disk writes and/or replication, which cost throughput and latency. For periodic sensor readings an occasional missing value may be fine; if you are counting events, every lost message means a wrong counter.

Direct messaging skips the middleman: UDP multicast for stock market feeds, brokerless libraries such as ZeroMQ and nanomsg, StatsD metrics over UDP, and webhooks (HTTP callbacks). These generally assume producers and consumers are constantly online, and the application must cope with lost messages.

Big idea 2 · message brokers

Two clerks, one pile of parcels

A message broker is a post office for events. Producers drop messages off; the broker looks after them and hands them to consumers. Nobody minds if a consumer steps out for a minute — the broker keeps its mail.

With two clerks behind the counter there are two ways to share. Load balancing: each parcel goes to one clerk, so they split the work. Fan-out: every clerk gets their own copy of every parcel, like two people tuned to the same radio station.

Clerks can faint mid-parcel. So a clerk must send an acknowledgment — “done!” — before the broker forgets a message. No ack? The broker hands the message to somebody else. Nothing is lost, but that message now arrives late, behind messages that were sent after it.

Try it: press “Deliver the next round” twice, so consumer 2 is busy with m3. Click consumer 2 to crash it, keep delivering, and read consumer 1's list. Then repeat the same crash in fan-out mode.

What the book says

A message broker (message queue) is essentially a database optimized for message streams. Because data is centralized in the broker, clients can connect, disconnect and crash, and the question of durability moves to the broker. Faced with slow consumers, brokers generally allow unbounded queueing, so consumers are asynchronous: the producer waits only for the broker to confirm it has buffered the message.

Unlike databases, traditional brokers delete a message once it is delivered, assume short queues (throughput degrades when they grow), offer topic-pattern subscriptions rather than queries, and notify clients when data changes. This is the world of the JMS and AMQP standards: RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO Enterprise Message Service, IBM MQ, Azure Service Bus, Google Cloud Pub/Sub.

Load balancing delivers each message to one consumer (a shared subscription in JMS); fan-out delivers each to all (topic subscriptions in JMS, exchange bindings in AMQP). Kafka's consumer groups combine the two.

If a connection closes or times out without an acknowledgment, the broker redelivers. The message may in fact have been processed and only the ack lost; handling that needs atomic commit or idempotence. Load balancing plus redelivery inevitably reorders messages (consumer 1 sees m4, m3, m5) — which matters when messages have causal dependencies. A separate queue per consumer avoids it.

A malformed message that crashes every consumer would be redelivered forever. Dead letter queues (DLQs) park such messages in a separate, monitored queue so an operator can drop, fix or replay them; Apache Pulsar and Kafka Streams support them too.

Big idea 3 · log-based message brokers

The notebook nobody erases

A post office forgets a parcel the moment it is delivered, so a latecomer can never see yesterday's mail. What if the broker worked like a class diary instead: every event written on the next free line, and never erased by reading it?

That is a log-based message broker. Each line gets a number, its offset. A reader only has to remember “I'm at line 5”. Two readers keep two bookmarks and never disturb each other, a new reader can start from the oldest line, and anyone can flip back and read again.

To go faster, the diary is split into several notebooks called partitions. All of one person's events go to the same partition — chosen by a key — so that person's events stay in order. And because paper isn't endless, the oldest pages get torn out now and then. Bad luck for a reader who was still back there.

Try it: send some events — the live board follows along by itself. The night reporter reads only when you tell it to. Let it fall behind, delete the oldest segment, and see who misses out. Then rewind it and read the same lines again.

What the book says

A log is an append-only sequence of records on disk. A producer appends; a consumer reads sequentially and waits for a notification at the end, like tail -f. For throughput the log is sharded; Kafka calls a shard a partition. Within a partition every message gets a monotonically increasing offset and messages are totally ordered; there is no ordering guarantee across partitions. Apache Kafka and Amazon Kinesis Streams work this way (Google Cloud Pub/Sub is similar underneath but exposes a JMS-style API), reaching millions of messages per second by sharding and tolerating faults by replicating.

Fan-out is trivial because reading doesn't delete. Load balancing assigns whole shards to the nodes of a consumer group, so at most as many nodes as shards can share the work, and one slow message holds up the rest of its shard (head-of-line blocking). Expensive messages where order doesn't matter suit JMS/AMQP brokers; high throughput with ordering suits logs — though Kafka now also offers JMS/AMQP-style consumer groups. Events that must stay ordered need the same partition key, e.g. the user ID.

The broker records only consumer offsets, not per-message acks — just like the log sequence number in single-leader replication, with the broker as leader and the consumer as follower. After a failure a consumer resumes from its last recorded offset, so it may see some messages twice.

The log is cut into segments; old ones are deleted or archived, making the log a big on-disk ring buffer. A 20 TB drive written at 250 MB/s takes about 22 hours to fill; in practice logs hold days or weeks. Kafka and Redpanda tier old messages to object storage; WarpStream, Confluent Freight and Bufstream keep everything there, as Iceberg tables.

A consumer that falls too far behind misses messages, but only it is affected; you can monitor its lag and alert. And since the offset is under the consumer's control, you can replay: start a copy of a consumer at yesterday's offset and reprocess, as often as you like.

Big idea 4 · keeping systems in sync

Two menu boards, two different lunches

A school keeps Friday's lunch in two places: the office computer (the database) and the hallway board everybody reads (think of it as the search index). Whenever the menu changes, the cook updates both. That is called dual writes.

At the same moment, Mei changes Friday to pizza and Omar changes it to soup. Each sends two messages, and the four messages cross in the network. The office hears “pizza”, then “soup”. The hallway hears “soup”, then “pizza”. Nobody saw an error — and the two now disagree forever.

The cure: only the office decides. Everyone writes to the database alone. The database notes each change in its log, in the order it chose, and the hallway board simply copies that log. This is change data capture. A follower can be behind, but it can never disagree with the leader about the order.

Try it: press “Both save at once” several times in each mode and watch the “ended different” counter. Then click the hallway board to switch it off, save again, and switch it back on.

What the book says

Most applications combine an OLTP database, a cache, a full-text index and a data warehouse, each holding its own copy of the data. Warehouses are usually synced by batch ETL. With dual writes the application writes to each system itself — and hits the race condition of Figure 12-4: the database ends at B, the index at A, permanently inconsistent, and without something like version vectors you won't even notice. A second problem: one write may fail while the other succeeds, which is the (expensive) atomic commit problem. The root cause is that there is no single leader.

Change data capture (CDC) observes every change written to a database and extracts it in a form that can be replicated elsewhere, ideally as a stream. The database decides the order and writes it to its replication log; the index applies the changes in the same order; another system is just another consumer. CDC makes one database the leader and the rest followers, and a log-based broker transports the changes because it preserves their order.

Tools: Debezium (connectors for MySQL, PostgreSQL, Oracle, SQL Server, Db2, Cassandra and more), Kafka Connect, Maxwell (MySQL binlog), GoldenGate (Oracle), pgcapture (PostgreSQL). MySQL and PostgreSQL send changes through the same replication log they use for replicas; Google's Datastream does it for its cloud databases; Cassandra exposes raw log segments per node and leaves merging to the consumer.

CDC is usually asynchronous: a slow consumer doesn't hold up the system of record, but all the problems of replication lag apply. It also turns the database schema into a public API — removing a column can break downstream services. Data contracts and the outbox pattern (a separate outbox table, written in the same transaction as the real change) decouple the two, at the price of extra writes and a transformation to maintain.

Big idea 5 · snapshots and log compaction

Shrinking the notebook without losing anything

A cat-video site keeps a play counter for each video. Every play changes a counter, and every change becomes one line in the change log: purr = 2.

Now you want a brand-new search index. If you still have the whole log, replay it from the first line and you're done. But logs get long, so old lines get thrown away — and replaying what's left misses every video that wasn't played lately. Then you need a snapshot first: a full copy of the database, stamped with the log position it matches.

There is a smarter way to tidy up: log compaction. For each key, keep only the newest line and throw out the older ones. The log shrinks to about the size of the database — and still contains a full copy of it. Deleting a video writes a special “gone” line, a tombstone, so compaction knows to drop that key completely.

Try it: click videos to play them and watch lines being appended. Pick a tidy-up rule, press “Tidy the log”, then “Build a new index from the log” and see which rule still gives a complete index.

What the book says

With the log of all changes you can rebuild the whole database by replaying it, but keeping everything forever takes too much disk and too long to replay, so logs are truncated. A new full-text index then needs a consistent snapshot that corresponds to a known offset in the change log, so you know where to continue. Some CDC tools integrate this; Debezium uses Netflix's DBLog watermarking algorithm for incremental snapshots.

Log compaction (the same idea as in log-structured storage engines) runs in the background, finds records with the same key and keeps only the most recent. A null value — a tombstone — marks a deleted key. The disk space needed then depends only on the current contents of the database, not on how many writes ever happened. The book's example (Figure 12-6) is exactly this: cat videos mew, purr, scratch and yawn with their play counts.

To rebuild a derived system you start a new consumer at offset 0 of the compacted topic and scan it: it is guaranteed to contain the latest value of every key. Apache Kafka supports this, which lets a broker be durable storage, not just transient messaging.

This works for CDC because each event holds the entire new version of a record. With event sourcing, events express a user's intent and later events don't override earlier ones, so you need the full history and can't compact the same way; such systems store snapshots of derived state purely as a performance optimization.

Big idea 6 · state, streams and immutability

Your shopping cart is the end of a story

Priya's cart holds a ball. That is the state: what is true right now. But how did it get that way? She added a kite, added a ball, then took the kite out again. Those are the events. The cart is simply what you get when you replay the story from the start.

Accountants have worked like this for centuries. They never rub out a line in the ledger; if a line was wrong, they add a new line that corrects it. The old line stays, so anyone can check what really happened.

Keeping the story gives you superpowers. You can travel back in time. You can learn that Priya thought about a kite — a database that just deletes it would forget that. And next year you can invent a brand-new view and fill it by replaying the same old log.

Try it: click things on the shelf to put them in the cart and take them out. Drag the time slider back. Press “Launch a new view”. Then switch to “Overwrite in place” and see which questions can no longer be answered.

What the book says

Mutable state and an append-only log of immutable events “are two sides of the same coin”. The log of all changes, the changelog, represents the evolution of state over time: state is what you get when you integrate an event stream over time, and a change stream is what you get when you differentiate state by time (Figure 12-7). Jim Gray and Andreas Reuter, 1992: “There is no fundamental need to keep a database at all; the log contains all the information there is.”

Advantages. An append-only ledger gives auditability; mistakes are fixed by a compensating transaction, not by erasing. Recovering from buggy code is far easier when it couldn't destructively overwrite data. Events also hold more than the current state — the book's own example is an item added to a cart and then removed.

Several views from one log. Druid ingests directly from Kafka; Kafka Connect sinks export to many databases and indexes. A new feature gets its own read-optimized view, built from the log and run side by side with the old one — easier than a schema migration. This is the idea of CQRS, and it makes the normalization-versus-denormalization debate largely irrelevant.

Concurrency. Views are usually updated asynchronously, so you may not read your own write. On the other hand a user action becomes a single self-contained event, appended atomically in one place, and a single-threaded consumer per shard needs no concurrency control.

Limits. With high churn the history can grow prohibitively large. And sometimes data really must go (GDPR, leaked secrets): Datomic calls it excision, Fossil shunning; crypto-shredding stores data encrypted and later forgets the key. Truly deleting data is surprisingly hard — it is more “making it harder to retrieve” than “impossible to retrieve”.

Big idea 7 · uses of stream processing

Questions that sit and wait for their answers

A normal database keeps the data and lets questions come and go. A stream processor flips that around: it keeps the questions and lets the data flow past. Each new event is shown to every waiting question — “is this the one you were looking for?”

Watch Lena's bank card. One stored question hunts for a suspicious pattern — the book names fraud detection as a classic use of complex event processing; the two-city demo below is our illustration of a stored query. One keeps a running average. One keeps a little table of totals always up to date. One is a saved search for bike shops.

Same stream, four different jobs — and each one answers the instant an event arrives, not tomorrow morning.

Try it: make Lena pay in Lima a few times, then straight away in Oslo. Reset and try again, but press “Wait 10 minutes” before the Oslo payment.

What the book says

With a stream you can write events into a database, cache or index; push them to people (alerts, a real-time dashboard); or process input streams into derived output streams. Code that does the last is an operator or job. The crucial difference from batch: a stream never ends, so sorting — and sort-merge joins — make no sense, and fault tolerance can't simply mean restarting from the beginning.

Complex event processing (CEP), from the 1990s, searches for patterns of events the way a regular expression searches for patterns of characters. Queries (often SQL-like, or a GUI) are stored long-term; the engine keeps a state machine and emits a “complex event” on a match. Esper, Apama, TIBCO StreamBase; Flink and Spark Streaming have SQL too. Classic uses: fraud detection, trading, factory monitoring, military and intelligence systems.

Stream analytics is about aggregations over windows: rates, rolling averages, comparisons with last week. Probabilistic algorithms (Bloom filters, HyperLogLog, percentile estimators) save memory, but they are only an optimization — there is nothing inherently approximate about stream processing. Apache Storm, Spark Streaming, Flink, Samza, Beam, Kafka Streams; Google Cloud Dataflow, Azure Stream Analytics.

Materialized views need a window that stretches back to the beginning of time (Kafka Streams, ksqlDB). Databases often refresh views by batch (PostgreSQL's REFRESH MATERIALIZED VIEW); incremental view maintenance — Materialize, RisingWave, ClickHouse, Feldera — recomputes only what changed.

Search on streams stores the queries and runs each document past them, e.g. the percolator feature of Elasticsearch: media monitoring, or a real estate site that notifies users when a new property matching their search criteria appears on the market. Actor frameworks also pass messages, but they manage concurrency rather than data, and usually don't guarantee delivery after a crash.

Big idea 8 · reasoning about time

Whose clock are we using, anyway?

Count the taps in a game app, minute by minute. Easy — until Tomás rides the metro through a tunnel. His phone keeps recording taps but can't send them. Five minutes later it is back online and delivers them all at once.

Every event now has two times: when it happened (event time) and when the server got it (processing time). Count by arrival and you see a burst of taps after 10:07 that never really happened. Count by event time and the numbers are right — but the 10:02 window had already been announced. Latecomers like these are stragglers: you either ignore them or publish a correction.

You also have to decide what “per minute” means. A window is the slice of time you add up over, and it comes in four common shapes.

Try it: bring the phone back online in each clock mode. Then try the four window shapes; in “sliding”, drag the window along yourself. In “session”, watch two visits melt into one when the tunnel taps turn up.

What the book says

A batch job uses the timestamps inside the events, which also makes it deterministic. Many stream frameworks window by the processing machine's clock (processing time) — simple, and fine while lag is negligible. But queueing, network faults, broker contention, a restart, or reprocessing old events all cause lag and can reorder events. (Think of watching Star Wars in release order: the episode number is the event time, the date you watched it is the processing time.) Figure 12-8: redeploy a processor, let it chew through the backlog, and a rate measured by processing time shows a spike that never happened.

Stragglers. With event-time windows you can never be sure a window is complete. Either ignore stragglers — and track how many you drop — or publish a correction, possibly retracting the old output. A special message saying “from now on, there will be no more messages with a timestamp earlier than t” can close windows, but with several producers each one must be tracked separately.

Whose clock? A phone may buffer events offline for hours or days, and its clock can't be trusted. One approach logs three timestamps: when the event occurred (device clock), when it was sent (device clock), and when it was received (server clock). The difference between the last two estimates the device clock's offset.

Window types. Tumbling: fixed length, every event in exactly one window (10:03:00–10:03:59). Hopping: fixed length with overlap, e.g. 5 minutes hopping by 1. Sliding: all events within some interval of each other — 10:03:39 and 10:08:12 share a 5-minute sliding window, though no fixed-boundary window would hold both. Session: no fixed length; it ends after a period of inactivity, e.g. 30 minutes. A counter needs constant state, but sliding windows must buffer events.

Big idea 9 · stream joins

Matching up two streams

Joining means matching things that belong together. In a batch job both piles are complete before you start. In a stream, the matching piece might turn up any second — or never. So the stream processor has to remember things while it waits.

Stream–stream: match each search with the click that follows it, if one comes within the hour. Stream–table: stick the user's name and city onto every activity event, using a local copy of the profile table that a changelog keeps fresh. Table–table: keep everybody's home timeline ready to read, by combining the stream of posts with the stream of follows.

All three keep some state from one input and look things up in it when the other input speaks. That makes order matter. Did the profile change arrive before the purchase, or after it?

Try it: step through each kind of join. In the stream–table join, press “Swap the last two arrivals” and run it again: same events, different answer.

What the book says

Stream–stream (window) join. To measure click-through rate you join search events with click events on the session ID. The click may never come, may come weeks later, or — thanks to network delays — may even arrive before the search. You pick a window (say, one hour), keep all recent events indexed by session ID, emit a match when both sides are present, and emit “not clicked” when a search expires. Embedding the search inside the click event is not equivalent: you would never learn about searches with no click.

Stream–table join (enrichment). Looking up each user ID in a remote database is slow and may overload it. Instead, load a copy of the table into the stream processor — a hash join against a local hash table or on-disk index — and keep it fresh by subscribing to the table's CDC changelog. It is really a join of two streams, where the table side has a window reaching back to the beginning of time.

Table–table join (materialized view maintenance). The timeline cache is the materialized result of joining posts with follows. New posts go to every follower's timeline; deleted posts are removed; a new follow pulls in recent posts; an unfollow removes them. Seen as calculus, the change stream of a join follows the product rule (u·v)′ = u′v + uv′.

Time dependence. If state changes over time and you join with it, which point in time do you use? With no ordering guarantee across streams or shards the join becomes nondeterministic: rerunning the same job may interleave the inputs differently. Data warehouses call this a slowly changing dimension and give each version of a record (say, a tax rate) its own identifier — which makes the join deterministic but rules out log compaction. Alternatively, denormalize the rate into every sale event.

Big idea 10 · fault tolerance

Crash in the middle — without counting twice

A batch job that dies can start over and throw its half-finished output away. A stream job that has been running for two years can't go back to the beginning. So it saves its place every so often — a checkpoint — and after a crash it returns to the last one and replays from there.

Replaying is perfectly safe inside the processor. But anything that already escaped — a row written to a database outside, an email sent — happens again. The ticket counter ends up too high.

Two cures. Atomic commit: the outputs and the “I've read up to here” bookmark are saved together, all or nothing. Or idempotence: make every write safe to repeat, by stamping it with the event's offset so the database can say “already got that one”. Either way it looks as if each event was handled exactly once — effectively once, to be precise.

Try it: process five sales, then click the processor to crash it, and finish the log. Compare “database says” with “really sold” in each of the three modes.

What the book says

Batch frameworks get exactly-once semantics (better: effectively-once) by discarding the output of failed tasks and making output visible only when a task succeeds. A stream never finishes, so that trick doesn't carry over directly.

Microbatching (Spark Streaming) cuts the stream into blocks of about a second and treats each as a tiny batch job — smaller batches mean more overhead, larger ones more delay. Checkpointing (Apache Flink) periodically writes rolling checkpoints of state to durable storage, triggered by barriers in the stream, without forcing a window size. Both give exactly-once within the framework; but once output leaves it — a database write, a message to an external broker, an email — a restart makes the side effect happen twice.

Atomic commit. All outputs and side effects of processing an event — downstream messages, database writes, operator state, and moving the consumer offset forward — must happen atomically or not at all. Google Cloud Dataflow, VoltDB and Apache Kafka do this efficiently by keeping the transaction internal to the framework rather than spanning heterogeneous systems as XA does, and by handling several input messages per transaction.

Idempotence. An operation is idempotent if doing it several times has the same effect as doing it once: deleting a key is; incrementing a counter is not. You can often add it with metadata — store the Kafka offset of the last applied message with the value (Storm's Trident does something similar). It assumes replay in the same order, deterministic processing, no other writer on the same value, and possibly fencing during failover.

Rebuilding state. Keep state in a remote replicated store (slow per message), or keep it local and replicate it: Flink snapshots operator state to a distributed filesystem, Kafka Streams sends state changes to a log-compacted Kafka topic, VoltDB processes each input redundantly on several nodes. Sometimes state can simply be rebuilt by replaying the input.

The seesaws from this chapter

A stream never ends, so every choice is about what happens “in the meantime”.

Buffer in a queue

The producer never waits — but the queue can outgrow memory, then disk

vs

Drop or push back

Bounded memory, paid for with lost messages or a blocked producer

May lose a message

Higher throughput and lower latency on the same hardware; fine for sensor readings

vs

Durable delivery

Disk writes and replication cost speed, but counters stay correct

AMQP/JMS-style broker

Shares work message by message, great for slow tasks; deletes after ack, may reorder

vs

Log-based broker

Ordered per partition and replayable; parallelism limited by partitions, one slow message blocks its shard

Dual writes

Simple application code, but races and half-failures leave systems disagreeing forever

vs

Change data capture

One leader fixes the order for everybody; followers lag a little behind

Change data capture

Bolts onto an existing database and compacts nicely; the schema becomes a public API

vs

Event sourcing

Events say what the user meant; needs the full history and a redesigned application

Keep every event

Audit trail, time travel, new views by replay

vs

Compact or delete

Bounded disk and the right to be forgotten — but truly deleting is hard

Event time

True and repeatable, but you never know whether a window is complete

vs

Processing time

Simple, but any lag paints spikes and dips that never happened

Checkpoints alone

Cheap, exactly-once inside the framework; outside effects can repeat

vs

Atomic commit or idempotence

Effectively-once all the way out, for some overhead and a list of assumptions

Words to know

Grown-up words, in plain language.

event
A small, unchangeable note that something happened, with the time it happened.
stream
Data that keeps arriving bit by bit and never counts as “finished”.
producer / consumer
The one who sends events, and the one who receives and handles them.
topic
A named group of related events, like a file name for a stream.
backpressure
Making the sender wait because the receiver is full. Also called flow control.
message broker
A server in the middle that takes messages from producers and hands them to consumers.
load balancing
Each message goes to just one of the consumers, so they share the work.
fan-out
Each message goes to every consumer, like a broadcast.
acknowledgment
The consumer's “done!” that lets the broker forget a message.
dead letter queue
A side queue for messages that keep failing, so they stop blocking the rest.
log-based broker
A broker that appends every message to a file and never erases it just because it was read.
partition
One slice of a topic's log. Order is guaranteed inside a partition, not across them.
offset
The line number of a message in its partition. A consumer's bookmark is just an offset.
consumer group
A team of consumers that split a topic's partitions between them.
