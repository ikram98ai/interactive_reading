Many specialized tools, one source of truth. How data gets into all the right places, in the right forms, and in the right order, and how batch and stream processing keep it there as the application evolves.

Data integration · no one right solution

A toolbox, not a Swiss Army knife

Zainab runs a small online shop. In one day her data gets asked six very different questions: fetch order 8812, find every “wool scarf”, add up sales per month for two years, render the same product page a thousand times a second, suggest similar items, and ping a shopper when a price drops.

Every piece of software, even one sold as a general-purpose database, is built for a particular usage pattern. One code path tuned for key lookups is not also the best column scanner, search ranker and push notifier. Trying to be all of them tends to give you weak versions of each. So real applications end up cobbling together several specialized tools, and the rest of this chapter is about how to make that cobbling reliable.

Try it: press Run the day with One database and watch which workloads come back slow or unsupported. Switch to Specialized tools and run again: every workload fits, but count the systems to run. Tap a workload to drop it from the day.

What the book says

This chapter brings together the goals of Chapter 2 (reliable, scalable, maintainable systems) and the streaming and event-driven ideas of Chapter 12 into one philosophy of application development. It is more opinionated than earlier chapters: a deep dive into one approach rather than a comparison of several.

For any problem, such as storing data and looking it up later, there are several solutions, each appropriate in different circumstances: log-structured storage, B-trees and column-oriented storage; single-leader, multi-leader and leaderless replication. A software implementation typically has to pick one. Getting one code path robust and fast is hard enough; satisfying too many use cases is likely to give poor implementations compared to specialized tools.

Every piece of software, even a so-called “general-purpose” database, is designed for a particular usage pattern. The first challenge is mapping products to the circumstances they fit; vendors are understandably reluctant to say which workloads their software is poorly suited for.

The second challenge: in complex applications data is used in various ways, and one piece of software is unlikely to suit all of them, so you inevitably end up having to cobble together several pieces of software.

Seven copies of the same order

Data integration · reasoning about dataflows

Two editors, two stores, two different answers

Aisha retitles listing 42 to “Blue lamp”. A moment later Bilal retitles it “Red lamp”. Each app server writes to the database and to the search index itself. The network delivers the writes in a different order to each store, so the database ends on Red and the index ends on Blue. Neither store is in charge of the order, and nothing will ever fix it.

The cure is to be explicit about the dataflow: where is data written first, and what is derived from what? Write only to the system of record, capture its changes (CDC) into a log, and let the index apply them in log order. One system decides a total order; everyone else replays it. That is state machine replication again, and because applying an ordered log is deterministic and idempotent, a consumer that crashes can simply replay from its last offset.

Try it: press Both edit at once in Dual writes and compare the two stores. Switch to Through the log and run it again, then press Crash consumer & replay: offsets get applied twice and the result doesn’t change.

What the book says

When copies of the same data are kept in several storage systems for different access patterns, you need to be very clear about inputs and outputs: where is data written first, and which representations are derived from which sources?

For example, write data first to a system-of-record database, capture its changes (change data capture) and apply them to the search index in the same order. If CDC is the only way of updating the index, the index is entirely derived from the system of record and therefore consistent with it (barring bugs). Writing to the database is the only way of supplying new input.

Letting the application write directly to both the search index and the database introduces the problem of Figure 12-4: two clients send conflicting writes concurrently and the two stores process them in a different order. Neither is “in charge” of determining the order of writes, so they may make contradictory decisions and become permanently inconsistent.

If all user input is funnelled through a single system that decides on an ordering for all writes, deriving other representations by processing the writes in the same order is much easier: an application of state machine replication. Whether you use CDC or an event sourcing log is less important than the principle of deciding on a total order. Updating derived data from an event log can often be made deterministic and idempotent, making it easy to recover from faults.

Data integration · derived data versus distributed transactions

Fresh but fragile, or late but sturdy

Mai marks order 77 as shipped. That fact has to reach the database and the search index. The classic way is a distributed transaction: a coordinator asks both to prepare, and only if both vote yes does it tell both to commit. The moment it says “ok”, a search shows the new status. But if the index is sick, Mai’s write fails, even though the database was perfectly healthy.

The log-based way commits to the database alone and lets the index catch up from the change log. Correctness comes not from an atomic commit protocol but from deterministic retry and idempotence. The price is timeliness: a search right after the write may still say “packed”. Same goal, different means, different failure modes.

Try it: press Mark next status in both modes and read the search result right after. Then press Take index down and write again: one mode refuses the write, the other accepts it and catches up when you bring the index back.

What the book says

The classic approach to keeping data systems consistent is distributed transactions (two-phase commit). At an abstract level both approaches reach a similar goal by different means: distributed transactions use an atomic commit protocol to apply changes atomically, while log-based systems achieve correctness through deterministic retry and idempotence.

The biggest difference: transaction systems usually guarantee that after a value is written you can immediately read the up-to-date value (reading your own writes). Derived data systems are often updated asynchronously, so by default reads are not guaranteed to be up-to-date.

Distributed transactions have worked in environments willing to absorb their performance and operational costs, but XA has poor fault tolerance and performance characteristics, which severely limit its usefulness. A better protocol might be possible, but getting it widely adopted and integrated with existing tools would be challenging and is unlikely to happen soon.

In the absence of a good, widely supported distributed transaction protocol, log-based derived data is the most promising approach for integrating different data systems. Still, guarantees like reading your own writes are useful, and it is not productive to tell everyone “eventual consistency is inevitable—suck it up and learn to deal with it” without good guidance; later the chapter looks for a middle ground.

Data integration · the limits of total ordering

One referee is easy. Then the stadium grows.

A single leader is like one referee writing every event of the match in one notebook: everyone who reads the notebook sees the same order. Single-leader databases build exactly such a log. But at scale, the notebook gets split, and once it is split, nobody can say whether a line in notebook A came before a line in notebook B.

The book names four ways this happens: too many events for one machine, so the log is sharded; a leader per region, because synchronous cross-datacenter coordination is too slow; microservices that each own their state; and clients that work offline. Deciding a total order is total order broadcast, which is equivalent to consensus, and most consensus algorithms assume one node can handle the whole stream.

Try it: press Deliver events in One leader: both readers see the same sequence. Then try each of the other four modes and press it a few times: the two readers keep disagreeing.

What the book says

For small enough systems a totally ordered event log is entirely feasible, as the popularity of single-leader replication shows. As systems scale, limits emerge:

  • A totally ordered log usually requires all events to pass through a single leader node. If throughput exceeds one machine, you shard the log, and the order of events in two shards is then ambiguous.
  • Servers spread across geographically distributed regions typically have a separate leader in each datacenter, because network delays make synchronous cross-datacenter coordination inefficient; events originating in two datacenters have an undefined order.
  • With microservices, each service and its durable state is often deployed as an independent unit with no shared durable state; events from different services have no defined order.
  • Applications that update client-side state immediately on user input, and even work offline, mean clients and servers are very likely to see events in different orders.

Formally, deciding a total order of events is total order broadcast, equivalent to consensus. Most consensus algorithms assume a single node’s throughput is sufficient to process the entire stream of events and provide no way for multiple nodes to share the work of ordering.

Data integration · ordering events to capture causality

The message Marco was never meant to see

Ines and Marco have just broken up. Ines removes Marco as a friend, then posts “Marco never paid me back” to her remaining friends. Friendships live in one service and messages in another, each with its own log. The notifier joins the two: for each new message, tell the sender’s friends. If the friends log lags, the notifier sees the message first, and Marco gets the notification.

The two events were never concurrent: the message was caused by a state in which Marco was already gone. A total order over both logs would capture that, but we just saw why one may not exist. The book offers starting points instead: logical timestamps (still need out-of-order handling and extra metadata), recording the state the user saw as an event with an ID that later events reference, and conflict resolution, which fixes state but cannot recall a notification already sent.

Try it: press Run the story in No causal link. Then try Reference the event ID, where the message says which friends-log event Ines had seen. Try Conflict resolution too, and flip Friends log to fast to see that the bug is a race.

What the book says

If there is no causal link between events, the lack of a total order is not a big problem: concurrent events can be ordered arbitrarily. Multiple updates of the same object can be totally ordered by routing all updates for one object ID to the same log shard. But causal dependencies sometimes arise in more subtle ways.

The example: one user removes their ex-partner as a friend, then sends a message to their remaining friends complaining about them, intending that the ex should not see it. If friendship status and messages are stored in different places, that ordering dependency may be lost, and a notification service may process the message-send event before the unfriend event and notify the ex. The notification is effectively a join between messages and the friend list, related to the time dependence of joins from Chapter 12. This problem doesn’t seem to have a simple answer.

  • Logical timestamps can provide total ordering without coordination, but recipients must still handle events delivered out of order, and extra metadata must be passed around.
  • If you log an event recording the state the user saw before making a decision, and give it a unique identifier, later events can reference that identifier to record the causal dependency.
  • Conflict resolution algorithms help process events delivered in an unexpected order. They are useful for maintaining state, but do not help if actions have external side effects, such as sending a notification.

Perhaps patterns will emerge that capture causal dependencies efficiently, and maintain derived state correctly, without forcing all events through the bottleneck of total order broadcast.

Data integration · batch and stream processing

The same recipe, for a pot or for a river

Data integration means getting data into the right form in all the right places: consume inputs, transform, join, filter, aggregate, train models, evaluate, and write outputs. The outputs are derived datasets: search indexes, materialized views, recommendations, aggregate metrics.

Batch and stream processors are the two tools for this, and they share most of their principles. The fundamental difference is the input. A batch job reads a bounded dataset of known size, so it can finish and say “here is the complete answer”. A stream processor reads an unbounded one, so its output is never final; it is kept up to date as events arrive.

The goal of data integration is to make sure that data ends up in the right form in all the right places. That requires consuming inputs, transforming, joining, filtering, aggregating, training models, evaluating, and eventually writing to the appropriate outputs. Batch and stream processors are the tools for achieving this goal.

As Chapters 11 and 12 showed, batch and stream processing have a lot of principles in common. The main fundamental difference is that stream processors operate on unbounded datasets, whereas batch process inputs are of a known, finite size.

Data integration · maintaining derived state

One sick consumer, or the whole shop closed?

Imani’s bookshop takes an order, and that order has to show up in three other places: the search index, the recent-orders cache and the sales dashboard. Each of them is a function of the orders: give it the same orders and it builds the same thing. Nothing else goes in.

She can update all three synchronously, inside one distributed transaction with the order, the way a database updates its own secondary indexes. Then every copy is current the moment checkout returns, but if the dashboard is down, the transaction aborts and nobody can buy a book. Or she can append each order to a log and let every derived system read it at its own pace. A crashed consumer just falls behind; it remembers its offset and catches up when it comes back. Asynchrony keeps a fault where it happened, while distributed transactions spread it.

Try it: click the sales dashboard to crash it, then press Place an order three times. Watch its lag grow while the others keep up, then click it again to bring it back and watch it replay what it missed. Now switch to Sync in one transaction and order again with the dashboard down.

What the book says

Batch processing has quite a strong functional flavor, even if the code isn’t written in a functional language. It encourages deterministic, pure functions whose output depends only on the input and that have no side effects other than the explicit outputs, treating inputs as immutable and outputs as append-only. Stream processing is similar, but it extends operators to allow managed, fault-tolerant state.

Deterministic functions with well-defined inputs and outputs are good for fault tolerance and also simplify reasoning about the dataflows in an organization. Whether the derived data is a search index, a statistical model or a cache, it helps to think in terms of data pipelines that derive one thing from another, pushing state changes in one system through functional application code and applying the effects to derived systems.

In principle derived data systems could be maintained synchronously, just as a relational database updates secondary indexes within the same transaction as writes to the indexed table. However, asynchrony is what makes systems based on event logs robust: a fault in one part is contained locally, whereas distributed transactions abort if any one participant fails, so they tend to amplify failures by spreading them to the rest of the system.

Secondary indexes often cross shard boundaries: a term-partitioned index needs writes sent to multiple shards, a document-partitioned one needs reads sent to all shards. Such cross-shard communication is also most reliable and scalable if the index is maintained asynchronously.

The question nobody asked when you built the view

What the book says

When maintaining derived data, batch and stream processing are both useful. Stream processing lets changes in the input be reflected in derived views with low delay, whereas batch processing lets large amounts of accumulated historical data be reprocessed to derive new views onto an existing dataset.

Reprocessing existing data is a good mechanism for maintaining a system, evolving it to support new features and changed requirements.

Without reprocessing, schema evolution is limited to simple changes like adding a new optional field to a record or adding a new type of record. With reprocessing it is possible to restructure a dataset into a completely different model to better serve new requirements.

Data integration · schema migrations on railways

Lay a third rail, then take one away

In 19th-century England, railways were built to competing gauges, the distance between the two rails. A train built for one gauge couldn’t run on the other. A standard was chosen in 1846, but you can’t close a line for years to rebuild it. So engineers laid a third rail: on mixed-gauge track, trains of both gauges run, each on two of the three rails. Trains are converted one by one, and only when the last old train is gone does the extra rail come up.

Derived views let data do the same thing. Keep the old schema and the new schema side by side, as two views independently derived from the same log. Send a few users to the new view, find its bugs, then move more. If anything goes wrong, send them back: the old view never stopped being maintained. Every step is reversible, which is exactly what lets you move fast.

Try it: in Railway, press Run a train after converting one, then Lay the third rail and run again. In Two views, drag the slider up, press Ship a bug in v2, and then Roll back: nobody is stuck.

What the book says

Large-scale schema migrations occur in noncomputer systems too. In the early days of railway building in 19th-century England there were various competing standards for the gauge (the distance between the two rails). Trains built for one gauge couldn’t run on tracks of another, which restricted the interconnections in the network.

After a single standard gauge was decided in 1846, tracks with other gauges had to be converted without shutting lines down for months or years. The solution was to first convert the track to dual gauge or mixed gauge by adding a third rail. Once that is done, trains of both gauges can run, using two of the three rails; once all trains have been converted, the rail for the nonstandard gauge can be removed. The undertaking is expensive, which is why nonstandard gauges still exist: the BART system in the San Francisco Bay Area uses a different gauge from most of the US.

Derived views allow the same gradual evolution. Instead of a sudden switch, maintain the old schema and the new schema side by side as two independently derived views onto the same underlying data. Shift a small number of users to the new view to test its performance and find bugs while most users stay on the old one, gradually increase the proportion, and eventually drop the old view.

Every stage of such a migration is easily reversible if something goes wrong: you always have a working system to go back to. Reducing the risk of irreversible damage lets you be more confident and so move faster to improve your system.

Data integration · unifying batch and stream processing

Replaying Monday on a Thursday

Lucía needs orders counted per day, for all of history and for today as it happens. The early way, the lambda architecture, ran history through a batch system and recent events through a separate stream system, then merged their answers: two systems to build, run and keep in agreement. It had a number of problems and has fallen out of use. Newer engines run both kinds of computation in one system, sometimes called the kappa architecture: to process history, you just replay old events through the streaming job.

That only works if the engine has three things. It must be able to replay historical events. It must be exactly-once: if a task fails halfway, its partial output is thrown away. And it must group events into windows by event time, the time stamped on the event. Replaying four days of orders takes seconds, so if you window by processing time (the clock on the machine doing the work), every one of them lands in “now.”

Try it: in One system (kappa), press Run the job with all three features on: the bars match the true counts. Then switch off Event time and run it again, and do the same for Exactly once and Replay. Each missing feature breaks the answer in its own way.

What the book says

An early proposal for unifying batch and stream processing was the lambda architecture, which had a number of problems and has fallen out of use. More recent systems allow batch computations (reprocessing historical data) and stream computations (processing events as they arrive) to be implemented in the same system, an approach sometimes known as the kappa architecture.

Unifying them in one system requires:

  • The ability to replay historical events through the same processing engine that handles the stream of recent events. Log-based message brokers can replay messages, and some stream processors can read input from a distributed filesystem or object storage.
  • Exactly-once semantics for stream processors: the output is the same as if no faults had occurred, even if faults did occur. As with batch processing, this requires discarding the partial outputs of any failed tasks.
  • Tools for windowing by event time, not by processing time, since processing time is meaningless when reprocessing historical events. Apache Beam provides an API for expressing such computations, which can then be run using Apache Flink or Google Cloud Dataflow.

Unbundling databases · Unix and the relational model

Pipes you wire yourself, or one sentence that does it all

Ravi wants the three most visited pages from a log. The Unix way: chain small tools with pipes, sort | uniq -c | sort -rn | head. Each tool sees nothing but a stream of bytes, and Ravi decides every step, including that the first sort must come before uniq. The relational way: one declarative SQL query. Ravi says what he wants, and the database decides how.

Both are “simpler”, in opposite senses. Unix is a thin, low-level wrapper over the hardware: files and pipes that are just bytes. A relational database hides data structures on disk, concurrency and crash recovery behind a high-level abstraction, and a short query quietly draws on an optimizer, indexes, join methods, concurrency control and replication. Databases, batch and stream processors and operating systems all store data and let you process and query it. This part of the chapter tries to take the best of both.

Try it: press Run the pipeline and watch the bytes go through four tools, one column at a time. Then switch to SQL query and press Run the query: the same answer, plus everything the database did that you never asked for.

What the book says

At an abstract level, databases, batch/stream processors and operating systems all perform the same functions: they store some data and let you process and query it. A database stores records of a data model (rows, documents, vertices in a graph), an operating system’s filesystem stores files, but at their core both are “information management” systems. Batch processors are like a distributed version of Unix.

There are many practical differences. Many filesystems do not cope well with a directory containing 10 million small files, whereas a database containing 10 million small records is completely normal.

Unix aimed to present programmers with a logical but fairly low-level hardware abstraction, while relational databases wanted a high-level abstraction hiding the complexities of data structures on disk, concurrency, crash recovery and so on. Unix developed pipes and files that are just sequences of bytes; databases developed SQL and transactions. Unix is simpler in being a thin wrapper around hardware resources; relational databases are simpler in that a short declarative query can draw on query optimization, indexes, join methods, concurrency control and replication without its author understanding the implementation.

The tension has lasted for decades (both emerged in the early 1970s) and still isn’t resolved; the NoSQL movement could be interpreted as applying a Unix-esque approach of low-level abstractions to distributed OLTP data storage. This section attempts to reconcile the two approaches and combine the best of both worlds.

Unbundling databases · creating an index

Build the new shelf while customers keep shopping

Ayaan runs CREATE INDEX on a busy users table, without locking it. The database takes a consistent snapshot at some position in its log, scans it, picks out the city of every row, sorts them and writes the index. But writes kept arriving the whole time. So next it processes the backlog: every change logged since the snapshot. Only then does it switch to keeping the index up to date on every write.

Look at those steps again: snapshot, copy, then the log since the snapshot, then live. That is exactly how a new follower replica is set up, and how CDC bootstraps a derived system from an initial snapshot. CREATE INDEX is the database reprocessing its existing data into a new view.

Try it: press Play (or Step) and watch two writes sneak in while the index is being built, then Ask: city = Lima. Set Backlog to skip and do it again: the index silently misses a user. Switch the mode to New follower or CDC bootstrap: the steps don’t change, only their names.

What the book says

When you run CREATE INDEX in a relational database, the database has to scan over a consistent snapshot of a table, pick out all the field values being indexed, sort them, and write out the index. Then it must process the backlog of writes made since the snapshot was taken (assuming the table was not locked, so writes could continue). Once that is done, it must keep the index up-to-date whenever a transaction writes to the table.

This process is remarkably similar to setting up a new follower replica, and also very similar to bootstrapping CDC in a streaming system (the initial snapshot).

Whenever you run CREATE INDEX, the database essentially reprocesses the existing dataset and derives the index as a new view onto the existing data. The existing data may be a snapshot of the state rather than a log of all changes that ever happened, but the two are closely related.

Seen this way, the dataflow across an entire organization starts to look like one huge database. Batch and stream processors are like elaborate implementations of triggers, stored procedures and materialized view maintenance; the derived data systems they maintain are like different index types, provided by various pieces of software on different machines, administered by different teams.

If no single data model or storage format suits all access patterns, there are two avenues for composing different tools into a cohesive system.

Federated databases (unifying reads): a unified query interface over a wide variety of storage engines and processing methods, also called a polystore. Unbundled databases (unifying writes): federation does not have a good answer to synchronizing writes across systems. Making it easier to reliably plug storage systems together, for example through CDC and event logs, is like unbundling a database’s index-maintenance features so that writes stay in sync across disparate technologies. A slow team shouldn’t stop the shop

Tariq’s order service has three downstream teams: search, caching and the warehouse loader. One Friday the warehouse team deploys a bug and their loader falls over. On Monday the fix ships, the loader resumes from its saved offset, and it misses nothing.

The traditional alternative is a distributed transaction across all of them: every write commits everywhere or nowhere. Within one system that can work well (some stream processors use it internally for exactly-once). Across systems built by different groups, there is no standard protocol, and every write now waits for the slowest participant and fails if any one is down. That is loose coupling versus tight coupling, both for machines and for teams.

What the book says

Federation and unbundling are two sides of the same coin. Federated read-only querying requires mapping one data model into another, which is manageable; keeping the writes to several storage systems in sync is the harder engineering problem.

The traditional approach is distributed transactions across heterogeneous storage systems, which are problematic. Transactions within a single storage or stream processing system are feasible (some stream processors use distributed transactions internally to achieve exactly-once semantics), but when data crosses the boundary between technologies built by different groups of people, the lack of a standardized transaction protocol makes integration much harder. An asynchronous, ordered log of events with idempotent consumers is a much simpler abstraction, and far more feasible across heterogeneous systems.

The big advantage of log-based integration is loose coupling. At a system level, asynchronous event streams make the whole more robust to outages or slowness of individual components: the log buffers messages, the producer and other consumers carry on, and the faulty consumer catches up once fixed, without missing data. Synchronous distributed transactions, by contrast, tend to escalate local faults into large-scale failures.

At a human level, unbundling lets different teams develop, improve and maintain components independently, each doing one thing well behind well-defined interfaces. Event logs are powerful enough to capture fairly strong consistency properties (thanks to durability and ordering) yet general enough for almost any kind of data.

This is exactly what we want at a data system level. A shared variable you can only keep re-reading

Arjun’s checkout service is stateless: any server can take any request and forgets it afterwards, so servers come and go at will. Databases inherited that: if Arjun wants to know when the exchange rate changes, his only option is to poll, asking over and over. Poll often and most queries find nothing new; poll rarely and the screen shows a stale rate. What the book says

In theory, databases could be deployment environments for arbitrary application code, like an operating system. In practice they are poorly suited to it: they don’t fit modern needs such as dependency and package management, version control, rolling upgrades, evolvability, monitoring, metrics, calls to network services and integration with external systems. Deployment and cluster management tools such as Kubernetes, Docker, Mesos and YARN are designed for running application code and, by doing one thing well, do it much better.

Most web applications are deployed as stateless services: any request can go to any server, which forgets the request after responding, so servers can be added and removed at will. The state has to go somewhere, typically a database. The trend has been to keep stateless application logic separate from state management: no application logic in the database, no persistent state in the application. As the functional programming community jokes, “We believe in the separation of Church and state”, a reference to Alonzo Church, whose lambda calculus has no mutable state.

In this model the database acts as a kind of mutable shared variable accessed synchronously over the network; the application reads and updates it, and the database makes it durable and provides some concurrency control and fault tolerance.

But in most programming languages you cannot subscribe to changes in a mutable variable, only read it periodically; unlike in a spreadsheet, readers are not notified when the value changes. You can implement notifications yourself (the observer pattern), but most languages lack it as a built-in feature. Databases inherited this passive approach: to find out whether content has changed, often your only option is to poll. Subscribing to changes is only just beginning to emerge as a feature.

Unbundling databases · dataflow: interplay between state changes and application code

Lag heals; a lost message never does

Yuki’s shop derives two views from the stream of price changes: a page cache and a search index. Each is a piece of application code that responds to state changes in one place by making state changes in another. That is the same idea as change data capture, actors, triggers and incremental view maintenance, now applied outside the database.

For it to work, two properties are non-negotiable. Order: if the two views see the same changes in different orders, they end up disagreeing with each other. Reliability: if a single message is lost, that view is permanently out of sync, because nothing will ever send it again. A log-based message broker gives both: one order for every reader, and an offset each reader can resume from after a crash.

Try it: in Fire and forget, press Deliver the changes, then Wait an hour: the views stay wrong. Switch to Log-based broker and deliver again. The search index crashes halfway, restarts from its offset, and both views end up matching the source.

What the book says

Thinking about applications in terms of dataflow means renegotiating the relationship between application code and state management. Instead of treating a database as a passive variable manipulated by the application, we think about the interplay between state, state changes and the code that processes them: application code responds to state changes in one place by triggering state changes in another. We have seen this idea in CDC, the actor model, triggers and incremental view maintenance; unbundling the database means applying it to derived datasets outside the primary database, such as caches, full-text indexes, machine learning or analytics.

Maintaining derived data requires two properties that log-based message brokers can provide. The order of state changes is often important: if several views are derived from an event log, they must process events in the same order to stay consistent with one another. Fault tolerance is essential: losing just a single message makes the derived dataset go permanently out of sync with its source, so both message delivery and derived state updates must be reliable.

Stable message ordering and fault-tolerant processing are stringent demands, but much less expensive and more operationally robust than distributed transactions. Modern stream processors provide them at scale and let application code run as stream operators, doing the arbitrary processing that built-in derivation functions don’t. Like Unix tools chained by pipes, stream operators can be composed: each takes streams of state changes as input and produces other streams of state changes as output.

Unbundling databases · stream processors and services

The fastest network call is the one you never make

Lucía’s shop prices a lamp in dollars; Tariq pays in euros. To charge him the right amount, the checkout code needs the current exchange rate. The usual microservice way is to ask a rate service over the network at the moment of purchase. If that service is slow, checkout is slow. If it’s down, nobody can buy anything.

The dataflow way turns it around. The checkout processor subscribes to the stream of rate updates ahead of time and writes each new rate into a local database, maybe in the same process. At purchase time it just looks the rate up locally. The RPC has become a stream join between purchase events and rate-update events. Teams still own separate pieces, as with microservices, but the wires are one-way, asynchronous message streams instead of request and response.

One catch: the join is time-dependent. Reprocess last week’s purchases today and the “current” rate is a different number. To rebuild the original output you need the rate as of each purchase, whichever architecture you picked.

What the book says

The dominant style of application development breaks functionality into services that communicate via synchronous network requests such as REST APIs. Its advantage over a monolith is mainly organizational scalability through loose coupling: different teams work on different services, as long as they can be deployed and updated independently. Composing stream operators into dataflow systems has many similar characteristics, but the communication is one-directional, asynchronous message streams rather than synchronous request/response.

Besides better fault tolerance, dataflow can also perform better than REST or RPC. Take a purchase priced in one currency and paid in another. In the microservices approach, the code that processes the purchase would query an exchange rate service or database for the current rate. In the dataflow approach, it subscribes to a stream of exchange rate updates ahead of time, records the current rate in a local database whenever it changes, and queries that local database when processing the purchase. A microservice could cache the rate locally, but keeping that cache fresh means polling or subscribing to a stream of changes, which is exactly the dataflow approach.

The dataflow approach is faster and more robust to the failure of another service. “The fastest and most reliable network request is no network request at all!” Instead of RPC, there is a stream join between purchase events and exchange rate update events.

The join is time-dependent: if purchase events are reprocessed later, the exchange rate will have changed, and reconstructing the original output requires the historical rate at the original time of purchase, whether you query a service or subscribe to a stream. Subscribing to changes brings us closer to a spreadsheet-like model of computation; issues like time-dependent joins remain open questions.

Unbundling databases · materialized views and caching

Slide the line between writing and reading

Rahul runs a classifieds site. With no index, every search greps every advert: writing is free, reading gets ruinous as adverts pile up. With an inverted index, each write does a bit more (one posting-list update per word) and reads get cheap. Go further and keep a cache of the most common queries: each new advert must also be added to every cached result it matches, and a common query becomes one lookup. That cache is really a materialized view.

Go all the way, precomputing the results of every possible query, and the write path explodes, because the number of possible queries is exponential in the number of words. So indexes, caches and materialized views all do one job: they move the boundary between the write path and the read path. Where it should sit depends on how often you read, how often you write and how much data there is.

Try it: drag Boundary through its four positions and press Send a write, Common query and Rare query to see where each one stops. Then move Reads per write and Documents: the cheapest boundary (green in the table) moves. With ten documents and few reads, plain grep wins.

What the book says

A full-text search index is a good example: the write path updates the index, and the read path searches it. Writes update the index entries for all terms in the document. Reads search for each word in the query and apply Boolean logic: AND to find documents containing all the words, OR for synonyms. Without an index, a query would scan all documents like grep, which gets very expensive with many documents: less work on the write path, a lot more on the read path.

You could imagine precomputing search results for all possible queries, leaving the read path almost nothing to do, but the write path far more expensive. The set of possible queries is infinite (or at least exponential in the number of terms in the corpus), so this is not possible. Precomputing results only for a fixed set of the most common queries would generally be called a cache of common queries, though it could also be called a materialized view, since it must be updated when new documents appear that belong in one of those results.

So an index is not the only possible boundary between the write path and the read path. Caching common results is possible, and grep-like scanning without an index is possible on a small number of documents. The role of caches, indexes and materialized views is simple: they shift the boundary, letting us do more work on the write path, by precomputing results, to save effort on the read path.

Normally writes go through the log, while reads are quick network requests straight to the store. What the book says

When a stream processor writes derived data to a store (database, cache or index) and that store is queried, the store is the boundary between the write path and the read path, allowing random-access reads that would otherwise require scanning the whole event log. Stream processors also maintain state for aggregations and joins. That state is normally hidden, but some frameworks allow outside clients to query it, turning the stream processor itself into a kind of simple database.

So far writes go through an event log while reads are transient network requests directly to the nodes storing the data. That is reasonable, but not the only option: read requests can also be represented as streams of events, sent together with the write events through a stream processor, which responds to read events by emitting the result to an output stream.

When both are events routed to the same operator, you are performing a stream-table join between the stream of read queries and the database. Each read event must be sent to the shard holding the relevant data, just as batch and stream processors copartition inputs on the same key for joins. A one-off read request passes through the join operator, which immediately forgets it; a subscribe request is a persistent join with past and future events on the other side.

A log of read events may also help track causal dependencies and data provenance: it lets you reconstruct what the user saw before making a decision. In an online shop, the predicted shipping date and inventory status shown to a customer likely affect whether they buy; to analyze that, you need to record the result of their query. Durable reads add storage and I/O cost, and reducing that overhead is an open research problem, but if you already log read requests for operational purposes, making that log the source of the requests is not a big change.

So correctness matters most where there is state. For about four decades the tools of choice have been the transaction properties: atomicity, isolation and durability. Yet they are weaker than they look. Weak isolation levels confuse experts, and it is very hard to tell whether a given isolation level or replication setup is safe for your application. What the book says

With stateless services that only read data, it’s not a big deal if something goes wrong: fix the bug, restart the service, and everything returns to normal. We want applications that are reliable and correct: programs whose semantics are well defined and understood, even in the face of faults. For approximately four decades, atomicity, isolation and durability have been the tools of choice. But those foundations are weaker than they seem, witness the confusion of weak isolation levels. If you need stronger assurances, serializability and atomic commit are established approaches, but they typically work only in a single datacenter and limit scale and fault tolerance. The traditional transaction approach is not going away, but it is not the last word in correctness; the rest of the chapter explores other ways of thinking about it in dataflow architectures.

Silence after the charge: give up, or try again?

Kofi’s order sends a message: charge card ••42, €20. The payment worker takes it, and then nothing comes back. Did the worker crash before charging, or did it charge and the confirmation got lost? Exactly once doesn’t mean the work runs once. It means the final effect is as if no fault had happened, even though the operation was retried. The usual tool is idempotence: making a repeat harmless. Charging a card isn’t naturally idempotent, so the worker keeps extra metadata: the set of operation IDs it has already applied, updated together with the effect. What the book says

Exactly-once (or effectively-once) semantics: if something goes wrong while processing a message, you can either give up (by dropping the message and incurring data loss) or try again. If you try again, there is the risk that the processing actually succeeded the first time and you just didn’t get a confirmation, so the message ends up being processed twice.

Processing twice is a form of data corruption: it is undesirable to charge a customer twice for the same service (billing them too much) or to increment a counter twice (overstating a metric). In this context, exactly once means arranging the computation such that the final effect is the same as if no faults had occurred, even if the operation was retried because of a fault.

One of the most effective approaches is to make the operation idempotent: it has the same effect whether it is executed once or multiple times. For an operation that is not naturally idempotent this requires effort and care: you may need to maintain additional metadata (such as the set of operation IDs that have updated a value) and ensure fencing when failing over from one node to another.

Aiming for correctness · duplicate suppression

TCP drops the duplicates, until the connection drops

Inside one TCP connection, duplicates are someone else’s problem. Every segment carries a sequence number; the receiver puts segments back in order, asks again for lost ones and throws away copies, before your program sees a single byte. Mei’s banking app sends a transfer of $11 as four statements on one connection, and the network can shuffle and duplicate them all it likes.

But the database ties the transaction to the connection. If the connection times out after Mei’s app sent COMMIT and before the reply arrived, the app has no idea whether the transfer happened. It reconnects and runs the transaction again, on a new connection with new sequence numbers, so TCP can’t recognise it as a repeat. The transfer is not idempotent: $22 moves instead of $11. The textbook example of atomicity is not correct, and real banks don’t work like this.

What the book says

The need to suppress duplicates occurs in many places besides stream processing. TCP uses sequence numbers on packets to put them in the correct order at the recipient and to determine whether any were lost or duplicated; lost packets are retransmitted and duplicates are removed by the TCP stack before it hands the data to an application. But this works only within the context of a single TCP connection.

In many databases a transaction is tied to a client connection. If the client suffers a network interruption and connection timeout after sending the COMMIT but before hearing back, it does not know whether the transaction has been committed or aborted. It can reconnect and retry, but now it is outside the scope of TCP duplicate suppression. Since the transaction in Example 13-1 is not idempotent, $22 could be transferred instead of the desired $11. Even though code like this is a standard example for transaction atomicity, it is not correct, and real banks do not work like this.

2PC protocols break the one-to-one mapping between a TCP connection and a transaction, since they must allow a coordinator to reconnect after a network fault and tell the database whether to commit or abort an in-doubt transaction. Is that sufficient to ensure the transaction is executed only once? Unfortunately not: even if duplicates between database client and server are suppressed, the network between the end-user device and the application server remains.

Aiming for correctness · the end-to-end argument

Only the two ends can be sure

Every layer of the network protects you a little. Wi-Fi checks each frame on its own hop, TCP checks every segment between two machines, TLS seals the channel between the browser and the server. Each guard watches its own stretch of the road. A fault that happens before a guard’s stretch starts, or after it ends, walks right past it.

In 1984, Saltzer, Reed and Clark put a name to this: the end-to-end argument. Some functions can only be done completely and correctly by the applications at the two ends. Duplicate suppression is one (the request ID from the last scene). Integrity is another: network checksums can’t see a bug in the server or a rotting disk, so you need an end-to-end checksum. Secrecy is a third: TLS doesn’t help if the server itself is compromised, only end-to-end encryption does. The low-level guards still earn their keep: they catch the common faults cheaply, so the end-to-end check rarely has to.

What the book says

Suppressing duplicate transactions is one example of a more general principle, the end-to-end argument, articulated by Saltzer, Reed and Clark in 1984: “The function in question can completely and correctly be implemented only with the knowledge and help of the application standing at the endpoints of the communication system. Therefore, providing that questioned function as a feature of the communication system itself is not possible. (Sometimes an incomplete version of the function provided by the communication system may be useful as a performance enhancement.)”

Here the function was duplicate suppression. TCP suppresses duplicate packets at the connection level, and some stream processors provide so-called exactly-once semantics at the message processing level, but that is not enough to prevent a user from submitting a duplicate request if the first one times out. Solving it requires a transaction identifier passed all the way from the end-user client to the database.

The argument also applies to integrity: checksums built into Ethernet, TCP and TLS detect corruption of packets in the network, but not corruption due to bugs in the software at the sending and receiving ends, or on the disks where the data is stored; for that you need end-to-end checksums. A similar argument applies to encryption: your home WiFi password protects against people snooping your WiFi traffic, but not attackers elsewhere on the internet; TLS/SSL protects against network attackers, but not against compromises of the server. Only end-to-end encryption and authentication protect against all of these.

The low-level features are still useful, since they reduce the probability of problems at higher levels: HTTP requests would often get mangled without TCP putting packets back in the right order. They are just not sufficient by themselves for end-to-end correctness.

What the book says

Just because an application uses a data system with comparatively strong safety properties, such as serializable transactions, does not mean it is guaranteed to be free from data loss or corruption. The application itself needs to take end-to-end measures, such as duplicate suppression, as well.

Fault-tolerance mechanisms are hard to get right. Low-level mechanisms such as those in TCP work quite well, so the remaining higher-level faults occur fairly rarely. So it is worth exploring fault-tolerance abstractions that make application-specific end-to-end correctness easy while keeping good performance and operational characteristics at scale.

A shared log ensures that all consumers see messages in the same order: the total order broadcast guarantee, which is equivalent to consensus. With log-based messaging, the unbundled approach can enforce uniqueness constraints in a very similar way.

What the book says

In Example 13-2 there are potentially three shards: one holding the request ID, one the payee account, one the payer account. Executing it traditionally needs an atomic commit across all three, forcing it into a total order with all other transactions on those shards; with cross-shard coordination, throughput is likely to suffer. Equivalent correctness can be achieved without cross-shard transactions by using sharded logs and stream processors (Figure 13-2).

(1) The transfer request is given a unique request ID by the user’s client and appended to a log shard based on the source account ID. (2) A stream processor maintains a database, entirely derived from the log, with the source account’s state and the IDs of requests already processed. For a new ID, it checks for enough money; if so, it reserves the amount and emits an outgoing payment event to the source account’s shard (its own input log), an incoming payment to the destination’s shard and an incoming payment to the fees account’s shard, all carrying the original request ID. (3) The outgoing event is eventually delivered back to the source processor (which may have received unrelated events meanwhile); it recognizes the reserved payment by request ID, executes it, and ignores duplicates. (4) The destination and fees shards are consumed by independent tasks that apply incoming payments and deduplicate by request ID.

The accounts could just as well be in the same shard. The only requirements are that events for any account are processed strictly in log order with at-least-once semantics and that the processors are deterministic. If the source processor crashes mid-request, its outputs may or may not have been emitted; after recovery it processes the same request again, makes the same decision, and emits the same messages with the same request ID, which downstream consumers ignore if they are duplicates.

“Atomicity in this system comes not from transactions, but from the fact that writing the initial request event to the source account log is an atomic action.” Once that event is in the log, all downstream events will eventually be written too, possibly after crashes and possibly with duplicates. Exactly-once semantics make this easier, since the processor’s local state is reset along with the messages it reprocesses. To learn the outcome, the user subscribes to the source account’s shard and waits for the outgoing payment, or a “declined payment” event. Every request is applied exactly once to both payer and payee, without an atomic commit protocol.

Late can be fixed by waiting. Wrong can’t.

Sana buys a coffee and opens her card statement. The coffee isn’t there yet. Annoying, but she knows card payments take a while to settle, and an hour later it shows up. That is a timeliness problem: she saw a stale but honest picture, and waiting fixed it.

That is an integrity problem: data that is wrong, lost or contradictory. Waiting does nothing. Someone has to notice and repair it. The word consistency mixes these two ideas together, and pulling them apart is the key to this part of the chapter: integrity matters far more than timeliness.

What the book says

In many transactional systems, as soon as one transaction commits its writes are immediately visible to other transactions (strict serializability). That is not the case when an operation is unbundled across several stages of stream processors: log consumers are asynchronous by design. A client can wait for a message on an output stream, like the user waiting for an outgoing payment or declined event in Figure 13-2, but the correctness of the balance check does not depend on whether the user waits; the waiting only informs the user.

The term consistency conflates two requirements. Timeliness means users observe the system in an up-to-date state; reading a stale copy (replication lag) is a temporary inconsistency, resolved by waiting and trying again. The CAP theorem’s consistency (linearizability) is a strong form of timeliness; read-after-write consistency is a weaker, useful one.

Integrity means absence of corruption: no data loss and no contradictory or false data; a derived dataset must be a correct view of the underlying data, as an index with missing records is not very useful. If integrity is violated the inconsistency is permanent; waiting and retrying won’t fix it, and explicit checking and repair is needed. ACID “consistency” is usually an application-specific notion of integrity, and atomicity and durability are important tools for preserving it.

“In slogan form: violations of timeliness are allowed under eventual consistency, whereas violations of integrity result in perpetual inconsistency.” In most applications integrity is much more important than timeliness. On a credit card statement, a transaction from the last 24 hours not yet appearing is unsurprising; banks reconcile and settle asynchronously. But a balance that isn’t the sum of the transactions plus the previous balance, or a charge that isn’t paid to the merchant, would be violations of integrity.

Aiming for correctness · correctness of dataflow systems

Four rules that keep the money right

An ACID database gives you timeliness and integrity in one package, so nobody bothers to tell them apart. A dataflow system splits them. Wen sends $20 and immediately looks at her balance: the processor hasn’t run yet, so she sees the old number. That is a timeliness gap, and she can close it by waiting for the output event.

Integrity, though, the dataflow system keeps without any distributed transaction, through four habits: (1) the whole write is one message, so it is either in the log or not; (2) every other update is derived deterministically from that message; (3) a client-made request ID travels through every stage, so retries and replays are harmless; (4) messages are immutable, so after a bug you fix the code and reprocess. Take any one away and a specific kind of corruption walks in.

What the book says

ACID transactions usually provide both timeliness (e.g., linearizability) and integrity (e.g., atomic commit), so from that point of view the distinction is fairly inconsequential. Event-based dataflow systems decouple them: when processing streams asynchronously there is no guarantee of timeliness unless you explicitly build consumers that wait for a message. A user could request a payment and read their account before the processor has executed it, and not see the payment.

Integrity, however, is central to streaming systems. Exactly-once or effectively-once semantics is a mechanism for preserving integrity: if an event is lost or takes effect twice, integrity could be violated. So fault-tolerant message delivery and duplicate suppression (e.g., idempotent operations) are important for maintaining integrity in the face of faults.

Reliable stream processing can preserve integrity without distributed transactions and atomic commit, potentially achieving comparable correctness with much better performance and operational robustness, through a combination of mechanisms: representing the content of the write as a single message, which can easily be written atomically (a good fit with event sourcing); deriving all other state updates from that message via deterministic derivation functions, similarly to stored procedures; passing a client-generated request ID through all levels of processing, enabling end-to-end duplicate suppression and idempotence; and making messages immutable and allowing derived data to be reprocessed from time to time, which makes it easier to recover from bugs.

Sell first, say sorry later

Kofi’s shop has three kettles left and five customers clicking Buy at once. The strict way: every order asks the warehouse first, synchronously, and the fourth and fifth are told “sold out.” That needs coordination on every click, and when the link to the warehouse is down, nobody can buy anything.

But Kofi needs an apology process anyway: last month a forklift ran over a kettle that had already been sold. So why not take every order straight away, check stock after the fact, and send the unlucky customers an apology, a discount and a new delivery date? That apology is a compensating transaction. Airlines overbook seats, hotels overbook rooms and banks charge overdraft fees for exactly this reason. One rule stays firm: check before doing anything you can’t undo, like shipping the box.

Try it: press Five orders at once in both modes and compare. Then press Reset, Cut the link and order again: the strict shop turns everyone away, the loose shop keeps selling. Forklift! breaks a kettle and shows that even the strict shop has to apologize sometimes.

What the book says

Enforcing a uniqueness constraint requires consensus, typically by funneling all events in a shard through a single node. That limitation is unavoidable for the traditional form of the constraint, and stream processing cannot get around it. But many real applications have a business requirement to allow violations of what you might think of as hard constraints.

If customers order more items than you have, you can order in more stock, apologize for the delay and offer a discount, the same thing you would do if a forklift truck ran over some items in your warehouse; the apology workflow already needs to be part of your business processes. Airlines overbook planes and hotels overbook rooms, with compensation processes (refunds, upgrades, a complimentary room at a neighboring hotel), which are needed anyway for cancelled flights. A bank can charge an overdraft fee, and limiting total withdrawals per day bounds its risk. Systems that integrate data across organizations need correction mechanisms, as in settlement of payments between banks.

So it is often acceptable to temporarily violate a constraint and fix it up later by apologizing. This kind of change to correct a mistake is called a compensating transaction. The cost of the apology is often quite low: you can’t unsend an email, but you can send a correction; a double charge can be refunded. Once money has been paid out of an ATM you can’t directly get it back, though you can send debt collectors.

Whether the cost of the apology is acceptable is a business decision. If it is, checking all constraints before writing the data is unnecessarily restrictive: it may be reasonable to write optimistically and check the constraint after the fact, while still validating before actions that would be expensive to recover from. These applications do require integrity (no lost reservation, no money disappearing through mismatched credits and debits), but not timeliness on the enforcement of the constraint.

Aiming for correctness · coordination-avoiding data systems

Sell now, tell the other office later

Ana in Lisbon and Joon in Seoul sell seats on the same 10-seat tour. If every sale needs a phone call to the other office first, nobody can ever sell the tenth seat twice. But the day the undersea cable is cut, nobody can sell anything at all, and every customer gets an apology for an outage.

So they stop calling. Each office writes its sales into its own log and ships a copy to the other office whenever the cable works. Both keep selling during the cut. Once in a while the tenth seat goes twice, and someone gets an apology and a voucher for an inconsistency. What never happens is a sale that vanishes or counts twice: every sale has an ID and lands in both logs exactly once. That is a coordination-avoiding system: weak timeliness (Seoul learns about Lisbon’s sale late), strong integrity.

Coordination isn’t all or nothing. Make the few operations you can’t undo wait for a check, and let the cheap-to-fix ones run free. Somewhere between the two extremes is the fewest apologies in total.

What the book says

Two observations: dataflow systems can maintain integrity guarantees on derived data without atomic commit, linearizability, or synchronous cross-shard coordination; and although strict uniqueness constraints require timeliness and coordination, many applications are fine with loose constraints that may be temporarily violated and fixed up later, as long as integrity is preserved throughout.

Together, these mean dataflow systems can provide data management services for many applications without requiring coordination, while still giving strong integrity guarantees. Such coordination-avoiding data systems can achieve better performance and fault tolerance than systems that need to perform synchronous coordination. For example, such a system could run across multiple datacenters in a multi-leader configuration, asynchronously replicating between regions; any one datacenter can keep operating independently. Its timeliness guarantees are weak (it could not be linearizable without introducing coordination), but its integrity guarantees can still be strong.

Serializable transactions are still useful as part of maintaining derived state, but they can be run at a small scope where they work well. Heterogeneous distributed transactions such as XA transactions are not required. Synchronous coordination can still be introduced where it is needed, for example to enforce strict constraints before an operation from which recovery is not possible, but not everything has to pay its cost if only a small part of an application needs it.

Coordination and constraints reduce the number of apologies you have to make for inconsistencies, but may also reduce performance and availability, and so increase the number of apologies you have to make for outages. “You cannot reduce the number of apologies to zero, but you can aim to find the best trade-off for your needs.”

Impossible is just unlikely, times a lot of machines

Farid’s team writes down what they plan for. Processes crash, machines lose power, the network delays and drops messages: they handle all of that. It’s called the system model.

The list is binary, but the world isn’t. Each item is really a probability per machine per day. One laptop will probably never see a memory word change by itself. A fleet of 100,000 machines runs 36.5 million machine-days a year, and a one-in-a-million event turns up dozens of times. The useful question isn’t whether it can happen, but whether it happens often enough that we will meet it.

What the book says

All the discussion of correctness, integrity and fault tolerance assumed that certain things might go wrong, but other things won’t. These assumptions are the system model: for example, processes can crash, machines can suddenly lose power, and the network can arbitrarily delay or drop messages; but data written to disk is not lost after fsync, data in memory is not corrupted, and the CPU’s multiplication instruction always returns the correct result.

These assumptions are quite reasonable, since they are true most of the time, and it would be hard to get anything done if we constantly worried about computers making mistakes. Traditionally, system models take a binary approach toward faults: some things can happen, others can never happen. In reality it is a question of probabilities, and the question is whether violations of our assumptions happen often enough that we may encounter them in practice.

Data can become corrupted in memory, on disk and on the network, as earlier chapters showed. “If you are operating at large enough scale, even very unlikely things do happen.”

ACID keeps you consistent only if the code is right

The hospital rule: at least one doctor is on call for shift 1234. Aisha and Bruno are both on call, both feel ill, and both press Go off call in the same second. Now break something. Run them at a weak isolation level used unsafely, and both commit: nobody is on call. What the book says

Besides hardware issues, there is always the risk of software bugs, which would not be caught by lower-level network, memory or filesystem checksums. Even widely used database software has bugs: past versions of MySQL have failed to correctly maintain uniqueness constraints, and PostgreSQL’s serializable isolation level has exhibited write skew anomalies in the past, even though both are robust, well-regarded and battle-tested. In less mature software, the situation is likely to be much worse.

Despite careful design, testing and review, bugs still creep in. They are rare and eventually get found and fixed, but there is still a period during which they can corrupt data.

Application code has to be assumed to have many more bugs, since most applications don’t receive anywhere near the review and testing that database code does. Many applications don’t even correctly use the features databases offer for preserving integrity, such as foreign-key or uniqueness constraints.

Consistency in the sense of ACID is based on the idea that the database starts off in a consistent state and a transaction transforms it from one consistent state to another. That only makes sense if the transaction is free from bugs. If the application uses the database incorrectly, for example using a weak isolation level unsafely, the integrity of the database cannot be guaranteed.

Aiming for correctness · don’t just blindly trust what they promise

To know it’s still there, read it

Three disks each hold a copy of six blocks. Now and then one copy quietly rots: no error, no log line, nothing. Nobody finds out until someone reads that block, and if by then all three copies have rotted, the data is gone for good. A scrubber reads every copy back on a schedule, compares it against its checksum, and rewrites a bad copy from a good one long before the last good copy is lost.

Backups have the same problem. A nightly job can report success for weeks while writing empty files. The only proof that a backup works is restoring it, so you test restores before the day you need one. Checking the integrity of your data like this is auditing.

Try it: in Replicas, press Run 12 months with the scrubber off and count the lost blocks; turn it on and run again. In Backups, press Run 30 days, then disaster with restore tests off, then weekly.

What the book says

With hardware and software not always living up to our ideals, data corruption seems inevitable sooner or later. So we should at least have a way of finding out if data has been corrupted, so we can fix it and track down the source of the error. Checking the integrity of data is known as auditing. It is not just for financial applications, but it is very important in finance precisely because everyone knows that mistakes happen.

Mature systems tend to consider the possibility of unlikely things going wrong and manage that risk. Large-scale storage systems such as HDFS and Amazon S3 do not fully trust disks: they run background processes that continually read back files, compare them to other replicas, and move files from one disk to another, to mitigate the risk of silent corruption.

If you want to be sure your data is still there, you have to read it and check. By the same argument, it is important to try restoring from your backups from time to time, or you may find out your backup is broken when it is too late. “Don’t just blindly trust that it is all working.”

Systems like HDFS and S3 still assume that disks work correctly most of the time, which is not the same as assuming they always do. Not many systems currently have this kind of “trust, but verify” approach of continually auditing themselves; in the future we may see more self-validating or self-auditing systems.

What the book says

If a transaction mutates several objects in a database, the underlying reason can be difficult to tell after the fact. Even if you capture the transaction logs, the insertions, updates and deletions in various tables do not necessarily give a clear picture of why those mutations were performed. The invocation of the application logic that decided on them is transient and cannot be reproduced.

Event-based systems can provide better auditability. In the event sourcing approach, user input is represented as a single immutable event, and any resulting state updates are derived from that event. The derivation can be made deterministic and repeatable, so running the same log of events through the same version of the derivation code results in the same state updates.

Being explicit about dataflow makes the provenance of data much clearer, which makes integrity checking much more feasible. For the event log, hashes can check that the event storage has not been corrupted. For any derived state, you can rerun the batch and stream processors that derived it to check whether you get the same result, or even run a redundant derivation in parallel.

A deterministic, well-defined dataflow also makes it easier to debug and trace why a system did something: the ability to reproduce the exact circumstances that led to an unexpected event is a kind of time-travel debugging.

Aiming for correctness · the end-to-end argument again

Check the whole pipeline, and every part is checked for free

Product prices flow from the shop’s database, through change capture, over the network into a log, through a stream processor, and into the search index. Each stage has its own guard: disk checksums, TCP checksums, a checksum on every message. Each guard catches its own kind of fault and nothing else. A bug in the processor computes the wrong price and then checksums it perfectly. A disk that acknowledges a write it never made has nothing to checksum.

An end-to-end check asks the only question that matters: does the index match what the source says it should be? Derive the expected value from the source, compare it with what the index holds. Every disk, network hop, service and algorithm on the path is included without being named. And once such a check runs continuously, you can ship a new processor version without fear: if it’s wrong, you find out in minutes, not when customers do.

What the book says

If we cannot fully trust that every individual component of the system will be free from corruption (that every piece of hardware is fault-free and every piece of software is bug-free), then we must at least periodically check the integrity of our data. If we don’t check, we won’t find out about corruption until it has caused some downstream damage, when it is much harder and more expensive to track down.

Checking the integrity of data systems is best done in an end-to-end fashion. The more systems we can include in an integrity check, the fewer opportunities there are for corruption to go unnoticed at some stage. If we can check that an entire derived data pipeline is correct end to end, then any disks, networks, services and algorithms along the path are implicitly included in the check.

Continuous end-to-end integrity checks increase your confidence about the correctness of your systems, which in turn allows you to move faster. Like automated testing, auditing increases the chances that bugs will be found quickly, and so reduces the risk that a change to the system or a new storage technology will cause damage. “If you are not afraid of making changes, you can much better evolve an application to meet changing requirements.”

Prove one record is in the log with three hashes

A public log of website certificates has millions of entries. Nadia wants to check that the certificate for noor.io really is in it, without downloading all of them. The log builds a Merkle tree: hash every record, hash each pair of hashes, and keep going until one root hash is left. The log publishes and signs that root.

To prove noor.io is in, the log sends just the sibling hash at each level: three hashes for eight records, twenty for a million. Nadia hashes the record, combines it with each sibling in turn, and checks that she arrives at the signed root. Change a single character in any record and every hash above it changes, all the way to the root. This is how certificate transparency works. Blockchains use the same tools, plus a Byzantine fault-tolerant consensus protocol, which costs far more.

Try it: in Inclusion proof, click a record, then press Verify the proof and follow the code. In Tamper, click a record to change one letter and watch the hashes turn red up to the root. The hashes are real SHA-256, shortened to 8 hex digits.

What the book says

Not many data systems make auditability a top-level concern. Some applications log all changes to a separate audit table, but guaranteeing the integrity of the audit log and the database state is still difficult. A transaction log can be made tamper-proof by periodically signing it with a hardware security module, but that does not guarantee that the right transactions went into the log in the first place.

Blockchains such as Bitcoin and Ethereum are shared append-only logs with cryptographic consistency checks; the transactions they store are events, and smart contracts are basically stream processors. Their consensus protocols ensure all nodes agree on the same sequence of events. The difference from the consensus protocols of Chapter 10 is that blockchains are Byzantine fault-tolerant: they still work if some participating nodes have corrupted data, because the replicas continually check one another’s integrity.

For most applications, blockchains have too high an overhead to be useful, but some of their cryptographic tools can be used in a lighter-weight context. Merkle trees are trees of hashes that can be used to efficiently prove that a record appears in a dataset (and a few other things). Certificate transparency uses cryptographically verified append-only logs and Merkle trees to check the validity of TLS/SSL certificates; it avoids needing a consensus protocol by having a single leader per log.

Integrity-checking and auditing algorithms like these might become more widely used in data systems in the future. Some work is needed to make them as scalable as systems without cryptographic auditing and to keep the performance penalty low.

The philosophy in eight sentences

From the book’s summary.

Compose, because no tool does it all

No single piece of software serves every access pattern, so applications combine several. Batch jobs and event streams carry data changes between them.

One system of record, the rest derived

Some systems hold the truth; indexes, materialized views, models and summaries are derived from them by transformations, in one agreed order.

Asynchronous means contained

Deriving asynchronously, through a log, keeps a slow or broken consumer from dragging the rest of the system down with it.

Evolve by re-deriving

Want a new index structure, or found a bug? Rerun the new transformation over the whole input and derive the output again, side by side with the old one.

The database, unbundled

This is what databases already do inside (indexes, replication, views), taken apart into loosely coupled pieces that different teams run.

All the way to the screen

Derived state can itself be observed. Push changes down to end-user devices and the UI updates live and keeps working offline.

Integrity without distributed transactions

End-to-end request IDs make operations idempotent; constraints are checked asynchronously. Clients wait for the check, or go ahead and risk an apology.

Trust, but verify

Avoid coordination where you can, keep integrity everywhere, and keep auditing: hash the log, re-derive, compare, restore the backup.

The seesaws from this chapter

Distributed transactions

Atomic commit; you read your own write right away. Blocks or aborts when any participant fails.

vs

Log-based derived data

Deterministic retry and idempotence; faults stay local. Reads may be a little behind.

vs

Shards, regions, services, offline clients

vs

One unified engine

Federated (unifying reads)

vs

Unbundled (unifying writes)

One integrated product

vs

Composed from many tools

Breadth no single product has, paid for in learning curves, configuration and operations

Work on the write path

vs

Work on the read path

Request/response and polling

vs

Subscribe and push

Words to know

Grown-up words, in plain language.

system of record
The place where a piece of data is written first and held as the truth. Everything else is derived from it.
derived data
Data computed from other data, such as an index, a cache or a model. If you lose it, you can compute it again.
dual writes
The application writing the same change to two systems itself. Concurrent clients can make the two systems disagree forever.
change data capture (CDC)
Reading a database’s changes, in order, and applying them to other systems.
total order broadcast
Delivering the same messages to every node in the same order. Equivalent to consensus.
causal dependency
One event happened because of, or after seeing, another. Lost if the two travel in different logs.
logical timestamp
A counter-based timestamp that orders events without coordination, at the cost of extra metadata and out-of-order delivery.
reprocessing
Running new derivation code over all the historical input to build a brand-new view of it.
lambda architecture
An early design that ran a batch system and a stream system side by side. It has fallen out of use.
kappa architecture
One processing engine that handles both historical replays and live events.
event time
When the event actually happened, as opposed to processing time, when a machine got round to it.
unbundling
Taking the features a database has inside (indexes, views, replication) and providing them with separate, composed tools.
federated database
A single query interface over many different storage engines. Also called a polystore.
loose coupling
Components that can fail, slow down or change without dragging each other along.
derivation function
The code that turns a source dataset into a derived one, from “sort by this column” to a whole ML pipeline.
observer pattern
Code that subscribes to changes in a value and is notified, instead of polling it.
write path
The work done eagerly when data comes in, whether or not anyone asks for it yet.
read path
The work done lazily, only when someone asks a question.
materialized view
A stored, precomputed query result that is kept up to date as its inputs change.
local-first / offline-capable
An app that keeps its state on the device, works without a connection and syncs in the background.
server-sent events, WebSockets
Ways for a server to keep a connection open and push messages to a browser.
consumer offset
How far a consumer has read in a log. Resume from it and nothing is missed.
stream-table join
Joining each event in a stream with the current state in a table, such as a read query against a database.
exactly-once (effectively-once)
The final effect is as if no fault had happened, even though some work was retried.
idempotent
Doing it twice has the same effect as doing it once.
fencing
Making sure a node that has been replaced can no longer write, so a failover can’t cause double effects.
request ID
A unique identifier made by the client and carried all the way to the database, so a retry can be recognized.
end-to-end argument
Some guarantees can only be provided by the application at the endpoints, not by the network or the database in between.
uniqueness constraint
A rule that no two records may share a value, such as a username. Enforcing it needs consensus.
compensating transaction
A later change that corrects a mistake: a refund, an apology, a voucher.
timeliness
Users see the system in an up-to-date state. Violations heal by waiting.
integrity
No corruption: nothing lost, nothing contradictory or false. Violations are permanent until repaired.
coordination-avoiding
A system that keeps integrity without synchronous coordination between nodes or regions.
system model
The list of things we assume can go wrong, and the things we assume never will.
auditing
Checking the integrity of data, so corruption is found and fixed.
Merkle tree
A tree of hashes. A short path of hashes proves that one record is part of a dataset.
Byzantine fault tolerance
Working correctly even when some participants are corrupted or lying, as blockchains aim to.
certificate transparency
Cryptographically verified, append-only logs of TLS certificates, with one leader per log.
