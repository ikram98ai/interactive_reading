Big idea 1 · combining tools by deriving data

Two tools, two different stories

The school library runs on two tools. The database is the careful record-keeper: it never forgets which books exist. The search index is the fast finder: type any word and it digs up matching titles. Neither can do the other's job well, so the library needs both — and both must hold the same facts.

One afternoon Noor and Pablo rename the same book at the same moment. The app sends each change to both tools. But messages race. The database hears Noor, then Pablo. The search index hears Pablo, then Noor. Each keeps the last thing it heard. Now they disagree — and because nobody was in charge of the order, nothing will ever bring them back together.

The fix: choose one place that decides the order. Every change goes into a single log first, and both tools copy from it, top to bottom. The search index is now derived from exactly the same sequence as the database, so it cannot end up telling a different story.

Try it: press “Both save at once” a few times while the app writes to both tools. Then switch to the log and try as hard as you like to make them disagree.

What the book says

Every piece of software, even a so-called “general-purpose” database, is designed for a particular usage pattern, so complex applications inevitably cobble several tools together. A common case is an OLTP database plus a full-text search index: PostgreSQL's built-in full-text indexing can be enough for simple applications, but sophisticated search needs specialist information-retrieval tools — and search indexes are generally not very suitable as a durable system of record. Warehouses, caches, denormalized copies, machine-learning and recommendation systems, and notifications add more copies of the same data.

So be very clear about inputs and outputs: where is data written first, and what is derived from what? If data is written to a system-of-record database and change data capture (CDC) is the only way the index gets updated, the index is entirely derived from the system of record and consistent with it (barring bugs). Letting the application write to both directly recreates the problem where two clients' conflicting writes are processed in a different order by the two stores, and they become permanently inconsistent.

Funnelling all user input through one system that decides a total order is an application of state machine replication. Whether you use CDC or an event-sourcing log matters less than that principle. Updating a derived system from an event log can often be made deterministic and idempotent, which makes recovering from faults quite easy.

Versus distributed transactions: both aim at the same goal — transactions by atomic commit, logs by deterministic retry and idempotence. The biggest difference is that transactions usually let you read your own writes immediately, while derived systems are often updated asynchronously. XA has poor fault tolerance and performance, so the book calls log-based derived data the most promising approach for integrating different systems — while adding that simply telling everyone “eventual consistency is inevitable — suck it up” is not productive without good guidance on how to deal with it.

Big idea 2 · the limits of one big order

The message Theo was never meant to see

One log is lovely while one machine can keep up. Bigger systems can't have it: the log gets split into shards, each region of the world gets its own leader, each service keeps its own data, and phones carry on working offline. Two events that start in two different places have no agreed order.

Usually that's fine. Sometimes it really isn't. Maya and Theo fall out. Maya first removes Theo as a friend, and then posts a grumpy message to her friends. Friendships live in one service; posts live in another. A third service sends the “new post!” notifications, and it needs both. If the post reaches it before the unfriending does, it looks at a friend list that still includes Theo…

The post depended on the unfriending — a causal link — and the system dropped it on the floor. One repair: let the post carry a little note saying which event its author had already seen, so the notifier knows to wait for that one first.

Try it: make the friends log slow with the slider and play the story. Then switch on the note and play it again.

What the book says

A totally ordered log is entirely feasible for small systems (it is what single-leader replication builds). The limits appear as systems grow:

  • A total order usually needs every event to pass through a single leader node. Beyond one machine's throughput you must shard the log, and the order of events in two shards is ambiguous.
  • With several geographically distributed regions you typically have a leader per datacenter, so events from two datacenters have an undefined order.
  • Microservices keep their durable state separate; events from two services have no defined order.
  • Client-side state that updates immediately, or works offline, means clients and servers see events in different orders.

Deciding a total order is total order broadcast, which is equivalent to consensus — and most consensus algorithms assume one node can handle the whole stream.

When events are not causally linked, the lack of a total order is not a big problem, and updates to one object can be ordered by routing them to the same shard. The unfriend example is subtler: the notification is effectively a join between messages and the friend list, with the same time-dependence as stream joins. The book says plainly that this problem does not seem to have a simple answer. Starting points: logical timestamps (order without coordination, but recipients must still cope with out-of-order delivery and extra metadata); logging an event that records the state the user saw before deciding, and referencing its ID from later events; and conflict resolution algorithms, which help maintain state but not when actions have external side effects such as sending a notification.

Big idea 3 · batch and stream, together

Lay a third rail

In 19th-century England, railways were built with different distances between the rails. Once a single standard was chosen in 1846, the odd lines had to change — but how, without closing them for months or years? Add a third rail. Now old trains and new trains can both run on the same line. When every train fits the new width, pull up the spare rail.

Data can move the same way. The library has a view that counts loans per book. Now it wants loans per reader — a completely different shape. Because every loan is still in the log, a batch job can replay all of history through new code and build the new view beside the old one, while the stream of fresh loans keeps both up to date.

Then you move readers across a few at a time. If the new view turns out to have a bug, send everyone back — the old one never went away. Every step can be undone, and that is exactly what makes you brave enough to move fast.

Try it: replay history into v2, slide some users across, press “Found a bug in v2!”, rebuild — and only drop v1 when everybody has moved. (Then see what a bug costs after you dropped it.)

What the book says

Batch and stream processors are the tools of data integration; their outputs are derived datasets — search indexes, materialized views, recommendations, aggregate metrics. The main fundamental difference is that stream processors work on unbounded datasets, while batch inputs have a known, finite size. Both favor deterministic, pure functions with immutable inputs and append-only outputs; stream processing adds managed, fault-tolerant state.

Derived data could be maintained synchronously, as a relational database does for its secondary indexes — but asynchrony is what makes log-based systems robust. A fault stays contained locally, whereas a distributed transaction aborts if any one participant fails, amplifying failures. Cross-shard secondary indexes, too, are most reliable and scalable if maintained asynchronously.

Reprocessing for application evolution: without it, schema evolution is limited to simple changes such as adding an optional field or a new record type; with it you can restructure a dataset into a completely different model. Old and new schema live side by side as two independently derived views; you shift a small number of users, then more, then drop the old view. Every stage is easily reversible. (The railway conversion was expensive, which is why nonstandard gauges still exist — BART in the San Francisco Bay Area uses a different gauge from most of the US.)

Unifying batch and stream: an early proposal, the lambda architecture, had a number of problems and has fallen out of use. More recent systems run both kinds of computation in the same system — sometimes called the kappa architecture. That needs: replay of historical events through the same engine that handles recent ones (log-based brokers can replay; some stream processors read from a distributed filesystem or object storage); exactly-once semantics; and windowing by event time, not processing time, which is meaningless during a replay. Apache Beam offers an API for such computations, runnable on Apache Flink or Google Cloud Dataflow.

Big idea 4 · unbundling the database

Take the database apart

Lift the lid off a database and you find a crowd of helpers. Secondary indexes find rows fast. Materialized views keep answers ready-made. A replication log keeps other copies up to date. When you type CREATE INDEX, the database re-reads everything it holds, derives an index from it, and then keeps that index fresh with every new write.

Sound familiar? It is exactly what log-and-derive does — only spread over different machines run by different teams. Squint, and a whole company's dataflow is one enormous database: the search server is its index, the cache is its materialized view, the warehouse is its replica.

There are two ways to glue separate tools into one system. Federation gives you one query window onto many stores: it unifies reads. Unbundling makes one write reach every store: it unifies writes, and that is the hard part. You could wrap all the stores in one big all-or-nothing transaction… or let each of them follow a log at its own pace.

Try it: click the search index to crash it, then save a few books — in both modes. Then click it again to heal it and watch what happens.

What the book says

Databases, batch/stream processors and operating systems all store data and let you process and query it. Unix offered a thin, low-level abstraction (files as byte sequences, pipes); relational databases offered a high-level one (SQL, transactions) that hides data structures, concurrency and crash recovery. Both emerged in the early 1970s and the tension is still unresolved; the book reads NoSQL as a Unix-esque approach applied to distributed OLTP storage.

CREATE INDEX scans a consistent snapshot, picks out and sorts the indexed values, writes the index, works through the backlog of writes made since the snapshot, and then keeps the index up to date — remarkably like setting up a new follower or bootstrapping CDC. Seen this way, batch, stream and ETL jobs are elaborate triggers, stored procedures and materialized-view maintenance, and derived systems are like different index types: the meta-database of everything.

Federated databases (polystores) unify reads behind one query interface — PostgreSQL's foreign data wrappers, and federated query engines such as Trino, Hoptimator and Xorq. Unbundled databases unify writes, in the Unix tradition of small tools that do one thing well. Federation has no good answer to synchronizing writes; doing that with distributed transactions across heterogeneous systems is problematic, while an ordered log with idempotent consumers is a much simpler abstraction. Its big advantage is loose coupling: a slow or failed consumer is buffered by the log and catches up later, so the fault is contained; and teams can build and run their pieces independently.

Unbundling will not replace databases — they are still needed to hold stream-processor state and to serve the outputs. Every extra piece of infrastructure has a learning curve and operational quirks, and building for scale you don't need is premature optimization. “It's about breadth, not depth”: if one product does everything you need, use it. Tools keep improving: Debezium extracts change streams from many databases, Kafka's protocol is becoming a de facto standard for event streams, and incremental view maintenance engines precompute and update caches of complex queries.

Big idea 5 · applications built around dataflow

What spreadsheets already knew in 1979

Type a new number into a spreadsheet and every total that depends on it updates by itself. You never press “recalculate”, and you never ask “has anything changed?”. The spreadsheet program VisiCalc could already do that in 1979. Most databases still can't. They sit there like a box on a shelf: to find out whether something changed, you have to keep opening the box. That's called polling.

Kofi's kite shop prices kites in euros. Aroha pays in dollars, so every sale needs today's exchange rate. One way: during every sale, the sales code phones the rate service and waits. The other way: the sales code subscribes to rate changes ahead of time and keeps the latest rate in a little table of its own. At sale time it just glances down at its own desk.

The second way is faster, and it keeps working when the rate service is having a bad day. As the book puts it: the fastest and most reliable network request is no network request at all.

Try it: sell a few kites and change the rate. Then click the rate service to crash it and sell again — in both modes.

What the book says

Application code as a derivation function: a secondary index picks out and sorts field values; a full-text index applies language detection, word segmentation, stemming or lemmatization, spelling correction and synonym identification before building an inverted index; an ML model is derived from training data; a cache holds an aggregation in the shape the UI needs. When the function isn't cookie-cutter, custom code is required — and that is where databases struggle: triggers, stored procedures and user-defined functions have been somewhat of an afterthought.

Separating code from state: databases fit poorly with dependency and package management, version control, rolling upgrades, monitoring and calls to network services, whereas tools like Kubernetes, Docker, Mesos and YARN are built to run application code. Hence stateless services with state kept in a database — “we believe in the separation of Church and state,” as functional programmers joke. The database then acts like a mutable shared variable over the network, and as in most programming languages you cannot subscribe to a mutable variable, only read it periodically (or write your own observer pattern). Subscribing to changes is only just beginning to emerge as a database feature.

Dataflow renegotiates that relationship: application code responds to state changes in one place by triggering state changes in another — as in CDC, the actor model, triggers and incremental view maintenance. It needs stable message ordering and fault-tolerant processing (one lost message leaves derived data permanently out of sync); those demands are stringent but much less expensive and more robust than distributed transactions. Stream operators compose like Unix tools chained by pipes.

Stream processors and services: the exchange-rate example replaces a synchronous request to another service with a query to a local database — a stream join between purchase events and rate-update events instead of an RPC. The join is time-dependent: if purchases are reprocessed later, the rate will have changed, so to reconstruct the original output you need the historical rate at the time of purchase. Many open questions remain, but the book calls this a promising direction.

Big idea 6 · observing derived state

Where the write path meets the read path

Every piece of data makes a journey, from the moment someone writes it to the moment someone else looks at it. Part of that journey can be done early — as soon as the data arrives, whether or not anybody ever asks. That's the write path. The rest is done late, only when somebody asks. That's the read path.

A library with no catalog does nothing when a note arrives — and then walks past every shelf for every question. A library with a word index does some filing per note and answers in a moment. A library that also pins the answers to its favorite questions on the wall does even more filing, and those answers cost nothing at all. Indexes, caches and materialized views all do one job: they move the boundary between the two paths.

Push the boundary all the way and the write path ends on your screen. The server sends each change to your phone as it happens, and there is nothing left to ask for. A phone that was offline simply picks the stream up where it left off.

Try it: drag the boundary, then add notes and run both searches. Watch which bar grows — and what happens to a search with no index as the library fills up.

What the book says

The write path is the precomputed part of the journey — done eagerly, like eager evaluation. The read path happens only when someone asks — like lazy evaluation. The derived dataset is where they meet (Figure 13-1 shows document updates meeting queries in a search index). With no index, a search must scan every document like grep; precomputing results for all possible queries is impossible because the set is infinite, or at least exponential in the number of terms; a cache of common queries — really a materialized view — sits in between. It is the same trade-off as the home-timeline case study from the start of the book, where the boundary was drawn differently for celebrities: “after 500 pages, we have come full circle!”

Stateful, offline-capable clients: on-device state is a cache of server state; the pixels on screen are a materialized view of model objects, which are a local replica of state in a datacenter. A normal web page is a stale cache until you reload (RSS is just polling); server-sent events (the EventSource API) and WebSockets let the server push. Pushing state changes to devices means extending the write path all the way to the end user; a device that was offline catches up the way a log consumer does, using its offset. Tools like React and Elm already re-render from state changes; end-to-end propagation could take under a second. Instant messaging and online games already work this way — but request/response is deeply ingrained, and few datastores let you subscribe to changes.

Reads are events too: read requests can themselves be sent through the stream processor, making a read a stream-table join; a one-off read passes through and is forgotten, while a subscription is a persistent join. Logging reads also records what a user saw before deciding (say, a predicted shipping date), which helps trace causal dependencies and provenance — at extra storage and I/O cost.

Multishard data processing: the same machinery can run queries that combine several shards — Storm's distributed RPC has been used to count the people who have seen a URL (the union of many follower sets), and fraud prevention joins reputation scores sharded by IP, email, billing and shipping address. If you need this, a database that offers multishard joins is probably simpler; streams are an option when you run into the limits of off-the-shelf solutions.

Big idea 7 · the end-to-end argument

Charged twice, and nobody did anything wrong

Ravi is on a bus, sending Aunt Mele $11. He taps Pay just as the bus dives into a tunnel. The request got out. The bank moved the money. But the answer never makes it back. His phone shrugs: “Something went wrong. Try again?” Ravi wants his aunt to get her money, so he taps again.

Now $22 has moved. And look how well every part behaved! The network's TCP layer throws away duplicate packets — but only inside one connection, and the retry was a new one. The database ran each transfer as a perfect all-or-nothing transaction — twice. Every layer guarded its own little stretch of road. Nobody guarded the whole trip.

The cure has to start where the trip starts. Ravi's phone invents a unique request ID and sends it with the payment; a retry carries the same ID. The database refuses to record one ID twice. Now trying again is harmless — the operation has become idempotent.

Try it: with a weak signal, tap Pay and then Retry a few times. Compare “meant to send” with “actually sent”. Then switch on the request ID and do it again.

What the book says

Using a data system with strong safety properties, even serializable transactions, does not guarantee freedom from data loss or corruption: a bug that writes bad data isn't stopped by them (an argument for immutable, append-only data). Exactly-once (or effectively-once) means arranging things so the final effect is the same as if no faults had occurred, even if an operation was retried. Making an operation idempotent is one of the most effective ways, but may need extra metadata (the set of operation IDs that updated a value) and fencing on failover.

TCP's duplicate suppression works only within one connection. If a client times out after sending COMMIT, reconnects and retries the book's Example 13-1 (balance + 11.00 / balance - 11.00), $22 moves instead of $11 — “real banks do not work like this.” 2PC doesn't settle it either, and there is still the hop from the end user's device: an HTTP POST on a weak cellular connection, a browser asking “Are you sure you want to submit this form again?” (the Post/Redirect/Get pattern doesn't help when the POST times out).

Example 13-2 adds a unique request ID — a UUID in a hidden form field, or a hash of the form fields — inserted into a requests table with a UNIQUE constraint in the same transaction. A repeat fails the INSERT and aborts. Relational databases generally maintain uniqueness correctly even at weak isolation levels. The requests table also acts as an event log from which the balance updates could be derived downstream.

This is the end-to-end argument of Saltzer, Reed and Clark (1984): a function can be completely and correctly implemented only with the knowledge and help of the application at the endpoints. It also applies to integrity (Ethernet, TCP and TLS checksums miss software bugs and disk corruption — you need end-to-end checksums) and to encryption (WiFi passwords and TLS don't protect against a compromised server). The low-level features remain useful: they make higher-level problems rarer. The book regrets that we have not yet found the right abstraction to take this burden off application code.

Big idea 8 · enforcing constraints

Whoever is first in the log wins

Some rules must never bend: two people can't own the same username, and an account can't spend money it doesn't have. When two requests clash, somebody has to decide which one came first. That is consensus, and the usual way to get it is to send every clashing request through one place.

A log can be that place. Each request for a name becomes a message, appended to the log shard picked by the name's hash — so rivals for @comet always land in the same shard. One single-threaded processor reads that shard from top to bottom, keeping a little table of taken names. First request: “it's yours.” Second: “sorry, taken.” Need more speed? Add shards; each one works alone.

A payment touches three accounts that may live in three different shards. Instead of one giant transaction, send it through in stages. The request lands in the payer's shard. The payer's processor checks the balance and sends out “money leaving”, “money arriving” and “fee” events, all stamped with the request's ID. If a processor crashes and redoes its work, the repeats carry the same ID — and get ignored.

Try it: race for @comet a few times. Then switch to the payment: keep paying until the money runs out, and arm a crash to watch duplicates being ignored.

What the book says

Uniqueness constraints (usernames, email addresses, file names, a seat on a flight) and their cousins (a balance that never goes negative, not overselling stock, no overlapping room bookings) require consensus in a distributed setting. The common way is a single leader; algorithms like Raft safely elect a new one if it fails. Checking scales out by sharding on the value that must be unique — by request ID, or by hash of username. Asynchronous multi-leader replication is ruled out, and if violating writes must be rejected immediately, synchronous coordination is unavoidable.

Uniqueness in log-based messaging: (1) every request is appended to a shard determined by the hash of the username; (2) a stream processor reads the shard sequentially on a single thread, tracks taken names in a local database, and emits a success or rejection message to an output stream; (3) the client watches the output stream for its result. It is the same construction as consensus from a shared log, and it scales by adding shards. The principle: any writes that may conflict are routed to the same shard and processed sequentially, with arbitrary validation logic.

Multishard request processing (Figure 13-2): the client gives the transfer a unique request ID and appends it to the log shard of the source account. That shard's processor — whose local database is entirely derived from the log — checks funds, reserves the amount, and emits an outgoing-payment event to its own shard plus incoming-payment events to the destination and fees shards, all carrying the request ID. When the outgoing event comes back round, it executes the payment. Every processor deduplicates by request ID. A traditional database would need an atomic commit across all three shards.

The only requirements are that events for an account are processed strictly in log order with at-least-once semantics and that processors are deterministic: after a crash the same request yields the same decision and the same output events, and downstream consumers ignore the duplicates. Atomicity comes not from a transaction but from the single atomic append of the request event. A user who wants the outcome subscribes to the source shard and waits for the outgoing-payment or “declined payment” event.

Big idea 9 · timeliness and integrity

Late can be fixed. Wrong is forever.

The word “consistency” hides two different promises. Timeliness means you see things up to date. This morning's ice cream isn't on your bank statement yet? Annoying — but wait a while and it shows up. Integrity means nothing is lost, doubled or contradictory. If the numbers on the statement don't add up, or money left your account and never reached the shop, waiting fixes nothing. Somebody has to find it and repair it.

Log-based systems pull these two apart. They are often a little late — but with ordered logs, request IDs and repeatable processing they can keep integrity rock solid, with no giant transactions at all.

And many real-world rules are softer than they look. A shop that sells one kite too many orders more stock and says sorry with a discount — it needs that routine anyway, for the day a forklift runs over a box. Airlines overbook on purpose. If saying sorry is cheap enough, you can sell first and check afterwards — and then your tills never have to wait for each other.

Try it: cut the link and keep selling from both tills — in both modes. Which kind of “sorry” do you end up saying?

What the book says

Timeliness means users observe the system in an up-to-date state; a stale read is an inconsistency that resolves itself by waiting and retrying. (CAP uses “consistency” to mean linearizability, a strong form of timeliness; read-after-write consistency is a weaker one.) Integrity means absence of corruption: no data loss, no contradictory or false data, derived data that correctly reflects its source. If integrity is violated the inconsistency is permanent until explicitly checked and repaired. In slogan form: violations of timeliness are “eventual consistency”, violations of integrity are “perpetual inconsistency”. A card payment missing from a statement for 24 hours is normal; a statement whose sums are wrong would be catastrophic.

ACID transactions usually give both, so the distinction rarely comes up. Event-based dataflow systems decouple them: no timeliness unless you build consumers that wait, but integrity is central. It was achieved by: representing the write as a single message written atomically; deriving all other updates with deterministic functions; passing a client-generated request ID through every level; and keeping messages immutable so derived data can be reprocessed to recover from bugs.

Loosely interpreted constraints: oversold stock (order more, apologize, offer a discount — the same routine as when a forklift runs over items), deliberately overbooked flights and hotels with compensation processes, overdraft fees bounded by daily withdrawal limits, and settlement between banks. A change that corrects a mistake is a compensating transaction. Whether the cost of the apology is acceptable is a business decision; if it is, you may write optimistically and check the constraint afterwards — validating only before actions that would be expensive to recover from. These applications still need integrity; they just don't need timeliness in enforcing the constraint.

Hence coordination-avoiding data systems: dataflow systems can keep integrity without atomic commit, linearizability or synchronous cross-shard coordination — for example running multi-leader across datacenters with asynchronous replication, each able to continue independently. Serializable transactions remain useful at small scope, and coordination can be added just where recovery is impossible. Coordination reduces the number of apologies for inconsistencies but can increase the number of apologies for outages; you cannot reach zero, only find the sweet spot.

Big idea 10 · trust, but verify

Don't just trust it — check it

We design systems by assuming that some things go wrong (crashes, lost messages) and that other things never do (the disk keeps what we saved; the chip multiplies correctly). But “never” really means “hardly ever” — and if you run enough machines for long enough, hardly-ever things happen. Software has bugs too. Even famous, battle-tested databases have shipped bugs that broke their own rules.

So don't only hope. Audit: go back and check that the data is still right. Big storage systems keep re-reading their own files and comparing the copies. And practice restoring your backups before the day you need them.

Event logs make checking easier. Every view was built from the log by repeatable code, so you can rebuild it and compare. The log itself can be fingerprinted with hashes. Stack the fingerprints into a tree — a Merkle tree — and one small fingerprint at the top stands for the whole log. Change any old record and the top no longer matches.

Try it: click any record to secretly change it, or let a bug spoil the balance. Notice that nothing complains. Then run the audit.

What the book says

A system model takes a binary view of faults — these can happen, those can't — but reality is a matter of probabilities. Data can be corrupted in memory, on disk and on the network, and at large enough scale even very unlikely things do happen. Software bugs slip past every lower-level checksum: past versions of MySQL failed to maintain uniqueness constraints correctly, and PostgreSQL's serializable isolation has exhibited write skew anomalies — in robust, well-regarded databases. Application code gets far less review, and many applications don't even correctly use features like foreign-key or uniqueness constraints. ACID “consistency” only means something if transactions are free from bugs.

Checking the integrity of data is called auditing. Large-scale storage systems such as HDFS and Amazon S3 do not fully trust disks: background processes continually read files back, compare them with other replicas, and move files between disks to mitigate silent corruption. “If you want to be sure that your data is still there, you have to read it and check” — and try restoring from your backups from time to time. The book expects more self-validating or self-auditing systems in future.

Designing for auditability: a transaction that mutates several objects doesn't record why. With event sourcing, user input is one immutable event and state updates are derived deterministically, so you can check the log with hashes, re-run (or run a redundant copy of) the derivation and compare, and even get time-travel debugging. Integrity checks are best done end to end: the more of the pipeline a check covers, the fewer places corruption can hide — and, like automated tests, continuous auditing lets you change things with confidence and move faster.

Tools: audit tables, or periodically signing the transaction log with a hardware security module (which still doesn't prove the right transactions went in). Blockchains such as Bitcoin and Ethereum are shared append-only logs with cryptographic consistency checks, and smart contracts are basically stream processors; they are Byzantine fault-tolerant, but have too high an overhead for most applications. Lighter-weight: Merkle trees, trees of hashes that can efficiently prove a record appears in a dataset, and certificate transparency, which uses cryptographically verified append-only logs and Merkle trees to check TLS/SSL certificates, with a single leader per log instead of a consensus protocol.

The seesaws from this chapter

The chapter argues for one side more than most — but each side still has its price.

One integrated product

Fewer moving parts and predictable performance — if it truly does everything you need

vs

Specialized tools, composed

Good at a much wider range of jobs, but every extra piece must be learned and run

Distributed transactions

Read your own writes at once — but one failed participant stops everybody

vs

Log-based derived data

Faults stay local and consumers catch up — but reads may lag behind

One total order

Every view replays the same sequence, so they can't disagree

vs

Shards, regions, services

Scales past one leader, but cause-and-effect between events can get lost

Sudden switch-over

One big migration day, and no way back if it goes wrong

vs

Old and new side by side

Reprocess, shift users gradually, reverse any step — at the cost of running both

Ask a service each time

Simple request and response; slow, and stuck when the other service is down

vs

Subscribe to its changes

A local copy that is fast and survives the other service's bad days — fed by a stream that must be ordered and reliable

Work on the write path

Indexes, caches and pushed updates: reads are nearly free, writes cost more

vs

Work on the read path

Writes are cheap, but every question pays — more and more as data grows

Check first (coordinate)

Few apologies for broken rules; more apologies for slowness and outages

vs

Act now, apologize later

Fast and always open; needs integrity plus a compensation routine

Blind trust

No checking cost — and you discover corruption when it is too late

vs

Continuous auditing

Some overhead, but problems surface early and you dare to change things

Words to know

Grown-up words, in plain language.

data integration
Getting the same data into all the right places, in the right shape for each tool.
system of record
The one place where a fact is written first. Everything else is a copy made from it.
derived data
Data you could throw away and rebuild from something else — an index, a cache, a view.
change data capture (CDC)
Watching every change a database makes and passing it on, in order, to other systems.
total order
One agreed sequence in which every event comes before or after every other.
causal dependency
“This only makes sense after that.” Lose the link and effects can overtake their causes.
deterministic
Same input, same output, every time — so redoing work gives the same result.
idempotent
Doing it twice has the same effect as doing it once.
reprocessing
Running old data through new code to build a new view of it.
kappa architecture
One system that both replays old events and handles new ones as they arrive.
federated database
One query window over many different stores. It unifies reads.
unbundled database
Separate tools, joined by a log, doing the jobs a database does inside. It unifies writes.
loose coupling
Parts that can be slow, broken or rebuilt without dragging the others down.
dataflow
Code that reacts to a change in one place by making a change in another, like spreadsheet cells.
polling
Asking “anything new?” over and over, because nobody will tell you.
materialized view
A ready-made answer that is kept up to date as the data changes.
write path
The work done early, as soon as data arrives, whether or not anyone asks.
read path
The work done late, only when someone asks a question.
end-to-end argument
Some jobs can only be done properly by the two ends of a journey, not by the pipes between.
request ID
A unique label made where a request starts, so every retry can be recognized as the same one.
exactly-once
The end result looks as if nothing ever failed, even though some work was redone.
timeliness
Seeing things up to date. If it's broken, waiting fixes it.
integrity
Nothing lost, doubled or contradictory. If it's broken, only checking and repair fix it.
compensating transaction
A second change that makes up for a mistake: a refund, a correction, an apology.
auditing
Going back and checking that the data is still correct, rather than assuming it.
Merkle tree
A tree of fingerprints where one top fingerprint stands for every record beneath it.
